# Shared Make rules

The files under `mk/` are the GNU Make fragments, and one shell fragment, that the in-house builds share: which architecture a build is for, which cross compiler builds it, where its products go, how a header edit or a flag change reaches the objects, and the rules of the products that are not RAM images. Each Makefile includes the fragments it needs, so a setting is decided in one place for the kernel, the guest programs, the host tools and the vendored ports alike. The vendored projects keep their own build systems, driven by their `build_*.sh` scripts, and take only the architecture from here.

## Interfaces

The fragments a component Makefile includes:

* `arch.mk` sets `ARCH`, `i686` unless `make ARCH=x86_64` names the other, and stops the build on any third value. From it come `ARCH_SUFFIX`, empty for i686 and `/x86_64` for x86-64; `ARCH_BUILD`, the build tree, `build` or `build/x86_64`; `ARCH_BUILDS`, both trees, for a rule that spans them, as the recovery key's does; `ARCH_VENDOR`, where a vendored port's extracted tree, its stamp and musl's install go, `vendor` or `build/x86_64/vendor-work`; `ARCH_MUSL`, musl's install directory under it; `CROSS_PREFIX`, `i686-elf-` or `x86_64-elf-`; `ARCH_CFLAGS`, `-m32` or `-m64`; `ARCH_LDFLAGS`, empty for i686 and `-Wl,-z,max-page-size=0x1000` for x86-64, so that a guest program's segments are aligned to 4 KiB pages rather than the linker's default of 2 MiB; `ARCH_USER_TEXT`, the address the freestanding programs link their text at, `0x08048000` or `0x400000`, which is where TinyCC links a program on that architecture; and `ARCH_QEMU`, `qemu-system-i386` or `qemu-system-x86_64`. The root Makefile and `toolchain.mk` include it.
* `toolchain.mk` includes `arch.mk` and sets `CROSS_CC` to the architecture's compiler: a `CROSS_CC` given by the caller, else a `CC` given on the command line, else `i686-elf-gcc` or `x86_64-elf-gcc` found on the path. An environment `CC` is not taken, since it is usually a host compiler. `CROSS_LD`, `CROSS_AR`, `CROSS_STRIP` and `CROSS_OBJCOPY` are derived from the compiler's name by replacing its final `gcc`, and each may be given instead. With no compiler found, every goal except `clean` stops with a message that names the missing compiler.
* `build.mk` sets `TOP` to `..`, `COMPONENT` to the directory's name, `BUILDROOT` to `$(TOP)/build$(ARCH_SUFFIX)` and `BUILD` to `$(BUILDROOT)/$(COMPONENT)`, each unless the Makefile set it first. A host component includes no toolchain, so `ARCH_SUFFIX` is empty for it and it builds into `build/` for either architecture.
* `deps.mk` sets `DEPFLAGS` to `-MMD -MP`: the compiler writes a `.d` file of the headers an object included, and an empty rule for each header, so a header removed since the last build does not stop make.
* `rules.mk` is the compile-then-link case: a `$(BUILD)/%.o` rule from `%.c` and an include of the `.d` files of `$(OBJECTS)`. `ish/` uses it.
* `fingerprint.mk` records the component's configuration in `$(BUILD)/.config` (see Design). A Makefile sets `CONFIG_TEXT` to its resolved flags, makes its objects and programs depend on `$(CONFIG)`, and may narrow `CONFIG_PURGE`, which is `$(BUILD)` by default.
* `warnings.mk` sets `KWARN`, the kernel's warning flags, all under `-Werror`: `-Wpedantic` for the C89 dialect that GCC and TinyCC share, and `-Wframe-larger-than=4096`, a quarter of the 16 KiB kernel stack, among them. Its comment lists the flags that were weighed and rejected, with the reason.

The fragments the root Makefile includes:

* `dryrun.mk` sets `DRY_RUN` non-empty when this make is a dry run, for the vendor stamps' recipes, which are marked `+` so that they run under `-n` and print what they would build. It reads the short flags in the first word of `MAKEFLAGS` only when that word is not a long option, so that `--no-print-directory`, which `tests/run` passes, is not read as `-n`, and it also matches `-n` and the long forms as whole words, as GNU Make 3.81 writes them.
* `host.mk` is the rule text every host program is compiled with: `HOSTCC`, `cc` unless set; `HOSTCFLAGS`, `-O2 -Wall -Wextra -Werror`; and `HOST_LINK`, which compiles and links the rule's C prerequisites into its target. The checkers under `tools/`, the runners and fixture makers under `tests/` and the image tools are built through it, so a flag added there reaches every program that decides a verdict.
* `images.mk` has the rules of the products that are not RAM images. It builds the six host tools the disk and stick scripts run, `MKMBR`, `MKGPT`, `FATCHAINS`, `GRUBEMBED`, `STICKCHECK` and `MKEXFATFIXTURE`, whose names the root Makefile defines before it includes this file; the metal ISO and the recovery ISO; the stick image (`make rach2-stick-image`); and the install stick (`make rach2-install-stick`), whose volume has the sealed disk, its manifest and the root update image with 256 MiB for metadata and saved sectors, and whose rule depends on this file, so a change of layout rebuilds the stick. The tools that build them are described in [the tools Readme](../tools/Readme.md). The root Makefile includes it before the suites' fragment, and `tools/verify/check.sh` refuses a rule under `tests/` that makes a product.
* `gnu.mk` builds the GNU layer ([its Readme](../vendor/gnu/Readme.md)) on a Linux host; none of it is part of `all`. `make gnu-toolchain` runs `vendor/gnu/build_toolchain.sh` for the cross toolchain of the architecture, `i686-linux-gnu` or `x86_64-rach2-linux-gnu`, under `build/vendor/gnu/` or `build/x86_64/vendor/gnu/`. Its stamp depends on the script, `vendor/gnu/arch.sh`, `fetch.sh` and `toolchain.pins`, a copy of the toolchain's own lines of `sources.txt` that is rewritten only when they change, so that pinning a port does not rebuild the compilers. `make gnu-ports` runs `vendor/gnu/build_port.sh --all`, which builds every recipe into an empty `root/` there, again whenever the toolchain, the script, a recipe, `fetch.sh`, `sources.txt` or `GNU_LINK` changes; `GNU_LINK=static` asks for static links, and `ports.link` records the choice.
* `gnu-extra.mk` has the GNU layer's programs that have build scripts of their own, each run from nothing behind a stamp under the same directory, again whenever its script or a list of sources it reads changes: `make gnu-native` (`vendor/gnu/native/build_native.sh`, GCC and binutils to run on Rach2), `make gnu-gdb` (`build_gdb.sh` beside it, GDB and gdbserver), `make gnu-js` (`vendor/gnu/spidermonkey/build_js.sh`, the SpiderMonkey shell) and `make gnu-chromium` (`vendor/gnu/chromium/fetch_chromium.sh`, Debian's chromium-headless-shell and its libraries). The three that compile are rebuilt when the cross toolchain is; the fourth only needs the toolchain to exist.
* `gnu-image.mk` has `make os-real-gnu-ext2`, the GNU system's root: `tools/image/mkext2.sh --overlay vendor/gnu/install_root.sh` over `krffs/manifests/os-real-gnu.manifest`, a 4096 MiB ext2 volume at `build/images/os-real-gnu.ext2`, or under `build/x86_64/images/`. It is built again when the manifest's inputs, the overlay, `fetch.sh`, `sources-extra.txt` or any of the five stamps above changes. It also has `make machine`, which runs `tests/run style` and then builds what an installed machine is given: the kernel, the recovery kernel, the recovery image with this tree's key, minted by a make of its own because make chooses the image's name when it starts, and the GNU root. The root Makefile includes the three GNU fragments in this order, after `images.mk` and before `tests/system/suites.mk`, whose `run-gnu` boots the root.

The shell fragment:

* `arch.sh` is `arch.mk` for the shell. The vendored ports' `build_*.sh` scripts, `vendor/musl/muslgcc`, the image scripts and the fault scripts under `tests/` source it with `RACH2_ARCH` set, which the root Makefile sets from `ARCH`, and it sets `CROSS`, `MFLAG`, `MUSL_TARGET`, `HOST_TRIPLE`, `ARCH_SUFFIX`, `ARCH_LDFLAGS`, `ARCH_QEMU`, `ARCH_USER_TEXT`, `ARCH_VENDOR`, `MUSL_PREFIX`, `ARCH_BUILD` and, for x86-64 when the caller has none, `RACH2_PATH_MAP`. It removes `ARCH`, and an `ARCH=` that make passed down in `MAKEFLAGS`, from the environment, since musl, BusyBox and TinyCC each have a make variable of that name with other values. The caller sets `REPO` to the repository's root.

## Design

### Output directories

An in-house build writes its objects, `.d` files and programs under the repository's ignored `build/`, in a tree that follows the source: the kernel is `build/rach2/kernel` beside `build/rach2/sys/...`, the utilities are under `build/utils/`, the KRFFS host tools under `build/krffs/`, and Doom under `build/ports/doom/`. The root Makefile puts the images under `build/images/` and stages what the images take from BusyBox, Dropbear, TinyCC, pdpmake and e2fsprogs under `build/vendor/`.

An x86-64 build has the same layout under `build/x86_64/`: `build/x86_64/rach2/kernel`, `build/x86_64/utils/`, `build/x86_64/images/`, `build/x86_64/vendor/`, and the vendored ports' extracted trees, stamps and musl's install under `build/x86_64/vendor-work/`. For i686 the ports extract their trees under `vendor/` and musl installs to `vendor/musl/install/`. The host tools under `build/tools/` and `build/krffs/` and the rendered manual under `build/man/` serve both architectures. The manifests name their host files by the i686 paths; for x86-64 the root Makefile exports `RACH2_PATH_MAP`, through which the stager, `krffs/manifest_deps.sh` and the set-id guard read `build/...` from `build/x86_64/...` and musl's install from the x86-64 one.

`BUILD` is relative to the component's directory, so `make -C utils` and the root Makefile's sub-make resolve `../build/utils` to the same place, and a repository path with a space in it never enters a target name, which make would split.

`make clean` runs each sub-make's `clean` and removes the architecture's images, and leaves the host tools under `build/tools/`, the manual under `build/man/`, the staged files under `build/vendor/` and the vendored ports' trees and stamps. `make distclean` removes those as well, and all of `build/`.

### Header dependencies

A compile with `$(DEPFLAGS)` writes a `.d` file beside its object, and the Makefile includes the `.d` files, so a header edit rebuilds the objects that include it and nothing else; `make clean` is never needed after one. The kernel, ISH, the KRFFS tools and Doom compile to objects and include their `.d` files the ordinary way. `tests/` and `utils/` compile and link most programs in one command, so their rules give `-MF` to put each program's `.d` file under `$(BUILD)`.

### The configuration fingerprint

`$(BUILD)/.config` has the compiler's path, its `ls -lnL` line (size and date, a symbolic link followed) and `CONFIG_TEXT`. Its recipe runs at every make, since the file depends on a phony target, and rewrites the file only when the text differs. When it differs, or when there is no file but `$(BUILD)` already has something in it, the recipe first removes `CONFIG_PURGE` and prints `COMPONENT: configuration changed: rebuilding from nothing` or `COMPONENT: no recorded configuration: rebuilding from nothing`. Objects and programs depend on the file, so a changed flag or a reinstalled compiler rebuilds the component, and one tree never mixes objects of two configurations. The removal comes before make judges the objects by their dates, so `make -j` finds no object vanishing under it, and an object written in the same second as the file, which make 3.81's whole-second times would call current, is gone. Under `make -n` the recipe does not run and removes nothing. The kernel, the guest test programs, ISH and the KRFFS tools include it.

## Tests

`tests/run style` runs `tests/system/dryrun_test.sh`, which runs a recipe of the vendor stamps' form over the real `dryrun.mk` with no flags, `--no-print-directory`, `-n`, `--dry-run` and `-n` beside `--no-print-directory`, and `tests/system/build_rules_test.sh`, which checks that `make clean` succeeds with no cross compiler and keeps what it should, and reads the root Makefile's rules, `images.mk`'s among them, from `make -pn` in a private tree. It also runs `tests/system/build_inputs_test.sh`, which relinks programs and a kernel after a changed library, startup object or linker script. Both scripts named first have a `--mutate` mode.

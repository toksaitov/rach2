# Build and verification tools

The programs and scripts under `tools/` prepare a machine to build Rach2 and check what the build makes. `setup/` checks a host for the tools the build and the suites need; `verify/` supplies the source checks whose prepared evidence the style cases verify; `inspect/` judges built kernels, programs and images; `image/` makes the ext2 roots, GRUB disks, sticks and ISOs; `etude/` is the native C collection runner, whose preparation and execution interfaces [its Readme](etude/Readme.md) describes; `ci/` is what the GitHub workflows run; `flow/` runs the worker and manager loops; `dev/` reaches the testing host and installed machines and builds the compilation database; `font/` makes the console's font; and `git-hooks/` has the git hooks that check commit messages and the style of what is committed and pushed. The root Makefile runs most of them with the arguments they need, so a person seldom calls one directly. The suites, their runner and their checkers are under [`tests/system/`](../tests/system/Readme.md).

## Use

On an enrolled testing endpoint, builds, worker checks, owner commands, CI and bisection use the [installed launch policy](etude/Readme.md#installed-launch-admission). The policy supplies one shared ledger and capacity before each build or test step; old checkouts use its installed external launcher.

### Setting up a machine

Preparing artifacts needs GNU Make, a host C compiler, the cross toolchain of its architecture (`i686-elf` for `make`, `x86_64-elf` for `make ARCH=x86_64`), e2fsprogs 1.43 or later, mandoc, `ssh-keygen`, awk, sed, tar, gzip, bzip2 and patch. Source-check preparation adds cppcheck, ShellCheck, Clang, clang-format and Python. `make host-source-tools` builds pinned native pmccabe and mandoc with the [source-judge recipes](setup/source-tools.md); the user-pointer check uses Clang and needs no Sparse installation. Image preparation may also need mtools, `qemu-img`, xorriso and OVMF. The platform package lists below are for this preparation environment. The default `make` downloads nothing; GNU preparation fetches its tarballs with curl or wget ([fetch.sh](../vendor/gnu/fetch.sh)).

A prepared desktop collection runs through `etude run` on Linux, macOS or Windows with compiled helpers and QEMU for cases that boot machines. It needs the preparation record, its immutable artifacts and the firmware their profiles declare. Execution starts no build and invokes no host shell, Python, Perl, OpenSSH, mtools, e2fsprogs or Linux tooling machine. [Native collection execution](etude/Readme.md#native-collection-execution) gives the commands. `tests/run` remains the compatibility shell entry used by existing build and CI scripts; its registry tool checks and implicit preparation belong to that path.

[prereqs](setup/prereqs) lists, for Ubuntu, macOS, Windows and Rach2, every tool the build and the suites need there and the commands that install each one. `sh tools/setup/prereq.sh` probes the machine it runs on for them and prints the commands that install the missing ones, under who runs them: this account, an administrator, or a person at the machine, for a step that needs the screen, a new login or a restart. With `--install` it runs those the account has the rights for and probes again. [`etude provision machine`](etude/provision_machine.sh) runs it on each machine that it makes ready for etude.

#### macOS

Xcode's command line tools supply `make`, `cc`, clang and python3, and Homebrew the rest. Run the `shellenv` line the Homebrew installer prints, since it does not put `brew` on the path.

    xcode-select --install
    /bin/bash -c "$(curl -fsSL \
        https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
    eval "$(/opt/homebrew/bin/brew shellenv)"
    brew install i686-elf-gcc i686-elf-binutils x86_64-elf-gcc x86_64-elf-binutils \
                 qemu mtools e2fsprogs mandoc cppcheck shellcheck clang-format \
                 xorriso rsync

The build finds e2fsprogs in its keg, which Homebrew never links, and the suites find OVMF in QEMU's `share/qemu`. rsync 3 is for [testing.sh](dev/testing.sh). `pkg-config` and the `fuse-t` cask serve `make -C krffs mount`, which no build or suite needs.

#### Debian and Ubuntu

    sudo apt install build-essential curl qemu-system-x86 qemu-utils ovmf mtools \
                     e2fsprogs mandoc openssh-client netcat-openbsd python3 xorriso \
                     cppcheck shellcheck clang clang-format

`pkg-config` and `libfuse-dev` serve `make -C krffs mount`. No package provides an `i686-elf` or `x86_64-elf` toolchain, but the archive's `i686-linux-gnu` and `x86_64-linux-gnu` cross compilers build this tree, since the kernel and guest programs are freestanding and the ports link against their libgcc. [elfwrap.sh](setup/elfwrap.sh) links their tools under the names the tree calls and wraps their compilers, in `$HOME/bin`, which a new login puts on the path:

    sudo apt install gcc-i686-linux-gnu binutils-i686-linux-gnu \
                     gcc-x86-64-linux-gnu binutils-x86-64-linux-gnu
    sh tools/setup/elfwrap.sh i686 "$HOME/bin"
    sh tools/setup/elfwrap.sh x86_64 "$HOME/bin"

The compiler is wrapped, not linked. A GCC that targets Linux defines `__linux__`, builds position-independent code, and adds the stack protector, control-flow protection, stack-clash probes, unwind tables and `_FORTIFY_SOURCE`; the ports and guest programs are written for a bare `i686-elf-gcc`, and a static `tcc` built position-independent faults at address 0x1c. The wrapper turns those defaults off ahead of the caller's own flags. It also records the checksums of the Linux compiler's driver and `cc1`. Running the script again keeps a wrapper whose bytes would not change, and a new wrapper takes the date of the compiler, not of its writing, so the build's configuration fingerprint, which reads the wrapper's size and date, rebuilds nothing until the compiler itself changes. The x86-64 compiler with `-m32` cannot stand in for the i686 one, since it has no 32-bit libgcc. The archive's GCC 15.2 and binutils 2.46, on Ubuntu 26.04, are the oldest this tree supports.

#### Windows

Windows artifact preparation uses the supporting programs already on the machine: MSYS2's shell, make, Python and POSIX utilities, and UCRT64's MinGW-w64 compiler for native programs. Only QEMU may be installed. QEMU's Windows accelerator is WHPX, the Windows Hypervisor Platform; request `RACH2_QEMU_ACCEL=whpx` explicitly.

The [private WHPX build recipe](setup/qemu-whpx/Readme.md) supplies the scoped QEMU XSAVE-size correction and matching build libraries without a global package installation. Its source, patch and package digests are pinned; the produced emulators need the unchanged affected checks before use.

QEMU's GLib command relays also need `gspawn-win64-helper.exe` and `gspawn-win64-helper-console.exe` beside its DLLs. The prerequisite installer completes this QEMU runtime dependency from the pinned MSYS2 package only when its GLib DLL matches exactly. It verifies the package, DLL and both helper digests before copying absent helpers, refuses changed existing files and prints the actual copy receipt. It neither installs a second GLib nor changes QEMU's DLLs. PowerShell converts the native archive and extraction paths with MSYS2 cygpath before passing them to MSYS2 tar.

Artifact preparation builds guest programs and images in the local Linux tooling machine, with its cross toolchains, e2fsprogs, mandoc and image builders. Native scenarios, host controllers and services are compiled with the Windows compiler. Prepared execution runs Windows QEMU directly. Independent image checks use a declared Rach2 helper containing mtools and e2fsprogs; no runtime command is forwarded to the Linux tooling machine. [The etude Readme](etude/Readme.md#the-tooling-machine) describes the cache, transfers and accounting. `sh tools/setup/prereq.sh --platform windows` checks the existing supporting programs and prints an installation command only for QEMU. A missing supporting program needs the owner's decision.

#### Rach2

The local public entry is `etude run native` on the already booted Rach2 system. `make native-assets ARCH=x86_64` prepares its executable, inventory, guest responder and immutable fixtures before deployment. The collection starts `etude-guest` directly over pipes. Deployment may use the owner's SSH access; execution needs no controller shell or SSH client. TinyCC, GNU programs and scripts remain available as declared workloads when their behavior is tested. [The native inventory](../tests/native/Readme.md#local-collection) gives the payload and invocation.

#### The testing host

The suites, the sets and the analyses run on the testing host, a Windows machine with an AMD Ryzen 9 7950X3D, 32 threads and 200 GB of memory, running Ubuntu 26.04 under WSL2. The Windows user's `.wslconfig` gives WSL 128 GB (`memory=128GB`), sets `nestedVirtualization=true`, sets both idle timeouts to -1, and turns off WSLg with `guiApplications=false`, since nothing on the host runs a graphical program and WSLg's compositor, weston, crashed and restarted about every 50 seconds; the scheduled task `Rach2 WSL` starts WSL when Windows boots, with nobody logged in. The distribution's disk, a file that grows, is under `D:\WSL\Ubuntu-26.04`. When its drive fills, Linux turns its root read-only part way through a run, so before a run of any suite but `style` and `host`, `tests/run` reads the drive's free space and refuses a run below `RACH2_MIN_FREE_GIB` or without a valid reading ([tests/Readme.md](../tests/Readme.md)). Changes to `.wslconfig` take effect after WSL is shut down and started again. Restart it only when no worker, CI job or release uses the host. The host is set up as Debian and Ubuntu above. The optional analyser is:

    sudo apt install clang-tidy

`make host-source-tools` prepares the pinned native source judges.

WSL's `/etc/sysctl.d/60-rach2-compaction.conf` sets `vm.compaction_proactiveness = 20`, applied at once with `sudo sysctl --system` and at boot by systemd. Background compaction maintains contiguous free memory for the Hyper-V socket channels that `wsl.exe` opens. Without it, fragmented memory caused 512 KiB channel allocations to fail despite gigabytes free, and commands from Windows SSH failed with `Wsl/Service/WSAETIMEDOUT`. The setting uses some CPU in `kcompactd` while memory is fragmented.

The `codexapi`, `museapi` and agent cases run their pinned upstream clients in a prepared GNU Rach2 guest. C controllers check requests and responses against the compiled fake API, including TLS, streaming and error cases. Their private QEMU network provides fixture-only access. The clients and their interpreters are programs under test, not host orchestration dependencies. Preparation fetches and verifies the required packages; no host Codex, Muse, npm, network namespace or host OpenSSL command is needed for execution.

Each person has an account in WSL named after their GitHub login, with a clone of their own, and logs in by key as `ssh rach2`, an alias for port 2227 of `auca.space`, which Windows forwards to the ssh server in WSL; that server refuses passwords. The top of the account's `.bashrc`, which bash reads for a command sent over ssh too, sets `RACH2_QEMU_ACCEL=tcg`, `WSL_DISTRO_NAME` and the PowerShell directory on `PATH`, which `tests/run` needs to ask Windows for the free space. Two GitHub Actions runners, `rach2-ci-1` and `rach2-ci-2`, run as the user `ghrunner`, each with its own directory and checkout, and take the jobs labelled `rach2`; their `.env` and `.path` set the same accelerator and Windows access. Each runner's checkout also has the shareware Doom WAD at `ports/doom/doom1.wad`, which `sh ports/doom/fetch_wad.sh` verifies there; the `doom` suite and the Doom rows of `uefi` need it, Git does not track it, and it stays because every workflow checks out with `clean: false`. The owner's copy of the tree is `/home/testing/rach2`, and each of the owner's worker loops has one of its own beside it; they are reached as `ssh testing` through [testing.sh](dev/testing.sh).

The installed `/etc/rach2/etude-site` accounts for builds and tests from all seven test accounts in one ledger. Its launcher preserves each ordinary run's worker and guest memory limits and claims memory for its builds and selected suites; processors and disk are shared, not reserved. A large-memory or explicitly serial suite takes the host alone. The installed wrapper uses umask 0002 so accounts can replace shared claim and verdict files. An old checkout, or a build or test outside the entry points above, must run through `/usr/local/libexec/rach2/etude-launch build|legacy COMMAND...`, as [installed launch admission](etude/Readme.md#installed-launch-admission) specifies. This includes a component-only build and a direct compiler command on the testing host. On an enrolled Windows endpoint, `C:/ProgramData/rach2/etude-authority` names the protected policy in its `site` field. Read that policy before changing admission; MSYS2's `/etc/rach2/etude-site` may be a separate file. Pass the protected policy as `ETUDE_SITE` when using the installed launcher. Windows and WSL use separate shares only when the owner has authorized both; a comparison run still waits for its own window without WSL load. The private site and access records are under `/var/lib/rach2-etude/enrollment/`. Enrollment leaves the accelerator and the later machine comparison unchanged.

The copies on the host share three caches of the build. `/var/cache/rach2-store` is the store of step outputs ([etude's Readme](etude/Readme.md#the-step-store)), from which a copy's `make` takes each vendored project and each step of the GNU layer that another copy has built from the same inputs; `/var/cache/ccache` is ccache's cache, which `/etc/ccache.conf` configures and the steps that the store does not have compile through; and `/var/cache/rach2-downloads` has the pinned tarballs of the host tools, from which [build_host_tool.sh](setup/build_host_tool.sh) takes each one a copy lacks before it downloads it ([source-tools.md](setup/source-tools.md)). Each is a directory of root's in the group `users` with the set-group-ID bit, so that every account and `ghrunner` can read it and add to it:

    sudo install -d -m 2775 -g users /var/cache/rach2-store
    sudo install -d -m 2775 -g users /var/cache/rach2-downloads

A host without the store's directory, such as the Mac, builds every step in its own copy, one without ccache compiles as before, and one without the directory of downloads downloads each tarball into each copy.

Before stopping a CI runner for maintenance, check its accepted jobs as well as its processes. `gh api repos/toksaitov/rach2/actions/runners --jq '.runners[] | {name,status,busy}'` reports each runner's state. Wait for both runners to be online with `busy: false`, and for the active workflows to finish, before stopping their services. In each runner's `_diag/Runner_*.log`, `Running job:` starts a job that remains active until its completion is recorded. The listener can be waiting for its first job-renewal request before it starts `Runner.Worker`; a timeout there still leaves an accepted job. An offline runner with `busy: true` needs investigation before maintenance proceeds. After stopping the services, check GitHub and the listener logs again for a job accepted during the checks. If one was accepted, restore the services and resolve its result before restarting WSL. Verify that both runners are online after maintenance.

The accounts are in the `kvm` group, and the runner uses `/dev/kvm` when it can open it and refuses a device it cannot. Runs on this host ask for the emulator all the same: the KVM is nested under Hyper-V, and the ATA driver polls a port after every sector it writes, each poll exiting through two hypervisors, so a disk write is slower than under the emulator.

Both runners have `ACTIONS_RUNNER_ACTION_ARCHIVE_CACHE=/home/ghrunner/action-archives` in their `.env`. The runner copies a cached archive before trying the network; its download client otherwise stops after 100 seconds, which a slow transfer from `codeload.github.com` can exceed before checkout starts. The cache is shared, owned by `ghrunner`, and contains one tar archive per resolved action commit, as [the runner's implementation](https://github.com/actions/runner/blob/v2.338.0/src/Runner.Worker/ActionManager.cs) specifies. A missing entry still downloads normally.

When a workflow changes an action or its version tag moves, prepare its archive from an account with `gh` signed in. This prepares the three actions the workflows use; the download has fifteen minutes, and only a complete archive enters the cache:

```sh
set -eu
cache=$HOME/action-archives
part=
trap '[ -z "$part" ] || rm -f "$part"' EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
for action in actions/checkout@v5 actions/upload-artifact@v7 actions/download-artifact@v8; do
    repo=${action%@*}
    ref=${action#*@}
    sha=$(gh api "repos/$repo/commits/$ref" --jq .sha)
    dir=$cache/$(echo "$repo" | tr / _)
    mkdir -p "$dir"
    archive=$dir/$sha.tar.gz
    [ ! -f "$archive" ] || continue
    part=$archive.part
    curl -fsSL --connect-timeout 30 --max-time 900 --retry 3 \
        -o "$part" "https://codeload.github.com/$repo/tar.gz/$sha"
    tar -tzf "$part" > /dev/null
    mv "$part" "$archive"
    part=
done
```

Copy the cache to `/home/ghrunner/action-archives` on the testing host, preserving its directory names and making it readable by `ghrunner`. Set the variable in each runner's `.env` and restart its service when it has no job; later cache additions need no restart. The runner's `_diag/Worker_*.log` records `Found action archive` when it uses an entry. An action download failure has no test artifact: read it with `gh run view RUN --log-failed`.

The native disk-image tools use checked 64-bit byte positions on every host. On Windows, mkfixture must mark an image sparse before extending it for the authority or wide-offset cases; failure stops the write. Partition fields retain their format limits independently of the host integer widths.

### Checking a machine: `setup/`

* [preflight.sh](setup/preflight.sh) is the build's tool check, an order-only prerequisite of the root Makefile's build targets, so every `make` and `tests/run` runs it. It checks the build's tools and the cross toolchain of `RACH2_ARCH`, and caches the result in `build/.preflight` or `build/x86_64/.preflight`, so that a check with nothing changed runs none of the tools. A missing tool fails the build by name before the cross toolchain compiles anything. When `RACH2_MIN_FREE_GIB` is set above 0, it also refuses a build while `space.sh` finds fewer GiB free, read on every run; the loops, ci and `dev/testing.sh run` set it to 40. `--report` prints a line for each tool.
* [prereq.sh](setup/prereq.sh) checks a platform against [prereqs](setup/prereqs) and prints or runs the commands that install what is missing. A stanza of the recipe names one or more tools, a probe run for each, and the install lines, each marked `user`, `admin` or `manual` for who may run it; the head of the recipe gives the format. The account has administrator rights when it is root, when `sudo -n true` succeeds, or when its PowerShell on Windows runs elevated. `--list` prints the platform's section with the placeholders replaced, for a program that reads it, and probes nothing. It exits 1 when a tool is missing. The Linux and macOS OVMF probes require a readable regular code image, including when `RACH2_OVMF_CODE` supplies its path.
  On Windows, the QEMU checks use the directory of the x86-64 emulator on native PATH, or `Program Files/qemu` when it is absent from PATH. The three programs, firmware and matching GLib command helpers are checked in that directory. [The private WHPX build](setup/qemu-whpx/Readme.md) supplies the corrected XSAVE size and matching UCRT runtime.
* [elfwrap.sh](setup/elfwrap.sh) makes `i686-elf` or `x86_64-elf` tools from Debian's Linux cross toolchain of the same processor, as linked tools and a wrapped compiler.
* [build_host_tool.sh](setup/build_host_tool.sh) builds a cross toolchain, e2fsprogs, mandoc or pmccabe from pinned sources into a prefix, for a host with no package of it.
* [space.sh](setup/space.sh) is the free-space check that `preflight.sh` runs. It reads the free space under the tree and, under WSL, on the Windows drive that holds the distribution's disk, since that drive can fill before Linux sees it. It reads the drive with df(1) on the disk file through the drive's mount under `RACH2_WSL_MOUNTS`, `/mnt` by default, which gives the free space Windows reports and starts no Windows program. Starting one through WSL can stall for many minutes while the rest of WSL answers, so PowerShell is asked only for the disk file's Windows path, from the registry, when the file `wsl-disk.DISTRIBUTION` in the account's cache, `$XDG_CACHE_HOME/rach2` or `~/.cache/rach2`, names no file that the mount has. A missing or invalid path or reading refuses the work, as does a query or a df that does not finish within a minute. PowerShell runs without interactive input, and a failed query cannot supply a path.
* [doctor.sh](setup/doctor.sh) is the wider report, run by hand, in five groups: the build and boot of both architectures, OVMF, e2fsprogs and mandoc included; the tools of `tests/run style`; the mtools commands and xorriso for image preparation; the optional tools; and the version of each tool in [judges](setup/judges) beside the one recorded there from the testing host, whose version decides a check that depends on one. It runs each required tool, and exits nonzero when one is missing or broken.
* [e2fsprogs_path.sh](setup/e2fsprogs_path.sh) adds Homebrew's keg, `/sbin` and `/usr/sbin` to the path and puts first the directory that has all of `mke2fs`, `debugfs` and `e2fsck`, so that the three come from one installation.
* [ovmf_path.sh](setup/ovmf_path.sh) finds OVMF for `doctor.sh` and the UEFI suites: `RACH2_OVMF_CODE` and `RACH2_OVMF_VARS`, else QEMU's own pair, else the `ovmf` package's. It leaves out the Secure Boot builds, since the pinned GRUB is unsigned.

### Running on the testing host: `dev/testing.sh`

[testing.sh](dev/testing.sh) puts the owner's tree in the copy at `/home/testing/rach2`, or the copy that `RACH2_TESTING_COPY` names, and runs commands there, as the [testing skill](../.agents/skills/testing/SKILL.md) requires:

    tools/dev/testing.sh sync
    tools/dev/testing.sh run 'tests/run NAME...'
    tools/dev/testing.sh get PATH...
    tools/dev/testing.sh sh
    tools/dev/testing.sh wait NAME [SEEN]

Root builds reserve each build through the launcher, and `tests/run` each case through the site's ledger. Direct tools outside those entry points use the [installed launcher](etude/Readme.md#installed-launch-admission); this includes a compiler and a component-only build. Pass the program and its arguments directly rather than enclosing several build and test steps in one shell reservation.

`sync` makes the copy match this tree, by content, except what `.gitignore` lists, of which it sends only the Doom WAD, so the host keeps its own `build/` and vendor trees. The copy's `.git` is a repository of its own: from a git worktree, whose `.git` file names a path on this machine, it sends the shared repository with the worktree's HEAD and index. It refuses while a run or any process but a person's shell works in the copy, or another caller has the copy's lock. `run` syncs and runs the command, one string that bash in the copy evaluates with `RACH2_QEMU_ACCEL=tcg`; it travels in base64, so its quotes reach that shell unchanged. `get` copies paths of the copy here, such as products only Linux builds. `wait` watches a run started as `/home/testing/NAME.sh` that writes its result lines to `NAME.out`, and returns on a new line, the run's end, 15 minutes with nothing changed under `NAME/`, or 100 minutes; when the host does not answer, it exits 1 and says so, since the run may still go on. The script needs rsync 3; macOS's openrsync would delete the host's build and vendor trees.

### The worker and manager loops: `flow/`

The work and the management of the process run as loops: shell scripts that start one agent session after another, so that no session waits on a person and each piece of work is a process that ends. [worker.sh](flow/worker.sh) runs worker sessions in the clone it is in, as the account that clone's `gh` and git use, [manager.sh](flow/manager.sh) runs the manager's checks, [reviewer.sh](flow/reviewer.sh) reviews the phase In progress, and [release.sh](flow/release.sh), which the manager starts, releases it. Each runs in a detached tmux session, from a clone of its own. An account on the testing host runs one, with its state in `~/flow`:

    tmux new-session -d -s worker 'sh ~/rach2/tools/flow/worker.sh'

The owner's computer runs four, with tmux from Homebrew:

    git clone https://github.com/toksaitov/rach2 ~/flow/claude/rach2
    git clone https://github.com/toksaitov/rach2 ~/flow/codex/rach2
    git clone https://github.com/toksaitov/rach2 ~/flow/manager/rach2
    git clone https://github.com/toksaitov/rach2 ~/flow/reviewer/rach2
    tmux new-session -d -s claude 'RACH2_TESTING_COPY=/home/testing/rach2-claude \
        sh ~/flow/claude/rach2/tools/flow/worker.sh -s ~/flow/claude'
    tmux new-session -d -s codex 'RACH2_TESTING_COPY=/home/testing/rach2-codex \
        sh ~/flow/codex/rach2/tools/flow/worker.sh -a codex -s ~/flow/codex'
    tmux new-session -d -s manager 'sh ~/flow/manager/rach2/tools/flow/manager.sh'
    tmux new-session -d -s reviewer 'sh ~/flow/reviewer/rach2/tools/flow/reviewer.sh'

On macOS a program in a tmux session reaches an address on the local network, such as the Lenovo's, only when the application that started the tmux server has Local Network access (System Settings, Privacy & Security, Local Network). Apple's own programs, such as `ssh` and `nc`, are exempt; any other, such as `native-deploy` or `python3`, gets `No route to host` for every local address. Start the server that runs the loops from a shell of the Claude app, which has that access, and check it from the server itself:

    tmux run-shell "python3 -c 'import socket; socket.create_connection((\"192.168.0.106\", 22), 5)' && echo reach: ok"

`touch STATE/stop` ends a loop after its current session; `tmux kill-session -t NAME` ends it at once and leaves that session running, still under its time limit. A loop started again with the same STATE finds the session's process group in `STATE/session` and waits for it to end before it starts another. [session.pl](flow/session.pl) runs each session: it leaves the loop's process group, writes the session's group to `STATE/session` and sets the limit before the session starts, and starts no session when the record cannot be written. A TERM or INT sent to `session.pl` stops the session's whole group, TERM and then KILL half a minute later, before `session.pl` exits, so that stopping either group stops the session. A loop needs `claude` or `codex` signed in, `gh` with the `project` scope, git that can push, and perl. A loop on the owner's computer also needs `ssh testing` and a copy of its own on the host, which `RACH2_TESTING_COPY` names, so that the loops do not refuse each other's syncs.

On Rach2 a loop runs on the x86-64 GNU root ([`vendor/gnu/`](../vendor/gnu/Readme.md)) as an ordinary user, in tmux and from a clone of its own. The root has the programs the loops' scripts call besides the agents and `gh`: bash, which is also `/bin/sh`, the coreutils, git, perl, jq, procps's `ps`, tmux, `flock`, OpenSSH's client, and Python for the manager's `status.sh`. The agents layer ([`vendor/gnu/agents/`](../vendor/gnu/agents/Readme.md)) adds `gh` to a root built with it; a loop there needs `gh`, and `claude` or `codex`, installed and signed in, as it does anywhere. The `agents` suite runs on that root, as the test account, the worker loop itself in its `worker-session` row, which takes two issues from a stand-in for `gh` and runs a session of Claude Code on each against the fake API server ([the agents layer](../vendor/gnu/agents/Readme.md#tests)).

Before a session, a worker loop that has no issue claims one with [board.sh](flow/board.sh), under a lock shared by the loops of one user on one machine, and keeps its number in `STATE/issue`, since the owner's two loops share one account. It claims only an issue labelled `ci` or a member of the phase In progress, as the Work section of `AGENTS.md` orders them. The issue may be a group, which `board.sh group` makes from up to eight small issues; the session then takes each member as it starts on it with `board.sh take N G`, the only take that accepts a member, and `board.sh release` hands one back. `board.sh release N owner` hands an issue to the owner, for a decision that `AGENTS.md` gives the owner: it sets Backlog and adds the label `owner`. `board.sh release N owner-only` keeps the issue Ready and adds the label `owner-only`, for work that only the owner's accounts can do, such as a step on the testing host through `ssh testing` from the owner's computer; `next` and `take` give such an issue only to the account that owns the board, which is the owner's, and `group` refuses it. `take` refuses a closed issue and `release` changes nothing on one, except to set it Done, and the manager runs `board.sh done` at each check, which sets Done on every closed issue whose Status is not, for one that closes while a take or a release of it runs. A grouping and a claim of the same issue that overlap cannot both succeed: `group` labels the members before it checks again that none is assigned, and `take` assigns before it checks again that the issue joined no group. The session's prompt, [worker.txt](flow/worker.txt), names the issue, and the session builds, checks and pushes as `AGENTS.md` says; the loop gives the next session the same issue until it is closed or handed back. Claude Code sessions run at high effort, cannot schedule a wakeup or start a Monitor, either of which keeps a finished session open, and wait for their helpers; Codex sessions run `gpt-6.1-sol` at high effort without a sandbox, as Claude Code's run with permissions bypassed. The loop stops a session after six hours, with every process in its group, stops and logs any process a session leaves in its group when it ends, waits fifteen minutes after a usage limit, backs off after sessions that end within two minutes and leave their issue open, slows after three sessions that leave one issue open unless another open issue waits on it, passes by an issue labelled `intermittent` for a day after an account was unassigned from it unless ci has commented on it or changed its labels since, so that sessions that hand back an unchanged failure do not repeat, and while a `hold` issue is open starts no session on an issue whose work is committed and waits only for its push: with a clean tree it parks that issue in `STATE/parked`, still assigned, puts the clone on `master`, takes a `ci` issue titled `Core tests fail on ...` or `Core tests did not finish on ...`, or a group that lists one, if one waits, and takes the parked issue back once that one is closed; with none waiting, it puts the clone back on the issue's branch and keeps the issue in `STATE/issue`. It runs from a copy of `tools/flow` taken from `origin/master` and restarts when master's copy changes, so that a change to the loops reaches every machine at its next session. When a step of the copy fails, as on a full disk, the loop keeps the copy it has, logs the failure and tries again a minute later.

When group creation fails, `board.sh group` removes the `grouped` label from each member it tried to label and closes any group it created. If a label cannot be removed, it prints the member and the cleanup left to do on stderr; if the group exists, it keeps it open and prints its URL. A failed close also prints the URL. A successful call prints only the new group's number on stdout.

[progress.py](flow/progress.py), called by `status.sh`, reads every page of the open issues, the phase's members and its start comment. It reports the last member closed, members that block other open issues, runnable ones first and then in descending order of their count, and test failures without an assignee, measured from their creation or last unassignment. Six hours without a member closed while work remains, six hours assigned to a member that blocks other work and has no open prerequisite, and thirty minutes without an assignee on a test failure produce incident lines; failures labelled `intermittent` are excluded. The manager also reads each blocking task's worker output for three sessions without landing or a missed landing time. Each check reads and replaces `STATE/progress`, its record of the cause, action, worker and deadline for unresolved delays, and follows an incident until its repair succeeds. The manager's duties and its incident procedure are in [AGENTS.md](../AGENTS.md#the-manager).

[board.sh](flow/board.sh) runs the board one phase at a time. A phase is an issue labelled `phase`; its members are its sub-issues and the issues whose body says `Part of #P`, and at most one phase is In progress. `current` prints that phase's number. `members P [open]` lists P's members, each with its state, the time it closed, its labels and its title, from every page of the repository's issues read through GraphQL, since the search index lags. It reads the closed issues without their bodies, which are the slow part of the answer, and keeps the numbers that a closed issue's body gives as `Part of #N` in the account's cache, `~/.cache/rach2/issue-parts`, by the time the issue last changed, so that only a body edited or closed since the last read is read again. `link N...` makes issues sub-issues of the phase In progress, or writes `Part of #P.` in an issue's body when GitHub refuses, as it does past a hundred. `start [P]`, when no phase is In progress, comments a sentence and the line `phase: started at SHA` on the top Ready phase with `master`'s head and only then sets it In progress, so that a start that fails part way keeps that commit when it runs again; it links each triaged issue that belongs to no phase, and sets the phase's members in Backlog Ready; a second run changes nothing. `next` and `take` offer only issues labelled `ci` and the members of the phase In progress whose Status is Ready, which `take` also accepts In progress, and an issue labelled both `ci` and `intermittent` only while the phase has other work open. `group` accepts `ci` issues and makes the group a member of the phase. `archive P` archives the cards of closed issues, except the closed members of another open phase. GitHub's list of the board's items can lack an item that the issue itself reports, so each subcommand that reads the board also reads the repository's open issues, or every issue for `archive` and `done`, and puts an issue whose item the list lacks after the others. Those reads ask for no bodies; the `Part of #P` numbers come from the read of the issues that `members` makes, of the open issues, or of every issue for `archive` and `done`, and `link` reads a closed issue's body itself. GitHub at times answers a query with an error page, for minutes at a time, so `board.sh` reads a list one page at a time and asks again for a page that fails, five times in all, ten seconds apart, before the read fails. `phase` prints, for the manager, the reviewer and the release, the phase, the commit it started at, `master`'s head, its open work, its `intermittent` and `hold` issues, the last complete review and the state of `ci/core` on the head, and ends with `ready: yes SHA` or `ready: no: REASON`.

The manager loop starts a headless Claude Code check with [manager.txt](flow/manager.txt) and the last lines of `STATE/manager.log`, stops a check still running after forty minutes, and starts the next twenty minutes after the last ended. A check reads the process through [status.sh](flow/status.sh), which prints `board.sh phase`, the release under way, ci's runs, the open issues, the loops that [workers](flow/workers) lists, the testing host's load, and the resources: free space, inodes and memory on this machine and the host, ending with `resources: ok`, `low`, `critical` or `unknown`. `status.sh sizes` prints the largest trees on both, for the manager to choose what to remove, and the leftovers that the manager's loop would remove before its next check. For each worker's test run, [test_status.py](flow/test_status.py) reads the admission records on the Linux testing host and prints host, port, memory and worker waits, their start times in UTC, and their holders with whether they live. Host and port holders come from `/proc/locks`; recorded run and pool holders are checked by PID, group and start time. A stale run record, tree lock or pool holder is reported as a fault for the manager to inspect and clear. A second run on one tree is refused immediately, so the tree lock is listed as held rather than as a wait. For a run of etude it reads the run's status record, as [the etude Readme](etude/Readme.md#the-status-record) says, and prints each attempt as waiting for admission, with its request's place in the ledger, as working within its bounds, or as stalled; it then reads each ledger that a record or the machine record of the tree's owner names, and prints the requests that wait and each claim that no running owner keeps, live or uncertain, as a fault. It runs `board.sh done` and `board.sh start`, which starts the top Ready phase when none is In progress; triages every new issue that is not a phase, a group, a `ci` issue or the task of a phase not yet started, making each it keeps a member of the phase In progress with `board.sh link`, grouping them with `board.sh group` and placing them with `board.sh ready` and `order`; starts `release.sh` when the phase is ready; sends the questions of new `owner` issues to the owner's phone with [notify.sh](flow/notify.sh); and warns the owner of an incident with notify.sh: a push to the phone from an interactive Claude Code session with Remote Control, the only kind that sends one. That session waits two and a half minutes before the push, because Claude Code sends none while its terminal was just typed in, and the prompt a session starts with counts as typing. Meanwhile the session reads the issues the message names and writes out the problem, so that the owner who opens it from the phone finds the explanation there. `status.sh day DATE` counts a day's commits, closed issues, runs and phases for the manager's day report, and fails with no count when it cannot read one of them whole.

The reviewer loop reviews the phase In progress once `board.sh phase` says `ready: no: review`: its members and the `ci` issues have closed, but no review has read the commits up to `master`'s head. It reviews the range from the phase's start, which `board.sh start` comments on the phase as `phase: started at SHA`, or from the last review's end, to the head, so that the fixes of a review's findings get a review of their own. A review runs `codex exec` in a read-only worktree of the range's last commit, with `gpt-6-astra` at xhigh effort as the lead, which may start three `gpt-6.1-sol` subagents at a time at high effort, for at most three hours, with the prompt [reviewer.txt](flow/reviewer.txt) and an answer in the form [reviewer.json](flow/reviewer.json) gives. The loop files each finding as a `bug` issue of the phase and comments the summary on the phase, ending, when the review read the whole range, with the line `review: BASE..HEAD complete` that `board.sh phase` reads; when one of these steps fails it tries again every five minutes before it starts another review. A review that ends without an answer runs again, three runs in all; one that reaches its limit does not. Either then gives the phase the label `review-failed` for the manager, who removes the cause and the label, and may divide a range too large for one review by writing a commit inside it to `~/flow/reviewer/until`. Another reviewer's program needs an adapter in `review`, beside the one for `codex`. The owner may set the lead's model and effort explicitly with `reviewer.sh -m MODEL -e EFFORT`. Both values survive refreshes of the loop from master and appear in its report. For the Codex-led recovery of phase #589, the owner chose `-m gpt-6.1-sol -e high`; the subagents keep their configured GPT-6.1 Sol model at high effort.

The loops remove what finished work leaves, as the Resources section of `AGENTS.md` allows. A worker loop that holds no issue runs `tidy` from [lib.sh](flow/lib.sh) before it claims one: it removes each helper's worktree under `.claude/worktrees` whose commit `origin/master` already has and that `git worktree remove` takes without force, which it refuses for a worktree with changes, untracked files or a lock, and only when nothing ignored in it is anything but build output, which goes with it; and it deletes each branch that `origin/master` already has, which `merged` decides by making the merge of the two with `git merge-tree` and requiring it to succeed without conflict and leave master's tree unchanged, except `master`, the branch checked out and the branches of the issue it holds or parked. Where the host has the store of step outputs, it also removes a GNU layer built in the clone, one whose `cross/` is a directory and not a link into the store, so that the layer's next use takes it from the store. Each loop prunes its sessions' output with `prune_logs`: files more than fourteen days old, and then the oldest while they add up to more than 1 GiB, never one written in the last day; the reviewer prunes only while no filing or failure waits. Before each check the manager's loop runs [scratch.pl](flow/scratch.pl) as root on the testing host, for at most ten minutes, with the stems that begin with `rach2` of the scratch names that master's tests and tools make, which `stems` in lib.sh reads from their mktemp templates and quoted Python prefixes. It removes from the host's `/tmp` each entry named as one of those stems, a dot and six to eight letters, digits or underscores; owned by an account other than root; unchanged for a day; and with nothing mounted in it and no process working in it, running a program from it, or holding or mapping a file there: the scratch of tests that were killed before their traps ran. It then runs [leftovers.pl](flow/leftovers.pl), through `leftovers` in lib.sh, as root on the testing host for the home directories of the owner's account and the five workers' accounts, and on the owner's computer for the Desktop, which has the owner's checkout. It removes three kinds of leftovers: the directories that `tests/run` keeps in `build/tests/failed` of each tree; the loose files and directories in a home directory on the host whose names begin neither with a dot nor with `rach2`, such as a session's logs and scripts, but not one that is or holds a repository, a key, a password, a tarball or a WAD, nor `flow`; and each copy of the repository beside a checkout, `rach2-*`, and each worktree under the checkout's `.claude/worktrees`, but not the default copy of `testing.sh`, the release's or a loop's. Each must be unchanged for a day, unused by any process or mount, and not cited by name in an open issue's title, body or comment, nor, for a failed test, by its run's name. A copy goes only when its worktree is not locked, it keeps no failed test that an open issue cites, git status finds nothing uncommitted or untracked in it, every file git ignores in it is build output, and `master` has its HEAD whole, as `merged` decides for a branch; git makes that merge in a scratch repository, so that the copy is not changed. Each removal is a line of the loop's log. Last, `store_expire` in lib.sh removes from the host's store of step outputs, `/var/cache/rach2-store`, the entries that no copy's stamp names and that no step has used for three days, with `etude build -e` as root ([etude's Readme](etude/Readme.md#the-step-store)). Its `etude build` is that of `origin/master`, which `etude/provision_version.sh` builds in root's cache of versions on the host, or finds built there, so that root runs nothing an account's copy built. Each entry it removes, and its total, is a line of the loop's log, and a host without the store gives none.

[release.sh](flow/release.sh) `P` releases phase P once `board.sh phase` says `ready: yes SHA`. The manager starts it in the tmux session `rach2-release` from its clone, and again when it ended on something that passes, such as a busy build copy. It starts [full.yml](../.github/workflows/full.yml) on SHA, which tests it on the one machine that SHA's [site](ci/site) selects, or finds the run already started by its title, `Release tests of SHORT for phase #P`, and waits for it; builds SHA from clean for the Lenovo in `/home/testing/rach2-clean`; boots the Lenovo's recovery system and replaces the recovery kernel and image on its recovery partition, keeping the partition's key and the accounts' archive, and boots the new one; sends the kernel and the GNU root to the recovery system's `/dev/shm`, installs the kernel with `bootctl kernel` and the root with `rach2-install --update`, started once and detached, so that a lost connection does not stop it; runs `machine_identity.sh` and `metal_accept.sh` on the trial boot and only then `bootctl commit`; writes `/etc/rach2/release` on the machine, with the commit, the phase, the full run and the root's digest, flushes it and its directories to the disk, failing when a flush fails, since the read-back may come from the buffer cache, and reads it back; and closes the phase, with a report that names the machine and the accelerator of the tests, archives its cards with `board.sh archive`, sends one push and removes its worktree with the build's products. Its record, `~/flow/manager/release/record`, lists each finished step, and a release started again skips those after it reads the machine's state. A failed full run ends the release and names the `ci` issues that report it. The next candidate of the same phase gets a rerun, a run of only the suites that failed, titled `Release tests of SHORT for phase #P: again only SUITE on ARCH, ...`, when every first-parent commit since the failed candidate has a `Closes #N` line for one of those issues and for no other, every one of them is closed and titled `Release tests fail on ARCH: SUITE, ...` with suites of the registry, every architecture that did not pass has one, and its `tools/ci/site` selects the machine and the accelerator that the failed candidate's did; otherwise, or when any of that cannot be read, it gets a full run. An issue of the failure that is still open, as one labelled `intermittent` stays, has no fix, so the next candidate, the same commit included, gets a full run, and the release changes no issue but its phase. A rerun that fails leads to another rerun under the same rule. `/etc/rach2/release` then has the line `rerun of R`, R the run whose failures were run again. Before the build, before the install, and before it closes the phase, `board.sh phase` must still say `ready: yes SHA`; otherwise the candidate is void, since a later commit, an open member, a `ci` issue or a hold means that SHA is not the phase's finished work. A failed step is said on the phase and in the record's last line, for the manager to act on. A release that ended without closing the phase passes on to the next the fact that it changed the machine, and its record is replaced only once the board gives a new candidate. An install that failed, or whose end the release did not see, stops every later release before it changes anything, until a person has checked the machine's root and deleted the record's `install started` line. A release that has closed its phase finishes archiving its cards, whatever phase it was started for, before the manager starts the next phase.

### ci: `ci/`

[The routine entry contract](ci/Readme.md) gives focused push selection, clean release preparation, measured reference inputs and the shared native evidence used across workflow jobs.

[run.sh](ci/run.sh) uses the native collection entry for routine checks. `core DIR` selects style, host and the core tier; `full DIR` selects every suite, including bigmem. `ARCH='i686 x86_64'` gives both architectures one preparation record, plan and schedule. A full rerun may name `ARCH:SUITE` words in `SUITES`. [ci.yml](../.github/workflows/ci.yml) and [full.yml](../.github/workflows/full.yml) read the tested commit's [site](ci/site) through [site.sh](ci/site.sh), then use that machine's labels and requested accelerator for the complete collection. Changing or accepting the selected site is separate from implementing this entry.

Routine entry requires an installed immutable native etude and a version-two admission policy, supplied by `ETUDE` and `ETUDE_SITE` or the policy's installed etude. It compiles no replacement runner before measurement. `etude run routine-sequence` starts the existing native phase owner and observer before admitted ordinary preparation. `etude prepare routine` builds and validates the selected artifacts, captures their source inputs and composes the same-run measurement context. The route, preparation, import, retention and reporting commands are native Etude entries; actual build and test tools remain declared preparation inputs. The phase owner confirms preparation cleanup, runs the native collection with that context and keeps observation active through collection cleanup. Routine purposes are `ci` for core and `release` for full; `ETUDE_PURPOSE=push` uses the push budget. They have charged ceilings of 600, 14400 and 300 seconds respectively, including ordinary preparation and cleanup. The native deadline reserves cleanup time; no shell timeout controls this path.

DIR contains one `history/` and `store/` for the collection. Its `KIND-i686` and `KIND-x86_64` directories contain a native-format marker, the selected suites, verdict, `failed`, logs and `done`. [report.sh](ci/report.sh) validates the complete shared history with `etude check verdict --project-architecture --require-budget` for each architecture. An ordinary assertion failure affects its own architecture and a case of no architecture affects both. Missing work, corrupt evidence, unconfirmed cleanup or an unknown or failed charged budget affects both. A missing native history cannot pass through an old result-lines fallback. A cancelled owner leaves no completed result.

Reporting keeps the existing commit statuses and failure issues, including every failed attempt that a retry later passed. A build, style, runner or default-suite failure in core opens the issue that holds unrelated pushes until both architectures pass. A job that no runner accepted is retried once as a lost job; a second loss on the same commit is reported as unfinished. [bisect.sh](ci/bisect.sh) repeats native commits through their public preparation and collection entry, with the original purpose budget and strict history verdict. A failed native history or budget leaves the range unresolved. Historical commits retain their own result-line or structured-history protocols and legacy admission bounds. Bisection names a failing commit only after it and its passing parent repeat; it labels a failure intermittent only if no newer run has reported it. [AGENTS.md](../AGENTS.md) gives the response to each result.

### The style check: `verify/`

The cases of [host.style.json](../tests/cases/host.style.json) check the in-house tree: the kernel, KRFFS tools, utilities, shell, tests and tools, excluding extracted upstream projects. Preparation runs [style.sh](../tests/cases/host/style.sh) through `etude prepare -H --only CASE style OUTPUT`, requires every declared assertion to pass, and records the source digest, architecture, command, judge versions and results. The native `style` program verifies that evidence and the current source digest; it runs no compiler or interpreter. Missing or stale evidence requires preparation again.

    build/tools/etude/etude prepare collection -a both style
    build/tools/etude/etude run -a both style

`ARCH`, i686 unless set, selects the kernel, musl and build inputs of architecture-dependent checks. The other checks read both architectures. Preparation builds the required components and checkers first. `sh tests/cases/host/style.sh CASE` remains the direct preparation/debugging interface in a built tree; it is not the native case program.

The `cppcheck`, `clang-format` and `clang` cases retain the recorded-version policy of [setup/judges](setup/judges). A direct script invocation may report `other`, `absent` or `unjudged`, but native preparation refuses that evidence. `make host-source-tools` builds pmccabe 2.8 and mandoc 1.14.6 natively on Linux, macOS and Windows, with source, recipe, binary, semantic-fixture and license receipts. The historical `sparse` case uses Clang to check `__user` pointers and parsed casts. [Native source judges](setup/source-tools.md) gives the exact checks and the Windows mandoc batch-mode limits. These three judges run on the desktop host. Other preparation checks may use the tooling machine; native style execution starts none. [Source-check evidence](../tests/cases/host/Readme.md#source-check-evidence) gives the record checks.

The following list describes what preparation verifies, rather than commands started during native execution.

The cases are:

* `assignments` runs [probecheck.sh](verify/probecheck.sh) and its test [probecheck_test.sh](../tests/system/probecheck_test.sh), and [nativecheck.sh](verify/nativecheck.sh) and its test [nativecheck_test.sh](../tests/system/nativecheck_test.sh). `probecheck.sh` requires every guest program either architecture builds to be in the default suite's list, in `tests/probe-suites` with a suite of `tests/registry`, or in `tests/probe-helpers` with a reason. `nativecheck.sh` requires each of them to have a native case in [`tests/native/`](../tests/native/Readme.md), to be staged by one, or to have a reason in `tests/native/machine`, and each case to fit the format that directory's Readme gives.
* `cppcheck` runs cppcheck at the warning, style, performance and portability levels, with the exceptions in [cppcheck.suppress](verify/cppcheck.suppress): at C89 over the i686 kernel and the guest programs that share its headers as 32-bit code, and over the x86-64 kernel as 64-bit code; at C99 over the host programs. The lists come from [srclists.sh](verify/srclists.sh). A cppcheck that fails to run fails the case under any version.
* `shellcheck` runs ShellCheck over every script that [scripts.sh](verify/scripts.sh) lists, with SC1091 off. The scripts at `rach2/*.sh` and `krffs/*.sh` also waive SC2034 and SC2086. An empty list fails.
* `conventions` checks the C files and headers for a `//` comment, a byte other than tab, newline, carriage return and printable ASCII (by [asciiscan.c](verify/asciiscan.c)), a header without a guard (`#ifndef` or `#pragma once`), and a `sti; hlt` outside `sys/arch/*/cpu.c` or a call of `arch_idle` or `arch_idle_masked` outside those files and `sys/proc/sched.c`, so that every idle wait is counted as idle. In the scripts it refuses a `--` before a process group in a `kill`, which dash refuses, and requires a `finished` flag in each script under `tools/` or `krffs/`, and in `tests/system/accept/su_command.sh`, that sets both `-e` and `-u` and traps EXIT, since bash 3.2 exits 0 when `set -u` stops such a script.
* `clang-format` runs `clang-format --dry-run --Werror` over every in-house C file and header. The commits that reformatted the tree are listed in [blame-ignore-revs](verify/blame-ignore-revs), which `git config blame.ignoreRevsFile tools/verify/blame-ignore-revs` makes blame skip.
* `build-inputs` runs [build_inputs_test.sh](../tests/system/build_inputs_test.sh), which requires a build for ARCH to relink each program whose library, startup object or linker script changed.
* `abi` checks the user ABI: a program linked statically against ARCH's musl must be an `EXEC` with no `INTERP`, ELF32 Intel 80386 with a load segment at 0x08048000 on i686, ELF64 X86-64 with one at 0x400000 on x86-64, and the entry point in that region. Where that musl is not installed, the case fails and names `make musl`, which builds it for ARCH.
* `sources` checks the source lists and the architecture layer. [check_sources.sh](verify/check_sources.sh), which `make check-sources` also runs, compares `C_SRC` with the kernel's C files on disk; [guestcheck.c](verify/guestcheck.c) compares the guest makefiles with the host build; no rule in `tests/system/suites.mk` may make an image, disk, ISO or stick; every in-house C source must be in a compilation database (below); and `make -C rach2 check-arch` runs [archcheck.sh](verify/archcheck.sh) over the kernel's shared code.
* `text` runs [textcheck.sh](verify/textcheck.sh), which refuses non-ASCII bytes, a spaced `--` used as a dash (in Python only in a comment, a docstring or a message, which [pyprose.py](verify/pyprose.py) tells from the strings a program runs or generates), `-` bullets in Markdown and `Phase N` or `Part N` tags, and in the component documents (every in-house `Readme.md` and `NAME.Readme.md` but the front page) a `##` heading out of the order of `AGENTS.md`'s Documentation section or a citation of a milestone by number; [prosecheck.c](verify/prosecheck.c) then runs `columns` (comment lines at 80 columns), its self-test, and `banned` (the terms of the register rule in `AGENTS.md`).
* `messages` runs [fmtcheck.sh](verify/fmtcheck.sh): every `klog`, `console_printf` and `k_printf` format uses only conversions `k_vprintf` has.
* `repro` builds the KRFFS tools, and [check_repro.sh](verify/check_repro.sh) stages one manifest twice and requires the same bytes, with directory entries in name order.
* `checkers` runs the checkers' self-tests: `elfcheck`, `cfgcheck`, etude's `pecheck`, `gen_compile_commands.sh` and `suitecheck.sh` with `--selftest`, `etude check --selftest` over [its fixtures](etude/fixtures/expect), and the tests [recovery_key_test.sh](../tests/system/recovery_key_test.sh), [dryrun_test.sh](../tests/system/dryrun_test.sh), [build_rules_test.sh](../tests/system/build_rules_test.sh), [style_scope_test.sh](../tests/system/style_scope_test.sh), [style_cases_test.sh](../tests/system/style_cases_test.sh), [verify_temp_test.sh](../tests/system/verify_temp_test.sh) and [style_hooks_test.sh](../tests/system/style_hooks_test.sh). `style_scope_test.sh` runs `scripts.sh` and `textcheck.sh` over a private tree and requires each kind of file they claim to be read; `style_cases_test.sh` plants faults in a private tree and in copies of the manifest and requires each to fail the case; `verify_temp_test.sh` requires `style.sh` to make a private log directory for each run; `style_hooks_test.sh` requires, in a scratch repository, the git hooks to format and stage a C file, to refuse a commit with an em-dash or a long comment line, and to refuse a push of a commit with faults.
* `devlog` runs `prosecheck devlog`: `dev-log/Readme.md` lists exactly the finished milestones, in the directories' order.
* `registry` checks `tests/registry`. Each row names a family of `tests/cases` whose identity ends in the row's name; each family has a row; `tests/system/suites.mk` has no `run-` target; no suite appears twice; and `tests/system/suites.md` is the output of `tests/run inventory`, with a sentence in `suites.mk` for every suite. `rach2/syscalls.md` must be what `make syscalls` writes: `mancheck --calls` reads the two kernels' tables and numbers as `manual` does, and prints a row for each call with its i386 and x86-64 numbers and its page. `man/programs.md` is the output of `make programs-md`.
* `waits` runs [suitecheck.sh](verify/suitecheck.sh): no test sleeps for a fixed time, bounds a duration or prints a skip and passes, except at an interval that `tests/system/intervals` lists with its reason, a finding of an older test that `tests/system/unconverted` counts, or a line whose timing a case's manifest declares; and [`etude check`](etude/Readme.md) finds the manifests and the contracts' examples valid.
* `manual` runs `make mancheck` (`mancheck-prepared` on Windows), which runs [mancheck.c](verify/mancheck.c) once for each architecture: every staged program, BusyBox applet and system call has a manual page or an alias, and every page passes the pinned mandoc's `-Tlint -Wwarning`. Windows preparation returns the generated BusyBox applet table before this native check.
* `clang` runs clang `-fsyntax-only` with `-Wcast-align -Wconditional-uninitialized -Wshadow-all -Wtypedef-redefinition -Wcomma` over ARCH's kernel sources.
* `sparse` retains its case identity and checks every kernel source with Clang's `__user` address-space and `noderef` annotations, plus a parsed audit of casts that remove the annotation. This preserves the tree's user-pointer contract; it does not add Sparse's unrelated analyses. [Native source judges](setup/source-tools.md#user-pointers) gives the trusted-copy rules and compiler fixtures. Normal GCC and TinyCC builds are unchanged.
* `sizes` runs [sizecheck.c](verify/sizecheck.c) over every in-house C file: at most 100 lines in a body, 6 parameters, a nesting depth of 4 and a cyclomatic complexity of 25 as pmccabe counts it, except for the functions [sizes.reasons](verify/sizes.reasons) lists, each with the ceiling it may not pass. `sizecheck --report` prints every function's measures.
* `links` runs [linkcheck.sh](verify/linkcheck.sh): every link in the Markdown files git tracks outside `dev-log/`, and in the milestone checklists under `dev-log/`, reaches a file that exists, and every anchor a heading in it.

The other files of `verify/` are not part of the style check:

* [doccheck.sh](verify/doccheck.sh) `[BASE]` is the check of a change to documents and comments alone, which AGENTS.md gives such a change in place of the build and the suites. It refuses, with status 2, a tree without BusyBox's build, which the manual's check reads, and a change with a file whose mode or type changes, a new file that is not a plain one, a C file that does not preprocess or whose tokens differ from BASE's once the comments are removed, a shell script whose interpreter line or commands, as bash prints them back without the comments, differ from BASE's, a makefile or manifest with a changed line that make or the manifest's reader does not skip, or any other kind of file; otherwise it runs the style check's document checks: the text and prose checks of the `text` case without prosecheck's selftest, the `devlog`, `manual` and `links` cases, the three generated lists of the `registry` case, and clang-format over the changed C files.
* [analyze.sh](verify/analyze.sh) is `make analyze`: GCC's `-fanalyzer` over the kernel and the guest programs and cppcheck at its exhaustive level, either of which fails the run on a finding, and two advisory reports, clang-tidy over the kernel and the sections the linker drops as unused. `--fast` leaves out the exhaustive cppcheck. The logs are in `build/verify/analyze/`.
* [coverage.sh](verify/coverage.sh) `[NAME...]` builds each host test again with `--coverage` and prints, for every kernel source the test compiles, the lines executed and the branches taken. It takes the compile commands from `etude prepare -H --print-commands`, so it needs a tree that `make` has built. No suite runs it.
* [sha256.c](verify/sha256.c) prints the SHA-256 digest of each file. The build makes it as `build/tools/verify/sha256`, so the build needs neither `sha256sum` nor `shasum`.
* [prose_report.sh](verify/prose_report.sh) compares the rates of watched phrases in the tree's prose with those in the pinned upstream sources, and never fails. `--baseline` and `--fixture` compare the counts with the records [prose_baseline.txt](verify/prose_baseline.txt) and [prose_upstream.txt](verify/prose_upstream.txt), and `--write` rewrites a record.

### The git hooks: `git-hooks/`

[commit-msg](git-hooks/commit-msg) refuses a commit message with an attribution line, which the Git section of `AGENTS.md` forbids: a `Co-Authored-By:`, `Claude-Session:` or `Signed-off-by:` line in any letter case, a "Generated with Claude Code" line with or without an emoji before it, or a trailer whose value ends in `<noreply@anthropic.com>`. It prints `commit-msg: refused: attribution on line N: TEXT` and exits 1. Each pattern starts in the first column, so a sentence that mentions a trailer passes, and so does the diff that `git commit -v` adds.

[pre-commit](git-hooks/pre-commit) and [pre-push](git-hooks/pre-push) run [hookcheck.sh](verify/hookcheck.sh), the fast part of `tests/run style` on the files a commit or a push changes, read from a copy of the tree as the index or the pushed commit has it. `pre-commit` formats each staged in-house C file and header with the clang-format that `tools/setup/judges` records and stages the result; a file that needs formatting and also has unstaged changes refuses the commit instead. It then runs `textcheck.sh` and `prosecheck columns` and `banned` on the staged files, and refuses the commit with a `style: FILE:LINE: fault` line for each finding. `pre-push` refuses a push to `master` whose commits change a file that is not formatted or has such a finding, changes no file, and prints `sh tools/verify/hookcheck.sh format FILE ...` for the files to format. The recorded clang-format is `clang-format` or `clang-format-21` on PATH; without it, as on a Mac, the files are formatted on the testing host through one `ssh testing`, or the host that `RACH2_STYLE_HOST` names. With no recorded clang-format anywhere, or a checker that does not build, the hooks warn and go on, unless `RACH2_STYLE_GATE` is `strict`, which the worker loops set; then they refuse. An ordinary commit takes about three seconds with the formatting on the host, and less with a local clang-format. A commit or push never passes `--no-verify`, which skips the hooks. A clone turns the hooks on with

    git config core.hooksPath tools/git-hooks

[.claude/settings.json](../.claude/settings.json) runs that command, with `--local`, when a Claude Code session starts, and sets `blame.ignoreRevsFile` in the same way; the worker loops, `tools/flow/worker.sh`, run it too. It also turns off the attribution Claude Code adds by default: `includeCoAuthoredBy` is false, the commit and pull request attributions are empty, and `sessionUrl` is false.

### The compilation database

[gen_compile_commands.sh](dev/gen_compile_commands.sh) writes `compile_commands.json` at the root of the tree, from which clangd reads each file's flags:

    sh tools/dev/gen_compile_commands.sh

GCC has no `-MJ`, so the script takes the commands from the build. It dry-runs the build units with `make -Bn`, or a preparation tool's print mode, joins continued recipe lines, and keeps each compiler command, one entry for each C source on it. An architecture assignment before `muslgcc` remains part of the command. The units are the four i686 kernels (`rach2`, `rach2-recovery`, `rach2-metal`, `rach2-harness`) and the x86-64 kernel (`rach2-x86_64`); the guest programs (`tests`, `ish`, `utils`, `musl-programs`, `doom`); the local Rach2 collection (`native-collection`); the host programs (`krffs`, `tools`, `collection-tools`, `host-tests`); and the GNU helper (`gnu-products`, `gnu-host-tests`). `print-collection-tools` lists collection-only targets without enlarging ordinary `make all`. The host-test units use `etude prepare -H --print-commands`, including routed fixtures and their compiled tools. The GNU product unit reads the same Make recipes used by product preparation, inventory preparation and root staging. The GNU helper units use its fixed x86-64 compiler and sysroot; the remaining units except `rach2-x86_64` use i686's guest inputs whatever `ARCH` says. The dry runs of `tests`, `utils` and `krffs` take the i686 musl's files they list as prerequisites as present, with make's `-o`, so a tree that has built only x86-64 has its database too. Each unit's database is validated line by line and written as `build/compile_commands/UNIT.json`. Their union replaces the root file only when it is valid and has every i686 kernel source. Git ignores the unit databases and the root file. The projects built by their own build systems (musl, BusyBox, Dropbear, TinyCC, pdpmake and e2fsprogs) are not in the database; the Doom engine under `ports/doom/src` is, since the port's Makefile compiles it.

Run the script again after adding or removing a source or changing flags. Source-check preparation runs it too, leaving a current database, and then runs [dbcheck.sh](verify/dbcheck.sh), which requires every in-house C source to be in a unit's database, to be included by name by a source in its directory (or by a host test through its `compat/` path), to be a fixture under `tests/system/fixtures` or `tests/host/fixtures` that a script of that tree refers to, or to be a source of etude's Windows programs under `tools/etude/win` that [wincheck.sh](etude/wincheck.sh) builds with MinGW-w64. Two further Windows-only routes are checked by exact source-to-build references: the scenario actor selected by the native host preparation adapter, and mandoc's entry and mapping adapter copied by `build_host_tool.sh` and compiled by `mandoc-batch.mk`. The checker-preparation case runs the generator's `--selftest`, six cases of its joining, selection, escaping and validation.

[.clangd](../.clangd) makes `i686-elf-gcc` the compiler of every entry under `rach2/`, `tests/`, `ish/` and `utils/`, the x86-64 kernel's among them, so that clangd reads the cross compiler's freestanding headers there; the KRFFS tools keep the host compiler their entries give. clangd asks a compiler for its headers only when it is allowed to, so start it with

    --query-driver=**/i686-elf-*gcc

In VS Code, set `"clangd.arguments": ["--query-driver=**/i686-elf-*gcc"]`; other editors pass the same option.

### Artifact checkers: `inspect/`

The programs and scripts under `inspect/` judge a built artifact: a kernel or a program, a staged image, a configuration a disk depends on. `make` builds the C programs into `build/tools/inspect/` and runs each check where its artifact is made; stamps in the root `Makefile` run some checks again when the checker changes, and remove an artifact that fails. Each file's opening comment states its whole contract.

* [elfcheck.c](inspect/elfcheck.c) judges ELF files by what Rach2 loads. `elfcheck [--arch i686|x86_64] FILE...` applies the loader's rules to user programs and refuses a dynamic one: `i686`, the default, takes ELF32 i386 programs in `[0x02000000, 0xBFFFF000)`, and `x86_64` takes ELF64 x86-64 programs in `[0x10000, 0x00007FFFFFFFE000)` with file offsets held to 32 bits. `elfcheck --kernel [--tcc] [--initrd IMAGE] FILE` judges a kernel by what QEMU's `-kernel` and GRUB read: an ELF32 kernel by its Multiboot header and two load segments, an ELF64 kernel as the header's a.out kludge loads it; `--tcc` accepts a kernel TinyCC linked. `--initrd` also requires the page-aligned physical kernel and module ends to leave 8 MiB below the 32 MiB boot allocator limit; the small image helper checks this during preparation. `--selftest` runs the refusal cases of both and the module-placement boundaries. `rach2/Makefile` runs `--kernel` on every kernel it links, and `make check-tcc`, `check-pdpmake` and `check-e2fsck` run the user check on the programs those ports stage.
* [check_link.sh](inspect/check_link.sh) `LIB_OR_OBJECT...` requires that musl's `libc.a`, TinyCC's `libtcc1.a` and the startup objects staged for the guest compiler leave no symbol undefined between them, so that a program linked on Rach2 needs no libgcc. It reads symbols with `CHECK_LINK_NM`, `i686-elf-nm` when unset; the callers pass `x86_64-elf-nm` for x86-64. `vendor/tcc/build_tcc.sh` runs it, and the root Makefile's TinyCC stamp runs it again when TinyCC or the script changes.
* [setidcheck.c](inspect/setidcheck.c) is the guard on set-id bits: privilege in an image comes only through the paths declared in [setid.allow](inspect/setid.allow), whose opening comment defines its directives. `setidcheck [MANIFEST...]` checks manifests, all of `krffs/manifests/` when none is given. `setidcheck --image FILE --manifest PATH` compares every node of a finished KRFFS image with the declarations, and `--ext2 FILE` in place of `--image` does so for an ext2 volume with a reader of its own, which shares no code with the kernel's driver and refuses a volume outside the profile `mkext2.sh` writes. `--applets` checks BusyBox's applet tables and configurations and the init binaries. In an x86-64 build it reads the host files a manifest gives through `RACH2_PATH_MAP`, as the stager does. `make check-setid` runs the sweep and `--applets`; `krffs/mkimage.sh`, `krffs/mkdisk.sh` and `image/mkext2.sh` check what they build; and the root Makefile's `.checked` stamps check the test, os-simple and os-real images again when the guard or its list changes.
* [binfind.c](inspect/binfind.c) `[--offset] STRING FILE` reports whether a file contains a byte string, by its exit status or with `--offset` by the first match's offset, and `binfind --replace OLD NEW FILE` overwrites the first match with a string of the same length. `make check-tcc` reads TinyCC's four refusal messages out of the shipped compiler with it, and the `sealed` cases mark a copy of the kernel and find bytes in their copy of the disk with it.
* [check_diskpolicy.sh](inspect/check_diskpolicy.sh) `KERNEL read-only|read-write` requires a kernel to contain the banner of the given disk policy and not the other's, and [check_recovery.c](inspect/check_recovery.c) `KERNEL recovery|ordinary` does the same for disk authority, with `check_recovery.sh` as its build-time entry. They catch a kernel built into the wrong tree; the `diskpolicy` and `authority` suites test what the kernels write. `make rach2-metal` requires the metal kernel to be read-only, `make rach2-recovery` requires the recovery kernel to have recovery authority and the read-write policy and the ordinary kernel ordinary authority, and `image/mkiso.sh` checks the kernel it stages.
* [cfgcheck.c](inspect/cfgcheck.c) checks two configurations a sealed disk depends on. `cfgcheck grubembed CONFIG` requires exactly the four commands of [grub-embed.cfg](image/grub-embed.cfg), in order, so that GRUB's core opens the boot partition's menu first and the recovery partition's only when that fails, and `cfgcheck grubefi CONFIG` the three of [grub-efi-embed.cfg](image/grub-efi-embed.cfg). Both refuse a quote mark or a line-end backslash anywhere in the file, comments included, since GRUB's rescue parser would read either as taking the commands below into a string. `mkdisk_grub.sh` runs both for every disk, and `regen_grub.sh` before it makes the images. `cfgcheck sealednet ADDRESS PREFIX MASK GATEWAY SCRIPT` requires the sealed disk's fallback address, prefix, mask and gateway to describe one subnet and `SCRIPT` to apply exactly those numbers; `make rach2-sealed-disk` runs it. `--selftest` runs both on their fixtures.
* [growset.c](inspect/growset.c) compiles [utils/growset.c](../utils/growset.c), which computes the sectors a grow of an ext2 root writes, for the host; [growset(8)](../man/man8/growset.8) describes its use. `make` builds it through a rule in `tests/system/suites.mk`, and the `grow` and `installer` suites and `dev/machine_grow_plan.sh` run it.

### Disk, stick and ISO builders: `image/`

The scripts under `image/` assemble boot media on the host with mtools, xorriso, e2fsprogs, the C programs beside them and the GRUB images pinned in [vendor/grub/](../vendor/grub/Readme.md); no GRUB toolchain, container or loop mount is needed. `mk/images.mk` builds the C programs into `build/tools/image/`. Each script writes its product under a temporary name and renames it only after every check passes. The products are under `build/images/` for i686 and `build/x86_64/images/` for x86-64.

#### ext2 roots

    sh tools/image/mkext2.sh [--overlay PROGRAM] MANIFEST OUTPUT [SIZE_MB [BLOCKS_PER_GROUP [BYTES_PER_INODE]]]

[mkext2.sh](image/mkext2.sh) builds an ext2 volume from a manifest: `stageimage.krffs --tree` stages it into a directory, the host's `mke2fs` formats the directory on the one profile the kernel's driver writes, `debugfs` sets each node's owner, mode and set-id bits from the manifest, and the volume must pass `e2fsck -fn` and `setidcheck --ext2`. The size is 1024 MiB unless given, sparse on the host. A group size and an inode ratio replace mke2fs's choices; a grow keeps the inodes of a group, so the ratio decides how much a grow to a large disk writes. The times, the UUID and the directory hash seed are fixed, so one manifest makes one image. `--overlay PROGRAM` runs PROGRAM on the staged directory before formatting, for a system a manifest cannot describe. `make` builds `os-real.ext2` this way, and `make os-real-gnu-ext2` the GNU system's root with `--overlay vendor/gnu/install_root.sh`.

#### GRUB disks

    RACH2_DISK_RECOVERY_MB=64 RACH2_DISK_EXT2_MB=1024 RACH2_DISK_EXT2_IMAGE=ROOT.ext2 \
        sh tools/image/mkdisk_grub.sh [KERNEL [OUTPUT]]

[mkdisk_grub.sh](image/mkdisk_grub.sh) builds a disk that boots by BIOS, and on a GUID table by UEFI as well. KERNEL is the built kernel unless given, and OUTPUT is `os-real-grub.disk` in the image directory, `os-real-grub-with-key.disk` in a tree with a recovery key. [disk(7)](../man/man7/disk.7) and [rach2-install(8)](../man/man8/rach2-install.8) describe the partitions, and [bootctl(8)](../man/man8/bootctl.8) the kernel slots, the menu and the environment block. From the first MiB the script lays out the FAT32 boot partition, the FAT32 recovery partition, one spare MiB, the ext2 root and one spare MiB; on a GUID table the BIOS boot partition is sectors 34 through 2047. The kernel slots are 4 MiB, room for the kernel that TinyCC builds on the machine itself, and a larger kernel is refused. Every disk has the disk GUID `1acef00d-0f1e-4d2c-8b3a-c0ffee000001`, or the MBR identifier `1acef00d`, and the FAT serials and labels `1acef00d` and `RACH2BOOT` on the boot partition and `1acef003` and `RACH2RECOV` on recovery. The script writes the table with `mkgpt` or `mkmbr` and GRUB with `grubembed`, and checks the embedded configuration with `cfgcheck` and the boot files' cluster chains with `fatchains` before it publishes the disk.

It reads eleven settings from the environment:

* `RACH2_DISK_TABLE`: `gpt`, the default, or `mbr`.
* `RACH2_DISK_BOOT_MB`: the boot partition's size, 33 by default on a GUID table and 16 on an MBR. An EFI system partition has one sector per cluster, and the script refuses one outside 65525 to 131070 clusters, the least UEFI firmware reads as FAT32 and the most `bootctl` walks: 33 to 64 MiB.
* `RACH2_DISK_CLUSTER`: sectors per cluster on the recovery partition and on an MBR's boot partition; unset, mformat chooses.
* `RACH2_DISK_RECOVERY_MB`: the recovery partition's size, required.
* `RACH2_DISK_RECOVERY_KERNEL` and `RACH2_DISK_RECOVERY_IMAGE`: the recovery kernel and RAM image staged there; without them the recovery entry's title says the system is not built.
* `RACH2_DISK_EXT2_MB` and `RACH2_DISK_EXT2_IMAGE`: the root partition's size and the image `mkext2.sh` built for it, which must fit; both required.
* `RACH2_DISK_APPEND`: kernel arguments added to every entry.
* `RACH2_DISK_DHCP_APPEND`: the network arguments, kept apart because the kernel refuses an address given twice.
* `RACH2_DISK_HELLO`: a file copied to `/hello.txt` on the boot and recovery partitions.

`RACH2_ARCH`, or `ARCH`, selects the build tree, and `SOURCE_DATE_EPOCH`, 1700000000 unless set, fixes the FAT timestamps.

`make rach2-sealed-disk` builds the disk the installer writes, `rach2-sealed.disk` (`rach2-sealed-with-key.disk` with a key): a 64 MiB boot partition, a 64 MiB recovery partition with the recovery system, and a 1024 MiB root, 1155 MiB in all. Its rule first runs `cfgcheck sealednet` over `SEALED_ADDRESS`, `SEALED_PREFIX`, `SEALED_MASK` and `SEALED_GATEWAY`, which may be set on the command line, and `krffs/rescue-static.script`. `make os-real-grub-disk` builds a disk of the same shape with the os-real root for `rach2/run_from_disk.sh`, and the suites build their own disks by rules in `tests/system/suites.mk`.

The other GRUB files:

* [grubembed.c](image/grubembed.c) `DISK BOOT.IMG CORE.IMG` installs GRUB on a disk image, which `grub-bios-setup` does only on a device: the boot image's first 440 bytes go into the MBR, which keeps its disk identifier and table, and the core into the sectors after the MBR on an MBR disk or into the BIOS boot partition on a GUID one. The core must fit the window `utils/grubslot.h` lays out, so that `bootctl grub` can replace it later.
* [grub-embed.cfg](image/grub-embed.cfg) and [grub-efi-embed.cfg](image/grub-efi-embed.cfg) are the configurations built into the BIOS cores and the EFI image, which [vendor/grub/Readme.md](../vendor/grub/Readme.md) describes. A build fails when either differs from the one the pinned images were made with.
* [mkgrubcore.sh](image/mkgrubcore.sh) `A|B OUTPUT` copies and verifies one of two pinned cores that print `GRUBCORE=A` or `GRUBCORE=B` on the serial line; the `grub` suite installs them in turn.
* [fatchains.c](image/fatchains.c) `IMAGE PATH...` prints the runs of clusters of files on a FAT16 or FAT32 image, as `mshowfat` does.
* [ubuntu-image.txt](image/ubuntu-image.txt) gives by digest the Ubuntu container in which `vendor/grub/regen_grub.sh` makes the GRUB images; no build or suite uses a container.

#### Partition tables

* [mkmbr.c](image/mkmbr.c) `[--lba] [--id HEX] DISK START:SIZE:TYPE[:boot|:logical] ...` writes an MBR's table, with START and SIZE in MiB, or sectors with `--lba`, at most four primary and sixteen logical partitions, and `--id` the disk identifier. It writes only the table, the signature and the identifier, so the boot code stays.
* [mkgpt.c](image/mkgpt.c) `[--seed N] [--guid GUID] [--damage-primary] DISK START:SIZE:KIND[@INDEX][=LABEL] ...` writes a GUID table with its protective MBR, both headers and both arrays, with START and SIZE in sectors, KIND `fat`, `data`, `linux` or `bios`, and at most fifteen entries. The GUIDs are made from the seed, so one seed gives one set of identities.

Both print a table with `--list DISK`. The disk builder and the suites write their tables with them.

#### Sticks

A stick image is a hybrid ISO from `mkiso.sh`, padded to a 1 MiB boundary and followed by an exFAT volume that `mkexfatfixture` ([tests/host/](../tests/host/Readme.md)) writes. `mkmbr --lba` gives the MBR three entries around GRUB's boot code: the ISO's file system, of type `0x17`; the volume, `0x07`; and the ISO's EFI boot image, `0xEF`, which UEFI firmware boots a USB device from. [stickcheck.c](image/stickcheck.c) `IMAGE VOLUME-START VOLUME-SECTORS`, linked with the kernel's `mbr.c` so that it applies the kernel's rules, judges the whole image, and `mkexfatfixture --check` walks the volume.

* [mkstick.sh](image/mkstick.sh) `ISO OUT MKEXFATFIXTURE MKMBR STICKCHECK` puts a 16 MiB volume after the metal ISO. `make rach2-stick-image` builds `rach2-stick.img`, which the `usbdisk` suite boots.
* [mkinstallstick.sh](image/mkinstallstick.sh) `ISO DISK OUT MKEXFATFIXTURE MKMBR STICKCHECK [EXTRA [FREE-MIB]]` puts after the recovery ISO a volume with the disk image, a manifest of its name, length and SHA-256, the EXTRA file, GRUB's EFI image with its digest, and FREE-MIB of free space, 4 unless given; [rach2-install(8)](../man/man8/rach2-install.8) describes what the installer reads there. `make rach2-install-stick` builds `rach2-install-stick.img` with the sealed disk, its root as EXTRA and 256 MiB free.

#### ISOs

    RACH2_ARCH=x86_64 sh tools/image/mkiso.sh IMAGE

[mkiso.sh](image/mkiso.sh) builds `IMAGE.iso` beside `IMAGE.krffs` for `test`, `os-simple`, `os-real`, `rach2-metal`, `rach2-recovery` or `rach2-recovery-with-key`, with xorriso and the pinned El Torito, hybrid and EFI images; GRUB loads the kernel and the image as its module. Every ISO boots by BIOS from a CD or a USB device, and by UEFI through a FAT image with GRUB's EFI image, appended as the MBR's second partition. The script requires the metal kernel to be read-only and every other kernel read-write. The metal menu's first entry sets the address `RACH2_METAL_IP` and gateway `RACH2_METAL_GATEWAY`, 192.168.0.105/24 and 192.168.0.1 unless set; the recovery ISO's one entry takes an address from DHCP. `make isos` builds the five ISOs, and `make test-iso`, `os-simple-iso`, `os-real-iso`, `rach2-metal-iso` and `rach2-recovery-iso` one each; `rach2/run_from_iso.sh` boots one in QEMU.

#### Names of keyed artifacts

[keyname.sh](image/keyname.sh) `PATH` refuses an artifact whose name disagrees with the tree: a name with `-with-key` while `krffs/recovery_authorized_keys` is absent, or one without it while the key is present. The rules of the recovery image, the recovery ISO, the sealed disk, the os-real GRUB disk and the install stick run it, since Make chooses those names when it starts. [krffs/Readme.md](../krffs/Readme.md) describes the recovery key list, and [the section below](#working-an-installed-machine-from-the-host) `make release`.

### The console's font: `font/`

    sh tools/font/mkfont.sh unifont_all-18.0.01.hex.gz > rach2/sys/display/vga_font.c

[mkfont.sh](font/mkfont.sh) writes the console's font from GNU Unifont 18.0.01. It refuses any file but `unifont_all-18.0.01.hex.gz`, by its SHA-256, whose signature was checked with `gpgv` and the GNU keyring; the script's opening comment gives where to fetch it and the signing key. The output is committed, since a build on Rach2 has no network to fetch the font from, and no build step runs the script. [rach2/sys/display/Readme.md](../rach2/sys/display/Readme.md) describes the tables it writes, and [console(4)](../man/man4/console.4) the characters the console shows.

### Working an installed machine from the host

The manual has the procedures that install and update a machine: [rach2-install(8)](../man/man8/rach2-install.8), [recovery(7)](../man/man7/recovery.7), [bootctl(8)](../man/man8/bootctl.8), [reflash(8)](../man/man8/reflash.8) and [disk(7)](../man/man7/disk.7). This section is what the host does around them; the [machine skill](../.agents/skills/machine/SKILL.md) has the check before a write.

Each root has an SSH host key of its own, a RAM root a new one at each boot, so give each system its own known-hosts file:

    ssh -i krffs/rach2_demo_ed25519 -o UserKnownHostsFile=/tmp/k-NAME \
        -o StrictHostKeyChecking=accept-new root@ADDRESS

Write `-i KEY` before the destination: after it, ssh takes the two words as part of the remote command, offers its default identities, and the login fails. Root logs in by key unless [sshd.conf(5)](../man/man5/sshd.conf.5) permits a password; `su` from another account is the other way in. Dropbear has no sftp server, so a file goes over as `ssh ... 'cat > /tmp/f' < f` and comes back as `ssh ... 'cat /tmp/f' > f`; the GNU system's root runs OpenSSH.

The development keys are committed, `krffs/rach2_demo_ed25519` for root and `krffs/rach2_test_ed25519` for the test account, so every image from any clone trusts them, and any host reaches any development machine on the private network. Git does not keep their mode, and ssh refuses a private key others can read; `krffs/gen_demo_key.sh`, which the build runs, and `tests/run` set it to 0600. A machine for any other network is built after `RACH2_REPLACE_KEYS=1 sh krffs/gen_demo_key.sh`; [krffs/Readme.md](../krffs/Readme.md) describes the key files.

A recovery image answers SSH only when built in a tree that has `krffs/recovery_authorized_keys`, which `make recovery-key` and `tests/run` create. To let in a key other than the development key, copy only its `.pub` file to the build host and run two commands, since Make chooses the `-with-key` artifact names when it starts:

```sh
make recovery-key RECOVERY_EXTRA_KEYS=/path/operator.pub
make rach2-install-stick
```

The second builds `build/images/rach2-install-stick-with-key.img`. `make no-recovery-key` removes the key and every artifact built with it, and `make release`, the install stick and recovery ISO for somebody else, is refused in a tree that has one.

With `rach2.netconsole` on the boot line, the kernel broadcasts its log in Ethernet frames of type `0x88b5` ([the network Readme](../rach2/sys/network/Readme.md)). `sudo tcpdump -i en0 -U 'ether proto 0x88b5' -w FILE` on the Mac keeps them, the only record of a panic on a machine with no serial port.

`build/images/rach2-install-stick.img`, written to a whole stick, boots recovery and has the installer's images; `build/images/rach2-stick.img` boots the metal system as a test. `tests/system/accept/metal_accept.sh HOST [PORT] [STICK-SERIAL]` is the scripted half of acceptance ([the system tests' Readme](../tests/system/Readme.md)).

### Machine measurements and the grow: `dev/`

These scripts update and measure an installed machine over SSH and run the recovery grow. Each script's header states its contract.

* [machine_update.sh](dev/machine_update.sh) `KERNEL [ADDRESS]` installs KERNEL on the installed Lenovo with `bootctl kernel`, boots it once as a trial and commits it once machine_identity.sh finds it running from the candidate slot. Before it writes, the machine must report the Lenovo's station address, a boot from a slot and no trial armed. A person runs it to try a kernel alone; a phase's release installs the whole system with `flow/release.sh`.
* [machine_identity.sh](dev/machine_identity.sh) runs before every measurement, as `RACH2_MEASURE_USER`, root by default. It lets the measurement go on only when the machine booted the slot `RACH2_MEASURE_SLOT` gives, `candidate` or `fallback`, has no trial armed, and has the host file `RACH2_MEASURE_KERNEL` in that slot by SHA-256, and logs what the machine reported.
* `machine_load.sh KEY ADDRESS SESSIONS SECONDS [DIR]` starts SESSIONS sessions a second apart, since Dropbear admits five unauthenticated connections from one address at a time. Each runs [machine_load_session.sh](dev/machine_load_session.sh): it copies `/src/rach2` under `/tmp`, builds it with the staged TinyCC and pdpmake for SECONDS of the machine's clock, removes the copy, and prints `SESSION N builds B failed F before-deadline W late L`. `RACH2_LOAD_USER` selects the account.
* [machine_net.c](dev/machine_net.c) times a TCP transfer with the same code on the host, where `make` builds `build/tools/dev/machine_net`, and on Rach2, where `tcc -static` builds it: `local MIB WRITE-BYTES TIMEOUT` on loopback port 27157, or `receive PORT MIB TIMEOUT` and `send ADDRESS PORT MIB WRITE-BYTES` on two machines, each stopped at 180 seconds.
* `machine_net_in.sh KEY ADDRESS REMOTE-PROGRAM SENDER MIB WRITE-BYTES TIMEOUT DIR` sends one transfer to the machine's port 27158 and keeps both ends' logs, the programs' digests and the interrupt counts under DIR. `RACH2_NET_USER` selects the account and `RACH2_NET_KNOWN` a known-hosts file.
* `poll_kernels.sh` builds the current kernel and one whose `poll` removes its waiters before the halt, in a private copy of the tree, and prints each as `RACH2_MEASURE_KERNEL=PATH`. It needs `build/tools/inspect/elfcheck`.

An interval read on the machine can be short by timer ticks lost while interrupts were masked, which inflates a rate. For an independent bound, time the whole command with the host's `/usr/bin/time -p`, which also counts SSH and setup. Try 1 MiB before a long transfer.

The recovery grow writes a seed root to the installed disk, times `growroot --measure` growing it, and restores the disk. On the host:

    sh tools/dev/machine_grow_plan.sh SEED DISK-SECTORS SERIAL DISK-ID DIRECTORY

SEED is a clean ext2 root such as `build/images/rach2-metal-disk.ext2`. DISK-ID is what `diskctl id` prints on the machine: an MBR's signature, or the disk GUID of the GUID table that a machine installed from the sealed disk has. The disk must have 64 MiB partitions at sectors 2048 and 133120 and the root from sector 266240 to the disk's end, or on a GUID table to the backup table in its last 33 sectors, with the BIOS boot partition from sector 34; `save` and `grow` refuse any other layout. On a GUID table the saved ranges also include the primary table and the backup, and `grow` writes its temporary table with `diskctl shrink`. The new DIRECTORY receives the plan, the sector ranges that the seed's write and the grow change, as the host's [growset](../man/man8/growset.8) computes them, the seed's digest, a copy of `machine_grow.sh`, and the digests of the recovery programs of `ARCH`, i686 by default. In recovery, as root, with the plan copied under `/tmp`:

    sh /tmp/grow-plan/machine_grow.sh save|grow|restore DISK STORE /tmp/grow-plan

STORE is an exFAT volume on another disk with the seed as `seed.ext2`; each action logs to a new `machine-grow.*` directory there, and recomputes the ranges before it writes. `save` copies the ranges and the 64 MiB boot partition to `STORE/saved`; check its `SHA256SUMS` on the host and return that file as `saved/host.sha256`, which `grow` and `restore` require. `grow` unmounts the store while it measures, so close every file on it first. `restore` puts everything back, repeatable after an interruption or power loss.

The install stick's 256 MiB of free space is too little for a full grow. Build the grow's stick with [mkinstallstick.sh](image/mkinstallstick.sh), a tar of the plan as EXTRA, and room for the seed and the saved copy as FREE-MIB, at most 8192; the builder makes the whole volume in host memory. `tests/run grow` rehearses the procedure on a 64 MiB root, on an MBR and on a GUID table, with each action cut part way and run again, and with a full RAM root; run that before a large build.

## Building

The C programs are compiled on the host with the rule text of [`mk/host.mk`](../mk/Readme.md), under `-Werror`, into `build/tools/SUBDIR/NAME`, and serve both architectures. `make` builds them all as `host-tools`, a prerequisite of `all`, and `make print-host-tools` prints their paths. A script that runs a checker names its built path, and the root Makefile builds the program before the rule that runs it. A script that may run outside make asks for the program with `make -C` and its path, and never compiles it by hand: make would read a hand-compiled binary as current and skip its `-Werror` build. The scripts need no build.

## Tests

The native host cases run prepared C controllers and fixtures. They cover build rules, source-check scope, image publication and recovery, worker and manager behavior, deployment and CI decisions. A product written in shell or Python runs in its declared GNU helper when that product is being tested; C creates its fixtures and judges the results. The former shell/Python test drivers remain reference or compatibility interfaces. [The host cases](../tests/cases/host/Readme.md) describe placement, inventories, instrumentation and cleanup.

Image and machine cases check the artifacts these tools produce with the independent file-system tools in their declared Rach2 helpers. Mtools and e2fsprogs use the small image helper; exfatprogs and dosfstools use the prepared GNU recovery helper through the compiled `fstool` dispatcher. [The system cases](../tests/system/Readme.md) describe those checks, and [etude's tests](etude/Readme.md#tests) describe the runner fixtures. Source and manual checks run during preparation as described above. No prepared runtime result substitutes for a check of a product's behavior.

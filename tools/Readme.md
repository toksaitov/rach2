# Build and verification tools

The scripts under `tools/` are grouped by role: `setup/` prepares and reports on a machine, `verify/` implements the style suite, `inspect/` validates built artifacts, `image/` constructs disks and ISOs, and `dev/` holds developer utilities. The root Readme documents the public interface. The Makefile supplies prerequisites and arguments that are easy to omit when calling a script directly. The test runner, suites, capture checkers, and fixtures live under [`tests/system/`](../tests/system/Readme.md).

`dev/machine_load.sh KEY ADDRESS SESSIONS SECONDS [DIR]` runs milestone 46's load row against an installed machine over SSH: each session copies the kernel tree and builds it with the staged TinyCC and pdpmake for the time given, and the sessions start a second apart because Dropbear allows five unauthenticated connections from one address at a time and twenty started together get five. `RACH2_LOAD_USER` selects the SSH account, root by default; the load needs no root privilege. The script creates and prints a private directory owned by that account under `/tmp`, and leaves its copies there. Each session's whole output is kept in a separate host log. The caller watches those logs while the run is active. The driver sends `machine_load_session.sh` over SSH stdin. Each window starts after its own source copy; its clock is `/proc/uptime`, which counts delivered ticks and can lose ticks while interrupts are masked. Every build records start, finish and status. `builds` counts all successful completions; `before-deadline` counts only finishes strictly before that session's deadline, and `late` counts finishes at or after it. These separate windows do not measure completions in one common wall-clock hour. Before any session starts, `dev/machine_identity.sh` must find the machine running the slot and the kernel named in `RACH2_MEASURE_SLOT` and `RACH2_MEASURE_KERNEL`. It logs in as `RACH2_MEASURE_USER`, root by default, because it reads the boot partition; the load account may be another. Its report is kept in `DIR/load-PID-identity.log`.

`dev/machine_net.c` is the common TCP sender and receiver for the host and Rach2. `make` builds it as `build/tools/dev/machine_net`; on Rach2 build it with `tcc -static`. `local MIB WRITE-BYTES TIMEOUT` forks the sender on loopback using port 27157, which must be free; Rach2 requires an explicit port for a TCP listener. `receive PORT MIB TIMEOUT` and `send ADDRESS PORT MIB WRITE-BYTES` run the ends on separate machines. A timeout of zero passes no timeout to `select`; a positive value is seconds. The receiver starts its monotonic clock after accept and releases the sender with one byte, so the measurement includes that exchange and the data transfer but excludes time spent starting the commands. It reports the exact byte count, microseconds and number of reads, and requires EOF at the declared byte count. The result labels its clock: on Rach2, `CLOCK_MONOTONIC` counts delivered 10 ms timer ticks. Masked interrupts can lose ticks and shorten the reported interval, inflating a calculated rate; zero readings support no rate. The native host build uses its host's monotonic clock. Each run is bounded at 180 seconds. Start with 1 MiB before measuring 256 MiB. `WRITE-BYTES` is the sender's write size and `TIMEOUT` the receiver's `select` timeout in seconds.

`sh dev/poll_kernels.sh` builds the current kernel and a copy whose poll core removes its waiters before the halt. Both retain entry 55's network interrupt repair and entry 57's loopback drain. It records the one source difference, the build configurations and SHA-256 hashes, removes the private poll object and kernel before each build, requires the changed kernel to differ, then restores and rebuilds the source and requires the restored binary to match the first. All sources and artifacts remain in the private directory it prints. This prepares entry 54's comparison; it does not install a kernel or start a measurement. `build/tests/system/runutil` and `build/tools/inspect/elfcheck` must already be built. It ends by printing each kernel's path as `RACH2_MEASURE_KERNEL=PATH`, the name the identity check takes. Its source change matches the poll core's code lines alone, so a comment above them does not stop it.

`dev/machine_net_in.sh KEY ADDRESS REMOTE-PROGRAM SENDER MIB WRITE-BYTES TIMEOUT DIR` runs one inbound TCP measurement on port 27158. `RACH2_NET_USER` selects the SSH account, root by default. `RACH2_NET_KNOWN` selects an existing scratch known-hosts file; otherwise the script creates one in its log directory and deletes that default after its final cleanup connection on success, failure or interruption. A supplied file remains caller-owned. Both the measurement and cleanup connections use it with `StrictHostKeyChecking=accept-new`. The remote program and host sender are builds of `machine_net.c`. The script waits for the receiver's listening message before sending, requires both processes to finish successfully, and keeps their complete logs, binary hashes and interrupt counters under a new directory in `DIR`. Run a 1 MiB case first. Before the transfer, `dev/machine_identity.sh` must find the machine running the slot and the kernel named in `RACH2_MEASURE_SLOT` and `RACH2_MEASURE_KERNEL`, asked as `RACH2_MEASURE_USER`, root by default; its report is kept as `identity.log` beside the transfer's logs, so each measurement names the kernel that answered it.

`dev/machine_identity.sh LOG SSH-COMMAND...` is that check; SSH-COMMAND is the driver's own ssh invocation, to which it appends one remote command. The booted slot is `rach2.slot=` on the machine's `/proc/cmdline`. The kernel is the SHA-256 of the booted slot's first bytes, as many as the named file holds, read from `/dev/bootpart` at the extent `bootctl status` prints; the slot's sectors are read as one run, which is how the image tools write a slot. It refuses with status 1 another slot, no slot, a trial armed in the boot environment, since the slot then holds a kernel the boot did not load, and a digest that is not the named file's; a caller that names no slot or no readable kernel file is refused with status 2. The machine's report, the names given and the verdict go to LOG. Two rewrites of the booted slot leave no mark the check can see: `bootctl fallback` on a machine booted from the fallback slot, and `bootctl kernel` on one booted from the candidate with its trial dropped by `bootctl cancel`.

For an independent clock check during a future authorized sitting, run the whole command under the host's `/usr/bin/time -p`. For loopback, time the SSH invocation of `machine-net local 256 65536 10`; for inbound, time the complete `machine_net_in.sh` invocation, which waits for both ends. Preserve `real`, the exit status and both program logs together. On success, the host interval encloses the receiver's transfer but also includes connection setup, SSH, the readiness wait and teardown. Bytes divided by that larger interval give an end-to-end rate, not the receiver's isolated rate; do not subtract a guessed overhead. Use 1 MiB first for correctness and longer transfers for the comparison. A shorter guest interval can reflect both excluded overhead and lost ticks, so these bounds alone cannot measure how many ticks were lost. The historical runs lack this independent timing and are not assigned one retrospectively.

`sh dev/machine_grow_plan.sh SEED DISK-SECTORS SERIAL MBR-ID DIRECTORY` prepares the recovery grow's saved ranges from a clean ext2 seed. The host and recovery builds of `growset` compile the same source, `utils/growset.c`. Its `--save` mode includes the complete seed overwrite and merges it with the later grow writes. `--ranges` emits only sector pairs for the machine-side comparison. Unsupported features, layouts and a seed length different from its block count are refused. The plan records the target serial, geometry, disk identifier and seed digest; `programs.sha256` includes the recovery range calculator.

`sh dev/machine_grow.sh save|grow|restore DISK STORE PLAN-DIRECTORY` runs as root in recovery after the owner approves the reported devices. Extract the plan and helper into `/tmp`; `STORE` must be an exFAT mount on another disk. The helper checks that mount before creating its private `machine-grow.*` work directory there, beside `saved`. It tests allocation of one MiB for work and logs before a target write; subsequent writes still check their results. Every action verifies the seed and recomputes the exact range list using the target's checked sector count before writing anything. `save` checks the original root, saves the ranges and complete 64 MiB boot partition under `saved.pending`, then compares both with fresh disk reads. Only a checked copy is published as `saved`. Preserve an interrupted pending directory under a new name before repeating save. Copy the published files to the host, verify `SHA256SUMS` there, and return that manifest as `saved/host.sha256` before either write action.

`grow` compares both disk extents again, checks that the store can be unmounted before any target write, prepares recovery as the saved default, writes and checks the temporary seed, unmounts the store and records the grow phases. While the store is unmounted, the helper captures at most 65537 bytes of output in process memory, with a final command-status record. After remounting, it saves `grow.log`; more than 64 KiB or a missing or failed status is an explicit failure. Measurement uses no RAM file and no backup-volume log write inside its counter interval. `restore` checks the serial and geometry even when the table is damaged, restores that table, repairs the boot partition, restores every range, compares the result and checks the root read-only. Boot repair uses `growboot` to read the verified `boot.img` without changing it and prepare only the 1024-byte environment in the work directory. All larger comparisons stream through `reflash --verify`, which requires the complete extent. It requires the saved 1024-byte environment to occupy one cluster and compares the live prefix, environment and suffix separately. A valid recovery default with no trial is preserved byte for byte; damaged parts are written from the backup and prepared environment and read back. A damaged live environment need not parse. Repeating restoration replays incomplete writes.

Command logs and `result.status` stay in the printed work directory on the store. `restore.log` appends every reflash completion; its size does not consume RAM-root space. Each logging pipeline checks the producer and the log writer independently. A failed write reports its path on stderr and on `/dev/console`, even if the caller redirected stderr into a full file. A range-calculation failure retains growset's own diagnostic and identifies `expected-ranges.txt`; output failure is never relabelled as unsupported geometry. A failed action returns nonzero and retains its work for diagnosis. Copy the work directories to the host before removing the store. The plan in RAM still disappears on power loss. After a lost session, boot USB recovery, identify the devices again, remount the store and re-extract `grow-tools.tar` before invoking restore directly. Keep the seed and both verified backups. The [milestone 50 procedure](../dev-log/50-shortcomings/recovery-grow.md) gives the commands and geometry requirements, and the two copies required before a Samsung write.

`make rach2-install-stick` builds a recovery ISO followed by an exFAT volume containing the sealed disk, `rach2-sealed.disk`, or `rach2-sealed-with-key.disk` in a tree with a recovery key, its length and SHA-256 manifest, and `rach2-metal-disk.ext2` for `rach2-install --update`. The volume adds 256 MiB to the two images' lengths for metadata and saved sectors. After metadata, it has room for copies of both 64 MiB boot and recovery partitions beside the images. It does not fill the physical stick or reserve space for a backup of a grown root. Check space for the actual save set before a write.

`image/mkinstallstick.sh` accepts `[EXTRA [FREE-MIB]]` after its six required arguments. The product rule supplies the root image as `EXTRA` and 256 as `FREE-MIB`; callers that omit them get no extra file and four MiB for metadata. `FREE-MIB` includes metadata, so check actual free space after staging additional files. The fixture builder allocates the whole exFAT volume in host memory. Prove the procedure with `RACH2_GROW_SMALL=1 tests/run grow` before building a larger recovery volume.

## Machine setup

To build and boot Rach2 a machine needs GNU Make, a host C compiler, the `i686-elf` freestanding cross toolchain, QEMU, `ssh-keygen`, e2fsprogs 1.43 or later, mandoc, which renders the manual pages the images stage, and the POSIX text utilities. The build finds `mke2fs`, `debugfs` and `e2fsck` on the path, under the Homebrew keg, which is never linked, or under `/sbin` and `/usr/sbin`, where Debian keeps them. To pass `tests/run style` it also needs cppcheck, ShellCheck, and clang-format. The suites that build a GRUB disk or a FAT volume need mtools, which `tests/registry` names for each of them; a plain `make` builds the three RAM images and reaches none of it. Nothing is fetched during a build: the six vendored projects are pinned tarballs already in the tree.

Install those, then run `sh tools/setup/doctor.sh`. It reports every tool in five groups and prints the install command for whatever is missing.

### macOS

Xcode's command line tools supply `make` and `cc`; Homebrew supplies the rest. Install Homebrew first if the machine has none, and run the `shellenv` line its installer prints, because it does not put `brew` on the path itself.

    xcode-select --install
    /bin/bash -c "$(curl -fsSL \
        https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
    eval "$(/opt/homebrew/bin/brew shellenv)"

    brew install i686-elf-gcc i686-elf-binutils qemu mtools e2fsprogs mandoc \
                 cppcheck shellcheck clang-format rsync

`ssh-keygen` ships with macOS. `xorriso` builds the ISOs (`make isos`) and the stick images made from them, which `tests/run usbdisk` boots, so a run of the whole set needs it. `pkg-config` with the `fuse-t` cask lets `make -C krffs mount` mount an image on the host, which no build or suite needs.

### Debian and Ubuntu

The archive has everything except the cross toolchain.

    sudo apt install build-essential curl qemu-system-x86 mtools e2fsprogs \
                     mandoc openssh-client cppcheck shellcheck clang-format

`xorriso` builds the ISOs and the stick images made from them, which `tests/run usbdisk` boots. `pkg-config` with `libfuse-dev` lets `make -C krffs mount` mount an image, which no build or suite needs.

No Debian package provides an `i686-elf` toolchain by that name, but the `i686-linux-gnu` cross compiler in the archive builds this tree: the kernel and the guest programs are freestanding, and the ported musl, BusyBox and Dropbear link against the libgcc it carries. The tree calls the tools by their `i686-elf-` names, so link them under those names on your path.

    sudo apt install gcc-i686-linux-gnu binutils-i686-linux-gnu
    mkdir -p "$HOME/bin"
    for t in ld ar objcopy strip nm objdump readelf as ranlib size strings; do
        ln -sf "/usr/bin/i686-linux-gnu-$t" "$HOME/bin/i686-elf-$t"
    done

The compiler itself is not linked but wrapped, because the archive's is a Linux-targeting GCC: it defines `__linux__`, compiles for PIE, adds the stack protector, control-flow protection, stack-clash probes and unwind tables, and sets `_FORTIFY_SOURCE`. A bare `i686-elf-gcc` does none of that, and the ports and the guest programs are written for the bare one: a `tcc` compiled for PIE and linked static reads its globals through a table the link never made, and faults at address 0x1c. `$HOME/bin/i686-elf-gcc` is this script:

    #!/bin/sh
    exec /usr/bin/i686-linux-gnu-gcc \
        -fno-pie -no-pie -fno-stack-protector -fcf-protection=none \
        -fno-stack-clash-protection -fno-asynchronous-unwind-tables \
        -fno-unwind-tables -U_FORTIFY_SOURCE -U__linux__ -U__gnu_linux__ -Ulinux \
        "$@"

The archive's version is the lower bound this tree supports: GCC 15.2 and binutils 2.46 on Ubuntu 26.04. Two defaults of that binutils are answered in the makefiles rather than the wrapper: the linker's `-z separate-code`, which would give the kernel a third `PT_LOAD` segment, and `--build-id`, whose note section would land on the `.text` of a program linked at a fixed address.

### The testing host

The suites, the sets and the analyses run on the testing host that `AGENTS.md` names, reached as `ssh testing`: Ubuntu 26.04 under WSL2 on a Windows machine with 32 threads and 200 GB of memory, with a copy of this tree at `/home/testing/rach2`. It is set up as any Debian or Ubuntu host above, with the analysers the audit milestone runs added:

    sudo apt install clang clang-tidy clang-tools sparse pmccabe mandoc xorriso

The ssh server on that machine answers in an MSYS shell, so anything meant for WSL starts through `wsl.exe`; `dev/testing.sh` does that for the sync and the run, and is the way to reach the copy. Its home directory is on WSL's own file system, not under `/mnt/c`, which is slow for a build.

The machine has `/dev/kvm`, since `nestedVirtualization=true` is set in the Windows user's `.wslconfig` and the account is in the `kvm` group, and the runner takes it when nothing says otherwise. `dev/testing.sh run` says otherwise, with `RACH2_QEMU_ACCEL=tcg`: that KVM is nested under Hyper-V, and the ATA driver polls a port after every sector it writes, each poll an exit through two hypervisors, so a 64 MiB write measured 236 s there and 25 s emulated, and the 4 KiB write rows outran the runner's silence limit. That is the host's setting, like its worker count, not the runner's rule.

The target prefix is not negotiable: `vendor/musl/build_libc.sh` configures with `CROSS_COMPILE=i686-elf-` and both `muslgcc` wrappers call `i686-elf-gcc` by name. A toolchain under that same command prefix works wherever it is installed, and so does the wrapped `i686-linux-gnu` toolchain described above.

### The two checkers

* `setup/preflight.sh` is the build's own cached tool check. `make` and
`tests/run` run it at each entry; it stats the recorded tool paths on a cache hit and repeats its compile probes only when the environment changed. A missing tool fails the build, named, before anything is compiled with the cross toolchain; a host tool may compile beside the check. `--report` prints one line per tool without caching.
* `setup/e2fsprogs_path.sh` is the one place the three e2fsprogs programs are
looked for off the path, sourced by `preflight.sh`, `doctor.sh` and `image/mkext2.sh`; it puts the first directory that has all three at the front, so that the three come from one installation.
* `setup/doctor.sh` is the wider machine report, in five tiers: what a build
and run need, which is everything `preflight.sh` requires plus QEMU; the three tools `tests/run style` refuses to start without; the three mtools commands the disk and FAT suites need; the optional `xorriso`, Docker (the `vendor/grub` regeneration procedure only), Git, and FUSE; and the judges, each tool's version beside the one `setup/judges` records from the testing host, a different version reported and not counted missing. It checks that tools run rather than that their names are present, probing `awk`, `sed`, and `ssh-keygen` by doing the work the build does with them, since none of the three accepts `--version` everywhere. For FUSE it runs `pkg-config --exists` for `fuse`, then for `fuse-t`.

## Working an installed machine from the host

The procedures a machine is installed and updated by are the manual's: `rach2-install(8)`, `recovery(7)`, `bootctl(8)`, `reflash(8)` and `disk(7)`. What is here is what the host does around them, and the machine's own address, geometry and offsets are in the milestone records under `dev-log/`.

Every root has an SSH host key of its own, generated at boot for the RAM roots, so a fresh known-hosts file per system is the rule:

    ssh -i krffs/rach2_demo_ed25519 -o UserKnownHostsFile=/tmp/k-NAME \
        -o StrictHostKeyChecking=accept-new root@ADDRESS

Write `-i KEY` before the destination: after it, ssh reads the two words as part of the remote command, offers the default identities instead, and the machine refuses a login that looks correct. Root logs in by key alone on an image built here, since `init` starts the server with `-g`, or OpenSSH's with `PermitRootLogin prohibit-password`, unless `/etc/rach2/sshd.conf` says `root-password-login yes`, which the installer writes on a machine it installs; `su` from the unprivileged account is the other way in. Dropbear has no sftp server, so on its roots a file goes over with `ssh ... 'cat > /tmp/f' < f` and comes back with `ssh ... 'cat /tmp/f' > f`; the GNU system's root has OpenSSH's, for `scp` and `sftp`.

Check the credentials before writing a root. The image trusts `krffs/authorized_keys`, which `krffs/gen_demo_key.sh` composes from the demo public key and an optional `krffs/authorized_keys.extra`. The private key used to log in must be the pair of one of those, and a copy carried between hosts can be older than the file it is meant to match:

    ssh-keygen -y -f krffs/rach2_demo_ed25519 | cut -d' ' -f2
    cut -d' ' -f2 krffs/authorized_keys

A root written with keys whose private halves are on another machine is then reached through the console, through an ordinary account and `su`, through a password login where `/etc/rach2/sshd.conf` says `root-password-login yes`, which the installer writes, or from recovery.

An install stick built on another host must trust the operator's key before it is written. Copy only the operator's `.pub` file to the build host, then run these as two commands in that tree:

```sh
make recovery-key RECOVERY_EXTRA_KEYS=/path/operator.pub
make rach2-install-stick
```

The first command replaces `krffs/recovery_authorized_keys` with the builder's root keys and the supplied public keys. With no `RECOVERY_EXTRA_KEYS`, it preserves any existing recovery list. The second builds `build/images/rach2-install-stick-with-key.img`; the separate command is required because Make chooses keyed artifact names at startup. The operator logs in with the matching private key kept on the operator's host. Repeat the first command with the intended public file when that list changes. `make no-recovery-key` removes recovery access and its built images, the sealed and GRUB disks under both names among them. This changes recovery access only; installed accounts follow the installer's account procedure. `make release` builds the install stick and the recovery ISO for a person who is to receive them, and it and `RELEASE=1` are refused, before anything is built, in a tree that has `krffs/recovery_authorized_keys`; `make no-recovery-key` makes a tree that can build a release.

With `rach2.netconsole` on the boot line, the kernel broadcasts its log records in Ethernet frames of type `0x88b5`. `sudo tcpdump -i en0 -U 'ether proto 0x88b5' -w FILE` keeps it, which is the only record of a panic on a machine with no serial port: the screen shows one line and the boot log is in memory the restart clears.

The recovery stick is `build/images/rach2-recovery-stick.img` written to the whole stick, its second partition then formatted as a save volume; the boot test is `build/images/rach2-stick.img` written the same way. `tests/system/accept/metal_accept.sh HOST [PORT] [STICK-SERIAL]` is the scripted half of acceptance, described in [the system tests' Readme](../tests/system/Readme.md).

## `tests/run style`

`verify/check.sh` runs a preflight followed by twenty-two numbered checks:

* Build the kernel with warnings treated as errors.
* Run scoped cppcheck with `verify/cppcheck.suppress`, over the kernel at c89 and the host programs at c99, judged by the cppcheck version `setup/judges` records; another version reports what it found and decides nothing, since the findings change between majors in both directions.
* Run ShellCheck on every in-house shell script, the list `verify/scripts.sh` prints. SC1091 is off for all of them; the run scripts under `rach2/` and the build scripts at `krffs/*.sh` also waive SC2086 and SC2034.
* Check source conventions such as ASCII text, C comment form, header guards, marked idle waits, group kills that dash accepts, and the `finished` flag that a script under `tools/` or `krffs/`, `tests/system/manual_probes.sh` or `tests/system/accept/su_command.sh` keeps when it combines `set -e`, `set -u` and an EXIT trap, since bash 3.2 lets such a script exit 0 when an unset name stops it.
* Require clang-format on every in-house C file, judged by the clang-format version `setup/judges` records; another version reports how many files it would change and decides nothing. The reformat commits are in `verify/blame-ignore-revs`, and `git config blame.ignoreRevsFile tools/verify/blame-ignore-revs`, which `.claude/settings.json` runs when a Claude Code session starts, makes blame look through them.
* Link a fresh musl program and inspect its ELF ABI.
* Check the shared source manifests and the guest build descriptions.
* Run the mechanical text, comment-width, and banned-prose checks.
* Check every kernel message against the conversions its formatter has.
* Run the probe scorer's self-test.
* Run the set-id checker's self-test and manifest sweep.
* Build the KRFFS host tools and test deterministic image staging.
* Run the ELF, configuration, and compilation-database checker self-tests, `tests/system/build_rules_test.sh`, and `tests/system/style_scope_test.sh`, which runs `verify/scripts.sh` and `verify/textcheck.sh` over a private tree and requires each kind of file they claim to read to be read.
* Check the dev-log index against the finished milestone directories.
* Check `tests/registry` against `tests/system/suites.mk`: every suite has a target and every target is a suite.
* Check that every product a `run-` target names is built by `prepare-all`.
* Check the suites' waits and criteria with `verify/suitecheck.sh`: no `sleep` for a number of seconds, no `wait=` harness step, no typed line longer than the console keeps, no upper bound on a duration in a probe, except an interval marked with a reason that `tests/system/intervals` lists.
* Check the manual against the machine with `verify/mancheck.c`: a page or an alias for every staged program, applet and registered call, every page lint-clean, the recovery pages staged.
* Run clang's positive warning list over the kernel, judged by the clang version `setup/judges` records.
* Run sparse over the kernel with `__CHECKER__` defined, so the `__user` address-space annotations are checked; skipped where sparse is absent.
* Check every Markdown link in the in-house documents with `verify/linkcheck.sh`: the target is a file that is there, and an anchor names a heading that is in it.
* Check function sizes with `verify/sizecheck.c` over every in-house C file: at most 100 lines in a body, 6 parameters, nesting 4, and cyclomatic complexity 25 as `pmccabe` counts it, judged against `verify/sizes.reasons`. Without `pmccabe` the three measures the checker takes itself are judged and the complexity waits for the testing host.

The supporting files under `verify/` have narrower jobs:

* `probecheck.sh` requires each built root or musl probe to appear in the default runner, `tests/probe-suites`, or `tests/probe-helpers`. The style suite runs it and `tests/system/probecheck_test.sh`.
* `check.sh` creates a private directory under `${TMPDIR:-/tmp}`, prints its path and retains its logs. `tests/system/verify_temp_test.sh` executes its directory setup and write statements against planted symlinks in an isolated temporary directory.
* `tests/system/build_inputs_test.sh`, run by the style suite, builds utilities, `dnstest` and a kernel against private copies of link inputs. Each changed library or startup object must relink the programs with its new marker value; a linker-script edit must produce its new symbol in the validated kernel. The test uses distinct future timestamps so it needs no clock delay.
* `check_sources.sh` compares `C_SRC` in `rach2/sources.mk` with `kernel.c` and the C files below `rach2/sys/`. `tests/system/build_rules_test.sh`, run by the style suite, requires it to name a source missing from the list and one missing from the disk.
* `guestcheck.c` checks five contracts: each component's host and guest builds derive from its shared source manifest (`rach2/sources.mk`, `utils/programs.mk`, `ish/sources.mk`), the kernel response file and link line, the utility program-to-source map, the guest file-descriptor and command-size limits, and the three source trees staged under `/src`.
* `asciiscan.c` reports every line holding a byte outside tab, newline, carriage return, and the printable range 0x20 through 0x7e, which is the set the text checks enforce. `make` builds it as `build/tools/verify/asciiscan`, and `textcheck.sh` runs it over the files it checks.
* `sha256.c` prints the SHA-256 digest of each file it is given. The vendor builds refuse a tarball whose digest is wrong and the suites compare staged artifacts by digest, so this is plain C compiled on first use rather than a dependency on `sha256sum`.
* `fmtcheck.sh` reads the text inside every `klog`, `console_printf` and `k_printf` call and refuses a conversion `k_vprintf` does not have. The formatter takes `%d %b %o %x %X %s %c %%`, each with an optional `0` flag and one digit of width. It writes an unknown conversion as its letter alone and consumes no argument, so every field after it in that message is read one slot early: the laptop printed `audio: not driven: 8086:a0c at 02x:02x.0` from `%x:%x at %02x:%02x.%d`, with three of its five fields wrong.

* `textcheck.sh` checks ASCII, prose uses of spaced `--`, Markdown bullet form, and development-phase tags. Its default Markdown scope includes root documents and documents below `rach2/`, `ish/`, `utils/`, `tests/`, `krffs/`, `tools/`, `mk/`, and `vendor/`. It excludes `dev-log/` and all of `ports/doom/`. Beside the Markdown it reads the C and headers, the assembly, the linker script, the awk checkers and the C fragments a test includes, the shell scripts `scripts.sh` lists, the make files, the Python tools, and the configuration files: the editor and formatter settings, the ignore lists, the manifests, the checkers' lists and reasons, the GRUB and BusyBox configurations, the patch series, and the tree's other text files. A spaced `--` on any line of a configuration file is a finding.
* `scripts.sh` prints every in-house shell script, one path a line: each `.sh` file, the scripts the images carry, which end in `.script`, and each file with no suffix whose first line runs a shell, such as `tests/run` and the `muslgcc` wrappers. It leaves out the extracted vendor trees, musl's install, the Doom engine's sources, and `krffs/vendor` and `krffs/vs-dokany`. The ShellCheck step runs over the list and `textcheck.sh` reads it.
* `prosecheck.c` holds the prose rules. `columns` checks 80-column comment wrapping in the in-house C, shell, Make, and Python files, including the project glue under `ports/doom/` and excluding `ports/doom/src/`. `banned` checks the mechanically prohibited vocabulary in comments, messages, and Markdown; its default scope is the root documents and the in-house source roots, including the Doom glue but excluding `vendor/` and `dev-log/`, and a path argument checks a file outside that default. `count` reports the word and phrase totals `prose_report.sh` tabulates, and `devlog` requires the dev-log index to name every finished milestone once, in directory order, and to omit plan-only milestones (it accepts `Readme.md` and milestone 6's `results.md` as completion records).
* `prose_report.sh` compares watched phrase rates with the pinned upstream corpus without failing the build; `--baseline` and `--fixture` compare with the committed records or rewrite them.
* `prose_baseline.txt` records project phrase counts for `prose_report.sh`; `prose_upstream.txt` records counts from the pinned upstream tarballs and Doom sources. They are measurements, not pass limits.
* `check_repro.sh` stages the same scratch manifest twice with the real KRFFS tools, requires identical image bytes, and checks that `exec-dir` and `tree` entries were stored in name order with the fixed staged instant, reading the node inventory through `setidcheck --nodes`.
* `cppcheck.suppress` contains the project-wide and path-scoped cppcheck exceptions read by `check.sh`.
* `sizecheck.c` measures every function's body lines, parameters and nesting from the source in the house format, reads the complexity from a `pmccabe` table when given one, and judges the four against limits and a reasons file. `--report` prints every function's measures.
* `linkcheck.sh` reads the `[text](target)` links of the in-house Markdown, skipping URLs, a bare anchor and an anchor of the form `L120`, which names a line. `dev-log/` is excluded: those records are history, and a path inside one is written as the repository sees it rather than as a link from that directory.
* `sizes.reasons` lists every function kept over a limit, one line each, `FILE:FUNCTION MEASURE VALUE REASON`: the value is the ceiling the function may not grow past, and an entry whose function is back within the limit fails the check as stale, so the file only shrinks.

## Artifact and configuration checkers

The inspectors under `inspect/` validate built artifacts; the validation stamps in the root Makefile re-run them when a checker or its artifact changes.

* `elfcheck.c` is the ELF validator. Without options it judges user executables against both the kernel loader and the project's static-executable policy; `make check-tcc` and `make check-pdpmake` use that form. `--kernel` validates a kernel ELF, its Multiboot header, its two load segments, its entry point, and its image end, requiring GNU ld symbols unless `--tcc` accepts the symbol-free TinyCC layout; `rach2/Makefile` runs it on every kernel link. `--selftest` runs both profiles' refusal batteries.
* `check_link.sh` uses `i686-elf-nm` to require that the libraries and startup objects staged for TinyCC leave no required symbol undefined. `vendor/tcc/build_tcc.sh` runs it.
* `setidcheck.c` has four related checks: manifest declarations, the resulting image nodes, the two BusyBox applet tables and resolved configs, and the strict and permissive init binaries. Its declarations live in `setid.allow` beside it; a `trusted overlay` declaration names a file a manifest's overlay program installs, as the GNU root's `install_root.sh` installs OpenSSH, which only the image check sees, and which must be a regular file with the declared mode and owner under directories only root may write. `tests/run style` runs its self-test and manifest sweep; `krffs/mkimage.sh` and `krffs/mkdisk.sh` run the image check; `make check-setid` runs the manifest, BusyBox, and init checks. `--free` and `--nodes` read a region's free bytes and node inventory for the suites. `--ext2 FILE --manifest PATH` inventories an ext2 image through a small read-only reader of its own, sharing nothing with the kernel's driver, which accepts exactly the profile `mkext2.sh` writes and refuses any other feature, any block outside the volume or inside its tables, any malformed directory entry, any inode it cannot place and a file of more than 512 MiB, about twice the largest any image stages, so that an image the guard cannot read is an image the build rejects; it lists every node reached from the root, the root itself included, with a second name for one inode as a node of its own, which is how a hard link to a set-id file meets the policy as an undeclared path, and a declared set-id entry must be a regular file, so a link or a device under a declared name is a finding. `--nodes --ext2 FILE` lists what it read. The self-test builds its ext2 fixtures with the host's `mke2fs` and `debugfs` and judges the reader against them.
* `binfind.c` answers whether a file contains a byte string, and can replace one in place. The TinyCC policy check reads the shipped compiler's four refusal diagnostics out of the binary this way, and the disk-policy and recovery checks and the menu suite use the same search. It replaces `strings` piped to `grep`, which put another host tool in the required set for one question.
* `check_diskpolicy.sh` requires a kernel to contain exactly one of the read-only and read-write policy banners. `check_recovery.sh` does the same for ordinary and recovery disk authority. These checks detect a mis-built artifact; the behavioral suites test actual disk writes.
* `cfgcheck.c` checks the two configuration files a sealed disk depends on. `grubembed` requires exactly four commands in `image/grub-embed.cfg`, in order: `search --no-floppy --label RACH2BOOT --set=root`, `configfile ($root)/boot/grub/grub.cfg`, `search --no-floppy --label RACH2RECOV --set=root`, and `configfile ($root)/boot/grub/recovery.cfg`. Comments and blank lines are allowed. Both GRUB core builders use this configuration. `sealednet` checks that the sealed disk's address, prefix, mask, gateway, and recovery fallback script describe one valid network configuration. The checker's self-test has 24 cases.

## The commit-msg hook

`git-hooks/commit-msg` refuses a commit message with an attribution line, which the Git section of `AGENTS.md` forbids: a line that starts with `Co-Authored-By:`, `Claude-Session:` or `Signed-off-by:` in any letter case, a line that starts with "Generated with Claude Code", after at most one emoji or other run of bytes outside printable ASCII, or a trailer whose value ends with `<noreply@anthropic.com>`. It prints the first such line and its number. Every pattern starts in the first column, so a sentence that only mentions a trailer passes, and so does the diff that `git commit -v` adds, whose added, removed and context lines start with +, - or a space. `git config core.hooksPath tools/git-hooks` turns the hook on in a clone. `.claude/settings.json` runs that command when a Claude Code session starts, and it also turns off the attribution Claude Code adds by default. `tests/system/commit_msg_test.sh`, which `tests/run host` runs, tests the hook.

## The testing host and the clangd database

`dev/testing.sh sync | run COMMAND... | get PATH... | sh` puts this tree on the testing host and runs a command in the copy there. `sync` replaces `/home/testing/rach2` with the tree here; `run` syncs and then runs COMMAND in the copy, passing it to the remote shell as one string; `get` copies each PATH of the copy, relative to it, to the same path here, compressed on the wire, which is how a product only the Linux host builds, the GNU system's ext2 root, reaches the Mac, where it is not sparse, since APFS keeps a hole only for a long run of zeros; `sh` opens a shell there. The suites and the analyses are run through it, as the `testing` skill in `.agents/skills/` says: `tools/dev/testing.sh run tests/run all`.

Of what `.gitignore` names, the sync sends one file: the shareware Doom data file, `ports/doom/doom1.wad`, which `ports/doom/fetch_wad.sh` downloads and the Doom suite stages. The rest, `build/`, the extracted vendor trees and their stamps, and the compilation database among it, stays as the host built it, so a run after a small edit rebuilds only what the edit touched. Files are compared by content, and rsync gives a file it transfers the time it arrives on the host, so make finds the file newer than the objects the host built from its older text. The receiving rsync starts inside WSL through `wsl.exe`, with `MSYS_NO_PATHCONV=1` so that the MSYS shell that answers ssh does not rewrite the destination path. The rsync on the Mac must be rsync 3 from Homebrew: macOS's openrsync deletes on the host what the filter excludes, the whole build and every vendor tree, and the script refuses to sync with it. The command, for a sync by hand from the top of the tree:

    rsync -a --no-times --checksum --delete \
        --filter='+ /ports/doom/doom1.wad' --filter=':- .gitignore' \
        --rsync-path='MSYS_NO_PATHCONV=1 wsl.exe -- rsync' \
        ./ testing:/home/testing/rach2/

`dev/gen_compile_commands.sh` builds the clangd database. Run it directly. It writes twelve databases under `build/compile_commands/`, one per unit, and joins them into `compile_commands.json` at the root: the four kernel variants, the tests, the shell, the utilities, Doom, the musl programs, the KRFFS tools with the mount tool, the host tools from a dry run of `print-host-tools`, and the host tests. It dry-runs each build, joins wrapped recipe lines, selects the compile commands by their first word, and publishes only after a line-by-line JSON validation. `verify/dbcheck.sh`, which step 7 of the style checks runs, then requires every in-house source to be in one database, or to be a fragment another source includes, or a fixture a test script compiles. Its `--selftest` exercises the join, selection, escaping, and validation stages on fixtures and runs under `tests/run style`. See [the shared Make documentation](../mk/Readme.md) for the clangd settings.

## GRUB and ISO builders

* `image/mkext2.sh [--overlay PROGRAM] MANIFEST OUTPUT [SIZE_MB] [BLOCKS_PER_GROUP]` builds an ext2 image from a manifest, 1 GiB and sparse by default: `stageimage.krffs --tree` materialises the manifest, the host's `mke2fs` formats the directory on the one profile the kernel's driver writes, revision 1, 4 KiB blocks, 128-byte inodes, `sparse_super`, `large_file`, `filetype` and `resize_inode` with every other feature named and off, the superblock is read back and refused outside that profile, `debugfs` sets each node's owner, mode, set-id bits and change time from the staged list, `e2fsck -fn` must find the volume clean, and `setidcheck --ext2` reads it with the guard's own reader. The times, the identifier and the directory hash seed are fixed, so one manifest makes one image, byte for byte. Every intermediate lives in a directory of the run's own beside the output, each program's exit status is checked, and the image is renamed into place only after every step passes. `make os-real-ext2` builds `build/images/os-real.ext2` this way. The optional group size is a multiple of eight from 256 through 32768 blocks and is checked in the finished superblock. The 64 MiB installer fixture uses 16384-block groups so its first group is complete, as `growset` requires; other callers retain mke2fs's default. `--overlay PROGRAM` runs PROGRAM with the staged directory after the manifest is staged and before the volume is formatted, for a system with what a manifest cannot say, such as links: `make os-real-gnu-ext2` installs the GNU layer this way with `vendor/gnu/install_root.sh`. A node the program added is root's, keeps its mode, and has the staged instant as its three times, as every node then has; a node the manifest staged keeps the owner and mode the manifest gives it, and one the program removed, or a name with a space, a quote or a backslash, which `debugfs` could not be given, fails the build. The same checks then run over the whole volume.
* `image/mkdisk_grub.sh [KERNEL [OUTPUT]]` builds a BIOS-bootable disk natively: mtools stage the FAT32 boot partition, `mkmbr.c` writes the partition table, and the pinned GRUB boot code embeds from [`vendor/grub/`](../vendor/grub/Readme.md). The disk has MBR identifier `1acef00d` and three partitions: the FAT32 boot partition, a FAT32 recovery partition, and the ext2 root the script requires, since both kernel entries name a root and a disk without one boots to nothing. Both entries select `rach2.root=MBRID=1acef00d,3 rach2.rootfstype=ext2`, so the fallback entry is the previous kernel on the same root and not another system; recovery boots a RAM root and mounts nothing from the disk. Every entry, including recovery, passes `rach2.boot=MBRID=1acef00d,1`. Partition 1 has FAT label `RACH2BOOT` and serial `1acef00d`; partition 2 has label `RACH2RECOV` and serial `1acef003`. Each menu entry finds its kernel's partition with `search --no-floppy --fs-uuid --set=root 1ACE-F00D`, or `1ACE-F003` for recovery. The separate recovery menu also begins with the recovery serial search. The script stages a fixed-size candidate kernel slot, a fallback kernel, a fixed-size menu slot, and a GRUB environment block, then validates the FAT chains and layout before publishing the image.
* `image/grubembed.c` writes the first 440 bytes of GRUB's MBR boot code and the core image, preserving the disk identifier at bytes 440 through 443 and the partition table. It patches the core-image pointers and rejects an image that does not fit the post-MBR gap or one tail slot.
* `image/mkstick.sh ISO OUT MKEXFATFIXTURE MKMBR STICKCHECK` builds the stick image `build/images/rach2-stick.img` (`make rach2-stick-image`): the metal hybrid ISO kept whole with its boot code, padded to the next 1 MiB boundary, followed by a 16 MiB exFAT volume built with its `PartitionOffset` at that sector, and two MBR entries written into the table bytes, the ISO's from sector 1 of type `0x17` and the volume's of type `0x07`. The firmware boots it from a USB socket and the kernel mounts the volume as `/dev/diskNp2`, the stick's number coming from `/proc/usb`.
* `image/stickcheck.c IMAGE VOLUME-START VOLUME-SECTORS` judges a stick image whole, linked with the kernel's own `mbr.c` so the partition rule is the kernel's: boot code and the signature in sector 0, exactly two partitions with none passed over, the volume as the second at its start and length on a 1 MiB boundary, the ISO's entry ending before it, an exFAT boot sector whose `PartitionOffset` and `VolumeLength` are the entry's, and an image that ends where the volume ends. `mkexfatfixture --check` walks the volume afterwards.
* `image/mkmbr.c [--lba] [--id HEX] DISK START:SIZE:TYPE[:boot|:logical] ...` writes an MBR with at most four primary and sixteen logical partitions. START and SIZE are whole MiB, or sectors with `--lba`; TYPE is hexadecimal and `:boot` sets the active flag. `--id HEX` writes the four-byte disk identifier at offset 440. A primary entry of type `05` or `0f` must precede any `:logical` arguments, which give each logical partition's own start and size. Their extended boot records are chained in argument order, numbered from 5: the first record is at the extended partition's start, and each later record is in the sector before its partition. `--list DISK` reads the four primary entries and prints each nonempty entry as `INDEX TYPE START SIZE`, with the type in hexadecimal and the extent in bytes.
* `image/mkgpt.c [--seed N] [--damage-primary] DISK START:SIZE:KIND[@INDEX][=LABEL] ...` writes a GUID partition table, a protective MBR, and the primary and backup headers and arrays with their checksums for the test suites' disks and sticks. It accepts at most fifteen partitions. START and SIZE are 512-byte sectors; KIND is `fat` or `data`; `@INDEX` selects a zero-based array position; and `=LABEL` supplies a name of at most 36 characters. Disk and partition GUIDs derive from the seed and entry index, allowing repeatable identities and cloned-table fixtures. `--damage-primary` writes the primary header with an incorrect checksum while leaving the backup valid. The tool prints `mkgpt: entry N guid TEXT` for each entry written.
* `image/mkgrubcore.sh {A|B} OUTPUT` verifies and hands out one of the two pinned marked core images the replacement suites install.
* `image/grub-embed.cfg` is the common embedded configuration. It searches for FAT label `RACH2BOOT` and opens `/boot/grub/grub.cfg` there. If that configuration call returns, it searches for `RACH2RECOV` and opens `/boot/grub/recovery.cfg` there. The disk builder puts `RACH2BOOT` on partition 1 and `RACH2RECOV` on partition 2; partition 3 is the ext2 root.
* `image/mkiso.sh` builds `test`, `os-simple`, `os-real`, `rach2-metal`, or `rach2-recovery` as a GRUB ISO with native `xorriso` and the pinned El Torito and hybrid images under [`vendor/grub/`](../vendor/grub/Readme.md). It checks the selected kernel's disk policy before staging it. The top-level `make isos` target builds all five. `rach2-recovery` is the recovery kernel and its RAM image on the same hybrid image, so a stick boots a machine into `reflash` without its disk; its boot line takes an address from DHCP.
* `image/ubuntu-image.txt` pins the Ubuntu container base by digest for the maintainer regeneration of the pinned GRUB artifacts (`vendor/grub/regen_grub.sh`); no build or suite uses a container.

`mkdisk_grub.sh` accepts ten `RACH2_DISK_*` settings. `RACH2_DISK_APPEND` gives every entry its common kernel arguments and `RACH2_DISK_DHCP_APPEND` its network tokens. `RACH2_DISK_BOOT_MB` and `RACH2_DISK_CLUSTER` set the FAT boot geometry. `RACH2_DISK_RECOVERY_MB`, `RACH2_DISK_RECOVERY_KERNEL` and `RACH2_DISK_RECOVERY_IMAGE` add recovery, which the root needs before it. `RACH2_DISK_EXT2_MB` and `RACH2_DISK_EXT2_IMAGE` are the root, the third partition, from an image `mkext2.sh` built, which must fit. `RACH2_DISK_HELLO` stages a file on each partition. The script fixes distinct FAT serials for the boot and recovery partitions and uses `SOURCE_DATE_EPOCH` for repeatable FAT metadata.

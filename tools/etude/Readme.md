# Etude

Etude is the test runner that replaces `tests/run`: a controller in hosted C99 that runs Rach2's tests on Linux, macOS, Windows and Rach2, and `etude-guest`, its helper inside Rach2. This directory implements the history store, the comparison of a run's times with that history, the executors of host processes on POSIX systems, Rach2 among them, and on Windows, the QEMU launcher on POSIX systems and the processor profiles of its machines, the ledger of a machine's resource claims and the admission of new ones, a worker's schedule of both architectures, the per-case watchdog and the supervisor that runs attempts under it on POSIX systems, shuffled and loaded repetitions with their load fixture, remote execution over frames, the store of immutable artifacts and the preparation graph that makes them on POSIX systems, `libetude-case`, the library of machine scenarios on POSIX systems, with the controller's side of `etude-guest` on a serial console, the driver of mutation proofs on POSIX systems, `etude-host`, which runs the host checks of `tests/run host` several at once, the cache of etude's versions on a machine, the deployment that makes a machine ready to run etude, and `etude-guest`, and defines the contracts the runner parts share: the case manifest, the report a test program writes, the results of an attempt, the frames between the controller and `etude-guest`, the invocation of a guest case, the interface of a machine scenario, the repetition record, the catalogue of a mutation proof, and the history of runs. Its validator, `casecheck`, checks manifests, reports and results against them.

## Use

`casecheck` is built by `make build/tools/etude/casecheck`, and `tests/run style` runs it through [`suitecheck.sh`](../verify/suitecheck.sh) over `tests/cases/*.json` and the examples here, and with `--selftest` over [its fixtures](fixtures/expect). Its commands:

    casecheck [-s SCHEMAS] [-r ROOT] manifest FILE...
    casecheck [-s SCHEMAS] [-r ROOT] timing FILE...
    casecheck [-s SCHEMAS] report [-f FEATURE=present|absent]... MANIFEST CASE ARCH PLACEMENT [OUTPUT]
    casecheck [-s SCHEMAS] results [-o OUTCOME] RESULTS MANIFEST...
    casecheck [-s SCHEMAS] schema NAME FILE...
    casecheck processor NAME
    casecheck --selftest DIR

`version.sh` builds etude's programs from the source of this tree, or of a commit, on a machine that has a POSIX sh, make, a C compiler and a SHA-256 tool and nothing of etude, unless that machine's cache has them built already:

    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] [-w] HOST
    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] -l
    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] -s

It reaches HOST through ssh(1), a Windows machine with `-w`; `-l` builds on this machine and `-s` prints the script it would send. `-c` gives the compiler's command line and `-C` the cache, each by default the platform's. It prints `etude-version: result: built KEY DIR` or `etude-version: result: reused KEY DIR`, DIR being the version's directory on the machine, whose `bin/` has the programs, and exits 0; it exits 1 when the version is neither built nor found.

`deploy.sh` makes a machine ready to run etude: it checks the machine for the prerequisites of [`tools/setup/prereqs`](../setup/prereqs) and installs those the account may, builds etude there with `version.sh`, prepares the ledger of the machine's claims, and records what the machine can do:

    sh tools/etude/deploy.sh [-n] [-r REV] [-c CC] [-C CACHE] [-S STATE] [-L LEDGER] [-w] HOST
    sh tools/etude/deploy.sh [-n] [-r REV] [-c CC] [-C CACHE] [-S STATE] [-L LEDGER] -l

HOST, `-w`, `-l`, `-r`, `-c` and `-C` are as for `version.sh`, and `-n` installs nothing. STATE is the directory of the machine's record and LEDGER the ledger's, each a path on the machine and by default the platform's (The machine record). The owner provides the SSH access. Deployment creates no account or key, changes no clone, deletes nothing of the machine's, writes no raw disk, restarts nothing and stops no test, and a run after one that finished or was cut short changes only what the earlier one left undone. It prints each step and its output, with the commands left for an administrator or a person at the machine, and last `etude-deploy: result: deployed KEY` and exits 0, or `etude-deploy: result: incomplete: WHY` and exits 1 when a prerequisite is missing or a step failed; it exits 2 on a wrong usage.

`etude-remote` is the responder of remote execution on Linux and macOS. `make build/tools/etude/etude-remote` builds it, and a cached version has it in its `bin/` on those systems. A controller runs it through ssh(1) without a terminal, as `ssh -T -o BatchMode=yes HOST DIR/bin/etude-remote --stdio -d STATE`:

    etude-remote --stdio -d DIR [-b BOOT] [-m MAXFRAME]

It speaks frames on its standard input and output until the controller's `bye` or the end of the connection, and keeps its ledgers, files and workspaces under DIR, which it makes when it is missing. BOOT is the token of the machine's boot, by default the digest of Linux's `boot_id` or of macOS's `kern.boottime`, and MAXFRAME the largest frame it takes, 65536 by default. Its diagnostics go to stderr. It exits 0 after a `bye`, 1 after the connection was lost or broken, and 2 for a wrong usage or a DIR it cannot use.

`etude-host` runs the host checks that [`tests/system/suites/host.sh`](../../tests/system/suites/host.sh) selects, several at once, on Linux and macOS. `make build/tools/etude/etude-host` builds it, and `tests/run host` runs it:

    etude-host [-j JOBS] -l LOGS -s SCRATCH SELECTION

SELECTION has one check a line, in six fields separated by tabs: the NAME of the check, of letters, digits, `_`, `.` and `-`; its bound in SECONDS, from 1 to 86400; its MODE, `shared`, or `alone` for a check that runs with no other beside it; the LABEL of its result line; the COMPILE command, which may be empty; and the RUN command. A line that is not a check, or a name given twice, refuses the whole selection before any check runs. JOBS is the most checks that run at once, by default the processors online. A step's output goes to `LOGS/NAME.clog` or `LOGS/NAME.rlog`, and each check has the empty directory `SCRATCH/NAME` as its `TMPDIR`. The program prints a line for each check as it ends, `PASS: LABEL` or `FAIL (WHY; see LOG): LABEL`, and a last line that counts them. It exits 0 when every check passed, 1 when one failed, 2 for a wrong usage or a refused selection, and 128 plus the signal after SIGTERM, SIGINT or SIGHUP, which end the running checks.

`manifest` checks each manifest's shape by its schema and then the rules below that relate its values: identities given once, alternatives that name declared assertions, an assertion's source that its domain has, a role that agrees with its end and its native plan, artifacts that `prepare` makes, processor profiles and the features they declare, bounds in order and inside the whole case's, the fixtures each placement has, and, with `-r`, a `where` that names a line of the tree at ROOT. `timing` checks them so and prints each line a timing assumption declares, as `FILE:LINE KIND CASE`. `report` judges a program's output as an executor will, by Report records, and prints each assertion the program must give, the report's state and the outcome; it exits 0 only for a pass. `results` checks each document of a JSON Lines file by Results, and with `-o` refuses an attempt whose assertions give another outcome than the one a history records. `schema` checks documents, or the lines of a `.jsonl` file, against `schemas/NAME.schema.json`. `processor` prints the QEMU `-cpu` value of a processor profile, for a script that boots QEMU itself. A finding goes to stderr as `casecheck: FILE:LINE: WHAT`; the status is 1 after one and 2 for a wrong usage or a file that cannot be read. SCHEMAS is `tools/etude/schemas` by default.

    etude-guest [--stdio] [--state DIR] [--stage DIR]... [--resend-ms N]

`etude-guest` takes the controller's frames on its standard input and sends its own on its standard output. Without `--stdio` they are the serial console, under QEMU: the kernel's debug shell starts it with `exec /etude-guest`, so that it is the boot's designated init, and it puts the console in raw mode. With `--stdio` they are the pipes of an SSH session on a running Rach2, and the program exits when the session ends. `--state` names the directory of its files, the stored files, the records and the workspaces, `$TMPDIR/etude-guest` or `/tmp/etude-guest` by default. Each `--stage` directory, eight at most, is searched for a file the controller would otherwise transfer. `--resend-ms` is the interval after which an unacknowledged frame on the serial console is sent again, and `alive` is repeated, 2000 by default. The exit status is 0 after `bye`, 1 when the connection was lost or the state could not be made, and 2 for a usage error.

A machine scenario is a program linked with `libetude-case`:

    SCENARIO INVOCATION

It runs one attempt of its case from the scenario invocation in the file INVOCATION, writes the case's report on its standard output and its diagnostics on its standard error, and exits 0 when its scenario passed, 1 when it did not, and 2 for a usage or an invocation, manifest or store it cannot use, as Machine scenarios says.

`history_compare` is built by `make build/tools/etude/history_compare`. It compares each case of a run with the earlier samples of the same case on the same machine and accelerator, and reports whether the run was slower:

    history_compare [-n] [-s SCHEMAS] [-b STORE] [-g REPO] [-o STREAM -i ID] RUN HISTORY...

RUN is the run compared and HISTORY the streams that hold it and its history. The command prints a report for each group of the run's items that share a case and a key, as The comparison says, and a last line with the count of each verdict. `-g` lists the commits in between with `git log` in the repository REPO; without it, the report gives the command. `-b` names the store, a directory of blobs each named by its SHA-256, where the report finds the plan's reproduce blob. `-o` appends a comparison record for each report to STREAM, a new stream with the identity ID, and keeps each report and the policy in the store. `-n` asks for a new baseline in place of an accepted one. A verdict, a regression included, does not change the status: it is 0 when every comparison was made, and 2 for a wrong usage, a stream that cannot be read, a record whose identity has two contents, a run without exactly one plan record, or a record or blob that cannot be written.

`etude-proof` is the driver of mutation proofs on Linux and macOS, built by `make build/tools/etude/etude-proof`. [`proof.sh`](proof.sh) builds it and runs it with this tree held, as a fault script holds it through `tests/system/runlock.sh`, so that no suite builds or boots the tree while a fault is in it:

    sh tools/etude/proof.sh [-w WORK] [-b STORE] [-k] PROOF [FAULT...]
    sh tools/etude/proof.sh --texts PROOF...
    etude-proof [-s SCHEMAS] [-t TREE] [-w WORK] [-b STORE] [-k] PROOF [FAULT...]
    etude-proof [-s SCHEMAS] [-t TREE] --texts PROOF...

PROOF is a catalogue, as Proofs says. Each FAULT named runs alone; with none, every fault runs. TREE is the tree whose sources the faults change and in whose root the commands run, `.` by default, and SCHEMAS is `TREE/tools/etude/schemas` by default. WORK is the work directory, which must not exist, by default a new `rach2-proof-NAME.XXXXXX` under `$TMPDIR` or `/tmp`; STORE is the artifact store, `WORK/store` by default; `-k` keeps the work after a pass. The driver prints a line for each phase, `etude-proof: NAME: PHASE: artifacts DIGEST...; WHAT`, each digest cut to twelve digits, and ends with `etude-proof: result: pass: NAME: N of M faults found; the sources and artifacts restored` or `etude-proof: result: fail: NAME: PHASE: WHY`, followed by `etude-proof: evidence: WORK`. It exits 0 for a proof that passed, 1 for one that failed, 2 for a wrong usage, a catalogue with findings, a tree that is not held or an error of the system, and 128 plus the signal's number after SIGHUP, SIGINT or SIGTERM, once it has ended what ran and restored the sources. `--texts` checks that each edit of each fault finds its text once in the tree's sources, writes nothing, and exits 0, 1 for an edit that does not, or 2; `tests/run style` runs it over `tests/proofs/*.json` and the example through [`faulttexts.sh`](../verify/faulttexts.sh).

### Cases

A case is one behavior under test, with its program, its requirements and its expected results. Each family of cases has one manifest, `tests/cases/FAMILY.json`. A case's `case_id` and each `assertion_id` are stable: a rename keeps them, and a change of meaning takes a new one. Assertion identities belong to their case, and those that begin with `etude.` belong to the executors. `units` lists the tests the case takes over from `tests/run`, by their names in the inventory of assertions under `dev-log/`.

The `domain` says where the program runs. The plan places each item of a run, and the history's `domain` records the placement:

| Domain | The program | Placements |
| --- | --- | --- |
| `host` | A program on the controller's host, or in its local tooling machine when `host_api` is `linux` and the host is not Linux | `host` |
| `guest` | A program on Rach2, a child of `etude-guest`, or the designated init when its role is `init` | `qemu`, in a fresh boot; `native`, on a running Rach2 over SSH, when `native.plan` is `native` |
| `machine` | A scenario on the host, linked with `libetude-case`, that boots Rach2 in QEMU and drives it | `qemu` |

`architectures` lists the Rach2 architectures whose build the case tests, and the plan selects one item for each. A host case whose program and inputs are the same for both lists `none`, and runs once.

A manifest gives no accelerator. The site profile of the run chooses TCG, KVM, WHPX or a native run, and a case's results do not depend on it; a case that needs a processor feature declares the feature, and its boot names a processor profile that declares it, as Processor profiles says. A case that passes under one accelerator and fails under another is redesigned, not left out.

`workload` fixes the work: the program's `arguments`; `inputs`, the sizes, paths and counts the program uses and its expected results depend on; `repetitions`, the items of the case in one run; and `seed`, given to the program as `ETUDE_SEED` in its environment when it is not null. A change to any of these is a change of workload, and starts a new baseline.

`requirements` gives what the case needs of the machine: `host_api` (`c`, hosted C alone; `posix`, a POSIX shell and utilities; `linux`, Linux interfaces), the host `tools` that `tools/setup/prereqs` installs, the processor `features` that must be `present` or `absent`, or may be `either`, and for a guest case the `qemu` profile of its boot: the kernel, an initial RAM image or none, the disks, the processor profile, the processors, the memory, the firmware, the devices and the boot options.

`execution` gives the program and its standard input as artifacts, its `role`, its privileges, the `isolation` of its host and QEMU placements, its children and its cleanup. Isolation is made of fixtures: `scratch` is a private directory under `TMPDIR`, and `disk` gives private writable copies of the named artifacts; a guest case under QEMU has a boot of its own. `children` is `none`, `reaped` (the program reaps every child on every path) or `reported` (it reports each child that may outlive it, and the executor ends those).

The role is `ordinary` when any process can be the case; `init` when the case must be the kernel's designated init, to which orphans go, whose exit the kernel records and whose death panics it; and `boot` when it needs a boot of its own: a kernel command line, a fresh kernel's state, a reset or a power-off. An `init` case runs under QEMU alone, and a `boot` case gets its boot from its QEMU profile.

A machine case also has `steps`, its stable operations, each in a stage and on one of its `machines`. A machine declares its QEMU profile, its console, whether it has a QMP monitor, and whether `etude-guest` runs in it.

`prepare` lists the artifacts the case needs, by the name it uses and the node of the preparation graph that makes them: a target in the architecture's build tree, `build` or `build/x86_64`, when `per_architecture` is true, and in `build` otherwise. Preparation makes every artifact before the case starts, and a cache keeps products of setup, never the operation under test.

`native` is the native plan: `native` with the fixtures that Native runs lists; `none` with the class and the reason a native run cannot test the case; or `host` for a host case. A machine case's plan is always `none`.

### Processor profiles

The `cpu` of a QEMU profile names a processor profile of [`processor.c`](processor.c): a QEMU processor model and the features it declares present or absent, by the names of QEMU and of Linux's `/proc/cpuinfo`. The launcher gives QEMU the model with `F=on` for each present feature, `F=off` for each absent one, and `enforce=on` when any is present, so that an accelerator that cannot give a present feature keeps QEMU from starting, which the launcher reports as QEMU's exit; an absent feature is off under every accelerator. A feature a profile does not declare is the accelerator's to give, and a case cannot depend on it.

| Profile | Model | Present | Absent |
| --- | --- | --- | --- |
| `max` | `max` | `rdrand`, `rdseed`, `xsave`, `avx` | |
| `max-nopdpe1gb` | `max` | `rdrand`, `rdseed`, `xsave`, `avx` | `pdpe1gb` |
| `qemu64` | `qemu64` | | `rdrand`, `rdseed`, `xsave`, `avx` |

A feature a case requires is one of those five. Its boot's profile declares it as the case requires it: present for `present`, absent for `absent`, and either way for `either`, so that under QEMU every group decided by the feature is decided. A native machine's features are its own, which the controller reads and gives the judge.

### Native runs

A native case runs on a Rach2 that is already up, such as the Lenovo, and gets no boot, command line or fresh kernel of its own. It runs as root, a child of `etude-guest` in a session and process group of its own, with no controlling terminal. Its descriptor 0 is `/dev/null` or a pipe of its declared input, 1 and 2 are pipes that `etude-guest` reads, and no other is open. Its working directory is its workspace, its umask 022, its signal mask empty and every disposition the default, and its environment has `PATH`, `HOME` set to the workspace, and `ETUDE_CASE` set to the case's identity. Its executables come from the candidate's build, copied into the workspace and checked by their digests. Each fixture is made before the case starts and removed after it ends, on every path:

* `workspace`: a directory of the case's own under `etude-guest`'s scratch directory, removed after a pass and kept after a failure. Every native case has one.
* `stage`: the companion files the case runs or reads, copied into the workspace with their modes, a set-id file owned by root.
* `volume`: a file system of type `krffs`, `ext2`, `vfat` or `exfat` from an image the preparation made, attached to a loop device the case reserves and mounted in the workspace.
* `tmpfs`: a tmpfs of the given size mounted in the workspace.
* `mountns`, `ipcns`, `utsns`: a mount, IPC or UTS namespace of the case's own.
* `root`: a private root of the given type on a volume, or in the workspace for `ext2-dir`, entered by `chroot` inside a mount namespace, for a case that uses fixed absolute paths or reads the type of `/`.
* `ids`: user and group ids that no account and no process of the machine has, given to the case as arguments.
* `pty`: a pseudo-terminal whose slave side is the case's descriptors 0 to 2 and controlling terminal; `etude-guest` keeps the master side, writes the declared input and reads the output.
* `ports`: local ports on 127.0.0.1 that `etude-guest` reserves, given as arguments; never port 22 or a service's port.
* `peer`: a network peer on the controller's side, or a second `etude-guest` process on 127.0.0.1, whose address and port are arguments.
* `log`: the kernel's records written while the case ran, read with `syslog(2)` action 3 before and after it. Other activity writes records among them, so a check may require a record, and may require the absence only of a panic, an oops or a record about the case's own processes.
* `alone`: no other native case runs on the machine meanwhile; its services still do.
* `console`: the machine's console and framebuffer, with `alone`, put back as they were found. A native run can type nothing at the console.

The class of a plan of `none` says why the case needs a machine of QEMU's: `QEMU`, for its monitor, its devices, its exit or its capture; `card`, for the driver of a device the native machine lacks; `init`; `boot`; `exhaustion`, for exhausting a resource of the whole machine; `count`, for judging a count of the whole machine that its services move; `feature`, for a processor feature or its absence; `layout`, for disks or controllers arranged its own way; `disk`, for a write to a disk node; `network`, for reconfiguring an interface or needing a network of its own; `image`, for a system image other than the installed one; `system`, for changing the installed system's configuration, accounts or services; `firmware`, for a memory map or firmware arrangement of its own; `input`, for keys, mouse reports or typed lines; and `architecture`, for i686 alone on an x86-64 machine.

### Assertions and branches

Each assertion says what it `checks` and its `source`: `program` for a report record of the case's program, `scenario` for a machine scenario's call, and `executor` for a kernel record that the executor finds on the console under QEMU, or with the `log` fixture natively; such an assertion gives the `record`. `where` may give the file and line of the check.

An executor adds these assertions to a case:

* `etude.termination`: the case ended as `termination` expects. The ends are `exited` and `signaled` for an ordinary process, `init_exited` and `init_killed` for the designated init, by the kernel's record that hands the debug shell back, `panic`, `reset` and `shutdown` for a machine, and `halted` for a machine whose processors are all halted with interrupts off. A value is the exit status or the signal, and the ends of a machine have none.
* `etude.kernel`, under QEMU, and natively with `log`: no panic, oops or fault of the kernel appeared, unless the termination expects a panic. A panic fails it whatever the program reported.
* `etude.report`, when an assertion's source is the program: it passes when the report is complete, as Report records says, fails when it is invalid, and is missing when it is truncated or absent, since the program then did not finish.

A branch group says that one of its alternatives runs and the others cannot, such as the trusted and the fail-closed paths of `rngprobe`. The assertions of the chosen alternative are required, and those of the others are not. A group decided by `features` takes the alternative whose `when` is `present` when any of the features is present on the processor, and the one whose `when` is `absent` when none is. Under QEMU the processor is the boot's processor profile; natively it is the machine's, whose features `casecheck report` takes as `-f NAME=present` or `-f NAME=absent`, and which a guest case placed `qemu` does not take. The program reports the branch it took, and a branch that disagrees with the profile's processor fails `etude.report`. A group decided by `report` takes the alternative the program reports; without that record, every assertion of the group is missing.

### Progress and bounds

`progress` lists the witnesses of the case's progress. A `step` witness counts completed steps. A `counter` counts completed units of bounded work toward its `limit`. A `quiet` witness marks the end of an opaque child's work, such as a compiler's, which writes nothing while it runs. Only a record whose units advance its witness is progress: a heartbeat, a repeated record, output or processor use does not reset a watchdog, and a count that goes back or past its limit is a report error. A record of a quiet witness at its present units, such as `progress compile 0` before the first compile, announces its work: from that record until the witness advances, the witness's own `bound` replaces the gap bound, and a repeated announcement does not move it.

`bounds` gives three bounds, each a `floor_us`, an `initial_us` and a `ceiling_us`: `case`, the whole case's time; `gap`, the longest time without progress; and `stages`, one for each of the executor's prepare, transfer, boot, capture and cleanup stages that the case uses. The plan fixes each bound before the run from the history of the same case, workload, profile, machine and accelerator, by the policy `watchdog-bounds-v1`: with fewer than five samples, the initial value; otherwise twice the sum of the largest sample and 3 * 1.4826 times the samples' median absolute deviation, rounded upward to a microsecond. Either is then held between the floor and the ceiling. A sample of the `case` bound is an attempt's elapsed time, one of the `gap` bound its longest gap between progress records, and one of a stage or a quiet witness the time of that stage or work. Only an attempt that passed undisrupted gives samples; a failed, incomplete, cancelled or disrupted one never makes a bound larger. A program and a scenario give no time limits of their own.

### Resources and timing

`resources` declares what admission reserves: `cpu_millis`, the first processor reservation in thousandths of a processor, and `cpu_ceiling_millis`, the most any reservation from history may be; `memory_bytes`, the combined peak of the case and its QEMU; `disk_bytes`; `guest_memory`, for the one profile whose configured memory, resident memory and backing differ; the host `locks` it takes shared or exclusive, such as the large-memory suite's exclusive lock; and the counts of local `ports` and native `loop_devices`.

`timing` declares each assumption about time that a case makes, with its file and line. Two kinds exist. A `clock_reference` compares a clock with an independent reference within the stated `uncertainty_us`. An `injected_delay` applies a delay as the stimulus and judges only the order or the state that follows. A completion bound is not an assumption about time. Synchronization by sleeping, a fixed poll or spin count, an assertion on wall time, a race with the host's disk and a forced accelerator have no kind and are refused. In the sources under `tests/cases/`, `suitecheck.sh` accepts a sleep only at a line an `injected_delay` declares, and an upper bound on a duration only at a line a `clock_reference` declares; a declared line with neither is a fault, and a program there reports a skip as `notrun`, never as printed text.

### Report records

A program reports on its standard output, in lines that begin with `@etude 1 `, as [`report.h`](include/etude/report.h) defines:

    @etude 1 begin guest.default.rngprobe
    @etude 1 assert cpuid-leaf7 pass
    @etude 1 branch source trusted
    @etude 1 assert trusted-urandom pass
    @etude 1 assert trusted-monobit fail 61 of 512 bits set
    @etude 1 end 4

`notrun ID REASON` says that an assertion could not be evaluated, `progress WITNESS UNITS` that a witness has completed UNITS in all, or for a quiet witness at those units that its work begins, and `child PID` that a process the program started may outlive it. A record is at most 255 bytes with its newline, and is written with one write(2), so that on the console it cannot be split by a kernel record. Fields are separated by single spaces; an identity is the manifest's, and a detail or a reason is printable ASCII. `begin` comes first and gives the case's identity, which a program that more than one case runs takes from `ETUDE_CASE`; every executor sets it in the case's environment. [`tests/probe_report.h`](../../tests/probe_report.h) writes the records for the freestanding probes. Each declared assertion is reported once, each group's branch once, and `end` last, with the count of `assert`, `notrun` and `branch` records before it. Every other line is the program's own output, kept as evidence and never read as a result.

The report is `complete` when it has all of that and nothing else. It is `absent` when it has no record, `truncated` when it has no `end` and no other fault, and `invalid` when a record does not parse, comes after `end`, repeats an assertion, gives an undeclared one, one that is not the program's or one of an alternative that did not run, gives another case's identity or a branch the processor contradicts, moves a witness back or past its limit, names a child of a case whose `children` are not `reported`, or has a count that does not match, and when a report with an `end` lacks an assertion it must give or a group's branch. A host program and a guest program under `etude-guest` write the records to a pipe; a program that is the designated init writes them to the console; a machine scenario writes them through `libetude-case`.

### Results

Each attempt has one results document, to which its history record's `assertion_results` refers. It gives the termination and what observed it, the state of the report, the branch of each group, and each assertion that the case requires, once: the declared assertions outside every group, those of the chosen alternatives, and the executor's. An assertion reported but not declared goes in `undeclared`.

An assertion's outcome is `pass`; `fail`, with what was seen; `not_run`, with the program's reason; or `missing`, when nothing reported it. The attempt's outcome follows from them:

* `failure` when an assertion failed, a declared one or an undeclared one;
* otherwise `incomplete` when one is missing or not run, or the report is not complete, or the end was `stopped` or `lost`;
* otherwise `pass`, and the history then requires confirmed cleanup as well.

A not-run assertion is absent coverage and never a pass. A machine's `shutdown` and `reset` are taken only from QEMU's own events, the designated init's end only from the kernel's record, and a transport closed without either is `lost`. An accelerator that QEMU could not start is `accel_failed`, and etude does not try another.

### Frames

The controller and a responder exchange frames, one line each: `etude-guest` over Rach2's serial console under QEMU, and `etude-guest --stdio` natively or `etude-remote --stdio` on Linux and macOS over their standard input and output through SSH, as [`frame.h`](include/etude/frame.h) defines:

    #E1 SESSION BOOT SEQ ACK TYPE FIELD... *CRC

SESSION is the first sixteen hexadecimal digits of the SHA-256 of the run's identity, and an ATTEMPT field the same of an attempt's. BOOT is the responder's token for the boot it runs in: the same for every responder of one boot, different in another. The responder is `etude-guest`, or `etude-remote` on Linux and macOS. SEQ counts the frames a side has sent on the connection, from 0. A process is named by its PID and its START, the time it started in the kernel's ticks since boot, so that a reused PID is told apart. A frame over the size bound, with a bad CRC, or from another session or boot is not acted on, and the responder keeps it as evidence.

Each command has a number, CMD, that the controller allocates, records before it sends the command, and never reuses in the run. The responder records each command's type and fields before it acts, and the events it caused, in its state directory, so that a later responder of the same boot has them too. A repeated command is answered by the same events again, and its effect is not repeated; a CMD sent again with other fields is answered by `error CMD conflict`. `data` and `seal` carry the CMD of their `put`, and are part of that command. `etude-remote` answers `hello`, `status`, `get` and `bye` afresh when they are repeated, since they have no effect to repeat.

* `etude-guest` sends `alive` when it starts, with the session `0000000000000000`, SEQ 0 and its versions, PID and START; on the serial console it sends it again at each resend interval until a hello comes. VERSIONS is a list of decimal versions separated by commas. The controller's `hello`, with BOOT from `alive`, a session of its own and SEQ 0, opens the session; it offers the versions and the largest frame, and `ready` answers with the version and the frame bound they share, 255 bytes at most on the serial console, or `error version`; a hello whose largest frame is under 255 bytes is answered by `error limit`. `etude-remote` takes the session's lock before its `ready`, so that a responder still ending the session's last connection finishes first.
* `put` names a file, its size, digest and mode, `data` frames give its bytes from offset 0, and `seal` ends it: `stored` answers the seal with the digest, or `error damaged` when the bytes do not have that size and digest, and they are not kept; data out of order or past the size are answered the same way, and a file over the responder's bound by `error limit`. Stored files are kept by digest. When the store or a `--stage` directory already has a file of that name, size and digest, no `data` is needed, and any that comes is ignored; a controller that knows the image stages the file sends `put` and `seal` alone. `get` sends a file of an attempt back in `data` frames with the get's CMD, and `sent` gives its size and digest for the controller to check. Its NAME is the attempt's token, a slash and a path in the attempt's directory: `work/...` for the workspace, and `out.1` and `out.2` for the output kept.
* `run` starts an attempt from an invocation stored before it, named by its digest. `etude-guest` checks the invocation, copies its files from the store into a new workspace and checks each digest, makes its fixtures, registers the child in the attempt's record before the child's exec, and sends `started`. The child's output comes in `out` frames, by descriptor and offset, and is kept up to the invocation's bound. A line `@etude 1 child PID` of its standard output names a process the child reported. When the child ends, its process group and the reported processes are killed, and `exit CMD ATTEMPT KIND VALUE` gives the end, `exited N`, `signaled S`, `stopped -` or `lost -`; `stream CMD ATTEMPT FD SIZE TOTAL SHA256`, for standard output (FD 1) and then standard error (FD 2), the bytes sent in `out` frames, the bytes the stream carried, and the SHA-256 of those sent, or `- - -` where they are not known; `usage CMD ATTEMPT CPU-US METHOD PEAK-BYTES METHOD` the processor time of the child and the descendants it reaped, in microseconds, and its peak memory, each a number, a number and `+` for a lower bound, or `-` where it cannot be read, with the method that measured it or `-`; and `cleaned` whether every process of the attempt is gone: `confirmed`, or `unconfirmed` when one is left after the grace period. The workspace stays until `remove`, which refuses an attempt that has not ended, and after a failure it stays for its evidence.
* `exec`, on the serial console alone, runs a case of the `init` role. Under QEMU `etude-guest` is the boot's designated init; it sends `started` with its own PID and START, waits until every frame it sent is acknowledged, puts the console back as it found it, and executes the program in its own place, so that the program becomes the designated init. No frames follow: the controller reads the report records from the console and the end from the kernel's record. Every other command meanwhile is refused. Over standard input and output `exec` is answered by `error refused`.
* `cancel` ends an attempt: its process group gets SIGTERM, then SIGKILL after the invocation's grace period, and the `exit` gives `stopped`. `state` answers the cancel with the state it found. `status` answers with the attempt's state, `unknown`, `preparing`, `running`, `ended` or `cleaned`, and sends its final events again; it changes nothing, so a repeat is answered from the present state. `bye` stops the attempts that run and ends the session: over SSH the responder then exits, and on the serial console `etude-guest` sends `alive` again for the next session. `etude-remote` removes the session's stored files at `bye`.

Over SSH a frame is never lost or reordered, so a bad CRC, a gap in SEQ, an acknowledgement of a frame not sent, a frame over the bound, and a frame of another session or boot end the connection. Over the serial console a receiver drops a damaged frame, a repeated one and one past a gap, and acknowledges what it has received in order; a sender sends every frame not yet acknowledged again, with the same SEQ and bytes, when the oldest has waited a resend interval. An `ack` frame carries an acknowledgement alone: its SEQ is the sender's next, not taken, and it is neither sequenced nor acknowledged. Lines of the console that are not frames are kept as evidence and searched for the kernel's records.

`etude-guest` enforces each attempt's deadline itself. When its connection is lost, by the end of its input, a frame it cannot accept over SSH, or SIGHUP or SIGTERM, it cancels its attempts, cleans up, keeps their final events in their records, and exits with status 1; the next connection's `status` reads them. An attempt whose `etude-guest` was killed before it recorded the end is settled by the next `status` or `remove`: its child, while it is still the process the record names, is killed with its group, and the attempt's end is recorded as `lost`, with its output's sizes and its usage unknown. `etude-remote` does the same at a lost connection; the session's next `etude-remote` records the end of an attempt whose responder was killed as `lost`, with its output's sizes and its usage unknown and its cleanup unconfirmed.

### Invocations

An invocation gives one attempt of a guest case: the run and attempt identities, the case, the program and its arguments, the environment, the standard input, the role, the files with their digests and modes, the fixtures with the values the controller assigned (`ids` and `ports` among them), the deadline and grace period that the plan fixed, and the most output to keep. `${WORKSPACE}` in an environment value is the attempt's workspace. A native invocation of the `init` role is refused. A scenario invocation gives one attempt of a machine case, as Machine scenarios says.

### Machine scenarios

A machine scenario is a host program that defines `etude_scenario` and links with `libetude-case`, whose `main` calls it once per attempt. The executor runs it as a host attempt, `SCENARIO INVOCATION`. The scenario invocation gives the run and attempt identities, the manifest and the case, the architecture, the store and the digest of each artifact of the case's `prepare`, the path of each host tool of its requirements, the site's accelerator, QEMU programs and UEFI firmware, the bound the plan fixed for each step and for the cleanup, the attempt's scratch directory, the grace period, the console and output bytes kept, and the resend interval of `etude-guest`'s frames.

The scenario begins each step with `etude_step`, in the order of the manifest; a step it passes over cannot be begun later, and a step ends when the next begins or the scenario returns. It boots machines, waits for text on a console at a known offset, types, sends QMP commands, runs invocations under the machines' `etude-guest`, runs host tools and artifacts of its manifest, and reports its assertions, all as [`scenario.h`](include/etude/scenario.h) declares. Each wait ends with `ETUDE_BOUND` when the step's bound expires, with `ETUDE_LOST` when the machine or its transport goes, and with `ETUDE_STOPPED` when SIGTERM, SIGINT or SIGHUP arrives; none is taken for the event waited for. Text is found only in console bytes QEMU wrote, and once QEMU has ended or closed the console, a wait for text not there is lost at once. A machine's end is the launcher's: a shutdown, a reset and a panic come only from QEMU's SHUTDOWN event, and an exit without one is `qemu_exited`, though the console says that the machine powered off. A request the manifest does not declare is `ETUDE_REFUSED`: a boot of another machine than the step's, a disk not of the machine's profile, QMP of a machine without it, typing at a machine without a console or whose console `etude-guest` has, an artifact or tool not of the case's, a step out of order, and any wait outside a step.

A machine's kernel and RAM image are read-only objects of the store, read by their digests before the boot. Each disk is the attempt's private writable copy of its artifact, which a `disk` fixture names, in `copies/` of the scratch directory; it is made at its first use and given again to every later boot and host tool of the attempt, so that dependent steps keep what earlier ones wrote. Each boot is a QEMU of its own, `MACHINE.N`, whose console goes to `evidence/MACHINE.N.console`. A machine whose `helper` is true boots to the kernel's debug shell, where the library types `exec /etude-guest --stage / --resend-ms N` once the shell says `Type 'help' for available commands.`, and the boot ends when `etude-guest` has answered hello. `etude_guest` runs an invocation artifact of the `ordinary` role and of the scenario's own case: each of its files is stored from `etude-guest`'s stage directory, or with its bytes from the store when the stage lacks it, then the invocation, and then the attempt runs, its report records other than `begin`, `end` and `child` becoming the scenario's own as they arrive. A host tool runs in the scratch directory, an artifact from an executable copy in `bin/`, its standard output kept in `evidence/OUTPUT` and its standard error in `evidence/OUTPUT.err`, which `etude_evidence` names.

The library writes the report: `begin`, each `assert`, `notrun`, `branch` and `progress` as the scenario reports it, a `progress` record of the case's first witness of kind `step` at the end of each step, and `end` once `etude_scenario` has returned 0 with no stop. In the cleanup stage it stops every machine still running and waits, within the cleanup's bound, for each to end. It removes its copies, executables and evidence when every assertion of the scenario's was reported once and held, nothing was refused, failed or lost through it, and every cleanup was confirmed; otherwise it keeps them and says `etude-case: kept: SCRATCH` on stderr. The exit status is 0 when `etude_scenario` returned 0, no stop arrived and every cleanup was confirmed; 1 otherwise; and 2 for a wrong usage or an invocation, manifest or store it cannot use.

### History

The plan's items refer to a case by three digests, each of a canonical JSON document taken from the manifest: members sorted by name, no space outside strings, and `schema_version` 1.

* The workload: `case_id`, `architecture`, `workload`, the program and role of `execution`, `steps` and `progress`.
* The assertion inventory: `case_id`, `assertions`, `branches` and `termination`.
* The profile: `case_id`, the placement, `requirements`, `machines`, `resources`, the privileges, and the `isolation` of a host or QEMU placement or the `native.fixtures` of a native one.

Equal manifests therefore give equal digests, and a comparison of two runs finds a changed workload by its digest. The results document of each attempt is the history's `assertion_results` blob.

The plan's `reproduce` blob is a document of [`schemas/reproduce.schema.json`](schemas/reproduce.schema.json), as [the example](schemas/reproduce.example.json) shows: for each item, the directory and the environment it runs in, the commands that prepare it, the command of the case, and the command that runs the case under a profiler, or the reason the platform has none.

### Repetition records

A run of repetitions looks for a result that depends on the order of the cases, on how many run at once, or on load beside them. Its seed fixes the plan by the policy `repeat-splitmix64-v1`. One splitmix64 generator, started at the seed, makes three choices in turn:

1. The selection: `pick` cases, the first places of a partial Fisher-Yates shuffle of their indices, kept in the order given; every case when `pick` is 0 or not below their count.
2. The order: each selected case's repetitions, in the order given, shuffled by Fisher-Yates from the last place down, the place `i` exchanged with a place below `i + 1`.
3. The loads: for each item in that order, a number below 100; when it is below `load_percent` and there are loads, a number below their count chooses the item's load.

A number below N is the generator's output modulo N, drawn again while the output falls in the incomplete last span of 2^64 values, so that no value is likelier than another. A seed is at most 2^53 - 1. It reproduces the selection, the order and the loads on any host, but not the host's schedule.

The repetition record is a document of [`repeat.schema.json`](schemas/repeat.schema.json): the policy, the run, the seed, what the plan was drawn from (each case with its architecture and repetitions, the loads with their kind and amount, `pick`, `load_percent`, the `width` of cases run at once and the `retries` of an attempt that did not pass) and the items in their order, each with its identity, `RUN:CASE:ARCH:rREP`, and its load or null. The plan record names it as its `selection` and its `concurrency`. A reader draws the plan again from the record's own inputs; a record whose items are not that plan's is refused.

### The version cache

A machine keeps the versions of etude built on it in a cache: `${XDG_CACHE_HOME:-$HOME/.cache}/etude` on Linux, macOS and Rach2, `%LOCALAPPDATA%\etude` on Windows, or the directory `-C` gives. A version is etude's programs built from one source by one recipe, for one platform, by one compiler. Its key is the SHA-256 of the first five lines of its record:

    etude-version 1
    source 1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0
    platform macos arm64
    compiler a856ec74c559401131ad608625ef252fb2db6c78bc0c480c1c4c782ee4896db1
    flags -std=c99 -O2

`source` is the SHA-256 of the source's list, a line `SHA256  PATH` for each of its files in the byte order of their paths. The source is the C files, headers and make files under `tools/etude` but its fixtures, the schemas under `tools/etude/schemas`, and `utils/sha256.c` and `sha256.h`; a change anywhere else, a kernel commit among them, keeps the key. `platform` is the platform as `tools/setup/prereq.sh` names it, and the machine as `uname -m` gives it. `compiler` is the SHA-256 of what the compiler prints for `-v`, and `flags` are its flags, which with `version.mk` make the recipe.

The rest of the record gives the `key`, the compiler's command line as `cc`, the version's directory as `build`, relative to the cache, and a line `program NAME SHA256` for each program. The cache has two directories:

| Path | Contents |
| --- | --- |
| `versions/KEY` | The record of a published version, a hard link of its build's `version` |
| `builds/KEY.XXXXXX/` | A build: `src/`, its source; `sources`, the source's list; `bin/`, the programs; `version`, its record |

Versions of different keys live side by side, and a published version is never changed. A version is published by a hard link, so the cache must be on a file system that has them: on Rach2, ext2 or tmpfs, and not KRFFS. A build directory that no record names is a build that failed or was stopped, and nothing uses it. A published version whose record or programs do not match their digests is damaged, and a request for it fails until a person removes `versions/KEY`.

### The machine record

Deployment keeps, for each account of a machine, a record of what the machine can do and of the version deployed, in a state directory: `${XDG_STATE_HOME:-$HOME/.local/state}/etude` on Linux, macOS and Rach2, `%LOCALAPPDATA%\etude-state` on Windows, or the directory `-S` gives. The directory has the record, `machine`, and the ledger, `ledger/`, unless `-L` names another. The record is text, a field on each line, in this order:

    etude-machine 1
    host testing
    platform linux x86_64
    cpus 32
    memory_bytes 135070339072
    qemu QEMU emulator version 10.2.1 (Debian 1:10.2.1+ds-1ubuntu3.2)
    accelerators kvm tcg
    admission etude-ledger 1
    ledger /home/testing/.local/state/etude/ledger
    version 1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0 /home/testing/.cache/etude/builds/1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0.Ab3dEf

`host` is the machine's name as `uname -n` gives it, and `platform` the platform as the version cache names it. `cpus` and `memory_bytes` are the whole machine's processors and memory, `-` where the system does not give them. `qemu` is the first line of `qemu-system-x86_64 --version`, and `-` where there is no QEMU. `accelerators` are those this account can run a guest under: `kvm` when it can read and write `/dev/kvm`, `hvf` when macOS's `kern.hv_support` is 1, and `whpx` when the Windows Hypervisor Platform is enabled, each followed by `tcg`; `-` without QEMU; and `native` on Rach2, whose cases run on the machine itself. `admission` is the version's admission format, the first line of the ledger file its `ledger.c` writes. `ledger` is the ledger's directory, in the form `C:/...` on Windows, and `version` the key and the directory of the version deployed, as `version.sh` reports them.

Versions of one admission format share a ledger. A version refuses a ledger file of another format whole (The ledger), and deployment does not record a version whose format is not that of the ledger's file, so two versions of different formats never both admit claims on one machine.

### Artifacts

An artifact is a regular file that preparation makes and a case reads: a kernel, an image, a probe or a scenario. The store keeps each as an object named by the SHA-256 of its content, and preparation is a graph of nodes, each of which makes one artifact. A store is a directory:

| Path | Contents |
| --- | --- |
| `objects/DIGEST` | An object: a whole file, read-only, whose content has the digest DIGEST |
| `nodes/KEY` | The record of the object a node published under its key |
| `locks/KEY` | The file whose lock a process has while it prepares the key |
| `tmp/part.XXXXXX` | A partial object or record, locked by its writer until it is named or removed |

A record is five lines, in this order and no others:

    etude-artifact 1
    key 67bd12142ce4d2e924f0e6798243a1906a93be0c782240e7bce665b2f6af8da6
    object b674ffd22590339190299ad579244d53f6ead46c3cd73c37f63135be7ee96fdf
    size 1048576
    node rach2/kernel

A node has a name, the manifest's `node`; a recipe, a command, or none for a file of the tree, which is published as it is; its output, a path in the recipe's work directory; its inputs, other nodes of the graph; further `key` text, such as a commit or a recipe's version; and the bound of its prepare stage. In the recipe's arguments and environment, `${WORK}` is the node's work directory, where the recipe runs, and `${IN:NAME}` the read-only path of input NAME's object. The node's key is the SHA-256 of its name, recipe, output, key text and inputs with their digests, each field written with its length. A change of an input's content changes the key of every node that uses it, and a change that leaves a product's content as it was leaves its dependents' keys as they were. A fresh node is made again by every run and has no record, for a product that is the operation under test and not its setup.

A run gives each node a state: `reused`, when the store has a record of its key whose object reads back with the record's digest and size; `built`, when this run made and published it; `failed`, when its recipe or its publication failed; `blocked`, when an input failed or was blocked, and its recipe never ran; or `pending`, when the run refused the graph and ran nothing. A case reads its artifacts by digest, and a case that writes one, such as a durability case's disk, gets a private writable copy, checked by its digest as it is copied.

### Proofs

A mutation proof shows that a test finds a fault: the test passes on the unmodified sources, fails as declared with the fault in them, and passes again once they are restored. Its catalogue is a document of [`proof.schema.json`](schemas/proof.schema.json), and catalogues are kept in `tests/proofs/`. It gives:

* `proof`, the name, and `summary`;
* `tree`: `private`, where the faults go into copies of the sources under the work directory, which the build reads in place of the tree's; or `shared`, where they go into the tree's own sources, for a build such as the kernel's that a private copy cannot reach;
* `sources`, the files, relative to the tree, that the faults change;
* `artifacts`, the files the build makes and the test runs or reads;
* `build` and `test`, each a command, `argv`, whose first word is a path, with its bound in seconds, `bound_s`; the test may give `fail_prefix`, how a line of its failure begins;
* `faults`, each with a `name`, a `summary`, its `edits` and `fails`. An edit names a source, the text `find`, which must occur once in what the fault's earlier edits left, and the `replace` that takes its place. `fails` gives the `lines` the test's output must contain, each within some line, the exit `status` when one is required (any but 0 otherwise), and `only`, which requires every line that begins with `fail_prefix` to contain one of `lines`.

In the commands and the artifacts' paths, `${TREE}` is the tree's root, `${SRC}` the root the sources are read from (the tree's for a shared proof, the private copy's otherwise), `${WORK}` the work directory and `${PHASE}` the phase. Any other `${NAME}` whose NAME is capitals and underscores is refused as a misspelt placeholder; other text, a shell's `${CC:-cc}` among it, is passed on unchanged. A fault named twice, an edit of a file that is not a source, and `only` without `fail_prefix` are refused.

A proof runs in phases. Each builds, keeps its artifacts in the store under their digests and runs the test:

1. `base`, on the unmodified sources. The test passes: it exits 0 and prints no line that begins with `fail_prefix`.
2. `fault-NAME`, for each fault: its edits are made, and at least one artifact must differ from the base's, or the fault did not reach what the test runs. The test must fail as `fails` declares.
3. `restored-NAME`: the saved sources are written back and must read back whole, every artifact must equal the base's byte for byte, and the test must pass.

The build must exit 0 within its bound. A command must end with each process it started, and one that runs past its bound, is killed by a signal or writes more than 16 MiB to a stream fails the phase. After each phase the sources must be as the phase left them, so a build or a test that writes a source fails the proof. An artifact that differs from the base's after the restoration, such as one a stale build kept or one made from state the faulty run left behind, shows the restoration incomplete, and the proof fails.

## Design

### Building a version

`version.sh` makes a script of `bootstrap.sh`, the source and the call of `etude_main`, and gives it to a POSIX sh on the machine with `ssh -T -o BatchMode=yes HOST 'sh -s'`. The account's own shell runs that command, and `sh -s`, a word and a flag, reads the same in sh, bash, dash, zsh, ksh, fish and csh; for Windows, `C:\msys64\usr\bin\env.exe PATH=/usr/bin:/ucrt64/bin sh -s` reads the same in cmd.exe and in PowerShell, the shells its SSH server offers. Each file of the source is the body of a quoted here-document whose end line has a random nonce in it. The script defines functions alone until its last line, `etude_main < /dev/null`, so that a script cut short anywhere ends in a syntax error or before that line, and changes nothing on the machine.

`etude_main` chooses the compiler and flags of its platform: `cc` with `-std=c99 -O2`; `-std=c99 -static -D__rach2__` on Rach2, whose TinyCC links only static programs and defines no `__linux__`; MinGW-w64's `/ucrt64/bin/gcc` and programs named `.exe` on Windows. It computes the key, and when `versions/KEY` exists it checks the record's key and the programs' digests and reports the version reused. Otherwise it makes a build directory with `mktemp -d`, writes the source there, requires the list's digest to be the one `version.sh` computed, runs `make -f tools/etude/version.mk` in the source, writes the record and checks it, and publishes it with `ln`, which fails when `versions/KEY` exists. Of two builds of one key at once the first link wins, and the other removes its directory and reports the winner's version reused. An exit trap removes the directory of a build that failed, or that a signal other than SIGKILL stopped.

The result is the line `@etude-version NONCE built|reused KEY DIR` on the machine's standard output. `version.sh` takes only the line with its own nonce, and passes the rest, such as what the account's startup files print, to stderr.

### Deployment

`deploy.sh` makes three requests of the machine, each of which can be cut short and made again. The first checks the prerequisites. A POSIX machine gets `tools/setup/prereq.sh`, its recipe and the scripts that the recipe's probes and install lines read, as quoted here-documents, as `version.sh` sends the source, and runs them in a scratch tree under its `TMPDIR`, which the script removes on exit; a probe runs in its tree's root, and in a clone it could write there. For Windows, `prereq.sh --platform windows` runs on the controller and reaches the machine's PowerShell over ssh(1). The install lines run as `prereq.sh --install` runs them, an administrator's only where the account has the rights, and the rest are printed. A missing prerequisite leaves the deployment incomplete without stopping it, since the account's other steps need no administrator.

The second request is `version.sh`'s, and deployment stops when it fails. The third sends a script of `bootstrap.sh`'s functions and its own, which, like `version.sh`'s, defines functions until its last line. It makes the state directory where it is missing, and the ledger, an empty `lock` and a directory `verdicts`. Where the ledger exists, it requires the account to be able to write the directory, its `verdicts` and its `lock`, and read its `claims`, and prints the `chmod` commands that would let it; and it requires `claims`, where present, to begin with the version's admission format. Either refusal leaves the machine as it was. It then makes the record and writes it, to a temporary file renamed over `machine`, only when it differs from the one there, so a deployment that changes nothing writes nothing, and one cut short leaves the old record or the new one whole.

Deployment writes no file of the ledger that exists, so a running test keeps its claims and verdicts, and its version, whose directory a new version leaves alone. It runs no git or ssh-keygen, and passes `-o BatchMode=yes` to ssh(1), which then asks for nothing.

### The history store

[`history.h`](include/etude/history.h) provides the C99 history API. `etude_history_open` creates a stream with exclusive creation and mode 0600, without inheritance by executed children. One thread in one process owns that stream. Each other writer creates a file of its own, with a globally unique stream ID allocated before execution. A forked child cannot append through its parent's writer. The writer never reopens, replaces or truncates an existing file.

The caller supplies the trusted version-one [`history.schema.json`](schemas/history.schema.json), the run ID and a byte limit. The store reads the schema once and validates each record before writing it. Its JSON reader rejects duplicate members (including escaped spellings), non-ASCII text, fractional numbers and integers beyond 53 value bits. It implements the vocabulary and patterns used by this schema; it is not a general JSON Schema implementation. The store also checks elapsed-time subtraction, paired null preparation identities, and the absence of a completed run interval when cleanup is unconfirmed.

`etude_history_record_id` gives the next ID as `STREAM/SEQUENCE`, which the caller can use in references before writing the record. The writer accepts that ID alone and adds the version, stream, sequence, run, UTC and kind to the supplied data object. It compacts whitespace outside strings. It flushes and synchronizes the object bytes before writing and synchronizing the newline. A failed write ends that stream; a new stream continues the run. The failed stream remains evidence.

A record is at most 4 MiB and a stream at most 65,536 records, subject to its byte limit. A full stream returns an error before writing any part of the next record. A caller must bound the total of streams and referenced blobs through admission and retention. This store deletes nothing, including accepted baselines and issue evidence.

`etude_history_read` checks the schema, local arithmetic, run and stream identity, contiguous sequences and unique record IDs. It accepts the contract's opaque record IDs, including those written by other producers. SHA-256 and byte length identify an exact replay, which is delivered once; a repeated ID with other bytes is an error. It returns 1 for an unfinished last line and -1 for malformed complete lines or I/O errors, with the line number. Its callbacks may have received a valid prefix before that error; the prefix cannot establish success. The input is a closed stream or a stable snapshot. The consumer must resolve references across streams, check content hashes and inventories, and derive aggregate outcomes before deciding whether a run passed.

### The collectors

`etude_history_now` reads UTC and the monotonic clock independently, with the clock resolution rounded upward. POSIX uses `clock_gettime`; Windows uses the performance counter and precise system time. The caller records the machine, boot and clock IDs and subtracts readings only in that domain. Elapsed metrics keep a conservative rounding bound; a missing end, backward reading or overflow stays unavailable.

`etude_history_wait_usage` converts final POSIX child usage to processor microseconds. It includes descendants whose reaped usage the operating system charged to the child, and reports a lower bound with unbounded error because other descendants may be missing. `etude_history_job_usage` reads Windows Job Object cumulative user and kernel time, which includes terminated members. Its caller owns the job, forbids breakaway and records the process creation identities in the scope blob. Neither interface mistakes a process's peak resident size or a job's peak commit charge for combined resident memory; that measurement is unavailable.

`etude_history_cpu_sum` adds disjoint accounting scopes with checked arithmetic. Missing scopes stay unavailable and incomplete accounting stays a lower bound. The executor supplies each inclusive scope once: it never adds a guest to its QEMU, a tooling VM to its internal processes, or a parent's inclusive usage to its children. `etude_history_memory_sample` takes simultaneous resident sizes for disjoint scopes and keeps their largest combined sample. It records the longest sampling interval and an unbounded error, and a missing sample makes the result unavailable. Summing individual peaks cannot supply it. The run's peak needs samples of the whole run, apart from its cases' peaks.

### The comparison

[`compare.c`](compare.c) reads every stream with `etude_history_read`. An invalid stream is left out whole, and the incomplete last line of a stream is not read; the report notes both. A record that two streams give with the same bytes is read once, and an identity with two contents ends the command.

Each attempt record is a sample. Its key holds the values that a same-site comparison matches by the plan's measurement record under `dev-log/`: the case, the architecture, the domain, the machine and the accelerator, which name the sample's series; the digests of the workload, the assertion inventory and the profile; the operating system and its version; the digests of the site profile, the tools, the cache state, the declared load and the concurrency policy; and the method of the elapsed time. The commit and the hashes of the tested programs are not in the key, so that a series crosses commits. A sample is eligible when its plan lists it, its result is a pass that was not disrupted, it retries no attempt, its elapsed time has an error bound and is not a lower bound, and its run has a run record that lists it and was not disrupted. A run without its record has no account of its load, so its samples are left out.

The run's items are grouped by key, and the candidates of a group are the first attempts of its items, so that the repetitions of one case are compared together. [`baseline.c`](baseline.c) chooses the group's baseline. A comparison record with a verdict of `within_noise`, `regression` or `improved` accepts its baseline, whose identity names the policy and the sample list. The newest baseline accepted for the candidate's whole key is used again, however many slower samples follow it, so that a slowdown does not become the baseline by repetition. When there is none, or `-n` asks, a new baseline takes the eligible samples of the key from other runs that ended before the candidates started and after the newest sample of the series' last accepted baseline. Its identity is `median-mad-v1:` and 32 hex digits of a SHA-256 of its sample identities. The report lists each sample of the series in that window that was left out, with the reason.

The statistics are those of `median-mad-v1`. The median of an even count is the midpoint of the two central values; the arithmetic is in quarters of a microsecond, where the midpoints are exact, and only the stored median and deviation are rounded upward. The band is the largest of 3 * 1.4826 times the deviation, one percent of the median, and the largest clock resolution or error bound of the samples. The verdict is `not_comparable` when no candidate is eligible, or when no earlier sample has the candidate's key but one of another key in the series does, as after a change of workload; `insufficient_history` with fewer than five baseline samples; and otherwise `within_noise` when the medians differ by no more than the sum of the two bands, and `regression` or `improved` when they differ by more.

[`compare_report.c`](compare_report.c) writes the report: the verdict and its reason; the medians, deviations and bands of both sides; the commits the baseline tested, the newest of them and the candidate's, and the commits in between; each step of the candidate compared with the same step of the baseline's attempts, so that a slower boot shows apart from a slower execution; the processor time of the tree and the time queued on both sides, apart from the elapsed time; each sample with its commit, end and time, and each one left out with its reason; the candidate's source, runner and artifacts by digest; and the commands of the plan's reproduce blob, which run the item again and under a profiler. [`compare_run.c`](compare_run.c) runs the command and builds the comparison records, which the history store validates before it writes them.

### The POSIX executor

[`posix/`](posix/) runs host processes for the controller, as [`exec.h`](include/etude/exec.h) declares, on Linux, macOS and Rach2. [`capture.c`](capture.c), which the Windows executor shares, keeps each output stream up to the attempt's bound, counts the rest, and finds the `child` records on standard output, beyond the bound as well.

Each attempt has a keeper, a process the controller forks in a session of its own ([`keeper.c`](posix/keeper.c)). The keeper closes every descriptor it does not need and forks the case's process, which makes a session and a process group of its own, puts its standard input and the write ends of two output pipes on descriptors 0 to 2, sets every signal to its default, clears its signal mask, and then waits on a pipe. The keeper reports the process's PID and start to the controller, whose registration function sees it before it runs anything; only then does the keeper write the go. A refusal kills the process unrun. A pipe closed on exec tells the keeper whether the exec succeeded, and an exec that failed makes `etude_exec_start` fail with its error after the keeper has reaped the process.

The controller ([`exec.c`](posix/exec.c)) talks with each keeper over two pipes in fixed messages of 32 bytes, each written whole, and polls the keepers' pipes and the cases' output pipes of every attempt at once. It gives the attempt's `child` function each running descendant that a `child` record names before it gives the descendant to the keeper; a refusal makes the cleanup unconfirmed. A process is named by its PID and its start, read from `/proc/PID/stat` on Linux and Rach2 and from `sysctl` on macOS, so that a reused PID is told apart.

When the case's process ends, the keeper reaps it and reports its end. The controller reads the output written before it, gives the keeper the descendants that `child` records name, and asks for the cleanup. The keeper sends SIGTERM and SIGCONT to the case's process group, to each reported descendant still the same process, and on Linux to each of its own children and their groups; it sends SIGKILL to what is left after the grace period, and again to what comes to it later. It reports the cleanup confirmed only when it finds nothing left, within the grace period after SIGTERM or within a second one after SIGKILL. A cancellation sends the same signals at once and SIGKILL after the grace period, so that a stopped process is resumed and can end gracefully; its end is `stopped`. When the controller's pipe ends, the keeper cancels the case, cleans up by itself, and records the cleanup in the attempt's `verdict` file, as The ledger says.

On Linux and Rach2 the keeper is a subreaper (`PR_SET_CHILD_SUBREAPER`): every orphan below it, one that escaped into a session of its own included, becomes its child, which it can find in `/proc/self/task/PID/children`, end and reap. Where it is not, it can end only the process group and the reported descendants; an unreported process in another session that keeps the case's output open shows itself, since the output must close within the grace period after the keeper has ended, or the cleanup is unconfirmed. The `posix_only` field of an attempt makes the keeper use POSIX interfaces alone, so that Linux can test that path.

Rach2 has the Linux interfaces the executor uses: `/proc/PID/stat`, `/proc/PID/task/TID/children` and the subreaper of prctl(2). Its TinyCC defines no `__linux__`, so [`process.c`](posix/process.c) takes them on Rach2 when `__rach2__` is defined, as the version's recipe there defines it; a build for Rach2 without it can read no process's start.

The processor time of the tree is the keeper's `RUSAGE_CHILDREN` after the cleanup, which counts each process that its parent or the keeper reaped. It is exact, as `posix-subreaper-rusage-v1`, when the keeper is a subreaper and confirmed the cleanup, and a lower bound, as `posix-rusage-children-v1`, otherwise, since an orphan reaped elsewhere is not counted. The peak memory, `posix-maxrss-v1`, is the largest resident size of any one process of the tree, a lower bound of the combined peak. Rach2 samples a process's resident size only when its address space ends, at its exit or exec, so there the value is the largest size any one address space of the tree had when it ended. A keeper killed before it reports leaves the end `lost`, the cleanup unconfirmed and both measurements unavailable.

### The host checks

[`posix/etude_host.c`](posix/etude_host.c) runs each step of a check as an attempt of the POSIX executor: `/bin/sh -c 'exec >"$1" 2>&1; eval "$2"'` with the step's log and command, so that what the command and its descendants write reaches the log in the order written. The step therefore starts in a session of its own, with standard input from `/dev/null`, an empty signal mask and every signal at its default, and the executor ends what it leaves behind. A check passes when its run exits 0 and the executor confirms that its processes have ended. A compile that fails, a run that exits otherwise or is killed, a step past its bound, and a step that leaves a process the executor cannot end each fail it. A compile's bound is 600 seconds and a run's the check's SECONDS; a step past it is cancelled, which sends SIGTERM and SIGKILL two seconds later, and reported as hung.

A check's environment is etude-host's, with `TMPDIR` set to its scratch directory and the sanitizers' settings replaced: `ASAN_OPTIONS=halt_on_error=1:exitcode=1`, `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1:exitcode=1`, and no `LSAN_OPTIONS`. An inherited `exitcode=0`, `abort_on_error=0` or `detect_leaks=0` therefore cannot make a sanitizer's report pass, and LeakSanitizer keeps its default, on where the platform has it.

The checks start in the order of their bounds, the longest first, and the `alone` checks after the others, each when nothing else runs; nothing starts beside one. A passing check's scratch directory is removed, and a failing one's is kept and named when it is not empty. Under a failure the program prints the lines of the sanitizers' reports in the log, marked `!`, and the log's last 20 lines, marked `|`, so that a failure reads without the log; under a pass it repeats each `NAME: not run: WHAT: WHY` line of the log.

### Windows execution

On Windows a host program runs through [`win/winexec.h`](win/winexec.h), which is built with MinGW-w64 against the UCRT and needs no MSYS2 or Cygwin runtime. [`win/pecheck.c`](win/pecheck.c) reads a program's import and delay-load tables and refuses such a runtime and any library that is not Windows's own.

* `etude_win_start` creates the child suspended, puts it in a Job Object of its own, and calls the executor's registration function before the child's first instruction. A registration that fails ends the child with `ETUDE_WIN_REFUSED_STATUS`, and it never runs. A process is named by its ID and its creation time, so that a reused ID is told apart.
* The job kills every process in it when its last handle closes, so the tree ends with the executor; no process can break away from it; and an unhandled exception ends a process without the dialog of Windows Error Reporting.
* The child inherits its standard input, the NUL device or a file, and two pipes for its output and its errors, and no other handle. It has a console of its own with no window, whose host process, `conhost.exe`, is in the job.
* `etude_win_poll` reads the output and learns of each end through one completion port. A child has ended when its first process has exited, its job is empty and both pipes are at their end, so output that a descendant writes after its parent exits is kept.
* `etude_win_usage` reads the job's accounting: the processor time of every process, ended ones included, at the resolution of the clock interrupt; the peak of committed memory of the job and of any one process, which is not the working set; and the bytes read and written.
* `etude_win_stop` ends every process of the job at once with `ETUDE_WIN_STOP_STATUS`. Windows has no signal that asks a process without a window to stop, so a stop has no grace period.
* Paths are UTF-8, made into `\\?\` paths of any length; a command line is quoted for the UCRT's parsing rules; an environment given whole replaces the executor's, and must then have `SystemRoot`, which Winsock reads; the monotonic clock is the performance counter; and a listening socket is on 127.0.0.1, where no child inherits it.

[`win/exec.c`](win/exec.c) implements [`exec.h`](include/etude/exec.h) on the adapter, so that the controller has one interface on every host. The job takes the part of the POSIX keeper, and the controller's own process is the keeper that a registration sees. When the case's first process ends, the executor stops its job, as the keeper ends the descendants of a case, and the attempt finishes when the job is empty and both streams have closed; the cleanup is then confirmed, since no process can leave the job. A `child` record counts as a child, and goes to the attempt's `child` function, when it names a process of the job, and counts as foreign otherwise. A cancellation stops the job at once, with no grace period, and its end is `stopped`; `grace_us`, `posix_only` and `verdict` have no effect. The processor time, `win32-job-accounting-v1`, is the job's and exact. The peak memory is unavailable, since a job reports its peak commit and not its resident memory. A registration that fails makes `etude_exec_start` fail with its error after the case has ended unrun.

### The ledger

[`ledger.h`](include/etude/ledger.h) keeps the claims of one machine's resources in a directory, so that a worker that dies cannot take its claims with it, and no worker can take what a claim's processes still use. A claim has the attempt's identity, the resources it reserves as named amounts, such as `cpu_millis` and `memory_bytes`, its owner, which is the worker's process, and the processes it runs.

A worker records a claim with `etude_ledger_reserve` before it starts anything; given the machine's limits, the reservation is refused when it would take a resource past its limit, counting every claim the ledger keeps. The worker gives the executor `etude_ledger_register` and `etude_ledger_child` as the attempt's `reg` and `child`, the ledger as `reg_ctx`, and the claim's `etude_ledger_verdict_path` as `verdict`. The executor calls the registration after it has made the case's process and before it lets the process execute its program, and the registration returns only once the identities of the keeper and the process are in the ledger file; a reported descendant is added when the executor reads its `child` record. When the attempt has finished, `etude_ledger_finish` releases the claim if the cleanup is confirmed, and keeps it as `uncertain` if it is not.

The directory has `claims`, `lock` and `verdicts/`. Every change takes an exclusive lock of `lock`, by `fcntl` on POSIX systems and `LockFileEx` on Windows, which the system gives back when the holder dies; reads `claims`; and writes the whole file again as `claims.new`, synced and renamed over `claims`, so that a reader finds the file as it was before a change or after it, never part of one. The file is text, a field on each line:

    etude-ledger 1
    claim ATTEMPT
    system linux
    boot 6f1c2d0e-8b4a-4f8e-9b1d-2a7c5e3f9d10
    owner PID START KNOWN
    account testing
    state running
    resource cpu_millis 1000
    process keeper PID START KNOWN
    process case PID START KNOWN
    process child PID START KNOWN
    end

A process is its PID, its start and whether the start is known, as `struct etude_pid` gives them. `account` is the account the claim was admitted for, and absent from a claim that `etude_ledger_reserve` made. `state` is `reserved` before a process is registered, `running` after, and `uncertain` once the owner has found the cleanup unconfirmed. A request that waits for admission, as the next section says, has the same form with the state `waiting`, or `blocked` for the one request that is protected, a line `ticket N`, its place in the order of arrival, and no process; it holds no resource. A file with two blocked requests is refused whole. `boot` is Linux's `boot_id` or macOS's boot session UUID, and `-` where the system gives none, as on Windows. A file that does not parse is refused whole, and nothing in it is released.

Recovery runs at each reservation and listing, and releases a claim only when it is proved free:

* A claim recorded in an earlier boot is free, since no process of that boot runs.
* Otherwise its owner must have ended. A process with the owner's PID and another start has reused the PID, so the owner has ended; a PID that runs with a start that cannot be read leaves the claim uncertain.
* A claim that registered no process is free.
* Otherwise each of its processes must have ended, the case's process group must have no member, its state must not be `uncertain`, and on POSIX systems its keeper must have written `confirmed` in the claim's verdict file.

A request is removed once its owner has ended, as a claim with no process is. A claim of another operating system is kept and not judged. `etude_ledger_list` gives each claim kept as owned, live, when a process of it runs, or uncertain, with the reason; `etude_ledger_drop` releases a claim that is not owned once a person has established that nothing of it runs.

The verdict covers what the ledger cannot see. A keeper whose controller has gone cancels the case and ends what it knows of; then it reads the case's output pipes, whose read ends it holds, and confirms the cleanup only if both close within the grace period, since a process that holds them open is the case's. It writes `confirmed` or `unconfirmed` in the verdict file and exits. A descendant that escaped unreported and holds the output therefore leaves the claim uncertain, and so does a keeper killed before it wrote. A keeper whose controller lives writes no verdict, and the controller's own report decides. On Windows the job ends every process of a case when the controller's last handle closes, and no process can leave it, so a claim there needs no verdict: it is free once its owner and its registered processes have ended.

### Admission

`etude_ledger_admit` admits a claim for an account within the machine's limits, which the caller gives as named amounts, under the same lock as every other change of the ledger, so two workers can never both take the last of a resource. A request refused for now can wait in the ledger, and its worker asks again with the same identity when a claim may have ended; the ledger gives no notice.

One waiting request of the machine is protected. A claim is admitted only when it fits beside every claim the ledger keeps and, of each resource it takes, leaves free what the protected request needs. The claims that run therefore end without being replaced by claims on what the protected request waits for, and it is admitted once enough of them have ended. A claim of a resource the protected request does not lack, such as processors alone beside a request blocked on memory, is admitted. Nothing is admitted on a forecast that it will end before the protected request could start, so there is no backfilling by time, and the schedule is not in general an optimal one.

The protected request is chosen when there is none: of the requests that could ever fit, the one whose account holds the fewest claims, and of those the one that has waited longest. It stays protected until it is admitted or withdrawn, so an account that later holds fewer claims cannot pass it. A request could never fit when it exceeds the limits alone (`ERANGE`), or cannot fit beside the claims whose worker and processes have ended with the cleanup unconfirmed, which only a person can drop (`ENOSPC`); it is refused, a protected one loses its protection, and the rest of the run goes on. A claim whose processes cannot be identified, as on a system that gives no start time, may still end, and its request waits. `etude_ledger_reserve` admits by the same rule without an account or a wait.

[`sched.h`](include/etude/sched.h) is a worker's side. `etude_sched_order` sorts its jobs, the cases of both architectures together, by the place of their last preparation in the order of preparation, then the costlier first, so that a long job does not start last, then by case and architecture. `etude_sched_admit` asks for each job whose preparation has finished, in that order. The worker keeps one request waiting: the job already waiting, or else the first refused; the others are asked without waiting, and each is admitted where it fits beside the protected request. A job the machine can never hold is marked refused and the others go on. `etude_sched_withdraw` withdraws the request of a worker that stops.

A job's cost is its expected elapsed time. [`cost.c`](cost.c) takes it from the samples that the comparison finds eligible, passes that were not disrupted and retry nothing, whose key matches the planned item's in every field but the load, the concurrency policy and the method of the elapsed time: the same case, workload, inventory and profile, on the same machine, system, accelerator, site profile, tools and cache state. It is the median of their elapsed times, or the case's declared initial bound with none. Its processor reservation, by the policy `cpu-median-v1` of `etude_sched_cpu`, is the median of each sample's processor time divided by its elapsed time, rounded upward, with 25 percent more, at least one thousandth of a processor and at most the case's `cpu_ceiling_millis`; with no sample it is the declared `cpu_millis`. A processor time that is a lower bound, as the POSIX executor's is, is taken as its value. Memory and disk reservations are the declared amounts.

### etude-guest

`etude-guest` is one process with one loop: it waits in `poll` for its input, a self-pipe its signal handlers write, and the next deadline among the resend interval, the attempts' deadlines and their grace periods, and handles what is ready. Children are reaped with `wait4`, which gives their usage: the processor time of the child and the descendants it reaped, `wait-reaped-descendants-v1`, and the largest resident size of any one of them, `posix-maxrss-v1`, each a lower bound, since a descendant that the child did not reap is not counted.

Its state directory has three parts. `f/SHA` is a stored file, named by its digest, written to a temporary name, synchronized and renamed, so that a file of the store is always whole. `s/SESSION/CMD` is a command's record: its first line is the command's type and fields, and each later line an event it caused, appended and synchronized before the event is sent. `a/TOKEN/` is an attempt's: `record` with the child's PID and START and its end, `work/` the workspace, and `out.1` and `out.2` its output. A record outlives the `etude-guest` that wrote it, which is how a repeated command, a later connection's `status` and an orphaned attempt are answered.

The child is made in two steps. After `fork` it makes its own session and process group and waits on a pipe; `etude-guest` writes the record with its PID and START, and only then lets it go on, so that no process of an attempt runs unrecorded. The child takes `/dev/null` or the invocation's standard input, pipes for its output, the workspace as its directory, mask 022 and the default signal actions, closes every other descriptor, and executes the program; an exec that fails is reported through a pipe closed on exec, as `error CMD failed`.

On the serial console `etude-guest` keeps every sequenced frame it sent until it is acknowledged, at most 32 frames and 1 MiB, and reads no more output while the queue is full. Its diagnostics go to `guest.log` in the state directory and never to the console, where they would mix with the frames.

### The QEMU launcher

[`qemu.h`](include/etude/qemu.h) boots a guest or machine case's QEMU profile on the site's accelerator. [`qemu_profile.c`](qemu_profile.c) makes the command line, the same on every host, and [`posix/qemu.c`](posix/qemu.c) runs the machine on Linux and macOS.

The machine is QEMU's default PC, for i686 on `qemu-system-i386` and for x86-64 on `qemu-system-x86_64`, as the site names them. `-nodefaults` leaves it the board's own devices and those of the profile, and `-display none`, `-no-reboot` and `-S` give it no window, make a reset end QEMU, and keep its processors stopped until the launcher starts them. The profile becomes these arguments:

| Profile | QEMU's arguments |
| --- | --- |
| The site's accelerator | `-accel NAME`, one alone, so that QEMU tries no other |
| `cpu` | `-cpu` with the processor profile's value |
| `processors`, `memory_bytes` | `-smp`, and `-m` in bytes, a whole number of mebibytes |
| `firmware` `direct` | `-kernel`, `-initrd` when there is one, and `-append` with the boot options separated by spaces |
| `firmware` `seabios` | nothing: the BIOS boots the first disk; no RAM image or boot options |
| `firmware` `ovmf` | `-bios` with the site's UEFI firmware of the architecture; no RAM image or boot options |
| Each of up to four `disks` | `-drive file=PATH,format=raw,if=ide,index=N,media=disk` |
| A device `rtl8139` or `e1000` | the card on a user network of its own, `-netdev user,id=netN` |
| A device `vga` | `-vga std` |
| Any other device | `-device NAME` |

The machine's serial console and its QMP monitor are Unix sockets in a private directory under `TMPDIR`, or under `/tmp` when their paths would not fit a socket's address there, which the launcher listens on before it starts QEMU, and to which QEMU connects as a client when it makes its character devices, before it starts the accelerator. QEMU fails at once if it cannot connect, nothing it writes is lost before the launcher reads it, and the launcher removes each socket once QEMU has connected. QEMU is an attempt of the launcher's own executor, registered before its exec and cleaned up with its descendants. `etude_exec_watch` waits for the executor's descriptors and the sockets together, so that a QEMU that ends before it connects is seen at once.

On QMP the launcher answers QEMU's greeting with `qmp_capabilities` and asks `query-accelerators` which accelerator QEMU uses; a QEMU that lacks the command is asked `query-kvm`, which tells only whether KVM is in use. When QMP names the accelerator asked for, `cont` starts the machine and its state becomes running. Every byte of the console is kept in memory up to the case's bound, counted past it, and written to the attempt's console file when it has one.

The end of a machine is told by these rules, in order:

| End | Observed |
| --- | --- |
| `accel_failed` | QMP named another accelerator, and the launcher made QEMU quit; or QEMU ended before the machine ran with a line of its standard error that its location of the option begins, `PROGRAM: -accel NAME: `, as QEMU writes when it cannot start an accelerator or does not have it |
| `stopped` | The caller cancelled the machine before its end |
| `shutdown`, `reset`, `panic` | QMP's event `SHUTDOWN` of the guest, with the reason `guest-shutdown`, `guest-reset` or `guest-panic` |
| `qemu_exited` | QEMU ended otherwise: a `SHUTDOWN` of the host, such as a signal, or an exit without an event, whose status the executor keeps |
| `lost` | QMP answered what the launcher cannot use, or QEMU's keeper ended before it reported QEMU's end |

The console is read again when the event arrives, so the offset of the end counts every byte QEMU wrote before it. A cancellation sends QMP's `quit` when QMP is past its capabilities, and the executor's cancellation, SIGTERM and then SIGKILL, when QEMU has not ended within the grace period, or at once without QMP. QEMU is never stopped by a signal and then asked to answer QMP.

Once the machine runs, the caller may send QMP commands of its own with `etude_machine_qmp` and read each reply by its id, from 100 up; the launcher's own ids are below 100. A QMP line is kept up to 1 MiB, so that the registers of 64 processors fit.

### The serial controller

[`serial.c`](serial.c) is the controller's side of `etude-guest`'s serial transport, as [`serial.h`](serial.h) declares it. It does no I/O and reads no clock: its caller feeds it the console's bytes with the time, writes the frames it makes through a callback, and calls it again at the time `etude_serial_deadline` gives. A session starts at `etude-guest`'s `alive` with a hello under SEQ 0, and its token is the digest of a name the caller gives, unique to the controller. At most four sequenced frames are in flight, so that a window fits the 4096 bytes of Rach2's serial receive ring; once the oldest has waited the resend interval, every frame in flight is sent again with its SEQ and bytes. Every call that received sequenced frames is answered by one `ack`. An event of an earlier operation's command is passed by, since `usage` and `cleaned` follow an error; an event of a command never sent ends the operation as a protocol fault, and so does a frame of the session whose CRC is right but whose fields do not parse, such as the old ten-field `exit`. A run ends with `exit`, a `stream` for descriptor 1 and then 2, `usage` and `cleaned`, and its output is complete when each stream's bytes match the size and digest of its `stream`. An `alive` of another process or boot is an `etude-guest` that started again, and loses the session.

### libetude-case

[`posix/scenario.c`](posix/scenario.c) reads the scenario invocation and the case's manifest, opens the store and makes one launcher, on whose executor the host tools also run, so that one wait, `etude_qemu_watch`, serves the machines, the host programs and the pipe that the handlers of SIGTERM, SIGINT and SIGHUP write. Each wait of the interface is that wait in a loop: after each return it judges the machines' results and, for a helper machine, feeds the console's new bytes to the serial controller, and it ends at its event, at the end of the machine or its console, at the step's bound or at a stop. The bound of a step is a deadline taken when the step begins, and no wait reaches past it. A machine's console and its end are the launcher's alone, so the library reads no record the kernel prints, and a text found on the console is found in what QEMU wrote, from the offset the caller gives.

The library is the only writer of the report, and writes each record with one write(2) after flushing standard output. It counts the scenario's assertions as it writes them, so that it can tell at the cleanup whether every declared one was given once and held, and a request refused, failed or lost through the interface counts as a fault of its own. A guest attempt's records come through `etude-guest`'s `out` frames: the library cuts them into lines, checks that `begin` names the scenario's case, writes the assertion, branch and progress records as its own, and drops `end`, `child` and the rest, since the scenario's report has one `begin` and one `end`.

### The watchdog

[`watchdog.c`](watchdog.c) keeps the watchdog of one attempt in plain C, with the time given by its caller. It reads the case's standard output a line at a time for progress records, and follows the stage the attempt is in. Its deadline is the earlier of the whole case's bound from its start and the bound of its stage: in execution, the gap bound from the later of the last progress and the start of execution, or while a quiet witness's work runs, that witness's bound from its announcement; in any other stage, the stage's bound from its start, when the case declares one. The longest gap of execution, the first and the last included, is the history's `max_progress_gap_us`. The first bound that runs out is kept, with a copy of the progress at that time: the stage, the time of the last progress, the witness that advanced last, and the counts of progress records, heartbeats, records refused and output since the last progress.

[`posix/supervise.c`](posix/supervise.c) runs attempts under their watchdogs on Linux and macOS: host attempts on an executor of its own, machines on a launcher of its own, and remote attempts on a running Rach2, whose transport the caller keeps, feeding the case's output and reporting its end and cleanup as `etude-guest`'s `out`, `exit` and `cleaned` frames give them. A host attempt's watchdog reads the case's standard output as far as the executor keeps it, and a machine's reads the console when the caller asks, as for a designated init's report, or what the caller feeds. A host or remote attempt is in execution from its start, and a machine in its boot until the caller moves it on. When a watchdog runs out, the supervisor:

1. marks the attempt incomplete and starts nothing more for it;
2. saves the progress at the expiry, the processes it owns (the keeper and the case's process, or QEMU's keeper and QEMU), a sample of the case's process or QEMU's, its processor time with the children it has reaped and its resident memory, read from `/proc` on Linux, and a machine's last twenty console lines;
3. for a running machine, sends QMP's `query-status`, `query-cpus-fast` and `human-monitor-command` with `info registers -a`, keeps each reply that comes within the capture stage's bound, or the grace period when the case declares none, and records each that did not; a QMP that hangs or has closed cannot make the wait longer;
4. asks the case to stop: a host case gets SIGTERM and SIGCONT through the executor, and a guest or remote case gets the caller's request, such as a `cancel` frame, and the grace period to report its end;
5. ends what it owns: a host case's tree gets SIGKILL after the grace, and a machine QMP's `quit` and then the executor's SIGTERM and SIGKILL;
6. finishes the attempt once the executor or the launcher has reaped what it owns and found the cleanup confirmed or not.

A remote attempt's end and cleanup are those the case reported. One whose transport is lost, or whose case reports no end within the grace after the ask, ends `lost` with its cleanup unconfirmed; a lost transport finishes it at once, without waiting for a bound, while the other attempts go on. An attempt whose cleanup is unconfirmed keeps its claims, as the result's `claim_kept` says, for the caller to keep reserved.

### Repetitions

[`posix/repeat.c`](posix/repeat.c) runs a plan of repetitions on Linux and macOS, as `etude_repeat_run` of [`repeat.h`](include/etude/repeat.h) declares. It keeps the repetition record in the store, writes the plan record, and runs the items in their order, `width` cases at once, on a supervisor of its own:

* Each attempt is admitted through the ledger, its load's claim before its case's, in the plan's order; while the attempt at the head waits for room, none after it is asked for. A load and a case that together exceed the machine's limits, and a claim the ledger refuses, end the attempt incomplete without running it.
* A load starts first, in a claim and a process group of its own, under a bound on its start that the site gives. Its case starts only once the load has written `etude-load: ready`, and the load is cancelled after its case has ended. A load that ends before its case is a disruption of the attempt, recorded beside its outcome.
* The case runs under its watchdog. An attempt passes when its case exits 0 within its bounds and the cleanup of the case and of its load is confirmed; it is a failure when the case exits otherwise or is killed by a signal; and it is incomplete when a bound ran out, its end was not observed, a cleanup is unconfirmed, or its load was never ready.
* An attempt that did not pass, unless admission refused it, is retried after every planned item, under the same load, until `retries` more attempts have run. A retry is an attempt of its own, `ITEM:aK`, whose record names the attempt it repeats in `previous_attempt_id`, and the plan lists every attempt identity an item may use.

The run record lists each item's attempt records and gives the item the worst of their outcomes, failure before incomplete, incomplete before cancelled and cancelled before pass, and the run the worst of its items'. A retry that passes thus leaves the item and the run a failure, and the failed attempt's record, its results and its output stay in the history; the run's reason names each case whose undisrupted attempts both passed and failed or did not finish as possibly flaky. Each attempt's results document gives its termination, as the executor saw it, and the `etude.termination` assertion. The store also gets the run's stage and family totals, its useful concurrency, and the loads applied, with the times they were ready and ended and their processor time. The budget is recorded with the verdict `unknown`, since the driver judges no budget.

`etude_repeat_tally` reads a history: of each case, architecture and workload, the attempts that passed, failed, did not finish or were cancelled, the retries among them, and the attempts with a disruption, which are counted apart, since their conditions were not those declared. A case is possibly flaky when its undisrupted attempts both passed and failed or did not finish, within one run or across several. A flaky case stays selected; nothing is quarantined or skipped.

`etude-load KIND AMOUNT` ([`posix/load.c`](posix/load.c)) applies a load until it is killed: `cpu N`, N processes that spin; `memory BYTES`, an allocation with each page written; and `disk BYTES`, a file of its working directory, unlinked once it is open, written and synchronized again and again. Admission reserves N thousand `cpu_millis`, or the bytes as `memory_bytes` or `disk_bytes`. It writes `etude-load: ready` with one write(2) once the load is in effect, and exits 2 for a wrong usage and 1 when it cannot apply the load.

### Remote execution

[`posix/serve.c`](posix/serve.c) is the responder of one connection, which `etude-remote` runs: it runs attempts through [`exec.h`](include/etude/exec.h), and reads the connection and serves the attempts in one loop. Its state directory has `evidence`, each line it did not act on with the reason, and a directory for each session, named by SESSION:

| Path | Contents |
| --- | --- |
| `lock` | The lock that the session's responder holds from its `ready` to its end |
| `cmd/CMD` | A command's record: the command's digest, the command, and each event it caused, a line each |
| `att/ATTEMPT` | An attempt's record: `run CMD`, and `process PID START` once its child is registered |
| `blob/SHA256` | A stored file, named by its digest; `blob/CMD.part` while its data arrive |
| `work/ATTEMPT/` | The attempt's workspace |

A command's record is made and synchronized before the command acts, and each event is recorded before it is sent, so that a command repeated after any loss is answered by what it did. A put's record is made at its seal, since nothing before the seal has an effect: a put cut short leaves no record, its partial file is removed, and the put sent again is acted on. An attempt's record is made with `O_EXCL` before its workspace, and its child's identity is synchronized into it before the child runs. On taking the lock, a responder records the end of each attempt whose run has none, which only a responder that was killed leaves, as `lost` with its cleanup unconfirmed, and removes the partial files of puts. Each file an invocation lists is copied from `blob/` into the workspace with the invocation's mode and checked by its digest again; `${WORKSPACE}` in an argument or an environment value is the workspace's path, the program runs there, and its standard input is `/dev/null` or a file of the invocation.

[`posix/remote.c`](posix/remote.c) is the controller's side. `etude_remote_open` starts the command `argv` gives, whose standard input and output are the connection, and requires the first frame to be `alive` with a version in common; text before it, as a shell's startup files print, is kept as evidence. Each command goes into the journal, with `fsync(2)`, before it is sent, and a controller that opens the journal again continues after its highest number. `etude_remote_put` sends a file, and a file refused as damaged is sent again under a new command. `etude_remote_run` stores the invocation, sends `run`, and takes the run's events: an event sent again must equal the first, output sent again must have the same bytes, and the attempt is complete when `started`, `exit`, a `stream` for each descriptor, `usage` and `cleaned` have arrived and each stream's output matches the size and digest of its `stream`. When the connection is lost or the responder breaks the protocol, it starts the command again, up to `reconnects` times in one operation, and sends the run again under the same CMD. The responder answers it from its ledger, so the attempt runs once, and gives the end the earlier responder recorded: the program's own, or `stopped` when the lost connection cancelled it. A responder in another boot leaves the attempt's end lost. At the caller's deadline the run sends `cancel`, and an attempt whose end does not come within its own deadline, its grace and two stage bounds after it was sent is taken as lost. `etude_remote_close` sends `bye`, closes the command's input and waits a stage bound for it to end, then sends it SIGTERM and SIGKILL.

### The artifact store

[`posix/store.c`](posix/store.c) publishes an object in four steps: it makes a partial file in `tmp/` with mkstemp(3) and takes a write lock on it with fcntl(2), copies the source into it while hashing it, synchronizes it and makes it read-only, and links it to `objects/DIGEST` with link(2), which fails when that name exists. A name in `objects/` therefore shows a whole, synchronized file or nothing, whatever ends the writer. When the name exists, the object there is read and checked: a good one is kept, so its inode does not change, and a damaged one is replaced with rename(2); a file system without hard links gets the rename too. A put with an expected digest, as a transfer has, refuses other content before anything is named. A record is written the same way, after its object, so a record that a reader finds refers to an object that exists; it is renamed to its key, replacing a damaged record or one whose object was damaged, and only the process that has the key's lock writes it.

A writer keeps its partial file's lock from the file's making until its removal. A sweep, which opening a store runs, tries a read lock on each partial file and removes those whose lock it gets, since their writers have ended. A sweep that takes its lock between a writer's mkstemp(3) and the writer's own lock makes that writer find its lock refused or its name gone, and make another file.

### Preparation

[`posix/prepare.c`](posix/prepare.c) checks a graph before it runs anything: every input is a node of the graph, every `${IN:NAME}` refers to an input of its node, and a depth-first walk finds no cycle. It then takes each node whose inputs are done. A node with a failed or blocked input is blocked; a file of the tree is published; any other node is reused when its record's object checks, and otherwise runs its recipe once it has its key's lock and one of the run's jobs is free.

A write lock on `locks/KEY` keeps two processes from running one key's recipe. The second tries the lock again every 20 ms, looks the key up again once it has the lock, and reuses what the first published; a node whose wait passes its bound fails. The lock goes with the process that had it, so a controller that is killed leaves nothing locked.

A recipe runs through the executor, in a work directory that mkdtemp(3) makes under the run's scratch directory, and is cancelled when it runs past its bound. Its product is published only when the recipe exited 0 and the executor confirmed that each of its processes has ended, so that nothing still writes the file. The product must be a regular file, not a link, and is copied into the store, so a later write in the work directory does not reach the object. The work directory is removed after a success and kept, with what the recipe left, after a failure, and the node's result gives the recipe's end, its standard error as kept and the reason it failed.

### The proof driver

[`proof.c`](proof.c) reads a catalogue with the strict JSON reader, checks it against its schema and then by its own rules, and makes the edits; [`posix/proof.c`](posix/proof.c) runs the proof. It saves each source whole, in memory and in `WORK/saved`, from which a person restores a shared tree should the driver be killed with SIGKILL, and for a private proof writes the copies under `WORK/src`. A source is written whole to a new file beside it, given its mode, renamed over it and read back, so a reader sees the old text or the new one. A build that judges by time stamps, as make(1) does, would take a source written within the second of an artifact for an old one, and an artifact may have a time ahead of the clock; the driver therefore sets a source's time to one second past the newest artifact's whenever the source is not newer. The restored phase's comparison with the base's digests finds a build that still did not make its artifacts again.

The build and the test run through the POSIX executor in the tree's root, with the driver's environment and standard input from `/dev/null`, and their output is kept in the work directory as `PHASE.build.out`, `PHASE.build.err`, `PHASE.test.out` and `PHASE.test.err`. The driver looks at a running command every 100 ms for its bound and for a signal. SIGHUP, SIGINT and SIGTERM set a flag: the driver then cancels the command, which the executor ends with SIGTERM and with SIGKILL two seconds later, restores the sources and removes the work directory. A shared proof requires the tree's run lock: the lock's owner file, `build/.run.lock/owner`, must name the process that `RACH2_TREE_HELD` names, and that process must run. `proof.sh` takes the lock through `runlock_exec.sh`, which passes a signal on to the driver once.

It returns 2 for invalid input or a lost final record. The normal host-tools build includes it. Executors link `history.c`, `history_json.c` and `history_collect.c` and `utils/sha256.c`, and include `include/`. The controller's side, `posix/remote.c`, is built by nothing yet but its host test. The Windows executor is `capture.c`, `win/exec.c`, `win/winexec.c`, `win/winsys.c` and `win/winfmt.c`, built with MinGW-w64 and linked with `-lws2_32`; nothing builds it yet but `wincheck.sh`. No Makefile target builds it yet; its host test compiles it with these sources, and a scenario links with the same list.

## Limits

The history store checks record shapes, stream order and local interval arithmetic. The executors other than the POSIX and Windows ones and the QEMU launcher of Windows are not implemented, and `tests/cases/` has no manifest. The probes print their own lines and are judged by their exit status, as `tests/run` judges them now. A schema-valid document alone does not establish a complete case, a valid report or a pass. Cross-stream references, hashed content, assertion coverage and aggregate results require the consumer's checks.

The comparison finds blobs only in the store that `-b` names, by digest, and not at the locations a blob reference gives. It matches the cache-state and load snapshots by digest without reading them, and takes the run record and its disruptions as the account of the load, since no part defines the snapshots' contents yet. The plan does not say whether its checkout was modified, so the comparison cannot leave such samples out. It records no equivalence review: a changed workload or assertion inventory always starts a new baseline. It compares cases and their steps, not whole runs, and a step that runs more than once in an attempt is not compared.

The POSIX executor's callers are the QEMU launcher, the supervisor, `etude-remote` and their tests. It waits for the keeper's handshake inside `etude_exec_start`, and is used from one thread. Signals to the case's process group after the case's process has been reaped could reach a group whose number the system has reused. Elsewhere than Linux, macOS and Rach2 a process's start cannot be read, so a `child` record makes the cleanup unconfirmed.

The ledger, the schedule and the costs have no caller but their tests. A worker whose request waits must ask again to be admitted, since the ledger sends no notice when a claim ends. The machine's limits are an argument of each call and are not kept in the ledger, so workers that give different limits are judged by their own. Deployment gives each account a ledger of its own unless `-L` names one that several share. A ledger is judged by processes of one operating system, so Windows and Linux in WSL on one machine cannot judge each other's claims. A process group number that an unrelated group has reused keeps a claim until that group ends. Several accounts can share a ledger only in a directory where each may replace the others' files, which a sticky directory forbids.

`bootstrap.sh` has not run on a Windows machine, and on Rach2 it has run only under QEMU, in the `etudeexec` suite. Its test runs the Windows path under stand-ins for MSYS2's `uname` and `cygpath`, and BusyBox's sh and tools where the host has BusyBox, but neither MinGW-w64 nor Rach2's TinyCC. Without a terminal, sshd sends no signal when a connection is lost, so a build goes on and publishes its version, which the next request reuses. A build stopped by SIGKILL leaves its directory, which nothing deletes.

`deploy.sh` has not deployed the Mac, Windows or Rach2. Its test runs the POSIX path over a stand-in for ssh(1), and the Windows path under stand-ins for PowerShell, MSYS2's `uname` and `cygpath`, and QEMU for Windows. Nothing reads the machine record yet, so a worker is given its ledger and its limits by its caller. The record's processors and memory are the whole machine's and not the share an account is given, and its accelerators are those the account can open, whichever QEMU was built with. A ledger that several accounts share needs each to be able to write it, which deployment checks and leaves to the ledger's owner to grant. A deployment stopped by SIGKILL leaves the record's temporary file, `machine.XXXXXX`, or the scratch copy of the prerequisites, `rach2-etude-prereq.XXXXXX`, which nothing deletes.

The responder and the controller's side are POSIX programs; neither has a Windows adapter, and the serial transport's acknowledgements are `etude-guest`'s. `etude-remote` runs the `ordinary` role alone and makes the `workspace` fixture alone, refusing an invocation that asks for another. It serves a `get` of a file directly in a workspace, `TOKEN/work/FILE`, and answers any other name, `out.1` and `out.2` among them, with `error unknown`; it has no `--stage` directory, and a put of a file it has stored before still sends the data. Nothing but the host test drives the controller's side yet. The CRC and the digests find damage by accident; a deliberate change of a frame is SSH's to refuse. A responder waits for the session's lock without a bound, so one that cannot end keeps the next responder's `ready` back until the controller's stage bound passes. `bye` removes a session's stored files, and nothing removes its ledger. A repeated command's events are sent again in frames of the size they were recorded in, so a controller offers the same largest frame on every connection of a run. The controller's side does one operation at a time, and the responder writes events while the controller sends a file only when an attempt from an earlier operation still runs.

`casecheck report` reads a file of output, not a live transport, and judges only the assertions whose source is the program; the executor's assertions need the end and the console that only an executor sees. No executor sets `ETUDE_CASE` yet, and a probe that `tests/run` starts from the debug shell reports under the identity it has for its first case, such as `guest.default.rngprobe`. The probes that write report records are `rngprobe`, `xsaveprobe` and `fpuprobe`. The source checks of `suitecheck.sh` read the forms a line shows: a sleep through a probe's own wrapper is found at the wrapper's system call, and a skip only where a line prints it.

`etude-guest` makes only the `workspace` fixture, which must give no arguments, and the `stage` fixture, whose arguments name stored files; an invocation with another fixture is refused with `error refused`. It runs no case natively on the Lenovo yet. On the serial console a frame is at most 255 bytes, so an `out` frame carries 78 bytes of output, and an event that does not fit the bound, such as the `stored` of a long file name, is sent as `error CMD limit` instead.

The QEMU launcher has no caller but the supervisor, `libetude-case` and the tests, and is used from one thread. It reads no kernel record from the console, so a panic printed there, a machine whose processors have all halted and the designated init's end are for its caller to find. Its profiles give the device names of the table above and IDE disks alone.

`libetude-case` has no scenario but its test's, and is used from one thread. It starts `etude-guest` only on a machine whose console reaches the kernel's debug shell, with `--stage /`, and finds the shell by its greeting. It runs guest invocations of the `ordinary` role alone, and refuses one of `init`. It reads only the first `console_max_bytes` of a console, which the launcher keeps, so a wait for text not in them, and a session of `etude-guest` that runs past them, are lost. A host tool's output is kept to `output_max_bytes`. A step's bound covers its waits, and not the scenario's own work between them.

The serial controller keeps four frames in flight, so a put of a file waits for an acknowledgement after every four data frames of about 140 bytes each. It numbers its commands from 1 in each session, so two controllers that drive `etude-guest`s sharing a state directory need names of their own; `libetude-case` gives each boot's attempt identity. An `etude-guest` that starts again while a session opens loses the open rather than receiving a new hello.

The supervisor has no caller but the repetition driver and the tests, and is used from one thread; while it runs host attempts and machines at once, it serves each kind in turn for 50 ms at most. Nothing yet gathers a bound's samples from the history, so the caller gives them to `etude_bound_fix`. A watchdog sees only the output its executor or launcher keeps, so the progress of a case that prints past its output's bound is not seen, and the case runs out of its gap. A process is sampled on Linux alone. Windows has no supervisor yet, and nothing connects it to the controller's side of remote execution: the caller feeds a remote case's output and reports its end and the loss of its connection.

The repetition driver has no caller but its test. It runs host cases alone, and on Linux and macOS alone, and judges a case by its exit status, not by report records. It asks the ledger again every 100 ms while the attempt at its head waits, since the ledger sends no notice. It samples neither the machine's load from outside the run nor combined memory, and its records say so. A seed fixes the order and the loads and not the host's schedule, so a race that depends on timing may need several runs of one seed to show. `etude-load` is not in a cached version, so a machine other than the controller's has none yet, and Windows has no load fixture.

The artifact store and the preparation graph have no caller but their test, and no Windows adapter. A product is one regular file, so a directory, such as the GNU root, is not yet an artifact. A lookup reads the whole object, which costs a read of every reused artifact on each run. A node's key covers only what its definition gives, so a recipe that reads a file that is neither an input nor in its key text is reused after that file changes. A recipe may change an input's object, which is read-only but owned by the same account; the next lookup finds the damage and makes the node again. Nothing removes an object, a record or a lock file, so the store grows without a bound until admission and retention account for it, and the work directories of failed recipes stay for their caller to remove.

The proof driver runs on Linux and macOS alone, and has no Windows adapter. Nothing runs a catalogue yet but a person and the driver's test: the `*_mutate.sh` proofs move to it in tasks of their own, and `tests/proofs/` has no catalogue yet. The comparison of artifacts needs a build that makes the same bytes from the same sources, so a build that writes a time or a random name into its product cannot be proved by the driver. A shared proof killed with SIGKILL leaves its fault in the tree, with the saved sources in `WORK/saved`. The check of the run lock reads the owner file and the process it names, and does not check that the process is an ancestor of the driver. A test's failure is read from its exit status and its lines, not from report records.

`etude-host` reads no manifest and no report records. It judges a check by its exit status alone, takes its bound from the selection and not from the history, and records no history. It compiles each check's program again in every run, since a key in the artifact store would not cover the headers the program includes. It runs on Linux and macOS alone.

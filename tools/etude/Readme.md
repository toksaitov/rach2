# Etude

Etude is a test runner in hosted C99 for Linux, macOS, Windows and Rach2, with `etude-guest`, its helper inside Rach2, built to take the place of `tests/run`. Until it does, `tests/run` starts every suite, and these parts of etude are in use: the host suite runs its checks through `etude-host`; the style check runs `casecheck` and `etude-proof --texts`; ci's report reads a run's history with `history_failures` when a result has one; bisection runs each test of an old commit through `etude-bridge` on a machine where etude admits tests; `tools/flow/test_status.py` reads its status records and ledgers; and the suites `etudeguest` and `etudeexec` test `etude-guest` and the executor on Rach2. This directory implements the history store, the comparison of a run's times with that history, the compatible formatter, which prints a run's history as the lines of `tests/run`, the status record of a run, the executors of host processes on POSIX systems, Rach2 among them, and on Windows, the QEMU launcher on POSIX systems and the processor profiles of its machines, the ledger of a machine's resource claims and the admission of new ones, a worker's schedule of both architectures, the per-case watchdog and the supervisor that runs attempts under it on POSIX systems, shuffled and loaded repetitions with their load fixture, remote execution over frames, the store of immutable artifacts and the preparation graph that makes them on POSIX systems, `etude-legacy`, which builds what the suites of `tests/run` read before one starts, as `tests/run` builds it, and runs a prepared suite under the supervision of `tests/run`, `libetude-case`, the library of machine scenarios on POSIX systems, with the controller's side of `etude-guest` on a serial console and the services that run beside a scenario's machines, the driver of mutation proofs on POSIX systems, the budget of routine testing, which forecasts a selection's time from recorded costs and checks a run's time from its records, `etude-host`, which runs the host checks of `tests/run host` several at once, the cache of etude's versions on a machine, the deployment that makes a machine ready to run etude, the local Linux tooling machine that runs the commands a host lacks, and `etude-guest`, and defines the contracts the runner parts share: the case manifest, the report a test program writes, the results of an attempt, the frames between the controller and `etude-guest`, the invocation of a guest case, the interface of a machine scenario, the repetition record, the catalogue of a mutation proof, the budget policy, and the history of runs. Its validator, `casecheck`, checks manifests, reports and results against them, and gives ci and bisection their verdict on a run from the run's history.

## Use

`casecheck` is built by `make build/tools/etude/casecheck`, and `tests/run style` runs it through [`suitecheck.sh`](../verify/suitecheck.sh) over `tests/cases/*.json` and the examples here, and with `--selftest` over [its fixtures](fixtures/expect). Its commands:

    casecheck [-s SCHEMAS] [-r ROOT] manifest FILE...
    casecheck [-s SCHEMAS] [-r ROOT] timing FILE...
    casecheck [-s SCHEMAS] [-r ROOT] families FILE...
    casecheck [-s SCHEMAS] report [-f FEATURE=present|absent]... MANIFEST CASE ARCH PLACEMENT [OUTPUT]
    casecheck [-s SCHEMAS] attempt [-f FEATURE=present|absent]... [-k CONSOLE]... MANIFEST CASE ARCH PLACEMENT OUTPUT RUN ATTEMPT ITEM END [VALUE]
    casecheck [-s SCHEMAS] results [-o OUTCOME] RESULTS MANIFEST...
    casecheck [-s SCHEMAS] schema NAME FILE...
    casecheck [-s SCHEMAS] verdict [-b STORE] [-c COMMIT] [-m CASES] ARCH SET SUITES HISTORY...
    casecheck processor NAME
    casecheck --selftest DIR

`version.sh` builds etude's programs from the source of this tree, or of a commit, on a machine that has a POSIX sh, make, a C compiler and a SHA-256 tool and nothing of etude, unless that machine's cache has them built already:

    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] [-w] HOST
    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] -l
    sh tools/etude/version.sh [-r REV] [-c CC] [-C CACHE] -s

It reaches HOST through ssh(1), a Windows machine with `-w`; `-l` builds on this machine and `-s` prints the script it would send. `-c` gives the compiler's command line and `-C` the cache, each by default the platform's. It prints `etude-version: result: built KEY DIR` or `etude-version: result: reused KEY DIR`, DIR being the version's directory on the machine, whose `bin/` has the programs, and exits 0; it exits 1 when the version is neither built nor found.

`deploy.sh` makes a machine ready to run etude: it checks the machine for the prerequisites of [`tools/setup/prereqs`](../setup/prereqs) and installs those the account may, builds etude there with `version.sh`, prepares the ledger of the machine's claims, and records what the machine can do:

    sh tools/etude/deploy.sh [-n] [-r REV] [-c CC] [-C CACHE] [-S STATE] [-L LEDGER] [-w] HOST
    sh tools/etude/deploy.sh [-n] [-r REV] [-c CC] [-C CACHE] [-S STATE] [-L LEDGER] -l

HOST, `-w`, `-l`, `-r`, `-c` and `-C` are as for `version.sh`, and `-n` installs nothing. STATE is the directory of the machine's record and LEDGER the ledger's, each a path on the machine and by default the platform's (The machine record). The owner provides the SSH access. Deployment creates no account or key, changes no clone, deletes nothing of the machine's, writes no raw disk, restarts nothing and stops no test, and a run after one that finished or was cut short changes only what the earlier one left undone. It prints each step and its output, with the commands left for an administrator or a person at the machine, and last `etude-deploy: result: deployed KEY` and exits 0, or `etude-deploy: result: incomplete: WHY` and exits 1 when a prerequisite is missing or a step failed; it exits 2 on a wrong usage.

`etude-remote` is the responder of remote execution on Linux and macOS. `make build/tools/etude/etude-remote` builds it, and a cached version has it in its `bin/` on those systems. A controller runs it through ssh(1) without a terminal, as `ssh -T -o BatchMode=yes HOST DIR/bin/etude-remote --stdio -d STATE`:

    etude-remote --stdio -d DIR [-b BOOT] [-m MAXFRAME]

It speaks frames on its standard input and output until the controller's `bye` or the end of the connection, and keeps its ledgers, files and workspaces under DIR, which it makes when it is missing. BOOT is the token of the machine's boot, by default the digest of Linux's `boot_id` or of macOS's `kern.boottime`, and MAXFRAME the largest frame it takes, 65536 by default. Its diagnostics go to stderr. It exits 0 after a `bye`, 1 after the connection was lost or broken, and 2 for a wrong usage or a DIR it cannot use.

`etude-native` runs one case on a Rach2 machine that is already up, such as the Lenovo, through `etude-guest --stdio` on that machine. `make build/tools/etude/etude-native` builds it on Linux and macOS:

    etude-native -R RUN -a ATTEMPT -c CASE -j JOURNAL -t TRANSPORT -f FILE... [-d MS] [-g MS] [-o BYTES]
                 [-x MS] [-s MS] [-r N] [-e EVIDENCE] [-E NAME=VALUE]... [-k] [--] PROGRAM [ARGUMENT...]

TRANSPORT is a command, run by `/bin/sh -c`, whose standard input and output reach `etude-guest --stdio` on the machine, such as `ssh -T -o BatchMode=yes root@HOST DIR/etude-guest --stdio --state DIR/state`. RUN, ATTEMPT and CASE are the identities of the run, the attempt and the case, in ASCII. JOURNAL is the file of the run's commands, which a later `etude-native` of the same run reads so that it never reuses a command's number. Each FILE is stored under its last component, with mode 0755 when it is executable and 0644 otherwise, and PROGRAM, the name of one of them, runs in the workspace with the ARGUMENTs and the environment of Native runs, to which each `-E` adds a variable. `-d` is the attempt's deadline, which `etude-guest` keeps, 600000 milliseconds unless given; `-g` its grace period, 5000; `-o` the bytes kept of each stream, 1048576; `-x` the controller's deadline, at which it cancels the attempt, none unless given; `-s` the bound of a connection and of each answer, 30000; and `-r` the connections made again within one operation, 3. EVIDENCE receives the lines not acted on. It prints the case's standard output on its own standard output and the case's standard error on its standard error, and then the result:

    etude-native: result: VERDICT: case CASE, attempt TOKEN: END; process PID, cleanup CLEANUP, reconnections N

TOKEN is the attempt's token, PID the case's process, CLEANUP `confirmed` or `unconfirmed`, and N the connections made again during the run. It removes the workspace after a pass unless `-k` keeps it. VERDICT is `pass`, with exit status 0, for an exit with status 0 whose cleanup is confirmed; `failure`, 1, for another exit, a signal, or a stop at the attempt's own deadline; `cancelled`, 3, for a stop at the controller's deadline; and `incomplete`, 4, when the whole end did not arrive, when it was lost with an `etude-guest` that was killed, when the attempt stopped because its connection was lost, or when it exited 0 with its cleanup unconfirmed. END says which, and a line `etude-native: why: WHAT` follows a run whose end did not arrive. A wrong usage exits 2.

`etude-host` runs the host checks that [`tests/system/suites/host.sh`](../../tests/system/suites/host.sh) selects, several at once, on Linux and macOS. `make build/tools/etude/etude-host` builds it, and `tests/run host` runs it:

    etude-host [-j JOBS] -l LOGS -s SCRATCH SELECTION

SELECTION has one check a line, in six fields separated by tabs: the NAME of the check, of letters, digits, `_`, `.` and `-`; its bound in SECONDS, from 1 to 86400; its MODE, `shared`, or `alone` for a check that runs with no other beside it; the LABEL of its result line; the COMPILE command, which may be empty; and the RUN command. A line that is not a check, or a name given twice, refuses the whole selection before any check runs. JOBS is the most checks that run at once, by default the processors online. A step's output goes to `LOGS/NAME.clog` or `LOGS/NAME.rlog`, and each check has the empty directory `SCRATCH/NAME` as its `TMPDIR`. The program prints a line for each check as it ends, `PASS: LABEL` or `FAIL (WHY; see LOG): LABEL`, and a last line that counts them. It exits 0 when every check passed, 1 when one failed, 2 for a wrong usage or a refused selection, and 128 plus the signal after SIGTERM, SIGINT or SIGHUP, which end the running checks.

`manifest` checks each manifest's shape by its schema and then the rules below that relate its values: identities given once, alternatives that name declared assertions, an assertion's source that its domain has, a role that agrees with its end and its native plan, artifacts that `prepare` makes, a profile's disks that the launcher attaches together, processor profiles and the features they declare, captures of the profile's own network cards, devices on buses that earlier devices give, each disk on a device attached by one device and each device's drive such a disk of the profile, bounds in order and inside the whole case's, the fixtures each placement has, forwards and guest forwards of a scenario's machines that the case's ports allow, suspensions of the case's own machines, each counting its stops on a counter witness of its own whose limit covers its cycles, and, with `-r`, a `where` that names a line of the tree at ROOT. `timing` checks them so and prints each line a timing assumption declares, as `FILE:LINE KIND CASE`. `families` checks them so and, when none has a finding, prints one line for each, `FAMILY_ID FILE`, in the order given; the last part of the family, split at dots, is the suite that runs its cases. `report` judges a program's output as an executor will, by Report records, and prints each assertion the program must give, the report's state and the outcome; it exits 0 only for a pass. `attempt` judges OUTPUT, a file or `-` for standard input, as `report` does, and prints the attempt's results document as one line of JSON, with the run, attempt and item identities RUN, ATTEMPT and ITEM. END is how the program ended as the executor saw it: `exited` or `signaled`, with the status or the signal as VALUE, `stopped` when the executor stopped it, or `lost` when its end was not observed. The document gives `etude.termination` from END, observed by `host_process` for a host case and a machine case's scenario and by `etude_guest` for a guest case; `etude.report` from the report's state when the case has assertions of its program or its scenario; and `etude.kernel` for an attempt that has it. Each `-k` names a console of the attempt's QEMU machines, given only for the placement `qemu`; for a machine case each is a `MACHINE.N.console` that `libetude-case` keeps. With them, `etude.kernel` fails with the first line, in the order the consoles are given, that begins `<2>[`, a record of the kernel's critical level, which only a panic and a fault of the kernel write. It passes by a line with the text that the console's machine declares as `critical`, and by a `panic` record when the case expects the end `panic`, and passes when the consoles have no other such line. A declared assertion whose source is the executor passes when a console has its `record` and fails when none has. Without `-k`, `etude.kernel` and an assertion of the executor are missing, since the command reads no console and not the kernel's log. The document is printed only when `results` would accept it, and the status is its outcome: 0 for a pass, 1 for a failure and 3 for an incomplete attempt. The status 2, with no document, is for a wrong usage, `-k` with `report` or with a placement other than `qemu`, a manifest, output or console that cannot be read, a case the manifest lacks, a placement or architecture the case cannot have, or a case with no assertion of its program whose output has report records. `results` checks each document of a JSON Lines file by Results, and with `-o` refuses an attempt whose assertions give another outcome than the one a history records. `schema` checks documents, or the lines of a `.jsonl` file, against `schemas/NAME.schema.json`. `verdict` judges one run from its history, for [`tools/ci/run.sh`](../ci/run.sh), as The verdict says. `processor` prints the QEMU `-cpu` value of a processor profile, for a script that boots QEMU itself. A finding goes to stderr as `casecheck: FILE:LINE: WHAT`; the status is 1 after one and 2 for a wrong usage or a file that cannot be read, except that `verdict` counts a history it cannot read as a finding. SCHEMAS is `tools/etude/schemas` by default.

    etude-guest [--stdio] [--state DIR] [--stage DIR]... [--resend-ms N]

`etude-guest` takes the controller's frames on its standard input and sends its own on its standard output. Without `--stdio` they are the serial console, under QEMU: the kernel's debug shell starts it with `exec /etude-guest`, so that it is the boot's designated init, and it puts the console in raw mode. With `--stdio` they are the pipes of an SSH session on a running Rach2, and the program exits when the session ends. `--state` names the directory of its files, the stored files, the records and the workspaces, `$TMPDIR/etude-guest` or `/tmp/etude-guest` by default. Each `--stage` directory, eight at most, is searched for a file the controller would otherwise transfer. `--resend-ms` is the interval after which an unacknowledged frame on the serial console is sent again, and `alive` is repeated, 2000 by default. The exit status is 0 after `bye`, 1 when the connection was lost or the state could not be made, and 2 for a usage error.

A machine scenario is a program linked with `libetude-case`:

    SCENARIO INVOCATION

It runs one attempt of its case from the scenario invocation in the file INVOCATION, writes the case's report on its standard output and its diagnostics on its standard error, and exits 0 when its scenario passed, 1 when it did not, and 2 for a usage or an invocation, manifest or store it cannot use, as Machine scenarios says.

`history_compare` is built by `make build/tools/etude/history_compare`. It compares each case of a run with the earlier samples of the same case on the same machine and accelerator, and reports whether the run was slower:

    history_compare [-n] [-s SCHEMAS] [-b STORE] [-g REPO] [-o STREAM -i ID] RUN HISTORY...

RUN is the run compared and HISTORY the streams that hold it and its history. The command prints a report for each group of the run's items that share a case and a key, as The comparison says, and a last line with the count of each verdict. `-g` lists the commits in between with `git log` in the repository REPO; without it, the report gives the command. `-b` names the store, a directory of blobs each named by its SHA-256, where the report finds the plan's reproduce blob. `-o` appends a comparison record for each report to STREAM, a new stream with the identity ID, and keeps each report and the policy in the store. `-n` asks for a new baseline in place of an accepted one. A verdict, a regression included, does not change the status: it is 0 when every comparison was made, and 2 for a wrong usage, a stream that cannot be read, a record whose identity has two contents, a run without exactly one plan record, or a record or blob that cannot be written.

`history_failures` is built by `make build/tools/etude/history_failures`. It lists the attempts of one run that did not pass, which [`tools/ci/report.sh`](../ci/report.sh) gives in ci's issues:

    history_failures [-s SCHEMAS] [-b STORE] HISTORY...

HISTORY is the streams of the run, which hold one plan record and at most one run record. The command prints a line for a run record whose outcome is not a pass, or a line that says the run has none. Then, for each item of the plan that did not pass on every attempt, or that the run record does not call passed, it prints a line with the item's case, its architecture and the worst outcome of its attempts, and an indented line for each attempt with its outcome, its reason, the attempt it retries and its disruptions. With `-b`, which names the store of blobs each named by its SHA-256, an attempt that did not pass also gives the state of an incomplete report and the assertions of its results document that did not pass, or why the document could not be read. An item that both passed and failed on attempts that no disruption touched is called possibly flaky. Its failed attempts stay listed, as they do when the run record calls the item passed, so that a passing retry does not hide the failure it followed. The listing has at most 80 lines of at most 240 bytes, six attempts of an item and four assertions of an attempt, and counts what it leaves out; a backquote is printed as a quote. The status is 0 when the run record passes and every attempt of every item passed, 1 when one did not or the run has no run record, and 2 for a wrong usage, a stream that cannot be read, is invalid or ends in an incomplete record, a record whose identity has two contents, a history without exactly one plan record or with more than one run record, or a record that names a plan, item or attempt the history lacks.

`history_lines` is built by `make build/tools/etude/history_lines`. It reads the history of one run and prints the lines that `tests/run` prints, so that ci, bisection and the release read a run of etude as they read one of the old runner:

    history_lines [-s SCHEMAS] [-f NAME]... MAP STREAM...

MAP gives the suites, one a line: the suite's name, as `tests/registry` gives it, and the identities of the families and cases it holds, separated by blanks, as `fpu guest.fpu`; an empty line and one that begins with `#` are skipped. STREAM are the streams that hold the run. Each `-f` names a failure of the run outside its suites, as `tests/run` names a run voided by a changed file or one that wrote an undeclared image, in the form of a suite's name; at most eight are taken. It prints the lines of Suite lines, with the names `-f` gives after the suites' in the line `run: result: failed: NAMES` and the run then failed, and exits 0 when every suite passed and the run has no fault and no such failure, and 1 otherwise. A map that cannot be read, that has a line of another form, names a suite twice, an identity twice or a suite without a case, or names no suite, is refused with a line `history_lines: MAP...` on standard error and the status 2, as is a wrong usage.

`etude-bridge` is the external POSIX admission wrapper for an old checkout or a new command, built by `make build/tools/etude/etude-bridge`; a cached version has it in its `bin/` on Linux and macOS:

    etude-bridge [-i] [-p] [-d LOCKS] [-w WAIT] [-r FILE] LEDGER ID ACCOUNT shared|alone RESOURCES CAPACITY SECONDS COMMAND [ARGS...]

LEDGER and LOCKS are absolute paths; LOCKS defaults to `/tmp`. RESOURCES and CAPACITY each give three positive decimal amounts separated by commas: thousandths of a processor, memory bytes and disk bytes. The machine's configuration supplies CAPACITY, the same for every account. The claim takes the memory alone: processors and disk are shared, not reserved. A test's guests use a small part of the processors counted for it, and runs that share too few processors only slow each other; the free space that `make` and `tests/run` require before they start guards the disk. ID is an attempt identity never reused. The command is admitted through LEDGER before execution, and registered before its program runs. Admission without room is refused, with no waiting request left. With `-w` the request waits in the ledger instead, asked again each second, for up to WAIT seconds, from 1 to 86400, and the wait for the locks has what is left of them; it is withdrawn at that bound or at a stop signal. Without `-w`, lock acquisition has a ten-minute bound. SECONDS, from 1 to 86400, bounds the command. Standard input is `/dev/null`, or the inherited standard input with `-i`. Output is streamed, with at most 64 MiB kept per stream. The exit status is the command's for a confirmed ordinary exit, 2 for refused or incomplete execution, and 128 plus the signal after cancellation. Startup failures, abnormal ends, unconfirmed cleanup and output beyond the bound print their cause on stderr as `etude-bridge: CAUSE: DETAIL`; a startup error includes the program's path and system error. Since a command may exit 2 itself, `-r` writes the bridge's own result to FILE as one line: `exited N` for the command's exit with status N, its cleanup confirmed and its output whole; `refused` when nothing ran; `incomplete` for a command that could not start, ended by a signal, lost output or left its cleanup unconfirmed; and `stopped N` after signal N stopped the bridge. A usage error writes nothing.

`alone` takes the old host lock exclusively. A memory declaration larger than half of CAPACITY also takes it exclusively, even with `shared`. `-p` takes a legacy port block and sets `RACH2_PORT_OFFSET` only after it owns that block. It refuses inherited `RACH2_PORT_OFFSET` and `SSH_TEST_PORT`; commands must not override the port table through their arguments. Without `-p`, new native port allocations use the range that `etude_bridge_native_port` accepts. Bisection runs an old checkout's `tests/run` so, with `-p`, without changing its source, as Compatibility with old runs says. The converting suite adapter instead uses the bridge interface around its own execution; it does not start the old scheduler.

`etude-ledger` lists the claims of a machine's ledger, and drops a claim that only a person can release, on Linux and macOS. `make build/tools/etude/etude-ledger` builds it:

    etude-ledger list LEDGER
    etude-ledger drop LEDGER ID

LEDGER is the ledger's directory, which must have its `verdicts` directory, so that a mistyped path is refused rather than made a new ledger. Each command first releases the claims that recovery proves free, as every reading of the ledger does (The ledger). `list` prints a line for each claim and request the ledger keeps: its status as `etude_ledger_list` judges it, `owned`, `live` or `uncertain`, with the reason for one that is not owned; its state, its system, its owner's PID and its account; for a claim, the count of its processes and what it holds; and for a request, what it asks. A last line counts each status:

    claim run1:xsave:a0: owned; state running, system linux, owner 41235, account testing, processes 2; holds cpu_millis 1000, memory_bytes 1073741824
    claim run1:hang:a0: uncertain: its owner found the cleanup unconfirmed; state uncertain, system linux, owner 40017, processes 3; holds cpu_millis 500
    request run1:big:a0: owned; state blocked, system linux, owner 41235, account testing; asks memory_bytes 77309411328
    etude-ledger: result: owned 2, live 0, uncertain 1

`drop` releases claim ID through `etude_ledger_drop` and prints `etude-ledger: result: dropped: ID`. A person runs it once they have established that nothing of the claim runs, as `tools/flow/test_status.py` asks of a claim it reports uncertain. It refuses a claim whose owner runs, with `etude-ledger: result: refused: ID: its owner, process PID, runs` on standard error, and an identity the ledger lacks, with `etude-ledger: result: refused: ID: the ledger has no such claim`. It also refuses a live claim, one of whose processes the ledger sees running, since that process still uses what the claim holds: `etude-ledger: result: refused: ID: its process PID runs`, or `its process group PID has a member` when only its case's process group is left. End what runs, and drop the claim once the listing calls it uncertain. The status is 0 after a listing or a drop, 1 for a drop refused, and 2 for a wrong usage, a path that is not a ledger, or a ledger that cannot be read, such as one whose claims file does not parse, which is left as it was.

`history_budget` is built by `make build/tools/etude/history_budget`. It forecasts the time a run would be charged from the costs the history records, and checks the budget of a run from its records, by a policy as The budget says:

    history_budget [-s SCHEMAS] forecast POLICY CLASS MANIFEST... [-- HISTORY...]
    history_budget [-s SCHEMAS] check POLICY RUN [MANIFEST...] -- HISTORY...

POLICY is a budget policy; CLASS the class of the run forecast, `push`, `ci`, `release`, `focused` or `phase_first_run`; MANIFEST a case manifest, every case of which the run selects; RUN the run checked; and HISTORY the streams that hold the history. SCHEMAS is `tools/etude/schemas` by default. `forecast` prints the class and the site, the count of items and of preparation nodes, the time the recorded costs give the preparation and the cases, and the deadline. `check` prints the run's plan and class, its charge, the one-time setup left out of the charge, and the ceiling; a charge that was not observed is `unknown`. With manifests, `check` also requires a preparation step for each node that a planned case prepares. Each then prints a line for each reason, `note: WHAT`, `unknown: WHAT`, `failure: WHAT`, or `record: WHAT` for a recorded budget that is not the judgement's, and last `history_budget: result: VERDICT`, with `; the run records another budget` after it in that case. VERDICT is `pass`, `failure`, `exempt` or `unknown`. The status is 0 for a pass or an exemption, 1 for another verdict or a recorded budget that differs, and 2 for a wrong usage or CLASS, a policy, manifest, schema or stream that cannot be read or is refused, a record whose identity has two contents, a run without exactly one run record or whose plan is not in the history, or a lack of memory.

`etude-proof` is the driver of mutation proofs on Linux and macOS, built by `make build/tools/etude/etude-proof`. [`proof.sh`](proof.sh) builds it and runs it with this tree held, as a fault script holds it through `tests/system/runlock.sh`, so that no suite builds or boots the tree while a fault is in it:

    sh tools/etude/proof.sh [-w WORK] [-b STORE] [-k] PROOF [FAULT...]
    sh tools/etude/proof.sh [-w WORK] [-b STORE] [-k] --base PROOF
    sh tools/etude/proof.sh --texts PROOF...
    etude-proof [-s SCHEMAS] [-t TREE] [-w WORK] [-b STORE] [-k] PROOF [FAULT...]
    etude-proof [-s SCHEMAS] [-t TREE] [-w WORK] [-b STORE] [-k] --base PROOF
    etude-proof [-s SCHEMAS] [-t TREE] --texts PROOF...

PROOF is a catalogue, as Proofs says. Each FAULT named runs alone; with none, every fault runs. TREE is the tree whose sources the faults change and in whose root the commands run, `.` by default, and SCHEMAS is `TREE/tools/etude/schemas` by default. WORK is the work directory, which must not exist, by default a new `rach2-proof-NAME.XXXXXX` under `$TMPDIR` or `/tmp`; STORE is the artifact store, `WORK/store` by default; `-k` keeps the work after a pass. The driver prints a line for each phase, `etude-proof: NAME: PHASE: artifacts DIGEST...; WHAT`, each digest cut to twelve digits, and ends with `etude-proof: result: pass: NAME: N of M faults found; the sources and artifacts restored` or `etude-proof: result: fail: NAME: PHASE: WHY`, followed by `etude-proof: evidence: WORK`; a work it removes after a pass, or after a signal, and cannot is named as `etude-proof: not removed: WORK: REASON`. `--base` runs the base phase alone, for a test whose build only its proof gives, and ends with `etude-proof: result: pass: NAME: the base passed; no fault was run`; no suite runs one yet. It exits 0 for a proof that passed, 1 for one that failed, 2 for a wrong usage, a catalogue with findings, a tree that is not held or an error of the system, and 128 plus the signal's number after SIGHUP, SIGINT or SIGTERM, once it has ended what ran and restored the sources. `--texts` checks that each edit of each fault finds its text once in the tree's sources, writes nothing, and exits 0, 1 for an edit that does not, or 2; `tests/run style` runs it over `tests/proofs/*.json` and the example through [`faulttexts.sh`](../verify/faulttexts.sh).

`etude-tooling` makes the tooling machine, a Linux virtual machine that gives a host the commands its tests need and the host lacks, such as `mkfs.exfat`, `unshare` and the GNU build's tools, and runs jobs in it. `make` builds it as `build/tools/etude/etude-tooling`, and `wincheck.sh` builds it for Windows:

    etude-tooling [-r RECIPE] [-C CACHE] [-a ACCEL] prepare [-c CPUS] [-t SECONDS] [HISTORY]
    etude-tooling [-r RECIPE] [-C CACHE] check
    etude-tooling [-r RECIPE] [-C CACHE] [-a ACCEL] run [-n] [-k] [-c CPUS] [-m MIB] [-s MIB] [-t SECONDS]
                  [-i PATH]... [-d DISK]... [-o NAME]... [-O DIR] [HISTORY] SCRIPT

RECIPE is the machine's recipe, [`tooling/`](tooling) by default; CACHE the directory of its image, its disk and its jobs, `ETUDE_TOOLING_CACHE` or else `build/tooling`; and ACCEL QEMU's accelerator, `RACH2_QEMU_ACCEL` by default. `prepare` downloads the image, checks its digest and provisions the machine once, with a network, in at most two hours unless `-t` gives another bound; a machine made already is reused. It prints `etude-tooling: result: made KEY DISK`, `reused KEY DISK` or `failed: WHY`, and exits 0 or 1. `check` prints the same `made` line, or `not made`, and exits 0 or 1. `run` runs the shell script SCRIPT as root in a private copy of the made machine. `-i` copies a file or directory into the job's working directory; `-d` attaches a raw disk image, whose device in the machine is `$ETUDE_DISK1`, `$ETUDE_DISK2` and so on; `-o` names a file or directory of the working directory to copy back into DIR, the current directory by default; and `-n` gives the job a network. `-c`, `-m` and `-s` give the processors, 2 by default, the memory, 2048 MiB, and the job volume, 64 MiB, and `-t` the deadline, 1800 seconds. The job's standard output and error become the command's, and it exits with the job's status, 124 when the job ran past its deadline, 125 when the machine failed, 126 when it is not made and 2 for a wrong usage. The job's directory is kept after a failure, and after any job with `-k`. Each command prints the boot's cost on standard error as `etude-tooling: cost: ...`. HISTORY, `-H STREAM -j STREAM_ID -R RUN -P PLAN [-I ITEM] [-A ATTEMPT] -M MACHINE -B BOOT -b STORE [-S SCHEMA]`, writes the boot's steps to a new history stream, as The tooling machine says. [`tests/system/tooling.sh`](../../tests/system/tooling.sh) is what a suite sources to use it: `tests/host/mkexfat_external.sh` and the suites `exfat` and `large` run exFAT's tools there on a host other than macOS that lacks them.

`etude-legacy` is the preparation adapter and the suite adapter on Linux and macOS: it builds what the suites of [`tests/registry`](../../tests/registry) read before a suite starts, as `tests/run` builds it, checks that those artifacts exist, and records them, and it runs one prepared suite under the supervision `tests/run` gives it, so that the old suites can run under etude while their families convert. `make build/tools/etude/etude-legacy` builds it. [`legacy.sh`](legacy.sh) builds it and runs it with this tree held, as `proof.sh` runs `etude-proof`, and gives a preparation the tree, and the architecture and the kernel from `ARCH` and `RACH2_KERNEL`, as `tests/run` takes them:

    sh tools/etude/legacy.sh prepare [-w WORK] [-o RECORD] [-s SECONDS] [-b GOAL]... SUITE...
    sh tools/etude/legacy.sh check [-d] RECORD
    sh tools/etude/legacy.sh run [-w WORK] [-i IDLE] [-s SECONDS] RECORD SUITE
    etude-legacy prepare [-t TREE] [-a ARCH] [-n KERNEL] [-w WORK] [-o RECORD] [-s SECONDS] [-b GOAL]... SUITE...
    etude-legacy check [-d] RECORD
    etude-legacy run [-w WORK] [-i IDLE] [-s SECONDS] RECORD SUITE
    etude-legacy set -l LEDGER -c CPU,MEMORY,DISK -o RESULTS -e EVIDENCE -S SCHEMAS [-K CASECHECK] [-d LOCKS] [-t TREE] [-a ARCH] [-n KERNEL] [-p RECORD] [-W WAIT] [-s SECONDS] [-i IDLE] [-j WIDTH] [-k] [-r STATUS] [-m STAMP] [-g COMMIT] [-q ARGS] [-P SITE] SELECTION

`prepare` prepares the SUITEs of the tree TREE, `.` by default, which must be held, as a shared proof's tree must be. ARCH is `i686`, the default, or `x86_64`, and KERNEL the NAME of the kernel `rach2-NAME/kernel` that the suites boot, as `RACH2_KERNEL=NAME` gives it to `tests/run`. WORK is the work directory, which must not exist, by default a new `rach2-legacy.XXXXXX` under `$TMPDIR` or `/tmp`; it has each step's log, `N-STEP.log`, and make's database. SECONDS is the bound of each step, from 1 to 604800, and 14400 by default, since the GNU system's root takes over an hour to build from nothing. RECORD is the file the record is written to; without `-o` the record is not kept. Each GOAL is a make goal of the tree, a relative path inside it such as `build/tests/cases/host/style`, which is built and recorded as an artifact of the suites; with a GOAL, no SUITE need be named. The program prints `etude-legacy: step: STEP` as each step starts, and a failed step's reason, its log's name and the end of its log. It ends with `etude-legacy: result: prepared: N suites, M files`; `etude-legacy: result: failed: WHY`, followed by `etude-legacy: evidence: WORK`; `etude-legacy: result: refused: WHY`; or `etude-legacy: result: stopped by signal N`. It exits 0 when every artifact exists, 1 when a step failed or an artifact is missing, 2 for a wrong usage, a request refused before anything was built or an error of the system, and 128 plus the signal's number after SIGHUP, SIGINT or SIGTERM, once the step that ran has ended. `check` compares each file a record lists with the file in its tree now: by its size, inode and modification time, or with `-d` by its size and SHA-256. It prints `etude-legacy: changed: PATH` or `etude-legacy: missing: PATH: WHY` for each that differs, and last `etude-legacy: result: unchanged: N files` or `etude-legacy: result: changed: K of N files`, and exits 0 when none differs, 1 when one does, and 2 for a record it cannot read.

`run` runs SUITE, which the preparation RECORD lists, in the tree, for the architecture and with the kernel that RECORD names. The tree must be held, every file of RECORD unchanged by its size, inode and time, and `RACH2_PORT_OFFSET` must name the port block the caller holds, as `etude-bridge -p` gives it; `run` takes no lock and no port of its own. QEMU's accelerator and each machine's processors come from `RACH2_QEMU_ACCEL`, `RACH2_KVM_DEVICE` and `RACH2_CPUS`, as `tests/run` takes them. Without an explicit accelerator, KVM is selected only when its device opens for reading and writing; the descriptor is then closed. A missing device selects HVF on an x86 Mac that supports it, or TCG otherwise. Any other open error refuses the run with the reason and the `RACH2_QEMU_ACCEL=tcg` remedy. IDLE is the seconds the suite may go without output, console output or processor time before it is stopped as hung, from 1 to 86400, and 300 by default, as `RACH2_IDLE_TIMEOUT` gives it to `tests/run`; SECONDS bounds the whole run, as for `prepare`. WORK is the work directory, as for `prepare`; it has the suite's output, `suite.log`, the machines' ledger and consoles, `machines` and `machines.console`, runutil's record of the suite's end, `end`, and after a run that did not pass the logs the suite wrote under the images, in `images/`. The program copies the suite's output as it runs, and prints `run: SUITE: starting (idle limit N s)` before it and `run: SUITE: PASS in Ns`, `FAIL in Ns` or `INCOMPLETE in Ns` after it, a line `etude-legacy: SUITE: left running: pid P, group G, COMMAND` for each machine or relay left running, and one `etude-legacy: SUITE: console cut: machine M, relay R` for each console cut. It ends with `etude-legacy: result: passed: SUITE`; `etude-legacy: result: failed: SUITE: WHY` or `etude-legacy: result: incomplete: SUITE: WHY`, followed by `etude-legacy: evidence: WORK`; `etude-legacy: result: refused: WHY`; or `etude-legacy: result: stopped by signal N`. It exits 0 when the suite passed, 1 when it failed or did not finish, 2 for a wrong usage, a request refused before the suite started or an error of the system, and 128 plus the signal's number after SIGHUP, SIGINT or SIGTERM, once the suite has been stopped. A suite runs so, with the host lock and a port block taken by the bridge, which runs its command by the path it is given and does not search `PATH`:

    sh tools/etude/legacy.sh prepare -o RECORD SUITE
    build/tools/etude/etude-bridge -p LEDGER ID ACCOUNT shared RESOURCES CAPACITY SECONDS \
        /bin/sh tools/etude/legacy.sh run RECORD SUITE

`set` runs the suites of SELECTION in the tree as one run of etude, as `tests/run` runs them: one suite a line, its name and the most guest memory its machines ask for at once in MiB, then `serial` for a suite that runs before the others with nothing beside it, `stops` for one whose failure stops the set, or both, and last `cases=MANIFEST` for a suite that the host, guest and machine cases of a case manifest run, as [The set driver](#the-set-driver) says; a line that begins with `#` is skipped. MANIFEST is absolute or from the tree's root, and CASECHECK, the path of `casecheck`, which judges each case, must be given when a line has one. LEDGER is the absolute directory of the ledger that admits the suites, made when it does not exist, and CPU, MEMORY and DISK its limits, in thousandths of a processor and bytes. With `-d`, each claim also takes the old runner's host lock and a port block in LOCKS, as `etude-bridge -p` takes them; without it the suites share the port block of the caller's `RACH2_PORT_OFFSET`. RESULTS is the directory of the history, `history/RUN.jsonl` and `store/`, and of each command's output, `output/`; EVIDENCE the directory under which a suite that does not pass keeps its work, as `RUN.SUITE`; SCHEMAS etude's schemas; RECORD the preparation's record, `RESULTS/prepare.record` by default. WAIT bounds each claim's wait for admission, from 1 to 86400 seconds and a day by default; SECONDS bounds the preparation and each suite, as for `prepare`; IDLE is each suite's idle limit, as for `run`; WIDTH, from 1 to 1024, is the most suites at once, the ledger's limits alone deciding without it. `-k` stops the set at the first suite that does not pass. STATUS is a status record, rewritten as the run goes and removed at its end; STAMP a file touched once the preparation has ended; COMMIT the tree's commit for the history, forty zeros without it; ARGS what the run was asked, for the status record; SITE the installed site policy that admitted the run, which `tests/run` gives when the launcher admitted it, and whose line `boundary_lazy bigmem-boundary-v1` alone permits the lazy boundary profile. `RACH2_QEMU_ACCEL` must name QEMU's accelerator and `RACH2_CPUS` gives each machine's processors, 2 by default. The program prints `run: preparing` and the preparation's lines, `run: NAME: starting (idle limit N s)` for each suite it starts, `run: NAME: CASE: starting` for each case, or `CASE rR` for a later repetition, and `run: NAME: CASE: evidence: PATH` for a case's workspace kept, each suite's output whole when it ends, or as it comes when the set has one suite, and, when the set stops, `run: stopped on the first failure; not started: NAMES`, `run: stopped: NAME failed; ...` or the names `stopped part way`, with `run: NAME: stopped before its end; its output so far:` before what a stopped suite wrote. It ends with `etude-legacy: result: ran: N suites, P passed`, a suite of cases passing when each of its attempts passed, `etude-legacy: result: preparation failed: WHY`, `etude-legacy: result: refused: WHY`, `etude-legacy: result: error: WHY` or `etude-legacy: result: stopped by signal N`, and exits 0 when every suite passed, 1 when one did not or the run could not go on once its plan was written, 2 for a wrong usage or a request refused before anything ran, 3 when the preparation failed, and 128 plus the signal's number after SIGHUP, SIGINT or SIGTERM. `history_lines` prints the suites' result lines from the history, as `tests/run` does with the map `NAME legacy.NAME`.

### Cases

A case is one behavior under test, with its program, its requirements and its expected results. Each family of cases has one manifest, `tests/cases/FAMILY.json`. A case's `case_id` and each `assertion_id` are stable: a rename keeps them, and a change of meaning takes a new one. Assertion identities belong to their case, and those that begin with `etude.` belong to the executors. `units` lists the tests the case takes over from `tests/run`, by their names in the inventory of assertions under `dev-log/`.

The `domain` says where the program runs. The plan places each item of a run, and the history's `domain` records the placement:

| Domain | The program | Placements |
| --- | --- | --- |
| `host` | A program on the controller's host, or in its local tooling machine when `host_api` is `linux` and the host is not Linux | `host` |
| `guest` | A program on Rach2, a child of `etude-guest`, or the designated init when its role is `init` | `qemu`, in a fresh boot; `native`, on a running Rach2 over SSH, when `native.plan` is `native` |
| `machine` | A scenario on the host, linked with `libetude-case`, that boots Rach2 in QEMU and drives it | `qemu` |

`architectures` lists the Rach2 architectures whose build the case tests, and the plan selects one item for each. A host case whose program and inputs are the same for both lists `none`, and runs once.

A manifest gives no accelerator. The site profile of the run chooses TCG, KVM, WHPX or a native run, and a case's results do not depend on it; a case that needs a processor feature declares the feature, and its boot names a processor profile that declares it, as Processor profiles says. A case that passes under one accelerator and fails under another is redesigned, not left out.

`workload` fixes the work: the program's `arguments`; `inputs`, the sizes, paths and counts the program uses and its expected results depend on; `repetitions`, the items of the case in one run; `seed`, given to the program as `ETUDE_SEED` in its environment when it is not null; and for a machine case `suspensions`, the cycles in which its scenario stops and resumes a machine's QEMU, as Machine scenarios says. A change to any of these is a change of workload, and starts a new baseline.

`requirements` gives what the case needs of the machine: `host_api` (`c`, hosted C alone; `posix`, a POSIX shell and utilities; `linux`, Linux interfaces), the host `tools` that `tools/setup/prereqs` installs, the processor `features` that must be `present` or `absent`, or may be `either`, and for a guest case the `qemu` profile of its boot: the kernel, an initial RAM image or none, the disks, the processor profile, the processors, the memory, the firmware, the devices, the boot options, `machine`, `pc` or `q35`, and `i8042`, false for a machine without the 8042 keyboard controller. A device is a name, or an object of its `model` and, as it needs them, its `id`, the `bus` of an earlier device, as `xhci.0` is the first bus of the device `xhci`, a USB `port` such as `1.2`, the `drive` it attaches, other `properties`, each a name and a value, and for a network card the options of its user network, its forwards and its station address. A profile's optional `captures` lists the network cards whose frames the boot records, each by its network: `net0` for the first card among the `devices`, `net1` for the second. The QEMU launcher says what each becomes.

Each of a profile's `disks` is the name of an artifact, a writable disk on IDE, or an object of that `name` and these members. `bus` is `ide`, the default; `ahci`, a port of the one ich9-ahci controller that the profile's disks on AHCI share; `nvme`, an NVMe controller of the disk's own, which needs a `serial` of at most 20 letters, digits, `.`, `_` and `-`, which a disk on IDE may also have and a CD or a disk on AHCI or on a device has none of; or `device`, the device whose `drive` is the disk's `id`, an identity that no other disk of the profile has. `media` `cdrom` makes the disk a CD on IDE whose medium is the artifact itself, read-only. `size_bytes` makes it an empty disk of that size, a sparse file of the attempt that is no artifact. `base` makes it an overlay: an empty qcow2 file of the attempt, in clusters of `cluster_bytes`, a power of two from 512 to 2097152, whose raw backing file is the object of artifact `base`, so that the guest's writes go to the overlay alone and `qemu-img map` of it lists the clusters they changed, while the base is read and never copied. An overlay is no CD and no empty disk, and only a machine's profile has one. `discard` true lets the guest's discards and its writes of zeros free the file's blocks; a CD has none. `boot` true makes the firmware boot the disk first, which needs the firmware `seabios` or `ovmf`, since QEMU boots the kernel of `direct` before any disk; a disk on a device has none, and its device's `bootindex` property orders it instead. A profile has at most eight disks, four of them on IDE, CDs among them, and six on AHCI, and one at most that boots first. `casecheck` requires each disk once in a profile, a device that attaches each disk on a device, an artifact of `prepare` for each disk but an empty one or an overlay and for each overlay's base, no artifact of an empty disk's or an overlay's name, the same size for an empty disk in each profile that names it, and the same base and cluster size for an overlay wherever a profile names it, and refuses a disk that boots first beside the direct firmware.

`execution` gives the program and its standard input as artifacts, its `role`, its privileges, the `isolation` of its host and QEMU placements, its children and its cleanup. Isolation is made of fixtures: `scratch` is a private directory under `TMPDIR`, and `disk` gives private writable copies of the named artifacts; a guest case under QEMU has a boot of its own. `children` is `none`, `reaped` (the program reaps every child on every path) or `reported` (it reports each child that may outlive it, and the executor ends those).

The role is `ordinary` when any process can be the case; `init` when the case must be the kernel's designated init, to which orphans go, whose exit the kernel records and whose death panics it; and `boot` when it needs a boot of its own: a kernel command line, a fresh kernel's state, a reset or a power-off. An `init` case runs under QEMU alone, and a `boot` case gets its boot from its QEMU profile.

A machine case also has `steps`, its stable operations, each in a stage and on one of its `machines`. A machine declares its QEMU profile, its console, whether it has a QMP monitor, and whether `etude-guest` runs in it, and may declare `critical`, the text of the one critical record of the kernel's log that its case makes the kernel print, such as the record of init's death. A machine may also declare `fault`, the fault its boots are expected to end in: its `end`, `panic` or `halted`, and its `records`, the texts of the critical records the fault makes the kernel print, in the order printed, such as the hardware fault and the panic that an NMI gives. `casecheck manifest` requires a serial console of a machine whose fault is a panic or has records, QMP of one whose fault is a halt, and an assertion of the scenario's in its case, whose report gives a boot's end. A machine case may also have `services`: host programs that run beside its machines across steps, such as a peer its machines reach at the user network's gateway, 10.0.2.2. Each has a `service_id`, a `program` that is a tool of its requirements or an artifact of its `prepare`, and the `ready` text its standard output has once it serves.

A card object of a machine's QEMU profile may give `forwards`. Each joins one of the case's local ports, named by `port`, its index among the `resources.ports` the plan reserves, counted from 0, to the guest's `guest_port`, by the `protocol` `tcp` or `udp`: QEMU listens at that port of 127.0.0.1 and joins each connection, or each datagram, to the port at the first address that DHCP gives on the card's network, 10.0.2.15 unless the card gives another network or `dhcpstart`. Each of its `guest_forwards` joins the guest's TCP connections to `guest_port` at `address`, an address of the card's network, to the case's local port `port`, where a service of the case typically serves. For each connection QEMU runs `relay`, whose first word is a tool of the case's requirements or an artifact of its `prepare`, with the words after it and the local port as its arguments; the connection is its standard input, output and error, so a relay writes no diagnostics, and it copies the connection's bytes to the local port and back. The address is none of the network's own address, its broadcast address, the host's, the name server's and the sixteen that DHCP gives from `dhcpstart`, each as the card gives it or as QEMU places it on the network; on the default network, 10.0.2.0/24, it is 10.0.2.N with N one of 1, 4 to 14 and 31 to 254, since 2 is the gateway, which is the host, 3 the name server, and DHCP gives the guest one of 15 to 30. A card whose `restrict` is true lets the guest reach nothing but its guest forwards, while the forwards to the guest still reach it. The example [`case.forward.example.json`](schemas/case.forward.example.json) gives the key login of the `ssh` suite, which reaches dropbear through the forward of the case's one port to the guest's port 22, and [`case.relay.example.json`](schemas/case.relay.example.json) gives the restricted network of the `fakeapi` suite, whose guest reaches the fake API server only at 10.0.2.100:443, through `fakeapi.py relay`. `casecheck manifest` refuses a forward of a port past those the case reserves, a local port forwarded twice by one protocol, a guest forward from an address QEMU cannot forward, one address and guest port forwarded twice, a guest forward to a local port that a TCP forward makes QEMU listen on, a relay that is neither a tool of the case's requirements nor an artifact that `prepare` lists, and forwards, guest forwards and a restricted network of a card in a guest case's `requirements.qemu`, since only a scenario's machines are given them.

`prepare` lists the artifacts the case needs, by the name it uses and the node of the preparation graph that makes them: a target in the architecture's build tree, `build` or `build/x86_64`, when `per_architecture` is true, and in `build` otherwise. Preparation makes every artifact before the case starts, and a cache keeps products of setup, never the operation under test.

`native` is the native plan: `native` with the fixtures that Native runs lists; `none` with the class and the reason a native run cannot test the case; or `host` for a host case. A machine case's plan is always `none`.

### Processor profiles

The `cpu` of a QEMU profile names a processor profile of [`processor.c`](processor.c): a QEMU processor model and the features it declares present or absent, by the names of QEMU and of Linux's `/proc/cpuinfo`. The launcher gives QEMU the model with `F=on` for each present feature, `F=off` for each absent one, and `enforce=on` when any is present, so that an accelerator that cannot give a present feature keeps QEMU from starting, which the launcher reports as QEMU's exit; an absent feature is off under every accelerator. A feature a profile does not declare is the accelerator's to give, and a case cannot depend on it.

| Profile | Model | Present | Absent |
| --- | --- | --- | --- |
| `max` | `max` | `rdrand`, `rdseed`, `xsave`, `avx` | |
| `max-nopdpe1gb` | `max` | `rdrand`, `rdseed`, `xsave`, `avx` | `pdpe1gb` |
| `qemu64` | `qemu64` | | `rdrand`, `rdseed`, `xsave`, `avx` |

A feature a case requires is one of those five. Its boot's profile declares it as the case requires it: present for `present`, absent for `absent`, and either way for `either`, so that under QEMU every group decided by the feature is decided. A native machine's features are its own, which the controller reads and gives the judge.

### Native runs

A native case runs on a Rach2 that is already up, such as the Lenovo, and gets no boot, command line or fresh kernel of its own. It runs as root, a child of `etude-guest` in a session and process group of its own, with no controlling terminal. Its descriptor 0 is `/dev/null` or a pipe of its declared input, 1 and 2 are pipes that `etude-guest` reads, and no other is open. Its working directory is its workspace, its umask 022, its signal mask empty and every disposition the default, and its environment has `PATH`, `HOME` set to the workspace, and `ETUDE_CASE` set to the case's identity. Its executables come from the candidate's build, copied into the workspace and checked by their digests, and the program starts with its absolute path as `argv[0]`. Each fixture is made before the case starts and removed after it ends, on every path. An invocation gives each fixture's values in `given`, as each item below says:

* `workspace`, given nothing: a directory of the case's own under `etude-guest`'s scratch directory, removed after a pass and kept after a failure. Every native case has one.
* `stage`, given the names of files of the invocation: the companion files the case runs or reads, copied into the workspace with their modes, a set-id file owned by root.
* `volume`, given its type, `krffs`, `ext2`, `vfat` or `exfat`, a file of the invocation that is its image, and `mounted` or `attached`: the workspace's copy of the image attached to a free loop device, and for `mounted` also mounted on `volN` of the workspace, N counting the case's volumes from 0.
* `tmpfs`, given its size in bytes: a tmpfs of that size mounted on `tmpfs` of the workspace.
* `mountns`, `ipcns`, `utsns`, given nothing: a mount, IPC or UTS namespace of the case's own. The volumes and the tmpfs of a case with a mount namespace are mounted in it, and go when it ends; those of a case without one are mounted in the machine's, and unmounted after the case.
* `root`, given its type, a file of the invocation that is its image, and the program's absolute path in it: a private root, entered by `chroot` inside a mount namespace of the case's own, for a case that uses fixed absolute paths or reads the type of `/`. The image, attached to a loop device, is mounted on `root` of the workspace; for the type `ext2-dir` it is an ext2 image whose tree is copied there, onto the workspace's own file system. The root gets `/proc`, the machine's `/dev` and `/sys` by bind mounts, and a tmpfs of its own on `/dev/shm`; the program of the invocation is copied over the root's file at the path given, and runs there with `/` as its working directory.
* `ids`, given pairs `OLD:NEW`: user and group ids, each NEW one that no account, group or process of the machine has, which the case uses in place of OLD. On Rach2 and Linux an account or a group is a line of `/etc/passwd` or `/etc/group`, and a name service such as LDAP is not asked; on macOS, which keeps most accounts in Directory Services and not in those files, it is also one that `getpwuid` or `getgrgid` finds there.
* `pty`, given nothing: a pseudo-terminal whose slave side is the case's descriptors 0 to 2 and controlling terminal; `etude-guest` keeps the master side, writes the declared input to it and reads it as the case's standard output.
* `ports`, given pairs `OLD:NEW`: local ports, each NEW free for TCP and UDP on 127.0.0.1 when the case starts, which the case uses in place of OLD; never port 22 or a service's port.
* `peer`, given an address, a port and at most eight `NAME=VALUE` arguments, NAME in lowercase letters: a network peer on the controller's side, or a second `etude-guest` process on 127.0.0.1. The arguments give the program what the peer's role knows of the machine's network, such as its gateway.
* `log`, given nothing: the kernel's records written while the case ran, read with `syslog(2)` action 3 before and after it and kept as `log` in the attempt's directory. Other activity writes records among them, so a check may require a record, and may require the absence only of a panic, an oops or a record about the case's own processes.
* `alone`, given nothing: no other native case runs on the machine meanwhile; its services still do.
* `console`, given nothing: the machine's console and framebuffer, with `alone`, put back as they were found. A native run can type nothing at the console.

`etude-guest` gives the values to the program as arguments after the invocation's own, in this order, each when its fixture is there: `ids=OLD:NEW,...`, `ports=OLD:NEW,...`, `loops=/dev/loopN,...` with the device of each volume in order, `peer=ADDRESS:PORT` followed by the peer's arguments, and `root=PATH`, the private root's directory as the machine's `/proc/mounts` names it. It refuses with `error refused` an invocation whose fixture is unknown or does not fit its form, an id that an account or a process has, and a port in use, and with `error failed` one whose fixture cannot be made. [`tests/native/`](../../tests/native/Readme.md) gives the native cases of the guest programs, and [`tests/probe_args.h`](../../tests/probe_args.h) reads these arguments in a program.

The class of a plan of `none` says why the case needs a machine of QEMU's: `QEMU`, for its monitor, its devices, its exit or its capture; `card`, for the driver of a device the native machine lacks; `init`; `boot`; `exhaustion`, for exhausting a resource of the whole machine; `count`, for judging a count of the whole machine that its services move; `feature`, for a processor feature or its absence; `layout`, for disks or controllers arranged its own way; `disk`, for a write to a disk node; `network`, for reconfiguring an interface or needing a network of its own; `image`, for a system image other than the installed one; `system`, for changing the installed system's configuration, accounts or services; `firmware`, for a memory map or firmware arrangement of its own; `input`, for keys, mouse reports or typed lines; and `architecture`, for i686 alone on an x86-64 machine.

### Assertions and branches

Each assertion says what it `checks` and its `source`: `program` for a report record of the case's program, `scenario` for a machine scenario's call, and `executor` for a kernel record that the executor finds on the console under QEMU, or with the `log` fixture natively; such an assertion gives the `record`. `where` may give the file and line of the check.

An executor adds these assertions to a case:

* `etude.termination`: the case ended as `termination` expects. The ends are `exited` and `signaled` for an ordinary process, `init_exited` and `init_killed` for the designated init, by the kernel's record that hands the debug shell back, `panic`, `reset` and `shutdown` for a machine, and `halted` for a machine whose processors are all halted with interrupts off. A value is the exit status or the signal, and the ends of a machine have none.
* `etude.kernel`, under QEMU, and natively with `log`: no panic, oops or fault of the kernel appeared, unless the termination expects a panic, or the record has the text that its machine declares as `critical`, or the record is on the console of a boot that ended in its machine's declared `fault`, as `etude.fault` takes it, and has one of the fault's `records`. Any other panic fails it whatever the program reported.
* `etude.fault`, for a machine case one of whose machines declares a `fault`: each such machine has a boot whose end a `machine` record of the scenario's report gives; every boot of it so given ended in the fault's end; and the console of each shows the fault: for a panic, a record of the kernel's panic, a critical record whose subsystem is `panic`, and for any fault, each of its `records` in a critical record, in their order. A boot that ended otherwise, such as by a reset, a console without the fault, and a complete report that gives no boot of the machine fail it, so that a scenario's exit, or a success text, is never taken for the machine's panic; a boot whose end was not observed, a console not given, and a report that did not finish leave it missing. The scenario's own end is still `etude.termination`'s.
* `etude.report`, when an assertion's source is the program or the scenario, whose report `libetude-case` writes on the scenario's standard output: it passes when the report is complete, as Report records says, fails when it is invalid, and is missing when it is truncated or absent, since the program then did not finish.

A branch group says that one of its alternatives runs and the others cannot, such as the trusted and the fail-closed paths of `rngprobe`. The assertions of the chosen alternative are required, and those of the others are not. A group decided by `features` takes the alternative whose `when` is `present` when any of the features is present on the processor, and the one whose `when` is `absent` when none is. Under QEMU the processor is the boot's processor profile; natively it is the machine's, whose features `casecheck report` takes as `-f NAME=present` or `-f NAME=absent`, and which a guest case placed `qemu` does not take. The program reports the branch it took, and a branch that disagrees with the profile's processor fails `etude.report`. A group decided by `report` takes the alternative the program reports; without that record, every assertion of the group is missing.

### Progress and bounds

`progress` lists the witnesses of the case's progress. A `step` witness counts completed steps. A `counter` counts completed units of bounded work toward its `limit`. A `quiet` witness marks the end of an opaque child's work, such as a compiler's, which writes nothing while it runs. Only a record whose units advance its witness is progress: a heartbeat, a repeated record, output or processor use does not reset a watchdog, and a count that goes back or past its limit is a report error. A record of a quiet witness at its present units, such as `progress compile 0` before the first compile, announces its work: from that record until the witness advances, the witness's own `bound` replaces the gap bound, and a repeated announcement does not move it.

`bounds` gives three bounds, each a `floor_us`, an `initial_us` and a `ceiling_us`: `case`, the whole case's time; `gap`, the longest time without progress; and `stages`, one for each of the executor's prepare, transfer, boot, capture and cleanup stages that the case uses. The plan fixes each bound before the run from the history of the same case, workload, profile, machine and accelerator, by the policy `watchdog-bounds-v1`: with fewer than five samples, the initial value; otherwise twice the sum of the largest sample and 3 * 1.4826 times the samples' median absolute deviation, rounded upward to a microsecond. Either is then held between the floor and the ceiling. A sample of the `case` bound is an attempt's elapsed time, one of the `gap` bound its longest gap between progress records, and one of a stage or a quiet witness the time of that stage or work. Only an attempt that passed undisrupted gives samples; a failed, incomplete, cancelled or disrupted one never makes a bound larger. A program and a scenario give no time limits of their own.

### Resources and timing

`resources` declares what admission reserves: `cpu_millis`, the first processor reservation in thousandths of a processor, and `cpu_ceiling_millis`, the most any reservation from history may be; `memory_bytes`, the combined peak of the case and its QEMU; `disk_bytes`; `guest_memory`, for the one profile whose configured memory, resident memory and backing differ; the host `locks` it takes shared or exclusive, such as the large-memory suite's exclusive lock; and the counts of local `ports` and native `loop_devices`.

A QEMU profile's optional `memory_profile` is `reserved` by default. `etude_qemu_memory` resolves its configured RAM, resident allowance, overhead and disk backing separately. An ordinary machine reserves all configured RAM plus 128 MiB for QEMU and its controller. The manifest validator requires `resources.memory_bytes` to cover the sum for every declared machine. A declaration of lazy or file backing alone cannot reduce that reservation.

`bigmem-boundary-v1` is the sole reduced reservation: the x86-64 direct rescue boot on the default PC with 72 GiB, one processor, the `max-nopdpe1gb` processor profile, an initial RAM image, no disks or devices, and `rach2.rescue` alone on the boot line. It reserves 2 GiB for guest pages and 2 GiB for QEMU, firmware and the controller, with no disk backing. Its `guest_memory` must declare those configured and resident amounts with `backing: lazy`. A case has at most one such machine, and may declare others beside it only when `resources.memory_bytes` covers them all. [`case.memory.example.json`](schemas/case.memory.example.json) gives the declaration.

A site permits the lazy backing with one line of its installed policy, `boundary_lazy bigmem-boundary-v1` (Installed launch admission), and in no other way. The owner adds that line once the site's own acceptance of the boundary boot has passed: `etude_qemu_hosttest --boundary` run on that endpoint under a claim of the 4 GiB reservation, with its peak and host readings recorded. The Mac has passed that acceptance, but has no installed policy and so no permission. A run that no installed policy admitted has no permission either. The launcher refuses the profile at a site without the permission with `ENOTSUP`. The launcher supplies an explicit anonymous `memory-backend-ram` with `prealloc=off` and `merge=off`, and `dump=off` outside macOS, selects it through `-machine memory-backend`, and disables memory locking. [QEMU's invocation reference](https://www.qemu.org/docs/master/system/invocation.html) describes these controls. On macOS it requires a zero soft `RLIMIT_CORE`, inherited by QEMU, since that host's QEMU cannot exclude anonymous RAM from a core file. On that host it refuses a nonzero limit with `ENOTSUP`. It refuses a boundary start without `memory_reserved_bytes` of at least the whole reservation, a kernel file over 64 MiB or an initial RAM image over 256 MiB. The caller obtains that reservation from the machine's ledger before starting QEMU and registers QEMU against it. A scenario invocation passes the site's permission through its optional `site.boundary_lazy`, which the set driver writes from the policy that admitted the run (The set driver), and `libetude-case` copies the profile's `memory_profile`. Since a case's machines may run at once, the library refuses, before QEMU starts, any boot of a case whose declared machines together reserve more than its `resources.memory_bytes`, and gives the launcher as `memory_reserved_bytes` that reservation less what the case's other machines reserve. On the boundary console only `exec /memprobe total\r` once and `poweroff\r` are accepted, and on its QMP only `qmp_capabilities`, `quit`, the `query-` commands and `human-monitor-command` with an `info` command line; another command, such as `object-add` or `migrate`, could make QEMU commit memory the reservation does not cover, and is refused with `EPERM`. This profile cannot run an allocation probe or `etude-guest`.

The allowance is a reservation for this fixed workload, not an operating system limit on QEMU's resident memory. The platform runtime proof must record the peak and retain the exact artifacts, QEMU version and host conditions before enabling it for comparison. Another workload, larger artifacts, another firmware or a preallocated backend needs a new analysis; it cannot reuse this profile. The 8 GiB boot that writes and reads 5 GiB keeps its full reservation.

`timing` declares each assumption about time that a case makes, with its file and line. Two kinds exist. A `clock_reference` compares a clock with an independent reference within the stated `uncertainty_us`. An `injected_delay` applies a delay as the stimulus and judges only the order or the state that follows. A completion bound is not an assumption about time. Synchronization by sleeping, a fixed poll or spin count, an assertion on wall time, a race with the host's disk and a forced accelerator have no kind and are refused. In the sources under `tests/cases/`, `suitecheck.sh` accepts a sleep only at a line an `injected_delay` declares, and an upper bound on a duration only at a line a `clock_reference` declares; a declared line with neither is a fault, and a program there reports a skip as `notrun`, never as printed text.

### Report records

A program reports on its standard output, in lines that begin with `@etude 1 `, as [`report.h`](include/etude/report.h) defines:

    @etude 1 begin guest.default.rngprobe
    @etude 1 assert cpuid-leaf7 pass
    @etude 1 branch source trusted
    @etude 1 assert trusted-urandom pass
    @etude 1 assert trusted-monobit fail 61 of 512 bits set
    @etude 1 end 4

`notrun ID REASON` says that an assertion could not be evaluated, `progress WITNESS UNITS` that a witness has completed UNITS in all, or for a quiet witness at those units that its work begins, and `child PID` that a process the program started may outlive it. `machine BOOT END`, which only a machine scenario writes, says that the boot BOOT, `MACHINE.N` with N counted from 1, ended as END: `panic`, `halted`, `reset`, `shutdown`, `qemu_exited`, `accel_failed`, `stopped` or `lost`, as the machine's ends are named under Results. A record is at most 255 bytes with its newline, and is written with one write(2), so that on the console it cannot be split by a kernel record. Fields are separated by single spaces; an identity is the manifest's, and a detail or a reason is printable ASCII. `begin` comes first and gives the case's identity, which a program that more than one case runs takes from `ETUDE_CASE`; every executor sets it in the case's environment. [`tests/probe_report.h`](../../tests/probe_report.h) writes the records for the freestanding probes. Each declared assertion is reported once, each group's branch once, each boot's end at most once, and `end` last, with the count of `assert`, `notrun` and `branch` records before it. Every other line is the program's own output, kept as evidence and never read as a result.

The report is `complete` when it has all of that and nothing else. It is `absent` when it has no record, `truncated` when it has no `end` and no other fault, and `invalid` when a record does not parse, comes after `end`, repeats an assertion, gives an undeclared one, one that is not the program's or one of an alternative that did not run, gives another case's identity or a branch the processor contradicts, moves a witness back or past its limit, names a child of a case whose `children` are not `reported`, gives the end of a boot of no machine of the case, or a second end of one, or comes from a case that is not a machine case, or has a count that does not match, and when a report with an `end` lacks an assertion it must give or a group's branch. A host program and a guest program under `etude-guest` write the records to a pipe; a program that is the designated init writes them to the console; a machine scenario writes them through `libetude-case`.

### Results

Each attempt has one results document, to which its history record's `assertion_results` refers. It gives the termination and what observed it; for a machine case, `machines`, the boots whose ends the scenario's `machine` records give, each with its end, beside the scenario's own end in the termination; the state of the report, the branch of each group, and each assertion that the case requires, once: the declared assertions outside every group, those of the chosen alternatives, and the executor's. An assertion reported but not declared goes in `undeclared`.

An assertion's outcome is `pass`; `fail`, with what was seen; `not_run`, with the program's reason; or `missing`, when nothing reported it. The attempt's outcome follows from them:

* `failure` when an assertion failed, a declared one or an undeclared one;
* otherwise `incomplete` when one is missing or not run, or the report is not complete, or the end was `stopped` or `lost`;
* otherwise `pass`, and the history then requires confirmed cleanup as well.

A not-run assertion is absent coverage and never a pass. A machine's `shutdown` and `reset` are taken only from QEMU's own events, the designated init's end only from the kernel's record, and a transport closed without either is `lost`. An accelerator that QEMU could not start is `accel_failed`, and etude does not try another.

### Frames

The controller and a responder exchange frames, one line each: `etude-guest` over Rach2's serial console under QEMU, and `etude-guest --stdio` natively or `etude-remote --stdio` on Linux and macOS over their standard input and output through SSH, as [`frame.h`](include/etude/frame.h) defines:

    #E1 SESSION BOOT SEQ ACK TYPE FIELD... *CRC

SESSION is the first sixteen hexadecimal digits of the SHA-256 of the run's identity, and an ATTEMPT field the same of an attempt's. BOOT is the responder's token for the boot it runs in: the same for every responder of one boot, different in another. The responder is `etude-guest`, or `etude-remote` on Linux and macOS. SEQ counts the frames a side has sent on the connection, from 0. A process is named by its PID and its START, the time it started in the kernel's ticks since boot, so that a reused PID is told apart. A frame over the size bound, with a bad CRC, or from another session or boot is not acted on, and the responder keeps it as evidence.

Each command has a number, CMD, that the controller allocates, records before it sends the command, and never reuses in the run. The responder records each command's type and fields before it acts, and the events it caused, in its state directory, so that a later responder of the same boot has them too. A repeated command is answered by the same events again, and its effect is not repeated; a CMD sent again with other fields is answered by `error CMD conflict`. `data` and `seal` carry the CMD of their `put`, and are part of that command. `etude-remote` answers `hello`, `status`, `get` and `bye` afresh when they are repeated, since they have no effect to repeat.

* `etude-guest` sends `alive` when it starts, with the session `0000000000000000`, SEQ 0 and its versions, PID and START. Over standard I/O it is the connection's first frame, so the `ready` that follows has SEQ 1, as `etude-remote`'s does; on the serial console it takes no SEQ, so a session's frames count from 0, and it is sent again at each resend interval until a hello comes. VERSIONS is a list of decimal versions separated by commas. The controller's `hello`, with BOOT from `alive`, a session of its own and SEQ 0, opens the session; it offers the versions and the largest frame, and `ready` answers with the version and the frame bound they share, 255 bytes at most on the serial console, or `error version`; a hello whose largest frame is under 255 bytes is answered by `error limit`. `etude-remote` and `etude-guest --stdio` take the session's lock before their `ready`, so that a responder still ending the session's last connection finishes first. An `etude-guest` that finds the lock held sends SIGTERM to the `etude-guest` that the session's owner file names, when /proc shows that it is still that process, since the machine may not have seen that one's connection end.
* `put` names a file, its size, digest and mode, `data` frames give its bytes from offset 0, and `seal` ends it: `stored` answers the seal with the digest, or `error damaged` when the bytes do not have that size and digest, and they are not kept; data out of order or past the size are answered the same way, and a file over the responder's bound by `error limit`. Stored files are kept by digest. When the store or a `--stage` directory already has a file of that name, size and digest, no `data` is needed, and any that comes is ignored; a controller that knows the image stages the file sends `put` and `seal` alone. `get` sends a file of an attempt back in `data` frames with the get's CMD, and `sent` gives its size and digest for the controller to check. Its NAME is the attempt's token, a slash and a path in the attempt's directory: `work/...` for the workspace, and `out.1` and `out.2` for the output kept.
* `run` starts an attempt from an invocation stored before it, named by its digest. `etude-guest` checks the invocation, copies its files from the store into a new workspace and checks each digest, makes its fixtures, registers the child in the attempt's record before the child's exec, and sends `started`. The child's output comes in `out` frames, by descriptor and offset, and is kept up to the invocation's bound. A line `@etude 1 child PID` of its standard output names a process the child reported. When the child ends, its process group and the reported processes are killed, and `exit CMD ATTEMPT KIND VALUE` gives the end, `exited N`, `signaled S`, `stopped -` or `lost -`; `stream CMD ATTEMPT FD SIZE TOTAL SHA256`, for standard output (FD 1) and then standard error (FD 2), the bytes sent in `out` frames, the bytes the stream carried, and the SHA-256 of those sent, or `- - -` where they are not known; `usage CMD ATTEMPT CPU-US METHOD PEAK-BYTES METHOD` the processor time of the child and the descendants it reaped, in microseconds, and its peak memory, each a number, a number and `+` for a lower bound, or `-` where it cannot be read, with the method that measured it or `-`; and `cleaned` whether every process of the attempt is gone: `confirmed`, or `unconfirmed` when one is left after the grace period. The workspace stays until `remove`, which refuses an attempt that has not ended, and after a failure it stays for its evidence.
* `exec`, on the serial console alone, runs a case of the `init` role. Under QEMU `etude-guest` is the boot's designated init; it sends `started` with its own PID and START, waits until every frame it sent is acknowledged, puts the console back as it found it, and executes the program in its own place, so that the program becomes the designated init. No frames follow: the controller reads the report records from the console and the end from the kernel's record. Every other command meanwhile is refused. Over standard input and output `exec` is answered by `error refused`.
* `cancel` ends an attempt: its process group gets SIGTERM, then SIGKILL after the invocation's grace period, and the `exit` gives `stopped`. `state` answers the cancel with the state it found. `status` answers with the attempt's state, `unknown`, `preparing`, `running`, `ended` or `cleaned`, and sends its final events again; it changes nothing, so a repeat is answered from the present state. `bye` stops the attempts that run and ends the session: over SSH the responder then exits, and on the serial console `etude-guest` sends `alive` again for the next session. `etude-remote` removes the session's stored files at `bye`.

Over SSH a frame is never lost or reordered, so a bad CRC, a gap in SEQ, an acknowledgement of a frame not sent, a frame over the bound, and a frame of another session or boot end the connection. Over the serial console a receiver drops a damaged frame, a repeated one and one past a gap, and acknowledges what it has received in order; a sender sends every frame not yet acknowledged again, with the same SEQ and bytes, when the oldest has waited a resend interval. An `ack` frame carries an acknowledgement alone: its SEQ is the sender's next, not taken, and it is neither sequenced nor acknowledged. Lines of the console that are not frames are kept as evidence and searched for the kernel's records.

`etude-guest` enforces each attempt's deadline itself. When its connection is lost, by the end of its input, a frame it cannot accept over SSH, or SIGHUP or SIGTERM, it cancels its attempts, cleans up, keeps their final events in their records, and exits with status 1; the next connection's `status` reads them. An attempt whose `etude-guest` was killed before it recorded the end is settled by the session's next `etude-guest --stdio` once it holds the lock, and otherwise by the next `status` or `remove`: what is left of the process group its child made is killed, whether or not the child itself still runs, and the attempt's end is recorded as `lost`, with its output's sizes and its usage unknown. A process is left of that group when it is in the group and in the session whose number is the child's PID, while that PID names the child or no process; `etude-guest` reads them from `/proc/PID/stat` on Linux and Rach2, and from the sysctl `KERN_PROC_PGRP` and getsid(2) on macOS. The record gives the boot the attempt ran in, and nothing is killed for an attempt of another boot. Its cleanup is recorded as confirmed when no process but a zombie is left of the group; `etude-guest` waits up to two seconds after the kill for that. At the lock `etude-guest` also gives the record of each of the session's runs the final events of its attempt's record that it lacks, after removing a last line cut short: the whole end of an attempt it has just settled, or the part of an end that an `etude-guest` killed while appending it did not append. The run sent again is then answered with the whole end. `etude-remote` does the same at a lost connection; the session's next `etude-remote` records the end of an attempt whose responder was killed as `lost`, with its output's sizes and its usage unknown and its cleanup unconfirmed.

### Invocations

An invocation gives one attempt of a guest case: the run and attempt identities, the case, the program and its arguments, the environment, the standard input, the role, the files with their digests and modes, the fixtures with the values the controller assigned (`ids` and `ports` among them), the deadline and grace period that the plan fixed, and the most output to keep. `${WORKSPACE}` in an environment value is the attempt's workspace. A native invocation of the `init` role is refused. A scenario invocation gives one attempt of a machine case, as Machine scenarios says.

### Machine scenarios

A machine scenario is a host program that defines `etude_scenario` and links with `libetude-case`, whose `main` calls it once per attempt. The executor runs it as a host attempt, `SCENARIO INVOCATION`. The scenario invocation gives the run and attempt identities, the manifest and the case, the architecture, the store and the digest of each artifact of the case's `prepare`, the path of each host tool of its requirements, the site's accelerator, QEMU programs and UEFI firmware, the bound the plan fixed for each step and for the cleanup, the local ports the plan reserved for the attempt, as many as its `resources.ports`, the attempt's scratch directory, the grace period, the console and output bytes kept, and the resend interval of `etude-guest`'s frames.

The scenario begins each step with `etude_step`, in the order of the manifest; a step it passes over cannot be begun later, and a step ends when the next begins or the scenario returns. It boots machines, waits for text on a console at a known offset, types, sends QMP commands, runs invocations under the machines' `etude-guest`, runs host tools and artifacts of its manifest, starts, waits on and stops its services, and reports its assertions, all as [`scenario.h`](include/etude/scenario.h) declares. Several machines may run at once: a boot is of the step's machine, and a wait, typing and QMP may go to any machine that runs. Each wait ends with `ETUDE_BOUND` when the step's bound expires, with `ETUDE_LOST` when the machine or its transport goes, and with `ETUDE_STOPPED` when SIGTERM, SIGINT or SIGHUP arrives; none is taken for the event waited for. Text is found only in console bytes QEMU wrote, and once QEMU has ended or closed the console, a wait for text not there is lost at once. `etude_console_find` searches the bytes already read, with no wait and outside a step; the library reads a running machine's console only while it waits, so the search shows a text absent, `ETUDE_FAILED`, only on a machine that has ended, and gives `ETUDE_LOST` when the console wrote more than the case keeps. `etude_case_id` gives the attempt's case, so that one program may be the scenario of every case of its family. A machine's end is the launcher's: a shutdown, a reset and a panic come only from QEMU's SHUTDOWN event, and an exit without one is `qemu_exited`, though the console says that the machine powered off. The end that `etude_wait_end` observes, or that `etude_boot` observes of a machine that ends while it starts, is written in the report as `machine MACHINE.N END`, as Report records says. The kernel's panic stops every processor with interrupts off and gives QEMU no event, so `etude_fault` records the fault of a boot that still runs: a panic only when the console bytes read have a critical record whose subsystem is `panic`, so the scenario waits for the panic's text first, and a halt only when the human monitor's `info registers -a` shows each processor of the profile halted with interrupts off. Otherwise it gives `ETUDE_FAILED` and records nothing. A boot's end is recorded once: the first stays, and a later fault or wait writes no other. `etude.fault` judges the record against the console. A request the manifest does not declare is `ETUDE_REFUSED`: a boot of another machine than the step's, a disk not of the machine's profile, QMP of a machine without it, typing at a machine without a console or whose console `etude-guest` has, a QMP command or console text that the launcher does not take on a boundary machine, a fault other than a panic or a halt, a fault of a boot whose end is recorded, a panic of a machine without a console, an artifact, tool or service not of the case's, a second start of a service that runs, a step out of order, and any wait outside a step; `etude_port` gives 0 for a port the case lacks.

A machine's kernel and RAM image, and the medium of a CD, are read-only objects of the store, read by their digests before the boot. Each other disk is the attempt's private writable copy of its artifact, which a `disk` fixture names, an empty disk of its declared size, a sparse file, or an overlay whose backing file is its base's object, by its absolute path, in `copies/` of the scratch directory; it is made at its first use and given again to every later boot and host tool of the attempt, so that dependent steps keep what earlier ones wrote. `etude_private_copy` gives a disk's path, so that a host tool such as `qemu-img`, a tool of the case's requirements, can read an overlay's map or convert it to a raw image between boots. Each boot is a QEMU of its own, `MACHINE.N`, whose console goes to `evidence/MACHINE.N.console` as QEMU writes it, so that the file has every byte before an offset that a wait gave. The consoles stay in the scratch directory on every path, for the executor to search for the kernel's records and to remove. A boot whose profile selects `audio` records to `evidence/MACHINE.N.wav`; `etude_audio` gives that boot's path for a host tool such as `wavcheck`. Read it after `etude_wait_end`, when QEMU has finished the WAV header and samples. Each boot has a separate file, removed after a passing attempt and kept with the other evidence after a failure. The frames of each card that the profile's `captures` names go to `evidence/MACHINE.N.netK.pcap`, which `etude_capture` gives in the same way, and which is whole once the machine has ended. A machine whose `helper` is true boots to the kernel's debug shell, where the library types `exec /etude-guest --stage / --resend-ms N` once the shell says `Type 'help' for available commands.`, and the boot ends when `etude-guest` has answered hello. `etude_guest` runs an invocation artifact of the `ordinary` role and of the scenario's own case: each of its files is stored from `etude-guest`'s stage directory, or with its bytes from the store when the stage lacks it, then the invocation, and then the attempt runs, its report records other than `begin`, `end` and `child` becoming the scenario's own as they arrive. A host tool runs in the scratch directory, an artifact from an executable copy in `bin/`, its standard output kept in `evidence/OUTPUT` and its standard error in `evidence/OUTPUT.err`, which `etude_evidence` names.

A service is a host attempt of the same kind that runs in the background. `etude_service` starts it with the scenario's arguments, typically a port that `etude_port` gives, and returns once its standard output has the manifest's `ready` text; a service that ends first is `ETUDE_FAILED` with its end, and one not ready within the step's bound is stopped and gives `ETUDE_BOUND`. `etude_service_wait` finds text in its standard output, and is lost once the service has ended without it; `etude_service_end` waits for it to end by itself, and `etude_service_stop` ends it. Each start N of service S keeps its standard output and error as `evidence/S.N.out` and `evidence/S.N.err` once it has ended. A service may be started again after it ended. A service whose end the scenario has not seen, by one of these calls or a lost wait, is ended by the cleanup, and must end by the cleanup's SIGTERM or SIGKILL: one that exited, or was killed by another signal, ended by itself while the case ran, and the attempt fails.

A suspension stops a machine's QEMU process for a time while the guest's clocks go on, as a host that deschedules QEMU does. A QMP `stop` is not the same, since it stops the virtual processors while QEMU still runs its timers. The workload declares each suspension in `suspensions`: its `suspension_id`, the `machine`, its `cycles`, the `run_us` the machine runs and the `stop_us` it stays stopped in each cycle, and the counter `witness` that its stops advance. `etude_suspend` runs the cycles in a step of that machine. In each it serves the case for `run_us`; has QEMU's executor send SIGSTOP to QEMU's process group; waits until the executor has seen QEMU stop, and reports the witness's progress; holds the stop for `stop_us` from the time the stop was seen; and has the executor send SIGCONT, and waits until it has seen QEMU continue. It gives the time of each stop seen and of each SIGCONT on the monotonic clock, so that a scenario can tell from the host's clock what the guest did in a stop. Every interval is a wait of the interface, which ends early at the machine's end, the step's bound or a stop, so the intervals are the workload's and none is a sleep. The scenario never has QEMU's PID: the signals go only to the process group of the QEMU that the executor started and keeps, so a scenario cannot stop or resume any other process, and QEMU's processor time, memory and cleanup stay the executor's. `etude_suspend` resumes QEMU before it returns, by every path, so that the cleanup's QMP commands are answered; when the scenario is killed outright, QEMU's keeper cancels QEMU with SIGTERM and then SIGCONT, and the launcher resumes a suspended QEMU before its `quit`. A suspension that the workload does not declare, one of another machine, and one outside a step are `ETUDE_REFUSED`.

The library writes the report: `begin`, each `assert`, `notrun`, `branch` and `progress` as the scenario reports it, a `progress` record of the case's first witness of kind `step` at the end of each step, and `end` once `etude_scenario` has returned 0 with no stop. The cleanup stage has the cleanup's bound. When the scenario did not return 0, a stop arrived, or an assertion of the scenario's was not reported once and held, it first collects the diagnostics of each machine that runs with QMP: the replies to `query-status`, `query-cpus-fast` and `human-monitor-command` with `info registers -a`, within the grace period, kept in `evidence/MACHINE.N.capture` a line each, with `no reply` or `not sent` for one that did not come. It then stops every service and machine still running and waits for each to end. Everything a case runs is an attempt of its own executor, whose keeper ends the attempt's process group and descendants, so the cleanup ends only the case's own processes, and a scenario killed outright leaves its keepers to end them. It removes its copies, executables and evidence other than the consoles when every assertion of the scenario's was reported once and held, nothing was refused, failed or lost through it, and every cleanup was confirmed; otherwise it keeps them and says `etude-case: kept: SCRATCH` on stderr. The exit status is 0 when `etude_scenario` returned 0, no stop arrived, every cleanup was confirmed and no service ended by itself unseen; 1 otherwise; and 2 for a wrong usage or an invocation, manifest or store it cannot use, an invocation's ports among them that are not as many as the case declares, each above 1023 and given once.

### History

The plan's items refer to a case by three digests, each of a canonical JSON document taken from the manifest: members sorted by name, no space outside strings, and `schema_version` 1.

* The workload: `case_id`, `architecture`, `workload`, the program and role of `execution`, `steps`, `services` and `progress`.
* The assertion inventory: `case_id`, `assertions`, `branches` and `termination`.
* The profile: `case_id`, the placement, `requirements`, `machines`, `resources`, the privileges, and the `isolation` of a host or QEMU placement or the `native.fixtures` of a native one.

[`digest.c`](digest.c) computes them. Equal manifests therefore give equal digests, and a comparison of two runs finds a changed workload by its digest. The results document of each attempt is the history's `assertion_results` blob.

The plan's `reproduce` blob is a document of [`schemas/reproduce.schema.json`](schemas/reproduce.schema.json), as [the example](schemas/reproduce.example.json) shows: for each item, the directory and the environment it runs in, the commands that prepare it, the command of the case, and the command that runs the case under a profiler, or the reason the platform has none.

### The verdict

`casecheck verdict` judges one run of ci from its history: the streams HISTORY names, each a `.jsonl` file or a directory of them, and the blobs in STORE, found by digest alone, as the comparison finds them. ARCH is `i686` or `x86_64`, SET is the name ci gives the set, and SUITES is the suites asked for, separated by commas. The case manifests are the `.json` files of CASES, `tests/cases` by default, and with `-c` the plan must have tested COMMIT. An item belongs to the suite that is the last part of its family's identity, split at dots, that SUITES names, so that the family `guest.default` is the suite `default`; an item of no suite asked for belongs to SET.

The run passes only when all of these hold:

* the streams are whole and valid, of one run, with one plan record and one run record of that plan, and each record identity once;
* each attempt record is of the plan, of one of its items and of an attempt the plan gave that item, once; each step record is listed by its own attempt or by the run's preparation; and an attempt lists no step record but its own;
* the plan has an item of each suite asked for, and, for each case of that suite's manifests that runs on ARCH or on the host, as many items of distinct repetitions as its workload's `repetitions`;
* each item has an attempt, and every attempt of it passed with confirmed cleanup, since an item comes to the worst of its attempts' outcomes, as the run record gives it, and a retry that passed does not hide the attempt it repeats;
* an attempt recorded as a pass has each of its steps passed with confirmed cleanup, and its results in STORE with the size and digest its record gives, valid by Results, of its run, attempt, item, case, placement and assertion inventory, and judged a pass for ARCH;
* each step of the run's preparation passed with confirmed cleanup, and so did the run's own cleanup;
* the run's summary lists each item once, with its attempt records and the outcome its attempts give, and its result is the one the items and the preparation give.

A finding goes to stderr. An item that did not pass is printed as `item ID: CASE on ARCH: OUTCOME, in SUITE`, a preparation step that did not pass as `preparation STEP: OUTCOME, cleanup CLEANUP`, and the last line is `casecheck: result: passed` or `casecheck: result: failed: NAME...`. The names are `runner` first, after any finding, since the records then cannot show what ran; then each suite asked for that has an item that did not pass or work left out of the plan, in the order asked; then SET, for an item of no suite asked for or a failed preparation. The status is 0 for a pass, 1 for a failure, and 2 only for a wrong usage or a results schema that cannot be read; a manifest, the case schema or a stream that cannot be read is a finding. Each item that [`history_failures`](failures.h) lists thus fails its suite or SET, or gives a finding, so that `tools/ci/report.sh` finds no attempt that did not pass in a run whose verdict passed.

### The budget

A budget policy is a document of [`schemas/budget.schema.json`](schemas/budget.schema.json), of the policy `budget-v1`, which sets for one site the limits that the plan's measurement record under `dev-log/` gives each class of run. `site` is the machine whose reference capacity routine testing is charged on: its `machine_id`, `os` and `accelerator`, which a plan's `environment` must give for its run to be charged there, and its `capacity`, in thousandths of a processor and in bytes of memory and disk. `classes` gives the limits of each class of run, which its plan's `purpose` names: `goal_us`; `growth_us`, the time past the goal kept for growth; `ceiling_us`; and `cleanup_reserve_us`. The goal and the growth together must be within the ceiling and the reserve below it, and the deadline of a run's work is the ceiling less the reserve. `one_time_setup` lists the step IDs whose first run on a machine is reported apart from the charge, such as the installation of prerequisites or the first build of a cross toolchain.

A run's `budget` names its policy document by the SHA-256 and size of its bytes, and records the four limits of its class. Its `charged_us` is the run's own interval, from the first grant of capacity to the confirmed end of cleanup, extended to cover each attempt and step of the run that lies outside it on the same clock. Steps of the `queue` stage are not charged. A step of the `one_time_setup` stage is left out of the charge, into `one_time_setup_us`, when the policy lists its step ID, no earlier run on the machine passed that step, and it ended before the run's other work began; any other is charged. Every other step is charged, preparation among them.

Preparation shared by a run's items is a step whose `item_id` and `attempt_id` are null, of the stage `build` or `prepare`, and the run record lists it in `preparation_steps`. Its `step_id` is the target of the node it prepares, as Cases gives it: `build/NODE`, or `build/x86_64/NODE` for an artifact made for each architecture when the architecture is x86_64. A run's attempts and preparation are its own: a run whose summary or `preparation_steps` gives a record of another run, an exempt first run's included, fails its budget.

A recorded verdict of `unknown` is accepted as unevaluated, as the repetition driver writes it; the checker still judges the run from its records and compares any known charge and one-time setup time. Other recorded verdicts must match the judgement.

### Repetition records

A run of repetitions looks for a result that depends on the order of the cases, on how many run at once, or on load beside them. Its seed fixes the plan by the policy `repeat-splitmix64-v1`. One splitmix64 generator, started at the seed, makes three choices in turn:

1. The selection: `pick` cases, the first places of a partial Fisher-Yates shuffle of their indices, kept in the order given; every case when `pick` is 0 or not below their count.
2. The order: each selected case's repetitions, in the order given, shuffled by Fisher-Yates from the last place down, the place `i` exchanged with a place below `i + 1`.
3. The loads: for each item in that order, a number below 100; when it is below `load_percent` and there are loads, a number below their count chooses the item's load.

A number below N is the generator's output modulo N, drawn again while the output falls in the incomplete last span of 2^64 values, so that no value is likelier than another. A seed is at most 2^53 - 1. It reproduces the selection, the order and the loads on any host, but not the host's schedule.

The repetition record is a document of [`repeat.schema.json`](schemas/repeat.schema.json): the policy, the run, the seed, what the plan was drawn from (each case with its architecture and repetitions, the loads with their kind and amount, `pick`, `load_percent`, the `width` of cases run at once and the `retries` of an attempt that did not pass) and the items in their order, each with its identity, `RUN:CASE:ARCH:rREP`, and its load or null. The plan record names it as its `selection` and its `concurrency`. A reader draws the plan again from the record's own inputs; a record whose items are not that plan's is refused.

### Suite lines

`history_lines` gives each item of the run's plan to the suite of the map that holds its case or its family, and each item the worst outcome of its attempts, so that a retry that passes leaves the failure: `failure` before `incomplete`, `incomplete` before `cancelled`, and `cancelled` before `pass`. A suite's outcome is the worst of its items', and a suite with no item in the plan did not finish. In the map's order, it prints for each suite a line for each item that did not pass, and then the suite's line:

    run: fpu: guest.fpu.xsave on x86_64: failure: the save area differs
    run: fpu: FAIL in 5s
    run: default: PASS in 3s

An item's line gives its case, its architecture unless it is `none`, its repetition unless it is 0, its outcome, and the reason of its first attempt of that outcome, or `no attempt of it ran`. A suite's line is `PASS` on standard output, and `FAIL`, `INCOMPLETE` or `CANCELLED` on standard error; its time runs from its first attempt's start to its last attempt's end, rounded up to a second, and is `?s` when an attempt has no end or the attempts were timed on different clocks.

A failed attempt is its suite's own, and so is an incomplete attempt that nothing outside its case disrupted, such as one whose bound ran out or whose cleanup was unconfirmed. An attempt that something outside its case disrupted, as a lost connection to its executor does, is a fault of the runner, and so is whatever leaves the account of the run in doubt: a stream cut short or not a history, a record of another run, a plan record missing or given twice, a run record missing, which means that the run did not finish, or given twice, an item in no suite of the map or in two, a suite with no item in the plan, an item with no attempt that was not cancelled, an attempt of another plan or one the plan did not give, and a run record that lists an item or an attempt that the plan or the history lacks, leaves one out, or disagrees with the attempts on an item's outcome or on the run's. A cancelled item is nobody's failure. Each fault is a line `run: runner: WHAT`, and they are followed by `run: runner: FAIL in Ns`, the run record's elapsed time. When the map has the runner's own suite, `runner`, a fault fails that suite instead: its line is `run: runner: FAIL in Ns`, with its own time, and no second line follows the faults.

Then `run: result: failed: NAMES`, on standard error, names the suites with an item that failed or did not finish by its own attempts, then the names `-f` gives, and `runner` when the run has a fault, once, whether or not the map has that suite; with none of them there is no such line. The last line, on standard output, is `run: result: failed` when an item failed or `-f` named a failure; otherwise `run: result: incomplete` when an item did not finish or the run has a fault; otherwise `run: result: interrupted` when an item was cancelled; and otherwise `run: result: all N suites passed`.

These are the lines of the old runner that the readers take. `tools/ci/run.sh` records as failed the names on the `run: result: failed:` line after the last line of a suite that passed or failed, `runner` among them, which `tools/ci/report.sh` takes as a reason for a hold, and the name of the set it ran when there are none, as after an interrupted run. Bisection takes a run that ends with `run: result: failed` for a failure, unless that line names `runner` and the bisection did not ask for the suite of that name, and any other result that is not a pass, as after a stalled case or a fault of the runner, for an untestable commit, never for a pass.

### The status record

The status record says what a run of etude does, for a person and the manager to read through [`tools/flow/test_status.py`](../flow/test_status.py). The reader finds it in the tree the run tests, as `build/.run.status.NAME`, where the old runner keeps its run records. `etude_status_write` of [`status.h`](include/etude/status.h) writes it to `PATH.new` and renames that over the record, so that a reader finds the old record or the new one whole. It is text, a field on each line:

    etude-status 1
    owner 41235 8812345 1
    run run1
    ledger /home/testing/.local/state/etude/ledger
    args core
    written 1792491300000000
    wait run1:big:a0 guest.memory.big x86_64 1792491293000000
    attempt run1:xsave:a0 guest.fpu.xsave x86_64 execute running gap 1792491295000000 1792491355000000 60000000
    attempt run1:hang:a0 guest.default.hang i686 execute expired gap 1792491289000000 - 1000000

`owner` is the process that writes the record, its PID, start and whether the start is known, as the ledger gives a process; `run` the run's identity; `ledger` the directory of the machine's ledger; and `args` what the run was asked to do. Times are microseconds since the epoch on the system's clock. A `wait` line is an attempt that waits for admission, with its case, its architecture and the time it began to wait. An `attempt` line is an attempt that runs, with its case, its architecture, its stage, `running`, or `expired` once its watchdog ran out and the run is ending it, and the bound that runs out next or that ran out, `case`, `stage`, `gap` or `quiet`; then the time of its last progress in execution, or of the start of any other stage, the time the bound runs out, `-` once it has, and the bound's length. `etude_status_watch` takes an attempt's fields from its watchdog.

The reader prints a `wait` line as a wait for admission, with the place of the attempt's request in the ledger: the protected request, one behind it, a claim admitted since the record was written, or no request at all. It prints an `attempt` line as working while its bound has not run out, as stalled and being ended once it is expired, and as stalled with a fault of the run once its bound has run out and it is still `running`. It then reads each ledger that a record or the machine record of the tree's owner names, and prints the requests that wait and the claims that no running owner keeps, live or uncertain with the reason, as recovery judges them (The ledger). For an uncertain claim it gives the `etude-ledger drop` command that releases it once a person has established that nothing of it runs.

### The version cache

A machine keeps the versions of etude built on it in a cache: `${XDG_CACHE_HOME:-$HOME/.cache}/etude` on Linux, macOS and Rach2, `%LOCALAPPDATA%\etude` on Windows, or the directory `-C` gives. A version is etude's programs built from one source by one recipe, for one platform, by one compiler. Its key is the SHA-256 of the first five lines of its record:

    etude-version 1
    source 1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0
    platform macos arm64
    compiler a856ec74c559401131ad608625ef252fb2db6c78bc0c480c1c4c782ee4896db1
    flags -std=c99 -O2

`source` is the SHA-256 of the source's list, a line `SHA256  PATH` for each of its files in the byte order of their paths. The source is the C files, headers and make files under `tools/etude` but its fixtures, the schemas under `tools/etude/schemas`, and `utils/sha256.c` and `sha256.h`; a change anywhere else, a kernel commit among them, keeps the key. `platform` is the platform as `tools/setup/prereq.sh` names it, and the machine as `uname -m` gives it. `compiler` is the SHA-256 of what the compiler prints for `-v`, and `flags` are its flags, which with `version.mk` make the recipe.

The rest of the record gives the `key`, the compiler's command line as `cc`, the version's directory as `build`, relative to the cache, and a line `program NAME SHA256` for each program. The cache has two directories:

| Path | Contents |
| --- | --- |
| `versions/KEY` | The record of a published version, a hard link of its build's `version` |
| `builds/KEY.XXXXXX/` | A build: `src/`, its source; `sources`, the source's list; `bin/`, the programs; `version`, its record |

Versions of different keys live side by side, and a published version is never changed. A version is published by a hard link, so the cache must be on a file system that has them: on Rach2, ext2 or tmpfs, and not KRFFS. A build directory that no record names is a build that failed or was stopped, and nothing uses it. A published version whose record or programs do not match their digests is damaged, and a request for it fails until a person removes `versions/KEY`.

### Compatibility with old runs

[`bridge.h`](include/etude/bridge.h) and [`posix/bridge.c`](posix/bridge.c) connect a durable claim to the old runner's POSIX record locks. After reserving the claim and before registering execution, the worker calls `etude_bridge_start`. Its separate lock holder takes `LOCKS/rach2-host.gate` before `LOCKS/rach2-host.lock`: an exclusive caller keeps both write locks, and a shared caller releases the gate's read lock once it owns the host's read lock. Thus an exclusive caller waiting for old runs keeps later shared callers behind it. For legacy execution the holder takes the first free `LOCKS/rach2-ports.N`, N from 0 to 9, and gives the offset N * 1000. Native TCP and UDP allocators choose and bind ports from 25000 through 65535, outside every old table and offset; a reservation does not replace bind(2).

The holder closes inherited descriptors, enters a session apart and reads the ledger through a handle of its own. It keeps the locks until recovery finds no claim of that identity. A worker's death, a live descendant, an unreadable ledger and unconfirmed cleanup therefore do not release the compatibility locks. A confirmed finish is followed by `etude_bridge_join`; an incomplete finish uses `etude_bridge_detach` and reports the holder's PID. For an uncertain claim, establish that nothing remains and drop the claim with `etude-ledger drop`. Do not kill its holder to recover capacity. A failure of the holder itself requires stopping admission and establishing the state of its execution before old runs resume, as a failure of the admission authority does.

Before enabling shared admission on a machine, route every subsequent old-checkout invocation through this wrapper and every new execution through the bridge. Then run a wrapper command with `alone` that does no work, such as `/usr/bin/true`. Its exclusive lock drains old unwrapped runs before the command completes. Only then enable shared scheduling. An old unwrapped run after enrollment would bypass resource accounting, even though its port and exclusive host locks still agree. Every account uses the same ledger and lock directory. Windows and WSL use the machine's single configured admission endpoint.

Bisection is the route of old checkouts. [`bisect.yml`](../../.github/workflows/bisect.yml) builds `master`'s etude in the version cache with `version.sh -l`, outside the tree whose commits [`tools/ci/bisect.sh`](../ci/bisect.sh) checks out, and gives the script that version's `etude-bridge`. On a machine with a record (The machine record), each build and each run of a test is then one bridge command, a claim of a quarter of the record's processors and memory and of the ledger's file system, and the old run is held to its claim by `RACH2_WORKERS` and `RACH2_MEMORY_MIB`; a run whose suite declares more memory claims more, and one past half the machine's takes the host alone. A run takes a port block with `-p`, so that the old `tests/run`, which takes neither the host lock nor a block when `RACH2_PORT_OFFSET` is set, cannot wait for a lock its own claim holds. That is true of every commit whose `tests/system/suites.mk` reads the offset; an older commit forwards fixed ports, and its run is untestable. The script reads the bridge's result from `-r`, so that a claim refused, cut off or left uncertain makes the commit untestable and the range unresolved, never a failure or a pass, and a run that passes is taken as one only with a result line for each suite it was asked for, in that run's own output. A commit whose `tools/ci/run.sh` reads etude's history (`results=history`) is judged as `run.sh` judges it: its `tests/run` writes the history of each run under the test's log through `RACH2_RESULTS`, and the commit's own `casecheck verdict` (The verdict) judges it against the commit's `tests/cases`. Such a run passes only when the verdict passes and `tests/run` exits 0, and fails only when an item of a suite asked for failed, the verdict does not name `runner`, and `tests/run` failed. An item that did not finish, a case left out of the plan, a failed preparation, a history missing or in doubt, a verdict not given, and a status that disagrees with the verdict make the commit untestable and the range unresolved; so does an unfinished run whose `run.sh` lists `runner`. bisect.sh's header gives the details.

### Installed launch admission

`launch.sh` is the temporary entry to shared admission, installed outside every checkout as an executable, for example `/usr/local/libexec/rach2/etude-launch`:

    etude-launch [-r FILE] build|legacy|alone COMMAND [ARGS...]

The root `make` and `tests/run` consult `/etc/rach2/etude-site`, or the absolute path `ETUDE_SITE` gives. With no default file they keep their existing behavior; an explicitly selected file that is missing is an error. Bisection consults this policy before the account's private machine record, and uses its installed launcher for each build and run, even after checking out an older commit. The owner transport, `tools/dev/testing.sh run`, and CI, `tools/ci/run.sh`, admit each build and test step separately. A direct tool or an old checkout uses the installed command above: `build` for a build, `legacy` for a command that may run its tests, and `alone` for a command that needs exclusive access. `make test` admits each of its three test steps separately. `legacy` refuses a checkout whose `tests/system/suites.mk` does not read `RACH2_PORT_OFFSET`.

The POSIX keeper and compatibility lock holder clear `RUNNER_TRACKING_ID` from their inherited environment bytes. GitHub Actions reads those bytes when it kills a job's orphan processes. The case keeps its marker; its keeper clears its own only after forking the case. Thus the keeper can finish cleanup and write its verdict after the job's controller has been killed, and the lock holder can release the claim and locks. A killed keeper still leaves an uncertain claim that requires an operator.

Every account, worker loop and CI service on one physical machine must select the same file. It is data, never shell code, with each field once and no other field:

    etude-site 1
    endpoint linux
    launcher /usr/local/libexec/rach2/etude-launch
    ledger /var/lib/rach2/etude/ledger
    locks /tmp
    bridge /usr/local/libexec/rach2/etude-bridge
    capacity 32000,103079215104,429496729600
    wait 20400
    seconds 20400

The optional field `boundary_lazy bigmem-boundary-v1` permits machine cases on this endpoint to boot the lazy 72 GiB boundary profile (Resources and timing); it names that profile, and the launcher refuses any other value. `endpoint` is `linux` or `macos` and must match the local system. Windows launches are refused: Windows and WSL may not each admit work against their own process tables. During Ubuntu enrollment all native Windows build and test entry points stay disabled. `launcher`, `ledger`, `locks` and `bridge` are absolute paths on the endpoint, accessible to every participating account. The ledger must already have a `claims` file of format `etude-ledger 1`; an unavailable or incompatible endpoint refuses execution. `capacity` gives the site's admitted thousandths of a processor, memory bytes and disk bytes, each positive and at most 15 digits, rather than the whole hardware reported by deployment. Claims are admitted by memory alone; the processors and disk bound one request, and the processors a build's unbounded `-j`. `wait` and `seconds` are the admission wait and execution bounds, each from 1 to 86400 seconds. The example is a format example, not a choice of the testing host's limits.

Ordinary builds and test selections use `shared` admission and a read lock on the compatibility host lock. A build counts its job count in processors and 40 GiB of temporary disk, and claims one GiB of memory per job plus one GiB. Its job count is at least `JOBS` (4 by default), increased by a larger `-j` or `--jobs` in the command or inherited make flags. An unbounded `-j` uses the admitted processor count. The root make keeps a smaller explicit job count; an unbounded count uses the admitted processor count. The make wrapper also preserves smaller explicit counts and make's default of one job. `ETUDE_BUILD_JOBS` passes it to `make.sh`, installed as `etude-bin/make` beside the launcher and prepended to `PATH`. This wrapper replaces a top-level make's unbounded `-j` with the admitted count, including builds from older preparation binaries. A child that clears the budget from its environment uses one job; if it also clears `ETUDE_MAKE_REAL`, the wrapper finds the real make on `PATH`. Recursive makes keep their parent's jobserver; `JOBS` also bounds the e2fsprogs build. A shared request larger than site capacity is refused.

A recognized `legacy tests/run SUITE...` (also through `sh`) selects suites from the checkout's registry, including `core` and `all` and filtering by `ARCH`. Ordinary selections preserve `RACH2_WORKERS` and `RACH2_MEMORY_MIB`, defaulting to 8 and 16384. It counts in processors the worker count times the larger of one processor and half `RACH2_CPUS` (2 by default). The guest memory reservation is the smaller of the pool budget and the sum of the largest selected suites that can fit its worker count, increased to the largest suite when that suite exceeds the budget. Host overhead adds 1152 MiB per worker and 1024 MiB, with a minimum total of 5 GiB for preparation. It counts 40 GiB of disk for preparation and temporary images. These are conservative reservations, not measured costs; per-case scheduling replaces them.

A selection with a suite declaring more guest memory than half the host's physical memory, or `serial` in the registry's optional seventh field, uses `alone` admission, reserves the full site capacity and takes the compatibility host lock exclusively. A serial selection uses one worker, so its own suites cannot overlap either. Preparation reads the architecture before that optional isolation field. The `serial` flags of `style` and `host` inside one test pool order that pool only; two accounts may run `host` concurrently. An explicit `alone` launch also takes the host alone. An opaque command, a `legacy` command whose selection cannot be read or a `build` command through `sh`, `bash` or `dash`, such as `sh tools/etude/proof.sh`, claims what a selection that fills the guest pool claims, and at least what its build would claim; the builds and suites it starts run inside that claim. `alone /usr/bin/true` can drain old unwrapped tests during enrollment.

Every claim also reserves a legacy port block before setting `RACH2_PORT_OFFSET`. `ETUDE_ADMITTED` is an internal inherited marker for commands already inside a reservation; callers must not set it. Recursive builds reuse the test's claim and port block. Do not enclose an orchestration script that changes from building to testing in a `build` claim: invoke its build and test entry points separately, or use `alone` for an old script. A nested launch may not change the site. The bridge's registration, cancellation, output bound, result file and confirmed or uncertain cleanup apply unchanged; `-i` preserves command input. A nested `-r` records the command's exit within the enclosing claim; a status of 128 or more is conservatively incomplete, since a shell cannot distinguish an exit of that value from a signal.

Enrollment installs and validates the launcher, bridge and policy for every account and service before enabling shared scheduling. Subsequent old-checkout launches must use this installed launcher. Let already running unwrapped builds and tests finish; then run an installed `alone /usr/bin/true`, whose exclusive compatibility lock drains old unwrapped tests. Only after that command passes may shared scheduling start. Changing the capacity while a claim runs requires keeping enough capacity for it. An update of the launcher may coexist with earlier claims at unchanged site capacity; queued earlier claims retain their original resource amounts.

### The machine record

Deployment keeps, for each account of a machine, a record of what the machine can do and of the version deployed, in a state directory: `${XDG_STATE_HOME:-$HOME/.local/state}/etude` on Linux, macOS and Rach2, `%LOCALAPPDATA%\etude-state` on Windows, or the directory `-S` gives. The directory has the record, `machine`, and the ledger, `ledger/`, unless `-L` names another. The record is text, a field on each line, in this order:

    etude-machine 1
    host testing
    platform linux x86_64
    cpus 32
    memory_bytes 135070339072
    qemu QEMU emulator version 10.2.1 (Debian 1:10.2.1+ds-1ubuntu3.2)
    ovmf_x86_64 /usr/share/OVMF/OVMF_CODE_4M.fd
    accelerators kvm tcg
    admission etude-ledger 1
    ledger /home/testing/.local/state/etude/ledger
    version 1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0 /home/testing/.cache/etude/builds/1ca680ae57597b453d86eb671e431d2d4d8967214c0a8c1e6f629c3501073ce0.Ab3dEf

`host` is the machine's name as `uname -n` gives it, and `platform` the platform as the version cache names it. `cpus` and `memory_bytes` are the whole machine's processors and memory, `-` where the system does not give them. `qemu` is the first line of `qemu-system-x86_64 --version`, and `-` where there is no QEMU. `ovmf_x86_64` is the readable x86-64 OVMF code image, or `-` when none is found. Deployment uses [`ovmf_path.sh`](../setup/ovmf_path.sh) on the target, with QEMU's directory on PATH; on Windows it uses QEMU's `share/edk2-x86_64-code.fd`. A target's `RACH2_OVMF_CODE` overrides discovery. Windows records the path as `C:/...`. A scenario's site uses this path as `ovmf_x86_64`, or null for `-`.

`accelerators` are those this account can run a guest under: `kvm` when `/dev/kvm` is readable and writable and opens for reading and writing (the descriptor is then closed), `hvf` when macOS's `kern.hv_support` is 1, and `whpx` when the Windows Hypervisor Platform is enabled, each followed by `tcg`; `-` without QEMU; and `native` on Rach2, whose cases run on the machine itself. `admission` is the version's admission format, the first line of the ledger file its `ledger.c` writes. `ledger` is the ledger's directory, in the form `C:/...` on Windows, and `version` the key and the directory of the version deployed, as `version.sh` reports them.

Versions of one admission format share a ledger. A version refuses a ledger file of another format whole (The ledger), and deployment does not record a version whose format is not that of the ledger's file, so two versions of different formats never both admit claims on one machine.

### Artifacts

An artifact is a regular file that preparation makes and a case reads: a kernel, an image, a probe or a scenario. The store keeps each as an object named by the SHA-256 of its content, and preparation is a graph of nodes, each of which makes one artifact. The store copies a file in chunks of 1 MiB and leaves a chunk of zeros a hole, so that a sparse disk image keeps its holes as an object and in a private copy. A store is a directory:

| Path | Contents |
| --- | --- |
| `objects/DIGEST` | An object: a whole file, read-only, whose content has the digest DIGEST |
| `nodes/KEY` | The record of the object a node published under its key |
| `locks/KEY` | The file whose lock a process has while it prepares the key |
| `tmp/part.XXXXXX` | A partial object or record, locked by its writer until it is named or removed |

A record is five lines, in this order and no others:

    etude-artifact 1
    key 67bd12142ce4d2e924f0e6798243a1906a93be0c782240e7bce665b2f6af8da6
    object b674ffd22590339190299ad579244d53f6ead46c3cd73c37f63135be7ee96fdf
    size 1048576
    node rach2/kernel

A node has a name, the manifest's `node`; a recipe, a command, or none for a file of the tree, which is published as it is; its output, a path in the recipe's work directory; its inputs, other nodes of the graph; further `key` text, such as a commit or a recipe's version; and the bound of its prepare stage. In the recipe's arguments and environment, `${WORK}` is the node's work directory, where the recipe runs, and `${IN:NAME}` the read-only path of input NAME's object. The node's key is the SHA-256 of its name, recipe, output, key text and inputs with their digests, each field written with its length. A change of an input's content changes the key of every node that uses it, and a change that leaves a product's content as it was leaves its dependents' keys as they were. A fresh node is made again by every run and has no record, for a product that is the operation under test and not its setup.

A run gives each node a state: `reused`, when the store has a record of its key whose object reads back with the record's digest and size; `built`, when this run made and published it; `failed`, when its recipe or its publication failed; `blocked`, when an input failed or was blocked, and its recipe never ran; or `pending`, when the run refused the graph and ran nothing. A case reads its artifacts by digest, and a case that writes one, such as a durability case's disk, gets a private writable copy, checked by its digest as it is copied.

### The preparation record

The record of a preparation lists the files that `etude-legacy` built or found for the suites, so that a later step can tell whether they changed. It is text, one item a line, in this order, with a `suite` line for each suite and a `file` line for each file:

    etude-legacy 1
    tree /home/testing/rach2
    arch i686
    kernel build/rach2/kernel
    suite default run-default
    file 5891b5b522d5df086d0ff0b110fbd9d21bb4fc7163af34d08286a2e846f6be03 2716672 1838212 1760960000123456789 build/rach2/kernel

`tree` is the tree's root, `arch` the architecture, `kernel` the kernel the suites boot, and a `suite` line has a suite's name and the target of the Makefile whose prerequisites are its artifacts. A `file` line has a regular file's SHA-256, its size in bytes, its inode, its modification time in nanoseconds since the epoch, and its path from the tree's root. An artifact that is a directory, such as a staging tree, must exist and is not listed. The values of the example are illustrations.

### Proofs

A mutation proof shows that a test finds a fault: the test passes on the unmodified sources, fails as declared with the fault in them, and passes again once they are restored. Its catalogue is a document of [`proof.schema.json`](schemas/proof.schema.json), and catalogues are kept in `tests/proofs/`. It gives:

* `proof`, the name, and `summary`;
* `tree`: `private`, where the faults go into copies of the sources under the work directory, which the build reads in place of the tree's; or `shared`, where they go into the tree's own sources, for a build such as the kernel's that a private copy cannot reach;
* `sources`, the files, relative to the tree, that the faults change;
* `artifacts`, the files the build makes and the test runs or reads;
* `build` and `test`, each a command, `argv`, whose first word is a path, with its bound in seconds, `bound_s`; the test may give `fail_prefix`, how a line of its failure begins;
* `faults`, each with a `name`, a `summary`, its `edits` and `fails`. An edit names a source, the text `find`, which must occur once in what the fault's earlier edits left, and the `replace` that takes its place. `fails` gives the `lines` the test's output must contain, each within some line, the exit `status` when one is required (any but 0 otherwise), and `only`, which requires every line that begins with `fail_prefix` to contain one of `lines`.

In the commands and the artifacts' paths, `${TREE}` is the tree's root, `${SRC}` the root the sources are read from (the tree's for a shared proof, the private copy's otherwise), `${WORK}` the work directory's absolute path and `${PHASE}` the phase. Any other `${NAME}` whose NAME is capitals and underscores is refused as a misspelt placeholder; other text, a shell's `${CC:-cc}` among it, is passed on unchanged. A fault named twice, an edit of a file that is not a source, and `only` without `fail_prefix` are refused.

A proof runs in phases. Each builds, keeps its artifacts in the store under their digests and runs the test:

1. `base`, on the unmodified sources. The test passes: it exits 0 and prints no line that begins with `fail_prefix`.
2. `fault-NAME`, for each fault: its edits are made, and at least one artifact must differ from the base's, or the fault did not reach what the test runs. The test must fail as `fails` declares.
3. `restored-NAME`: the saved sources are written back and must read back whole, every artifact must equal the base's byte for byte, and the test must pass.

A 64-bit Mach-O artifact is compared by its digest with four parts zeroed: the path and the time of each object in its debug map (the `N_OSO` entries of its symbol table), its UUID and its code signature. With `-g`, Apple's linker writes each object's path and time into the debug map, and a one-step `cc -g` names its objects at random in `TMPDIR`; the UUID is a hash of the whole output, and the ad hoc signature hashes its pages, so these parts differ between two links of the same sources. Every other byte of the file must be the same. The store keeps the file as it is, so its digest in the phase's line differs from phase to phase. A Mach-O file whose load commands do not fit it is compared whole.

The build must exit 0 within its bound. A command must end with each process it started, and one that runs past its bound, is killed by a signal or writes more than 16 MiB to a stream fails the phase. Each command has a new, empty directory in the work directory as its `TMPDIR`, under one path for every build, so the scratch that a test keeps when it fails, as it must with a fault, is removed with the work after a pass and kept with it after a failure. After each phase the sources must be as the phase left them, so a build or a test that writes a source fails the proof. An artifact that differs from the base's after the restoration, such as one a stale build kept or one made from state the faulty run left behind, shows the restoration incomplete, and the proof fails.

## Design

### Building a version

`version.sh` makes a script of `bootstrap.sh`, the source and the call of `etude_main`, and gives it to a POSIX sh on the machine with `ssh -T -o BatchMode=yes HOST 'sh -s'`. The account's own shell runs that command, and `sh -s`, a word and a flag, reads the same in sh, bash, dash, zsh, ksh, fish and csh; for Windows, `C:\msys64\usr\bin\env.exe PATH=/usr/bin:/ucrt64/bin sh -s` reads the same in cmd.exe and in PowerShell, the shells its SSH server offers. Each file of the source is the body of a quoted here-document whose end line has a random nonce in it. The script defines functions alone until its last line, `etude_main < /dev/null`, so that a script cut short anywhere ends in a syntax error or before that line, and changes nothing on the machine.

`etude_main` chooses the compiler and flags of its platform: `cc` with `-std=c99 -O2`; `-std=c99 -static -D__rach2__` on Rach2, whose TinyCC links only static programs and defines no `__linux__`; MinGW-w64's `/ucrt64/bin/gcc` and programs named `.exe` on Windows. It computes the key, and when `versions/KEY` exists it checks the record's key and the programs' digests and reports the version reused. Otherwise it makes a build directory with `mktemp -d`, writes the source there, requires the list's digest to be the one `version.sh` computed, runs `make -f tools/etude/version.mk` in the source, writes the record and checks it, and publishes it with `ln`, which fails when `versions/KEY` exists. Of two builds of one key at once the first link wins, and the other removes its directory and reports the winner's version reused. An exit trap removes the directory of a build that failed, or that a signal other than SIGKILL stopped.

The result is the line `@etude-version NONCE built|reused KEY DIR` on the machine's standard output. `version.sh` takes only the line with its own nonce, and passes the rest, such as what the account's startup files print, to stderr.

### Deployment

`deploy.sh` makes three requests of the machine, each of which can be cut short and made again. The first checks the prerequisites. A POSIX machine gets `tools/setup/prereq.sh`, its recipe and the scripts that the recipe's probes and install lines read, as quoted here-documents, as `version.sh` sends the source, and runs them in a scratch tree under its `TMPDIR`, which the script removes on exit; a probe runs in its tree's root, and in a clone it could write there. For Windows, `prereq.sh --platform windows` runs on the controller and reaches the machine's PowerShell over ssh(1). The install lines run as `prereq.sh --install` runs them, an administrator's only where the account has the rights, and the rest are printed. A missing prerequisite leaves the deployment incomplete without stopping it, since the account's other steps need no administrator.

The second request is `version.sh`'s, and deployment stops when it fails. The third sends a script of `bootstrap.sh`'s functions and its own, which, like `version.sh`'s, defines functions until its last line. It makes the state directory where it is missing, and the ledger, an empty `lock` and a directory `verdicts`. Where the ledger exists, it requires the account to be able to write the directory, its `verdicts` and its `lock`, and read its `claims`, and prints the `chmod` commands that would let it; and it requires `claims`, where present, to begin with the version's admission format. Either refusal leaves the machine as it was. It then makes the record and writes it, to a temporary file renamed over `machine`, only when it differs from the one there, so a deployment that changes nothing writes nothing, and one cut short leaves the old record or the new one whole.

Deployment writes no file of the ledger that exists, so a running test keeps its claims and verdicts, and its version, whose directory a new version leaves alone. It runs no git or ssh-keygen, and passes `-o BatchMode=yes` to ssh(1), which then asks for nothing.

### The history store

[`history.h`](include/etude/history.h) provides the C99 history API. `etude_history_open` creates a stream with exclusive creation and mode 0600, without inheritance by executed children. One thread in one process owns that stream. Each other writer creates a file of its own, with a globally unique stream ID allocated before execution. A forked child cannot append through its parent's writer. The writer never reopens, replaces or truncates an existing file.

The caller supplies the trusted version-one [`history.schema.json`](schemas/history.schema.json), the run ID and a byte limit. The store reads the schema once and validates each record before writing it. Its JSON reader rejects duplicate members (including escaped spellings), non-ASCII text, fractional numbers and integers beyond 53 value bits. It implements the vocabulary and patterns used by this schema; it is not a general JSON Schema implementation. The store also checks elapsed-time subtraction, paired null preparation identities, and the absence of a completed run interval when cleanup is unconfirmed.

`etude_history_record_id` gives the next ID as `STREAM/SEQUENCE`, which the caller can use in references before writing the record. The writer accepts that ID alone and adds the version, stream, sequence, run, UTC and kind to the supplied data object. It compacts whitespace outside strings. It flushes and synchronizes the object bytes before writing and synchronizing the newline. A failed write ends that stream; a new stream continues the run. The failed stream remains evidence.

A record is at most 4 MiB and a stream at most 65,536 records, subject to its byte limit. A full stream returns an error before writing any part of the next record. A caller must bound the total of streams and referenced blobs through admission and retention. This store deletes nothing, including accepted baselines and issue evidence.

`etude_history_read` checks the schema, local arithmetic, run and stream identity, contiguous sequences and unique record IDs. It accepts the contract's opaque record IDs, including those written by other producers. SHA-256 and byte length identify an exact replay, which is delivered once; a repeated ID with other bytes is an error. It returns 1 for an unfinished last line and -1 for malformed complete lines or I/O errors, with the line number. Its callbacks may have received a valid prefix before that error; the prefix cannot establish success. The input is a closed stream or a stable snapshot. The consumer must resolve references across streams, check content hashes and inventories, and derive aggregate outcomes before deciding whether a run passed.

### The collectors

`etude_history_now` reads UTC and the monotonic clock independently, with the clock resolution rounded upward. POSIX uses `clock_gettime`; Windows uses the performance counter and precise system time. The caller records the machine, boot and clock IDs and subtracts readings only in that domain. Elapsed metrics keep a conservative rounding bound; a missing end, backward reading or overflow stays unavailable.

`etude_history_wait_usage` converts final POSIX child usage to processor microseconds. It includes descendants whose reaped usage the operating system charged to the child, and reports a lower bound with unbounded error because other descendants may be missing. `etude_history_job_usage` reads Windows Job Object cumulative user and kernel time, which includes terminated members. Its caller owns the job, forbids breakaway and records the process creation identities in the scope blob. Neither interface mistakes a process's peak resident size or a job's peak commit charge for combined resident memory; that measurement is unavailable.

`etude_history_cpu_sum` adds disjoint accounting scopes with checked arithmetic. Missing scopes stay unavailable and incomplete accounting stays a lower bound. The executor supplies each inclusive scope once: it never adds a guest to its QEMU, a tooling VM to its internal processes, or a parent's inclusive usage to its children. `etude_history_memory_sample` takes simultaneous resident sizes for disjoint scopes and keeps their largest combined sample. It records the longest sampling interval and an unbounded error, and a missing sample makes the result unavailable. Summing individual peaks cannot supply it. The run's peak needs samples of the whole run, apart from its cases' peaks.

### The comparison

[`compare.c`](compare.c) reads every stream with `etude_history_read`. An invalid stream is left out whole, and the incomplete last line of a stream is not read; the report notes both. A record that two streams give with the same bytes is read once, and an identity with two contents ends the command.

Each attempt record is a sample. Its key holds the values that a same-site comparison matches by the plan's measurement record under `dev-log/`: the case, the architecture, the domain, the machine and the accelerator, which name the sample's series; the digests of the workload, the assertion inventory and the profile; the operating system and its version; the digests of the site profile, the tools, the cache state, the declared load and the concurrency policy; and the method of the elapsed time. The commit and the hashes of the tested programs are not in the key, so that a series crosses commits. A sample is eligible when its plan lists it, its result is a pass that was not disrupted, it retries no attempt, its elapsed time has an error bound and is not a lower bound, and its run has a run record that lists it and was not disrupted. A run without its record has no account of its load, so its samples are left out.

The run's items are grouped by key, and the candidates of a group are the first attempts of its items, so that the repetitions of one case are compared together. [`baseline.c`](baseline.c) chooses the group's baseline. A comparison record with a verdict of `within_noise`, `regression` or `improved` accepts its baseline, whose identity names the policy and the sample list. The newest baseline accepted for the candidate's whole key is used again, however many slower samples follow it, so that a slowdown does not become the baseline by repetition. When there is none, or `-n` asks, a new baseline takes the eligible samples of the key from other runs that ended before the candidates started and after the newest sample of the series' last accepted baseline. Its identity is `median-mad-v1:` and 32 hex digits of a SHA-256 of its sample identities. The report lists each sample of the series in that window that was left out, with the reason.

The statistics are those of `median-mad-v1`. The median of an even count is the midpoint of the two central values; the arithmetic is in quarters of a microsecond, where the midpoints are exact, and only the stored median and deviation are rounded upward. The band is the largest of 3 * 1.4826 times the deviation, one percent of the median, and the largest clock resolution or error bound of the samples. The verdict is `not_comparable` when no candidate is eligible, or when no earlier sample has the candidate's key but one of another key in the series does, as after a change of workload; `insufficient_history` with fewer than five baseline samples; and otherwise `within_noise` when the medians differ by no more than the sum of the two bands, and `regression` or `improved` when they differ by more.

[`compare_report.c`](compare_report.c) writes the report: the verdict and its reason; the medians, deviations and bands of both sides; the commits the baseline tested, the newest of them and the candidate's, and the commits in between; each step of the candidate compared with the same step of the baseline's attempts, so that a slower boot shows apart from a slower execution; the processor time of the tree and the time queued on both sides, apart from the elapsed time; each sample with its commit, end and time, and each one left out with its reason; the candidate's source, runner and artifacts by digest; and the commands of the plan's reproduce blob, which run the item again and under a profiler. [`compare_run.c`](compare_run.c) runs the command and builds the comparison records, which the history store validates before it writes them.

A blob of the store is named by the SHA-256 of its bytes. `cmp_store` of [`compare_report.c`](compare_report.c), which the repetition driver uses too, writes the bytes to a partial file of its own process, synchronizes it and renames it to that name, so that a write cut short, as on a full disk, leaves nothing under the name, and a file found there with other bytes is replaced.

### The POSIX executor

[`posix/`](posix/) runs host processes for the controller, as [`exec.h`](include/etude/exec.h) declares, on Linux, macOS and Rach2. [`capture.c`](capture.c), which the Windows executor shares, keeps each output stream up to the attempt's bound, counts the rest, and finds the `child` records on standard output, beyond the bound as well.

Each attempt has a keeper, a process the controller forks in a session of its own ([`keeper.c`](posix/keeper.c)). The keeper closes every descriptor it does not need and forks the case's process, which makes a session and a process group of its own, puts its standard input and the write ends of two output pipes on descriptors 0 to 2, sets every signal to its default, clears its signal mask, closes the unused ends of the go and exec-status pipes, and then waits on the go pipe. If the keeper dies before the go, the child reads EOF and exits without executing the program. The keeper reports the process's PID and start to the controller, whose registration function sees it before it runs anything; only then does the keeper write the go. A refusal kills the process unrun. A pipe closed on exec tells the keeper whether the exec succeeded, and an exec that failed makes `etude_exec_start` fail with its error after the keeper has reaped the process.

The controller ([`exec.c`](posix/exec.c)) talks with each keeper over two pipes in fixed messages of 32 bytes, each written whole, and polls the keepers' pipes and the cases' output pipes of every attempt at once. It gives the attempt's `child` function each running descendant that a `child` record names before it gives the descendant to the keeper; a refusal makes the cleanup unconfirmed. A process is named by its PID and its start, read from `/proc/PID/stat` on Linux and Rach2 and from `sysctl` on macOS, so that a reused PID is told apart.

When the case's process ends, the keeper reaps it and reports its end. The controller reads the output written before it, gives the keeper the descendants that `child` records name, and asks for the cleanup. The keeper sends SIGTERM and SIGCONT to the case's process group, to each reported descendant still the same process, and on Linux to each of its own children and their groups; it sends SIGKILL to what is left after the grace period, and again to what comes to it later. It reports the cleanup confirmed only when it finds nothing left, within the grace period after SIGTERM or within a second one after SIGKILL. A cancellation sends the same signals at once and SIGKILL after the grace period, so that a stopped process is resumed and can end gracefully; its end is `stopped`. When the controller's pipe ends, the keeper cancels the case, cleans up by itself, and records the cleanup in the attempt's `verdict` file, as The ledger says.

`etude_exec_suspend` has the keeper send SIGSTOP to the case's process group, and `etude_exec_resume` SIGCONT. The keeper reaps with `WUNTRACED` and `WCONTINUED`, and reports the stop once waitpid(2) has seen the case's process stopped, and the continuation once it has seen it continue; a SIGCONT before any stop was seen is reported at once. Neither status is taken for an end. Since not every system sends SIGCHLD when a child continues, the keeper looks every 10 milliseconds while it waits for either. The result's `suspension` follows the state, `suspensions` counts the stops seen, and `suspended_us` and `resumed_us` give the last stop and continuation seen. A suspension of an attempt that has ended, is cancelled or is already suspended is refused, and a resumption of an attempt that is not suspended does nothing.

On Linux and Rach2 the keeper is a subreaper (`PR_SET_CHILD_SUBREAPER`): every orphan below it, one that escaped into a session of its own included, becomes its child, which it can find in `/proc/self/task/PID/children`, end and reap. Where it is not, it can end only the process group and the reported descendants; an unreported process in another session that keeps the case's output open shows itself, since the output must close within the grace period after the keeper has ended, or the cleanup is unconfirmed. The `posix_only` field of an attempt makes the keeper use POSIX interfaces alone, so that Linux can test that path.

Rach2 has the Linux interfaces the executor uses: `/proc/PID/stat`, `/proc/PID/task/TID/children` and the subreaper of prctl(2). Its TinyCC defines no `__linux__`, so [`process.c`](posix/process.c) takes them on Rach2 when `__rach2__` is defined, as the version's recipe there defines it; a build for Rach2 without it can read no process's start.

The processor time of the tree is the keeper's `RUSAGE_CHILDREN` after the cleanup, which counts each process that its parent or the keeper reaped. It is exact, as `posix-subreaper-rusage-v1`, when the keeper is a subreaper and confirmed the cleanup, and a lower bound, as `posix-rusage-children-v1`, otherwise, since an orphan reaped elsewhere is not counted. `etude_proc_sample` samples a running case: on Linux and Rach2, the processor time of its process and of the children it has reaped, and its resident size, from `/proc/PID/stat`; on macOS it gives no sample. The peak memory, `posix-maxrss-v1`, is the largest resident size of any one process of the tree, a lower bound of the combined peak. Rach2 samples a process's resident size only when its address space ends, at its exit or exec, so there the value is the largest size any one address space of the tree had when it ended. A keeper killed before it reports leaves the end `lost`, the cleanup unconfirmed and both measurements unavailable.

### The host checks

[`posix/etude_host.c`](posix/etude_host.c) runs each step of a check as an attempt of the POSIX executor: `/bin/sh -c 'exec >"$1" 2>&1; eval "$2"'` with the step's log and command, so that what the command and its descendants write reaches the log in the order written. The step therefore starts in a session of its own, with standard input from `/dev/null`, an empty signal mask and every signal at its default, and the executor ends what it leaves behind. A check passes when its run exits 0 and the executor confirms that its processes have ended. A compile that fails, a run that exits otherwise or is killed, a step past its bound, and a step that leaves a process the executor cannot end each fail it. A compile's bound is 600 seconds and a run's the check's SECONDS; a step past it is cancelled, which sends SIGTERM and SIGKILL two seconds later, and reported as hung.

A check's environment is etude-host's, with `TMPDIR` set to its scratch directory and the sanitizers' settings replaced: `ASAN_OPTIONS=halt_on_error=1:exitcode=1`, `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1:exitcode=1`, and no `LSAN_OPTIONS`. An inherited `exitcode=0`, `abort_on_error=0` or `detect_leaks=0` therefore cannot make a sanitizer's report pass, and LeakSanitizer keeps its default, on where the platform has it.

The checks start in the order of their bounds, the longest first, and the `alone` checks after the others, each when nothing else runs; nothing starts beside one. A passing check's scratch directory is removed, and a failing one's is kept and named when it is not empty. Under a failure the program prints the lines of the sanitizers' reports in the log, marked `!`, and the log's last 20 lines, marked `|`, so that a failure reads without the log; under a pass it repeats each `NAME: not run: WHAT: WHY` line of the log.

### Windows execution

On Windows a host program runs through [`win/winexec.h`](win/winexec.h), which is built with MinGW-w64 against the UCRT and needs no MSYS2 or Cygwin runtime. [`win/pecheck.c`](win/pecheck.c) reads a program's import and delay-load tables and refuses such a runtime and any library that is not Windows's own.

* `etude_win_start` creates the child suspended, puts it in a Job Object of its own, and calls the executor's registration function before the child's first instruction. A registration that fails ends the child with `ETUDE_WIN_REFUSED_STATUS`, and it never runs. A process is named by its ID and its creation time, so that a reused ID is told apart.
* The job kills every process in it when its last handle closes, so the tree ends with the executor; no process can break away from it; and an unhandled exception ends a process without the dialog of Windows Error Reporting.
* The child inherits its standard input, the NUL device or a file, and two pipes for its output and its errors, and no other handle. The pipes are named for the process and for the count of children it has started, so that two supervisors of one process do not take one name. It has a console of its own with no window, whose host process, `conhost.exe`, is in the job.
* `etude_win_poll` reads the output and learns of each end through one completion port. A child has ended when its first process has exited, its job is empty and both pipes are at their end, so output that a descendant writes after its parent exits is kept.
* `etude_win_usage` reads the job's accounting: the processor time of every process, ended ones included, at the resolution of the clock interrupt; the peak of committed memory of the job and of any one process, which is not the working set; and the bytes read and written.
* `etude_win_stop` ends every process of the job at once with `ETUDE_WIN_STOP_STATUS`. Windows has no signal that asks a process without a window to stop, so a stop has no grace period.
* Paths are UTF-8, made into `\\?\` paths of any length; a command line is quoted for the UCRT's parsing rules; an environment given whole replaces the executor's, and must then have `SystemRoot`, which Winsock reads; the monotonic clock is the performance counter; and a listening socket is on 127.0.0.1, where no child inherits it.

[`win/exec.c`](win/exec.c) implements [`exec.h`](include/etude/exec.h) on the adapter, so that the controller has one interface on every host. The job takes the part of the POSIX keeper, and the controller's own process is the keeper that a registration sees. When the case's first process ends, the executor stops its job, as the keeper ends the descendants of a case, and the attempt finishes when the job is empty and both streams have closed; the cleanup is then confirmed, since no process can leave the job. A `child` record counts as a child, and goes to the attempt's `child` function, when it names a process of the job, and counts as foreign otherwise. A cancellation stops the job at once, with no grace period, and its end is `stopped`; `grace_us`, `posix_only` and `verdict` have no effect. The processor time, `win32-job-accounting-v1`, is the job's and exact. The peak memory is unavailable, since a job reports its peak commit and not its resident memory. `etude_proc_sample` samples a running case: the processor time of every process its job has held, and the working set of its first process. A registration that fails makes `etude_exec_start` fail with its error after the case has ended unrun.

### The ledger

[`ledger.h`](include/etude/ledger.h) keeps the claims of one machine's resources in a directory, so that a worker that dies cannot take its claims with it, and no worker can take what a claim's processes still use. A claim has the attempt's identity, the resources it reserves as named amounts, such as `cpu_millis` and `memory_bytes`, its owner, which is the worker's process, and the processes it runs.

A worker records a claim with `etude_ledger_reserve` before it starts anything; given the machine's limits, the reservation is refused when it would take a resource past its limit, counting every claim the ledger keeps. The worker gives the executor `etude_ledger_register` and `etude_ledger_child` as the attempt's `reg` and `child`, the ledger as `reg_ctx`, and the claim's `etude_ledger_verdict_path` as `verdict`. The executor calls the registration after it has made the case's process and before it lets the process execute its program, and the registration returns only once the identities of the keeper and the process are in the ledger file; a reported descendant is added when the executor reads its `child` record. When the attempt has finished, `etude_ledger_finish` releases the claim if the cleanup is confirmed, and keeps it as `uncertain` if it is not.

The directory has `claims`, `lock` and `verdicts/`. Every change takes an exclusive lock of `lock`, by `fcntl` on POSIX systems and `LockFileEx` on Windows, which the system gives back when the holder dies; reads `claims`; and writes the whole file again as `claims.new`, synced and renamed over `claims`, so that a reader finds the file as it was before a change or after it, never part of one. The file is text, a field on each line:

    etude-ledger 1
    claim ATTEMPT
    system linux
    boot 6f1c2d0e-8b4a-4f8e-9b1d-2a7c5e3f9d10
    owner PID START KNOWN
    account testing
    state running
    resource cpu_millis 1000
    process keeper PID START KNOWN
    process case PID START KNOWN
    process child PID START KNOWN
    end

A process is its PID, its start and whether the start is known, as `struct etude_pid` gives them. `account` is the account the claim was admitted for, and absent from a claim that `etude_ledger_reserve` made. `state` is `reserved` before a process is registered, `running` after, and `uncertain` once the owner has found the cleanup unconfirmed. A request that waits for admission, as the next section says, has the same form with the state `waiting`, or `blocked` for the one request that is protected, a line `ticket N`, its place in the order of arrival, and no process; it holds no resource. A file with two blocked requests is refused whole. `boot` is Linux's `boot_id` or macOS's boot session UUID, and `-` where the system gives none, as on Windows. A file that does not parse is refused whole, and nothing in it is released.

Recovery runs at each reservation and listing, and releases a claim only when it is proved free:

* A claim recorded in an earlier boot is free, since no process of that boot runs.
* Otherwise its owner must have ended. A process with the owner's PID and another start has reused the PID, so the owner has ended; a PID that runs with a start that cannot be read leaves the claim uncertain.
* A claim that registered no process is free.
* Otherwise each of its processes must have ended, the case's process group must have no member, its state must not be `uncertain`, and on POSIX systems its keeper must have written `confirmed` in the claim's verdict file.

A request is removed once its owner has ended, as a claim with no process is. A claim of another operating system is kept and not judged. `etude_ledger_list` gives each claim kept as owned, live, when a process of it runs, which it names, or uncertain, with the reason; `etude_ledger_drop` releases a claim that is not owned once a person has established that nothing of it runs. A person does both with `etude-ledger` (Use).

The verdict covers what the ledger cannot see. A keeper whose controller has gone cancels the case and ends what it knows of; then it reads the case's output pipes, whose read ends it holds, and confirms the cleanup only if both close within the grace period, since a process that holds them open is the case's. It writes `confirmed` or `unconfirmed` in the verdict file and exits. A descendant that escaped unreported and holds the output therefore leaves the claim uncertain, and so does a keeper killed before it wrote. A keeper whose controller lives writes no verdict, and the controller's own report decides. On Windows the job ends every process of a case when the controller's last handle closes, and no process can leave it, so a claim there needs no verdict: it is free once its owner and its registered processes have ended.

### Admission

`etude_ledger_admit` admits a claim for an account within the machine's limits, which the caller gives as named amounts, under the same lock as every other change of the ledger, so two workers can never both take the last of a resource. A request refused for now can wait in the ledger, and its worker asks again with the same identity when a claim may have ended; the ledger gives no notice.

One waiting request of the machine is protected. A claim is admitted only when it fits beside every claim the ledger keeps and, of each resource it takes, leaves free what the protected request needs. The claims that run therefore end without being replaced by claims on what the protected request waits for, and it is admitted once enough of them have ended. A claim of a resource the protected request does not lack, such as processors alone beside a request blocked on memory, is admitted. Nothing is admitted on a forecast that it will end before the protected request could start, so there is no backfilling by time, and the schedule is not in general an optimal one.

The protected request is chosen when there is none: of the requests that could ever fit, the one whose account holds the fewest claims, and of those the one that has waited longest. It stays protected until it is admitted or withdrawn, so an account that later holds fewer claims cannot pass it. A request could never fit when it exceeds the limits alone (`ERANGE`), or cannot fit beside the claims whose worker and processes have ended with the cleanup unconfirmed, which only a person can drop (`ENOSPC`); it is refused, a protected one loses its protection, and the rest of the run goes on. A claim whose processes cannot be identified, as on a system that gives no start time, may still end, and its request waits. `etude_ledger_reserve` admits by the same rule without an account or a wait.

[`sched.h`](include/etude/sched.h) is a worker's side. `etude_sched_order` sorts its jobs, the cases of both architectures together, by the place of their last preparation in the order of preparation, then the costlier first, so that a long job does not start last, then by case and architecture. `etude_sched_admit` asks for each job whose preparation has finished, in that order. The worker keeps one request waiting: the job already waiting, or else the first refused; the others are asked without waiting, and each is admitted where it fits beside the protected request. A job the machine can never hold is marked refused and the others go on. `etude_sched_withdraw` withdraws the request of a worker that stops.

A job's cost is its expected elapsed time. [`cost.c`](cost.c) takes it from the samples that the comparison finds eligible, passes that were not disrupted and retry nothing, whose key matches the planned item's in every field but the load, the concurrency policy and the method of the elapsed time: the same case, workload, inventory and profile, on the same machine, system, accelerator, site profile, tools and cache state. It is the median of their elapsed times, or the case's declared initial bound with none. Its processor reservation, by the policy `cpu-median-v1` of `etude_sched_cpu`, is the median of each sample's processor time divided by its elapsed time, rounded upward, with 25 percent more, at least one thousandth of a processor and at most the case's `cpu_ceiling_millis`; with no sample it is the declared `cpu_millis`. A processor time that is a lower bound, as the POSIX executor's is, is taken as its value. Memory and disk reservations are the declared amounts.

### Budget checks

[`budget.c`](budget.c) forecasts the time of a selection and judges the budget of a run, and `history_budget`, in [`budget_run.c`](budget_run.c), prints what they find. Neither ever takes an unknown cost as zero: a cost or a time that was not recorded or observed makes the verdict `unknown`, unless a failure is found beside it.

A forecast selects every case of its manifests: an item for each of a case's architectures, or one for `none`, and for each repetition of its workload. A host case is placed on the host, and another in QEMU, or, on a site whose accelerator is `native`, on the machine itself when its native plan is `native`; a case the site can run neither way is unknown. [`digest.c`](digest.c) gives the item's workload, inventory and profile digests, and the item costs what `cost.c` gives for the newest eligible sample of the same case, architecture, placement, digests, machine, system and accelerator, so that the site profile, tools and cache state are the newest recorded. A preparation node costs the median elapsed time of the steps that prepared its target, passed undisrupted with a measured time, and were listed in the preparation of an undisrupted pass of a run of the class on the site, or, for a release, of a first run, which prepares from clean as a release does; of those, only the steps that share the newest one's system version, site profile, tools and cache state. An item or node with no such sample is reported unknown and adds nothing to the time. The nodes are charged one after another before any case, and the items then run as `etude_budget_schedule` runs them on the policy's capacity: in the order of `etude_sched_order`, each admitted when it fits beside the items running and leaves free, of each resource it takes, what the first item refused needs, as the ledger protects a waiting request. An item larger than the capacity is a failure. The forecast fails when the recorded costs alone pass the deadline, since an unknown cost can only add to them, is unknown when a cost is missing, and passes otherwise. A note says how much of the growth the time uses, or that it passes the goal and the growth together.

A judgement reads every stream given, as the comparison does, and finds the run's one run record and its plan, whose `purpose` gives the class. A stream left out as invalid, or a last line cut short, may hide a record, and leaves the verdict unknown. Then:

* A budget that does not name the policy by its digest and size, or records other limits than the policy's for the class, fails.
* A plan whose environment is not the policy's site is unknown, since the policy says nothing of the time elsewhere.
* A first run's exemption holds when it names the plan's selection as its manifest, lists the run, and lists every attempt of the plan's items; one that does not hold fails, and gives no leave to pass a limit.
* An item of the plan that the run's summary leaves out, that is incomplete or cancelled, or that has no attempt is unknown. An attempt that is not in the history is unknown; one of another run, or of another plan or item, fails.
* A preparation step that the run lists and another run recorded, or that is a step of an item, fails, and so does a shared step of the run that it does not list. With the manifests of the run's cases, a node that a planned case prepares and no listed step of the run prepared fails.
* The charge is computed as The budget defines it. Unconfirmed cleanup, a run whose end was not observed, an elapsed time that is only a lower bound or has no error bound, an attempt or shared step timed on another clock than the run's, and one with no observed end each leave it unknown. A note names each record that extends the interval, and each one-time setup step that is charged, with the reason.

The verdict is a failure for any of the failures above, whatever the exemption; `exempt` for a first run whose exemption holds; a failure when the charge passes the ceiling; unknown when anything above was unknown or the charge is within the ceiling by less than the error bound of the run's elapsed time; and a pass otherwise. Last, the budget the run records is compared with the judgement: the verdict, and, when the charge is known, the charge and the one-time setup. A difference is a `record` line, and `history_budget` exits 1.

### etude-guest

`etude-guest` is one process with one loop: it waits in `poll` for its input, a self-pipe its signal handlers write, and the next deadline among the resend interval, the attempts' deadlines and their grace periods, and handles what is ready. Children are reaped with `wait4`, which gives their usage: the processor time of the child and the descendants it reaped, `wait-reaped-descendants-v1`, and the largest resident size of any one of them, `posix-maxrss-v1`, each a lower bound, since a descendant that the child did not reap is not counted.

On Rach2, the first helper of a boot publishes 32 random bytes as hexadecimal in `/dev/shm/etude-guest-boot`, and later helpers read the same file. It reads `/dev/urandom`, falling back to `getrandom` with `GRND_INSECURE` when that read fails or is short. The token distinguishes boots and needs no secure randomness, so the helper also starts on a processor without hardware entropy. The file is published whole with `link`, must belong to the helper's user and must not be writable by other users.

Its state directory has three parts. `f/SHA` is a stored file, named by its digest, written to a temporary name, synchronized and renamed, so that a file of the store is always whole. `s/SESSION/CMD` is a command's record: its first line is the command's type and fields, and each later line an event it caused, appended and synchronized before the event is sent. `s/SESSION/lock` is the session's lock, which `etude-guest --stdio` takes with flock(2) before its `ready` and holds until it exits, and `s/SESSION/owner` the PID and START of the process that holds it, START being the time the process started, which tells it from a later process given the same PID. `a/TOKEN/` is an attempt's: `record` with the child's PID and START and its end, `work/` the workspace, and `out.1` and `out.2` its output. The state directory, `a` and each attempt's directory have mode 0711 and the workspace 0755, so that a case's mapped ids and accounts can reach the workspace by its path, though no other user can list the attempts; `f` and `s` have mode 0700. A record outlives the `etude-guest` that wrote it, which is how a repeated command, a later connection's `status` and an orphaned attempt are answered.

The child is made in two steps. After `fork` it makes its own session and process group and waits on a pipe; `etude-guest` writes the record with its PID and START, and only then lets it go on, so that no process of an attempt runs unrecorded. The child takes `/dev/null` or the invocation's standard input, pipes for its output, the workspace as its directory, mask 022 and the default signal actions, closes every other descriptor, and executes the program; an exec that fails is reported through a pipe closed on exec, as `error CMD failed`.

On the serial console `etude-guest` keeps every sequenced frame it sent until it is acknowledged, at most 32 frames and 1 MiB, and reads no more output while the queue is full. Its diagnostics go to `guest.log` in the state directory and never to the console, where they would mix with the frames.

### The QEMU launcher

[`qemu.h`](include/etude/qemu.h) boots a guest or machine case's QEMU profile on the site's accelerator. [`qemu_profile.c`](qemu_profile.c) makes the command line, and [`posix/qemu.c`](posix/qemu.c) runs the machine on Linux and macOS.

The machine is QEMU's default PC, or its q35 when the profile's `machine` is `q35`, whose own AHCI controller is function 2 of device 31 on the first bus, 0:31.2, as on the Intel chipsets of real machines. Direct and SeaBIOS boots use `qemu-system-i386` for an i686 kernel and `qemu-system-x86_64` for an x86-64 kernel, as the site names them. OVMF boots use the site's `qemu_x86_64` and `ovmf_x86_64` for either kernel, as the uefi suite does; the processor profile must run x86-64 firmware. The site's `ovmf_i686` field is reserved and unused. `-nodefaults` leaves it the board's own devices and those of the profile, and `-display none`, `-no-reboot` and `-S` give it no window, make a reset end QEMU, and keep its processors stopped until the launcher starts them. The profile becomes these arguments:

| Profile | QEMU's arguments |
| --- | --- |
| The site's accelerator | `-accel NAME`, one alone, so that QEMU tries no other |
| `cpu` | `-cpu` with the processor profile's value |
| `processors`, `memory_bytes` | `-smp`, and `-m` in bytes, a whole number of mebibytes |
| `firmware` `direct` | `-kernel`, `-initrd` when there is one, and `-append` with the boot options separated by spaces |
| `firmware` `seabios` | nothing: the BIOS boots the first disk, or the one whose `boot` is true; no RAM image or boot options |
| `firmware` `ovmf` | `-drive if=pflash,format=raw,readonly=on,file=PATH` with the code image of the site's x86-64 UEFI firmware, the first flash device, read-only, its variables kept in memory; no RAM image or boot options |
| A disk of `disks` on IDE | `-drive file=PATH,format=FORMAT,if=ide,index=N,media=disk` |
| A disk on IDE with a `serial` | `-drive file=PATH,format=FORMAT,if=none,id=etude-diskM` and `-device ide-hd,drive=etude-diskM,bus=ide.C,unit=U,serial=SERIAL`, and `,bootindex=0` after it when the disk boots first |
| A CD, `media` `cdrom` | `-drive file=PATH,format=raw,if=ide,index=N,media=cdrom,readonly=on` |
| A disk on NVMe, `bus` `nvme` | `-drive file=PATH,format=FORMAT,if=none,id=etude-diskN` and `-device nvme,drive=etude-diskN,serial=SERIAL` |
| A disk on AHCI, `bus` `ahci` | `-drive file=PATH,format=FORMAT,if=none,id=etude-diskN` and `-device ide-hd,drive=etude-diskN,bus=etude-ahci.P`, after one `-device ich9-ahci,id=etude-ahci` before all the disks |
| A disk on a device, `bus` `device` | `-drive file=PATH,format=FORMAT,if=none,id=ID` |
| `boot` true | `,bootindex=0` at the end of the disk's `-device`; a disk or CD on IDE that boots first is `-drive file=PATH,format=FORMAT,if=none,id=etude-diskM`, with `,media=cdrom,readonly=on` for a CD, and `-device ide-hd` or `-device ide-cd` with `,drive=etude-diskM,bus=ide.C,unit=U` |
| An overlay, `base` | FORMAT `qcow2`; it is `raw` for any other disk |
| `discard` true | `,discard=unmap,detect-zeroes=unmap` at the end of the disk's `-drive` |
| `machine` `q35` | `-machine q35` |
| `i8042` false | `-machine i8042=off` |
| A device `rtl8139` or `e1000` | `-netdev user,id=netN` and `-device MODEL,netdev=netN`, then the device's members as for any other device |
| A card's `net`, `host`, `dhcpstart`, `dns` | the supplied options appended to that card's `-netdev` |
| A card's `mac` | `,mac=ADDRESS` appended to that card's `-device` |
| A card's `restrict` true | `,restrict=on` appended to that card's `-netdev` after its options |
| A card's `forwards` | `,hostfwd=PROTOCOL:127.0.0.1:PORT-:GUEST_PORT` for each, appended to that card's `-netdev` after its restriction |
| A card's `guest_forwards` | `,guestfwd=tcp:ADDRESS:GUEST_PORT-cmd:'WORD' ... PORT` for each, appended to that card's `-netdev` after its forwards |
| `netN` of `captures` | `-object filter-dump,id=netN-dump,netdev=netN,file=PATH` after that card's `-device`, PATH being the file the caller gives |
| A device `vga`, with no other member | `-vga std` |
| Optional `audio` `hda` | `intel-hda` and `hda-duplex` on the `wav` backend |
| Optional `audio` `sb16` | `sb16` on the `wav` backend |
| Any other device | `-device MODEL`, then `,id=`, `,bus=`, `,port=` and `,drive=` with the members given, and `,NAME=VALUE` for each property |
| `smbios_vendor` | `-smbios type=0,vendor=TEXT`, the commas of TEXT doubled; printable ASCII of 1 to 64 bytes |

N of a disk or a CD on IDE counts the profile's disks on IDE before it, so that they take the four places of the PC's two IDE channels in the profile's order, C being N divided by 2 and U its remainder, or on the q35 machine the first four ports of its own AHCI controller, whose buses `ide.0` to `ide.5` have one unit each, C being N and U 0, and a disk on IDE with a serial or that boots first has the identity `etude-diskM`, M being its place among all the profile's disks; P of a disk on AHCI counts the profile's disks on AHCI before it, so that they take the controller's ports from 0 in the profile's order; and N of any other disk is its place among all the profile's disks, counted from 0. Each comma of a path is doubled, as QEMU's option syntax requires. Every disk but a CD is a file of the attempt: a private copy, as the `disk` fixture gives it, an empty disk or an overlay. The launcher refuses a device that names a bus no earlier device has, or a drive that is no disk of the profile on a device or that another device attaches, a disk on a device that no device attaches, and a property that is one of the members above or has a comma or an `=` in it, which QEMU would read as another option.

A network card is a device of the model `rtl8139` or `e1000`, such as `{"model": "e1000", "net": "192.168.90.0/24", "host": "192.168.90.2", "dhcpstart": "192.168.90.20", "dns": "192.168.90.3", "mac": "52:54:00:12:34:58"}`. Each card has a user network of its own; `netN` counts cards from zero in device order. The five options are independent and optional. Omitted options keep QEMU's defaults. `casecheck manifest` and the launcher require `net` to be a dotted decimal IPv4 network address with a decimal prefix from 0 through 32 and no host bits set. `host`, `dhcpstart` and `dns` are dotted decimal IPv4 addresses within that network, excluding its network and broadcast addresses; without `net` they are checked against 10.0.2.0/24. Leading zeroes in octets and prefixes are refused. `mac` has six hexadecimal octets separated by colons and is a nonzero unicast address. Two cards in one machine cannot have the same explicit or default station address; hexadecimal letter case makes no difference. The check follows [QEMU's allocation of default addresses](https://github.com/qemu/qemu/blob/master/net/net.c), in device order, starting at `52:54:00:12:34:56` and skipping addresses already used. Network options are valid only on a network card.

A capture records every frame the card sends or receives, in pcap format. QEMU creates or truncates its file before the machine starts and writes each frame as it passes, so the file is whole once the machine has ended. The launcher refuses a capture of a card the profile does not have, a card captured twice and a capture without a file.

A card's `forwards` forward the case's local ports to the guest, each as `{"protocol": "tcp", "port": 0, "guest_port": 22}`, where `port` is an index of the profile's `ports`. QEMU listens at PORT, the port of that index, on the loopback address alone, and joins each connection or datagram to GUEST_PORT at the first address that DHCP gives on the card's network: `dhcpstart`, or QEMU's default, 10.0.2.15 on the default network. A card whose `restrict` is true adds `restrict=on` before its forwards: its guest reaches only its guest forwards, and the forwards to the guest still reach it. A card's `guest_forwards`, each as `{"address": "10.0.2.100", "guest_port": 443, "port": 1, "relay": ["fakeapi", "relay"]}`, add `guestfwd=tcp:ADDRESS:GUEST_PORT-cmd:'WORD' ... PORT`, where PORT is the profile's port of the index: QEMU parses the command as a shell would, so each word of the relay is in single quotes, with a quote in it written `'\''`, and a comma doubled, as QEMU's option syntax needs. One card may have its network options, its station address, the restriction, forwards and guest forwards together, in its one `-netdev` and its `-device`. The launcher refuses with `EINVAL` a forward, a restriction or a guest forward on a device that is no network card, a forward of an index past the profile's `ports` or of a port below 1024, a guest port outside 1 to 65535, a local port that two forwards of one protocol name, which QEMU could not listen on twice, and a guest forward from an address of its card's network that QEMU cannot forward, as `etude_qemu_guest_address` says, from one address and guest port that another guest forward of the card has, to a port that the profile does not hold or that a TCP forward makes QEMU listen on, or through a relay without a program or with a byte outside printable ASCII. `libetude-case` gives the launcher the ports of the scenario invocation, and each relay's program as the path of the tool or of the artifact's executable copy, so that a boot whose forward names a port the case does not hold ends before QEMU starts, as `ETUDE_FAILED` with the end `qemu_exited`. A profile gives no forward from the host to another guest address. QEMU starts a relay for each connection and does not end it, so a relay must end when its connection ends.

The machine's serial console and its QMP monitor are Unix sockets in a private directory under `TMPDIR`, or under `/tmp` when their paths would not fit a socket's address there, which the launcher listens on before it starts QEMU, and to which QEMU connects as a client when it makes its character devices, before it starts the accelerator. QEMU fails at once if it cannot connect, nothing it writes is lost before the launcher reads it, and the launcher removes each socket once QEMU has connected. QEMU is an attempt of the launcher's own executor, registered before its exec and cleaned up with its descendants. `etude_exec_watch` waits for the executor's descriptors and the sockets together, so that a QEMU that ends before it connects is seen at once.

The optional `audio` field selects one recorded card, `hda` or `sb16`; without it the launcher adds no audio backend. The manifest gives no output path. The launcher reserves a new file and passes `-audiodev wav,id=etude-audio,path=PATH`, quoting commas in the path, and attaches the selected card to that backend. HDA includes its controller and its codec on the controller's own bus. A caller of `etude_qemu_start` may give a new `audio_path` for evidence; otherwise the launcher makes a temporary WAV in the machine's private directory. The result's `audio_path` remains valid until the machine is freed. Freeing removes a temporary recording and leaves a caller-given file. An existing file is never replaced.

On QMP the launcher answers QEMU's greeting with `qmp_capabilities` and asks `query-accelerators` which accelerator QEMU uses; a QEMU that lacks the command is asked `query-kvm`, which tells only whether KVM is in use. When QMP names the accelerator asked for, `cont` starts the machine and its state becomes running. Every byte of the console is kept in memory up to the case's bound, counted past it, and written to the attempt's console file when it has one.

The end of a machine is told by these rules, in order:

| End | Observed |
| --- | --- |
| `accel_failed` | QMP named another accelerator, and the launcher made QEMU quit; or QEMU ended before the machine ran with a line of its standard error that its location of the option begins, `PROGRAM: -accel NAME: `, as QEMU writes when it cannot start an accelerator or does not have it |
| `stopped` | The caller cancelled the machine before its end |
| `shutdown`, `reset`, `panic` | QMP's event `SHUTDOWN` of the guest, with the reason `guest-shutdown`, `guest-reset` or `guest-panic` |
| `qemu_exited` | QEMU ended otherwise: a `SHUTDOWN` of the host, such as a signal, or an exit without an event, whose status the executor keeps |
| `lost` | QMP answered what the launcher cannot use, or QEMU's keeper ended before it reported QEMU's end |

The console is read again when the event arrives, so the offset of the end counts every byte QEMU wrote before it. A cancellation sends QMP's `quit` when QMP is past its capabilities, and the executor's cancellation, SIGTERM and then SIGKILL, when QEMU has not ended within the grace period, or at once without QMP. `etude_machine_suspend` and `etude_machine_resume` stop and resume a running QEMU through the executor, as The POSIX executor says, and a cancellation resumes a suspended QEMU before its `quit`, so that QEMU is never asked to answer QMP while a signal holds it stopped.

Once the machine runs, the caller may send QMP commands of its own with `etude_machine_qmp` and read each reply by its id, from 100 up; the launcher's own ids are below 100. A QMP line is kept up to 1 MiB, so that the registers of 64 processors fit.

### The serial controller

[`serial.c`](serial.c) is the controller's side of `etude-guest`'s serial transport, as [`serial.h`](serial.h) declares it. It does no I/O and reads no clock: its caller feeds it the console's bytes with the time, writes the frames it makes through a callback, and calls it again at the time `etude_serial_deadline` gives. A session starts at `etude-guest`'s `alive` with a hello under SEQ 0, and its token is the digest of a name the caller gives, unique to the controller. At most four sequenced frames are in flight, so that a window fits the 4096 bytes of Rach2's serial receive ring; once the oldest has waited the resend interval, every frame in flight is sent again with its SEQ and bytes. Every call that received sequenced frames is answered by one `ack`. An event of an earlier operation's command is passed by, since `usage` and `cleaned` follow an error; an event of a command never sent ends the operation as a protocol fault, and so does a frame of the session whose CRC is right but whose fields do not parse, such as the old ten-field `exit`. A run ends with `exit`, a `stream` for descriptor 1 and then 2, `usage` and `cleaned`, and its output is complete when each stream's bytes match the size and digest of its `stream`. An `alive` of another process or boot is an `etude-guest` that started again, and loses the session.

### libetude-case

[`posix/scenario.c`](posix/scenario.c) reads the scenario invocation and the case's manifest, opens the store and makes one launcher, on whose executor the host tools and the services also run, so that one wait, `etude_qemu_watch`, serves the machines, the host programs and the pipe that the handlers of SIGTERM, SIGINT and SIGHUP write. The wait also returns when a host program writes output, so that a service's text is found as it comes. Each wait of the interface is that wait in a loop: after each return it judges the machines' results and, for a helper machine, feeds the console's new bytes to the serial controller, and it ends at its event, at the end of the machine or its console, at the step's bound or at a stop. The bound of a step is a deadline taken when the step begins, and no wait reaches past it. A machine's console and its end are the launcher's alone, so the library reads no record the kernel prints, and a text found on the console is found in what QEMU wrote, from the offset the caller gives.

The library is the only writer of the report, and writes each record with one write(2) after flushing standard output. It counts the scenario's assertions as it writes them, so that it can tell at the cleanup whether every declared one was given once and held, and a request refused, failed or lost through the interface counts as a fault of its own. A guest attempt's records come through `etude-guest`'s `out` frames: the library cuts them into lines, checks that `begin` names the scenario's case, writes the assertion, branch and progress records as its own, and drops `end`, `child` and the rest, since the scenario's report has one `begin` and one `end`.

### The watchdog

[`watchdog.c`](watchdog.c) keeps the watchdog of one attempt in plain C, with the time given by its caller. It reads the case's standard output a line at a time for progress records, and follows the stage the attempt is in. Its deadline is the earlier of the whole case's bound from its start and the bound of its stage: in execution, the gap bound from the later of the last progress and the start of execution, or while a quiet witness's work runs, that witness's bound from its announcement; in any other stage, the stage's bound from its start, when the case declares one. The longest gap of execution, the first and the last included, is the history's `max_progress_gap_us`. The first bound that runs out is kept, with a copy of the progress at that time: the stage, the time of the last progress, the witness that advanced last, and the counts of progress records, heartbeats, records refused and output since the last progress.

[`supervise.c`](supervise.c) runs attempts under their watchdogs on Linux, macOS and Windows: host attempts on an executor of its own, machines on a launcher of its own on Linux and macOS, and remote attempts on a running Rach2, whose transport the caller keeps, feeding the case's output and reporting its end and cleanup as `etude-guest`'s `out`, `exit` and `cleaned` frames give them. A host attempt's watchdog reads the case's standard output as far as the executor keeps it, and a machine's reads the console when the caller asks, as for a designated init's report, or what the caller feeds. A host or remote attempt is in execution from its start, and a machine in its boot until the caller moves it on. When a watchdog runs out, the supervisor:

1. marks the attempt incomplete and starts nothing more for it;
2. saves the progress at the expiry, the processes it owns (the keeper and the case's process, or QEMU's keeper and QEMU), a sample of the case's process or QEMU's, its processor time with the children it has reaped and its resident memory, read from `/proc` on Linux, or on Windows the processor time of every process the case's job has held and the working set of the case's process, and a machine's last twenty console lines;
3. for a running machine, sends QMP's `query-status`, `query-cpus-fast` and `human-monitor-command` with `info registers -a`, keeps each reply that comes within the capture stage's bound, or the grace period when the case declares none, and records each that did not; a QMP that hangs or has closed cannot make the wait longer;
4. asks the case to stop: a host case gets SIGTERM and SIGCONT through the executor on POSIX systems, and a guest or remote case gets the caller's request, such as a `cancel` frame, and the grace period to report its end;
5. ends what it owns: a host case's tree gets SIGKILL after the grace, or on Windows its job is ended at once, and a machine QMP's `quit` and then the executor's SIGTERM and SIGKILL;
6. finishes the attempt once the executor or the launcher has reaped what it owns and found the cleanup confirmed or not.

A remote attempt's end and cleanup are those the case reported. One whose transport is lost, or whose case reports no end within the grace after the ask, ends `lost` with its cleanup unconfirmed; a lost transport finishes it at once, without waiting for a bound, while the other attempts go on. An attempt whose cleanup is unconfirmed keeps its claims, as the result's `claim_kept` says, for the caller to keep reserved.

On Windows the supervisor's launcher is [`win/noqemu.c`](win/noqemu.c), which refuses every machine with `ENOSYS`. A controller there that is killed while its case runs takes the case with it, since the last handle of the case's job closes, and its claim is freed by the next recovery once those processes have ended. The OpenSSH server of Windows ends nothing when a connection without a terminal is lost, so a controller started over SSH goes on after the loss: the watchdog ends the case when one of its bounds runs out, and the controller releases the claim itself.

### Repetitions

[`posix/repeat.c`](posix/repeat.c) runs a plan of repetitions on Linux and macOS, as `etude_repeat_run` of [`repeat.h`](include/etude/repeat.h) declares. It keeps the repetition record in the store, writes the plan record, and runs the items in their order, `width` cases at once, on a supervisor of its own:

* Each attempt is admitted through the ledger, its load's claim before its case's, in the plan's order; while the attempt at the head waits for room, none after it is asked for. A load and a case that together exceed the machine's limits, and a claim the ledger refuses, end the attempt incomplete without running it.
* A load starts first, in a claim and a process group of its own, under a bound on its start that the site gives. Its case starts only once the load has written `etude-load: ready`, and the load is cancelled after its case has ended. A load that ends before its case is a disruption of the attempt, recorded beside its outcome.
* The case runs under its watchdog. An attempt passes when its case exits 0 within its bounds and the cleanup of the case and of its load is confirmed; it is a failure when the case exits otherwise or is killed by a signal; and it is incomplete when a bound ran out, its end was not observed, a cleanup is unconfirmed, or its load was never ready.
* Admission refused, a case that could not start, a load never ready, a lost end, a stop without a watchdog expiry, and unconfirmed cleanup are disruptions of the attempt, recorded with their causes. A watchdog expiry with its end observed and cleanup confirmed is the case's own incomplete result.
* An attempt that did not pass, unless admission refused it, is retried after every planned item, under the same load, until `retries` more attempts have run. A retry is an attempt of its own, `ITEM:aK`, whose record names the attempt it repeats in `previous_attempt_id`, and the plan lists every attempt identity an item may use.

The run record lists each item's attempt records and gives the item the worst of their outcomes, failure before incomplete, incomplete before cancelled and cancelled before pass, and the run the worst of its items'. A retry that passes thus leaves the item and the run a failure, and the failed attempt's record, its results and its output stay in the history; the run's reason names each case whose undisrupted attempts both passed and failed or did not finish as possibly flaky. Each attempt's results document gives its termination, as the executor saw it, and the `etude.termination` assertion. The store also gets the run's stage and family totals, its useful concurrency, and the loads applied, with the times they were ready and ended and their processor time. The budget names the site's policy and records the limits of the plan's class under it, with the verdict `unknown`, since the driver judges no budget.

`etude_repeat_tally` reads a history: of each case, architecture and workload, the attempts that passed, failed, did not finish or were cancelled, the retries among them, and the attempts with a disruption, which are counted apart, since their conditions were not those declared. A case is possibly flaky when its undisrupted attempts both passed and failed or did not finish, within one run or across several. A flaky case stays selected; nothing is quarantined or skipped.

`etude-load KIND AMOUNT` ([`posix/load.c`](posix/load.c)) applies a load until it is killed: `cpu N`, N processes that spin; `memory BYTES`, an allocation with each page written; and `disk BYTES`, a file of its working directory, unlinked once it is open, written and synchronized again and again. Admission reserves N thousand `cpu_millis`, or the bytes as `memory_bytes` or `disk_bytes`. It writes `etude-load: ready` with one write(2) once the load is in effect, and exits 2 for a wrong usage and 1 when it cannot apply the load.

### Remote execution

[`posix/serve.c`](posix/serve.c) is the responder of one connection, which `etude-remote` runs: it runs attempts through [`exec.h`](include/etude/exec.h), and reads the connection and serves the attempts in one loop. Its state directory has `evidence`, each line it did not act on with the reason, and a directory for each session, named by SESSION:

| Path | Contents |
| --- | --- |
| `lock` | The lock that the session's responder holds from its `ready` to its end |
| `cmd/CMD` | A command's record: the command's digest, the command, and each event it caused, a line each |
| `att/ATTEMPT` | An attempt's record: `run CMD`, and `process PID START` once its child is registered |
| `blob/SHA256` | A stored file, named by its digest; `blob/CMD.part` while its data arrive |
| `work/ATTEMPT/` | The attempt's workspace |

A command's record is made and synchronized before the command acts, and each event is recorded before it is sent, so that a command repeated after any loss is answered by what it did. A put's record is made at its seal, since nothing before the seal has an effect: a put cut short leaves no record, its partial file is removed, and the put sent again is acted on. An attempt's record is made with `O_EXCL` before its workspace, and its child's identity is synchronized into it before the child runs. On taking the lock, a responder records the end of each attempt whose run has none, which only a responder that was killed leaves, as `lost` with its cleanup unconfirmed, and removes the partial files of puts. Each file an invocation lists is copied from `blob/` into the workspace with the invocation's mode and checked by its digest again; `${WORKSPACE}` in an argument or an environment value is the workspace's path, the program runs there, and its standard input is `/dev/null` or a file of the invocation.

[`posix/remote.c`](posix/remote.c) is the controller's side. `etude_remote_open` starts the command `argv` gives, whose standard input and output are the connection, and requires the first frame to be `alive` with a version in common; text before it, as a shell's startup files print, is kept as evidence. Each command goes into the journal, with `fsync(2)`, before it is sent, and a controller that opens the journal again continues after its highest number. `etude_remote_put` sends a file, and a file refused as damaged is sent again under a new command. `etude_remote_run` stores the invocation, sends `run`, and takes the run's events: an event sent again must equal the first, output sent again must have the same bytes, and the attempt is complete when `started`, `exit`, a `stream` for each descriptor, `usage` and `cleaned` have arrived and each stream's output matches the size and digest of its `stream`. When the connection is lost or the responder breaks the protocol, it starts the command again, up to `reconnects` times in one operation, and sends the run again under the same CMD. The responder answers it from its ledger, so the attempt runs once, and gives the end the earlier responder recorded: the program's own, or `stopped` when the lost connection cancelled it. A responder in another boot leaves the attempt's end lost. At the caller's deadline the run sends `cancel` and sets the result's `cancelled`, and an attempt whose end does not come within its own deadline, its grace and two stage bounds after it was sent is taken as lost. `etude_remote_close` sends `bye`, closes the command's input and waits a stage bound for it to end, then sends it SIGTERM and SIGKILL.

[`posix/etude_native.c`](posix/etude_native.c) is `etude-native`, the controller of one native case through `remote.h`. It writes the invocation from its command line, with the `ordinary` role, the `workspace` fixture alone and no standard input, stores the files and the invocation, runs it, and judges the result as Use says. The end of an attempt gives no reason for a `stopped`, so `etude-native` takes it from the result: its own `cancel` when `cancelled` is set, a lost connection when the run had to connect again, and the attempt's own deadline otherwise.

### The artifact store

[`posix/store.c`](posix/store.c) publishes an object in four steps: it makes a partial file in `tmp/` with mkstemp(3) and takes a write lock on it with fcntl(2), copies the source into it while hashing it, synchronizes it and makes it read-only, and links it to `objects/DIGEST` with link(2), which fails when that name exists. A name in `objects/` therefore shows a whole, synchronized file or nothing, whatever ends the writer. When the name exists, the object there is read and checked: a good one is kept, so its inode does not change, and a damaged one is replaced with rename(2); a file system without hard links gets the rename too. A put with an expected digest, as a transfer has, refuses other content before anything is named. A record is written the same way, after its object, so a record that a reader finds refers to an object that exists; it is renamed to its key, replacing a damaged record or one whose object was damaged, and only the process that has the key's lock writes it.

A writer keeps its partial file's lock from the file's making until its removal. A sweep, which opening a store runs, tries a read lock on each partial file and removes those whose lock it gets, since their writers have ended. A sweep that takes its lock between a writer's mkstemp(3) and the writer's own lock makes that writer find its lock refused or its name gone, and make another file.

### Preparation

[`posix/prepare.c`](posix/prepare.c) checks a graph before it runs anything: every input is a node of the graph, every `${IN:NAME}` refers to an input of its node, and a depth-first walk finds no cycle. It then takes each node whose inputs are done. A node with a failed or blocked input is blocked; a file of the tree is published; any other node is reused when its record's object checks, and otherwise runs its recipe once it has its key's lock and one of the run's jobs is free.

A write lock on `locks/KEY` keeps two processes from running one key's recipe. The second tries the lock again every 20 ms, looks the key up again once it has the lock, and reuses what the first published; a node whose wait passes its bound fails. The lock goes with the process that had it, so a controller that is killed leaves nothing locked.

A recipe runs through the executor, in a work directory that mkdtemp(3) makes under the run's scratch directory, and is cancelled when it runs past its bound. Its product is published only when the recipe exited 0 and the executor confirmed that each of its processes has ended, so that nothing still writes the file. The product must be a regular file, not a link, and is copied into the store, so a later write in the work directory does not reach the object. The work directory is removed after a success and kept, with what the recipe left, after a failure, and the node's result gives the recipe's end, its standard error as kept and the reason it failed.

### The preparation adapter

[`posix/legacy.c`](posix/legacy.c) runs the preparation of `tests/run` one step at a time through the POSIX executor. Each step is a `make -C TREE --no-print-directory ARCH=ARCH`, with `BOOT_KERNEL` when a kernel is named, run in the tree's root with its output in its log and cancelled at its bound. A preparation never makes a suite's own target, `run-NAME`, which would start the suite without its locks, and the adapter starts no scheduler of `tests/run`.

Before anything is built it checks the request: each goal must be a relative path inside the tree of letters, digits, `.`, `_`, `+`, `-` and `/`, with no part empty, `.` or `..`, and not begin with `-`; each suite must be in the registry, named once and of the architecture asked for, the commands its registry entry names must be on the path, with `qemu` for the architecture's QEMU, and the tree must be held. The steps are then, in order: the path, the caller's with the directories that `tools/setup/e2fsprogs_path.sh` adds; for a set, the commands that `make -s prepare-tools` prints, checked the same way; the recovery key, `make recovery-key`, when the tree has `krffs/manifests/rach2-recovery.manifest` and no `krffs/recovery_authorized_keys`, and the mode 0600 on the committed demo and test keys; `make -j components`; `make NAME-kernel` for a kernel named; `make -j prepare-all` for a set; make's database, `make -pn prepare-tools`; and last one `make -j` of the artifacts that no step before built, the goals given with `-b` among them. The first two steps build nothing, so a set refused for a command its preparation lacks has built nothing either.

A suite's artifacts are what its target reaches in make's database, through the prerequisites of each rule and the words of `prepare-all`'s recipe that begin with `prepare-`, since that recipe makes its two halves with a make of its own: each path under `build/`, and each other target of a rule with a directory in its name, such as `krffs/shadow`, that is not phony. An absolute path inside the tree is recorded from the tree's root, so that a file the Makefile names both ways is one artifact, and make is given the name it knows. An e1000 suite's target is its plain twin's. A file that make knows only as a prerequisite, which the database marks `# Not a target:`, a target's own variable and a multi-line variable are not rules. For one suite, the last step builds every artifact, which the suite's own target would otherwise build as it starts; for a set, those outside `prepare-all`'s, such as the GNU system's images. The kernel the suites boot and each goal are artifacts too. Every artifact must then exist, and each regular file is read and recorded.

A step's environment is the caller's with `LC_ALL=C` and the path, and without `MAKEFLAGS`, `MFLAGS` and `MAKELEVEL`, so that a make that runs the adapter passes neither its flags nor its jobserver to the steps. Every make is given `ARCH`, and for a kernel named `BOOT_KERNEL`, on its command line, which an `ARCH` in the caller's environment does not override. A step passes when it exited 0, the executor confirmed that each of its processes ended, and the executor kept all of its standard output. SIGHUP, SIGINT and SIGTERM set a flag: the adapter then cancels the step that runs, which the executor ends with SIGTERM and with SIGKILL five seconds later, time for make to remove the target it was writing, and runs no other. The record is written to a new file beside RECORD, synchronized and renamed to it, so that a reader finds the whole record or none. The work directory is removed after a success, a refusal and a stop, and kept after a failure.

### The suite adapter

`etude_legacy_run` in [`posix/legacy.c`](posix/legacy.c) runs one prepared suite as `run_one` in `tests/run` runs it, `make run-NAME` under `runutil`, with the shims, the ledger and the cleanup of `tests/run`, and judges its end from evidence that `tests/run` does not keep. It takes no lock: its caller holds the tree, the host lock and a port block, as `etude-bridge -p` and `legacy.sh` hold them, so that the suite runs with the locks `tests/run` would take for it and no scheduler of `tests/run` starts. A `RACH2_PORT_OFFSET` that is unset or not a number is refused, since the suite would forward the ports of the first block, which another run may hold. The record must list the suite and each of its files must be unchanged, so that a suite does not start on artifacts that changed after their preparation; the suite, its commands and the hold are then checked as for a preparation.

The work directory has `runutil`, compiled from the tree's `tests/system/runner/runutil.c` as `tests/run` compiles it, and a shim for each QEMU on the steps' path, the script `tests/run` writes: it adds `-accel` and, when `RACH2_CPUS` is not 1, `-smp`, and execs the emulator through `runutil machine`. The suite's environment is a step's with the shims first on the path and the variables `tests/run` gives a suite, `RACH2_QEMU`, `RACH2_QEMU_ACCEL`, `RACH2_CPUS`, `RACH2_RUN_UTIL`, `RACH2_QEMU_LEDGER` and `RACH2_QEMU_SHIMS`, so that each machine, whether its script finds QEMU by name or through `RACH2_QEMU`, is recorded in the ledger with its relay.

The target runs through the executor under `runutil record NAME IDLE LEDGER END`, which supervises it as the `suite` mode does, with the idle limit, the group ledger and the liveness pipe. The suite's output goes to the work's `suite.log`, which the adapter copies to its own output as it grows. The case's standard output stays the executor's, and `runutil machine` writes on it a `child` record for each machine and each relay, so that where the keeper reaps no orphans the executor still ends a machine whose supervisor was killed. Once the target has ended by itself, runutil gives the machines five seconds to end, the time a machine that its suite signalled and did not wait for may need, and writes to END a `left` line for each machine or relay still running, and a `cut` line for each other machine whose relay did not add its pid to `LEDGER.closed`. A relay adds it only once the transcript has the whole of the machine's output, at its end or when the suite stops reading it, so a relay killed with its machine's output unread has cut the console. A stop signal sent to the relay with its machine, as a `pkill -f` of the machine's arguments sends it, leaves the relay five seconds to copy the rest of the output, and a machine that ends in that time has its console whole. runutil then stops what is left, as the `suite` mode does, and finishes END with the target's status, the idle stop, the signal it received, the liveness check and the machines that outlived their SIGTERM, and renames it into place, so that a reader finds the whole record or none.

The adapter judges the suite from END and the executor's result. A run past its bound, a case whose end the executor did not see, a record that is missing or not whole, as when runutil is killed, an idle stop, a signal to runutil, a console cut and a cleanup the executor could not confirm leave the suite incomplete. A suite that finished fails for a machine left running, a machine that outlived its SIGTERM, a process that outlived the suite, a target killed by a signal or one that did not exit 0, and passes only with none of them. A stop cancels the case, which the executor ends with SIGTERM and with SIGKILL thirty seconds later, time for runutil to stop the suite and its machines, which takes it up to twenty seconds when a machine outlives SIGKILL, and write its record. The work is kept after a run that failed or did not finish, with a copy of each log under the images that the suite wrote after it started and owns by the globs of its registry entry, as `keep_logs` in `tests/run` keeps them, and removed otherwise.

### The set driver

[`posix/legacy_set.c`](posix/legacy_set.c) runs a set of prepared suites through the scheduler of [Admission](#admission), with the ledger's claims in place of the old runner's pool. The history's plan has one item for each suite, `RUN:legacy.NAME:ARCH:r0`, of the case and family `legacy.NAME`, and the run's identity is `tests.ARCH.TIME.PID`. The preparation is the first claim, of every limit of the ledger, with the host lock alone when `-d` is given, and runs `etude-legacy prepare` with its output to `output/prepare.log` and to the driver's own; it is the history's step of the build stage. Each suite is then a claim of its own: half a processor for each of the machines' processors, at least half a processor, its memory and 128 MiB for QEMU, and a GiB of disk, each held within the ledger's limit, so that a suite larger than a limit runs alone rather than never. With `-d`, a suite whose memory is more than half the limit takes the host lock alone. The serial suites go first, one at a time, and a suite with the host lock alone has nothing beside it; the others are admitted in the order given, as many as the ledger and the width admit, the admission asked again every second.

A suite runs as `etude-legacy run -w EVIDENCE/RUN.NAME -i IDLE -s SECONDS RECORD NAME`, with its output to `output/`, under a watchdog of the whole suite, and the driver judges it by the last `etude-legacy: result:` line and the exit status: a pass, a failure, or a suite that did not finish by its own fault, as for `run`; a stop of the watchdog, a signal, a lost end or a line of another form is a disruption, and the suite did not finish. The driver drops the `run: NAME: PASS in` lines of `run`, since `history_lines` prints them from the history, and prints its own starting line in place of `run`'s for a set of more than one suite. A suite cancelled by a stop is cancelled unless it passed or failed all the same, and a suite never started has no attempt and the outcome cancelled. An attempt that did not pass keeps the end of its output, at most 16 MiB, as its evidence in the store. A signal withdraws the claims that wait, stops the suites that run, which `run` ends with their machines, and writes the run record before the driver exits.

A suite with `cases=MANIFEST` is run by the host, guest and machine cases of its manifest in place of its target, and the memory its line gives is not used. The manifest is read by the strict JSON reader, and the set is refused when it cannot be read, when the last part of its family, split at dots, is not the suite's name, when none of its cases runs on ARCH, or when a case that does is of a domain other than `host`, `guest` and `machine`, reads standard input, needs host locks, needs loop devices, or needs a fixture other than `scratch`, and `disk` for a guest or machine case, when a host or guest case needs local ports, or when a machine case has arguments. A guest case whose profile forwards no port takes its local ports and loop devices only in a native run, which the driver does not make, so it may reserve both, and the driver gives it none. A guest case is refused too when its role is `init`, when it ends other than as `exited` or `signaled`, when it has no QEMU profile, or one whose firmware is OVMF or whose memory is not reserved, when its kernel or RAM image is no artifact of its `prepare`, or when a disk that is not empty is no such artifact, or neither a CD nor in a `disk` fixture. The schema's other rules are `casecheck manifest`'s to check. A set with a machine case is refused unless RESULTS and EVIDENCE are absolute, since its scenario runs in its workspace and is given their paths. Each case whose `architectures` is `none` or names ARCH gives one item for each of its workload's `repetitions`, `RUN:CASE:ARCH:rR`, with ARCH `none` for a case of no architecture, of the case and of the manifest's family, and the item's workload, assertion inventory and profile are the canonical documents whose digests [`digest.c`](digest.c) takes. The members of a case keep their suite's `serial`, and a suite that `stops` stops the set once each of its members has ended, so that the other cases of the suite run after one fails. The preparation is given each case's `prepare` artifacts as goals, once each: the node as `build/NODE`, or as `build/x86_64/NODE` for an artifact made for each architecture when ARCH is `x86_64`. With `-n KERNEL`, which `tests/run` gives for `RACH2_KERNEL`, the artifact that a guest case's QEMU profile names as its kernel, when its node is `rach2/kernel`, is the goal `rach2-KERNEL/kernel` in the same directory, the kernel the preparation builds for the legacy suites, and the case boots it; a case whose kernel is another node keeps that node. The attempt record has no member that names the kernel; the plan's reproduction of a guest item gives `RACH2_KERNEL`. The legacy suites are its SUITEs, and a set of cases alone names none.

Each item of a case has a workspace, the directory `EVIDENCE/RUN.CASE.rR`, which is made before the case starts, removed after a pass and kept after any other outcome. A host case runs as its program, the goal of the artifact its `execution.program` names, by its path in the tree with the workload's arguments, in its workspace with its input from `/dev/null` and its output to `output/CASE.rR.log`. Its environment is the driver's, `ETUDE_ADMITTED` and `ETUDE_SITE` among it, so that a program that runs `make` is admitted as the driver was, less the driver's own `ARCH` and `ETUDE_SEED`, with `ETUDE_TREE`, the tree's absolute path, `ETUDE_CASE`, `ETUDE_SEED` when the seed is not null, `ARCH` when the item has an architecture, and, for a case with the fixture `scratch`, `TMPDIR`, the workspace. Its watchdog has the initial `case` and `gap` bounds of the manifest and its witnesses of progress, and reads the program's output as it comes; bounds from the history are not taken yet. Its claim is the case's `cpu_millis`, `memory_bytes` and `disk_bytes`, those above 0, each held within the ledger's limit, and with `-d` the host lock shared and no port block.

A guest case runs on a machine of its own, booted from its QEMU profile with the run's accelerator. Its claim is the case's `cpu_millis` and `disk_bytes` and, in place of its `memory_bytes`, the memory the launcher reserves for the profile, the guest's and QEMU's overhead; with `-d` it takes a port block too, and the host lock alone when that memory is more than half the limit, which runs it with nothing beside it. Its watchdog has the manifest's initial `case` and `gap` bounds, the initial bound of each stage its `bounds.stages` gives, and its witnesses of progress. The kernel, the RAM image and the disks' artifacts are put into a store of the run's own, `EVIDENCE/RUN.store`, each with the digest the preparation's record gives it, so that an artifact changed after the preparation does not boot; the store is removed when the run ends. The kernel and the RAM image are read from the store's objects, a CD's medium is its object, a disk of a `disk` fixture is a private copy in the workspace's `disks/`, and an empty disk a sparse file there. The machine starts in the watchdog's boot stage, with its console written to the workspace's `console` and QEMU's processes registered with the claim. Once the kernel's debug shell greets, the driver types `exec /etude-guest --stage / --resend-ms 1000` and opens `etude-guest`'s session on the serial console, as libetude-case does. In the transfer stage it stores the program, from the image's root when the image has it and with its bytes from the store otherwise, and then the invocation: the program with the workload's arguments in the attempt's workspace on Rach2, the role `ordinary`, no standard input, `PATH`, `HOME` the workspace, `ETUDE_CASE`, `ETUDE_SEED` and `ARCH` as for a host case, `TMPDIR` the workspace for a case with `scratch`, the case's bound as the deadline, and 4 MiB of each stream. In execution it follows the run until `etude-guest` reports it cleaned, the program's standard output going to `output/CASE.rR.log`, whose records feed the watchdog, and its standard error to `output/CASE.rR.err`. The machine is then stopped, and the attempt ends when QEMU has ended, with QEMU's cleanup as its own. An expiry of the watchdog asks `etude-guest` to cancel the run and stops the machine after the grace, and a stop of the run does the same. The end is the one `etude-guest` reported, unless an expiry or a stop came first, which gives `stopped`; a session that failed gives `lost`, and its fault is a disruption beside casecheck's reason.

Once a case ends, `casecheck attempt` judges its output and its end, placed `host` for a host case, and for a guest case placed `qemu`, so that the profile's processor decides the branches its features decide, with the machine's console as `-k`, so that a panic or a fault of the kernel fails it. The end is `exited` or `signaled` with the status or the signal, `stopped` after an expiry of the watchdog or a cancellation, and `lost` otherwise; casecheck runs with no input, its document goes to `output/CASE.rR.results` and its errors to `output/CASE.rR.judge`, and it is killed after a minute. When it exits 0, 1 or 3 with a document, the document is the attempt's results and the attempt passes, fails or is incomplete as casecheck says, its reason the assertion that decided it, with its detail, and the bound it ran past after an expiry. When casecheck cannot judge, the attempt is incomplete, with the reason as a disruption and a results document of the driver's own. A cancelled case stays cancelled unless casecheck says it passed or failed, and a pass with its cleanup unconfirmed is incomplete. The run record's totals are by stage and by family, and its reason counts items.

A machine case runs as its scenario, the artifact its `execution.program` names, with one argument, its scenario invocation, which the driver writes to `output/CASE.rR.invocation` once the preparation has passed. Before that the driver publishes the `prepare` artifacts of each machine case to the run's store, `EVIDENCE/RUN.store`, each file by its path in the tree, and the invocation gives each artifact's digest, the store, the case's tools found on `PATH`, `qemu-system-i386` and `qemu-system-x86_64` found on `PATH`, `RACH2_QEMU_ACCEL`, `boundary_lazy` true when SITE has the line `boundary_lazy bigmem-boundary-v1` and false otherwise, the case's `gap` bound as each step's, its `cleanup` stage's bound as the cleanup's, or 5 s without one, the local ports its `resources.ports` asks for, and its workspace as the scratch directory, which a machine case always has. The ports are of the caller's port block, which `RACH2_PORT_OFFSET` names: from 2400 past its offset on, each member's its own, in the order of the plan, and at most 100 for the set, so that they end in 400 to 499, which no port of the table in [`tests/system/suites.mk`](../../tests/system/suites.mk) does in any block. A set that needs them is refused with `-d`, whose claims take blocks of their own, and without an offset. A member whose emulator or tool is not on `PATH`, or whose artifacts cannot be published or invocation written, ends incomplete before it runs, with the reason as a disruption. So does a member whose case declares a machine of `bigmem-boundary-v1` when the site does not permit that profile, or when the ledger's memory limit is less than the case's `memory_bytes`: its claim would be cut to the limit, while `libetude-case` gives the launcher the case's `memory_bytes` as reserved. A set whose SITE cannot be read is refused. Its claim, its watchdog and its environment are a host case's, and its grace from SIGTERM to SIGKILL is 5 s more than its cleanup's bound, so that `libetude-case` can capture its machines' state and stop them. `casecheck attempt` judges it placed `qemu`, with a `-k` for each console that the scenario kept in `evidence/` of its workspace, in the order of their names, at most 64.

### The proof driver

[`proof.c`](proof.c) reads a catalogue with the strict JSON reader, checks it against its schema and then by its own rules, and makes the edits; [`posix/proof.c`](posix/proof.c) runs the proof, and [`macho.c`](macho.c) gives the digest by which it compares a Mach-O artifact. It saves each source whole, in memory and in `WORK/saved`, from which a person restores a shared tree should the driver be killed with SIGKILL, and for a private proof writes the copies under `WORK/src`. A source is written whole to a new file beside it, given its mode, renamed over it and read back, so a reader sees the old text or the new one. A build that judges by time stamps, as make(1) does, would take a source written within the second of an artifact for an old one, and an artifact may have a time ahead of the clock; the driver therefore sets a source's time to one second past the newest artifact's whenever the source is not newer. The restored phase's comparison with the base's digests finds a build that still did not make its artifacts again.

The build and the test run through the POSIX executor in the tree's root, with standard input from `/dev/null` and the driver's environment, `TMPDIR` and the sanitizers' settings aside, and their output is kept in the work directory as `PHASE.build.out`, `PHASE.build.err`, `PHASE.test.out` and `PHASE.test.err`. The test's `TMPDIR` is `WORK/PHASE.test.tmp`, which the driver makes before it starts. The build's is `WORK/build.tmp` in every phase, which the driver makes before it starts and renames `WORK/PHASE.build.tmp` when it ends, since a compiler may write the path of its scratch into what it makes, as Apple's linker does in a debug map, and a path of another length would move the rest of the file. A work directory given by a relative path is made absolute first, so that a command finds its `TMPDIR` from any directory. A command's sanitizer settings are the driver's own, `ASAN_OPTIONS=halt_on_error=1:abort_on_error=0:exitcode=1` and `UBSAN_OPTIONS=halt_on_error=1:abort_on_error=0:exitcode=1`, with no `LSAN_OPTIONS`, so that a sanitizer's report ends a test with status 1 on Linux and macOS alike; macOS would otherwise abort it with SIGABRT, and an inherited `exitcode=0` could let a fault pass. A catalogue that wants other settings gives them in its command, through `env`. When the driver removes the work directory, it makes each directory in it readable, writable and searchable before reading it, since a test's scratch may have one that is not. The driver looks at a running command every 100 ms for its bound and for a signal. SIGHUP, SIGINT and SIGTERM set a flag: the driver then cancels the command, which the executor ends with SIGTERM and with SIGKILL two seconds later, restores the sources and removes the work directory. A shared proof requires the tree's run lock: the lock's owner file, `build/.run.lock/owner`, must name the process that `RACH2_TREE_HELD` names, and that process must run. `proof.sh` takes the lock through `runlock_exec.sh`, which passes a signal on to the driver once.

### The tooling machine

The tooling machine is an Ubuntu cloud image for x86-64, named by its URL and SHA-256 in [`tooling/image`](tooling/image), which QEMU runs on every host, under TCG where the host cannot accelerate x86-64, as on the Mac. Its key is the SHA-256 of the recipe's files, each with its name and size: `image`, `user-data`, `meta-data`, `provision.sh`, `runner.sh`, `etude-job.service` and `tools`, so a change of any of them makes another machine. The cache has the image as `image-SHA.img`; the made machine as `tooling-KEY.qcow2`, an overlay on the image; and the commands it provides, with their paths and versions, as `tooling-KEY.tools`. The three are read-only.

`prepare` boots a new overlay of the image with a FAT volume labelled `CIDATA`, which mtools makes from the recipe and cloud-init reads as its NoCloud source. [`tooling/user-data`](tooling/user-data) runs [`tooling/provision.sh`](tooling/provision.sh) from that volume. It installs the packages and Codex at the version it names, allows unprivileged user namespaces, installs the job runner, turns off the services a job does not need and cloud-init itself, and checks each command of [`tooling/tools`](tooling/tools). It prints each one's path and version on the second serial port and then `etude-tooling: provision: ok`, and powers the machine off; a command that is missing fails it. The overlay is made under a partial name and renamed after that line alone, so a disk in the cache is a whole machine.

A job boots a private overlay of the made machine, `job-PID-N/root.qcow2`, its root disk first in the boot order, with no network unless `-n` asks for one. A second FAT volume, whose virtio serial is `etude-job`, has `job.sh`, the list of outputs and `in/`, and each `-d` disk is a raw virtio disk whose serial is `etude-dN`. The guest's `etude-job.service` runs [`tooling/runner.sh`](tooling/runner.sh) once that volume appears. The runner copies `in/` to a working directory and runs the script there as root, with `ETUDE_DISKn`, `ETUDE_DISKS` and `ETUDE_WORK` set; it writes the script's standard output, error and status to the volume and the outputs to `out/`, and powers off. It says `etude-job: start`, `ran N` and `end N` on the second serial port. The job's status is the one `end` gives, and the volume's must be equal to it. A boot that ends without `end`, a status missing or unequal, and a boot past its deadline, which is cancelled, fail the job.

A job's boot is three steps of the history: `tooling.start`, of stage `tooling_start`, from QEMU's start to `etude-job: start`; `tooling.job`, of stage `execute`, to `ran`; and `tooling.end`, of stage `cleanup`, to the end of QEMU's processes and the removal of the job's directory. Provisioning is one step, `tooling.prepare`, of stage `one_time_setup`, since a machine is made once. Each step's witness is its marker. Its processor time and peak memory are QEMU's, sampled by `etude_proc_sample` at the markers: on Linux its process's, as `tooling-qemu-cpu-v1` and `tooling-qemu-rss-v1`; on Windows its job's processor time and its working set, as `tooling-qemu-job-cpu-win32-v1` and `tooling-qemu-working-set-win32-v1`; and on macOS none. The scope, a blob of STORE, has the key, QEMU's process, and the totals of the boot: the processor time and peak memory of QEMU's tree, as the executor measures them, and the disk bytes it used: the image's and the made machine's for a provisioning, and the private overlay's, the job volume's and the job's disks' for a job.

## Limits

The history store checks record shapes, stream order and local interval arithmetic. The executors other than the POSIX and Windows ones and the QEMU launcher of Windows are not implemented. The probes print their own lines and are judged by their exit status, as `tests/run` judges them now. A schema-valid document alone does not establish a complete case, a valid report or a pass. Cross-stream references, hashed content, assertion coverage and aggregate results require the consumer's checks.

The comparison finds blobs only in the store that `-b` names, by digest, and not at the locations a blob reference gives. It matches the cache-state and load snapshots by digest without reading them, and takes the run record and its disruptions as the account of the load, since no part defines the snapshots' contents yet. The plan does not say whether its checkout was modified, so the comparison cannot leave such samples out. It records no equivalence review: a changed workload or assertion inventory always starts a new baseline. It compares cases and their steps, not whole runs, and a step that runs more than once in an attempt is not compared.

The POSIX executor's callers are the QEMU launcher, the supervisor, `etude-remote` and their tests. It waits for the keeper's handshake inside `etude_exec_start`, and is used from one thread. Signals to the case's process group after the case's process has been reaped could reach a group whose number the system has reused. Elsewhere than Linux, macOS and Rach2 a process's start cannot be read, so a `child` record makes the cleanup unconfirmed.

The schedule and the costs have no caller but their tests, and no program but `etude-bridge` and `etude-ledger` uses the ledger. `etude-ledger` is not in a cached version, so it runs from a built tree. A worker whose request waits must ask again to be admitted, since the ledger sends no notice when a claim ends. The ledger takes its limits as arguments; installed launch admission supplies the same site capacity to every supported entry point. Direct callers of the ledger API must supply that same capacity. Deployment gives each account a ledger of its own unless `-L` names one that several share. A ledger is judged by processes of one operating system, so Windows and Linux in WSL on one machine cannot judge each other's claims. A process group number that an unrelated group has reused keeps a claim until that group ends. Several accounts can share a ledger only in a directory where each may replace the others' files, which a sticky directory forbids.

The budget has no caller but `history_budget` and its test, and no committed policy: the site and its capacity are chosen with the test machine, and until then the example's invented site is the only one. No executor records preparation or one-time setup steps as The budget defines them, and the repetition driver records the verdict `unknown`, so `history_budget` reports every run it recorded as one that records another budget and exits 1, whatever its verdict. A forecast charges the preparation of its nodes one after another, as if no two were built at once. It takes each artifact's node from the manifest and not the inputs of the preparation graph, so a node that only another node needs is not charged. A judgement finds a node that a planned case prepares and the run did not only when it is given the case's manifests. An attempt or shared step timed on a clock other than the run's leaves the charge unknown, so a run whose work spans several machines cannot pass.

`bootstrap.sh` has not run on a Windows machine, and on Rach2 it has run only under QEMU, in the `etudeexec` suite. Its test runs the Windows path under stand-ins for MSYS2's `uname` and `cygpath`, and BusyBox's sh and tools where the host has BusyBox, but neither MinGW-w64 nor Rach2's TinyCC. Without a terminal, sshd sends no signal when a connection is lost, so a build goes on and publishes its version, which the next request reuses. A build stopped by SIGKILL leaves its directory, which nothing deletes.

`deploy.sh` has deployed the Ubuntu endpoint of the testing PC, which its enrollment then gave an installed site policy and a ledger that the test accounts share (Installed launch admission). It has deployed the Mac only locally, with `-n -l`, into private cache, state and ledger directories, and no site policy is installed there. It has not deployed Windows or Rach2. Its test runs the POSIX path over a stand-in for ssh(1), and the Windows path under stand-ins for PowerShell, MSYS2's `uname` and `cygpath`, and QEMU for Windows. Bisection reads a private machine record only when no installed site policy is selected. Shared launch admission reads the installed policy's ledger and limits. The record's processors and memory are the whole machine's and not the share an account is given, and its accelerators are those the account can open, whichever QEMU was built with. A ledger that several accounts share needs each to be able to write it, which deployment checks and leaves to the ledger's owner to grant. A deployment stopped by SIGKILL leaves the record's temporary file, `machine.XXXXXX`, or the scratch copy of the prerequisites, `rach2-etude-prereq.XXXXXX`, which nothing deletes.

The responder and the controller's side are POSIX programs; neither has a Windows adapter, and the serial transport's acknowledgements are `etude-guest`'s. `etude-remote` runs the `ordinary` role alone and makes the `workspace` fixture alone, refusing an invocation that asks for another. It serves a `get` of a file directly in a workspace, `TOKEN/work/FILE`, and answers any other name, `out.1` and `out.2` among them, with `error unknown`; it has no `--stage` directory, and a put of a file it has stored before still sends the data. `etude-native` drives the controller's side for one case at a time, named on its command line. The CRC and the digests find damage by accident; a deliberate change of a frame is SSH's to refuse. A responder waits for the session's lock without a bound, so one that cannot end keeps the next responder's `ready` back until the controller's stage bound passes; `etude-guest` sends the holder SIGTERM first, and still waits for it to end. An attempt stopped at its own deadline in a run that also connected again is reported by `etude-native` as stopped by the lost connection. `bye` removes a session's stored files, and nothing removes its ledger. A repeated command's events are sent again in frames of the size they were recorded in, so a controller offers the same largest frame on every connection of a run. The controller's side does one operation at a time, and the responder writes events while the controller sends a file only when an attempt from an earlier operation still runs.

`casecheck report` reads a file of output, not a live transport, and judges only the assertions whose source is the program or the scenario; the executor's assertions need the end and the console that only an executor sees. `casecheck attempt` takes the end from its caller and the consoles from the files its caller gives with `-k`, and reads no kernel log. Without `-k` it gives as missing every assertion that the console would decide, so that an attempt placed `qemu` without it is never a pass. Its caller is the set driver, [`posix/legacy_cases.c`](posix/legacy_cases.c), which judges each attempt of a host or guest case with it. The set driver sets `ETUDE_CASE` for its cases alone, and a probe that a suite's target starts from the debug shell reports under the identity it has for its first case, such as `guest.default.rngprobe`. The programs that write report records are the probes `rngprobe`, `xsaveprobe`, `fpuprobe`, `poolprobe`, `blockprobe` and `bootprobe`, and the musl programs `textbusymusl`, `bindholdmusl`, `saltnoent`, `passwdmusl` and `keygennoent`. The source checks of `suitecheck.sh` read the forms a line shows: a sleep through a probe's own wrapper is found at the wrapper's system call, and a skip only where a line prints it.

`casecheck verdict` has two callers, [`tools/ci/run.sh`](../ci/run.sh) and [`tools/ci/bisect.sh`](../ci/bisect.sh), and each judges a run's history with it only when the tree's `run.sh` sets `results=history`. `master`'s sets `results=lines`, so ci and bisection read the runner's lines, which `tests/run` prints from its history with `history_lines`, and the verdict has judged only its fixtures and the histories that the tests of `run.sh` and of the set driver make. The manifest under `tests/cases/` does not change this: its cases run through the set driver, which judges each attempt with `casecheck attempt`, and no runner consults the verdict. It reads the evidence of an attempt recorded as a pass and takes any other outcome as recorded, since evidence can only lower an outcome. It does not read a step's own evidence, the comparison records or the plan's `reproduce` blob, and it finds a suite by the family's name alone, so the items of a family whose name has no part that names a suite asked for belong to the set.

`etude-guest` reserves nothing across cases: two cases given the same NEW id or port at once, or more volumes than the four loop devices, are for the controller's admission to keep apart, and `alone`, `console` and `peer` are the controller's to arrange. `exec` takes the `workspace` and `stage` fixtures alone. When it settles the attempt of a killed `etude-guest`, it would also kill a group that another process made in the same boot with the child's PID as the number of its group and its session, which can happen only after the attempt's group has ended, the PIDs have come round to that number, and that process has ended; and it kills no process that the attempt left in another group, such as one the child made in its session with setpgid(2), or that a `child` record reported. The `log` fixture finds where the records written during a case begin by the last 256 bytes of the log before it; when the kernel's buffer has wrapped past those bytes, the whole log after the case is kept. `etude-native` runs a case on the Lenovo one at a time, and the cases of [`tests/native/`](../../tests/native/Readme.md) do not run there yet. Built on macOS, as the host tests build it, it refuses the fixtures `volume`, `root`, `tmpfs`, `mountns`, `ipcns`, `utsns` and `log`, which need the kernel's loop devices, mounts, namespaces or log; it takes the boot's token from the sysctl `kern.bootsessionuuid`, and a process's START and ids from the sysctl `KERN_PROC`, since macOS has no `/proc`. On the serial console a frame is at most 255 bytes, so an `out` frame carries 78 bytes of output, and an event that does not fit the bound, such as the `stored` of a long file name, is sent as `error CMD limit` instead.

The QEMU launcher has no caller but the supervisor, `libetude-case` and the tests, and is used from one thread. It reads no kernel record from the console, so a panic printed there, a machine whose processors have all halted and the designated init's end are for its caller to find. Its profiles give raw disks alone, and no device that needs a member the table above lacks, such as a `-chardev` or `-netdev` of its own. Only `libetude-case` gives a capture its file, since no program runs a guest case's boot yet.

`libetude-case` is used from one thread. It starts `etude-guest` only on a machine whose console reaches the kernel's debug shell, with `--stage /`, and finds the shell by its greeting. It runs guest invocations of the `ordinary` role alone, and refuses one of `init`. It reads only the first `console_max_bytes` of a console, which the launcher keeps, so a wait for text not in them, and a session of `etude-guest` that runs past them, are lost. A host tool's output is kept to `output_max_bytes`, and so is a service's, which a wait cannot search past. A step's bound covers its waits, and not the scenario's own work between them. Its services run on the controller's host, and its ports are the invocation's; the set driver takes them from the caller's port block, and no claim of the ledger reserves them. A service that catches SIGTERM and exits is taken to have ended by itself unless the scenario stops it.

The serial controller keeps four frames in flight, so a put of a file waits for an acknowledgement after every four data frames of about 140 bytes each. It numbers its commands from 1 in each session, so two controllers that drive `etude-guest`s sharing a state directory need names of their own; `libetude-case` gives each boot's attempt identity. An `etude-guest` that starts again while a session opens loses the open rather than receiving a new hello.

The supervisor's callers are the repetition driver, the set driver and the tests, and it is used from one thread; while it runs host attempts and machines at once, it serves each kind in turn for 50 ms at most. Nothing yet gathers a bound's samples from the history, so the caller gives them to `etude_bound_fix`. A watchdog sees only the output its executor or launcher keeps, so the progress of a case that prints past its output's bound is not seen, and the case runs out of its gap. A process is sampled on Linux and Windows alone. On Windows the supervisor runs no machine, and on no system does anything connect it to the controller's side of remote execution: the caller feeds a remote case's output and reports its end and the loss of its connection. A process of a case on Windows leaves its job's count of active processes and closes its handles a moment before its own handle is signaled, so just after the executor confirms a cleanup, `etude_process_state` can still find a process of the case running, for less than 16 ms on the testing PC; a recovery in that moment keeps the claim until the next one.

The repetition driver has no caller but its test. It runs host cases alone, and on Linux and macOS alone, and judges a case by its exit status, not by report records. It asks the ledger again every 100 ms while the attempt at its head waits, since the ledger sends no notice. It samples neither the machine's load from outside the run nor combined memory, and its records say so. A seed fixes the order and the loads and not the host's schedule, so a race that depends on timing may need several runs of one seed to show. `etude-load` is not in a cached version, so a machine other than the controller's has none yet, and Windows has no load fixture.

The preparation graph has no caller but its test, and the artifact store none but its test and the set driver, which keeps the guest cases' artifacts of one run in a store of its own and removes it at the run's end. Neither has a Windows adapter. A product is one regular file, so a directory, such as the GNU root, is not yet an artifact. A lookup reads the whole object, which costs a read of every reused artifact on each run. A node's key covers only what its definition gives, so a recipe that reads a file that is neither an input nor in its key text is reused after that file changes. A recipe may change an input's object, which is read-only but owned by the same account; the next lookup finds the damage and makes the node again. Nothing removes an object, a record or a lock file of a store kept across runs, so such a store grows without a bound until admission and retention account for it, and the work directories of failed recipes stay for their caller to remove.

`etude-legacy` runs on Linux and macOS alone; `tests/run` calls it through `set`. Before it builds, it checks the suites and their commands, as `tests/run` checks them, and the hold, and not the host's free space. Its record lists the artifacts and not the sources they were made from, so a check finds an artifact changed or removed, and not one that a change of its sources has left out of date; a check by status also misses a change in place that keeps a file's size and time. A file that only a phony target's recipe makes, outside `components`, is neither built nor checked; in the tree now such recipes check the e2fsprogs programs, `check-e2fsck`, or boot a suite's machines, `dhcp-card`, `netif-card` and their `-stack` targets, and `make run-NAME` runs them as it starts the suite. `MAKEFLAGS` does not reach the steps, so a flag given to a make that runs the adapter, such as `-k`, does not apply to them.

`run` runs one suite at a time and takes no lock, so the tree, the host lock and the port block are its caller's to hold. A machine is recorded only when its suite starts it through a shim, by the name `qemu-system-i386` or `qemu-system-x86_64` on the path or through `RACH2_QEMU`; a QEMU started by its full path is seen only by the liveness check, as under `tests/run`. A machine that its suite signalled and did not wait for has five seconds to end, multiplied by `RACH2_DEADLINE_FACTOR` under scaled deadlines, and one that takes longer fails the suite, where the old pool passed it; a cut console, which the old pool did not look for, leaves the suite incomplete. The logs of a failure are kept in the work directory, which `set` places under `build/tests/failed` for `tests/run`. It has run a real suite on the Linux testing host alone; on macOS only its test has run, under TCG, so the choice of HVF has not run.

`set` admits the suites through the ledger it is given, and `tests/run` gives it a private one in the run's scratch, inside the claim of the whole machine that the installed launcher holds for each command. Two runs therefore do not share the machine between their suites: each holds the whole machine, and waits for the other, until the suites' claims are made in the machine's own ledger, with a port block each through `-d`. The driver's status record names the private ledger, whose claims the status command shows.

The set driver runs a guest case on a fresh machine of its profile and starts `etude-guest` from the kernel's debug shell, so a profile whose console does not reach that shell, or an image without `/etude-guest`, boots until the boot stage's bound or the case's. It runs no case of the `init` role, since the serial controller sends no `exec`; it does not find OVMF; it gives a guest case no standard input, local ports, forwards or fixtures but its workspace, `scratch` and `disk`; and it refuses the memory profile `bigmem-boundary-v1`. Ends other than `exited` and `signaled`, such as `panic` and `shutdown`, and scenarios are machine cases, which it does not run. Each attempt puts its artifacts in the run's store again, which reads each whole, and no store outlives its run, so the artifacts are copied again for every run. Guest cases run in its host test, on the tree's test image, and as `tests/run pools`, `authority`, `textbusy`, `fpu` and `noentropy`, on the test image, and `disk`, `disk-ahci` and `disk-q35`, on a disk of their own.

The proof driver runs on Linux and macOS alone, and has no Windows adapter. A person runs the catalogues of `tests/proofs/`; no suite does, and `tests/run style` checks only their texts. The proofs of the storage and image tests, and a few others, are `*_mutate.sh` scripts. The comparison of artifacts needs a build that makes the same bytes from the same sources, so a build that writes a time, a random name or the path of its `TMPDIR`, which differs in each phase, into its product cannot be proved by the driver. A shared proof killed with SIGKILL leaves its fault in the tree, with the saved sources in `WORK/saved`. The check of the run lock reads the owner file and the process it names, and does not check that the process is an ancestor of the driver. A test's failure is read from its exit status and its lines, not from report records.

`etude-host` reads no manifest and no report records. It judges a check by its exit status alone, takes its bound from the selection and not from the history, and records no history. It compiles each check's program again in every run, since a key in the artifact store would not cover the headers the program includes. It runs on Linux and macOS alone.

The tooling machine has run on Linux alone. It has not run on the Mac or on Windows, whose proofs are the owner's; on Windows nothing but `wincheck.sh` has run it, against stand-ins for QEMU, curl, `qemu-img` and mtools. A job there needs QEMU for Windows, curl and mtools on the `Path`, and etude-tooling takes its arguments, its environment and its paths in the ANSI code page, so a path that the code page cannot spell fails. On the testing host QEMU cannot open KVM, so the machine runs under TCG there: provisioning took from 10 to 29 minutes, as the host's load and Ubuntu's mirror allowed, and 810 to 1,210 processor seconds, with a peak of 3.2 GiB, and a job's boot takes about 65 seconds and 100 processor seconds, with a peak of 1.6 GiB, of which the job's own time is a few seconds. Provisioning needs the network, and installs the packages that Ubuntu's archive has that day, so two machines of one key may differ in their packages' versions, which their `.tools` files record. The job volume is FAT, so a file copied in or out keeps its name and its data but not its mode, its owner or a symbolic link. A step's processor time and memory are sampled on Linux and Windows alone. Nothing removes the machine of an older recipe or a job's kept directory, and a command killed by SIGKILL leaves its job's directory, or the partial disk of a provisioning, for a person to remove.

The formatter is not in a cached version. The boot traces each system call the kernel lacks, and an etude program that asks for one fails the suite. `tests/system/etudeexec_mutate.sh` proves it with three faults in a private copy of the files: the adapter not chosen on Rach2, a keeper never made a subreaper, and the recipe without `-D__rach2__`.

`tests/run host` also runs [`etude_bridge_hosttest.c`](../../tests/host/etude_bridge_hosttest.c). Private lock files exercise shared old runs beside new claims, distinct port blocks, exclusive access in both directions, exhausted blocks, native port bounds, the external wrapper's offset, registration and exit status, a command that waits with `-w` until a claim ends and then gives its own status 2 as `exited 2`, a wait that reaches its bound, which is `refused`, a stop signal during the wait, which is `stopped 15` and runs nothing, a command killed by a signal, which is `incomplete`, the diagnostic for a program that cannot start, a command admitted beside claims that hold more processors and disk than the capacity has left, and, on Linux, a killed controller whose executor confirms cleanup and a dead worker whose uncertain claim keeps its locks until an operator releases it. [`etude_bridge_mutate.sh`](../../tests/host/etude_bridge_mutate.sh) proves the lock and wrapper assertions with eleven faults in private copies, among them a request that does not wait, a request judged by its processors or its disk, a stop and an incomplete end recorded as other results, and a refusal recorded for a command's exit, with a pass before and after them. [`etude-bridge-diagnostics.json`](../../tests/proofs/etude-bridge-diagnostics.json) proves the missing-program diagnostic by removing it in a private copy. On Linux a fixture job starts through exec with a runner marker, checks that its controller and case are marked but its keeper and holder are not, and applies the runner's orphan sweep. It requires the case to end and its claim and locks to be released. [`etude-runner-cleanup.json`](../../tests/proofs/etude-runner-cleanup.json) proves the row by retaining either supervisor's marker and by using unsetenv without clearing the inherited bytes.

`tests/run host` also runs [`etude_ledgercmd_hosttest.c`](../../tests/host/etude_ledgercmd_hosttest.c), which runs `etude-ledger` in a child of itself on a ledger of real processes: a claim of its own, a request of its own that waits, a claim whose worker found its cleanup unconfirmed, one whose worker ended with no keeper's verdict, and one whose registered process still runs. The listing must give each with its status, its reason, its state, its owner, its processes and its resources, and count each status. Drops of the claim whose owner runs and of the claim whose process runs are refused, each naming what runs and leaving its claim; a drop of an identity the ledger lacks is refused; and a drop of an uncertain claim removes that claim alone. A wrong usage is refused, and so are a path that is not a ledger, which must not become one, and a ledger whose claims file does not parse, which must be left as it was. [`etude_ledgercmd_mutate.sh`](../../tests/host/etude_ledgercmd_mutate.sh) proves it with eleven faults in private copies of `posix/etude_ledger.c` and `ledger.c`: an owned claim dropped by the ledger, and reported dropped by the command; a live claim dropped, and its process left unnamed by the listing; a missing claim taken for an error; a drop never written; live and uncertain swapped; the reason left out; a request listed as a claim; every status counted as owned; and a path that is not a ledger opened. A pass comes before and after them.

`tests/run host` runs `tests/system/etude_launch_test.py` against private copies of the real build, worker, owner, CI and bisection entry points and the built bridge. Each build or test step must observe its registered, sized claim, the host lock and its own port block before execution. CI and owner transport steps release their claims between builds and tests. Two account identities running host selections must have two running claims and distinct port blocks; large-memory and serial selections wait until both finish. The fixtures check nested commands, an opaque shell or legacy command that claims an ordinary selection's share, a port block already occupied, an old checkout, owner quoting, input and exit status, unavailable or incompatible configuration, a policy that permits the lazy boundary profile and one whose `boundary_lazy` names another, port overrides, contention and cancellation with released claims. `tests/proofs/etude-launch.json` proves these assertions with faults in the private launch hooks and policy handling. The bridge host test separately proves uncertain cleanup retains claims and locks.

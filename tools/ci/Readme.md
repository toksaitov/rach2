# Release tests

`tools/ci/` runs the release tests on GitHub Actions: every suite of both architectures, with the in-house code built from clean and the vendored and GNU builds taken from the host's store where it has them, at the commit that a release names, on the self-hosted runner of the one machine that the commit's `site` selects. [`tools/flow/release.sh`](../flow/release.sh) starts the workflow, [`full.yml`](../../.github/workflows/full.yml), as one step of a release and reads its failures. Nothing runs on a push.

## Use

`full.yml` is started by hand or by release.sh with `gh workflow run full.yml --ref BRANCH -f sha=SHA [-f title=TITLE] [-f suites='ARCH:SUITE ...']`. BRANCH is the milestone's branch, so that the workflow is the one that goes with the scripts at SHA. `sha` is the commit's whole hash; `suites`, when given, limits the run to those suites, as release.sh asks when it runs again only what failed. The workflow checks the inputs, reads `site` at SHA, and then on the selected runner:

* `run.sh full OUT` cleans and builds both architectures and runs their suites as one run of `tests/run`, `bigmem` after it as a run of its own, or only the `ARCH:SUITE` words of `SUITES`. An architecture that `SUITES` names nothing of is not built and is `skipped`. It writes `OUT/full-ARCH/` for each architecture: `log`, `err` (the standard error of tests/run, without the other architecture's lines), `failed` (one name a line: a suite, `build`, `runner`, or `all` or `bigmem` for a run that failed without naming a suite), `kept` (the kept logs of failed cases), and `done` once the run has finished. A TERM stops the run without `done`.
* `report.sh SHA OUT FILE` writes FILE with one line `ARCH:ITEM` for each failure, ITEM being a name of `failed`, `runner` for a failure that only the native verdict found, or `unfinished` for an architecture without `done`, and gives each architecture's result, the first lines of `err` that name a failure and the command that fetches its logs in the job's summary. It exits 1 when anything failed.

`site` has one line `runner LABEL`, the label of the runners of the machine that runs the tests, and one line `accelerator NAME`, which the workflow puts in `RACH2_QEMU_ACCEL`; `site.sh` checks it and prints it as the workflow's outputs. etude's routine entry reads the same file.

## Results

A run keeps, for 14 days, the artifacts `failures` (FILE above, which release.sh fetches with `gh run download ID --name failures`), `full-i686` and `full-x86_64` (each architecture's directory), and with the native entry `full-native-evidence`. The run's conclusion is `success` only when both architectures passed. The workflow files no issue and sets no commit status.

## Design

### What a release builds

`run.sh` runs `make clean` and then `make` for each architecture with the host's store of step outputs ([etude's Readme](../etude/Readme.md#the-step-store)), `/var/cache/rach2-store` on the testing host, as every other copy there builds. `make clean` removes the kernel, the guest programs, the host tools and the images, so a full run builds them from the commit's sources. The vendored projects and the GNU layer are steps of the store: a step whose key, the SHA-256 of its record, has an entry takes that entry's outputs, made by the first copy that built the key, and runs no recipe; a step with a new key is built into the store, where the copies after it find it. A runner copy whose GNU layer was built in the copy, without the store, loses it to the first make that uses a GNU target, which then takes each step's links from the store ([vendor/gnu/Readme.md](../../vendor/gnu/Readme.md)).

A release therefore proves that the commit's in-house code builds and that every suite passes on the outputs the store gives. It takes as built each vendor and GNU step whose architecture, platform, compiler identities, input files and used steps' keys are those of an entry: that the recipe builds from its tarballs was shown by the build that made the entry, not by the release. What the key does not count, such as a host program the recipe runs that is not one of its compilers, or the environment, may differ between that build and a fresh one without the release seeing it. A changed recipe, pinned tarball or host compiler, or a used step built again, changes the key, and the release builds the step. `RACH2_STORE= sh tools/ci/run.sh full OUT` builds every step in the copy instead.

### The native routine entry

The current `run.sh` selects `results=lines`, the existing entry, until T95 activates the selected native site. full.yml allocates a temporary result directory for that entry and retains each architecture's ordinary logs. Activation changes the selection to `results=native` after installing the site policy, reference costs, evidence retention and reporting reader. Native allocation and reporting then require those installed inputs and never fall back when one is absent. A compatibility check is not native-site acceptance. The existing entry directs failed-case evidence to its own `kept` directory through `RACH2_FAILED`; collection does not depend on filesystem timestamp resolution.

`etude run routine push OUT SUITE...` checks explicit affected suites, including `ARCH:SUITE` operands. Only the installed `ETUDE`, the program on the site's `etude` line, runs it; the entry refuses any other copy. It accepts the native selector's `RACH2_CASES`, `RACH2_AGENTS_ROWS` and `RACH2_ACCEPT_AGENTS` filters. The public allocator exports the complete selected case, architecture and repetition set before execution. `check verdict --selection EXPORT --require-budget` requires exactly those planned items and their selection digest, while still checking every result and the current manifests. CI and release refuse inherited case filters and retain whole-suite coverage.

The commit's `site` selects the Actions runner label and accelerator. Activation supplies the installed `ETUDE_SITE` version-two admission policy and immutable `ETUDE` outside mutable build outputs. The native routine site reader checks its endpoint, paths, ledger, capacity and time bounds. The selected profile also fixes `JOBS`, `RACH2_WORKERS`, `RACH2_CPUS` and `RACH2_MEMORY_MIB` where needed. The machine's ledger bounds aggregate reservations even when more workers are configured. Changing a site or restarting its services waits for accepted jobs and their cleanup; this code does neither.

`etude run routine` selects the collection and projects its final C verdicts. `etude run routine-sequence` gives preparation and execution to the existing native phase owner. Preparation has its own admitted claim, released before case admission. `etude prepare routine` writes `prepare.record`, `preparation.receipt.json`, `selection.list`, `selection.export.json`, source snapshots and `context/context.json`. The observer spans the first grant through cleanup. The native execution starts no shell, interpreter or build. Preparation may use the existing build programs.

The entry remains a native process while its sequence runs. The existing C executor checks its parent's PID and creation identity and owns every child through cleanup. The CI shell replaces itself with the native entry; no logging pipeline or shell phase owner intervenes.

An installed physical route uses `ETUDE_ROUTINE_ROUTE`. Before reading a disabled endpoint's policy, the entry asks the fixed installed authority to verify the route and policy identities. The entry then dispatches the same purpose, architecture and selection to the route owner. Direct WSL execution keeps its own `linux.log` and `linux.sequence.receipt`, separate from the physical owner's log and receipt. After cleanup, both architecture verdicts require the terminal record named by the single absolute path in `routine-completion.path` and its retained `routine-proofs` directory. After the route owner returns, entry copies the final history and its completion proof closure before judging either architecture. A missing or malformed completion, or an incomplete proof copy, is a runner failure.

The purposes `push`, `ci` and `release` have 300, 600 and 14400-second charged ceilings and 30, 60 and 600-second cleanup reserves. The full goal is 3600 seconds with another 3600 for growth. A routine invocation has no first-measurement exemption. Its C verdict refuses an unknown, failed or missing budget. Preparation, transfer, verification, native compilation, context composition, execution and cleanup remain inside the same charged interval.

### Release preparation and imported products

Release preparation sets `ETUDE_PREPARATION_CLEAN=1`. The C preparation removes these products inside its tree lock and lifetime. It removes in-house component, kernel variant, image, checker and test products for the selected architectures, including the guest probe names declared by `tests/Makefile`. It retains vendor builds and their dependency checks, tooling/download/source-judge caches, unrelated failed-run evidence and the current output directory. A changed vendor recipe still invalidates its ordinary keyed build. It does not run `distclean` or erase a store.

`ETUDE_PREPARATION_IMPORT` is an optional absolute configuration for the fixed producer-import adapter described in [etude's preparation contract](../etude/Readme.md). The C preparer validates it, owns its commands, writes the final local record and same-run receipt, and removes the input from subordinate builds. The native owner also clears the import and clean inputs before execution. Staged producer inputs must stay outside in-house product directories that the release cleans. `OUT` itself is preserved.

An admitted Linux preparation may set `ETUDE_PREPARATION_EXPORT=1` to write `OUT/producer.json` with the fixed exporter. This validates the successful selected producer record and its ordinary production receipt; it starts no build or transfer. Export failure prevents collection. Its verification remains in the contiguous charged interval. Importing a previous Linux product does not make that production one-time setup. Retain its own receipt and report the upstream production cost separately from the local import/build/run interval; do not combine unrelated monotonic clocks or count one producer invocation as five independent measurements.

`etude prepare producer OPERATION.json` performs the fixed operations in an existing responder workspace: source projection, fresh production, authority freeze, restore, facts and transport cleanup. It reads the same route, nonce and candidate bundle, retains the real repository lock and admission, and invokes the native collection preparer and exporter. Every sample has a new output directory; the exact clean candidate can reuse its vendor and compiler caches. The accepted-job check compares GitHub state before and after reading current-boot listener logs. Missing boot evidence, an unfinished accepted job or a changed server snapshot refuses an authority transition. Transport cleanup requires the actual zero-status admission receipt and absence of both the producer claim and its child claims.


### Reference costs

`ETUDE_REFERENCE` names an immutable version-one JSON object with `format: "etude-site-reference"`, `schema_version: 1`, `policy` and a nonempty `histories` array. Each descriptor has absolute `path`, `sha256` and `size_bytes`. The policy follows etude's budget schema. Activation supplies measured reference data for the selected machine; this repository supplies no invented site costs.

During routine preparation, `etude prepare reference` verifies every referenced byte and the actual machine, endpoint, accelerator and capacity. It calls the native `etude estimate forecast` over every current manifest in the release class. Windows has the same C command. The report gives the goal, growth, ceiling, expected preparation and cases, and any unknown or failure. Missing costs fail this check; the completed run's budget is a separate judgement. `reference.forecast` and its receipt retain the command, selected reference descriptors, status and log hash.

A native plan includes a hash-bound `etude-preparation-nodes` document beside its artifact record. It declares the complete deduplicated goal set, selected architectures and kernel override. Forecasting may use the actual aggregate preparation step once when that complete set and its architecture flags match, the run and cleanup passed without disruption, continuous-load evidence is eligible, and the samples share the selected site and newest matching operating-system, tools and cache context. An unknown or different set cannot borrow that cost. Older per-node measurements retain their original path. No aggregate duration is divided into unmeasured node costs. The selected site's baseline histories and all their referenced proof bytes must remain available for reference checks.

A release preparation cost also requires the actual receipt's `conditioning.inhouse` to be `clean`. A retained `phase_first_run` may establish a comparison baseline, but cannot supply a clean release preparation cost. A first-measurement invocation may explicitly set `ETUDE_PREPARATION_CLEAN=1` and use the installed ordinary route with a fresh clean producer for each imported sample. Its public preallocation is checked before production and remains exact through the physical handoff. Five such whole samples can provide comparison and clean-release reference evidence without a sixth whole run. Older receipts without conditioning remain unknown for release forecasting. The preparation adapter records `retained` unless its clean-in-house step completed. This preparation condition is separate from the measured cache state.

An imported preparation binds its original provenance by hash in the local receipt. Portable goals require a successful clean ordinary producer receipt; native goals and inventories require the actual clean local build. Cleaning the destination does not make a retained producer clean. Forecasting retains both events and uses each recorded interval without adding an earlier producer's elapsed time to the local sample.

### Shared evidence and reporting

`etude prepare evidence stage RESULTS NEW_DIRECTORY` copies the common history, blob store, context, receipts and logs and records each file's hash and size. It excludes executable artifact objects and per-architecture projections, which are uploaded separately. `restore SOURCE RESULTS` verifies every file before creating any destination file and refuses overwrites. `etude prepare evidence pack OUT [ROOT...]` uses the same copier to retain the late finalized routine proof closure. It accepts existing matching proof objects, refuses changed or ambiguous proofs and preserves original locators. full.yml's reporter runs in the execution job, beside the results, and the job uploads the staged copy as the artifact `full-native-evidence`.

The reporting host supplies its own absolute `ETUDE_REPORT_READER` (or `ETUDE`) and `ETUDE_REPORT_READER_RECORD`. The latter is a trusted local `etude-prepare 1` record containing that exact installed executable once, with its SHA-256 and size. `etude prepare reader PROGRAM RECORD` hashes it before execution; its native `check record -d` then verifies the record. The reporter never chooses or executes an uploaded producer executable. The installed reader must implement the current native history and budget contracts. Missing shared history, changed evidence, an unverified reader or an unknown budget becomes a runner failure for both architectures.

Site activation updates the selected runner and its environment together. The release builds and installs on the Lenovo only after the full run passes; installation and trial acceptance remain separate release steps.

### Retained routine evidence

Activation supplies `ETUDE_RETENTION`, an absolute selected-site policy, as well as the admission site and measured reference. `etude prepare retention` is native preparation and administration code. It starts no case. Its version-one `etude-retention-policy` document has `root`, the exact admission-file `site_sha256`, positive integer `max_bytes`, `max_age_days`, `reserve_bytes` and `issue_snapshot_max_age_seconds`, `baselines` (protection descriptors), `anchors` (immutable external proof descriptors), and `open_issues` (a snapshot descriptor, or null while its contents are uncertain). Descriptors give absolute `path`, `sha256` and `size_bytes`. Activation chooses the limits from the selected machine's available storage; there is no implicit unlimited policy or invented measured baseline.

The persistent root must be new, outside disposable checkouts and free of symlink parents. Initialize it once, then allocate each output before invoking the ordinary entry:

    etude prepare retention --policy "$ETUDE_RETENTION" --site "$ETUDE_SITE" init
    etude prepare retention --policy "$ETUDE_RETENTION" --site "$ETUDE_SITE" allocate --reference "$ETUDE_REFERENCE" > new-output.path
    IFS= read -r out < new-output.path
    "$ETUDE" run routine push "$out" host

full.yml uses the allocator's `--github-env` output, `ETUDE_RESULTS`, for execution, result projection and staging. An arbitrary or previously used output is refused by native entry. No symlink or post-run relocation is involved: the original absolute history and observation locators remain valid in the persistent bundle. Actions artifacts are reporting copies with their existing expiration, not the retained source of accepted references or issue evidence.

The registry records a reservation before entry. Active, interrupted, failed, changed or incomplete bundles remain protected. A bundle becomes ordinary only after the actual sequence receipt confirms preparation and collection cleanup, the routine verdict passes, and complete terminal history and its reachable blobs are present. Sealing hashes every bundle file, including executable artifact objects. The byte account includes every file under the managed root, unknown objects, external proof bytes and the unused part of each active or uncertain reservation. It uses logical file sizes, conservatively counting sparse files at their full length. Reservations reserve retention capacity, not a disk quota; an unexpectedly larger run is kept and prevents further allocation until the excess has been resolved. Native registry updates record last use as whole epoch seconds rounded upward. Existing fractional values are read through the external-data JSON reader; when one is updated, its original numeric token remains as `last_used_previous` with `last_used_normalization: "ceil-epoch-seconds-v1"`. Expiration uses a current time rounded downward, so this normalization cannot shorten the one-day protection. Strict contract JSON remains unchanged.

A blob reference with `sha256`, `size_bytes` and `locations` retains reachable bytes with that digest, recursively including observation traces. Input path/hash lists in copied source, compiler and import provenance describe the inputs used; they are not additional blob references unless a history reader dereferences them. True proof locations outside registered bundles need explicit immutable anchors. Missing or changed proof bytes prevent ordinary sealing. Accepted selected-site reference descriptors are copied into the registry and retain their histories, policies and proof closure. A policy's additional baseline descriptor has `format: "etude-retention-protection"`, `kind: "baseline"` and nonempty descriptor `roots`. There is no age-based removal of accepted references.

An administrator refreshes open-issue protection with `etude prepare retention issues --repository toksaitov/rach2 --mapping MAPPING --output NEW_SNAPSHOT`. The mapping is an object whose issue-number keys give explicit evidence-root descriptor arrays; an empty array explicitly states that the issue has no registered run evidence. The read-only GitHub query captures all open issues and their comments, hashes their exact snapshots, and verifies every mapped proof closure. The resulting `etude-retention-open-issues` descriptor is placed in the policy. Missing mappings remain unknown. An absent, stale, damaged or unknown protection snapshot protects every existing bundle and forbids pruning. Another run is allowed only if that protected storage plus its reservation still fits; otherwise allocation reports the excess and requires a refreshed protection snapshot or a larger explicit policy. Closing an issue never removes an accepted baseline.

`etude prepare retention ... prune` reports candidates without deletion; `prune --apply` and allocation may remove only unchanged, sealed ordinary bundles. Both operations hold the same OS file lock as registration and routine proof readers. Before actual deletion they revalidate the live open-issue set and update timestamps against the snapshot. A changed set, authentication error, unavailable GitHub or a query exceeding 30 seconds prevents deletion; allocation can still use spare capacity without pruning. Allocation that has no deletion candidates makes no network query. Age removal and byte-pressure removal require at least one day since sealing and the last recorded use or file change. A referenced bundle protects its older dependencies. Pruning removes an entire owned bundle and its registry entry together, never individual blobs from a retained run. Unknown directories are counted and kept. Flow's scratch and leftover cleanup also keeps a marked retention root. The focused fixture `etude_platform_hosttest --retention-only` uses only temporary owned bundles; it exercises closure, protection, limits, concurrent allocation and refusal without touching production evidence.

A physical Windows/WSL routine owner retains `routine.grant.json`, `routine.lease.json`, optional `routine.upstream.json`, `routine.completion.json` and the caller-readable completion locator in `routine-completion.path`. Its completion follows actual process and observer cleanup. The shared evidence stage follows their hash references into a `routine-proofs` directory and retains packing errors without discarding failed-run evidence. The reporting job uses its own native C reader with the explicit completion and proof directory. Missing proof, an unknown terminal budget or an incomplete physical lease fails the report. No uploaded executable is used as a reader.

[Routine route provisioning](routine-route.md) describes the fixed physical authority, fresh producer event, retained proof files and selected-site activation checks.

## Tests

The host cases of [`tests/cases/host/host.list`](../../tests/cases/host/host.list) drive the scripts with compiled stand-ins for GitHub, Git, make and tests/run: `ci_run` (`flow_ci_run.c`) runs `run.sh` on lines, kept logs and killed steps, `ci` (`flow_ci.c`) runs `report.sh` on finished, unfinished and native results, and `release_resume` (`flow_release.c`) runs tools/flow/release.sh. The routine contract tests run in the existing native platform fixture, `etude_platform_hosttest --routine-entry-only`. The fixture keeps the input validators, preparation ordering, sequence vectors and result projections in C and substitutes only their lower-level process boundaries. The listener fixture and `etude_producer_hosttest` keep their separate accepted-job, boot-revalidation, fresh-workspace and clean-condition checks, and `etude_route_hosttest` the fixed route actions.

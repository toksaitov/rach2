# Routine native checks

`run.sh core OUT` prepares and runs style, host and the core tier. `run.sh full OUT` runs every suite on the architectures that `ARCH` selects. `ARCH='i686 x86_64'` gives both architectures one schedule. For a release repair, `SUITES='i686:NAME x86_64:NAME'` retains the exact failed-suite selection. Only the selected architectures are prepared.

`push.sh OUT SUITE...` checks explicit affected suites, including `ARCH:SUITE` operands. It accepts the native selector's `RACH2_CASES`, `RACH2_AGENTS_ROWS` and `RACH2_ACCEPT_AGENTS` filters. The public allocator exports the complete selected case, architecture and repetition set before execution. `check verdict --selection EXPORT --require-budget` requires exactly those planned items and their selection digest, while still checking every result and the current manifests. CI and release refuse inherited case filters and retain whole-suite coverage. A documents-only check keeps its separate document-check command; selecting a site does not turn it into a core run.

The commit's `site` selects the Actions runner label and accelerator. Activation supplies the installed `ETUDE_SITE` version-two admission policy and immutable `ETUDE` outside mutable build outputs. `native_site.sh` checks its endpoint, paths, ledger, capacity and time bounds. The selected profile also fixes `JOBS`, `RACH2_WORKERS`, `RACH2_CPUS` and `RACH2_MEMORY_MIB` where needed. The machine's ledger bounds aggregate reservations even when more workers are configured. Changing a site or restarting its services waits for accepted jobs and their cleanup; this code does neither.

`native_sequence.sh` gives preparation and execution to the native C phase owner. Preparation has its own admitted claim, released before case admission. `native_prepare.sh` writes `prepare.record`, `preparation.receipt.json`, `selection.list`, `selection.export.json`, source snapshots and `context/context.json`. The observer spans the first grant through cleanup. The native execution starts no shell, interpreter or build. Preparation may use the existing build programs.

The purposes `push`, `ci` and `release` have 300, 600 and 14400-second charged ceilings and 30, 60 and 600-second cleanup reserves. The full goal is 3600 seconds with another 3600 for growth. A routine invocation has no first-measurement exemption. Its C verdict refuses an unknown, failed or missing budget. Preparation, transfer, verification, native compilation, context composition, execution and cleanup remain inside the same charged interval.

## Release preparation and imported products

Release preparation sets `ETUDE_PREPARATION_CLEAN=1`. The fixed `clean_inhouse.py TREE ARCHES OUT` runs inside the preparation's tree lock and lifetime. It removes in-house component, kernel variant, image, checker and test products for the selected architectures, including the guest probe names declared by `tests/Makefile`. It retains vendor builds and their dependency checks, tooling/download/source-judge caches, unrelated failed-run evidence and the current output directory. A changed vendor recipe still invalidates its ordinary keyed build. It does not run `distclean` or erase a store.

`ETUDE_PREPARATION_IMPORT` is an optional absolute configuration for the fixed producer-import adapter described in [etude's preparation contract](../etude/Readme.md). The C preparer validates it, owns its commands, writes the final local record and same-run receipt, and removes the input from subordinate builds. The native owner also clears the import and clean inputs before execution. Staged producer inputs must stay outside in-house product directories that the release cleans. `OUT` itself is preserved.

An admitted Linux preparation may set `ETUDE_PREPARATION_EXPORT=1` to write `OUT/producer.json` with the fixed exporter. This validates the successful selected producer record and its ordinary production receipt; it starts no build or transfer. Export failure prevents collection. Its verification remains in the contiguous charged interval. Importing a previous Linux product does not make that production one-time setup. Retain its own receipt and report the upstream production cost separately from the local import/build/run interval; do not combine unrelated monotonic clocks or count one producer invocation as five independent measurements.

## Reference costs

`ETUDE_REFERENCE` names an immutable version-one JSON object with `format: "etude-site-reference"`, `schema_version: 1`, `policy` and a nonempty `histories` array. Each descriptor has absolute `path`, `sha256` and `size_bytes`. The policy follows etude's budget schema. Activation supplies measured reference data for the selected machine; this repository supplies no invented site costs.

During routine preparation, `reference.py` verifies every referenced byte and the actual machine, endpoint, accelerator and capacity. It calls the native `etude estimate forecast` over every current manifest in the release class. Windows has the same C command. The report gives the goal, growth, ceiling, expected preparation and cases, and any unknown or failure. Missing costs fail this check; the completed core run's budget is a separate judgement. `reference.forecast` and its receipt retain the command, selected reference descriptors, status and log hash.

A native plan includes a hash-bound `etude-preparation-nodes` document beside its artifact record. It declares the complete deduplicated goal set, selected architectures and kernel override. Forecasting may use the actual aggregate preparation step once when that complete set and its architecture flags match, the run and cleanup passed without disruption, continuous-load evidence is eligible, and the samples share the selected site and newest matching operating-system, tools and cache context. An unknown or different set cannot borrow that cost. Older per-node measurements retain their original path. No aggregate duration is divided into unmeasured node costs. The selected site's baseline histories and all their referenced proof bytes must remain available for reference checks.

## Shared evidence and reporting

`native_evidence.py stage RESULTS NEW_DIRECTORY` copies the common history, blob store, context, receipts and logs and records each file's hash and size. It excludes executable artifact objects and per-architecture projections, which are uploaded separately. `restore SOURCE RESULTS` verifies every file before creating any destination file and refuses overwrites. Core's separate report job restores this common evidence before reading either architecture. Full retains the same common artifact even though its reporter runs in the execution job.

The reporting host supplies its own absolute `ETUDE_REPORT_READER` (or `ETUDE`) and `ETUDE_REPORT_READER_RECORD`. The latter is a trusted local `etude-prepare 1` record containing that exact installed executable once, with its SHA-256 and size. `native_reader.py` hashes it before execution; its native `check record -d` then verifies the record. The reporter never chooses or executes an uploaded producer executable. The installed reader must implement the current native history and budget contracts. Missing shared history, changed evidence, an unverified reader or an unknown budget becomes a runner failure for both architectures. Old commits keep their historical reporting and bisection paths.

Site activation updates the selected runner and its environment, the affected-check transport used by workers, and their instructions together. The release still builds and installs the reviewed candidate on the Lenovo only after the selected site's required full check. Installation and trial acceptance remain separate release steps.

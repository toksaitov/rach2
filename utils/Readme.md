# OS Utils

![List of Rach2 Utilities](https://raw.githubusercontent.com/rachmiroff/images/refs/heads/main/rach2/utils.png)

Minimal implementations of core Unix utilities in C for 32-bit x86. Each utility is an ordinary hosted C program linked statically against the ported musl libc (see [vendor/musl/](../vendor/musl/)): it uses the real standard headers (`<stdio.h>`, `<unistd.h>`, `<fcntl.h>`, `<dirent.h>`, `<sys/socket.h>`, ...), musl's `crt1` startup, and libc's syscall wrappers. The hand-rolled `int $0x80` stubs and `crt0.c` were dropped in the musl port. (`resolv.c`, the stub resolver, is shared by `ping`, `nc`, and the `dnstest` test, all linked against the same musl. It reads `/etc/resolv.conf` and `/etc/hosts` when they are there and the flat `/resolv.conf` and `/hosts` otherwise: both shipped images stage a real `/etc` and the flat test image stages neither, so a resolver that must work under all of them looks in both places, in that order.)

Built for the Rach2 kernel with `make` against `../vendor/musl/install` (run `vendor/musl/build_libc.sh` once first). A separate `Makefile.linux` builds them natively on Linux, out of tree into `build/utils/linux/`.

## Utilities

* `true.c`: Returns exit code 0
* `false.c`: Returns exit code 1
* `echo.c`: Prints arguments separated by spaces, followed by newline
* `yes.c`: Repeatedly outputs "y" or provided arguments indefinitely
* `cat.c`: Concatenates files to stdout; reads stdin if no arguments
* `pwd.c`: Prints current working directory
* `touch.c`: Creates files or updates timestamps
* `mkdir.c`: Creates directories
* `rm.c`: Removes files; supports `-r` for recursive directory removal
* `mv.c`: Moves/renames files
* `cp.c`: Copies file contents
* `ls.c`: Lists directory entries, each with its type flag and a fixed `rw-` placeholder rather than its real mode, since it does not `stat` them
* `ping.c`: Sends ICMP echo requests via the SC_PING socketcall (`ping [host]`, default gateway 10.0.2.2); `host` may be a dotted-quad or a name. It is not a drop-in `ping`: the echo and the wait both happen in the kernel, there is one in-flight request for the whole machine, and it sends four. That single slot is the raw-socket non-goal made visible to users, since with a real `SOCK_RAW` each caller would own its own socket, and it is why a second caller gets `EBUSY` rather than a queue: a queue needs a fairness rule to give a shell command a wait it cannot see. So a ping at a dead address holds the slot for about four seconds and refuses everyone else for that long, and this program prints `ping: another ping in flight` and stops rather than counting the refusal as a timeout, which would report a live host as dead. `SC_PING` returns ticks, `-ETIMEDOUT`, `-EBUSY` or `-EINTR`; the timeout used to be a bare -1, which musl's return convention decodes as `EPERM`.
* `nc.c`: Minimal TCP client (`nc <host> <port>`); relays a line of input and prints the reply over the socket descriptor; `host` may be a dotted-quad or a name
* `httpd.c`: Minimal HTTP/1.0 server serving a diagnostic status page (the client endpoint, the request line and User-Agent the stack decoded, uptime and per-connection counters; listen on port 80, reach it via QEMU hostfwd)
* `dhcpc.c` (with `dhcpmsg.c`, the message library): the DHCP client for the image that has no busybox. os-real takes its address with busybox's `udhcpc`; this is the same job in this project's own code, over the same kernel interface, so the two machines behave the same way on a network. `dhcpc [-i INTERFACE] [-b] [-l SECONDS]`, and `dhcpc -i INTERFACE -k` to stop the client that holds one. Everything it sends it builds: an IP header, a UDP header and a BOOTP message with both checksums, sent through an `AF_PACKET/SOCK_DGRAM` socket, because a server answers a machine that has no address by broadcasting and a machine with no address cannot receive through the IP layer at all. It runs the discover, request and acknowledge exchange, applies the address, the netmask and the default route through the `SIOCxIF*` ioctls, writes `/etc/resolv.conf` from the lease by replacing it rather than editing it, then holds the lease: it renews to the granting server at T1, rebinds by broadcast at T2, and when a lease finally runs out it takes the address off and starts again, because an address whose lease has expired belongs to somebody else now. A server that names its own T1 and T2 is followed where the pair is in order and inside the lease, and RFC 2131's half and seven eighths are used where it is not. No lease is acted on for longer than a week whatever the server says, since the infinite lease of 0xFFFFFFFF overflows the arithmetic the timers are made of; `-l` lowers that cap, which is how the renewal path is exercised on a network that hands out days. There is no configure-once mode, deliberately: a client that applied a lease and exited would leave an address on the interface with nothing to take it off when the lease ended, and the machine would go on answering for an address the server had since given to somebody else. With `-b` it stays in the foreground until the first answer, so whatever started it learns whether the machine is configured, and then goes to the background (through `setsid`, so the end of a login session does not take the lease with it) and holds the lease. A boot that finds no server backgrounds too rather than giving up, because a machine that gave up is one nobody can reach until somebody walks to it, and walking to it is what the sealed machine exists to avoid. One client per interface, recorded in `/var/run/dhcpc.INTERFACE.pid`: the claim is made with `O_CREAT|O_EXCL` and the pid written inside that descriptor, so a claim is never a file with nothing in it, a second client is refused by name, and a claim naming a process that is gone is read once more and then removed and taken. A client reads the claim again before it configures the interface and before every renewal it applies: another live client named there and it leaves the interface alone, without removing a claim that is not its own; a claim that has simply gone it writes again, since it is still the client the address is configured for and walking away would leave an address with nobody to take it off. That is a check and not a lock, because this kernel grants every `fcntl` lock unconditionally, so there is no lock here to take; one administrator at a time is the contract, as it is for `bootctl`. TERM, INT and HUP are answered rather than taken as they come: the handler sets a flag, the poll returns, and the client leaves through the same door every failure leaves through, which takes the address off and drops the claim. That is what `-k` is for, since a leased address cannot be replaced by a fixed one while something is renewing it. A lease is judged whole before any of it is applied, through `ipcheck.c` below, and one that cannot be applied is treated as no answer at all: the client goes on asking rather than giving up on a network whose server said something wrong once. Of everything above, the half that needs no system call is `dhcpmsg.c`: the framing, the checksums, the option parsing and the lease arithmetic, driven by `tests/host/dhcpmsg_hosttest.c` with the messages a server will not produce on request.
* `netup.c` (with `netcfg.c`, the configuration reader): `ifup -a` for the machine that has no busybox. It reads the same `/etc/network/interfaces`, in the same format, so one description of a network serves both images: `auto NAME` lines, and `iface NAME inet dhcp` or `iface NAME inet static` with `address`, `netmask` and `gateway`. `netup [-a] [INTERFACE ...]`; a named interface is brought up whether or not `auto` names it. The file is read in two passes over one open, because it does not have to be in a helpful order and a machine that noticed only the stanzas it had already seen an `auto` line for would configure itself differently depending on how somebody arranged the file. A line longer than the buffer is refused rather than split, since a split line is two directives and the second is whatever the first happened to end in; a method this does not implement (`manual`, `ppp`, `loopback`) is refused rather than taken for static, which would configure a machine in a way nobody asked for; and a name longer than an interface field is refused, since it would be stored cut and looked for whole. A `dhcp` stanza runs `dhcpc -b`. A `static` stanza is judged whole before any of it is applied, by the rules the kernel will judge it by: changing the address ends every connection the machine has, so a stanza that was going to fail at its last line must fail before its first, or the way in is cut off for nothing. It refuses a stanza with no netmask, one whose netmask is not a run of ones, an address that is its subnet's network or broadcast address, and a gateway that is not a host on that subnet. It also refuses to configure an interface a DHCP client is holding, naming the process and how to stop it, since a static address applied under a live client is undone by that client's next renewal. What it does apply it can put back: the address and netmask in force are read first and restored if a later step fails, and the old default route is cleared before a new one is added. `netcfg.c` is the reading and the judging of the file, with no system call in it, driven by `tests/host/netcfg_hosttest.c`. os-simple has no editor, so it stages `/etc/network/interfaces.static` beside the file it uses: copying that over and running `netup -a` is how the machine is moved to a fixed address, and it is the second half of a format the image would otherwise only ever show one half of.
* `ipcheck.c`: the one judgement of whether an IPv4 configuration is one a machine can hold, linked into both `netup` and `dhcpc`. A static stanza an administrator wrote and a lease a server sent are the same question, and two copies of the rule would be two answers waiting to differ. It refuses an address whose first octet is 0, 127, or 224 and above, for the address and for the gateway alike, because the kernel does; a netmask that is not a run of ones, and one with no room for a host; an address that is its subnet's network or broadcast address; and a gateway that is not a host on the subnet the address is on. Where no netmask is given it judges under the mask the kernel will derive from the address, since that is the mask the machine will be running with. The refusal is a sentence the caller prints in its own voice, so a test can tell one refusal from another.
* `su.c`: The reference su (`su [-] [-l|--login] [user] [-c command]`, user defaulting to root): a setuid-root program that authenticates the target's `/etc/shadow` password through the credential library below (root exempt), drops to the target's group and then user, sets a minimal environment, and execs their shell. It is os-simple's way up, staged there at 04755 beside `passwd`, and it is what os-real used before that image took its account tools from busybox: the two now stand side by side, the same job in this project's code and in the code a real system ships, which is what having two images is for. Making a whole busybox setuid instead would run every one of its setuid-requiring applets as root unless a config file confined them, a path that tripped a busybox use-after-free the kernel's strict `munmap` faults (see `dev-log/15-privilege`); os-real's answer is busybox's own, a second binary holding only `login`, `passwd` and `su` with the bit on that one alone. A bare `-`, `-l` and `--login` select login mode, which is three things: the target's home becomes the working directory, `argv[0]` becomes a `-` followed by the shell's base name (`-sh` for `/bin/sh`), which is how a shell here is told it is a login shell, and the environment is the one su builds from nothing either way. A home that cannot be entered is fatal, since the directory and the dash are the whole of `-`. Any other unrecognized option is a usage error rather than a silently discarded argument. Non-login mode is unchanged, working directory and `argv[0]` included. The PAM/login.defs policy layer stays a non-goal.
These sources are also STAGED, into os-real at `/src/utils`, so the machine can build them on itself: `tcc -static -o /tmp/cat /src/utils/cat.c` at that machine's own prompt produces a working `cat`, and `make tcc-test` proves it by running the result against busybox's `cat` over the same file and requiring the same bytes out. They are not the same binary and are not meant to be, since the shipped one was linked against libgcc on the host and the new one against `libtcc1.a` on the machine. `guest.mk`, staged beside the sources, is the whole set as one build: a POSIX makefile pdpmake reads in the guest (`make -f guest.mk`), one hosted `cc -static` link per program with the same per-program source map as the Makefile here, the companion sources (`pwauth.c`, `resolv.c`) and the two `-D` builds included. `tools/check_guest.py`, inside the verify gate, holds the two maps equal, so a source added here without its `guest.mk` half fails on the host.

The privilege family (`init`, `su`, `sudo`, and whatever else climbs or has authority) builds into `build/utils/sbin/` rather than beside the ordinary tools. The reason is the os-simple manifest's `exec-dir 0755 /bin build/utils`, which stages every regular file directly in that directory and skips subdirectories: a program left at the top level is staged into every image that sweeps, whether or not that image has the `/etc` it needs to authenticate against, and whether or not anyone chose to ship it. A subdirectory makes shipping a privileged program a deliberate act, one `file` line naming it, which is also what lets `tools/check_setid.py` hold a complete allowlist of the set-id paths in each image rather than a sample of them.

The sweep is pruned before each build for the same reason. The build is out of tree and incremental, so a binary an earlier build left in `build/utils` (one since renamed, dropped, or moved into `sbin/`) would go on being staged from a tree that no longer builds it; `make -C utils` removes anything that is not a current target first, at both levels. `sbin/` is swept too, and for a reason: its contents are staged by name, so a stale binary there is only reachable through a manifest line naming it, and `check_setid.py` compares a manifest's declared source against its own table without ever stat-ing the host file. A rename that missed one manifest line would go on staging the old binary with nothing reporting it.

* `bootctl.c` (with `bootslot.c`, `bootverb.c` and `grubslot.c`, the boot-slot, verb-table and GRUB-slot libraries): manage the boot partition of a machine nobody will open again. `bootctl kernel <file>` puts a machine-built kernel into the candidate slot as a one-boot trial, `bootctl commit` promotes it once it has booted, and `bootctl status` reports the four boot files' sector extents, what the environment block holds, whether a trial is armed or consumed, and which slot this boot came from. The name is systemd's, whose bootctl manages a boot partition's kernels and defaults on most Linux machines, so the knowledge transfers off this machine; the verbs are this project's own trial and commit vocabulary from milestone 23. The library does everything that touches the volume behind caller-supplied sector callbacks: it validates the FAT32 BPB before trusting a field of it, requires the two FAT copies identical, walks the whole reachable namespace under a visited bitmap (a cluster reached twice is a cross-link and a refusal to proceed), resolves `/boot/kernel`, `/boot/fallback`, `/boot/grub/grubenv` and the rewritable menu slot `/boot/boot.cfg` where a disk has one, and installs in the order the interruption matrix in `dev-log/23-install/plan.md` documents: the fallback file validated as a bootable kernel first (program headers, loads and entry included, the same loader surface `tools/check_kernel.py` judges), then one environment transition that moves the saved default to the fallback AND drops any stale armed trial, then the slot written cluster by cluster and read back byte for byte, and only then the one-boot `next_entry` trial armed; every environment write is itself read back and compared. The menu's four kernel entries are two pairs, one taking whatever the network gives it and one carrying a fixed address for a network with no DHCP server, and an install or a commit keeps the machine in the pair it is running from: writing the other pair's ids would move a machine that has no lease to entries that ask for one. Which pair is running is read off `/proc/cmdline`, from the address itself, since that is what differs between them. `bootctl commit` runs only where `/proc/cmdline` says the candidate is running AND the block has the consumed-trial marker (`next_entry=`, the empty value GRUB's scripted consumption saves): an armed line means the slot was refilled after this machine booted, and a block with no line at all is a fresh disk or an interrupted install, whose slot bytes are not the running kernel either way. One administrator at a time: the tool takes no lock over the boot partition, and two concurrent kernel installs are outside its contract. A power cut at any point leaves a machine that boots. The guest binary binds the callbacks to `/dev/bootpart` (root-only, absent outside a GRUB-disk boot) and requires the `rach2.slot=` state on `/proc/cmdline`; the host test (`tests/host/bootctl_hosttest.c`) drives the same library over fixture images from an independent python FAT writer, with a write callback that drops, tears and cuts.
* `reflash.c` (with `sectorcopy.c`, the stream-to-sector library): write a byte range of a device from standard input (`reflash DEVICE OFFSET BYTES`). Recovery's half of rewriting a disk from an SSH pipe: it coalesces a stream that arrives in whatever sizes the network gives it into whole sectors, bounds the write by subtraction so a length can never wrap past the end of the device, and requires the input to end exactly where it said it would, since a short stream that reported success would leave a partly written root nobody would look at again

  The other verbs manage the menu and the boot loader. `bootctl config <file>` overwrites `/boot/boot.cfg`, the rewritable half of the menu that `/boot/grub/grub.cfg` sources, refusing a file larger than the slot before anything is written and rewriting every sector of the slot so a shorter menu leaves nothing of a longer one behind. `bootctl env <key> [value]` reads or sets one of the two grubenv keys through an allowlist, and `bootctl trial <entry>` and `bootctl cancel` arm and clear a one-boot entry. A staged menu is GRUB script that the stub runs, so whoever writes it can direct the boot; what the stub guarantees is that a damaged one still leaves a bootable machine.

  `bootctl grub <file>` replaces the boot loader itself, and its contract is different enough from the kernel install to state separately. It takes a complete GRUB core image for i386-pc, 2 to 1024 sectors. Sector 0 is never written: the gap holds two 1023-sector tails, at LBA 2 and LBA 1025, and LBA 1 is the entry sector whose blocklist selects between them, so an install writes the tail that is not in use, reads all 1023 sectors of it back and compares, and only then rewrites LBA 1. Which tail is in use is read from the entry sector, and that reading establishes only that its blocklist holds exactly one record, naming one of the two slots with a length that fits one. A conventional GRUB disk passes it too, and the tool claims LBA 2 through 2047 on whatever disk it runs on: on a disk this project built, the gap is the tool's and the half not in use is free; on a disk it did not build, that half may hold something no partition table mentions, and the install overwrites it. A second blocklist record, which is how a loader spread over several extents in the gap declares itself, is refused. Everything before that last write leaves the machine booting as it did. That last write is the one exposure in the scheme: a torn or bad write there makes GRUB unreachable, and the recovery image cannot help, because GRUB is what loads recovery. The candidate is judged before any write, for fitting a slot, for carrying GRUB's blocklist segment, and for declaring a tail length that matches its length in sectors; that check is on sectors, so a transfer cut inside the image's last sector cannot be distinguished from the whole file, and nothing establishes that the image has the modules this disk needs. Compare `sha256sum` at both ends of the transfer before installing. Unlike the kernel install, this one does hold the device: the kernel admits a single opener of `/dev/grubcore`, refusing a second with `EBUSY`, because two installs at once could each verify their own tail and then leave the entry sector naming one image with the other one's length. `tools/Readme.md` gives the layout and `tests/host/grubslot_hosttest.c` drives the library over a model gap, including one that reports a write as done and drops it.
* `passwd.c`: Change an account's password (`passwd [user]`, the account defaulting to the caller's own). A setuid-root program, and the first that writes a credential file. It decides what its caller may do from the REAL uid: the binary is 04755, so `geteuid()` is 0 for everyone who runs it and a test on the effective uid would authorize the world; naming another account is the administrative exception and needs `getuid() == 0`. Root changes any password without proving the old one, everyone else proves the account's current one.
The survey and every prompt happen before the transaction is taken, and the transaction is held across a re-read and the publish alone. An earlier draft took it first, which made the account found, the hash authenticated against and the file replaced one image by construction; that is the right property reached the wrong way, because the lock was then held across two or three terminal reads, so any account could start `passwd`, sit at the prompt, and stop every other writer for as long as it liked on a machine with sixteen process slots. The property is kept by checking under the lock that BOTH the caller's claim and the record still hold: the caller's real uid must still name the same account in a re-read `/etc/passwd`, and the record must still be the one authenticated against. The first is not a refinement of the second, since a name is not owned forever: an administrator can remove the account or hand the uid to somebody else while the password is being typed, and none of that need touch the shadow hash, so a writer that rechecked only the record would publish as root for an account that had just stopped being the caller's. Checking under the lock that the record authenticated against is still the record about to be replaced: what an early lock made impossible, a late one makes detectable, and detectable is enough, because the only honest answer to a record that changed while the password was being entered is to say so and change nothing. `getspnam` is not called here at all: it would be a second, independent read that can answer from a different file than the one about to be replaced, and an authentication that passed against a line the replacement then overwrote is a lost update wearing a success message. A name appearing more than once in either database is refused, naming the file, because musl's parsers stop at the first match and the line that authenticates and the line that is rewritten could otherwise be different ones. That count is taken again under the lock, for root as much as for anyone else, and not only the caller's uid lookup: a second line carrying the same login at a different uid appearing while the password is typed leaves the caller's uid still resolving to the same name and every other check satisfied, while `getpwnam` now answers with the other account, so the hash about to be published would authenticate a uid that is not the caller's. The salt is minted after the old password is accepted and before the new one is asked for, so a machine with no trusted entropy refuses without first collecting a secret it cannot use; the new password is read twice and must agree, and an empty one is refused. Both of `cred_rewrite`'s and `cred_txn_end`'s answers reach the exit status, since a change that is live but not on the platter is not a clean finish. It accepts the conventional end-of-options `--` before a name, which is how an account whose login begins with a dash is named at all, and it takes a name equal to the caller's own from anybody: that is the same request as naming none, and it is how the command is usually written. It holds to the limits the readers impose rather than to its own buffers: a password longer than `PWAUTH_MAX_PASSWORD` (100, which is dropbear's `DROPBEAR_MAX_PASSWORD_LEN`, checked before it ever calls `crypt`) is refused, since a longer one would work at the console and never over the network, and the credential library refuses an over-long entry outright rather than storing the prefix it fitted, which would be a secret the user never typed. An entry holding a NUL byte is refused for the same reason and not truncated at it: `strcmp` and `crypt` both stop there, so two entries differing only past a NUL would confirm each other at the second prompt and the stored secret would be the prefix alone. That limit is the library's and not each caller's: `pwauth_read_password` caps at `PWAUTH_MAX_PASSWORD` whatever buffer it is handed, so `su` and every later reader agree with dropbear without having to remember to. A record is refused unless a newline follows it and the result fits musl's 256-byte `getspnam` line, because that reader rejects a matching record whose last character is not a newline and reports it as no account at all. It refuses a database holding a NUL byte, since everything it does parses with string functions and a NUL would end each of them early and publish a file with the remainder cut off; and it refuses to rewrite a shadow record that is not one, nine colon-separated fields with the aging fields empty or decimal, because a replacement keeping a malformed line's shape would publish a file this program calls changed and every reader goes on rejecting. That last judgment is made twice, and the second time on the text about to be written rather than on the text that was read: the shape can rot while the prompts are open the way the hash can, an aging field turned to junk or the final newline taken off, and neither touches the hash the locked re-read compares, while `replace_hash` copies both through. Its passwd parser is musl's and not a looser one: `__getpwent_a` wants six colons and reads the uid and the gid with a digit loop that must land exactly on the next colon, so `x:1000junk` and a three-field line are records `getpwnam` and `getpwuid` skip entirely, and a program here that resolved them anyway would authenticate as a name no reader can find and then report a password changed for an account nobody can enter. The uid is read with the same wrapping arithmetic musl uses rather than through `strtoul`, which saturates, so the two cannot come to different conclusions about an absurd field. An empty numeric field is the one place this is stricter: musl reads it as 0, and a blank that silently means root is not something to carry into a credential writer. Only the target's own record is judged: the rest come through byte for byte, and refusing the whole file for a line nobody asked about would let one bad record lock every account out of a password change. It reads the databases with `read` rather than `fread`, which is not a style choice but a habit from before this kernel had `readv`: musl's buffered read asks for that call whenever it is given more than one byte, and until the busybox account tools forced the gap open it was not there. A direct `read` is still the honest thing for a credential file, which is read whole and parsed in memory.
* `halt.c`: Stop the machine (`halt [-p|-r]`, power off by default, `-r` to restart). Root's, because `reboot(2)` is. It exists for the images that carry no busybox: os-simple is built out of this project's own code alone, so without it that image would be the one with a system call to stop the machine and no program that makes it. os-real does not stage it, and the manifest says why: busybox's standalone shell dispatches `halt`, `poweroff` and `reboot` as applets before it looks at the file system, so a binary of that name there would be one nobody reaches. It tears nothing down first, because the kernel flushes and clears the flag inside the call with scheduling already off, and a program that stopped its neighbours politely would be adding a scheduling policy to the last moment of the machine's life.
* `login.c`: Authenticate whoever is at the console and become them. init's session child execs it, so the console is behind a password rather than in front of one. It has no set-id bit and needs none: init is root, so the program starts as root and spends that authority once. It prompts, reads the password through the credential library, and says the same thing whichever half was wrong, since a message that told an unknown name from a wrong password would turn the prompt into an oracle for which accounts exist. A refusal pauses and asks again, three times, and then exits: init brings the prompt back, so the respawn is the retry and a wedged reader cannot hold the console. An over-long name is refused rather than truncated, the way an over-long password is, and the limit is the library's `PWAUTH_MAX_NAME`, which `adduser` also refuses past, so what one writes the other can read. The drop is `setgroups`, `setgid`, `setuid`, in that order, because the first two need the privilege the third gives away, and each is checked: carrying on from a failure would mean running a shell as an identity nobody chose. It does not `setsid` and does not claim the terminal, since init's child already did both and this exec inherits them; a second claim after the drop would be refused anyway. `/etc/motd` is printed after the drop, deliberately, so the file's own modes answer whether the account may read it. The environment is built from nothing, for the reason `su` builds one, and it has the same `PATH=/bin:/usr/bin` su sets: a shell handed no `PATH` resolves nothing but the names its caller spells out in full, so the first bare `ls` after a login would fail.
* `init.c`: PID 1, and three artifacts from the one source. It answers three signals as a shutdown request, which is how a bare `halt`, `poweroff` or `reboot` works at all: those programs signal pid 1 rather than calling `reboot(2)` themselves, and the map is busybox's, SIGUSR1 to halt, SIGUSR2 to power off, SIGTERM to restart. The handler does the work rather than setting a flag for the loop, which inverts the usual rule and for a stated reason: the work is one bare system call that never returns, so it is async-signal-safe and cannot be re-entered, while a flag would race against the `waitpid` init blocks in, since a signal arriving after the loop tested it and before the kernel blocked init would sit unread until the next child event, which on an idle console never comes. Closing that window needs a wait that unmasks atomically, and this kernel's `ppoll` takes a signal mask without applying it. Nothing is torn down first: the kernel flushes and clears the flag inside the call with scheduling already off, so no committed write is lost, and what is given up is asking the programs on the machine to stop politely, which would be a scheduling policy of init's own at the last moment of the machine's life. `init-shell` is the older behavior: a table of shells (`/bin/sh`, then `/ish`) tried in turn. `init-login` execs `/bin/login` and nothing else, with the table and the loop that walks it compiled out, so the strict binary holds no code path and no string that names a shell; `tools/check_setid.py` asserts exactly that on the bytes, and asserts the converse of `init-shell` so an empty or unreadable scan fails rather than passes. The split is at compile time rather than at run time because every runtime signal is a thing an edit can drop, and the drop must not be the permissive direction: a marker file left out of a manifest, or a boot token lost from a command line, would hand the console back to an unauthenticated root shell. Two artifacts carry no such state, and which init an image gets is visible in the manifest diff. Neither is named plain `init`, so a manifest left on the old path fails to stage rather than silently taking whichever the tree happens to build. In the strict build every `execve` failure is one case, `ENOENT` included: the child says it cannot exec `/bin/login`, says once how to get back in, and exits, and the parent respawns it forever, more slowly than the shell build does so a permanent failure states its reason instead of scrolling it away. It never gives up, because giving up means init exits and an exited init is a panic, which refuses a shell no harder while turning a transient failure into a permanent one. The way back into an image that will not offer a prompt is booting `rach2.rescue`, where the kernel never consults the image's init at all and the debug shell comes up with the file system mounted and writable. That is the only way back in on the images whose init starts no network service. The third artifact, `init-metal`, is `init-login` plus a supervised dropbear, staged only by the metal manifest: the machine that image is for is across the room, so the SSH server has to be running when the machine finishes booting rather than typed at a console nobody is standing at. It is held to the same byte-level rule as `init-login`, since the console it puts behind `/bin/login` is exactly the recovery path for a machine whose network is the broken part, and a fall-through to a shell there would hand that machine to whoever walks up to it. The supervision itself is the ordinary one: each child is tracked by pid, a child that dies is respawned, and one that died within two seconds of starting costs a five-second pause first, so a server failing for a permanent reason (no trusted entropy for its host key, no network, a port already held) does not respawn at full speed. Only the console child does `setsid` and claims the terminal; dropbear must not, since it makes a session and a pty per login and the console is the one thing that must stay uncontested. `make metal-test` proves the whole of it with nothing typed at the console, including killing the server by pid and requiring a different pid to answer. The trade is deliberate and asymmetric. The failure being removed is reachable by whoever walks up to the serial line; the failure being accepted is reachable only by rebooting with a flag the operator controls.
* `adduser.c`: Create an account (`adduser [-u number] [-s shell] name`). Root's, and deliberately not setuid: it refuses a caller whose `getuid()` is not 0 before it opens anything, which is the same rule the set-id programs follow, applied where nothing can confuse the two ids. The shell defaults to `/bin/sh` and is not checked for existence, since an account may legitimately be created before the program it logs in to is staged.
It writes three databases and a home directory under one transaction, and every check is made against the one image read under the lock: the name must be absent from `/etc/passwd`, `/etc/group` AND `/etc/shadow`, the number must be free as a uid and as a gid, and with no `-u` the lowest number at or above 1000 free in both is chosen. Choosing a number outside the lock is exactly how two runs hand out the same uid, so the read, the choice and the writes are one transaction rather than three. Shadow is in the absence check and not only in the write list, because it is written first: a run that tested only passwd and group would pass both tests over a crashed run's leftovers and append the name to shadow a second time, and nothing would then report it, since musl's parsers all stop at the first match, so which of two lines authenticates a login and which one `passwd` rewrites is decided by file order and the two can differ.
The publication order is the whole of what makes an interrupted run safe, because no lock makes four changes one change: KRFFS has no journal, each replacement publishes one file, and a failure part way through publishes nothing further while undoing nothing already published. So every prefix of the order is a system a reader can still make sense of. Shadow with a locked `!` field first, since it consumes no number and names no group; then group; then the home directory, created 0700 and chowned before any mode change, since setting an owner clears the set-id bits; then passwd. The account becomes visible only at that last step, so no interruption leaves a passwd field of `x` with no shadow entry, nor a gid that names no group. What each prefix leaves, and how root clears it:
    * Nothing published: no file changed. A crash can still leave the lock.
    * Shadow only: a locked field under a name no account claims. No reader reaches it, since every path into `getspnam` starts from a passwd entry. Remove the line; no number was consumed, so an account created meanwhile may legitimately have taken the one the dead run chose.
    * Shadow and group: adds a group with no members whose gid no account names. `getgrnam` and `getgrgid` both find it, so the number is consumed and a later run's scan skips it, which is correct rather than a leak. Remove both lines.
    * Shadow, group and home: adds a 0700 directory owned by a uid and a gid that resolve to no name, so `ls -n` is the listing that shows the truth of it. Remove the two lines and the directory.
    * All four: not a residue but the intended end state before `passwd` runs, an account that exists and cannot be entered. `passwd NAME` completes it.
The lock is the fifth residue, and the next writer reports it rather than breaking it, so recovery is `rm /etc/.pwlock` as root. A name in all three databases is `adduser: bob already exists`; a name in some of them names exactly the files that hold it, because a live account and a residue want different repairs. It never resumes a partial account and never rolls one back: resuming would mean deciding that a partial state is a residue rather than something an operator wrote by hand, and adopting a uid it did not choose, while rolling back would mean a second series of replacements, each able to fail the way the first did, on files another writer may since have changed. The cost is that a crashed name is refused until root removes the leftover lines, which is the same editing account removal already requires. Where it fails rather than crashing there is someone to tell, so any failure after the first publication says what it published and that nothing was rolled back.
The transaction is dropped before the password program is exec'd (`/bin/passwd`, falling back to `/passwd` for the flat test image), which is required and not tidy: the lock is a file, it outlives `execve`, and a transaction carried across would deadlock `passwd` against its own predecessor. Until that `passwd` succeeds the field stays `!`. There is no `/etc/skel` and the absence is deliberate: a skeleton is a policy about what a new account should already believe, and this system has none to state. Account removal in this image is root editing the three databases: there is no in-house `deluser`, and writing one to match would be a second implementation of what os-real takes from busybox. The asymmetry is the point of the two images rather than a gap in one of them.

* `sudo.c`: The reference sudo (`sudo <command> [args...]`): a setuid-root program that permits the command only if the caller's real uid is listed in `/etc/sudoers`, clears the environment, assumes root through the saved id, and execs. It is the coursework answer key, staged only into the test image and gated by `tests/sudoprobe.c`; neither shipped image has a sudo, leaving the student to write their own against the same probe. Password prompting, per-command rules, and TTY handling are deliberately left as the exercise.
* `init.c`: PID 1, staged at `/sbin/init` (it builds into `build/utils/sbin/`, not beside the ordinary utilities, so the os-simple `exec-dir` sweep does not also drop it at `/bin/init`; see the staging rule below). The kernel boots it; it forks a session child that claims the console as its controlling terminal and execs `/bin/login` (or, in the `init-shell` build, the first shell of `/bin/sh`, then `/ish`), reaps every orphan the kernel reparents onto it, and respawns the child when it exits. The `init-metal` build supervises an SSH server beside that console child, so a machine nobody is standing at is reachable as soon as it has booted. It never exits; the kernel panics if it does.

## Credentials

`pwauth.c` (declared in `pwauth.h`) is the credential library, linked into `su` the way `resolv.c` is linked into `ping` and `nc`, and into every later program that authenticates or writes an account. It is the only code in the image that compares a password against a stored hash, mints a salt, or replaces a credential file.

A reader and a writer are not symmetric. A reader resolves the entry itself and takes no lock, because a write-new-then-rename replacement is atomic for a reader in fact: a descriptor names one file from open to close, so a reader sees the old file or the new one, whole, whether it opened before the rename or after it. `su` and `login` are readers, as dropbear is on os-real, so nothing about entering the box depends on a lock. A writer is different: a credential change is a read-modify-write, and rename alone does not make that interval exclusive, so two writers could read the same pre-image and the second rename would restore the first one's old hash. A writer therefore takes `cred_txn_begin` before its first read and holds it through its last rename. The kernel is no help here: every `F_SETLK` is granted and `F_GETLK` always answers `F_UNLCK`, documented no-conflict semantics dropbear depends on, so an advisory lock records nothing. The transaction is a lock file, `/etc/.pwlock`, created `O_CREAT|O_EXCL` at 0600 and holding the holder's pid; the exclusive create is the whole of the exclusion, since a syscall on this kernel does not yield.

The release is registered before the lock is created, and a registration that fails refuses the acquire: `atexit` allocates once its builtin slots are full and can fail there, and a transaction whose release was never registered would leak the lock on the ordinary `exit` the registration exists to cover. A transaction belongs to the process that took it. The library's state is file-scope, so a `fork` copies it, but the pid recorded at the acquire is what says who the holder is: in the child every entry point declines, its `exit` and its death drop nothing, and an acquire of its own goes through the ordinary wait and refusal naming the parent. A transaction does not survive an `exec` either, since the new image has neither the state nor the registered release, so a writer must not exec while holding one. The same rule points the other way at release time: the lock is unlinked, and a replacement is published, only while the file still records this process, because a name is not proof of a file. Two files that carried one name in turn even share an inode number here (`st_ino` is a hash of the name), so one lock cleared by hand would otherwise cascade, each writer's release taking the next writer's lock.

The release needs no descriptor of its own. It closes the lock's own descriptor first and reads the recorded pid back through the slot that frees, so a writer that has filled its descriptor table still releases; an ownership check that opened a second one would read `EMFILE` as another writer's lock, decline to unlink, and strand the lock for everyone while reporting success. `cred_txn_end` returns -1 when it could not look at the lock or could not remove it, and the caller must report that rather than a clean finish, since a lock still lying in `/etc` is the next writer's ten-second wait and refusal. It returns `CRED_UNFLUSHED` for the third case, a lock gone from the file system whose removal did not reach the disk: that is the last write a transaction makes and often the only one, so reporting it as clean would promise the one thing a power cut takes back.

The lock is reported and never broken. An acquire that finds it says so once and retries ten times a second apart; if it is still there the acquire fails and the recorded pid decides only which line is printed, never whether anything is removed: a pid that is alive (or answers `EPERM`) is `credential database busy (pid N)`, a pid that is gone is `stale lock /etc/.pwlock (pid N is gone)`, and a file recording no pid is the same with `(no holder recorded)`. Every one of the three names the removal, and that `rm /etc/.pwlock` is the whole recovery. The two stale forms say `remove it as root and retry` outright; the live one says to remove it if pid N is not a writer, because a pid does not identify a process across a reboot. This kernel restarts `next_pid` at every boot and the writers run early, so a lock left on a persistent image names a small pid that some unrelated process now holds, and an operator told only to wait would wait forever. Breaking a lock instead is what an age bound would amount to, and it cannot be made safe: a holder stopped with `^Z` is indistinguishable from an abandoned one, and breaking its lock lets a second writer publish while the first still holds its snapshot, so the lost update the lock exists to prevent happens with the lock's blessing. There is no `funlink` either, so a breaker cannot bind the removal to the file it inspected and may take a live writer's lock instead. The cost of refusing falls on the right person, since no reader takes the lock at all. An acquire that cannot write the pid into the lock it just created fails and removes it, rather than holding one every later writer would be told to clear.

The library holds itself to that last limit rather than claiming to be above it. Its own release reads the recorded pid and then unlinks by name with no syscall in between, comparing against the pid recorded at the acquire rather than asking the kernel again, and its own publish checks the lock and then renames by name; nothing here can bind either second step to the file the first one saw. So a lock removed by hand inside that window, and a successor's lock created at the name, would be unlinked by the release it interrupted. What is left of the window is the scheduler alone, since the two calls are adjacent and a syscall on this kernel does not yield, and it opens only where the never-break rule has already been broken by hand. Closing it needs an unlink and a rename that name an open descriptor, which this kernel does not have; that is stated as deferred rather than papered over.

A stop at a password prompt is handled and a `SIGSTOP` is not. `^Z` restores the terminal's modes before the process stops, so a suspended prompt leaves a usable console, and the continue re-applies echo-off and reprints the prompt. The resume also starts the line over, and it is the only thing that does, whether the resume was seen before the read or during it: a stop can be served while the modes are set or the prompt written, with no read outstanding, and a reader that only looked after the read would discard the first character typed after the `fg` and refuse a correct password. The few instructions between that check and the read itself are a residue rather than a fix: a stop served there is indistinguishable afterwards from one served during the read, so the byte is dropped, and the cost is a whole authentication rather than a keystroke: the line discipline stays canonical, so the one-byte read returns only once the line has been submitted, the byte discarded is its first, the rest is taken as a password missing a character, and no caller retries. Telling them apart needs an unblock and a wait that are one operation, and `sys_ppoll` accepts a signal mask here without applying it. The residue points the safe way, since the alternative is a character typed and echoed before the stop becoming part of a password. The rule is: the line discipline flushes what is queued when it recognizes the suspend character and no more, so a byte typed behind that character in the same write is returned by the read before the stop is served, and dropping the line is what keeps it from becoming the first character of the password. A continue does not carry the terminal with it, since a shell's `bg` is that signal without it, so the reader touches the terminal only while it is still the foreground group; continued in the background it leaves the modes alone and stops again on `SIGTTIN`. Echo is taken away only while the reader's process group owns the terminal, which is the same question the resume asks before it re-applies the modes. `su &` is one keystroke and this kernel raises nothing for a `tcsetattr` from the background, guarding only the read with `SIGTTIN`, so a reader that silenced the terminal on entry would leave the shell that started it echoing nothing, with no program running that knows how to put it back and no help from killing the stopped job, since the modes belong to the terminal. The modes are still prepared, so the `SIGCONT` a `fg` sends applies them through the resume path, which is where a background reader is meant to acquire them. Asking and acting are one step, with the job-control signals blocked around them, because the answer goes stale the instant a stop is served: a reader that asked while it was foreground, took a `^Z` before it could act, and was continued in the background by a shell that had meanwhile reclaimed the terminal would resume holding a yes that is no longer true. `SIGSTOP` cannot be blocked, so that one window stays open and is the residue already named for stops that cannot be caught. A death arriving at a prompt puts the modes back before it clears the flag that records them, so a second death entering that restore does the work rather than finding it apparently done and skipping it; and it disarms the resume first, since the resume is the one thing here that does the opposite of a restore, and one arriving inside a dying process's restore would silence the terminal it was in the middle of giving back. `SIGSTOP` cannot be caught, so a stop that way leaves the console with echo off until the reader is continued or killed; nothing correctness-bearing rests on it, because no lock is broken and no update is lost. A death signal is the transaction's business, and which signals those are is decided by what the kernel does rather than by the four names a writer expects. `ksig_default_action` terminates a process for every signal except four it ignores and four it stops for, and `cred_may_signal` lets a process signal one whose real uid matches its own, which a setuid program keeps from whoever ran it: so `SIGUSR1` or `SIGALRM` from the user who ran `su` is as fatal as `SIGTERM`, and handling only the habitual four would leave every other signal as a way for that user to leave a console with echo off or a lock in `/etc`. `cred_txn_begin` therefore handles every catchable signal the kernel default-terminates for, and a caller installs none of its own, since the lock outlives the terminal read and the terminal read is only one part of what a signal must undo. Four groups are excluded with reasons: `SIGKILL` and `SIGSTOP`, which cannot be caught; the kernel's own ignore and stop sets, the latter being the prompt's business; `SIGPIPE`, which is handled as a failed write instead; and signals 32 to 34, which this libc reserves and refuses from both `sigaction` and `sigaddset`, here and on Linux. The fault numbers are not excluded, and the usual reason to exclude them does not apply here: a real CPU exception never reaches a disposition on this kernel, since `_exception_handler` and the page-fault path both call `terminate_current_process`, which zombifies the process without consulting `sigacts`. The only `SIGSEGV` a handler can see is one that was sent, which is an ordinary death. So the residue is the five that cannot be handled at all: a writer ended by `SIGKILL`, `SIGSTOP` or 32 to 34 leaves its lock, and the next writer reports it rather than breaking it. They are also blocked wherever the state a handler reads is being published, because no publication here is one store: from just before the lock file is created until the holder pid is in it, so no death is served while the file exists and nothing says whose it is, and across the write of the temporary file's name, whose truncation at one exact length is the name of the credential database itself. Two more stretches block them for reasons of their own. The release does, because its unlink and the flush that makes the unlink durable are one step: a death in between leaves through `exit`, and the registered release that runs then finds the lock already gone and reports a clean finish, so the flush would be owed to nobody. And the registered release itself does, because it runs inside `exit` and the handler leaves through `exit`, which would re-enter it.

Two more dispositions belong to the same rule, and both are about a death nobody sent on purpose. `SIGPIPE` is caught for a prompt's length and for a transaction's whole lifetime, because the prompt goes to standard error after echo is off and a writer reports as it goes: with standard error a pipe nobody reads, the default action kills the process at exactly the point where the console is silenced, or where the lock is held and no `atexit` will run. The write is allowed to fail instead. It is a handler that does nothing rather than `SIG_IGN`, which the write cannot tell apart, because an `exec` resets a caught disposition and has an ignored one into the new image: a child forked under a transaction holds none of it and has no way to hand back what it inherited, so `SIG_IGN` would leave this library's policy in force in a program that never linked it. It is blocked as well for the length of the acquire, alongside the deaths, over the interval in which it is still fatal: the handler goes in several calls after the lock file exists, and `cred_may_signal` lets a process signal one whose real uid matches its own, so the user who ran a setuid writer can send it a `SIGPIPE` in that window and strand the lock where no `atexit` runs. And the prompt's state is taken down with the stop and continue signals blocked, since the modes go back before the handlers come off: a `SIGCONT` served in between re-applies echo-off through a handler about to be removed, and the reader returns leaving the terminal silenced for good. Any process in the same session may send that signal, so it is blocked rather than reasoned about.

`cred_rewrite` is the required idiom for any file the system authenticates against: check the lock, write `<path>.tmp.<pid>` with `O_EXCL`, take the original's owner and then its mode (that order, because a chown clears the set-id bits), flush, check the lock once more, rename, and flush again through the descriptor still open on the file, which is what makes a writeback error reportable at all; `sync(2)` returns 0 unconditionally and would throw it away. The temporary name has the writer's pid so that it belongs to one process: a fixed `<path>.tmp` is shared, and a writer whose lock had been removed by hand could unlink and recreate the file a successor already had open and written, whose rename by name would then publish it over the database. The first of the two lock checks comes before that unlink for the same reason, so a replacement refused for a lock that is not this transaction's changes nothing at all. The inheritance is faithful and has no floor: a database staged 0644, or carrying a set-id bit, is reproduced as it is, and a `chmod` by root between the snapshot and the rename is reverted to what was read, since the lock excludes other writers through this library and not an operator at the console. The three returns are what the caller reports. A failure before the rename removes the temp, leaves the target byte for byte as it was, and is `CRED_UNCHANGED`, the only one a caller may report as unchanged; a failure of the flush or the close after it is `CRED_UNFLUSHED`, where the new file is already the one the system authenticates against and the disk may still carry the old one. The release is flushed too, through the descriptor the ownership check left open, and a flush that fails there is `CRED_UNFLUSHED` from `cred_txn_end` and not a printed line alone, since the lock can otherwise be back on the platter after a power cut that followed a run the writer called clean. A writer killed between the create and the rename leaves its own `<path>.tmp.<pid>` behind, which nothing reclaims: sweeping the pattern would be the never-break rule broken against a different file, since a pid names nothing across a reboot. It blocks nothing and is root's to remove along with the lock. No lock makes a multi-file change atomic, so the ordering does the rest: a writer publishes shadow with a locked `!` first, then group, then passwd, so a crash leaves at worst an account nobody can enter and no name that points at it.

The network utilities use the `SYS_SOCKETCALL` interface and target QEMU's SLIRP network (gateway 10.0.2.2). `ping` and `nc` resolve a host argument through a small stub resolver (`resolv.c`, declared in `netdb.h`): a numeric literal, then the hosts file, then a DNS query to the nameserver in the resolver config (SLIRP's forwarder 10.0.2.3). Both are `/etc/hosts` and `/etc/resolv.conf` in the shipped images, and the flat `/hosts` and `/resolv.conf` where there is no `/etc`.

## Build for Rach2 (Default)

Requires `i686-elf-gcc` specifically (the musl utilities link a 32-bit libgcc that a non-multilib `x86_64-elf-gcc` cannot supply) and the ported musl built once. The simplest path is the top-level `make` (it builds libc first, in order); to build just these utilities once libc exists:

```
make
```

This links each utility statically against the ported musl (`../vendor/musl/install`: musl's `crt1/crti` + `libc.a` + `crtn`, no hand-rolled `crt0`) as a freestanding ELF32 executable at `0x08048000`. The binaries are staged into the os-simple image by its manifest (`make os-simple-image` from the repo root) and run on the kernel.

## Build for Linux

Uses the host compiler, not the cross-compiler the Rach2 build uses:

```
make -f Makefile.linux
```

This builds hosted native binaries against the host libc, not the freestanding ones the Rach2 build produces, and only the subset of the programs that make sense off the machine. It is for trying a program's logic on the development machine, not for producing anything Rach2 runs.

make clean

## Usage (Linux)

`make -f Makefile.linux` builds the native utilities out of tree into `build/utils/linux/`. Run them from there:

```
cd build/utils/linux
./true && echo "success"
./false || echo "failed"
./echo hello world
./cat file.txt
./pwd
./touch new_file.txt
./mkdir new_dir
./rm new_file.txt
./mv file.txt hello.txt
./ls
```

## Usage (Rach2)

Add compiled binaries to a KRFFS file system image, boot Rach2, and run from the shell:

```
> exec echo hello world
hello world
Process exited with status 0

> exec cat hello.txt
hello, world
Process exited with status 0
```

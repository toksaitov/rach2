# The VM's GPU backend

`bed/vm/` is the Linux side of the test bed's shared-memory GPU transport ([`../shm/`](../shm/Readme.md)): a Debian 13 virtual machine whose backend serves Rach2's virtio-gpu from the region that QEMU's ivshmem device shares with the host. [`module/`](module/) is `vgpushm.ko`, which binds the ivshmem device in the VM and hands its region and doorbell vectors to the backend. [`backend/`](backend/) is `vgpu-backend`, which runs the transport's device side, renders virgl and Venus through libvirglrenderer and shows the scanout on the VM's KMS as its DRM master. [`image/`](image/) prepares the VM from Debian's cloud image and checks the whole path against [`peer.c`](../shm/peer.c), which plays Rach2's driver on the host.

## Running

    sh bed/vm/image/vm.sh prepare [-n]
    sh bed/vm/image/vm.sh check [-V | -b] [-c CPUS] [-m MIB]
    sh bed/vm/image/vm.sh rach2 [-o RAW]

`prepare` boots an overlay of the cloud image that [`tests/graphics/debian-ref/image`](../../tests/graphics/debian-ref/image) pins once with a cloud-init seed. [`image/setup.sh.in`](image/setup.sh.in) installs [`image/packages`](image/packages) from Debian's snapshot of the date that file names, rebuilds Debian's virglrenderer with GBM allocation and a check of its GBM device, builds vkms with [`image/vkms.patch`](image/vkms.patch), adds `intel_iommu=on iommu=pt` to the kernel's command line and vfio's leave to take unremapped interrupts, and adds the service that writes the versions and `bed-vm: ready` to the serial console at each boot. The result is `prepared.qcow2`, read-only, in `build/cache/bed-vm` of the main clone, which its worktrees share, or in `BED_VM_CACHE`, with the key of the seed's files beside it; `-n` keeps an image of the same key, and `check` refuses one of another.

`check` builds the peer into `build/bed/vm` and starts it as QEMU's ivshmem server with a region of 32 MiB, boots a new overlay with 4 CPUs and 4096 MiB (`-c`, `-m`) and the region on an `ivshmem-doorbell` of two vectors, copies the tree's `module/`, `backend/` and `rach2/sys/virtio/vgpushm.h` into the VM and builds them there, and runs the backend as the device while the peer drives it. With `-V` the backend takes the device through vfio-pci under QEMU's emulated intel-iommu in place of the module. With `-b`, once the peer has drawn, a service in the VM takes anonymous memory until MemAvailable reads 0 and keeps it there, each piece as large as MemAvailable less 64 MiB and the last ones 1 MiB past it, until timeout(1) kills it 30 s on, which gives the memory back without the VM's programs, since a VM held so livelocks in reclaim; the peer then asks for eight backings of 64 MiB in turn (`VGS_CMD_BACKING`), for resources it made before the fill, since a create past the VM's room is refused too, and for a texture of 1024 by 1024 (`RESOURCE_CREATE_3D`), which the backend must each refuse with `ERR_OUT_OF_MEMORY`, where a pin of memory the VM has not got, or a texture the GPU's driver fills, wakes its OOM killer, and then answer every command after. Once the fill has ended, the backend is moved into a memory cgroup of its own, `/sys/fs/cgroup/bed-pin`, whose `memory.max` of 64 MiB holds what it allocates from then on, and the peer asks for a backing of 1 GiB, which the VM's counts allow and the cgroup cannot hold: its pin's allocation fails in the cgroup, and the backend must refuse it with `ERR_OUT_OF_MEMORY` too, where a pin that wakes the cgroup's OOM killer ends the backend. The accelerator is KVM where `/dev/kvm` opens, as [`rach2/qemu_devices.sh`](../../rach2/qemu_devices.sh) chooses.

`rach2` makes the VM that Rach2 drives over its own transport under its own KVM: `rach2.qcow2` beside the prepared image, an overlay of it with the tree's module and backend built and installed and a service, `bed-vm-backend`, that at each boot loads the module and runs `vgpu-backend -v` surfaceless on the ivshmem device, writing each of its lines to the console after `bed-vm: `, and at the backend's end `bed-vm: backend: ended: status S`, 128 and the signal's number for a kill, with the VM kernel's lines of an OOM kill, a segfault or a trap as `bed-vm: kernel: ` lines, which the console's log level keeps off it. The backend's lines reach `sed` over a FIFO that whatever the backend starts holds open too, so the service waits for the backend alone: once it has ended, the service kills every other process of its cgroup but `sed`, the render server and its workers among them, and with them every object they held, until none is left, then prints `bed-vm: backend: ended: N of its processes left, killed and gone` before the kernel's lines, and ends. A service of its own, `bed-vm-memory`, so that it goes on through the backend's end and restart, reads the VM's MemAvailable and the first line of i915's `i915_gem_objects` in debugfs once a second, seeking that file at each reading until it finds it, since i915 may bind after the service starts, and again once it has gone, and writes `bed-vm: memory: available A kB, least L kB; i915 N objects, K kB, most M kB` when either has moved 64 MiB since its last line or i915's file has come or gone, the least and most being those of the seconds since then, or `i915 none` without i915, so that a run's least MemAvailable is on record while a steady VM writes nothing to its slow console. When the VM has an Intel display function, a GPU given to it through vfio-pci as on the Lenovo, the service waits up to 60 s for i915's render node and runs the backend without `LIBGL_ALWAYS_SOFTWARE`, so that Mesa's surfaceless EGL renders GL on the node, Crocus on the Lenovo's HD 4400, and prints `bed-vm: gpu: BDF: GL on renderDN`; and with `VK_DRIVER_FILES` naming Mesa's two Intel Vulkan drivers, hasvk and anv, so that Venus renders on the GPU and not on lavapipe, and prints `bed-vm: gpu: BDF on i915, Venus on FILES`. Without the GPU, GL renders on llvmpipe. A second service, `bed-vm-control`, reads lines from the VM's second serial port, ttyS1, which `tests/run bed-shm` makes a pipe ([kvm](../../tests/kvm/Readme.md)): `stop`, `cont` and `kill` send the backend SIGSTOP, SIGCONT and SIGKILL, `hold` SIGUSR2 and `refuse` SIGWINCH, `start` starts `bed-vm-backend` again, which then finds the module loaded, and each is said on the console as `bed-vm: control: WORD: done`; a VM without that port, as on the Lenovo, runs it to no effect. When QEMU gives the firmware entry `opt/rach2/vgpu-profile`, as `bed-shm.sh` does with `BED_VM_PROFILE_PORT`, the service runs the backend with `-T /run/vgpu-profile`, and with `-C` as well when the entry is `1`, and prints `bed-vm: profile: OPTIONS`; the console has no getty, `serial-getty@ttyS0` being masked, since its unit hangs up the tty as it starts, after these services, and a descriptor of the tty they opened before then writes nothing; the account `gfx` takes `krffs/rach2_demo_ed25519.pub`, and perf is installed, which [`profile.sh`](../measure/Readme.md) uses. When QEMU gives the entry `opt/rach2/mesa-debug`, as `bed-shm.sh` does with `BED_VM_MESA_DEBUG`, the service exports it to the backend as Mesa's `MESA_DEBUG` and prints `bed-vm: mesa-debug: FLAGS`; any value but `silent` has Mesa log each GL error and the call that raised it, in every GL context the renderer makes, as `bed-vm: Mesa: error: ERROR in CALL`. virglrenderer's own `VREND_DEBUG` does nothing there, since Debian builds it with `NDEBUG`. With `-o` it also writes the image whole as the raw disk `RAW`, which `tests/run bed-shm` boots ([kvm](../../tests/kvm/Readme.md)).

In the VM the backend runs as root, so that it can be the KMS device's master:

    LIBGL_ALWAYS_SOFTWARE=1 vgpu-backend [-m NODE | -V BDF | -f FILE] [-k CARD] [-g DEV]
                                         [-d] [-w] [-x | -I] [-N] [-P] [-p PEER] [-1] [-v] [-C] [-H] [-T FILE]

* `-m NODE` takes the region and vectors from the module's node, `/dev/vgpushm0` by default; `-V BDF` from the ivshmem device at PCI address `BDF` bound to vfio-pci; `-f FILE` maps a file shared another way and polls.
* `-k CARD` shows the scanout on the KMS device `CARD`; `-g DEV` names the DRM device virglrenderer allocates on through GBM, `CARD` by default. Without a KMS device the backend acknowledges each flush without reading pixels. `-C` enables diagnostic readback and a software CRC for each surfaceless flush.
* `-T FILE` counts each control command's bytes and wall time in the region read, execution and answer. It also counts diagnostic flush bytes and time in the readback, CRC and log, and, on its `ahead` line, what the look-ahead did with each `VGS_CMD_BACKING` it consumed: served ahead (`served`), found at its turn (`turn`), or kept in order because it is fenced or its id is 0 or in the table (`known`), an earlier entry other than its unfenced create names the id or no such create is queued (`named`), the table lacks room (`room`), or an earlier chain breaks the rules (`bad`). SIGUSR1 writes a complete snapshot to `FILE` at the next turn of the serving loop. Execution time includes the diagnostic's time. The answer column measures immediate answer handling or the deferral to a fence, the fence call among it, and the driver's counters measure the wait for a deferred answer. Each command's row also gives `queue_ns`, the time from the look-ahead's read of each chain to the start of its service; `slow` and `slow_ns`, the executions of 4 ms or more and their time; `max_ns`, the longest execution; and `held` and `fence_ns`, the commands held for their fences and the time from each fence call to the answer.
* `-d` scans a resource's own buffer out when it can; `-w` checks each frame through the device's writeback connector.
* `-x` starts virglrenderer without Venus; `-I` imports each resource a Venus context takes into Vulkan and reports its CRC.
* `-N` enables the DRM native-context renderer and its capset, using the matched library of [`../nctx/`](../nctx/Readme.md). It needs that library built with an i915 renderer and an i915 render node in the VM; without `-N` the backend offers no DRM capset, even when linked to that library.
* `-P` offers no page lists (`VGS_TF_PAGES`), which the backend otherwise offers through the module with doorbells, so that a blob of host memory cannot be mapped.
* `-p PEER` sets the peer id the backend offers; `-1` exits when the driver detaches; `-v` reports each epoch.
* `-H` has SIGUSR2 hold the serving thread before the next new backing for 45 s (`VR_HOLD_S`), past the driver's 30 s limit on a still heartbeat, for Rach2's test of a long command, and SIGWINCH refuse the next new backing for want of memory (`vr_refuse`), for its test of the driver's backing from the region's heap; without it both signals keep their default actions.

`LIBGL_ALWAYS_SOFTWARE=1` keeps Mesa's GBM and EGL on llvmpipe over vkms, which has no render node; without it Mesa looks for a hardware driver for the card, prints `kmsro: driver missing`, and EGL finds no device.

## Results

`check` prints the backend's lines and the peer's, each prefixed `bed-vm:`, then one line for each check and a last line, `bed-vm: result: the VM drew and showed the peer's frames`, or the reason it failed. It writes the VM's record to standard error as `bed-vm: record:` lines: the versions of `libvirglrenderer1`, `libgl1-mesa-dri`, `mesa-vulkan-drivers`, vkms and the kernel, the accelerator, QEMU's version, the image with its SHA-512, the snapshot and the device's path, `vgpushm` or `vfio-pci`. Its checks:

* frames written back: the CRC of each frame vkms's writeback copied, in order, equals the CRC the peer expects: its 2D image, the display frame whole, and its top-left quarter;
* Venus's import: the CRC of the frame's buffer as Vulkan imported it equals the CRC of its rows as the peer read them back;
* direct scanouts: the whole frame was scanned out from its own buffer, once, and the quarter copied;
* the backend was woken by the queue's doorbell and the peer by the VM's, and the peer ended well;
* with `-b`, MemAvailable read 0 before the peer asked for the backings, and all eight were refused with `ERR_OUT_OF_MEMORY` by the VM's counts, as was the texture, `backend: create: resource ID: refused: 16777216 bytes: no room in the VM's counts`; the backing of 1 GiB was refused with `ERR_OUT_OF_MEMORY` by its pin, and the VM's kernel logged no kill by a memory cgroup's OOM killer; the fill prints `bed-vm: fill: MemAvailable read 0 after N pieces`.

The backend's own lines: `backend: scanout: writeback WxH of mode MxN, crc X` for each frame checked; `backend: kms: mode MxN for a scanout of WxH` for each mode set; `backend: kms: resource ID is copied: REASON` the first time a resource cannot be scanned out directly; `backend: venus: imported resource ID, WxH, crc X`; and at the end `backend: result:` lines with the device's counts (epochs, commands, errors, fenced commands, completions, doorbells rung, faults, wakes by each vector and steps that found work no doorbell announced), the module's (interrupts and eventfd signals by vector, doorbell writes, and the pins held, their pages, those kept, and the pins made and refused) and the display's (flushes, copies, direct scanouts, modesets, page flips, skipped flushes, writebacks).

A stall prints a report between `backend: stall: WHY` and `backend: stall: end`: when the serving thread has stayed in one place, a step through the queues, virglrenderer's poll or the wait on the doorbells, for 30 s, WHY names the place and, in a step, the command; when the oldest fenced command has waited 30 s for its fence, WHY names its fence, context and ring and the `backend: result:` lines come first. Then each of the backend's threads gives a line of its name, state and wait channel, its kernel stack from `/proc`, and its frames, which it prints from a handler of SIGRTMIN, `lib(function+offset)[address]` a line, or `no frames` when it blocks signals, as Mesa's threads do, or sleeps uninterruptibly; and the last 60 lines of the VM's kernel log follow, which hold i915's hangs and resets that the console's `loglevel=3` keeps off it. The report comes again every 300 s while the stall lasts.

Measured on the testing PC under KVM, QEMU 10.2.1, the VM with virglrenderer 1.1.0-2+rach21 and Mesa 25.0.7: `prepare` took 2 minutes, and `check` passes both ways. The frames' CRCs are a9e0acd7 for the 32 by 32 2D image, f10af47a for the 1024 by 768 frame as shown, faccd412 for its quarter, and 6e8e217c for the frame's rows as stored, which the import reads. Through the module the device served 26 commands, 5 of them fenced, and was woken 26 times by the queue's vector and twice by the control vector, with 26 and 3 interrupts in the module, and polled none; the peer rang 29 doorbells and was woken 28 times. Through vfio the device's and the peer's counts were the same but for 3 wakes by the control vector. The runs' output is in [`dev-log/83-testbed/83-4/`](../../dev-log/83-testbed/83-4/).

## Interfaces

The module binds every ivshmem device (1af4:1110) and makes a misc node, `/dev/vgpushmN`, that one process may hold open at a time. Its ioctls, in [`module/vgpushm_uapi.h`](module/vgpushm_uapi.h):

| Request | Argument | Does |
|---|---|---|
| `VGPUSHM_IOC_INFO` | `struct vgpushm_info` out | the region's size, the VM's peer id from IVPosition, and the MSI-X vectors enabled: 2 for an `ivshmem-doorbell`, 0 for an `ivshmem-plain`, whose peer id is ~0 |
| `VGPUSHM_IOC_EVENTFD` | `struct vgpushm_eventfd` in | binds an eventfd to a vector, or unbinds it with fd -1; the vector's interrupt signals it |
| `VGPUSHM_IOC_RING` | `__u32` in | writes the value, `VGS_DOORBELL(peer, vector)`, to the doorbell register |
| `VGPUSHM_IOC_COUNTS` | `struct vgpushm_counts` out | interrupts and signals by vector and doorbell writes since the device was bound, the pins held, their pages and those kept for the driver's epoch, and the pins made and refused |
| `VGPUSHM_IOC_PIN` | `struct vgpushm_pin` in and out | pins whole pages of the buffer behind a descriptor, a memfd or another shmem file, or a dma-buf whose pages are RAM, for the driver's epoch, and gives a handle, its kind and its pages' count; `EINVAL` for a range not page-aligned, over 1 GiB (`VGPUSHM_PIN_MAX_SIZE`) or past the buffer, or a descriptor of another kind; `EBADF` for a descriptor not open; `EFAULT` for a dma-buf with no pages; `EOPNOTSUPP` for a dma-buf on a kernel with `CONFIG_DMABUF_DEBUG` |
| `VGPUSHM_IOC_PAGES` | `struct vgpushm_pages` in and out | the runs of a pin's VM-physical pages from a page on, each as long as the pages follow each other, at most `max` of them, and the page after the last; `ENOENT` for no such pin; `EINVAL` for a first page past the pin's end, or `max` 0 or over 4096 (`VGPUSHM_PAGES_MAX_RUNS`) |
| `VGPUSHM_IOC_UNPIN` | `__u32` in | lets go of a pin by its handle; `ENOENT` for no such pin |
| `VGPUSHM_IOC_BACKING` | `struct vgpushm_backing` in and out | makes a shmem file of whole pages, at most 1 GiB, pins it whole for the driver's epoch, its pages zeroed, and gives a new descriptor of it, open for reading and writing with `O_CLOEXEC`, the pin's handle and its pages' count; a backing that fails leaves no file and no page; `EINVAL` for a size of 0, not whole pages or over 1 GiB, or a `reserved` word not 0; `EMFILE`; `ENOMEM` |

`mmap` at offset 0 maps the region, BAR 2, shared and write-back. A removed device fails each call with `ENODEV` while its node is held. A node closed while the device's block answers the driver's epoch as `READY` or `RUNNING`, as when the backend dies or is killed, has the module store `FAILED` or `NEEDS_RESET` there with `VGS_E_LOST` and ring the driver's control vector ([shm](../shm/Readme.md)). A pin lasts until it is let go or its node is closed; a pin whose node is closed while the driver is still in the pin's epoch, as when the backend dies, is kept until the driver leaves that epoch or detaches, which the module reads from the region every 100 ms, since Rach2 may map its pages until then.

## Sources and license

The module is GPL-2.0-only, as a Linux module must be, and its UAPI header GPL-2.0-only with the Linux syscall note; the backend is GPL-2.0-or-later, as QEMU's virtio-gpu code is, whose use of libvirglrenderer its renderer follows. Each file's SPDX line says which.

## Local changes

The VM changes two of Debian's packages, in `image/setup.sh.in`:

* virglrenderer 1.1.0-2 is rebuilt from Debian's own source with `-Dminigbm_allocation=true` as version `1.1.0-2+rach21`, held at that version. Debian builds it without GBM allocation, and only a resource allocated through GBM has a dma-buf: without one a GL resource can be neither scanned out directly nor attached to a Venus context, which takes resources only as file descriptors. The rebuild also adds `gbm &&` to the condition of `vrend_create_buffer`'s memory-object branch (`src/vrend_renderer.c:8315`): under `VIRGL_RENDERER_USE_EXTERNAL_BLOB` a persistent buffer takes that branch, which calls `gbm_bo_create` on a NULL device when no render node opened, as in QEMU's VM ([`dev-log/84-locks/upstream.md`](../../dev-log/84-locks/upstream.md#virglrenderer-dereferences-a-null-gbm-device-for-a-persistent-buffer-under-external-blobs)). With the check such a buffer gets no storage, and its export is refused with `-EINVAL`.
* vkms, which Debian's kernel does not build, is built from `linux-source-6.12` of the running kernel's version with `image/vkms.patch`, two fixes Linux's master has and 6.12.115 lacks: the encoders' possible clones, without which a commit with the writeback connector is refused, and the writeback's rows, which a reflected plane wrote in the plane's order. [dev-log/83-testbed/upstream.md](../../dev-log/83-testbed/upstream.md) has both faults.

## Design

### The module

The module enables the PCI device, maps BAR 0's registers uncached and BAR 2's region write-back, reads the VM's peer id from IVPosition and asks for MSI-X vectors; a device without them is served without doorbells. The region is the host's RAM, which Rach2 maps cached, and KVM honours the VM's memory type while it assigns a device that does not snoop, as the Lenovo's GPU is, so an uncached mapping would make each byte the backend reads a bus cycle: the region is mapped with `memremap` and not `pcim_iomap`, whose uncached type x86's PAT would give `mmap`'s mapping of the range too. A write-back mapping needs the VM's MTRRs to leave the BAR write-back, as SeaBIOS does for a 64-bit BAR it places above 4 GiB; under QEMU 10.2.1 it is at `0xe0000000000`, and `/sys/kernel/debug/x86/pat_memtype_list` shows both mappings write-back. Each vector's handler signals the eventfd bound to it under a spinlock and counts. The device's lifetime is a reference count that the node's open holds, and a mutex with a `gone` flag keeps the ioctls from a device being removed. `mmap` maps the region with `vm_iomap_memory`; it reads `gone` without the mutex, since it runs under `mmap_lock`, which the ioctls' copies to and from user memory take under the mutex, and a mapping made as the device goes stays as one made before. A pin allocates its record and its tables, and a pin of a shmem file its pages, with `__GFP_RETRY_MAYFAIL`, as i915 allocates its objects', so that one reclaim cannot meet, in the VM or in the backend's memory cgroup, fails with `ENOMEM`, which the backend answers as a refusal, where the file's own mask would wake the OOM killer and hold the VM, and every answer with it, until a victim exits. A pin that fails lets its pages go and removes nothing from the file, such as a blob's memfd that virglrenderer exported: shmem gives no way to know which pages of a shared file the pin brought in, since a fault through another mapping takes no lock the pin could hold, so those pages stay as the file's, as a guest's touch of the blob would leave them, until the blob is freed. A backing's file is the module's own: `VGPUSHM_IOC_BACKING` makes it with `shmem_file_setup`, pins it, copies the answer out and only then installs the descriptor, so no process can reach the file before its pin is made, and every page in it is the pin's. A backing that fails at any step, the answer's copy among them, lets the pages go, truncates the file and puts it, which frees at once what the pin brought in: left in the file, those pages would stay charged to the VM and the backend's memory cgroup, to which the pin charges them as a memfd's are charged to the process that faults them in, and the backend's next fault would wake the OOM killer. It holds a reference on each page and marks each dirty when it lets go, since Rach2 writes them through KVM, which leaves the VM no dirty bit, and reclaim would drop a clean page unwritten. A pin of a dma-buf maps it for the device and reads each entry's page from the mapping. The pins of a closed node move to a kept list, which a delayed work reads against the region's driver block every 100 ms, letting go of each pin whose epoch the driver has left. The close also tells the driver of a backend that left the epoch it served without detaching: the backend's process can no longer write the device's block, so the module stores the loss there, as the backend would, and rings the control vector, since nothing else would tell the driver, which waits for answers without a deadline.

### The backend

[`backend/device.c`](backend/device.c) is the transport's device side, in C99 with only libc, so that the fuzzer links it alone. It offers chains of 16 descriptors that carry each way as many bytes as the region holds (`max_cmd`), so that a submission of any size the heap holds comes whole in one command, and copies each chain out of the region with `memcpy` once into a buffer of a megabyte that grows to the chain's bytes; a chain it has no memory to copy is answered `ERR_OUT_OF_MEMORY` and logged as `backend: command 0xTYPE: refused: BYTES bytes: no memory for its copy`. It parses only the copy: the handshake of each epoch, as the transport's Readme gives it, the two queues, and virtio-gpu's commands, each body's size checked, each id found in the epoch's table, each memory entry checked with `vgs_check_range` and charged to the device's backing limit before the renderer sees it. It offers `VGS_TF_PARTS` and joins a stream sent in parts into one buffer of the VM's memory, allocated whole at the first part, which the `SUBMIT_3D` after them gives the renderer; a stream it has no memory for is logged as `backend: part: refused: BYTES bytes: no memory for the stream`, and `CTX_DESTROY` frees the stream of the context it ends, whose later parts are refused with `ERR_CONTEXT_ID`. A fenced command's completion waits for its fence, a refusal's too, a SUBMIT_3D's that the renderer refuses among them, as it refuses every stream of a context in error, since the driver retires every earlier fence of the timeline with the answer and the renderer's work behind them may still be pending; a response with data or an error unfenced completes at once and rings the driver, which waits for those, while a bare OK rings at the end of the pass. A fence the renderer refuses to make is logged as `backend: fence: refused: id N of context C, ring R: error E: ...`, and its command stays held: a later fence on its timeline retires it, or the backend asks the renderer again on each turn while it is the newest command held there. `CTX_DESTROY` answers every command held on the context's rings, its fence taken or refused, since virglrenderer frees a destroyed context's fences without retiring them. The completions, the table of fenced commands and the used rings are under the device's lock, since a fence's completion comes from the renderer's threads; the serving thread holds it only between its calls to the renderer, and is the only thread that holds a command, so a fence it asks for without the lock is still that of the newest command it held. Before the pass, and after each command for the entries that came meanwhile, the device looks ahead at the control queue: a resource's first `VGS_CMD_BACKING`, unfenced, whose id the table does not hold and whose only earlier entry not yet served that names it is its unfenced RESOURCE_CREATE_2D or _3D, runs with that create ahead of the entries before them, which, made before the resource, cannot name it, and its answer goes out at once, so that a guest's create and map wait for the backing's own time and not for the submissions queued before it. An id still in the table, as through an UNREF not yet served, keeps its order, and so does a fenced create, whose answer would signal every earlier fence of its timeline; a create goes ahead only while the table has room for it after every earlier create not yet served and without the UNREFs queued before it, so that neither it nor an earlier create fails where both would succeed in order, and nothing goes ahead of a chain that breaks the rules. The look-ahead consumes the avail entries in order, as far as a queue's length past the in-order pass, keeping each chain's head, and the pass runs them from those heads: a guest that has the answers of the entries served ahead may reuse their descriptors and ring places, and the entries it has not yet seen consumed are then only those of chains it has no answer for, which the ring's size bounds. Between two control commands the renderer polls (`poll`). The cursor queue's chains complete empty. A transport fault stores `NEEDS_RESET`.

[`backend/virgl.c`](backend/virgl.c) drives libvirglrenderer as QEMU's `virtio-gpu-virgl.c` does: EGL on GBM over the KMS device, or surfaceless without one, with Venus through the render server unless `-x`. It sets `VIRGL_RENDERER_USE_EXTERNAL_BLOB`: a persistent GL buffer must use exportable GBM storage, since the page-list transport pins a descriptor and cannot share a pointer from `glMapBufferRange` in the backend. Without the flag, virglrenderer prefers `glBufferStorage`, whose buffer has no descriptor to export, so Mesa's persistent staging allocations fail. With the flag virglrenderer offers `VIRGL_CAP_ARB_BUFFER_STORAGE` only on a GBM device whose backend is named `i915` or `amdgpu`, as minigbm names them (`vrend_renderer.c:12703-12712`); Mesa's libgbm, which Debian's virglrenderer uses, names its backend `drm` (`src/gbm/backends/dri/gbm_dri.c:1196` in Mesa 25.0.7), so the capability is withheld on the Lenovo's i915 as in QEMU's VM, which has no render node. Mesa in Rach2 then asks for no persistent buffer, and its OpenGL stops at 4.3, since 4.4 needs buffer storage. A persistent buffer a guest asks for anyway is a GBM buffer where a render node opened, and has no storage where none did, from the rebuild's check of the GBM device. The capsets offered are those virglrenderer gives a size, virgl's two, Venus's unless `-x`, and DRM's with `-N`. A 2D resource is created as QEMU creates one, a render target with its first row at the top. After each context's create the backend makes vrend's context 0 current (`virgl_renderer_force_ctx_0`), as QEMU does before every command: `vrend_create_context` leaves the new context's GL context current without recording it, so the next submission of the context vrend last ran would skip its switch and run in the new GL context, which has none of its vertex arrays, and its first draw would fail with `GL_INVALID_OPERATION` ([`dev-log/84-locks/upstream.md`](../../dev-log/84-locks/upstream.md#virglrenderer-leaves-a-new-contexts-gl-context-current-without-recording-it)). Fences retire through virglrenderer's callbacks, on the global timeline or a context's ring, under `VIRGL_RENDERER_ASYNC_FENCE_CB`: vrend's sync thread waits on each GL fence in turn and calls back as it signals, as do each Venus context's and native context's own threads, and the callback completes the fenced commands and rings the driver at once, under the device's lock. vrend's commands stay on the serving thread, whose GL context they need, in each context's order. A fence that queries wait on holds vrend's sync thread until the serving thread polls virglrenderer, which it does between two commands when virglrenderer's descriptor is readable. When vrend's sync thread does not start, which leaves it no poll descriptor, the renderer starts again without the asynchronous callbacks or the thread and polls its fences, `backend: fences: no sync thread; polled`. Each new epoch stops virglrenderer and starts it again, rather than calling `virgl_renderer_reset`, which in 1.1.0 joins vrend's sync thread and starts none (`vrend_renderer_prepare_reset`, and the `TODO respawn sync thread` of `vrend_renderer_reset`), after which no asynchronous fence of vrend's would retire; the main loop reads the poll descriptor again on each turn. At exit the renderer stops, joining the threads that call back into the device, before the device's lock is destroyed. A read of a resource for the display gives the rows as a display shows them: a resource whose first row is the bottom one, as GL draws, is read from the mirrored rectangle and its rows reversed, as QEMU shows it.

[`backend/kms.c`](backend/kms.c) is the display, by atomic commits on the first connected connector, its crtc and its primary plane. A scanout's mode is one of its size, the preferred mode first, else the smallest that holds it, else the preferred one; the connector's preferred mode and EDID are what the device reports. A flush is shown one of two ways: directly, when `-d` is given and the resource's dma-buf is exactly the scanout's rectangle and the mode, imported as a framebuffer and shown through the plane with `reflect-y` when its rows are bottom first; otherwise copied into the dumb buffer not shown, which then is. The display's open of the card is DRM's master, and GBM has an open of its own, since GEM handles belong to an open file and the display closes those it imports. With `-w` each commit that shows a frame also attaches the writeback connector and waits for its fence, and the CRC of the frame's top-left corner, the scanout's size, is printed.

[`backend/vkprobe.c`](backend/vkprobe.c) is `-I`'s check of Venus's path: when a resource is attached to a Venus context, which virglrenderer passes to Venus's render server as a dma-buf, the backend exports the same dma-buf, imports it into Vulkan's device memory on the first device that imports dma-bufs, lavapipe in the VM, maps it and prints the CRC of its rows.

[`backend/main.c`](backend/main.c) takes the region and its doorbells. Through the module it binds an eventfd to each vector and rings with `VGPUSHM_IOC_RING`. Through vfio it opens the device's IOMMU group in a type-1 container, maps BAR 2, turns bus mastering on, reads IVPosition and rings by writing BAR 0's registers through the device, and binds the two MSI-X vectors to eventfds with `VFIO_DEVICE_SET_IRQS`. The loop steps the device until it is idle, then sleeps on the eventfds and virglrenderer's poll descriptor, a second at most with doorbells accepted and a millisecond without them, or while a fence is pending when fences are polled. A thread of its own, with every signal blocked, moves the region's heartbeat each second (`VGS_TF_BEAT`, `vd_beat`), so that Rach2 takes the backend for gone when its process stops for 30 s, as SIGSTOP stops every thread, while a serving thread that spends that long in one command, a pin or a renderer's call, is still waited for, as Linux's guest waits out a host's long command. The thread stops, and the main thread waits for it, once the serving loop ends, so that the count does not outlive the serving. Under `-H`, SIGUSR2 has the serving thread hold the next new backing 45 s (`VR_HOLD_S`) before it makes it, which Rach2's test of a long command asks for, and SIGWINCH has it refuse the next new backing, `backend: back: resource N: refused: BYTES bytes: as asked`, which its test of the heap's backing asks for. [`backend/stall.c`](backend/stall.c) is the stall's report: the loop notes each turn, a thread of its own watches the turns, and the loop itself watches its oldest fenced command.

### Page lists

With `VGS_TF_PAGES` accepted, RESOURCE_MAP_BLOB of a mappable blob of host memory is answered with the blob's VM-physical pages from the page its offset names ([virtio](../../rach2/sys/virtio/Readme.md)), as many runs as the chain's writable bytes hold. At the first ask the backend has virglrenderer export the blob's memory, a dma-buf or a memfd as Venus and the shared-memory blobs give it, reads its cache type, and pins it whole through the module for the driver's epoch; each ask reads the runs from the pin. UNMAP_BLOB, UNREF and a new epoch let the pin go, and so does an ask whose page list fails, since the driver sends no UNMAP_BLOB for a map it was refused and a pin kept until the epoch's end would take one of the table's places for good. A blob that is not a mappable one of host memory is refused with `ERR_PARAMETER`, and one whose memory virglrenderer cannot export, or the module cannot pin, with `ERR_UNSPEC`, which fails the driver's creation of the blob. `-v` prints `backend: pin: resource ID, fd type T, KIND, N pages` at each pin, and a refusal prints its reason; an answer holds as many runs as the driver's pages for it hold, up to 3836 in Rach2's 60 KiB, at most 4092 in the backend's largest response of 64 KiB, which holds no more after its 56-byte header (`VGS_PAGES_OFF`), below the 4096 `VGPUSHM_IOC_PAGES` gives at once; no line is printed for each answer, since the VM's serial console is slow; the `backend: result:` lines add the maps answered, the backings answered, the pins made, the backings among them, those refused and let go of, and the module's pin counts.

With `VGS_TF_BACKING` accepted, which the backend offers with page lists, a resource of RESOURCE_CREATE_2D or RESOURCE_CREATE_3D is backed by the VM's own memory, not the region's heap, so that a buffer is bounded by the VM's memory as a Linux guest's is by its RAM: Rach2 sends `VGS_CMD_BACKING` with the backing's size in place of ATTACH_BACKING, and at the first ask the backend has the module make a shmem file of that size and pin it whole for the driver's epoch with `VGPUSHM_IOC_BACKING`, which brings in its pages zeroed and frees the file and its pages again if the pin fails, maps it, and attaches the mapping to the resource as its one iovec, as QEMU attaches a guest's pages; each ask is answered with the runs of the pin as MAP_BLOB's is. DETACH_BACKING, UNREF, a refused ask and a new epoch detach the backing, let the pin go and unmap it. A backing past the 1 GiB of the module's largest pin is refused with `ERR_PARAMETER`, and one that would leave the VM less available memory than an eighth of its own, as `/proc/meminfo` counts it, with `ERR_OUT_OF_MEMORY`, a MemAvailable of 0 among them, which Linux reads once the free pages are down to its watermarks, so that a guest that asks for more than the VM has gets an error answer before the pin's reclaim stalls the VM and every answer with it; Rach2 then attaches pages of the heap instead. A RESOURCE_CREATE_2D or RESOURCE_CREATE_3D is judged by the same counts, its storage bounded as a buffer's width or a texture's texels at the most bytes a texel its format can have, 32 for a format of 64-bit channels and 16 for any other, summed over its mipmap chain, each level's width, height and a 3D texture's depth half the last's, by its layers, six for a cube, and its samples, and rounded up to a page: past the room it is refused with `ERR_OUT_OF_MEMORY` and `backend: create: resource ID: refused: N bytes: no room in the VM's counts`, since the renderer takes a resource's storage from the VM's memory, which i915 fills and does not give back while the resource lives, and the OOM killer then ends the process that maps the most, the backend. Creates and backings are judged against one account: the room is MemAvailable less an eighth of the VM's memory and less the bytes of the GPU objects the renderer holds that have no pages yet, which i915 makes at an object's first use, not at its creation, so that a texture made and not yet drawn holds its place against the backings and creates after it. Those bytes are `drm-total-system0` less `drm-resident-system0` in the fdinfo of each DRM descriptor of each process of the backend's cgroup, which holds the render server and its workers too, as Linux's DRM usage stats give them per client, each client that `drm-client-id` and `drm-pdev` name counted once however many descriptors share it. They are read before MemAvailable, so that an object made resident between the two readings is counted twice, never not at all. Each create and backing reads them afresh, since the renderer also makes GPU objects at submissions, at blob creates and in Venus's workers, which only a new reading counts. A reading stats each descriptor's link in `/proc/PID/fd` and reads the fdinfo only of a character device of DRM's or accel's major, of every such descriptor, since another thread may close one and reuse its number between two reads, so that a match of descriptors to the files already read could skip a client: a reading of every descriptor's fdinfo took 2.0 to 2.5 ms of the serving thread on the Lenovo under Crysis, by perf's samples half of it in i915's fdinfo, which the backend's two clients gave through seven descriptors, and half in the other descriptors' fdinfo and the reading's own work. A descriptor or process that ends during the reading adds nothing, and any other failure to read them, for want of memory or descriptors among them, counts as no room, with `backend: counts: PATH: ERROR`. With no GPU they are none, since llvmpipe fills a texture's memory at its create. The bound judges only the create itself, since once the resource is made its storage is in those counts, so an error of one create lies within the eighth the room keeps. Rach2, as Linux, logs an error answer to a create, and the guest's later commands on the resource fail. The backend sets glibc's mmap threshold to 1 MiB, so that the textures llvmpipe frees go back to the VM at once and the counts do not refuse a create that memory could hold. A `/proc/meminfo` that cannot be opened for want of memory, or whose read fails, counts as no room. `backend: back: resource ID: refused: N bytes: STEP: ERROR` says why, STEP the one that refused: `as asked`, by SIGWINCH under `-H`, `no room in the VM's counts`, `the pin`, the module's backing, whose allocation fails with `ENOMEM` when reclaim cannot meet it, which is answered with `ERR_OUT_OF_MEMORY` as well, `the mapping`, or `the attach`. The table holds 8192 objects, 8128 resources and 64 contexts, since a program such as piglit's streaming-texture-leak keeps every buffer Mesa staged an upload in alive until its next submission.

### The check

The peer's frame comes from `peer -W`, a stream that clears a 1024 by 768 scanout render target and draws a box off its centre; the peer reads it back and computes the CRC of its rows as stored and as a display shows them. vkms's writeback copies the composed frame, so its CRC tests the whole display path, the mode, the copy or the direct scanout and the reflection, against what the peer drew.

## Limits

* vfio-pci maps BAR 2 uncached, so the vfio way reads each chain from the region at the speed of uncached memory, not of RAM as through the module.
* The vfio way needs QEMU's intel-iommu with `intremap=off` and the VM's vfio to take unremapped interrupts: with remapping, QEMU 10.2.1's ivshmem routes its vectors before the VM programs them, which remapping refuses, and no doorbell reaches the VM ([upstream.md](../../dev-log/83-testbed/upstream.md)).
* The backend shows one scanout, and the cursor queue's commands are taken but not drawn.
* `RESOURCE_MAP_BLOB` is served only with page lists, through the module: the region is the only memory the two sides share otherwise, and vfio's way pins nothing.
* A pin holds a shmem file's pages by a reference each, which keeps them from being freed or moved while pinned, and marks them dirty as it lets go, as i915 does with its shmem pages. Unlike i915 it does not mark the file unevictable, since the file is virglrenderer's, so reclaim still scans the pinned pages, and keeps them for their extra reference.
* A pin is at most 1 GiB, so a Venus allocation larger than that cannot be mapped, and the backend answers its map with `ERR_UNSPEC`, and a resource's backing larger than that comes from the region's heap.
* The VM's memory holds both the backings and the VM's own GPU allocations. `bed-shm.sh` defaults to 2 GiB, and native `bed/shm` gives the VM the machine's MemTotal less 3 GiB for Rach2 and its session, at most 16 GiB, 13,175 MiB on the Lenovo ([tests/native](../../tests/native/Readme.md)). piglit's streaming-texture-leak keeps some 1,250 textures and the 4 MiB staging buffer of each upload until Mesa's command buffer fills, 4.93 GiB of backings, and textures, which i915 keeps in the VM's memory: on the Lenovo a VM of 13175 MiB ran out with i915 at 8450 MiB and the backings at 4759 MiB and the test still growing, so its `# need 16384 MiB` in the bed's piglit list skips it in a smaller VM. Under llvmpipe, while the backend's C library kept the textures llvmpipe freed, it ran a VM of 14 GiB out of memory in QEMU, and no run has measured it since, so the list's `llvmpipe never` skips it there, and it is not in bed-shm's readback row, whose VM has 2 GiB ([dev-log/84-locks/bed-memory.md](../../dev-log/84-locks/bed-memory.md)).
* The dma-buf pin reads each page from the importer's scatterlist, which dma-buf scrambles under `CONFIG_DMABUF_DEBUG`, so it needs that option off, as Debian 13's kernel 6.12.115+deb13.1 has it, and refuses with `EOPNOTSUPP` otherwise.
* The VM renders GL on llvmpipe and Venus on lavapipe unless it has an Intel GPU.

## Tests

`sh bed/vm/image/vm.sh check`, `check -V` and `check -b` are the backend's checks against the peer; they run no suite. The device's parser is fuzzed by [`tests/fuzz/vgpudev_fuzz.c`](../../tests/fuzz/vgpudev_fuzz.c), which the host suite replays over its corpus.

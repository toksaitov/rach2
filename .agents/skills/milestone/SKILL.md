# Milestone

The manager runs a milestone as the Milestones, Work and Testing sections of `AGENTS.md` say. This skill has the commands and the order of the steps.

## The plan

* Read the owner's goal, the code it touches and what earlier milestones in `dev-log/` found, and the research already in the milestone's own directory, such as `dev-log/76-graphics/research/`. Research the owner asked for goes to the owner whole.
* Measure what the plan needs from a machine before relying on it: that a tool, an accelerator or a device exists and works there.
* Write `dev-log/NN-name/plan.md` as the Milestones section of `AGENTS.md` says. Split so that tasks never share files, and name what each task that must wait waits on. Put a step on the Lenovo at the end of its task, and split a task that would go on with much code after one. Name the checkpoint slice: the cases, suites and runners, in QEMU on WSL and on the Lenovo when the milestone touches its hardware, that prove the goal in minutes. Milestones that build on each other's code form a stack on one branch, which the plan names with its milestones.
* Start the three reviews at once, each on its own with the questions `AGENTS.md` gives: Codex with `codex exec -s read-only` in the checkout, as the `codex-exec` skill says; and agy and Muse as the `second-opinion` skill says. A reviewer that answers with its usage-limit message is named to the owner as missing, and the plan goes on without it.
* On the owner's approval:
  * make the GitHub milestone: `gh api repos/toksaitov/rach2/milestones -f title="NN name" -f description="Branch: BRANCH"`, BRANCH being `milestone/NN-name`, or for a later milestone of a stack the first one's;
  * cut the branch from master and push it, unless the milestone joins a stack's branch;
  * title each task and subtask in one short plain line that says what the work does, the plan's id after it, such as "Submit GPU work to the Intel driver (78-5b)";
  * file each task as an issue in the milestone, and each subtask as an issue in the milestone linked under its task with `gh api repos/toksaitov/rach2/issues/TASK/sub_issues -F sub_issue_id=ID`, ID being the subtask's `id`, not its number;
  * file a task that only ends on the Lenovo with no `owner-only` label, since its worker adds the label at that step; only a task that is nothing but a step on the Lenovo is filed with it;
  * mark each task that waits on another as blocked by it with `gh api repos/toksaitov/rach2/issues/N/dependencies/blocked_by -F issue_id=ID`, ID the blocker's `id`, so that `board.sh next` offers it only once the blocker is closed;
  * order the cards while they are not yet Ready, with `sh tools/flow/board.sh move N [AFTER]`, which puts N right after AFTER, or first: the tasks that others wait on first, and the tasks that need the Lenovo early. The board's own workflows add each new issue to it and set a closed one Done;
  * then run `sh tools/flow/board.sh ready N...` for the tasks, and read its exit status: it adds an issue the board lacks and fails loudly when it cannot set one Ready.

## While it runs

* Start what is not running: the team's worker loops and the owner's Codex loop, as `tools/Readme.md` says, and up to three loops of the manager's own, each in a worktree of the main checkout with a state directory of its own: `git worktree add --detach build/worktrees/mK origin/master` and `env -u TMUX tmux new-session -d -s mK -c build/worktrees/mK "RACH2_TESTING_COPY=/home/testing/rach2/build/worktrees/mK sh tools/flow/worker.sh -s CHECKOUT/build/flow/mK"`, K from 1 to 3 and CHECKOUT the main checkout's path. They take tasks as every loop does, `owner-only` ones among them, and `linux-host` ones, which build the GNU layer in their copy on the testing host, as the Codex loop does. `status.sh` lists them after the rows of `tools/flow/workers`, and says who holds the Lenovo's lock and since when, so that a lock left by a stopped loop is seen and removed.
* Keep `sh tools/flow/board.sh watch build/flow/watch` running at all times, in the background with the tool's own notice of each line it prints: in Claude Code, a Monitor. It prints a line as soon as an issue on the board gets a comment, is closed or reopened, gains or loses the label `owner` or `owner-only`, or is handed back. When the Monitor expires or the watch stops, arm it again with the same file, so that it goes on where the last one stopped. Pass each question to the owner and each hand-back to the chat at once; act on the rest as on the half-hourly check.
* Check with `sh tools/flow/status.sh` as often as `AGENTS.md` says, and read the board in the same look. Act at once: hand a task over from an account out of its limit or stalled, restart a stopped loop, free disk space, clear a stuck run or machine, put a wrong card right.
* A handover: first stop what writes the task, so that nothing changes the clone while the task moves. In the stalled account's loop state directory, `touch STATE/stop STATE/session.stop`, as `stop.sh` does, and signal nothing: the session's `session.pl` stops the session's group, TERM and KILL thirty turns later, and the loop ends once its session has, within five seconds of any wait, a usage limit's among them. Wait until `STATE/loop.live` is not locked, which `perl -MFcntl=:flock -e 'open(L, "<", shift) or exit 1; exit(flock(L, LOCK_SH | LOCK_NB) ? 1 : 0)' FILE` tells by exiting 0 while a process holds FILE, the loop's tmux session is gone, and `perl STATE/run/session.pl -q STATE/session`, the one decider of the session, prints `ended`. `lost GROUP` means a `session.pl` that was killed left its session, which may still run: list the group with `ps -A -o pgid=,pid=,args=` and the clone's processes with `stop.sh -n`, since a process may have left the group, stop what is left of the session, remove `STATE/session` and ask again; touch nothing in that clone until it prints `ended`. Then, in that clone, commit what is uncommitted on `task/N` with the message `Save unfinished work of task #N` and push it. If that push is refused because the worker had begun its final rebase, finish the task as the worker would have: compile, push to the milestone branch and close it. Otherwise release the task from that account, run there as `RACH2_WORKER_STATE=STATE sh STATE/run/board.sh release N`, which also empties the stopped loop's `STATE/issue` so that it does not take the task up again, and comment on it where the next worker should go on. Remove `STATE/stop` and start the loop again once its account has limit left.
* Keep the queue in order with `board.sh move` as tasks close and waits change; a card the owner moved, which the chat passes on, stays where the owner put it.
* A task handed back `owner-only` at its step on the Lenovo goes to a loop of the owner's as soon as the Lenovo's lock is free. One handed back with `trial` waits in Backlog for your go: read its readiness note and the diff, as the `machine` skill says, then say go on the issue and run `board.sh ready N`, or say on it what is missing, remove `owner-only` and set it Ready for any loop. Prepared steps may share one boot as that skill allows.
* A step on the Lenovo that is Ready while its lock is free waits for no loop's code: if no loop of the owner's takes it within ten minutes, run it yourself or hand it, as any handover, to the owner's loop that has done least on its task.
* Fold the owner's new requests and small fixes into an open task as subtasks; file a new task only for work of a task's size, and for each batch of a checkpoint's or the end's fixes, one task in the milestone with a subtask for each finding. Once a worker has taken a task, an addition goes in only as a subtask, never only in its body or a comment, which the worker read at its start and its finish does not check.
* When a long run starts, name its sign of progress and arm a check that fires on silence, in Claude Code a Monitor, besides the notice at its end.
* Send the chat a message at each step a person would want to know of, and at once for a failure or a big incident. While the owner discusses something with the chat, send only the end of the work, a failure or a big incident.

## The checkpoint

* A milestone of a stack has a checkpoint once every task of it is closed and on the branch; it runs while the other milestones' work goes on. A milestone that releases alone has none: its end follows at once.
* The stack's first `plan.md` keeps the reviewed head: the commit up to which Codex has reviewed the branch, `origin/master` before the first review. Have Codex review from the reviewed head to the branch's head with `tools/flow/reviewer.txt`, as the `codex-exec` skill says, @BASE@ the reviewed head, @TITLE@ the milestones whose tasks the range holds, as `milestone "76 display"` or `milestones "76 display" and "77 vgpu"`, and @PLAN@ their plans. A review that is split into passes runs at most three passes at a time, each sized to end without compaction. Record that head as the reviewed head when both answer. Run no check of your own on those commits until both answer; the workers' own boots of their tasks go on.
* Put their findings in one list in the milestone's `plan.md` and file them as one task of fixes. When that task is closed, have both review again from the reviewed head to the new head, which holds the fixes and whatever else reached the branch, and record the new reviewed head. A finding in what the slice runs is fixed and reviewed this way before the slice runs; one elsewhere joins the list of the milestone it belongs to.
* Then, with `/dev/udmabuf` present on WSL as the testing skill says, run the slice the plan names at the reviewed head, in a worktree of that commit through `tools/dev/testing.sh run`, in QEMU on WSL, and its trial boot on the Lenovo, under the lock, if the milestone touched the Lenovo's hardware. Read each result from the run's own output. Run more only when something looks wrong, and say why.
* A failure is fixed on the branch, reviewed as above, and the part of the slice that failed runs again at the new reviewed head.
* Record in the milestone's `plan.md` the reviewed head the slice ran at, what ran and its result, remove the Lenovo's lock if the checkpoint took it, and tell the chat. A checkpoint moves no master and closes no milestone.

## The end

* The end comes for a milestone that releases alone when its tasks are closed, and for a stack when each of its milestones has passed its checkpoint.
* List in one place, the last milestone's `plan.md`, every open card, known fault and pending request of the milestones, and fix them all in the first batch, so that nothing is found late. Make first the changes that force a rebuild or a new install: the build itself, the vendored projects, the GNU root and the Lenovo's image, so that a later fix costs only a rerun.
* With every task closed and on the branch, have Codex review from the reviewed head to the branch's head, or a lone milestone's whole diff from `origin/master`, with `tools/flow/reviewer.txt` and its placeholders filled as the checkpoint says, and run nothing on the branch until both answer. Put their findings in the same list, file them as one task of fixes, and have both review the fix commits when it is closed.
* Then rebase the branch onto master if master moved, and push it with `git push --force-with-lease origin BRANCH`, BRANCH as `board.sh milestone M` prints it, the one force push `AGENTS.md` allows; a conflict the rebase resolves is a fix and gets its own review. The end runs and the release take the head once, as M, the last milestone of the stack, with `-c N` for each other open milestone whose description names the branch.
* Then, on the Mac, run `sh tools/verify/hookcheck.sh range origin/master SHA`, which takes a minute or two and finds most of what the style run would, and the narrow proof of each fault the milestone set out to fix, on each machine it affects. A failure is fixed, reviewed, pushed to the milestone branch and proved again.
* Once those pass and none is still running, run `sh tools/flow/release.sh -p M SHA` at the branch's head. At once, it builds SHA for both architectures incrementally in a copy on the testing host, `build/worktrees/prepare` of the owner's, which it keeps between runs and checks out at SHA in place, and runs `tests/run style` and the host tests there, makes Windows' preparation in its copy and the Mac's in its own, as the release makes them, the tooling machines' GNU host checks among them, unless `tools/flow/machines` leaves those machines out, as it does until the owner says otherwise, and reports each machine's pass or the lines that say why it failed.
* Add every failure to that list, fix them in one batch, have Codex review the fix, push, and run `release.sh -p` again at the new head.
* Start the release from a tmux server with macOS's Local Network access, as `tools/Readme.md` says, since the Lenovo's part needs it. The release takes the Lenovo's lock itself when it reaches the Lenovo; while a task holds it, the release exits 75 and is started again once the task is done.
* Once `release.sh -p` passes and `/dev/udmabuf` is present on WSL as the testing skill says, start the release detached: `env -u TMUX tmux new-session -d -s rach2-release "sh tools/flow/release.sh [-c N]... M SHA >> build/flow/release/out 2>&1"`, with SHA on M's branch. Watch it as any long run. On a failure, act at once while the machines it does not touch keep running: reproduce it, fix it, have Codex review the fix, push NEWSHA to M's branch, and run `release.sh -r [-c N]... M NEWSHA`, with every `-c N` of the first release, which keeps the passes of the last record and runs only what failed, with the Lenovo's install and native cases as on every release. On a pass it has moved master, closed M and each `-c` milestone and archived their cards.
* Read the sweep's output, which the release keeps as `build/flow/release/*.sweep`, and record in the milestone's `plan.md` what was accepted: the commit, the runs and their results.

# Testing

## The testing host

* Every build, suite, full set (`tests/run all`) and analysis runs on the testing host: a Windows machine with an AMD Ryzen 9 7950X3D, 32 threads and 200 GB of memory, whose Windows Subsystem for Linux (WSL2) distribution, Ubuntu 26.04, has 128 GB of it. `tools/Readme.md` describes its setup.
* The distribution's disk is the file `D:\WSL\Ubuntu-26.04\ext4.vhdx`, which grows as the disk fills and does not shrink when files are deleted. To give freed space back to drive D:, run `fstrim /` in WSL, stop Docker Desktop with `docker desktop stop`, since it starts WSL again within seconds, and run `wsl --shutdown`. Copy the file, compact it with `Optimize-VHD -Mode Full`, and check it with `qemu-img check -f vhdx` before WSL starts: a compaction can leave block-table entries that point past the end of the file, and WSL then refuses the disk as corrupt. Start Docker Desktop again with `docker desktop start`.
* Before a machine runs the tests, `sh tools/setup/prereq.sh` checks it for every tool the build and the suites need and prints the commands that install what is missing, apart for this account, an administrator and a person at the machine; `--platform windows`, run in WSL, checks the Windows side of the testing host. "Setting up a machine" in `tools/Readme.md` has the platforms.
* Each person works in their own account there, named after their GitHub login and reached as `ssh rach2`, in a clone of their own. The account's `.bashrc` gives each run the person's share of the machine, a command sent over ssh included: 8 workers and 16 GiB of guest memory. The `ci` runners, `rach2-ci-1` and `rach2-ci-2`, have 12 workers and 24 GiB each. Each run claims a block of host ports for its network suites, so the clones and the runners can run the same suite at once; `tests/Readme.md` says how. The machine also runs Hyper-V guests for other work, so the full set runs only in a phase's full run, `full.yml`, which `tools/flow/release.sh` starts, or when the owner starts one. A full run runs on the one machine, and under the one accelerator, that `tools/ci/site` names at the commit it tests.
* A person's own computer, whatever its system, is only a terminal to the testing host. The computer the owner edits on builds only what editing needs: a compile or one host test. A run a person waits for, such as a suite, the host tests (`tests/run host`), a full set or `make analyze`, is never started on any of them. The rules below apply on the testing host unchanged.
* The owner reaches a copy of the tree at `/home/testing/rach2` from that computer through `tools/dev/testing.sh`, and each of the owner's worker loops a copy of its own, which `RACH2_TESTING_COPY` names. `testing.sh sync` replaces the copy with the computer's tree, `testing.sh run COMMAND` syncs and then runs the command there, as in `testing.sh run 'tests/run default'`, and `testing.sh sh` opens a shell there.
* On an enrolled host, the root `make` and `tests/run` admit each step separately. `testing.sh run` transports the command without enclosing it in a claim. A direct compiler or component-only build still needs the installed external launcher, as `tools/etude/Readme.md` specifies. Use `build` for a build or bounded host command, `legacy` for a command that may start suites, and `alone` for exclusive access. A shell command claims an ordinary test run's share, and the builds and suites it starts run inside it.
* That copy is never edited on the host, and it is synced before every run, which `testing.sh` refuses while anything still works in the copy or another of its callers holds it: `testing.sh run` does that itself, and a run started from `testing.sh sh` needs a `testing.sh sync` first. What `.gitignore` names is not sent, except the Doom WAD, so the host keeps its own `build/` and vendor trees. `tools/Readme.md` and the script's header say how the script reaches WSL and which rsync it needs.

## Running

* Before maintenance that stops the testing host or its CI runners, follow the accepted-job checks in `tools/Readme.md`. A runner can have an active job before its worker process starts; wait for the job to finish before stopping its service.
* Try a new row (one check in a suite), suite or tool small first, on the smallest inputs that exercise every step: a 64 MiB disk where the real one is 232 GiB. Start it at full size only after it passes there.
* Never build while a run is in flight. The suites read the kernel and the images from `build/`, so a build part way through changes what the remaining suites boot and what the finished ones were judged on, and the run is void. Check with `ps` for a run in progress before `make`, and wait for it or stop it deliberately.
* Watch a run in flight. Stream its log and act on the first failing line, since most failures come in the first seconds. Do not sleep until the run ends to find out how it ended.
* An agent starts a long run detached with `setsid nohup`, as `~/NAME.sh` in the account's home, writing its result lines, each beginning `NAME: `, to `~/NAME.out` and its work under `~/NAME/`, and watches it as a background command. From the owner's computer, `tools/dev/testing.sh wait NAME SEEN` watches such a run in the `testing` account. The wait returns on a new result line, the run's end, a stall of 15 minutes or 100 minutes gone; read what it printed, act on it, and wait again with the new count. A turn never ends while a run on the host has no wait watching it. A watch that woke only at a run's end, or one killed by the two-hour limit on a background command, left finished results unread for hours, and the owner had to ask.
* Read a run's rate at its first stage. A copy, a hash or a boot running at a small fraction of a similar step's earlier rate is a symptom: the emulator's USB storage moves tens of kilobytes a second where its IDE moves megabytes, a wrong block size makes a call per sector, a wait runs until its timeout expires. Stop the run, find and remove the cause, and only then start it again.
* Keep the whole output of a long run in a file on the host that runs it, and read all of it. Never pipe it through `tail` or `head`, which throws the failure away.
* Stop a run with SIGTERM, so its cleanup releases what it has taken. Before starting it again, wait until every process of the old run has exited, since the old run's cleanup would otherwise remove files of the new one, and look for anything it left, such as a lock file or a mounted image.
* Run the suites a step needs as one `tests/run A B C`, which pools them across the host's threads. A script that calls `tests/run NAME` once for each runs them one at a time and leaves the host idle: on 2026-10-04 that put some fifty suites on course for four hours.
* Resume a failed run at the failing step: rebuild what changed, run the suite that failed, and run the others again only when the change could have touched them. Start work that does not depend on a running job beside it.
* Believe a number only with the binary that produced it. `make` does not rebuild the recovery kernel or the install stick, so a measurement on a stick, an ISO or a recovery boot first checks that the artifact has the change: its timestamp against the source's, or a string the change added.

## Writing a suite

* Check a published native program through its declared native file path. MSYS existence checks may resolve a suffixless name to an unrenamed `.exe`.

* Copy a path returned from a rotating or static buffer into caller-owned storage before retaining it across loops or calls that reuse that buffer. When one fixture fails this way, inspect its sibling fixtures for the same lifetime error.
* Use directory predicates for directory entries and regular-file predicates for byte length. A fixture that ages inputs must restore and check their timestamps after its last write or copy.
* Derive exact screen text from the pinned program's complete output. When a screen wait fails, preserve the whole pane and distinguish missing output from an expectation that differs from the program's wording.
* When changing a private function or type, search the fixtures that include its implementation as well as ordinary callers. Update those fixtures before the combined build, and include them among the affected checks.
* When a fixture compiles from a source archive, add every new local header to the archive's inputs as well as the host build's dependencies. Follow the included headers too. A compile from the checkout does not check the archived source set.
* A test that kills a controller without cleanup kills and reaps it before closing its pipes. Closing them first can let the controller detect a lost connection and clean up the processes that the test needs orphaned.
* A suite judges what the kernel counts, never the clock, and sets no time limit of its own. Etude stops a case only when it has made no progress for longer than the case's history on that machine allows. A time is printed for the record, not judged.
* A boot identity must agree across processes, survive wall-clock corrections and change at another boot. Use the platform's boot token or loader sequence. A reported boot wall time is not an immutable identity. Check the native value and the rejection of a different boot before a long measurement.
* What would make a row slow (a spin, a wait, a walk over a list, a call per page) is counted by the kernel, and the row checks each count against a bound that is the same on every machine. Where the kernel has no counter for it yet, a multiple of a baseline measured in the same boot is the last resort, and each such row is listed with its reason.
* A suite or test script removes its scratch on every exit path, as the Testing section of `AGENTS.md` says. Install the exit trap before the first `mktemp`, with the variable empty until then, so that an early exit removes nothing; in the trap stop and wait for the children, restore the sources, and only then remove the scratch, guarding each removal, as `[ -z "$work" ] || rm -rf "$work"`. Never put a variable that may be empty in front of a path or a glob in an `rm`. Python removes its directories in `finally` or with `tempfile.TemporaryDirectory`. Name scratch under `${TMPDIR:-/tmp}` `rach2-NAME.XXXXXX`, or give Python the prefix `'rach2-NAME.'`: the manager's sweep (`tools/flow/scratch.pl`) removes what a killed test left only under a stem that begins with `rach2`. A run on the testing host that leaves scratch fills its `/tmp`, which is its memory: on 2026-10-17 the host held some 2,400 directories that tests had left, 7 GiB of them.

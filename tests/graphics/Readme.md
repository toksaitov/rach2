# Graphics tests

The machines of the graphics tests: the QEMU display profiles that Rach2 and its Linux reference boot alike, the accelerators they run under, the Debian 13 reference and builder guest in the same QEMU, and the environment each run sets inside its guest. Every graphics result of Rach2 is judged against the Debian guest's in the same profile, by case and by count, never by the clock.

## Running

The Debian guest is fetched and prepared once for each clone, and each run boots a new copy of it:

    sh tests/graphics/debian-ref/debian-ref.sh fetch
    sh tests/graphics/debian-ref/debian-ref.sh prepare
    sh tests/graphics/debian-ref/debian-ref.sh run -p virtio-vga -g conformance 'lspci -nn'

`fetch` downloads the image that [`debian-ref/image`](debian-ref/image) pins and checks its size and SHA-512. `prepare` boots it once with a cloud-init seed, whose `network-config` is empty, as [`debian-ref/setup.sh.in`](debian-ref/setup.sh.in) says: it points apt at Debian's snapshot of the pinned date, installs [`debian-ref/packages`](debian-ref/packages), Mesa 25.0.7-2+deb13u1 among them, and Mesa 26.1.6's Venus driver, builds vkms, turns cloud-init off so that every later boot is the same, and powers off; the result is `prepared.qcow2`, read-only. It takes a few minutes on the testing PC, most of them apt's downloads. `run` boots an overlay of the prepared image, copies [`guest-env.sh`](guest-env.sh) to `/tmp/guest-env.sh`, runs the command in sh as the user `gfx` over SSH with that file sourced, powers the guest off, removes the overlay and exits with the command's status. Its options are the display profile (`-p`, `std-vga` by default), the CPUs (`-c`, 8), the memory in MiB (`-m`, 8192), the run's class (`-g`, `performance`), `-d` for a Done's run, `-r FILE` for the record, `-i FILE` for a file copied to the guest's `/tmp` before the command, and `-o FILE` for one copied from the guest's `/tmp`, by its last component, once the command has succeeded; each may be given more than once. `prepare` keeps the image's key beside it, `prepared.qcow2.key`, the SHA-256 of the seed's files, the image's pins and the Venus driver's pin; `prepare -n` prepares only when no prepared image of the tree's key exists, as a build that uses the guest does, and `run` refuses an image of another key ([IGT's tests](../../vendor/gnu/Readme.md#igts-tests)). The images and the key that logs in are in `build/cache/debian-ref` of the main clone, which its worktrees share, or in `DEBIAN_REF_CACHE`.

A run on a machine with an installed site policy is a claim of the site's ledger, as [Admission](#admission) says; `-l` marks a light guest. [`capture/drmcapture.c`](capture/drmcapture.c) reads the frame a card scans out and prints its CRC-32, the same on both sides for the same frame:

    sh tests/graphics/debian-ref/debian-ref.sh run -p std-vga -c 2 -m 2048 -l \
        -i tests/graphics/capture/drmcapture.c \
        'cc -std=c99 -O2 -o /tmp/drmcapture /tmp/drmcapture.c && sudo /tmp/drmcapture -p'

On Rach2 it is `/drmcapture` of the test image, which `tests/Makefile` builds from the same source against the ported musl.

Rach2's run scripts take the same profiles: `DISPLAY_PROFILE=virtio-gpu ARCH=x86_64 sh rach2/run.sh os-simple` boots with that display in place of QEMU's default VGA ([rach2/qemu_devices.sh](../../rach2/qemu_devices.sh), [rach2/run.Readme.md](../../rach2/run.Readme.md)). A machine case names its profile in its QEMU profile's `display` ([etude's display profiles](../../tools/etude/Readme.md#display-profiles)).

The browser runners, [`runners/webgl.sh`](runners/webgl.sh) and [`runners/video.sh`](runners/video.sh), run inside a guest, Rach2's or Debian's. [`runners/debian.sh`](runners/debian.sh) runs one in the Debian guest and keeps its output, as the stored references were made:

    sh tests/graphics/runners/debian.sh webgl OUT -b chromium -v 2.0.1 all
    sh tests/graphics/runners/debian.sh video OUT -b firefox h264-1080p.mp4 vp9-1080p.webm
    sh tests/graphics/runners/debian.sh clips

The display and GL runners, [`runners/igt.sh`](runners/igt.sh), [`runners/modetest.sh`](runners/modetest.sh), [`runners/piglit.sh`](runners/piglit.sh) and [`runners/glmark2.sh`](runners/glmark2.sh), run the same way:

    sh tests/graphics/runners/debian.sh igt -p none OUT kms_atomic
    sh tests/graphics/runners/debian.sh modetest -p std-vga OUT
    sh tests/graphics/runners/debian.sh piglit OUT all
    sh tests/graphics/runners/debian.sh glmark2 OUT

A runner's command takes the profile (`-p`, `virtio-vga`), the CPUs (`-c`, 4) and the memory (`-m`, 8192 MiB) before OUT, and the runner's own options after it; each boots the guest as a Done's run, of the performance class for glmark2 and the conformance class for the others, copies in the runners and `igt-76.list`, and what the runner needs: for `webgl` the pinned suite from the GNU layer's cache, for `igt` the IGT stage, which it builds with `make ARCH=x86_64 gnu-igt` when the tree has none, with Debian's `intel-gpu-tools` for its libraries and Linux's sw_sync, which [`debian-ref/sw_sync.sh`](debian-ref/sw_sync.sh) builds as a module from the guest kernel's own source and loads, since Debian's kernel has none (CONFIG_SW_SYNC is not set, and it is a boolean), for `modetest` `drmcapture`, compiled there, and for `piglit` Debian's `piglit`; it installs a package from the snapshot for that boot alone, so that the prepared image stays the one every worktree shares. `igt` and `modetest` run their runner as root, with vkms loaded in the profile `none`, and it puts the runner's output in OUT with its `status`. `clips` makes the six clips in the build cache of the main clone, `build/cache/graphics-clips`, unless they are there already, and `-t TAR` also writes them as an archive. On Rach2 the same runners are the `webgl` and `video` suites, `tests/run webgl` and `tests/run video`, a case for each chunk or clip, such as `machine.webgl.chromium-webgl2-03` or `machine.video.firefox-av1-1080p` ([Browser runners](#browser-runners)), and the others the `igt`, `modetest`, `piglit` and `glmark2` suites, such as `machine.igt.kms_atomic-vkms`, `machine.modetest.std-vga`, `machine.piglit.glsl-1.10` and `machine.glmark2.wayland` ([Display and GL runners](#display-and-gl-runners)).

[`runners/deqp.sh`](runners/deqp.sh) runs dEQP-GLES2, GLES3, GLES31 or VK of VK-GL-CTS from `/opt/vk-gl-cts-VERSION` inside a guest, Rach2's GNU root or one with the same build, every Nth case of a list, and [`runners/judge.py`](runners/judge.py) compares its results with a reference's by case:

    sh tests/graphics/runners/deqp.sh -v 1.4.7.1 -e 200 -o OUT gles2
    sh tests/graphics/runners/deqp.sh -v 1.4.1.1 -e 500 -l LIST -f FLAKES -o OUT vk
    python3 -I tests/graphics/runners/judge.py deqp REF/results.csv.gz OUT/results.csv.gz OUT/flakes

Its options are the release (`-v`, 1.4.7.1, the Lenovo's references, or 1.4.1.1, Mesa 25.0.7's CI pin), every Nth case (`-e`, 1), the case to count from (`-s`, 1), the processes at once (`-j`, 4), a list of one case a line in place of the release's mustpass list (`-l`), a file of extended regular expressions naming flakes (`-f`), the Vulkan ICD file to use alone (`-i`), the release's directory (`-c`), the output (`-o`, `.`) and `-q` to keep dEQP's `.qpa` logs; dEQP options may follow the suite ([The dEQP runner](#the-deqp-runner)). `debian.sh deqp` runs it in the Debian guest, with the release `-v` names from the GNU layer's build, which it makes with `make ARCH=x86_64 gnu-vk-gl-cts` when the tree has none, and the Venus lists in the guest's `/tmp`, as the Venus references were made:

    sh tests/graphics/runners/debian.sh deqp -p venus -c 8 OUT -v 1.4.1.1 \
        -i /usr/share/vulkan/icd.d/venus_icd.x86_64.json \
        -l /tmp/deqp-vk-lavapipe.txt.gz -f /tmp/deqp-vk-lavapipe.flakes vk

On Rach2 the `venus` suite, `tests/run venus`, runs the same lists through Venus, a case such as `machine.venus.smoke` or `machine.venus.fraction-3`, and kills the host's render server under it in `machine.venus.device-lost` ([Venus's dEQP](#venuss-deqp)).

[`runners/vkcube.sh`](runners/vkcube.sh) presents vkcube to a Weston of its own on the guest's card, as root, holds it at two frames and reads each back inside the guest; `-i` names the Vulkan ICD file to use alone and `-o` the output. `debian.sh vkcube` runs it in the Debian guest, as the reference was made, and the `vkpresent` suite, `tests/run vkpresent`, on Rach2, as the case `machine.vkpresent.vkcube` ([vkcube presenting](#vkcube-presenting)):

    sh tests/graphics/runners/debian.sh vkcube -p venus -c 8 OUT \
        -i /usr/share/vulkan/icd.d/venus_icd.x86_64.json

[`runners/games.sh`](runners/games.sh) plays a native game's fixed replay, SuperTuxKart's profile race or 0 A.D.'s visual replay, from the replays the games layer installs, as an ordinary user, and records every frame's time, as Linux's reference runs on the Lenovo took them; `-o` names the output, `-s` the fullscreen size in place of 1280x800, `-t` the race's seconds in place of `supertuxkart.args`'s 90 and 0 A.D.'s window in place of 150 s, `-r` the replays' directory in place of `/usr/share/games/rach2/replays`, and `-d` draws on the caller's Wayland display in place of a headless Weston of its own, as on the Lenovo. The `games-native` suite, `tests/run games-native`, runs its small form, `-s 640x400 -t 10`, on Rach2, a case for each game, `machine.games-native.supertuxkart` and `machine.games-native.0ad` ([Native games](#native-games)):

    sh tests/graphics/runners/games.sh -o OUT supertuxkart
    sh tests/graphics/runners/games.sh -o OUT 0ad

## Results

Each Debian run writes a record, to the file `-r` names or to standard error as `debian-ref: record:` lines, one `NAME VALUE` a line: `profile`, `firmware` (`seabios` or `ovmf`), `accelerator`, `cpu` (QEMU's processor), `cpus`, `memory_mib`, `qemu` (its version line), `image` with its SHA-512, `snapshot`, and the guest's environment as `env NAME=VALUE` lines that `graphics_env` prints. A Rach2 case's history records its accelerator, and its QEMU profile, with the display and the CPUs, is in the profile's digest ([etude's Readme](../../tools/etude/Readme.md#the-history-store)).

A browser runner writes to its output directory `record`, `results`, its result lines, and a file for each chunk or clip. Its record begins with the guest: `runner`, `system`, `kernel`, `cpus`, `memory_kib`, `mesa` (the version of Debian's Mesa, from dpkg, or on Rach2, which has no dpkg database, from the package's changelog), `iommu` (the units of `/sys/class/iommu`, the count of `/sys/kernel/iommu_groups` and the kernel's IOMMU words), `cache mesa` (the shader cache's files and whether it was emptied), `cache browser` (a new profile for each browser), `size` (Weston's 1280x800), `load start` and `processes start`, and `graphics_env`'s `env` lines; then the case, `warmup`, `repetitions`, the `browser`'s version, its `switches` or Firefox's `prefs`, the `compositor`, the suite's `list` with its length and SHA-256 or each `clip` with its codec, size and SHA-256, and the `renderer` of a WebGL 1 and a WebGL 2 context; and ends with `load end` and `busy`, the share of the guest's CPUs busy from start to end. `kernel_before` and `kernel_after` retain `/proc/stat` around the run, including Rach2's scheduler, timer and VM counters. `debian.sh` adds the guest machine's lines of `debian-ref.sh`'s record as `guest ...` and the host's as `host`, `host_load` and `host_claims`, the claims in etude's admission ledger, the other runs on the host. A Rach2 case keeps the same output as the evidence `out.tar.gz`, and the host's lines as `host-record`.

`webgl.sh` prints a line for each chunk:

    webgl: result: chromium 2.0.1 chunk 0 of 12 pages 250 pass 249 fail 1 timeout 0 crash 0 hung 0 skip 0 empty 0 notrun 0 rerun 1 subtests passed 26567 failed 2

and writes `BROWSER-VERSION-NN.pages`, a line a page in the list's order: `INDEX STATUS PASSED FAILED SKIPPED TIMEOUTS FIRST URL`, where STATUS is `pass`, `fail` (a subtest failed), `timeout` (the harness's 20 s limit), `skip`, `empty` (no result at all), `crash` (the browser ended while the page ran), `hung` (it stopped) or `notrun`, and FIRST is the first run's status of a page that was run again. `video.sh` prints a line for each clip:

    video: result: chromium h264-1080p.mp4 codec h264 size 1920x1080 frames 300,300,300 dropped 0,0,0 corrupted 0,0,0 decoder FFmpegVideoDecoder errors 0 browser done

and writes `BROWSER-CLIP.plays`, a line a play, `REP WARM TOTAL DROPPED CORRUPTED SECONDS WIDTHxHEIGHT ERROR` (`-` for a count the browser does not give, as Firefox gives no corrupted frames), and `BROWSER-CLIP.decoders`, the decoder's name as the browser gives it. A runner exits 0 when every page or play ran; a failed page is a result, which [`runners/judge.py`](runners/judge.py) compares with the reference's.

The display and GL runners write the same record, without the browser's lines and with their own: `igt.sh` the IGT stage, the cards, whether `sync/sw_sync` exists, each driver that debugfs's `dri/N/name` names, and the list's length and SHA-256; `modetest.sh` the driver and the count of modes; `piglit.sh` piglit's version, the platform and each part's pattern; `glmark2.sh` its version and the renderer. Each prints one line:

    igt: result: 1 tests, 21 results: pass 14 skip 7 fail 0 other 0
    modetest: result: 15 modes on 1 connectors: set 15 failed 0
    piglit: result: gl-1.0 386 results: pass 378 skip 0 fail 5 other 3
    glmark2: result: 33 scenes: Success 27 Failure 0 Unknown 6 score 890

`igt.sh` writes `TEST.results` for each test program and `piglit.sh` `PART.results` for each part, a line a test or subtest, `NAME RESULT`; `modetest.sh` writes `modes`, a line a mode, `CONNECTOR INDEX NAME REFRESH set WxH CRC` or `... failed`; `glmark2.sh` writes `validations`, `SCENE RESULT`, and `scores`, each scene's frames per second and the score. Each script's header gives the format whole.

`deqp.sh` writes the record, begun as a browser runner's without the browser's profile and the window's size, then the case, the `list` with its length and SHA-256, the `sample`, the `program` and its release, dEQP's `options`, the `env` lines of the drivers' variables that are set, the `flakes` file, and the `renderer`: GL_RENDERER and GL_VERSION from dEQP's own information cases for GLES, and the device's name, API version and driver version from `dEQP-VK.info.device` for Vulkan. For Vulkan it writes `vulkaninfo.out`, `vulkaninfo --summary` of the drivers it runs, before the cases. It writes `results.csv.gz`, `CASE,STATUS` a line in the sample's order, the form of the second discovery run's step 9 results under [`ref/lenovo/deqp`](ref/lenovo/Readme.md), whose GLES runs are the AOSP lists whole and whose Vulkan runs are every 50th and every 500th case of `vk-default`, as `-e 1`, `-e 50` and `-e 500` choose them; `flakes`, `CASE,FIRST,SECOND,WHY` a line; `summary.txt`, the sample's size and the count of each status, as step 9's `summary.out`; and `logs/`, each process's output. It prints one line:

    deqp: result: gles2 1.4.7.1 cases 86 of 17165 every 200 jobs 4 pass 85 fail 0 notsupported 1 warning 0 crash 0 timeout 0 other 0 missing 0 flake 0

`judge.py deqp` prints each change of status from the reference's as `judge: change: FROM -> TO N`, each worse case and `judge: result: pass` or `fail`.

`vkcube.sh` writes the record, begun as `deqp.sh`'s, then the case, the `icd`, vkcube's version, the `compositor`, Weston's GL `renderer`, the `gpu` vkcube chose and the layer's `timing`. It writes `frames`, a line a held frame, `frame N WxH crc32 0xCRC`; `frame-N.png`, the shot that gave it; `timing`, the layer's line and `rate R`, the presents a second; `gpu`, vkcube's line that names the device; and the logs of Weston, vkcube, the screenshooter and the layer. It prints one line:

    vkcube: result: frames 300 0x75d4ad32 345 0x1a0d31d7; 300 presents in 2.502 s, 119.90 a second

`judge.py vkcube` prints each frame that differs, `judge: rate:` with both rates and their ratio, and `judge: result: pass` or `fail`.

`games.sh` writes the record, begun as `deqp.sh`'s, then the `compositor`, the `size`, the game's new home, the `env` lines of SDL, the HUD and the locale, the case, the replay's turns and SHA-256 for 0 A.D., the game's version, its `arguments`, SuperTuxKart's `profile` summary, the game's `start frame` in the dump and the GL `renderer` its log names. It writes the game's log, `GAME.log`; `hud`, every frame time the HUD wrote, one a line in milliseconds; `frametimes`, the measured window's; and `summary`, a line each for the `window`'s first and last frame in the dump, its `seconds`, the `frames`, the mean `fps`, the `median`, `p90`, `p99`, `p99.9` and `max` in milliseconds, the frames over 16.7, 33.3, 50 and 100 ms, and the `end`, as Linux's runs' `frames.py` gives them. It prints one line:

    games: result: supertuxkart frames 200 seconds 158.968 fps 1.26 median 773.50 p90 880.90 p99 1426.00 p99.9 2270.00 max 2270.00 over50 200 end profile

The Debian references are stored in [`ref/debian`](ref/debian/Readme.md), a directory for each display profile, each run's directory with its `record`, `results` and the files above.

[`ref/lenovo-crc.txt`](ref/lenovo-crc.txt) is Linux 6.12's pipe CRC of the Lenovo's eDP panel at thirteen modes through the fitter, as `crcmodes` printed it under Debian 13; Rach2's i915 gives the same lines.

## Design

### Display profiles

| Profile | QEMU's device | PCI id and class, as Rach2 and Debian read them | Debian boots by | Use |
| --- | --- | --- | --- | --- |
| `std-vga` | `VGA` | 1234:1111, 0300 | SeaBIOS | bochs-drm, fbdrm through GRUB's mode |
| `virtio-vga` | `virtio-vga` | 1af4:1050, 0300 | SeaBIOS | virtio-gpu with a VGA for the firmware and GRUB |
| `virtio-gpu` | `virtio-gpu-pci` | 1af4:1050, 0380 | OVMF | virtio-gpu alone |
| `virgl` | `virtio-vga-gl` with egl-headless | 1af4:1050, 0300 | SeaBIOS | the host's GL through virglrenderer, on the testing PC |
| `venus` | `virtio-vga-gl` with Venus, blobs and egl-headless | 1af4:1050, 0300 | SeaBIOS | Vulkan through Venus over the host's lavapipe, GL on llvmpipe, on the testing PC |
| `none` | none | none | OVMF | vkms inside the guest, which a run loads with `modprobe vkms` |

Each device has `edid=on,xres=1280,yres=800`: its EDID prefers the window's fixed 1280x800, since QEMU's EDID also offers modes up to 5120x2160 and a program such as glmark2-drm takes the largest; the modes stay listed for the mode tests. The pointer is the PS/2 mouse of the PC's 8042, the same for Rach2 and the Debian reference; no USB tablet is attached.

Debian's GRUB under SeaBIOS resets the machine at once when the display has no VGA, with `virtio-gpu` and with `none` (measured: QEMU ended on the reset before the kernel started), so the Debian guest boots those two by OVMF, where GRUB draws on the firmware's GOP, and the others by SeaBIOS. Rach2's own GRUB, which carries `vbe`, `video` and `video_fb`, was tried once under SeaBIOS with `virtio-gpu` alone: it boots, and the kernel reaches its login prompt in 7 s, but GRUB finds no VBE mode to set and hands the kernel no framebuffer (`boot: screen: text; the loader described none`), where with `std-vga` it hands 1280x800 at 32 bits. A Rach2 run of the `virtio-gpu` profile therefore draws through Rach2's virtio-gpu driver alone, with no firmware framebuffer, and a direct boot does the same.

### Accelerators

Rach2's own suites run under TCG on the testing PC, the fastest there for their boots: Rach2 reaches its login prompt in 0.51 s under TCG against 2.14 s under KVM, whose 300,000 exits of a boot's PCI searches each cost some 4.6 us at the second level of nesting (run 2, step 1). `tools/ci/site`'s `accelerator tcg`, which the release's run and etude's routine entry read, and `RACH2_QEMU_ACCEL=tcg` in each account's `.bashrc` and in `tools/dev/testing.sh run` choose it ([tools/Readme.md](../../tools/Readme.md#the-testing-host)).

A graphics run asks for KVM where `/dev/kvm` opens for reading and writing, and TCG elsewhere: under KVM llvmpipe and lavapipe run 29 to 34 times as fast as under TCG, and the CPU job 11 times. etude takes it from `RACH2_QEMU_ACCEL=kvm` or `-A kvm`; `rach2/qemu_devices.sh` and the Debian guest choose it themselves, unless `ACCEL` names another. Under KVM the processor is QEMU's `host`, with `invtsc=on`: the named AMD models ask for `pcid`, `pku` and `la57`, which WSL's nested KVM lacks, and the invariant counter lets Rach2 measure the time-stamp counter, so that its vDSO reads the clock without a system call. Measured on the testing PC in each profile: with `invtsc=on` Rach2 logs `vdso: clock: the tsc, 4191900 counts a tick` (4,191,892 to 4,191,994), and without it `vdso: clock: the system call; no tsc at one rate was measured`, as under TCG.

### The reference guest

The guest is Debian 13's generic cloud image of 2026-11-03, the one the second discovery run used, with its packages from Debian's snapshot of 2026-11-08, so that every prepared image has the same versions: Mesa 25.0.7-2+deb13u1, Weston 14.0.2, Chromium 156.0.8078.79, Firefox ESR 153.6.0 and Linux 6.12.115. The browsers come with the fonts Rach2's root stages and, as apt is set up there, without their recommended packages, as Rach2's root takes Debian's packages without them. Its machine is q35 with the profile's display, a virtio disk, a virtio network card on QEMU's user network with SSH forwarded from a free port on the loopback address, and a virtio random number generator, on the accelerator and processor above. It serves as the reference of every graphics run and as the builder of packages that Rach2 takes from Debian's sources.

The guest's Venus driver is the one Rach2's root has, Mesa 26.1.6's from trixie-backports, installed as the root installs it ([Venus](../../vendor/gnu/Readme.md#venus)): `prepare` fetches the package that [`vendor/gnu/debian/venus.list`](../../vendor/gnu/debian/venus.list) pins and checks its SHA-256, puts its library in `/usr/lib/x86_64-linux-gnu/venus` and its ICD, naming that library, in `/usr/share/vulkan/icd.d/venus_icd.x86_64.json`, and diverts 25.0.7's `virtio_icd.json` and `libvulkan_virtio.so` to names with `.mesa25` after them, which the loader does not read. Every other driver is 25.0.7's.

Debian 13's kernel is built without vkms (`# CONFIG_DRM_VKMS is not set` in its configuration), so the preparation builds the module from `linux-source-6.12` of the running kernel's own version, 6.12.115-2, against its headers, and installs it in `updates/`; it stays unloaded until a run of the `none` profile loads it, and then appears as `card0` with a virtual and a writeback connector. The kernel's headers stay installed for the builder.

### The guest's environment

[`guest-env.sh`](guest-env.sh) is sourced in the guest of every graphics run, Rach2's or Debian's, with `GRAPHICS_CLASS` set:

* `conformance`, for dEQP-VK, piglit, the WebGL suite and Wine's tests: `LP_NUM_THREADS=0`. These suites run a process on each CPU already, and llvmpipe's own threads buy nothing alone and cost 4 to 5% with five guests (run 2, step 4).
* `vkd3d`, for vkd3d-proton's suite at its measured setting until it is qualified at 0: llvmpipe's threads at the guest's CPU count, and `VKD3D_JOBS`, the suite's processes at once, at the CPU count in a guest of 16 GiB or more and 4 below, since at 8 jobs in 8 GiB the guest's kernel killed tests for memory.
* `performance`, for glmark2, the WebGL fill and ALU gates, vkcube, the game routes and the comparisons of 77-2 and 77-5: `LP_NUM_THREADS` at the guest's CPU count, which both sides of a comparison set alike.

`GRAPHICS_DONE=1`, `-d` of `run`, empties Mesa's shader cache, `MESA_SHADER_CACHE_DIR`, before the run, so that no shader compiled by an earlier run is reused. `graphics_xvfb` starts Xvfb at 1280x800 with `-noreset`, so that it does not reset when its last client leaves, and `graphics_env` prints the environment for the record.

### Admission

A guest of the graphics tests runs a process on each of its processors, or measures its performance, so it claims its processors as well as its memory, and the guests of every account on the testing PC are counted against the site's 32 processors: four CPU-bound guests of 8 run at once and a fifth waits. A CPU-bound guest claims every processor and a light one two ([etude's Readme](../../tools/etude/Readme.md#admission)).

* A Rach2 case names its class in its `resources` as `cpu_class`, `bound` or `light`, and etude reserves by it in place of the processors its history measured; inside a launcher claim the case also claims its processors in the site's ledger.
* The Debian guest's `run` re-runs itself as one claim of the site's ledger through the tree's `etude admit -c`, CPU-bound unless `-l` says it is light, with its memory and QEMU's 1 GiB, and waits in the ledger for the site's wait. The claim's identity and the live host ledger are in the run's record. A machine without a site policy, such as the Mac, runs it unclaimed; an explicitly selected unreadable policy is refused.

The WebGL, video and browser cases name the `bound` class. `common.sh host` reads the site's regular `claims` file, counts its claim records and retains its contents as `host_ledger` lines, including processor reservations. The Debian guest records this while its own claim is held, before the browser command starts.

`python3 tests/graphics/browser/loaded.py OUT`, followed by `--` and the command with its arguments, runs a prepared comparison beside three bound Debian guests of eight processors each. The wrapper enters the installed launcher, then reserves all 28 processors for the three load guests and the four-processor comparison in one bound claim before starting a guest. The launcher supplies the comparison's memory reservation. The wrapper names its claim to the command in `DEBIAN_REF_CLAIM` and `ETUDE_SITE_CPU_CLAIM`, so that a Debian comparison shares the group claim and native etude's cases ask the site's ledger for no processors of their own, as [etude's Readme](../../tools/etude/Readme.md) says; without that, each case's four were counted beside the 28, and the case waited behind another account's request for as long as the load ran. Thus neither side holds a partial processor group while the measured guest waits. Each guest runs eight independent CPU workers; readiness requires every worker's completed-work counter to advance. `OUT` retains their arguments, counter logs and the live ledger. The native comparison uses one worker and four processors, `-j1 -C4`. The wrapper stops and reaps all three guests on every exit and waits for their cleanup; its enclosing admission releases their shared claim. Prepare every artifact before starting this load; the comparison command must start no build. The video references and their Rach2 comparisons use this same load.

### Capture

QEMU's screen dump has no surface once the scanout is a dma-buf, so a frame is read inside the guest. `drmcapture` finds the first CRTC that scans out a framebuffer, takes the buffer's handle with GETFB2, which Linux gives to root and the card's master alone, maps it with MAP_DUMB and mmap, and folds each pixel's red, green and blue bytes, row by row, into a CRC-32 (zlib's), without the padding byte or the row's padding; two drivers that lay one picture out in different 32-bit formats or pitches give the same sum. It reads linear XR24, AR24, XB24 and AB24. `-o FILE` writes the frame as a binary PPM, whose pixel bytes give the same CRC-32 to `zlib.crc32`. With `-p` it first sets a pattern of its own, red across, green down and blue their XOR, on the preferred mode of the first connected connector as the card's master, and reads it back the same way; at 1280x800 its sum is `0x85b019e6`, as the Debian guest's std-vga gave it under bochs-drm, as Rach2's test image gives it under its own bochs-drm on i686 with `exec /drmcapture -p`, and as the pattern computed on the host gives it. It uses the C library and the kernel's ioctls alone, with Linux's structures written out, so that neither side needs libdrm.

### Venus on the testing PC

The `venus` profile gives the guest Vulkan through Venus, over the host's lavapipe, with its frames on screen: QEMU's `virtio-vga-gl` with `venus=on,blob=on,hostmem=4G`, the guest's RAM a shared memfd, and egl-headless on WSL's render node with QEMU's GL on llvmpipe. Three things in QEMU's environment make it work, and etude, `rach2/qemu_devices.sh` and the Debian guest set them alike:

* `GALLIUM_DRIVER=llvmpipe`: Venus's frames are black when QEMU's GL is Mesa's d3d12 driver on the RTX 4080, so Venus and `virgl` are two profiles (run 2, step 6).
* `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.json`: virglrenderer's render server, which QEMU starts and which inherits the environment, takes lavapipe as the Vulkan device it relays.
* `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libm.so.6`: llvmpipe's compiled shaders look libm's functions up in the process's global scope, and `/usr/libexec/virgl_render_server` links only libvulkan and libc, so without the preload a shader that calls one, such as dEQP-VK's `float_controls2` cases on Mesa 26.1's Venus, calls address 0, and the render server dies of the segmentation fault.

lavapipe exports memory and fences as dma-bufs and sync files only through `/dev/udmabuf`, which WSL's kernel lacks; without it lavapipe drops `VK_EXT_image_drm_format_modifier`, `VK_KHR_external_fence_fd` and `VK_KHR_external_semaphore_fd`, and Venus stops at Vulkan 1.2 with no swapchain. Root loads the module after each start of WSL ([tools/Readme.md](../../tools/Readme.md#the-testing-host)), and the account that runs QEMU must be in `kvm`, the group of `/dev/udmabuf`. lavapipe exports through udmabuf every allocation that Venus maps, and the module makes no buffer over its `size_limit_mb`, 64 MiB by default: with 64, an allocation over 64 MiB on Venus fails on the host, the guest's `vkMapMemory` returns `VK_ERROR_MEMORY_MAP_FAILED`, the render server logs "failed to look up object N of type 8" and the context's ring goes fatal (measured in the Debian guest at 64 and 65 MiB): the lines that dEQP-VK's huge `cube_array` crash and a vkd3d-proton test's stall there gave. A host whose Venus runs on a GPU does not export through udmabuf, so `load.sh` sets the limit to 16384, a guest's whole memory.

Measured on the testing PC with the module loaded, by `debian-ref.sh run -p venus` under KVM with 8 CPUs and 8 GiB: the Debian guest's virtio-gpu offers 3 capability sets, blobs and a host-visible window of 4 GiB; with Venus's driver alone, `vulkaninfo` gives `Virtio-GPU Venus (llvmpipe (LLVM 21.1.8, 256 bits))` at Vulkan 1.3.269 with `VK_KHR_swapchain`, `VK_EXT_external_memory_dma_buf`, `VK_EXT_image_drm_format_modifier` and `VK_KHR_synchronization2`; its GL is `virgl (LLVMPIPE (LLVM 21.1.8, 256 bits))`, OpenGL 4.5 core and ES 3.2; and vkcube on Venus presents 600 frames to a headless Weston on its GL renderer and exits 0. The boot, run and power off take 33 s. That was Mesa 25.0.7's Venus driver; the guest's driver is now 26.1.6's, which gives Vulkan 1.4.307 with 164 device extensions, `VK_KHR_load_store_op_none`, `VK_KHR_maintenance6` and `VK_EXT_map_memory_placed` among them ([`ref/venus-wsl/`](ref/venus-wsl/Readme.md)).

QEMU on Windows gives no Venus. The test engine's QEMU 11.1.2 (`rach2-whpx-d0`, `D:/rach2/build/qemu`) has no `virtio-vga-gl` and no display but `none`. The stock QEMU 11.1.0 (`v11.1.0-12130-ge470268ff4`, `C:/Program Files/qemu`) has the device with its `venus`, `blob` and `hostmem` options, but its virglrenderer is built without the render server: started once under WHPX with `venus=on,blob=on,hostmem=1G` and egl-headless, it logs "Render server support was not enabled in virglrenderer", "failed to initialize venus renderer" and "virgl could not be initialized: -1", and keeps running; the Debian guest's virtio-gpu offers `+virgl +edid +resource_blob +host_visible +context_init` and 2 capability sets, times out reading the first (`timed out waiting for cap set 0`), and falls back to its own llvmpipe for GL and lavapipe for Vulkan.

### Browser runners

Each runner draws into a headless Weston of its own at the window's 1280x800, under kiosk-shell, so that the browser is fullscreen, and serves its pages and files from a small server on a free port of the loopback address, [`runners/server.py`](runners/server.py), which appends each page fetched and each event a page posts to an events file, flushed line by line; [`runners/events.py`](runners/events.py) reads it. Weston's renderer is Pixman, which offers clients shared memory alone: with its GL renderer Weston offers linux-dmabuf on the display's `card0`, and Chromium's GPU process, as an ordinary user who is not the DRM master, cannot make a dumb buffer there ("DRM_IOCTL_MODE_CREATE_DUMB failed: Permission denied") and loses every context (measured in the Debian guest under `virtio-vga`). The browsers' own GL, WebGL's and video's, runs on llvmpipe either way; Chromium's WebGL renderer is "ANGLE (Mesa, llvmpipe (LLVM 19.1.7 256 bits), OpenGL ES 3.2)", Firefox's "llvmpipe, or similar". The GPU profile of the `browser` family's `crocus-fake` case and the Lenovo's step, below, is the exception: on a machine whose only render node is the HD 4400's, `RUNNER_RENDERER=gl` has Weston render with Crocus and offer linux-dmabuf there, so that each client's GL runs on Crocus too, and `RUNNER_XWAYLAND=1` loads Weston's Xwayland module and exports the display that Weston's log names.

Chromium runs with `--ozone-platform=wayland --no-first-run --no-default-browser-check --password-store=basic --start-fullscreen --ignore-gpu-blocklist --disable-gpu-process-crash-limit --js-flags=--expose-gc --disable-background-timer-throttling --disable-renderer-backgrounding --disable-background-networking --disable-hang-monitor --autoplay-policy=no-user-gesture-required`: the discovery run's set, which Chromium's own WebGL conformance runner uses or which keeps a test page from being throttled, with `--ignore-gpu-blocklist`, without which Chromium gives llvmpipe no WebGL, and three that keep a run from waiting on the network, a hang dialog or a gesture. Firefox ESR runs with `--new-instance --no-remote --kiosk` and `MOZ_ENABLE_WAYLAND=1`, and its profile's `user.js` turns off the first-run pages, the slow-script dialog, which would stop a page, and session restore after a crash, and forces WebGL on. Every browser starts with a new profile.

`webgl.sh` drives the suite through [`runners/webgl.html`](runners/webgl.html), which runs the suite's own harness, `js/webgl-test-harness.js`, as `webgl-conformance-tests.html` does: it reads the `00_test_list.txt` files with their `--min-version` and `--max-version` options, giving 971 pages for 1.0.4 and 2,865 for 2.0.1, and runs the pages whose indexes it is given one after another in a frame. It posts each page's start and result as they happen, and a tick every 10 s while a page runs, so that a browser that crashes loses no result it had sent. A chunk is 250 pages, so the suite is 4 chunks for 1.0.4 and 12 for 2.0.1, and each chunk has a new browser: in the discovery run one GPU process crash in a whole 2.0.1 run in one browser failed 163 pages in the 10 minutes after it. A browser that ends before its chunk does is replaced by a new one for the pages left, the page it ran being `crash`; each page that does not pass is then run once more in a new browser, and its second status is its verdict, the first kept beside it. The harness ends a page after 20 s without a result, which is the page's `timeout`, a status like any other: the pages that time out vary from run to run. A browser that posts nothing for 120 s, six times the harness's limit, has stopped, and is ended; the page it ran is `hung`. That is the runners' one use of the clock, and it decides nothing alone, since the page is run again.

`video.sh` plays each clip through [`runners/video.html`](runners/video.html), muted, under its own headless Weston or, with `-d`, on the caller's Wayland display, as on the Lenovo, once to warm up and three times counted, each play to the clip's end in a new video element, whose `getVideoPlaybackQuality()` then gives the frames shown, dropped and corrupted; browser numbers in QEMU vary from play to play, by about 50% for fill rates on the discovery run's first night, and the repetitions show by how much. Each clip has a new browser. A case which names one clip uses `video.sh -t`: it first plays the preceding clips in the reference's H.264 720p, H.264 1080p, VP9 720p, VP9 1080p, AV1 720p, AV1 1080p order in the same boot and compositor. The browser cases retain the host's live load and admission ledger in the runner record before playback. Weston uses `--no-config`, so neither side reads a desktop configuration or starts Xwayland. Chromium names its decoder through its DevTools protocol: [`runners/cdp.py`](runners/cdp.py) starts it with `--remote-debugging-pipe`, enables the Media domain in each page before opening the clip's page, and keeps the players' `kVideoDecoderName` and `kIsPlatformVideoDecoder`. The clips are 10 s at 30 frames a second of ffmpeg's `testsrc2` pattern with temporal noise, so that each frame costs its decoder about what a filmed one would: H.264 High at 4 and 8 Mbit/s, VP9 at 3 and 6 and AV1 at 2 and 4, at 1280x720 and 1920x1080, made by `video.sh make` with the reference guest's ffmpeg, each encoder on one thread. `debian.sh clips` installs ffmpeg from the snapshot for that boot alone, so that the reference guest's browsers find no system codec library that Rach2's root lacks; two boots made the same bytes, which [`runners/clips.sha256`](runners/clips.sha256) pins, and both `video.sh` and `debian.sh` refuse a clip that differs.

### The dEQP runner

`deqp.sh` takes the cases as the second discovery run's step 9 took them, so that a result compares by case with the stored references: the release's mustpass list, the AOSP list `GLESN-main` for GLES and `vk-default` with its includes expanded in order for Vulkan, or the file `-l` names, and of it the first case and every Nth after it. GLES runs in `glcts` and Vulkan in `deqp-vk`, each from its directory. GLES draws to 256x256 pbuffers of the config `rgba8888d24s8ms0` on EGL's surfaceless platform, `EGL_PLATFORM=surfaceless`, as Mesa's CI runs it and as the Lenovo's references were made; Vulkan uses the drivers the loader finds, or those `VK_DRIVER_FILES` names, which the record keeps.

The sample is shared among 4 processes, each given every fourth case, as step 9 ran it. dEQP's own watchdog ends a case after 300 s, the limit step 9's runner set. 1.4.7.1 takes both its limits as options, and the runner sets the per-iteration limit to 300 s too, since a software renderer in a guest can spend more than the default 30 s in one iteration; 1.4.1.1 has no such options and keeps its fixed 300 s a case and 30 s an iteration, and the record's `options` line shows which applied. A process that ends in a case leaves that case `Crash`, or `Timeout` when its watchdog ended it, and a new process runs the cases it had left. A process that ends with cases left and none running has met cases its program does not have; when a new process then runs none of them, twice in a row, or once after a process that ended cleanly, they are `Missing`, which makes the runner exit 1. This is the runner's one use of the clock, and it is dEQP's.

Every case that did not pass, Missing aside, then runs once more, in processes of its own. The first status is the result, as each case ran once in step 9, and a case that passes the second time is named in `flakes` as `rerun`; one that fails again and matches a line of the `-f` file is named as `named`. `judge.py deqp` does not count a named flake as worse. A case is worse when it passes in the reference, Pass or a warning, and does not pass here, NotSupported among the statuses that do not pass, since the system then offers less; when the reference does not support it and it fails here; or when the reference does not have it. It compares only the cases the run has, so a sample compares with a reference of the whole list.

### vkcube presenting

`vkcube.sh` shows a Vulkan program's frames on the display through the whole path a desktop uses: vkcube draws on Venus, Mesa's Wayland swapchain hands each image to Weston as a dma-buf, Weston composites it with its GL renderer on virgl, and the DRM backend flips the result onto virtio-gpu's scanout, which QEMU's egl-headless display takes. It ends any Weston that runs, Rach2's boot session among them, and starts its own on the card with its GL renderer, kiosk-shell, which gives vkcube the whole 1280x800 output, `--debug`, which offers the screenshot protocol, and `--no-config`, so that no guest's `weston.ini` adds to it, as root through libseat's noop backend, the same in both guests. vkcube presents 346 frames in FIFO, its default.

The frames are read inside the guest, since QEMU's screen dump has no surface once the scanout is a dma-buf: `weston-screenshooter` asks Weston for its output, which Weston reads back from its renderer, and [`runners/frame.py`](runners/frame.py) checksums the PNG's pixels as `drmcapture` checksums a scanout. vkcube's picture changes every frame, so a frame is read only while vkcube is held: [`runners/vkhold.c`](runners/vkhold.c), a Vulkan layer that the runner builds with the guest's GCC, since root's `cc` on Rach2 is TinyCC, which makes no shared object, and enables with `VK_INSTANCE_LAYERS` and `VK_ADD_LAYER_PATH`, passes every call down but vkQueuePresentKHR, and after the 300th and the 345th present waits on a FIFO until the runner has read the screen; the shots are repeated until two in a row give one sum. vkcube turns its cube by a fixed angle each frame it draws, never by the clock, so the Nth frame is the same picture in every run, and its sum is the Debian guest's when Venus draws on the same host and Weston composites the same way. The layer declares the few Vulkan types it needs itself, as `drmcapture` declares Linux's, since neither guest has Vulkan's headers.

The layer also times the first 300 presents, from the first call to the 300th return. The rate is the guest's whole presenting path at the pace of FIFO, which QEMU's display sets; it is recorded beside the Debian guest's and not judged ([`ref/venus-wsl`](ref/venus-wsl/Readme.md#results)).

### Native games

The `games-native` suite plays the native games' replays of the [games layer](../../vendor/gnu/games/Readme.md#native-games) on llvmpipe and keeps their frame times. They are the replays, arguments, settings and environment of Linux's reference runs on the Lenovo, [`tools/lenovo/debian-ref/games.sh`](../../tools/lenovo/debian-ref/games.sh), and the window and figures are its [`frames.py`](../../tools/lenovo/debian-ref/frames.py)'s, so that a run on the Lenovo's Crocus compares with Linux's under the gate, no loss over 10% with the IOMMU's translation off; QEMU keeps no reference of its own. A case plays the small form, 640x400 and a race of 10 s or a window of 10 s, since llvmpipe under TCG draws these games at about one frame a second: the result line under [Results](#results) is SuperTuxKart's on the testing PC, where both cases took 15 minutes and 0 A.D.'s window held 4 frames of about 3 s, and the full form's 90 s of race, at least 1,800 frames, would take hours. A case passes when its game played the replay through the window: SuperTuxKart to its profile summary, and 0 A.D. still playing when the window was whole. The times are evidence, recorded and not judged. Each case boots the x86-64 GNU root with the `virtio-vga` display, 4 CPUs and 8 GiB, and runs `games.sh` as the test account in the performance class.

The frame times are Mesa's: `GALLIUM_HUD=frametime` with `GALLIUM_HUD_VISIBLE=false`, which draws nothing, and `GALLIUM_HUD_DUMP_DIR`, where the HUD writes, at each frame a context presents, the time since the last in milliseconds, from the monotonic clock (Mesa 25.0.7's `hud_fps.c`), to the file `frametime_(ms)`. Any Gallium driver has the HUD, llvmpipe in QEMU and Crocus on the Lenovo's Haswell alike, so that one runner times both games on both sides without a hook in either. The window starts 5 s after the last frame of 1 s or more in the dump's first 120 s, the end of the loading screen, and lasts to the end of the dump for SuperTuxKart and 150 s for 0 A.D., which `games.sh` ends once its dump holds the whole window, as Linux's runs ended it by a timeout. The window never starts before the game's own start: for 0 A.D. the frames the HUD had written when the engine printed `GAME STARTED, ALL INIT COMPLETE`, and for SuperTuxKart the race's frames counted back from the dump's end until they make the race's time, each giving at most 50 ms of it. On a machine that draws the loading screen's frames in milliseconds frames.py's start is the later, so the Lenovo's window is frames.py's; under TCG, where every frame lasts about a second and no frame marks the loading's end, the game's start is. SuperTuxKart's profile summary counts its simulation's steps, 120 a second, not the frames drawn.

SuperTuxKart's profile mode drives every kart by its AI and steps the race by the wall clock, but by no more than 50 ms a frame (1.4's `main_loop.cpp`), so a machine drawing fewer than 20 frames a second, as llvmpipe in QEMU does, plays the race slower than real time, 50 ms of it a frame, and a faster one draws as many frames as it can in the race's own time. 0 A.D.'s visual replay runs its simulation, the AI players' turns among them, at the game's speed, one 200 ms turn at a time, and draws as many frames as the machine can between turns. Both games draw through SDL2 on Wayland without libdecor, fullscreen in the headless Weston, whose kiosk-shell gives them the whole output, with GL from EGL on the guest's Mesa.

## Limits

* `virgl` and `venus` are the testing PC's alone: the render node's path, the adapter's name and the libraries' paths are its own, the test engine's QEMU on Windows has no GL display, and etude refuses both there.
* `venus` needs the udmabuf module, which a restart of WSL unloads until root loads it again; `grep '^udmabuf ' /proc/modules` says whether it is loaded, and `/sys/module/udmabuf/parameters/size_limit_mb` must read 16384, as `load.sh` sets it.
* On Rach2 `drmcapture` needs a DRM CRTC with a valid mode and a framebuffer; an output without a framebuffer has nothing to capture.
* The Debian guest's packages come from the snapshot of one date; a newer reference takes a new date in `debian-ref/image` and a new `prepare`.
* IGT's tests are built for x86-64 alone, on an x86-64 Linux host, so the `igt` suite runs there alone ([IGT's tests](../../vendor/gnu/Readme.md#igts-tests)).
* Debian's sw_sync is Linux's code built as a module for the boot, not the kernel's built-in; it makes the same `sync/sw_sync` and `sync/info`.
* The browser suites run on x86-64 and on Linux hosts alone: the references are the Debian guest's on the testing PC under KVM, and on the Mac an x86-64 guest runs under TCG.
* The pages that time out at the harness's 20 s limit vary from run to run, and so do the frames dropped; the judge allows for both as Browser runners says.
* Firefox drops more frames on Rach2 than in the Debian guest under the references' load, so `runners/video.limits` names its six clips, in the `video` family and the `browser` family alike, and their drops are printed and not judged. The count of plays, the frames shown, the media errors and the decoder of those clips are judged as before, and so are Chromium's drops. Rach2 serves every kernel entry under one big lock, and Firefox's decoder threads make about 4,300 futex calls and 7,800 page faults a second, which Linux serves on all processors at once. Measured beside three bound Debian guests of eight processors, 28 of the testing PC's 32 in one claim: Firefox's AV1 clip at 720p dropped 26, 35 and 22 frames in one run and 38, 29 and 29 in the next, against Debian's 1, 6 and 3, where Chromium's VP9 clip at 720p dropped 0, 1 and 0 against 7, 19 and 9. In the second run, about 250 s on 4 processors, the processors waited 225 s for the lock (`bkl_wait_us`), the longest wait 0.71 s against a frame's 33 ms, and of its holds the timer tick's came to 33.0 s, futex's to 27.7 s and the page faults' to 13.9 s (`bkl_hold_entry`); no single hold was long. The limit ends, and `video.limits` loses its lines, when futex, page faults and the timer tick no longer take that lock, which is work of a milestone's size.
* On the Lenovo's firmware framebuffer, where Weston composites with Pixman, Chromium drops 14 to 27 frames of 1,722 in 58 s of H.264 or VP9 at 1080p, and Debian on the same machine, compositing on i915, drops none. It is the same lock: 13 to 20 of each play's drops fall in its first 9 s, while the browser starts; in the play read each second, the four processors then waited 1.5 to 2.3 s a second for the lock, which `mmap`, page faults and `openat` held longest. The step there is run by hand and no suite judges it. It is measured again when the lock's work ends, and Debian's Chromium is measured then under `nomodeset`, so that both systems composite in software on the firmware's framebuffer.

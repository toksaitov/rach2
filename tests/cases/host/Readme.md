# Prepared host checks

`host_checks_scenario.c` runs the five C groups of `host.host.json` over the inventory and executor in `host.c`. It executes native platform checks on the collection host and POSIX fixtures in one declared x86-64 GNU Rach2 helper per case. The separate scripts scenario controls the `host.list` checks. Every check uses prepared binaries, private scratch and complete output. The desktop requires no compiler, interpreter, tar, mtools, e2fsprogs or Linux tooling machine.

## Use

### Preparation

`etude prepare collection host` builds the native driver and the inventories under `build/tests/host-suite/`. The `tests` and `boots` inventories are separate for i686 and x86-64; the other four cases run once in a collection. The build-only tool `prepare.py` compiles host tests, checker selftests and fuzz replay programs. It reads the existing `host-deps:`, `host-cflags:`, `host-first:`, `host-alone:` and `host-arch:` metadata. Alone checks follow shared checks.

`host-tools:` declares fixture builders and checkers that a C test launches. Independent tar, mtools and e2fsprogs checks execute in the GNU helper; they are never desktop tool dependencies. Preparation compiles them into `build/tests/host-suite/tools` and adds every tool binary and source to the test's input fingerprint. `command_host.c` launches their argument vectors through the native executor, with complete file output or bounded stdout capture and confirmed child cleanup. It never invokes a shell or compiler. `HOST_TEST_TOOLS` may name the prepared tools directory in a GNU helper. The independent FAT and exFAT format checkers retain their existing process-exit leak setting; address and undefined-behavior failures remain fatal.

The boot inventory also hashes each check's runtime files. Preparation builds the native etude validator and the selected architecture's kernel, test image, etude-guest and rngprobe before publishing that inventory. The scenario check's hello program and disk are inputs too. Schema files are copied to `build/tests/host-suite/schemas`, declared as prepared artifacts, and hashed with their source files; the set-driver regression reads that prepared directory.

Protocol checks transfer the prepared `etude-workload` executable with its binary length and digest. Its compiled roles produce output, fail, wait for cancellation and create process witnesses. This small payload replaces shell fixtures and is built without sanitizer instrumentation; the host test and production protocol code retain their sanitizers. No fixture is compiled during execution.

Each inventory records its manifest digest, group, architecture and compiler: its command, resolved executable, SHA-256 and version output. Each entry records an assertion, label, shared or alone scheduling, relative executable path, arguments, executable SHA-256, input paths with SHA-256 and the compiler command's sanitizer instrumentation. A separate compiler dependency scan for each translation unit includes local headers and recursively included `.c` files. Dependency paths are normalized relative to the tree without resolving links into the build store. An input filename with non-ASCII bytes uses lowercase hexadecimal in `path_hex`; the driver decodes it before applying the same relative-path and digest checks as `path`. The two path fields are mutually exclusive. Absolute external dependencies reported by the compiler, such as the Mac SDK configuration, are recorded separately as `compiler_inputs`. Their digests control build reuse; test execution requires only the prepared binary and tree inputs, so it needs no SDK. Fuzz entries also record the corpus directory and every corpus file as an argument and input. Reuse requires the same compiler identity, command, inputs and binary. A missing source, empty corpus or compilation failure fails preparation. Source metadata `host-inputs:` adds product scripts and other runtime data to the immutable input list; `host-tools:` declares prepared executables. The lines fixture uses a prepared GNU Python interpreter to execute the production status reader. Its `RACH2_STATUS_PROC_ROOT` points to copies of actual process records and a kernel-observed lock witness; the reader defaults to `/proc` outside the fixture.

`adapters.json` maps a `host.list` assertion to a prepared executable and optional arguments. Make rules prepare those executables before publishing the scripts inventory. A missing adapter produces an unsupported entry rather than executing the old command. The API protocol assertions use `build/tests/system/fakeapi_test`.

`etude_platform` executes on the collection's own host. POSIX uses the native executor to check complete stdout and stderr beyond capture limits, truncation, merged streams, handle release and refusal when a sink cannot be opened. Windows preparation builds `winfixture.exe`, `wintarget.exe`, `winstand.exe`, `etude.exe`, `etude-volume.exe` and `image-command.exe` into the platform directory, and fingerprints every binary, source and schema. The entry runs every Windows fixture, including the same output-file checks. The Windows fixtures use the check's private `TMPDIR`; executable and schema paths remain in the prepared directory. These checks require no interpreter. They retain the Windows job, accounting, suspension, path, argument, environment, socket, lock, ledger, supervisor and tooling assertions.

The QEMU and watchdog fixtures execute on the desktop that runs the collection. Their stand-ins connect through the launcher's native transport: Unix sockets on POSIX and loopback TCP on Windows. Quiet-child execution, processor accounting, suspension and termination use the platform's process APIs. A forced Windows job termination must report the executor's Windows status; the POSIX checks retain their signal assertions. Native QEMU discovery includes the Windows executable suffix and its firmware directory.

The installed Windows GCC has no sanitizer runtimes. Its native platform and boot fixtures therefore record an empty instrumentation list. GNU helper checks and the POSIX controller fixtures record `address` and `undefined`; their sanitizer failures remain fatal. Windows behavioral checks still execute locally, including process, output, socket, path, job and real QEMU assertions.

### Execution

The driver verifies the manifest, group and architecture before any check starts. It checks each binary and input before and after execution, rejects scripts even on POSIX, and rejects newly added corpus inputs. The manifest, prepared inventory and live source or script list must agree. Every declared check stays visible, including unsupported checks. Missing checks fail their own assertions; extra checks fail `listed` and are not executed.

The collection and host-driver regression fixtures write script bytes only to test this refusal. Preparation recognizes those two data fixtures while still rejecting interpreter calls in their sources. Both checks run natively on POSIX and fingerprint the prepared runner or driver they invoke.

The interpreter check ignores C comments and verifies suspect included sources against the compiler's preprocessed output. This excludes inactive branches, such as init's shell fallback in a console-login build. Doom's platform source includes its shell-based error dialog and runs in the GNU helper. The set-driver fixture links the history reader it uses, without the unused Git comparison reporter.

`RACH2_WORKERS` limits concurrency, default four. A check marked alone starts with no other check running. Each child receives its own `TMPDIR`, fatal ASan and UBSan options, and the tree as its current directory. Its output is retained whole in `NAME.log`. The executor registers children before release and confirms cleanup before the driver accepts a pass. A signal cancels and reaps active checks. Unconfirmed cleanup keeps the evidence directory.

A completed check writes one assertion and one `progress checks N` record. The case has no clock limit. Etude's case and progress bounds apply. A passing case removes its workspace; a failing case prints the path it keeps.

### Fixture placement

The seven extracted kernel fixtures (`chown`, `krffs_open`, `krffs_root_lock`, `krffs_stat`, `pagecache`, `kstack` and `endothers`) are compiled during preparation, then run as native binaries with their original assertions. Their extraction inputs and generated includes enter the fingerprint. The two threaded fixtures use pthreads on POSIX and SRW locks, condition variables and native threads on Windows. Kernel include directories apply only to quoted includes, so pthreads reads the system scheduler header. `build/tests/host-suite/vfs_unmount` prepares the same unmount fixture for the USB disk case.

The GNU helper supplies the POSIX environment of filesystem, compiler, build, deployment and worker-loop checks. Their C controllers create fixtures and judge results. A product written in shell or Python runs in its own language when its behavior is the subject of the check. The old test driver does not run. TinyCC and Doom checks use binaries prepared for the tested architecture.

Native executor, platform and QEMU checks run on the collection host. Preparation rejects an undeclared interpreter or missing adapter; execution reports a missing check as a failure. `host.sh` remains as the legacy build-command interface. The prepared collection does not call it. `etude_hostdriver_hosttest.c` and the compiled host-suite controller check scheduling, interruption and immutable inputs.

### Source-check evidence

`style.c` reads source-check evidence made by `prepare_style.py` during artifact preparation. The preparation host runs the existing checks, requires every assertion to pass, and requires the recorded compiler and formatter versions, the Clang user-pointer contract and a judged complexity result. The evidence records the command, architecture, judge versions, assertions, branches, preparation time and source digest. The pinned pmccabe and mandoc receipts and the actual Clang executable digest enter that record; a changed judge requires new evidence. [Native source judges](../../../tools/setup/source-tools.md) describes the portable tools and the user-pointer contract. The native case reports that these checks ran during preparation.

The source digest includes sorted paths and file contents, so adding or removing a source changes it. `source_snapshot.c` enumerates the in-house source, build, test, manual and milestone directories and the port recipes; it excludes extracted upstream trees, installed products, caches and binary artifacts. The native reader checks this digest and exact assertion and branch coverage before reporting a pass. A missing or stale record is incomplete and needs preparation again. It never launches a compiler or interpreter. The collection's prepared artifact record also protects the evidence file itself.

`krffscheck.c` runs the offline KRFFS tools directly through the native executor. It constructs corrupt images and each prefix of the update protocol in C, then checks repair, retained data and wrong write orders. `native.c` keeps its images under `build/tests`, records complete child output and removes successful scratch after process cleanup is confirmed.

### Product and driver regressions

`host-build-check` is a prepared C controller for the compiler, build and runner assertions of `host.list`. The controller creates fixtures, launches product programs, reads results and checks them through `fixture.c`. Command substitutes are native C entries of the same executable. The products retain their own command language: a commit hook runs by its executable entry, a port recipe runs in its normal shell, and make runs its own recipes. No old test shell driver runs.

The compiler checks retain the assembler instruction and byte comparisons, the linker's segment, section, symbol and PC-relative address checks, and both Doom ABI runs. The build checks retain all launch-script settings, commit-message inputs, prerequisite reports and privilege cases, malformed recipes, firmware probes, interrupted port resumes, make job limits and parallel maker requests on both architectures.

`case_select` invokes the native collection entry on private manifests, preserving order, architecture restrictions, agent row choices and refusals before build state exists. Its accepted rows use the public dry selection entry because native execution does not build artifacts. `host_suite` invokes the prepared host driver over native probes, including real ASan, UBSan and, on Linux, LSan faults. The probes are compiled during preparation as `host-suite-probe`; the controller never compiles them. It checks every result, assertion and progress count, retained evidence, scratch isolation, exclusive scheduling, duplicate refusal and cleanup after a signal.

The products directory defaults to `/host-products`, or `HOST_PRODUCTS` for a native fixture run. It provides `etude`, `host`, `host-suite-probe`, `doom_libc-i686`, `doom_libc-x86_64`, `tcc/i386-tcc` and `tcc/x86_64-tcc`. The fallback `ROOT/prepared` supports a staged native fixture. The GNU helper must provide working sanitizer runtimes before it can run the sanitizer probes; a missing runtime is a failed preparation or execution, never a skipped check.

### Product-family checks

`family_scenario` runs the grow host cases through the declared GNU products helper. The prepared `host-family-check` C controller creates the counter records, file systems, plans, disk faults and measured-output fixtures, invokes the actual checker and grow programs, and compares their results. It copies only the product functions under test from `machine_grow.sh`; the former shell test driver does not run. The controller reports the original case and assertion identities in etude report records, which the native scenario accepts only after a whole report and confirmed process cleanup.

The helper uses a private 12 GiB disk and writes its fixtures under `/host-work`. The replay compares every restored byte of all 1856 ranges and both ends of every intervening gap. Its target and backup are removed on failure too. Other failed fixtures are exported as `family-fixtures.tar` before the helper is ended. The prepared tools include `growset`, `growboot`, `growroot`, `growroot-memory`, `reflash`, `diskctl`, `bootctl`, `mkfatfixture`, `mke2fs`, `e2fsck` and `resize2fs`. The helper boots with `rach2.slot=recovery` so that the real bootctl reads its normal command-line source.

The five imagerace cases use the same native scenario and the prepared `family_image*.c` controller. Concurrent image builders meet at their own temporary-image publication step; a native command hook interrupts each observed publication step in turn. The controller compares the image and both dependency lists after every stop. The prerequisite and edited-probe checks use the actual root Makefile and component Makefile with private minimal images and the prepared TinyCC compiler. All manifests retain their own path expressions during the dependency check; C creates regular, executable, nested and hidden input fixtures and rejects a directory among the expanded prerequisites. No prepared result substitutes for a runtime check.

The disk-policy host case transfers its declared ordinary and read-only kernel artifacts to the helper, then runs the actual `check_diskpolicy.sh` with the prepared `binfind`. C checks the five original acceptance and refusal results; the script never builds a checker or reads an undeclared kernel.

The metal family keeps its two host assertions. Its C transport controller runs every one of the 17 fault cases with both root-key and su transport, including the approved disk serial, refusal of similarly prefixed disk names, failed transfers and hashes, and FAT unmount, remount and independent host-read checks. Native command substitutes model remote replies; the actual deployment acceptance script makes its own decisions. The password controller runs all nine prompt, echo, split-output, repeated-prompt and pre-session connection cases against the prepared PTY fixture and real `ptydrive`. It audits the helper transcripts before cleanup and requires the original status, prompt and answer counts, retry count and returned bytes. The deployment scripts themselves are unchanged.

### GNU host inventories

`make ARCH=x86_64 gnu-host-checks` compiles the GNU helper's host checks with the separately prepared ASan and UBSan runtimes. It never runs a check. The cached output is `GNU_OUT/host-checks/`: `driver` enters its prepared `tree/`, becomes the ordinary `test` account, and starts `/host-products/host --one GROUP ASSERTION ARCH`. Both target-ABI inventories are present. The tree contains the binaries, their source fingerprints, corpus files, independent filesystem inputs and native GNU tools. The image stages this output at `/host-products/host-checks`.

Native inventory entries record `backend` as `native` or `gnu`. The scenario validates every identity before execution, runs native checks through the existing executor, then boots the declared helper if any GNU row needs it. Each GNU invocation runs exactly one prepared assertion; its own driver verifies sources and binaries before and after execution. Its output remains evidence of that assertion. Native process cancellation also notifies the case library, so both executors clean up their children.

The four checks that boot real QEMU machines remain on the collection host: `etude_qemu`, `etude_scenario`, `etude_watchdog` and `etude_legacyset`. Windows runs `etude_platform` there as the complete Windows adapter fixture set. Other Windows host checks use the GNU sanitizer inventory until their native platform adapters are supplied. No assertion is removed or accepted as unsupported.

The GNU driver creates one private writable source and binary copy under `/host-work` on the test root's disk for each group in its helper. The image manifest assigns `/host-work` to the ordinary test account with mode 0700. The driver sets `HOST_TEST_WORKDIR` to the private copy's check directory, so host-check images and scratch use that disk; unrelated small guest commands retain `TMPDIR`. It runs as the ordinary test account. The prepared tree below `/host-products` remains unchanged, and the host driver verifies the private copy's recorded inputs before and after every check. A successful group removes the copy through the C driver; a failure names it as evidence. Native Windows kernel fixtures retain their complete behavioral rows and use the same native thread adapters without sanitizer flags that the installed compiler cannot provide.

The set-driver regression (`etude_legacyset`) reexecutes compiled roles for its preparation, reports, scenarios and QEMU argument recorder. It launches the installed desktop QEMU for guest cases. A stop uses SIGTERM on POSIX or a console break on Windows; the Windows driver records the break as the same stop request and finishes its history and ledger cleanup. Its child has a private Job Object, whose remaining processes are stopped and counted before fixture removal.

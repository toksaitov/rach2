# Prepared host checks

`host_checks_scenario.c` runs the mixed C cases of `host.host.json` over the inventory and executor in `host.c`. It executes native platform checks on the collection host and POSIX fixtures in one declared x86-64 GNU Rach2 helper per case. The boots group uses `host boots` directly as a host-domain case. All four boot fixtures run natively on each supported host; they start their own QEMU instances and judge their prepared kernels, including intentional fault cases. No unused outer GNU helper or outer kernel-console witness is declared for this group. The separate scripts scenario controls five partitions of the complete `host.list` inventory. Every check uses prepared binaries, private scratch and complete output. The native host report uses unbuffered stdout, so its begin record precedes direct assertion and child records on Windows as well as POSIX hosts. The desktop requires no compiler, interpreter, tar, mtools, e2fsprogs or Linux tooling machine.

## Use

### Preparation

`etude prepare collection host` builds the native driver and the inventories under `build/tests/host-suite/`. The `tests` and `boots` inventories are separate for i686 and x86-64; the remaining groups and the two Etude scheduling partitions run once in a collection. The native `etude prepare -H GROUP OUTPUT` entry prepares host tests, checker selftests and fuzz replay programs. Make owns their compiler commands and separate translation-unit dependency scans; Etude reads the resulting files and publishes their inventory. It reads the existing `host-deps:`, `host-cflags:`, `host-first:`, `host-alone:` and `host-arch:` metadata. Alone checks follow shared checks.

`--jobs N` builds a group's checks in N worker processes on Linux and macOS, which take the checks in the inventory's order from one queue; Windows builds them one at a time. Each worker publishes the entry of each check it prepared, and the inventory lists them in the same order as a build of one check at a time does. The first worker to fail, or a stop signal, stops the others, and the work directory stays as evidence. `--slots FILE` bounds the checks built at once across every preparation given the same FILE to N: a worker, or a preparation that builds its checks one at a time, holds one of N slots, a byte of FILE write-locked with fcntl(2), while it builds a check, and a process that ends, however it ends, releases its slot.

`host-tools:` declares fixture builders and checkers that a C test launches. Declared external programs, including Git and tar, come from the directory that `HOST_TEST_PREPARED_TOOLS` names. For the native preparation the Makefile makes it `build/tests/host-suite/prepared-tools`, with links to the `git` and `tar` that the desktop's `PATH` finds; the GNU helper names a directory of its own root's programs. Preparation copies each, or on macOS links one from the sealed system volume, such as `/usr/bin/git`, since macOS kills a copy of such a program, and hashes its native bytes and resolved-source provenance; a missing directory or invalid file fails preparation, and its message names the tool. Independent tar, mtools and e2fsprogs checks execute in the GNU helper; they are never desktop tool dependencies. Machine filesystem cases also use the prepared GNU `fstool` product for independent exfatprogs and dosfstools checks; their C scenarios bind only private images and preserve the original checker branch and status contracts. Preparation compiles them into `build/tests/host-suite/tools` and adds every tool binary and source to the test's input fingerprint. `command_host.c` launches their argument vectors through the native executor, with complete file output or bounded stdout capture and confirmed child cleanup. It never invokes a shell or compiler. `HOST_TEST_TOOLS` may name the prepared tools directory in a GNU helper. The independent FAT and exFAT format checkers retain their existing process-exit leak setting; address and undefined-behavior failures remain fatal.

Shared native fixture tools retain a build record beside their executable. Preparation reuses those exact bytes across inventory processes only when the compiler identity, normalized command, source files and all compiler-reported headers match. This dependency scan includes system headers; external SDK digests belong to the preparation record, not the runtime file set. The inventory hashes both executable and build record. Each compiled check sorts its complete deduplicated input list by relative path after adding tools and companions, so fresh compilation and reuse publish the same order. A changed recipe or input requires a real compile, while changed executable bytes or an invalid existing record fail preparation. A preparation holds a write lock on `build/tests/host-suite/tools.lock` while it builds, copies and records the shared tools of a check, so that the workers and the preparations of other groups and architectures take turns at them; a check that declares no tool takes no lock. GNU preparation can copy a shared tool and its original build record from the preceding stored tree after comparing the complete current recipe. Compiler and SDK aliases are resolved before comparison; the copied record retains the actual original command. No prior executable or record is modified.

Windows platform companions use the same compiler, command, dependency and executable checks. A changed input rebuilds only the affected companion. A missing or invalid local record or changed local executable also rebuilds that companion. Imported records and shared fixture tools retain their refusal on damaged records or executable bytes. The inventory includes every companion's build record and the history schema.

`fstool_io` is declared in the tests case. Its C model checks both GNU positional-write ABIs against sector-only block writes, with byte preservation, boundaries, interrupted and short transfers, errors and regular-file passthrough. It uses no disk, child or platform block device. Linux and macOS run the model natively; Windows retains its declared GNU inventory route. The independent real formatter and repair checker still need their machine assertions.

The boot inventory also hashes each check's runtime files. Preparation builds the native etude validator and the selected architecture's kernel, test image, etude-guest and rngprobe before publishing that inventory. The scenario check's hello program and disk are inputs too. Schema files are copied to `build/tests/host-suite/schemas`, declared as prepared artifacts, and hashed with their source files; the set-driver regression reads that prepared directory.

Protocol checks transfer the prepared `etude-workload` executable with its binary length and digest. Its compiled roles produce output, fail, wait for cancellation and create process witnesses. This small payload replaces shell fixtures and is built without sanitizer instrumentation; the host test and production protocol code retain their sanitizers. No fixture is compiled during execution.

Each inventory records its manifest digest, group, architecture and compiler: its command, resolved executable, SHA-256 and version output. Each entry records an assertion, label, shared or alone scheduling, relative executable path, arguments, executable SHA-256, input paths with SHA-256 and the compiler command's sanitizer instrumentation. A separate compiler dependency scan for each translation unit includes local headers and recursively included `.c` files. Dependency paths are normalized relative to the tree without resolving links into the build store. An input filename with non-ASCII bytes uses lowercase hexadecimal in `path_hex`; the driver decodes it before applying the same relative-path and digest checks as `path`. The two path fields are mutually exclusive. Absolute external dependencies reported by the compiler, such as the Mac SDK configuration, are recorded separately as `compiler_inputs`. Their digests control build reuse; test execution requires only the prepared binary and tree inputs, so it needs no SDK. Fuzz entries also record the corpus directory and every corpus file as an argument and input. GNU entries record `compile_inputs` separately from runtime data. Reuse requires the same compiler identity, command, exact compiler dependency set and binary; changed runtime files are freshly hashed without recompiling the check. For an older stored inventory, preparation reconstructs the compiler dependency set in its original tree and checks every dependency against that inventory before reuse. An older local inventory without this separation is rebuilt once. A missing source, empty corpus or compilation failure fails preparation. Source metadata `host-inputs:` adds product scripts and other runtime data to the immutable input list; `host-tools:` declares prepared executables. The lines fixture uses a prepared GNU Python interpreter to execute the production status reader. Its `RACH2_STATUS_PROC_ROOT` points to copies of actual process records, a kernel-observed lock witness and the boot identity the ledger stamps on its claims, which on Rach2 is etude-guest's token and not procfs's `boot_id`; the reader defaults to `/proc` outside the fixture.

On macOS an instrumented native entry also records `sanitizer_symbolizer`, the relative path of a prepared copy of the native `/usr/bin/atos`. Its executable snapshot and source-path provenance are hashed inputs. Apple system atos cannot execute from that copied path: the identical copy was killed by signal 9 in a live process query while the installed tool resolved the address. The sanitizer field identifies the snapshot; its resolved-source provenance binds execution at the native source path. Before and after each check, the driver verifies that the resolved native path and snapshot both match the recorded digest, then supplies the native path as `ASAN_SYMBOLIZER_PATH`, replacing any inherited value. A changed OS tool requires new preparation. This keeps symbolization available under a restricted runtime PATH without exposing other system tools. Platform and executor self-reexecution passes only the fixed fatal ASan and UBSan settings and this prepared symbolizer path. The USB latency-checker and VFS unmount cases declare the regular file `tests/host-suite/sanitizer/tools.json` as an artifact and verify the same native source binding before and after their instrumented child and give it the same narrow environment. The manifest records the actual platform tool set, empty on hosts that need no atos. Import preparation validates this native data file, every referenced regular file and the resolved native source; its provenance hashes the manifest and its referenced files.

`adapters.json` maps a `host.list` assertion to a prepared executable and optional arguments. Make rules prepare those executables before publishing the scripts inventory. A row with neither an adapter nor a kernel fixture is an unsupported entry of the native inventory, whose detail names the row; its C controller runs in the GNU helper. The API protocol assertions use `build/tests/system/fakeapi_test`.

`etude_platform` executes on the collection's own host. POSIX uses the native executor to check complete stdout and stderr beyond capture limits, truncation, merged streams, handle release and refusal when a sink cannot be opened. Windows preparation builds `winfixture.exe`, `wintarget.exe`, `winstand.exe`, `etude.exe`, `etude-volume.exe` and `image-command.exe` into the platform directory, and fingerprints every binary, source and schema. The five companion programs retain individual build records. Preparation scans their current dependencies, including system headers and new shadowing headers, and reuses a program only when its compiler identity, complete recipe, inputs and bytes match. The prepared inventory includes each build record; the history schema is copied and hashed on every preparation. Changed inputs compile only affected companions, and invalid records or changed program bytes fail preparation. The entry runs every Windows fixture, including the same output-file checks. The Windows fixtures use the check's private `TMPDIR`; executable and schema paths remain in the prepared directory. These checks require no interpreter. They retain the Windows job, accounting, suspension, path, argument, environment, socket, lock, ledger, supervisor and tooling assertions.

The QEMU and watchdog fixtures execute on the desktop that runs the collection. Their stand-ins connect through the launcher's native transport: Unix sockets on POSIX and loopback TCP on Windows. Quiet-child execution, processor accounting, suspension and termination use the platform's process APIs. A forced Windows job termination must report the executor's Windows status; the POSIX checks retain their signal assertions. Native QEMU discovery includes the Windows executable suffix and its firmware directory.

The installed Windows GCC has no sanitizer runtimes. Its native platform and boot fixtures therefore record an empty instrumentation list. GNU helper checks and the POSIX controller fixtures record `address` and `undefined`; their sanitizer failures remain fatal. Windows behavioral checks still execute locally, including process, output, socket, path, job and real QEMU assertions.

### Execution

The driver verifies the manifest, group and architecture before any check starts. It checks each binary and input before and after execution, rejects scripts even on POSIX, and rejects newly added corpus inputs. The manifest, prepared inventory and live source or script list must agree. Every declared check stays visible, including unsupported checks. Missing checks fail their own assertions; extra checks fail `listed` and are not executed.

The collection and host-driver regression fixtures write script bytes only to test this refusal. Preparation recognizes those two data fixtures while still rejecting interpreter calls in their sources. `tests/cases/machine/netcase.c`, which the scenario check includes, names the guest's `/bin/sh` only in argument vectors that a Rach2 machine runs, and `tests/host/compat/netcase_bulk_host.c` only compares such a vector in its stand-in for the guest; preparation accepts those names in these two files while still rejecting interpreter calls. Both checks run natively on POSIX and fingerprint the prepared runner or driver they invoke.

The launcher fixture's shell stand-in recognizes both the relative tests/run operand and the exact absolute private checkout path that Rach2 supplies for a script interpreter. Launcher commands and arguments that survive setup or another check use caller-owned path buffers; the shared path helpers return rotating storage. The worker row runs the actual entry.

The interpreter check ignores C comments and verifies suspect included sources against the compiler's preprocessed output. This excludes inactive branches, such as init's shell fallback in a console-login build. Doom's platform source includes its shell-based error dialog and runs in the GNU helper. The set-driver fixture links the history reader it uses, without the unused Git comparison reporter.

The prepared tests, shared Etude, checkers, fuzz and scripts cases share collection capacity with other cases. `host.host.etude_quiet` contains `etude_platform`, `etude_remote` and `etude_repeat`; it and the boots group run alone to preserve native platform isolation and short response windows. The platform check declares host-alone on POSIX as well as in its Windows adapter, so both prepared modes agree with this same partition. Ordinary collections schedule these quiet cases first; seeded repetitions retain their allocated order. Both Etude cases consume the same complete `etude.inventory.json` and existing binary paths. Their declarations must be disjoint, cover every prepared and live check, and agree with each entry's shared or alone mode. A wrong partition fails before any child starts. Each case runs only its own native and GNU checks, with a separate GNU workspace and cleanup. `host --one etude ASSERTION` resolves the assertion's owning partition. CPU reservations start at the declared cpu_millis value; compatible eligible history later gives the median sustained CPU ratio with headroom under the ceiling. Parallel native checks do not turn the ceiling into an initial estimate. Memory and disk reservations retain their conservative values. Style reads prepared evidence and may run beside other cases.

`RACH2_WORKERS` limits concurrency, default four. A check marked alone starts with no other check running. Each child receives its own `TMPDIR`, fatal ASan and UBSan options, and the tree as its current directory. Its output is retained whole in `NAME.log`. The executor registers children before release and confirms cleanup before the driver accepts a pass. A signal cancels and reaps active checks. Unconfirmed cleanup keeps the evidence directory.

A completed check writes one assertion and one `progress checks N` record. This check counter is separate from the scenario library's `stage` witness, which counts completed manifest steps. Native keeper and child identities are reported before release, so the outer executor can also confirm their cleanup. The case has no clock limit. Etude's case and progress bounds apply. A passing case removes its workspace; a failing case prints the path it keeps.

### Fixture placement

The seven extracted kernel fixtures (`chown`, `krffs_open`, `krffs_root_lock`, `krffs_stat`, `pagecache`, `kstack` and `endothers`) are compiled during preparation, then run as native binaries with their original assertions. Their extraction inputs and generated includes enter the fingerprint. The two threaded fixtures use pthreads on POSIX and SRW locks, condition variables and native threads on Windows. Kernel include directories apply only to quoted includes, so pthreads reads the system scheduler header. `build/tests/host-suite/vfs_unmount` prepares the same unmount fixture for the USB disk case.

On macOS these eight fixtures compile each translation unit to a stable object path in their own `NAME-sources` directory and link with Apple's `-reproducible` option. This keeps random temporary object names and timestamps out of the executable's debug map while retaining debug information and sanitizers. Different fixtures share no object path. The scripts inventory records the actual link vector as `command` and its preceding compiler vectors as `compile_commands`; reuse compares both. Other host checks and the Linux and Windows compiler paths retain their single compiler vector.

The scripted checks have five cases: `scripts_native` has the seven kernel and three protocol assertions; `scripts_images` has five image assertions; `scripts_build` has eleven compiler and build assertions; `scripts` has fourteen worker and CI assertions; and `scripts_tools` has six Etude, deployment and credential assertions. The four GNU partitions use the same prepared scenario binary; the native partition uses the direct prepared host driver and complete scripts inventory. Both entry points use the same classification and full case manifest. Preparation derives the inventory backend from those five declarations: the ten native rows stay native, and the other 36 use the GNU helper. A missing or repeated declaration fails preparation before publishing the inventory. Before dispatch, the scenario requires disjoint declarations that cover all 46 original assertion identities exactly once. Missing, duplicate, unknown or wrongly assigned assertions fail `listed` before any helper starts. Each partition retains its selected rows' original list order. Each GNU partition boots its own helper, prepares its private workspace and removes it after success. The native partition is a host-domain case and starts no helper. Its driver selects only the ten native rows and runs them serially in their original list order. The scheduler orders the independent cases normally, including seeded repetitions; each case retains the existing bounds. The collection fixture checks the GNU step order and real scenario dispatcher with recorded helper operations. The host-driver fixture checks the direct native partition and rejects a wrong declaration before any child starts.

The GNU helper supplies the POSIX environment of filesystem, compiler, build, deployment and worker-loop checks. Their C controllers create fixtures and judge results. A product written in shell or Python runs in its own language when its behavior is the subject of the check. TinyCC and Doom checks use binaries prepared for the tested architecture.

The version-publication and deployment fixtures share `flow_version_mock_source` to shorten private C and header contents for repeated mock-compiler checks. They keep the real source paths, make rules, schemas, configuration and bootstrap and provision scripts. Deployment restores the complete `ledger.c` after shortening: provisioning reads its `LEDGER_MAGIC` definition, and the committed-revision assertion changes that definition. Changes to the short `json.c` still invalidate the source identity and mock-compiler output. The deployment, source-byte, cache identity, shell, interruption and publication assertions remain intact. Before the version fixture's real compiler check, it removes that private tree and copies the complete product source again. The real build and its schema, history and command checks use the full source.

The deployment fixture models Linux with `uname -s` reporting `Linux` and `uname -r` reporting `6.0.0-fixture`, including when it runs in the GNU Rach2 helper. Architecture and host name come from the actual machine. Its exact Windows SSH command sets a private platform marker for the uname stand-in. A shell may pass only the command basename in argv[0], so the fixture does not infer the platform from that argument. Deployment records and accelerator assertions therefore use the intended platform without inheriting the helper's `-rach2` release suffix.

Native executor, platform and QEMU checks run on the collection host. Preparation rejects an undeclared interpreter or missing adapter; execution reports a missing check as a failure. `etude_hostdriver_hosttest.c` and the compiled host-suite controller check scheduling, interruption and immutable inputs.

The `krffs_tools` controller, `host_image_krffs.c`, runs the KRFFS tools that preparation builds from `krffs/`, and each row makes its own small image with `mkfs.krffs`. Rows require the stager to refuse, in its own words, a malformed path, a path under `/dev` or `/proc`, a path staged twice into an image or into the tree the ext2 builder reads, a directory under a file, a file that does not fit the image, and a second directory whose name mixes to the identifier of another; the image builder, `krffs/mkimage.sh`, to leave the previous image as it was when a manifest fails part way; the visualiser to draw the node ring in order; the defragmenter to close a hole, in a whole image and in a region of a larger file given by `--offset` and `--size`; and the node editor to write the one field it is asked for and nothing else. The defragmenter's and the node editor's rows read the image with a reader of the node ring that shares no code with the tools.

The tooling cache fixture records the completed amd64 image and tool record before preparing arm64. It requires a different complete arm64 pair beside the amd64 pair, which stays, then runs the ARM job and checks its QEMU arguments. The cache keeps the recipe's pair of each architecture and pairs used by active jobs or retained evidence.

The parallel-maker fixture copies every included Make fragment into its private tree before querying the real GNU Make database. It checks all eight maker rules and requests their outputs together on both architectures. Its command substitutes create the declared outputs and record each invocation.

### Source-check evidence

`style.c` reads source-check evidence made by the native `etude prepare -H --only CASE style OUTPUT` entry during artifact preparation. The preparation host runs the existing checks, requires every assertion to pass, and requires the recorded compiler and formatter versions, the Clang user-pointer contract and a judged complexity result. The evidence records the command, architecture, judge versions, assertions, branches, preparation time and source digest. The pinned pmccabe and mandoc receipts and the actual Clang executable digest enter that record; a changed judge requires new evidence. [Native source judges](../../../tools/setup/source-tools.md) describes the portable tools and the user-pointer contract. The native case reports that these checks ran during preparation. On Windows, the sizes check converts its absolute native checker operands explicitly, so evidence preparation also works when the native parent disables MSYS argument conversion.

The source digest includes sorted paths and file contents, so adding or removing a source changes it. The `--fingerprint TREE` command emits exactly 64 lowercase hex digits followed by one LF byte on every platform. `source_snapshot.c` enumerates the in-house source, build, test, manual and milestone directories and the port recipes, with every extensionless script that begins with `#!`, every `Makefile.*` and every file under `tests/native`, since `scripts.sh`, `textcheck.sh` and `nativecheck.sh` read them; it excludes extracted upstream trees, installed products, caches and binary artifacts. A file that another program removes while the walk runs, as a build step removes its temporary files, is not part of the tree and is skipped; any other file that cannot be read fails the digest with its path and the error. The native reader checks this digest and exact assertion and branch coverage before reporting a pass. A missing or stale record is incomplete and needs preparation again. It never launches a compiler or interpreter. The collection's prepared artifact record also protects the evidence file itself.

`krffscheck.c` runs the offline KRFFS tools directly through the native executor. It constructs corrupt images and each prefix of the update protocol in C, then checks repair, retained data and wrong write orders. `native.c` keeps its images under `build/tests`, records complete child output and removes successful scratch after process cleanup is confirmed.

### Product and driver regressions

`host-build-check` is a prepared C controller for the compiler, build and runner assertions of `host.list`. The controller creates fixtures, launches product programs, reads results and checks them through `fixture.c`. Command substitutes are native C entries of the same executable. The products retain their own command language: a commit hook runs by its executable entry, a port recipe runs in its normal shell, and make runs its own recipes.

Fixture command substitutes are private copies owned by the account that runs the check. They do not share inodes with prepared executables. The prerequisite firmware checks make only their private tree readable and retain each recursive path in caller-owned storage. Setup failures report the operation, path and system error before returning; the unreadable firmware file remains mode 0000 for the original privilege assertions.

The agent guest interruption check writes one byte through its open input FIFO and waits for the product's cat command to copy that byte into its private log before sending TERM to the child group. A newly created empty log is only evidence of redirection, which precedes execution of cat. The writer remains open until the wait completes; exit 143 and complete scratch removal remain required. The separate work interruption and broken-pipe rows keep their original inputs and judgments.

The compiler checks retain the assembler instruction and byte comparisons, the linker's segment, section, symbol and PC-relative address checks, and both Doom ABI runs. The native Doom controller runs the x86-64 fixture in the products helper and transfers the prepared i686 fixture to a declared i686 recovery helper. Each run must exit 0, provide its complete checked output and print the exact 64-bit format line. The i686 helper uses the small image-tools initrd; it needs no GNU root or runtime compiler and is ended before the assertion returns. The build checks retain all launch-script settings, commit-message inputs, prerequisite reports and privilege cases, malformed recipes, firmware probes, `elfwrap.sh`'s kept wrapper, its same bytes and date in a fresh directory, and its replacement after a changed `cc1` or driver on both architectures, interrupted port resumes, make job limits and parallel maker requests on both architectures.

The make database and CMake jobserver fixtures invoke the prepared GNU Make at `/usr/bin/make`. The helper also supplies pdpmake as `make` for the musl system; that program does not implement GNU Make's database format or jobserver contract. All eight parallel makers are still checked for each architecture.

The launcher fixture checks durable claims for builds, worker checks and owner commands, including nested identity and claim release. Its CI row copies the production script into its private tree and explicitly selects its native mode, accepting only the known lines or native selector, runs the native entry as the release does, `full` on both architectures, with a valid private site and verifies that missing retention configuration prevents all work. The assertion is independent of the production site's activation. The native entry's projections, refusals, counted vectors and preparation order are checked by `etude_platform_hosttest --routine-entry-only`, which [the host tests' Readme](../../host/Readme.md) describes and the `etude_platform` check runs on the collection host. The separate `ci_run` fixture checks the lines and history entries of `tools/ci/run.sh`. The retired CI path's four independent launcher claims are not a contract of the native entry.

The release fixture keeps each mock WSL claim alive until its matching preparation or collection ends. Probes ignore ended claims, including when retries reuse a run identifier. The Windows row without a status rejects the first probe after each grant and requires all three attempts to prepare and collect. Only the interrupted hold row makes the sleep substitute stop the release.

`case_select` invokes the native collection entry on private manifests, preserving order, architecture restrictions, agent row choices and refusals before build state exists. Its accepted rows use the public dry selection entry because native execution does not build artifacts. `host_suite` invokes the prepared host driver over native probes, including real ASan, UBSan and, on Linux, LSan faults. The probes are compiled during preparation as `host-suite-probe`; the controller never compiles them. It checks every result, assertion and progress count, retained evidence, scratch isolation, exclusive scheduling, duplicate refusal and cleanup after a signal.

The products directory defaults to `/host-products`, or `HOST_PRODUCTS` for a native fixture run. It provides `etude`, `host`, `host-suite-probe`, `doom_libc-i686`, `doom_libc-x86_64`, `tcc/i386-tcc` and `tcc/x86_64-tcc`, and `tcc/i386-tcc-dynlink` and `tcc/x86_64-tcc-dynlink`, the drivers of TinyCC's library that `check_ifunc` links a dynamic executable and a shared library with. The fallback `ROOT/prepared` supports a staged native fixture. The GNU helper must provide working sanitizer runtimes before it can run the sanitizer probes; a missing runtime is a failed preparation or execution, never a skipped check.

### Product-family checks

`family_scenario` runs the grow host cases through the declared GNU products helper. Preparation compresses the immutable source archive with gzip. The files of the helper that change in ordinary work are not in `gnu-test.disk`. `tests/system/suites.mk` puts that archive and each architecture's two kernel profiles in `images/gnu-test-products.tar`, and `mk/gnu-image.mk` puts the files of the helper's products, `GNU_OUT/host-products/`, the cases' compiled controllers, etude and the KRFFS tools, in `images/gnu-host-products.tar`. Each case of `family_scenario` and `host_scripts_scenario` attaches the two ustar archives beside the helper's disk as the overlays `products-files-disk` and `host-products-disk`, the guest's `/dev/disk1` and `/dev/disk2`. Before it reads any of their files, the scenario unpacks both disks into `/host-products` as the helper's root, so a change to a test script, a case's source or a kernel remakes archives of some 35 MiB and boots the image of 24 GiB as it was. The image's `/host-products` holds only `fstool`, which the FAT and exFAT checks' helper runs. It then compares the guest SHA-256 of `/host-products/scripts-assets.tar` with the declared archive before unpacking its private source tree; no source archive crosses the serial channel. The prepared `host-family-check` C controller creates the counter records, file systems, plans, disk faults and measured-output fixtures, invokes the actual checker and grow programs, and compares their results. It copies only the product functions under test from `machine_grow.sh`; the former shell test driver does not run. The controller reports the original case and assertion identities in etude report records, which the native scenario accepts only after a whole report and confirmed process cleanup.

The helper uses a private 12 GiB disk and writes its fixtures under `/host-work`. The replay compares every restored byte of all 1856 ranges and both ends of every intervening gap. Its target and backup are removed on failure too. The family and script controllers export failed fixtures as complete direct files of at most 1 MiB, within a 7 MiB archive allowance, as `family-fixtures.tar` before the helper is ended. Its bounded inventory lists each selected or omitted direct entry. Larger files and directory contents remain on the retained private products disk. An export failure is reported explicitly. The prepared tools include `growset`, `growboot`, `growroot`, `growroot-memory`, `reflash`, `diskctl`, `bootctl`, `mkfatfixture`, `mke2fs`, `e2fsck` and `resize2fs`. The helper boots with `rach2.slot=recovery` so that the real bootctl reads its normal command-line source.

The five imagerace cases use the same native scenario and the prepared `family_image*.c` controller. Concurrent image builders meet at their own temporary-image publication step; a native command hook interrupts each observed publication step in turn. The controller compares the image and both dependency lists after every stop. The prerequisite and edited-probe checks use the actual root Makefile and component Makefile with private minimal images and the prepared TinyCC compiler. All manifests retain their own path expressions during the dependency check; C creates regular, executable, nested and hidden input fixtures and rejects a directory among the expanded prerequisites. No prepared result substitutes for a runtime check.

The disk-policy host case copies the selected architecture's prepared ordinary and read-only kernels from the helper's `/host-products/diskpolicy` directory and checks their hashes against its declared artifacts before running the actual `check_diskpolicy.sh` with the prepared `binfind`. Each architecture's products archive holds its own two kernel profiles, and this case boots the matching helper with it; no kernel crosses the runtime serial channel. C checks the five original acceptance and refusal results; the script never builds a checker or reads an undeclared kernel.

The metal family keeps its two host assertions. Its C transport controller runs every one of the 17 fault cases with both root-key and su transport, including the approved disk serial, refusal of similarly prefixed disk names, failed transfers and hashes, and FAT unmount, remount and independent host-read checks. Native command substitutes model remote replies; the actual deployment acceptance script makes its own decisions. The password controller runs all nine prompt, echo, split-output, repeated-prompt and pre-session connection cases against the prepared PTY fixture and real `ptydrive`. It audits the helper transcripts before cleanup and requires the original status, prompt and answer counts, retry count and returned bytes. The deployment scripts themselves are unchanged. The native transport scenario invokes all 34 fault rows as explicit commands of the same prepared controller, each under its declared step. A row has a validated one-based selector and its own scratch directory, so a later row cannot remove an earlier failure's evidence. Only a complete checked report, matching command status and confirmed child cleanup advances the declared transport-rows counter. A failed row remains failed while the other rows still run; a missing result or uncertain cleanup leaves the aggregate incomplete. The full-controller form remains available to existing callers. No clock heartbeat or wider bound substitutes for completed work.

The cached output is `GNU_OUT/host-checks/`: `driver` enters its prepared `tree/`, becomes the ordinary `test` account, and starts `/host-products/host --one GROUP ASSERTION ARCH`. Both target-ABI inventories are present. A new GNU store entry may reuse checks from the copy's preceding stored inventory. Preparation compares the compiler identity, commands, every recorded input and the program's digest before copying a binary. Absolute GNU compiler, sysroot, sanitizer and library operands compare through their store links; changed dependency entries or flags require compilation.

# Etude's cases

This directory has the case manifests of the suites that etude runs as cases, one family to a file, `FAMILY.json`, the programs of their host cases under `host/`, and the scenarios of their machine cases under `machine/`. A manifest says what each case runs, what it asserts and how it ends, in the contract that [etude's Readme](../../tools/etude/Readme.md#cases) gives. The suite of a family is the last part of its identity, split at dots: `host.style.json`, the family `host.style`, is `tests/run style`, the source checks of the tree, whose program is [`host/style.sh`](host/style.sh). `host.codexapi.json` and `host.museapi.json` are `tests/run codexapi` and `tests/run museapi`, the fake API server proved against Codex and Muse Code, whose program is [`host/agentapi.sh`](host/agentapi.sh). `host.imagerace.json` is `tests/run imagerace`, how `krffs/mkimage.sh` publishes an image when two builds of it run at once or one is stopped, and the prerequisites that keep an image current, whose program is [`host/imagerace.sh`](host/imagerace.sh). `host.krffscheck.json` is `tests/run krffscheck`, the offline checker `fsck.krffs` on KRFFS images broken on purpose, whose program is [`host/krffscheck.sh`](host/krffscheck.sh). `host.host.json` is `tests/run host`, the host tests of [`tests/host`](../host/Readme.md), the checkers' selftests and the fuzz corpora under the sanitizers, and the scripted checks that [`host/host.list`](host/host.list) names, an assertion for each check, whose program is [`host/host.c`](host/host.c), over the prepared inventory that [its Readme](host/Readme.md) describes; its case `boots` runs once for each architecture, booting that architecture's kernel, and the others once for both. `guest.disk-q35.json` is `tests/run disk-q35`, whose program, [`blockprobe`](../blockprobe.c), writes files through the page cache of a KRFFS root that `rach2.fsdisk` mounts from a disk on the AHCI controller of the q35 machine at 0:31.2, and reads them back. It boots a private copy of the disk that [`etude-disk.manifest`](../../krffs/manifests/etude-disk.manifest) stages. `guest.pools.json` is `tests/run pools`, the kernel's pools of pipes, ptys, sockets and processes filled at once, and made and closed a thousand times each without a leak of the heap, whose program is the guest probe [`poolprobe`](../poolprobe.c). `guest.authority.json` is `tests/run authority`, which kernel may write the whole disk: two guest cases boot each kernel with `tests/bootprobe` on a disk over AHCI. The scenario starts each service, waits for its listening record, checks its verdict after stopping it and leaves cleanup to etude. After an action fails, it stops its API service and reports dependent assertions as not run.

## Running

`tests/run NAME` runs a family's cases as it runs any suite, and prints a line for each case as it starts and the suite's result at the end. Before any suite runs, `etude check families` checks every manifest here against its schema and its rules, and a manifest at fault refuses the run, whatever suites it names. A host case's program can also be run alone, from the root of a tree that `make` has built:

    sh tests/cases/host/style.sh conventions
    sh tests/cases/host/agentapi.sh codex exchange
    ARCH=x86_64 sh tests/cases/host/imagerace.sh prerequisites
    sh tests/cases/host/krffscheck.sh prefixes
    sh tests/cases/host/grow.sh check

`RACH2_CASES` chooses cases of any suite by identity, as [the tests' Readme](../Readme.md) says. `RACH2_AGENTS_ROWS` chooses rows of `agents`, and `RACH2_ACCEPT_AGENTS` agents of `agentsaccept`, by the last part of their identities, in the order given. Each refuses a repeated name or an unknown name; unset or empty, the suite runs every case. [`case_select.py`](../system/case_select.py) makes all three choices.

The Muse cases also need Muse Code, which `make build/downloads/muse/muse` fetches.

A machine case's scenario runs alone with a scenario invocation, as [Machine scenarios](../../tools/etude/Readme.md#machine-scenarios) gives it, whose `case_id` names the case; a scenario of several cases reads it to choose its work:

    build/tests/cases/machine/raw_scenario invocation.json

## Interfaces

A host case's program is the node its `prepare` names, which the preparation builds under `build/`, or under the build of the architecture when the step is `per_architecture`; the rule in the root `Makefile` copies `host/NAME.sh` to `build/tests/cases/host/NAME`. The set driver runs it with the workload's arguments in a workspace of the item's own under the evidence directory, `build/tests/failed` or the one `RACH2_FAILED` names, which the driver keeps after a failure and removes otherwise. It gives `ETUDE_TREE` the root of the tree, `ETUDE_CASE` the case's identity, `ARCH` the item's architecture when the case has one, `ETUDE_SEED` when the workload gives a seed, and `TMPDIR` the workspace when the case has the `scratch` fixture. A program that reads the tree changes to `ETUDE_TREE` first, as `host/style.sh` does. A guest case's program runs on Rach2 instead, under the machine its QEMU profile gives, as [etude's Readme](../../tools/etude/Readme.md#the-set-driver) says: a guest program of [`tests/`](../Readme.md) that the test image stages at its root, which the preparation names by its file in the architecture's build, such as `tests/poolprobe`, through a rule of the root `Makefile` that runs the `tests` sub-make. The machine boots the test image, whose debug shell starts `etude-guest`, so the program runs as an ordinary child of it: in a workspace of its own with no terminal, standard input from `/dev/null` and its output to pipes, not as the shell's transient init on the console. A machine case's program is a scenario in `machine/`, a host program linked with `libetude-case`, which boots the machines of the case's `machines`, types at their consoles, runs host tools between the boots and reports each assertion itself, as [Machine scenarios](../../tools/etude/Readme.md#machine-scenarios) says. Each boot has a private copy of its disk, or an empty disk of the size its profile gives, so a scenario compares a copy with its artifact byte for byte after the boot, as the `diskpolicy` and `diskdiag` scenarios do, writes into a copy between two boots of it, as the `install` scenario writes the environment blocks of GRUB and the `sealed` scenario destroys sectors of its copy and runs `debugfs` and `e2fsck` on the root inside it, at the root's offset in the file, or writes file systems into empty disks with host tools before it boots them, as the `diskrate` scenario does. Each boot of a machine is a QEMU of its own, and a `reboot -f` in the guest ends one, since QEMU runs with `-no-reboot`. The keys and passwords of the demo and test accounts that a scenario uses are artifacts too, the root `Makefile`'s copies of them under `build/tests/cases/credentials/`, readable by their owner alone. The program writes its report records on its standard output, as [Report records](../../tools/etude/Readme.md#report-records) gives them, with any lines for a person between them, and `etude check attempt` judges the item by the manifest, the records and how the program ended. A case passes only when every assertion its branches select passed, the program ended as `termination` says and nothing in the report contradicts the manifest; a check whose tool is absent or at a version that does not judge reports a branch, never a printed skip.

A guest program reports through [`tests/probe_report.h`](../probe_report.h), and takes its case's identity from `ETUDE_CASE`. The authority cases have the role `boot`: each boots the test image with `rach2.bootprobe=auth-ordinary` or `auth-recovery` on the kernel's command line, which selects `bootprobe`'s mode, and a private copy of `images/auth-test.disk`, which `mkfixture auth` makes: 4 GiB of zeros with an MBR whose FAT-typed entry 1 the kernel publishes as `/dev/bootpart`, and whose signature makes it publish `/dev/grubcore`. `bindholdmusl` writes its report only once its rows have ended, since each row counts the free blocks of the boot root, on which `etude-guest` keeps the program's output. The textbusy cases have no `scratch` fixture, so that each program makes its directory under `/tmp`: their mount points would be longer under the workspace than the 63 bytes the kernel takes for one (`VFS_COVERED_PATH_MAX` in `rach2/sys/fs/vfs.h`).

The real account case and the credential persistence case each keep one private disk through three cold boots. Their boots depend on the previous boot's writes, so each sequence is one case. Every other process case has one boot. The procfiles applet case starts one `sshpeer` service on its reserved port and waits for the SSH server's identification before running the applets; no clock decides whether the connection exists. Its probe is staged in a copy of os-real. The root mount cases run `procprobe mount` with the exact mount line of their profile. The descriptor cases use the disk of etude's guest cases, with a boot partition added to the raw-offset case's copy.

Each agent row has a case in `machine.agents.json`. The scenario creates each private SSH key once and passes its path to the workload and acceptance controllers; the controllers borrow these paths until the scenario cleans them up. Its guest file, `tests/system/agents/NAME.sh`, defines `row`, which `agents_rows.sh` runs as the test account in a private directory. The host scenario is C. It reads the row's `hosts`, `script`, `package` and `verifier` headers from the prepared source archive, creates a private authority with the compiled API service, and renders the selected script with the service's `render` command. The archive and authority go to the guest through etude-guest's framed channel. A local SSH login with the test key checks the guest's SSH server and account before the row runs. The scenario checks the row's status and `AGENTROW OK NAME`, stops the API service and checks its verdict, then runs its C record and archive verifiers. Git comparisons run in the guest; JSON audit, program digests, worker-loop board state, session transcripts and log ordering are checked by C on the host. The Codex digest is a prepared artifact from the verified upstream package. No host shell, interpreter, Git or OpenSSL command runs in these cases. The fake API case uses the guest's curl and the prepared C WebSocket client to check certificate rejection, verified TLS, JSON, chunked events, ping, masked frames and the close handshake.

The API cases keep their identities, `host.codexapi.exchange`, `host.codexapi.refusal`, `host.museapi.exchange` and `host.museapi.refusal`, but have the domain `machine`. Their C scenario, `machine/agentapi_scenario.c`, runs the exact pinned upstream CLI from the prepared GNU agents root, with a fresh home and repository. QEMU's restricted user network permits only the C fake API route; an attempted outside connection must fail. The exchange cases retain the catalog, WebSocket warmup and continuation, HTTPS fallback, tool results, bearer keys, user agents, edited greeting, commit author, changed paths and clean work tree checks. The refusal cases change the notes and require the first incorrect tool result to fail the service while leaving the greeting and history unchanged. Muse is observed still running when the first rejection arrives, then cancelled through the framed channel. Cleanup removes the home and certificate keys, reaps the service and waits for QEMU's exit. No Linux namespace tool or tooling machine runs these cases.

Each guest case of `fpu` and `noentropy` boots the test image under its own processor profile and boot line, so that the kernel chooses its path once: `max`, which declares XSAVE, AVX, RDRAND and RDSEED; `max` with `rach2.noxsave` or, on i686, `rach2.nofxsr`; and `qemu64`, which declares none of them. A probe reports the branch it took, which `etude check attempt` judges against the profile where a group is decided by features, and a case whose boot line or profile turns XSAVE or FXSR off also requires, as an assertion of the executor, the kernel's line `fpu: fxsr: ..., sse: ..., xsave: ...` that says so on the console. The musl programs are not at the test image's root, so the set driver sends their bytes to `etude-guest`. `passwdmusl` exits with status 1 on its fail-closed side, which its case expects, and `keygennoent` runs the `dropbearmulti` that the test image stages at os-real's path.

The `imagerace` cases `concurrent`, `interrupted` and `restage` build their images in a private tree under `TMPDIR`, running `krffs/mkimage.sh` from the root of the tree as the root `Makefile` does. The first two put shims of `dd`, `sed`, `grep`, `mv` and `touch` first on the build's path. A shim whose arguments name the image under test is a step of the build: it counts the step, stops the build with SIGTERM at the step the case chose, or holds the touch of the temporary image until the other build has made its own. `prerequisites` asks the tree's own make about the shared images and writes a marker below the build tree's `tests/system`, which it removes; `probe` runs [`imagerace_probe.sh`](../system/imagerace_probe.sh), which copies the makefiles into a directory of its own under `build/tests/system`.

A machine case's program is a scenario, a host program that `make build/tests/cases/machine/NAME` links with `libetude-case`, the same for both architectures. The set driver publishes the artifacts of the case's `prepare` to a store under `build/tests`, and runs the scenario with one argument, a [scenario invocation](../../tools/etude/Readme.md#machine-scenarios) that gives their digests, the emulator on the path, the bounds of the steps and the scratch directory. The scenario boots the machines its manifest declares on private copies of their disks, reports each assertion, and keeps each machine's console in the scratch directory. `etude check attempt` reads the consoles for the assertion `etude.kernel`: a record the kernel printed at the critical level fails the case, unless the case ends in a panic or the record has the text that its machine's `critical` gives, as `machine.shutdown.init-death` gives for the halt after init's death, or one of the records of its machine's `fault` on the console of a boot that the scenario reported ended in that fault. Such a case also has `etude.fault`, which takes the machine's panic or halt from the scenario's report and the boot's console, apart from the scenario's own exit. A scenario over `machine/lifecycle.c` reads a machine's console with `lc_console`, waits for the debug shell with `lc_shell`, and with `lc_run` types a command there and judges the record with which the kernel hands the shell back: a record that the program was killed fails it, and so does a first exit record with a status other than 0. It also reads a value the machine printed, such as a count, from that console with `lc_text`, and waits for an event the machine shows, never for a time: the HDA case reads intrprobe's count of the controller's messages before and after the scale, and the Doom case waits for the game's report of its first frame and for the end of a demo, whose last report must count more than one frame. A boot whose profile names an `audio` card records what the card played, which the case ends with QMP's `quit` so that QEMU finishes the file before `wavcheck`, an artifact of the case's `prepare`, reads it.

The shared scenario disk-range copier uses the image tools' signed 64-bit stream positions, including native Windows seeks. A partition past two terabytes must be copied to and read from its full byte position; an independently addressed sparse extent in the scenario host fixture checks both directions and neighboring bytes.

The UDP clock reference shared by the clockmusl and self-build scenarios runs in a private thread on Windows. Its socket uses read events; stopping it signals a separate event, joins the worker and then closes the socket. No thread closes a socket while another is receiving from it. The POSIX reference remains a child process that the scenario kills and reaps.

The krffsmount scenario runs `fsck.krffs --strict` on the volume of the disk copy between boots, at its partition's offset and the volume's length, so that the check repairs nothing the next boot would see. Its `pull` case boots a stick on an xHCI controller, a disk on a device of the profile, and pulls it with QMP's `device_del` once `krffsprobe pull` writes it; when the probe says that the stick has gone, it plugs the same file in again as a second drive, which the human monitor's `drive_add` makes as the old harness did, and a second `usb-storage` device, which QMP's `device_add` makes, while the old mount is still there. The pulled stick's drive stays in QEMU and keeps its lock on the file, so the second drive is made with `file.locking=off`. Its `failed` case boots under `rach2.blocklag=1` and `rach2.blockfail=24` on a disk with `flush` false, as the lag cases of `mount` and `loopdev` do.

One scenario serves the cases of a family, chosen by `etude_case_id`, and may serve several families: [`machine/e1000_scenario.c`](machine/e1000_scenario.c) the three boots of the e1000 family, [`machine/netconsole_scenario.c`](machine/netconsole_scenario.c) the two netconsole families, whose cards' frames QEMU records for pcapcheck to read, [`machine/metal_scenario.c`](machine/metal_scenario.c) the metal image reached over SSH with nobody at its console and the acceptance script's installed-root rows, [`machine/drill_scenario.c`](machine/drill_scenario.c) the two cases of the drill, and [`machine/dhcp_scenario.c`](machine/dhcp_scenario.c) the ten cases of the dhcp family, each on a user network of its own or, for the boot that must find no server, on a hub of QEMU's with nothing else on it. They, the menu, install and sealed scenarios share [`machine/netcase.c`](machine/netcase.c), which types at the console and logs in there, runs host tools such as ssh against the port the machine's card forwards, and reads the console and what the tools wrote; a file a scenario writes itself is evidence that `net_path` names, which it removes after an attempt that passed. The metal scenario runs the tree's `metal_accept.sh` as the release does, from the root that `ETUDE_TREE` names, and the metal family's two host cases run the acceptance script's own tests through [`host/metalchecks.sh`](host/metalchecks.sh). [`machine/sshpeer.c`](machine/sshpeer.c) is the host's side of the connections that are not logins: the metal scenario waits with it until the guest's server answers, and the ssh cases' service holds forty of them open against the server and says each time it answers another. The drill's repair case boots one private copy of its disk through SeaBIOS and GRUB seven times, and between the boots changes the copy itself, as the drill changes a machine whose case nobody opens: it destroys the root's superblock, arms recovery in GRUB's environment block, and destroys the start of partition 2 and then of partition 1. Its no-dhcp case puts the card on a hub of QEMU's with nothing else on it, so that no DHCP server answers. Their disks and sticks are made by rules in `system/suites.mk`.

The scenarios of `socket`, `dgram`, `raw`, `persist` and `load`, and [`machine/netif_scenario.c`](machine/netif_scenario.c), which serves the netif and addressed families and also links `netcase.c`, are also linked with [`machine/console_report.c`](machine/console_report.c). A scenario that needs the host to act while its probe runs, such as the dgram case's datagram from outside, or to read what the probe cannot see, such as a capture of the card's frames or an echo server's log, boots a machine without `etude-guest`, types `exec /PROBE` at the kernel's debug shell as the old suites did, and gives `console_report` the console from that point: the probe's records on the console become the scenario's own, so its manifest lists the probe's assertions beside its own, all with the source `scenario`.

The persist cases boot their machine twice on one copy of `images/persist-test.disk`, which [`persist-test.manifest`](../../krffs/manifests/persist-test.manifest) stages: the first boot writes the file, syncs it and is ended by QMP's `quit`, as a power cut would end it, and the second reads the file back. The `lag` case of `load` has each request of disk 0 answered a tick late with `rach2.blocklag=1`, and gives its disk `flush` false, so that a flush of the guest's does not wait for the host's disk, which is not what the case judges; `polled` reads the disk by programmed I/O, `rach2.atapio`, and runs the loads `Wnr`, one writer that does not sync and the console's reader.

The fault cases end as their probes do, by SIGSEGV, so no program report is written; each asserts, as the executor, the kernel's record of the kill, `vm: fault: killing pid N: bad write at 0x...`, which `judge.c` finds on the console. `diskfull` boots the test image for itself, since it fills the root. `queue.fault` boots no RAM image: `rach2.root=disk` mounts its root from the first partition of `images/queue/root.disk`, and `ahciprobe` runs `blockprobe` there with its standard output on standard error, so that the records on the console are `ahciprobe`'s alone. The disks of the queue and load cases are made by rules in `system/suites.mk`.

The scenarios of the two USB families, [`machine/usb_scenario.c`](machine/usb_scenario.c) and [`machine/usbdisk_scenario.c`](machine/usbdisk_scenario.c), share [`machine/usbcase.c`](machine/usbcase.c), which types at the kernel's debug shell, presses keys and moves the mouse through the monitor, plugs and pulls devices and media, runs a probe and reads the console it wrote. The sticks, the far volume and the checker of the keystroke records that their cases name are made by rules in `system/suites.mk`, the sticks by [`system/usbdisk_sticks.sh`](../system/usbdisk_sticks.sh), and [`host/usbchecks.sh`](host/usbchecks.sh) is the program of the two families' host cases.

The hub-pull case waits for four complete slot-return records before counting them. A console wait returns just after its matched text, which may precede the rest of a line.

Each gnu case boots `images/gnu-test.disk`, which `system/suites.mk` makes from the GNU root, `os-real-gnu.ext2`, with one partition at 1 MiB, through a qcow2 overlay of its own, so that the 4 GiB disk is published to the store once a run and copied for no case. The scenario waits for init's record that it started OpenSSH's sshd and then for the server's identification through `sshpeer wait`, which waits 50 milliseconds after each refused identification before opening another connection. The delay limits the host TCP state created while the server makes its host keys; only the actual SSH identification establishes readiness. A row's case puts `gnu_rows.sh` on the machine with scp, with the files the row reads, GNU sed's tarball for `autotools` and `clockmusl` for `ntpd`, and runs the row as root; its one assertion holds when the output has the whole line `GNUROW OK NAME` and ssh ended with status 0. The ntpd case starts the compiled [`system/sntpserver.c`](../system/sntpserver.c) as its service on its second port, and the row points the machine's ntpd at it through the user network's gateway, 10.0.2.2. Each row runs its programs on the machine: `autotools` unpacks GNU sed, runs its `configure` and `make` and runs the sed it made, `gcc` compiles and runs C and C++ programs, and `chromium` runs a page's script in the headless browser; no result comes from an earlier run.

The SSH scenarios run their clients inside a declared Rach2 machine, `channel-client`, on a private overlay of the prepared GNU image. Its first step opens etude-guest's framed console channel. The controller sends key and input files through that channel, runs the installed OpenSSH clients and the guest ptydrive, and fetches sftp's output through the same channel. The clients reach each server through QEMU's gateway and the case's reserved forwarding port. The extra machine, processor, memory and disk are declared in each case that uses it and end with the case. Password, terminal, key, scp and sftp assertions still exercise their protocols. Ordinary GNU rows instead open the channel on their target after root's console login and use it for command and file transport.

The unattended metal case uses [`machine/metal_accept.c`](machine/metal_accept.c) for its acceptance checks. The host controller judges the command results, selects a stick by serial, refuses recovery media and duplicate serials, checks mount and remount persistence, and compares the unmounted bytes with independent filesystem tools. Root commands through the test account use `net_su`, which drives the real guest SSH terminal, requires one password prompt and answer, and returns the command's output and exact status. The Lenovo's native acceptance scripts retain their existing route.

## Adding tests

A new case goes into its family's manifest with a new `case_id`, and a new assertion with a new `assertion_id`; changing what an identity means takes a new one. The program reports each assertion the manifest lists for the branches it chooses, and nothing else. A new family takes a row in `tests/registry` whose name is the last part of its identity, a sentence `` `tests/run NAME`: `` in `system/suites.mk` with no target under it, and the suite's line in `system/suites.md`, which `tests/run inventory` prints. `tests/run style` refuses a row that has both a target and a family, and a manifest that is at fault.

## Tests

`tests/run style` checks the manifests with `etude check` and the programs with ShellCheck, and runs [`style_cases_test.sh`](../system/style_cases_test.sh), which requires a planted source fault and a planted manifest fault each to fail its case. [`verify_temp_test.sh`](../system/verify_temp_test.sh) requires `style.sh` to keep its logs in a private directory of each run. [`host_suite_test.sh`](../system/host_suite_test.sh), a check of the host case `scripts`, runs `host.sh` in a private tree of fixture tests, scripts and a manifest, and requires a result, a record of progress and an assertion for each check, the assertion `listed` to fail for a test the manifest does not name and for one the tree lacks, and a stop signal to end a script that never ends.

The native host driver regression, `etude_hostdriver_hosttest.c`, runs prepared fixture binaries and checks source identity, scratch isolation, fatal sanitizer settings, missing assertions and refusal of interpreter artifacts. The legacy `host_suite_test.sh` remains declared until its process interruption and scheduling checks have native fixture adapters.
The image and installer checks of `host.host.scripts` use `host/host_image.c` and its component controllers. The C controller creates each fixture and judges every row. The declared GNU helper executes the actual `mkext2.sh`, `mkimage.sh` and `tooling_image.sh` products and the installer's complete account functions; it does not execute the old shell or Python test controllers. The tooling signal fixture is compiled C. KRFFS tools run as native prepared executables. The collection check exercises the declared image helper with real file-system tools, including names with spaces, a byte offset, a populated ext2 tree, and partial output from a compiled tool that exits 7. The former Python adapter's goal and style dispatch checks are replaced by execution of this native controller under the same assertion identity.

`host/flow_board.c` and `host/flow_ci.c` control the board and CI regressions in the prepared GNU helper. Their GitHub, Git, clock, build and run stand-ins are compiled C. The actual `board.sh`, `report.sh` and `bisect.sh` scripts remain the products under test. Board checks retain all 70 rows. CI checks retain report recovery, issue and status changes, bisection continuation, late standard-error results, structured history verdicts and admission records. Each controller uses the shared private-file and child-process fixture.

`host/flow_ci_run.c` retains the CI run driver's 29 rows. Its compiled run and build stand-ins supply lines, history streams and kept directories. A C monitor observes killed commands, inner step shells and the run's parent through a pipe that remains open until every writer has ended. The controller checks that a stopped run starts no later step, writes no `done`, and retains each architecture's own records.

The grow scenarios read saved exFAT files directly with the prepared native `mkexfatfixture`, whose complete output goes to a file. The native archive reader extracts `ranges.txt` from the grow plan and requires exactly one regular entry with that name. The drill runs the prepared C recovery-authority checker; its shell entry is used only during artifact preparation.

The GNU login controller writes its SFTP batch in binary mode, as the UEFI controller writes its install-answer script. The Rach2 client adapter reads these command bytes without native newline translation; a destination's basename or shell token must not contain a CR from a Windows text-mode writer. The real commands, returned bytes and confirmed client cleanup remain the assertions.

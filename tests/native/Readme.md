# Native cases

This directory says how each guest program runs on a Rach2 that is already up, such as the Lenovo: as an ordinary child of `etude-guest`, with no boot, command line or fresh kernel of its own. A program, or a part of one, that needs the designated init, a boot of its own or a device that QEMU makes stays in its suite under QEMU, and `machine` says why. `tools/verify/nativecheck.sh` checks that every guest program has a case here, is staged by one, or has a line of `machine`.

## Interfaces

The first case, `lenovoacpi`, accepts the Lenovo G50-70's ACPI initialization, embedded controller and its enabled GPE, and the named keyboard, power button and video bus. It runs before other cases can evict the boot records. With the panel unblanked and powered on, it sets a middle brightness, calls `\_SB.PCI0.LPCB.EC0._Q11` and `_Q12` through `/proc/acpi/call`, reads their brightness keys without grabbing the video device from the installed `acpid`, and requires the requested and actual backlight levels to follow each action. It restores the original requested level on success, failure and an ordinary stop signal: first it waits for the level of an action whose key it read, then it takes the lock the brightness action holds while it runs, `/var/run/acpi.lock`, so that no action overwrites the restored level. A second stop request ends that wait. The collection's progress bound ends a missing event or action; the probe sets no deadline. Physical keys, screen sleep, poweroff and persistence across a reboot still need the sitting with the owner.

`probes.cases` has the cases of the freestanding probes, `musl.cases` those of the musl programs, `rows.cases` those of the GNU and agents rows and of `tccbuild.sh`, and `gpu.cases` the Lenovo's GPU conformance cases, which run each runner of `tests/graphics` on the machine's own GPU and judge it against Linux's run on the same machine, as [the graphics tests' Readme](../graphics/Readme.md#the-lenovos-conformance) says. `gpu.cases` also runs, after the conformance cases, the end's Lenovo runs, each from a state that starts at once, through scripts of this directory: `testbed.sh`, a scene of the test bed's harness (`bed/measure`) set beside Linux's line; `display.sh`, the display's rows of 76's checkpoint slice, a mode set and flip on the panel's card, Weston killed with the console back, the touchpad's capabilities and the kept file of the data partition; `tests/system/games/lenovo.sh`, the native games' replays judged against Linux's frame times; and `crysis.sh`, Crysis's flyby and a save loaded after the release's update, on a private copy of the game the data partition holds: in the case's own namespace it mounts the partition read-only, builds `/data/crysis` in the workspace's `private` from links to the game's files and copies of its prefix, saves and caches, which the `private` fixture removes however the case ends, so that nothing of the owner's is written and no copy outlives the case. `gpu.cases` runs as well `gpuvideo.sh`, the video checks against Linux's decodes, browser plays and hangs, with the clips on the data partition, and `bed.sh`, the test bed's rungs through a VM on the GPU, whose disks the data partition holds. `rows.cases` has `vmexit.sh`, kvm-unit-tests' vmexit group set beside Linux's cycles. Each case is one line:

    case NAME FIXTURE... -- PROGRAM [ARGUMENT...]

NAME is the program's unit in the inventory, such as `credprobe` or `musl/ctrlcmusl`, with `.VARIANT` added when the unit has more than one native case, as `dirprobe.krffs` and `dirprobe.ext2`. PROGRAM is the program's path under the build's `tests` directory, or, when it begins with `native/`, `system/` or `graphics/`, a script of `tests/` itself, and the ARGUMENTs are given to it as they stand. A `#` begins a comment, and a line may be continued with a final `\`.

Each case has a workspace: a directory of its own, its working directory, removed after a pass. A FIXTURE adds to it:

* `stage:PATH[,PATH]...`: each program of the build's `tests` directory, such as `hello` or `musl/statushelper`, or each file of this directory, such as `native/hello.txt`, copied into the workspace under its last component, or to the root's `/` in a case with a private root.
* `file:PATH`: the file PATH of the source tree, such as `tests/graphics/runners/judge.py`, copied into the workspace under its last component. A case gives etude-guest at most 16 files: its program, its staged programs and these.
* `image:IMAGE[,IMAGE]...`: each image that `maps` names, copied into the workspace as the file IMAGE and neither attached nor mounted.
* `volume:TYPE:IMAGE` and `volume:TYPE:IMAGE:attached`: the image that `maps` names IMAGE, of file system TYPE, copied into the workspace and attached to a loop device; the first form also mounts it on `vol0`, `vol1` and so on in the workspace, in the order of the case's volumes.
* `tmpfs:SIZE`: a tmpfs of SIZE bytes, or with `K` or `M`, mounted on `tmpfs` in the workspace.
* `root:TYPE` and `root:TYPE:MIB`: a private root made for the case as a `krffs` or an `ext2` volume with MIB mebibytes free beyond its files, 64 unless given, or as a directory on the workspace's own file system for `ext2-dir`. It has the test image's tree, its set-id copies and accounts among them, with the ids of `maps`, and the program and the case's staged files at `/`. The case runs in it, in a mount namespace of its own, with the machine's `/proc`, `/sys` and `/dev`, its `/dev/shm` and `/dev/mqueue` among them, `/` as its working directory, and the program at `/PROGRAM`.
* `mountns`, `ipcns`, `utsns`: a namespace of that kind of the case's own.
* `private`: a directory `private` in the workspace, removed with all it holds once every process of the case has ended, after a pass, a failure or a forced stop alike, while the rest of a failed case's workspace is kept as evidence.
* `gpumin`: each card's minimum GPU clock, `gt_min_freq_mhz`, read before the case starts and written back once every process of the case has ended, after a pass, a failure or a forced stop alike.
* `ids:OLD[,OLD]...`: the user and group ids the program uses, which the run maps as `maps` says.
* `ports:OLD[,OLD]...`: the local ports the program uses, mapped likewise.
* `pty` and `pty:INPUT`: a pseudo-terminal whose slave side is the program's descriptors 0 to 2 and its controlling terminal; INPUT, a file of this directory, is written to the master side.
* `peer:ROLE`: a process on the controller's side that plays ROLE. Its address and port reach the program as `peer=ADDRESS:PORT`, and what the role knows of the machine's network as further arguments. `echo` is a TCP and UDP echo server, as `tests/system/runner/hostpeer.c` plays it; `dgram-outside` sends one datagram to the port that 7502 maps to once the program prints `DGRAMPROBE OUTSIDE`; and `network` answers echoes and gives `ifname=NAME` and `addr=ADDRESS/PREFIX`, the machine's own interface and address, `gateway=ADDRESS`, `far=ADDRESS`, an address off the subnet that answers echoes, `empty=ADDRESS`, an address on the subnet that nobody has, and `silent=ADDRESS`, one that nobody answers, from the machine's declared network.
* `log`: the kernel's records written while the case ran are kept beside its output.
* `alone`: no other case runs on the machine meanwhile.
* `console`: the machine's console and framebuffer, with `alone`: the desktop's Weston, which holds the display and the card's master while it runs, is ended before the case starts, and the session is started again once every process of the case has ended.
* `env:NAME=VALUE` and `env:NAME`: the variable NAME set to VALUE, or left out, in the case's environment, which otherwise has `PATH`, `HOME` set to the workspace, and `ETUDE_CASE`.
* `end:signal:N`: the case passes when the program is killed by signal N; otherwise it passes when the program exits 0.

`maps` has the maps, the test account and the images. `idmap OLD:NEW...` and `portmap OLD:NEW...` lines give each id and port a case may name, and the native value given in its place; a NEW is used by one OLD alone. Exactly one `account NAME UID` line declares the ordinary test account. Its uid is from 1 to 65535 and differs from every mapped id; its name has at most 63 letters, digits, `.`, `_`, `+` or `-`. `image NAME TYPE MIB` names an empty volume image of TYPE and MIB mebibytes, and `image NAME TYPE MIB from PATH` the image of the build that PATH names, such as one a suite's preparation makes. PATH may end in `@BYTEOFFSET`; then preparation copies MIB mebibytes from that byte offset in the source disk. The ext2 fixture uses the declared fixture disk this way, so preparation does not depend on an undeclared volume side file. A `vfat` image is FAT32, and an `ext2` image has blocks of 4096 bytes.

`tccbuild.sh` is a TinyCC build that `etude run native` of [`tools/etude/`](../../tools/etude/Readme.md) runs on the machine with `etude-guest`, as its host test does with the host's cc: `tccbuild.sh pass` compiles a small program, linked `-static` as every program for Rach2 is, or without it on macOS, whose linker makes no static program, runs it and checks its output; `fail` compiles a file that stops at `#error`; and `loop` builds again until it is stopped. The compiler is `$TCC`, `tcc` unless set.

`machine` has a line `NAME REASON` for each guest program that has no native case and is staged by none: the reason its checks need a machine of QEMU's, in a few words.

The bind-holder program receives `mounted` for its private KRFFS root. It requires the mounted volume's exact filesystem magic and runs all twenty holder and reclamation assertions. Its virtual-machine case supplies no such argument and still requires the boot root's different magic. Mounted-mode copies retain the exact ELF prefix and add checked zero padding so each file extent, including its KRFFS header, is a whole 4096-byte block. Intermediate writes preserve that alignment too. This respects the mounted backend's refusal of metadata fields split between blocks; every holder checks the full file, padding and EOF, and every row still requires exact space reclamation.

A program learns its native values from its arguments, which `etude-guest` appends after the case's own, as [`probe_args.h`](../probe_args.h) reads them: `ids=OLD:NEW,...` and `ports=OLD:NEW,...` for its maps, `loops=DEVICE,...` for the devices of its volumes in order, `peer=ADDRESS:PORT`, and `root=PATH`, the private root's directory on the machine, though the program's own `/proc/mounts` names that root `/`. A case whose program has checks that need the machine gives `machine=native`, and the program leaves those checks out; a comment above the case names them. The program starts with its absolute path as `argv[0]`. Run with none of these arguments, as the test image runs it, a program uses the ids, ports and paths of the test image and makes every check. The GNU and agents rows, `tests/system/gnu_rows.sh` and `tests/system/agents_rows.sh`, take arguments of the same kind, as their headers say.

### Local collection

The prepared public command `etude run native` runs on the already booted Rach2 system. It reads `probes.cases`, `musl.cases`, `rows.cases`, `gpu.cases`, `maps` and the prepared `images/roots` index. It starts the declared `etude-guest` executable directly over pipes and uses the existing framed invocation, file, result and cleanup protocol. It invokes no host shell, SSH client or interpreter. The scripts named as GNU, agent and TinyCC workloads still run on Rach2 as the inventory declares them.

`make native-assets ARCH=x86_64` cross-builds the driver and prepares its immutable payload under `build/x86_64/tests/native/prepared`. `etude prepare native --architecture ARCH --output DIR` of [`tools/etude/`](../../tools/etude/Readme.md) prepares it, with the build's KRFFS tools and exFAT builder, one installation of e2fsprogs, mtools' `mformat`, Git and gzip; `--mke2fs`, `--debugfs`, `--e2fsck` and `--mformat` name other copies of those tools. It refuses a tree with uncommitted changes, since the payload records the commit. It creates the mapped private roots, preserves their owners and modes, checks the ext2 roots, and writes an index and SHA-256 list of the supplied files. Its `tree` directory contains the inventory, programs, source recipes and images; `stage` and its seven numbered subdirectories contain files etude-guest resolves by name, size and digest. Different programs with the same final filename occupy separate directories; all eight directories are supplied to etude-guest through its existing repeated `--stage` option. No test executes during preparation. A staged image is copied into the attempt before any test writes it.

Deployment copies this prepared payload and the architecture's etude-guest to the owner-approved directory, ordinarily `/var/native`, and makes the `account` of `maps` if needed, and the account's home directory when it is missing, since an update of the machine's root keeps the account but not a home under the target. Deployment keeps its existing SSH transport. It verifies the payload digest and account id before starting the collection, and changes no files in a payload that a collection uses. The ordinary GNU test account, 60000, remains separate from the probes' mapped ids.

On Rach2, an invocation is:

```text
/var/native/p-DIGEST/tree/build/x86_64/tests/native/etude run native --tree /var/native/p-DIGEST/tree --guest /var/native/p-DIGEST/tree/build/x86_64/tools/etude/guest/etude-guest --state /var/native/state --stage /var/native/p-DIGEST/stage --results /var/native/results-RUN --peer MAC-ADDRESS:PORT --outside-peer MAC-ADDRESS --interface eth0 --address MACHINE-ADDRESS/PREFIX --gateway GATEWAY --far FAR --empty EMPTY --silent SILENT
```

`etude run native list` prints the declared case names. `-- CASE...` selects exact names and refuses an unknown or repeated name. `--arch i686` selects the i686 program paths; the GNU and agents entries of `rows.cases` describe the installed x86-64 GNU system. The collection runs one case at a time under an exclusive directory lock. It records every selected case in `summary`, including an interrupted case and those not started after interruption. A missing file, map, root or peer is a failed case with a reason, never an omitted case. Each case retains `out`, `err`, the protocol evidence and journal, and `result.json`, with both the API status and the collection's judgment. A pass requires a whole result, the declared exit or signal, confirmed process and fixture cleanup, and removal of the private workspace.

The external echo peer remains the Mac's prepared `hostpeer echo PORT 0`, bound with `HOSTPEER_ADDRESS` to the Mac's address. The datagram peer is `hostpeer send-repeat 47502 outside`, with `HOSTPEER_ADDRESS` set to the machine's address or the value that the port map gives 7502 in place of 47502. Its destination is the IPv4 address in `--network`, which may differ from the SSH host name. A send that finds no route, host down or network unreachable, as macOS reports while it has not yet learned the machine's link address after a reboot, is sent again the next second, and the first of a run of them is named on stderr; any other send error ends the peer. The deployment process owns both peer process identities, records them, and sends termination and waits for both on every exit, failure and interruption. The Rach2 driver never substitutes a local peer for either external peer and never signals an unowned process.

### TinyCC proof

`etude run native proof` takes the same tree, guest, state, stage and result options. It runs `tccbuild.sh` in four modes: a successful compile and execution, an intended compiler failure, cancellation of a repeated build, and a pipe connection cut after the first completed build. The cut uses a compiled transport entry of the driver; a new connection reads the attempt's recorded end and confirms cleanup. The proof keeps the raw result and checks the expected cancellation or connection-loss outcome separately, then removes the ended workspace. It supplies code for the four machine checks of issue 963; only a recorded run on the Lenovo supplies their hardware evidence.

`make -f tests/native/local.mk CC=tcc`, from a private copy of the supplied source tree on Rach2, builds `build/tests/native/local/etude` locally with TinyCC, with the same public entry and validator as the cross-built command. It uses the same source list and framed library as the cross-built executable. The TinyCC build workload remains supplied as source in `tccbuild.sh`, including its deliberate `#error` and repeated-build cases.

### Owner-side deployment

`make build/tools/dev/native-deploy build/tools/dev/native-hostpeer` builds the Mac's C deployment helper and its external peer. It starts only the configured SSH client and the prepared `native-hostpeer` executable, with structured arguments. It neither runs a host shell nor interprets test output. Deployment starts only after the reviewed candidate passes its complete virtual-machine run; this helper builds no candidate and changes no boot slot.

`make native-assets` also writes `prepared.tar.gz` and `prepared.tar.gz.sha256` beside the prepared directory. The local preparation record identifies that exact archive. The helper checks both archive digests and the supplied maps digest before connecting, requires a private SSH key, and records the supplied host, the Lenovo's station address, slot, kernel digest, target and process identities in a new absolute LOGS directory. Its interface is:

```text
native-deploy stage PAYLOAD HOST SLOT KERNEL KEY TARGET RUN LOGS
native-deploy run PAYLOAD HOST SLOT KERNEL KEY TARGET RUN LOGS --hostpeer FILE --peer MAC-IP --echo-port PORT --network MACHINE-IP/PREFIX --gateway IP --far IP --empty IP --silent IP [-- CASE...]
native-deploy proof PAYLOAD HOST SLOT KERNEL KEY TARGET RUN LOGS --hostpeer FILE --peer MAC-IP --echo-port PORT --network MACHINE-IP/PREFIX --gateway IP --far IP --empty IP --silent IP
```

PAYLOAD is the prepared directory, such as `build/x86_64/tests/native/prepared`; its archive is PAYLOAD followed by `.tar.gz`. SLOT is `candidate` or `fallback`, and KERNEL is the exact kernel file expected there. TARGET is a root-owned directory of mode 0711, ordinarily `/var/native`, at most 16 characters long so the case's attached image paths fit the kernel. Other mapped ids must be able to search this parent directory to reach their own workspaces; only root may write it. A stage creates the digest-named payload once and checks its files and mapped test account. Later run and proof invocations can share it, with a new RUN and LOGS each time. Existing payloads, result directories and collection claims are never overwritten.

Each remote command checks the Lenovo's station address, the booted slot, the absence of an armed trial and the SHA-256 of the named kernel's bytes in that slot, in the same process before writing or sending a signal. The run uses the public `etude run native` on Rach2, with direct local pipes to etude-guest. Its receipt has a random deployment owner token, the controller's PID, its kernel start identity and the kernel's `/proc/sys/kernel/random/boot_id`, which every boot has and no program writes; cleanup checks them before sending termination. The setup still publishes etude-guest's boot token in `/dev/shm/etude-guest-boot` for the measurement contexts that read it. The two external peers stay alive until the remote controller has ended. Every local SSH client and peer has a registered keeper and confirmed cleanup on success, failure or an ordinary stop signal. A failed stage or failed remote cleanup is reported as unconfirmed, with the target and logs retained for inspection.

Each Rach2 attempt has a child-subreaper owner. The owner keeps the actual program PID and exit status separate, adopts detached descendants and ends and reaps them before cleanup is confirmed. Cancellation and responder loss retain the same obligation; a surviving detached daemon cannot be reported as cleaned.

Each attempt has its own persistent responder session and command journal. A reconnection keeps both; the next case uses a different attempt identity even when it shares the collection run and state directory. The collection's status determines success. The deployment helper retrieves the whole results directory as a compressed archive in LOGS, preserving its JSON results and protocol evidence, then stops and reaps the peers. It leaves the immutable payload, account and recorded results on the machine; it removes neither an existing collection's state nor an unowned process.

Native KRFFS root preparation reserves `/.etude-native-root-padding`, a root-owned file of mode 0444 with a zero-filled payload. The supported stager appends it after the complete root tree, with a size that places the sole free extent on a 4096-byte boundary. A collision with that path fails preparation. The final chain, alignment and requested free-space allowance are checked before publication. This deterministic fixture placement keeps the first runtime metadata allocations independent of the staged executable sizes. The kernel still refuses a metadata update whose changed bytes span physical blocks; the timestamp probes retain their values and assertions.

## Limits

A case gives its program the init role never: a check that needs the designated init or a boot of its own stays in its suite under QEMU, as the inventory says. The ids and ports of `maps` are the same for every case, so two cases that name the same one do not run at once.

### Bounds and measured history

The native collection reads its declared initial, floor and ceiling values from the prepared `bounds.json`. It fixes whole-case, execution-gap, transfer, capture and cleanup bounds before starting any selected attempt, using the shared `watchdog-bounds-v1` policy. Five complete, undisrupted successful runs of the same machine, architecture, exact prepared workload, assertion inventory, profile and kernel identity can teach new bounds. Failures, cancellations, protocol proofs, repeated attempts from one run and unconfirmed cleanup teach none. With fewer samples the declared initial bound remains in force.

Native programs are opaque bounded steps. Their completion advances the collection; ordinary output, repeated output, heartbeats and undeclared progress do not reset an execution bound. The shared transport observes stage transitions and feeds only newly accepted stdout bytes, so a replayed frame cannot become progress. The whole-case bound remains active through all stages. An observed transfer uses nonblocking writes, so a full pipe cannot prevent deadline checks; callers without an observer retain their existing transport behavior. Cancellation has a separate bounded cleanup exchange. An expired watchdog makes the case incomplete even if cancellation later confirms its processes ended.

`--machine-id ID --kernel-sha256 SHA` binds learning to an identified machine and exact running candidate. The deployment helper supplies the station address and the kernel digest it verifies immediately before execution. A direct invocation without these identities still records results and uses initial bounds, but borrows no prior timings. `--purpose phase_first_run` explicitly requests the phase's first-run exemption. The plan records its exact selection and every preallocated attempt ID before work; the ordinary default is `focused`, with no exemption. `native-deploy run` and `proof` accept the same purpose option.

Each new results directory contains the standard validated `history.jsonl` and its immutable `store` blobs, in addition to the existing summary, raw results, stdout, stderr, protocol evidence and journals. The history records actual UTC and monotonic readings, per-stage and per-attempt elapsed time, serial queue time, reported tree processor time and peak memory, process and boot identities, fixed bounds and sample counts. Unavailable measurements have a reason. The sequential run's case-tree sums and peak are lower bounds because collector and transport overhead is excluded; per-stage resource attribution and outside activity are unavailable. These histories cannot establish a performance baseline without the missing load and preparation observations.

The measured collection interval begins when its exclusive claim is acquired and ends after owned attempt cleanup and claim release. Payload production and initial asset verification occur outside that interval and are reported separately; the native command creates no production receipt. Each completed or incomplete run is indexed below `STATE/history` for later learning. Retain its results and referenced blobs while retaining the index. An unconfirmed cleanup retains `collection.lock`, records the remaining cases as not run, and prevents another collection from reusing its resources. The lock holds `owner`, the collecting process's PID, start and `boot_id`, the fields of the deployment's receipt. A reboot ends every process, mount and loop attachment a run held, so the setup of `native-deploy run` removes a collection lock or a controller claim whose recorded boot is not the running one, with a `native-deploy: cleared:` line naming it and its owner, unless it was recorded with an etude token and its recorded PID still runs with the recorded start. A recorded boot is the running one when it is the running `boot_id` or the etude boot token in `/dev/shm/etude-guest-boot`, which an older deployment recorded and which lives as long as the boot; the token is read only from a regular file of the setup's user, 64 bytes long and writable by no one else, as `tools/etude/boot_identity.c` reads it, and while it cannot be read so, a recorded boot of hexadecimal digits alone may be the running one's and is kept. Every change of the lock, the setup's removal of a stale one and the collection's making and release of its own, writes `STATE/collection.journal` first, with the owner record of the lock it changes, and removes it once the change is whole; a journal seen under the flock below was left by a process stopped midway, so the setup removes the lock when its owner record is absent, the one the journal names or the start of it, as a stopped write leaves, keeps a lock of another owner, refuses while any `etude run native` runs on the machine, as a collection staged before the flock may without taking it, removes a lock with no owner record by `rmdir` alone, which fails should an owner appear meanwhile, and removes the journal, with a `native-deploy: cleared:` line for a lock it removed. A collection refuses to start beside a journal, leaving it for the setup. KRFFS, the installed machine's root, refuses a directory's rename, so the lock cannot be moved aside before its removal. The setup holds flock(1) on `STATE/collection.serial` from its look at the claims and the lock until its own controller claim is made, the collection holds flock(2) on the same file while it takes or releases its lock, and the deployment's cleanup, which makes `STATE` if it is absent, holds flock(1) on it for each look at its controller claim, the first reading the receipt and the second checking the lock and removing the claim, and waits for the controller to end between them without it, so that no setup removes a claim or a lock made after its reading, no two of them remove the same claim, and no cleanup sees a claim half written; a claim absent at the second look counts as removed, and one with no owner record, which only a writer that died leaves, is removed with a `native-deploy: cleared:` line; BusyBox's `flock` applet and the GNU root's util-linux both provide the command. It refuses a lock of the running boot, or one with no owner record, with a `native-deploy: refused:` line, unless a journal is there and the lock's owner record is absent, the journal's or the start of it; the owner must establish cleanup before removing that claim. Existing results, claims and history streams are never overwritten.

# tests/system: the system suites and their machinery

This directory contains everything that boots Rach2 to test it, and the tests of that machinery. The runner, `tests/run`, takes the suites `tests/registry` lists and runs each as its [etude cases](../cases/Readme.md), with every machine accounted for. The programs under `runner/` are the runner's helper and the drivers and peers that cases run; the checkers under `checkers/` judge what a machine wrote, `fixtures/` has the disk maker and the programs the self-tests use, and `fakeapi/` has the fake API server that the agents' suites talk to. `accept/` is the scripted half of the acceptance of a real machine. The guest programs the suites run are in [`tests/`](../Readme.md), which also says how to run a suite and read its result.

## Running

Every suite runs through `tests/run`, as [the tests' Readme](../Readme.md) describes. On an enrolled endpoint, tests/run first enters the [installed site admission](../../tools/etude/Readme.md#installed-launch-admission), which reserves its build and execution before the runner starts.

A script here runs by hand from the top of the tree as `sh tests/system/NAME.sh`; its header comment, or its usage message, gives its arguments. `ARCH` chooses a script's architecture as it chooses the runner's, except where the script's header names one.

The `textbusy` cases, [`guest.textbusy.json`](../cases/guest.textbusy.json), run offline on x86-64 with 128 MiB, each on a boot of its own of the test image. `musl/textbusymusl` checks executable and interpreter lifetimes on KRFFS and tmpfs, duplicate writers, fork, exec, failed exec, rename and unlink.

The case `guest.textbusy.bindhold` runs `musl/bindholdmusl`, which checks a descriptor and its duplicate, a mapping after close, a descriptor in flight on an AF_UNIX socket, a running image and a forked image through a bind remounted read-only. Unlink and rename through the original mount or its writable bind must preserve the file's bytes through replacement allocations, and last close or exit must reclaim its space.

The scenario of the case `machine.clock.clockload` times no line of the console, so the judgment does not depend on when a line arrives.

## Design

The clock checks share [`../clockref.h`](../clockref.h)'s interval judgment. [`../musl/clockref.h`](../musl/clockref.h) obtains an independent host timestamp over a private UDP socket, between guest clock reads. The host monotonic clock measures elapsed time; the host real-time clock supplies the date. Samples wider than 100 ms are retried at most 32 times. A whole error interval inside the bound passes, one wholly outside fails for a clock mismatch, and an interval crossing the bound fails for an uncertain measurement. No reference is a failed measurement, never a clock pass.

The `clock` suite is etude's case [`machine.clock.json`](../cases/machine.clock.json). Its reference, [`clockpeer`](../cases/machine/clockpeer.c), answers requests while `clockloadmusl` runs pipe round trips and arithmetic. The first sample precedes the readiness line. The scenario stops and resumes the machine's QEMU thirty times through `etude_suspend`, then types the newline that ends the workload, and the program takes the second sample. Both guest clocks' elapsed intervals must agree with the host monotonic interval to 250 ms, including both samples' uncertainty. Console delays extend the workload without changing its judgment. The case runs once, under the accelerator the site chooses, since a case's manifest gives none. The GNU ntpd row waits for a new service log record that the daemon set the clock, then runs `clockmusl` against the SNTP server's own time scale.

### The registry and the recipes

`tests/registry` has one line per suite: `name|tools|tier|images|memory|architectures|host isolation`. A suite is the cases of the family of `tests/cases` whose identity ends in its name. The tools are the external commands the suite needs beyond the build, separated by commas, `-` for none, and `qemu` among them is the emulator of the run's architecture. An entry of choices, such as `hdiutil+newfs_exfat/mkfs.exfat+fsck.exfat`, is met when the host has every command of one choice, the commands of a choice joined by `+` and the choices separated by `/`. The choice `tooling` is etude's tooling machine ([etude's Readme](../../tools/etude/Readme.md#the-tooling-machine)), which a host that is not Linux has when it has `qemu-system-x86_64`, `qemu-img`, mtools and `tar`, and Linux never has, so that `codex+python3+openssl+git+unshare+ip/tooling` asks Linux for those six commands and another host for the tooling machine. The tier is `core` or `full`. The images are globs, separated by commas, of what the suite writes under the images directory; left empty, they are `NAME-test*`, `NAME.*`, `NAME-*` and `NAME/*`, and for a twin `NAME-e1000` the plain suite's names with `-e1000` before the extension. The memory is the most guest memory the suite's machines ask for at once, in MiB, 128 when left out; the installed launcher reserves a run's memory from it. The architectures are `i686`, `x86_64` or both separated by a comma, both when left out. `serial` in the last field makes the launcher reserve the host alone. Order is the schedule order: the driver admits the suites' cases from the top, so the long ones come first.

`suites.mk`, which the root `Makefile` includes, has the disks, fixtures, captures and ports of the suites, which the cases' manifests name as artifacts, and the test tools it builds under `build/tests/system/`. It exports `RACH2_ARCH`, `ARCH_BUILD` (`build` or `build/x86_64`) and `RACH2_QEMU` (`qemu-system-i386` or `qemu-system-x86_64`) to its recipes. A comment line in `suites.mk` that begins `` `tests/run NAME` `` says what the suite proves; `tests/run inventory` prints those sentences with the registry's fields, and [`suites.md`](suites.md) is its output, which `tests/run style` compares with the command's. The test tools are host programs and stay under `build/` for both architectures.

A suite's cases and [the cases' Readme](../cases/Readme.md) say what each of its boots requires.

### The runner

`tests/run` is a POSIX shell script. It compiles `runner/runutil.c` with the host's `cc` into a private scratch directory, and that helper gives it what POSIX shell lacks: a monotonic clock and fractional sleeps, process groups and record locks. The suites' cases run under etude's set driver, `etude-legacy set`, which [etude's Readme](../../tools/etude/Readme.md#the-set-driver) describes. The run's locale is `C`; on macOS, whose mtools from Homebrew appends `_` to some of the names it copies out of a volume in that locale, the runner puts wrappers first on the path that run each mtools program under `C.UTF-8`, and it sets `COPYFILE_DISABLE`, without which macOS's tar adds a `._NAME` file of each file's extended attributes to an archive. A run proceeds in this order:

1. It checks every name, refuses one that is unknown, has no family of cases, is named twice or is not registered for `ARCH`, and looks for every tool the suites name.
2. It tries what the host must allow: `tools/setup/hostcheck.c` binds a TCP, a UDP and a Unix socket, unless the run is only `style` and `host`, and, on a Mac, attaches a disk image when a suite names `hdiutil`, as `large` does among its choices. A run of any suite besides those two also needs `RACH2_MIN_FREE_GIB` free under the tree and, under WSL, on the Windows drive where the distribution's disk is, which fills before Linux sees it.
3. It refuses a glob two suites declare, checks the timeout factor and `RACH2_CPUS`, and chooses the accelerator: KVM where `/dev/kvm` can be read and written, HVF on an x86 Mac that reports it, the emulator otherwise. A `/dev/kvm` this user cannot open is refused rather than run under the emulator, whose speed the completion bounds were not written for; `RACH2_QEMU_ACCEL=tcg` asks for the emulator.
4. It takes the tree, then, when a suite boots a machine, the host lock and a block of ports, as described below.
5. It prints its start line, makes the recovery system's key if the tree has none, and hashes the scripts that decide a result.
6. It builds `etude-legacy`, `history_lines` and `casecheck` and copies them into its scratch, so that no build a case starts replaces them while they run, and checks every manifest of `tests/cases` with `casecheck families`, which refuses the run when one is at fault.
7. It runs the set driver on the suites' cases, which prepares them with `etude-legacy prepare`: the components first in a make of their own, the kernel `RACH2_KERNEL` names, and then every artifact the cases' manifests name, in one make, so that no two cases build the same file; the preparation records each artifact with its SHA-256. The driver then runs the cases of `style` and `host` one after the other, and the rest at once, as described below. A failed `style` stops the set, since the edit that fixes it changes what the other suites would judge, and `RACH2_STOP_ON_FAIL` makes any failure stop it.
8. It hashes the scripts again and checks the recorded products with `etude-legacy check -d`, and voids the run on a difference or a missing file. It checks the image files the run made, and prints the run's lines with `history_lines` from the history the driver wrote, ending with `run: result:`.

#### Running the cases

The driver runs each case of a suite as an attempt of its own, one for each repetition its workload asks for, in a history that `RACH2_RESULTS` names, or the scratch directory without it, under a watchdog of the case's bounds; [etude's Readme](../../tools/etude/Readme.md#the-set-driver) says how it runs a host case's program, a guest case's machine and a machine case's scenario, and how `casecheck` judges each attempt. It admits the cases through a ledger in the run's scratch, whose limits come from the run's: at most `RACH2_WORKERS` at once, and `RACH2_MEMORY_MIB` of guest memory beside 128 MiB for each QEMU. Processors and disk do not keep a run below its width, since the machine shares them among its runs: the ledger has room for `RACH2_WORKERS` machines of `RACH2_CPUS` processors each, and its disk is the free space of the build tree. A case's claim is the resources its manifest declares, and a guest case's memory is what the launcher reserves for its machine; a case larger than a limit is held to it, and so runs alone rather than never. The run as a whole holds the machine through the installed launcher, as the top of this Readme says, and the machine cases take their local ports from its block. [The tests' Readme](../Readme.md) has the defaults. A case's output is kept and printed whole when it ends. Every two seconds the runner hashes the scripts again and stops the set if one has changed.

The driver's status record replaces the run's in `build/.run.status.PID` while it runs, with the claims that wait and each attempt that runs and its watchdog; [the manager's status command](../../tools/Readme.md#the-worker-and-manager-loops-flow) reads both forms.

A signal that reaches the runner while the driver runs is passed to the driver, which stops each case that runs with its processes and machines, prints what each unfinished case had written and writes the run's history; the runner then prints its lines and `run: result: interrupted by SIGNAL`, and exits with 128 plus the signal's number. A signal before the driver starts or after it ends stops the make the runner waits for and ends the run at once. A run started from a shell with job control is the leader of a group that also contains the rest of its pipeline, such as a `tail` its output is piped to, so it starts again under `runutil lead`, which makes a new group, passes INT, TERM and HUP to it, and exits with the run's status.

#### The tree lock

One run works on a tree at a time. `runutil lock` holds a POSIX record lock on `build/.run.guard` through the exec of the runner, and the runner makes the directory `build/.run.lock`, whose `owner` file records its PID, group, scratch directory, start time and arguments. A second run is refused with the first one's PID and arguments. A directory left by a run that is gone is taken over only when no process of its group and no machine of its ledgers is left; one with no owner file is taken to be in the making until it is ten seconds old.

A script run outside the runner holds the tree the same way. `tools/etude/legacy.sh` and `tests/cases/host/host.sh` hold it through [`etude-hold`](../../tools/etude/Readme.md#use), which keeps the same lock, directory and owner record; the other scripts source `runlock.sh` and call `runlock_hold`, which runs the script again under `runlock_exec.sh`. That wrapper takes the lock and the directory, runs the script in a process group of its own, passes TERM, HUP or INT to that group as TERM, once, and removes the directory when the script has ended, unless KILL ended it. Its owner file says `held`, and the runner never takes such a directory over, since a script killed before its trap ran may have left work running; a person removes it. A run or a script started under a hold finds the holder among its ancestors through `RACH2_TREE_HELD` and runs without taking the lock again.

#### Ports and the host lock

The trees on one host share its ports, so a run whose suites boot a machine claims a block of them once every check has passed and it holds the tree. `runutil ports` takes a record lock on the lowest free of `/tmp/rach2-ports.0` to `/tmp/rach2-ports.9`, files of mode 0666 that every account can lock, and starts the runner again with `RACH2_PORT_OFFSET` set to the block's number times 1000. `suites.mk` adds the offset to every port it forwards; within a block the numbers end in 222 to 331, 777 and 898 to 999, so no port of one block is a port of another. A run that inherits `RACH2_PORT_OFFSET` claims nothing. The set driver gives each machine case that asks for local ports its own ports of the block, as [etude's Readme](../../tools/etude/Readme.md#the-set-driver) says.

Before the block, the helper takes the host lock that `tests/run` asks for in `RACH2_HOST_LOCK`. A run whose suites each declare at most half of the host's memory takes a read lock on `/tmp/rach2-host.lock`, which any number of runs hold at once; a run with a larger suite, as `bigmem` is on the testing host, takes a write lock, so it waits for the runs in progress and no other run that boots a machine starts beside it. A write lock waiting only for read locks to go could wait for ever, so a run first locks `/tmp/rach2-host.gate`: a run that needs the host alone keeps a write lock on it while it waits and runs, and any other run takes a read lock there and gives it back once it has the host lock. The locks are held through exec while the runner lives. While it waits for the host or a block, the run says so once and keeps the tree; a signal then ends it with 128 plus the signal's number, and removes the tree's lock and the run's scratch. The helper also writes `claim.wait` in its scratch directory, with the wait's reason, start time and lock paths, and removes it when the claim succeeds. Each run publishes its scratch path and identity in `build/.run.status.PID`, which the set driver's status record replaces while it runs and which is removed at the end; [the manager's status command](../../tools/Readme.md#the-worker-and-manager-loops-flow) reads these records on the testing host.

#### What a run checks of itself

Before a run, the runner hashes with POSIX `cksum` the files that decide a result: `tests/run`, the registry, `suites.mk`, the root `Makefile`, `mk/*.mk`, the runner sources, the scripts and Python programs here, the scripts under `accept/`, the files under `accept/agents/`, `agents/` and `fakeapi/`, the awk checkers and shell fixtures, the loops' scripts under `tools/flow/`, the scripts of `tools/image/` and `krffs/`, the case manifests and their programs under `tests/cases/`, and the manifests. The preparation records the kernel and every artifact the cases' manifests name, each with its SHA-256. A file that differs or is gone at the end voids the run by name, as `run: voided: FILE changed during the run`, and the run fails as `voided`.

After the run, every file made under the images directory since the products were built must match the image globs of exactly one suite of the run; one that matches none or two is named, and the run fails as `images`. The check is of names, so it cannot see a suite that wrote a file another suite owns.

A case that does not pass keeps its workspace as `build/tests/failed/RUN.CASE.rR`, or under the directory `RACH2_FAILED` names, where RUN is the run's identity in the history and R the repetition: what its program or scenario kept there, a guest case's console among it. The line `run: NAME: CASE: evidence: DIR` names the directory.

### Completion bounds

A suite waits for a token and judges what the kernel counts, never the clock; a number of seconds in a suite is a completion bound. `RACH2_TIMEOUT_FACTOR=F` multiplies every bound, for a single suite or a set: the runner passes it on as `RACH2_DEADLINES=scaled` and `RACH2_DEADLINE_FACTOR=F`, which the harness, `runtests`, `ptydrive` and `hostpeer` read, and a shell suite writes a bound as `$(scaled N)` from `deadline.sh`. A bound that asserts a rate, the time a row applies a load for, a guest's own deadline and the idleness limit are not multiplied. The runner measures nothing about the host.

The `clock` suite is the one exception, since the clock is what it tests: it compares the guest's clocks with the host's across thirty stops of the machine, within 250 ms, which its case declares as a clock reference (see [`machine.clock.json`](../cases/machine.clock.json)).

A row whose verdict compares a request with the guest's own deadline keeps the guest's flushes from the host: its disk is `cache=unsafe`, or its file node `cache.no-flush=on`. The disk drivers end each write with a flush, which QEMU makes an fdatasync of the image, and the deadline counts it, so on a loaded host a flush could outlast the deadline and quarantine a request the device answered. These rows are the boots under `rach2.blocklag`; a case of etude gives such a disk `flush` false in its QEMU profile. The `queue` cases use unthrottled disks with real flushes. Their deadline boundaries, late answers, quarantine and full-pool waits are checked by `request_hosttest.c` with logical ticks and held completions; `ahci_hosttest.c` checks the real driver's independent ports and held write flush over controlled registers. Each write still reaches the host's page cache, where a later reader of the image finds it; such a row claims nothing about what survives a failure of the host, and every other row keeps its flushes.

`tools/verify/suitecheck.sh`, which `tests/run style` runs, refuses a `sleep` or `usleep` for a number of seconds in a suite or a host test's script, on the host or typed into the guest, a typed line longer than 240 characters, since the console's line discipline keeps 255 bytes of a line and drops the rest, a sleep call and an upper bound on a duration in a probe or a host test, and a line that prints a skip in a test that passes. A deliberate interval is marked `interval: REASON` in a comment and listed in `intervals` with the same reason; a mark without an entry, or an entry without a mark, fails the check. `unconverted` counts, for each older test, the sleeps, bounds and skips that its conversion to etude's cases removes; a file whose count differs from its entry fails the check.

### The machine drivers

The programs under `runner/` are host programs that `suites.mk` builds.

* `harness.c` boots one machine, headless, and drives its serial console with steps: wait for a pattern, type a line or raw bytes, press a key or move the mouse through QEMU's monitor, plug or pull a device, connect to a forwarded port, run a probe. It decides a run by the exit status the kernel prints for the probe; with a kernel built with `HARNESS=1`, QEMU stops through its `isa-debug-exit` device when that process exits. `--ok TOKEN` decides the run by a serial token instead, and `--never TEXT` fails it if a text appears. The header comment lists the options, steps and exit statuses. `--selftest` checks the matcher, the waits and the writes without QEMU.
* `runtests.c` runs every program of the `default` suite's `PROBES` list in turn in one boot of the test image, when a person runs it by hand, as [the tests' Readme](../Readme.md) describes; the suite itself runs them as etude's cases.
* `hostpeer.c` is the host end of a connection: `hold` keeps a TCP connection open while the machine reads `/proc/net/tcp`, `echo` sends back what arrives over TCP and UDP, for a time or until it is stopped, and `send` sends one UDP datagram. Etude's socket and dgram cases run `echo` and `send`.
* `ptydrive.c` runs a command, such as `ssh`, on a pseudo-terminal of a given size and answers one password prompt from an environment variable, which it removes from the command's environment and from the output it passes on.
* `deadline.c` runs a command in a process group of its own and kills the group when a time limit passes, with status 124.
* `screentext.c` prints the text a framebuffer console shows in a QEMU screen dump, matching each cell against the kernel's own font, `rach2/sys/display/vga_font.c`; `--colors` prints how many colours the dump has.
* `runutil.c` is the runner's helper above. Built at `build/tests/system/runutil`, its `watch NAME IDLE COMMAND` also runs a command for `tools/dev/poll_kernels.sh` and `accept/su_command.sh`, and stops it, with status 124, when for IDLE seconds it has written nothing and its processes have used next to no processor time.

A suite that starts QEMU itself with `-serial stdio < FIFO > LOG` sources `drive.sh`: `drive_feed` holds the FIFO open, `drive_type` types a line once the output it answers has arrived, `drive_expect` and `drive_prompt` wait for fresh output after the last match or the first line typed since it, `drive_sent` waits until the typed lines are in the machine's input, and `drive_login` logs in.

### Checkers and fixtures

* `checkers/pcapcheck.c` reads a QEMU packet capture: `bcast` checks a broadcast datagram, a source address, an ARP reply or request, or the gateway a packet left through; `netconsole` checks the kernel's netconsole frames and the log in them; `rawwire` checks the hop limits and checksum of the raw-socket probe's sends.
* `checkers/wavcheck.c` reads the recording of QEMU's `wav` audio backend and checks that the machine played the square-wave notes it was asked for, in order, and no other tone, measuring each 50 ms by the median length of the wave's runs, which a period played twice or missed does not move. It accepts at most 16 frequencies and refuses a longer list.
* `checkers/usblatency.awk` and `checkers/grow_measure.awk` read the USB latency records and the grow's counters off a console log.
* `fixtures/mkfixture.c` makes three disks for `bootprobe`: a FAT-typed partition filled with the probe's pattern, a sparse 260 GiB disk with known sectors at 5 GiB and 258 GiB for the 64-bit disk offsets, and the `authority` cases' disk, 4 GiB of zeros with an MBR signature; `mkext2fixture.sh` makes the ext2 suite's fixture disk. `mkrootdisk.sh` makes the ext2 roots of the bootline and servicelog cases: one whose `/sbin/init` is a symbolic link to itself, and one with init-shell, `update` and BusyBox.
* The other C files under `fixtures/` are programs the self-tests compile: the runner's helper with test hooks, a worker that leaves processes behind, a dummy SSH peer, and the VFS unmount path with substitutes. `fixtures/grow_tool.sh` is typed into the recovery machine by the grow suite to wrap its ext2 tools with counter reads. `fixtures/old_ports.py` claims the host lock and a port block as an older checkout's runutil does, for `etude_launch_test.py` and `tests/host/etude_ports_hosttest.c`.

### The fake API server

`fakeapi/fakeapi.py` stands in for a vendor's API, so that a suite can run a program that calls one with no network and no credential. For each run it makes a certificate authority and a server certificate, which the suite gives the program by the program's documented settings and removes afterwards. On the host it serves HTTP/1.1, server-sent events and WebSocket over TLS, plays a script of expected requests and replies in turn, records every request, and fails the run on a request the script does not expect. A step marked unordered is played whenever a request matches it, for a client that sends two requests at once; one marked repeated as well is played by any number of requests, none among them, for a request a client sends on a timer of its own. A step is played once its reply has ended, or a WebSocket's once the server starts to close it; a connection that ends in a WebSocket exchange before then fails the run. A step marked held keeps its reply until a request for `/fakeapi/release`, and a request for `/fakeapi/held` is answered once the held step's request has come, so that a row can inspect a client while it waits for an answer. `fakeapi/fakeapi_test.py`, run by `host`, checks all four. A guest on QEMU's user network with `restrict=on` has no route out; it reaches the server at `10.0.2.100:443` through a `guestfwd` rule, which starts `fakeapi.py relay` for each connection. Each protocol is a module of its own, `fakeapi/proto_NAME.py`, behind the interface that the server's header comment describes, together with how to write a script; `proto_plain.py` writes requests and replies out literally. The `fakeapi` suite proves the server from the GNU system with curl and `fakeapi/wsclient.py`, as an [etude machine case](../cases/Readme.md). The `agents` and `agentsaccept` suites run as machine cases too; etude owns their private disks, forwarded ports and fake API services.

The `anthropic` protocol implements the [Messages API](https://platform.claude.com/docs/en/api/messages), [tool results](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) and [streaming events](https://platform.claude.com/docs/en/build-with-claude/streaming). `fakeapi/claude-session.json` reads a fixture with Read, runs Bash, changes it with Edit and commits with Bash. Each step requires the preceding tool result; the final answer requires all four. Tool JSON and text are sent in several deltas. The host checks the edited file, the committed tree, the commit count and subject, the clean work tree and every recorded request. A step may also give a `body` the request's must match, which tells a request the client makes for its own use from a turn of the conversation. `fakeapi/claude-screen.json` has the requests a session in Claude Code's screen sends beside the conversation: at its first start, in an empty home, it checks that it reaches Anthropic's services with `GET /api/hello` at `api.anthropic.com` and `GET /v1/oauth/hello` at `platform.claude.com`, and beside the first turn it asks the model for the session's title, with no tools and a JSON schema for the answer; all three are unordered. `fakeapi/anthropic_test.py`, run by `host`, also checks whole JSON responses, a step's body, and refusal of incorrect, failed, duplicate and unpaired results.

On Linux, `python3 -B tests/system/fakeapi/claude_test.py BINARY` runs the script against the published linux-x64 Claude Code 2.1.296 binary, whose SHA-256 is checked at each use against [Anthropic's manifest](https://downloads.claude.ai/claude-code-releases/2.1.296/manifest.json). `make ARCH=x86_64 GNU_AGENTS=claude gnu-agents` fetches it, checks the manifest's signature and the binary against the manifest ([the agents layer](../../vendor/gnu/agents/Readme.md#claude)), and stages it as `build/x86_64/vendor/gnu/agents/claude/opt/claude/bin/claude`. The proof uses `unshare` and `ip` to run in a network namespace with only loopback. It makes a fresh home and repository and passes no inherited credentials or settings. It uses `ANTHROPIC_BASE_URL`, `NODE_EXTRA_CA_CERTS` and a dummy `ANTHROPIC_API_KEY`, with nonessential traffic, updates and marketplace installation disabled by [Claude Code's settings](https://code.claude.com/docs/en/env-vars). No sign-in or outside service is needed. A second session supplies an incorrect expected shell result and requires the server to refuse it before sending the edit. The script removes its scratch on success or a signal and prints its evidence directory on failure.

A guest suite can use the same script and driver in three parts: `claude_test.py prepare WORK` creates the fixture repository, fresh home and `WORK/script.json`; the host serves that script; `claude_test.py client BINARY WORK URL CA` runs the guest client with the documented settings; and `claude_test.py verify WORK RECORD` judges the repository and server record, whatever the number of steps. WORK must be the same absolute path on the host and guest, and the caller removes it. Copy the guest repository back before verifying it on the host. The server's verdict is checked separately. These commands do not fetch anything. The `agents` suite's `claude-print` and `claude-screen` rows make the repository on the machine instead, and `agents/claude_session_verify.py` renders their script with `render`, which names the repository where the row makes it, and judges what they return with `verify` ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)).

`proto_responses.py` is OpenAI's Responses API as Codex uses it: a `POST /v1/responses` answered with server-sent events, and WebSocket mode, in which each `response.create` message continues the response before it, a warmup with `"generate": false` included. Its steps write the model's side as turns: the conversation each request must have, the output of each earlier tool call among it, and the messages and tool calls the model answers with. `fakeapi/codex.json` is the script the agents' Codex suites play, on a clone of `fakeapi/repo`: Codex reads `notes.txt` and runs `check.sh` over a WebSocket, the server refuses the WebSocket it opens again with 426, which is where Codex falls back to HTTPS, and Codex then edits `greeting.txt` with `apply_patch` and commits. The `codexapi` cases, [`host.codexapi.json`](../cases/host.codexapi.json), play it against the host's Codex, in a fresh home and a network namespace that has only a loopback interface. The `agents` suite's `codex-exec` and `codex-screen` rows play it on Rach2, with `codex exec` and in Codex's screen in tmux. As it starts, the screen fetches a notice from `raw.githubusercontent.com`, and beside the first turn it asks the model for the session's title on a connection of its own, which tries a WebSocket first; `fakeapi/codex-screen.json` adds the steps that answer them, a 404 for the notice, a second refusal with 426 and the title, all unordered, and `agents/codex_session_verify.py` puts them after the script's and judges what the rows return ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)).

Muse Code speaks the same protocol to Meta's Model API, as its [Responses API](https://dev.meta.ai/docs/protocols/responses) documents it: a `POST /v1/responses` answered with server-sent events, over HTTPS only. Its tools are the functions of one [namespace](https://dev.meta.ai/docs/tool-search) tool, `muse`, and a turn calls one with `"namespace": "muse"` beside its name. Before its first turn Muse fetches a model catalog with `GET /muse-code/models` at the server's origin, a path the Model API's reference does not list; the script answers it with the reference's [list of models](https://dev.meta.ai/docs/api-reference/models/list-models), which Muse accepts. Meta documents the settings the cases give it: the key in `META_API_KEY` ([authentication](https://dev.meta.ai/docs/muse-code/auth)), the server by `--base-url`, which `muse --help` lists, and a certificate authority's file by `ca_bundle`, which the [changelog](https://dev.meta.ai/docs/muse-code/changelog) of 1.4.3 names and which Muse takes as `endpoint_transport.ca_bundle`, beside `endpoint_transport.base_url`. Its [observer agents](https://dev.meta.ai/docs/muse-code/extending) make model calls beside the main agent's, in an order no script can fix; the documentation says the settings file can turn them off without naming the keys, and the cases turn off each `runtime_capabilities` entry the program has for one. `fakeapi/muse.json` is the script: Muse reads `notes.txt` with `read_file`, runs `check.sh` with `bash`, edits `greeting.txt` with `edit_file` and commits with `bash`. The `museapi` cases, [`host.museapi.json`](../cases/host.museapi.json), play it against Muse Code 1.4.10-R6427.1, which `fakeapi/fetch_muse.sh` downloads once into `build/downloads/muse/` and checks against the SHA-256 that Meta's release manifest lists whenever the cases' preparation runs, in a fresh home and a network namespace that has only a loopback interface. Muse retries a refused request for minutes, so the refusal case, in which the server must refuse a wrong tool result, stops Muse once the server has refused it.

The `gemini` protocol implements the Gemini API's [streamed generateContent](https://ai.google.dev/api/generate-content), with [function calls](https://ai.google.dev/gemini-api/docs/function-calling) and their [thought signatures](https://ai.google.dev/gemini-api/docs/thought-signatures), which a later request must return with each call. Antigravity CLI uses it when its settings name the Gemini API as the model provider and `GEMINI_API_KEY` holds a key, and sends it to the server that `GOOGLE_GEMINI_BASE_URL` names, as [Google's installation page](https://antigravity.google/docs/install?tab=cli) documents. Google documents no setting for a certificate authority. The program is Go, so the proof uses the Go runtime's [`SSL_CERT_FILE`](https://pkg.go.dev/crypto/x509#SystemCertPool), which replaces the system's roots with the test CA. `fakeapi/agy-session.json` reads the fixture with `view_file`, runs `run_command`, changes it with `replace_file_content` and commits with `run_command`, with the same checks of results, file, tree and commit as the Claude Code script. Its first step is the conversation title that the program asks a smaller model for beside its first turn; it is unordered, since the two requests are sent at once. `fakeapi/gemini_test.py`, run by `host`, checks refused results and signatures, both response forms and unordered steps.

On Linux, `python3 -B tests/system/fakeapi/agy_test.py TARBALL` runs the script against Antigravity CLI 1.4.0, the `cli_linux_x64.tar.gz` that [Google's linux_amd64 manifest](https://antigravity-cli-auto-updater-974169037036.us-central1.run.app/manifests/linux_amd64.json) names; it checks the tarball's SHA-512 against the manifest's and unpacks the program, `antigravity`, which the installer names `agy`. The proof runs as the Claude Code proof does, in a network namespace with only loopback and a fresh home, headless with `-p`, `--dangerously-skip-permissions` and `AGY_CLI_DISABLE_AUTO_UPDATE`, `"enableTelemetry": false` in its settings, which this version disregards ([the agents layer](../../vendor/gnu/agents/Readme.md#agy)), and a dummy key. The parts `agy_test.py prepare WORK`, `client BINARY WORK URL CA` and `verify WORK RECORD` serve a guest suite as `claude_test.py`'s do, `BINARY` being the unpacked program; `verify` takes a repeated step played any number of times. The `agents` suite's `agy-print` and `agy-screen` rows make the repository on the machine instead, and `agents/agy_session_verify.py` renders their script, after the steps of `fakeapi/agy-services.json`, and judges what they return ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)).

### The SNTP server

`sntpserver.py` is the time server of the `gnu` family's ntpd case, which starts it as the case's service on the case's second port. It answers SNTP requests on that UDP port of the host's loopback with a time that begins at the epoch it is given and advances at the host's rate, so that a clock the machine's ntpd set to it differs from the host's by years. The guest reaches it at `10.0.2.2`, which QEMU's user network delivers to the loopback. It exits when its parent does.

### Acceptance

Acceptance of a real machine is not a suite: no `tests/run` set includes it, and the hardware rules of `AGENTS.md` govern it. `accept/metal_accept.sh HOST [PORT] [STICK-SERIAL]` is its scripted half. Over SSH as root, or as an account through `su` with `RACH2_ACCEPT_SU=1` and `accept/su_command.sh`, it reads the machine's identity, network, entropy, disks and devices, fetches its boot log, compares the facts that have a baseline, checks the installed ext2 root, and writes only the root, a loop image under `/tmp`, and the stick whose serial it is given. It saves the boot log it reads as `metal-bootlog.txt` in the directory that `RACH2_ACCEPT_RECORDS` names, `build/images` by default, and its image row needs the host KRFFS tools that `make krffs` builds. Its header comment gives its variables, and a comment before each part of the script describes the row.

The cases of `tests/run metal`, [`tests/cases/machine.metal.json`](../cases/machine.metal.json), rehearse it against QEMU machines. One boots the metal image with a hub, a keyboard and three sticks, which `metal_sticks.sh` makes, and runs the script against it, with no stick named and with one; five boot the installed-root rows on small GRUB disks with an MBR and with a GUID table, which `metal_installed_disks.sh` makes, and must pass two and fail three. Two cases of the family boot nothing: they run `accept/transport_test.sh`, the whole script against private SSH and `su` fixtures, and `accept/password_test.sh`, the `su` helper against a dummy SSH peer on a real pseudo-terminal.

`accept/agents_accept.sh lenovo USER [ADDRESS]` accepts the coding agents of the agents layer on the installed Lenovo, once the owner has signed in to each as USER; [the agents layer's Readme](../../vendor/gnu/agents/Readme.md#use) gives the owner's commands. From this host it works in each agent's screen as a person does, in tmux over SSH: a change in a disposable repository, tested and committed, a cancelled turn, a resized terminal, a lost connection and a reopened conversation; then it reboots the machine and requires the credentials, the versions and each agent's answer to a request after it. Its machine half, `accept/agents_guest.sh`, runs on the machine. Its internal `etude ACTION AGENT` mode runs the same assertions in steps of the [agent acceptance cases](../cases/Readme.md); it boots no machine and starts no API server. The `agentsaccept` suite runs the same script in its QEMU mode, on the GNU root with the agents layer, against the fake API server, which plays `accept/agents/AGENT.json` for each program. The script's header comment describes each step and what it requires.

## Adding tests

A suite is a line in `tests/registry` and a family of cases, `tests/cases/FAMILY.json`, whose identity ends in its name, as [the cases' Readme](../cases/Readme.md) says; `tests/run style` refuses a tree where the two name different suites. Put the line where its length belongs in the schedule, declare the images it writes when they are not named after it, and declare its memory when its machines together ask for more than 128 MiB at once. In `suites.mk`, write a comment that begins `` `tests/run NAME`: `` with one sentence on what the suite proves, beside the rules of the artifacts its cases name, then regenerate the inventory with `tests/run inventory > tests/system/suites.md`.

A script that writes several files at once has one pattern rule, whose targets are `$(call together,FILES)`, which make runs once for all of them, since GNU Make 3.81, the make of macOS, has no grouped targets (`&:`); the comment on `together` in `suites.mk` says what else 3.81 needs. Add the script to the list in `together_test.sh`, which checks each one.

A suite waits for what the machine prints and bounds each wait; a shell suite writes the bound as `$(scaled N)`, and the harness scales its own. A suite that keeps an interval on purpose marks it and lists it in `intervals`. A program the suite runs is listed in `tests/probe-suites` with the suite's name.

## Limits

* The runner checks image files by name. It cannot tell which suite wrote a file, so a suite that writes a file another suite owns passes the check.
* Equal hashes before and after a run show that the files the run used are the files there now, not that they did not change in between.
* A suite's completion bounds are written for an idle host under KVM. On a loaded host or under the emulator, `RACH2_TIMEOUT_FACTOR` is the remedy; the runner does not adjust them.

## Tests

`tests/run runner` runs the self-tests of the programs above that `tests/run` and the old drivers still use, booting nothing: the harness's `--selftest`, runutil's process groups and processor time, and the test status reader, the cases of [`host.runner.json`](../cases/host.runner.json). `tests/run drive` tests `drive.sh` and the harness's waits against fake machines that choose when they are ready, the case of [`host.drive.json`](../cases/host.drive.json), whose program, `tests/cases/host/drive.sh`, runs `drivetest.sh`. Both are in the core tier.

The account, login, procfiles, descriptor-lock and credential-persistence suites run the process and account families under `tests/cases/`. Their [case contracts](../cases/Readme.md) describe the private boot media and the reports of their guest programs.

# tests/system: the system suites and their machinery

This directory contains everything that boots Rach2 to test it, and the tests of that machinery. The runner, `tests/run`, takes the suites `tests/registry` lists and runs each as its [etude cases](../cases/Readme.md), with every machine accounted for. The programs under `runner/` are the runner's helper and the drivers and peers that cases run; the checkers under `checkers/` judge what a machine wrote, `fixtures/` has the disk maker and the programs the self-tests use, and `fakeapi/native/` has the compiled TLS API service that the agents' suites talk to. `accept/` is the scripted half of the acceptance of a real machine. The guest programs the suites run are in [`tests/`](../Readme.md), which also says how to run a suite and read its result.

## Running

Every suite runs through `tests/run`, as [the tests' Readme](../Readme.md) describes. On an enrolled endpoint, the build enters the [installed site admission](../../tools/etude/Readme.md#installed-launch-admission) through the root `make`, and each case is a claim of the site's ledger.

A script here runs by hand from the top of the tree as `sh tests/system/NAME.sh`; its header comment, or its usage message, gives its arguments. `ARCH` chooses a script's architecture as it chooses the runner's, except where the script's header names one.

The `textbusy` cases, [`guest.textbusy.json`](../cases/guest.textbusy.json), run offline on x86-64 with 128 MiB, each on a boot of its own of the test image. `musl/textbusymusl` checks executable and interpreter lifetimes on KRFFS and tmpfs, duplicate writers, fork, exec, failed exec, rename and unlink.

The case `guest.textbusy.bindhold` runs `musl/bindholdmusl`, which checks a descriptor and its duplicate, a mapping after close, a descriptor in flight on an AF_UNIX socket, a running image and a forked image through a bind remounted read-only. Unlink and rename through the original mount or its writable bind must preserve the file's bytes through replacement allocations, and last close or exit must reclaim its space.

The scenario of the case `machine.clock.clockload` times no line of the console, so the judgment does not depend on when a line arrives.

## Design

The clock checks share [`../clockref.h`](../clockref.h)'s interval judgment. [`../musl/clockref.h`](../musl/clockref.h) obtains an independent host timestamp over a private UDP socket, between guest clock reads. The host monotonic clock measures elapsed time; the host real-time clock supplies the date. Samples wider than 100 ms are retried at most 32 times. A whole error interval inside the bound passes, one wholly outside fails for a clock mismatch, and an interval crossing the bound fails for an uncertain measurement. No reference is a failed measurement, never a clock pass.

The `clock` suite is etude's case [`machine.clock.json`](../cases/machine.clock.json). Its reference, [`clockpeer`](../cases/machine/clockpeer.c), answers requests while `clockloadmusl` runs pipe round trips and arithmetic. The first sample precedes the readiness line. The scenario stops and resumes the machine's QEMU thirty times through `etude_suspend`, then types the newline that ends the workload, and the program takes the second sample. Both guest clocks' elapsed intervals must agree with the host monotonic interval to 250 ms, including both samples' uncertainty. Console delays extend the workload without changing its judgment. The case runs once, under the accelerator the site chooses, since a case's manifest gives none. The GNU ntpd row waits for a new service log record that the daemon set the clock, then runs `clockmusl` against the SNTP server's own time scale.

The SSH, clock and SNTP peers use unbuffered standard output for their readiness and progress records. Windows treats the C library's line-buffered mode as full buffering. A controller must receive a peer's actual readiness line before starting work that depends on it; waiting for the peer to exit would leave that dependency unresolved.

### The registry and the recipes

`tests/registry` has one line per suite: `name|tools|tier|images|memory|architectures|host isolation`. A suite is the cases of the family of `tests/cases` whose identity ends in its name. The tools are the external commands the suite's preparation needs beyond the build, separated by commas, `-` for none, and `qemu` among them is the emulator of the run's architecture; `tests/run inventory` lists them, and a case names the commands it runs itself in its manifest's requirements. An entry of choices, such as `hdiutil+newfs_exfat/mkfs.exfat+fsck.exfat`, is met when the host has every command of one choice, the commands of a choice joined by `+` and the choices separated by `/`. The choice `tooling` is etude's tooling machine ([etude's Readme](../../tools/etude/Readme.md#the-tooling-machine)), so that `mkfs.exfat+fsck.exfat/tooling` asks Linux for those two commands and another host for the tooling machine. The tier is `core` or `full`. The images are globs, separated by commas, of what the suite writes under the images directory; left empty, they are `NAME-test*`, `NAME.*`, `NAME-*` and `NAME/*`, and for a twin `NAME-e1000` the plain suite's names with `-e1000` before the extension. The memory is the most guest memory the suite's machines ask for at once, in MiB, 128 when left out; the installed launcher reserves a run's memory from it. The architectures are `i686`, `x86_64` or both separated by a comma, both when left out. `serial` in the last field makes the launcher reserve the host alone. Order is the schedule order: the driver admits the suites' cases from the top, so the long ones come first.

`suites.mk`, which the root `Makefile` includes, has the disks, fixtures, captures and ports of the suites, which the cases' manifests name as artifacts, and the test tools it builds under `build/tests/system/`. It exports `RACH2_ARCH`, `ARCH_BUILD` (`build` or `build/x86_64`) and `RACH2_QEMU` (`qemu-system-i386` or `qemu-system-x86_64`) to its recipes. A comment line in `suites.mk` that begins `` `tests/run NAME` `` says what the suite proves; `tests/run inventory` prints those sentences with the registry's fields, and [`suites.md`](suites.md) is its output, which `tests/run style` compares with the command's. The test tools are host programs and stay under `build/` for both architectures.

A suite's cases and [the cases' Readme](../cases/Readme.md) say what each of its boots requires. The etudeexec source archive retains the files under `tools/etude` and `tests/native` and its explicit auxiliary inputs, excluding generated `__pycache__` directories and `.pyc` and `.pyo` files. Python imports therefore do not change its source set.

### The runner

`tests/run` builds etude with `make` and starts `etude run -B` with the names it was given, so a run is etude and the programs its preparation built. [Etude's Readme](../../tools/etude/Readme.md#native-collection-execution) says what the command does; in short:

1. It reads `tests/registry` and the case manifests, and refuses a name that is unknown, has no family of cases, is named twice or is not registered for `ARCH`, and a choice of cases that `RACH2_CASES`, `RACH2_AGENTS_ROWS` or `RACH2_ACCEPT_AGENTS` gives and that names no case of a suite of the run.
2. It takes the tree, as described below, and prepares the cases' artifacts with `etude prepare`: the recovery system's key if the tree has none, the components in a make of their own, the kernel `RACH2_KERNEL` names, and then every artifact the cases' manifests name, in one make, so that no two cases build the same file. The preparation records each artifact with its SHA-256 in `build/tests/prepare.record`. With `ARCH='i686 x86_64'` it builds both architectures' trees.
3. It chooses the accelerator: KVM where `/dev/kvm` opens for reading and writing, HVF on an x86 Mac that reports it, the emulator otherwise. A `/dev/kvm` this user cannot open is refused rather than run under the emulator; `RACH2_QEMU_ACCEL=tcg` asks for the emulator. A run whose cases boot machines needs `RACH2_MIN_FREE_GIB` free under the tree.
4. It runs the cases on the prepared artifacts under etude's set driver, which checks each artifact against the record first: the explicitly serial suites and the quiet host groups one after the other, and the rest at once, the cases of both architectures in one schedule, the longer cases first, and a case of no architecture once. A failed `style` stops the set, since the edit that fixes it changes what the other suites would judge, and `RACH2_STOP_ON_FAIL` makes any failure stop it.
5. It checks the artifacts against the record again, and prints the run's lines from the history the driver wrote, ending with `run: result:`.

#### Running the cases

The driver runs each case of a suite as an attempt of its own, one for each repetition its workload asks for, in a history under `RACH2_RESULTS`, or `build/tests/results` without it, under a watchdog of the case's bounds; [etude's Readme](../../tools/etude/Readme.md#the-set-driver) says how it runs a host case's program, a guest case's machine and a machine case's scenario, and how `etude check` judges each attempt, and how the earlier successful runs in that history set a case's bounds. On a machine with an installed site, each case is a claim of the site's ledger, which every account's runs share; without one, a ledger under the results. The run's own limits are at most `RACH2_WORKERS` cases at once, and `RACH2_MEMORY_MIB` of guest memory beside 128 MiB for each QEMU. A case's claim is the resources its manifest declares, and a guest case's memory is what the launcher reserves for its machine. [The tests' Readme](../Readme.md) has the defaults. A case's output is kept and printed whole when it ends.

The driver's status record is `build/.run.status.PID` while it runs, with the claims that wait and each attempt that runs and its watchdog; [the manager's status command](../../tools/Readme.md#the-worker-loops-the-board-and-the-release-flow) reads it.

A signal that reaches the run while the driver runs stops each case that runs with its processes and machines, prints what each unfinished case had written and writes the run's history; the run then prints its lines and `run: result: interrupted by SIGNAL`, and exits with 128 plus the signal's number. A signal during the preparation cancels the make that runs.

#### The tree lock

One run works on a tree at a time. The run holds it through [`etude lock tree`](../../tools/etude/Readme.md#use), which holds a record lock on `build/.run.guard` while it lives and makes the directory `build/.run.lock`, whose `owner` record gives the holder's identity, its command's process group, the time it was taken and the arguments; the run proper is the lock's command, a process group of its own. A second run is refused with the first one's PID and arguments. A directory left by a run that is gone is taken over only when its holder has ended and no process of its command's group is left; one with no owner record is taken to be in the making until it is ten seconds old. The holder removes the directory when the run proper has ended.

A script run outside the runner holds the tree the same way: it sources `tools/etude/hold.sh` and calls `etude_hold`, which runs the script again under the helper. The helper takes the same lock and directory, runs the script as a process group of its own, passes TERM, HUP or INT to that group as TERM, once, and removes the directory when the script has ended, unless KILL ended it. Its owner record says `held`, and a run never takes such a directory over, since a script killed before its trap ran may have left work running; a person removes it. A run or a script started under a hold finds the holder among its ancestors through `RACH2_TREE_HELD` and runs without taking the lock again.

#### Ports and the host lock

The trees on one host share its ports, so a run whose cases boot a machine holds a block of them, with the host lock, from its first case until every case's claim is gone. The block is a record lock on the lowest free of `/tmp/rach2-ports.0` to `/tmp/rach2-ports.9`, or of the directory that `RACH2_PORT_DIR` or the site names, and the run gives the set driver its offset, the block's number times 1000, as `RACH2_PORT_OFFSET`. `suites.mk` adds the offset to every port it forwards; within a block the numbers end in 222 to 331, 777 and 898 to 999, so no port of one block is a port of another. The set driver gives each machine case that asks for local ports its own ports of the block. The host lock is a read lock on `rach2-host.lock` beside the blocks, which any number of runs hold at once, or a write lock for a run with a serial suite or one that declares more than half of the ledger's memory, as `bigmem` does on the testing host.

A run started inside a claim of the installed launcher takes neither: the launcher holds the host lock and the block that `RACH2_PORT_OFFSET` names, and the run's cases are claims of its own ledger.

A case that does not pass keeps its workspace as `build/tests/failed/RUN.CASE.rR`, or under the directory `RACH2_FAILED` names, where RUN is the run's identity in the history and R the repetition: what its program or scenario kept there, a guest case's console among it. The line `run: NAME: CASE: evidence: DIR` names the directory.

### Completion bounds

A suite waits for a token and judges what the kernel counts, never the clock. Etude stops a case only when it has made no progress for longer than the case's history on that machine allows, as [etude's Readme](../../tools/etude/Readme.md#progress-and-bounds) says. The drivers a case runs set no time limit of their own: `ptydrive` waits until its command ends or a signal stops it, and `hostpeer echo`, as the socket cases run it, serves until it is stopped. The runner measures nothing about the host and scales no bound.

The `clock` suite is the one exception, since the clock is what it tests: it compares the guest's clocks with the host's across thirty stops of the machine, within 250 ms, which its case declares as a clock reference (see [`machine.clock.json`](../cases/machine.clock.json)).

A row whose verdict compares a request with the guest's own deadline keeps the guest's flushes from the host: its disk is `cache=unsafe`, or its file node `cache.no-flush=on`. The disk drivers end each write with a flush, which QEMU makes an fdatasync of the image, and the deadline counts it, so on a loaded host a flush could outlast the deadline and quarantine a request the device answered. These rows are the boots under `rach2.blocklag`; a case of etude gives such a disk `flush` false in its QEMU profile. The `queue` cases use unthrottled disks with real flushes. Their deadline boundaries, late answers, quarantine and full-pool waits are checked by `request_hosttest.c` with logical ticks and held completions; `ahci_hosttest.c` checks the real driver's independent ports and held write flush over controlled registers. Each write still reaches the host's page cache, where a later reader of the image finds it; such a row claims nothing about what survives a failure of the host, and every other row keeps its flushes.

`tools/verify/suitecheck.sh`, which `tests/run style` runs, refuses a `sleep` or `usleep` for a number of seconds in a suite or a host test's script, on the host or typed into the guest, a sleep call and an upper bound on a duration in a probe or a host test, and a line that prints a skip in a test that passes. A deliberate interval is marked `interval: REASON` in a comment and listed in `intervals` with the same reason; a mark without an entry, or an entry without a mark, fails the check. `unconverted` counts, for each older test, the sleeps, bounds and skips that its conversion to etude's cases removes; a file whose count differs from its entry fails the check.

### The machine drivers

The programs under `runner/` are host programs that `suites.mk` builds.

* `hostpeer.c` is the host end of a connection: `hold` keeps a TCP connection open for a number of seconds, `echo` sends back what arrives over TCP and UDP, for a time or until it is stopped, and `send` sends one UDP datagram. Etude's socket and dgram cases run `echo` and `send`. Each job uses 127.0.0.1 unless `HOSTPEER_ADDRESS` names another IPv4 address, as the [native collection setup](../native/Readme.md) requires for a peer on the Lenovo's network.
* `ptydrive.c` runs a command, such as `ssh`, on a pseudo-terminal of a given size and answers one password prompt from an environment variable, which it removes from the command's environment and from the output it passes on. It waits for the command without a time limit unless `--timeout` gives one, and a SIGTERM, SIGINT or SIGHUP ends the command with it.
* `screentext.c` prints the text a framebuffer console shows in a QEMU screen dump, matching each cell against the kernel's own font, `rach2/sys/display/vga_font.c`; `--colors` prints how many colours the dump has.

### Checkers and fixtures

* `checkers/pcapcheck.c` reads a QEMU packet capture: `bcast` checks a broadcast datagram, a source address, an ARP reply or request, or the gateway a packet left through; `netconsole` checks the kernel's netconsole frames and the log in them; `rawwire` checks the hop limits and checksum of the raw-socket probe's sends.
* `checkers/wavcheck.c` reads the recording of QEMU's `wav` audio backend and checks that the machine played the square-wave notes it was asked for, in order, and no other tone, measuring each 50 ms by the median length of the wave's runs, which a period played twice or missed does not move. It accepts at most 16 frequencies and refuses a longer list.
* `checkers/usblatency.awk` and `checkers/grow_measure.awk` read the USB latency records and the grow's counters off a console log.
* `fixtures/mkfixture.c` makes three disks for `bootprobe`: a FAT-typed partition filled with the probe's pattern, a sparse 260 GiB disk with known sectors at 5 GiB and 258 GiB for the 64-bit disk offsets, and the `authority` cases' disk, 4 GiB of zeros with an MBR signature; `mkext2fixture.sh` makes the ext2 suite's fixture disk. `mkrootdisk.sh` makes the ext2 roots of the bootline and servicelog cases: one whose `/sbin/init` is a symbolic link to itself, and one with init-shell, `update` and BusyBox.
* The other C files under `fixtures/` are programs the self-tests compile: `pty_secret.c`, a dummy SSH that asks for a password on a pseudo-terminal, and `vfs_unmount.c`, the VFS unmount path with substitutes. `fixtures/grow_tool.sh` is typed into the recovery machine by the grow suite to wrap its ext2 tools with counter reads.

### The fake API server

[`fakeapi/`](fakeapi/Readme.md) has the fake API server, `agent_server`, a C program that stands in for a vendor's API, so that a suite can run a program that calls one with no network and no credential. For each run it makes a certificate authority and a server certificate, which the suite gives the program by the program's documented settings and removes afterwards. On the host it serves HTTP/1.1, server-sent events and WebSocket over TLS, plays a script of expected requests and replies in turn, records every request, and fails the run on a request the script does not expect. A step marked unordered is played whenever a request matches it, for a client that sends two requests at once; one marked repeated as well is played by any number of requests, none among them, for a request a client sends on a timer of its own. A step is played once its reply has ended, or a WebSocket's once the server starts to close it; a connection that ends in a WebSocket exchange before then fails the run. A step marked held keeps its reply until a request for `/fakeapi/release`, and a request for `/fakeapi/held` is answered once the held step's request has come, so that a row can inspect a client while it waits for an answer. `build/tests/system/fakeapi_test`, compiled from `fakeapi/native/selftest.c` and run by `host`, checks all four. A guest on QEMU's user network with `restrict=on` has no route out; it reaches the server at `10.0.2.100:443` through a `guestfwd` rule, which starts `agent_relay`, the same program under another name, for each connection. A script names its protocol: `plain` writes requests and replies out literally, and `anthropic`, `responses` and `gemini` are the vendors' APIs below; [the server's Readme](fakeapi/Readme.md) gives its commands and how to write a script. The `fakeapi` suite proves the server from the GNU system with curl and `/etude-wsclient`, as an [etude machine case](../cases/Readme.md). The `agents` and `agentsaccept` suites run as machine cases too; etude owns their private disks, forwarded ports and fake API services.

The `anthropic` protocol implements the [Messages API](https://platform.claude.com/docs/en/api/messages), [tool results](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) and [streaming events](https://platform.claude.com/docs/en/build-with-claude/streaming). `fakeapi/claude-session.json` reads a fixture with Read, runs Bash, changes it with Edit and commits with Bash. Each step requires the preceding tool result; the final answer requires all four. Tool JSON and text are sent in several deltas. The host checks the edited file, the committed tree, the commit count and subject, the clean work tree and every recorded request. A step may also give a `body` the request's must match, which tells a request the client makes for its own use from a turn of the conversation. `fakeapi/claude-screen.json` has the requests a session in Claude Code's screen sends beside the conversation: at its first start, in an empty home, it checks that it reaches Anthropic's services with `GET /api/hello` at `api.anthropic.com` and `GET /v1/oauth/hello` at `platform.claude.com`, and beside the first turn it asks the model for the session's title, with no tools and a JSON schema for the answer; all three are unordered. The self-test also checks whole JSON responses, a step's body, and refusal of incorrect, failed, duplicate and unpaired results.

The `agents` suite's `claude-print` row plays `fakeapi/claude-session.json` with Claude Code on Rach2, which reaches the server by `ANTHROPIC_BASE_URL`, trusts its authority by `NODE_EXTRA_CA_CERTS` and signs in with a dummy `ANTHROPIC_API_KEY`, with nonessential traffic, updates and marketplace installation turned off by [Claude Code's settings](https://code.claude.com/docs/en/env-vars). `agent_server render` names the repository where the row makes it, and the case judges the requests with `agent_server verify` and the repository and commit the row returns ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)).

The `responses` protocol is OpenAI's Responses API as Codex uses it: a `POST /v1/responses` answered with server-sent events, and WebSocket mode, in which each `response.create` message continues the response before it, a warmup with `"generate": false` included. Its steps write the model's side as turns: the conversation each request must have, the output of each earlier tool call among it, and the messages and tool calls the model answers with. `fakeapi/codex.json` is the script the agents' Codex suites play, on a clone of `fakeapi/repo`: Codex reads `notes.txt` and runs `check.sh` over a WebSocket, the server refuses the WebSocket it opens again with 426, which is where Codex falls back to HTTPS, and Codex then edits `greeting.txt` with `apply_patch` and commits. The `codexapi` cases, [`host.codexapi.json`](../cases/host.codexapi.json), play it against Codex on a GNU machine of its own, in a fresh home, with the fake server its only route out. The `agents` suite's `codex-exec` row plays it on Rach2 with `codex exec`; the case judges its requests and repository ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)). The retained `agentsaccept` Codex case drives the interactive screen through its trust and model questions, repository work, cancellation, terminal resize, lost SSH connection and conversation resume.

Muse Code speaks the same protocol to Meta's Model API, as its [Responses API](https://dev.meta.ai/docs/protocols/responses) documents it: a `POST /v1/responses` answered with server-sent events, over HTTPS only. Its tools are the functions of one [namespace](https://dev.meta.ai/docs/tool-search) tool, `muse`, and a turn calls one with `"namespace": "muse"` beside its name. Before its first turn Muse fetches a model catalog with `GET /muse-code/models` at the server's origin, a path the Model API's reference does not list; the script answers it with the reference's [list of models](https://dev.meta.ai/docs/api-reference/models/list-models), which Muse accepts. Meta documents the settings the cases give it: the key in `META_API_KEY` ([authentication](https://dev.meta.ai/docs/muse-code/auth)), the server by `--base-url`, which `muse --help` lists, and a certificate authority's file by `ca_bundle`, which the [changelog](https://dev.meta.ai/docs/muse-code/changelog) of 1.4.3 names and which Muse takes as `endpoint_transport.ca_bundle`, beside `endpoint_transport.base_url`. Its [observer agents](https://dev.meta.ai/docs/muse-code/extending) make model calls beside the main agent's, in an order no script can fix; the documentation says the settings file can turn them off without naming the keys, and the cases turn off each `runtime_capabilities` entry the program has for one. `fakeapi/muse.json` is the script: Muse reads `notes.txt` with `read_file`, runs `check.sh` with `bash`, edits `greeting.txt` with `edit_file` and commits with `bash`. The `museapi` cases, [`host.museapi.json`](../cases/host.museapi.json), play it against Muse Code 1.4.10-R6427.1 of [the agents layer](../../vendor/gnu/agents/Readme.md) on a GNU machine of its own, in a fresh home, with the fake server its only route out. Muse retries a refused request for minutes, so the refusal case, in which the server must refuse a wrong tool result, stops Muse once the server has refused it.

The `gemini` protocol implements the Gemini API's [streamed generateContent](https://ai.google.dev/api/generate-content), with [function calls](https://ai.google.dev/gemini-api/docs/function-calling) and their [thought signatures](https://ai.google.dev/gemini-api/docs/thought-signatures), which a later request must return with each call. Antigravity CLI uses it when its settings name the Gemini API as the model provider and `GEMINI_API_KEY` holds a key, and sends it to the server that `GOOGLE_GEMINI_BASE_URL` names, as [Google's installation page](https://antigravity.google/docs/install?tab=cli) documents. Google documents no setting for a certificate authority. The program is Go, so the rows use the Go runtime's [`SSL_CERT_FILE`](https://pkg.go.dev/crypto/x509#SystemCertPool), which replaces the system's roots with the test CA. `fakeapi/agy-session.json` reads the fixture with `view_file`, runs `run_command`, changes it with `replace_file_content` and commits with `run_command`, with the same checks of results, file, tree and commit as the Claude Code script. Its first step is the conversation title that the program asks a smaller model for beside its first turn; it is unordered, since the two requests are sent at once. The self-test checks refused results and signatures and both response forms.

The `agents` suite's `agy-print` row plays `fakeapi/agy-session.json` with Antigravity CLI on Rach2, headless with `-p`, `--dangerously-skip-permissions` and `AGY_CLI_DISABLE_AUTO_UPDATE`, `"enableTelemetry": false` in its settings, which this version disregards ([the agents layer](../../vendor/gnu/agents/Readme.md#agy)), and a dummy key. `agent_server render` puts the steps of `fakeapi/agy-services.json` before the session's, and the case judges what the row returns as it does for Claude Code ([the agents layer](../../vendor/gnu/agents/Readme.md#tests)).

### The SNTP server

`sntpserver.c` is the time server of the `gnu` family's ntpd case, which builds it as `build/tests/cases/gnu/sntpserver` and starts it as the case's service on the case's second port. It answers SNTP requests on that UDP port of the host's loopback with a time that begins at the epoch it is given and advances by the host's monotonic clock, so that a clock the machine's ntpd set to it differs from the host's by years, and answers a `CLOCKREF` request on the same port with the same time, for the case's own probe of the guest's clock. The guest reaches it at `10.0.2.2`, which QEMU's user network delivers to the loopback. It exits when its parent does.

### Script tests

These are tests of scripts, build rules and host helpers, run against private copies and fixtures:

* Run by `tests/run style`: `build_rules_test.sh` (the build's rules, read from `make -pn` of private trees), `build_inputs_test.sh`, `dryrun_test.sh` (the vendor stamps' dry-run guard), `recovery_key_test.sh` (the recovery image's key list), `style_scope_test.sh`, `style_cases_test.sh` (a fault planted in the sources or in the style cases' manifest fails its case), `verify_temp_test.sh`, `style_hooks_test.sh` (the commit hook in a scratch repository), `probecheck_test.sh` and `nativecheck_test.sh`.
* The checks of the loops, ci, the build tools and the image tools that `tests/run host` runs are the rows of [`host.list`](../cases/host/host.list), judged by the C controllers of [`tests/cases/host`](../cases/host/Readme.md).

### Acceptance

Acceptance of a real machine is not a suite: no `tests/run` set includes it, and the hardware rules of `AGENTS.md` govern it. `accept/metal_accept.sh HOST [PORT] [STICK-SERIAL]` is its scripted half. Over SSH as root, or as an account through `su` with `RACH2_ACCEPT_SU=1` and `accept/su_command.sh`, it reads the machine's identity, network, entropy, disks and devices, fetches its boot log, compares the facts that have a baseline, checks the installed ext2 root, and writes only the root, a loop image under `/tmp`, and the stick whose serial it is given. It saves the boot log it reads as `metal-bootlog.txt` in the directory that `RACH2_ACCEPT_RECORDS` names, `build/images` by default, and its image row needs the host KRFFS tools that `make krffs` builds. Its header comment gives its variables, and a comment before each part of the script describes the row.

The cases of `tests/run metal`, [`tests/cases/machine.metal.json`](../cases/machine.metal.json), rehearse it against QEMU machines. One boots the metal image with a hub, a keyboard and three sticks, which `metal_sticks.sh` makes, and runs the script against it, with no stick named and with one; five boot the installed-root rows on small GRUB disks with an MBR and with a GUID table, which `metal_installed_disks.sh` makes, and must pass two and fail three. Two cases of the family boot no machine of their own: `transport` runs the whole script against private SSH and `su` fixtures, and `password` runs the `su` helper against a dummy SSH peer, `fixtures/pty_secret.c`, on a real pseudo-terminal, both under C controllers in a GNU helper machine that [the cases' Readme](../cases/Readme.md) describes.

`accept/agents_accept.sh lenovo USER [ADDRESS]` accepts the coding agents of the agents layer on the installed Lenovo, once the owner has signed in to each as USER; [the agents layer's Readme](../../vendor/gnu/agents/Readme.md#use) gives the owner's commands. From this host it works in each agent's screen as a person does, in tmux over SSH: a change in a disposable repository, tested and committed, a cancelled turn, a resized terminal, a lost connection and a reopened conversation; then it reboots the machine and requires the credentials, the versions and each agent's answer to a request after it. Its machine half, `accept/agents_guest.sh`, runs on the machine. The `agentsaccept` cases, [`machine/agent_accept.c`](../cases/machine/agent_accept.c), make the same checks in C on the GNU root with the agents layer, with the machine half's `qemu` mode, against the fake API server, which plays `accept/agents/AGENT.json` for each program. The script's header comment describes each step and what it requires.

## Adding tests

A suite is a line in `tests/registry` and a family of cases, `tests/cases/FAMILY.json`, whose identity ends in its name, as [the cases' Readme](../cases/Readme.md) says; `tests/run style` refuses a tree where the two name different suites. Put the line where its length belongs in the schedule, declare the images it writes when they are not named after it, and declare its memory when its machines together ask for more than 128 MiB at once. In `suites.mk`, write a comment that begins `` `tests/run NAME`: `` with one sentence on what the suite proves, beside the rules of the artifacts its cases name, then regenerate the inventory with `tests/run inventory > tests/system/suites.md`.

A script that writes several files at once has one pattern rule, whose targets are `$(call together,FILES)`, which make runs once for all of them, since GNU Make 3.81, the make of macOS, has no grouped targets (`&:`); the comment on `together` in `suites.mk` says what else 3.81 needs. The check `together`, [`tests/cases/host/build_together.c`](../cases/host/build_together.c), finds each such rule in make's database and requires one parallel request of all its files to run the script once.

A suite waits for what the machine prints and sets no time limit of its own: etude's watchdog ends a case that has made no progress for longer than its bounds allow. A suite that keeps an interval on purpose marks it and lists it in `intervals`. A program the suite runs is listed in `tests/probe-suites` with the suite's name.

## Limits

* The runner checks image files by name. It cannot tell which suite wrote a file, so a suite that writes a file another suite owns passes the check.
* Equal hashes before and after a run show that the files the run used are the files there now, not that they did not change in between.

## Tests

The account, login, procfiles, descriptor-lock and credential-persistence suites run the process and account families under `tests/cases/`. Their [case contracts](../cases/Readme.md) describe the private boot media and the reports of their guest programs.

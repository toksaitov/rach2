# tests/system/: the behavioral test machinery

This directory contains everything that runs Rach2 to test it: the QEMU runners under `runner/`, the suite scripts under `suites/`, the capture checkers under `checkers/`, the fixture builders under `fixtures/`, and the real-machine acceptance procedure under `accept/`. The suites themselves are Make targets in `suites.mk`, which the root `Makefile` includes with one line so no test rule sits among the product rules. The guest probe sources stay in [`tests/`](../Readme.md) and the native sanitizer tests in [`tests/host/`](../host/Readme.md).

## The runner

`tests/run NAME [NAME...]`, `tests/run core` and `tests/run all` are the entry points. The runner is the shell script `tests/run` beside `tests/registry`, and the registry is three fields: the suite's name, the external commands it needs, and its tier. The make target is the name with `run-` in front, so it is not written down; `tests/run style` checks that every name has a target and every target has a name.

Six mechanisms, and the reason for each:

* Names and tools are checked before anything is built. A run whose last suite needs a missing `mformat` fails in the first second instead of an hour later.
* `prepare-all` builds the product and the test tools once, before any suite starts. Twenty suites each running Make on the same tree would build the same object twenty times, or race over it.
* The suites then run in a pool, `RACH2_WORKERS` at a time, default twice the processor count and at least four, eight when the count cannot be read. Most of a suite's time is spent waiting for an emulated machine rather than computing, so the useful count is above the core count; on a ten-core machine the full run takes 1286s at four workers, 587 at twelve, and stops improving at twenty.
* Each pooled suite's output is held and replayed at the end in the order the suites were named, which for `all` and `core` is the registry's. Twenty suites writing to one terminal is not a report.
* Registry order is the schedule order, longest suite first. A pool finishes when its longest member does, so a long suite started last leaves the machine idle around it.
* A shim named `qemu-system-i386` goes first on `PATH` and writes its own pid to the ledger of the suite that is running. A machine still alive when its suite ends is named with the suite that left it. Listing every QEMU on the host would work only while one suite ran at a time.

`style` and `host` run alone, before the pool: `style` rebuilds the kernel with its own flags, and both share a scratch directory. `usb`, `usbdisk`, `sealed` and `mount` run alone after it: the first two plug devices in and out through QEMU's monitor, which stops answering on a saturated host, and the other two are the longest sequences of boots, each step waited for with a deadline that the pool's load overruns.

`tests/run runner` (`selftest.sh`) drives the runner against a registry and a makefile of its own in a temporary directory, and boots nothing. It is the only test of the runner itself.

## QEMU runners

* `runner/harness.c` starts `qemu-system-i386` headless, accepts optional initrd, disk, network, device, and extra QEMU arguments, and executes ordered serial steps. Step forms include `expect=`, `send=`, `sendraw=`, `wait=`, `tcp=`, `udp=`, `exec=`, and `probe=`. `--bios` gives the emulator no kernel, so its firmware boots whatever the drives and devices hold in the order their `bootindex` says, which is how a machine boots from a stick image. `sendraw=` writes its text with no newline after it, and reads `\xNN` and the usual escapes, which is how a guest terminal in raw mode is given one byte. `key=`, `mouse=`, `usb=add:`, `usb=del:`, `drive=add:` and `drive=del:` go to QEMU's own command channel on a unix socket beside the serial line, because a key pressed, a mouse moved or a device plugged in comes from the emulated hardware rather than from anything the guest can be asked to do. A stick plugged in after the boot is two steps: `drive=add:` makes the medium and `usb=add:` the device over it, naming the drive; pulling the device leaves the medium, so a replug is `usb=add:` alone. The socket is opened only for a run whose steps need it, so every other suite's command line is unchanged. Each such command waits for the monitor's prompt before the run goes on: a second command written while the first is still being read is the one that is lost, and the key it was carrying never arrives. It enforces a run deadline and per-step deadlines. With a harness kernel it can decode the guest process status through QEMU's `isa-debug-exit` device; `--ok` instead requires a serial token and a machine that did not stop on its own with an even exit status (a stop through `isa-debug-exit` is odd), and `--never` fails the run if a text ever appears, which is how a probe that must be killed is checked.
* `runner/runtests.c` implements the shared boot of the `default` suite, which is the first entry in the core tier. It runs the ordered probe list and scores each probe from the kernel line that returns its transient init process to the debug shell. Every probe the shared boot can set up runs here; the ones that need typed input, a host peer, a disk, or a deliberate fault have a suite of their own, most of them through the harness, which decodes an exit status the same way. `--selftest` checks the scorer without QEMU. The boot's transcript is kept at `build/images/test.krffs.default.log`, so a probe that fails names the record it failed on.
* `runner/hostpeer.c` is the host end of a connection a guest test needs. `hold` keeps a TCP connection open while the machine reads its own `/proc/net/tcp`; `echo` serves TCP and UDP on a port and sends back what arrives, which is what makes the socket probes prove a round trip rather than QEMU's willingness to accept.
* `runner/ptydrive.c` runs a command on a pseudo-terminal of a known size and answers its password prompts from the environment. The SSH suites need a client that reads a password from a terminal.
* `runner/deadline.c` runs one program with a time limit and kills its whole process group. The host suite gives each native test 60 seconds through it.

## Capture checkers and fixtures

* `checkers/wavcheck.c` reads the recording QEMU's `wav` audio backend writes and says whether the machine played the scale it was asked for: each named frequency the loudest in its turn, in the order named. The notes are not equal parts of the recording, so it sweeps rather than dividing. It is the only test tool that links the maths library.
* `checkers/pcapcheck.c` reads Ethernet pcap files produced by QEMU, one subcommand per question. `bcast` checks a broadcast UDP datagram, a packet source address, an ARP ownership reply, or use of a gateway for an off-subnet destination. `netconsole` validates and reassembles Rach2 netconsole frames, including their broadcast address, boot id, sequence, payload length, checksum, and required log text. `rawwire` checks the hop limits and caller-supplied ICMP checksum emitted by the raw-socket probe.
* `fixtures/mkfixture.c` builds both disk fixtures. `boot` rewrites a small MBR disk into the `/dev/bootpart` fixture and fills its FAT-typed partition with the probe's byte pattern; `wide` creates a sparse 260 GiB disk with known sectors at 5 GiB and 258 GiB for 64-bit disk-offset tests.

## Suites

The two verification suites come first. `suites/host.sh` (`tests/run host`) discovers every `tests/host/*_hosttest.c`, compiles it with the host C compiler and AddressSanitizer plus UndefinedBehaviorSanitizer, and runs it; a test lists separately compiled sources in repeatable `host-deps:` comments, and the project `deadline` tool limits each test to 60 seconds. The style suite lives under [`tools/verify/`](../../tools/Readme.md) because it checks the tree, not the running system.

The behavioral suites receive built artifacts and credentials from their Make targets. They use disposable copies or dedicated fixtures, and each script that starts QEMU installs cleanup for it.

* `suites/account.sh` (`tests/run account`) checks account creation, authentication, password changes, and database consistency in both os-real and os-simple. The os-real profile also checks deletion across reboots.
* `suites/tcc.sh` (`tests/run tcc`) compiles and runs programs as the unprivileged account, compares a machine-built `cat` with the staged one, and checks the unsupported TinyCC output forms.
* `suites/make.sh` (`tests/run make`) checks incremental pdpmake behavior, dependency rebuilding, `.PHONY`, compiler overrides, and timestamps across a reboot.
* `suites/selfbuild.sh` (`tests/run selfbuild`) builds the kernel twice in clean guest workspaces, requires equal hashes, builds utilities and ISH, extracts and checks the exact kernel, and boots it through the probe suite. It also boots that kernel through GRUB, on a disk assembled natively from the pinned GRUB artifacts. `tests/run selfbuild-ext2` runs the same suite with `SELFBUILD_ROOT=ext2` on a disk whose partition is the os-real system as an ext2 volume, booted with `rach2.root=ext2`: the free space and the built kernel are read by `debugfs`, and `e2fsck -fn` must find the volume consistent after the synced stop.
* `suites/ssh.sh` (`tests/run ssh`) checks root key login, unprivileged password login, pty and terminal-size propagation, and rejected authentication attempts. The pty driver `runner/ptydrive.c` answers the password prompts on a sized terminal.
* `suites/procfiles.sh` (`tests/run procfiles`) checks `/proc/mounts` on RAM, page-cache, and disk roots, then checks the `/proc` data used by `ps`, `df`, `free`, `uptime`, `dmesg`, `route`, `arp`, and `netstat`. It also reads `/proc/interrupts` and `/proc/stat` on the machine: the timer's vector must have counted and be named `pit`, the per-vector counts must add up to no more than `/proc/stat`'s `intr` line, and both are read from the same boot.
* `suites/login.sh` (`tests/run login`) compares strict and permissive init behavior when `/bin/login` is absent, checks recovery of a stopped console session, and verifies `rach2.rescue`.
* `suites/exitline.sh` (`tests/run exitline`) requires plain process-exit diagnostics under the debug shell, suppresses them under init, and checks both the scoring markers and the no-token harness path.
* `suites/shutdown.sh` (`tests/run shutdown`) checks forced and signal-driven halt, poweroff, and reboot paths, root permission, QEMU termination where required, and offline KRFFS state.
* `suites/bootline.sh` (`tests/run bootline`) checks rejected disk-root command lines, an unmountable disk root, and the rescue exemptions.
* `suites/crash.sh` (`tests/run crash`) checks the dirty-mount flag after a killed boot, clean halt, poweroff, and attempts to clear the root's overlapping set-id bit.
* `suites/diskpolicy.sh` (`tests/run diskpolicy`) proves that the ordinary kernel changes a mounted fixture while the write fails under the read-only kernel and leaves every byte unchanged.
* `suites/diskdiag.sh` (`tests/run diskdiag`) checks read-only disk inspection over unattended SSH, compares selected sectors with the host image, requires the diagnostic disk copy to remain unchanged, and checks the no-disk case.
* `suites/reset.sh` (`tests/run reset`) runs each of the three restart mechanisms with the earlier mechanisms skipped.
* `suites/metal.sh` (`tests/run metal`) boots the metal image without console input, checks SSH and file transfer, kills Dropbear, and requires init to start a different server process. It also runs `accept/metal_accept.sh` against the QEMU guest.
* `suites/drill.sh` (`tests/run drill`) destroys a root partition, enters the recovery image, reflashes the root over SSH, verifies the written extent, and boots the repaired system. `tests/run drill-ext2` runs it with `DRILL_ROOT=ext2` on a disk whose fourth partition is the ext2 root the candidate entries boot: that root is the one destroyed, rewritten and mounted again, the saved default stays the candidate through the repair, and the whole-disk window refuses to open for writing at all under the root's claim, which is the refusal the drill then records.
* `suites/menu.sh` (`tests/run menu`) checks the immutable GRUB stub, the rewritable menu slot, fallback numbering, static-address fallbacks, a truncated menu, and in-place slot writes.
* `suites/grub.sh` (`tests/run grub`) alternates marked GRUB core images between the two tail slots and proves each replacement by the marker printed by the running core.
* `suites/install.sh` (`tests/run install`) checks kernel trial, commit, fallback, repair, and determinate interrupted environment states on a GRUB disk. `tests/run install-ext2` runs it on a disk whose candidate entries boot an ext2 root on the fourth partition, so the kernel is built on and installed from the ext2 root, the fallback boots are the KRFFS root, and the repair from the fallback mounts the ext2 partition to reach the kernel built there.
* `suites/sealed.sh` (`tests/run sealed`) runs the finished sealed disk through an injected-fault sequence over SSH and a separate control run that must use neither fallback nor recovery. The candidate entries boot the ext2 root on the fourth partition and the fallback entries the KRFFS root, and both command lines and both mounted roots are asserted; under an armed trial the ext2 root is made missing, faulty and dirty in turn and each boot after falls back to KRFFS with nothing armed, recovery's `init` repairs it, and the candidate is committed again; the KRFFS root is the one destroyed and rewritten from recovery.
* `suites/socket.sh` (`tests/run socket`) starts one `hostpeer echo` and runs the UDP and TCP probes against it, which is the only place the guest opens a connection of its own and is answered.
* `suites/subset.sh` (`tests/run subset`) boots the kernel with each optional device switched off, and requires the probe to record that it was skipped rather than merely requiring a shell.
* `suites/usb.sh` (`tests/run usb`) is twenty-one boots over the USB stack, one of them in two parts. Eight are the stack itself: enumeration at both device speeds, a key typed through the emulator's monitor reaching the debug shell and then a program, a mouse moved on both axes, a device plugged in and pulled out after the boot, the empty `/proc/usb` a machine booted with `rach2.nousb` has, a device this kernel cannot drive refused once and left alone while the devices beside it are enumerated, and a mouse unplugged and plugged back in beside one such device, which stands for the three the notebook has soldered to it. Seven are the controller's own interrupt: the counts in `/proc/interrupts` after keys are typed on messages, the same machine with `rach2.nomsi`, a mouse whose reports are counted on the vector, the four stamps of one keystroke's path under `rach2.usblatency` with the handler required to enter within a millisecond of the drain and the reader to run within two milliseconds of the wake, the same keystroke without the flag read with nothing printed, a machine silenced after three messages by `rach2.msidrop` that goes on typing on the timer's pump, and the 8259's own keyboard and timer with the APIC between them and the processor. Five are the tree: a keyboard and a mouse behind QEMU's hub listed with their path by `usbprobe` under `rach2.hubtree` and the keyboard typing; a stick behind the hub written, pulled from under a mount through the monitor and plugged back in, on the ordinary kernel since the probe runs in parts; the hub pulled with all three behind it, the stick's mount answering `EIO` and unmounting, the log showing every device below the hub going before the hub, and all four slots given back; a keyboard behind a hub behind a hub at its path, typing; and two hubs with eleven devices filling the twelve-entry table with the thirteenth refused by name. Eleven of the boots take the 8042 away, because a key typed on a machine that still has a PS/2 keyboard could have come from either keyboard, and a check that passes either way says nothing about the stack this suite is for.
* `suites/usbdisk.sh` (`tests/run usbdisk`) is nine boots over a flash drive as a disk. Three sticks are built on the host: one with an MBR holding a FAT32 and an exFAT volume, one with a GUID table holding the same two with its first used entry at index 6, and one that is an exFAT volume from sector zero with no table. The boots: the MBR stick named, sized and a block device, with both volumes mounted and the table read back through `/dev/usb0`; the GUID stick the same; the stick with no table mounted through its whole node and recorded as one volume; a file written, synced, unmounted, read back after a remount and read off the image by mtools; the stick pulled out through the monitor while the probe holds a file open on the mounted volume, which answers `EIO` to the read in flight, `EBUSY` to `umount2` while the file is open and success once it is closed, then plugged back in and mounted again with nothing inherited, and the log showing the first one reclaimed; ten plugs and pulls of a stick nobody opened, each reclaimed and every name free afterwards; BusyBox on os-real finding the volume by its label with `findfs` and `mount LABEL=`, copying from it and unmounting, with no change to BusyBox; a 16 MiB read of `/dev/usb0` timed by the machine's own clock and recorded, not judged; and the stick image `build/images/rach2-stick.img` booted by the firmware with no kernel given to the emulator, where GRUB loads the metal kernel and its RAM root off the stick, the stick comes up as the machine's `usb0` with two partitions, and the machine mounts the stick's second partition through `/dev/usb0p2`.
* `suites/fatwrite.sh` (`tests/run fatwrite`) is six boots on a disk whose second partition is a FAT32 volume mtools formatted: `fatwriteprobe` writes files of every kind and unmounts, the host walks the volume with `mkfatfixture --check` and reads the bytes and names with mtools (and `fsck.fat -n` where it is installed), the next boot reads every byte back, a boot is killed in the middle of a write sequence and the boot after it checks and repairs the volume with a record, BusyBox copies, moves, writes and removes on the volume with the copied program compared through mtools and a 4 MiB write and its removal bounded in the disk commands they cost, and two writers and a sync interleave under the lag device.
* `suites/ext2.sh` (`tests/run ext2`) boots the harness kernel beside a disk whose first partition is an ext2 volume `mkext2fixture.sh` wrote with the host's `mke2fs` from a tree of the shapes the walker must answer, and runs `ext2probe`'s link rows on the mounted volume: a fast link, an absolute one, a link to a directory, a dangling one, one of 300 bytes, a chain of forty ending at a file and one of forty-one, `O_NOFOLLOW`, `O_CREAT|O_EXCL`, `stat` against `lstat`, `readlink`, `link`, `EXDEV` and the `/proc` links. Then it builds a root disk, the os-real system on an ext2 first partition and an empty ext2 second one, and boots the ordinary kernel with `rach2.root=ext2` six times: the root mounts writable before the USB stack starts and `/proc/mounts` names it, a write to a partition node answers `EPERM`, and the machine is killed after a synced write; the boot after records `check: clean`, reads the file, and unmounts the root at `poweroff` with the valid bit set; a lost block set by `debugfs` mounts writable with the error bit set and `e2fsck -fn` still owed it; a reached inode whose bit is clear mounts the root read-only with the fault named and `EROFS` for a write; the recovery kernel and image boot on the same disk, whose `init` runs `e2fsck -p` on both partitions with the statuses recorded, and a partition node takes a write there; and the repaired root boots without a check.
* `loopdev.sh` (`tests/run loopdev`) builds a disk whose one partition is a FAT32 volume, puts a FAT32 image and an ext2 image inside it, and boots `loopdevprobe` once per image: the image is attached to a loop device, mounted, read, written, unmounted, detached, attached again and read back, with every refusal an attachment owes asked for in the same boot. The host then reads the image file out of the volume with mtools and finds the bytes the machine wrote inside it, which is what says the writes went through the file.
* `krffscheck.sh` (`tests/run krffscheck`) breaks images on purpose and reads the offline checker's verdict, then replays the kernel's update protocol over an image of its own. A fresh image passes strict and repairing runs; a wrong backward link at a node and at the root, and the dirty flag, are each refused under `--strict`, repaired without it, and clean afterwards; a bad signature and a data size larger than its node are refused either way and the image is left byte for byte as it was. The protocol rows apply every prefix of a create, a write past the end, a truncate, a removal and a move, in the order [`rach2/sys/fs/krffs.Readme.md`](../../rach2/sys/fs/krffs.Readme.md) fixes, and require the check to accept or repair each one, to keep one node per name, and to keep the longer of two copies; the free space is poisoned, so a length published before its bytes shows up as a file claiming bytes nobody wrote. Five wrong orders end the suite, one per rule, and every one of them must be caught.
* `krffsmount.sh` (`tests/run krffsmount`) is four boots on a disk whose one partition is a KRFFS volume the host tools built from a manifest: `krffsprobe read` mounts it read-only, reads a 64 KiB file whose bytes follow a rule to the last one, reads a file in a subdirectory, stats a file and two directories, lists the mount, finds `/proc/filesystems` naming `krffs` and `/proc/mounts` calling the mount read-only, is refused a write and a create, unmounts, mounts again without `MS_RDONLY` and is given read-only anyway; the host then compares the partition with the image it wrote, byte for byte. Then `krffsprobe write` mounts it for writing and creates, writes, reads back, grows, truncates, renames, removes, makes and removes a directory and changes a mode, and the host's `fsck.krffs --strict` must call the unmounted volume clean; the boot after it reads every one of those back. A boot killed while writing must leave the dirty flag set, the volume must still read, and the next mount that writes must say what it repaired. A volume broken on purpose, with a wrong backward link, a node whose name is gone and one name on two nodes, must be repaired by the mount with those counts in its line. Two writers on one mount write files that read back. The last three boots give the kernel a volume with a bad signature, one whose chain is malformed, and one on a partition longer than the ring, and require `mount(2)` to answer `EINVAL` with the kernel naming the rule the volume broke.
* `imagerace.sh` (`tests/run imagerace`) builds one image twice at the same moment and requires both builds to finish, the image and its dependency file to be there, and no temporary left behind. A parallel run of the suites produces exactly that, and with one fixed name per temporary the second build removed the first's file and make deleted the image both needed.
* `suites/doom.sh` (`tests/run doom`) is one boot of the os-real system on a disk root with the Doom port started in the background: after ten seconds the game is still running, the disk commands it cost are recorded, and its zone line reports at least 10 MiB, which is the zone sized from the machine's free memory through a heap that grows with brk where the fixed heap held 6.
* `suites/exfat.sh` (`tests/run exfat`) is six boots on a disk whose second partition is an exFAT volume `mkexfatfixture --empty` built: a program writes a tree and unmounts it, the host's reader walks the volume and reads its bytes (`--check`, `--list`, `--read`, since mtools cannot read exFAT) and the external checker judges it where the host has one, the next boot reads every byte back, a boot killed inside a write sequence leaves the dirty bit set and the next mount checks and repairs the volume, BusyBox copies and moves and removes through the shell, and two writers and a sync run under the lag device.
* `suites/mount.sh` (`tests/run mount`) is nine boots on a disk whose second partition is a FAT32 volume written by mtools: the partition nodes and a read sleeping through the lag device, a device that never answers in time, the root beside a lagged partition, a write copied before the device sleeps, `mountprobe` with an awk over the unmount records, the mounted half of `lagprobe`, the boot partition refusing the raw writer while mounted, and BusyBox on os-real mounting, listing, reading and unmounting the volume with the listing compared against `mdir`.

The remaining suites run through `runner/harness.c` and `runner/runtests.c` directly from their Make recipes, with no script of their own: `default` and the disk, network, persistence and stress families, and three that exist to run probes the shared boot cannot. `tests/run audio` records the five-note scale through QEMU's WAV backend and checks it with `wavcheck`, and reads `/proc/interrupts` before the notes and after them so that the count on the audio controller's message vector must have grown while it played. `tests/run fault` runs the three probes that must be killed rather than served, and ends by running a program that prints a token, which a kernel that took a fault with it could not do. `tests/run console` types at the console for the two probes that block until something is typed, and asserts the text they read back, not only the count.

## Real-machine acceptance

`accept/metal_accept.sh HOST [PORT]` is the non-destructive scripted half of real-machine acceptance. It reads identity, network, entropy, disk, and device information over root SSH and compares the disk facts for which milestone 24 recorded a baseline. Physical actions and the final disk write remain manual procedures under `dev-log/24-metal/` and `dev-log/25-sealed/`. Acceptance is not a suite: it is never part of `tests/run all` and remains governed by the hardware rules in `CLAUDE.md`.

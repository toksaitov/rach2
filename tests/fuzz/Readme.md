# Fuzz harnesses

This directory has the libFuzzer harnesses for the kernel's parsers of bytes that come from a disk or a wire, one file for each: the ELF loader of the i686 kernel and of the x86-64 kernel (`elf_fuzz.c`, `elf64_fuzz.c`), the network receive path (`packet_fuzz.c`), the MBR and GUID partition table readers (`mbr_fuzz.c`, `gpt_fuzz.c`), the KRFFS, FAT, exFAT and ext2 drivers (`krffs_fuzz.c`, `fat32_fuzz.c`, `exfat_fuzz.c`, `ext2_fuzz.c`), the decoder of the guest instructions that reach KVM's MMIO exits (`x86dec_fuzz.c`), and the ioctl decoders of the display stack, DRM, dma-buf, sync file, sw_sync and evdev, which take their bytes from a program (`drm_ioctl_fuzz.c`). Each harness compiles the kernel's own source on the host, so a fuzzer can run it millions of times under the sanitizers. The corpora under `corpus/NAME/` are committed, and every host run replays them, so an input that once found a fault is tested again on every change.

## Running

`build.sh replay [NAME...]` compiles each harness named, or every one, with the host compiler (`cc` unless `CC` is set), AddressSanitizer and UndefinedBehaviorSanitizer, and the `main` that `fuzz.h` supplies under `FUZZ_REPLAY`, which runs the harness once on each file named on its command line. `build.sh fuzz [NAME...]` compiles the libFuzzer program with clang. The programs are `build/tests/fuzz/NAME` and `build/tests/fuzz/NAME-fuzz`.

`tests/run host` replays every corpus through its replay program. A fuzzing run is started by hand, for example:

    sh tests/fuzz/build.sh fuzz fat32
    build/tests/fuzz/fat32-fuzz -max_total_time=300 -timeout=10 -rss_limit_mb=2048 work/ tests/fuzz/corpus/fat32

A run of a fixed count gives `-runs=N` in place of the time, as the ioctl harness was run for 2,000,000 inputs:

    sh tests/fuzz/build.sh fuzz drm_ioctl
    build/tests/fuzz/drm_ioctl-fuzz -runs=2000000 -timeout=10 -rss_limit_mb=2048 work/ tests/fuzz/corpus/drm_ioctl

## Results

A replay program prints `fuzz: replayed N input(s)` and exits 0 when the parser survives every input, and a sanitizer's report and a nonzero exit when it does not. The ELF64 harness also aborts, after `elf64-fuzz: loader fault: RULE`, when the loader accepts an image that breaks one of its rules, and the x86 decoder harness after `x86dec-fuzz: decoder fault: RULE` when a decode breaks one of `decode.h`'s; `tests/run host` names the harness that failed and keeps its log. An input longer than `FUZZ_INPUT_MAX`, 4 MiB, is refused with status 2 rather than replayed short, since a shortened input is a different one. A crash found by fuzzing is filed as a `bug` issue, and its minimised input joins the corpus.

## Design

Every harness defines the one function `fuzz.h` declares, `LLVMFuzzerTestOneInput`, and names the sources it links in `fuzz-deps:` comment lines and any more compiler flags in `fuzz-cflags:` lines, as the host tests name theirs in `host-deps:` and `host-cflags:` lines. The harnesses build with `RACH2_HOSTTEST`, as the host tests do, so they compile the i686 configuration of the kernel's code whatever the host is; one that adds `-DRACH2_HOST_X86_64` on a `fuzz-cflags:` line compiles the x86-64 configuration, as `elf64_fuzz.c` does.

* The ELF harness includes `rach2/sys/proc/elf.c` and loads the input as a program image into pages it allocates one at a time, so that a write past a page is a write past an allocation.
* The ELF64 harness includes the same file in the x86-64 configuration, so the loader reads ELF64 headers and checks segments against the x86-64 user window, and puts the input through each path a program takes: `elf_check` over the bytes in memory, a copy at the image's own addresses, as the boot loads, and `elf_read_layout` and a load mapped from a file at the bias execve gives a program and at the one it gives an interpreter. Its model page directory is a list of the pages it has mapped. A load that fails has rejected the image; one that succeeds is checked against the headers the harness reads from the input itself: every page mapped once and inside the window from `USER_ADDR_MIN` to `USER_STACK_BASE`, every segment record matching a PT_LOAD whose file bytes the file has, in ascending order, its bytes and zeros after them in the pages filled, and the entry point and the program header table inside the window. The seeds are two x86-64 test programs, `hello` and the musl `muslhello`, and a position-independent image with an interpreter, `pie`; four more each break one rule the loader enforces and are otherwise valid: a segment past the top of the window (`pasttop`), two segments in one page (`overlap`), an entry point at the window's top (`entrytop`) and a file offset of 2^32 or more (`offset4g`).
* The packet harness includes the packet host test and hands the input, cut to 1514 bytes, to `ethernet_rx` as one Ethernet frame, from the end of an allocation of exactly its length.
* The MBR harness includes `rach2/sys/block/mbr.c`, pads the input to a sector with zeros and puts the table through each check the kernel makes of one. The GPT harness links `rach2/sys/block/gpt.c` and takes the input as a header sector followed by the entry array, and recomputes both checksums, so that the checks behind them are reached.
* The x86 decoder harness includes `rach2/sys/kvm/decode.c` and decodes the input's first 32 bytes in 16, 32 and 64-bit mode; the decoder reads at most 15 of them. Each decode that succeeds is checked against `decode.h`'s rules: a length inside the bytes and copied, known operations and flags, sizes, segments and registers the mode has, no address on a string operation, the same decode from the instruction's bytes alone and none from one byte less. The input's internal error is then checked against the layout of Linux's `emulation_failure`. The seeds are instructions of the host test's table, one refused and one 16 bytes long.
* The ioctl harness links the DRM core, KMS, vkms, PRIME, sync objects, dma-bufs, fences, sync files, sw_sync, evdev, debugfs with DRM's files in it, and the x86-64 kernel's translations of an i386 program's DRM and GPU ioctls whole, each its own unit, and models the rest of the kernel around them: one process with a table of descriptors, a clock that moves only when the input says or a wait would sleep, a heap that refuses a request over 64 MiB as the kernel's refuses one it has no room for, and user memory that is an arena of 64 KiB, where a user address is an offset and one below 4096 or past the end faults. The input is a program: a byte of flags, root or not and an i386 program or not, bytes for the arena, then steps that open vkms's card, a render device of the harness's with sync objects and PRIME, a sw_sync timeline, an event node of a mouse or a touchpad, or one of fifteen debugfs files (sw_sync's, sync/info, and each device's `name`, `clients` and `gem_names`, with vkms's framebuffers, state, CRC control and data, bridges, and its connector's `force` and `edid_override`), and make ioctls, reads, writes, polls, closes, input events, CRC reads and clock steps. An ioctl's number is built from a type of the stack's, a number, a direction and a size, and its argument is the bytes after it. In an i386 program an ioctl of DRM, dma-buf, sync file or sw_sync goes through `ia32_ioctl_drm.c` or `ia32_ioctl_gpu.c`, which call the native ioctl through the user-copy window the harness models, and evdev gives 16-byte records. An event written to a node goes nowhere past evdev, since the harness has no console or mouse queue. A wait that would sleep moves the clock, runs the vblanks, vkms's composer and the commit queue, and then returns as a signal would; a wait no signal ends that never ends aborts the run. After the steps every descriptor is closed, and the devices keep what the closes leave. Replayed, the harness prints each ioctl and its result. Its seeds each reach one decoder: VERSION and GET_CAP, the mode resources, a dumb buffer with a framebuffer, an atomic commit, sync objects, sw_sync and a sync file, PRIME between two devices, evdev's queries and events, and `evdev-defuzz`, an EVIOCSABS fuzz whose arithmetic overflowed in evdev's filter; `debugfs-crc`, `debugfs-edid` and `debugfs-sync` read and write the debugfs files, `evdev-write` and `i386-evdev-write` write events to a mouse and a touchpad, and `i386-drm`, `i386-evdev` and `i386-sync` are an i386 program's ioctls.
* The KRFFS harness takes the input, up to 1 MiB, as a whole volume behind a memory backend, lists up to 64 entries of the root and reads each.
* The FAT, exFAT and ext2 harnesses share `fs_common.h`: the kernel calls their drivers make are stubbed as the host tests stub them, a block device answers from a volume in memory of up to 4 MiB, and one walk mounts the volume, lists up to 64 entries of the root, reads up to 4 KiB of each file among them and unmounts. The block cache is invalidated before every mount, since it outlives the call and would otherwise answer a new input with blocks the last one read. ext2 takes the input as a whole volume, and its seeds are 64 KiB volumes `mke2fs` made. FAT and exFAT take a smaller input and scatter it over a volume the fixture makers build in memory, through the builders `tests/host/mkfatfixture.c` and `tests/host/mkexfatfixture.c` expose: for FAT, a 4 MiB volume, the input being the boot sector, 4 KiB of the first table and 16 KiB from the start of the data region; for exFAT, a 1 MiB volume, the input being the 24 sectors of the two boot regions, 4 KiB of the table and 32 KiB from the start of the cluster heap, with both boot checksums recomputed after the scatter, since the driver refuses a region whose checksum is wrong. A region past the end of a short input is zeros, not the seed's bytes.

## Adding tests

A new harness is `NAME_fuzz.c` with its `fuzz-deps:` lines and a seed under `corpus/NAME/`; `build.sh` and `tests/run host` find it by its name.

## Limits

Only the ELF loader is fuzzed in both configurations; the other harnesses compile the i686 configuration alone. The display stack's decoders have no code of either architecture, and under `RACH2_HOSTTEST` their structures take the host's sizes in both; the i386 translations define the i386 structures by fixed-width members, so on a 64-bit host the harness converts between the two layouts the kernel does. `ia32_ioctl.c`, which translates the i386 ioctls of the rest of the kernel, is not linked. The ioctl harness drives no mmap, eventfd or udmabuf, whose memory and descriptors the model does not have; `tests/drmfuzz.c` drives those on a running kernel ([the tests' Readme](../Readme.md)).

The ext2 corpus includes `xattr`, a raw external attribute block with a binary `user.DOSATTRIB` value and Linux's name, value and block hash. The harness feeds each input to the attribute codec and, as a volume, to the driver; the inode walk reads and lists attributes too.

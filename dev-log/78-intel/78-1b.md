# 78-1b: the watchdog's expiry on the Lenovo

The proof that the chipset's TCO watchdog resets the Lenovo and that the firmware boots the installed Rach2 afterwards, before any hang experiment of the graphics stack relies on it: one expiry under Debian on p5, then Rach2's own driver (`rach2/sys/arch/x86/itco.c`, 78-1a) armed, fed for two minutes and left unfed on a trial boot. The Debian expiry left the machine down, so Rach2's trial stopped the timer by magic close instead of letting it expire, and the expiry moved to the owner's sitting (84-4). The trial boot also runs `gfxtool` on the display the firmware set up, whose dump becomes `tests/fixtures/lenovo-gpu/firmware-dump.txt`. Both parts are silent: nothing plays and nothing is drawn beyond the boot's console.

## Readiness

Why the trial's new code cannot leave the machine stopped, as the machine skill's Trial boots asks.

* Register sequences, against Linux 6.12's `drivers/watchdog/iTCO_wdt.c`, version 2: start (`iTCO_wdt_start`) clears NO_REBOOT, bit 5 of GCS at RCBA + 0x3410, and reads it back, writes 1 to TCO_RLD, clears bit 11 (halt) of TCO1_CNT and reads it back; stop (`iTCO_wdt_stop`) sets halt, reads it back and sets NO_REBOOT; a feed (`iTCO_wdt_ping`) writes 1 to TCO_RLD and nothing else; the timeout (`iTCO_wdt_set_timeout`) is seconds times 10 / 6 in 0.6 s ticks, 4 to 0x3ff, written into TCOv2_TMR at + 0x12 keeping bits 15:10, and read back; the time left (`iTCO_wdt_get_timeleft`) is TCO_RLD's low 10 bits times 6 / 10, the current stage only. `itco_start`, `itco_stop`, `itco_ping`, `itco_timeout` and `itco_timeleft` do the same accesses in the same order. The probe's status clearing (8 to TCO1_STS, then 2 and 4 to TCO2_STS) and its 30 s heartbeat are `itco_attach`'s. Linux leaves SMI_EN's TCO_EN alone on version 2 (`turn_SMI_watchdog_clear_off` is 1), and so does Rach2, so the first stage's SMI goes to the firmware as under Linux.
* Where Rach2 differs: `itco_attach` halts the timer at boot, where Linux would leave a timer the firmware started running and feed it. Linux found it inactive on this Lenovo, so the halt changes nothing there. A failed start halts the timer again.
* The file interface follows Linux 6.12's `drivers/watchdog/watchdog_dev.c`: open arms; a write scans for `V` and feeds only a running timer; a close stops on magic close, else feeds once and stays armed; GETSTATUS gives MAGICCLOSE and KEEPALIVEPING; SETOPTIONS without a flag is `ENOTTY`. This task brought the last three, and the untouched halted timer, into line.
* The addresses come from the board profile alone: TCOBASE is PMBASE + 0x60, 0x1860 on the Lenovo's Lynx Point-LP, and RCBA is LPC register 0xF0 with its enable bit. `board_rcba` answers only for the `ich9` and `lynxpoint-lp` profiles, and other boards get no device.
* Waits: the driver has none. Each operation is a fixed sequence of port and MMIO accesses. `wdtrial`'s two loops end by its own clock: feeding after FEED seconds, the unfed phase at 4 x TIMEOUT + 30 s, when it halts the timer by magic close. `gfxtool` waits at most a second or 10000 reads for a register.
* Interrupts: the driver takes none.
* The machine cannot stay stopped once `wdtrial` holds the device: a hang while it feeds ends in the TCO's reset within 60 s, which returns to the fallback slot. A hang before that is as for any trial of the branch.
* `gfxtool` reads through `/dev/mem` and writes two registers, both restored at exit: FORCEWAKE_MT for the ring reads, and PIPE_CRC_CTL, which it refuses to touch when the CRC is already on or when the eDP route bypasses pipe A. It refuses a GPU a driver owns, and no driver on the branch binds 8086:0a16.
* Host test, run alone: `tests/host/itco_hosttest.c`'s `trial` row runs the trial's path on the TCO model: attach, open, a 30 s timeout, twelve feeds 10 s apart with the time left read at 20 s before each, then nothing until the first stage expires 30 s after the last feed (time left 30 s again) and the reset at 60 s, with only TCO_RLD written between the timeout and the reset. `itco_hosttest: ok`.
* QEMU 10.2.1 on the testing host, q35 under KVM, the x86-64 kernel of this commit with `wdtrial` built by Rach2's own tcc (`tcc -static`, no warnings with `-Wall -Werror`), `wdtrial 15 30`: three feeds with 4 s left before each, status 0x8000, then 13 s down to 0, 14 s down to 0, and QEMU's reset 30.0 s after the last feed, two stages of 15 s.

### Debian's expiry

1. Boot Debian: `D arm`, then `D wait-debian`. Passes: "answered" within 6 minutes.
2. Facts: `D sh 'uname -r; cat /proc/cmdline; lsmod | grep -i tco; wdctl; ls -l /dev/watchdog*; for f in identity state timeout timeleft nowayout status bootstatus; do echo "$f: $(cat /sys/class/watchdog/watchdog0/$f 2>&1)"; done; systemctl show -p RuntimeWatchdogUSec -p RebootWatchdogUSec -p WatchdogDevice; grep -E "CONFIG_(ITCO_WDT|WATCHDOG_NOWAYOUT|WATCHDOG_HRTIMER_PRETIMEOUT)=" /boot/config-$(uname -r); dmesg | grep -i -E "itco|watchdog"' > debian-facts.txt`. The `status` line and `CONFIG_WATCHDOG_HRTIMER_PRETIMEOUT` say whether Debian's GETSTATUS also carries WDIOF_PRETIMEOUT (0x200), which Rach2 does not set.
3. Turn systemd's runtime watchdog off for this boot: `D sh 'busctl set-property org.freedesktop.systemd1 /org/freedesktop/systemd1 org.freedesktop.systemd1.Manager RuntimeWatchdogUSec t 0; systemctl show -p RuntimeWatchdogUSec; cat /sys/class/watchdog/watchdog0/state /sys/class/watchdog/watchdog0/timeout'`. Passes: `RuntimeWatchdogUSec=0` and `inactive`, since systemd halts the timer by magic close as it lets go. Note the timeout it leaves, 30 if systemd set it.
4. Arm and leave it unfed, with the Mac timing the machine: `up > ping-debian.txt &`, then `D sh 'exec 3> /dev/watchdog0; echo "armed at $(cut -d" " -f1 /proc/uptime)"; while :; do echo "$(cut -d" " -f1 /proc/uptime) $(cat /sys/class/watchdog/watchdog0/state) left $(cat /sys/class/watchdog/watchdog0/timeleft)"; sleep 1; done' | while IFS= read -r l; do echo "$(date +%T) $l"; done | tee wd-debian.txt`. The stream ends when the machine resets. Expected: `left` counts the timeout down twice, the two stages of a version 2 TCO, and the reset follows about twice the timeout after `armed`.
5. If no reset has come 3 minutes after `armed`, that is the finding: interrupt the stream, halt the timer with `D sh 'printf V > /dev/watchdog0'`, record it, leave by `D leave`, and report it on this issue at once. The Rach2 trial then does not run until the cause is known.
6. Back: `D wait-rach2`, then at once `L 'mixer vol 1'`. Stop the ping loop (`kill %1`). Then `L 'cat /etc/rach2/release; bootctl status; cat /proc/cmdline' > debian-back.txt`: the release runs from the candidate slot, and `next_entry` is empty because the trial was consumed. Then `D restore`, which must print p1's SHA-256 equal to `p1-before.sha256`.

### What this proves, and what it does not

Rach2's driver works on the Lenovo's Lynx Point-LP as on the model and in QEMU: it finds the TCO at 0x1860, takes the timeout, is fed by both write and WDIOC_KEEPALIVE, counts the current stage down and stops on magic close. It does not prove that an expiry brings the machine back: under Debian the first stage's expiry left the machine down until it was powered on by hand, and Rach2 programs the TCO as Linux does, so no hang experiment may count on the watchdog to return the machine.

The starting point for the sitting's expiry is Linux 6.12's SMI handling in `drivers/watchdog/iTCO_wdt.c`. `iTCO_wdt_probe` clears TCO_EN, bit 13 of SMI_EN at PMBASE + 0x30, only when `turn_SMI_watchdog_clear_off >= iTCO_version`; the parameter defaults to 1, so on version 2 Linux leaves TCO_EN as the firmware set it, and the first stage's timeout raises an SMI that the firmware's handler takes. Booting Debian with `iTCO_wdt.turn_SMI_watchdog_clear_off=2` clears TCO_EN, so the first stage raises no SMI and the second stage's expiry resets the machine through the chipset alone. Watching the screen at each expiry, with and without that option, tells an SMI handler that stops the machine from a reset that hangs in the firmware. Rach2 has no such option and leaves SMI_EN alone.

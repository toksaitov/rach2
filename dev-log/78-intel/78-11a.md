# 78-11a: the kernel calls hasvk makes

Each call that Mesa's Crocus made for `eglinfo` and hasvk for `vkcube --wsi display` under Linux 6.18 on the Lenovo (`dev-log/76-graphics/research/work/tonight/lenovo.md`, "The kernel interface Mesa uses"), and each that the sources of hasvk in Mesa 25.0.7, Rach2's pin for it, make (`src/intel/vulkan_hasvk/anv_gem.c`, `src/intel/common/i915/intel_gem.c`, `src/intel/common/intel_gem.c`, `src/vulkan/runtime/vk_drm_syncobj.c` and `src/vulkan/wsi/wsi_common_drm.c`), checked against Rach2: its handler, and the host test that runs it. Every number in the table matches Linux 6.12's: the driver's in `i915_exec_hosttest.c`'s `trace` row, read by compiling Linux's `include/uapi/drm/i915_drm.h`, and the DRM core's and dma-buf's in `drm_abi_hosttest.c`.

## Two that were missing

* `I915_GEM_EXECBUFFER2` with `I915_EXEC_USE_EXTENSIONS` and the timeline fences, `DRM_I915_GEM_EXECBUFFER_EXT_TIMELINE_FENCES`. GETPARAM already answered `HAS_EXEC_TIMELINE_FENCES` 1, as Linux does, while the call refused the extension with EINVAL. hasvk reads the parameter (`anv_device.c:1743`) and then sends every submission that names a syncobj point through the extension (`anv_batch_chain.c:2200-2206`), so on Rach2 its queue submissions with timeline semaphores failed. Served now as Linux's `add_timeline_fence_array`; 78-11a.1.
* `I915_REG_READ`, which hasvk calls once when it opens the device to see whether the render ring's timestamp can be read from the processor (`anv_device.c:1791`) and again whenever the device is asked for the GPU's time (`anv_device_get_timestamp`, `anv_device.c:2340`), whose failure marks the device lost with "Failed to read the TIMESTAMP register". Served now in `i915_reg_read.c`; 78-11a.2.

## What differs from Linux

* PERF_REMOVE_CONFIG: Linux answers ENOENT for the probe's id, `UINT64_MAX`, and Mesa then takes the dynamic configurations of i915 perf as there (`src/intel/perf/i915/intel_perf.c`, `i915_has_dynamic_config_support`). Rach2 has no i915 perf and answers EINVAL, which Mesa takes as no dynamic configurations. Performance queries are not in milestone 78's plan.
* GEM_MMAP, the old map of an object into the caller's memory: hasvk calls it only when MMAP_GTT_VERSION is below 4 (`anv_gem.c:120-123`), and Rach2 answers 5, so it uses MMAP_OFFSET as under Linux. Rach2 has no row for it and answers EINVAL where Linux maps; programs built on the old libdrm_intel would need it.
* REG_READ without `I915_REG_READ_8B_WA` reads the low half and then the high, as 32-bit Linux's `readq`, where 64-bit Linux makes one 8-byte read, which Linux's uapi header says returns a wrong value for this register. Mesa always passes the flag.
* Linux's `add_timeline_fence_array` keeps one error variable across its entries, so an entry with no flags on a syncobj with no fence after a point to signal that the timeline has not reached fails the call with the earlier entry's EINVAL. Rach2 judges each entry alone; [upstream.md](upstream.md#linux-refuses-a-timeline-fence-with-the-error-of-the-entry-before-it) records the fault.
* The fence array refused nothing for an entry to wait for with no fence when it also signalled; Linux's `add_fence_array` refuses it with EINVAL, and Rach2 now does too.

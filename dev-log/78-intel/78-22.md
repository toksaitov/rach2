# 78-22: a panic that resets the machine

The owner's order of 11 November, after the Lenovo hung during 78-14b's trial boot: a panic must pause to show its message and then reset the machine. Before this task `k_panic` drew its picture and record and halted for ever. It now does what Linux 6.12.115 does with `panic=N`, and resets the machine in Linux's `emergency_restart` order, with `reboot=` choosing the method. Each behaviour below names the Linux line it follows.

## What the kernel does

* `panic=N` on the boot line, and `/proc/sys/kernel/panic`, are Linux's `panic_timeout` (`kernel/panic.c`: `core_param(panic, panic_timeout, int, 0644)`, the loop after `if (panic_timeout > 0)` and `emergency_restart()` after `if (panic_timeout != 0)`). 0 halts as before; N above 0 writes `panic: rebooting in N seconds..` at `KLOG_CRIT`, waits N seconds in steps of `PANIC_TIMER_STEP`, 100 ms, counted by `k_udelay` with interrupts off, and resets; below 0 resets at once. Each `panic=` is read in turn and one that is not an integer is logged and left out, as `param_set_int` leaves the old value (`kernel/params.c`).
* `oops=panic` and `/proc/sys/kernel/panic_on_oops` are Linux's `panic_on_oops` (`oops_setup`, `early_param("oops", ...)`). Every exception the kernel takes in its own code already panics (`arch/x86/isr.c`), which is what Linux does with the value set; the value is kept for programs that read and write it.
* `power_emergency_restart` (`arch/x86/power.c`) is the loop of `native_machine_emergency_restart` (`arch/x86/kernel/reboot.c`): `a`, the FADT's reset register, with `acpi_reboot`'s 15 ms wait (`drivers/acpi/reboot.c`); `k`, ten pulses of the 8042 with `kb_wait`, back to `a` once when `a` came first; `e` and `b`, logged and passed over, since the kernel calls neither EFI's `ResetSystem` nor the BIOS; `p`, port 0xCF9 with 0x0E for a cold reset or 0x06 for a warm one over the register's other bits; `t`, an empty IDT and `int3`; and round again to `k`. `reboot=` is read as `reboot_setup` reads it (`kernel/reboot.c`), with `panic_` before a mode for the panic's alone. A restart with `reboot=` on the line runs the same loop, as Linux's `native_machine_restart` does after its shutdown; without it a restart keeps its own chain, which `rach2.resetskip` and `tests/run reset` cover.
* The other processors are stopped first, as before, and now as `native_stop_other_cpus` stops them (`arch/x86/kernel/smp.c`): the interprocessor interrupt, a second's wait for all, then an NMI to each still running and 10 ms more. The NMI handler halts a processor whose stop was asked (`smp_stop_nmi`), as `smp_stop_nmi_callback` does. A processor spinning with its interrupts off, which is what a hard lockup leaves, used to be left running while the panic drew.

## The Lenovo's reset, by reading Linux

The Lenovo's FADT is revision 5, has a reset register, and its PM1 block at 0x1804 says it is not hardware-reduced (`dev-log/80-games/80-6/evidence/lenovo/dmesg-kernel-boot.txt`: `acpi: fadt: revision 5, pm1a 0x1804, ... reset register, 8042 yes`). Linux 6.12.115's `reboot_dmi_table` has no Lenovo entry, so `reboot_init` changes nothing, and `efi_reboot_required` is false on a machine that is not hardware-reduced, so the type stays `BOOT_ACPI`. Linux's emergency restart on the G50-70 therefore writes the FADT's reset register first, and the kernel now does the same. That is also the first method of the kernel's ordinary restart, which has restarted the Lenovo on every release.

The installed menu's candidate lines carry `panic=10` from the next install or `rach2-install --console term --update` on (`tools/image/mkdisk_grub.sh`, `utils/rach2-install`), and a trial root's line copies the booted line's words, so a trial that panics shows its record for ten seconds and resets, and the firmware's next boot takes the saved default, the fallback. The fallback's and recovery's lines have no `panic=` and halt, so no two kernels reset each other in turn. Until the Lenovo's menu is updated, a trial gets the token only when it is added to the candidate line by hand.

## Measured in QEMU

`tests/run panic`, six cases on each kernel, all 30 assertions passed on i686 and on x86-64: `reboot=a` on q35, whose FADT has a reset register, resets by the register alone; `k`, `p` and `t` each reset by their method alone; no `reboot=` on `pc`, whose FADT has none, logs that and resets by the 8042; and `panic=-1` resets with no wait. By hand, with the host's clock stamping each serial line, the record of `rebooting in 5 seconds..` came 4.94 to 4.96 s before the first method's on both kernels, and `panic=2` and `panic=3` gave 1.94 and 2.94 s, under 1% short of the kernel's count of the wait; the cause of that difference in the host's stamps was not traced, and the suite judges no time. An ordinary `reboot` with `reboot=t` reset by a triple fault.

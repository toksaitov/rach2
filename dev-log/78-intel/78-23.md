# 78-23: a crash record across a reset, and the kernel's TCO feed

The check on the Lenovo that ramoops's region survives a warm reset: two trial boots of this task's x86-64 kernel with the region on the line, the second of which must show the first boot's log as `/sys/fs/pstore/console-ramoops-0`. The rest of the task's Done ran in QEMU, as Results says.

## Readiness

Why the trial's new code cannot leave the machine stopped, as the machine skill's Trial boots asks.

* The region: `ramoops_reserve` (`rach2/sys/pstore/ram.c`) runs before `init_paging` and only with the `ramoops.` options. It does arithmetic on the options and on the frame map and refuses, with a record, whatever it doubts: sizes that do not fit, a region of 4 GiB or more, one past what the kernel maps, one that is partly usable memory, or one that holds the kernel or a module. On the Lenovo 0x40000000 to 0x400FFFFF lies inside the firmware's usable range 0x100000 to 0xA56B0000 (`dev-log/50-shortcomings/lenovo-boot.log`), and GRUB puts the kernel and its modules far below it.
* The mapping: `ramoops_init` maps the megabyte through `map_mmio_typed` write-combining, as Linux's `persistent_ram_vmap` maps RAM with `ramoops.mem_type=0` (`fs/pstore/ram_core.c:414`), and drains the write buffers after each write (`arch_dma_fence`). The frames are out of the allocator, so nothing else writes them.
* The writes: each record of the log is copied into the console zone with its Reed-Solomon parity, a fixed amount of work for at most 256 bytes, inside `klog`'s ring append with interrupts off. A panic copies the ring's tail once. Neither allocates, takes a lock or waits.
* The files: `/sys/fs/pstore` is a mount inside `/sys` that holds the records in kernel memory; reading and removing them touches the region only through a zap of its header.
* Waits: none of the new code waits. Interrupts: it takes none.
* The TCO: the trial's line has no `rach2.itco.arm`, so the kernel starts no timer. `itco_attach` keeps a timer running only when the firmware left it counting toward a reset, halt and NO_REBOOT both clear; 78-1b found it halted on this Lenovo, so it is halted as before and `itco_tick` returns at once.
* Host tests, run alone: `tests/host/pstore_hosttest.c` (the Reed-Solomon code with errors in data and parity, a zone's header, wrap and second-boot copy, ten damaged bytes mended across a reset with `ecc=1`) and `tests/host/itco_hosttest.c` (the kernel's feed, the open deadline, nowayout, the out-of-range heartbeat and a firmware-started timer). Both pass under ASan and UBSan.
* QEMU: `machine.watchdog.pstore` passes on i686 and x86-64 (Results).

6. A warm reset into the same kernel: `L 'bootctl trial candidate && reboot'`; wait for SSH; at once `L 'mixer vol 1'`.
7. The second boot: `L 'dmesg | grep -E "ramoops|pstore"; ls -l /sys/fs/pstore; wc -c /sys/fs/pstore/console-ramoops-0; head -n 3 /sys/fs/pstore/console-ramoops-0; tail -n 6 /sys/fs/pstore/console-ramoops-0' > pstore-second.txt`. ### For the manager

* Every later boot of the Lenovo reserves and reads the region only if its lines carry the tokens. A new install from the sealed disk does (`SEALED_RAMOOPS` in the Makefile). The installed menu's candidate and fallback lines do not; `rach2-install --update` keeps them as they are. Adding `$RAMOOPS` to the trial staging of the machine skill's Trial boots, and once to the installed lines, is the manager's call.
* `rach2.itco.arm` is not on this step's line. 78-1b found that a TCO expiry leaves this Lenovo down, not reset, because the first stage's SMI goes to the firmware. `iTCO_wdt.turn_SMI_watchdog_clear_off=2`, Linux's option and now Rach2's, clears TCO_EN so that the second stage resets through the chipset alone; whether that brings the Lenovo back is the experiment 78-1b moved to the sitting. Until it passes, a trial line with `rach2.itco.arm` turns a hang into a machine that is off, which costs the same visit.
* A panic's dmesg record is not checked on the Lenovo: nothing reached over SSH panics the kernel, since there is no `/proc/sysrq-trigger` and the debug shell's `fault` is on the console alone. 78-22's `panic=N` now resets the machine after a panic, a warm reset that keeps RAM, so the record would survive one; the check needs only a trigger, at the sitting through the console or once one exists.

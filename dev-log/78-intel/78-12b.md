# 78-12b: the accelerated browsers on the Lenovo

The trial that runs 78-12a's checks, [`tests/graphics/lenovo/browsers-gpu.sh`](../../tests/graphics/lenovo/browsers-gpu.sh), on the Lenovo's HD 4400: Chromium's GPU process and WebGL on Crocus, Firefox's WebRender on Crocus, each browser's processes sandboxed as Debian's on the same binaries, an X11 GL program through Xwayland and a Direct3D 9 probe through Proton's Wine on WineD3D's GL renderer, each read back. It boots the trial root with the Intel driver's display on. Its readiness note, Linux's references and the step come first; the results go at the end.

## What the step runs

`browsers-gpu.sh desktop OUT`, as root on the trial root, with the graphics payload at `/tmp/graphics` and the Direct3D payload at `/tmp/d3d`, as `machine.browser.crocus-fake` stages them in QEMU. `desktop` is the root's ordinary account, uid 1001, in the groups `render` and `video` (`krffs/manifests/os-real-gnu.manifest`). The script runs four checks, each judged on the machine:

* `chromium`: `browser/sandbox.py desktop chromium OUT gpu`, Chromium under a headless Weston that renders with Crocus, with Debian's switches and no `--ignore-gpu-blocklist`; `browser/judge.py chromium gpu` requires chrome://gpu's `GL_RENDERER` to name the HD 4400, WebGL `Hardware accelerated`, `GPU0` 0x8086:0x0a16, WebGL's renderer not llvmpipe and its pixel orange, `[255, 128, 0, 255]`, and each process's seccomp mode and namespaces, chrome://gpu's `Sandboxed` and chrome://sandbox equal to Debian's sandbox case on the same Chromium.
* `firefox`: `browser/run.sh firefox gpu` as `desktop`; the judge requires about:support's `Compositing` to be `WebRender`, its driver vendor `mesa/crocus`, its GPU 0x8086:0x0a16, WebGL's pixel orange, and its sandbox table equal to Debian's.
* `x11`: Xwayland under the same Weston: `glxinfo -B` names the HD 4400 with direct rendering, and `glmark2 --validate -b build -b texture` reads back both scenes as `Validation: Success`.
* `d3d9`: `d3d/run.py -a host probe wined3d/9` on that Xwayland: the adapter is `vendor 0x8086 device 0x0a16` and the probe prints `D3D9 OK` for its two pixels.

It prints `browsers-gpu: result: pass` and exits 0 when all four pass. Without `-f` every readback is judged.

## Readiness

Why the trial's paths cannot leave the machine stopped, as the machine skill's Trial boots asks. The trial boots the branch head that the manager's go names; this note reads the branch at 3374f084e.

### The GPU

* Every program of the step draws through Mesa 25.0.7's Crocus as an ordinary user: Weston's GL renderer, Chromium's GPU process through ANGLE's GL back end, Firefox's WebRender and WebGL, Xwayland's glamor, `glxinfo`, `glmark2` and WineD3D. Crocus makes the same calls whichever program drives it: GEM objects, their maps and domains, contexts, EXECBUFFER2, waits, syncobjs, and PRIME export and import within the one device, which Weston uses for its clients' buffers. 78-5c's four trials ran these as root, IGT's `prime_self_import` and `gem_userptr_blits` among them, and 78-6c's ran Crocus as an ordinary user beside nine GPU hangs, each recovered by an engine reset.
* An ordinary user's batch goes through 78-8b's command parser, which refuses what Linux's refuses, and a refused batch never reaches the chip. 78-6c matched every result of IGT's `gen7_exec_parse` with Linux's. The aliasing PPGTT keeps a batch inside what is bound.
* A batch that never ends is reset by the heartbeat after 5 to 7.5 s, then the whole GPU, then the GPU is wedged and its requests fail with EIO; 78-6c ran that path on this machine. A reset in this trial is recorded and the run goes on; a wedge ends it.
* Changed on the GPU's path since 78-6c's second trial kernel, and so run here first: d9f75ceb7, the wait for ring room no longer moves the ring's head itself, and leaves it to retirement, so the driver no longer counts as free the commands the chip has not read; 9afa63a93, the error state's text; 8277d3ba6, 88d127e76 and 15a8aac02, the fences' names, callback lists and a commit's fence count, under the big lock with interrupts masked where a signal can come from the interrupt; cb0cd11c7 and 939a344ca, DRM's event queue and GETCONNECTOR's lock; fdab6e0b3, debugfs's crtc directories. Each is bookkeeping in memory; none writes a register or adds a wait on the chip.

### The display

78-6c booted with `rach2.i915.disable_display`, so the display's code last ran on the chip in 78-10d's trial. This trial binds with the display on, as the release will. What the bind runs:

* Writes: the display's chicken registers of Linux's `hsw_init_clock_gating` and `lpt_init_clock_gating` (8f82a0143), read-modify-writes with no wait, before the readout. Checked line by line against Linux 6.12's `intel_clock_gating.c:467-491` and `:306-319` and the offsets and bits of its `i915_reg.h`:

| Linux 6.12 | Register | Bit | Rach2 |
|---|---|---|---|
| WaFbcAsynchFlipDisableFbcQueue, pipe A | `CHICKEN_PIPESL_1(A)`, 0x420b0 | `HSW_FBCQ_DIS`, 22 | the same |
| WaPsrDPAMaskVBlankInSRD | `CHICKEN_PAR1_1`, 0x42080 | `HSW_MASK_VBL_TO_PIPE_IN_SRD`, 15 | the same |
| WaPsrDPRSUnmaskVBlankInSRD, each pipe | `CHICKEN_PIPESL_1(A to C)`, 0x420b0, 0x420b4, 0x420b8 | `HSW_UNMASK_VBL_TO_REGS_IN_SRD`, 15 | the same, over `I915_NUM_PIPES`, 3 |
| `HAS_PCH_LPT_LP` | `SOUTH_DSPCLK_GATE_D`, 0xc2020 | `PCH_LP_PARTITION_LEVEL_DISABLE`, 12 | under a ULT or ULX part, which the HD 4400 0x0a16 is and which has the LPT-LP PCH |
| WADPOClockGatingDisable | `TRANS_CHICKEN1(A)`, 0xf0060 | `TRANS_CHICKEN1_DP0UNIT_GC_DISABLE`, 4 | the same |

  Linux's two GT registers of `hsw_init_clock_gating`, `GEN7_SQ_CHICKEN_MBCUNIT_CONFIG` and `GAM_ECOCHK`, are among the GT's workarounds of 67cbfec4a, which 78-6c ran: `workarounds: applied: 3 of the GT and 6 of rcs0, 0 lost`. Linux writes all of these at every boot of Debian on this machine.
* Reads: the PLLs are set up before the readout (894a0cd1d), as Linux's `intel_shared_dpll_init`; `intel_dpll_init` reads `FUSE_STRAP3` and each PLL's control register and writes nothing.
* The rest of the adoption is 78-10d's: the readout, the panel power sequencer's delays, the AUX messages to the panel and the watermarks, with the waits that note lists, each bounded and logged at its bound.
* On a commit only: the scanout's binding above the aperture (aab78dbab), the remapped view of a wide framebuffer (f1289a374, a67714b3e), the cursor's latch (9f60e4c05) and the mode checks (89d250612, which only refuse). The step makes no mode set and shows no plane: Weston is headless and every program draws off-screen. The only commits are the console's, of the firmware's framebuffer, which is kept in the GTT where the firmware left it.
* What a fault of the display costs: a dark or frozen panel does not stop the processor, SSH still answers, and the put-back reboot gives the firmware's picture back.

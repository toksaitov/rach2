# 78-6c: GPU hangs, RC6 and the parser on the Lenovo

The task's review of the reset and power code against Linux 6.12, what it found and fixed, and the trial it prepares on the Lenovo's HD 4400: the nine piglit tests that hung the GPU under Linux, beside an ordinary user's Crocus; IGT's `gen7_exec_parse` and `gem_reset_stats`; and RC6's residency at idle. The trial's results go at the end.

## Review note (78-6c.1)

Read against Linux 6.12.115's `drivers/gpu/drm/i915`: `gt/intel_reset.c`, `gt/intel_engine_heartbeat.c`, `gt/intel_ring_submission.c`, `gt/intel_gt.c`, `gt/intel_workarounds.c`, `gt/intel_rc6.c`, `intel_pcode.c` and `intel_clock_gating.c`, beside `i915_reset.c`, `i915_hangcheck.c`, `i915_ring.c`, `i915_rc6.c` and `i915_rps.c`.

### GDRST

* `gdrst` is `gen6_hw_domain_reset`: the domain's bits written to `GEN6_GDRST`, a wait of 2 ms until they read clear, both done twice, then 50 us. The domains are Linux's: `GEN6_GRDOM_RENDER`, `MEDIA`, `BLT` and `VECS` for the four rings, `GEN6_GRDOM_FULL` for the chip.
* An engine's reset is `__intel_engine_reset_bh` with the legacy ring's `reset_prepare`, `reset_rewind` and `xcs_resume`: the ring stopped, a stop that times out forgiven; the domain reset; the first request not completed made guilty, its payload turned to `MI_NOOP`; the ring started at its head. A domain that does not reset falls to the chip's reset, as `intel_gt_handle_error` does.
* The chip's reset is `intel_gt_reset` with `do_reset`: `GEN6_GRDOM_FULL` tried up to three times one after another, as `__intel_gt_reset` does for every engine, and three more such rounds after 10, 20 and 30 ms; the fences written back; the engines resumed; a chip that does not reset wedged. A round used to try once, four tries in all where Linux makes twelve; it now tries three times, and `i915_reset_hosttest.c`'s wedge row counts them.
* One difference stays: Linux writes `GEN6_GDRST` and waits under its register lock with interrupts off, so that no other register access falls between. Rach2 holds forcewake and runs under the big kernel lock, as every other caller of the GT's registers does, and takes the device's interrupt as it comes, whose handlers read and acknowledge the identity registers and write no register of a ring.

### The pcode mailbox

* `pcode_rw` is `__snb_pcode_rw`: `-EAGAIN` when `GEN6_PCODE_READY` is still set, the two data registers written, the command written with the ready bit, a wait for the bit to clear, the data read back for a read, and the status decoded as `gen7_check_mailbox_status` does, code by code.
* A read waits Linux's 500 us and then 20 ms. A write waits the same 20.5 ms, where Linux's `snb_pcode_write` gives up after the 500 us; the longer bound fails nowhere that Linux's passes, and every wait is bounded.
* Linux takes `sb_lock` around a command; Rach2's callers, the bind and the frequency's code, run under the big kernel lock.

### RC6

* `i915_rc6_enable` writes `gen6_rc6_enable`'s values in its order: the three wake rate limits, the evaluation interval 125000, the idle hysteresis 25, each engine's `RING_MAX_IDLE` 10, `GEN6_RC_SLEEP` 0, and the thresholds 1000, 50000, 150000 and 64000; it reads `GEN6_PCODE_READ_RC6VIDS`, which Linux corrects only on graphics version 6; the control word is RC6 with the hardware's timers and `EI_MODE(1)`, Haswell having no RC6p.
* Parked, `GEN6_RC_CONTROL` holds RC6 alone and `GEN6_RC_STATE` asks for it; unparked, the control word again, as `intel_rc6_park` and `intel_rc6_unpark`.
* The residency is `GEN6_GT_GFX_RC6` in units of 1.28 us, accumulated over the 32-bit wrap, as `intel_rc6_residency_ns` does.
* The RC6 registers are outside the reset domains: Linux does not write them again after a reset, and neither does Rach2. The trial reads the residency before and after the hangs.

### No workarounds

The review found one more fault, the larger. Linux writes three lists to a Haswell at load and again after resets, and Rach2 wrote none of them; 78-4b's note had left them for later, and no task took them up. The chip ran on its power-on values, which Linux never runs Mesa on. The fix, in `i915_ring.c`, `i915_reset.c` and `intel_display.c`:

| Linux | Registers | When Linux writes them | Rach2 now |
|---|---|---|---|
| `hsw_gt_workarounds_init` | `HSW_SCRATCH1` = L3 data atomics off; `HSW_ROW_CHICKEN3` masked: L3 global atomics off; `GEN7_FF_THREAD_MODE` with `GEN7_FF_VS_REF_CNT_FFME` cleared | `intel_gt_init_hw`: at load, after a reset of the chip | `i915_gt_init_hw`, at the same two points |
| `intel_gt_init_hw` | `HSW_MI_PREDICATE_RESULT_2` = lower slice disabled on a GT2; `HSW_IDICR`'s hash mask when the part has eDRAM | the same | the same |
| `rcs_engine_wa_init` | `MI_MODE` masked: asynchronous flip performance off; `GFX_MODE` masked: explicit TLB invalidation and replay mode; `CACHE_MODE_0_GEN7` masked: HiZ raw stall optimization on, RC operational flush off; `CACHE_MODE_1` masked: pixel subspan collection off; `GEN7_GT_MODE` masked: WIZ hashing 16x4; `HSW_HALF_SLICE_CHICKEN3` masked: sample C performance | `intel_engine_resume`: at load, after the engine's reset and the chip's | the render ring's start, `i915_ring_resume`, which runs at the same three points |
| `hsw_init_clock_gating`, the GT's part | `GEN7_SQ_CHICKEN_MBCUNIT_CONFIG` with `SQINTMOB`; `GAM_ECOCHK` with `HSW_ECOCHK_ARB_PRIO_SOL` | once, at load | `i915_gt_init`, once |
| `hsw_init_clock_gating` and `lpt_init_clock_gating`, the display's part | `CHICKEN_PIPESL_1(A)` with `HSW_FBCQ_DIS`; `CHICKEN_PAR1_1` with `HSW_MASK_VBL_TO_PIPE_IN_SRD`; each pipe's `CHICKEN_PIPESL_1` with `HSW_UNMASK_VBL_TO_REGS_IN_SRD`; `SOUTH_DSPCLK_GATE_D` with `PCH_LP_PARTITION_LEVEL_DISABLE` on a low-power PCH; `TRANS_CHICKEN1(A)` with `TRANS_CHICKEN1_DP0UNIT_GC_DISABLE` | once, at load | `intel_display_init`, once |

Each workaround with a read mask is read back, as Linux's `wa_verify`; one the chip did not keep is logged as `i915: workarounds: NAME: lost` and counted. The bind logs `i915: workarounds: applied: 3 of the GT and 6 of rcs0, 0 lost`. Linux's one context workaround of graphics version 7, `INSTPM`'s forced ordering, was already in the default context image; the comment there named two of the engine's as context workarounds, which is corrected.

`tests/host/i915_reset_hosttest.c` has the row: the model's render and chip resets now put these registers back to their power-on values, and the row finds both lists standing after the bind, the engine's after an engine reset, both after a chip reset, and a workaround the model does not keep logged and counted. With the chip reset's call taken out the row fails. `tests/host/i915_trial_hosttest.c`, the bind as the Lenovo's firmware leaves the chip, allows the new registers and no others; its count of pages still live after first light had stood at 10 since the video rings and the PPGTT came, and is 21.

The display's part is not on this trial's path, which binds under `rach2.i915.disable_display`; its first run on the Lenovo is the next boot with the display, the stack's checkpoint or 78-12b.

### i915_exec_hosttest's ring rows (78-6c.4)

The rows for the video rings failed from the commit that added them, 386b88374. The cause was in the test's chip: it took an MI command's length from the low eight bits, so the video ring's invalidating flush, `MI_FLUSH_DW` with `MI_INVALIDATE_BSD` in bit 7, which the driver emits as Linux's `gen6_emit_flush_vcs`, was read as 131 dwords and the chip passed over the `MI_BATCH_BUFFER_START` behind it. The chip now reads the low six bits, as `i915_model_ring.c` does, and the test prints `ok`. The driver's commands were Linux's throughout.

### The parser as an ordinary user

IGT 2.0 has the parser's test as `gen7_exec_parse`, not `gem_exec_parse`. No IGT test of the device runs as an ordinary user, on Linux either: the first open of an i915 device in `drm_open_driver` writes debugfs's `i915_gem_drop_caches` and asserts that the write went through. The test runs as root on both systems; its batches are not secure, so they pass the parser as an ordinary user's do, and the registers it expects only a master to write are checked from its master descriptor. The ordinary user in this trial is Crocus under uid 1000, every batch of which passes the parser, and `gem_reset_stats`' children that give up root.

## Readiness

Why the trial's new paths cannot leave the machine stopped, as the machine skill's Trial boots asks. The trial boots this task's head: the milestone branch as merged at b044727d1, with this task's commits.

* The workarounds are the one path this task adds to the bind. They are register writes with no wait: the GT's under the forcewake reference that `i915_gt_init` already holds for the rings' start, before the rings start, and the render engine's first in the ring's start. Each register, bit and order is Linux's, as the table above gives them, taken line by line from `intel_workarounds.c`, `intel_gt.c` and `intel_clock_gating.c`; Linux writes the same values to this machine at every boot of its Debian. The read back only logs. A register that does not keep its value changes no later step.
* After a reset the same writes run again, under the forcewake the reset holds: the engine's in `i915_ring_resume`, the GT's in `i915_reset_gt` between the fences and the engines.
* The host tests, run alone at 687093ff1, the last commit that changes the kernel: `i915_reset_hosttest.c` with the workaround row and the wedge row's twelve tries, `i915_trial_hosttest.c`, which runs the trial's bind whole against the model as the firmware leaves the chip and finds no wait at its bound and no write outside its list, and `i915_exec_hosttest.c`: `ok` each.
* Engine resets have run on this machine: the second trial of 78-5c logged eight, of rcs0 and bcs0, each recovered, the tests after them and both piglit parts run on the same boot. New here are a reset of a ring that a 3D program hung, resets of vcs0 and vecs0 through `GEN6_GRDOM_MEDIA` and `GEN6_GRDOM_VECS`, bans, and, if a domain should not reset, the chip's reset and the wedge. Every wait on these paths is bounded: the ring's stop 100 ms, the domain's reset 2 ms twice, the chip's twelve tries of 2 ms with 60 ms between their rounds, the ring's start 5 ms. A reset that fails wedges the GPU: every request fails with `EIO`, programs get errors, and the processor, the disk and SSH go on, so the put-back step still runs.
* A program that waits on a hung GPU sleeps interruptibly and can be killed; the heartbeat runs from the submission worker and from each waiter's one-second slice, so a hang is found whether or not the worker runs.
* The parser's test submits batches the parser must refuse; a refused batch never reaches the chip. Those it must pass are stores and register loads from Linux's tables, which Crocus has used on this machine since the first trial.
* The display: under `rach2.i915.disable_display` the bind returns before `intel_display_init`, so the display's part of the clock gating does not run, no display register is written and the console stays on the firmware's framebuffer.
* Merged on the GPU's path after the fourth trial of 78-5c ran, and so run here unless a later boot ran them: 9bbdad230 (a wedge takes back the requests the chip never had, the wait for ring room, the 10 s bound on another driver's fence, forcewake while the error registers are cleared), e3db9f479 (`i915_wedged`'s engine ids, the error state's size in /sys, the debugfs files' locking) and 6903218d5 (the release and bring-up through /sys, which nothing in this trial calls). The first is on the reset's path and has `i915_reset_hosttest.c`'s rows of the wedge and of the fence that never signals.
* Not tried in QEMU: the fake chip reads no batch, so nothing hangs there as it does on the chip, and the host tests run the reset's path against the model.
* What is left: a fault that stops the processor on a path not reviewed here would leave the machine down until the owner is home, as for any trial. To tell where, the step reads the log after the boot, runs `eglinfo` alone, then the hang script, whose triggers come one at a time with the kernel's lines saved after each, and IGT last.

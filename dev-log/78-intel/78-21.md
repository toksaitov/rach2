# 78-21: lockup detection on the Lenovo

The soft-lockup, hard-lockup and hung-task detectors, as Linux 6.12's `kernel/watchdog.c`, `kernel/watchdog_perf.c`, `kernel/watchdog_buddy.c` and `kernel/hung_task.c`, with the hard-lockup check driven by a core counter of unhalted cycles that raises an NMI each `watchdog_thresh` seconds (`rach2/sys/arch/x86/pmu.c`). QEMU proves all three, under KVM with AMD's counters and under TCG with the buddy check (`machine.smp.softlockup`, `hardlockup`, `hungtask` and `lockups`). This records the one step only the Lenovo could show: Intel's architectural counter on its Core i3-4030U (Haswell), whose answers the host test `tests/host/pmu_hosttest.c` had taken from the Lenovo's Linux dmesg alone.

## Readiness

* The register sequences follow Linux 6.12's `intel_pmu_init`, `x86_perf_event_set_period` and `intel_pmu_handle_irq`. These cover the full-width counter `MSR_IA32_PMC0` when `PERF_CAPABILITIES` bit 13 is set, the event select 0x53003C written last, and the acknowledge through `GLOBAL_OVF_CTRL` with the reload before `APIC_LVTPC` goes back to NMI.
* Event selects 1 to 3 are zeroed and `GLOBAL_CTRL` is set to 1, so that a counter the firmware left running cannot raise an NMI that the handler would not place.
* Every wait is bounded, and the counter's APIC entry stays masked until the NMI handler claims its NMIs.
* The manager gave the go on the issue for build 743e16f69.

## The step

On 11 November, 18:48 to 18:52 (UTC+6), by the owner's loop m3 under the Lenovo's lock. The x86-64 kernel of 743e16f69, 3,936,728 bytes with SHA-256 `1ae5569f...ccffb3`, was staged in the candidate slot with `bootctl kernel` and booted once with the release's line. Release 12 (bb151e3ba), kernel `0effe5ac...`, was in both slots before; `machine_identity.sh` found it in both before and after.

This boot sent no log to the Mac. The kernel at 743e16f69 predates `netconsole=` (78-20) and has only the raw frames of ether type 0x88b5, which the Mac cannot read without root. The go named this build, and review round 79z was reading the milestone head that carries 78-20. The record is the machine's own dmesg, read over SSH.

## Results

Passed. The machine answered SSH 25 s after each reboot and throughout every step, and played nothing.

1. The probe: `nmi_watchdog: counter: intel arch version 3, 48 bits, 1895 MHz`, then `nmi_watchdog: enabled: permanently consumes one hw-PMU counter`. `/proc/sys/kernel/nmi_watchdog` read 1. Uptime was 15.81 s and then 75.88 s, so the machine ran on for a minute with all four processors' counters raising their NMIs.
2. With `watchdog_thresh` 2, `hung_task_timeout_secs` 3 and `hardlockup_all_cpu_backtrace` 1, `echo soft 15 > /sys/kernel/debug/test_lockup` gave `watchdog: BUG: soft lockup - CPU#3 stuck for 5s! [sh:119]` at 90.563 s, with the registers and a `Call Trace:`, and again at 10 s and 15 s. These are Linux's `watchdog_timer_fn` reports.
3. `hard 15` gave `watchdog: watchdog detected hard LOCKUP on cpu 3` at 107.479 s. It was followed at once by `watchdog: CPU: 3 PID: 139 Comm: sh` and `RIP:`, the counter's own NMI (Linux's `watchdog_hardlockup_check`). Then came `nmi_backtrace: sending NMI from CPU 3 to CPUs 0-2:` and an `NMI backtrace for cpu` record for each of CPUs 0, 1 and 2. The SSH command returned 16 s after it was sent.
4. `hung 15` gave `hung_task: INFO: task sh:153 blocked for more than 3 seconds.` at 137.614 s, with `task:sh state:D pid:153 tgid:153 ppid:152 wchan:wq_wait_event_nointr` and its trace, every 3 s while the shell slept. This is Linux's `check_hung_task`.

The kernel's ring had dropped the soft lockup's records by the time the hung task ended, so the log is in two files. [`78-21/lenovo-dmesg-soft-hard.txt`](78-21/lenovo-dmesg-soft-hard.txt) was read after step 3 and [`78-21/lenovo-dmesg-hard-hung.txt`](78-21/lenovo-dmesg-hard-hung.txt) after step 4.

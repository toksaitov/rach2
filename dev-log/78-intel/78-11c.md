## Review note (78-11c.1)

The paths hasvk reaches that no earlier trial ran on the chip, read against Linux 6.12's `drivers/gpu/drm/i915/gem/i915_gem_execbuffer.c`, `drivers/gpu/drm/i915/i915_ioctl.c` and `intel_uncore.h`, and against hasvk in Mesa 25.0.7, `src/intel/vulkan_hasvk/anv_device.c`. Every call hasvk makes was checked against Rach2 in [78-11a](78-11a.md); this note reads the two that 78-11a added, and what they reach.

### The timeline fences of EXECBUFFER2

`eb_ext_timeline_fences`, `eb_fences_grow`, `eb_timeline_fence` and `eb_signal_fences` against Linux's `parse_timeline_fences`, `add_timeline_fence_array` and `signal_fence_array`:

* The count: Linux refuses more entries than `min(ULONG_MAX / 16, SIZE_MAX / sizeof(*f)) - num_fences` with EINVAL; `eb_fences_grow` refuses the same two overflows with EINVAL, and a total past 2^32 entries with ENOMEM, which Linux's `krealloc` of 160 GiB would give.
* The user ranges: the handles' range, then the values', each EFAULT when not the program's, as Linux's `access_ok`; then the array grown by the new entries, ENOMEM as Linux.
* Each entry in Linux's order: the entry copied (EFAULT), unknown flags EINVAL, the point read (EFAULT), the syncobj looked up (ENOENT), its fence taken; no fence with flags and no `I915_EXEC_FENCE_SIGNAL`, EINVAL; `dma_fence_chain_find_seqno` failing without SIGNAL, EINVAL; no fence and no SIGNAL, a point signalled and collected, left out; a point not 0 with SIGNAL, EINVAL with WAIT, as waiting and signalling one point would break the timeline, and otherwise its chain record allocated now (ENOMEM), since the add after the request cannot fail. The entry keeps the syncobj, the fence, the flags and the point, as Linux's `eb_fence`.
* The wait: `eb_await_fences` awaits every kept fence, whatever its flags, as Linux's `await_fence_array`. A timeline point unwraps to its own fence and each earlier point not yet signalled (`unwrap` in `rach2/sys/dmabuf/fence.c`, Linux's `dma_fence_unwrap`); each leaf is a callback on the request, not a wait in the call; a leaf of the engine's own fence context is skipped, since ring submission keeps one timeline an engine, as Linux's legacy timeline; and another driver's fence is waited for 10 s at most, Linux's `CONFIG_DRM_I915_FENCE_TIMEOUT`.
* The signal: a chain record goes to `drm_syncobj_add_point` with the request's fence and the point, and the syncobj takes it; a binary syncobj's fence is replaced; as Linux's `signal_fence_array`. `drm_syncobj_add_point` links the record after the syncobj's fence, wakes the syncobj's waiters and walks the chain once to let go of signalled points, as Linux's.
* What differs, both recorded by 78-11a: Linux keeps one error variable across the entries ([upstream.md](upstream.md#linux-refuses-a-timeline-fence-with-the-error-of-the-entry-before-it)), where Rach2 judges each entry alone; and Rach2 grows the array before it checks the values' range, so a call with both a bad `values_ptr` and no memory answers ENOMEM where Linux answers EFAULT. hasvk sends neither.

### I915_REG_READ

`i915_reg_read_ioctl` against Linux's `i915_reg_read_ioctl`:

* The allowlist is Linux's one entry for graphics 4 to 12: `RING_TIMESTAMP(RENDER_RING_BASE)`, 0x2358, with its upper half at 0x235c, 8 bytes; the offset's low three bits are the flags. Any other offset, the upper half alone, an offset past 32 bits or a flag other than `I915_REG_READ_8B_WA` is EINVAL, as Linux's.
* With `I915_REG_READ_8B_WA`, which hasvk always passes (`i915_gem_read_render_timestamp` in Mesa's `src/intel/common/i915/intel_gem.c`), `i915_read64_2x32` reads the upper half, then the lower and the upper again until the upper holds still, three tries at most, as Linux's `intel_uncore_read64_2x32` (`loop++ < 2`). Without the flag Rach2 reads the low half and then the high, as 32-bit Linux's `readq`; 64-bit Linux makes one 8-byte read, which its uapi header calls wrong for this register.
* Both under forcewake, as Linux's: `i915_forcewake_get` and `_put`, the same path every register write of the GT has taken since 78-4b's first trial. Linux holds a runtime-PM wakeref; Rach2's i915 never suspends the device.
* `DRM_IOCTL_I915_REG_READ` is 0xc0106471 with `DRM_RENDER_ALLOW`, as Linux's table.
* hasvk calls it once when it opens the device, and advertises `VK_EXT_calibrated_timestamps` only if that read answers (`anv_device.c:283`, `:1791`), so `vulkaninfo`'s extension list shows that the call worked.

### Found while reading

The exec host test's chip model read an MI command's length from eight bits; Linux's command parser reads six for every MI command on Gen7. The video ring's `MI_FLUSH_DW` sets `MI_INVALIDATE_BSD`, bit 7, so the model took a three-dword flush for 131 dwords and never reached the batch start, and five rows of the video rings failed (`rings: BSD starts it on vcs0` and the four after it), at the commit that added them as at the milestone's head. The driver was right; the model now uses `MI_OPCODE` and `MI_LENGTH` as `i915_model_ring.c` does, and every row passes.

## Readiness

Why the trial's new paths cannot leave the machine stopped, as the machine skill's Trial boots asks.

* What the chip can reach is 78-5c's: the aliasing PPGTT, so a batch reaches only what is bound, the scratch page elsewhere; and every batch of a root program without `I915_EXEC_SECURE`, hasvk's among them, goes through 78-8b's command parser, as Crocus's did in 78-5c's four trials.
* `I915_REG_READ` makes three to seven reads of the render ring's timestamp with the flag, two without, and one forcewake request and release; forcewake's waits are bounded, 50 ms for each acknowledgement and 5 ms for the GT's threads, and it takes no other lock than the uncore's spin lock, as before.
* The timeline extension waits for nothing in the call: it looks up syncobjs, takes references and allocates. What it adds to a request are fence callbacks; a request whose fence never signals stays queued, which blocks its engine's later requests and the programs that wait on them, never the processor: every wait of a program on a syncobj (`waiter_sleep` in `drm_syncobj.c`) ends at a signal or its deadline, a wait on a GEM object or a request ends at a signal, and another driver's fence is given up after 10 s.
* A batch that never ends is reset: the heartbeat resets the engine through its domain of GDRST after 5 to 7.5 s, waited for 2 ms at most, twice, then the whole GPU, then the GPU is wedged and its requests fail with EIO (78-6a). That path has not run on the Lenovo yet; 78-6c is its trial. Under Linux no case of the sample timed out or crashed, and its two piglit hang triggers are not in this list. A reset in this trial is recorded and the run goes on; a wedge ends it.
* What has changed on the chip's paths since the last trials, 78-10d's and 78-5c's fourth, which came after it: the wedge's taking back of requests not yet given to the chip, the ring-room wait, the bound of 10 s on another driver's fence and forcewake held while the error registers are cleared (9bbdad230); pins that look again after a sleep (25fad35ae); the context held across SETPARAM (861de5525); the bind's undoing when it fails (b143b0bbc); the PCI binding's links (36fc29ad2); and the debugfs files (e3db9f479, b5ceb5318). Since then, too: a fence's mark of signalled and its callbacks' list change with interrupts masked, the callbacks run after (37f2083fe), which shortens no wait and adds none; a syncobj wait on no handles answers 0, unknown TRANSFER flags are refused and a TIMELINE_SIGNAL of point 0 chains (0181d53e9); a sync file's name comes from its fence (39a3232f4); and the xHCI and USB HID input changes of the display milestone, which run at every boot on the Lenovo's keyboard and mouse whatever the trial runs. The display's changes do not run under `rach2.i915.disable_display`.
* Host tests, each run alone at the milestone's head with this task's fix to the model: `tests/host/i915_exec_hosttest.c`, whose `timeline_points` and `timeline_refusals` run EXECBUFFER2 with the extension against the chip model, waiting for and signalling timeline points through a request, and `wsi_sync_files` the sync files of a buffer around EXECBUFFER2: `i915-exec-test: ok`; and `tests/host/i915_ctx_hosttest.c`, whose `row_reg_read` reads the timestamp across a carry under forcewake and checks the refusals: `i915-ctx-test: ok`.
* Not tried in QEMU: the fake chip runs no batch and hasvk binds only Intel's PCI devices, so nothing there would show more than the host tests.
* What is left: a fault that stops the processor on a path not read here would leave the machine down until the owner is home, as for any trial. To tell where, the step reads the log after the boot, runs `vulkaninfo` alone first, then the smoke set in one process, then the sample in four, reading the log between them.

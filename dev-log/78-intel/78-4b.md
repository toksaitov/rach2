# 78-4b: first light on the Lenovo

The first trial of the Intel driver on the Lenovo's HD 4400, silent: the bind under `rach2.i915` (forcewake, the display power well, stolen memory, the global GTT, the interrupts, the render and blitter rings), then first light under `rach2.i915.firstlight`, one `MI_STORE_DWORD_IMM` from the render ring read back by the processor, with the firmware's display left as it was. Nothing plays and nothing is drawn beyond the boot's console; the screen is not taken.

## Review note (78-4b.1)

The six files the trial runs, read line by line against Linux 6.12's `drivers/gpu/drm/i915/` at tag v6.12. Three differences were fixed on `task/2648` before this note; the rest are listed with why they do not matter to the trial.

### i915_uncore.c: forcewake and the GT FIFO

* `i915_uncore_init` as `intel_uncore_init_mmio` and `forcewake_early_sanitize`: `FPGA_DBG`'s unclaimed bit cleared when set, `GTFIFODBG` written back when nonzero (`gen6_check_for_fifo_debug`), `FORCEWAKE_MT` written `_MASKED_BIT_DISABLE(0xffff)` (`fw_domain_reset`, WaRsClearFWBitsAtReset), the FIFO's count read from `GTFIFOCTL`.
* A get as `fw_domains_get_with_thread_status` on Haswell (`FORCEWAKE_MT`, `FORCEWAKE_ACK_HSW`): wait for the ack's bit 0 to clear, 50 ms (`FORCEWAKE_ACK_TIMEOUT_MS`); write `_MASKED_BIT_ENABLE(FORCEWAKE_KERNEL)`; wait for the ack, 50 ms; wait for `GEN6_GT_THREAD_STATUS_REG & 0x7` to read 0, 5 ms, a timeout counted (WaRsForcewakeWaitTC0). A put writes `_MASKED_BIT_DISABLE(FORCEWAKE_KERNEL)`. Linux logs an ack timeout and goes on; Rach2 fails the get by name and withdraws the request, so no read is made of a GT that did not wake.
* The FIFO as `__gen6_gt_wait_for_fifo`: the cached count used until it falls to the reserve of 20, then `GTFIFOCTL`'s free entries read until above it, 10 ms (`GT_FIFO_TIMEOUT_MS`), the count less one kept.
* Fixed: the ranges. Linux 6.12 reads Haswell's registers through `__gen6_fw_ranges`, one range, 0x0 to 0x3ffff, and writes through `gen6_write`, which waits on the FIFO when `NEEDS_FORCE_WAKE`, below 0x40000 or from 0x116000. Rach2 took forcewake and the FIFO below 0x40000 and from 0x1c0000, an older bound. It now wakes the GT for reads below 0x40000 alone and waits on the FIFO below 0x40000 and from 0x116000. The trial's path touched nothing in either changed range through these accessors, so this changes no access of the trial.
* Not done, as on Linux's path for this chip: the forcewake timer that keeps a reference for a millisecond after the last put. Rach2 drops it at once; the cost is extra acks, not a wrong value.

### i915_power.c: the display power well

* `hsw_power_well_sync_hw`: when the BIOS's request (`HSW_PWR_WELL_CTL1`) is set, the driver's (`CTL2`) is set if clear and the BIOS's cleared. `hsw_power_well_enable`: the request set by read-modify-write and the state bit waited for, 1 ms (`enable_timeout` 0 gives 1 ms). `hsw_power_well_requesters` reads bits of CTL1, CTL3 and CTL4. Same registers, same order.
* The Lenovo's firmware leaves the well on at the BIOS's request (`firmware-dump.txt`: CTL1 0xc0000000, CTL2 to CTL4 0x40000000), so the bind's takeover moves the request and the well stays on throughout; the trial never releases it. `hsw_power_well_post_enable`'s VGA I/O reset (`intel_vga_reset_io_mem`) is not done; it matters after the well comes on from off, which does not happen here.
* The panel runs on the eDP transcoder from pipe A always on (`TRANS_DDI_FUNC_CTL_EDP` 0x82200000, input bits 14:12 zero), which Haswell keeps outside the well, so the well's state could not blank the panel in any case.

### i915_stolen.c: stolen memory

* The range from `SNB_GMCH_CTRL`'s GMS (32 MiB units) and BDSM (`INTEL_BSM`, mask 0xfff00000), as `gen6_stolen_size` and `intel_stolen_base`; the firmware's part from `GEN6_STOLEN_RESERVED` as `gen7_get_stolen_reserved` (enable bit 0, base bits 31:18, size 1 MiB or 256 KiB by bit 5). Register values checked against `i915_reg.h`.
* Read only: the bind writes no register here and maps none of stolen memory. On the Lenovo it finds 0xaba00000 to 0xaf9fffff, inside the GPU's RMRR, 0xab800000 to 0xaf9fffff.

### i915_gtt.c: the global GTT

* Size from `SNB_GMCH_CTRL`'s GGMS (2 MiB of entries, 2 GiB of address space), the aperture from `HSW_MSAC` (256 MiB), entries at BAR 0 + 2 MiB mapped write-combining (`ggtt_probe_common`'s `ioremap_wc`).
* Entries as `hsw_pte_encode`: valid bit, address bits 31:12 and 38:32 in 10:4, `HSW_WB_LLC_AGE3` for a cached level, nothing for `I915_CACHE_NONE`. Linux's `HSW_WT_ELLC_LLC_AGE3` for write-through is folded into write-back; nothing on this path asks for write-through.
* Invalidation as `gen6_ggtt_invalidate`: `GFX_FLSH_CNTL_GEN6` written `GFX_FLSH_CNTL_EN` and read back, under the register lock.
* The firmware's framebuffer kept, as Linux's initial plane takeover reserves it before `init_ggtt` clears the holes: pipe A's enabled plane gives `DSPSURF` 0, stride 5504 and 768 rows, so entries 0 to 0x407 (4128 KiB) are kept and never written. Every other entry is written to the scratch page. On the Lenovo that unmaps the rest of stolen memory, entries 0x408 to 0x3fff, which the firmware mapped and nothing scans out, and overwrites 0x4000 up, which the dump read as uninitialised all ones with the valid bit set.

### i915_irq.c: interrupts

* The reset as `ilk_irq_reset`, `gen5_gt_irq_reset` and `ibx_irq_reset`: DE, then GT and PM, then SDE, each `GEN3_IRQ_RESET` (IMR all ones, posting read, IER 0, IIR all ones twice with posting reads); `GEN7_ERR_INT` all ones; Haswell's `EDP_PSR_IMR` and `EDP_PSR_IIR` all ones; `SERR_INT` all ones. It runs before the message is enabled.
* The handler as `ilk_irq_handler`: DEIER's master bit off, SDEIER 0, then GTIIR, DEIIR (SDEIIR behind the PCH event, written back after its handlers, as `cpt_irq_handler`) and PMIIR each read, written back and dispatched; DEIER and SDEIER restored. A bit with no handler is masked and disabled once, so a source the firmware left latched cannot raise messages without end.
* After the bind the only enables are DEIER's master bit and GTIER's render and blitter user interrupts, and every mask is set. Linux also enables and unmasks the L3 parity interrupt on Haswell (`irq_keep_mask`); Rach2 has no handler for it yet and keeps it off.
* Register values: 120 constants of `i915_reg.h` compared by name with Linux 6.12's headers by script, none different; the parameterised ones (`RING_*`, `TRANSCONF`, `TRANS_DDI_FUNC_CTL`, `DSP*`, `HSW_PWR_WELL_CTL*`) by hand.

### i915_ring.c: the rings

* The start as `xcs_resume`: `stop_ring` (head to tail, posting read, `RING_CTL` 0, head and tail 0, head checked, tried twice as `reset_prepare`); `set_hwsp` to `RENDER_HWS_PGA_GEN7` 0x4080 or `BLT_HWS_PGA_GEN7` 0x4280 with a posting read; `flush_cs_tlb` (warning when `MODE_IDLE` is clear, `INSTPM` written `_MASKED_BIT_ENABLE(INSTPM_TLB_INVALIDATE | INSTPM_SYNC_FLUSH)`, `INSTPM_SYNC_FLUSH` waited clear, 2 ms); posting read of the head; `RING_START`; `set_pp_dir`, which writes nothing without a PPGTT; head and tail 0, posting read; `RING_CTL` with `RING_CTL_SIZE` and `RING_VALID`, waited for, 5 ms; `STOP_RING` cleared.
* Rach2 also requests `STOP_RING` and waits for `MODE_IDLE`, 100 ms, before the first `stop_ring`, as `intel_engine_stop_cs` in `reset_prepare`; a ring whose head equals its tail is forgiven a timeout, as Linux. On the Lenovo both rings are off (`RCS_CTL` 0), so the stop finds them idle.
* Fixed: `set_hwstam`. Linux masks every status-page write but leaves the render ring's bit 0 unmasked on graphics version 6 and up; Rach2 masked all of the render ring's. Now as Linux: `RING_HWSTAM` of rcs0 0xfffffffe, of bcs0 0xffffffff. The status page's dword 0 then takes the render ring's interrupt status; the breadcrumb is at dword 0x40.
* Status pages and rings in kernel pages mapped through the GTT at `HSW_WB_LLC_AGE3`, as Linux's internal objects on an LLC part, so the chip snoops what the processor writes. They take GTT space from the top down: rcs0's status page at 0x7ffff000 and ring at 0x7fffb000, bcs0's at 0x7fffa000 and 0x7fff6000.
* Differences left for later tasks: the breadcrumb is `MI_STORE_DWORD_INDEX` and `MI_USER_INTERRUPT`, where Linux 6.12 writes the seqno with a `PIPE_CONTROL` on rcs0 (`gen7_emit_breadcrumb_rcs`) and `MI_FLUSH_DW` on bcs0, so that it follows the render caches' writes; first light writes with an MI command, so no cache stands between, and 78-5a's requests take Linux's form. No hardware context is loaded (`CCID` stays 0) and no `MI_SET_CONTEXT` is sent, as before 78-5a; the GT workarounds of `intel_gt_init_hw` and MOCS are not applied, and none of them governs an MI store.

### i915_firstlight.c

* `MI_STORE_DWORD_IMM_GEN4 | MI_USE_GGTT`, 0, the GTT offset of a fresh page, 0x1915f157; then the breadcrumb; `RING_TAIL` written after a fence. Gen7's render ring may store a dword (`intel_engine_can_store_dword`). The processor polls the status page, 50 ms at most, reads the value back, then waits 10 ms at most for the user interrupt, taken by the handler or latched in `GTIIR`. The page is unmapped and freed after, success or failure.

## Readiness

Why the trial's new code cannot leave the machine stopped, as the machine skill's Trial boots asks.

* Register sequences: as the review note above, against Linux 6.12, with the three differences fixed.
* Every wait is bounded and ends with a named error: forcewake's acks 50 ms each and its threads 5 ms, the FIFO 10 ms, the power well 1 ms, a ring's stop 100 ms, its TLB flush 2 ms, its start 5 ms, room in a ring 10 ms, first light's breadcrumb 50 ms and its interrupt 10 ms. Each spins on the processor's counter in steps of at most 1 ms (`i915_wait_for`, `i915_wait_until`). The bind's one long loop writes the GTT's 524,288 entries once.
* Interrupts: every bank masked, disabled and cleared before the message is enabled; afterwards only the master enable and the two rings' user interrupts are enabled, and those are unmasked only while first light waits. A bit without a handler is masked on its first message. The message goes through the graphics unit's interrupt remapping, which 81-6d.3 proved on both units at boot; this is the first message that unit carries. A message that does not arrive costs only first light's 10 ms wait, and first light then logs `user interrupt latched` instead of `taken`.
* What the chip can reach: the GTT maps the kept framebuffer, the two status pages, the two rings, first light's page and the scratch page, nothing else; VT-d's translation is off for the host's own drivers, as on the release. The rings run only what the driver writes: on the first boot nothing, on the second eight dwords on rcs0.
* The display: no register of the planes, pipes, transcoders, DDI, panel power or backlight is written, and neither are the framebuffer's 1032 GTT entries. The power well stays on. The console keeps drawing where the plane scans out.
* Host test, run alone: `tests/host/i915_trial_hosttest.c` binds the driver through `i915_driver_bind`, as the probe does, to the model seeded from the Lenovo's dump (`firmware-dump.txt`: the power well, the eDP route, the plane and the GTT with all of stolen memory mapped), with `rach2.i915` alone and with `rach2.i915.firstlight`, the processor's interrupts on and off, through a boundary that notes every register and GTT entry written. Each run finds no wait at its bound, no register written outside the GT but the interrupt registers, the GTT's flush and the well's takeover, nothing in the GT but forcewake and the two rings, the framebuffer's entries and the plane, pipe and eDP route as the firmware left them, the well never released, no address reached by the chip but the driver's pages, and every source masked after. `i915-trial-test: ok`. Two mutants fail it as they should: one that forbids the well's takeover write (`register 045400 written`), and one whose GTT keeps no firmware entry (`no write reached the firmware's framebuffer entries`).
* The watchdog is not armed, though 78-4b.2 asked for it. 78-1b found that an expiry leaves the Lenovo down until someone powers it on, under Linux as under Rach2, so an armed watchdog cannot bring the machine back and would turn any boot slower than its timeout into an outage.
* What is left: a fault that stops the processor, which nothing here waits on without a bound, would leave the machine down until the owner is home, as for any trial. To tell such a hang in the bind from one in the GPU write, the step boots twice: first `rach2.i915` alone, read over SSH, then with first light.

## The step

On the Mac, by a loop of the owner's under the Lenovo's lock, in the main clone, after the manager's go on #2648. Silent: nothing plays and nothing is drawn beyond the console; gfxtool only reads. Definitions:

```
mkdir build/flow/lenovo && echo 2648 > build/flow/lenovo/issue
L() { ssh -i krffs/rach2_demo_ed25519 -o BatchMode=yes -o ConnectTimeout=5 -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no -o ServerAliveInterval=5 -o ServerAliveCountMax=3 root@192.168.0.106 "$@"; }
up() { while :; do if ping -c 1 -t 1 192.168.0.106 > /dev/null 2>&1; then echo "$(date +%T) up"; else echo "$(date +%T) down"; fi; sleep 1; done; }
back() { i=0; until L true 2> /dev/null; do i=$((i + 1)); [ $i -ge 180 ] && { echo "no answer"; return 1; }; sleep 2; done; L 'mixer vol 1'; echo "$(date +%T) answered"; }
T=build/worktrees/t2648
```

`back` waits six minutes at most for SSH and sets the volume at once.

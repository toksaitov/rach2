# 78-5c: submission on the Lenovo

The first trial of the Intel driver's buffers and submission on the Lenovo's HD 4400, silent and as root: IGT's buffer and submission tests from `tests/graphics/igt-gem-trial.txt`, two parts of piglit and `eglinfo` on Crocus off-screen, on a trial root of the GNU system booted once from the data partition with `rach2.i915 rach2.i915.disable_display`, and the same IGT list under Debian on p5 as Linux's reference. Step 9 of the discovery run has piglit's reference for the two parts but no IGT buffer test, so Linux's IGT results come from this step's Debian boot.

## Review note (78-5c.1)

The paths the trial runs for the first time on the chip, read against Linux 6.12's `drivers/gpu/drm/i915/` with Haswell's branches taken. Four faults were fixed on `task/2649`, and IGT needed three interfaces it lacked, which were added; the rest match.

### Contexts and the switch

* `MI_SET_CONTEXT` as `mi_set_context` on Haswell: `MI_ARB_ON_OFF | MI_ARB_DISABLE`; for each other engine of the platform, `MI_LOAD_REGISTER_IMM` of its `RING_PSMI_CTL` with `GEN6_PSMI_SLEEP_MSG_DISABLE` set; `MI_NOOP`; `MI_SET_CONTEXT` with the image's GTT offset, `MI_MM_SPACE_GTT`, `MI_SAVE_EXT_STATE_EN | MI_RESTORE_EXT_STATE_EN`, or `MI_RESTORE_INHIBIT` for an image never saved; `MI_NOOP`; the registers again with the bit cleared; `MI_STORE_REGISTER_MEM` of the last of them into the scratch page, Linux's delay; `MI_NOOP`; `MI_ARB_ON_OFF | MI_ARB_ENABLE`.
* Fixed: Rach2 held the blitter's sleep messages alone. Linux counts the engines of the platform, not the engines it drives, and Haswell's mask is 0xf, so it holds the blitter's, the video ring's and the video enhancement ring's, a command of 12 + 4n dwords with n = 3. Rach2 now does the same from the platform's mask, whatever rings it starts.
* The image is 17 pages (`HSW_CXT_TOTAL_SIZE`) at the LLC's level; the default image is recorded with Linux's gen7 context workarounds, as 78-5a's note says.

### Requests, flushes and breadcrumbs

* The invalidate before a batch is Linux's `gen7_emit_flush_rcs`: a `PIPE_CONTROL` that stalls the command streamer at the scoreboard, as the workaround before a state cache invalidate asks, then one that invalidates the TLB and the instruction, texture, VF, constant and state caches with a write to the scratch page. On the blitter it is `gen6_emit_flush_xcs`'s `MI_FLUSH_DW` with `MI_INVALIDATE_TLB` and a store to the status page.
* The flush after a batch is in the breadcrumb, `gen7_emit_breadcrumb_rcs`'s flushing `PIPE_CONTROL` and `gen7_emit_breadcrumb_xcs` with its 32 extra stores, as 78-4b's note left for 78-5a; same dwords, same order.
* The batch start is `MI_BATCH_BUFFER_START` with `MI_BATCH_PPGTT_HSW` and `MI_BATCH_NON_SECURE_HSW` on the render ring and `MI_BATCH_NON_SECURE_I965` on the blitter, Linux's flags. No PPGTT is made yet (78-8a), as in Linux 3.12 with PPGTT disabled, which set the same bit: the chip then translates the batch through the global GTT, whose entries not in use point to the scratch page, so a stray access lands there.
* A root program's batch without `I915_EXEC_SECURE` goes through 78-8b's command parser, reviewed in its own task; IGT's tests submit that way.

### Buffers and their lifetime

* Fixed: an object closed while its batch ran was freed with its bindings as its last handle went, so the GPU could still write pages back in the allocator. Linux keeps a request's bindings active until it retires. 78-8b added the same hold, a reference to each object of the call and the parser's shadow, held by the request until it retires; the merge keeps that one, and a binding of a busy object refuses to be undone (`-EBUSY`): eviction and the shrinker pass over busy objects, and a pin that must move a binding, a change of tiling and userptr's invalidation wait for the object to go idle first, as Linux's unbind waits in `i915_vma_sync`.
* Fixed in the merge: a request that found no room in its ring for its breadcrumb was failed without letting go of that hold, which kept its objects for ever.
* GTT maps, fences and swizzling: the fault path, the fence registers' values and the swizzle read from `MAD_DIMM` match Linux, as `i915_gem_hosttest.c` checks against Linux's selftest `tiled_offset`.
* RC6, the frequency and the pcode mailbox, which the GT's park and unpark run around each burst of work: Linux's values and sequences.

### What IGT needs to open the device

* `drm_open_driver` writes `DROP_RESET_ACTIVE | DROP_RESET_SEQNO | DROP_ACTIVE | DROP_RETIRE | DROP_IDLE | DROP_FREED` to `dri/N/i915_gem_drop_caches` and asserts the write; Rach2 had no such file. It is added as Linux 6.12's `i915_drop_caches_set`, with one difference: `DROP_RESET_ACTIVE` gives the engines Linux's 200 ms, and a GPU still busy then is logged and waited for, since the reset is 78-6a's. IGT finds the directory through `dri/MINOR/name`, which the minors' links give.
* `igt_require_gem` calls `DRM_IOCTL_I915_GEM_THROTTLE`, which answered `EINVAL`. It is added as Linux's `i915_gem_throttle_ioctl`: `EIO` when wedged, otherwise a wait, interruptible, for the file's newest request emitted more than 20 ms ago.
* `gem_mmap__cpu` and gem_mmap's fixture use the legacy `DRM_IOCTL_I915_GEM_MMAP`, which Linux serves on Haswell. It is added as Linux's `i915_gem_mmap_ioctl`: its refusals in Linux's order, then the WB or WC offset mapped from the page `offset` names through the caller's own descriptor of the device, as Linux's `vm_mmap` of the object's file.
* `rach2.i915.disable_display`, Linux's `i915.disable_display`, binds the device without its display, so that the trial leaves the panel, the backlight and the firmware's framebuffer as the firmware left them.

## Readiness

Why the trial's new paths cannot leave the machine stopped, as the machine skill's Trial boots asks.

* What the chip can reach: the global GTT maps the kept framebuffer, the rings, status pages and context images, the objects bound for a batch, a GTT map or a pin, and the scratch page everywhere else. There is no PPGTT, so a batch reaches nothing outside the global GTT. Unprivileged batches pass the command parser, which refuses register writes outside Linux's allowlists.
* No reset: a batch that never ends would leave its requests waiting. The list holds no subtest that hangs the GPU on purpose (of `gem_reset_stats` only `params` and `params-ctx`, and none of `gem_exec_hang`, `gem_eio` or `hangcheck`), and neither piglit part hung the GPU under Linux. The waits that a hung GPU would block, a program's WAIT or THROTTLE, a pin's or a tiling change's wait for idle and `DROP_IDLE`, sleep interruptibly, so a hang stops the test and its program, never the processor: SSH still answers, the hung program can be killed, and the reboot of the put-back step ends it. `DROP_RESET_ACTIVE`'s wait is bounded at 200 ms and logged.
* The display: under `rach2.i915.disable_display` the bind returns before `intel_display_init`, so no register of the planes, pipes, transcoders, DDI, panel power, AUX or backlight is written, the eDP mode set of 78-10 does not run, and the console keeps drawing on the firmware's framebuffer. The device offers no mode setting, and Crocus draws off-screen through the render node.
* The bind, the rings and first light are 78-4b's, which passed on the Lenovo; the OpRegion and VBT are read only.
* Host tests, run alone at the step's commit: `tests/host/i915_ctx_hosttest.c` (the switch with the three engines' messages held, THROTTLE, `i915_gem_drop_caches`), `i915_gem_hosttest.c` (the legacy map), `i915_exec_hosttest.c` (a batch and its target closed while their request runs, kept bound until it retires) and `drm_core_hosttest.c` with `drm_core64` (the legacy map's mmap through the caller's descriptor): `ok` each.
* Not tried in QEMU: the fake chip reads no batch, so the tests that submit would fail there whatever the driver does, and the open path is what the host tests run.
* What is left: a fault that stops the processor on a path not reviewed here would leave the machine down until the owner is home, as for any trial. To tell where, the step reads the log after the boot, runs `eglinfo` alone before IGT, and IGT's tests in the list's order, the busiest last.

# Milestone 46 notes

## Phase 1: the frame map

* QEMU's maps at the five sizes, as the kernel printed them, are in `tests/host/frame_hosttest.c`; the boot's record of the map is what milestone 50 reads off the Lenovo's netconsole. QEMU's map has three fixed holes, the kilobyte at 0x9FC00, the 384 KiB below 1 MiB and the 128 KiB at the end of low RAM, and puts what is above 3 GiB at 4 GiB.
* The frame table is one 32-bit word per frame below the map's top and lives below the window with the other boot tables: 4 MiB on a 4 GiB machine, inside the 32 MiB with the 16 MiB os-real image. A frame the map offers above the window is managed and marked not yet reachable; phase 2 makes it reachable.
* The boot reports managed from the table's count and not from the map's arithmetic, so the memory suite's check that managed is usable less reserved compares two computations. The mutation that catches it leaves the boot's own tables unreserved; the mutation that treats every frame as usable is invisible on QEMU's maps, whose holes lie below the break or past the table's top, and is the host test's to catch.

## Phase 2: the layout and the heap

* The kernel's gigabyte gets all 256 page tables at boot, a megabyte below the window, so a clone of the directory shares them and a mapping made later is seen by every process; the boot self-test maps a page after cloning a directory and reads it through the clone.
* `map_mmio` returns an address in the MMIO region and eight drivers use what it returns; the diagnostic, the two network drivers, AHCI and HDA used the physical address as a pointer.
* The physical-address writers were the lazy zero in `vm_resolve`, the copy-on-write copy, the loader's four sites, and the initial user stack in `execve` and `exec_program`; the last two were found by the 64 MiB probe faulting in kernel mode at 45 MiB.
* A scan for a free frame from the bottom of the table on every page fault is the table's length squared over a large mapping; a hint from which no frame below is free keeps it linear.
* `munmap` leaves the mapping's page tables with the process until it exits, one page per 4 MiB; the probe's leak check allows them.
* The `rach2.framefail` count counts only allocations made inside a system call, so a page fault of the process arming it is not the one that fails; at 64 MiB the sweep of sixty-four arms fired ten times, since a count past an operation's allocations fires on nothing.
* The modules are mapped into the module region on every boot, so QEMU's placement below the window exercises the path; a module above the window is a case no QEMU boot here makes.

## Phase 3: the objects

* Pipes, ptys and sockets are heap objects on lists. A pty's index is the lowest no live pty has, so `/dev/pts` names stay small; the `/dev/pts` walk asks the pty code for its index limit. `sockfull`, which filled the pool of sixteen sockets, is retired: there is no pool to fill, and `poolprobe` is the row that crosses the old sixteen for all three.
* `/proc/meminfo` gained `HeapPages` and `HeapUsed`, which is how a probe holds the heap to where it started.
* Open-file descriptions, TCP control blocks, `/proc` snapshots, synthetic directories and synthetic nodes are heap objects too; the description's lock queue moved into a record beside it, since the wait-queue header cannot be included from `fd.h`. `tcbfull`, which filled the pool of sixteen blocks, is retired with the pool. A walk of the control blocks that frees the one it is at reads its successor first.
* Processes are heap records on a doubly linked list; the scheduler walks it round-robin from the successor of the process scheduled last, and forgets a record that is freed. Kernel stacks and the `execve` workspace come from the heap, the workspace kept in the record for its life. `procfull`, which filled the table of sixteen, is retired; `poolprobe` holds forty processes at once. A fork the heap cannot serve answers `ENOMEM`, the memory error, since `EAGAIN` is the limit's, and milestone 46's phase 5 brings the limit.
* A wait queue is a list of the sleepers' own records: one in every process record, and `poll` supplies one per watched object from its stack, so a sleep allocates nothing and a queue has no size. The wait-queue host test drives sixty-four waiters.
* The mount table is a growable array of pointers to heap records, the three permanent mounts in slots 0 to 2; `vfs_mount_slots` is the array's length. The first run of the mount suite after this failed in its BusyBox row, on a kernel rebuilt while the suite ran; on the settled kernel it passes.
* The ext2, FAT32, exFAT and KRFFS mounts and their nodes and open records are heap objects on per-mount lists; the host tests hold two hundred ext2 nodes, forty FAT32 nodes and a hundred new ext2 files at once, and the KRFFS suite mounts three volumes where two was the table. The first run after this failed the ext2 root boot with a kernel page fault at 0xF000FF53, which is the address the interrupt vector table holds at zero: the boot's `vfs_init_root` ran before `vfs_init` had allocated the mount array, and read slot zero through a null array. The array is now made by whichever of the two runs first.
* A block request is allocated for the transfer, with its page a frame of the identity-mapped window, since a stick's driver hands the page's address to the controller as it is; the request is held by its caller and its device and freed when both have let go, so a quarantined request is the late completion's to free, and a completion is checked against the list of live requests and a generation no two requests share before it is believed. `rach2.blockpool` is now a limit on live requests, the policy the stall rules divide between devices, and not a table.
* The descriptor table is a heap array that starts at sixteen entries and doubles as it fills to a limit of 1024, the width of a select set; `fdfull` opens a thousand and twenty-one files and is refused at the limit. A process's regions are a heap array from sixteen entries to a limit of 65536; the host test grows one to forty-eight and copies it. `poll` and `select` take their per-call arrays from the heap, since a thousand entries would not fit a kernel stack. The record's layout changed with both, and the offsets `switch.s` reads are now checked at build time in `process.c` by an array whose size goes negative when they drift; the boot check that did this at run time carried the old numbers and stopped every boot until it was removed.
* A `/proc` text is built in a buffer that grows as it is appended to, so `/proc/net/tcp` iterates the control blocks and `/proc/mounts` lists every mount; the per-file bounds and the 3072-byte buffer are gone, `/proc/disk` keeps the one fixed width its formatter is given. A text the heap cannot hold is refused with `ENOMEM`.
* UDP bindings, raw registrations and packet bindings are heap records on lists, each raw or packet binding holding its own queue of eight datagrams. The four loop devices stay, since each is a node in `/dev` a program names; the bound is classified in `loop.h` as policy, and so are the temporary-mapping slots, the module records, the TCP rings, the accept backlog and the working directory's length, with the ARP cache as a cache.

## Phase 4: the caches and the rules

* The page cache takes a frame when a page is first read and the buffer cache makes a buffer when it needs one, up to half of the caches' target each, a quarter of managed memory together; `mem_reclaim` takes frames back from both, clean pages first and dirty ones written back, when the free count falls below a sixteenth of managed memory, and runs from fork, exec, mmap, brk and a user page fault, the places that are about to allocate and may sleep. `/proc/meminfo` reports `Buffers` and `Cached` from the two counts and `MemAvailable` as the free count and the two together.
* The reserve is a thirty-second of managed memory, not the plan's hundred-and-twenty-eighth: a login on the console is a fork by init and two programs loaded whole, over a megabyte on a machine of 128, where a hundred-and-twenty-eighth was a megabyte. A frame for a process whose effective uid is not 0 is refused inside the reserve; root, interrupt handlers and the kernel outside any process take from it.
* Whether an allocation is a handler's was first a global depth, which the boot's first switch to a user process left at one for ever, since that switch happens inside a timer interrupt that never returns; the depth is in the process record now, and a handler that switches away is left by the process it interrupted when that one runs again.
* The dirty row first failed with the buffer cache never shrinking, which was the depth above, and then with `EIO` on every read after the pressure: the probe's pages had taken every frame below the identity-mapped window, and a request's page must come from there, since a stick's driver hands the controller the page's address. User pages and kernel objects now take frames above the window first and leave the window's last sixty-four to the requests and the page cache.
* The queue row's deadline claim is proved by the mutation that starts the deadline at the queue rather than at the take; the row's sixteen readers queue for the one request the disk may hold under `rach2.blockpool=2`, and the last waits eight seconds with a five-second deadline.
* The hog row logs the test account in on the console, takes every frame outside the reserve through reads of `/dev/zero` into fresh pages, which the kernel refuses with `EFAULT` where a touch would have killed the process, finds `fork` refused with `ENOMEM`, then logs root in fresh beside it and kills it.

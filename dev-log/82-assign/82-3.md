# Assignment in nested QEMU

The assignment checkpoint uses TCG inside Rach2. On the testing PC, the same Debian guest with the same assigned NIC took 36 s under TCG and 277 s under nested KVM; both received all eight ping replies and released every counted assignment resource. The outer Rach2 machine uses KVM on WSL in both cases. These are author runs of the new cases, not the milestone's reviewed checkpoint.

## Machine

The outer machine is q35, two virtual CPUs and 2 GiB of RAM, with `intel-iommu,intremap=on,caching-mode=on`. Rach2 boots its GNU root from NVMe by MBR identity `82274701,1`; the assignment payload is a read-only AHCI disk. The host keeps e1000 on 10.0.2.0/24 and virtio-gpu. A modern virtio NIC, with `iommu_platform=on`, is at 0000:01:00.0 behind the PCIe root port at 0000:00:06.0, with a separate gateway at 10.0.3.2. QEMU's EDU device is at 0000:00:07.0. The NIC's root port enables its function-level reset capability.

The nested Debian guest has one virtual CPU and 128 MiB of RAM; the second guest of the reassignment case uses the shared KVM runner's 256 MiB default. It boots the pinned kernel and initramfs from `tests/assign`, loads the virtio PCI and network drivers, configures its static address, pings 10.0.3.2 eight times, prints `ASSIGNGUEST OK` and powers off. The kill cases add `assign.hold`, which keeps network traffic running and prints `ASSIGNGUEST TRAFFIC` after each completed batch.

Throughout each case, Rach2 writes 64 KiB of random data to its ext2 root, records the checksum, syncs, checks the data and pings its own gateway. The count below is the number of complete disk and network rounds; elapsed time does not decide a pass.

## Interfaces exercised

The nested KVM path registers assignment through KVM_CREATE_DEVICE and the KVM_DEV_VFIO_FILE attributes. The bridge retains each VFIO file and the VM, rejects duplicate aliases, and enables the guest PAT policy until the last assignment reference is released. Linux's AMD SYSCFG and NB_CFG probe behavior is provided too. The new bridge host test passed with AddressSanitizer and UndefinedBehaviorSanitizer on WSL.

The interrupt probe writes the real MSI registers through the privileged PCI `config` file in sysfs. VFIO's configuration shadow still isolates the guest's ordinary configuration writes. Raw config writes preserve byte, word and dword widths, including in ECAM. The new binary-config host rows passed with the same sanitizers on WSL.

The checkpoint cases are `machine.assign.boot`, `machine.assign.nic-tcg`, `machine.assign.dma`, `machine.assign.index`, `machine.assign.compat`, `machine.assign.kill` and `machine.assign.reassign`. The comparison used `machine.assign.nic-kvm`; that case was removed after TCG was chosen, while `run.sh nic-kvm` remains available in the outer guest. The seven author cases passed at `d3923acb1` with the corrected virtio interrupt path, zero faults before each case and exactly the injected fault count afterward. The device-memory correction below then required four of those cases to run again.

## Interrupt remapping

The interrupt probe first used `iopl`, which Rach2 does not provide; it now writes the real MSI configuration through sysfs. The compatibility-MSI injection then exposed QEMU's missing CFI handling by source inspection. The official 10.2.1 archive needs `tests/assign/qemu-vtd-cfi.patch`: it updates CFIS when CFI changes, blocks a compatibility message while CFIS is clear, and records reason 0x25. The existing upstream record in `upstream.md` now covers the delivery fault as well as the missing status.

The private outer emulator is `build/cache/qemu/out/qemu-system-x86_64` in the testing copy. Its version is `10.2.1 (rach2-vtd-cfi)` and its SHA-256 is `1043de70967512f2a6aa91539f25a7b708811bac06a829feb7c756c554a8eb5e`. GCC 15.2.0, Meson 1.10.1, Ninja 1.13.2 and Python 3.14.4 built it with GLib 2.88.0, pixman 0.46.4 and slirp 4.9.1. The archive digest and build flags are in the assignment Readme. The libraries and headers were unpacked under `build/cache/qemu/deps`; the system packages and global emulator were not replaced.

The corrected emulator exposed two compatibility-format MSI faults from the host's virtio-gpu before the probe injected anything. The virtio transport programmed its queue entries directly, so only entry zero used the PCI remapper. It now programs every entry through `pci_msix_entry_set` and releases all remappings before releasing their vectors, including partial setup failures. The new host rows cover three entries, shared-vector fallback and allocation failure cleanup; they passed under AddressSanitizer and UndefinedBehaviorSanitizer on WSL.

## Device memory

QEMU also registers the assigned NIC's 16 KiB BAR as a DMA mapping. VFIO rejected this with EFAULT because ordinary page pins refused device memory. Linux 6.12's `drivers/vfio/vfio_iommu_type1.c`, `vaddr_get_pfns`, accepts reserved or unmanaged physical pages through a VM_PFNMAP mapping without charging them to the locked-RAM limit. Rach2 now does the same through an explicit device-page option used by VFIO. Allocator-managed RAM still needs a pin, and its limit still applies in a mixed range. Unmapping, revoking or protecting device memory removes the DMA translation before its backing changes.

The `vfio_dma_io_pages` counter distinguishes mapped device pages from `vfio_dma_pages`, which counts pinned RAM. The kill and reassignment cases require both counts to be positive before SIGKILL and every resource count to return to its starting value afterward. The new pin rows passed on the i686 and x86-64 page-table models under AddressSanitizer and UndefinedBehaviorSanitizer on WSL, as did the VFIO rows. They cover mixed ranges, locked-memory limits, refused managed RAM, read-only mappings, absent devices, partial failures and each revocation path. Their output is in `build/runs/2747-pin-mmio.out`, `2747-pin64-mmio.out` and `2747-vfio-mmio.out` in the testing copy.

# Milestone 24: Rach2 on the Lenovo G50-70

## The goal

One milestone: the current Rach2 runs on the real notebook, and networking comes first inside it. The machine is a Lenovo G50-70 (i3-4030U Haswell, HM86, InsydeH2O BIOS in Legacy/CSM MBR mode, 16 GB RAM, Samsung 870 EVO SATA SSD carrying a Windows that stays, RTL8168GU PCIe gigabit Ethernet, no serial port, 8042 keyboard and VGA text, MC146818 RTC with no century register). The boot medium is a portable USB flash drive; no Rach2 code or milestone tool writes the SSD until its owner approves a carved partition after a full backup (Windows writes its own disk in its own sessions, which is outside the rule), and Windows must boot on every stick-less power-up throughout the milestone.

The order of value: first a RAM-only Rach2 booted from the USB stick (GRUB reads the stick through the BIOS; the kernel has no USB stack, so the loaded KRFFS module is the whole machine and nothing persists), then the RTL8168GU driver to the point where dropbear answers SSH over the LAN, which is the moment the development loop stops needing a person at the laptop for most work, then the rest of the supported surface, and only then, owner-approved, SATA persistence and the milestone 23 install flow on carved partitions. A failed phase must leave Windows bootable and the notebook recoverable by removing the stick.

## How the work splits between this desk and the laptop

Everything code-shaped is built, tested and reviewed locally first, with the laptop absent; the laptop sessions then only run proofs that need the hardware. Three QEMU arrangements make the local half unusually complete:

* The whole SSH contract rehearses in QEMU: the `rach2-metal` image boots under QEMU with the RTL8139, `rach2.ip=10.0.2.15/24 rach2.gateway=10.0.2.2` passed explicitly (the same values the defaults supply, so SLIRP still works), dropbear supervised by the metal init, and the harness connects by key through a forwarded port. Every piece of phase C except the physical NIC is proved this way before the laptop exists.
* Netconsole rehearses in QEMU too: QEMU's packet-capture filter writes the guest NIC's traffic to a pcap file, so the raw broadcast frames (framing, sequence numbers, checksums) are asserted on the host over the RTL8139 path, independent of the new driver.
* The PXE chain rehearses in QEMU: QEMU's user network carries a TFTP server and boot filename, and `-boot n` boots its PXE ROM, so the whole chainload (iPXE, its script, the kernel and module over HTTP) is proved locally before anyone touches the router.

What can never be proved locally is exactly the RTL8168GU driver against its silicon, the Insyde firmware's behavior, and the physical acts. Those wait for the laptop; everything else does not. The driver code itself is held to a stricter review because its first execution is on the hardware: the chip-model tests with their golden transcripts, plus repeated adversarial reviews, plus one dedicated line-by-line comparison of the ported sequences against the pinned reference, all before the first laptop session.

The supported surface, stated now so phase D cannot shrink it silently: Ethernet, VGA text, the 8042 keyboard, the RTC, HD Audio playback, AHCI access to the SSD, power-off and reset. Explicitly excluded: WiFi, Bluetooth, runtime USB, suspend and hibernation, battery reporting, the camera, and any graphics beyond VGA text. Each included device must pass its phase's proof; an excluded device is listed in the record, not skipped quietly.

## What was settled by research before this plan

* The driver reference is pinned: Linux v6.16 (commit `038d61fd642278bab63ee8ef722c50d10ab01e8f`), files `drivers/net/ethernet/realtek/r8169_main.c`, `r8169_phy_config.c`, `r8169_firmware.c`, `r8169.h`. The chip table maps XIDs matching `(xid & 0x7cf) == 0x509` (the xid read as `(TxConfig >> 20) & 0xfcf`) to `RTL_GIGA_MAC_VER_42`, "RTL8168gu/8111gu". A cross-check against v6.6 found every fact this plan relies on unchanged between the two.
* The reference's order is three stages, and the port follows all three rather than a flattened summary. Probe: map the memory BAR (not the I/O BAR), read the XID and stop on anything that does not match `(xid & 0x7cf) == 0x509`, disable PCIe L1 through configuration space, preserve `CPlusCmd`, initialize `RxConfig`, mask and acknowledge interrupts, run `rtl_hw_initialize` (for this chip `rtl_hw_init_8168g`: RxDV gate on, command bits cleared, `NOW_IS_OOB` cleared, the MAC-OCP `0xe8de` link-list-ready handshake with bounded waits), run the first bounded `CmdReset`, then read the MAC. Open: allocate and initialize the rings, enable bus mastering, initialize the PHY, then the reset-work sequence: mask and acknowledge again, close the RX filter, RxDV gate, the second reset, TX state cleared, RX ownership returned, and `rtl_hw_start`. Inside `rtl_hw_start` the order is: unlock `Cfg9346`, keep chip ASPM and CLKREQ disabled, write `CPlusCmd`, set the EEE txidle timer, run the `rtl_hw_start_8168` wrapper (its `MaxTxPacketSize` early size first, then the chip-specific `rtl_hw_start_8168g_2`: the `rtl_hw_start_8168g` fifo, pause, packet-filter, ERI and L2/L3 work, then the nine-entry EPHY table), write `IntrMitigate` zero, run the exit-L1 OCP write (`0xc0ac` for this version), then `RxMaxSize`, then the descriptor bases (high halves first), lock the config, the jumbo configuration at the default MTU, a PCI posting read, `ChipCmd (CmdTxEnb|CmdRxEnb)`, `RxConfig`, `TxConfig`, and the address filter. The golden transcript in the host model classifies EVERY step of the reference's path as ported or omitted by name (the interrupt-enable and offload steps are the named omissions; the ASPM re-enable is ported as the no-op it is for this version), so an accidental omission cannot pass as a decision.
* EEE follows the reference initially: `rtl8168g_config_eee_phy`, the txidle timer, and `rtl8168_config_eee_mac` run as Linux runs them, because omitting them does not clear whatever state Windows or firmware left, and the first baseline must be the reproducible one. Turning EEE off is a separately tested change afterward, if measurements want it.
* ASPM needs implementation, and on both ends of the link: the reference disables link states through the PCI core, which programs the downstream port and the endpoint together, so the kernel's PCI layer gains a bounded capability traversal, the driver clears the L1 bits in the endpoint's `LNKCTL` AND in the root port above it (found as the bridge whose secondary bus carries the NIC), and clears `Config2.ClkReqEn` and `Config5.ASPM_en`; the reference never re-enables them for this chip version and neither does the port.
* The PHY configuration for this exact version is `r8169_apply_firmware` plus the EEE calls and nothing else: no per-register PHY surgery, link by standard autonegotiation, and Linux proceeds when the firmware file is absent, printing a warning. The first attempt runs without the blob. The contingency, activated only if link does not appear or does not hold on this board, is a port of the reference's validated firmware-action interpreter plus the blob `rtl_nic/rtl8168g-3.fw` from linux-firmware tag `20250211` (version 0.0.1 per its WHENCE entry), whose SHA-256 and license text are recorded when it is fetched and reviewed before it enters the tree.
* The programming surface is the C+ descriptor ABI: 16-byte descriptors (`opts1` carries `DescOwn` bit 31, `RingEnd` 30, `FirstFrag` 29, `LastFrag` 28, length in the low 14 bits; a 64-bit buffer address), ring bases at `TxDescStartAddrLow 0x20` / `RxDescAddrLow 0xe4`, the doorbell an 8-bit `NPQ (0x40)` write to `TxPoll 0x38` that must be rung again while descriptors stay owned, because the reference documents that closely spaced poll requests can be lost. RX lengths include the FCS (subtract four). RX buffers are the reference's 16383 bytes with `RxMaxSize 16384`; the ring is 64 descriptors (about 1 MiB of buffers), which is a deviation from the reference's 256 and is therefore burst-tested in the model and on the laptop. The rings are 256-byte aligned, a write barrier precedes every `DescOwn` transfer to the device, and a read barrier follows every observed ownership return before the descriptor's other fields are read; the register model cannot see compiler or DMA reordering, so these three rules are a separately reviewed contract in the driver's comments and the review. Indirect access goes through ports of the source helpers: `rtl_eri_read/write` (ERIAR/ERIDR at `0x74`/`0x70`), `r8168_phy_ocp_*` (GPHY_OCP `0xb8`, MDIO OCP base `0xa400`, page selection via MII `0x1f`), `r8168_mac_ocp_*` (OCPDR `0xb0`), `rtl_ephy_*` (EPHYAR `0x80`); every completion wait bounded and named.
* Deliberately off for the whole milestone: MSI and MSI-X (the kernel is PIC-only and polled), interrupt-driven RX (the NIC's interrupts stay masked), jumbo frames, offloads, RSS, VLAN. The 100 Hz polling cadence is a hypothesis; phase C carries the counters and numbers that make it pass or fail.
* The stack's metal gaps are known exactly. The address, netmask and gateway are compile-time QEMU SLIRP constants (`NET_IP_ADDR` and neighbors in `sys/network/net.h`) consumed by ARP, IP, TCP, routing and the socket syscalls. `init_network` and `ethernet_tx` call `rtl8139_*` directly, and `net_core.c` also carries a literal `"RTL8139 10.0.2.15"` status string, direct `rtl8139_error` use, direct RTL8139 register accessors, and a literal address line in `net_print_info`, so the driver interface must cover transmit, poll, status, error and diagnostic output, or those paths must become device-neutral. Dropbear is started by hand today, and the strict os-real init is deliberately checked to hold only the console-login path, so the metal profile needs its own third init variant rather than an edit to that artifact. Entropy has a precondition and a check: Haswell has RDRAND (RDSEED is a Broadwell feature this CPU lacks) and `krandom_is_trusted` accepts RDRAND alone, but trust is established only when the boot's eight hardware words all arrive, so the metal acceptance includes a `getrandom` probe and the banner's reported source, and the named failure is dropbear unable to mint its host key.
* The RAM machine's budget comes from the kernel, whatever the notebook installs: the direct map ends at 32 MiB (`paging.h`), the boot rejects a module past it (`kernel.c`), and the allocator reserves through the highest module end. GRUB does not promise a placement, so the metal image is built small and the boot prints and checks the layout. The 16 GB of installed RAM changes nothing until the kernel's physical ceiling does, which is not this milestone.
* The RTC needs nothing: the kernel already infers the century in software and never reads register 0x32.
* The power values come from the machine's own tables, supplied by its owner: S5 is `outw(0x1804, 0x3C00)`; reset is `0xFB` to port `0xB2` (the FADT reset register), then `0xCF9`, then the 8042 pulse, tried in that order; ACPI enable, if `SCI_EN` is clear under CSM, is `0xA0` to SMI command port `0xB2` with a bounded wait; SCI is IRQ 9 and stays masked, because no SCI handler exists this milestone. These land as a named Lenovo board profile selected and overridable from the command line, not as a generic ACPI implementation; FADT parsing and AML are out of scope.
* The NIC's state at entry is part of the problem: Windows, its Fast Startup path, or a prior Linux boot each leave different MAC, PHY, EEE and firmware state, and a Linux boot in particular runs r8169, loads the blob, and resets everything, hiding exactly the state our driver must survive. The laptop procedure therefore writes down what ran before each boot, and Linux stays off the machine entirely: the inventory comes from the installed Windows, so the only entry states are cold power and after a Windows shutdown.
* PXE is only a way to move files faster, and it gets one laptop session to prove itself: chainload iPXE's `undionly.kpxe` from the firmware's PXE ROM, fetch the kernel and module over HTTP, boot them multiboot. It rides the firmware's own UNDI driver, so it proves nothing about our NIC driver, and Insyde CSM PXE quality is unknown. If it works, new builds travel over the LAN and the stick stops being rewritten; if not, the stick keeps doing that job.

## What the first inventory measured (Windows report, 2026-08-16)

The Windows-side checklist ran before the first stick boot and settled these; the XID and the BIOS page photographs remain for the laptop session.

* The MBR holds TWO used entries (the 500 MiB System Reserved at LBA 2048, then C: spanning the rest of the 1 TB) and entries 3 and 4 are EMPTY, with no unallocated space but 844 GB free inside C:. BitLocker is off on every volume and the machine has no TPM. Phase E's arithmetic is therefore decided: two free primary slots exist, the shrink-and-carve branch applies, and the extended-partition walk is the branch not taken on this machine (it stays out of scope unless a future inventory differs). The MBR's 512 bytes are hashed in the report (SHA-256 652ad40f...) with the standard Windows boot code and disk signature 0x4905B015.
* The SATA controller runs in AHCI mode (PCI class 010601, the BIOS setup says AHCI, Intel's iaStorA driver bound), ABAR at 0xC061B000. One measured platform fact matters to us: this machine once lost its SATA link on WARM REBOOT under SATA link power management (the firmware then found no disk and looped through PXE), and the owner fixed it in Windows by disabling HIPM/DIPM. Rach2 never enables link power management, and the phase D COMRESET work is the recovery if a warm reboot still brings the link up dead.
* The NIC's resources: I/O 0x3000 (256 B), MMIO 0xC0504000 (4 KiB) and 0xC0500000 (16 KiB), behind root port 00:1c.0; the driver reads the BARs from configuration space and takes the first memory BAR by index, as the reference does. Windows runs it with MSI, EEE AND Advanced EEE AND Green Ethernet all enabled, and the adapter's ASPM registry setting on, which confirms both plan decisions: the EEE-follow baseline (Windows leaves EEE state behind) and the ASPM disable work.
* Fast Startup is ENABLED (a plain "Shut down" is a hybrid shutdown; Shift held during shutdown forces a full one), which phase D's entry-state boot and phase E's carving rule already account for. The BIOS is 9ACN32WW, the final release for the board, freshly flashed, with Back Flash disabled.
* Virtualization: VT-x on, no hypervisor running, virtualization-based security off, no active DMA protection, CSM boot; the indirect evidence says DMA remapping is inactive, and the BIOS page photograph remains the direct confirmation.
* The Ethernet cable was out during collection, so the wired IP, mask, gateway and DHCP lease do not exist yet; the WiFi side shows the LAN is 192.168.0.0/24 with the router at 192.168.0.1. The wired address is chosen and reserved in the router in the morning, and `rach2.ip=` takes whatever is chosen.

The report itself is `Lenovo_G50-70_report_temp.txt` in the repository root: it stays untracked, never enters a commit, and is deleted at the very end of the milestone, after the hardware work concludes.

## Phase A: the local build, and the hardware inventory when the laptop arrives

Build first, then the laptop session, one stick. The build side: a `rach2-metal` manifest (busybox, dropbear, the new metal init, `/etc`, the authorized key; no `/src`, no tcc, no pdpmake, no install-kernel; the image held to a few MiB), its Makefile target and image-inventory wiring, `mkiso.sh` accepting the new profile with three menu entries (normal, verbose diagnostic, rescue debug shell), `make help` updated, and the diagnostic boot printing the kernel end, each module's range, the reserved end, the free-frame count, and the NIC's masked XID read from `TxConfig` (a read-only PCI and MMIO peek, no driver, skipped with a printed reason if the device's memory decoding is off; the peek changes no PCI command bits), with the boot refusing module overlap or a module past the direct map.

The inventory comes from the machine's own Windows, which already produced this plan's hardware dump and carries an assistant that can extract what a checklist names; no Linux boot is needed, which also removes an entire NIC entry state from the experiment (Linux's r8169 resets the chip and loads firmware; a machine that never boots Linux never carries that state). The checklist, run from Windows as administrator: the PCI configuration of the NIC and the AHCI controller (IDs, BARs, capabilities), the adapter's driver-reported link and Wake-on-LAN settings, the SSD's first sectors read raw and hashed (the MBR and its four entries), through a read-only physical-drive handle whose model and serial are verified as the 870 EVO before the read, the SATA mode, the BIOS version as flashed and its pages photographed (SATA mode options, boot order, PXE and WoL toggles, VT-d if present), and the Fast Startup state. The XID is deliberately NOT read from Windows, because it needs a raw MMIO read no stock tool does safely: the Rach2 diagnostic boot entry reads `TxConfig` itself and prints the masked XID, so our own read-only code supplies the one number the driver gates on.

The build half and the inventory half are independent: the Windows-side checklist can run any time (its output feeds the plan's numbers), and the stick is written whenever it is convenient, because the same image boots in QEMU first (the ISO the build produces is a hybrid image, bootable in QEMU and written to a stick unchanged). The laptop session, with the origin of each boot written down: the Rach2 stick boots from a cold power-off (the first entry state), the diagnostic entry's VGA output is captured (layout numbers, PCI identities, the XID), and the normal entry reaches the RAM machine's login on VGA with the 8042 keyboard; a second Rach2 boot follows a normal Windows shutdown (the other entry state this machine will actually present). Last, Windows boots with the stick removed. The measured numbers, the XID above all, are written back into this plan before phase B begins. A Linux live stick is no longer part of the protocol; it remains the named escalation tool if the no-firmware link attempt fails in phase B (to observe what Linux's driver does on this exact board) and the rescue medium for phase E.

* Proof, host side: the stick's contents reproducible and hashed; the module-bound checks shown failing against a crafted oversized module AND against two crafted overlapping modules in QEMU; the manifest gated like every other.
* Proof, at the laptop: the captures and the login, with the boot order and provenance log kept in the record; the Windows-side checklist output filed with it. A capture proves the displayed state and nothing more; this phase's deliverable is measured facts.
* Readmes: the metal profile's manifest and the laptop protocol documented.

## Phase B: the driver interface, the chip model, and the first transmitted packets

First the driver interface, before any new hardware code: device operations for transmit, poll, status, error and diagnostic reporting behind the existing `network/driver/` boundary, RTL8139 moved behind it unchanged, `net_core.c`'s literal strings and direct calls replaced by calls through that interface, and every existing QEMU network suite held green.

Then the RTL8168GU driver to the TX point, in the pinned three-stage order stated above. Phase B has no timer hook yet, so its transmit is a bounded synchronous path: write the descriptor, ring `TxPoll`, poll `DescOwn` with a bounded wait, and ring again while the descriptor stays owned, per the reference's lost-doorbell rule; the timer-driven path arrives in phase C. Beside it, raw netconsole: the serial stream duplicated into hand-built broadcast frames (EtherType `0x88b5`, sequence number, boot id, length, checksum; no allocation, no ARP, no recursion into the driver's own logging; a bounded buffer holds what was printed before TX existed). A host test drives the whole driver in `verify-host` against a software model of the chip's registers: access widths, completion-flag transitions, W1C status, the OOB handshake, both resets in order, descriptor ownership and ring wrap, the lost-doorbell case, RX-burst behavior at the 64-descriptor ring, bounded timeouts, and golden transcripts against the pinned sequence. The model must pass before a laptop visit is worth making; it cannot prove PCIe ordering, DMA reachability, PHY behavior, or this board's firmware need, and the record says which proofs can only come from the laptop.

* Proof, host side: the model suite, and the RTL8139 regression (every existing network probe and capstone unchanged); the netconsole layer's frames captured and checked from QEMU's pcap over the RTL8139 path, so only the 8168-specific transmit path waits for the hardware.
* Proof, at the laptop: the dev host's packet capture shows our broadcast frames with source MAC `28:D2:44:7E:E0:AF`, ordered sequence numbers and valid checksums, once against a gigabit peer and once against a 100 Mbps port; the VGA banner shows XID, MAC, negotiated speed and duplex. The capture is the TX proof; a link LED proves only the PHY.
* Shown failing: a golden-transcript mutation (one ERI write dropped) fails the model suite; the XID gate against a crafted wrong id ends the probe with the diagnostic naming both values, and an accepted-alias case (a raw id differing only in the unmasked bits) passes the gate; suppressing the doorbell in the model leaves the descriptor owned and fails the TX case.
* Readmes: the network Readme's driver section rewritten for the driver interface and the second driver.

## Phase C: RX, the stack on real addresses, and SSH

RX delivery through the driver interface's `poll` operation on the existing 100 Hz tick (a bounded per-tick budget, single-fragment frames only, FCS stripped, receive errors rejected and counted), TX reclaim and the re-ring moved onto the same tick, ARP answered, and the stack's compile-time address replaced: `rach2.ip=A.B.C.D/prefix` and `rach2.gateway=A.B.C.D` parsed and validated at boot into one immutable configuration read by every current consumer of the constants, including the socket syscalls and `net_print_info`. The tuple rule: no options, the full SLIRP tuple as today, QEMU behavior byte-for-byte unchanged; `rach2.ip=` alone, no default gateway at all, because a SLIRP gateway beside a real LAN address would be wrong on both networks. The board reset sequence also lands here rather than in phase D, because this phase's loop needs remote warm reboots: `0xFB` to port `0xB2`, then `0xCF9`, then the 8042 pulse, tried in that order under the board profile. The metal profile's init (the third variant, staged only in `rach2-metal`, the strict os-real artifact untouched) supervises dropbear (`dropbearmulti dropbear -F -R -g -p 22`) beside the console login, with restart backoff, child tracking for both, orphan reaping, and the console kept as the recovery path. `-R` mints a volatile host key per boot, so the harness side uses a per-run known-hosts file rather than disabling verification. DHCP and DNS are out of scope; a numeric address is the contract. The phase's counters decide the polling hypothesis against numbers: a 64-frame burst at 100 Mbps completes with zero drops (it fits the ring); a sustained bulk transfer at 100 Mbps holds a counter-verified drop rate under one percent (a hash-correct transfer alone can hide loss behind retransmission); the same measurements are recorded at gigabit, where drops are expected and quantified (64 full frames arrive in under a millisecond); and an idle SSH session echoes a keystroke inside 100 ms. Failing numbers mean a bigger ring or a faster poll, and the record says which was taken.

* Proof, at the laptop once, then from the dev host: the peer captures the ARP exchange; ping both directions; SSH by key to a PTY shell; a file transferred each way and hash-compared; repeated connect cycles; warm reboots over SSH. The human-only items are named as such: a cable pulled and replaced, and cold power cycles, need hands.
* Proof, in QEMU: the address parser's host tests (malformed, duplicate, broadcast, network, prefix range), the full network suite over RTL8139 with and without `rach2.ip=` present, the metal init's supervision tests, and the full rehearsal: the `rach2-metal` image booted in QEMU with explicit address options, dropbear supervised, an SSH login by key through a forwarded port, a file transferred and compared. After that rehearsal, the laptop adds only the real NIC and the real LAN.
* Shown failing, split correctly: suppressing the TX doorbell fails the netconsole capture; a deliberately wrong `rach2.ip=` leaves netconsole running (it is below IP) while ARP and SSH fail; the parser's negatives are refused in the host test.
* Readmes: the network Readme (addressing), the dropbear notes (supervised mode), `tools/Readme.md` for the remote-probe idiom.

## Phase D: the rest of the supported surface, nothing written to the SSD

The board profile's remainder (the reset sequence shipped with phase C): poweroff through `0x1804`/`0x3C00`; the bounded ACPI-enable handshake when `SCI_EN` is clear; IRQ 9 masked; every real-device poll bounded, and any absent device parameterized off cleanly by command line, the kernel booting with any subset present. AHCI on real hardware to the identify-and-read point: the missing metal pieces are the HBA reset and per-port COMRESET (the BIOS/OS handoff already exists in `ahci.c`; COMRESET is also the recovery for this machine's measured warm-reboot failure shape, a SATA link that comes up dead), a port scan tolerant of empty and ATAPI ports, and a read-only diagnostic path that does NOT mount (the disk-root mount writes the dirty flag at mount time, which is an SSD write this phase forbids): a `/proc` diagnostic or a dedicated probe exposes identify data and sector hashes to SSH. The no-write rule is enforced at the one place commands leave the driver: under the metal build switch, the AHCI and ATA command paths carry an allowlist that refuses `WRITE DMA EXT` and `FLUSH CACHE EXT` outright, a host test proves the refusal, and the artifact check verifies which build policy the image carries; string and symbol absence alone proves nothing, since the commands are numeric and the functions static.

* Proof, at the laptop: reboot and poweroff observed, cold boots repeated, keyboard and VGA exercised, audio heard by a person (SSH can prove the call returned; only ears prove sound); one recorded boot enters Rach2 immediately after a normal Windows shutdown with the Fast Startup state noted, because that is the NIC and platform entry state the OOB and reset sequences exist for; Windows boots with the stick removed.
* Proof, over SSH: everything else, including identify data and sector hashes compared against phase A's Windows-captured baseline.
* Shown failing: the reset sequence demonstrated in QEMU with the first two methods stubbed; the AHCI read path's bounds against a crafted response in the host test; the write-path artifact check against a deliberately mis-built image.
* Readmes: the board profile and the metal build switch documented.

## Phase E: owner-approved persistence and the install flow

Gated twice: on phase A's MBR inventory, and on the owner's explicit approval after a full SSD backup, with Windows Fast Startup disabled before any resize; the owner performs the resize and carve with trusted tools. Precisely what is preserved: the SSD's boot code, every Windows filesystem except the approved shrink, and Windows bootability; the partition table itself necessarily changes, and saying so is part of the approval.

The topology: the USB stick remains the only boot device; the SSD gains a FAT slots partition (candidate, fallback, `grubenv`) and a KRFFS partition. The stick's GRUB gains a persistent entry whose config addresses the SATA volumes explicitly: `search --fs-uuid` sets the slot volume, and `load_env`/`save_env` name that volume's `grubenv` by explicit path, because `$prefix` stays on the stick and the implicit environment file would too; the RAM rescue entry stays on the stick forever. The kernel content-probes the carved KRFFS partition for its root (`rach2.fsdisk`), and `/dev/bootpart` selects the slots volume by `rach2.bootuuid=` (the FAT volume id) instead of the entry-zero rule. Before any metal attempt, a two-disk QEMU fixture proves the whole topology: USB GRUB plus SATA slots and KRFFS, trial consumption, `save_env` across devices, the fallback, the rescue entry, and swapped BIOS disk numbering; the milestone 23 harness idioms run against it.

The MBR arithmetic is already decided by the inventory: entries 3 and 4 are free, so the carve uses primary slots and no extended-partition support is needed on this machine. The general branches (a bounded walk of logical partitions when only those fit; blocked-by-topology with a written owner decision when nothing fits) stay recorded here as the paths not taken, and none of their code is built this milestone.

* Proof: Windows boots after the carve and on every stick-less boot; the milestone 23 loop runs on the notebook over SSH (install a marked kernel, reboot, prove the marker, corrupt, prove the fallback, repair from inside, commit); `/src` and the self-build return; the host key becomes persistent; the two-disk QEMU fixture stays as a regression.
* Shown failing: a wrong `rach2.bootuuid=` leaving the device absent. The swapped-numbering case, where the volumes are still found by id, belongs to the positive proof above.
* Readmes: the install and layout documentation extended from milestone 23's single-disk story to the two-disk topology.

## Phase F: the sweep, the record, and the gate

The staleness sweep over everything touched; the record in `dev-log/24-metal/Readme.md` with the measured facts, the per-phase proofs and who supplied each (the human-only items listed), what was refuted, what stays deferred, and the supported-surface table with its exclusions; the index line; the full QEMU gate from a clean tree; a written metal acceptance checklist, the SSH-driven part scripted, the human part enumerated, executed once end to end; and, once the hardware work has concluded the milestone, the deletion of `Lenovo_G50-70_report_temp.txt` from the repository root, where it lived untracked.

## Risks, in expected order

1. The RTL8168GU's entry state (Windows warm state, Fast Startup, firmware residue): mitigated by the OOB handshake, the two recorded entry states (cold power and after a Windows shutdown), per-boot provenance, and the firmware contingency with its recorded activation condition; keeping Linux off the machine keeps its driver's state out of the matrix.
2. Insyde CSM behavior is measured in phase A: USB-HDD boot selection, PXE quality (held to a fixed time budget), VT-d default (assumed off; DMA is blocked if on, and the toggle is recorded in phase A), WoL toggles.
3. The module-placement budget under the 32 MiB direct map: the slim image, the printed layout, the boot checks, and `--quirk-modules-after-kernel` as the recorded fallback.
4. Before SSH exists, every test round needs a person at the laptop, which is the old slow loop: phases A and B are shaped to need few visits, and PXE may remove the stick rewriting if its trial session succeeds.
5. The MBR slot budget on a Lenovo Windows disk decides phase E's shape, up to blocked-by-topology with a written acceptance decision.
6. The 64-descriptor RX ring is a deviation from the reference's 256: burst tests in the model and on the laptop decide it, and the fallback is the reference's geometry at the cost of memory.
7. Provenance and licensing: the driver is a port of a pinned GPL reference into a project that already vendors GPL components, and the firmware blob, if activated, enters only with its recorded terms; both decisions land in the record.

## What must not be broken

* Windows on the SSD boots on every stick-less power-up, and nothing writes the SSD before phase E's double gate; phase D's metal profile carries the command allowlist under the metal build switch and the artifact check of the build policy.
* Every QEMU suite and the whole existing gate stay green throughout: the RTL8139 path behind the new driver interface, the SLIRP defaults without `rach2.ip=`, the strict os-real init untouched, and the milestone 23 harnesses as regression surface.
* The kernel remains one source tree for gcc and tcc; the guest build lists and `check_guest` grow with any new kernel files.
* The register rule in every committed line, and the one-milestone discipline: internal phases, one record.

# Milestone 24: Rach2 on the Lenovo G50-70

## The goal

This milestone boots the current Rach2 on the physical notebook, with networking implemented first. The Lenovo G50-70 has an i3-4030U Haswell processor, HM86 chipset, InsydeH2O BIOS in Legacy/CSM MBR mode, 16 GB of RAM, a Samsung 870 EVO SATA SSD with an existing Windows installation, RTL8168GU PCIe gigabit Ethernet, no serial port, an 8042 keyboard and VGA text display, and an MC146818 RTC without a century register. A portable USB flash drive provides the boot medium. No Rach2 code or milestone tool may write the SSD until the owner approves a new partition after a complete backup. Writes made by Windows during its own sessions are outside this restriction. Windows must boot whenever the notebook powers on without the stick.

Work proceeds in this order. First, boot a RAM-only Rach2 from the USB stick. GRUB reads the stick through BIOS; because the kernel has no USB stack, the loaded KRFFS module provides the complete machine and nothing persists. Next, implement RTL8168GU support until Dropbear accepts SSH over the LAN, removing the need for a person at the notebook during most development. Then implement the remaining supported hardware. Only after owner approval, add SATA persistence and the milestone 23 installation procedure on new partitions. Failure in any phase must leave Windows bootable and permit recovery by removing the stick.

## How the work splits between this desk and the laptop

Build, test, and review every software change locally before using the notebook. Hardware sessions run only the checks that require the physical machine. Three QEMU configurations cover the remaining work:

* Rehearse the complete SSH contract in QEMU. The `rach2-metal` image uses RTL8139 and receives `rach2.ip=10.0.2.15/24 rach2.gateway=10.0.2.2` explicitly. These are the default values, so SLIRP still operates. Metal init supervises Dropbear, and the harness connects by key through a forwarded port. This proves every phase C component except the physical NIC before the notebook session.
* Rehearse netconsole in QEMU. The packet-capture filter writes guest NIC traffic to a pcap file. Host assertions check framing, sequence numbers, and checksums in raw broadcast frames from the RTL8139 path, independently of the new driver.
* Rehearse the PXE chain in QEMU. The user network provides a TFTP server and boot filename, while `-boot n` starts the PXE ROM. This proves the complete chainload of iPXE, its script, and the kernel and module fetched over HTTP before changing the router.

Local tests cannot verify the RTL8168GU driver on silicon, Insyde firmware behavior, or physical actions. Those checks require the notebook. Before its first hardware execution, the driver must pass chip-model tests with golden transcripts, repeated adversarial reviews, and a dedicated line-by-line comparison of the ported sequences with the pinned reference.

The supported hardware is Ethernet, VGA text, the 8042 keyboard, the RTC, HD Audio playback, AHCI access to the SSD, power-off, and reset. Phase D must not reduce this list. WiFi, Bluetooth, runtime USB, suspend and hibernation, battery reporting, the camera, and graphics beyond VGA text are excluded. Each included device must pass its phase-specific check, and the record must list every exclusion explicitly.

## What was settled by research before this plan

* Pin the driver reference to Linux v6.16 at commit `038d61fd642278bab63ee8ef722c50d10ab01e8f`, using `drivers/net/ethernet/realtek/r8169_main.c`, `r8169_phy_config.c`, `r8169_firmware.c`, and `r8169.h`. Its chip table maps XIDs satisfying `(xid & 0x7cf) == 0x509`, with the XID read as `(TxConfig >> 20) & 0xfcf`, to `RTL_GIGA_MAC_VER_42`, "RTL8168gu/8111gu". A comparison with v6.6 found no change to any fact used by this plan.
* Preserve the reference's three-stage order rather than reducing it to a summary. Probe maps the memory BAR instead of the I/O BAR, reads the XID, and stops unless `(xid & 0x7cf) == 0x509`. It disables PCIe L1 through configuration space, preserves `CPlusCmd`, initializes `RxConfig`, masks and acknowledges interrupts, and runs `rtl_hw_initialize`. For this chip, `rtl_hw_init_8168g` enables the RxDV gate, clears command bits and `NOW_IS_OOB`, and performs the MAC-OCP `0xe8de` link-list-ready handshake with bounded waits. Probe then performs the first bounded `CmdReset` and reads the MAC. Open allocates and initializes the rings, enables bus mastering, and initializes the PHY. Its reset-work sequence masks and acknowledges interrupts again, closes the RX filter, enables the RxDV gate, performs the second reset, clears TX state, returns RX ownership, and calls `rtl_hw_start`. Within `rtl_hw_start`, unlock `Cfg9346`, keep chip ASPM and CLKREQ disabled, write `CPlusCmd`, set the EEE txidle timer, and call the `rtl_hw_start_8168` wrapper. That wrapper first sets the early `MaxTxPacketSize`, then calls the chip-specific `rtl_hw_start_8168g_2`. The latter runs the `rtl_hw_start_8168g` FIFO, pause, packet-filter, ERI, and L2/L3 work, followed by the nine-entry EPHY table. Next, write zero to `IntrMitigate`; perform the exit-L1 OCP write, `0xc0ac` for this version; set `RxMaxSize`; write the descriptor bases with high halves first; lock the configuration; apply jumbo configuration at the default MTU; perform a PCI posting read; set `ChipCmd (CmdTxEnb|CmdRxEnb)`, `RxConfig`, and `TxConfig`; and program the address filter. The host model's golden transcript classifies every reference step by name as ported or omitted. Interrupt enable and offloads are the named omissions, while ASPM re-enable is ported as the no-op used by this version. An accidental omission must fail the transcript.
* Initially configure EEE exactly as the reference does. Run `rtl8168g_config_eee_phy`, set the txidle timer, and run `rtl8168_config_eee_mac`. Omitting these operations would leave unknown state from Windows or firmware, while the first baseline must be reproducible. If measurements require disabling EEE, test that as a separate later change.
* Implement ASPM control at both ends of the link. The reference uses the PCI core to configure the downstream port and endpoint together. Add bounded capability traversal to the kernel PCI layer. Clear the L1 bits in the endpoint's `LNKCTL` and in its upstream root port, located as the bridge whose secondary bus contains the NIC. Also clear `Config2.ClkReqEn` and `Config5.ASPM_en`. The reference does not re-enable these features for this chip version, and neither should the port.
* For this version, PHY configuration consists only of `r8169_apply_firmware` and the EEE operations. Do not add per-register PHY changes; use standard autonegotiation. Linux warns but continues when the firmware file is missing, so the first attempt omits the blob. Activate the contingency only if the link fails to appear or remain active on this board. It ports the reference's validated firmware-action interpreter and adds `rtl_nic/rtl8168g-3.fw` from linux-firmware tag `20250211`, version 0.0.1 according to WHENCE. Record its SHA-256 and license, and review it before adding it to the tree.
* Use the C+ descriptor ABI. Each descriptor is 16 bytes. In `opts1`, bit 31 is `DescOwn`, bit 30 is `RingEnd`, bit 29 is `FirstFrag`, bit 28 is `LastFrag`, and the low 14 bits contain the length; the buffer address is 64 bits. Ring bases use `TxDescStartAddrLow 0x20` and `RxDescAddrLow 0xe4`. Ring the doorbell with an 8-bit `NPQ (0x40)` write to `TxPoll 0x38`. Repeat the write while descriptors remain owned because the reference states that closely spaced poll requests can be lost. RX lengths include the FCS, so subtract four. Use the reference's 16383-byte RX buffers with `RxMaxSize 16384`. The ring has 64 descriptors and about 1 MiB of buffers, rather than the reference's 256 descriptors; test this difference with bursts in the model and on the notebook. Align rings to 256 bytes. Place a write barrier before every `DescOwn` transfer to the device. After observing ownership return, place a read barrier before reading the descriptor's other fields. The register model cannot detect compiler or DMA reordering, so review these three rules separately as a documented driver contract. Port the reference helpers for indirect access: `rtl_eri_read/write`, using ERIAR/ERIDR at `0x74` and `0x70`; `r8168_phy_ocp_*`, using GPHY_OCP `0xb8`, MDIO OCP base `0xa400`, and MII page selector `0x1f`; `r8168_mac_ocp_*`, using OCPDR `0xb0`; and `rtl_ephy_*`, using EPHYAR `0x80`. Bound and identify every completion wait.
* Keep MSI and MSI-X disabled for the entire milestone because the kernel uses the PIC and polling. Keep NIC interrupts masked rather than implementing interrupt-driven RX. Also omit jumbo frames, offloads, RSS, and VLAN. Treat the 100 Hz polling interval as a hypothesis; phase C records the counters and measurements that accept or reject it.
* Address every known metal-network gap. The address, netmask, and gateway are compile-time QEMU SLIRP constants, including `NET_IP_ADDR` and adjacent definitions in `sys/network/net.h`, used by ARP, IP, TCP, routing, and socket syscalls. `init_network` and `ethernet_tx` call `rtl8139_*` directly. `net_core.c` also contains the literal status string `"RTL8139 10.0.2.15"`, direct `rtl8139_error` use, RTL8139 register accessors, and a literal address line in `net_print_info`. The driver interface must provide transmit, poll, status, error, and diagnostic operations, or these call sites must become device-neutral. Dropbear currently starts by hand. The strict os-real init is required to provide only console login, so add a third init variant for the metal profile instead of changing that artifact. Entropy has both a prerequisite and a check. Haswell provides RDRAND but not RDSEED, which first appeared in Broadwell, and `krandom_is_trusted` accepts RDRAND alone. Trust still requires all eight hardware words during boot. Metal acceptance therefore runs a `getrandom` probe and checks the source reported in the banner. The named failure is Dropbear being unable to create its host key.
* Derive the RAM-machine budget from the kernel rather than installed memory. The direct map ends at 32 MiB according to `paging.h`, the boot rejects a module beyond it in `kernel.c`, and the allocator reserves memory through the highest module end. GRUB does not guarantee module placement, so keep the metal image small and print and validate its layout at boot. The installed 16 GB has no effect until the kernel's physical-memory limit changes, which is outside this milestone.
* Make no RTC change. The kernel already infers the century in software and never reads register 0x32.
* Use the power values from the notebook tables supplied by the owner. S5 is `outw(0x1804, 0x3C00)`. Reset writes `0xFB` to port `0xB2`, the FADT reset register, followed by `0xCF9` and the 8042 pulse, in that order. Under CSM, if `SCI_EN` is clear, enable ACPI by writing `0xA0` to SMI command port `0xB2` and waiting within a bound. SCI uses IRQ 9 and remains masked because this milestone provides no SCI handler. Implement these values as a named Lenovo board profile selected and overridden from the command line, rather than as generic ACPI support. FADT parsing and AML remain out of scope.
* Record NIC state before each boot. Windows, Fast Startup, and a preceding Linux boot leave different MAC, PHY, EEE, and firmware states. Linux r8169 loads the firmware blob and resets the device, concealing the state that the new driver must handle. Do not boot Linux during the notebook procedure. Collect the inventory from installed Windows, leaving only cold power and a Windows shutdown as the tested initial states.
* Give PXE one notebook session as an optional faster transfer path. Chainload iPXE `undionly.kpxe` from the firmware PXE ROM, fetch the kernel and module over HTTP, and boot them as multiboot inputs. This uses the firmware UNDI driver and therefore proves nothing about the Rach2 NIC driver. Insyde CSM PXE behavior is unknown. If it succeeds, transfer later builds over the LAN instead of rewriting the stick. Otherwise, continue using the stick.

## What the first inventory measured (Windows report, 2026-08-16)

The Windows checklist ran before the first stick boot and established the following facts. The XID and BIOS-page photographs remain for the notebook session.

* The MBR has two used entries: the 500 MiB System Reserved partition at LBA 2048, followed by C: over the rest of the 1 TB disk. Entries 3 and 4 are empty. The disk has no unallocated space, although C: has 844 GB free. BitLocker is disabled on every volume, and the notebook has no TPM. This determines phase E arithmetic: two free primary entries permit the shrink-and-partition branch. Extended-partition traversal is not used on this notebook and remains out of scope unless a later inventory differs. The report hashes all 512 MBR bytes, SHA-256 652ad40f..., which contain standard Windows boot code and disk signature 0x4905B015.
* The SATA controller uses AHCI mode: PCI class 010601, AHCI selected in BIOS, and the Intel iaStorA driver bound, with ABAR at 0xC061B000. The notebook previously lost its SATA link after a warm reboot with SATA link power management enabled. Firmware then found no disk and entered a PXE loop. The owner corrected this in Windows by disabling HIPM and DIPM. Rach2 does not enable link power management. If a warm reboot still leaves the link dead, phase D uses COMRESET for recovery.
* NIC resources are I/O 0x3000 with 256 B, MMIO 0xC0504000 with 4 KiB, and MMIO 0xC0500000 with 16 KiB, behind root port 00:1c.0. Following the reference, the driver reads BARs from configuration space and selects the first memory BAR by index. Windows enables MSI, EEE, Advanced EEE, Green Ethernet, and the adapter's ASPM registry option. This supports both plan decisions: reproduce the inherited EEE state for the baseline and disable ASPM explicitly.
* Fast Startup is enabled. A plain "Shut down" performs a hybrid shutdown, while holding Shift forces a complete one. The phase D entry-state boot and phase E partition rule account for this. BIOS 9ACN32WW is the newly installed final release for the board, with Back Flash disabled.
* VT-x is enabled, with no running hypervisor, virtualization-based security, or active DMA protection. The notebook boots through CSM. This indirect evidence indicates that DMA remapping is inactive; the BIOS-page photograph provides direct confirmation.
* The Ethernet cable was disconnected during collection, so no wired IP address, mask, gateway, or DHCP lease existed. WiFi showed LAN 192.168.0.0/24 with router 192.168.0.1. In the morning, select and reserve a wired address in the router, then pass it through `rach2.ip=`.

The source report, `Lenovo_G50-70_report_temp.txt`, remains untracked in the repository root and must never be committed. Delete it only after the milestone's hardware work is complete.

## Phase A: the local build, and the hardware inventory when the laptop arrives

Build one stick before the notebook session. Add a `rach2-metal` manifest containing BusyBox, Dropbear, `/etc`, and the authorized keys, but no `/src`, TinyCC, pdpmake, or install-kernel. Keep the image within a few MiB. Initially stage the strict `init-login` artifact. A new artifact in phase A would be a byte-for-byte duplicate of `init-login` because metal init does not supervise Dropbear until phase C. Phase C adds `init-metal` and changes the manifest to use it. Add the Makefile target and image-inventory integration, make `mkiso.sh` accept the profile with normal, verbose-diagnostic, and rescue-debug-shell menu entries, and update `make help`. The diagnostic boot prints the kernel end, each module range, reserved end, free-frame count, and the NIC's masked XID from `TxConfig`. This is a read-only PCI and MMIO inspection without a driver. If memory decoding is disabled, skip it with a diagnostic, and do not change PCI command bits. Reject overlapping modules and modules beyond the direct map. Local hardware cannot provide the target chip, so rehearse the inspection against RTL8139 in a scratch build. It must find the device, skip the I/O BAR for the memory BAR, map the window, read `TxConfig`, and reject the wrong XID. Only the 8168 response remains unrehearsed.

Collect the inventory from the notebook's installed Windows, which already produced the hardware report and can extract the checklist fields. Do not boot Linux. Its r8169 driver would reset the NIC and load firmware, adding another initial state to the experiment. Run the checklist as a Windows administrator. Record NIC and AHCI PCI identifiers, BARs, and capabilities; driver-reported link and Wake-on-LAN settings; SATA mode; Fast Startup state; and the installed BIOS version. Photograph BIOS pages for SATA options, boot order, PXE, WoL, and VT-d when present. Through a read-only physical-drive handle, first verify the 870 EVO model and serial, then read and hash the SSD's initial sectors, including the MBR and all four entries. Do not read the XID from Windows because it requires raw MMIO access that no stock tool performs safely. The Rach2 diagnostic entry reads `TxConfig` and prints the masked XID, supplying through read-only code the one value checked by the driver.

The build and inventory work are independent. Run the Windows checklist at any time and use its output for the plan's values. Write the stick when convenient because the hybrid ISO first boots in QEMU and then goes to the stick unchanged. Record the preceding state of each notebook boot. First boot the Rach2 stick from a cold power-off. Capture diagnostic VGA output containing layout values, PCI identities, and the XID, then require the normal entry to reach the RAM-machine login on VGA with the 8042 keyboard. Perform a second Rach2 boot after a normal Windows shutdown, the other expected initial state. Finally, remove the stick and boot Windows. Add the measured values, especially the XID, to this plan before phase B. A Linux live stick is no longer part of the normal procedure. Retain it as the escalation tool if the phase B no-firmware link attempt fails, to observe Linux behavior on this board, and as the phase E rescue medium.

* Host proof: check the manifest like every other profile, adding `rach2-metal` to the set-id sweep, and read the three menu entries back from the built ISO. Implement module placement as a pure function in `sys/mm/modlayout.c` with a host test. QEMU can produce only one of four failures: an oversized module supplied as a file. Show that case failing in QEMU with a diagnostic that identifies the rule and range. A bootloader cannot be directed to overlap two modules, overlap one with the kernel, or report a wrapping range. Construct those three cases in `tests/host/modlayout_hosttest.c`, along with accepted placements that are adjacent, out of order, or end exactly at the ceiling; an incorrect rule would panic on them.
* Notebook proof: retain the captures, login, boot order, and preceding-state log in the record, together with the Windows checklist output. A capture proves only the displayed state. This phase must produce measured facts.
* Readmes: document the metal-profile manifest and notebook procedure.

## Phase B: the driver interface, the chip model, and the first transmitted packets

Add the driver interface before new hardware code. Behind the existing `network/driver/` boundary, define device operations for transmit, poll, status, errors, and diagnostics. Move RTL8139 behind it without changing that driver. Replace literal strings and direct calls in `net_core.c` with interface operations. Keep every existing QEMU network suite passing.

Implement RTL8168GU transmission in the pinned three-stage order. Phase B has no timer hook, so transmission is bounded and synchronous: write the descriptor, ring `TxPoll`, poll `DescOwn` within a time limit, and ring again while the descriptor remains owned, following the reference's lost-doorbell rule. Phase C adds timer-driven operation. Also implement raw netconsole by copying the serial stream into constructed broadcast frames with EtherType `0x88b5`, sequence number, boot id, length, and checksum. It performs no allocation or ARP, does not recurse through driver logging, and uses a bounded buffer for output produced before TX exists. In `verify-host`, test the complete driver against a software register model. Cover access widths, completion-flag transitions, W1C status, the OOB handshake, both ordered resets, descriptor ownership and ring wrap, a lost doorbell, RX bursts with the 64-descriptor ring, bounded timeouts, and golden transcripts for the pinned sequence. Require the model to pass before visiting the notebook. It cannot prove PCIe ordering, DMA reachability, PHY behavior, or firmware requirements for this board, so assign those checks explicitly to the hardware session.

* Host proof: pass the model suite and every existing RTL8139 network probe and capstone. Capture and check netconsole frames from QEMU pcap through RTL8139, leaving only 8168-specific transmission for the hardware.
* Notebook proof: capture broadcast frames on the development host with source MAC `28:D2:44:7E:E0:AF`, ordered sequence numbers, and valid checksums, once with a gigabit peer and once with a 100 Mbps port. Require the VGA banner to report the XID, MAC, negotiated speed, and duplex. The capture proves transmission; a link LED proves only PHY operation.
* Shown failing: dropping one ERI write from the golden transcript fails the model. A crafted wrong XID ends probing with a diagnostic containing both values, while an alias differing only in unmasked bits is accepted. Suppressing the doorbell leaves the descriptor owned and fails the model TX case.
* Readmes: rewrite the network Readme driver section for the common interface and second driver.

## Phase C: RX, the stack on real addresses, and SSH

Deliver RX through the driver interface's `poll` operation on the existing 100 Hz tick. Bound work per tick, accept only single-fragment frames, remove the FCS, and reject and count receive errors. Move TX reclaim and repeated doorbell writes to the same tick, and answer ARP. Replace compile-time stack addressing with `rach2.ip=A.B.C.D/prefix` and `rach2.gateway=A.B.C.D`. Parse and validate them at boot into one immutable configuration read by every current consumer, including socket syscalls and `net_print_info`. Without options, retain the complete SLIRP tuple and byte-for-byte QEMU behavior. With `rach2.ip=` alone, configure no gateway because combining a real LAN address with the SLIRP gateway would be wrong on both networks. Add the board reset sequence in this phase because remote warm reboots are part of its development cycle. Under the board profile, write `0xFB` to port `0xB2`, then `0xCF9`, then issue the 8042 pulse. Add the third init variant only to `rach2-metal`, leaving strict os-real init unchanged. It supervises Dropbear with `dropbearmulti dropbear -F -R -g -p 22` alongside console login, applies restart backoff, tracks both children, reaps orphans, and retains the console as recovery. Because `-R` creates a temporary host key on each boot, use a separate known-hosts file for each harness run rather than disabling verification. DHCP and DNS remain out of scope; use numeric addresses. Measurements decide whether polling is adequate. A 64-frame burst at 100 Mbps must fit the ring and complete with zero drops. Sustained transfer at 100 Mbps must show a counter-verified drop rate below one percent because a correct final hash can conceal retransmission loss. Record the same measurements at gigabit, where drops are expected and quantified because 64 full frames arrive within a millisecond. An idle SSH session must echo a keystroke within 100 ms. If these limits fail, increase the ring size or polling rate and record which change was made.

* Notebook and development-host proof: capture the ARP exchange at the peer, ping in both directions, authenticate by key to an SSH PTY, transfer and compare a file in both directions, repeat connection cycles, and perform warm reboots over SSH. Mark cable disconnection and reconnection and cold power cycles as manual checks.
* QEMU proof: host-test malformed, duplicate, broadcast, network, and prefix-range addresses. Run the complete RTL8139 network suite with and without `rach2.ip=`, and test metal-init supervision. Rehearse the complete `rach2-metal` image with explicit address options, supervised Dropbear, key-authenticated SSH through a forwarded port, and a transferred and compared file. The notebook session then changes only the NIC and LAN.
* Shown failing: suppressing the TX doorbell fails netconsole capture. An invalid `rach2.ip=` leaves lower-layer netconsole operating while ARP and SSH fail. The host test rejects every invalid parser case.
* Readmes: document addressing in the network Readme, supervised mode in the Dropbear notes, and the remote-probe procedure in `tools/Readme.md`.

## Phase D: the remaining supported hardware, nothing written to the SSD

Complete the board profile after the phase C reset sequence. Power off through `0x1804` and `0x3C00`; perform a bounded ACPI-enable handshake when `SCI_EN` is clear; and keep IRQ 9 masked. Bound every physical-device poll. Command-line options must disable any absent device cleanly, and the kernel must boot with every subset of devices. Extend physical AHCI support through identification and reads. Add HBA reset and per-port COMRESET; the BIOS/OS handoff already exists in `ahci.c`. COMRESET also recovers the measured warm-reboot failure in which the SATA link remains dead. Scan ports while tolerating empty and ATAPI devices. Provide read-only diagnostics without mounting the disk because mounting a disk root writes its dirty flag, which this phase forbids. A `/proc` diagnostic or dedicated probe exposes identification data and sector hashes over SSH. Enforce the no-write rule where commands leave the driver. Under the metal build option, AHCI and ATA command allowlists reject `WRITE DMA EXT` and `FLUSH CACHE EXT`. A host test checks rejection, and an artifact check identifies the build policy in the image. Missing strings or symbols are insufficient evidence because command values are numeric and functions are static.

* Notebook proof: observe reboot and power-off, repeat cold boots, exercise keyboard and VGA, and have a person hear audio because SSH can prove only that the call returned. Record one Rach2 boot immediately after a normal Windows shutdown, including Fast Startup state, to test the NIC and platform states addressed by the OOB and reset sequences. Remove the stick and boot Windows.
* SSH proof: check all remaining behavior, including identification data and sector hashes against the Windows baseline from phase A.
* Shown failing: demonstrate reset in QEMU with the first two mechanisms stubbed. Test AHCI read bounds against a constructed host-test response. Run the artifact check against a deliberately incorrect image.
* Readmes: document the board profile and metal build option.

## Phase E: owner-approved persistence and the install flow

Phase E requires both the phase A MBR inventory and the owner's explicit approval after a complete SSD backup. Disable Windows Fast Startup before resizing. The owner performs the resize and partitioning with trusted tools. Preserve SSD boot code, every Windows file system except for the approved shrink, and Windows bootability. The partition table must change, and the approval must state that consequence.

The USB stick remains the only boot device. Add a FAT slots partition to the SSD for candidate, fallback, and `grubenv`, plus a KRFFS partition. Add a persistent GRUB entry to the stick that addresses SATA volumes explicitly. Use `search --fs-uuid` to select the slots volume. Give `load_env` and `save_env` an explicit path to that volume's `grubenv` because `$prefix` remains on the stick and would otherwise select the stick's environment file. Retain the RAM-rescue entry permanently on the stick. The kernel probes the new KRFFS partition contents for its root through `rach2.fsdisk`. `/dev/bootpart` selects the slots volume by FAT volume id through `rach2.bootuuid=` instead of assuming entry zero. Before any notebook attempt, test the complete layout with a two-disk QEMU fixture: USB GRUB, SATA slots and KRFFS, trial consumption, cross-device `save_env`, fallback, rescue, and swapped BIOS disk numbering. Apply the milestone 23 harness procedures to that fixture.

The inventory already determines the MBR arithmetic. Entries 3 and 4 are free, so use primary entries without extended-partition support on this notebook. Record but do not implement the general alternatives: bounded logical-partition traversal when only logical entries fit, or a written owner decision that the topology prevents installation when nothing fits.

* Proof: boot Windows after partitioning and on every start without the stick. ## Risks, in expected order

1. RTL8168GU initial state varies after Windows, Fast Startup, and firmware activity. Mitigate this with the OOB handshake, two recorded starting states (cold power and after Windows shutdown), per-boot provenance, and a firmware contingency with a recorded activation condition. Keep Linux off the notebook so its driver state does not enter the matrix.
2. Measure Insyde CSM behavior in phase A: USB-HDD selection, PXE behavior within a fixed time, the VT-d default, and WoL options. Assume VT-d is disabled, record its setting, and note that enabled DMA remapping blocks DMA.
3. The 32 MiB direct map limits module placement. Use a small image, print its layout, enforce boot checks, and retain `--quirk-modules-after-kernel` as the fallback.
4. Before SSH operates, every test requires a person at the notebook. Minimize visits in phases A and B. If the PXE trial succeeds, use it instead of rewriting the stick.
5. Available MBR entries on the Lenovo Windows disk determine phase E partitioning. If the topology prevents installation, require a written acceptance decision.
6. The 64-descriptor RX ring differs from the reference's 256 descriptors. Decide it through burst tests in the model and on the notebook. If it fails, use the reference geometry at greater memory cost.
7. Record provenance and licensing. The driver ports a pinned GPL reference into a project that already vendors GPL components. If activated, add the firmware blob only with its recorded terms. Include both decisions in the milestone record.

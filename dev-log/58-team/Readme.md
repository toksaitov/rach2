# The team workflow, tried end to end

On 2026-10-13 and 14 the workflow of `AGENTS.md` ran from the board to the Lenovo, with the five team accounts doing the work. The owner's session put small faults from the tree on the board as issues of phase #4, and each account's Claude Code, started as `claude -p` over SSH in a `tmux` session of its own, took the top Ready issue, fixed it, checked it, pushed, opened the pull request with auto-merge, and came back to it when it fell behind `master`, conflicted or failed. Then the owner's session ran the night's work: Codex's review of the phase's diff, the build from clean, the full set on both architectures, and a kernel update of the Lenovo. The first night's full sets failed, and the fixes of what they found went through the workflow again before a second night. The goal gave three to five hours from 10:27 UTC; the work ended at 05:36 UTC on the 14th, 19 hours later. This record gives what ran, what broke, where the time went and what the workflow costs, so that the next change to it starts from measurements.

## What ran

* In the first round thirteen pull requests merged, each from a branch named for its issue: the workflow's own setup (#1), two of the owner's fixes to the host's setup (#3, #10), and ten of the team's (#11 to #14, #19, #21 to #24, #30). From opening to merge they took 22 minutes at the least, 158 at the most, and 61 at the median.
* Three pull requests met a conflict with `master`, and their authors resolved it without help: d's in `.agents/skills/testing/SKILL.md` against #10, v's twice in `tests/Readme.md` against #22 and #21, and a's rebase of `tests/run` over #24, where a also checked that the two changes do not interfere.
* The team found and filed faults of their own: d's #15 (a run piped to `tail` stopped the `tail`) and v's #25 (the usb suite's hub-pull row failed once under a full ci pool), which v also judged to be outside the change and ran again; and later v's #46, the same row's failure for a cause v could not read.
* Codex reviewed the phase's merged diff in six units of at most six files each, and gave a seventh to the design of faster test runs. Its findings that held became seven issues, #16 to #18, #20, #26, #27 and #29; the first four were fixed in the same phase.
* The first night's work, at `a4bd4535`: the build from clean and `make machine ARCH=x86_64`, both exit 0; the Lenovo's kernel update through `bootctl kernel`, one trial boot, back in 20 seconds, and `bootctl commit`; the scripted metal acceptance, which passed at `f85d74c7` once #30 had merged; and the full set on both architectures under TCG. Each set passed 92 suites. On i686 `gnu` failed, and on x86-64 `gnu` and `grow`. Run alone, `grow` passed and `gnu` failed again. The night report is #33.
* In the second round the first night's findings, the review's and the faults found on the way went through the workflow again: fifteen pull requests, #35 to #59. The team's were d's #37, #41 and #57, s's #38 and #48, v's #43 and #47, m's #44 and #59, and a's #56. The owner's were this record's first form (#35) and #49, #51, #52 and #58, each written by a helper in the owner's session and checked there before it was pushed. From opening to merge they took 20 minutes at the least, 227 at the most, and 152 at the median.
* Codex reviewed the second round's merged diff, `a4bd4535..15d3ea4e`, in seven units the same way. Of sixteen findings, eleven held and became eight issues, #60 to #67, left for the next round. Five were rejected: `execq=` leaves its verdict to the run by design; a step that never ran is named with its number and text and has no seconds to give; an overlay's hard link to a file outside `mkext2.sh`'s private tree, which the one overlay does not make; a link's mode under umask on macOS, which does not build the overlaid image; and compiler search paths reaching the gnu image's build-host Python, which no gnu script exports.

The night report is #68.

## What broke, and what was fixed

* The demo keys were checked out with mode 644 by `actions/checkout`, and ssh refused them in the ssh and metal suites. `tests/run` now sets them to 600.
* `powershell.exe` fails when started from a directory inside another account's home, which is mode 750, so the free-space check failed in every account but the owner's. `tests/run` starts it from `/` (#3).
* `claude` was not on `PATH` for a command sent over SSH, since a non-login shell reads `.bashrc` alone. Each account's `.bashrc` and `/etc/skel/.bashrc` now add `~/.local/bin`.
* Two trees on one host forwarded the same host ports, and ci failed in the metal suite when two runs met. `tests/run` now claims one of ten 1000-port blocks for each run (#14), and the review's findings on the claim became #16, #17, #18, #20, #27 and #29.
* `metal_accept.sh` took an installed machine whose root is named by `GPTID=` for a stick boot, and failed two rows on the Lenovo, whose disk has a GUID table since its `--update`. The night's run found it; it was filed as #28, m fixed it with a GPT row in the installed acceptance and a mutation that drops the `GPTID=` form, and the fix merged as #30.
* The night's first full set ran under KVM, because its script was started through `testing.sh sh`, which does not set `RACH2_QEMU_ACCEL=tcg` as `testing.sh run` does. On this host's nested KVM the ext2 suite's zombie row took about 45 seconds against its 40-second step bound. Both sets ran again under TCG.
* Under TCG the gnu suite's `autotools` row failed at its 900-second bound on both architectures and when run alone. A run with the bound raised to 2400 seconds showed GNU sed's `configure` still at work after 870 guest seconds, and still to be followed by the `make` of sed. The bound was set under KVM, where `configure` takes about 50 seconds (`50-shortcomings/plan.md`, entry 294). With KVM the ext2 suite fails instead, so no single accelerator passes the full set on the testing host. This was #32. a measured the row under TCG on the testing host at 1706 and 1635 seconds on i686 and 1397 on x86-64, and #56 bounds it at 2700 seconds and prints each row's seconds beside its result.
* `grow` failed once in the x86-64 set, under the set's load: the guest's ATA driver reported "no answer in 500 ticks: status 0xC0" during the seed write, and the row, which does not watch for `machine-grow: failed`, waited for the runner's 300-second idle limit. It passed alone. This was #31: the IDE driver's sleeping wait is now bounded at thirty seconds, as the AHCI and NVMe drivers bound theirs (#38), and the harness ends an expect, boot or seen step as soon as a `--never` text appears (#37).
* The usb suite failed in ci four times in changes that do not touch USB: the hub-pull row three times and the row that pulls a stick during a read once. v made that row and the sixteen-device row independent of timing, and kept the harness's own lines of the pull rows (#47, for #25 and #45). The hub-pull failures were the row's first step, which waited out its 60 seconds for the shell's `Type 'help'` banner. A helper in the owner's session read ci's kept serial log and found the cause: a kernel record raised by an interrupt was printed inside the banner and split it. A record raised inside a line the debug shell prints is now held until the line ends (#49, for #46). Entry 38 of milestone 50 was the same fault in another form, a record splitting `AHCIPROBE OK`. ci keeps a failed suite's logs where only root can read them in WSL, so the team's accounts could not, and two of their investigations ended without the cause.
* Faults found on the way, each fixed in a pull request of its own: the gnu image's python recipe built its build-host Python against the target root's pkg-config files and i686 libraries, and failed a ci run of a change that did not touch it (#48, for #39); `mkext2.sh` staged group-writable directories from a tree checked out under umask 002, and `check-setid` refused the image (#51, for #40); the selftest's `hostpeer` rows bound the fixed port 47123, which two runner suites on one host share (#52, for #42); the harness reported how many steps failed but not which (#57, for #50), and its new report named the step in its own first ci failure; a sync from a tree without the Doom WAD deleted the host copy's WAD, and two syncs could both pass the check that the copy is free (#58, for #53 and #54); and a lock directory left with an empty owner file by an interrupted run refused every fault script (#59, for #55).
* Windows Update restarted the testing host at 22:46 UTC on 2026-10-13, as SYSTEM, for "Operating System: Upgrade (Planned)". It ended both runners' jobs, a team session with 35 minutes of x86-64 checks, and a helper's run. The runner services came back by themselves; the run that had been in progress stayed in progress on GitHub until it was force-cancelled. The host has no active hours or restart policy that keeps it up at night, and setting one is the owner's.
* From 03:00 to 03:04 UTC on the 14th both runners lost their connection to GitHub's run service, their requests timing out, with the host up and GitHub reporting no incident. A job queued then was cancelled as "not acquired by Runner of type self-hosted", and ran again once the runners came back by themselves.
* The owner's dispatcher, the loop that sent an author back to a pull request that fell behind, conflicted or failed, missed conflicts at first, and later started two sessions for one head when GitHub reported it first as behind and then as conflicting. It then keyed each dispatch on the pull request's head commit and one of two reasons, update or failure, and was replaced at 21:44 UTC by the merge queue described below.
* A `claude -p` session does not exit while a background `Monitor` it started is still running; a leftover `tail -F` kept one alive until it was killed.
* `gh project item-list` shows a new item minutes late; a session that picked its task from that listing skipped #17. The GraphQL `projectItems` of the issue is current.

## The overrun

The first round alone took the five hours, 10:27 to 15:20 UTC, and the work ran on for 14 hours more. The time went to these, the largest first:

* Strict up-to-date merging on two runners. Each merge makes every other open pull request behind, and its run starts again on the new `master`. With six or more pull requests open they land one per ci round of 20 to 35 minutes, and the second round had fifteen.
* A night started with a known fault. The gnu suite's bound had been on record as entry 294 of milestone 50 since 2026-10-04, so the full set could not pass on this host, and the night found it again. The fix was one number, but measuring it took a gnu image built in an account and runs of 30 to 50 minutes under TCG.
* ci failures outside the change: the usb suite four times and the gnu suite once, each costing a run and a session for its author.
* Work held back. Twice, issues sat in Backlog while accounts were idle: from 19:15 to 20:20 UTC, held for the night's sake, and from about 23:00 to 00:00 UTC, filed by the helpers and not moved to Ready.
* The owner's session itself: the first full set ran under KVM because its script did not set the accelerator `testing.sh run` sets; it called the first night finished with both sets failing; it watched the work through one-minute polls of SSH and `gh` that timed out under load; its dispatcher missed conflicts, started two sessions for one head and once started a session with an empty prompt; and for three hours after the queue took the rebase over, the prompt that sent authors back still told them to rebase, so four pull requests were up to date and in ci at once on two runners.
* The host's restart at 22:46 UTC and the runners' four minutes offline.

## The merge queue

GitHub's merge queue is not available to this repository (item 5 below), so from 21:44 UTC the owner's session ran one of its own, a shell loop over `gh pr list`:

* One pull request at a time is brought up to date with `master` by `gh pr update-branch --rebase` and run; the others are left behind, so no push cancels their runs. Auto-merge lands it when its run passes.
* A conflict or a failed run sends the author back, once for each head commit. From 00:50 UTC the author was told to leave the rebase to the queue, and to push nothing for a failure outside the change; the queue runs such a failure again in its turn, once the author's session has ended.

From 21:44 to 03:31 UTC it landed eleven pull requests, one every 32 minutes, with the restart and the outage inside that time. Before it, from 18:00 UTC, nine runs (203 runner minutes) were cancelled by a later push against six that passed (226); under it three were cancelled (42 minutes), one superseded, one queued behind `master` and one never acquired, against seventeen that passed (465). A faster run on the second runner, an author's own push or a new pull request could still overtake the queue's head, whose run was then behind and lost; and a cancelled run kept its runner for five minutes while `tests/run` stopped its machines.

## What the workflow costs

* ci is `make test` on two runners of the testing host, 17 to 20 minutes for one run alone and 25 to 36 minutes with both runners and the team's own suites on the host.
* Strict up-to-date merging lets one pull request merge per ci round: each merge makes every other open pull request behind, its author rebases, and ci runs again. Of the runner minutes spent on pull requests by 15:20, 338 went to runs that passed, 318 to runs a later push cancelled, and 54 to failures.
* A rebase took an author's session 5 to 20 minutes, because each one ran `tests/run style` and its suites again before pushing.
* Use of the subscription was small: each account's five-hour window stood at 2 to 5 percent at the end, and the 44 sessions together came to about 33 dollars at API prices.

## Where a ci run's time goes

The run of #21 took 17 minutes 18 seconds, with the host's load average near 4 of its 32 threads:

* `style`, 162 seconds, then `host`, 409 seconds, then the core pool: `make test` runs three `tests/run` commands one after another (`Makefile:966`), and `run_set` would run style and host before the pool even in one command (`tests/run:979`).
* `host` runs its 156 tests one at a time; `exfat_hosttest` takes 160 seconds and `fat32_hosttest` 103.
* The pool, 12 suites at once under TCG, ends 35 of its 36 suites in 3.7 minutes. The runner's selftest takes 313 seconds; it is line 122 of the 128 in `tests/registry`, whose order is the schedule, so it starts last and runs alone at the end.
* The pool is not short of memory: the core suites declare 8576 MiB in all against a budget of 24576.

The machines boot under TCG because the ATA driver polls a status port after every sector it writes, and on this host each poll is an exit through two hypervisors (`tools/Readme.md`).

## What would make it faster

Only the fixed port of item 12 is changed. In order of the time saved for the work, with the arithmetic from the run above:

1. Start the longest work first: `runner` at the top of `tests/registry`, `exfat_hosttest` and `fat32_hosttest` first in `host.sh`. Up to two minutes, for a few lines.
2. Run style, host and the pool at once after one shared build, and give `host.sh` a bounded queue of jobs, launched through `runutil` so that each test's signal dispositions are reset, which `pwauth_hosttest` checks. The 884 seconds of serial work become about 313, the runner's selftest, and a run about 6 to 7.5 minutes.
3. Split the runner's selftest into independent scenarios with fixtures of their own, keeping together those that test an order. Four groups bring it from 313 seconds toward 80, and the pool then ends with its next longest suite, at about 222.
4. Shard the exFAT and FAT32 interruption matrices by cutoff, with a check that the shards' case identifiers together are the original set, and keep the pristine fixture image instead of building it again for every load.
5. Stop discarding ci work. Without a change to the host, a dispatcher can rebase only the pull request whose ci ends next. Dropping strict up-to-date merging is cheaper still, since a `pull_request` run already tests the pull request merged with `master` as it was when the run started; a run on `master` after each merge and the night's full set would catch two changes that pass apart and fail together. GitHub's merge queue is not available to this repository while it is private and owned by a user: GitHub offers it to an organization's public repositories, and to its private ones on Enterprise Cloud. The queue of the second round was the first of these, run by hand.
6. Skip a suite whose inputs are unchanged since it passed. The runner already hashes each run's scripts and products (`tests/run:830`); a pass recorded under those hashes would let a pull request that changes only documentation skip the suites, as Bazel does with `--cache_test_results=auto`. Only passes are recorded, so a failure always runs again, and the night's full set runs without the record.
7. Disk images by reflink or qcow2 overlay instead of whole copies in the ssh, metal and crash suites, as grow already does with backing files; one overlay must last through a sequence that tests persistence.
8. KVM for the suites that do not write a disk by PIO, with TCG kept for the rest and for the processor behaviour the two differ on, such as debug watchpoints; each suite measured first. A write path in the ATA driver that completes by DMA or by interrupt would take away most of the exits, make KVM usable for every suite, and help the driver on real hardware too. A native Linux on the testing host would give first-level KVM. Until one of these is done, the gnu suite has bounds measured under TCG (#56).
9. Boot once and restore a saved machine state for the suites that boot many similar machines, such as usb and memory; cold boots stay for start-up, memory maps, enumeration, recovery and persistence. Restored clones need fresh entropy and a network identity of their own, as the Firecracker work on snapshot uniqueness describes.
10. A network namespace for each suite would let every machine forward the same ports and end the limit of ten blocks, but saves no time today; Ubuntu restricts unprivileged user namespaces through AppArmor, so it needs a profile.
11. Two runners on one host add places in the queue, not processors. Once a run is parallel inside, a host-wide budget of processors, compilers and disk writers across ci and the team's accounts is worth more than a third runner.
12. Two smaller faults in the runner bear on this: the selftest's `hostpeer` rows used the fixed port 47123, outside the table, so two runner selftests at once collided, which #52 fixed; and `tests/run` takes KVM whenever `/dev/kvm` opens, so a script that forgets `RACH2_QEMU_ACCEL=tcg` gets the slow path, as the night's first set did.

# Milestone 41: hubs

A USB hub works. The controller interface describes a device by where it is in the tree and not only by a root port, the core enumerates a hub's ports the way it enumerates the root controller's, and a hub class driver powers, resets and watches those ports; a keyboard, a mouse and a stick behind a hub, and a keyboard behind a hub behind a hub, are devices this kernel drives, and a hub pulled takes everything below it down, children before their hub, exactly as a stick on a root port goes. QEMU's hub is a full-speed USB 1.1 hub, so QEMU proves the tree, the route string and the hub protocol; the transaction translator, which a low-speed keyboard behind a high-speed hub needs, is written into the slot context and checked against the specification by the host test, and only the notebook can prove that a controller schedules from it. That proof, the owner's hub carrying their keyboard, mouse and stick at once, is written into the metal acceptance and run in milestone 43. Nothing touched the Lenovo.

## What was built

`hcd.h` gained `struct usb_location`, the tree address: the root port, the depth, the route string with four bits for each hub tier and the port on the hub nearest the root lowest, and for a low or full-speed device below a high-speed hub the handle and port of the hub that translates for it. `device_open` takes it, `device_hub` is new, and `xhci.c` writes the three location words of the slot context in one function for every command that carries them: the route string, the multi-TT bit, the hub bit and the port count, the root port, and the translator's slot and port, with a high-speed hub's think time in its own context. `device_open` returns an error for a sixth tier and for a route with bits above its depth; twelve slots and twelve device entries, from the notebook's inventory with headroom.

`core.c` puts a device's port behind a vtable, the controller's for a root port and the hub driver's for a hub port, so the debounce, the reset, the addressing and the descriptors are one state machine for both. A device's location is built from its hub's, walking up to the nearest high-speed hub for its translator. Class 9 is matched to the hub driver, and a SuperSpeed hub, protocol 3, is refused by name. A hub's ports are refused on the hub's own bitmap. `device_gone` closes a device's subtree before the device, a closing hub waits for its subtree before it asks for its slot back, and a hub's report of a connection change closes what was on the port before what is there now is looked at. Records name a device by its path, `5.2` for port 2 of the hub on root port 5, and `/proc/usb` gives the same path.

`hub.c` is the class driver, a state machine over one control request at a time per hub, stepped from the pump. It reads the hub descriptor, selects a translator per port where the hub has them, tells the controller through the core's command turn, powers the ports as the descriptor's mode says, waits the power-good time, reads every port's status once and acknowledges the change bits it finds, and then keeps a transfer on the change endpoint: its bitmap names the hub and the ports with something to report, each is asked for its status, every change bit is acknowledged with its own request, and the core is told. It runs a port's reset for the core, reads the speed from the status word, records an enable lost, powers a port off for an over-current and on again once after a second, and gives a hub up by name when its descriptor, a port's power, its change endpoint or any request fails.

## What running it found

The hub reports a device present at its first scan and then reports the same connection again through the change endpoint, since the connection change bit set at power-on is still set; every device behind a hub arrived twice, which showed only when the table was full. The first scan acknowledges what it finds before the change endpoint is read.

The USB suite had used QEMU's hub as its stand-in for a device this kernel cannot drive; a HID device with no boot protocol stands in now. And a probe run in parts cannot run on the harness kernel, which ends the machine at its first process's exit.

A hub with three devices behind it comes up under QEMU in about half a second from the hub's own enumeration; each device behind it is a few dozen control transfers through the one command turn.

## What the review found

The round at the close was two Codex units, one over the reader-facing documents and one over the driver, the core's tree, the controller's words, the host test, the suite's boots and the acceptance script. The documents unit found seven claims the code contradicted, two of them defects in the code: a hub that refused a translator per port had its children opened with the multi-TT bit anyway, and an over-current present at a hub's first scan was recorded and not acted on. The code unit found nine defects, all confirmed: a device pulled while its Enable Slot was in flight lost the slot and, with another command in flight, held the command turn forever; a completion taken in the pump of a disconnection was handed to the next device in that entry; a full completion queue dropped a transfer event, which for a hub's change endpoint was a hub that never reported again; a device behind a hub that found the table full was never retried; a refused power-on after an over-current left the port neither on nor off; the hub-pull rows counted closes asked for and not slots given back; and the acceptance script took a hub that failed after recognition for no hub. Each fix has a row that fails without it, except the stale completion, which is recorded as fixed by inspection. `notes.md` has every finding with what changed.

## Verification

`tests/run host` runs `hub_hosttest`, new: the core and the hub driver over a model of a tree, where the controller stubs give a slot for a location and the model answers on it as what sits there. Its rows are the descriptor read and the port count told, a full-speed hub told nothing of translators and a multi-TT high-speed hub told its translators and think time with a low-speed device below it carrying the hub at its port, the three power modes, the power-good wait before the first port is read, a device found by the scan and enumerated at its location, a reset that completes and one that never does with the port refused until its device leaves, the speed from the status word, a disconnection closing the device below, a hub pulled with two devices below closing both before itself, twenty ports told as fifteen, a hub that will not give its descriptor, the change endpoint out and out again after each answer, a device plugged in after the hub is up, the hub's own status, a swap closing the old device before the new, an enable lost, an over-current powered off, retried once and left off, the multi-TT setting selected or refused, and a stalled change endpoint closing the hub. `xhci_hosttest` gained twelve rows for the location words. `tests/run usb` is nineteen boots, five of them the tree.

Every check added here was proved by a mutation that makes it fail: four for the location, four for the core's tree of which one is recorded as uncatchable because a pulled hub's children also leave through their port status, seven for the driver, each failing exactly its row, with the reset change caught by the reset row rather than the second connection the plan named, and seven for the review's fixes. Two mutations first failed to build and were re-made in forms that build; one row was strengthened after its mutation escaped.

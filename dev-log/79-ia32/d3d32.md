# i386 Direct3D on lavapipe and Venus

Task 79-8d runs the i386 builds of 76-21's Direct3D 9, 11 and 12 probes through GE-Proton11-12 in both of Proton's modes for a 32-bit program: WoW64, an x86-64 process of the x86-64 Wine, and the default, an i386 process of the i386 Wine on the root's i386 layer. On lavapipe they go through DXVK and vkd3d-proton, 6 rows of the `d3d` suite; on Venus through DXVK and vkd3d-proton and through WineD3D on Vulkan with Wine's vkd3d, 12 rows of `d3dvenus`. Each row is judged against the Debian reference guest's run of it in the same QEMU profile ([the graphics Readme](../../tests/graphics/Readme.md#i386-direct3d)).

## Where the rows live

The task named `tests/cases/guest.ia32.json` for its cases. They are in the `d3d` and `d3dvenus` families instead: each boots the GNU root with the Direct3D payload's disk, 8 CPUs and 16 GiB, as those families' cases do and as the `ia32` family's direct boots of the test image with 128 MiB do not, and their registry lines already declare the memory and `mke2fs` that a case of 17 GiB needs.

## Linux's runs

The Debian guest ran all 18 rows twice on 2026-11-10, and all 36 runs drew and read both pixels back right ([the runs](../../tests/graphics/ref/d3d32-wsl/Readme.md)). Linux runs every row, so every row is registered; nothing is refused. On Venus each i386 row draws with Mesa 26.1.6's `VK_EXT_map_memory_placed`, which 77-7a found WoW64's mappings need: the WineD3D and Wine vkd3d rows under WoW64, which failed under Mesa 25.0.7 with "does not fit 32-bit pointer", draw.

The guest has no i386 libraries of its own, so `reference.sh` installs the root's i386 layer in it before a list with a row in the default mode (`d3d/i386.sh`). A first try had the three default-mode rows on lavapipe refused by `run.py`, which wanted an i686 lavapipe ICD: Debian's `lvp_icd.json` names its library alone and is shared by both architectures, as the root's is, so there is none, and `run.py` now takes it for both.

## The probe cannot read its own map

The first probes printed the Unix half of Wine they ran on, read from `Z:\proc\self\maps`. Every one printed none. A 32-bit `cmd.exe` that typed the same file showed the map of `files/bin/wineserver`: Wine's server opens a file for its clients and passes the descriptor back, so `/proc/self` is the server's. 79-8c's row met the same and reads the program's map from outside while it waits. The probes now do likewise: with `PROBE_HOLD` set a probe prints `hold` and waits for the file it names, and `run.py` reads the executable's ELF class and the map of the process of the probe's name that has that variable, then makes the file. In every Debian run each WoW64 probe was a 64-bit process with `x86_64-unix/ntdll.so`, and each default-mode probe a 32-bit one with `i386-unix/ntdll.so`.

## apt's warning

The first try of the second Venus run drew all 12 rows, but its guest printed `W: Tried to start delayed item ... libllvm19 i386 ..., but failed` at least 453,439 times after apt's install had succeeded, past the 64 MiB of standard error that `etude admit` lets a run have, and the run was refused. `i386.sh` keeps apt's output in a log in the guest now. The fault is in [upstream.md](upstream.md#apt-repeats-a-warning-about-a-delayed-download-after-its-install-has-ended).

## Rach2's first run was under TCG

The first run of the 18 rows on Rach2 ran under TCG, since the account's shell sets `RACH2_QEMU_ACCEL=tcg` for the suites that boot faster so, and a graphics run asks for KVM only through that variable ([the graphics Readme](../../tests/graphics/Readme.md#accelerators)). Under TCG with the testing PC's load at 15 to 26, a Wine prefix took some 2.5 min and explorer.exe missed Wine's 10 s for the desktop: 10 rows lost it on each of their three tries and failed, and 6 passed. Two more failed with the program running, both Direct3D 9 in the default mode, and the one of them run again under KVM failed again, as below. Graphics rows run under KVM, as the last run below did.

## Wine's fsync could not map its first page

In an i386 Wine, Proton's fsync maps its shared memory a page at a time, and the first map failed: the Proton log had `err:fsync:get_shm Failed to map page 0 (offset 0)`, and the kernel then killed the process for a write at 0x19B, which is -1, the address mmap failed with, plus 0x19C; Proton's exit was 245, 256 less SIGSEGV. WineD3D's Direct3D 9 on Venus died so under TCG, and DXVK's on lavapipe, which under TCG ran on to read back zeros after `DxvkSubmissionQueue: Timeout occured, GPU likely hung.`, died so under KVM.

The cause is where Rach2 put a mapping without a hint: in the highest free range below the mmap base and above the heap's top. Linux searches down to the bottom of user space, and above the mmap base when that fails. An i386 Wine starts in `wine-preloader`, a static program at 0x7D400000, so its heap starts just above that, moved up by as much as 32 MiB. The preloader's table, read from the binary, reserves 0x110000 to 0x68000000 and 0x7F000000 to 0x82000000, and the map failed although Rach2 searched up to 0xF7FFE000, so nothing above 0x82000000 was free either. Rach2 offered the 0 to 28 MiB between the heap's start and 0x7F000000; Linux offers the 340 MiB between 0x68000000 and the preloader as well. `mmap_free` now searches as Linux does, and vmprobe's `below-break` takes the room between the heap and the mmap base and checks that the next mapping goes below the heap. With the change both rows drew under KVM.

## Rach2's run

With the change, the 18 rows ran on Rach2 under KVM in one `tests/run d3d d3dvenus` of 2026-11-10, with `RACH2_QEMU_ACCEL=kvm`, from 18:19 to 18:49 with vmprobe beside them, and all 18 matched Linux's references: each probe drew both pixels, its process was the mode's, and its adapter Linux's. No row lost its desktop.

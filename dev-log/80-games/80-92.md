# Crysis's level load against Linux's in QEMU

Task 80-92 (issue #4159) measured where the island level load of 64-bit Crysis spends its time on Rach2 against Linux in QEMU, and fixed what Rach2 did slower, in five passes. On the testing host on 2026-11-12, at the milestone branch's head of 09:57 with the block layer off the big lock, the load took 11.45 s and 10.90 s on Rach2 against 8.97 s and 8.59 s on Linux. The third pass built the kernel at `-O2`, as Linux is built, and cut the AHCI driver's register accesses to Linux's: the load then took 9.14 s to 9.69 s on a quiet host, against 8.47 s to 9.54 s for Linux in the same hours. Before the first pass the same harness measured 15.4 s to 19.4 s on Rach2 against 8.4 s to 9.3 s on Linux. In the fifth pass, on 11-13 at the milestone's head of 11-12 23:37, Rach2 took 8.94 s to 10.13 s, median 9.18 s, against Linux's 8.61 s to 9.25 s, median 8.76 s. The load was then close to Linux's range but not reliably inside it. In the sixth pass, on 11-13 at the milestone's head of 11-13 07:41, after 80-94 to 80-97, Rach2 took 8.07 s to 9.30 s, median 8.47 s, against Linux's 8.36 s to 11.33 s, median 8.70 s, in the same hour: the load in QEMU is within Linux's range. The same pass found and fixed a fault of 80-97's idle tick in the processor-time account, below. What is left is the one load on the Lenovo, which [80-92/lenovo.md](80-92/lenovo.md) prepares.

## The measurement

[crysis-load.py](80-92/crysis-load.py) boots the GNU root of the release's `gnu-test.disk`, which carries GE-Proton, under Rach2's kernel or under Debian's (`build/cache/debian-ref/prepared.qcow2`, kernel 6.12, the game in a chroot), with a 14 GiB ext2 data disk that holds the game, the island's save and a Wine prefix and shader cache a Linux run had warmed. Each run takes copy-on-write overlays of the disks, so every run starts from the same state. It starts the game with `+load` of the save, times the load from Game.log's "Successfully activated profile" to "Level island loading time", and powers the guest off. QEMU runs with KVM in WSL 2 on the testing host, four processors and 4 GiB, so the guest is nested under Hyper-V and every VM exit is costly. Around the load the script reads `/proc/stat`, `/proc/vmstat`, `/proc/diskstats` and each thread's `stat`, and with `VIEW_PROF=1` Rach2's `bkl/calls` and its profile in whole-kernel mode. [crysis-load.sh](80-92/crysis-load.sh) runs it as one claim of the testing host's admission ledger. Paths in both are the testing host's.

The profile that names where the main thread's kernel time goes came from a test kernel that [profile-tid.py](80-92/profile-tid.py) patches: it samples one thread, user ticks as one bucket, and was never committed. [prof2.py](80-92/prof2.py) ranks its samples by caller chain, [calls.py](80-92/calls.py) ranks `bkl/calls`, and [tasks.py](80-92/tasks.py) gives each thread's user and system ticks over the load.

## Where the time went

The load is single-threaded at its core: Crysis's main thread reads the level's archives through Wine. On Linux that thread used 5.3 s to 6.1 s of user time and 1.7 s to 2.0 s of system time in an 8.4 s to 9.3 s load. On Rach2 before the fixes it used 6.9 s of user time and 10.0 s of system time. User time summed over every thread was the same on both systems (13.8 s against 13.8 s in the runs of [rach2-after](80-92/evidence/rach2-after/) and [linux](80-92/evidence/linux/)), so the kernel holds the difference.

The disk was the first excess. A file read in order filled a run of up to 1 MiB of the buffer cache at every second block, where Linux's readahead window is 128 KiB: Rach2 read 1,160 MB from the data disk during the load against Linux's 358 MB, and 1.29 GB before the load against 180 MB.

The main thread's kernel samples then fell into these groups ([before](80-92/evidence/rach2-before/), 13,118 samples of which 6,598 were user time):

| Group | Samples | What |
|---|---|---|
| read | 2,004 | 845 in `req_run_one`, 563 of them with interrupts off while a request's buffer was mapped or unmapped |
| openat | 988 | the full path walk, under the big lock |
| getdents64 | 883 | 148 in zero-padding each entry's 256-byte name |
| newfstatat | 709 | the path walk and the entry's wait for the big lock |
| getrusage | 497 | 460,000 calls, half of each spent waiting for the big lock |
| page faults | 346 | 173 zeroing frames, which Linux also does |

Two experiments ruled causes out. Transparent huge pages are on in Debian's kernel (272 MiB of anonymous memory in 2 MiB pages during the load); with them off Linux loaded in 8.93 s and 9.01 s, so they are not its lead. The TSC as Rach2's clock in place of the HPET (`rach2.tscreliable`), which shortened the tick's hold of the big lock from 26 us to 19 us, gave 19.96 s and 15.46 s, no change beyond the runs' spread.

## The fixes

* The buffer cache reads at most 128 KiB in a run, Linux's default readahead window (`VM_READAHEAD_PAGES`, include/linux/pagemap.h:1375). A window that grows from 16 KiB as Linux's `get_next_ra_size` grows it (mm/readahead.c:361-391) measured worse, 19.8 s and 19.0 s, because the file page cache asks the buffer cache for one page at a time and each step of the ramp became a request. After the fix the load read 375 MB in 4,554 requests, against Linux's 358 MB in 3,626.
* A disk file's shared pages are found in a table of 256 buckets by inode number, not by a walk of every shared file at each read.
* A request of 2 to 32 pages takes a kept buffer of 32 pages, and a freed one is kept mapped, up to four. Each request had mapped 32 fresh frames and on completion unmapped them, flushing each page and every processor's TLB, with interrupts off; Linux reads into the page cache's own pages and maps nothing per request. `req_run_one` fell from 845 samples to 245.
* `getrusage` runs without the big lock for `RUSAGE_THREAD`, which reads only the calling thread's counters, as Linux's `getrusage` (kernel/sys.c:1825-1829). Its 717,548 calls in the next run held the lock for no time.
* ext2's `readdir` copies a name by its length, as Linux's `dir_emit` (fs/ext2/dir.c:311).
* The path walk asks whether a component lies toward the working directory only after its search check fails; the question scans the path and the working directory's path.
* A user copy's prefault answers with one check when every page is present and allows the access, where it resolved each page and then checked the range again. Linux's `copy_user_generic` checks nothing and resolves only a page that faults (arch/x86/include/asm/uaccess_64.h:119-131).

## The second pass

The second pass ran on the milestone branch of 11-12 05:56 and then of 08:14, with two changes to the harness. The data disk is made without `dir_index`, which Rach2's ext2 refuses to write (`tune2fs -O ^dir_index` and `e2fsck -fyD` on the images; Linux's runs after the change load as before), and `VIEW_PROFNAME` profiles a thread by name. Four counters a test kernel printed in `/proc/stat` showed where the main thread still took the big lock.

* The cached walk crosses a covering mount, as Linux's `__follow_mount_rcu` (fs/namei.c:1521-1563), so a path under `/data` no longer leaves it at the mount.
* It follows a link whose target the inode holds, ext2's fast link, as Linux's walk under RCU reads `i_link` (fs/namei.c:1860-1870).
* inotify's read, open and close hooks take the big lock only while a watch is on the file's own file system, as `fsnotify_sb_has_watchers` (include/linux/fsnotify.h:34-37).
* After an absolute link the cached walk jumps to the caller's root whatever slashes the spliced path begins with, as Linux's `pick_link` calls `nd_jump_root` (fs/namei.c:1877-1882). Wine's `dosdevices/z:` is a link to `/`, so every Windows path through `Z:` spliced to `//data/...`, which the walk handed to the full walk under the big lock: 292,000 of them during the load, against 1,051 the cached walk finished. With the fix none went to the full walk.
* A read of a disk file takes the big lock only while a shared mapping may have stored into its file's pages, by a count in each of the 256 buckets of mapped files. Before, any mapping of any disk file put every read under the lock, and Wine always has one: 160,700 of the load's 160,900 file reads took it. Linux's `filemap_read` reads the file's own folios without a lock of the kind (mm/filemap.c:2614-2700). The reads that hold the big lock fell from 175,000 to 44,000 in a load.

|---|---|---|

| With the jump to the root | 10.88, 10.83 | 8.53, 8.55 |
| With the read's gate on shared mappings | 10.98, 10.84 | 8.49, 8.35 |
| The milestone of 08:14 merged | 10.77, 10.77 | 8.30, 8.61 |

The TSC as Rach2's clock (`rach2.tscreliable`), which Linux picks in this guest over kvm-clock and the HPET, gave 11.44 s against 11.68 s and 12.04 s for the HPET in the same hour, within the spread.

## The third pass

The third pass ran at the milestone branch's head of 11-12 09:57 (`8cfc7e929`), which has the buffer cache's requests and AHCI's interrupt off the big lock (84-20), each wait queue's own lock (84-14) and x2APIC (84-16). Rach2 took 11.45 s and 10.90 s, Linux 8.97 s and 8.59 s. The main thread used 6.38 s of user time and 4.10 s of system time on Rach2, 5.65 s and 1.67 s on Linux.

The kernel was built without optimisation: `rach2/Makefile` passed no `-O` flag, where Linux builds at `-O2` (Makefile:813). A kernel built with Linux's `-O2 -fno-strict-aliasing -fno-delete-null-pointer-checks` took 9.27 s and 9.23 s against Linux's 8.33 s in the same hour, and the main thread's system time fell from 4.10 s to 2.78 s. The kernel is now built so, with the frame pointer kept (`-fno-omit-frame-pointer -fno-optimize-sibling-calls`, Linux's Makefile:851) for the profiler and the panic's backtrace. GCC's flow analysis at `-O2` found seven sites, none a fault the kernel meets: four locals it could not prove set (ext2's unlink and rmdir, HDA's verb wait, KVM's VM descriptor, i915's relocation offset), a 4,320-byte frame in the wireless association builder once it inlined its element builder (`K_NOINLINE` now), an array parameter of the wireless work kick that it took for a region of 40 bytes, and i686's write of the BIOS reset flag at 0x472, which it took for a store through a null pointer. Every kernel the tree builds, the ordinary, lock-order, recovery, read-only and 64-bit-only ones on both architectures, compiles clean under `-Werror`.

Each disk request cost more register accesses than Linux's, and in a nested guest each is a VM exit. The interrupt read every disk's PxIS, then PxCI, then PxIS and PxTFD again to judge the command, then read and wrote PxIS and wrote IS: nine accesses for three disks, where Linux's `ahci_single_level_irq_intr` reads IS, reads and clears the port's PxIS, reads PxCI and writes IS back (drivers/ata/libahci.c:1970-1979, 1875-1898, 2023-2056), five. The issue cleared PxIS before writing PxCI, where `ahci_qc_issue` writes PxCI alone (libahci.c:2061-2084). Each read also evicted its whole buffer from the cache, 2,048 `clflush` for a 128 KiB run, inside the interrupt, where x86 DMA is coherent and Linux's DMA sync does nothing (kernel/dma/direct.h:56-75). The driver now takes the interrupt in Linux's order, judges a completed command by the status of the D2H register FIS in the port's FIS area, issues by PxCI alone and evicts nothing. With it the load took 9.14 s and 9.26 s against Linux's 9.04 s.

The testing host's load from other accounts moved every figure that afternoon, Rach2's more than Linux's, so the later runs alternate the kernels:

|---|---|---|
| The milestone of 09:57 | 11.45, 10.90 | 8.97, 8.59 |
| The same, TSC as the clock | 11.49, 11.74 | 8.67 |
| `-O2`, a test build | 9.27, 9.23 | 8.33 |
| `-O2` and the AHCI changes | 9.14, 9.26 | 9.04 |
| The same, alternating, host load 7.5 then 3.6 to 4.2 | 10.67, 9.48, 9.47 | 8.52, 8.47, 8.83 |

| The same, with Linux's huge pages on and off, alternating | 9.32, 9.69 | 9.54, 8.96 on; 8.98, 8.79 off |

Two causes are ruled out. The clock: with the TSC in place of the HPET (`rach2.tscreliable`) the load is no faster, though a disk request reads the clock five times, four in the block layer and one in the interrupt. Transparent huge pages: Linux with them off loaded in 8.98 s and 8.79 s beside 9.54 s and 8.96 s with them on, so in today's runs they are not what Linux is ahead by.

The main thread's profile at `-O2` with the AHCI changes ([rach2-o2](80-92/evidence/rach2-o2/), 9,057 samples in a 9.34 s load, 6,538 of them user time) has `read` at 989, of which 383 land where the thread is switched back in after its disk wait and 146 in the PxCI write that issues the command; page faults at 284, 220 of them zeroing frames; getrusage 233, getdents64 219, newfstatat 161 and openat 156. The thread used 6.42 s of user time and 2.68 s of system time, against Linux's 5.75 s and 1.95 s in the same hour.

In about half of Rach2's runs the data disk took 460 to 1,270 writes of 8.5 MB in all during the load, each with its flush, 1.3 s to 4.3 s of write time summed, and in the rest almost none; Linux wrote twice, since its page cache holds dirty data for 30 s before writing it back. The runs with the writes were not the slower ones, so they are not shown to delay the load.

## The fourth pass

The fourth pass ran at the milestone branch's head `b3ef47abf` on 11-12, Rach2 and Linux alternating in the same hour on the testing host with the same island save. With the host's load at 10, Rach2 took 11.98 s and 11.48 s, Linux 10.09 s and 10.03 s. With the load at 6 to 9, over eleven runs each, Rach2 took 9.22 s to 10.99 s, median 9.62 s, and Linux 8.62 s to 9.54 s, median 9.21 s. Rach2's spread is the wider one, and its fastest runs are within Linux's range.

Over the load the main thread used 6.44 s to 7.43 s of user time and 2.10 s to 2.60 s of system time on Rach2, against 5.64 s to 6.45 s and 1.79 s to 2.28 s on Linux, about 0.9 s more CPU, most of it user time. It took 180,000 minor faults against Linux's 150,000. A full `strace -f` of both shows the same work: the main thread makes about 224,900 system calls on each, and the game looks up the same shader cache entries, 514 before it opens `level.pak` and 671 after. Wine's `winedevice.exe` makes the same calls on both, about 700 one-millisecond `clock_nanosleep` and 1,800 `poll` a second, but costs 0.55 s to 0.62 s of system time on Rach2 against 0.10 s to 0.13 s on Linux; it runs on another processor and does not hold up the main thread. From the game's start to the load's start Rach2 takes 9 s to 10 s, Linux 6 s to 7 s.

Four more causes are ruled out, each by a test build or a Linux setting run alternating with the baseline:

| Runs | Rach2, s | Linux, s |
|---|---|---|
| Baseline | 9.44, 10.04 | 9.33, 8.72 |
| Rach2's kernel mappings global (CR4.PGE) | 9.51, 9.91 | |
| Rach2 ticking at 250 Hz | 9.53, 10.00 | |
| Linux with huge pages never | | 9.16, 9.44, 8.86 |

* PCID. The WSL guest that runs QEMU offers INVPCID but not PCID, so neither guest has it, and Linux switches address spaces with a full flush as Rach2 does. A Rach2 build with Linux's six address-space IDs on each processor (`TLB_NR_DYN_ASIDS`, arch/x86/include/asm/tlbflush.h:65, and `choose_new_asid`, arch/x86/mm/tlb.c:217-252) found no PCID and ran as the baseline.
* Global kernel pages. Rach2's x86-64 kernel sets no global bit, so each CR3 load also drops the kernel's translations, which Linux keeps (`native_flush_tlb_global`, arch/x86/mm/tlb.c:1220-1245). A build with the direct map and the kernel image global loaded in 9.51 s and 9.91 s against the baseline's 9.44 s and 10.04 s.
* The tick. At 250 Hz, Debian's rate, Rach2 loaded in 9.53 s and 10.00 s.
* Huge pages, again: Linux with them never took 9.16 s, 9.44 s and 8.86 s, and its threads took 285,000 minor faults, Rach2's figure, without losing time.

Every line is in [pass5/runs.txt](80-92/evidence/pass5/runs.txt).

Six of Rach2's eleven loads fall inside Linux's range. A twelfth, 17.24 s, is left out: its guest counted 1,762 steal ticks over the load, 17.6 s of processor time that the host gave something else, and every other run of the pass counted at most 4.

Over the load every thread together used the same user time on both systems, 12.48 s on Rach2 and 12.57 s on Linux on average, and 0.74 s more system time on Rach2, 3.65 s against 2.91 s. The main thread used 6.43 s of user time and 2.20 s of system time on Rach2, 5.96 s and 1.87 s on Linux. So the user time the fourth pass found extra in the main thread is matched by less in other threads, and the system time is what Rach2 spends more.

Four checks are ruled out:

* Idle processors that poll. Debian's kernel here runs with no cpuidle driver (`current_driver` reads `none`): `cpuidle-haltpoll` is built but loads only with KVM's realtime hint, which QEMU does not give, so Linux halts at once. A Rach2 kernel whose `idle_halt` halts at once loaded in the baseline's time, median 9.16 s, though its QEMU process used 20.3 s of host time over the load against the baseline's 21.0 s and Linux's 19.4 s.
* The tick's EOI. A kernel that gives KVM a word for the paravirtual end of interrupt, as Linux's `kvm_guest_cpu_init` and `kvm_guest_apic_eoi_write` do (arch/x86/kernel/kvm.c:363-374, 397-406), loaded no faster, and KVM counted as many exits as for the baseline.
* Accessed bits. A kernel that sets the accessed bit in every user entry and table it makes, as Linux's protections do (arch/x86/include/asm/pgtable_types.h:192, 207-225), loaded in the baseline's time.
* How time is charged. Debian's configuration has `CONFIG_HZ=250`, `CONFIG_NO_HZ_FULL=y` with no `nohz_full=` on its command line, so the tick stops only on idle processors, `CONFIG_VIRT_CPU_ACCOUNTING_GEN=y`, which acts only on `nohz_full` processors, and no `CONFIG_IRQ_TIME_ACCOUNTING`. Linux charges each tick to what it interrupted, as Rach2 does, at 250 Hz against 1000 Hz, and neither takes interrupt time out of a thread's.

The fifth check, the main thread pinned off processor 0, was not run.

KVM's counters show where the extra system time may go. Over the load Rach2's VM took 812,000 to 985,000 exits, Linux's 182,000 to 208,000; halts 47,000 to 52,000 against 54,000 to 62,000; interrupt-window exits, which KVM takes when it has an interrupt to give and the guest has interrupts off, 24,000 to 29,000 against 4,600 to 5,600; and halts that KVM's own poll on the host ended before sleeping, 1,400 to 1,800 against 22,000 to 27,000, since Rach2 polls in the guest first. Of the exits, 670,000 to 750,000 on Rach2 and 84,000 to 96,000 on Linux are in none of KVM's named counters (halts, port and memory-mapped accesses, interrupts and interrupt windows), while KVM gave Rach2's guest 87,000 to 99,000 interrupts and Linux's 68,000 to 78,000. A histogram trigger on KVM's `kvm_exit` trace event counted only 21,000 to 30,000 exits a load on either system, so it does not name them; why it counts so few is not traced.

## The sixth pass

The sixth pass measured the load again on 11-13, from 06:52 to 07:31 on the testing host's clock (UTC+5), at the milestone branch's head `719d619c2`, which carries 80-94's exits, 80-95's readahead, 80-96's write-back and 80-97's idle tick, with the same harness and island save, Rach2 and Linux alternating with the host's load at 0.4 to 5. [pass6/runs.txt](80-92/evidence/pass6/runs.txt) has every line and each run's summary.

| Kernel | Loads, s | Median, s |
|---|---|---|
| Linux, 12 runs | 8.36 to 11.33 | 8.70 |
| Rach2 at the head, 9 runs | 8.07 to 9.30 | 8.47 |
| Rach2 with the account's fix, 6 runs | 8.14 to 8.62 | 8.17 |

Linux's 11.33 s counted 1 steal tick and came at a host load of 3.2; without it Linux's range is 8.36 s to 9.49 s, and Rach2's runs at the head fall inside it but one, 9.30 s, at a host load of 2.6. The load in QEMU is within Linux's range, which is this task's condition for the step on the Lenovo.

At the head the threads' times were wrong. Over a load Rach2's four llvmpipe threads were charged 0.8 s to 2.0 s of user time against Linux's 4.1 s to 7.1 s, every thread together 6.3 s to 7.4 s against Linux's 10.8 s to 16.6 s, and in one pair the guest's `/proc/stat` counted its processors 78% idle against Linux's 55%, while QEMU's vCPU threads cost the host the same time for both. A program of four threads that each spin a fixed burst, timed by the monotonic clock, and then sleep ([burst.c](80-92/evidence/pass6/burst.c), run by 80-94's `vm.py` with its paths set to the owner's copy) showed it directly: of 1 ms bursts between 2 ms sleeps the head charged 15% of the time the clock measured, of 0.3 ms bursts 7% and of 3 ms bursts 48%, where Linux charged 101%, 104% and 100%, and the fifth pass's kernel, before 80-97, 107%, 117% and 101%.

The cause was 80-97's idle account. When an idle wait ended, `sched_account_tick(0, 0)` counted every whole millisecond since the processor's last count as idle, and a halt's end does that whether its tick was stopped or ran through it. So the run of the last thread from its last tick to its sleep went to idle, and with the guest's tick at 250 Hz most short runs began after one tick and ended before the next. Linux's tick charges each edge to what it finds, and a stopped tick's idle span is charged by the jiffies it crossed (`tick_nohz_account_idle_time`, kernel/time/tick-sched.c:1395-1415), so a run between two edges is charged a whole period whenever an edge falls in it, which is right on average. Two commits on the branch make Rach2's account the same: the stopped tick's span and the end of every scheduler halt are charged only to the last scheduler edge (`sched_idle_account`, `sched_edge_ticks`), so a halt under a running tick charges nothing, and the next tick charges its whole period to the thread it finds. With them the burst program is charged 98% to 102% of the clock's time in every case, and over a load the main thread 5.8 s to 6.3 s of user time and 1.5 s of system time against Linux's 5.8 s to 6.1 s and 1.8 s to 2.0 s, llvmpipe 3.6 s to 6.8 s against 4.1 s to 6.0 s. The first commit alone, which charged only the stopped tick's span to its edge, left the burst program at 2% to 62%. The host test's scheduler rows model the edge in both cases; neither the rows nor any suite was run.

## The reviews' fixes

Review j144 found the account's fix right in the kernel, but its two host rows in the old 1 ms ticks, while the scheduler's host test compiles at 250 Hz, and `tick_stop_period` described in milliseconds where it holds kernel ticks. 80-92a (#4888) rewrote `nohz_accounting` and `nohz_switch` in 4 ms ticks, each wake more than half a tick past its edge so that charging to the nearest tick would count one tick more than the edge does, and added a row for a two-tick period whose wake lies past a tick's edge but before the period's next. Review j139 found that a second signal could stop `kvmstat.py` before it removed its histogram triggers. 80-92b (#4898) has its handler only record the signal, which ends the main loop, so the removal runs whatever arrives after. The rows compile; none was run.

## What is left

The load in QEMU is within Linux's range. What is left is this task's last step: one load of the island on the Lenovo, on a trial boot of the milestone's kernel with the account's fix, beside Linux's 19.7 s on the same machine (80-12.md), which [80-92/lenovo.md](80-92/lenovo.md) prepares. The fifth pass's other findings are 80-94 to 80-97's, which landed before this pass. Rach2's ext2 mounts a volume with `dir_index` read-only, where Linux's ext2 mounts it read-write (fs/ext2/ext2.h:545-552); 80-93 (#4476) took that, and the harness's data disk is made without `dir_index`.

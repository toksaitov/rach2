# Crysis on the data partition

Task 80-6 adds `crysis.sh`, its two hash manifests and its manual. Installation and renderer startup passed in QEMU. The PI futex dependency is merged, and a zero relative sleep now enters the timed wait. The game wrote an island checkpoint, a later boot read it, and Mesa recorded 203 cache hits and 177 misses. These are storage proofs; the loaded view was black and is not a gameplay proof. The prepared Lenovo step has no manager's go, and the Lenovo has not been written for this task.

## Errors in my preparation

My first commit attempt used ambiguous empty `CDPATH` assignments; the hook refused them. A later commit attempt had two overlong comment lines, also refused. Both were corrected and the hooks passed.

I started a boot after a failed tar transfer without checking the kernel digest. Its 3,839,488 bytes were exactly the prefix of the 3,841,440-byte built kernel; both ELF load segments ended before the truncation, at 3,067,482 and 3,313,384, but the file identity was wrong. I repeated the focused probe with the exact file and added a digest assertion before further boots. The passing installation boot used that exact file.

The borrowed GNU image lacked innoextract. After staging it and Boost, I omitted `ldconfig`, so the loader could not find Boost. Both runs stopped before extraction and removed the temporary directory and lock. The passing run had innoextract 1.9 and an updated loader cache. I also gave the i686 compiler an incorrect libgcc path, then used the path the compiler printed. Two generated debugger commands had quoting errors; they produced no measurements and were corrected before the register dump.

I incorrectly treated PI support as an owner's scope decision. The manager classified it as task-sized, filed the priority-inheritance futex task (80-10c), and blocked this task on it. The standing Linux-behavior rule already required that fix; a Wine fallback is set aside.

I stopped the first-level attempt when its log ceased advancing and the later shutdown attempts after taking their backtraces. Their outer commands include exits 0 and 1 after I terminated Wine; these are stopped attempts, not successful game exits. The first shutdown also left Xvfb holding the runtime mount; the host controller stopped QEMU in its cleanup. Those earlier commands and their claims ended.

On resumption, a wrong relative path in a tar command produced an incomplete archive. I corrected it to absolute paths and checked the kernel digest before booting. A generated controller had a quoting error, corrected by parsing it before the boot. The native admission program required an absolute command path; its first `python3` command failed before starting a guest. I cancelled an oversized admission request for the small Linux probe and used its actual resources. The first i686 probe compile used the wrong musl install path, then an unsupported `-pthread`; both were corrected. The first private RAM-image manifest was refused by the set-id guard; the corrected disk-test manifest passed. These preparation failures produced no passing game result.

The first resumed level attempt was stopped with `wineserver -k`; its outer exit 0 is a stopped attempt. A marker beside that run's status records the stop. The controller now attempts an orderly guest power-off on every exit, with termination as its fallback. A file-system check of the stopped data volume found no repair needed.

## Configuration

The testing host ran private copies of the existing GNU test images in QEMU under KVM, `host,invtsc=on`, AHCI and an RTL8139. The x86-64 guest had four processors and 8 GiB; the i686 guest had two processors and 2 GiB. The game used Xvfb at 640x480x24 with `-noreset`, llvmpipe (LLVM 19.1.7), four Mesa threads, GE-Proton11-12 and the ordinary `test` account. A private 14 GiB ext2 volume was mounted at `/data`. The three installer files came from the Mac's pinned `build/cache/crysis/` copy, through a private 8 GiB installer volume. This was a correctness run with concurrent work on the host; it measured no performance gate.

The final game attempt used a PulseAudio null sink. Crysis's own log lists PulseAudio Output and Null Output, initializes FMOD-EX and finds the default profile that the first boot created under `Z:\data\crysis\saves`. The first two game attempts had no audio device and are not sound proofs.

## Completed checks

`crysis.sh install` checked all three installer hashes, unpacked them through innoextract as `test`, and checked every file against `game.sha256`. It reported `installed, all 2358 files match`; the final file count was 2358 and neither `.install.*` nor `.install-lock` remained. The script publishes only the checked tree and refuses an existing game. The game and all state paths are on `/data`; no game files enter the GNU image.

The game's log names the 64-bit `Bin64/Crysis.exe`, llvmpipe as its D3D9 adapter and `/data/crysis/saves` as its user directory. The working directory was `Bin64`, and the command passed `-dx9` through `rach2-game`. This completed the renderer-start check. The later storage check below obtained an actual checkpoint and live Mesa cache-hit counters. The earlier count of 101 cache files alone proved neither a hit nor a completed save.

Two kernel faults found during this work were fixed:

* `getrusage` returned zero context-switch counts even though the scheduler kept them. Wine reads those counts around `sched_yield` to judge whether it yielded. The fix reports native-width counts for a thread, all threads of a process, ended threads and reaped descendants, and in `wait4`; the i386 compat structure retains its 72-byte layout. It does not establish that the zero counts caused the original game stall.
* An i386 `CLONE_SETTLS` on x86-64 changed the child's descriptor but kept the parent's saved GS base. The first switch restored that base over the new descriptor. The 32-bit musl worker changed the parent's thread record and left its own join state at `DT_JOINABLE`. The fix changes the saved FS or GS base when its selector names the new descriptor, as the existing ptrace path and Linux do.

The new standalone probe [80-6/rusage.c](80-6/rusage.c) passed on the native i686 kernel, the native x86-64 kernel and as a static i686 musl program on the x86-64 kernel after the TLS fix. Each reported 32 switches across yields, 32 from the ended thread and 34 from the reaped child; the child's reported counts were added once to `RUSAGE_CHILDREN`. The compatibility run before the TLS fix waited on the child's unchanged private join word, expected 2, while `__thread_list_lock` was zero.

Both kernels compiled; the changed manual pages rendered; the git hooks passed. No suite, host test or separate style check ran. The probes ran alone in the task's manual boots. The exact x86-64 kernel after both fixes is `f791483d90805ee3888579b363ce5f9d08179b7f2103b9bb949f27b09b05c9ab`; the counter-only i686 kernel is `4c87cc9298f24c1a7af15c1defe8b766bc989d4ecdef9606538430ca497d0761`.

## The earlier audio-detach failure

In the final attempt Crysis logged `System:Quit`, but its process did not exit. The main thread waited in `pthread_mutex_lock`, `free_phys_device_lists`, `pulse_process_detach` in `winepulse.so`. `g_phys_mutex` had lock 2, owner 239, one user and kind 0: an ordinary mutex whose owner was no longer present. Only the main thread and nine Mesa threads remained. Automatically releasing an ordinary mutex when its owner ends would be wrong.

The standalone [mutex attribute probe](80-6/mutex-attributes.c), compiled against the deployed GNU root, showed `FUTEX_UNLOCK_PI_PRIVATE -> ENOSYS`; initialization with PI and robust attributes returned 95 (`ENOTSUP`), while default initialization returned 0 with kind 0. GE's [pinned audio patch](https://github.com/GloriousEggroll/proton-ge-custom/blob/GE-Proton11-12/patches/proton-ds5-haptic/0010-winepulse-mmdevapi-Add-support-for-hotplugged-audio-.patch#L645) retries failed attributed initialization with default attributes. This accounts for the observed mutex type. Wine's exit terminates its other Windows threads before DLL detach. The exact point where owner 239 ended was not captured; the shutdown backtrace and unsupported-PI probe are retained, without claiming a new native x86-64 TLS fault.

Codex identified both ABI faults and the Winepulse fallback during read-only diagnosis; each was checked against the code and the measured probe before use. Fable was tried first. Its CLI printed `[claude-code:unrecognized_model] {"model":"claude-fable-5-2","query_source":"sdk"}` and supplied no answer before I stopped its owned command. The line did not itself end the command, and was not a usage-limit response.

Full PI support needs futex owner tracking, priority propagation through blocked owners, robust owner death, timeout and signal handling, lock/trylock/unlock and PI requeue operations for condition variables, and tests on both kernels and the compat ABI. That crosses the futex, process, scheduler and wait-queue contracts. The smaller alternative is to rebuild the pinned Wine audio module with a robust fallback that drops only PI; it leaves the kernel capability absent. The manager classified this as task-sized and filed [the priority-inheritance futex task, 80-10c](https://github.com/toksaitov/rach2/issues/3347), with six subtasks at the top of the board. It merged before this task resumed. A Wine fallback is set aside because the standing rule requires the Linux contract in the milestone under way.

## Resumption after PI

The first resumed kernel, SHA-256 `339761fce91678edf236d9bfa062dd761388a94bfc69aeca29f9496fb5b063d8`, got past the earlier audio mutex: `g_phys_mutex` was destroyed, with kind `0xffffffff`, rather than a locked ordinary mutex. At the later wait the main thread was in `fsync_wait_objects`, waiting for a shared word of 0 that still contained 0. Neither that snapshot nor the ordinary futex compare, enqueue and wake code established a missed kernel wake. The setting thread and event's purpose remain to be identified if that shutdown wait recurs.

A separate kernel difference was concrete. `sleep_for` returned immediately for a zero interval. Wine's `fsync_pulse_event` sets its event, wakes waiters, calls `usleep(0)`, then resets the event; its code itself says that a pulse may be missed. Linux 6.12's [hrtimer sleep](https://github.com/torvalds/linux/blob/v6.12/kernel/time/hrtimer.c#L2023) arms a timer even for a zero relative request. The fix uses the existing interruptible wait until the next tick. This is a timed wait at Rach2's 1 ms resolution, not Linux's high-resolution timer slack. An already-past absolute request keeps its immediate return.

The new standalone [zero-sleep probe](80-6/zero-sleep.c) puts a runnable worker on the caller's processor and counts voluntary context switches around 16 zero requests of each form: `nanosleep`, relative real-time `clock_nanosleep`, and relative monotonic `clock_nanosleep`. Before the fix all three counts were 0; Linux reported 16 for each. With the fix, musl on native i686, native x86-64 and the compat ABI, and glibc on x86-64, each reported 16 for all three forms, with worker progress. The musl probes ran alone in private 128 MiB RAM-image boots on the Mac under TCG, each of which powered itself off; the glibc probe ran alone before Crysis in the GNU guest. No existing suite or host test ran.

Both kernels compiled. The corrected x86-64 kernel at `87de537b2` has 4,029,608 bytes and SHA-256 `54dbe3d11826a2cf798a89e1fe7572b083f3310bdfe2f121015dd283b8fe91db`. This proof establishes the sleep correction, not the cause of the Crysis load's duration. WineD3D's map wait calls `NtDelayExecution` with a zero timeout, which calls `sched_yield`; it does not use this zero-nanosleep path.

The corrected kernel's `+map island +savegame task2653 +quit` completed the level load in 1071.53 seconds. Its earlier Windows stack was in texture mapping through WineD3D, and advancing disk reads and resident memory were progress through that load. The diagnostic later pinned the game's threads to processor 0; this is no performance result. The game rejected my `savegame` command as unknown, then logged `System:Quit` and waited in DirectInput. That attempt was stopped, not a successful game exit. It nevertheless wrote the level's actual checkpoint, `SaveGames/default_Contact_crysis.CRYSISJMSF`, 623135 bytes with SHA-256 `bf0f664d9d2efcb732aa57ed7f3440a0b0c351212cfc20d9a64605dd79260a37`. Its XML metadata names `island`, `SinglePlayer` and save time `2026-11-10T05:46:08Z`. The files persisted through the later probe and preflight boots. Opening them is not yet proof of a completed restore.

Fable was tried first again, with the CLI alias `fable` at xhigh; it supplied no answer in five minutes and was stopped. This attempt printed only the sign-in expiry warning, not the earlier model error or a usage-limit message. Codex and Muse supplied read-only diagnoses, checked against the source: neither identified a missed kernel wake from the unsignaled event, and both required the event's producer or changing I/O measurements before declaring a load deadlock.

## DirectInput shutdown

The final shutdown capture identifies `dinput8+0x19b49`, the return address of `WaitForSingleObject(stop_event, INFINITE)` in `input_thread_remove_user`, and `dinput8+0x57f9`, the call from `dinput7_Release`. CryInput's global destructors release the last interface during `LdrShutdownProcess`. Only main and nine native Mesa threads remain. Wine has already terminated its other Windows threads, including the input worker, before calling DLL detach handlers. Only that worker's normal exit sets this fresh event. It has no remaining producer; changing the kernel's futex wake would not fix it. Codex independently traced these addresses and the shutdown order; both were checked against the exact DLL and pinned source.

The new [DLL probe](80-6/dinput-shutdown.c), loaded by [its executable](80-6/dinput-shutdown-main.c), creates and acquires a keyboard outside the loader lock and releases its interfaces from DLL detach. With an argument the executable unloads the DLL before process exit, the control; without one it calls `ExitProcess` with the DLL still loaded. In the original runtime ordinary unload returned 0, while process detach with `reserved=1` reached the stop handshake without returning; the manual controller stopped it. With the source guard both forms returned 0 and printed `dinput-probe: detached`. The process-exit form no longer entered the stop handshake. These were new probes alone, not a suite. The 64-bit probe ran; both architectures' four replacement DLLs compiled.

`vendor/gnu/proton/dinput-shutdown.patch` returns from `input_thread_remove_user` before taking its critical section when `RtlDllShutdownInProgress` is true. Ordinary cleanup keeps the event handshake, which deliberately finishes before `FreeLibraryAndExitThread` can need the loader lock. `make gnu-proton` rebuilds only the DirectInput 7 and 8 DLLs from the pinned Wine source with GE's DirectInput and HID changes. Codex's independent archive and dependency reading found no other required change; the selected hunks were applied to the pinned source and compiled. The rest of the release is retained. The actual Crysis preflight, with `+save task2653-preflight +load task2653-preflight +quit`, then exited 0 with no unknown-command diagnostic, but reported no restoration and no Mesa statistics. It is a shutdown proof, not the save/cache proof.

The source preparation had further errors of mine: I used submodule directories as if they were absent, then a symlink layout whose physical parent broke relative paths. I corrected the layout. GE's full preparation sequence then rejected unrelated winecfg hunks; the DirectInput build instead applies only its verified source changes. The first configure attempts lacked explicit X and FreeType exclusions, and needed Wine's Vulkan and syscall-header generation. The first DLL link lacked `llvm-dlltool`. The tools were unpacked under the clone's build cache, not installed system-wide. The normal build compiled all four DLLs but first failed replacing the release's read-only files; the recipe makes its own destination writable before replacement. A diagnostic stat of an absent share directory also stopped my retry before it began. The corrected normal build staged the release and the four DLLs successfully. None of these preparation failures is a game pass.

## Storage across boots

A later game boot ran `+load default_Contact_crysis.CRYSISJMSF`, with no `+map` or `+quit`. The checkpoint retained its 623135-byte size and SHA-256 `bf0f664d9d2efcb732aa57ed7f3440a0b0c351212cfc20d9a64605dd79260a37`. A native inotify watch, started after hashing and before the game, recorded open, seven access events and close on that exact binary save. The game then loaded `island` in 882.05 seconds. This consumed the first boot's actual game state; no save was manufactured by the harness. Its XML contains Player `Dude`, entity 30583, with inventory and a nonzero position and rotation.

The game's native Mesa cache reported `enabled = true, hits = 203, misses = 177`, with path `/data/crysis/cache/mesa/mesa_shader_cache_db`, type `DISK_CACHE_DATABASE` and `path_init_failed = false`. GDB read the live fields on Wine's command thread, Linux 262, using Debian's matching debug object, build ID `f34ab849e878d8ffbbb15533a597ca31ebd583ec`. The context's `Cache` pointer equalled its llvmpipe screen's `disk_shader_cache`. The actual `_mesa_glapi_get_context` instructions load the TLS offset from the library's GOT at relative address `0x287db68`; reading that slot and the selected thread's FS base located the context without an inferior call. Mesa's pinned `disk_cache.c` increments these counters when `disk_cache_get` returns data or misses, and prints them only on cache destruction. This is the game's cache measurement, not a file count or another program's cache.

After the loading screen's continue prompt, the view was black. Console input worked, and a later save command reported `Suppressing QS`. I did not establish a usable restored view or the cause of the black view. The missing `LoadGame` completion message did not settle it: Codex traced all three load messages to verbosity 2, while both logging variables default to 1. The saved ViewSystem's empty XML is also expected by this build's serializer. A driver snapshot showed three raster workers at a barrier and one at a mutex; a later capture showed that worker had passed the mutex, so that snapshot did not establish a persistent deadlock. The game closed normally through its window protocol, returned 0, and the guest unmounted `/data` with paired opens and releases before powering itself off. This completes the specified save-read and cache-hit storage check, not a gameplay acceptance.

My counter capture initially used Python support absent from the guest GDB, then an unbound TLS symbol after manually loading debug symbols. Both produced invalid readings; only the later hardware TLS-slot reading above supplies the counters. My one-second grave-key press repeated into the console and made the first verbosity command unknown. The later command set verbosity 2; the key helper now uses a short press. A screenshot helper also inherited shell input until I gave ordinary SSH commands null input and file transfers their own input mode. Fable was retried for the graphics wait but supplied no answer before I stopped its owned command; it printed only the sign-in expiry warning. Codex's read-only source and binary diagnoses were checked against the records.

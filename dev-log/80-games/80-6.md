# Crysis on the data partition

Task 80-6 adds `crysis.sh`, its two hash manifests and its manual. Installation and renderer startup passed in QEMU. The game wrote an island checkpoint, a later boot read it, and Mesa recorded 203 cache hits and 177 misses. The view after that restore was black. Linux draws the island from the same save in the same guest profile, so the fault was Rach2's: `getrusage` walked the whole page table at every call, and Wine calls it around every `sched_yield`. With the resident pages counted as they change, the level loads in 29 seconds, not 416, and Rach2 draws the frames Linux draws. `/proc/PID/status` gained `RssAnon`, `RssFile` and `RssShmem`, from which Wine takes the memory figure the game shows. The silent Lenovo install passed on 2026-11-10: the game's 2,358 files are on the data partition, every hash matching, and the release was back in both slots. One run of the game on the Lenovo in software followed that night: the level loaded in 45 seconds and the opening scene drew at 3 to 10 frames a second on llvmpipe. The machine was left on its trial root for the first launch on its GPU (80-12), which puts the release back.

## The earlier audio-detach failure

In the final attempt Crysis logged `System:Quit`, but its process did not exit. The main thread waited in `pthread_mutex_lock`, `free_phys_device_lists`, `pulse_process_detach` in `winepulse.so`. `g_phys_mutex` had lock 2, owner 239, one user and kind 0: an ordinary mutex whose owner was no longer present. Only the main thread and nine Mesa threads remained. Automatically releasing an ordinary mutex when its owner ends would be wrong.

The standalone [mutex attribute probe](80-6/mutex-attributes.c), compiled against the deployed GNU root, showed `FUTEX_UNLOCK_PI_PRIVATE -> ENOSYS`; initialization with PI and robust attributes returned 95 (`ENOTSUP`), while default initialization returned 0 with kind 0. GE's [pinned audio patch](https://github.com/GloriousEggroll/proton-ge-custom/blob/GE-Proton11-12/patches/proton-ds5-haptic/0010-winepulse-mmdevapi-Add-support-for-hotplugged-audio-.patch#L645) retries failed attributed initialization with default attributes. This accounts for the observed mutex type. Wine's exit terminates its other Windows threads before DLL detach. The exact point where owner 239 ended was not captured; the shutdown backtrace and unsupported-PI probe are retained, without claiming a new native x86-64 TLS fault.

Codex identified both ABI faults and the Winepulse fallback during read-only diagnosis; each was checked against the code and the measured probe before use. Fable was tried first. Its CLI printed `[claude-code:unrecognized_model] {"model":"claude-fable-5-2","query_source":"sdk"}` and supplied no answer before I stopped its owned command. The line did not itself end the command, and was not a usage-limit response.

Full PI support needs futex owner tracking, priority propagation through blocked owners, robust owner death, timeout and signal handling, lock/trylock/unlock and PI requeue operations for condition variables, and tests on both kernels and the compat ABI. That crosses the futex, process, scheduler and wait-queue contracts. The smaller alternative is to rebuild the pinned Wine audio module with a robust fallback that drops only PI; it leaves the kernel capability absent. The manager classified this as task-sized and filed [the priority-inheritance futex task, 80-10c](https://github.com/toksaitov/rach2/issues/3347), with six subtasks at the top of the board. It merged before this task resumed. A Wine fallback is set aside because the standing rule requires the Linux contract in the milestone under way.

## Resumption after PI

The first resumed kernel, SHA-256 `339761fce91678edf236d9bfa062dd761388a94bfc69aeca29f9496fb5b063d8`, got past the earlier audio mutex: `g_phys_mutex` was destroyed, with kind `0xffffffff`, rather than a locked ordinary mutex. At the later wait the main thread was in `fsync_wait_objects`, waiting for a shared word of 0 that still contained 0. Neither that snapshot nor the ordinary futex compare, enqueue and wake code established a missed kernel wake. The setting thread and event's purpose remain to be identified if that shutdown wait recurs.

A separate kernel difference was concrete. `sleep_for` returned immediately for a zero interval. Wine's `fsync_pulse_event` sets its event, wakes waiters, calls `usleep(0)`, then resets the event; its code itself says that a pulse may be missed. Linux 6.12's [hrtimer sleep](https://github.com/torvalds/linux/blob/v6.12/kernel/time/hrtimer.c#L2023) arms a timer even for a zero relative request. The fix uses the existing interruptible wait until the next tick. This is a timed wait at Rach2's 1 ms resolution, not Linux's high-resolution timer slack. An already-past absolute request keeps its immediate return.

The new standalone [zero-sleep probe](80-6/zero-sleep.c) puts a runnable worker on the caller's processor and counts voluntary context switches around 16 zero requests of each form: `nanosleep`, relative real-time `clock_nanosleep`, and relative monotonic `clock_nanosleep`. Before the fix all three counts were 0; Linux reported 16 for each. With the fix, musl on native i686, native x86-64 and the compat ABI, and glibc on x86-64, each reported 16 for all three forms, with worker progress. The musl probes ran alone in private 128 MiB RAM-image boots on the Mac under TCG, each of which powered itself off; the glibc probe ran alone before Crysis in the GNU guest. No existing suite or host test ran.

Both kernels compiled. The corrected x86-64 kernel at `87de537b2` has 4,029,608 bytes and SHA-256 `54dbe3d11826a2cf798a89e1fe7572b083f3310bdfe2f121015dd283b8fe91db`. This proof establishes the sleep correction, not the cause of the Crysis load's duration. WineD3D's map wait calls `NtDelayExecution` with a zero timeout, which calls `sched_yield`; it does not use this zero-nanosleep path.

The corrected kernel's `+map island +savegame task2653 +quit` completed the level load in 1071.53 seconds. ## DirectInput shutdown

The final shutdown capture identifies `dinput8+0x19b49`, the return address of `WaitForSingleObject(stop_event, INFINITE)` in `input_thread_remove_user`, and `dinput8+0x57f9`, the call from `dinput7_Release`. CryInput's global destructors release the last interface during `LdrShutdownProcess`. Only main and nine native Mesa threads remain. Wine has already terminated its other Windows threads, including the input worker, before calling DLL detach handlers. Only that worker's normal exit sets this fresh event. It has no remaining producer; changing the kernel's futex wake would not fix it. Codex independently traced these addresses and the shutdown order; both were checked against the exact DLL and pinned source.

The new [DLL probe](80-6/dinput-shutdown.c), loaded by [its executable](80-6/dinput-shutdown-main.c), creates and acquires a keyboard outside the loader lock and releases its interfaces from DLL detach. With an argument the executable unloads the DLL before process exit, the control; without one it calls `ExitProcess` with the DLL still loaded. In the original runtime ordinary unload returned 0, while process detach with `reserved=1` reached the stop handshake without returning; the manual controller stopped it. With the source guard both forms returned 0 and printed `dinput-probe: detached`. The process-exit form no longer entered the stop handshake. These were new probes alone, not a suite. The 64-bit probe ran; both architectures' four replacement DLLs compiled.

`vendor/gnu/proton/dinput-shutdown.patch` returns from `input_thread_remove_user` before taking its critical section when `RtlDllShutdownInProgress` is true. Ordinary cleanup keeps the event handshake, which deliberately finishes before `FreeLibraryAndExitThread` can need the loader lock. `make gnu-proton` rebuilds only the DirectInput 7 and 8 DLLs from the pinned Wine source with GE's DirectInput and HID changes. Codex's independent archive and dependency reading found no other required change; the selected hunks were applied to the pinned source and compiled. The rest of the release is retained. The actual Crysis preflight, with `+save task2653-preflight +load task2653-preflight +quit`, then exited 0 with no unknown-command diagnostic, but reported no restoration and no Mesa statistics. It is a shutdown proof, not the save/cache proof.

The source preparation had further errors of mine: I used submodule directories as if they were absent, then a symlink layout whose physical parent broke relative paths. I corrected the layout. GE's full preparation sequence then rejected unrelated winecfg hunks; the DirectInput build instead applies only its verified source changes. The first configure attempts lacked explicit X and FreeType exclusions, and needed Wine's Vulkan and syscall-header generation. The first DLL link lacked `llvm-dlltool`. The tools were unpacked under the clone's build cache, not installed system-wide. The normal build compiled all four DLLs but first failed replacing the release's read-only files; the recipe makes its own destination writable before replacement. A diagnostic stat of an absent share directory also stopped my retry before it began. The corrected normal build staged the release and the four DLLs successfully. The cause was found in the kernel, not in the frame's path. During the load the Rach2 guest spent 88% of its four processors in the kernel: `/proc/stat` grew by 293 user ticks and 1756 system ticks in five seconds. [A sampler](80-6/rip-sample.py) read every processor's RIP through QMP 400 times: 58.6% of the samples were in `arch_relax`, the wait for the big lock, 14.7% in `paging_user_count`, 4.5% in user code. `paging_user_count` had one hot caller, `mm_resident`, which `sys_getrusage` called for `ru_maxrss`: a walk of every leaf table of the process, under the big lock. GE-Proton's Wine reads `getrusage(RUSAGE_THREAD)` before and after each `sched_yield` to tell whether it yielded; the test kernel counted 30 million such calls in 378 seconds. [The probe](80-6/maxrss.c) measures the call with 512 MiB touched: 286 ns on Linux, 208,156 ns on the kernel before. The earlier fix of this task, which made `getrusage` report context switches, did not add the walk; the walk was there before it.

Why the slow load left the view black was not traced further: the same save, binaries and settings draw the island on the same kernel once the load is fast, and three runs agree. The game's log has no line for it.

The fix keeps the count Linux keeps. An address space counts its present user entries as each writer sets or clears one (`mm_resident_add` from `map_user_frame`, `alloc_user_page`, `unmap_user_range`, `paging_move_range` and the last `mm_put`), and keeps the peak, as `hiwater_rss`. `getrusage`, `VmRSS`, `VmHWM` and `statm` read the two numbers. A test kernel compared the count with the old walk at every 1024th `getrusage` through a boot, the level load, the cutscene and the game's exit: 29,700 comparisons, no difference. With the fix the probe takes 305 ns a call and `ru_maxrss` and `VmHWM` keep the peak after `munmap`, as on Linux; before, both fell to 708 kB. The i686 kernel passed the probe with 256 MiB in a RAM-image boot on the Mac, which powered itself off. Both kernels compile. [The measurements](80-6/evidence/view-comparison.txt) have every number above.

The game's statistics showed `Mem=0MB` on Rach2 where Linux shows the process's memory. Wine computes the pagefile usage from `RssAnon` and `VmSwap` of `/proc/self/status`, and Rach2's file had no `RssAnon`, `RssFile` or `RssShmem` line. The file now has the three: they divide `VmRSS` by a walk of each region's tables, with the rule smaps has, a private region's pages being the process's own but for the unwritten pages of a file's region, and a file's pages counted as shared memory when the file is in memory. [A second probe](80-6/rsskind.c) maps and writes memory of each kind, private and shared anonymous, a memfd shared and private, a disk file private and shared, and prints how the four counts change at each of eleven steps: Rach2's changes are Linux's at every step, and the three sum to `VmRSS` ([output](80-6/evidence/rsskind.txt)). In a fourth run of the restore, on the kernel `eb18a790`, the level loaded in 31.29 s and the cave's frame shows `Mem=1332MB` at 26.5 frames a second ([frame](80-6/evidence/view-rach2-cave-mem.png)); Linux's cave frame shows `Mem=1326MB`, and the kernel before showed `Mem=0MB` at 21.6. The walk runs at each read of the file, not at `getrusage`. `procprobe` has the row `status-rss-kinds`, that the three lines are there and sum to `VmRSS`; run alone on the i686 kernel in a RAM-image boot on the Mac, which powered itself off, the row passed.

What is left differs from Linux and is not fixed here:

* The load takes 29 s where Linux takes 11 s. During the cutscene the fixed kernel's samples are 37.8% user, 27.6% idle and 19.0% `arch_relax`: the yields and the `getrusage` calls, some 80,000 a second, each take the big lock. That is the lock's cost, not one call's.
* With `rach2.trace=enosys` the three Rach2 runs logged two missing calls: 323, `userfaultfd`, asked for by `wine` and `wine64` (36 lines in the three runs), after which Wine keeps its write watches by `mprotect`, and 430, `fsopen`, asked for by `mount` (6 lines), after which `mount` uses mount(2). The game runs without both.

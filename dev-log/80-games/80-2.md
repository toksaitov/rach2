## The refused page

Run2 step 10's reproducer, "kvm run failed Bad address": step 10's guest under KVM with QEMU's display headless (`egl-headless` on the render node; the fault needs no panel), `d3d11probe64.exe` with `PROTON_USE_WINED3D=1`, and `efault.bt` attached to `hva_to_pfn`, `follow_pfnmap_end` and `hva_to_pfn`'s return (Debian's build inlines `hva_to_pfn_remapped`, so the plan's probe point does not exist).

* `shmem_enabled` at `never`: the probe draws ("center 255 128 0 255 corner 0 0 128 255 draw OK"), the VM runs, `ShmemHugePages` 0, 450,109 calls to `hva_to_pfn` of which 9 walked a PFNMAP mapping, none refused.
* `shmem_enabled` at `always`: QEMU stops in `internal-error`, `ShmemHugePages` 489,472 kB, 315,346 calls, 5 PFNMAP walks, one refused.

The refused page, from `trace-always.txt`:

* comm "CPU 0/KVM", the mapping `anon_inode:i915.gem` with `vm_flags` 0x2c0644fb (`VM_IO | VM_PFNMAP` among them).
* pfn 0x330601: flags 0x17ffffc0000209, reference count 0, `_mapcount` -1. Its `compound_head` points at pfn 0x330600, so it is the folio's second page; in that page the low byte of the flags holds the folio's order, 9, and bit 9 is `PG_large_rmappable`.
* The head, pfn 0x330600: flags 0x17ffffc0060068, which are `PG_uptodate`, `PG_lru`, `PG_head`, `PG_swapbacked` and `PG_unevictable` (`include/linux/page-flags.h` of 6.12.115); reference count 513; `_mapcount` -1.
* Stack: `kvm_faultin_pfn`, `kvm_tdp_page_fault`, `kvm_mmu_do_page_fault`, `kvm_mmu_page_fault`, `vmx_handle_exit`, `kvm_arch_vcpu_ioctl_run`, `kvm_vcpu_ioctl`.

The first attempt (`efault-first/`) refused the same kind of page: pfn 0x17f201, the second page of the order-9 folio at 0x17f200. So KVM takes its reference with `get_page_unless_zero` on the tail page itself, whose own count is 0 while the folio's count lives in its head, and the refusal becomes -EFAULT. This confirms the source reading of milestone 76's upstream entry, "KVM stops a guest on a huge page of a PFNMAP GPU mapping", which now cites this trace.

## WebGPU on Venus

Chromium 156 in step 10's guest, with risk 15's settings (IOMMU translation off, `shmem_enabled` at `never`), QEMU's display headless and virglrenderer's log at info, under the guest's Weston; four switch sets, each with `--enable-logging=stderr` and Dawn's and Chromium's GPU modules at verbose level 3 (`gwebgpu.sh`, `venus.sh`).

* Every set returned SwiftShader's adapter (`isFallbackAdapter` true) and none Venus's: `--enable-unsafe-webgpu --ignore-gpu-blocklist`; that with `--use-vulkan=native`, which Chromium reads as forced native Vulkan and which skips its GL-interop check; that with Intel's IDs given as the GPU's; and Dawn's GL ES backend in compatibility mode, which returned an empty adapter.
* Dawn's own list names "Vulkan backend - Virtio-GPU Venus (Intel HD 4400)" as available, and the GL ES backend on ANGLE over virgl.

Why: Dawn hands Chromium a Vulkan adapter only if `PhysicalDevice::SupportsExternalImages()` holds (Dawn at 8114a24a35eed1db88d1d897e8bd193a8c334712, Chromium's `CanUseAdapter`). On Linux outside ChromeOS that needs external memory (`VK_KHR_external_memory_fd` and `VK_EXT_image_drm_format_modifier`) and opaque-fd semaphores that are both exportable and importable. `extsem.c` asked each device:

| Device | external_memory_fd | drm_format_modifier | semaphore fd | OPAQUE_FD features | SYNC_FD features |
|---|---|---|---|---|---|
| Venus over hasvk, guest | yes | yes | yes | none | export, import |
| Venus over lavapipe, guest | yes | yes | yes | none | export, import |
| hasvk, host | yes | yes | yes | export, import | export, import |

Venus offers only sync-fd semaphores, so Dawn refuses it and Chromium falls back to SwiftShader; on the host hasvk offers opaque fds and passes. This is Dawn's stated requirement and Venus's limit, not a fault of either; milestone 76's upstream entry "Chromium returns no WebGPU adapter for Venus" now says so. The guest's GL also lacks `GL_EXT_memory_object_fd` and `GL_EXT_semaphore_fd`, which the host's has; `--use-vulkan=native` skips Chromium's check of them and still gets no Venus adapter, so the semaphore check is the one that decides. For Rach2's guests, WebGPU on Venus needs Dawn to accept sync-fd semaphores (as it does on ChromeOS) or Venus to export opaque fds.

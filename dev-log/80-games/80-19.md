# Splice copies under the big lock

Task 80-19 found why GNU cat's copy of a cached file swung from seconds to minutes on the Lenovo while `dd` stayed fast, and fixed it. The swing was a livelock of the boot processor's user code: that processor's tick always waited for the big lock, and once the waits passed a tick the next tick was pending at every return to user mode, so a program there made no progress while the other processors kept the lock busy. Two faults of the splice path made the copy slow even without it: the pipe's bytes were copied one at a time, and `F_SETPIPE_SZ`, which GNU cat asks for 512 KiB, was refused, so each splice moved 64 KiB and took the lock eight times as often. With the three fixed, a forcing load in QEMU copies 16 MiB of a cached file by splice in 0.30 s under load, where it took 3 to 41 s, and in 0.028 s alone, against 0.025 s by read(2). The runs were made on 2026-11-11 between 07:33 and 07:52 UTC+6 on the Mac; the raw logs are in `build/runs/task3489/` there, and the lines that matter in `80-19/evidence/`.

## The forcing load

`spliceload` writes a 256 MiB file on the ext2 volume, reads it whole so that it is in the file page cache, and copies 16 MiB of it to `/dev/null`, by read(2) and write(2) a mebibyte at a time and by splice from the file into a pipe and from the pipe to `/dev/null`, with the pipe sized as GNU cat 9.12 sizes its own (`src/splice.h`: `F_SETPIPE_SZ` of 512 KiB, else what `F_GETPIPE_SZ` gives). The copier is pinned to the boot processor. Each copy runs alone, then twice beside three processes pinned to the other processors, each a loop of pread(2) of the same cached mebibyte, which holds the big lock for the copy. It requires `/proc/vmstat`'s `pgpgin` not to move during a copy, so every row reads only the cache. It times with `CLOCK_MONOTONIC` and prints `/proc/stat`'s lock and timer counters before and after each copy; no limit is judged on time.

## The cause

The earlier worker's trace (`evidence/ticktrace.txt`, the patch of commit ae0e9f84a) counted the timer ticks the boot processor took in user mode at one instruction before its next system call. Under the load the copier sat at one user instruction for 3,588 ticks, 11.9 s, before a splice, and for 2,321 ticks before a read; with no load, never more than 64. A program that ran for those ticks would have moved on; the same instruction for thousands of ticks means it did not run.

The code says why. `_irq_router` (`rach2/sys/arch/x86/isr.c`) let a processor past the first end its tick without the big lock when another held it, but the boot processor's tick always waited with `bkl_enter`. Behind three processors that each hold the lock for a mebibyte's copy, the wait passes a tick; the tick that came meanwhile is pending when the first returns to user mode, and x86 takes it before the next user instruction. So every tick waits, and between two of them the copier runs nothing. It gets out only when the waits happen to fall under a tick. The load's other counters agree: in the first before run the lock's waits grew by 90 s across the four processors while the copier read `/proc/stat` and `/proc/vmstat` between two rows, and the other processors made the timer pass 6,855 times for the boot processor, whose own was late (`timer_passes_late`).

That is why the times swung. Every system call's return to user mode is a chance for the livelock to start, and a splice copy through a 64 KiB pipe makes 16 times the returns of a read(2) copy a mebibyte at a time, so it was caught far more often; a read(2) copy was caught too, once, for 12.9 s of one pair. On the Lenovo, GNU cat was slow when it ran on the boot processor and fast when it ran on another, by this account; that was not traced there, since QEMU showed the fault, as the task allows. 80-11's late timed wakes had their sleeper pinned to the boot processor as well, and may share this cause; they were not measured again.

## The fixes

* The boot processor's tick ends without the big lock when another processor holds it, as the others' do (12077d61e). It still waits when `sched_tick_waits` says a queued process has waited four ticks, when no reference keeps the clock, since its tick alone counts the clock then, and at its fourth such tick in a row, so that its periodic work, the network poll, the TCP timers, USB, input and the console, is at most four ticks late. The timer pass that wakes the sleepers is made meanwhile by the processor that holds the lock, whose tick nests inside its hold, once the tick count has not moved over two of its ticks, as before. The load averages now count their five-second period by the tick count, since a skipped tick no longer calls them.
* `pipe_splice_peek` and `pipe_tee` copied the pipe's bytes one at a time; they copy a contiguous span at a time with `k_memcpy` (be49efeea). Alone, this took the 16 MiB splice copy from 0.193 s to 0.041 s.
* `F_SETPIPE_SZ` gives a pipe a ring of a power of two from a page up, copying what it holds, as on Linux, with `/proc/sys/fs/pipe-max-size`, 1 MiB, as an unprivileged caller's limit and 64 MiB in all as the limit of the rings grown, Linux's `pipe-user-pages-soft` (be49efeea). GNU cat's 512 KiB pipe takes a splice of 512 KiB, a lock entry an eighth as often as at 64 KiB. `tests/pipeprobe.c` checks the refusal below the bytes held, the rounding, the growth and the bytes kept.

## What is left

Under the load a splice copy still takes twice as long as the read(2) copy, 0.30 s against 0.15 s on x86-64. Each copy waits for the lock at every system call, behind the three readers' holds, and the splice copy makes 64 calls, a splice into the pipe and one out of it for each 512 KiB, where the read(2) copy makes 32, a read and a write for each mebibyte; per call the waits are the same, 4.7 ms. That is the big lock itself, whose removal the owner put in the next milestone. On Linux neither copy waits for the others.

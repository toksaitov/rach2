# Wine on the Lenovo's GPU

Task 80-5 runs a Direct3D 9 program on the Lenovo's GPU through Crocus under Rach2 and checks its pixels against Linux's on the same machine, and times WineD3D's Vulkan renderer on hasvk beside its GL renderer as research for small programs. The game route is 80-1's: GE-Proton11-12 with WoW64 and WineD3D on OpenGL. This file has the probes, the trial root and its rehearsal in QEMU; the Lenovo step is [80-5/lenovo.md](80-5/lenovo.md), and its results are under The Lenovo step below.

## The probes

The gpu row of the Wine probes, `run.py gpu` (`tests/system/games/`), makes a prefix with `rach2-game` under a headless Weston on GL with Xwayland, and runs:

* `gl64`, `d3d964`, `gl32` and `d3d932`: the GL and Direct3D 9 probes of 80-3, 64-bit and 32-bit under WoW64, each drawing a shaded triangle over a clear and printing the CRC-32 of its 64x64 readback. Under Linux on the same machine these sums are the reference; a sum that differs fails the row.
* `trip-gl` and `trip-vulkan`: `tripprobe`, new here, which creates a Direct3D 11 device and 1000 times clears a 64x64 target to green, copies it to a staging texture and maps it, as the second graphics run's test did under Linux (`dev-log/76-graphics/research/work/tonight/lenovo.md`; that program was not kept), and prints the time. `trip-gl` runs through the route; `trip-vulkan` runs Proton with the route's settings, which `rach2-game --print` lists, and `WINE_D3D_CONFIG=renderer=vulkan`, since the route always takes GL. The row checks that Proton's log names the renderer asked for and that the probe exited 0. The times judge nothing.

Each Direct3D probe, `d3d9` and `tripprobe`, must also print an adapter that names `GAMES_RENDERER` and, given Linux's results, has Linux's PCI vendor and device, so that lavapipe cannot pass the row for hasvk.

`GAMES_RENDERER` names the GL renderer Weston and the GL probes must report: `HD Graphics 4400` on the Lenovo, `llvmpipe` in the rehearsal, `virgl` for the `games-wine` family by default. `GAMES_COMPARE` names Linux's `results.json`.

`gpu.sh` runs the row as root on the machine itself: it sets `mixer vol 1` where Rach2 has a mixer, runs the row as the GNU root's `test` (or Debian's `gfx`), and saves the identity, the results and the kernel's log, printing each call the kernel lacks once with the number of times it was logged. Under Linux it runs this directory's launcher with `/opt/proton` linked to the Proton `-p` names, as 80-2's session left it on p5.

## The rehearsal in QEMU

[80-5/qemu.sh](80-5/qemu.sh) makes a 33 GiB disk whose GUID table has the Lenovo's identity, `1acef00d-0f1e-4d2c-8b3a-c0ffee000001`, and one entry, 6, `Rach2 data`, from sector 2048, made with Rach2's `mke2fs.conf` as the Lenovo's was; the root and the probes are files on it. It boots the kernel under KVM on four processors with 8 GiB, AHCI, an RTL8139, HDA and a plain VGA, with `rach2.rootimage=GPTID=1acef00d-0f1e-4d2c-8b3a-c0ffee000001,6:/trial2654/root-61194a495c3378d2.img rach2.slot=trialroot rach2.trace=enosys`, then runs `gpu.sh -r llvmpipe` over SSH and powers the guest off. [The outputs](80-5/evidence/qemu/) are kept.

80-5.1's check: the kernel logged `root: image: /trial2654/root-61194a495c3378d2.img on /dev/disk0p6, ext2 through /dev/loop0; /data is /dev/disk0p6`, and the guest had `/dev/loop0` on `/` and `/dev/disk0p6` on `/data`.

80-5.2's check: the step's script ran to its end and printed `GPU OK`. On llvmpipe (LLVM 19.1.7) and lavapipe:

| Probe | Exit | Result |
|---|---|---|
| `gl64`, `gl32` | 0, 0 | crc32 `f1c362f2`, renderer llvmpipe |
| `d3d964`, `d3d932` | 0, 0 | crc32 `b2c0c4e2`, adapter llvmpipe |
| `trip-gl` | 0 | 1000 round trips in 934.5 ms, "Using the OpenGL renderer" |
| `trip-vulkan` | 0 | 1000 round trips in 8.9 ms, "Using the Vulkan renderer", on lavapipe |

The sums are llvmpipe's and are not Linux's virgl sums of 80-3 (`3f9a06f0` for Direct3D 9), since the rasterizer differs; the Lenovo step compares Crocus with Crocus. An earlier run of the same row, before the renderer's check was added, gave 822.8 and 7.9 ms.

Two faults of the rehearsal's own were fixed on the way: `mke2fs` wipes a GUID table it finds on the disk, so the table is written after the file system, and this host's `sgdisk -q` wrote no table while it exited 0, so the flag is gone. A first run stopped at `mixer vol 1` in a guest with no sound card; `gpu.sh` now sets the volume only where `/dev/mixer` is, and the rehearsal gives the guest HDA, as the Lenovo has.

## Missing calls

The owner's rule of 2026-11-10: a call is added in this stack only when a program the plans name calls it and then fails or loses a function for lack of it. With `rach2.trace=enosys` the rehearsal's programs asked for one call Rach2 lacks:

```
     12 323: not implemented (asked for by wine)
    105 323: not implemented (asked for by wine64)
```

* 323, `userfaultfd`: Wine asks for it to keep its write watches, and on `ENOSYS` keeps them by `mprotect` and the fault handler, as 80-6 found on the Lenovo; every probe drew and read back right without it. The program goes on by its own fallback, so no task is filed.

The Lenovo step's run gave the same lines, with the same counts, and nothing else:

```
     12 323: not implemented (asked for by wine)
    105 323: not implemented (asked for by wine64)
```

Every probe drew and read back right on the Lenovo's GPU without it, so `userfaultfd` stays a call the program goes on without.

# Crysis's acceptance

Task 80-9 accepts Crysis on the Lenovo: the flyby through umu and directly at 24 frames a second or more beside Linux's numbers, the suit's reboot with the HUD back, the 32-bit game's flyby, and a save that loads after a cold restart and an update, through the existing prefix and a new one. 80-9.1 made the scripts and rehearsed them in QEMU on 2026-11-11, between 20:10 and 21:05 UTC+6; every step of the Lenovo's procedure passed there. It also registered `save-update`, which passed once. The Lenovo's three trial boots, 80-9.2 to 80-9.6, follow [`80-9/lenovo.md`](80-9/lenovo.md). The figures below are from the files in `80-9/evidence/qemu/`.

## Errors in my work

* On the Lenovo step I stopped my ping loop with `pkill -f 'up()'`, a pattern that matched every process of the owner's user with "up" in its command line. It sent SIGTERM to the chat's Claude Code session, m3's worker session and many of the Mac's helpers at 22:02:40; the app and the loop started them again. A process is now stopped by its PID.
* The step named `default_Contact_crysis.CRYSISJMSF` as the save before the suit's reboot without checking which program wrote it. It is the game's own start checkpoint, which each flyby rewrites, so the first HUD run played the opening jump in a loop.
* hud-3 set the log levels at the start, which slowed the load sixfold; hud-4 sets them after it.
* The first rehearsal booted no root: `gnu-test.ext2` is an intermediate that the `gnu-test.disk` rule deletes, and I had asked make for the disk. The rehearsal now cuts the root out of the disk; the Lenovo's procedure asks make for `gnu-test.ext2` alone, which keeps it.
* `save-update` ran mke2fs on the data disk inside the guest, and the ordinary kernel refuses raw writes through a disk node with EPERM, as disk(7) says. I had not read the page. The host now makes the volume, `save-volume.ext2`, from Rach2's `mke2fs.conf`.
* `save.py` read the registry value back from what `reg query` prints, which does not reach the launcher's output through Proton. It now reads the file `reg export` writes.
* `crysis.py` read the previous run's `Game.log`, so the umu flyby's "loaded in 36.00 s" is the direct run's line. The script now removes the log before each start; the 32-bit run's 38.81 s and every load after are the runs' own.
* `crysis.py` typed the save command at once, while "PRESS ANY KEY TO CONTINUE" still showed and then during the level's opening cinematic, in which the game refuses a save. It now reads the prompt from a screenshot, presses Return until the prompt goes, waits 90 s and tries the save up to twelve times, 10 s apart.
* A sync of the testing host's copy was refused while the rehearsal ran in it, and I stopped that run, `t2665u`, before it began, rather than test stale code; its claim left the admission ledger.

## save-update

`save-update` boots the GNU root, makes a Proton prefix and a save on a data volume, writes a registry value, and then boots a second root image on the same volume, as an update does. The save loads there through the old prefix, which keeps the value, and through a new one, which lacks it. It passed at 20:55 UTC+6 in 301 s (`save-update-pass.txt`: `SAVEROW OK save`, `SAVEROW OK load`). The run before it, at 20:49, failed once in the first boot. `wineboot` ended with status 247, which is Proton passing on a child killed by SIGKILL. The kernel's log had no line for it (`save-update-wineboot.txt`). This is its first appearance; if it comes a second time, the load that forces it is to be built and run with tracing.

## A fault fixed: virtio-gpu's fences

The first rehearsal panicked the kernel 679 s after boot, in the middle of the direct flyby: a page fault in kernel mode in the `virtio_gpu` worker (`panic.txt`). `cmd_done` signalled the earlier fences of a context by walking `vg->live` without the device's lock, and another processor freed a command on the list during the walk. `signal_through` now finds each earlier unsignalled fence under the lock, takes a reference, and signals it after unlocking. The next rehearsal ran the four direct loops, the umu loop and the 32-bit loop with no fault.

### 80-9.4, the suit's reboot: passed on the fourth run

* hud-1 loaded `default_Contact_crysis.CRYSISJMSF`, which the procedure named. The direct flyby's `+map island` had rewritten that file at 22:18:36 as the level's start checkpoint (play time 0), and every `+map island` writes it again. The game played the opening jump, the player lay in the water, died and was reloaded three times, and refused the save, for which the script waited without end. I ended it at 22:44 with SIGINT, so that its own cleanup ran. The owner's own save from play is `default_00_Contact_01m_18s.CRYSISJMSF`, checkpoint Island_01 at 78 s, as Linux's save 07 at 1 min 17 s was. It is unchanged, `d6458dec...392b`, and a second copy of it and its XML is in `/data/crysis-kept/` on the Lenovo.
* hud-2, from the owner's checkpoint: the HUD came back 35 s after the trigger, with the minimap, the ammunition, the bars, the crosshair and "Rendezvous with Jester. Activated" (`hud-2-after.jpg`), at 40.6 frames a second by the game's counter, and GameRules `hudShow="1"`. The dialog lines were not logged: of the three console lines typed together, `ds_loglevel 4` did not reach the game, and only `log_Verbosity` echoed.
* hud-3 set both log levels on the command line and loaded in 295.60 s. The game's load profile, which verbosity 4 prints, put 242.0 s of it in `CTexture::Precache` (`hud-3-load-profile.txt`); disk reads were nil and Mesa's cache did not grow. The game then ran at 13.7 frames a second, and 35 s after the trigger the suit menu still showed its malfunction state, so GameRules read `hudBroken="1"`.
* hud-4, the control, loaded the same copy at default verbosity in 53.20 s and set the levels after the load, one line at a time until each echoed. The two dialog lines played at 1.71 s and 8.42 s, Show 4,710 ms after the boot sequence against Linux's 4,693; GameRules `hudShow="1"`; the screenshot shows the HUD back (`hud-4-after.jpg`). So verbosity during the load was hud-3's whole cause.

`hud` now loads a copy of the save under the name `default_accept_src_NAME`, which it removes afterwards, so no step loads or writes a save under a name of the owner's; it sets the log levels after the load and tries its save six times, as `save` does.

### PulseAudio's OSS thread

With nothing playing, PulseAudio's OSS I/O thread was charged half a processor of system time: 519 ticks in 10 s at USER_HZ, 965 s over the boot's first 61 minutes, and 22 to 30% during the games. strace shows its ordinary loop at about 57 turns a second, `ppoll` on `/dev/dsp` blocking 1.5 to 22 ms, a write of 3,760 bytes of silence and a capture read of 4,096 (`pa-strace-head.txt`). Over 10 idle seconds `ppoll` held the big lock 3.6 ms in all (`calls-idle.txt`), so the time is spent outside the lock and is not contention. Where the thread's ticks go was not traced; the detail is on #2665.

## Missing calls in the rehearsal

The trace of missing calls named these in both rehearsals (`missing.txt`). Each program went on by its own fallback:

* 323, `userfaultfd`, by `wine` and `wine64`: Wine's write watches fall back to their own, on page protection, as in 80-12.
* 430, `fsopen`, by `mount`, at the rehearsal's own mount of the game's disk: util-linux falls back to `mount(2)`, and the mount succeeded.
* 444, `landlock_create_ruleset`, by `xz`, once in each rehearsal, at the umu flyby's start in the first and during `prepare` in the second; which program ran xz was not traced. xz takes Landlock as optional and runs without its sandbox.

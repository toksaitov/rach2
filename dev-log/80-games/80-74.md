# 80-74: HD Audio's periods rendered outside its interrupt

80-41's step on the Lenovo ([80-41.md](80-41.md)) measured the HD Audio interrupt, vector 48, holding the big lock 668 us each time in SuperTuxKart (6,622 times, 4.42 s of a 112.5 s run) and 626 us in 0 A.D. (10,115 times, 6.33 s of 173.6 s): it rendered each period in the interrupt, the mix of the open streams and its rate conversion among it. Linux's `azx_interrupt` only acknowledges the stream and calls `snd_pcm_period_elapsed`, which wakes the writer (sound/pci/hda/hda_controller.c:1056 and 1070, sound/core/pcm_lib.c:232, Linux 6.12.115); the copy into the ring runs in the writer's own call (`__snd_pcm_lib_xfer`, pcm_lib.c:2274), and PulseAudio mixes and resamples in user space.

## The change

The interrupt now reads `INTSTS`, clears each stream's status and wakes a kernel thread, `khda`; the timer tick wakes it when either stream's position has passed into a period the service has not seen, for a machine whose interrupts do not arrive. The thread runs the two services with interrupts on and the big lock held: the input stream's hand-over, then the output stream's refill, and with it the mix's `transfer`, the rate conversion and the streams' `period` calls. The services turn interrupts off only around the reads and updates of the position and the period state the delay is computed from, `hw_period_last`, `stream_in`, `stream_taken` and `cap_next`, and around the `period` calls, as Linux's `__snd_pcm_lib_xfer` drops the stream's lock around the writer's copy (sound/core/pcm_lib.c:2380-2387); the mix (`vchan.c`) holds its lock, with interrupts off, for one block of 256 frames at a time. The thread sets `in_syscall` while it serves, so that an interrupt only asks for a switch, and takes the switch once the service ends, so that no system call runs in the middle of a refill. It runs under `SCHED_FIFO` at priority 50, Linux's for an interrupt's thread (`sched_set_fifo`, kernel/sched/syscalls.c:873, from `irq_thread`, kernel/irq/manage.c:1310), so that a refill waits behind no ordinary program. The first program's start makes it (`hda_thread_start`, beside `platform_threads_start`), so that init stays process 1; before then, and while the scheduler is off, as under the debug shell, the interrupt and the tick run the services themselves, as before.

When the thread wakes it counts the hold of the lock that switched to it, an interrupt from user mode or a system call on its way out, as ended and starts its own as an entry of none, without giving the lock up (`bkl_thread_hold`, `smp.c`), so that `bkl/calls` charges the render to vector 0, with the returns from idle waits, and not to vector 48 or to the system call that happened to be leaving. Its time on the processor is in `/proc/PID/schedstat` of `khda`, counted in ticks.

The thread calls `hda_service_capture` and `hda_service_stream`, which the interrupt called; round 80's review (80-74.4 to .7) had the first version, which ran them with interrupts off and gave the big lock away on each wake, changed as above. [The audio Readme](../../rach2/sys/audio/Readme.md) says where the service runs now, and [the process subsystem's](../../rach2/sys/proc/Readme.md) and [debugfs(5)](../../man/man5/debugfs.5) how its hold is counted. The task was compile only: both kernels build, and `tests/host/hda_hosttest.c` compiles, whose rows run the services where the interrupt and the tick ask for them, since the host build has no thread; no test was run and nothing was booted.

Round 81's fixes (80-74.8 to .11) correct the comments and documents: a `bkl_thread_hold` ends a hold record without releasing the lock, so the wait's count of holds, the longest hold and the sampled age measure those records; only a thread calling it starts its own record. The audio Readme names each context of the mix and says that interrupts come between refill blocks only in `khda`, and the timer comment says the tick keeps HDA's wake requests going during a call. The nearby counter comments in `smp.c` and `percpu.h` now name the record too. Both kernels compile after these fixes and the merge from the milestone branch; no test ran and nothing booted. The manager gave the trial below its go at 83b763cb9; Results records that boot.

## Readiness

The step boots one new path on the Lenovo: the service in a kernel thread. It cannot stop the machine in a way the old path could not:

* No register sequence is new. The handler reads `INTSTS` and clears each stream's `SD_STS` as before, in the same order; the services read and write what they did. The thread sends no verb.
* No wait is new but the thread's own sleep, `wq_wait_event_idle`. The thread wakes holding the big lock, which the entry that switched to it held, and keeps it.
* Interrupts now come in during a refill on the thread's processor. The handler and the tick only ask for the thread then, and a service asked for while one runs returns at once (`hda_serve`), so no service runs inside another.
* The handler and the tick return at once after the wake. If the thread never ran, the device would play its three periods over and over and `/dev/dsp`'s writers would sleep for room; the interrupts, the tick and the rest of the system would go on, and SSH would answer.
* The thread is made from the first program's start, after the controller and its interrupt are set up, and only when HDA is the driver.

At the first handover the new path had not run anywhere: the task forbade a boot. The manager then gave the reviewed head its go for the Lenovo step, whose first result is below.

### The idle fix

The desktop loaded `module-oss` without `module-suspend-on-idle`. The trial root's source, 182c39024, has the same configuration. This leaves both endpoints open: PulseAudio's OSS driver writes silence and reads capture even in its IDLE state. That is its stated contract, not an upstream fault ([PulseAudio 17.0, module-oss.c:21-33](https://github.com/pulseaudio/pulseaudio/blob/v17.0/src/modules/oss/module-oss.c#L21)). The idle sample's `playing 1`, `capture running 1`, growing frames and refills therefore describe active silent streams, despite having no sink inputs.

The desktop configuration now loads `module-suspend-on-idle`, as [PulseAudio's default configuration does](https://github.com/pulseaudio/pulseaudio/blob/v17.0/src/daemon/default.pa.in#L143). Its [default timeout is five seconds](https://github.com/pulseaudio/pulseaudio/blob/v17.0/src/modules/module-suspend-on-idle.c#L421). The OSS module suspends each direction through its trigger; once both suspend, [it drains and closes the device](https://github.com/pulseaudio/pulseaudio/blob/v17.0/src/modules/oss/module-oss.c#L492). A new client opens it again. In Rach2, `dspdev_close` halts both directions, `vchan_stop` and `vchan_capture_stop` stop their device stream when its last running channel leaves, and HDA clears the stream's run and interrupt bits. The kernel therefore has no idle policy to add: it must keep serving an application that deliberately streams silence.

Linux 6.12.115 has the same stop behavior: [azx_pcm_trigger calls snd_hdac_stream_stop](https://github.com/gregkh/linux/blob/v6.12.115/sound/pci/hda/hda_controller.c#L260), whose [clear and stop at hdac_stream.c:167-189](https://github.com/gregkh/linux/blob/v6.12.115/sound/hda/hdac_stream.c#L167) stop DMA and mask the stream's interrupts. With no stream status, [azx_interrupt's loop ends at hda_controller.c:1089-1092](https://github.com/gregkh/linux/blob/v6.12.115/sound/pci/hda/hda_controller.c#L1089). The fix changes the desktop's policy only; it adds no register access or kernel wait. Its idle, resume and post-game results still need the next trial. It does not establish the cause of the earlier missed revolution or game p99.

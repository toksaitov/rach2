# 80-75: what the timer tick does under the big lock

80-41's step on the Lenovo measured the timer tick, vector 32, holding the big lock 39.3 us a tick in SuperTuxKart (219,728 ticks, 8.63 s held, 9.33 s waited in 112.5 s) and 41.1 us in 0 A.D. (313,612 ticks, 12.88 s held, 15.69 s waited). The boot processor's tick runs some sixteen services, and the profile, which the tick takes, cannot sample the tick itself. This task counts each part of the tick, moves out of it the work Linux's tick does not do, and hands the Lenovo's reading to a trial boot. The big lock stays, by the owner's decision: work moves, the lock is not split.

## The counts

debugfs's `bkl/tick` ([debugfs(5)](../../man/man5/debugfs.5), [the process subsystem](../../rach2/sys/proc/Readme.md)) has a row for each part of the tick: the calls, their time in TSC cycles and in microseconds, and the longest. `timer_handler` (`rach2/kernel.c`) reads the cycle count after each part and charges it (`bkl_tick_charge`, `rach2/sys/proc/smp.c`); `entry` is the router's work from the take of the lock to the handler; `return` is the time from the tick's `sched_preempt` to the end of its hold, and `switch` the same when the hold ended at a switch to another thread, which lets the lock go (`schedule`); the thread switched to takes the lock again in a hold of its own, which `bkl/calls` counts as a take after a switch. `nested` counts the ticks that came inside a hold, whose time is that hold's. The rows but `nested`, less `nested`, sum to vector 32's `held_us` in `bkl/calls`: 99.97% and 99.9% of it in the two idle readings below.

## On QEMU

Over the 10 s vector 32 held the lock 2,392 ms before and 816 ms after, of 35,961 and 39,982 ticks. With four busy loops in user mode it held it 2,254 ms before and 783 ms after. What is left is `entry`, which under KVM is the local APIC's end of interrupt, a write that exits, and `clock`, the read of the HPET's counter that `timer_tick_clock` makes, which QEMU emulates; on real hardware each is about a microsecond.

The same boot with the changes: the keyboard enumerated at boot; a tablet hot-plugged through QEMU's monitor enumerated on port 6 half a second after `device_add`, its `device_del` was seen at once (`usb: device: port 6: gone`), and a second tablet enumerated on port 7; `/proc/interrupts`' `usb fallback` stayed 0, and every command typed on the serial console arrived (COM1's interrupts went from 7 to 13 over the run).

## What moved

* USB's root ports. Every tick `xhci_events` read each root port's PORTSC (`port_scan`) and `usb_core_step` read each device's port and each root port again: 2 x 8 reads on QEMU, and on the Lenovo's controller twice its ports. Linux reads a root port only after a Port Status Change Event, polling the root hub every quarter second until no change bit is left (`drivers/usb/host/xhci-ring.c:2124-2137`, `xhci-hub.c:1705-1708`, `drivers/usb/core/hcd.c:764-770`; the citations here are of 6.12.115). The scan now runs after such an event, while a connect is inside its 100 ms debounce, and every 250 ms; the core's tick reads the scan's connect bits (`xhci_port_connected`). Rach2 dropped the event and never cleared a connect change, so the controller raised no second event; a scan now clears the change bits it finds, but the reset's, over Linux's neutral bits (`xhci_port_state_to_neutral`, `xhci_clear_port_change_bit`, `xhci-hub.c:392-449, 580-623`), so that a reset under way is not written again. The quarter-second reading does not stop as Linux's does, so that a change the reset's bit hid from the events is still read. A timer's drain that took no event no longer writes the dequeue pointer; the handler's drain still does, as Linux writes it in its interrupt handler alone (`xhci-ring.c:3139-3187`).
* HD Audio's stream service. The interrupt refills each period played, and the tick refilled them too, every tick while a stream played, with two register reads; a period the tick reached first was rendered in the tick. Linux serves a stream from its interrupt alone (`azx_interrupt` and `stream_update`, `sound/pci/hda/hda_controller.c:1056-1094`). The tick now serves the output and the input stream only until each one's first interrupt after its start, and afterwards only while more than a period and a half has passed since the last, half a period after the next was due (`hda_irq_late`), so a machine whose interrupts never arrive still plays from the tick. Since 80-74 merged, the services run in its kernel thread, `khda`, which the interrupt and the tick only wake (`hda_service_kick`); the interrupt marks each stream's interrupt beside its request, and the tick decides each stream's request by the same gate before it reads that stream's position, which it reads only to wake the thread once the stream has passed into another period (`hda_service_due`). So a quiet tick reads no stream register, and before the thread runs the tick's request goes through the same serving guard as the interrupt's (`hda_serve`).
* The console's UART. The tick read COM1's line status every tick, though the receive interrupt moves the bytes. Linux reads an 8250 that has an interrupt from no timer: its backup timer only sends, for a UART with the THRE bug (`drivers/tty/serial/8250/8250_core.c:269-275`), and a port without an interrupt is polled every `uart_poll_timeout` (207-213). The tick now reads the port at every tick until the receive interrupt has taken a byte, and every fifth of a second after, Rach2's own fallback for a lost edge; the delivery from the ring to a reader, which touches no register, stays at every tick. Reading the port every millisecond had hidden that the handler, which took at most 64 bytes and returned with data still in the FIFO, left IRQ 4's edge-triggered line high, so that no interrupt came again; the handler now makes passes until the line drops, as Linux's `serial8250_interrupt` does (68-110).

## What stays, and why

* `clock`, `account` and `wake`: the count of the tick, the clock's pass, the time charged and the sleepers and timers due. Linux's tick does the same work, with no global lock (`tick_sched_handle`, `kernel/time/tick-sched.c:253-278`, and `update_process_times`, `kernel/time/timer.c:2514-2529`). The clock's pass reads the reference counter, the HPET on the Lenovo, where Linux's reads the TSC; whether that costs enough to move is what the Lenovo's reading says.
* The other processors' ticks, `ap_account` and `ap_late_pass`. They take the lock only when it is free or when work is queued, and their accounting charges CPU timers and sends their signals, which needs it; taking it less often would change what `times` and the interval timers see.
* The fourteen cheap services, `netdev`, `ath9k`, `tcp`, `ip_frag`, `ip6`, `netlink`, `ip_loop`, `input`, `block_lag`, `block_request`, `platform`, `vkms`, `speaker` and `hda`'s jacks and beep: 2.6 us a tick together on QEMU, touching no register on a quiet tick. Linux runs each from a timer that fires only when armed. Moving them to a kernel thread woken each tick would cost a switch there and back under the lock, the `return` row and an `entry`'s worth, more than they cost now, and arming a timer for each needs each subsystem to keep its next deadline, which is work the size of its own task. The Lenovo's reading says whether any of them costs more there, and reads `netconsole`, the netconsole's service, and `klog`, the writing out of log records kept for a holder of the big lock, which reached the branch after the readings above, each in a row of its own.

## Readiness for the trial

The trial boots code that has never run on the Lenovo. What reaches a device:

* The PORTSC write that clears change bits is Linux's: the neutral bits as read, RO and RWS, `0x4E00FFE9`, with the change bits found set, less PRC while a reset of the port is under way. It never writes PR, PED, LWS or a reserved bit, so it cannot start a reset or disable a port. On a port with no reset under way, one whose device left during its reset among them, it clears PRC too, as Linux's `port_event` clears a stray C_RESET (`drivers/usb/core/hub.c:5811-5813`), and the write that starts a reset clears a PRC still set, so that a reset change bit left by an abandoned reset neither holds back the port's events nor passes for the next reset's end. `xhci_hosttest`'s `check_port_scan`, run alone before these two, checks the reads, the clearing, the reset bit left alone and the quarter-second reading over the controller model; its rows for the two were compiled, not run.
* The dequeue pointer is written by every drain that took events and every drain of the interrupt handler, as before; only a timer's drain that took nothing writes nothing. The busy bit it would have cleared is set only by an interrupt whose events a drain took, and that drain wrote it, or whose handler has still to run and will.
* HD Audio and the UART make fewer reads of the registers they read before and no new access. No path adds a wait or changes what is masked.
* The counters are arithmetic under the lock and a debugfs file.

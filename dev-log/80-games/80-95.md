# 80-95: Linux's on-demand readahead for file reads

80-92 ([80-92.md](80-92.md)) found Crysis's level load waiting on every readahead window: the file page cache read the next 128 KiB only when a reader reached it, so the main thread waited for each run, 4,500 to 7,100 requests a load against Linux's 3,600. A read that did not go on exactly where the description's last read ended got no window at all, only the pages it asked for. This task gives file reads Linux's on-demand readahead (mm/readahead.c of Linux 6.12.115). read(2) of an ext2 file reads its data into the file page cache past the buffer cache, so the window is the file page cache's; the buffer cache's read run of 128 KiB (bcache.c) still serves metadata and the pages the file page cache reads through the buffer cache, as Linux reads buffer heads apart from the page cache's readahead.

## What the kernel does

Each description keeps Linux's `struct file_ra_state` (`ofd->ra`, [fd.h](../../rach2/sys/fs/fd.h)): the last window, `size` pages from `start`, of which the last `async_size` start the next; the most a window takes; the byte after the last one read; and POSIX_FADV_RANDOM. The rules are Linux's, function for function ([filecache.c](../../rach2/sys/mm/filecache.c)):

* A miss reads a window from the page it wants at once (`fc_sync_ra`, `page_cache_sync_ra`). At the start of the file, for a read longer than the most a window takes, or for a read that goes on from the last one, the window is the first size (`get_init_ra_size`). Otherwise the pages the cache has just before the miss tell a stream from a random read (`page_cache_prev_miss`): a random read reads what it asks for and leaves the state alone.
* The page at `start + size - async_size` is marked when it is read, a bit of the page's record that stands for PG_readahead. A read that reaches it clears it and queues the next window (`fc_async_ra`, `page_cache_async_ra`), grown by `get_next_ra_size` up to the most, and goes on without waiting.
* The most is 32 pages, 64 after POSIX_FADV_SEQUENTIAL, and for a longer read as many pages as one request to the device moves (`ractl_max_pages`), 256 on AHCI. A window goes to the disk in requests that long: a run of `read_frames` takes up to 256 pages, its arrays from the heap past 32, and ext2 plans that many pages at once.
* A queued window is a job, one of 16, which up to four kernel threads, `kreadahead`, read oldest first. Linux puts a window's folios in the page cache locked before the device fills them; here a reader that reaches a page of a job's window waits for the job's end, and reaching the job's marked page first queues the next window before the wait. A job holds its description and has entered its mount, so an unmount waits for it, as Linux's waits on the locked folios.
* POSIX_FADV_WILLNEED and readahead(2) queue the range as a job, at most the larger of the window's most and one request (`force_page_cache_ra`). POSIX_FADV_DONTNEED drops the range's whole pages, which are all clean here. [readahead(2)](../../man/man2/readahead.2) gives the user's view and [the memory Readme](../../rach2/sys/mm/Readme.md#the-file-page-cache) the design.

The block layer polls a disk for a caller outside a system call and stops the kernel on a disk that cannot be polled, so the first version's worker polled AHCI through a bounce buffer of 32 pages: it read correctly but in requests of 128 KiB, and on a USB disk would have stopped the kernel. The worker now marks itself in a call across each job, as a fault's resolution does; it does not between jobs, since a kernel thread so marked counts as one that is exiting.

## The check in QEMU

The x86-64 kernel booted under TCG on the Mac, two processors and 1 GiB, with the os-real root of the clone on AHCI and a data disk of 320 MiB on AHCI holding a file of 256 MiB of random bytes, made with `mke2fs -t ext2 -b 4096 -O ^dir_index`. BusyBox's init ran a script and powered the machine off. Each read ran on a fresh mount, so nothing of the file was cached; the requests are the reads `/proc/diskstats` counted on the data disk, among them the file's 65 indirect blocks and the windows they split in two.

| Read | Base bc68ef2d9 | This task bd2b98391 |
|---|---|---|
| `dd bs=4096`, requests | 2,180 | 2,181 |
| `dd bs=4096`, seconds | 0.82 | 0.80, and 0.68 and 0.69 in two earlier boots of this task's work |
| `md5sum`, requests | 2,182 | 2,183 |
| `dd bs=1048576`, requests | 2,181 | 390 |
| `dd bs=1048576`, seconds | 0.45 | 0.25 |
| 200 reads of one page at scattered offsets, requests | 268 | 268 |

A read in order in pages of 4 KiB already read 128 KiB windows at the base, which counted a read that went on from the last one; what it lacked is the window started early, which TCG, whose disk answers from the host's cache, cannot show by time, and a window for a read that does not go on exactly from the last one. A read of 1 MiB now takes one request of 1 MiB per window, as Linux's bio of up to 256 pages does, where the base read 128 KiB a request. Random reads of a page read the page alone on both.

The same boot checked readers that share a file: two `md5sum` of the file at once gave the right sum each in 2,182 requests, every page read once; three streams at different places, two `dd` and an `md5sum`, read the whole file in 2,177; `readahead` on the file and an unmount at once both returned 0; and four `kreadahead` threads ran.

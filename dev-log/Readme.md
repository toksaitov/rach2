# dev-log

This directory records how each Rach2 milestone was planned and built, with one subdirectory per milestone. Milestone 1 retains its prompts; later milestones retain their plans.

A milestone runs from its `plan.md`. It stops only when the goal is met or when a phase remains impossible after three supported attempts. The latter result includes its evidence. The starting prompt is one line of fewer than thirty words that identifies the plan file, because the receiving interface truncates longer prompts.

These records establish what was decided and when, but they do not define the writing style. Milestones before 26 predate a measurable register rule and retain the habits addressed by milestone 26. Use them for history and use `CLAUDE.md` for the writing standard. Their wording remains unchanged because a rewrite would alter the record.

The list contains completed work, and its last entry describes the current tree. A directory containing only a `plan.md` represents planned work and is absent because an index entry asserts completion. `tools/check_devlog.py` enforces this correspondence during every `make verify-style`.

* `01-foundation`: the first OS, including boot, paging, system calls, the shell, audio, and Doom.
* `02-networking-and-userland`: the TCP/IP stack, ported musl libc, BusyBox, Dropbear SSH server, and modernized build.
* `03-text-standard`: the text and documentation standard, the refactor that applied it, and the check that preserves it.
* `04-normalization`: application of that standard to the remaining in-house tree, including the tests, KRFFS host tools, utilities, and ish shell, with a wider check for the added scope.
* `05-images`: replacement of one overloaded RAM disk with three images: a test image, an in-house simple-tools image, and a BusyBox, Dropbear, and Doom environment. A manifest-driven stager builds them, `make test` checks a boot, and each image has a bootable ISO.
* `06-review`: a complete audit of the system's code, comments, documentation, support files, and manual tests. Every candidate finding required verification before acceptance; safe fixes used scoped commits, followed by checks of the style rules, boots, and capstone against a recorded baseline.
* `07-init`: a persistent userland init at `/sbin/init` that reaps orphans and respawns the login shell, the kernel orphan reparenting required by that behavior, and a `rach2.rescue` boot flag that makes the kernel debug shell an explicit rescue mode instead of the default environment.
* `08-disk`: Path B moved KRFFS from the RAM-disk module to an ATA disk through a kernel page cache and demand-paged kernel virtual window. The fault polls sectors instead of sleeping because interrupts are disabled. The result includes write-back, fsync, a dirty-mount flag, and GRUB boot from disk.
* `09-audit`: a four-part audit of code, comments, documentation, and support files after the disk milestone. Ten risk-ordered multi-agent phases verified every candidate finding. The audit found and fixed one defect: a user read of the page-cache window panicked the kernel instead of producing a clean segmentation fault. It also aligned comments and Readmes with the disk-backed system.
* `10-ahci`: the modern SATA half of the disk layer. An AHCI driver publishes the same `block0` interface as the ATA driver and polls `PxCI` for completion, allowing calls from the page-cache fault while interrupts are disabled. Selection through `rach2.disk=ahci` leaves the legacy IDE boot byte-for-byte unchanged. The disk probes and the SSH and Doom capstones all run over a SATA disk.
* `11-audit`: the post-AHCI audit used eight risk-ordered multi-agent phases to verify every candidate finding, followed by an independent Codex check of each phase. It found and fixed eleven defects. The most serious were in error paths absent from QEMU: command completion reported two hardware-only fatal errors as success. Both are now detected and the port is recovered in place. The audit also aligned comments, Readmes, and support scripts with the code.
* `12-review`: a production-readiness review covered the entire OS in thirty risk-ordered multi-agent phases: boot, memory, page cache, KRFFS, syscall ABI, processes and signals, file descriptors, TTY and pty, poll and pipes, network stack, audio, peripherals, freestanding library, userland, host tools, and trust boundary. It confirmed and fixed about fifty defects, with the most serious in TCP closing states and send-side backpressure. It also established two negative results: hostile frames cannot cause an out-of-bounds access at any layer, and ring 3 cannot escape. Codex independently rejected the group's refutation of the keyboard early-unmask defect and found two regressions in the review's TCP fix. Live tests included the network and capstones.
* `13-post-review`: small follow-ups to milestone 12 were committed on `master` instead of forming another milestone. They added the full BusyBox applet set (`defconfig` except Linux-only tools), a VT100/ANSI interpreter for the VGA console so line editing and `vi` render in the QEMU window, and a fix for SSH forwarding in `run_from_disk.sh`.
* `14-multiuser`: five reviewed phases added the classic Unix multi-user model. Processes have V7 credentials with POSIX saved IDs. New files receive ownership at creation, with working `chmod` and `chown`. Every open, create, and exec path enforces the nine permission bits. The SSH capstone logs into an unprivileged `test` account as well as root, and the kernel isolates each from the other.
* `15-privilege`: six reviewed phases added controlled privilege recovery. A host tool using vendored musl crypt creates a real `/etc/shadow` with `$6$` hashes at build time. IP loopback uses a `127/8` alias delivered through a timer-drained ring. The test account accepts SSH passwords while root remains public-key only. Exec applies setuid and setgid bits and sets `AT_SECURE`. A small setuid-root `su` is the only privilege-elevation path; a reference `sudo` is included only as coursework. BusyBox remains unprivileged because an attempted setuid build exposed a latent BusyBox use-after-free that the kernel's strict `munmap` detects.
* `16-review`: the privilege audit used six risk-ordered phases, with Codex independently checking the trust boundary and network. Traces rejected every candidate privilege escalation. The audit fixed four defects: `su` inherited the caller's environment and exposed a `PS1` command-substitution vector; a missing martian-source filter allowed a spoofed local address into the loopback path; two privilege probes could pass after a crash because they used `WEXITSTATUS` without `WIFEXITED`; and the generator left temporary files unignored.
* `17-completion`: seventeen reviewed phases closed milestone 15's deferrals. Each deferral ended in a probe that can fail or in a stated policy with its reason. A descriptor identifies the same file across `unlink`, `rename`, and relocation. One credential library provides an uninterrupted lock, durable replacement, and signal-safe prompt. `passwd` and `adduser` use it; the latter publishes four items in an order where every prefix is usable, proved by a crash build that stops at each point. Console access passes through `login` and cannot fall back to an unauthenticated shell because init builds twice and the strict artifact contains no string identifying such a shell. Ping waits by sleeping instead of letting an unprivileged request freeze every process for four seconds. An attached disk is mounted, making os-real the writable Rach2. Empty datagrams, bound client ports, one listener per port, and simultaneous open close the remaining network gaps. `make test` grew from 44 probes to 51; `make login-test` and `make ping-test` became required checks.
* `18-shutdown`: nine reviewed phases completed clean shutdown, the final deferral from milestone 15. Userland can stop the machine because `reboot(2)` is syscall 88 and `/sbin/init` is pid 1 in the implementation as well as the documentation; bare `halt`, `poweroff`, and `reboot` signal that process. One kernel path now stops the machine, parks the CPU in a loop instead of one `cli; hlt`, derives the PIIX4 power-management base from PCI configuration space instead of assuming a port, and reports the requested and observed result. Clean unmount flushes before clearing the dirty-mount flag. Planning found that a partial write-back could previously fail the complete operation after writing part of the cache, allowing the early clear to mark an image clean while data was missing. The flag now identifies an interrupted boot instead of every boot. `make test` grew to 52 probes, and `make shutdown-test` added eight boots to the required checks.
* `19-busybox-first`: the milestone assigned each implementation according to one rule: use as much BusyBox functionality as possible. Os-real now uses BusyBox account tools, including three set-id programs from a SECOND build containing only `login`, `passwd`, and `su`, as BusyBox's `Config.in` recommends. Os-simple changed from a root-level shell and utility collection into a small Unix made from project code with login in front. This preserves the programs from the privilege milestones and permits comparison between the two images; nothing was deleted. The work found that the kernel lacked `readv`, which musl buffered I/O uses when requesting more than one byte. Every program using `fgets` or `fread` had therefore failed silently, while three in-house comments described the failure as system behavior. It also found two kernel defects. A process left its process group at exit instead of reap, denying the terminal to a shell when a pipeline's first command had already finished. A write pre-fault reported a copy-on-write page as backed, promising a page that faulted on the next store. Image checks now inspect the staged applet tables and `oldconfig`-resolved configurations beside their binaries. They also check the mode, owner, and source of every unprivileged program run by root because `/bin/login` staged with mode 0777 needs no set-id bit to create a vulnerability. `make test` grew to 54 probes, and `make account-test` runs both images.
* `20-compiler`: TinyCC lets a student build a program on Rach2 as well as for it. It is vendored and cross-built like musl, BusyBox, and Dropbear, then staged in os-real with its configured sysroot: musl headers and `libc.a`, startup objects, TinyCC's runtime, and project utility sources at `/src/utils`. One TinyCC binary provides the compiler, assembler, and linker. GCC and Clang would provide only compilation and require additional ports for the other tools and for a missing `make`. A pinned patch gives a specific refusal for every unsupported output: `-run`, which compiles into memory and jumps through the unavailable `mprotect`; shared libraries; executable links without `-static`, because the loader maps `PT_LOAD` and ignores `PT_INTERP`; and raw images, whose output format differs from the output type. A manifest directive stages the sysroot as a directory tree because listing 218 headers separately is impractical. The kernel also needed more than twelve simultaneous mappings; on a machine with free memory, that limit produced `memory full (malloc)`. `make ssh-test` now implements its documented capstone without interactive input: it logs in by key and password, proves which method admitted each session, and rejects three prohibited attempts. `make test` grew to 55 probes. `make tcc-test` compiles a program and one project utility on the machine as an unprivileged user. Every boot harness now terminates its machine on every exit path.
* `21-time-and-make`: pdpmake first required working file times. Make compares modification times, but the kernel reported zero for every file and did not stamp writes. A build could therefore appear successful while doing no work; pdpmake treats a zero time as a missing file and would build nothing. At boot, the machine now reads the CMOS clock once and anchors an epoch to the reported second and the uptime second of the read. It advances from uptime seconds instead of ticks because a 32-bit tick counter wraps after 497 days. It rejects clock contents that the hardware marks untrustworthy, such as those from a dead battery, while preserving the existing meaning of `CLOCK_MONOTONIC`. Every `stat` path reports stored file-system times. One helper applies POSIX timestamps, while reads do not update them because this file system uses a write-back page cache. Staging node times also made two builds of the same tree byte-for-byte identical. `execve` increased from 15 arguments and 512 string bytes to 63 entries per vector and a shared 3072-byte budget. The limit comes from the initial stack's single page and is checked during copy-in, before destroying the old image would turn refusal into termination. `system(3)` and `popen(3)` now work. Review rejected a planned `clone` shim because the kernel had not received that operation; vendored musl instead forks from `posix_spawn`, while syscall 120 still returns `ENOSYS`. pdpmake 2.0.4 is vendored as `/bin/make`, TinyCC is also staged as `/bin/cc`, and `make make-test` proves a build across reboot. `make test` grew to 61 probes.
* `22-selfbuild`: Rach2 builds itself. The kernel, 24 utilities, and ish shell compile and link on the machine. Staged TinyCC runs under pdpmake using POSIX `guest.mk` files beside the sources at `/src`. The proof builds the kernel twice in clean workspaces and requires equal hashes, extracts the exact bytes from the disk image, checks their kernel structure on the host, and boots all 61 probes. Both toolchains use one source tree. Its 49 interrupt stubs are written out because TinyCC lacks `.macro`; three unsupported instructions are emitted as bytes; standard memory routines satisfy calls generated by both compilers; the entry is `_start` and the image end comes from `_end`; and TinyCC's native two-segment link uses a computed text address instead of an unreadable linker script. Self-build measurements also changed system limits. A 1 MiB page cache made each compile take more than a minute, so it became 4 MiB with a smaller value on constrained machines. The 64-entry VMA table failed while linking `login`, so it became 128 with a probe at the boundary. Accelerated BusyBox SHA faulted because the kernel lacks SIMD state, which remains a deferred contract. `make selfbuild-test` completes the loop in about seven minutes.
* `23-install`: the machine installs its self-built kernel and runs it at the next boot. The GRUB boot partition became the installation interface. install-kernel rewrites a candidate slot in place while leaving the fallback kernel untouched. GRUB's environment block selects exact menu ids. Each installation is a one-boot trial revoked by a power cycle until root commits the running kernel. Supporting this required a /dev permission model with the first restrictive device, a root-only raw boot-partition window, and kernel-buffered transfers; /proc/cmdline to report the booted entry; a pure MBR parser; and a host-tested FAT core. Before writing a sector, the FAT code validates the volume, chains, both kernels, and loader-visible region. Its interruption order leaves the machine bootable after a power loss at any point. Experiments established that GRUB ignores slot padding, rewrites its environment block in place, consumes next_entry only when scripted by the configuration, and resolves fallback by entry number. `make install-test` proves the loop twice on the booted disk, including marker-identified kernels, fallback, and in-place repair. `make bootpart-test` proves the device boundaries.
* `24-metal`: the local preparation for the notebook. The target is a Lenovo G50-70 without a serial port, with a Realtek RTL8168GU unavailable in local emulators and an SSD containing another person's Windows installation. Each constraint determined part of the work. A failed module-placement check includes its reason in the panic, and boot switches can skip individual device probes because the screen is the only output after a stopped boot. The network stack gained a device interface and an RTL8168GU driver based on a pinned Linux reference. A host test uses a software chip model in place of unavailable boot evidence. A second kernel enforces read-only disk access through an allowlist at each driver's command boundary; checks read that policy from the artifact and demonstrate it against disk-image bytes. Additional work sends the kernel log as broadcast frames below IP, takes an address from the boot line without inventing a gateway, polls the card from the 100 Hz tick, tries three restart mechanisms from broadest to narrowest, supervises SSH from init for unattended access, and resets AHCI during bring-up now that the driver can restore the link. Measurement found three defects. The largest made every kernel hardware wait between two and seven times too short because `init_pit` selects 8254 mode 3, where the counter advances by two per input clock. New proofs are `make metal-test`, `make diskpolicy-test`, `make netconsole-test`, `make test-addressed`, and `make subset-test`. This work did not touch the laptop, and the record identifies the claims awaiting hardware. It was the repository reference for the current tree.
* `25-sealed`: one image targets a 250 GB SSD that is written once and later maintained through SSH. The design has two disk-authority levels. The ordinary kernel may write the boot partition and post-MBR gap through two bounded devices. Only a separately built recovery kernel may write any drive sector because GRUB command lines are editable but compile-time policy is not. The disk geometry is part of the contract: a 64 MiB FAT32 boot partition with 4 KiB clusters, a 500 MiB root, and a 64 MiB recovery partition. The running machine can replace its boot loader by writing the inactive tail slot at LBA 2 or 1025 and then rewriting only the entry sector. A seven-entry menu assigns contractual numbers and resolves fallback by number instead of name. The device windows use 64-bit offsets to address the complete drive. Network configuration works on the attached network. A packet socket receives DHCP replies before the machine owns an address. A raw descriptor provides the `SIOCxIF*` interface ioctls expected by BusyBox. Images with BusyBox use `udhcpc`; other images use the project client. Recovery consists of a kernel and RAM root on partition 3 that mount nothing from the repaired disk, allowing `reflash` to rewrite it from an SSH pipe. `make sealed-test` exercises the artifact over SSH in eight phases: install, trial, and commit of a kernel; fallback from a destroyed candidate and repair through that fallback; complete and torn menu staging; boot-loader replacement through both tail slots; destruction and byte-identical recovery of the root through one pipe; and a control boot with neither fallback nor recovery. Hardware work proved separate claims in two environments. After a USB-adapter write and readback, QEMU booted the physical SSD rather than an image file. The ordinary root mounted from partition 2 through AHCI, `bootctl` reported a committed candidate with no trial armed, and `tcc` compiled and ran a program. On the Lenovo through the same adapter, only recovery entries can run because the kernel has no USB driver and cannot see its boot drive. That boot acquired the router's reserved address, accepted keyed SSH, and allocated a pty. It also found the laptop's Windows disk through AHCI, left it unmounted, and read back an unchanged first sector. The sealed root therefore ran in emulation from the physical drive but not on the laptop; at that point, the sealing session that installs the SSD remained outstanding. A later session installed the sealed SSD in the laptop and passed ordinary boot, networking, SSH, persistence, update, and recovery checks on the hardware.
* `26-portable`: prose, documentation, and migration to another machine. Since milestone 6, the register rule had required subjective review but had not governed the resulting prose. An outside reader identified recurring model habits, including the project's two largest measured anomalies. The five vendored upstream projects and Doom contain about 700,000 words of third-party comment prose, providing an in-tree control corpus. `tools/prose_check.py` reads the pinned tarballs, so the comparison also works from a fresh clone. Relative to upstream, `carries` fell from 35 times the rate to none, `holds` from 17 to 4, and `rather than` from 34 to 4, although much of the last reduction moved into `, not`. The 94 uses of one banned word were manually replaced with the four separate meanings they represented. The 80-column and vocabulary checks now fail a build; repetition remains a measured report for human review. For portability, `make doctor` stopped classifying the four tools required by `verify-style` as optional. Homebrew formulae moved into an installable manifest, the Ubuntu image used by GRUB steps became digest-pinned, and a clean clone builds `make full` and passes both suites without fetching dependencies.
* `27-prose`: one pass read every project-owned document and comment against the code it described, extending the vocabulary measurement from milestone 26. The worklist ordered vendored ports for provenance, reader-facing material, the kernel and headers at high effort, tools, and tests. Corrections included stale claims in a `dirtest` header that still said "KRFFS has no directories" after hierarchical directories existed, a `guest.mk` object count that remained 71 after reaching 87, and a `blockprobe` path helper described for fewer files than it built. Prose fixes covered a mangled-"has" with a missing verb, recurring orphaned words after comment wrapping, and a bad reflow that left one word on its own line. Reading found the reflow first; a later grep checked whether isolated words would fit on the preceding line and rejected three suspected cases as ordinary wrapping. The pass also fixed comment lines longer than 80 columns outside the directory checked by `check_comments.py`, repeated words, prohibited spaced-em-dash punctuation, and a Doxygen block separated from its code by a later function. Vendored upstream sources and the Doom port were read only for provenance and remained byte-for-byte unchanged because project writing rules do not govern third-party code. No accepted defect was later reverted. Three non-prose issues were recorded for milestone 28: a `.gdbinit` path stale since build-directory unification, a possible off-by-one in the `kio.c` control-byte check, and fragility in the `blockprobe` path helper. Keeping those code changes separate preserved the scope of this reading. `make verify-style` and `make verify-host` both pass.
* `28-polish`: machine-state diagnostics. `ps`, `df`, `free`, and `uptime` required missing `/proc` files. Each new value comes from kernel state. With no idle task, the timer measures idle time by sampling markers around the kernel's `sti; hlt` waits. Supporting `df` also required the previously absent `statfs64`. `netstat`, `route`, and `arp` needed three more files in the exact formats their parsers consume. Those files also required socket identity. Sockets previously had neither inode nor owner, which would make every row describe the same root-owned socket. A connection allocated in receive context now inherits the listener's uid. Every `/proc` text is generated at open in a bounded buffer; text exceeding its declared maximum is refused with a diagnostic instead of returning a silent truncation. The DHCP-oriented packet socket gained a second protocol, allowing `arping` to answer. A raw ICMP socket and configurable hop limit support `traceroute`, which reports the gateway as its first hop. Investigation of `stty` over SSH found correct kernel behavior and a client-requested zero-by-zero window, so no kernel fix was needed. The same investigation found and fixed a constant name used for every pipe. A boot that skips its requested root disk now halts instead of entering an unauthenticated shell; any boot with no mounted root also halts. A measured mapping limit increased from 128 to 512, replacing the value chosen after an earlier link failure, and exhaustion now identifies the process on the serial log. `dmesg` prints the boot log through the machine's existing interface. New proofs are `make raw-test`, `make bootline-test`, and `make procfiles-test`. The laptop remained powered off, leaving the hardware network checks and sealed drive for later work.
* `29-documentation`: every project-owned Markdown file was reviewed under one inventory. Current-contract documents were checked against the tree; historical records received prose and style review without factual revision. The work corrected build, test, file-system, process, network, port, and hardware contracts, then checked their terminology and ownership by subsystem and across the repository. Official vendor documents remained unchanged, while the project's vendor integration Readmes were included. The complete fixed-base diff contains only Markdown. The final tree passes the full build, style and host checks, all 63 default guest probes, six specialized evidence targets, and the dev-log checker.
* `30-build`: the build system and the tooling around it, rebuilt around a small public interface, one scripting language beside C, and a smaller required tool set. No kernel source, utility, or probe contract changed. The advertised interface is `make`, `make test`, `make clean`, `make distclean`, `tests/run NAME`, and `rach2/run.sh IMAGE`; the forty-seven targets it replaces survive as aliases that print a retirement notice. The default build became correct rather than merely quick. Every published artifact with a semantic validator is built to a temporary file, validated, and renamed into place, with the validator a prerequisite of a stamp that consumers depend on, so editing a checker revalidates the artifact without recompiling it and a failed revalidation removes the artifact instead of leaving it. The three images became file targets with a complete staging closure that records the directories traversed and the optional files absent, so only an affected image restages. Vendor builds declare their outputs and patch inputs, heal a deleted output at parse time, and join the caller's job budget instead of each choosing its own parallelism; a plain `make` is therefore serial for the first time, at 119 s cold against a 60 s baseline that only looked serial, and `make -j8` builds cold in 35 s. Python, Expect, Perl, `gtimeout`, `parted`, `grub-editenv`, host SHA-256 tools, and host `strings` left the tree, and every binary format the build reads is now parsed by a small C program: ELF and multiboot, MBR tables, the GRUB core embedding, packet captures, KRFFS images and the set-id inventory, FAT fixtures, and the prose, guest-build, and configuration checks. The QEMU harness, probe runner, and pty driver are C as well. Each replacement ran beside its predecessor over real and crafted inputs before the predecessor was removed. Docker left every build, image procedure, and test: six GRUB boot artifacts are pinned under `vendor/grub/` with a provenance manifest, a digest verifier every consumer runs, and a maintainer regeneration procedure pinned to one dated archive snapshot, and the disk a native build produces matches the container's except for two bytes of mformat's OEM string. Two conversion faults were found by running rather than reading: seven suite targets invoke their runner from the suite script rather than the recipe, so a prerequisite scan missed them, and a menu fixture padded from a length two bytes short and destroyed the GRUB environment block behind it. Two independent reviews then read the new C and returned twenty-two defects between them: four memory faults in parsers reading untrusted bytes, and the rest one fail-open fault repeated, where a checker that could not read something reported the same result as a clean tree. All are fixed, each with a case that fails without its fix.
* `31-setup`: milestone 30's two leftovers, and the stale claims found while closing them. The forty-seven retirement aliases are gone, so the interface is what the root Readme documents and nothing else; every document, comment, and manifest that named a retired target now names the current command. The Mac-only bootstrap script and its formula manifest are deleted in favour of setup instructions in `tools/Readme.md` for the latest macOS and for Debian and Ubuntu, including the cross-toolchain build no Debian package provides and the reason it must carry `all-target-libgcc`. Five declarations did not match the tree and were found by reading rather than by a failing run: `tests/registry` still required `perl` and `expect`, which nothing invokes since the Python conversion, so a machine following the documented dependency list would have had five suites refuse to start; the same registry declared no mtools for the seven suites that build GRUB disks; `doctor.sh` called `ssh-keygen` optional although the default build provisions demo login keys with it, and checked neither mtools nor `xorriso`; and `mk/toolchain.mk` offered an `x86_64-elf-gcc` fallback that cannot work, because musl and both `muslgcc` wrappers name the `i686-elf` prefix. Eleven comments still called Docker required after it left the build in milestone 30, one file contradicting itself within twenty-five lines; Docker remains genuinely required only by the `vendor/grub` regeneration procedure. `prosecheck` classified hash-commented files by extension, so files named `Makefile` escaped the eighty-column rule entirely: ninety-eight comment lines across seven makefiles were over it, and the classifier now names `Makefile`, the root Makefile joins the walked roots, and the reflow was checked by comparing the set of comment words in every file before and after.
* `32-netdev`: a third network driver, and the driver interface that carries three instead of accommodating two. The kernel could not drive the card QEMU attaches when nobody asks for one, so a plain `qemu-system-i386` command line produced a machine with no network and no explanation; the root Readme recorded that and left it. The new driver is the Intel 82540EM, the descriptor-ring design with no indirect-access windows and no vendor firmware, which makes it the one to read before the RTL8168GU rather than after it. It was written first against the interface as it stood, and the interface was revised afterwards with three drivers in hand, on the reasoning that an interface designed from two examples and validated by a third is a guess. Three members were added, each with a consumer already in the tree: `tx` returns a verdict, because every driver drops frames under conditions it cannot avoid and `/proc/net/dev` printed its drop columns as zeros with a comment claiming that was what a healthy card reports; `stop` silences a card, because nothing quiesced a bus-mastering device at shutdown and a mutation that removes the call puts `poweroff: powering off` on the captured wire; and `link` reports the link, because `IFF_RUNNING` meant only that a card was bound. Two defects surfaced from the proofs rather than from reading. `k_puts` writes to the VGA console alone, so the shutdown line never reached serial and a machine read over netconsole was never told it was stopping. `kstring.c` cannot be compiled natively above `-O0` without a sanitizer, because it defines `memset` as a wrapper around `k_memset` whose loop the compiler turns back into a call to the wrapper; the suite's sanitizers had always hidden it. New proofs are `tests/host/e1000_hosttest.c`, `tests/host/netdev_hosttest.c`, `tests/run e1000` with its three probe-order boots, a sixteen-field check on `/proc/net/dev`, and a netconsole shutdown contract read through a new `pcapcheck --reject`. Two independent reviews of six files each then returned fifteen findings, the most serious found by both: the transmit ring could publish a full ring as an empty one, which would have stopped the link for good, and the host test asserted that behaviour was correct. The reset also used the memory window Intel's erratum warns against, two `stop` implementations failed in the case the operation exists for, an interrupt line above fifteen would have installed a network handler on an exception vector, and the shutdown contract was untrue because a transmit returns when the descriptor is posted rather than when the frame has left. All are fixed. Thirty-eight mutations each made one named check fail and only that one. All 44 suites pass.
* `33-fast`: `tests/run all` went from 81 minutes to under 8, and no check was weakened to do it. The suite was not slow but asleep and serial: a boot costs 4.76 seconds and a fifth of a processor, and one QEMU sat at three percent of one core while nine others idled. The suites now run through a pool after one `make -j prepare-all`, with `style` and `host` outside it because they share a scratch directory and one of them builds the kernel. The `e1000` suite, 917 seconds of a 1205 second run, was not trimmed: the host model proves the driver in isolation but does not run the stack through the device, so instead the card picks the ports and tags the files each run writes, and both cards' suites run at once for 336 seconds with coverage intact. The worker count is twice the processors, measured at 1286, 728, 587, 527, 499 and 500 seconds for four through twenty-four workers; four, which an earlier draft called a measured ceiling without measuring, is two and a half times slower than the knee. The pool starts the longest suite first from what each took last time, because the three longest sat at registry positions 20, 32 and 40 and became a tail nothing overlapped. Going faster then found three defects that serial execution had hidden: the `crash` suite leaked three machines a run because `qemu_disk` was a backgrounded shell function whose pid was the subshell's and never QEMU's, with fifteen alive on one machine and the oldest three days old; the two credential generators raced under `make -j` on their temporary files, which was the cause of `selfbuild` passing alone in 230 seconds and failing in 52 under load; and several suites wrote each other's images and forwarded each other's ports. Two changes were considered and refused. `pump` was not made to stop on the success pattern, because that would defeat every timed absence assertion, `reset` among them, where the token is printed before the thing the interval is watching for. `account`'s per-line pacing was not converted, because the suite types ahead of the prompts that read it and a feeder that waits for quiet leaves `passwd`'s three prompts unanswered. * `34-messages`: the kernel log, and the test system that was supposed to catch what it said. * `44-krffsmount`: mounting KRFFS. A volume that is not the root is mounted by `mount(2)`: a partition of a disk or a stick, or an image file on any mounted file system through a loop device, and the kernel has one implementation of the format instead of two. `krffs.c` addresses nodes by their offset from the first byte of the region and reaches the medium through a backend of three calls, so the root in memory and a volume on a disk differ by three functions; the root keeps the pointer interface its callers use. `krffsmount.c` is the block backend and the VFS type: two volumes at once, sixteen open files each, the mount's lock around every change, and a node that moves followed into the descriptions, working directories, covering mounts and loop devices that named it. `/dev/loop0` to `/dev/loop3` stand on regular files, attached through `/dev/loop-control` by `loopctl` and listed in `/proc/loop`; a write to one is a write of the file and a sync of it, so the cache's promise holds. The block layer gained a third kind of device for them, one that answers in the caller's own call and takes no slot of the request pool, and a device now names the device its bytes live on, which the buffer cache reads so that a file system on a loop device may take a block of the device under it. The order of writes is the substance: the forward chain is the truth, the bytes reach the medium before the field that publishes them, one field publishes one change, and the backward link is derived and repaired at the next mount. One state that order cannot rule out is a field the medium takes in two pieces, since a header falls where the packing puts it; the core compares what it is about to write with what is there and refuses only when the changed bytes fall on both sides of a cache block. Four Codex rounds ran at the boundaries and a fifth over the whole milestone, returning 7, 11, 12 and 44 findings; every one is fixed and proved by putting the code back, among them a split that could leave an unmountable volume, a shrink that wrote the allocator's header inside a file's live bytes, a repair that could take a directory's name away, a truncate of an unlinked file that could delete its parent, a create that threw away the mode and the owner it was given, an unmount that cleared the dirty flag of a volume whose device had failed, a loop slot freed by a detach while its attach was still running, and a buffer cache that could key one block twice after a writeback that slept. `execve` gained a workspace per process, because a program read from a mounted volume sleeps and a second exec used to overwrite the first's arguments. `tests/run krffsmount` is eleven boots, `tests/run loopdev` seven, `tests/run krffscheck` replays the protocol against the offline checker, and the host tests replay every prefix of every operation and every lost cache block.

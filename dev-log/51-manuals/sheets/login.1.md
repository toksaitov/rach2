# login(1)

NAME: login - authenticate at the console and begin a session.

Two programs answer to this name and the page covers both, saying which image has which:
* On os-real and the installed root, `/bin/login` is BusyBox's applet from the set-id build (`busybox-suid`), started by init's session child. Usage (BusyBox 1.36.1): `login [-p] [-h HOST] [[-f] USER]`; `-f` do not authenticate, `-h HOST` the host the user came from, `-p` preserve the environment; `$LOGIN_TIMEOUT` seconds (default 60, 0 disables). Configured with shadow passwords and BusyBox's own crypt (SHA); no securetty, no login scripts, no nologin feature (the config sets `FEATURE_SHADOWPASSWDS`, `USE_BB_CRYPT`, `USE_BB_CRYPT_SHA`). It prints `/etc/motd` and runs `/etc/profile` through the login shell. Adapted from BusyBox's documentation, GPL-2.0.
* On os-simple, `/bin/login` is this project's (`utils/login.c`), started by `init-login` as root; it has no set-id bit. It prompts `rach2 login: `, reads the password without echo through the credential library, verifies it against `/etc/shadow`; a wrong name and a wrong password get the same answer, `login: incorrect`, after a pause of 2 seconds; three tries (a bare newline is not a try), then `login: too many tries` and exit, and init starts it again. A name longer than 63 characters is refused as a name that names nothing. It resets the terminal to canonical mode with echo before asking (a session that left `stty -icanon` behind would otherwise break every later login), discards pending input, drops supplementary groups, gid and uid in that order (a failure is fatal: `login: cannot become NAME: ERROR`), enters the account's home or falls back to `/` with `login: DIR: ERROR; using /`, prints `/etc/motd`, closes descriptors above 15, builds the environment from nothing (`PATH=/bin:/usr/bin`, `HOME`, `SHELL`, `USER`, `LOGNAME` from the account record) and execs the account's shell as a login shell (`argv[0]` is `-` and the shell's base name). It does not `setsid` and does not claim the terminal: init's child did both. `login: cannot exec SHELL: ERROR` on failure.
* Both: the console is behind a password; there is no unauthenticated shell (`tests/run login` proves an image without `/bin/login` reaches no shell).
* FILES: /etc/passwd, /etc/shadow, /etc/motd, /etc/profile (BusyBox's login; the project's does not read it).
* EXAMPLE: the console prompt `rach2 login:`, answered with `root` and the password; `tests/run login` and `tests/run account` run it.
* SEE ALSO: su(1), passwd(1), sh(1), passwd(5), shadow(5).

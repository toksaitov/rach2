# Milestone 25: the sealed disk

The plan is in `plan.md`, written before any code and put through four rounds of adversarial review before a line was implemented. This file records what was built, what was proved and where, what was refuted along the way, and what is still waiting for the hardware.

The goal is a laptop whose disk is written once and never removed again. Everything that changes afterwards arrives over SSH: kernels, the boot menu, GRUB itself, and in the worst case the whole disk from a recovery image.

## Phase A: the receiver window update

Milestone 24 measured bulk transfer at 0.9 KB/s on the laptop against 1.1 KB/s in QEMU, and reasoned from how close those two numbers are that the fault lay in the TCP stack rather than in the new driver or the 100 Hz poll. That reasoning was right. Its record then called the result "a property of the TCP stack", and that part was wrong: it is one defect, in one direction, with a one-function fix.

A TCP receiver has to report a window that shrank and a window that grew. This stack only reported the first. The inbound paths in `tcp.c` recompute `rcv_wnd` whenever a segment arrives, so a filling buffer was announced at once. A draining buffer was announced to nobody, because `socket_tcp_recv` and `socket_tcp_try_recv` advance `recv_head` in syscall context and sent nothing. A peer that had filled the window waited for its own persist timer before probing again, and that timer set the transfer rate.

The fix is `tcp_window_update`, called from both receive paths after `recv_head` advances. It takes `net_lock` itself and holds it from the TCB snapshot through the send, because an IRQ-side `tcp_close` detaches the TCB. It sends at most one bare ACK and only from ESTABLISHED, where the closing states have no reader making room. Whether to send is the whole of `rach2/sys/network/tcp/rcvwnd.c`: a pure function, no state and no transmit, that stays quiet until the window has grown by one maximum segment size or half the buffer, whichever is smaller. That is the RFC 1122 4.2.3.3 rule. Announcing sooner would spend a segment per byte read and draw segments just as small in reply.

Measured host to guest over SSH into `/dev/null`, same image, same QEMU invocation, with the call removed and restored:

| Bytes   | Without | With    | Rate without | Rate with |
|---------|---------|---------|--------------|-----------|
| 4096    |         | 0.361 s |              | 11.4 KB/s |
| 65536   | 60.179s | 0.291 s | 1089 B/s     | 225 KB/s  |
| 1048576 |         | 0.408 s |              | 2.57 MB/s |

The 64 KiB figure without the update reproduces milestone 24's measurement to three digits, which is what identifies the two as the same defect rather than two separate slow things.

Proof: `tests/host/rcvwnd_hosttest.c` drives the rule at ring and segment sizes the running kernel never uses, because which half of the rule wins depends on the geometry: at 4 KiB one segment is smaller than half the buffer, at 8 bytes half the buffer is smaller. Four mutations were shown to fail it: never announcing, announcing every byte, using two segments instead of one, and dropping the 16-bit clamp. The measurement above is the other half, and the column without the update is the phase's shown-failing case.

### What the review changed

An independent review of the phase raised five findings. Three were confirmed and fixed in the same commit. The bar was two maximum segment sizes, which is not the RFC 1122 rule; it is one segment or half the buffer, whichever is smaller, and the old value made the receiver quieter than it should be. The returned window was cast to 16 bits without a clamp, so a ring of 65536 would have announced zero, which this function uses to mean stay quiet, and a fully drained buffer would have announced nothing. And the new function was inserted between `tcp_is_connected`'s documentation block and `tcp_is_connected` itself, stranding the block on the wrong function.

### What is deferred, and why

The rule governs the update a reader triggers, not every window the stack advertises. The inbound paths still recompute `rcv_wnd` from free space whenever they owe an ACK, so a segment arriving after a small read can advertise a window below the bar. This predates the milestone, and the update path largely hides it: a reader draining normally announces a full-sized window before a peer has cause to probe. Correcting it means holding the advertised right edge fixed as data is accepted rather than recomputing it from free space, which changes the receive state machine that phase A deliberately does not touch, and it needs a stateful test to be proved rather than asserted. It is the next thing worth chasing in the stack.

The host test covers the rule, not the wiring: deleting both call sites leaves it passing. The wiring is proved by measurement instead, run once with both call sites present and once with them removed, and that measurement is manual. Every figure here is host to guest; the reverse direction was never slow and was not measured again. An automated guard would need a packet recorder around a live connection, which is worth building when something else needs one too.

## Phase B: the tool's new name and shape

`install-kernel` is now `bootctl`, after systemd's tool, which manages a boot partition's kernels and defaults on most Linux machines; a student who learns this one carries the knowledge off the machine. The verbs stay this project's own, because the kernel diagnostics, the Readmes and the harness already speak trial and commit:

    bootctl status         what is installed, committed, and booting next
    bootctl kernel FILE    stage a kernel into the candidate slot
    bootctl commit         make the booted trial the saved default

No alias is shipped. `--commit`, `--where` and a bare kernel path are refused, and there is a test that says so, because a compatibility spelling nobody documents has to be carried forever to be worth anything.

Three boundaries held the change to twenty-one files. The `bootslot` library keeps its name, since it is named for what it manages rather than for the tool that drives it, and two dozen of its error substrings are matched literally by a host test. `dev-log/` keeps its history as written. `make install-test` keeps its name, because the loop it proves still installs a kernel.

`status` is the phase's one new behavior, and it exists because the tool is the only window onto a disk nobody will open: the three files' sector extents, what the environment block holds, whether a trial is armed or consumed, and which slot this boot came from. It says nothing about the GRUB core image, because the device that would answer that does not exist until phase C.

Two changes were made that the phase did not strictly need, both to close hazards the plan predicted.

`prune-stale` now sweeps `build/utils/sbin` as well as the top of `build/utils`. It did not before, on the reasoning that sbin's contents are staged by name rather than by sweep. That reasoning has a hole: a manifest line left on the old name would keep staging the old binary, and `check_setid.py` compares a manifest's declared source against its own table without ever stat-ing the host file, so nothing would report it. The rename left exactly that artifact behind on the first build, which is what closed the gap.

The harness's `awk` was anchored. `tools/install_test.sh` read the candidate's first sector with `/candidate/{print $5}`, which was unambiguous when `--where` printed three lines and is not now that `status` prints six, three of which contain the word. In the shipped line order the loose pattern still happens to work, because the extra matches yield an empty field five and the shell strips the trailing newlines; put a non-extent line first and it yields a leading newline instead, and `dd` gets a malformed seek. The pattern is now anchored on the extent line's own shape, which does not depend on the order.

Proof: `make install-test` green end to end, twice through the loop on one disk, which is what shows the trial, commit, fallback and repair machinery survived the rename; `make selfbuild-test` green, which builds `bootctl` from `guest.mk` on the machine itself and so proves the guest list moved with the host list. `tests/host/bootverb_hosttest.c` covers the parser.

Shown failing: the harness pointed at the old `install-kernel: committed` string fails the run, so that assertion is reaching the tool's output rather than passing vacuously. Two mutations of the parser fail its host test: accepting `--commit` again, and tolerating a surplus operand. The anchored `awk` against a reworded extent line yields nothing rather than a wrong sector.

### What the review changed

Six findings, all confirmed. Two were defects in new code and two were in code the rename only touched in passing.

`status` called every empty environment value a consumed trial. Only `next_entry` carries that meaning; an empty `saved_entry` says nothing about a trial. The annotation is now asked for by the caller rather than assumed by the printer.

A known verb given the wrong number of operands was reported as though it were not a verb at all, so `bootctl kernel` with no path answered "not a command this tool takes: 'kernel'". Exit status was right and the message was not. `bootverb_known` now separates the two, and arity refusals print the usage line alone, as they did before the rename.

`bootslot_commit` matched the armed-trial marker as a bare 21-byte string with no leading newline, so a preserved line ending in `next_entry=candidate` would have been read as this machine's armed trial and blocked a commit that should have succeeded. The writer deliberately preserves lines it does not recognise, so such a line can exist. The pattern is now anchored the way the consumed marker already was, both bounds are checked independently so neither shortens the other's search, and a fixture carrying `x_next_entry=candidate` beside a real consumed marker proves it. This is older than the milestone; the rename found it by putting a second reader on the same block.

The parser test asserted only that `kernel` yielded some operand, not which one. A parser returning `argv[1]` instead of `argv[2]` passed it, and would have made `bootctl kernel FILE` try to open a file called `kernel`. The test now checks the value, and that mutation fails it.

The remaining two were smaller. `utils/Readme.md` still described `--commit`, named the host test by its old filename, and said pruning covered only the top level, which stopped being true in this phase. And the new parser test carried section labels inside its body, which the project's comment rule does not allow; they are gone.

A second round over those fixes found one more and refuted nothing. `bootverb_parse` and `bootverb_known` had grown separate copies of the verb list, so a verb added to one and missed in the other would compile and then report itself as no verb at all. They share one catalog now, and a test walks it: every verb the parser accepts must also be one the diagnostic knows, which fails if the two ever drift.

One finding from that round was refuted with evidence. The new fixture in `tests/host/bootctl_hosttest.c` opens with a comment introducing the case, which the comment rule reads against. That file is a sequence of eighteen such cases, each introduced the same way, and the rule is written for production bodies rather than for a test whose structure is its scenarios. Following the file is right here; restyling it is a separate cleanup, not part of a rename.

## Phase C step 1: the geometry

The sealed disk's layout is now something the build produces rather than something the plan asserts. `make rach2-sealed-disk` writes it, and every number in the plan's map was checked against the built image: 660602880 bytes, 1290240 sectors, 630 MiB; partition 1 at LBA 2048 for 131072 sectors, type 0x0c; partition 2 at 133120 for 1024000; partition 3 at 1157120 for 131072; entry 4 empty; 4096 bytes per cluster in the boot partition.

`tools/mkdisk_grub.sh` grew three knobs, each defaulting to what it always built, so no existing caller changes: the boot partition's size, mformat's sectors per cluster, and a third partition that is absent at zero. The two size knobs are not independent, and the plan says why: `bootslot_open` refuses a volume whose FAT is over 512 sectors or whose cluster count is over 65536, and a 64 MiB partition at one sector per cluster is about 130500 clusters with a 1020-sector FAT. At eight sectors per cluster it is 16348 clusters with a 128-sector FAT.

Three things had to change to make that build correct rather than merely produce a file.

The builder's chain verifier compared cluster counts against sector counts. It was right only because mformat had always chosen one sector per cluster, and it now reads the cluster size out of the volume it just formatted and divides by that. Its report names the figure, so a geometry that silently changed would be visible in the log.

The same verifier read `mshowfat` output with a pattern that matched only a run of clusters, `<a-b>`. A file that fits a single cluster prints as `<a>`, which never happened at 512 bytes and happens to `grub.cfg` immediately at 4096. It now accepts both.

`krffs/mkdisk.sh` refused any partition over 256 MiB, citing the kernel's mount window. That window became 512 MiB in milestone 24 when it moved above the region real firmware uses for MMIO, and this copy of the number was left behind. It is corrected, with the reason recorded so the next person does not have to rediscover it. This path did not block the sealed image, which goes through `mkimage.sh`, but the number was wrong wherever it was read.

The host fixture assumed one sector per cluster in fifteen places, which is why the library's cluster arithmetic had never been exercised: at one sector per cluster the multiply by `cluster_sectors` is the identity, so a version that dropped it entirely would have passed every test in the suite. `mkfatfixture.py` now takes the geometry as a parameter, `--cluster8` builds the same files at 4096 bytes per cluster, and every existing option was checked to produce a byte-identical image to before. A new case opens that volume, checks the library reports eight sectors per cluster and 512 clusters for the 2 MiB slot rather than 4096, and installs and refuses a commit there.

Proof: the sealed image built and its table read back and compared field by field against the plan; the current kernel booting that image, mounting the 500 MiB root and reaching a login with partition 3 ignored; `make install-test` green at the unchanged default geometry, its log naming 512 bytes per cluster.

Shown failing: dropping the `* cluster_sectors` from the library's cluster-to-sector conversion now fails the host test, which it did not before this fixture existed; and computing the volume's cluster count as a sector count fails it too.

### What the review changed

Four findings, all confirmed.

Partition 3 had a type byte and no filesystem. `parted`'s filesystem argument selects the MBR type and creates nothing, so the entry named FAT32 over 64 MiB of zeros, and GRUB could not have read the partition the recovery entry will need. It is now formatted, with the two directories its contents will live in. What goes into it still belongs to phase G.

The image was not reproducible. Two builds of one tree differed in the FAT volume serial, which mformat randomises, and in the creation and access dates mcopy stamps into every directory entry from the clock. Both are pinned, the second through `SOURCE_DATE_EPOCH`, which mtools honours, and two builds now produce one byte-identical image. Two inputs are deliberately left unpinned and are named as inputs rather than treated as noise: the container is the floating `ubuntu:24.04` tag, and the machine's SSH host key and password salt are generated per tree.

The new cluster case did not constrain everything the geometry made relevant. It checked the cluster-to-sector conversion but not the volume's cluster count, and a version computing that count as though a cluster were a sector passed: the wrong value is larger than the volume, so it bounds nothing, and every chain in the fixture ends well below it. The count is now asserted directly, and a second fixture at the same geometry runs a chain past the end so the count is exercised as a bound rather than as a number that is merely reported.

The owning documentation still described a two-partition disk and none of the new knobs.

## Phase C step 2: the level-one devices

Two devices carry level one of the disk model: `/dev/bootpart` over the boot partition, and `/dev/grubcore` over the post-MBR gap where GRUB's core image lives. Every image may write both, including the everyday one, because updating a kernel or a boot loader is ordinary work.

The old order made that impossible for the case it matters most in. `/dev/bootpart` was published at the very end of a successful KRFFS mount, so a machine booting a RAM image and mounting nothing from the disk had no way to touch the boot partition that had stopped it booting, which is precisely what recovery is for. Discovery now runs before the root source is chosen: the disk is probed once, sector 0 is read and judged once, both devices are published, and only then does the machine decide where its root comes from.

Judging entry 0 needed a second question, because the old one cannot be asked without a mounted root. `mbr_bootpart_pick` compares entry 0 against the entry the root was found in; a RAM-root boot has no such entry. `mbr_bootpart_ok` compares it against the whole table instead: FAT-typed, non-empty, inside the disk, starting at or after the end of the post-MBR gap, and sharing no sector with any other non-empty entry. `mbr_bootpart_pick` is now that judgement plus its own two constraints, so the two cannot drift apart. The mount still has one fact discovery cannot know, which entry holds the root, so a disk whose FAT entry 0 turns out to be the root itself loses the device again through `devfs_bootpart_withdraw`.

The gap rule found a real problem in the project's own test fixture. `tools/mkbootfixture.py` had been placing its FAT boot partition at LBA 64, inside the 1 MiB gap that holds the boot loader. That was harmless while nothing else reached those sectors and stopped being harmless the moment `/dev/grubcore` was published over them: a boot partition overlapping the boot loader is a disk this kernel now refuses to offer one for. The fixture moved into the free space after the KRFFS partition.

`/dev/grubcore` is minor 3, mode 0600, over LBA 1 through 2047. Its range is a constant of the layout rather than anything the partition table reports, so a damaged table cannot widen it. Sector 0 is deliberately outside: it carries the partition table, and a disk writes whole sectors, so there is no way to touch the eight bytes of boot code that point at the core image without rewriting the table beside them.

Both devices now share one implementation. `raw_window_read` and `raw_window_write` took over from the bootpart-specific pair, so the second device runs the path the first one proved. The write handler gained one check it did not have: the effective uid, tested at write time rather than trusted from the open. The mode stops a non-root caller at open and nothing else, because the credential check passes uid 0 whatever the mode says, so a process could open the device while privileged, drop privilege, and keep writing through the descriptor. `block_ready` caches the probe, so the three callers that each used to reset and re-identify the controller now agree on one answer.

Proof: `make bootpart-test` grew a third boot that mounts a RAM image with the disk attached and requires both devices anyway, which is the milestone property stated as a test. It drives the gap window end to end: its exact extent, a read at the start, exactly 0 at the end, `-ENOSPC` at and across the end, `-EINVAL` for an unaligned offset and for a partial-sector count, and `-EACCES` for an unprivileged open. `mbr_hosttest` covers the new judgement, and gained a labelled macro because it had been counting failures without naming them.

Shown failing: making discovery return before it publishes anything fails the RAM-root boot; dropping the write-time uid check lets the privilege-drop write through and fails it; widening the gap window past 2047 fails its extent and end-of-window assertions. In `mbr_hosttest`, dropping the gap check and comparing entry 0 against only entry 1 each fail.

### What the review changed

Six findings, all confirmed, and the first was a way to destroy a file system.

`/dev/grubcore` was published before sector 0 had been read at all, and its only condition was that the disk held 2048 sectors. On a disk with an unreadable or unsigned table, or one whose partitions reach into the gap, the window would have handed out write access to sectors a file system owned. That is not hypothetical: this repository's own test fixture put a partition at LBA 64 until this milestone. Nothing is published now until the table has been read and its signature accepted, and `mbr_gap_clear` withholds the window when any non-empty entry reaches into LBA 1 through 2047.

Discovery and the mount each read sector 0 and parsed their own copy, so the record's claim that the table is read once was false, and two reads of one sector can disagree. Discovery keeps the parsed table and the mount uses it.

`block_ready` cached failure as well as success, which quietly disabled the rescue shell. A controller that did not answer at boot could never be asked again, and the rescue shell exists for exactly that machine. It now answers from `block0` when a disk has already been found, so a working controller is still never reset twice, and retries when none has.

The rescue shell's `ahci` command re-initialises the controller, which clears `block0` and the HBA globals. Before this step that was harmless, because no raw window existed on a boot that had not mounted a disk; now one does, and it would have been left addressing a driver with no port. The command takes all three raw windows down first, `/dev/disk0` included, and republishes afterwards on both the success and the failure path.

The last two were documentation: the devfs and block Readmes still described the old contract, and three comments had drifted from the declarations they belonged to, including a claim that the boot partition is 16 MiB.

### A scope decision worth challenging

The plan asks for MBR validation against the geometry compiled into the build: the exact type and bounds of entries 0, 1 and 2. That is not what was built. Pinning those numbers would make every image that is not the sealed disk fail the check, so `install-test`, `test-disk` and the rest would lose `/dev/bootpart` and fail. What is built instead is a judgement that holds for any disk: the gap rule, containment, and non-overlap. The review agreed the gap rule was the part that mattered for safety and raised it to a finding; it did not accept that the exact pinning can wait. Pinning the sealed layout belongs with the sealed kernel build, which step 4 introduces, and it is recorded here rather than done quietly.

## Phase C step 3: offsets wide enough for a real drive

Reflashing a 250 GB disk from recovery means addressing its far end, and nothing in this kernel could. An open file's offset was 32 bits, `_llseek` refused anything above 4 GiB, and `/dev/disk0`'s window was clamped to 8388607 sectors for exactly that reason, with the clamp's comment saying so.

The plan warned this was the step most likely to break something unrelated, because that one offset is shared by every descriptor in the system. It is, so it was left alone. The open-file description gained a second field, `raw_offset`, 64 bits wide, and only the three raw disk windows read or write it; every file, procfs, pipe and terminal path keeps the 32-bit offset it always had. The field lives in the open-file description rather than in the descriptor, so `dup` and `fork` still share one offset the way POSIX requires.

Two size queries replaced two others, and the split matters. `devfs_fd_bootpart_size` and `devfs_fd_disk_size` were doing three jobs between them, and one of those jobs was the boot log, which is not a disk window at all and reads through the ordinary offset. They are now `devfs_fd_raw_size`, returning 64 bits for the three raw windows, and `devfs_fd_log_size`, returning 32 for the log. Both seek syscalls branch on which one answers. `lseek` refuses a result it cannot express rather than truncating it, which is what makes `_llseek` the way to reach the far end rather than an alternative spelling.

With the offset wide, the window clamp had nothing left to protect and rose from 8388607 sectors to 2^32 of them, which is 2 TiB. That ceiling is the window's own choice rather than anything forced on it: the ATA path stops earlier at its 28-bit LBA and AHCI programs a 48-bit one. `/proc/disk` still prints the drive's true size beside the window's, so the two disagree visibly on a disk larger than the ceiling.

Proof: a fourth boot in `make bootpart-test`, against a sparse 260 GB image built by `tools/mkwidefixture.py` and attached over AHCI, because the ATA driver's 28-bit LBA stops at 128 GiB. It seeks to the end and requires the whole drive rather than a truncation; reads known markers at 5 GiB and at 258 GiB, comparing every byte, where the far one needs 38 bits of offset; walks `SEEK_CUR` across the 4 GiB line in both directions and refuses a seek before the start; duplicates a descriptor parked at 258 GiB and reads through the copy, so the wide offset is proved shared through the open-file description rather than the descriptor; and requires the 32-bit `lseek` to report overflow on an end it cannot name. Before this step the window stopped at 4 GiB and none of those sectors existed as far as the machine was concerned. `make test`'s 62 probes, `verify-host`, `bootpart-test`, `diskdiag-test`, `test-disk` and `persist-test` all stayed green, which is the evidence that the blast radius stayed inside the disk windows.

Shown failing: pointing `/dev/disk0`'s read at the old 32-bit offset fails the 5 GiB read; keeping only 33 bits of the resolved offset fails the 258 GiB read while still passing at 5 GiB, which is why the fixture is 260 GB rather than a few; in the host test, the old 4 GiB byte bound fails its case.

### What the review changed

Seven findings, all confirmed.

Both seek paths added the displacement to the base as a signed 64-bit value and then checked the sum for negativity. That check is not a bound: a descriptor parked at the top of the signed range and seeked forward by one has no defined result to test, and negating the most negative displacement is undefined too. One resolver now does the arithmetic unsigned, takes the displacement's magnitude without ever negating it, and bounds both directions before adding rather than after.

A seek whose result is a real offset the 32-bit call simply cannot return was reported as `-EINVAL`, which says the seek was invalid when it was not. It is `-EOVERFLOW` now, and the probe requires that.

Raw identity was being decided by whether the window was currently published, so withdrawing one during a controller re-probe turned an already-open descriptor from a seekable disk window into an unseekable generic device. `devfs_fd_is_raw` answers what the descriptor is, from the operations bound at open, and seek returns `-ENXIO` while the backing is away.

The raised window cap was set to the largest 32-bit LBA and used as a sector count, which left the last addressable sector unreachable. It is a count of 2^32 now.

The wide test proved less than it appeared to. Its 6 GiB fixture would have been satisfied by an implementation keeping 33 bits of offset, and it never exercised `SEEK_CUR` or the shared offset at all. The fixture is 260 GB, larger than the drive being sealed, so its far marker needs 38 bits; it is attached over AHCI because the ATA driver's 28-bit LBA stops at 128 GiB; and the boot now walks `SEEK_CUR` across the 4 GiB line in both directions, refuses a seek before the start, and duplicates a descriptor parked at 258 GiB to prove the wide offset is shared through the open-file description rather than the descriptor.

The last two were prose: the filesystem and block Readmes still described one offset and the old cap, and several comments had drifted from what the code does.

## Phase C step 4: who may write the whole disk

The two levels of disk authority are now real rather than planned. Level one, the boot partition and the boot loader's gap, is writable by every image, because installing a kernel and updating GRUB are ordinary work on a machine nobody will open again. Level two, any sector of the whole device through `/dev/disk0`, is what reflashing a broken root needs and what an everyday boot has no business being able to do: a mistake there destroys the machine rather than one file.

The split is a build switch. An everyday kernel compiles a write that returns `-EPERM` with no path around it; only `-DRACH2_RECOVERY` compiles a body that can write. A token on the kernel command line would have been editable at the GRUB prompt by anyone standing at the machine, which is the same objection this project already recorded when it made the read-only disk policy a compile-time switch, and it applies with more force here.

`RACH2_DISK_READONLY` could not be reused for this, and the two look interchangeable enough that the difference belongs in the record. That switch is enforced below devfs, in the drivers' command allowlist, so a kernel carrying it cannot write the boot partition either, and both builds need to. The new one decides exactly one thing: whether devfs exposes a writable whole-disk node. `rach2/sys/block/recovery.c` carries a banner naming which build an artifact is, `tools/check_recovery.py` reads it back in both directions, and `make rach2-recovery` checks both kernels so a mislabelled one cannot reach a test.

The write path also stopped being one sector at a time. Every raw transfer, in either direction and through any of the three windows, now passes through one 32 KiB buffer in `.bss` sixty-four sectors at a time, which is a single command for both drivers: ATA chunks at 256 and AHCI refuses above 8192. The buffer is in `.bss` because the linker places that below the 32 MiB identity-mapped limit, so its virtual address is the physical one the AHCI PRDT needs, and one buffer serves every window because a syscall cannot be preempted. The size is what makes a whole-disk reflash finishable: at one sector per call a 500 MiB write was about a million driver calls, and since both drivers flush the drive's cache after every write command, a million cache flushes with it. At sixty-four it is sixteen thousand.

Proof: `make authority-test` boots both kernels against one sparse image, differing only in the kernel. The everyday build must refuse the write with `-EPERM` and the sector must still read as zero afterwards, so the refusal is shown to have written nothing rather than merely returned an error. The recovery build must write a sector past 2 GiB, read it back byte for byte, and take a 200-sector write whole.

Batching needed instrumenting to be provable at all, and the first attempt was not. A 200-sector write returns the same answer whether it took four driver calls or two hundred; only the time differs, and a test that watched the return value proved nothing. `/proc/disk` now reports the batch size and a live count of driver calls, the probe reads the count either side of the write, and requires the difference to be four.

Shown failing: compiling the recovery write body into the everyday kernel fails the ordinary boot, which is what proves the refusal is the build switch and not something else; setting the batch to one sector fails the driver-call assertion while still passing every assertion about the write's result, which is exactly the gap the instrumentation closed; shrinking the chunk in the bounded windows' read loop alone fails the gap-window case; and making AHCI split each call into one-sector commands fails the command and flush counts while leaving every count above the driver untouched.

### What the review changed

Eleven findings, all confirmed, and the first made the authority a claim about one function rather than about the kernel.

The rescue shell's `disk write` command wrote the last sector by calling `block0->write` directly, around devfs and around the `-EPERM` everything else has to pass. An ordinary kernel booted with `rach2.rescue` could therefore write outside both bounded windows, which is precisely what this step exists to prevent. It is compiled out of an ordinary build now, and the refusal says why.

Batching widened a real ambiguity, and the first attempt to close it did not work. The block interface answers with zero or an errno and cannot say how much of a request it completed, while the ATA driver writes sector by sector inside one command and can fail after several have gone; a failed 64-sector call can therefore alter up to 63 sectors while reporting none. Re-issuing the failed batch one sector at a time looked like an answer and is not: the retry can fail earlier than the original did, so it measures the retry rather than what the first attempt changed. The contract is written down instead, in three parts because only the first is a guarantee: the sectors a short return counts are written, the batch beginning at the returned offset is the one that failed and its state is unknown, and everything past that batch was never attempted. That batch is 64 sectors, or fewer when it was the last the request had room for. A caller continues by writing again from the returned offset, which covers the unknown batch as well as the rest. Narrowing it would take a block interface that can report a partial command, which this one cannot, and that is a change to every driver and every caller rather than to this step.

The instrumentation I had added proved less than it claimed. It counted calls into the block interface, which says how well devfs batched and nothing about what the driver did with each call: a driver splitting one 64-sector request into 64 commands would look identical from above while costing exactly the million cache flushes batching exists to avoid. Commands and cache flushes are now counted immediately before the register write that issues one, so a refused or abandoned command is not counted, `/proc/disk` reports both, and the test requires exactly eight commands and four flushes for a 200-sector write rather than a bound they could pass by counting nothing.

Three more were about what the test reached. It exercised only the whole-disk window, only over AHCI, and only its write, so a batching regression in either bounded window or in the read loops would have passed. All four batched loops are now driven over more sectors than one batch holds: the gap window read and written, and the whole-disk window read as well as written. The remaining gap is named rather than closed: the ATA backend is not exercised by this target, and no test provokes a mid-transfer failure, because doing so needs a fault injector the block layer does not have.

The rest were smaller. A first-chunk fault from the whole-disk writer returned `-EIO` where the bounded writer correctly returned `-EFAULT`. The call counter was 32 bits, which wraps after about nine passes over a 250 GB disk, and the probe parsed it into a signed 32-bit value that would overflow sooner. The DMA buffer had no declared alignment despite the AHCI PRDT taking its address directly. `make rach2-recovery` checked an artifact it did not depend on, so a clean tree could reach a missing file. And several comments still described `/dev/disk0` as read-only on every kernel.

One claim was overstated rather than wrong, and is corrected in place: `check_recovery.py` catches a kernel built without the switch, which is the mistake worth catching early, but the banner and the handler are separate conditionals, so it is not proof against a tampered artifact. `make authority-test` boots both kernels and is the proof of what they do.

## Phase D: the boot menu that can be rewritten

GRUB reads two files on this disk now. `/boot/grub/grub.cfg` is the stub, written once when the disk is built and never again. It defines every entry the machine needs and then sources `/boot/boot.cfg`, the rewritable half `bootctl config` overwrites in place, preallocated to 8192 bytes so no write extends a file or moves a cluster chain.

The order is the safety property and the reason the plan pinned it before any code was written. `source` merges the second file's entries onto the tail of the first's, and `set fallback` names an index rather than an id, so the stub's entries have to hold the low indices whatever a staged menu adds. With them first, a menu that is missing, truncated mid-write, or simply wrong costs nothing but the entries it meant to add.

The entry list is fixed because the numbers are a contract: candidate 0, fallback 1, candidate-static 2, fallback-static 3, debug 4, recovery 5. The two static-address entries carry a token set that is empty until the networking phase gives this machine an address; they exist now to hold their numbers. Entry 5 names a kernel and a RAM image on partition 3 that the recovery phase has not built, and is marked in its title as not yet bootable for the same reason.

One question the plan left open had to be answered here, and the first answer was wrong. The plan's proof line asks for a machine that boots an entry only the staged file defines, and the obvious way to arrange that is to let the staged file name its own default in a variable the stub reads last. That was built, and it does not hold. A slot overwritten in place is not written atomically, so a power cut can leave a syntactically valid prefix of a new menu above the tail of an old one, and a file in that state could set the variable and point the machine at an entry that might not even fail in a way the fallback catches. Worse, `load_env` imports every grubenv key as a variable, so a value written into the environment block could set it too, which is the opposite of the property the design claimed.

The mechanism is gone. What replaced it is a smaller and true statement, arrived at after a second review round rejected the first replacement too. `source` runs GRUB script, so a staged file can set the environment keys the stub reads, or load a kernel itself, before control returns. There is no way to make it a declarations-only menu. Whoever can write that file can direct the boot, and that is the authority level one already grants, since `bootctl kernel` replaces the kernel that boots next.

What the stub does guarantee is narrower and is the property that matters here: a menu which is damaged rather than written leaves a bootable machine. Every entry the machine needs is defined before the staged file is read, so one that is missing, truncated mid-write or unparseable costs only the entries it meant to add.

`bootctl` grew four verbs. `config` stages a menu, refusing a file larger than the slot before anything is written. `env` reads or sets one of the two grubenv keys, through an allowlist rather than as a general editor. `trial` arms one boot of an entry the stub defines, and `cancel` clears it. The library grew `boot.cfg` as a fourth resolved file and a writer that rewrites every sector of the slot whether the new text reaches it or not, so a shorter menu leaves nothing of a longer one behind, and reads each sector back before writing the next.

Proof: `make menu-test`, four boots of one disk. The first stages a two-entry menu through `bootctl config`, round-trips a grubenv key through `bootctl env` and `bootctl cancel`, and corrupts the candidate kernel so the next boot must take the fallback. The second proves both staged entries reached the menu and that the fallback number still named the stub's own entry rather than a staged one. The third truncates the staged file mid-entry from the host and the machine still boots through the stub, with GRUB's parse error in the log. The fourth reads the slot's extent back and it has not moved.

Shown failing: moving the stub's entries after the `source` line makes `set fallback=1` select `stagedtwo` instead of the stub's own fallback, and GRUB says so by name in the log. A menu one byte over the slot is refused. A writer that touched only the sectors the new text reaches leaves a longer menu's tail behind, which the host test catches by writing a full slot and then a short one over it.

### What the review changed

Ten findings, all confirmed.

Two were the same defect seen from opposite sides, and together they removed a feature rather than fixing one: a torn slot write could publish a staged default, and `load_env` imports grubenv keys as variables, so the environment block could set that variable too. The claim that it could not was false. The mechanism is gone.

A second round then rejected the replacement claim as well, and was right to. Removing the variable did not make the staged file inert: `source` runs GRUB script, so it can set the environment keys the stub reads, or load a kernel outright, before control returns. There is no way to restrict it to declarations. What is written down now is the true and smaller statement, above.

The two static-address entries carried only the static token set, which is empty until the networking phase, so on the sealed disk they would have booted with no `rach2.disk=ahci` and failed to find their root. They carry the machine's tokens as well now.

`bootctl trial` accepted two ids the stub never consumed, which would have left a value armed forever, blocking every later commit while selecting nothing. The stub consumes them now. It also accepted `recovery`, promising a boot of a kernel no phase has built yet; that one is out of the allowlist until it exists.

The menu writer computed its sector count by truncating division, so a slot whose size was not a whole number of sectors left its last bytes stale, and a slot of no size returned success having written nothing. Both are now refused when the volume is opened, where a disk built wrong is a better place to fail than a write that half-succeeds.

Requiring the menu slot made every older boot partition unmanageable: `status`, `kernel` and `commit` need no menu and would have stopped working on any disk built before this phase. The slot is optional now and only `config` requires it.

The rule that a staged menu must end in a newline was neither necessary nor sufficient. It rejects a valid GRUB file ending at its final brace, and accepts a transfer cut after a whole entry. It is gone, and the tool says plainly that it checks the size and nothing else.

Three test gaps and a set of stale comments made up the rest, including a `--menu-short` fixture option that existed and was never used by any case.

A third round found the worst of them, and it was one I had introduced. `bootctl cancel` wrote `next_entry=` with an empty value, and an empty `next_entry` is not "no trial": it is the marker GRUB's scripted consumption leaves after a trial has actually booted, and `bootslot_commit` requires it. So installing a kernel, cancelling the trial, and committing would have made a kernel the default that never ran once. Cancelling removes the key now, `env` refuses to write an empty value at all and says which command to use instead, and a host case installs, cancels, and requires the commit to be refused.

The second round found four more. `bootctl env` validated only the key, so `env next_entry recovery` armed an entry `trial` refuses, and a newline in a value would have written a second grubenv assignment nobody asked for; values are now checked for control characters and against the same entry list `trial` uses. `config` read into a fixed buffer without probing for one more byte, so on a large enough slot an oversized menu would have been truncated and reported as staged. The harness asserted only the fallback index, so swapping entries 2 and 3 passed; it now reads every title off the drawn menu and requires the whole order. And the claim that a zero-size slot is refused was not true and not needed: an empty file with no cluster is treated as absent, which is the right answer anyway.

## Phase E: replacing the boot loader from the running machine

Sector 0 is never written after a disk is built. It holds the partition table, a disk writes whole sectors, and the boot code at byte 0x5c naming where the core image starts sits beside that table. So the gap is laid out to make LBA 1 the selector instead: GRUB's `diskboot` sector carries a blocklist at offset 0x1f4, an 8-byte LBA and a count at 0x1fc, and the gap holds two tails, A at LBA 2 and B at LBA 1025, 1023 sectors each. Replacing the core image means writing the tail not in use and then rewriting one sector.

`utils/grubslot.c` is that layout as arithmetic. `grubslot_active` reads the blocklist and answers which tail is in use, refusing a layout an install cannot work on: more than one record, or a count that does not fit one slot. It judges the layout, not who built the disk; `grubslot_other` names the other; `grubslot_patch` writes a replacement image's own blocklist, refusing anything under 2 sectors or over 1024. `grubslot_install` is the sequence: read the entry sector, patch the image for the inactive tail, write all 1023 sectors of it, read all 1023 back and compare, and only then write LBA 1. It takes the sector reader and writer as a callback, so the same code runs against `/dev/grubcore` on the machine and against a model disk in a host test. `bootctl grub FILE` is a file read, a size check, and that call.

The whole tail is written, not only the sectors the image reaches, so a shorter image leaves nothing of a longer predecessor behind. Every failure before the last write leaves the old entry sector and the old tail selected and the machine boots as it did. The one risk is the last write: a torn write to LBA 1 makes GRUB unreachable, and recovery cannot help, because GRUB is what loads recovery. The plan states this and does not claim otherwise.

Proof: `make grub-test`, three boots of one disk. `tools/mkgrubcore.sh` builds two core images differing only in a configuration embedded by `grub-mkimage -c`, which prints `GRUBCORE=A` or `GRUBCORE=B`. The first boot installs B and reboots, the second must print B and installs A, the third must print A. The marker is printed by a configuration embedded in the image itself, so it names the image that is running. Reading the blocklist back would prove only bytes at rest, and a tool that wrote the pointer and nothing else would pass that. The two installs must also report two different tails.

Shown failing: a readback that never disagrees passes the dropped write, and the host test fails on three cases. A `grubslot_other` that answers with the tail in use fails eight. Removing the second-open refusal from the kernel makes `make grub-test` fail. The harness itself was seen failing twice before it passed, once because the embedded configuration echoed before any terminal existed and once because the count of markers was wrong.

### What the review changed

The embedded configuration sets the serial terminal up itself. It runs before the configuration on the partition does, so an `echo` there reaches the screen and nothing a harness reading the serial line can see.

The two core images are staged through `optional-file` lines in `os-real.manifest`, the way Doom's wad is, rather than through a manifest generated into the build tree. `check-setid` requires every manifest it allows to be a source file, which is the right rule: a generated manifest is a way to get a new set-id set past the checker.

The claim that two swaps in a row prove the tails alternate was false. Overwriting one tail twice still boots whatever was written there last, so the markers alone would pass a tool that never used the second slot. The harness now requires the two installs to name two different tails.

The install sequence was inline in `bootctl` over a file descriptor, where the case that matters most could not be tested: a disk that reports a write as done and drops it. It moved into `grubslot_install` behind a callback, and the host test drives it over a model gap that does exactly that. The requirement is that the readback catches it, the entry sector still names the old tail, and the old image is still under it.

The second round found six more, all confirmed.

Nothing established that the file being installed was a GRUB core image. The size was checked and the contents were not, so a truncated transfer or the wrong file of at least 513 bytes was padded, written, read back successfully, and activated, and the next boot ran invalid code with no way to repair it remotely. A candidate is now judged before any write: it must carry GRUB's blocklist segment 0x0820 at offset 0x1fe, and the tail length it declares for itself at 0x1fc must match its length in sectors.

`grubslot_active` read the blocklist's start LBA and ignored its count, so a core image whose tail ran out of tail A and into tail B was treated as living in A, and installing into "inactive" B would have overwritten the running image. The count must now be 1 through 1023. `grub_embed.py`, which builds the first core image, allowed anything that fit before the first partition, which is 2047 sectors; it now refuses more than 1024, where a disk built wrong is cheap to rebuild.

The install had no exclusive access. Two of them could each read the same active tail, each verify their own write, and leave the entry sector naming one image with the other one's length. `/dev/grubcore` now admits one opener at a time, refusing a second open with `EBUSY`. A lock file would have been simpler and worse: a stale one on a sealed machine across the room is unrecoverable, while the kernel flag clears when the last descriptor closes, which process exit does.

The two marked core images were staged through `optional-file` lines in `os-real.manifest`, and the claim that every other build would find them absent was false: `make grub-test` leaves them in the build tree, so any later production image would have carried them. They are in `krffs/manifests/grub-test.manifest` now, which is os-real plus those two lines, and the target diffs the two files before it builds so they cannot drift apart.

The Readme described the embedded pair of `configfile` calls as something the build already does. It does not; `mkdisk_grub.sh` passes no `-c` today. The paragraph is gone until the recovery phase adds it.

And the prose personified the code: a core that speaks and says which one it is. Rewritten to say what happens, which is that a configuration inside the image prints a marker.

A third round found one more, and it was a limit in the second round's own fix rather than a defect in it. The declared-length check compares sectors, and a core image records no byte length anywhere: the current one is 157703 bytes, so a transfer cut in its last 6 bytes still rounds to 309 sectors and passes. Losing a whole sector is refused. The review proposed replacing the file format with a packaged image carrying a digest, which would close it completely and would also stop the machine installing a core image built by grub-mkimage, which is the point of the verb. So the limit stands and is now written down where someone about to install one will read it, in `utils/grubslot.h` and in the `tools/Readme.md` GRUB section, together with what to do instead: compare `sha256sum` at both ends of the transfer. The shape is checked; that the image can boot this disk is not, and the harness is what proves a real one.

The same round found two more, both confirmed. The test that claimed to pin the truncation boundary did not: it installed a whole synthetic image of 309 sectors and never removed a byte, because the rounding and the zero padding lived in `bootctl` where no host test could reach them. They are `grubslot_prepare` now, and the test drives cuts of zero through seven bytes off a 157703-byte image and asserts both halves of the boundary, that six bytes are invisible and seven are refused. And `utils/Readme.md`, which owns the tool, still described only the three verbs of milestone 23 and stated that the tool takes no lock over the device. It now carries the menu verbs and a separate contract for `bootctl grub`: what it accepts, the write order, the one exposure at LBA 1, what the candidate check does and does not establish, and the single-opener rule that makes the claim about locks false for this verb alone.

The review also proposed decoding the image's LZMA payload and requiring the output to be the length the image declares at 0x20c, which would catch the six bytes. That is deferred, with the reason recorded rather than left implied. It means carrying an LZMA decoder in the installer and one validator per compression mode grub-mkimage can emit, to check an image the operator can check with `sha256sum` before sending it; and `grub-install`, which does the same job on every other machine, validates the core image it writes not at all. The exposure that remains is a transfer damaged in its final sector by an operator who skipped the checksum.

The fourth round found one defect and one overstatement. `grubslot_prepare` rounded a byte count up to sectors before judging it, so a length near the end of the 32-bit range wrapped to zero sectors, passed every bound, and wrote past the buffer. The current caller cannot produce such a length, but the function is public and its contract takes one. It judges the count first now, and the host test covers the wrap, the exact capacity, one byte past it, and a whole image exactly.

The overstatement was in the guard on the disk itself. The code and the prose said an entry sector that names neither tail is a disk this project did not build; a conventional GRUB installation also puts its core image at LBA 2 with a length under 1023, so it passes. The review called that a path to destroying an unrelated disk, and it is not: `/dev/grubcore` is published only where no partition overlaps LBA 1 through 2047, which `mbr_gap_clear` decides, so a disk whose first partition starts at LBA 63 has no window at all. What installing over a conventional GRUB disk does is write the unused half of the gap and select it, leaving the old image where it is, which is what the operator asked for. So the remedy proposed, a versioned layout marker written into the gap, is not taken: it would be a new on-disk format that no existing disk carries, to prevent an outcome that is not harmful. The claim is now what the code establishes, in `utils/grubslot.h`, in the refusal the tool prints, and in both Readmes.

The fifth round pressed the same point further and half of it held. GRUB's boot code reads a list of blocklist records, twelve bytes each, growing downward from 0x1f4 and ending at the first record whose count is zero, so a loader spread over several extents names sectors this code never looked at. Every image this project builds has one record, and so does every contiguous embedding grub-mkimage writes; a second one is now refused, with a host case for it. The other half, that a disk with no partition in the gap may still hold something in it that no partition table mentions, is true and is not fixed. Fixing it means an ownership marker written into the gap, which is a new on-disk format that no disk carries and which the plan, reviewed four times before any code was written, deliberately does not have. What is done instead is to say plainly, in the tool's header, in `utils/Readme.md` and in `tools/Readme.md`, that `bootctl grub` claims LBA 2 through 2047 on whatever disk it runs on. On a disk this project built, that region is the tool's. The machine this milestone seals boots a disk this project built.

The sixth round found the one-record rule applied to the running image and not to the file being installed, and my own test fixture was hiding it: `make_core` filled the terminator with 0x5c5c, so every successful install in that file was using a candidate GRUB would have read through a second extent. The fixture writes a zero terminator now, `grubslot_patch` refuses a candidate that carries a second record, and a case asserts it with nothing written. The order of the candidate's checks also changed: the segment is judged before the record list, so a file that is not a core image at all is reported as that rather than as a bad extent list. The same round found the phase summary above still claiming `grubslot_active` refuses a disk this project did not build, which the fifth round had already established it does not; that sentence now says what the code does.

## Phase F: networking, one interface ABI and two clients

Being built in six steps, in this order, each one committed on its own: the packet socket and `recvmsg`, which is the half a DHCP client cannot work without; the interface ioctls, the rule that changing the address clears ARP and aborts the TCBs that recorded the old one, and the `rach2.ip=none` token; connected UDP and real answers for `SO_BROADCAST`, `SO_BINDTODEVICE`, `SO_REUSEADDR` and `PACKET_AUXDATA`; the busybox patch, configuration and stamp prerequisite that make `udhcpc` build; the in-house client, `/etc/network/interfaces` and the written `/etc/resolv.conf`; then the harnesses and the Readmes.

Step 1 is the packet socket. `ip_rx` drops every datagram not addressed to this machine, and every reply a DHCP client waits for is one of those, so `ethernet_rx` now offers each IPv4 frame's payload to the sockets bound above it before `ip_rx` judges the destination. `AF_PACKET` with `SOCK_DGRAM` means the link header is nobody's business in either direction: a receive delivers the IP packet, a send takes one and this layer prepends the header from the MAC in the `sockaddr_ll`. Opening one needs effective uid 0. `recvmsg` arrived with it, as socketcall 17, because the client reads through `recvmsg` rather than `read` so it can look for `PACKET_AUXDATA`; that option is refused with `ENOPROTOOPT`, which is the true answer, and the client then verifies the UDP checksum itself.

The ABI was read out of the vendored busybox rather than remembered: `networking/udhcp/packet.c` and `dhcpc.c` name every call and every structure, and the `sockaddr_ll` offsets in the first draft were wrong until the probe caught them.

Proof: `make packet-test`, which does a DHCP exchange for real. The probe builds a discover with a correct IP header checksum, sends it to the broadcast MAC, and waits for SLIRP's offer. Both halves are proved at once, because the frame must have left well formed or nothing would answer, and the answer is addressed to 255.255.255.255, which `ip_rx` throws away. It waits with `poll` the way the client waits, requires `select` to agree, and checks the refusals: a stream packet socket, an EtherType other than IPv4, `PACKET_AUXDATA`, an interface that does not exist, a destination that is not a MAC address, and an ordinary user. Shown failing three ways: removing the `ethernet_rx` hook, removing the root check, and making `poll` blind to the queue.

### What the review changed

Five findings in the first round, all confirmed. `packet_send` called `ethernet_tx` without `net_lock`, so a receive interrupt could transmit through the same one assembly buffer mid-fill. The one datagram slot the rest of the datagram path has was wrong here, because everything the machine receives arrives at this socket, not only what is addressed to it: one interrupt drains several frames, and an offer followed by other people's traffic would be overwritten before the client ran. Each bound socket has a queue of eight now, dropping the newest when full and saying so once. `do_recvmsg` consumed the datagram before validating the caller's iovecs, so a bad pointer destroyed a message and then reported the fault. The AF_INET sender it reported was 8 bytes where a `sockaddr_in` is 16. And the probe leaned on an ICMP reply that `ip_rx` would have accepted anyway, which proved neither the send nor the case the socket exists for.

The second round found four more, and the first of them would have cost a session at the laptop: `poll` and `select` reported nothing for a packet socket, because readiness read `recv_full` and the queue never sets it, and `udhcpc` polls its raw socket before it reads. The probe now waits that way instead of sleeping. `recvfrom` invented an AF_INET sender of 0.0.0.0 port 0 for a packet socket and validated its writeback only after taking the datagram; `recv` refused every datagram socket, so one of the four ways of reading a socket disagreed with the other three about whether a queued datagram existed; and a zero-capacity `msg_name` did not report the true length.

One thing found on the way is worth writing down and is not this step's to fix. `select` here reads and writes the whole 1024-bit `fd_set` its type is, whatever `nfds` says, while Linux touches only the bytes covering `nfds`. Nothing in this tree is hurt, because musl's `fd_set` is that size and every caller uses it, but a program written to Linux's actual behaviour and passing a smaller object would have its memory overwritten. This probe was such a program for an hour.

The third round found two more in `recvfrom`, one of them older than this step. A blocking receive interrupted by a signal returned through the address writeback with `src_ip` and `src_port` never set, so the caller was handed whatever those stack words held, and a fault on that copy would have reported `EFAULT` for a receive that was really `EINTR`. And the pre-check validated the caller's whole declared capacity where the writeback touches sixteen bytes at most and none at all for a packet socket, so a valid call could be refused; worse, the capacity was read again after the datagram was taken, which a caller whose length word overlaps its own receive buffer could change underneath. The address a receive will write is now settled before the datagram is taken, from a capacity read once, and a receive that failed writes nothing. The probe checks both: an empty socket must report empty and leave the arguments untouched, and a packet socket's successful receive must report a length of zero and write no address.

The fourth round found the same capacity defect once more, in `recvmsg`, which had been fixed in `recvfrom` and not beside it: an AF_PACKET receive with a large unmapped `msg_name` was refused although nothing would have been written there. Both now settle the address length before receiving and check only what they will write. It also found that the probe read a child killed by a signal as a child that was refused, since both leave a zero exit byte; the signal is checked first now.

Step 2 is the interface. A DHCP client learns the address after the machine is running, so `rach2/sys/network/netif.c` carries Linux's `SIOCxIF*` ioctls on a socket descriptor: the name by index, the index, the hardware address, the MTU, and the get and set pairs for address, netmask, broadcast address and flags, plus `SIOCADDRT` and `SIOCDELRT` for the default route. Reading is anyone's and setting is root's. The descriptor they are asked through is a raw one, `AF_INET/SOCK_RAW/IPPROTO_RAW`, because that is what busybox opens; it carries ioctls and refuses every other operation, since this stack has no raw IP path to offer. `rach2.ip=none` is the third answer on the boot line beside an address and no option at all, and the sealed image is what will carry it.

Changing the address is not a number. `netconf_set_address` empties the ARP cache, aborts every TCP connection that recorded the old address, drops a gateway that is no longer on the subnet, and holds the whole transition under `net_lock`. A listener is not a connection and follows the address instead of dying with it. `ip_rx` accepts the two broadcasts a DHCP reply arrives as, and delivers a broadcast to UDP alone.

Proof: `make netif-test`, two boots. The first reads everything the interface reports, checks every refusal, changes the address with a connection open across it, requires that connection to end with `ENETRESET` through a write, a blocking read, a nonblocking one and `SO_ERROR`, requires the listener to accept a new connection to the new address, takes the interface down and proves it deaf as well as mute, and puts everything back. The second boots with `rach2.ip=none` and configures the machine from nothing in the order `ifconfig` does it. Shown failing: removing the notice to the connections, refusing an address with no mask, making `poll` blind, and removing the receive guard.

### What the review changed

Thirteen rounds, twenty-five findings, every one confirmed. Four are worth naming because each would have cost a session at the laptop.

`rach2.ip=none` had no legal way out of itself. The address ioctl passed the current mask, which was zero, and the mask ioctl passed the current address, which was zero, so each refused the other and a machine booted with no address could never be given one. `ifconfig` sets the two in separate calls, so an address with no mask takes the classful one its first byte implies until the real one arrives. An address that is a host only under a wider mask waits out of force instead, so a client killed between the two calls leaves nothing answering for a network address, and reapplying the pair a machine already holds changes nothing at all, because a DHCP client runs the same `ifconfig` on every renewal and a machine that tore its connections down each time would drop every session on it at the lease interval.

`AF_INET/SOCK_RAW/IPPROTO_RAW` was refused, and that is the first thing busybox's client opens: it would have exited before reaching any of this.

An address change killed listeners. dropbear's would have stopped accepting on the first lease, without dropbear knowing.

`SIOCADDRT` with no gateway cleared the one in force, so `route add default dev eth0` would have removed the route a machine across the room is reached through. `SIOCDELRT` succeeded whether or not there was anything to remove, and busybox's lease script removes old routes in a loop that ends when the removal fails, so the machine would have spun there forever instead of taking its lease.

The rest: no `net_lock` across the transition; half-open passive blocks leaked on a change; an unconfigured machine owning 0.0.0.0; broadcast admission letting an echo request through, which is how one packet becomes many replies at whatever address the sender claimed; `SIOCGIFNAME` implemented backwards; `IFF_UP` gating transmit but not reception, and gating netconsole, which is the log of a machine whose network was just misconfigured; a route ignoring the device it names; the implicit subnet route reporting that it had been removed; and a reset reported as a permission error, because a closed connection answered a bare -1.

One of the review's suggestions became a tool. Proving that a machine that is down does not receive needs a frame from outside, and the harness could not send one; `tools/harness.py` now has a `udp=PORT:TEXT` step and the test forwards a host port into the guest, which the DHCP steps will want as well.

Step 3 is what a DHCP client needs of an ordinary datagram socket. `connect` records a peer, so `write` and `send` go there and nothing else is heard from; `AF_UNSPEC` lets go of it. `SO_BROADCAST` is required before a datagram may reach every machine on the wire, and `ip_tx` sends such a datagram to the broadcast hardware address rather than routing it; only UDP is ever broadcast. `SO_BINDTODEVICE` takes the whole `struct ifreq` busybox passes and judges the name with the same code the ioctls use. `SO_REUSEADDR` lets two sockets share a UDP port, which is how a renewal is sent while the listener stays bound, and the answer goes to the socket connected to the sender.

Proof: `make dgram-test`. The broadcast is proved from the wire, not from a return value: the run captures every frame and `tools/bcast_check.py` requires one addressed to `ff:ff:ff:ff:ff:ff`, which fails when `ip_tx`'s broadcast arm is removed. The sender filter is proved with a datagram the harness injects from outside, a source address loopback cannot produce.

### What the review changed

Seven rounds. The first found eight, of which one blocked DHCP outright: `SO_BINDTODEVICE` refused any argument longer than a name, and busybox passes a whole `struct ifreq`, so both of the client's sockets would have failed before sending anything. `ip_tx` broadcast every protocol, not only the one that has any business being broadcast. `send` with no address was refused on a connected socket, `getpeername` did not know one, the datagram limit was 1500 where a UDP payload can be 1472, the peer tuple was published unlocked beside the receive interrupt, `AF_UNSPEC` demanded a whole address, `getsockopt` had no answer for `SO_BINDTODEVICE` and reported a length it had not written, and the probe proved neither the broadcast nor the filter it claimed.

The second round found three, one of them a hole I had just opened: an `AF_UNSPEC` connect on a stream socket fell through with six bytes of this function's own stack as the destination, and would have sent them on the wire. The third found that holding the network lock across the ephemeral bind let any user stop the machine's interrupts by filling the eight-slot table and connecting one more socket. The fifth found that `SO_REUSEADDR` was still only a flag, so the renewal the client sends could never be sent, and implementing it properly meant unbinding by socket and choosing between two sockets on a port.

The sixth round's finding was one I had already fixed once: a `git checkout` to undo an unrelated truncation reverted it, and I did not notice until the review said so. It also found that sharing a port needed a credential rule, which uncovered a hole older than this step: nothing stopped an ordinary user binding a port below 1024, so anyone could have taken the port a DHCP client or an SSH server answers on. That rule is in now, and the seventh round found what it broke: the self-build test runs the in-house `httpd` as an ordinary user on port 80. `httpd` takes a port argument now and the test uses 8080, which is the fix at the cause rather than a weakened rule.

Step 4 is the client. busybox's `udhcpc` builds against the ported musl now, through the first patch this vendored tree has ever carried: `networking/udhcp/dhcpc.c` includes `<linux/filter.h>`, which is needed only by a BPF block upstream has kept inside `#if 0` for years, and `<linux/if_packet.h>`, which becomes musl's `<netpacket/packet.h>` plus the auxiliary-data structure and status bit that header does not carry. Copying the Linux headers in was tried and does not work; they pull in four more. `BUSYBOX_STAMP` depends on the patches and on their directory, so an edit, an addition or a removal all invalidate it.

`ifconfig` is on and `CONFIG_FEATURE_IFUPDOWN_IP` is off, because that switch selects the `ip` backend for `ifup` and every `ip` applet is off. `/etc/network/interfaces` says `dhcp`, the four hook directories `ifup` runs through `run-parts` exist, and `/usr/share/udhcpc/default.script` turns a lease into an address, a route and a resolver with the commands an administrator would use.

Three things had to be built before any of that worked. `execve` honours a script's first line, because a DHCP client execs its lease script directly and before this only a shell could run one. `/proc/net/dev` exists, because without it `ifconfig eth0` answers that no such interface exists, which is a poor answer on a machine nobody can walk up to. And init empties `/var/run` at boot, because `ifup` records there which interfaces it has configured and this file system has nowhere to put runtime state that a reboot clears.

Init also brings the network up on the metal profile, after the console login and before the SSH server, so a network that fails to come up cannot take the local way in with it. It does that only where the boot line said userland owns the address, which is `rach2.ip=none`, and that is what the sealed disk now carries instead of a fixed 192.168.0.105.

Proof: `make dhcp-test`, five parts. The RAM image takes a lease and must end with the address, the netmask, the broadcast, the resolver and a default route, the route proved from the wire because a packet for an address on no subnet of this machine's must leave addressed to the gateway's hardware address. The same twice on a disk, where `/var/run` survives the reboot between the boots. The metal image unattended, with nothing typed: the proof there is that packets were sent FROM the leased address after a knock on its SSH port, since the lease line is printed before the script that applies it runs. A boot told its address on the command line, on a network with a server ready to hand out a different one, which must keep the address it was given. And a network with no server at all, where the client must go to the background and keep asking while the console login still works.

### What the review changed

Two reviewers ran on this step: Codex, five rounds, and a four-lens fan-out whose findings were each put to an agent asked to refute it. Fourteen findings, all confirmed.

The two that would have cost a machine: the client's options were `-R -n`, so it gave up after three unanswered discovers and a sealed laptop whose switch had not started forwarding would have stayed unreachable until somebody walked to it; and init ran `ifup -a` on every metal boot, so a machine told its address on the command line would have had that address taken off by `deconfig` and, on a network with no server, never given one back.

The tests were wrong in three ways worth naming. The unattended run asserted only the lease line, which busybox prints before it runs the script, so dropping the script from the image would have passed. The no-server run asserted a login prompt that had already been printed before the network was even attempted. And a knock on a forwarded port is not an assertion at all: QEMU's user network accepts the host side of a connection before it knows whether the guest is there, so what the guest did has to be read from a capture of the wire.

The rest: the lease script invented a /24 for a lease that carried no netmask, left the last network's resolver in place when a lease named none, ignored every write when building the new one, and said nothing when a lease named no router; `/var/run`'s sweep could have been walked out of by a damaged stored name carrying a slash; a shebang line that filled the buffer was cut rather than refused, so a truncated interpreter name could name a different program that exists; the interpreter path was not canonicalized, so `#!/bin/../dev/x` walked around the check that keeps exec out of the synthetic mounts; `/proc/net/dev` printed its counters signed; the style checker read no file ending in `.script`; the busybox Readme still called the tree unmodified and its bump steps never mentioned the patch; and two doc blocks ended up describing the wrong function.

One thing found here is worth carrying: a success token that is not split in the middle is matched by the harness against the command's own echo, and a mutation test then reports a pass. That happened once in this step, on the static-address case, and the mutation only failed once the token was written `STATIC""KEPT`.

Step 5 is the same job in this project's own code, for the image that carries none of busybox. `utils/dhcpc.c` builds every byte it sends: an IP header, a UDP header and a BOOTP message with both checksums, over the packet socket step 1 built, because a server answers a machine with no address by broadcasting and a machine with no address cannot receive through the IP layer at all. It runs the discover, request and acknowledge exchange, applies the lease through the ioctls step 2 built, replaces `/etc/resolv.conf`, and then holds the lease: it renews to the granting server at T1, rebinds by broadcast at T2, and takes the address off when the lease finally runs out. `utils/netup.c` is `ifup -a` for the same image, reading the same `/etc/network/interfaces`, and running the client for a `dhcp` stanza or applying a `static` one itself. There is no lease script and no shell to run one, so the client applies the lease itself.

Both programs are split, and the half with no system call in it is a library the host gate drives. `dhcpmsg.c` is the framing, the checksums, the option parsing and the lease arithmetic; `netcfg.c` is the reading of the interfaces file; `ipcheck.c` is the judgement both programs make, since a stanza an administrator wrote and a lease a server sent raise the same question and two copies of the rule would be two answers waiting to differ. That is the shape `bootslot.c` has under `bootctl`, and it is here for the same reason: what these two halves read comes from the wire and from a file an administrator edits, and neither will produce a malformed case on request.

`tests/host/dhcpmsg_hosttest.c` writes the messages a server will not send: a truncated option, an option that claims more than the message holds, a code with no length after it, no end marker, a wrong transaction id, another machine's hardware address, no magic cookie, a fragment, every header length and port wrong in turn, and both checksums broken. Every message goes through the library on a heap copy of its exact length. That copy is what makes the bounds falsifiable: read into the client's own 576-byte buffer, an option that runs past the message is read harmlessly and the parse then fails for a different reason, so the check that refuses it can be deleted and every test still passes. On an exact copy the same deletion is an AddressSanitizer report. Nine of the eleven mutations tried are caught by name; the two length guards at the top of the frame check mask each other, and removing both is what the three-byte frame catches. `tests/host/netcfg_hosttest.c` does the same for the file, and each refusal is matched by its own text so a mutation cannot pass by tripping a different rule.

The seam test found a defect before any review saw the code: an interface name longer than the field was stored cut and looked for whole, so a stanza naming one could never be found. Cutting both sides would have made two long names that begin alike the same interface, which is worse. No interface can have such a name, so the file is wrong and now says so.

One client holds an interface at a time. The claim is `/var/run/dhcpc.INTERFACE.pid`, created with `O_CREAT|O_EXCL` and written inside that descriptor, so it is never a file with nothing in it; an empty one is read as busy, a claim naming a process that is gone is read once more and then removed and taken, and the parent that backgrounds a client publishes the child's pid before it exits. Every client reads the claim again before it configures the interface and before each renewal it applies. Another live client named there and it leaves the interface alone; a claim that has simply gone it writes back, because it is still the client the address is configured for and walking away would leave an address with nobody to take it off. That is a check and not a lock: this kernel grants every `fcntl` lock unconditionally, so there is no lock here to take, and one administrator at a time is the contract, as it is for `bootctl`. There is no configure-once mode for the same reason the check exists: a client that applied a lease and exited would leave an address on the interface and nothing to remove it when the lease ended, and the machine would go on answering for an address the server had since given away. A client that is killed must take the address with it, because the kernel's configuration outlives the process and an address nobody is renewing is one the server hands to somebody else while this machine still answers for it. TERM, INT and HUP set a flag, the poll returns, and the client leaves through the same door every failure leaves through. `dhcpc -i eth0 -k` is the other end of that: it signals the client that holds the interface and waits for the claim to go, which is what a machine being moved to a fixed address needs first. Without it os-simple had no way to stop a client at all, since that image has no `kill`.

Deferred, and named here because nothing in the suite covers it: rebinding. QEMU's server answers the unicast renewal every time, so the client never reaches T2 in any test, and the rebinding path is proved by reading and by the timers the host test drives, not by a boot. What can be arranged on the machine is the renewal, and that is what the twenty-second lease does.

Proof: `make dhcp-test` grew two boots, both on a `/16`. The first is os-simple taking a lease with its own tools, and the `/16` is what makes the netmask provable: the classful mask for a 10.x address is /8, so a client that took the address and not the mask would reach 10.200.0.1 by ARPing for it, and the capture requires that packet to have gone to the gateway. It then stops the client and requires the gateway to stop answering, a second `netup -a` to take a lease again, and the gateway to answer once more: the first says the address really came off, the second says the claim was released. The second boot caps the lease at twenty seconds so the renewal falls due inside the run, and requires the client to have asked for an address exactly once, since a client that let every lease lapse and discovered again would print the same lease line without ever renewing. Shown failing: with the unconfigure removed from the signal path the gateway still answers after the client is stopped, and the run fails there.

### What the review changed

Fifteen rounds, forty-eight findings, every one confirmed. The client was rewritten around three of them.

The lease timers were wrong in three ways, each of which is a machine that stops renewing. The first draft started the lease from the moment the acknowledgement arrived, so a slow exchange spent part of the lease before the clock started. It ignored the server's own T1 and T2, then took a pair that was out of order or past the lease, then took each of the two defaults only when neither was named. It turned a lease of zero seconds into a week and an acknowledgement with no lease time at all into a week, and a renewal acknowledged without one moved the boundaries as if it had said something. Now the lease runs from the request, the server's pair is taken when it is in order and inside the lease, an acknowledgement that names no length this client can hold is refused, and a renewal that names none leaves the boundaries where they were and waits as if nothing had answered, because a server answering wrongly as fast as it can would otherwise be asked again the instant its answer arrived.

Seven eighths was `(seconds / 8) * 7`, which is zero for every lease under eight seconds, and half of a one-second lease is zero too: the client would have rebound the instant it was configured and gone on doing it. `DHCP_MIN_LEASE` is the answer to the whole class: ten seconds, below which there is no room for two boundaries and an expiry, and a lease shorter than that is refused rather than kept up with. Seven eighths is `(seconds * 7) / 8`.

The claim was a file that said who held the interface and did not make it so. Two clients started at once over a claim left by a machine that lost power could both find it dead, both remove it and both take it. The claim is created with `O_CREAT|O_EXCL` and the pid written inside that descriptor, it is read once more immediately before a dead one is removed, and every client confirms the claim still names it before configuring the interface and before applying a renewal. That last check is what turns a lost race into one client leaving quietly rather than two clients renewing one address. It is a check and not a lock because there is no lock here to take: this kernel grants every `fcntl` lock unconditionally, which is right for the single-user machine it was written for and useless as an interlock. One administrator at a time is the contract, as it is for `bootctl`.

Two of the fixes were themselves defective, which is why the rounds kept going. Reading the claim before configuring told a claim that had gone from a claim another client held, and both answers were the same: leave. So an administrator who removed the file by hand would have made the client exit with the address still on the interface and nothing left to take it off, which is the failure the check was written to prevent. A claim that has gone is now written back. And the stop path removed a stale claim without the re-read the claiming path had grown, so a client that took the claim in that instant would have had its file removed and become unfindable.

The handoff into the background had three holes of its own. A parent that could not publish its child's pid exited with a failure while the child ran on, unfindable and unstoppable; it now stops the child and drops the claim. A stop signal arriving between the fork and the publication set the flag in the parent, which then published and exited while the child, which inherited a flag of false, kept the lease; the parent now passes the signal on, and `dhcpc -k` follows a claim that changes hands while it waits. And a parent killed outright in that same interval left a child holding a lease under a claim naming a dead process: `dhcpc -k` would have read that claim, taken the address off, removed it and reported that it had stopped a client that was still running, and that client would have gone on to renew or to take off whatever address was set after it. There is a pipe across the fork now, and the child does not begin holding the lease until the parent has published it; an end of file there is that death, and the child answers it by giving the address up and going. Three rounds went on that one branch, and each found the same class of mistake in the fix before it: the child cleaned up without asking who held the claim, so it could take a successor's address off; then it asked, but the parent had already removed the claim on its way out, so the child found nothing to match and left the address configured; then it kept the claim but removed it whether or not the address had actually come off. The rule the file follows now is one rule everywhere: the address goes first, and the claim goes only if the address went with it, because the claim is the only record of which address to remove.

Three more were the difference between a machine that recovers and one that does not. The signal handlers were installed after the claim was made, so a signal in that window took the default action and left a claim with nobody behind it. `netup` read a claim that was present but held nothing as free, which is exactly what a claim being made at that moment looks like. And `netup` recorded a failed snapshot as zero, so a rollback could have set the address to 0.0.0.0; it now refuses before it mutates anything if it cannot read what is there. It also stopped removing the old default route before adding the new one, since setting a gateway replaces what is there and removing it first meant a failure left the machine with neither.

Three of the client's answers to failure were wrong in the same direction: they ended the client. An acknowledgement carrying a netmask that is not a run of ones, or a router on another network, was applied a field at a time until the kernel refused one, which changed the address and then left the machine half configured and the client exited; a renewal that could not be applied did the same; so did a failure to write the resolver. A machine across the room that did that is a machine nobody can reach. Every lease is now judged whole before any of it is applied, through `ipcheck.c`, which is the same judgement `netup` makes of a static stanza, and an unusable lease is treated as no answer at all: the client goes on asking. A failure to apply anything unconfigures and goes back to asking, from the background if that is what it was told to do.

The one-shot mode went rather than being fixed. `dhcpc -1` applied a lease and exited, leaving an address on the interface with no process and no timer to take it off when the lease ran out: the machine would have gone on answering for an address the server had since given to somebody else, which is the one failure this whole client exists to avoid. Nothing used it.

The claim learned to carry the address as well as the pid, because a client killed outright runs nothing on its way out: it leaves an address with no lease behind it, and whoever takes the claim over is the only one who could know to remove it. So the claim records what was configured, before it is configured, and a takeover or a `dhcpc -k` of a client that is gone takes that address off, but only if the interface still holds exactly it, since an administrator may have set another one since. The address goes first and the claim second, because the claim is the only record of which address to take off. The claim itself is replaced by writing a new one beside it and renaming over it: this kernel has no `ftruncate`, so a rewrite in place would have to open with `O_TRUNC`, and a client killed in that instant would leave a claim holding nothing, which every reader is required to treat as busy. Nothing would then start, and nothing would know which address to remove.

The rest: rebinding that sent one request and then waited out the last eighth of the lease in silence; SIGPIPE ignored only after the client backgrounded, so a lease line written to a terminal that had closed killed a client holding an address; a shorter message than RFC 1542's 300 octets, which real relays drop; every socket left open across the backgrounding; no rollback in `netup` at all; a `-l` that could raise the week cap rather than only lower it; a static stanza with no netmask that could take the live address off and report success; and the interfaces file read in one pass, so a stanza written before its `auto` line was ignored.

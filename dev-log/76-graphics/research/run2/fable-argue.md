1. Step 8's ext2 errors
* I now agree with the report against my own review: the evidence fits the documented state of an unclean stop on a write-back mount, and no fault is shown. The inode bitmap differences are exactly the nine inodes (`step8/out/e2fsck-after-stop.log:3-19,28`), so the block bitmap differences at `:25` are their blocks; nothing else was wrong, and `-fy` repaired it in one pass (`:35-40`).
* A root mounted without `sync` or `dirsync` writes back (`rach2/sys/fs/ext2.Readme.md:7,52`), and the Readme says a stop then leaves whatever had reached the disk for `e2fsck` (`:68`), with a file removed while open kept until its last holder goes (`:103`). Boot 2 ended in a `pkill` from a new session with no `sync` and no `shutdown: root: unmounted` (`report.md:135`; boot 3 has both, `step8/out/rach2-boot3.serial.log:810`), and the stop script's `sync; poweroff` path was not what ended it (`step8/scripts/wsl-rach2-stop.sh:5-8`). "Deleted inode has zero dtime" is what any ext2 gives for an unlinked-but-open file at a stop.
* Not yet known, and the only open part: whether Rach2 left anything beyond those orphans, since `e2fsck -fy` ran before boot 3 and Rach2's own check never saw the volume (`rach2-boot3.serial.log:87-88` has `mounted`, no `ext2: check:` line).

## The five questions

### Mode setting

Yes, on every display driver, through atomic KMS (Linux's display interface for a check-then-commit of a whole display state), with the legacy calls built on top of it as Linux's helpers do. Weston, the wlroots compositors and Chromium's own display code all prefer atomic; a driver written legacy-only would be written twice.

* QEMU: std-vga gets a small bochs driver with real modes; virtio-gpu takes its modes from the host's EDID, which QEMU rewrites with the window's size as the preferred mode when the window is resized, raising a display event that the driver handles as a hotplug.
* Any PC: fbdrm keeps the one mode the firmware set, as Linux's simpledrm does; GRUB's configuration (`gfxpayload`) can ask the firmware for another mode at boot.
* Haswell: the driver first reads the state the firmware left and keeps it, so the first boot does not flicker; a full mode set covers eDP (panel power sequencing, the AUX channel, link training), HDMI and DisplayPort on the DDI ports, the PLLs, the panel fitter (a lower mode scaled to the panel), hotplug, the VBT blocks for the panel and backlight, and watermarks. Haswell's low-power chipset has no analog VGA output (Linux, `intel_display.c:7767`): a VGA port on this laptop, if fitted, is a DisplayPort-to-VGA converter and is driven as DisplayPort.
* The console becomes a DRM client and follows the mode; `video=` on the command line sets it.
* Weston takes its mode from its configuration; a game that asks for a lower resolution is scaled by Xwayland and Wine, as on Linux desktops today.
* Mode setting is also what makes the driver VM's death survivable: the dead VM's driver leaves the display in a state Rach2 did not set, and only a full mode set lights the panel again under Rach2, as Linux's i915 does after the GPU's function-level reset (measured). An ordinary hang is cheaper on Haswell: Linux resets the hung engine alone and falls back to the whole GPU, and its reset does not clear the display (`has_reset_engine` and `gpu_reset_clobbers_display: no` on the Lenovo; `i915_pci.c:319`, `:388`).
* Tests: IGT's KMS tests on every driver, built from source (Debian's `intel-gpu-tools` 2.0 ships IGT's tools, such as the register and VBT dumpers, but not its tests, which the second run built from Debian's 2.0 source); a software test display with CRCs, as Linux's vkms, so IGT's CRC tests run in QEMU; the pipe CRC on Haswell against Linux's CRC of the same pattern; IGT's EDID injection for HDMI modes without a monitor. IGT reads CRCs and forces connectors and EDIDs through debugfs, which Rach2 does not have yet (76-18).

### KVM-like virtualization

Yes. The right form is Linux's own KVM interface (`/dev/kvm` and its ioctls), so that Debian's QEMU 10.0 runs unchanged. QEMU then brings what the test bed needs and what we should not write: vfio-pci with Intel's IGD support, the emulated intel-iommu for testing assignment without the Lenovo, virtio-gpu with virgl and Venus, ivshmem shared memory, and Linux guests.

* Two backends: Intel VMX with EPT on the Lenovo; AMD SVM with nested paging, debugged on the testing PC and the Mac where the GPU work is not waiting. Rach2's `os-simple` reaches its login prompt in 2.14 s under KVM on the testing PC and in 0.51 s under TCG, whose PCI searches cost no exits (measured), so 81-2 can meet real SVM as soon as 81-1 boots a guest. The testing PC has nested SVM in WSL (`svm` on all 32 threads, kvm_amd with `nested=1`), so Rach2 there can run under KVM with real SVM; but a guest's exits then pass through three hypervisors, and a minimal Linux boot in such a third-level guest took 20 to 25 times longer under KVM than under TCG (60 to 71 s against 2.9 s), and Rach2 reached its login prompt there in 180 s against 6.1 s, 138 s of it in PCI scans of every bus at two port exits per empty slot (`tonight/qemu-wsl.md`). Both profiles stay: TCG for the exit-heavy boots and Rach2's own suites, nested KVM as the check against hardware, and each longer workload placed by its measured throughput and exit counts; the Mac has TCG only. On the Lenovo, Linux's KVM boots the same Linux to its first process in 1.1 s, against 8.8 s under TCG: the reference for 81.
* What QEMU requires, read in its source: 18 named capabilities, the local APIC in the kernel with the rest of the interrupt controllers in QEMU (the split irqchip; QEMU 8.0 removed the fully userspace one), irqfd, ioeventfd, MSI routing, and a decoder for guest accesses to device memory.
* Device assignment: an Intel VT-d driver (DMA and interrupt remapping, the reserved regions, one of which is the GPU's stolen memory) and VFIO (type1 containers, vfio-pci, the GPU's OpRegion region that QEMU's IGD support reads). Linux on the same Lenovo assigned the GPU this way on QEMU's q35 machine with no video ROM and no legacy IGD mode, which cannot run there for want of a ROM (82).
* Tests: Linux's KVM selftests and kvm-unit-tests, unchanged; QEMU's emulated intel-iommu for VT-d and VFIO.
* Left out: a VMM of our own, shadow paging, nesting inside Rach2's guests, migration, GVT-g-style sharing of one GPU between VMs (Intel never supported Haswell there).

### What to proxify

The bed carries the levels that exist and measures them on one machine; the levels are a ladder, not a choice made in advance.

1. The device: the driver VM owns the whole GPU through VFIO, display included. This is the base, not proxying.
2. The API level: OpenGL through virgl (Mesa's Gallium commands) and Vulkan through Venus. The client needs no driver for the GPU, so any GPU Linux supports serves Rach2; the cost is serialization and, for virgl, a second shader translation. virgl is what works on Haswell's server side today and is the first rung; virgl's future is uncertain (the press reports Mesa 26.1's announcement calling it unmaintained; the release notes and driver pages do not say so), so the bed pins it as the baseline and treats Venus, and OpenGL on Venus through Zink, as the long-run API path. On the Lenovo, Venus runs over hasvk, which offers what Venus asks of its server on Linux (Vulkan 1.1 and external memory) but is not on Venus's tested list. Through Debian's QEMU under KVM a guest's Venus reports hasvk at Vulkan 1.2.305, vkcube presents through QEMU's displays, and a blob of hasvk's memory mapped into the guest is coherent both ways at 96 to 105 percent of the host's CPU bandwidth (measured). What stays to be proven is the reversed mapping, Rach2's programs using the VM's buffers (83-5).
3. GPU commands: DRM native context. The client runs the GPU's own Mesa driver (Crocus here), and only its kernel calls and buffers cross; close to native speed, but the client needs the right driver. Mesa 26.1 added it to Crocus, behind a build option Debian leaves off; virglrenderer 1.3's server takes Crocus's relocations and lets the VM's kernel apply them, and refuses no GPU generation, but is marked experimental. Two costs are known from the code: Mesa and virglrenderer must be built with their options, and the client never learns the GPU addresses, so the VM's kernel relocates every batch. hasvk has no native context, so Vulkan on Haswell crosses only by Venus. The rung enters the bed after a check proves Haswell.
4. Windows (cross-domain): display only, not rendering.

Raw batches forwarded without native context are not worth a rung: on Haswell a batch needs relocations patched and the command parser run by whoever owns the GPU, so the host would keep the very code the VM is meant to hold.

### Existing protocols or our own

Existing ones for everything that crosses: the virtio-gpu command set and its context types (virgl, Venus, native context), virglrenderer as the server, Mesa's drivers as the clients, Linux's buffer and fence semantics. They are maintained, tested by ChromeOS, Android's emulator and QEMU's users, and cost nothing to keep current.

The one new piece is the transport, because the usual direction is reversed: here the host uses a GPU its guest owns. Nothing standard does that with QEMU unchanged: QEMU's separate GPU backend (`vhost-user-gpu`) speaks only virgl, with no blob resources, context init or Venus, and rust-vmm's released one is no further; virtio-msg, the coming standard for virtio over shared memory, is still a proposal. So the transport keeps the virtio-gpu protocol and its standard virtqueues, and only moves them into one shared region with doorbells:

* On Rach2: the same virtio-gpu driver that runs in QEMU, with a second transport beside virtio-pci. The render node, its interface and Mesa's drivers are unchanged.
* Between: QEMU's ivshmem device maps one region of Rach2 memory (a memfd) into the VM; every queue and buffer the device touches lives there: Rach2's driver allocates its commands and every resource's backing from the region itself, so nothing is bounced as in Linux's restricted DMA pools, and the device sees offsets into the region as DMA addresses; a full region is ENOMEM, never a silent fallback. A small Rach2 daemon is both QEMU's ivshmem server (its documented protocol, about 200 lines; Debian ships none) and the host's peer: it gives QEMU the memory and the doorbell eventfds and hands the same to Rach2's driver. Under Rach2's KVM, the VM's doorbell write becomes an ioeventfd and Rach2's notification an irqfd, so neither leaves the kernel. Polling first, doorbells second.
* In the VM: a small virtio-gpu device backend around libvirglrenderer (about 2,500 lines of ordinary C on Linux; crosvm's backend, and rust-vmm's in its unreleased source, now carry blob, context init and Venus, but adopting one would add a vhost-user frontend inside the VM and a Rust build and leave the mapping problem where it is, so they are code to borrow from), modelled on QEMU's own virglrenderer glue, which handles virgl, Venus and native context alike; it takes its interrupts through the small kernel module described below, since Debian's kernel is built without vfio's no-IOMMU mode, or through vfio-pci over QEMU's emulated intel-iommu, and shows Rach2's frames on the VM's display as the DRM master, by copy first and then by scanning out the frame's buffer.
* Rules: every offset and length checked on both sides, resource ids tagged with a generation, quotas, every pending fence failed when the VM dies, and a fuzzer. Venus's host-visible memory and native context's mappable buffers are the VM's memory, scattered over its pages: a small kernel module in the VM pins each mappable buffer (through its dma-buf, or the memfd behind Venus's shared memory) and reports its list of VM-physical pages; Rach2's KVM resolves them through its memory slots into frames that Rach2 maps into the program as one object it can revoke, with the cache mode of the GPU's own mapping, torn down when the VM dies. Linux's own path through QEMU pays most when a buffer is freed and another mapped (83-5), so the transport keeps mappings and reuses them. The other way, allocating mappable buffers inside the shared region and importing them into the GPU, is measured beside it. That mapping is the bed's first research problem; copying is the baseline it is measured against.

### Why the industry drops 32-bit on 64-bit, and what Rach2 does

* Who drops what: macOS removed 32-bit programs (2019); Arm's newer cores and some Android phones are 64-bit only; Windows 11 has no 32-bit edition but keeps WoW64; Intel's X86S proposal would have kept 32-bit programs under a 64-bit kernel and was dropped; Linux keeps its compat layer and added a boot switch to turn it off (`ia32_emulation=`, 6.7); Debian 13 builds no i386 kernel or installer and keeps i386 libraries for multiarch; Ubuntu (2019) and Fedora (2025) tried to drop i386 packages and backed down over Steam and games.
* Why: a second ABI to build, test and secure, for fewer users each year; the compat entry has had security bugs of its own.
* Why it still matters: Valve's 64-bit Steam client (beta, October 2026) still needs 32-bit libraries; old native Linux games and many Windows games are 32-bit; Wine's new WoW64 runs 32-bit Windows code in 64-bit processes, but the CPU still runs 32-bit code, which the kernel must support.
* For Rach2, all three reviews agree: keep the full compat ABI (your decision), on by default; add Linux's boot switch, a build switch that leaves it out, and a pure 64-bit image with no i386 libraries. Rach2's own i686 suites then also run on the 64-bit kernel, which tests it hard for free.

## Decisions

### Decisions the second run raised

A. Which host carries Venus for the agents' work in QEMU on the testing PC (77-4, 77-6, 77-7, 77-8), and, if the module, how it loads. lavapipe there exports buffers only through udmabuf, and WSL's kernel is built without it, so with no change to the host Venus stops at Vulkan 1.2 with no swapchain.
   1. udmabuf as a module of WSL's own kernel. Built out of the tree from Microsoft's source for the running 6.18.54.1 with a three-hunk patch (`run2/step6/udmabuf-module.diff`), it loads into the stock kernel, so no kernel of your own is named in `.wslconfig` and nothing changes on Windows. Measured: a guest under KVM gets Venus at Vulkan 1.3.269 with a swapchain, external memory and synchronization2; vkcube's frames reach the screen with QEMU's GL on llvmpipe (through Mesa's d3d12 driver on the RTX they are black, so virgl on the RTX and Venus on screen are two profiles); a blob maps in 7.2 to 31.0 ms and unmaps in 2.4 to 3.6 ms, coherent; WineD3D on Vulkan and Wine's vkd3d draw on it for 64-bit programs. Costs: it must be loaded after each start of WSL (the second part, below); the kernel is tainted; an oops in it panics the whole WSL machine for every account (`panic_on_oops` and `panic=-1`; none in 15 minutes of use); and each WSL kernel update needs it rebuilt from that release's source, about 4 minutes on 32 threads, with the compiler check and the installed modules' CRCs checked before it loads. 77's Done stands as written. The plan's recommendation.
   2. The fallback, if a WSL kernel will not take the module: a Debian VM on the testing PC as the Venus host, since Debian's kernel has udmabuf. Measured on 2026-11-04: in its guest under TCG, Venus gives Vulkan 1.3 with a swapchain, vkcube runs and DXVK 2.6 runs a Direct3D 11 program. In the VM `/dev/udmabuf` and `/dev/kvm` are root:kvm, so the account that runs QEMU joins `kvm`. Rach2 then runs a level lower and under TCG, and the VM's QEMU cannot show Venus's frames, so 77's Done has Venus off-screen with readback, and presenting leaves it.
   3. Neither: Venus stops at 1.2, off-screen. DXVK and vkd3d-proton still run on the guest's lavapipe (76-21); 77's Done then has no Venus presenting and no Direct3D on Venus.
   With option 1, its load: root loads the module after each start of WSL, from the profile's setup, which changes nothing that persists (the plan's recommendation); or you allow it to load at boot, which saves the step and puts the module, and the panic an oops in it brings, into every WSL session from the start.

## The milestones

All eight can be opened together; the board's order is the order of dependency. A task is worked on its own milestone's branch, so a milestone whose tasks need another open milestone's code is stacked on it: its branch is cut from that milestone's branch and merges that branch in as it moves, a merge and never a rebase or force push, so every push stays a fast-forward. A task blocked by another milestone's task starts once the blocker is closed and its milestone branch merged in. A wait on a Linux reference or a trace imports no code: it is marked "(evidence)", needs no branch merge and adds no stacking. A stacked milestone releases after the milestones it stacks on, or with them when they end together (Order). Each task carries its tests, manual pages and Readme changes. Sizes are new kernel lines, as scope, and are estimates.

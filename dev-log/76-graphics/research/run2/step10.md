## A blob mapped into the guest (risk 5, 80-5's Linux baseline)

* `blobtest.c` (built in the guest with gcc 14 against `libvulkan-dev`, `blobtest-build.txt`; the same binary copied to the host): it picks the device named like "HD Graphics 4400", takes the first host-visible coherent memory type, times allocate, map with a first touch, and unmap with free for sizes from 4 KiB to 64 MiB; maps 32 blobs of 64 KiB with none freed between; then with two 64 MiB buffers it times CPU writes, reads and `memcpy` through the mapping (best of five), GPU `vkCmdCopyBuffer` and `vkCmdFillBuffer` between them, and checks every word after each GPU write. Under Venus each host-visible allocation that is mapped is a blob resource that QEMU maps into the 4 GiB host-memory window. Run in the guest on Venus over hasvk, and on the host on hasvk directly (`VK_DRIVER_FILES` naming hasvk's ICD), as `gfx`, the guest idle otherwise.

| Measure (64 MiB buffers unless named) | Guest, Venus on hasvk (`blob-guest-2.txt`) | Host, hasvk (`blob-host-2.txt`) |
|---|---|---|
| Memory type used | 1: device-local, host-visible, coherent, cached | the same |
| The guest's mapping (`/proc/self/maps`) | `rw-s ... /dev/dri/renderD128` | `rw-s ... anon_inode:i915.gem` |
| CPU write through the mapping | 5,781 MB/s (5,847 in `blob-guest-1.txt`) | 6,027 MB/s (6,098) |
| CPU read | 9,328 MB/s (8,848) | 8,864 MB/s (9,155) |
| CPU `memcpy` mapping to mapping | 8,209 MB/s (8,249) | 8,566 MB/s (8,595) |
| GPU copy, first / best of 8 | 37.7 ms / 8.83 ms (7,601 MB/s) | 38.6 ms / 8.67 ms (7,741 MB/s) |
| GPU fill | 8.82 ms | 8.64 ms |
| Words wrong after GPU copy, GPU fill, and four rounds of CPU write, GPU copy, CPU read | 0 of 16,777,216 each time | 0 each time |
| Allocate, 4 KiB to 64 MiB | 0.04 to 0.06 ms | 0.02 to 0.51 ms |
| Map and first touch, in a loop that frees each blob before the next | 52.5 to 58.1 ms at every size | 0.02 ms (4 KiB) to 12.6 ms (64 MiB) |
| Unmap and free, same loop | 8.9 to 10.9 ms | 0.01 to 0.53 ms |
| 32 maps of 64 KiB, none freed between | mean 5.05 ms; first 51.9 ms; the other 31 about 3.5 ms each | mean 0.036 ms |
| 32 unmaps and frees, then one map | 15.9 ms, then 116.8 ms | 0.41 ms, then 0.96 ms |

* So the blob path works on hasvk under KVM: the mapping is coherent both ways with no flush (the memory type says coherent and cached, and 0 words of 16.8 million were stale or wrong in six checks), and the CPU moves data through it at 96 to 105 percent of the host's rate, the GPU at 98 percent. A read through the guest's mapping is as fast as on the host, which an uncached or write-combined mapping would not be; the guest's page attributes were not read.
* The cost is in mapping and above all in unmapping. `strace -T` in the guest (`blob-strace.txt`, a 16 MiB run) puts the 50 ms in the guest's `mmap()` of the blob, the call in which the guest kernel sends `RESOURCE_MAP_BLOB` and waits; `DRM_IOCTL_VIRTGPU_RESOURCE_CREATE_BLOB` takes 0.42 ms on average. `strace` of QEMU's threads and of the render server on the host (`qtrace.sh`, `qtrace/`) shows QEMU's `KVM_SET_USER_MEMORY_REGION` adding each blob's slot in 0.07 to 0.16 ms and removing one in about 5 ms, and the next add coming some 60 ms after a removal. QEMU 10.0.13's source (`qemu-src/`, Debian's orig tarball checked by apt against the signed `.dsc`, SHA-256 `6a0888e8...dde59ae`; no Debian patch touches these files) says why: `virtio_gpu_virgl_unmap_resource_blob` (`hw/display/virtio-gpu-virgl.c:165-213`) removes the region, sets `renderer_blocked` and suspends the command, and command processing (`hw/display/virtio-gpu.c:1099`, `:1130`) stays blocked until the region's finalizer runs from QEMU's RCU thread; that thread (`util/rcu.c:269-270`) sleeps 10 ms at a time, up to five times, while fewer than `RCU_CALL_MIN_SIZE` (30) callbacks are queued. So every unmap holds the whole virtio-gpu queue for about 50 ms, and the first command behind it, here the next map, pays it. A map with no unmap ahead of it costs about 3.5 ms against the host's 0.03 ms.
* For Rach2: risk 5's remainder is cleared for Linux. A blob of hasvk's host-visible memory maps into a Linux guest through Debian's QEMU and virglrenderer under KVM, coherent, at near native bandwidth. 80-5's Linux baseline is these numbers: about 3.5 ms per map, 50 ms of stalled queue per unmap, and 96 to 105 percent of native CPU bandwidth once mapped. A transport that unmaps without such a stall, or keeps mappings and reuses them, beats QEMU here by a wide margin; one that pays 50 ms per release loses to copying for any short-lived buffer.

## The guest stopped by KVM: "kvm run failed Bad address"

* 04:35, during the Direct3D probes below: with WineD3D on OpenGL in the guest (`PROTON_USE_WINED3D=1`, so Wine draws with the guest's virgl driver, whose GL runs on the host's Crocus), QEMU printed `error: kvm run failed Bad address` and a register dump, and stopped the VM: QMP `query-status` gave `{"status": "internal-error", "running": false}`; the guest stopped answering SSH (`qemu-sdl1.log`). The guest was in user mode (CPL 3) in a `rep movsb` (code bytes `<f3> a4`) copying 0x4000 bytes, with RDI 0x...a8000 and RCX 0x3000 left: its first 4 KiB page had been written and the second could not be. The host's kernel logged nothing and the host's GPU was untouched; QEMU was quit by QMP and started again.
* It repeats: the same probe alone, after a fresh start, stopped the VM the same way, at the same instruction with RCX 0x3000 (04:39, `proton-b.txt`, `qemu-sdl2-efault.log`). QEMU then held 169 mappings of `anon_inode:i915.gem` (`efault-2.txt`), i915's CPU mappings of GEM objects, which i915 makes `VM_PFNMAP | VM_IO` (`i915_gem_mman.c:1013`).
* The cause, from the running kernel's source (Debian's `linux_6.12.115.orig.tar.xz`, checked by apt against the signed `.dsc`, SHA-256 `eaccd6c9...bd2172d`; no Debian patch touches i915, and the KVM ones are s390's; the files read are in `linux-src/`):
  * i915 puts its objects in a private tmpfs mounted `huge=within_size` on graphics before version 11 only when VT-d is active (`i915_gemfs.c`, `i915_gemfs_init`: `if (GRAPHICS_VER(i915) < 11 && !i915_vtd_active(i915)) return;`). Debian's kernel turns DMA translation on by default, and this boot's log says "VT-d active for gfx access" and "Using Transparent Hugepages" (`lenovo-setup/facts/dmesg-i915.txt`). `/proc/meminfo` showed 28,672 kB of `ShmemHugePages` while `shmem_enabled` was `never`, so they are i915's.
  * KVM maps a `VM_PFNMAP` page into a guest only if it can take a reference on it: `hva_to_pfn_remapped` calls `kvm_try_get_pfn`, which is `get_page_unless_zero`, and returns `-EFAULT` when that fails (`virt/kvm/kvm_main.c:2886-2959`); its comment names pages "allocated without refcounting", which the tail pages of a huge page are (their own count is zero). `-EFAULT` from `KVM_RUN` is QEMU's "Bad address".
* The test of that cause: with `/sys/kernel/mm/transparent_hugepage/shmem_enabled` set to `deny` (which refuses huge pages to every tmpfs mount, i915's too) and QEMU started again, the same probe drew correctly (04:40, `proton-c-deny.txt`), and again in the next set (04:41, `proton-d.txt`). `never`, the value found, was put back at 04:54, before the browser runs.
* Why Venus does not hit it: with one 64 MiB Venus blob held mapped in the guest (05:07, `blobmaps.sh`, `blob-maps.txt`), QEMU's new mappings are `rw-s ... /i915 (deleted)`, the i915 object's shmem file mapped through its dma-buf, with VmFlags `rd wr sh mr mw me ms dc sd hg`: no `pf` and no `io`, so KVM takes those pages through `get_user_pages`, which handles huge pages. QEMU's mappings of `anon_inode:i915.gem`, made by its own GL on Crocus for virgl's resources, carry `pf io`, and those are the ones KVM refuses. So the fault needs virgl's GL path, the guest touching a host GL buffer that QEMU maps into the guest, and i915's huge pages; Venus's blobs, vkcube and WineD3D on Vulkan ran without it. Which of WineD3D's GL calls leads to that mapping was not traced. Whether a newer KVM maps such pages was not checked.

## What it changes for the plan

* Risk 5, forward mapping: cleared for Linux. A Venus blob of hasvk's memory maps into a guest through QEMU under KVM, coherent both ways, at 96 to 105 percent of the host's CPU bandwidth and 98 percent of its GPU copy rate. QEMU maps it from the i915 object's shmem file through the dma-buf, as ordinary shared pages.
* 80-5's Linux baseline: about 3.5 ms per map, about 50 ms of stalled virtio-gpu queue per unmap (QEMU's RCU wait), near-native bandwidth once mapped. Rach2's transport must also meet the kind of page that stopped the VM here: i915's CPU mappings are `VM_PFNMAP | VM_IO` over huge pages whose tail pages carry no count, and Linux 6.12's KVM answers them with `-EFAULT`. Rach2 must map them or refuse them with an error the VM survives.
* The Linux reference in QEMU on the Lenovo (74, 77): with Debian's default VT-d, a guest that uses virgl's GL can stop the VM; such runs need `shmem_enabled=deny` (tested), or `intel_iommu=off`, which by i915's source keeps it from mounting its huge-page tmpfs on this GPU (not tested). This bears on the chat's `intel_iommu=off` question: the setting changes i915's memory (step 9's numbers were taken with huge pages in i915's tmpfs) and QEMU's stability. Step 11 assigns the GPU to a VM, so the host's i915 does not drive it and QEMU maps none of its objects; the fault should not arise there (not tested).
* 74-4: Venus presents on a GPU host. QEMU's GTK and SDL displays with `gl=on` show Venus's frames on the panel through the guest's Weston, the open question of 74-4 on the testing PC; FIFO runs at 50 to 56 FPS against the host's 60. Decision A gains a measured GPU-host option: Linux on the Lenovo presents.
* 74-6 and 77: the pinned GE-Proton's DXVK 3.1.1 and vkd3d-proton 3.1 refuse the HD 4400 everywhere, for hasvk's own reasons, so Direct3D on this GPU stays with WineD3D, as the plan says; WineD3D on Vulkan through Venus works for 64-bit programs, and Wine's own vkd3d gives Direct3D 12 at feature level 11_0 on Venus. On a Venus host that DXVK accepts, the guest's Mesa must pass `VK_KHR_load_store_op_none` and `maintenance5` and `6`; Debian 13's 25.0.7 does not, so DXVK 2.6's success on the testing PC does not carry over to the pinned 3.1.1 with that guest Mesa. 32-bit programs under WoW64 need `VK_EXT_map_memory_placed` in the guest's Venus; 25.0.7 lacks it, 26.1.6 has it. So Rach2's ported Mesa must be newer than 25.0.7. Alpine's 26.1.6 passes `maintenance5`, `6` and `VK_EXT_map_memory_placed` on hasvk; whether it passes `VK_KHR_load_store_op_none` over lavapipe was not measured, and no version between the two was.
* 77-2 and 74-6, WebGPU on Venus: not reached. Chromium 156 in a Linux guest lists Venus over hasvk as available and never returns it; ANGLE on Vulkan cannot start, because Debian's virglrenderer cannot pass a GL-made buffer to Venus. 74-6 keeps SwiftShader as the guest's WebGPU, and "WebGPU on Venus" stays unproven on Linux. For Rach2's host side, sharing a GL-made buffer with Venus needs a dma-buf behind every GL resource (virglrenderer's GBM allocation, or the equivalent).

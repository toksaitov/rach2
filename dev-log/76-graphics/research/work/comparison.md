# Comparison of the three research reports

The chat's position (position-chat.md, written before reading the others), Codex's report (codex/report.md, 461 lines, finished 21:24) and Fable's report (fable.md, pending). Each claim taken from another report was checked against the code before it was used here; "checked" marks those.

## Codex: facts I lacked (checked)

* `file_ops` has read, write, poll, ioctl and close and no mmap (rach2/sys/fs/file.h:10-23). A device mmap contract is new core work, a prerequisite of GEM, dumb buffers, dma-buf and GTT maps. Checked.
* No uevent is ever generated: NETLINK_KOBJECT_UEVENT is only accepted as a protocol (netlink.c:313, 2807) and no "ACTION=" message exists in the kernel. Coldplug works through sysfs; hotplug (USB keyboard or mouse plugged in under Weston) needs kernel uevents. Checked.
* evdev stamps events with real time (evdev.c:209, rtc_realtime) and has no EVIOCSCLOCKID; libinput asks for CLOCK_MONOTONIC (libinput src/evdev.c:2426). Checked for the clock. Mice reach a separate queue, not evdev: input_mouse() calls mouse_push_packet() (rach2/sys/input.c:155-158) and no mouse source calls into evdev (mouse.c, arch/x86/ps2mouse.c, usb/hid.c). Weston would have no pointer. Checked.
* The harness already has QMP: etude opens a QMP control socket (tools/etude/qemu_profile.c:1284-1289) and a console scenario sends keys through it. My note "no QMP anywhere" was wrong; frame capture extends etude. Checked.
* A bubblewrap port exists (vendor/gnu/ports/bubblewrap.sh); the GNU root image targets 4096 MiB (vendor/gnu/Readme.md:16): browsers, Mesa with LLVM, Proton and a game need a measured size plan.
* Seccomp reports the compile-time architecture (rach2/sys/proc/seccomp.c:328, 360); an int 0x80 entry must report AUDIT_ARCH_I386, which Wine's own filter tests (signal_x86_64.c:2008-2014).
* No MAP_32BIT in the mmap path (syscall_proc.c:6170); Wine's low reservation must be measured.
* Debian trixie's pulseaudio ships module-oss; PulseAudio's OSS module falls back to read and write without mmap, which Rach2's /dev/dsp serves.
* GOG's current Crysis includes C1-Launcher (preservation update); the executable's PE machine type must be read from the files, not the directory name. PROTON_USE_WINED3D=1 selects WineD3D in Proton.
* Mesa's Intel probe tries I915_QUERY (topology, hwconfig, memory regions) even on Haswell and falls back when they fail (intel_device_info.c:568-588): those must fail cleanly, not be faked. MMAP_GTT_VERSION >= 4 turns on MMAP_OFFSET. Crocus asks for non-recoverable contexts (crocus_bufmgr.c:1530), so a reset must report context loss.
* The machine skill asks for a manager review before the first trial of new hardware code (reference comparison, bounded waits, interrupt order, a chip-model test) and a ten-minute notice for display work (machine SKILL.md:21-23).

## Agreements

* Linux uAPI unchanged at the boundary; Debian binaries for Mesa, Weston, both browsers.
* Legacy KMS with universal planes first; atomic later. Real planes and properties, not a stub capability.
* Software rendering as its own accepted path (fbdrm over the firmware framebuffer, shadow copy, simpledrm as reference), then virgl, then Haswell.
* Crocus needs relocations, real contexts, syncobj fences, correct swizzle, clean failure of unsupported queries.
* Keep the firmware's eDP mode and flip the primary plane; read the real pipe, plane and placement first instead of assuming pipe A.
* New WoW64 needs GDT 0x23, int 0x80 set_thread_area, a sigreturn that keeps CS, TLS per thread.
* Fsync's futex_waitv is optional; start with server sync, then esync.
* Recovery on the Lenovo first: trial boot alone cannot reset a hung machine.
* Slow down at three boundaries: buffer and mapping lifetime, Haswell command validation and reset, mixed-mode entry and signal return.

## Disagreements and how each is settled

1. Command validation on Haswell. I proposed privileged GGTT batches without a parser, as a documented limit. Codex: a browser-capable driver must validate. Codex is right: MI_LOAD_REGISTER_IMM in a privileged batch reaches the MMIO range, and Haswell's GTT entries live in the same BAR, so any process with the render node could own the machine. Unprivileged batches without a parser lose the registers Crocus writes (Linux's parser rationale, i915_cmd_parser.c:45-60). Settled: bring-up may run privileged behind a debug switch; Linux's Haswell parser (MIT) is ported before browsers run on the Lenovo.
2. Seat. I proposed libseat's noop backend with Weston as root. Codex: seatd with SEATD_VTBOUND=0 and an ordinary user. Codex is right; it is the upstream arrangement and keeps the compositor unprivileged. Settled.
3. Sound. I proposed alsa-lib's oss plugin with no daemon; Codex proposes PulseAudio's module-oss. Open: argue in round 2. My case: no daemon, the kernel already mixes, every client speaks ALSA. Codex's case: Proton's first driver is winepulse, browsers prefer Pulse, it is the ordinary desktop interface.
4. Wine for diagnosis. Codex proposes a controlled Wine source build with new WoW64. I propose Proton's own wine binaries (files/bin-wow64) run directly, which needs no build; a Wine source build needs a MinGW cross toolchain the GNU layer lacks. Open: argue in round 2.
5. Milestone count. Codex splits into eight (A to H) plus ia32. Each Rach2 release runs every suite on three machines and the Lenovo (milestone 71's took from 18:13 to about 00:30), so fewer milestones mean fewer releases. I propose four graphics-and-games milestones plus ia32, with Codex's eight as task groups. Open: argue in round 2.
6. The Linux Crysis baseline first. Codex ranks "Crysis is not playable through WineD3D on HD 4400" first and measures it on Linux on the Lenovo before anything else. I had it fourth. Codex is right that it is the one measurement that can void the December goal cheaply; it needs the owner to buy the game and to allow Linux boots on the Lenovo beyond the skill's single discovery boot. Two owner decisions.

## Codex round 3: attack on plan v1 (codex/round3.md, 56 lines, finished 22:08; checked at 22:10)

Accepted, each checked:

* Storage that survives a release. An update writes the whole root image over partition 3 and keeps only /home, /root and the keys, copied through the recovery system's RAM (utils/rach2-install:874 keeps them in /tmp/rach2-update-keep, :988-995) and archived on the 64 MiB recovery partition (:8-12); the release stages the 4 GiB root in the Lenovo's /dev/shm (tools/flow/release.sh:863), and tmpfs takes half of RAM by default (rach2/sys/fs/tmpfs.c:1090). So a 15 GiB game, Proton and prefix cannot live in the root or in /home. The plan needs storage on its own partition, which the installer and every update leave alone, rehearsed in QEMU with representative data, in the first release, before the baseline and the game.
* Aliasing PPGTT. Linux runs Haswell with INTEL_PPGTT_ALIASING and a 31-bit PPGTT (i915_pci.c:311-324, GEN7_FEATURES); an unprivileged batch runs in the PPGTT and a secure one from the GGTT (gt/gen6_engine_cs.c:250, hsw_emit_bb_start). 74's engine work must design the address spaces with the parser's shadow and trampoline, not GGTT alone.
* Implicit synchronization in 73-3: each object's earlier work is waited on before a new request starts (i915_gem_execbuffer.c:2136), SYNC_IOC_MERGE is needed (crocus_fence.c:401), and the cases are a delayed producer, concurrent readers and a failed producer.

* Full ia32 needs a versioned coverage matrix of every syscall_32.tbl entry, translation and ioctl; the i686 tests alone cannot show the whole ABI. Example: Linux's 16-bit ID calls and modify_ldt (syscall_32.tbl:38, 138); Rach2 has no modify_ldt (only a mention in rach2/sys/arch/tls.Readme.md).

* Measure the root's real growth: 1315 MiB is an upper bound, much of it may already be in the GNU root (vendor/gnu/install_root.sh:57); an image above 4096 MiB is not shown yet.
* Decision 13 holds with a qualification: a fresh prefix runs the 32-bit SysWOW64 rundll32.exe even for a 64-bit game (wine programs/wineboot/wineboot.c:1510, 1723), so 75-1's WoW64 slice is on Crysis's path: compatibility mode, selector 0x23, low mappings, FS and TLS per thread, int 0x80 for set_thread_area, signals and FPU state on return to 32-bit code. No ELF32 loading. Every ELF the pinned launcher and runtime start from a fresh prefix must have its class recorded before the claim is final.
* Dependencies: the synthetic i915 backend follows 73's contracts, not 74-4; 74-3 waits on 74-4's GGTT allocation and pinning, and display and engine share one owner for MMIO, reservations and interrupts; a partial prerequisite must be its own task, since `next` offers a task only when every blocker is closed (tools/flow/board.sh:43-48); the watchdog measurement is separate from the purchase-dependent Linux session; Proton's runtime diagnosis (`/bin/true` in pressure-vessel) starts apart from Wine's graphics.

* 73-2, 73-4, 74-4 and 75-2 are task groups: DRM objects apart from KMS; fbdrm, the virtio transport and virtio display apart; GPU memory, contexts and submission, reset and RPS apart; compat entry, ELF32 loading, signals and core dumps apart.

## Fable round 2 (fable-round2.md, 40 lines; checked)

## Argon's second opinion (second/argon.md, 22:3x), checked against the code

Its first run read for ten minutes and was refused a shell command; the resumed session answered from what it had read. Each citation was read.

* Accepted: kcmp. Mesa's `os_same_file_description` calls `kcmp(KCMP_FILE)` (util/os_file.c:228-269) and neither of Rach2's call tables has it. Crocus keeps the caller's descriptor while its buffer manager works on a dup of it (crocus_screen.c:667-671); without kcmp, `crocus_bo_export_gem_handle_for_device` takes the two as different files, imports the buffer through PRIME into the same file, gets the same handle back and closes it twice (crocus_bufmgr.c:1414-1460, :618-631; Mesa's own comment there names the double close). virgl's screen sharing makes the same test (virgl_drm_winsys.c:1335). KCMP_FILE goes into 73-4, before any Mesa test.

Ten findings, most serious first. All checked against the sources named.

1. Plan line 112 (decision 8), tasks 77-1, 77-2, 77-9: Crysis is pinned to GE-Proton with PROTON_USE_WOW64 and -dx9, but nothing sets PROTON_USE_WINED3D.
Wrong: Proton defaults D3D9 to DXVK, not WineD3D. DXVK will be copied into the prefix, will look for Vulkan 1.3, and hasvk on Haswell reports 1.2 (no softpin on gen7), so Crysis fails to start on the GPU path or falls back to lavapipe, which cannot meet about 24 FPS. The Linux reference in 77-2 would measure the same wrong stack.
Evidence: build/research/src/proton/proton:951 and :1091 (dxvkfiles includes d3d9 unless wined3d), :1638 (PROTON_USE_WINED3D is the switch); build/research/src/mesa/src/intel/vulkan_hasvk/anv_device.c:974-975 (1.3 only with softpin or override, else 1.2).
Change: add PROTON_USE_WINED3D=1 to decision 8, 77-1, 77-2 and 77-9, and make 77-2 and 77-9 record from the Wine log that wined3d's d3d9 loaded and no DXVK d3d9 is in the prefix.

2. Plan line 110 (decision 6), tasks 73-13, 73-14, 73-17, 77-4: sound is promised (lines 7, 16, 18) but no task builds an ALSA kernel interface, and no task proves the proposed OSS chain works with the pinned Debian userland.
Missing: Rach2 gives programs only OSS /dev/dsp and /dev/mixer; there is no /dev/snd. Chromium, Firefox and PulseAudio speak PulseAudio or ALSA, not OSS. "ALSA's OSS plugin and PulseAudio both shipped" is a package list, not a working route: PulseAudio's ALSA sink over the OSS plugin needs mmap and timing behaviour the plugin does not provide by default, and 73-14's "both sound routes" names neither route.
Evidence: rach2/sys/audio/Readme.md:3 and :32 (programs get /dev/dsp only); no snd device in rach2/sys/audio/.
Change: add a task before 73-17 that either builds the /dev/snd PCM, control and timer subset, or proves PulseAudio on the OSS plugin end to end (mmap off, delay from GETODELAY and GETOPTR), with acceptance judged by a recorded tone through the loopback the audio subsystem already has, not by a process staying alive.

3. Plan line 146 (73-17), line 148 (73 Done), line 304 (left out): 73 Done requires video to drop no more frames than Debian's browsers on the same Lenovo, while the plan leaves GPU video decoding out and no milestone owns it.
Wrong ordering: on Debian, Firefox and Chromium use VA-API on the HD 4400 for H.264 and VP9 where the hardware supports it. Rach2 in 73 would decode on the CPU and composite through llvmpipe on the same two cores. 1080p parity is not reachable that way. Line 304 says VA-API is "added only if" 73-17 or 75-12 fail, but VA-API on Intel is the separate i965 libva driver, which needs the i915 GEM interface and the VCS (video) ring; 75-4 builds only the render ring and 73-13's package list has no libva or intel-vaapi-driver.
Evidence: plan lines 142, 173, 304; build/research/src/mesa/src/gallium/targets/va/meson.build:86-96 (Mesa's VA drivers come from Gallium pipe drivers; Crocus has no video codec interface, so Mesa 25.0.7 gives no Intel VA driver).
Change: either drop frame-drop parity from 73 Done and judge 73 video by software-decode counts alone, or move VA-API into 75 as its own task (VCS ring, i965 ioctls, libva packages) and compare against Debian only there.

4. Task 76-7, 77-3, 77-9: no task adds futex_waitv (syscall 449), so Proton's fsync silently turns itself off on Rach2 while the Linux reference runs with it on.
Missing: Rach2's futex has only WAIT, WAKE and their BITSET forms. Wine probes futex_waitv once and disables fsync for the whole run on ENOSYS; Proton sets WINEFSYNC=1 by default. Games still run through esync or the wineserver, at higher CPU cost on a two-core i3, against a 77-2 baseline taken with fsync active. That alone can be the difference at 24 FPS and will look like a GPU shortfall.
Evidence: rach2/sys/proc/futex.h:14-19; syscall 449 absent from rach2/syscalls.md; build/research/src/wine/dlls/ntdll/unix/fsync.c:152-174; build/research/src/proton/proton:1665-1667.
Change: add futex_waitv to 76-7 (both 64-bit and compat forms), and require 77-2 and 77-9 to record whether fsync and esync were actually active.

5. Plan lines 40, 148, 184, tasks 73-12, 75-1, 75-13: IGT's KMS CRC tests, connector forcing and EDID injection are in the Done criteria, but they run through debugfs, which Rach2 does not have and no task builds.
Missing: pipe CRC on Linux is read from debugfs crc/control and crc/data files; forcing a connector and overriding its EDID are debugfs writes. Without a debugfs, 73-12's CRCs, 75's pipe CRC against Linux, and "IGT's EDID injection meanwhile" for HDMI cannot run at all, so 73 Done and 75 Done are unreachable as written, and HDMI has no test before the owner's sitting.
Evidence: rach2/sys/fs/ has procfs, tmpfs, synthfs and no debugfs; build/research/src/linux/drivers/gpu/drm/i915/display/intel_pipe_crc.c:28; build/research/src/linux/drivers/gpu/drm/drm_debugfs.c:394 and :683 (connector force file).
Change: add a debugfs task to 73 (mount, per-device and per-connector files, CRC control and data, connector force and EDID override) and the i915 files IGT's gem tests open, or remove those items from both Done lists.

6. Plan line 34 (Mode setting), task 73-8, line 17: "virtio-gpu takes its modes from the host's EDID, and a resized host window is a hotplug" joins two paths that exclude each other in Linux's driver.
Wrong: when an EDID is present, Linux's get_modes returns the EDID modes at once and never turns the host's suggested size into a mode. The suggested size from display-info becomes the preferred mode only on the no-EDID path. A driver ported as line 34 says, run against a QEMU profile with EDID on, will not follow a window resize, so "the same in QEMU at any window size" fails.
Evidence: build/research/src/linux/drivers/gpu/drm/virtio/virtgpu_display.c:160-189.
Change: make 73-8 choose and name one behaviour: run the QEMU profiles with edid=off and build the preferred mode from display-info on each display event, or synthesize a mode from the suggested size even when an EDID exists. Put the chosen QEMU properties in 73-16's profiles.

7. Tasks 73-1, 73-4, 73-6, 75-2: the interface contract never pins each driver's DRM identity, which is what Mesa, GBM and IGT dispatch on.
Missing: Mesa's loader picks a driver by PCI id map and by exact kernel driver name ("i915" or "xe"), falling back to the name from DRM_IOCTL_VERSION; GBM likewise loads a DRI driver by that name, with kms_swrast reached by name. Linux's names are "virtio_gpu", "bochs-drm" and "simpledrm". The plan's own names (fbdrm, test display) have no Mesa driver file, so Weston GL on the Lenovo framebuffer and Crocus in the fault backend can fail to load or silently fall back to llvmpipe, and IGT's per-module opens will not match.
Evidence: build/research/src/mesa/src/loader/loader.c:130, :705-722, :755; build/research/src/linux/drivers/gpu/drm/virtio/virtgpu_drv.h:46; build/research/src/linux/drivers/gpu/drm/tiny/bochs.c:601; build/research/src/linux/drivers/gpu/drm/tiny/simpledrm.c:31 and :1017.
Change: 73-1 should carry a per-driver table: version name, major and minor, date, driver features (DRIVER_RENDER only where a render node exists), the PCI ids published in sysfs, and which Mesa driver each must load, tested by 73-16 with the loader's own diagnostics.

8. Plan line 166 (75 goal), tasks 75-5, 75-6: "a program that hangs the GPU loses its work while others keep rendering" overpromises on Haswell, and the ioctls Mesa uses to report loss are never named.
Wrong and missing: gen7 reset in Linux is the gen6 engine-domain reset; there is no per-context engine reset before gen8, so a reset interrupts every context on the ring. Crocus learns about it through DRM_IOCTL_I915_GET_RESET_STATS and sets I915_CONTEXT_PARAM_RECOVERABLE and PRIORITY when it makes a context; hasvk refuses to start without a command parser version on gen7. None of reset stats, context setparam, or parser version appears in 75-5 or 75-6, so GL robustness and the browsers' GPU process restart (73-17, 75-12) have nothing to read.
Evidence: build/research/src/linux/drivers/gpu/drm/i915/gt/intel_reset.c:342 and :686; build/research/src/mesa/src/gallium/drivers/crocus/crocus_batch.c:794-797; build/research/src/mesa/src/gallium/drivers/crocus/crocus_bufmgr.c:1546-1567; build/research/src/mesa/src/intel/vulkan_hasvk/anv_device.c:1665-1671.
Change: name GETPARAM parser version, context create and setparam, and GET_RESET_STATS in 75-5 and 75-6, and reword the 75 goal to Linux's ring semantics: the guilty context is banned, the others recover after the reset.

9. Task 75-10: the outputs task lists DDI, eDP, AUX and link training, HDMI with infoframes, PLLs, fitter, VBT and hotplug, but omits GMBUS, the I2C controller that reads an HDMI monitor's EDID.
Missing: on Haswell, HDMI EDID is read over DDC through GMBUS pins assigned per DDI port; AUX serves DisplayPort and eDP only. Without GMBUS (and its bit-bang fallback for the displays that need it) the driver cannot probe an HDMI monitor's modes, so 75 Done's "an HDMI monitor at its modes" can only ever use forced or injected modes.
Evidence: build/research/src/linux/drivers/gpu/drm/i915/display/intel_gmbus.c:44 and :79 (separate controller and pin table, about 900 lines beside intel_ddi.c).
Change: add GMBUS with the DDC pin map and GPIO fallback to 75-10, sized in the milestone total.

10. Plan line 112 (decision 8), tasks 77-8, 77-9: Crysis acceptance is ordered through umu-launcher and the Steam Linux Runtime container, although the direct route in 77-3 is enough to prove the game, and Rach2's namespace limits put the container and the browsers in competition.
Bad ordering: pressure-vessel and bubblewrap need mount namespaces per launch, /dev/dri pass-through and a D-Bus proxy, none of which is a named subtask beyond 77-8's one line. Rach2 allows 32 mount namespaces system-wide and 5 extents per uid_map. A desktop with both browsers sandboxed plus a game container can meet ENOSPC in normal use, and any container failure then blocks the owner's Crysis criterion for reasons unrelated to graphics.
Evidence: rach2/sys/proc/ns.c:34 (NS_MNT_MAX 32); rach2/sys/proc/ns.h:33 (NS_EXTENTS 5); rach2/sys/proc/ns.Readme.md, Limits section.
Change: accept Crysis in 77-9 on the direct GE-Proton route first, keep umu as a measured extra that cannot block the criterion, and add a task to raise or rework the mount namespace limit before browsers and containers are required to run together.

One claim checked and found right, for the record: line 36 on the absent VGA output. The cited code does say Haswell ULT has no CRT (build/research/src/linux/drivers/gpu/drm/i915/display/intel_display.c, intel_ddi_crt_present), so treating a fitted VGA port as a DisplayPort converter is correct.

Verdict: the Crysis path is sound in kernel scope and wrong in one scheduling step. The December risk is the launcher chain and the delayed baseline, not Crysis's PE or the WoW64 slice's size.

## 1. What would stop Crysis

* Wrong order in the table, against the plan's own principle. The baseline is the one measurement that can void December ([plan-v2.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/plan-v2.md:162)), yet 76-2 waits on 73's release ([plan-v2.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/plan-v2.md:136)). The data partition is a convenience, not a prerequisite: the earlier settled procedure put persistence on today's partition 3 ([comparison.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/comparison.md:48)).
* A silent fallback to ELF32. Proton picks WoW64 only if `PROTON_USE_WOW64=1` or `files/bin/wine` is absent ([proton](/Users/toksaitov/Desktop/rach2/build/research/src/proton/proton:533)), and `files/bin/wine` is the i386 loader ([Makefile.in](/Users/toksaitov/Desktop/rach2/build/research/src/proton/Makefile.in:579)). If umu or pressure-vessel drops the variable, Rach2 gets an ELF32 exec and dies. The plan never says to delete `files/bin/wine` from the pinned tree, which makes WoW64 unconditional by that same test.
* Three exactness points inside 75-1, each fatal if read loosely. (a) `set_thread_area` is not alloc-once: Wine calls `alloc_fs_sel` again per new thread with the existing index ([signal_x86_64.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/ntdll/unix/signal_x86_64.c:2990)), reading `user_desc` through 32-bit `%ebx` on a low stack ([signal_x86_64.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/ntdll/unix/signal_x86_64.c:103)). (b) Rach2's GDT is per-CPU ([percpu.h](/Users/toksaitov/Desktop/rach2/rach2/sys/arch/x86_64/percpu.h:75)), so the thread's TLS descriptors must be reinstalled on every switch and migration. Wine reloads `%fs` from the descriptor in its signal return path ([signal_x86_64.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/ntdll/unix/signal_x86_64.c:874)). A stale entry means another thread's TEB. (c) `rt_sigreturn` must restore the frame's CS and SS, not only save them. Today it forces the 64-bit pair ([sigframe.c](/Users/toksaitov/Desktop/rach2/rach2/sys/arch/x86_64/sigframe.c:359)). The `int 0x80` gate must also return `-ENOSYS` for other numbers, because today it faults ([idt.c](/Users/toksaitov/Desktop/rach2/rach2/sys/arch/x86_64/idt.c:75)).
* Seccomp reporting is wider than the entry test. Wine's filter decides by `seccomp_data.arch` and instruction pointer ([signal_x86_64.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/ntdll/unix/signal_x86_64.c:2010)), and Rach2 hard-wires the compile-time arch in both the filter data and the SIGSYS siginfo ([seccomp.c](/Users/toksaitov/Desktop/rach2/rach2/sys/proc/seccomp.c:328), [seccomp.c](/Users/toksaitov/Desktop/rach2/rach2/sys/proc/seccomp.c:372)). 75-1 must cover the trap siginfo too.
* A late display meeting. WineD3D through winex11 is GLX with DRI3 over Xwayland and Glamor, not the EGL Wayland path the browsers prove in 74-12. The first WineD3D-on-Crocus test is 76-7, after all of 74 ([plan-v2.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/plan-v2.md:141)). A D3D9 smoke on the no-op i915 backend (74-10) and on the Lenovo right after 74-11 costs little and moves that risk a month earlier.

## 2. Is the WoW64-only claim right

Yes, for the game, wineserver and wine process tree. Evidence: Proton's x86-64 wine build enables i386 only as a Windows arch ([Makefile.in](/Users/toksaitov/Desktop/rach2/build/research/src/proton/Makefile.in:520)); `bin-wow64` installs only the x86-64 wine, preloader and wineserver ([Makefile.in](/Users/toksaitov/Desktop/rach2/build/research/src/proton/Makefile.in:568)). A 32-bit PE runs in the same 64-bit process through `wow64cpu` thunking ([syscall.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/wow64/syscall.c:747)), with CS hard-coded to 0x23 ([signal_x86_64.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/ntdll/unix/signal_x86_64.c:2897)). The fresh prefix's SysWOW64 rundll32 is a PE, not an ELF ([wineboot.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/programs/wineboot/wineboot.c:1727)). Even if `Bin64/Crysis.exe` proves to be a 32-bit launcher for `crysis64.exe`, still unverified ([findings-chat.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/findings-chat.md:71)), WoW64 covers it. No ELF32 is exec'd, so no ELF32 loader and no compat table. Two caveats. The claim holds only with the fallback above removed. It is unproven for the launcher and runtime chain, whose ELF census is scheduled in 76-5, after the baseline that should produce it. Sniper is required by the tool manifest ([toolmanifest_runtime.vdf](/Users/toksaitov/Desktop/rach2/build/research/src/proton/toolmanifest_runtime.vdf:5)) and is not in the cloned tree, so nobody has yet checked pressure-vessel's helpers.

## 3. Is the order right

In principle, yes. Baseline first settles playability on a 1.9 GHz two-core part through WineD3D before kernel work depends on it. Proton's own `bin-wow64` wine is the right diagnostic, since it is the binary Proton itself execs ([proton](/Users/toksaitov/Desktop/rach2/build/research/src/proton/proton:533)) and a source build needs MinGW, which the GNU layer lacks ([comparison.md](/Users/toksaitov/Desktop/rach2/build/flow/coordinator/graphics-research/comparison.md:45)). Xwayland first is right: winex11 gets relative mouse from XInput2 raw events and refuses to clip without it ([mouse.c](/Users/toksaitov/Desktop/rach2/build/research/src/wine/dlls/winex11.drv/mouse.c:483)), plus Xwayland's emulated modes. But the plan's "GE-Proton or UMU-Proton" is not yet a pin. UMU-Proton is meaningful only inside umu, pressure-vessel and sniper. GE-Proton can run `proton run` against host libraries. A baseline under sniper measures sniper's libraries and masks GNU-root gaps, and puts pressure-vessel's graphics import on the critical path, which 76-5 gives one line. Pick one before 76-2, and measure that one.

## 4. The one change first

Move 76-2 to the front, this week, on the current disk layout. In the same step: pin GE-Proton run directly as the December target, demote umu and pressure-vessel to a later task, delete `files/bin/wine` from the pinned tree, and record the class of every ELF the baseline execs. One Lenovo session then settles performance, the launcher question and the no-ELF32 claim, before 73 releases.

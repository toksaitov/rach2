1. Plan location: `build/flow/coordinator/graphics-research/plan-draft4.md:72` ("What to proxify") and task `80-5` (`plan-draft4.md:262`).
What is wrong or missing: The plan says the VM backend answers a `MAP_BLOB` request with "a range of VM-physical memory" that Rach2's KVM translates through its memory slots into pinned frames mapped into the program and torn down through `filemap_shmem_cut` when the VM dies. In Deliverable 2, `virglrenderer` runs inside the Linux driver VM. Mesa's Venus driver requires `supports_blob_id_0` and allocates its ring and command buffers as `VIRTGPU_BLOB_MEM_HOST3D` with `blob_id = 0` (which `virglrenderer` backs with guest `memfd`), and allocates `HOST_VISIBLE` `VkDeviceMemory` through `hasvk` (`i915` GEM shmem in the guest). In the Linux guest, both `memfd` and `i915` GEM shmem objects consist of discontiguous 4 KiB guest pages rather than one contiguous guest-physical range, and an unprivileged guest daemon cannot pin `i915` write-combined `PFNMAP` mappings or translate them to guest physical addresses by itself. On the Rach2 side, `ksys_mmap_pgoff` only maps contiguous physical device ranges (`VM_PROT_IO`) or `struct shmem` page trees (`filemap_share`), and `filemap_shmem_cut` only cuts mappings backed by `filemap_share` or `filemap_share_disk`.

2. Plan location: `build/flow/coordinator/graphics-research/plan-draft4.md:48` ("KVM-like virtualization"), task `78-3` (`plan-draft4.md:230`), task `79-2` (`plan-draft4.md:245`), and task `79-3` (`plan-draft4.md:246`).
What is wrong or missing: On the Lenovo G50-70, the graphics IOMMU `dmar0` (`0xfed90000`, for `00:02.0`) reports `ecap = 0xf0101a` and the second IOMMU `dmar1` (`0xfed91000`, for `00:03.0` and the rest of PCI) reports `ecap = 0xf010da`. Three hardware rules follow that the plan omits. First, bit 0 of `ecap` (`ECAP_C`, page-walk coherency) is `0` on both `dmar0` and `dmar1`, so neither IOMMU snoops CPU caches when walking root, context, or second-level DMA page tables; without `clflush` after every table write in `79-2` and `79-3`, the hardware IOMMU reads stale unmapped entries from RAM. QEMU's emulated `intel-iommu` in `79-2` and `79-4` is coherent in software and will not catch this. Second, bit 7 of `ecap` (`ECAP_SC`, snoop control) is `0` on `dmar0` and `1` on `dmar1`; on `dmar0`, bit 11 (`DMA_PTE_SNP`) of second-level PTEs is reserved and setting it causes a DMA fault on every GPU memory access. Third, because `dmar0` lacks snoop control, it cannot force the HD 4400's no-snoop DMA (GTT walks, ringbuffers, WC buffers, and display scanout) to snoop CPU caches; if `78-3` sets EPT memory type to Write-Back with `EPT_IPAT` (Ignore PAT, bit 6) set on guest RAM, guest `i915` WC and UC writes remain in the CPU cache while the GPU reads stale RAM.
Evidence: `dev-log/70-wifi-chip/linux/dmesg.txt:191-194`, `build/flow/coordinator/graphics-research/plan-draft4.md:48`, `build/flow/coordinator/graphics-research/plan-draft4.md:230`, `build/flow/coordinator/graphics-research/plan-draft4.md:245-246`, `https://github.com/torvalds/linux/blob/v6.18/drivers/iommu/intel/iommu.c` (`__iommu_flush_cache`, `domain_update_iommu_snooping`), `https://github.com/torvalds/linux/blob/v6.18/arch/x86/kvm/vmx/vmx.c` (`vmx_get_mt_mask`).
Proposed change: In `79-2` and `79-3`, flush modified root, context, and second-level PTE cache lines with `clflush` when `ECAP_C == 0`, and leave `DMA_PTE_SNP` (bit 11) clear when `ECAP_SC == 0`. In `78-3`, leave `EPT_IPAT` clear on EPT entries for guest RAM when a non-coherent VFIO device is attached so guest PAT `WC` and `UC` attributes take effect.

3. Plan location: `build/flow/coordinator/graphics-research/plan-draft4.md:62`, `plan-draft4.md:65`, and task `80-1` (`plan-draft4.md:258`).
What is wrong or missing: Task `80-1` says QEMU's user-mode networking forwards a guest port to `virgl_test_server` on the Linux host and `GALLIUM_DRIVER=virpipe` on Rach2 runs `glxgears` over a socket with Mesa 25.0.7 unchanged. Second, even with a local `AF_UNIX`-to-TCP relay on Rach2, `virgl_vtest_connect` negotiates `VTEST_PROTOCOL_VERSION` 3 with `virgl_test_server`. 4. Plan location: `build/flow/coordinator/graphics-research/plan-draft4.md:70` ("Existing protocols or our own"), task `80-3` (`plan-draft4.md:260`), and task `80-4` (`plan-draft4.md:261`).
What is wrong or missing: Line 70 and task `80-3` state that the Rach2 `virtio-gpu` driver allocates from the shared `ivshmem` region through a restricted DMA pool whose DMA addresses are offsets into the region, so no bounce buffer is needed. In Linux's `drivers/gpu/drm/virtio/`, `virtio-gpu` does not allocate its command buffers or backing pages through `dma_alloc_coherent`: control headers (`vbuf->buf`, `vbuf->resp_buf`) come from `kmem_cache_zalloc` or `kzalloc`, `SUBMIT_3D` payloads and `ents` arrays (`vbuf->data_buf`) come from `kvmalloc` or `kmalloc` and are queued via `sg_init_one`, and 2D/3D resource pages (`VIRTIO_GPU_CMD_RESOURCE_ATTACH_BACKING` and `BLOB_MEM_GUEST`) come from `drm_gem_shmem_create` (`shmem` page cache). 5. Plan location: Task `78-3` (`build/flow/coordinator/graphics-research/plan-draft4.md:230`), task `79-3` (`plan-draft4.md:246`), and task `79-5` (`plan-draft4.md:248`).
What is wrong or missing: On the Lenovo G50-70, the HD 4400 (`00:02.0`) has a 4 MiB MMIO BAR (`BAR 0` at `0xc0000000`) and a 256 MiB aperture BAR (`BAR 2` at `0xb0000000`). When `79-3` sets `VFIO_REGION_INFO_FLAG_MMAP` on BARs, QEMU 10.0.13's `vfio_region_mmap` `mmap`s both BARs into QEMU's user address space and registers those virtual ranges with `KVM_SET_USER_MEMORY_REGION` (`78-3`). (a) Linux's VFIO PCI uAPI places region `index` at byte offset `index << 40` (`VFIO_PCI_OFFSET_SHIFT = 40`, page offset `index << 28`), which QEMU passes to `mmap`, `pread64`, and `pwrite64` when region offsets use the standard encoding or for `VFIO_PCI_ROM_REGION_INDEX` / IGD quirk regions (`index >= 8`), whereas `ksys_mmap_pgoff` in `rach2/sys/syscall_proc.c:6379-6386` truncates `pgoff` to `uint32_t` (`vma_t.pgoff`) and rejects `pgoff + len / PAGE_SIZE > 0xFFFFFFFFul` with `-EOVERFLOW`.

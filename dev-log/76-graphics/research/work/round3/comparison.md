# Round 3: the three reviews compared

The chat's comparison of `position-chat.md`, `codex.md` and `fable.md`, with the facts checked on 2026-11-04 between 00:00 and 00:20 (UTC+6). Paths are relative to the repository; `S/` is `build/research/src/`.

## Facts settled tonight

* F1. `memfd_create` is in both system call tables: `rach2/sys/arch/x86_64/systab.c:383` and `rach2/sys/arch/i686/systab.c:155`; `rach2/syscalls.md:141` gives 319 on x86-64 and 356 on i386. Fable's "absent from the x86-64 table" (fable.md:144, :407) is wrong, so QEMU's `memory-backend-memfd` is available.
* F2. Mesa 26.1.0 (2026-05-06) lists in its changes "intel: Add virtio-gpu native context", "iris: Support virtio-gpu native context", "anv: Support virtio-gpu native context" and "crocus: Support virtio-gpu native context" (https://docs.mesa3d.org/relnotes/26.1.0.html). Fable's "crocus and iris have no virtio code" (fable.md:114, :122, :418) was a grep of Mesa 25.0.7 (`S/mesa/VERSION`). Still unverified: how Crocus's native context carries gen7's relocations, and whether virglrenderer's `drm-intel` server, experimental and tested on Tiger Lake and newer, accepts them on Haswell.
* F3. Haswell ULT has no CRT: `intel_ddi_crt_present` returns false for `IS_HASWELL_ULT` (`S/linux/drivers/gpu/drm/i915/display/intel_display.c:7767`). The i3-4030U is Haswell ULT. Codex's "implement VGA if present; do not assume its connector must be behind an external bridge" (codex.md:41-42) does not hold for this chipset: a VGA port on the G50-70, if fitted, is a DP-to-VGA converter on a DDI and a DP sink to the driver.
* F4. QEMU's `contrib/vhost-user-gpu` (master, `virgl.c`) handles 19 commands: virgl 2D and 3D, capsets VIRGL and VIRGL2 only. It has no blob resources, no context init, no Venus and no native context; any other command answers ERR_UNSPEC. Its display protocol (https://www.qemu.org/docs/master/interop/vhost-user-gpu.html) covers scanout, cursor and dma-buf sharing only. rust-vmm's `vhost-device-gpu` 0.1.0 also lacks blob and Venus, waiting on vhost-user shared-memory mapping (https://lib.rs/crates/vhost-device-gpu). So an unchanged vhost-user GPU backend carries virgl and nothing else today; the chat's adapter design (position-chat.md:47) would cap the bed at virgl.
* F5. virtio-msg, a message transport that keeps virtqueues in shared memory, is under standardization (Linaro, Arm; RFC patches for Linux in 2025, not merged as far as found: https://www.linaro.org/blog/what-is-virtio-msg-a-message-based-virtio-transport-for-heterogeneous-systems/). It is the nearest standard for virtio over shared memory, and a model to follow, not a dependency.
* F6. The testing PC has no nested virtualization: WSL's `/proc/cpuinfo` shows `hypervisor` but no `svm`, and only `kvm.ko` is loaded (no `kvm_amd`), measured 2026-11-03 at 23:3x. The brief's "nested under Hyper-V" was wrong; Rach2's SVM runs there under TCG, as on the Mac. Turning nesting on would change the owner's Windows setup.
* F7. IGT is in Debian trixie as `intel-gpu-tools` 2.0; the brief's "no igt-gpu-tools" was the old package name (Fable found it).

## What all three agree on

* Atomic KMS on every driver, legacy calls over it; real modes on std-vga (bochs) and virtio-gpu (EDID); fbdrm keeps one mode; on Haswell the firmware's state is read out and kept, and a full mode set covers eDP (power sequencing, AUX, link training), HDMI and DP on the DDIs, the panel fitter, PLLs, hotplug, the VBT blocks and watermarks; the console is a DRM client; games get lower resolutions by Xwayland's and Wine's scaling, not by a mode set.
* Linux's KVM interface, so that Debian's QEMU 10.0 runs unchanged; VMX with EPT and SVM with NPT; the split irqchip with the LAPIC in the kernel; an MMIO decoder; KVM selftests and kvm-unit-tests as the corpus.
* VT-d with interrupt remapping and the RMRRs, and VFIO type1 with vfio-pci and the IGD's regions; QEMU's emulated `intel-iommu` before the Lenovo; QEMU's legacy IGD mode tried in the Linux session first.
* The driver VM owns the whole IGD, display included; Rach2 keeps input, the compositor and every program; the VM shows Rach2's frames on its KMS; on the VM's death programs see a lost device and Rach2 takes the GPU back.
* Existing protocols for everything that crosses (virgl, Venus, the virtio-gpu command set, Linux's object semantics); only the transport that reverses the direction is new.
* Full ia32 compatibility, plus a pure 64-bit profile (a build switch and a boot switch, as Linux's `ia32_emulation=`).
* Conformance against Debian on the same Lenovo (IGT, piglit, dEQP, the WebGL suite, glmark2), video measured, eviction of idle buffers, RC6 and frequency control, Steam outside the build unless the owner decides otherwise.

## Disagreements, and the chat's proposed resolution

* D1. The reverse transport and its two ends.
  * Chat: Rach2's own virtio-gpu driver over a virtio transport in shared memory; in the VM an adapter to an unchanged vhost-user GPU backend.
  * Fable: a host proxy render node with the virtio-gpu uAPI over a ring of our own in ivshmem; in the VM a server of our own around libvirglrenderer (fable.md:134-140, :304-305).
  * Codex: a broker and a versioned envelope with object generations, quotas and fuzzing; a guest agent around virglrenderer (codex.md:140-169).
  * Proposed: the wire is the virtio-gpu command set in standard split virtqueues, every queue and buffer inside one shared region (a restricted DMA pool), notifications by doorbells, polling first. On Rach2 this is the same virtio-gpu driver that serves QEMU with a second transport beside virtio-pci, so the render node, the uAPI and Mesa's virgl, Venus and native-context drivers are unchanged. In the VM it is a small virtio-gpu device backend around libvirglrenderer (Fable's server, with standard framing), modelled on QEMU's `hw/display/virtio-gpu-virgl.c`, which handles blob, context init, Venus and native context; F4 rules out the unchanged vhost-user backend. Codex's rules apply to the transport whole: checked offsets and lengths, generation-tagged ids, quotas, failure of every pending fence on the VM's death, a fuzzer. Fable's vtest rung (virpipe to `virgl_test_server` over QEMU's user networking) comes first, with no kernel code.
* D2. Native context on Haswell. Fable: none for gen7. Codex and chat: Crocus has it (F2). Proposed: a rung of the bed after virgl, entered only after a check proves the server side on Haswell (capsets enumerated and a small scene rendered with a matched stack: QEMU 11, virglrenderer 1.3 or later with `drm-intel-experimental`, Mesa 26.1, guest Linux 6.14 or later), in the Linux session on the Lenovo.
* D3. Vulkan. Chat: kernel side now, lavapipe, Venus and hasvk in the stack. Fable: lavapipe and Venus in, hasvk as a measured task, DXVK tried once. Codex: lavapipe and Venus as research, no hardware Vulkan promise. Proposed: the kernel side now (timeline syncobjs, sync_file import and export, blob, context init, host-visible memory); lavapipe in the desktop; Venus in QEMU and on the bed; hasvk a task with a measured result and no product promise; DXVK and vkd3d never a dependency. This changes the owner's decision 5.
* D4. Milestones: chat 8, Fable 7, Codex 11. Proposed: milestones shaped by what a user sees, as AGENTS.md asks ("the goal as a user sees it"): Codex's R0 evidence and G1 contracts become the first tasks of the desktop and games milestones; virtio-gpu 3D stays its own milestone so that it releases without the Lenovo; 8 in all.
* D5. Trial root image on the data partition (fable.md:176): unreleased userland tested on the Lenovo without touching the installed system. Proposed: adopt; it is the owner's rule to change (decision 14).
* D6. Wine's 32-bit starter: adopt `PROTON_USE_WOW64` (codex.md:199-200, `S/proton/proton:528-536`) instead of deleting a file; check the pinned GE-Proton.
* D7. umu and the Steam runtime: Codex says support the standard outside-Steam route; the earlier rounds put GE-Proton run directly first. Proposed: direct first; umu-launcher with the Steam Linux Runtime a task with a measured result (it needs user namespaces and bubblewrap).
* D8. Performance gate: Codex 10% from matched Linux; Fable and chat a ratio set later. Proposed: Codex's 10% on the fixed GL workload set, ratified by the owner after the Linux reference numbers; Crysis keeps the owner's criterion.
* D9. Return of the IGD after the VM dies: Fable promises FLR and a new mode set; Codex accepts a required reboot if FLR fails. Proposed: the Linux session tests FLR and rebind first; Done takes the return without a reboot if Linux manages it, and names the reboot with evidence if not.
* D10. Codex additions the others lack, proposed adopted whole: the security limit of the shared GPU address space stated in the documents; the wider browser acceptance (HTTPS, storage, downloads, uploads, clipboard, fonts, GPU-process restart); the fake GPU renamed an ABI and fault backend; userptr only with its invalidation rules.

## Facts added after the argument round started (00:2x)

* F8. Debian trixie's virglrenderer 1.1.0 is built with `-Dvenus=true` (https://sources.debian.org/src/virglrenderer/1.1.0-2/debian/rules/), so Venus in QEMU needs no private build. Forky's 1.3.0 has Venus but no DRM native-context renderer (no `drm-renderers` option in its rules).
* F9. trixie-backports has Mesa 26.1.6 and QEMU 11.1.2 (packages.debian.org); forky has virglrenderer 1.3.0. The native-context check therefore needs only virglrenderer built from source with its Intel option; Mesa and QEMU come as Debian binaries.
* F10. Rach2 has user namespaces, unshare, setns, eventfd2 and pidfd_open (`rach2/sys/proc/ns.c:71`, `rach2/sys/arch/x86_64/systab.c:349-387`), which umu's container and the transport's doorbells use.
* F11. Debian's `qemu-system-common` ships no ivshmem-server; the protocol is QEMU's documented one, so Rach2 runs a small server of its own.

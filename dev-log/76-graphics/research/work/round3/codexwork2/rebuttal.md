## 3. Open questions

### Q1. Crocus relocations and the Intel server

Mesa 26.1 has an explicit relocation-carrying path. Crocus's submit_batch constructs EXECBUFFER2 with I915_EXEC_HANDLE_LUT, I915_EXEC_BATCH_FIRST and I915_EXEC_NO_RELOC, while retaining command and state relocation arrays. NO_RELOC is a presumed-offset optimization; it is not EXEC_OBJECT_PINNED or proof that softpin is required. Evidence: [Crocus batch submission at Mesa 26.1](https://github.com/chaotic-cx/mesa-mirror/blob/mesa-26.1.0/src/gallium/drivers/crocus/crocus_batch.c#L824).

The client helper copies the exec-object array, appends every object's relocation entries, translates object handles to virtio resource IDs, records the total relocation count, and submits I915_CCMD_GEM_EXECBUFFER2 through vdrm_execbuf. HANDLE_LUT makes relocation targets indices into that same object array, so they survive the object-handle translation. Fence arrays and timeline points become virtgpu input/output syncobjs. Evidence: [Mesa's execbuffer transport](https://github.com/chaotic-cx/mesa-mirror/blob/mesa-26.1.0/src/intel/dev/virtio/i915_virtio_ccmd_execbuf.c) and [wire structures](https://github.com/chaotic-cx/mesa-mirror/blob/mesa-26.1.0/src/intel/dev/virtio/i915_proto.h).

The server checks the request and array lengths, copies the payload, resolves resource IDs to its Linux GEM handles, rebuilds relocs_ptr values as local addresses, and calls DRM_IOCTL_I915_GEM_EXECBUFFER2_WR. Linux i915 performs the real relocation and command-validation work. The returned fence fd drives the renderer timeline. The server does not impose a softpin-only submission contract. This path needs Crocus and the virtual-device interface on Rach2, not a second hardware i915 submission driver or duplicate Haswell command parser there. Evidence: [upstream-origin i915 implementation](https://github.com/arehnman/virglrenderer/blob/5295b403fcd399752b5be94ddb5e5f880fa7102c/src/drm/i915/i915_ccmd.c).

The common dispatcher selects the kernel driver named i915; i915_renderer_probe records PCI identity and wire-format version without a GPU-generation allowlist. Thus the inspected code accepts an i915 Haswell device into the probe path; it does not reject everything before Tiger Lake. That is not a claim of validated Haswell rendering. Evidence: [renderer dispatcher](https://github.com/arehnman/virglrenderer/blob/5295b403fcd399752b5be94ddb5e5f880fa7102c/src/drm/drm_renderer.c) and [i915 probe](https://github.com/arehnman/virglrenderer/blob/5295b403fcd399752b5be94ddb5e5f880fa7102c/src/drm/i915/i915_renderer.c).

The virglrenderer files were read through a fork that preserves upstream history. The cited [introducing commit](https://github.com/arehnman/virglrenderer/commit/5295b403fcd399752b5be94ddb5e5f880fa7102c) names upstream merge request 1384, and the inspected file history contains no later change to i915_ccmd.c. Its [Meson options](https://github.com/arehnman/virglrenderer/blob/5295b403fcd399752b5be94ddb5e5f880fa7102c/meson_options.txt) use drm-renderers=i915-experimental. Do not describe a tested-generation note from an earlier proposal as a restriction in this code.

One remaining qualification is relocation feedback and pressure behavior. The Mesa helper submits asynchronously and does not copy changed object offsets or presumed offsets back into Crocus's original arrays. That does not establish a rendering bug, because the server kernel can relocate the shared batches, but it makes allocation pressure, rebinding, repeated submissions and fence/error behavior necessary parts of the Haswell check. Capset enumeration and one triangle should be the entry check, followed by those cases before publishing performance or compatibility claims.

### Q2. Separate-process GPU backends and SHMEM_MAP

Separate-process backends with blobs, context init and Venus exist. That does not mean Debian's unchanged QEMU 10 GPU frontend can use them. There are three distinct components: the virtio-gpu frontend in the VMM, the external device backend, and the renderer library or render-server process.

* QEMU's contrib/vhost-user-gpu daemon remains a virgl baseline. Its command switch has no CREATE_BLOB, MAP_BLOB or UNMAP_BLOB handlers; context creation uses the older virgl_renderer_context_create interface, and capset enumeration offers VIRGL and VIRGL2. This part of F4 is correct. Evidence: [contrib daemon at inspected QEMU head](https://github.com/qemu/qemu/blob/a3565937b39779d4e3704298095f566e7559ad53/contrib/vhost-user-gpu/virgl.c).
* rust-vmm's published vhost-device-gpu 0.2.0 still documents no blobs or Venus, as did 0.1.0. The inspected main branch is different, despite its Cargo.toml still saying 0.2.0. It advertises RESOURCE_BLOB and CONTEXT_INIT, dispatches create/map/unmap, enables Venus and its render server, and sends SHMEM_MAP/UNMAP with a file descriptor through the backend-request channel. SET_SCANOUT_BLOB remains unsupported, and opaque-fd mapping is rejected. Thus a source revision with this work is a candidate; installing the released crate is not enough. Evidence: [published crate](https://docs.rs/crate/vhost-device-gpu/0.2.0), [device implementation](https://github.com/rust-vmm/vhost-device/blob/79bccc0ee2a071a21e8070d0dd98114cd053f761/vhost-device-gpu/src/device.rs), [renderer adapter](https://github.com/rust-vmm/vhost-device/blob/79bccc0ee2a071a21e8070d0dd98114cd053f761/vhost-device-gpu/src/backend/virgl.rs) and [mapping helper](https://github.com/rust-vmm/vhost-device/blob/79bccc0ee2a071a21e8070d0dd98114cd053f761/vhost-device-gpu/src/backend/common.rs).
* crosvm's GPU device can run as a separate vhost-user backend. Its GpuBackend forwards the common GPU feature set and negotiates SHMEM; the common GPU implementation dispatches blob operations and context_init to rutabaga. Its builder exposes Vulkan and render-server configuration for the virglrenderer/Venus path; Venus is not enabled merely by starting the default device. The standalone launcher accepts GPU parameters and forces external_blob for descriptor sharing. SharedMemoryMapper sends backend mapping requests with descriptors. Pin crosvm and its renderer dependencies together; its display and vhost-user extensions are not automatically interchangeable with every QEMU GPU frontend. Evidence: [standalone GPU backend](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/vhost_user_backend/gpu.rs), [launcher configuration](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/vhost_user_backend/gpu/sys/linux.rs#L257), [common GPU and renderer setup](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/gpu/mod.rs#L927), [resource mapping](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/gpu/virtio_gpu.rs) and [vhost-user mapping adapter](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/vhost_user_backend/handler.rs).

The QEMU version boundary is narrower than "QEMU 11 supports it":

* In the inspected v10.0.0, v10.0.13 and v11.0.0 core implementations, SHMEM_MAP/UNMAP and GET_SHMEM_CONFIG are absent. [QEMU 10.0.13 core](https://github.com/qemu/qemu/blob/v10.0.13/hw/virtio/vhost-user.c), [QEMU 11.0 core](https://github.com/qemu/qemu/blob/v11.0.0/hw/virtio/vhost-user.c).
* QEMU v11.1.0 implements GET_SHMEM_CONFIG and backend SHMEM_MAP/UNMAP. It maps backend-supplied fd ranges into registered VirtIO shared-memory regions and checks bounds and overlap. This is the common transport facility. [QEMU 11.1 core](https://github.com/qemu/qemu/blob/v11.1.0/hw/virtio/vhost-user.c#L1917).
* The GPU frontend is a separate missing step. In v11.1.0, v11.1.3 and the inspected current head it still does not forward RESOURCE_BLOB or CONTEXT_INIT and does not register the needed shared-memory region. The proposed patch series adds precisely these pieces, plus a mapping-transaction deadlock fix. Do not treat successful patch application in an archive as an upstream merge. [QEMU 11.1.3 GPU frontend](https://github.com/qemu/qemu/blob/v11.1.3/hw/display/vhost-user-gpu.c), [inspected head](https://github.com/qemu/qemu/blob/a3565937b39779d4e3704298095f566e7559ad53/hw/display/vhost-user-gpu.c), [GPU frontend patch series](https://patchew.org/QEMU/20260717134920.265128-1-dbassey%40redhat.com/).

QEMU's display-side vhost-user-gpu protocol describes cursor and scanout exchange. Its short command list does not bound the rendering commands carried in the virtqueues, and cannot by itself prove that all vhost-user backends lack Venus. The reverse service VM would use its own adapter as the frontend to an unchanged guest-local backend; outer QEMU's vhost-user-gpu frontend is not in that path. The resource-mapping problem below still has to be solved.

### Q3. Reverse transport with unchanged QEMU 10.0

Use ivshmem-doorbell as the existing carrier. It already includes the shared-memory BAR and notifications. ivshmem-plain is sufficient for the first polling experiment, but is not an additional device that has to be combined with doorbell. Keep QEMU unchanged; add a Rach2 protocol peer and kernel binding, a Linux guest endpoint, and the virtio transport control layer. This recommendation follows the [QEMU 10 ivshmem specification](https://github.com/qemu/qemu/blob/v10.0.0/docs/specs/ivshmem-spec.rst), not a new QEMU device model.

The two ends are different. Linux inside the service VM sees the emulated PCI device: BAR0 registers, BAR1 MSI-X state, and BAR2 shared memory. Rach2, which hosts QEMU, has the backing file and eventfds. It has no corresponding physical PCI function and receives no hardware interrupt from this virtual device. A host driver cannot use the guest's BAR address or a guest file-descriptor number.

The ivshmem-server protocol is a local Unix socket protocol. It sends signed little-endian 64-bit messages: version 0, the client's ID, -1 with the shared-memory fd, then peer IDs with eventfds, one descriptor per vector. The client's own ID accompanies its receive eventfds; other IDs accompany send eventfds. A later peer-ID message without a descriptor announces disconnection. SCM_RIGHTS transfers these references between processes under Rach2, including QEMU; none crosses into Linux as a descriptor. A small Rach2 helper can be the server and host endpoint, or the server can have a separate host peer. Start from the contributed [ivshmem-server](https://github.com/qemu/qemu/blob/v10.0.0/contrib/ivshmem-server/ivshmem-server.c) and [ivshmem-client](https://github.com/qemu/qemu/blob/v10.0.0/contrib/ivshmem-client/ivshmem-client.c) implementations: the latter already handles peer descriptors, eventfd notification and a receive callback. Add bounded parsing, disconnect handling and the project resource policy. The helper passes validated file references to the kernel through a narrow local ioctl; that kernel binding is new work.

The notification flow is precise:

* Rach2 publishes a command with the virtqueue's required memory ordering and signals the eventfd for the Linux guest's peer/vector. QEMU converts that event to an MSI-X notification. The guest's PCI driver handles it and wakes the backend or signals its guest-local kick eventfd.
* Linux publishes the used entries, then writes BAR0 offset 12 with `(host_peer_id << 16) | vector`. QEMU writes the host peer's eventfd. A Rach2 wait or kernel eventfd callback drains that counter and processes completions. The transport must implement and retain those eventfd references; the existence of eventfd2 alone does not implement a kernel callback.
* Queue indices remain the source of truth. Notifications can be coalesced and are wake-up hints, not one event per command. The polling version polls queues. Revision 1 does not provide the legacy INTx mask/status mechanism as an alternative to MSI-X.

This uses QEMU's existing MMIO doorbell handling and eventfd integration. ioeventfd and irqfd can accelerate it when available; no invented I/O port is required. Agree a small fixed vector set, for example 0 and 1, since the inspected MMIO handler masks the vector to eight bits. Evidence: [QEMU 10 ivshmem device](https://github.com/qemu/qemu/blob/v10.0.0/hw/misc/ivshmem-pci.c#L172).

The transport control area must identify roles, peer IDs, a version and a connection epoch; IDs can be reused after disconnection. It must provide virtio feature negotiation, status/reset, configuration, queue setup and failure notification. Validate each descriptor chain, offset, length and indirect table against registered memory, and bound outstanding work and resource memory. On disconnect, fail pending fences, revoke mappings and retire the old epoch before reuse. Keep generation bookkeeping in the transport and object tables; do not insert private fields into standard virtio_gpu command structures. This is the exact replacement for my earlier loosely specified envelope and for D1's "generation-tagged ids."

There are two reasonable Linux implementations. First evaluate an ivshmem adapter that acts as the frontend of a pinned crosvm or rust-vmm vhost-user GPU backend within the same Linux guest. It must export a restricted shared-pool mapping through a Linux-local fd and translate guest-local kick/call eventfds to the ivshmem notifications. It must also implement the backend's shared-memory mapping requests. This is new adapter work, not transparent forwarding of host fd numbers. If that adapter or the required native-context capset is not supported cleanly, a small virtio-gpu backend around libvirglrenderer is the fallback. Reuse existing command handlers and renderer APIs in either case. Q2 supplies evidence for the existing backends; it does not establish their complete Intel-native configuration.

Blob memory is the separate proof. The fixed ivshmem file supplies queue and guest-backed transfer storage. A renderer-owned host-visible blob is an allocation in the Linux service VM, possibly exported as a dma-buf; its fd is neither an ivshmem offset nor automatically a contiguous part of QEMU's RAM mapping. A generic DMA buffer can involve different page layouts and cache attributes. Copying bytes can serve the initial virgl/readback experiment, but does not implement coherent Vulkan mapped memory. The need for distinct mapping machinery is visible in [crosvm's blob mapper](https://github.com/google/crosvm/blob/3ec8c847128f81010ec6b004fd193332fb7c03dc/devices/src/virtio/gpu/virtio_gpu.rs#L1167), which distinguishes fd-backed and opaque Vulkan memory, and in the SHMEM_MAP path discussed in Q2.

Choose and prove one mapping mechanism before advertising the feature: either a supported allocator/import path backed by the shared pool, or a guest helper that pins exportable pages and a Rach2 broker that maps only validated pages from registered VM RAM. The latter needs page references, cache-mode checks, DMA/IOMMU ownership, fence ordering and revocation on object release, VM termination and memslot changes. It must reject non-exportable GPU apertures and unsupported opaque handles. Demonstrate CPU-to-GPU and GPU-to-CPU visibility on a real blob, then release and kill the VM while mappings and submissions are live. This is a design requirement, not a claim that the helper or allocator already exists. It preserves unchanged QEMU as the carrier.

The guest presenter also needs a defined control path for physical connector modes, refresh, hotplug and recovery. A virtio-gpu scanout rectangle alone does not request a physical KMS mode. The guest owns KMS while it owns the IGD; its presenter imports or copies the composed resource using the chosen, measured path. The host compositor and applications remain on Rach2.

The alternatives do not improve the fixed-QEMU-10 starting point:

* virtio-msg preserves the desired queues and supplies a useful configuration model, but its bus binding still has to define sharing and notifications. Its published account describes prototypes and an evolving specification. Follow or reuse the relevant draft structures where suitable, pin the revision, and call the ivshmem binding a project transport until conformance is established. Evidence: the Linaro design account cited in F5.
* virtio-vhost-user addresses the direction directly: a vhost-user backend inside a VM. The [QEMU proposal](https://lists.nongnu.org/archive/html/qemu-devel/2022-05/msg03884.html) adds virtio-vhost-user.c and a new PCI device, but those entries are absent from [QEMU 10's virtio build list](https://github.com/qemu/qemu/blob/v10.0.0/hw/virtio/meson.build). It is useful prior art, not a device the unchanged binary can instantiate.
* vhost-user alone is a process interface using same-kernel shared fds. vsock, virtio-serial or TCP can carry control or copied pixels, but do not carry those descriptor objects across kernels and do not solve blob mappings. Use them for a diagnostic channel if useful; they do not replace the memory mechanism above.

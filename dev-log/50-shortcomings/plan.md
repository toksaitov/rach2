# Milestone 50: the machine and the shortcomings

## The goal

Put the system of milestones 45 through 49 on the Lenovo, in one sitting of the owner's, and fix every previously known problem, every problem recorded during those milestones, and everything the machine shows. Milestones 45 through 49 prove their work in QEMU and do not touch the machine, so this milestone is the first run on the Lenovo of the new kernel, the disk registry, the AHCI interrupt path, the per-controller USB stack, the installer and the stick. The list of shortcomings is written as the work goes: an entry the day the problem is found, and nothing is deferred past this milestone. The manuals and the audit follow it, so that what they describe is the finished system and not one with known defects; an entry made during those two reopens the technical work before the document that describes it is accepted. The milestone is complete when the Lenovo runs the installed system with every device it had before, the twenty-session load has run on it for an hour, every entry is marked fixed with its proof, and the close below has run.

## What the tree settles before this plan

* The stick behind the SuperSpeed hub stopped answering and its removal panicked the kernel once; the record leaves the reset-and-removal sequence with stale completions open (`dev-log/43-machine/notes.md:291`). A healthy stick pulled is not the same test.
* Milestone 44 needed four full runs to get one clean, and records the failures as pooled execution (`dev-log/44-krffsmount/notes.md:412`). A successful rerun does not explain the earlier failure. Diagnose the kernel, harness and scheduling before closing the entry.
* The Lenovo's disk is 488397168 sectors of 512 bytes on SATA, internal, and does not leave its bay (`dev-log/43-machine/hardware.md:43`). It has the sealed layout: a 64 MiB boot partition, the 500 MiB KRFFS fallback root, the 64 MiB recovery partition, and a fourth entry of 2 GiB with the 1 GiB ext2 root in it; the rest is unused. It has one xHCI controller and an EHCI the kernel names (`hardware.md:41`).
* Milestone 43's recovery stick, with its older kernel and its own host key, boots the machine today (`hardware.md:121`). That recovery repairs every ext2 partition it finds during its own boot (`utils/init.c:200`, the call at `:243`), has `reflash` and no `rach2-recover`, and is not changed by this milestone.
* The Lenovo's USB sockets are the right black, the left black and the left blue, with the hub on the blue one (`hardware.md:131`).
* The metal acceptance writes a file to the first USB disk it finds with a FAT or exFAT volume (`tests/system/accept/metal_accept.sh:500`, the write at `:527`). It would write to a recovery stick's image half.
* The hardware rule in `CLAUDE.md`: a write that cannot be undone by rebuilding needs the owner's approval at the time, with the device shown; before a write to the Lenovo's disk that is not a kernel through `bootctl`, a stick with recovery is booted and shown to work, every sector about to be overwritten is saved on the host and on that stick, and recovery is the saved boot default until the write is verified.
* Milestone 49's installer prints the device, asks for its name typed back, and prepares the image with recovery as its saved default. Its save set is the image's extent and the block ranges the grow writes into the groups it adds, computed by milestone 47's tool from the new image's superblock, the root's offset on the target and the target's size. Its phase 5 rehearses this milestone's sitting in QEMU on a disk of the Lenovo's size and layout, with the restore made through `rach2-recover` and through the older recovery's `reflash`.
* Milestone 24's boot switches skip individual device probes, milestone 47 keeps a boot option for polled AHCI, milestone 46's kernel prints its memory map at boot, and netconsole sends the kernel log as frames the host captures before SSH is up.

## Entries

An entry has: a date; the milestone that found it; its severity, with a loss of data or a panic first; how to reproduce it; the contract it breaks, with file and line; what it depends on; the test that will show it fixed; and, once done, the commit and the proof. The two above are the first entries, numbered 1 and 2, and the list is worked in order of severity and dependency, not of the code it touches. What the machine shows in the sitting is entered the same way and worked in phase 4.

An entry is fixed when its test passes in QEMU and its review has run. A fix made after the sitting reaches the Lenovo in milestone 52's sitting, which is that milestone's deployment, and the entry says so; a kernel fix may go on earlier through `bootctl` over SSH when the machine is on and the owner approves that write, and this is never required. The documents may be written once every entry is fixed. A fix without which the machine does not run at all calls the owner again with the same preparation as the sitting, and the report says that it did.

1. The stopped stick: reproduce the never-answering reset and the removal with completions still pending, in QEMU with a stick that stops answering, and fix what the kernel does with the stale completions.
2. The pooled runs: find why a suite that passes alone fails in the pool, which is milestone 52's scheduling work brought forward as far as the cause requires. A further instance from milestone 45's close (2026-09-06): in the second full set, `tests/run selfbuild-ext2` failed in the pool with `the built kernel was never set aside for extraction`; its console log shows the line the harness typed, `cp build/rach2/kernel ...`, arriving at the guest's shell as `uild/rach2/kernel ...`, its first characters lost while the machine was still busy with the build. Console input dropped under load is a kernel matter, the serial receive path, and not the harness's; the suite passed alone afterwards. A third instance from milestone 46's close (2026-09-06): `musl/pwauthmusl` in `default-e1000` timed out waiting ten seconds for the session leader's report after a continue, twice in pooled sets, and passed alone and in `default` in the same sets.
3. The acceptance's stick: the metal acceptance takes the stick it writes by identity from its arguments and refuses a stick that contains a Rach2 recovery ISO; proved in QEMU with three sticks plugged, two of them recovery sticks, and by the mutation that drops the refusal.
4. The clean tree's preparation (2026-09-06, milestone 45; severity: a wrong result, no data lost): with `build/` removed, `tests/run host` stops in `prepare-all` with `No rule to make target build/utils/ping, needed by build/images/os-real.krffs`. The image rules take the products a manifest stages as ordinary prerequisites (`Makefile:435`, through `krffs/manifest_deps.sh`), and no rule makes such a file on its own: the component that builds it is an order-only prerequisite of the same rule, which make does not consult for a missing ordinary one. On a tree where the file exists the rule works, which is why `make` and then `tests/run all` passes and the runner alone does not. It breaks the runner's claim that `prepare-all` builds the product from whatever state the tree is in (`tests/system/suites.mk:9`). Depends on nothing. Fixed when `rm -rf build && tests/run host` passes, and when a mutation that removes the component from the rule's order-only list fails it again. Milestone 45's runner builds the components in a make of their own before the images (`7eb1108`), so the runner's claim holds again: on 2026-09-06 `tests/run all` from a removed `build/` built everything and ran. The rule itself is entry 5's.
5. The clean tree's `make -j` (2026-09-06, milestone 45; severity: a wrong result, no data lost): with `build/` removed, `make -j` stops in its first second with `No rule to make target build/tests, needed by build/images/test.krffs`, while `make` without `-j` builds everything, because `all` names the components before the images and a serial make meets them in that order. The cause is entry 4's: `krffs/manifest_deps.sh` prints every staged path as an ordinary prerequisite of the image rule (`Makefile:416` for the test image) whether or not the file exists, and make has no rule for a file that is not there. It breaks the Readme's claim that `make` builds everything, for the `-j` form. Depends on nothing. Fixed when `rm -rf build && make -j` passes, and when a staged program rebuilt on a built tree still restages its image, since the fix must not lose entry 4's rebuild; a mutation that touches a probe and finds the test image unchanged fails it. Seen again on 2026-09-07 in milestone 47's close, and the serial form fails now as well: `rm -rf build && make` stops at `No rule to make target build/tests, needed by build/images/test.krffs`, since the test manifest stages `build/tests` as an `exec-dir` and the directory is an ordinary prerequisite with no rule. The close was run through `rm -rf build && tests/run all`, whose `prepare-all` builds the components in a make of their own first, as milestone 46's close was.
6. A process always inside a system call starves the rest (2026-09-06, milestone 46; severity: the machine stops answering, no data lost): a process that writes a file on a polled disk in a loop, `loadprobe Wn` on a FAT32 or KRFFS volume of the IDE disk in QEMU, keeps the processor for as long as it runs. The timer preempts a process in user mode only, and the kernel's exit from a system call never reschedules (`rach2/sys/isr.c`, the `_irq_router` comment), so a process that returns to user mode for an instruction between two calls is preempted only when the tick lands in that instruction; a parent sleeping twenty seconds beside it never runs, and the console does not answer. The lag device hides it, since each write sleeps in a request. It breaks the scheduler Readme's claim of round-robin scheduling among the runnable. Depends on nothing; milestone 47's SATA through the request layer makes the writer sleep but does not change the rule. Fixed when a reschedule requested by the tick is taken at the system call's exit and `tests/run load` passes with its writers' ten-millisecond pause removed; a mutation that drops the exit-path reschedule fails it.
7. The raw windows' one staging buffer (2026-09-06, milestone 47; severity: a slow result, no data lost; fixed there): every raw transfer staged through one 32 KiB buffer in `rach2/sys/fs/devfs.c`, taken in turn, so two processes reading two disks through their nodes ran one after the other, each holding the buffer across its sleep on its device; with the AHCI disks on their interrupts the queue suite's fast reader waited the slow disk's whole read. Fixed in milestone 47's driver phase: a transfer stages through pages of its own from the heap and the static buffer is the fallback when the heap has none; `tests/run queue` shows it, the fast reader finishing in tens of milliseconds beside a throttled disk.
8. A partition view kept its backing's flags from when it was cut (2026-09-06, milestone 47; severity: a wrong result, no data lost; fixed there): `block_partition_init` copied `flags` and `submit` at the cut (`rach2/sys/block/block.c`), so a view cut at boot over a polled disk kept `BLOCK_FAULT_SAFE` after the disk went over to its interrupts and every transfer through the view stayed polled, holding the processor. Fixed in milestone 47's driver phase: `block_flags` reads the backing's flags when asked and a view always forwards `submit`; `tests/run queue` shows it.
9. The sparse_super rule took products for powers (2026-09-06, milestone 47; severity: a wrong result, no data lost; fixed there): `has_super` in `rach2/sys/fs/ext2.c` divided a group number by 3, 5 and 7 in turn and called the group a backup when 1 was left, so group 15, 21 and 35 were taken to hold a superblock copy that mke2fs never wrote there, and the mount's descriptor check refused every ext2 volume of sixteen groups or more, 2 GiB at 4 KiB blocks, with `refused: group descriptor`; the same rule was in `tools/inspect/setidcheck.c`. The sealed root is eight groups, which is why nothing had shown it. It broke the ext2 Readme's claim that a volume the profile allows mounts. Fixed in milestone 47's file phase, since the 5 GiB file row cannot run without it: a group is a backup when it is a power of one of the three bases alone; `tests/run large` mounts a 6 GiB volume and `tests/run grow` a 931 GiB one.
10. The disk path moved one page per request (2026-09-07, milestone 47; severity: a slow result, no data lost; fixed there): a sleeping device took one request of at most a page (`rach2/sys/block/request.c`, `req_run_one`), the buffer cache wrote and filled one 4 KiB block per request, each a sleep until the completion, and found a block by walking its whole list, thousands of buffers on a machine with memory, so a file written through ext2 on the AHCI disk in QEMU went at 4 MiB/s and through exFAT at 1 MiB/s, and `tests/run large` at 5 GiB took hours. It broke no stated contract; it made the full tier take hours. Fixed in milestone 47's file phase, since every later run and sitting paid for it: a request moves up to the device's `max_sectors`, 64 on AHCI, in heap pages the command table describes page by page; the cache's sync writes a run of adjacent dirty blocks in one request through a staging buffer; the cache finds a block through an index by device and block; an ext2 write marks its bitmap bytes, descriptors and pointer slots dirty and writes them at its end, the bitmaps and descriptors first, instead of writing each through per block. Measured after: ext2 8 MiB/s, exFAT 10 MiB/s on the same 1 GiB write. What remains, for a later milestone: the cache still walks its list once for the hold rule and once for the victim on every take, and a read fills one block at a time; the polled IDE channel's port I/O stays at 2 MiB/s.
11. A disk with 4096-byte sectors is refused, not served (2026-09-07, milestone 47; severity: a refusal by name, no data lost): the block layer, the partition parser, the raw windows and the file systems count in 512-byte sectors, so the IDE and AHCI drivers refuse a drive whose IDENTIFY word 106 says its logical sector is not 512 bytes, by name, and publish no node; `tests/run bus` shows both refusals. Milestone 47's plan allows the restriction while it is reported and not hidden. It breaks the plan's aim that the sector size is the disk's. Depends on nothing. QEMU cannot present such a drive to either driver: `ide-hd`, which serves both the IDE channels and the AHCI ports, takes `logical_block_size=4096` only with a discard granularity that is a multiple of it, and then refuses any granularity but 512, so the row this milestone wrote was removed and the refusal is unproved in QEMU. Fixed when a machine that can present a 4096-byte-sector disk mounts and checks one, and the MBR limit for that sector size is documented; a mutation that keeps a 512-byte sector count fails it. The refusal itself is `rach2/sys/block/ata.c` and `ahci.c`, both reading IDENTIFY word 106.
12. The kernel does not boot on 8 MiB (2026-09-07, milestone 47; severity: a crash at boot, no data lost): the recovery kernel and image on a QEMU machine with `-m 8` stop in `panic: stopped: Unrecoverable error: page fault while in kernel mode` before the login; at 16 MiB they boot and grow a root. A machine too small should be refused by name in the memory manager's first report, not faulted in. It breaks no stated contract; the smallest memory the Readme names is what `tests/run memory` runs. Depends on nothing. Fixed when a boot at 8 MiB prints the refusal and stops; a mutation that removes the check faults again.
13. An exFAT append walked the chain from its first cluster (2026-09-07, milestone 47; severity: a slow result, no data lost; fixed there): `ex_write` cleared the node's chain hint after every write (`rach2/sys/fs/exfat.c`), so the next append's walk to the tail started at the first cluster, one FAT read per cluster of the file, and a file written in 1 MiB pieces took longer with each piece: the fourth gibibyte of a 5 GiB write took more than thirty minutes where the first took fifteen, and the harness cut it. It broke the exFAT Readme's claim of a bounded walk per operation in effect, since the bound was the file's length. Fixed in milestone 47's file phase, since the 5 GiB row cannot run without it: the hint is kept across an append, which changes no cluster the chain had; `tests/run large` at `RACH2_LARGE_MIB=5120` shows it.
14. A request slow past five seconds fails the mount (2026-09-07, milestone 47; severity: a wrong result, no data lost): a request that a sleeping device has not answered in five seconds is quarantined and, with every slot of the device past its deadline, the device is declared stalled (`rach2/sys/block/request.c`, `REQ_DEFAULT_DEADLINE`), the write fails with `EIO`, the buffer stays dirty and the file system turns the mount read-only: `block: request deadline: 1 slots quarantined`, `block: device stalled`, `vfs: read-only: /big`. In QEMU on a host busy with a second machine's disk the answer came late, not never, and the volume was lost to the run; a disk that answers late is not a disk that went away. It breaks the block Readme's claim that a slow device is waited for. Depends on nothing. Fixed when a late completion of a quarantined request is taken as the answer and the mount keeps writing, with the stall declared only after a bounded number of deadlines in a row; `tests/run queue` with a disk throttled below one request in five seconds shows it, and a mutation that fails the request at the first deadline fails the row.
15. A KRFFS node could not be made where its id fell astride two units (2026-09-07, milestone 47; severity: a wrong result, no data lost; fixed there): `krffs_put` refuses a field whose changed bytes reach the medium in two units, the rule that keeps a reader from seeing half of a live field, and applied it to the id and the parent of a node being created, which no path reaches until its name is written last; so a create whose free node happened to place the 64-bit id across a 4 KiB boundary failed with `refused: a field at N would reach the medium in two pieces`, and `tests/run mount` failed its dirty row once the staged probes' sizes moved the volume's free space there. Fixed in milestone 47's file phase: the id and the parent of a node being made, and of a copy being filled before it is linked, are written without the rule. What remains: a rename in place changes a live node's id under the rule and can be refused by the same layout; `tests/run krffsmount` shows the create.
16. The network does not come up on a warm restart (2026-09-07, milestone 47; severity: the machine is unreachable after a reboot, no data lost): in `tests/run sealed` the first boot of the sealed disk gets its lease and answers SSH, and the second boot, made by `sync; reboot -f` sent over SSH inside the same QEMU, prints `init: network: ifup -a did not configure the interface` with nothing at all from `udhcpc`, so the machine comes back to its login prompt and never answers SSH again; the console log of the run of 2026-09-07 shows `udhcpc: lease of 192.168.0.15 obtained` on the first boot and no `udhcpc` line on the second. The same reboot done by hand at the console, with the same network device, does get its lease, so what differs is the reboot arriving over SSH while dropbear holds the connection. `tests/run drill`, `drill-ext2` and `metal` also failed in the same set and also reboot; whether they share this cause is unverified. It breaks the Readme's claim that the installed machine is reached over SSH after a reboot. Depends on nothing. Fixed when `tests/run sealed` passes its second and third boots; a mutation that skips the network device's reset on a warm start fails it.

## Decisions

### The code is reviewed before the machine is written

The installer, the kernel and the recovery image this milestone's fixes changed are what the sitting writes with, and `CLAUDE.md` puts a destructive write after the review of the code that performs it. So the review of phases 1 and 2 runs in full before the sitting: build from clean, the full set, the Codex review, every finding fixed, the full set again. The fixes made after the sitting are reviewed once, as one batch, at the close.

### The owner is called once, with everything ready

Before the owner is called, the following are done and recorded in `notes.md`:

* The reviewed kernel and images built, their hashes recorded, and the stick image booted in QEMU.
* The save-set tool run against the Lenovo's recorded geometry: its ranges, their total bytes, and the new stick's free space recorded; milestone 49's rehearsal run again against that manifest.
* The restore commands written out twice, for `rach2-recover` on the new stick and for `reflash` on milestone 43's stick.
* The third stick's layout decided, one exFAT volume labelled `RACH2TEST` over the whole stick, written in the sitting's first step; the pull test's read command, a `dd` of the whole stick to nowhere over SSH; its readiness signal, the first 64 MiB reported by the host; and its deadline, the removal reported by the kernel within one minute of the pull.
* Every answer the installer asks for prepared: the account name and the key in `notes.md`, the passwords in the credential file on the host that the acceptance reads.
* The sitting's commands in order, with what each shows, what the owner is asked, the observable condition for each physical action, and which boot switch answers which symptom.

Nothing in the sitting is discovered on the day. A step that turns out to need something not prepared stops the sitting with the disk untouched or restored, and the owner is called again only after the gap is closed.

### The install replaces the grow

Milestone 47 proved `growroot` in QEMU. The Lenovo does not get its root grown in place; the installer writes the sealed image and grows the ext2 root into the free space of the disk, as milestone 49 decided. The saved set is what the installer writes: the image's extent and the growth ranges from the tool. The rest of the disk is not written and is not saved.

### A known-working recovery path stays outside the change

Milestone 43's stick is kept as it is. If the new stick fails to boot, or fails after the disk has been written, the older stick boots and its `reflash` puts the saved set back. Its boot-time repair may write into a damaged root before the restore runs; the restore rewrites every sector of the set, and the sectors outside the set were unused before the install, so the repair changes nothing the restore does not overwrite. Milestone 49's rehearsal proves this path with a recovery ISO built at the commit milestone 43 installed. The new stick is a second stick, and the acceptance and the pull test use a third stick that carries nothing; milestone 43's stick is not written at all, and the new stick's boot image is not written after its preparation; the save goes to the new stick's data volume.

### The pull test is the removal half of entry 1

There is no way to make a physical stick stop answering on demand. On the Lenovo the third stick is read over SSH from the host, and while the read runs the owner pulls it when the host says so; the kernel must report the removal, keep running, and take the stick back when it is plugged in again. The never-answering half is proved in QEMU by entry 1.

### What the owner does

At the desk, at the start: approves the write of the new stick and the formatting of the third, naming each as the host reports it, and plugs both into the notebook. At the notebook, at the start: powers it on, plugs in the keyboard, mouse, hub, card and the third stick as milestone 43 had them, and chooses the new stick as the boot device when asked. At the desk: approves each later write by naming the device the installer or the host reports, including the change of the saved boot default. At the notebook, once: types the target disk's name into the installer and the prepared answers. At the notebook, once more: pulls the third stick when the host says so and plugs it back. At the notebook, last: moves the keyboard and then the mouse through each of the three sockets and the hub, typing a line and moving the pointer at each, with the host reading what arrived. The owner's part ends before the load runs.

## Phases

### Phase 1: the fixes

The entries recorded so far, in order of severity, each with the smallest suite that covers it and a mutation for any new check.

### Phase 2: the review before the machine

Once and in this order: build from clean; the full set; everything that comes up fixed; the whole milestone's diff so far to Codex in units of six files, most serious first; every finding fixed; the full set again. Then the preparation the decision above lists, ending with the rehearsal in QEMU and the sitting's commands in `notes.md`.

### Phase 3: the sitting

One sitting, in this order, each step with a durable state before the next, each timed as it runs, the boot state recorded after each transition:

1. The new stick written on the host from the proved image and the third stick formatted, the owner naming each, the new stick hashed back and both identities recorded.
2. Power on, the devices and the sticks plugged in, the netconsole capture started on the host, the machine on the network.
3. The new stick booted on the Lenovo, its recovery menu shown to work, `rach2-recover` listing the disks with the Lenovo's disk shown as the rule describes, and the memory map from the netconsole capture saved for milestone 46's fixture.
4. The save: the owner names the disk; every sector of the save set copied to the host and to the new stick; the stick's copy hashed back against the host's. A failed hash ends the sitting here, with the disk untouched.
5. Recovery made the saved boot default, with the owner's approval, and the change read back.
6. The install: `rach2-install` on the Lenovo's disk, the owner naming it and giving the prepared answers; the readback against the manifest hash; the trial boot of the candidate with recovery still the saved default. An install that fails is restored from the new stick with the written commands, and the sitting ends.
7. From the running candidate: the root's identity, its writable mount, its grown capacity and the installed credentials checked; the acceptance with those credentials and the third stick; only then `bootctl commit`.
8. The devices: the metal acceptance on the installed system; the reboot from SSH; the pull test on the third stick; the keyboard and the mouse at each socket and through the hub, the host reading each line typed and each pointer movement from the console over SSH.

The owner's part ends here. Then, unattended: twenty sessions running milestone 46's load row for an hour; the numbers into `hardware.md` and the Readme's Limits section; the sitting's times, including the stick's sustained read during the save and the install against milestone 49's ten-minute budget. What the machine shows becomes entries. The notebook may be turned off after the load; nothing later in this milestone needs it.

### Phase 4: the machine's entries

The entries phase 3 added, worked as phase 1 worked its own.

### Phase 5: the close

Once and in this order: build from clean; the full set; the diff since phase 2 to Codex in units of six files, most serious first; every finding fixed; the full set again. Record the results, the sitting's log with its times and boot states, and the numbers in `notes.md` and the milestone's Readme. Add the index entry.

## Risks

* Notify the owner when a severe problem is added. One entry that loses data matters more than twenty that do not.
* The sitting is the first run of five milestones' kernel changes on real hardware, and the new recovery image shares them. A new stick that does not boot ends the sitting at step 3 with the disk untouched. A boot that stops before SSH has the netconsole capture and the screen; the boot switches skip individual probes, and polled AHCI is a boot option. A damaged install is restored from the new stick, or from milestone 43's stick if the new one no longer boots, with the written commands.
* The save writes the image's extent and the growth ranges to the stick, the path that once failed. The hash back is the check.
* An interruption during the image copy leaves the disk's own loader and recovery partition half written; the stick is the boot device then, and its recovery is what boots. Milestone 49's rows prove both boundaries.
* Two sittings, this one and milestone 52's, are the plan. A hardware failure that needs the owner's hands calls a third, prepared the same way, and is reported as such.

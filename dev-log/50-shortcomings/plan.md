# Milestone 50: the machine and the shortcomings

## The goal

Put the system of milestones 45 through 49 on the Lenovo, in one sitting of the owner's, and fix every previously known problem, every problem recorded during those milestones, and everything the machine shows. Milestones 45 through 49 prove their work in QEMU and do not touch the machine, so this milestone is the first run on the Lenovo of the new kernel, the disk registry, the AHCI interrupt path, the per-controller USB stack, the installer and the stick. The list of shortcomings is written as the work goes: an entry the day the problem is found, and nothing is deferred past this milestone. The manuals and the audit follow it, so that what they describe is the finished system and not one with known defects; an entry made during those two reopens the technical work before the document that describes it is accepted. The milestone is complete when the Lenovo runs the installed system with every device it had before, the twenty-session load has run on it for an hour, every entry is marked fixed with its proof, and the close below has run.

## What the tree settles before this plan

* The stick behind the SuperSpeed hub stopped answering and its removal panicked the kernel once; the record leaves the reset-and-removal sequence with stale completions open (`dev-log/43-machine/notes.md:291`). A healthy stick pulled is not the same test.
* Milestone 44 needed four full runs to get one clean, and records the failures as pooled execution (`dev-log/44-krffsmount/notes.md:412`). A successful rerun does not explain the earlier failure. Diagnose the kernel, harness and scheduling before closing the entry.
* The Lenovo's disk is 488397168 sectors of 512 bytes on SATA, internal, and does not leave its bay (`dev-log/43-machine/hardware.md:43`). It has the sealed layout: a 64 MiB boot partition, the 500 MiB KRFFS fallback root, the 64 MiB recovery partition, and a fourth entry of 2 GiB with the 1 GiB ext2 root in it; the rest is unused. It has one xHCI controller and an EHCI the kernel names (`hardware.md:41`).
* Milestone 43's recovery stick, with its older kernel and its own host key, boots the machine today (`hardware.md:121`). That recovery repairs every ext2 partition it finds during its own boot (`utils/init.c:200`, the call at `:243`), has `reflash` and no `rach2-recover`, and is not changed by this milestone.
* The Lenovo's USB sockets are the right black, the left black and the left blue, with the hub on the blue one (`hardware.md:131`).
* The metal acceptance writes a file to the first USB disk it finds with a FAT or exFAT volume (`tests/system/accept/metal_accept.sh:500`, the write at `:527`). It would write to a recovery stick's image half.
* The hardware rule in `CLAUDE.md`: a write that cannot be undone by rebuilding needs the owner's approval at the time, with the device shown; before a write to the Lenovo's disk that is not a kernel through `bootctl`, a stick with recovery is booted and shown to work, every sector about to be overwritten is saved on the host and on that stick, and recovery is the saved boot default until the write is verified.
* Milestone 49's installer prints the device, asks for its name typed back, and prepares the image with recovery as its saved default. Its save set is the image's extent and the block ranges the grow writes into the groups it adds, computed by milestone 47's tool from the new image's superblock, the root's offset on the target and the target's size. Its phase 5 rehearses this milestone's sitting in QEMU on a disk of the Lenovo's size and layout, with the restore made through `rach2-recover` and through the older recovery's `reflash`.
* Milestone 24's boot switches skip individual device probes, milestone 47 keeps a boot option for polled AHCI, milestone 46's kernel prints its memory map at boot, and netconsole sends the kernel log as frames the host captures before SSH is up.

## Entries

An entry has: a date; the milestone that found it; its severity, with a loss of data or a panic first; how to reproduce it; the contract it breaks, with file and line; what it depends on; the test that will show it fixed; and, once done, the commit and the proof. The two above are the first entries, numbered 1 and 2, and the list is worked in order of severity and dependency, not of the code it touches. What the machine shows in the sitting is entered the same way and worked in phase 4.

An entry is fixed when its test passes in QEMU and its review has run. A fix made after the first sitting reached the Lenovo at the second, and what phases 6 and 7 add is deployed and proved there before this milestone closes, nothing of it waiting for milestone 52, and the entry says so; a kernel fix may go on earlier through `bootctl` over SSH when the machine is on and the owner approves that write, and this is never required. The documents may be written once every entry is fixed. A fix without which the machine does not run at all calls the owner again with the same preparation as the sitting, and the report says that it did.

## Decisions

### The code is reviewed before the machine is written

The installer, the kernel and the recovery image this milestone's fixes changed are what the sitting writes with, and `CLAUDE.md` puts a destructive write after the review of the code that performs it. So the review of phases 1 and 2 runs in full before the sitting: build from clean, the full set, the Codex review, every finding fixed, the full set again. The fixes made after the sitting are reviewed once, as one batch, at the close.

### The owner is called once, with everything ready

Before the owner is called, the following are done and recorded in `notes.md`:

* The reviewed kernel and images built, their hashes recorded, and the stick image booted in QEMU.
* The save-set tool run against the Lenovo's recorded geometry: its ranges, their total bytes, and the new stick's free space recorded; milestone 49's rehearsal run again against that manifest.
* The restore commands written out twice, for `rach2-recover` on the new stick and for `reflash` on milestone 43's stick.
* The third stick's layout decided, one exFAT volume labelled `RACH2TEST` over the whole stick, written in the sitting's first step; the pull test's read command, a `dd` of the whole stick to nowhere over SSH; its readiness signal, the first 64 MiB reported by the host; and its deadline, the removal reported by the kernel within one minute of the pull.
* Every answer the installer asks for prepared: the account name and the key in `notes.md`, the passwords in the credential file on the host that the acceptance reads.
* The sitting's commands in order, with what each shows, what the owner is asked, the observable condition for each physical action, and which boot switch answers which symptom.

Nothing in the sitting is discovered on the day. A step that turns out to need something not prepared stops the sitting with the disk untouched or restored, and the owner is called again only after the gap is closed.

### The install replaces the grow

Milestone 47 proved `growroot` in QEMU. The Lenovo does not get its root grown in place; the installer writes the sealed image and grows the ext2 root into the free space of the disk, as milestone 49 decided. The saved set is what the installer writes: the image's extent and the growth ranges from the tool. The rest of the disk is not written and is not saved.

### A known-working recovery path stays outside the change

Milestone 43's stick is kept as it is. If the new stick fails to boot, or fails after the disk has been written, the older stick boots and its `reflash` puts the saved set back. Its boot-time repair may write into a damaged root before the restore runs; the restore rewrites every sector of the set, and the sectors outside the set were unused before the install, so the repair changes nothing the restore does not overwrite. Milestone 49's rehearsal proves this path with a recovery ISO built at the commit milestone 43 installed. The new stick is a second stick, and the acceptance and the pull test use a third stick that carries nothing; milestone 43's stick is not written at all, and the new stick's boot image is not written after its preparation; the save goes to the new stick's data volume.

### The pull test is the removal half of entry 1

There is no way to make a physical stick stop answering on demand. On the Lenovo the third stick is read over SSH from the host, and while the read runs the owner pulls it when the host says so; the kernel must report the removal, keep running, and take the stick back when it is plugged in again. The never-answering half is proved in QEMU by entry 1.

### What the owner does

At the desk, at the start: approves the write of the new stick and the formatting of the third, naming each as the host reports it, and plugs both into the notebook. At the notebook, at the start: powers it on, plugs in the keyboard, mouse, hub, card and the third stick as milestone 43 had them, and chooses the new stick as the boot device when asked. At the desk: approves each later write by naming the device the installer or the host reports, including the change of the saved boot default. At the notebook, once: types the target disk's name into the installer and the prepared answers. At the notebook, once more: pulls the third stick when the host says so and plugs it back. At the notebook, last: moves the keyboard and then the mouse through each of the three sockets and the hub, typing a line and moving the pointer at each, with the host reading what arrived. The owner's part ends before the load runs.

* **51, the probes and the root they judge. Done, and the hang was two other things.** Each probe that encoded the boot root's answers now asks the kernel instead. `fdstale` does not hang: on an ext2 root it stopped at its scope case, where it required `rmdir` to take a directory out from under an open descriptor. ext2 refuses that with `EBUSY`, which its Readme states and POSIX permits, so the probe now reads the root's type and asserts the refusal, that the descriptor still reads, and that the close is what releases the name; on the boot root it asserts the removal and the `EBADF` that follows, as before. What looked like a hang on the machine was the probe's leak loops: 256 rounds of a file filled with sixteen writes of 4096 bytes, unlinked and closed, which is 16 MiB in 4 KiB calls and tens of seconds on a disk where such a call is four commands and two flushes. Running it a second time took the machine off the network, which is entry 56. `tests/run default` passes with the change, 71 of 71 probes. The whole probe set was run on the machine at the close, which is what the entry still owed, and it found four more of the same kind. `loopprobe` carried the emulator's address, 10.0.2.15, as the one every loopback peer must report; it now asks the kernel for the machine's own through `getsockname` on a socket connected to 127.0.0.1, which is the rule the rows judge, and it passes on the machine. `jobprobe`, `procprobe`, `suidprobe` and `sudoprobe` cannot pass anywhere but the test image and now say so in a line at the top: job control needs a shell that gives each command its own process group, the `/proc/net/tcp` and pool rows need the machine to itself, and the two set-id probes need fixtures the shipped image does not carry. Of the twenty probes run there, `modeprobe` passes on the ext2 root, which is entry 48's machine proof, and `vfsprobe` was run against its own stated need for a KRFFS root, which was my error and not the probe's.

* **53, the port's alignment test. The patch and its proof are in; what the patch is worth is not what the entry claimed.** `tests/host/e2fsprogs_alignment_hosttest.c` and its 64-bit twin compile the port's own `unix_io.c` with every data call and seek intercepted, and judge a misaligned buffer over reads and writes, a large aligned request, a partial sector preserved, a short transfer retried and then reported, and an error reported rather than swallowed. Proved by mutation through `tests/host/e2fsprogs_alignment_mutate.sh`, which restores the port's source from a trap: patched, 64 checks pass; with the guard put back to the address test, 28 misaligned checks fail; restored, 64 pass and the source matches byte for byte. The controlled grow is named and reproduced: the recovery system on a 16 GiB disk holding a 1 GiB ext2 volume at sector 2048, booted by `build/tests/system/harness` on a qcow2 overlay, running `growroot MBRID=47470001,1`, which rewrites the table entry, runs `e2fsck -f` and then `resize2fs` over `/dev/disk0p1`, a raw window. Measured with `/proc/disk` read either side of that command: 9595 disk commands and 8 seconds with the port as it stands, and 9595 commands and 9 seconds with the alignment test put back. They are the same. A grow on the machine tells the same story: a file-backed volume grown there costs 32 commands at 16 MiB and under a second, and the two binaries differ by nothing that is not noise. So the patch is right about what `unix_io.c` does, which the host test proves, and the figure this entry carried, a full-size grow's 477659 write calls turned into 9346, is not reproduced by either measurement and is withdrawn. Entry 58 required the separate physical phase measurements. Those are now recorded from the recovery sitting on 2026-09-16: the grow totals 14.75 guest-tick seconds, including 14.54 for resize. The earlier ten-minute complete install is no longer described as a ten-minute grow; neither the alignment patch's physical speedup nor the old install's time distribution is inferred.

* **The residuals the close must dispose of.** Entry 36's race is real and fixed: `rach2/sys/usb/hub.c` records a port's status when it reads it, and the acknowledgement of those change bits goes out a tick or more later, after the whole scan, so a port that read as disconnected with a change already latched and that connects during the scan has the new device's latch cleared unread, and the core's pass at `core.c:1589` then sees a record that says disconnected and skips it forever. The driver now reads a port's status once more after acknowledging its change bits, and `rach2/sys/usb/Readme.md` says so. Proved by a row in `tests/host/hub_hosttest.c` where a device lands on a port the instant after its status is read: the row passes as the source stands, fails with the re-read never asked for, and passes again restored. `vendor/e2fsprogs/Readme.md` is corrected: two programs are staged, `e2fsck` and `resize2fs`, the configure enables the resizer, and the size limits the root `Makefile` enforces are stated. The load harness is in the tree as `tools/dev/machine_load.sh` rather than in a scratch directory, and it starts its sessions a second apart: Dropbear allows five unauthenticated connections from one address at a time, which is `MAX_UNAUTH_PER_IP` in the port's `default_options.h` and is not changed by `localoptions.h`, so twenty started together get five. The ext2 writeback contract is rewritten whole only when the batch lands, and the batch is not taken in this milestone; the paragraph the second store's removal changed was rewritten with it. The load harness must start its SSH sessions a second apart, since Dropbear allows five unauthenticated connections from one address at a time and twenty at once give five; the change and its row belong here. `vendor/e2fsprogs/Readme.md` still says only `e2fsck` is built and calls the resizer disabled, which the build has not matched since the port patch, and the ext2 writeback contract in `rach2/sys/fs/ext2.Readme.md` is rewritten whole when the batch lands, not only its allocation paragraph.

* **55, SSH inbound. Done.** The cause is the card's message discipline and it is named, measured and repaired above: the handler now masks the sources while it runs and unmasks at its end. SSH inbound 22.3 MB/s against 2.4, a raw socket 118.3 against 6.4, outbound unchanged. The kernel that measured it is the one this tree builds, installed through `bootctl` and committed on the machine. What is left of the gap between SSH and a raw socket is Dropbear's own path, 22.3 in against 35.7 out, which is the cost of the protocol and not a defect; the finding is in `notes.md`. Every inbound measurement taken in this milestone before 2026-09-13 was taken on a machine whose card had fallen into the tick's pace, and the later logs do not identify their running kernel. Entry 54 withdraws its claimed per-kernel comparison; unit D adds no new one to the sitting.

### Phase 8: the first run

The third sitting reported five things about what a person meets the first time
they use this system, and they are one piece of work rather than five entries: a
line of coloured text at the end of every boot that vanished before it could be
read, the kernel's checks costing about a second of every boot, messages still
arriving on the screen after the login prompt, an installer that never said what
it was or what it would do, and boot menus of eight and three entries written in
words only this project uses.

What was decided, with the owner, and built.

**The screen has three phases.** The kernel writes to it during boot and stops
when a real `/sbin/init` starts; after that only a panic reaches it. Everything
still goes to the ring, the serial port and netconsole, so nothing is lost, and
`/dev/screenlog` reads and sets the level. Three boots keep their messages: one
whose line named a level, a `rach2.fsck` recovery boot, which has minutes of
work to show, and a read-only root, which the owner needs to know about before
working on the machine. `power_stop` takes the screen back, because a machine
that has stopped must be able to say so and there is no log to read afterwards.
The screen is no longer cleared at init, so the login prompt appears under the
boot the person has just read.

**The boot log is what a person can act on.** About a hundred records moved to
debug: the lines that only say a step of initialisation finished, the per-port
USB detail, the message-signalling vectors, the card identity dumps and the
counters that are all zero at bring-up. The `X: started` lines for slow work
stayed, because a boot that hangs is named by the line that did not finish. 122
visible lines became about 25.

**The checks at boot are the ones only the hardware can answer.** Eleven went:
memory, heap, strings, paging, system calls, context switching, isolation, round
robin, KRFFS write, ELF load, page cache. Each is exercised by the first program
that starts and covered by the host tests and the probe suites; the memory one
read 256 bytes and the page-cache one ran against a RAM disk. Three stayed, run
at every boot, and print their measurements rather than a verdict:

    timing: tick 100 Hz, 200 ms delay measured 200 ms, 2000 us wait measured 2001 us

A machine whose delays run short boots and logs in perfectly well and fails
months later as an intermittent device fault. The clock check earned its place
on this laptop, where an interrupt handler took a PIT latch between two samples
and 2000 us read as 1361 (`dev-log/43-machine/notes.md`).

**The menus name what they do.** The stick has one entry, `Install Rach2`:
installing is why a person boots it, and repairing is what that system offers
once they are in. The installed disk has three, all of them saying Rach2 because
all three are Rach2, each of the other two saying how it differs:

    Start Rach2
    Start Rach2 with the previous kernel
    Start the Rach2 recovery system

Earlier drafts failed on exactly that. "Repair this computer" promises the boot
repairs something; "Start the repair tools" promises tools start; "Start the
recovery system" reads as not-Rach2. Five entries went. The kernel debug shell
came off both menus, since it authenticates nobody and was a root shell one
keypress from an installed machine's boot menu; its code stays, because the test
image boots into it and 22 of the 44 suites depend on that. The check-disks
entry went, since it set a boot token to run `e2fsck` before anything else and
`e2fsck` is a program a person runs from recovery. The three fixed-address
entries went, since a fixed network address is a property of where a machine
lives and not a choice made at every boot.

Removing that pair removed the machinery serving it: `running_static_entries`,
`bootslot_use_static_entries`, the `-static` decoration of entry ids, and the
`set fallback=3` in `grub.cfg`. That last one mattered. GRUB 2.12 parses
`fallback` as a number and discards a name, so the order of the entries is part
of the file's contract, and the draft that replaced the number with an id would
have disabled the automatic fallback silently. Codex found that before it was
written.

**The disk has three partitions.** The KRFFS root is gone: a second complete
system with the demonstration accounts, which the fallback entry booted so a
machine came up to something when the installed root would not mount. The
recovery system does that and more, from RAM, with the tools to repair the
machine. So the fallback slot now guards the one failure GRUB detects by itself,
a kernel image that will not load, and boots the person's own root with it,
which is also what makes the entry nameable.

The two FAT partitions stay separate. A merge was considered and rejected: GRUB's
core lives in the gap before the first partition and can reach either file
system, the boot partition is written at every kernel install and every trial
while the recovery partition is written at an install and an update, and
`grub-embed.cfg` already falls through to the second when the first cannot be
read. Keeping the rescue path out of the volume that gets written is protection
against the likeliest damage.

**The installer speaks to a person.** It greets, says it writes nothing until
the last question, and says how to stop. No question ends the run: a wrong
answer says what is wrong and asks again, since nothing is written until the
confirmation. Disks are numbered. Text addressed to a person carries no
`rach2-install: ` prefix, which is a diagnostic's, and no line runs past 80
columns: the key prompt was 90, the no-keys summary 85 with a legal account
name, and the disk list row 132.

What this phase still owes, after a review of the plan by Codex and the owner's
decisions on what it found. The review opened with "I would not build phase 8 as
written", and six of its findings changed the work.

**The interrupted update has nowhere to land, and that is a regression this
phase caused.** `rach2-install` saves the `fallback` entry before it overwrites
the root and arms `candidate` afterwards. That was safe while the fallback
booted the KRFFS root; both entries now boot the ext2 root, so a power cut
during the write leaves neither usable, where before the machine still came up.
The installer must save `recovery` before any root write, keep it saved through
the write and the readback, and let only an explicit commit make the candidate
permanent. The second FAT partition does not cover this: `grub-embed.cfg`
reaches it when the boot partition cannot be read, and a readable menu loading a
kernel whose root is broken never goes down that path.

**Two disk targets are leftovers and two are live suites.** `os-real-grub-disk`
and `rach2-metal-grub-disk` are from before the installer existed, when a
machine got Rach2 by imaging a disk over a USB adapter and swapping it in; they
go, with their documentation. `run-grub` and `run-drill` are the `grub` and
`drill` suites, `grub` in the core tier, and they built disks whose root was the
KRFFS partition. They need a root supplied, as `run-drill-ext2` already does,
and the builder must refuse to build a disk with no root rather than produce one
that boots nothing.

**Recovery has no login, no SSH and no keys, on the stick and on the disk.** The
password this phase planned would not have been a boundary: the recovery image
still stages the demonstration keys and starts SSH regardless of what happens at
the console, and a person at the GRUB menu can still add `rach2.rescue` to a
boot line. Closing only the menu entry would have invited trust the arrangement
could not carry. The archived account files cannot authenticate either: they are
refreshed at an install and an update and not when root runs `passwd`, so they
can hold a password the owner has replaced; they carry nothing that says which
installation they came from; and `write_archive` removes the old copy before
renaming the new one, so a stop between the two leaves none. They stay what they
were built to be, the copy that puts accounts back after an update.

So both recovery systems boot to a shell, no image carries a standing
demonstration key, and the documentation says plainly that physical access to a
machine is control of it. The installed system is unchanged: SSH with the
account's key, and root by password.

Whether a recovery system answers the network is decided by one rule, and the
rule is not a mode: **the SSH server starts only where there is an authorized
key, so no key means no server.** A credential is a build input rather than a
property of the code, which is what makes this work for the three cases at
once. A stick built for development has the owner's key and updates a machine
remotely the way it does now. A stick built for anybody else has none, starts
nothing, and is reachable only after a person puts a key on it. The recovery
partition of an installed disk has none either, so the installer offers to
place one, and a machine nobody administers remotely has no door.

This matters because a root update cannot be done from the running system: the
update overwrites the whole root partition and the kernel refuses to open a
partition whose file system is mounted, with `EBUSY`, which is the fault
`tests/run drill` proves. So a root update runs from recovery, and a recovery
that answers nothing is a machine that can only be updated at its keyboard. A
kernel update is not affected, since `bootctl` writes the boot partition.

The danger of that rule is that a development image and a release image are
identical from outside, so the difference has to be visible. Two guards are
built here: the machine says at boot whether a key was built into it, and a
development build writes its image under a name that says so. A third, a build
that refuses to produce a release image while a key is present, is the real
guard and is not built: this repository has no release procedure to hang it on.
It belongs to the release engineering that does not exist yet, and is written
down here so that work finds it.

**The `sealed` suite is rewritten, not renumbered.** It damages the ext2 root
and then requires a working KRFFS system, and later destroys and repairs that
partition. Those rows are about the thing this phase removed. They become what
the machine now does: damage the root, land in recovery, repair from there.

**Two of the three known problems block the close.** The metal kernel is built
by a phony target while the disk images depend on the file it leaves behind,
with no rule between them, so editing `kernel.c` does not rebuild the kernel
that ships; it shipped a stale one today, caught by reading a boot log rather
than by a check. And `/var/log/services` must have a bound within a boot, since
a service that fails in a loop can fill an installed root or a recovery
system's memory. The AHCI second per empty port stays measured and accepted.

**Machines on the old layout are not migrated.** `--update` keeps the partition
table, so it cannot move an installation from four partitions to three, and the
new menu must never be applied to the old layout. The owner's decision is that
the next stick installs fresh over whatever is there.

**Two faults of the build itself came out of the close, both of the same
shape.** A component was reachable by two routes with no edge between them, so
`make -j` took both: the name `rach2` ran a sub-make and the kernel's file rule
ran another, and a clean parallel build compiled every kernel object twice into
the same files and linked one that a second job was still writing
(`undefined reference to krandom_seed`). `ish` had it too, and the three KRFFS
tools share one rule, which make reads as a rule per target, so three missing
files were three sub-makes of one directory. Each component now has one file
rule that asks its sub-make, and the component name asks for that file. The
second fault was the allowlist: the two init programs were declared against
each other's manifest, so no image could be staged at all, and `utils/guest.mk`
had no rule for `init-recovery`, so the guest build of the utilities did not
build it. Both are the kind a clean build finds and an incremental one hides.

**The string sweep came back as a boot option.** It was one of the eleven
checks removed from every boot, and the only exhaustive exercise of the word
moves in `sys/lib/kstring.c`, which are i386 instructions the host test beside
that file cannot run. `rach2.strings` runs it: 68 lengths at four source and
four destination alignments, copy, fill and move both ways, with the bytes
around each range required to be untouched. `tests/run memory` boots it once.
The copy's byte tail removed reports the first length that is not a multiple of
four; restored, it passes again.

Then the suites that name a partition number, `tests/run all`, a review of the
whole diff, and the stick.

## Risks

* Notify the owner when a severe problem is added. One entry that loses data matters more than twenty that do not.
* The sitting is the first run of five milestones' kernel changes on real hardware, and the new recovery image shares them. A new stick that does not boot ends the sitting at step 3 with the disk untouched. A boot that stops before SSH has the netconsole capture and the screen; the boot switches skip individual probes, and polled AHCI is a boot option. A damaged install is restored from the new stick, or from milestone 43's stick if the new one no longer boots, with the written commands.
* The save writes the image's extent and the growth ranges to the stick, the path that once failed. The hash back is the check.
* An interruption during the image copy leaves the disk's own loader and recovery partition half written; the stick is the boot device then, and its recovery is what boots. Milestone 49's rows prove both boundaries.
* Three sittings: the first, the second of 2026-09-12, and the short recovery sitting phase 7 needs for entry 53. A hardware failure that needs the owner's hands calls a third, prepared the same way, and is reported as such.

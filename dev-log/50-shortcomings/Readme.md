# Milestone 50: the machine and the shortcomings

The Lenovo runs the system built in milestones 45 through 49, installed from the stick with its root grown into the SSD. The install, the device checks and an hour of twenty-session load are done, and the 47 entries `plan.md` held at the first close are fixed. A second sitting on the evening of 2026-09-12, a fresh install of the tree at `01d02656` watched at the console and a night's work on the installed machine, added eight more, entries 48 to 55. Four are taken: the chown rule, the frame the drivers copied a byte at a time, the poller woken with a deadline, and the inode stored once a write. Four are open: the loopback ring's drain and its refused acknowledgement, the probes that can only judge the image they were written for, the ext2 batch that would span calls, and SSH's inbound rate. Each of the taken four still owes the proof its entry names. The milestone is therefore open again, since nothing here is deferred. This was the first run on the machine of the new kernel, the disk registry, the AHCI interrupt path, the per-controller USB stack, the installer and the stick, and it took one sitting of the owner's.

## What was fixed

Eight entries came from the machine itself. The block cache is capped at half the kernel heap's pages, so a machine with memory no longer wedges recovery at the save; the RTL8168 takes its messages with the timer as the fallback; a disk request is 2048 sectors where it was 64; the kernel's copies and fills move a word at a time through the string instructions; TCP sends a missing segment on the third duplicate acknowledgement and the lost run again as the window grows; the port advertises pause both ways and the card's own error counts reach `/proc/net/dev`; the heap keeps sixteen runs of a megabyte in reserve for a large allocation beside a full cache; and a delay whose clock reading went backwards inside a tick is dropped rather than kept as the longest ever seen.

Thirteen entries are the storage path: its bookkeeping, one page per request, the raw windows' single staging buffer, a USB stick's command per page, an exFAT append that walked the chain from its first cluster, an exFAT directory that grew slower with every file, a pointer block that could reach the disk before its bitmap, a request answered late failing the mount, the `sparse_super` rule taking products for powers, a KRFFS node astride two units, a KRFFS rename refused after removing its destination, a partition view keeping its backing's stale flags, and a disk with 4096-byte sectors, which is refused by name with the refusal now proved.

Seven are kernel costs and waits: a process always inside a system call starving the rest, the console losing typed input under load, a kernel record beginning inside a program's console write, the pipe's copies, `getrandom` giving way and the memory refusal running before the bootstrap tables rather than after, the kernel's boot on 8 MiB, and the network on a warm restart. Twelve are the runs: the clean tree's preparation and its parallel make, the preflight's host access, two suites building one image at once, a run that does not own what it uses, the suites' waits by the clock, one scenario run twice in a set, the storage proofs, the pooled failures and the two suites that lost rows to host load, and `mshowfat` aborting at random on the build host. Seven are the deployment: the stopped stick's stale completions, the acceptance writing to a stick it should refuse, the device table from one modelled hub, the configuration saved only on the root it describes, the fallback kernel written on its own, the sitting rehearsed at the machine's own size, and the guest build's link.

## The sitting

The sitting ran over the night of 2026-09-11 and the afternoon of 2026-09-12. One SanDisk carried both halves the plan had given to two: the install image at its start and a third exFAT volume, `RACH2TEST`, over the remaining 59.8 GB for the save and the pull test. That layout was proved in QEMU first.

The first save wedged the recovery system, which is entry 40. With the cache capped, all 1852 ranges of the disk went to the stick in 527 s and each hashed on the machine as the disk does. The second copy, over the wire to the Mac, showed the network on the timer tick at 400 KB/s, entry 41; with the card on its messages it ran at 11 MB/s, the 100 Mbit wire's ceiling, and 1842 of the 1852 ranges hashed, ten cut short by stalls. The Mac's capture showed what a stall is: a run of 1 to 16 frames lost between the notebook's card and the Mac's port, and a stack that sent one segment back per timeout with the timeout doubling to a minute. Those are entries 44 and 45. The cause was the Mac's cable, which held that port to 100 Mbit; with a good cable and both ports at a gigabit, 1.74 GB copied in 163 s with no segment sent again.

Recovery was made the saved boot default with the owner's word before anything was written. The first `rach2-install` died with the SSH session that carried it, leaving the image on the disk byte for byte and nothing after it done; a second run, detached on the machine with its answers in a file, went through in ten minutes: the image checked against the manifest, written, read back, the table read again, root and `toksaitov` written with the acceptance's key, the configuration archived on the recovery partition, and the root grown to 487106928 sectors. The write ran at 14 MB/s under entry 46, the heap unable to find a contiguous megabyte beside a full cache; with the reserve the same path runs at 174 MB/s.

The candidate booted from the disk on its own and answered SSH with the key. The acceptance passed 66 rows run as root, after its test for an installed kernel was taught the installer's `rach2.root=MBRID=` form. Word copies took the SSD's raw read from 94 to 328 MB/s and the stick's from 33 to 44. The owner typed and moved the pointer at the two black sockets, swapped them, and then ran both through the hub on the blue one, with `KEYLAT OK` and `MOUSEPROBE OK` at each, and played Doom at the console. The pull test read the stick's first 64 MiB at 44 MB/s and the stick was pulled under the read: the kernel reported the port gone, kept the request in flight, failed it once the slot was given back and reclaimed the disk, the reader getting an I/O error and the machine running on.

The load row ran unattended: twenty SSH sessions as root, each copying `/src/rach2` and building it with the staged TinyCC and pdpmake for an hour. 361 builds, none failed, a lone build taking four seconds and one beside nineteen others about three minutes. The longest timer gap was 30 ms against 14 ms idle, the longest wait for the request limit 27 ms, the console never waited, and the heap held at its cap of 36000 pages. The disk's own longest delay read as entry 47's wrapped figure, so the row has no disk number; that entry's fix is in the tree and has not yet run on the machine. The notebook runs the tree's kernel at `59b99e5a` in its candidate slot, and the stick's recovery system and install image are the tree at `ea61e916`.

## What proves it

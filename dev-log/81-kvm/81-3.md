# VMX on the Lenovo (81-3b)

Rach2's VMX backend, which until now has run only on the host test's model of the Lenovo's Haswell, runs guests on the Lenovo itself: Debian's QEMU on a trial root of the x86-64 GNU root boots the Debian guest of `tests/kvm/guests` and Rach2's own i686 disk with `-accel kvm`, and runs kvm-unit-tests and Linux's KVM selftests as `tests/kvm/corpus.sh` judges them. This file has the readiness note that the trial boot waits on (81-3b.1) and the Lenovo's results (81-3b.2); the step's commands are on the task's issue.

## Before the trial

Every selftest reads `/sys/module/kvm/parameters/force_emulation_prefix` in its constructor and skips without it, so on Rach2 every selftest the list expects to pass would have skipped. The task adds the files Linux's selftests read, made by `kvm_start` with `/dev/kvm` ([sysfs(5)](../../man/man5/sysfs.5)). An x86-64 Rach2 at that commit, booted from its GRUB disk under the testing PC's KVM with `-cpu host`, logged `kvm: ready: svm` and no `kvm: failed` line, reached `boot: starting /sbin/init`, and at its serial login read `force_emulation_prefix` 0, `enable_pmu` N, `tdp_mmu` Y, `eager_page_split` N, and `kvm_amd`'s `npt` Y and `avic` N.

The i686 guest is `os-real-grub.disk`, booted by SeaBIOS, whose token is the kernel's `boot: starting /sbin/init` on the serial port. `kvm-boot.sh -m 512 -d os-real-grub.disk -t 'boot: starting /sbin/init'` under the testing PC's own KVM passed in 69 s, the guest's kernel reaching init at 3.58 s of its own clock; the rest is GRUB's menu and the runner's wait for a power-off the guest does not make.

## Readiness (81-3b.1)

Why no path the trial adds can leave the Lenovo stopped, as the `machine` skill's Trial boots asks. Line numbers are those of `rach2/sys` at this file's commit.

* What runs at boot. The probe (`vmx_probe`, `vmx.c:2576`) reads CPUID and, only when CPUID.1:ECX.VMX is set, IA32_FEATURE_CONTROL and the VMX capability MSRs, and installs the panic hook; `kvm_start` registers `/dev/kvm` and makes the `/sys/module` files, which only allocate entries of `sysfs.c`, and a failure there is a logged warning. No VMX instruction runs at boot. The first runs when QEMU calls KVM_RUN, in the step's first stage, after the boot has been read over SSH.
* VMX is on only inside one section with interrupts off. `vmx_enter` (`vmx.c:1532`) turns it on (`vmx_on`, 1009) and off (`vmx_off`, 1057) around each run, with every failure going through `vmx_leave` (973), which clears CR4.VMXE again. IA32_FEATURE_CONTROL on the Lenovo reads 0x5, locked with VMX on, so it is never written. VMXON is refused with EIO before it runs when the host's CR0 or CR4 is outside VMX's fixed bits, where it would #GP. Each entry is VMLAUNCH after a VMCLEAR, so no VMCS stays current outside the section and a vCPU moves between processors with nothing to migrate.
* Every wait is bounded. Each entry arms the preemption timer at 2^22 TSC ticks (`VMX_RUN_BOUND_TSC`, `vmx.c:354`, written at 1469), 2.2 ms at the i3-4030U's 1.9 GHz, and the probe refuses a processor without external-interrupt exiting, NMI exiting, virtual NMIs or the timer (2580), so the host's timer tick, an IPI or an NMI also ends a run. `vmx_run.s` has no loop and `vmx.c` none that waits. The one spin that waits on a guest, `kvm_tdp_flush` (`tdp.c:204`), waits for a vCPU's mode to leave KVM_MODE_IN_GUEST, which `vcpu.c:609` sets as soon as `enter` returns and before the big lock is taken again, so it lasts at most one run. A halted vCPU sleeps in `kvm_lapic_prepare` (`vlapic.c:1255`) on a wait that a signal ends with EINTR, and a signal ends KVM_RUN before the next entry too, so killing QEMU ends any guest.
* VMX is off on panic and on reboot. `k_panic_begin` calls the hook first, with interrupts off (`panic.c:135`); `vmx_panic` (`vmx.c:985`) clears the current VMCS and runs VMXOFF when its processor is inside the section, as Linux's `vmx_emergency_disable_virtualization_cpu`. The other processors stop on `smp_stop_others`' IPI, which a processor takes only with interrupts on, so outside the section, within the 1 s the panic waits. An NMI or machine check that ends a run reaches the host's handler after VMXOFF. A reboot or a power cycle therefore never meets a processor in VMX operation, whose INIT would be blocked.
* Memory. EPT's leaves are write-back with the guest's PAT ignored, since no device is assigned; the tables map only the pages of QEMU's own address space, through the slots that follow it.
* The host test runs the same path. `tests/host/kvm_vmx_hosttest.c` drives `vmx.c` whole over a model of the Lenovo's capability MSRs and of the VMX instructions with the SDM's entry checks: the probe, VMXON, the VMCS built, entries, each exit kind the corpus's guests cause, the preemption timer's exit, both kinds of failed entry, VMX off and CR4 back after every run and every failure, and a panic inside a run. It passed alone at 0df1c2fb0 (81-3a.4 and 81-3a.5), and `rach2/sys/kvm` has not changed since but for this task's `/sys/module` files in `kvm_start`, which the host test links with stubs.
* What the model cannot vouch for. The host state the VMCS holds, the GDT, IDT, TR, FS and GS bases and the host's MSRs, is read from the real processor on each entry; a wrong value would fault in the host at the first exit, and the panic would halt the machine with VMX off, which leaves it down until the owner is home. The step therefore enters a guest first alone, the Debian guest, with the log read over SSH before and after, and goes on only once that exit came back.
* The trial kernel is the milestone branch's head with this task's commit. It carries other tasks' kernel changes made since the last branch kernel booted on the Lenovo (76-11b's, merged at 398f00ae7): the DRM core's hotplug queue and connector properties, the futex PI work, TLB shootdowns by range, the timer's pass between processors, VFIO without an IOMMU, the widened message vector pool, ext2 attributes and the /sys CPU, cache, node and DMI files, among them. They run at the trial kernel's first boot, on the installed root, before any VMX instruction; the step stops there on any fault in that log. Booted without `rach2.i915`, the i915 driver leaves the GPU to the firmware's framebuffer. Running this trial after the other open trials of the stack, so that its boot runs nothing new but VMX, is the manager's choice.

## Results (81-3b.2)

The step ran on 2026-11-10, loop m2, from 17:39 to 20:00 (UTC+6) in four boots of a trial kernel. The kernel boots and Debian and Rach2's i686 disk boot under VMX. The corpus does not pass yet: 7 of 58 unit tests and 51 of 66 selftests differ from the lists, nearly all for parts of Linux's KVM that Rach2's lacks on either backend. Four tasks of 81 build them: 81-10 the PIC, IOAPIC and PIT in the kernel, 81-11 the paravirtual leaves, kvmclock and the clocksource file, 81-12 the wider emulator with `syscall` and `debug`, and 81-13 the small capabilities and the two rows of the lists that are wrong for the machine. guest_memfd, SMM and async page faults wait for the owner's decision. The corpus runs once more on the Lenovo, as this task's last step, when the four are closed. The outputs are in [`81-3/`](81-3/).

### The run pages' frames

About one QEMU start in ten of the first run printed nothing and spun in SeaBIOS; `vmexit_cr0_wp`, `rdpru`, `umip`, `hyperv_synic` and `debug` were lost to it. A vCPU's two run pages come from `kalloc_pages`, whose pages are contiguous in virtual memory only, and `run_page` mapped the second, the port I/O page, at the first frame's address plus 4096. When the two frames were not neighbours QEMU's port I/O page was another owner's frame: every OUT carried what QEMU last left there and every IN read 0. QEMU's trace of a stuck start has `pci_cfg_read empty ff:1f.7 @0xff -> 0xffffffff` 92 times where a good one has `pci_cfg_read i440FX 00:00.0 @0x0 -> 0x8086`: SeaBIOS's first write to port 0xcf8 arrived as 0xffffffff, the shadow RAM stayed locked, and the guest ran zeros. QEMU's answers to INs went into the foreign frame; 34 lines `kheap: free of a page without the header` in that boot's log are heap pages whose first word they overwrote. The installed root was not mounted in that boot, and the trial files read back with their digests from a clean boot of the release.

100d650c5 reads each run page's frame from the kernel's tables, and gives SVM's I/O and MSR permission maps, which made the same assumption over 12 KiB and 8 KiB, pages whose frames are consecutive. On the second trial kernel, 60 starts of `umip` and `rdpru` through `x86/run` and three corpus runs since: no stuck start, no `kheap` line.

### After the step

The release went back each time the machine was left: at 20:00:05 `machine_identity.sh` found `0effe5acc26e1bf2f20b87b73e92ad8a9d769b708086b5ba700873f7e95e2cad` running from the candidate slot and in the fallback slot, no trial armed and the staged menu cleared. `/data/trial` (17 GiB: the root image, the i686 disk, the runners and the four kernels) stays for that last run.

Two things about the tools: gdb cannot read a vCPU's mapping through `/proc/PID/mem` or ptrace on Rach2, so the run page was read by a call of `memcpy` in QEMU itself; and such a call without `handle SIGUSR1 nostop noprint nopass` kills the QEMU, which is the `terminated on SIGSEGV` of the first run's `vmexit_cr0_wp`.

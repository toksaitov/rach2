# 81-6d: the PCI walk and the VT-d units on the Lenovo

One silent trial boot of the x86-64 kernel of `milestone/76-display` on the Lenovo, read-only, that proves 81-6a's walk finds the devices the installed release finds and that 82-1's reading of the DMAR table and of both units' registers gives the values Linux's log has (`dev-log/70-wifi-chip/linux/dmesg.txt:190-200`).

## The kernel

* The boot line adds `intel_iommu=off intremap=off`. Since 97cf9816f the kernel, given both words, reads the DMAR table and each unit's version, capability, extended capability and status registers, logs them, and programs no unit, as Linux does with the same words (`intel_iommu_init` stops at `intel_disable_iommus`); it writes a unit's command register only to turn off translation the firmware left on, which the Lenovo's firmware does not. Without the words the boot would set each unit's root table, invalidation queue and fault event, and turn interrupt remapping on, which is 82-1.7's trial (#2926), not this one.
* The walk reads configuration space and writes none of it: vendor and device ids, header types and the bridges' secondary bus numbers (`pci.c`, `pci_list_build`). The SB16 probe reads the data port once after each base's reset and gives up when it reads all ones.
* Checked before the trial: `tests/host/vtd_hosttest.c`, whose rows `read_only` and `read_only_te` start the driver on the Lenovo's two units with both words and find no register written, or one command when translation was on; and a boot under QEMU 10.2.1 in WSL (`-machine q35,kernel-irqchip=split -device intel-iommu,intremap=on`), which logged the table, `dmar0: at 0xfed90000, version 1.0, cap 0x80d2008c222f0606, ecap 0xf00f5a`, `dmar0: status 0x0` and `off by intel_iommu=off intremap=off: 1 units read`, and went on with its boot.

## Passes when

* `/proc/cmdline` has `rach2.slot=candidate intel_iommu=off intremap=off`, and the kernel's SHA-256 is the one built for the step.
* The listing of `/sys/bus/pci/devices`, each function's `uevent`, equals the listing of the boot before, under the installed release.
* The log has these lines, Linux's values (`dmesg.txt:190-198`) in Rach2's words, among the scopes' lines, and no `translation was on` and no `interrupt remapping was on`. Linux's log gives neither the table's flags nor the scopes' bus numbers, so those are recorded as read: the I/O APIC's and the HPET's scopes are the requester ids 82-1.7 (#2926) takes from Linux's log as f0:1f.0 and 0:f.0, and this boot is the first to read them on the machine.

### The AR9565's messages under boot 1

In boot 1 `/proc/interrupts` had no line for the AR9565's vector 53: it took no message, though the card had joined its network, served by the tick. A second boot 1 at 01:47 gave the same. A control boot of the same kernel with `intel_iommu=off intremap=off`, at 01:48, gave the card vector 52, and it counted 515 messages in a minute; the release gives it 52 too. With VT-d on, the fault event takes vector 48 first, and every later device moves up one.

The card writes its message number into the low two bits of the message data, whatever Multiple Message Enable says: its MSI capability offers four vectors (`Count=1/4` in Linux's lspci, `dev-log/70-wifi-chip/linux/info.txt:401`), and the driver sends every cause as message 0 (`AR_INTCFG`). Vector 53 therefore arrives as 52, the RTL8168's. Vector 52 is a multiple of four and arrives as itself, and with remapping on the unit routes the message by its handle and ignores the data, which is why boot 2 counted. Linux drives this card by its INTx line, so it never meets the case. 3940fb6e4 gives the card a vector aligned to the count its capability offers, through `isr_alloc_vector_aligned`; its proof on the Lenovo is 81-6d.4.

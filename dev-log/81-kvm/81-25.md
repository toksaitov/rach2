# kvm-unit-tests with Rach2 and Linux as the host (81-25)

kvm-unit-tests' x86 suite ran on the testing PC with Rach2's KVM as the host, inside QEMU under WSL's KVM with the host processor and SVM exposed, and the same subset ran with Debian's Linux 6.12 as the host of the same machine. Of the 58 tests of the subset, in the final runs at the task's last commit, each host passed 44, skipped 9 and failed 5, the same tests, Rach2 in 1,269 s and Linux in 1,206 s. Three tests differed in their subtests, each with a subtask of its own: an SVM single step that reached the guest in `x2apic` (81-25.1) and the speculation controls missing from CPUID and the MSRs in `msr` (81-25.2), both fixed, and branch counts over the bound in `pmu` (81-25.3), which Rach2's 1000 Hz tick causes under an outer KVM that counts its own work. One subtest of `x2apic` depends on where a report line ends within the timer's period, under either host, as the final runs show.

## The configuration

Every run was on the testing PC, an AMD Ryzen 9 7950X3D, under WSL's Linux 6.18.58 and its KVM, inside `qemu-system-x86_64` 10.2.1 with the `host-svm` profile of the kvm suite's nested cases: `-cpu host,svm=on,npt=on,nrip-save=on,tsc-scale=on,vmcb-clean=on,flushbyasid=on,pause-filter=on,decodeassists=off,v-vmsave-vmload=off,vgif=off,enforce=on`, two processors and 6 GiB, the x86-64 GNU root's `gnu-test.disk` and the suite's `kvm.ext2` on an ich9-ahci, both under QEMU's snapshot. The host of the tests was either:

* Rach2: the x86-64 kernel of `task/4642`, run by the case `machine.kvm.unit-subset-nested` of `tests/cases/machine.kvm.json`.
* Linux: Debian's 6.12.107+deb13-cloud-amd64 of `tests/kvm/guests/debian.txt`, with the initramfs of `tests/kvm/guests/mklinuxhost.sh`. The first runs booted it with a script of its own, `linuxhost.sh`, on QEMU's `pc` machine without `invtsc`; the final run booted it with `tests/kvm/linux-corpus.sh -k unit`, which replaced that script, on `q35` with `invtsc=on`, the invariant TSC that `rach2.tscreliable` stands for on Rach2's command line.

Either host runs `tests/kvm/corpus.sh unit unit-subset.list` in the GNU root: kvm-unit-tests at commit 5a221342 under the GNU root's QEMU 10.2.1 with `ACCEL=kvm,kernel-irqchip=split` and no time limit, one `run_tests.sh` a test, so that each test's seconds are known. Each test's guest runs under three hypervisors: Hyper-V, WSL's KVM and the host under test.

## The subset

`tests/kvm/unit-subset.list` holds 58 tests: every test `unit-tests.list` runs but `debug` and `xapic`. Linux as the host did not finish either in 900 s: `debug` stopped after "Usermode Single-step #DB w/ MOVSS blocking" and `xapic` after "FAIL: nmi-after-sti". Under Rach2, before 81-25.1's fix, `xapic` gave no result in 15 minutes either. The list's LINUX column is Linux's result, and `tests/kvm/Readme.md` gives the commands that run each side.

The differences in results:

* `hyperv_clock` passed under Rach2 and skipped under Linux, since the test requires the host's clock source to be the TSC, and Linux's on a machine without an invariant TSC is kvm-clock: Linux 6.12.115 puts the TSC above kvm-clock only where the processor declares the TSC constant and nonstop (`arch/x86/kernel/kvmclock.c:342-345`). With `invtsc=on` in the final run it passes under Linux too.
* `x2apic` failed under both, differently: Linux failed `nmi-after-sti` of its 56 subtests in 716 to 849 s, as the outer layers make it, and Rach2 stopped in 30 s on an unhandled #DB (81-25.1). After the fix it fails `nmi-after-sti` and `TMCCT should not be reset to TMICT value` under Rach2, in 803 s (the final runs, below).

The same message fails each of `hyperv_connections`, `la57` and `pcid-disabled` under both. `pmu` fails under both, as `unit-tests.list` expects under a hypervisor, 22 of 77 subtests under Linux and 32 under Rach2 (81-25.3). `msr` passes under both, with six subtests fewer under Rach2 before 81-25.2.

Without `x2apic`, which Rach2 cut short before 81-25.1, the subset took 820 s under Rach2 and 890 s under Linux, and two tests took Rach2 longer: `sieve`, 102 s to Linux's 13, and `pmu`, 28 s to 10. Both fill large buffers; `pmu`'s 16,047 nested page faults, below, show the cost of Rach2's 4 KiB mappings of a guest's memory, and `sieve`'s exits were not counted.

## The final runs

At the task's last commit, on 2026-11-12, the subset ran whole under each host again, Rach2 by `machine.kvm.unit-subset-nested` and Linux by `linux-corpus.sh -k unit`. Each passed the same 44 tests, skipped the same 9 and failed the same 5: `hyperv_connections`, `la57` and `pcid-disabled` with the same messages, `pmu`, 28 of its 77 subtests under Rach2 and 21 under Linux (81-25.3), and `x2apic`. The subset took Rach2 1,269 s and Linux 1,206 s; `x2apic` took 747 and 640 of them, `msr` 146 and 168, and `sieve` 39 and 7.

`x2apic` failed `nmi-after-sti` under both, and under Rach2 `TMCCT should not be reset to TMICT value` too. The subtest, in `test_apic_change_mode` (x86/apic.c), starts a one-shot count of 0x999999 at a divisor of 1, 10.07 ms, waits until TMCCT is below half of it, switches LVTT to periodic mode, reads TMCCT, prints a report line and reads TMCCT again, which must still be below half. Rach2 follows Linux's `apic_update_lvtt` (`arch/x86/kvm/lapic.c:1781-1797`): a switch between one-shot and periodic mode keeps the count. A trace of Rach2's vLAPIC, in a run of `x2apic` alone, showed it: the one-shot was due 3.6 ms after the switch, the first read found 2,738,226 counts left, the count went on into periodic mode, and the second read came 101 ms later, in the tenth period after it, with 2,288,523 left, and passed. That 101 ms held ten lines of the trace itself on the Rach2 host's console.

The report line between the reads is some 80 exits to QEMU, since each character is a read of the UART's line status and an `outb` (`lib/x86/io.c:15-21`). `vmexit_inl_pmtimer` and `vmexit_cpuid`, run alone under each host on 2026-11-12, measured such an exit to QEMU at 2,064,303 TSC cycles under Rach2 and 2,024,934 under Linux, about 490 microseconds at 4.19 GHz, and an exit that the host's kernel answers, CPUID, at 1,357,535 and 991,734. So the line takes some 40 ms under either host, about four periods of the timer, and the subtest passes only when the line ends in the second half of a period. Of the runs with output kept, Rach2 failed it in three of four and passed it in the traced one, and Linux passed it in all three. The subtest's premise, that a report line takes less than the half period left, does not hold at this depth under either host, and Rach2's vLAPIC keeps the count as Linux's does, so it is not listed as a gap. The CPUID exit's extra 37% under Rach2 is a cost, not a failure, and no case of the subset judges it.

## The gaps
### The NMI window's single step reached the guest (81-25.1)

`x2apic` under Rach2 stopped in `test_sti_nmi` with

```
PASS: PV IPIs testing
Unhandled exception 1 #DB(0) at ip 0000000000400234
error_code=0000      rflags=00000346      cs=00000008
```

0x400234 is the `nop` after the STI-shadowed `testb` at `post_sti` (0x400231) of the staged `apic.flat`, and RFLAGS 0x346 has TF, which the test never sets. Neither host has a virtual NMI under the outer layers, so both open the NMI window by stepping the guest. Rach2 kept the step armed through an event's injection (`rach2/sys/kvm/svm.c`: `entry_fields` sets TF and RF while `nmi_ss` holds, and `svm_inject` injected with it held): the event's frame on the guest's stack took TF, the step ended at its #DB, and the guest's IRET put TF back, so the next instruction's #DB went to the guest. Linux 6.12.115 disarms the step whenever it injects an event and exits at once after the delivery (`arch/x86/kvm/svm/svm.c:4356-4373`, with `disable_nmi_singlestep` at `svm.c:1058-1069`). `svm_enter` now does the same, with a self-IPI that the processor takes as an exit once GIF is set.

After the fix, on 2026-11-12, `x2apic` ran its 56 subtests under Rach2 in 803 s and failed `nmi-after-sti`, as Linux does, and `TMCCT should not be reset to TMICT value`, which depends on the timing of a report line (the final runs, above).

### The speculation controls (81-25.2)

`msr` ran 1,838 subtests under Rach2 and 1,844 under Linux, and passed under both. `test_mitigation_msrs` (x86/msr.c) reads and writes IA32_SPEC_CTRL with each of the eight combinations of IBRS, STIBP and SSBD where CPUID offers them, and checks only the #GP of both accesses where it does not. Rach2's KVM offered no speculation control: in `rach2/sys/kvm/cpuid.c` leaf 7's EDX lacked SPEC_CTRL, INTEL_STIBP, SPEC_CTRL_SSBD and FLUSH_L1D, leaf 0x80000008's EBX was empty, and `rach2/sys/kvm/msr.c` had no SPEC_CTRL, PRED_CMD or FLUSH_CMD.

The KVM now offers them as Linux 6.12.115 does where the host has them: leaf 7's bits and leaf 0x80000008's AMD_IBPB, AMD_IBRS, AMD_STIBP, AMD_STIBP_ALWAYS_ON, AMD_SSBD, AMD_SSB_NO and AMD_PSFD, each completed from the other vendor's bits (`arch/x86/kvm/cpuid.c:702-719`, `776-803`), and on SVM VIRT_SSBD where the host has AMD_SSBD (`svm/svm.c:5423-5425`). SPEC_CTRL takes a value the host's own register takes, tested by writing it and putting the old one back, as `kvm_spec_ctrl_test_value` (`x86.c:12867-12890`); PRED_CMD's IBPB and FLUSH_CMD's L1D flush run on the host (`x86.c:3381-3421`); SVM's VIRT_SPEC_CTRL holds SSBD (`svm/svm.c:3148-3156`). Every access of SPEC_CTRL exits, and SVM's and VMX's entries load the guest's value, with SSBD added where VIRT_SPEC_CTRL asks for it, when it differs from the host's, and put the host's back after the exit, as Linux does where it intercepts the register. ARCH_CAPABILITIES is still not offered: Linux's value names the host's processor flaws, from its list of them in `arch/x86/kernel/cpu/common.c`, which Rach2's kernel does not keep.

After the change, `msr` ran Linux's 1,844 subtests under Rach2 and passed, in 112 s, and passed again at the final commit, in 107 s.

### The counters' excess (81-25.3)

In the subset's runs `pmu` failed 32 of its 77 subtests under Rach2 and 22 under Linux. The ten more were the branch counts, `AMD: branches-0` to `-5` and `AMD: K7: branches-0` to `-3`, at 1,134,210 to 1,247,009 for a bound of 1,100,000, and Rach2's instruction counts read 6 to 52% high to Linux's 2 to 13%. Run alone under `tests/kvm/exits.sh` ([81-25/](81-25)), the test took 29,234 exits under Rach2 and 8,829 under Linux:

| Exit | Rach2 | Linux |
|---|---|---|
| nested page fault, 0x400 | 16,047 | 280 |
| I/O, 0x7b | 7,528 | 7,266 |
| interrupt, 0x60 | 4,548 | 212 |
| CPUID, 0x72 | 602 | 602 |
| MSR, 0x7c | 490 | 410 |
| the rest | 19 | 59 |

Two kinds make the difference. The nested page faults fill the test's 64 MiB loop buffer, 16,384 pages of 4 KiB, which Rach2 maps a page at a time and Linux in 2 MiB pages, as [81-7.md](81-7.md) found of the Debian guest's boot. They fall in the first loop that touches the buffer and stretch the test from 6 s to 15 s, but no count the test judges. The interrupts are the host's tick on the vCPU's processor, at 1000 Hz on Rach2 (`TICK_HZ` in `rach2/sys/timer.h`) and at 250 Hz on Debian's kernel, whose package's configuration has `CONFIG_HZ=250`. Each one during a measured loop is an exit, and the guest's counter counts the work of that exit beneath the host as well, in WSL's KVM or Hyper-V, since the outer KVM does not keep the Guest-only bit of the host's own selectors ([upstream.md](upstream.md#linuxs-kvm-drops-the-guest-only-and-host-only-bits-of-an-amd-guests-event-selectors)); Rach2's KVM runs a guest's counters only between the entry and the exit (`kvm_pmu_svm_enter` and `kvm_pmu_svm_exit` in `rach2/sys/kvm/pmu.c`), with Guest-only set. A kernel built with `TICK_HZ` 200, for this one run, took 624 interrupt exits; its instruction counts read 2.2 to 2.4% high but for two, every branch count was in bounds, and the test failed 19 subtests to Linux's 22.

So the gap is the tick's rate under an outer KVM that counts its own work, not Rach2's KVM, and 81-25.3 changes no code. On a machine of its own the processor keeps Guest-only and the tick adds nothing to a guest's counts. Linux would match Rach2 here only with a slower tick for the whole kernel or by stopping the tick on a processor while it runs a guest, which Linux does only under `nohz_full`; either is a change to the kernel's timekeeping, which `rach2/sys/arch/x86/Readme.md` gives as a periodic 1000 Hz tick on every processor, and is the owner's to order.

## The tools

The task found and fixed four faults of the tools on its way, each named in its commit, and moved the Linux side's run into `linux-corpus.sh -k unit`, so that one script boots Linux in the nested machine for either corpus:

* `tests/kvm/guests/linux-host-init` had no `/dev/fd`, so every kvm-unit-test under Linux skipped on `arch-run.bash: /dev/fd/63: No such file`; it now makes the links after it mounts devtmpfs.
* The same init took `sda` for the GNU root, but the two AHCI disks probe in either order, and 21 of 60 boots stopped on `Can't lookup blockdev`; it now takes the disk with a partition table.
* `corpus.sh` ran the whole list in one `run_tests.sh`, so no test's seconds were known and a test that never ended held the rest; it now runs one test at a time and prints each one's seconds after its result.
* With one `run_tests.sh` a test, each run moved the runner's `logs/` to `logs.old` and removed the one before (`run_tests.sh` lines 191-193), so the judge found only the last two tests' logs; each test now has its own `unittest_log_dir`.

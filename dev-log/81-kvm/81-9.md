# Guest performance counters (81-9)

The counter implementation is on `task/3363`. On the testing PC, the AMD half gives Linux's results in all six PMU rows (81-9.1, [below](#the-testing-pc)). The Intel half, 81-9.2, had its first trial on the Lenovo on 2026-11-11 ([below](#the-lenovo-first-trial)): four rows matched Debian, `pmu_lbr` skipped where Debian passes it, and `pmu_counters_test` failed on fixed counter 0. The second Intel design, which switches the counters as Linux does, gives the guest the LBR stack, and places each guest counter on a physical counter its event may use beside the detector's, compiles, and waits for its own trial, whose steps are on task 3363.

## Implementation

`rach2/sys/kvm/pmu.c` implements the registers, CPUID, event filters, per-VM disable, RDPMC, overflow delivery and Intel's legacy LBR stack. The register contract and the switching are in [the KVM Readme](../../rach2/sys/kvm/Readme.md#performance-counters).

Linux 6.12.115's `arch/x86/kvm/pmu.c`, `svm/pmu.c`, `vmx/pmu_intel.c`, `vmx/vmx.c` and `x86.c` are the reference: counter indices and widths, selectors, global-register permissions, capability changes, reset, RDPMC, masked filters, the emulated retired-instruction event, the atomic switch of IA32_PERF_GLOBAL_CTRL, PERF_CAPABILITIES' LBR format, DEBUGCTL's supported bits and the freeze of the LBR stack on a PMI. Linux 6.12 computes the architectural events a guest's CPUID marks unavailable but does not stop them from counting, and `pmu_counters_test` makes no check of their counts, so Rach2 does the same.

The milestone's hard-lockup detector, merged into this task on 2026-11-11, holds one counter and its NMI on each processor while it runs: Intel's fixed counter 1 where the processor has it, as Linux's scheduler places the cycles event, and general counter 0 otherwise and on AMD. The first design wrote every physical counter at every entry: VMX's host list cleared GLOBAL_CTRL and the selectors, and SVM's entry cleared every counter and selector, so a guest's run stopped the detector. A guest's counters, general and fixed, now run on the counters the host does not hold, each on one its event may use by Linux's constraint tables, a guest's fixed counter on a general one when the host holds its fixed counter; the host's counters count in the guest as Linux's do. Linux's exclusion of memory events between a core's two threads on Sandy Bridge, Ivy Bridge and Haswell, and family 10h's shared northbridge counters, are not done; the KVM Readme lists them among its limits.

The first design zeroed each Intel counter through the VM-entry MSR-load list and read it through the VM-exit MSR-store list while it still counted. On the Lenovo that overcounted fixed counter 0 in a few windows of each thousand ([below](#the-fixed-counter-fault)). The second writes no counter: the selectors and FIXED_CTRL are set before the entry, while the host's global control holds them stopped, the VMCS's load controls switch IA32_PERF_GLOBAL_CTRL, and each count is read before the entry and after the exit that stopped it.

Debian passes `pmu_lbr` on the Lenovo with Haswell's 16 records, so the stack is part of this task. PERF_CAPABILITIES offers the host's LBR format from format 4 on; a guest with it has DEBUGCTL's LBR and FREEZE_LBRS_ON_PMI, and its LBR registers go through the entry's and exit's MSR lists while DEBUGCTL.LBR is set. The guest's accesses of them exit, and a write is tried on the processor's register first, so that it faults where the guest's own WRMSR would under Linux, which passes the registers through. PEBS is not offered; Debian skips `pmu_pebs` on the Lenovo too.

`tests/kvm/corpus.sh` sets `kernel.nmi_watchdog` to 0 for its run and puts it back on every exit, since the merged detector makes it read 1: kvm-unit-tests' configuration skips `pmu` and `pmu_lbr` unless it reads 0, and `pmu_counters_test` uses every general counter. Its new flag `kvm_lbr`, read from the PERF_CAPABILITIES that `/dev/kvm` offers, settles `pmu_lbr`'s row: pass where KVM offers an LBR format, as on the Lenovo, and skip elsewhere, as on the testing PC.

## Readiness for the Lenovo

The VMX path and its bounded preemption timer are recorded in [81-3](81-3.md#readiness-81-3b1). These are the second design's new paths on the Intel machine.

* The VMCS's controls that load IA32_PERF_GLOBAL_CTRL, exit control bit 12 and entry control bit 13, are set only where the TRUE capability MSRs allow both and the host has the register, PMU version 2, as on the Haswell; their fields, 0x2808 and 0x2C04, hold only bits of counters that exist, the host's being the register's own value with the guest's counters cleared. Intel's SDM volume 3C, sections 27.2.2 and 27.3.1.1, refuses reserved bits there; a refusal is a failed entry, reported to the caller, not an abort. Linux uses the same controls on this processor. Nehalem and Westmere, family 6 models 0x1A, 0x1E, 0x25, 0x2C and 0x2E, whose exits may clear the register's fixed-counter bits, switch it by the MSR lists instead, as Linux's `setup_vmcs_config` does; the Haswell, model 0x45, keeps the controls. The detector's move to core counter 2 on AMD's family 15h leaves Intel's path as it was.
* The host's MSR-load list on the Haswell is the five fixed entries it had before the PMU: GLOBAL_CTRL goes to it only without the VMCS's controls, and the selectors only on a version 1 PMU. A failure of the host list is a VMX abort, so nothing new enters it on this machine.
* The guest's list carries the LBR stack only while the guest's DEBUGCTL.LBR is set: LBR_SELECT, LBR_TOS and 16 FROM and TO registers, 34 entries after the six fixed ones, below the host list at entry 128. At the boot each of them is read and written back with its own value through the safe MSR instructions, with interrupts off, and the stack is offered only if all 34 take it. A guest's write is tried on the register before it is kept, and each FROM value is loaded with Linux's sign-extension for format 4 without TSX. A refused entry of the list is a failed entry, reported to the caller.
* No physical performance interrupt is enabled by KVM: the selectors have INT and PIN cleared and a guest's FIXED_CTRL fields only OS and USR. On the Haswell the detector runs on fixed counter 1, field 0xB of FIXED_CTRL. The entry writes FIXED_CTRL only when it changes, with the host's fields of the fixed counters it holds kept and the guest's fields added, while the host's GLOBAL_CTRL has the guest's counters cleared; the guest's fields stay after the exit, gated off by GLOBAL_CTRL, so the host's next read does not count them as held. The detector's counter keeps its field, its count and its NMI; it counts in the guest, and its NMI there exits the guest as any NMI does and reaches the host's handler after VMX is off, as before.
* With the detector on, the guest's general counters map to the same physical ones and its fixed counter 1, event 0x3C, runs on a free general counter; when every general counter is in use it does not count, as Linux's pinned perf event would not. `corpus.sh` turns the detector off for the rows, as Debian's run does.
* GUEST_IA32_DEBUGCTL holds LBR and FREEZE_LBRS_ON_PMI, bits 0 and 11, only for a guest with the stack, and BUS_LOCK_DETECT and RTM_DEBUG, bits 2 and 15, only where the host's CPUID.7 has them, which the Haswell's does not. The exit clears the processor's DEBUGCTL, which the host does not use.
* The new loops are bounded by eight general counters, three fixed counters and 32 records. There is no new wait or polling loop.
* The placement is a bipartite matching over at most 11 counters, with recursion bounded by the counters' count.
* The model runs the entry's programming, the VMCS's values and the lists, the simulated run, the exit's collection and the LBR stack's lists in that order, and checks the detector's registers before and after. It does not execute VMX. The first guest, run alone, is the first real run of the VMCS's controls, and `pmu_lbr` of the LBR lists.

The SDM reference is [Intel's volume 3C](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3c-part-3-manual.pdf). The trial is silent and headless, with `mixer vol 1` after every Rach2 boot. It uses the kept GNU trial root and Debian guest and never commits a trial kernel. Its ordered commands and the return to the release are on task 3363.

### The fixed-counter fault

`pmu_counters_test`, built from 6.12.115 with each count printed, failed only on fixed counter 0 under Rach2, in about 3 of some 1,300 fixed-counter windows a run, by 3 to 15. The same binary on Debian, three runs, printed none. A probe that counts one window 200,000 times reproduced it: fixed counter 0 alone overcounted in 263 to 525 windows of 200,000, by 1 to 22, while a general counter counting event 0xC0 was exact in every window. A second probe, a real-mode guest on `/dev/kvm`, showed no carry from one window to the next and a rate that grows with the entries and exits inside a window: 41 to 62 windows of 30,000 with none, 372 to 396 with ten. Any general counter programmed with 0xC0, even counting user mode only, made fixed counter 0 exact again; one counting cycles did not. Linux never writes a counter at an entry, switches GLOBAL_CTRL by the VMCS and reads a counter only after it has stopped, which the second design does.

The logs are in [81-9/](81-9): Debian's `lenovo-linux-pmu.log`, `lenovo-linux-pmu_lbr.log`, `lenovo-linux-pmu_pebs.log`, `lenovo-linux-selftests.txt` and `lenovo-linux-counters-printed.txt`, and Rach2's `lenovo-rach2-1-unit.txt`, `lenovo-rach2-1-pmu_lbr.log` and `lenovo-rach2-1-selftests.txt`. ### The cause and the fix

Fable read the switching code against Linux's and the probes' sources. The probe's general-counter mode never counted on a general counter alone: `GUEST_MEASURE_EVENT` expands its value unparenthesized, so `(mode & 2) ? 1ull : BIT_ULL(32)` put 1 in EDX in every mode, and modes 2 and 3 enabled global bits 0 and 32 together. With both guest counters running, the placement gave the guest's general counter 0 physical fixed counter 0, and the guest's fixed counter 0 physical general counter 0 counting 0xC0 beside it, which is the first trial's cure. So in every measurement the physical fixed counter 0 overcounts when it counts retired instructions with no general counter counting them beside it, and is exact otherwise; a guest counter on a physical general counter was exact in every window of the first design's selftest and kvm-unit-tests runs.

Nothing in Rach2's entry, exit or host code adds the counts: the counter that is read is programmed alike in the good and the bad mode, its base is read while it is stopped and its count after the exit has stopped it, no host code sets global bit 32, and the run is under interrupts off. Linux places the same events on the same counter, in the same order of writes, with no quirk for it, and is exact on the same machine; which difference keeps it so (its PMI bit in the fixed field, its counter written to minus the period before the start, DEBUGCTL.FREEZE_IN_SMM, VMX left on between runs, or its idle sibling thread against Rach2's 1000 Hz tick) is not known. Fable recalled a Haswell erratum on fixed counter 0 overcounting retired instructions with Hyper-Threading on; its number and text were not checked.

The second trial's failures are this fault. `pmu_counters_test` failed in version 1's arch events, where the guest has no fixed counter: the failing counter was a general counter counting 0xC0, which the placement put alone on physical fixed counter 0, as it did the general counter 2 of `pmu`'s `instructions-2`.

5974149ec places a guest counter on fixed counter 0, on the models with Haswell's table, only when no general counter its event may use is free; Linux's order, fixed counters first, holds elsewhere. A guest that uses all four general counters and fixed counter 0 still runs one on fixed counter 0, as Linux would. The probe's value is now one variable, and `pmcwin`'s mode 0 expects the four extra instructions in the first window alone; both are in `build/runs/pmu-3363-2/probe` on the Mac.

## The testing PC

On 2026-11-11 the six rows ran on the testing PC, an x86-64 Rach2 booting the GNU test disk with the rows' lists narrowed to them, by `tests/run kvm` with `RACH2_CASES`: `machine.kvm.unit-tests-nested` and `machine.kvm.selftests-nested` under WSL's KVM on `host-svm`, so that Rach2's guest counters are the counters WSL's KVM gives Rach2, and `machine.kvm.unit-tests` and `machine.kvm.selftests` under TCG, which gives Rach2 none. The processor has PerfCtrExtCore and no PerfMonV2, at both depths.

| Row | Linux on the testing PC | Rach2 under WSL's KVM | Rach2 under TCG |
| --- | --- | --- | --- |
| `pmu` | fail, 7 to 10 overflows | fail, as Linux 6.12.115 at the same depth | skip: `enable_pmu` is `N` |
| `pmu_lbr`, `pmu_pebs` | skip | skip | skip: `enable_pmu` is `N` |
| `pmu_event_filter_test` | pass | pass | skip |
| `pmu_counters_test` | skip: not Intel | skip: not Intel | skip |
| `vmx_pmu_caps_test` | skip: no PDCM | skip: no PDCM | skip |

Three faults in Rach2 kept kvm-unit-tests from comparing at first, each fixed on this task. Its runner skips `pmu` unless `/proc/sys/kernel/nmi_watchdog` reads 0, and `pmu_lbr` unless KVM's `ignore_msrs` parameter reads `N`; Rach2 had neither file. It now reads `ignore_msrs` as `N`, read-only, and `nmi_watchdog` is the merged detector's, writable, which reads 1 while a counter runs, so `corpus.sh` sets it to 0 for its run. `corpus.sh` threw away the runner's log of a failed test; it now prints it, so a failure names its subtests.

`pmu` cannot pass under a hypervisor on this PC, on Linux or on Rach2. Linux's KVM clears the Guest-only bit of a guest's event selector ([upstream](upstream.md#linuxs-kvm-drops-the-guest-only-and-host-only-bits-of-an-amd-guests-event-selectors)), so a counter that a hypervisor inside it enables counts the work done for that hypervisor's guest on each exit. Run directly by WSL's Linux 6.18.58, the test fails 7 to 10 of its overflow subtests, by turns, in five runs. Run by Debian 13's Linux 6.12.115 in a guest of WSL's KVM, as deep as Rach2's KVM is, it fails 21 or 22 of 77 in five runs: nearly every instruction count of its 10,000,000-instruction loop is high, at 10,205,211 to 10,283,110 against a bound of 10,200,000, as are the six counters together and every overflow; its branch counts pass. Rach2's KVM there fails 30 or 31 in two runs: instruction counts of 10,396,086 to 10,767,419, the six together, every overflow, and eight of ten branch counts, 1,103,547 to 1,140,045 against a bound of 1,100,000. Rach2 took 30,781 exits in the test's 16.7 s, Linux 8,800 in 6.3 s, of which 197 to 224 were interrupts; Rach2's tick is 1000 Hz and Debian's 250 Hz.

Before this run, Rach2 started each AMD counter in the middle of the writes that switch the others, each of which is an exit to WSL's KVM while the counter runs; its counts were 10,744,235 to 11,032,074 and its branches up to 1,418,622, with 32 failures. The run above stopped and cleared every counter before it started any, and stopped all before it read them; the second design keeps that order with no counter cleared, the host's own counter untouched, and each count read before VMRUN and after the selector stops. The row expects `pmu` to pass on a machine of its own, fail under a hypervisor, and skip without counters, which kvm-unit-tests' configuration requires.

The logs are in [81-9/](81-9): `linux-wsl-pmu.1.log` to `.5.log`, `linux-nested-pmu.log` and `rach2-nested-pmu.log`. The kvm-unit-tests binary was the GNU root's, `pmu.flat` SHA-256 a8244678e9743de87f023a6ee18a049a9be1ce9300ba6a98282914ed1910a681, in every run.

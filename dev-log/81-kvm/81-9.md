# Guest performance counters (81-9)

The counter implementation is on `task/3363`. On the testing PC, the AMD half gives Linux's results in all six PMU rows (81-9.1, [below](#the-testing-pc)). The Intel half, 81-9.2, compiles and passes the register model, and waits for its trial on the Lenovo, which compares it with Debian there; its steps are on task 3363.

## Implementation

`rach2/sys/kvm/pmu.c` implements the registers, CPUID, event filters, per-VM disable, RDPMC and overflow delivery. The SVM backend switches AMD's physical counters around VMRUN, with GuestOnly selectors. The VMX backend appends Intel's counters and selectors to its existing guest MSR load/store area and the disabling writes to its host MSR load area. The register contract is in [the KVM Readme](../../rach2/sys/kvm/Readme.md#performance-counters).

Linux 6.12.115's `arch/x86/kvm/pmu.c`, `svm/pmu.c`, `vmx/pmu_intel.c` and `x86.c` are the reference: counter indices and widths, selectors, global-register permissions, capability changes, reset, RDPMC, masked filters and the emulated retired-instruction event. Physical counters belong to KVM on Rach2; there is no host perf subsystem to share them with.

LBR and PEBS are not implemented. The recorded Linux reference on the testing PC skips both, but there is no Lenovo PMU reference yet. A skip caused by their omission here is not proof of parity: if Debian on the Lenovo passes either row, its implementation remains part of this task. The lists' Intel expectations must be settled from that reference, with the same binaries and QEMU CPU options. The testing PC's recorded `pmu` result is 77 tests with 10 unexpected failures and 10 skips; the output of those failures must be compared too, rather than treating every failed PMU run as equivalent.

## Readiness for the Lenovo

The new Intel path is the PMU list appended by `kvm_pmu_vmx_enter`, stored by VM exit, and collected by `kvm_pmu_vmx_exit`. The existing VMX path and its bounded preemption timer are recorded in [81-3](81-3.md#readiness-81-3b1).

* Boot discovery on Intel reads CPUID only. No PMU MSR is written until a guest runs. The optional safe MSR instructions and their two exact #GP fixups serve AMD's counter probe; the Intel backend never calls that probe.
* The lists occupy the existing single physical MSR page. The guest's list has at most 27 entries including the existing six, below the host list at entry 128. Each new entry has a 32-bit MSR index, a zero reserved word and a 64-bit value. Counts are rewritten at every entry, including a vCPU with no PMU, so old entries cannot leak into a later run.
* The guest list zeros physical counters, loads validated selectors and the fixed control, then enables only the counters that preparation chose. The host list disables global counting before clearing selectors and fixed control. Guest-controlled values never enter the host list. Intel's SDM volume 3C, sections 26.4 and 27.6, defines the lists' order and checks; the PMU entries use writable MSRs that CPUID qualifies. A host-list failure causes a VMX abort, so the first guest is run alone and its return is checked before any corpus row.
* No physical performance interrupt is enabled. The physical general selectors have INT and PIN cleared, and fixed control has only OS and USR. Counters start at zero on each entry; virtual wrap and PMI are calculated after exit. This needs no new interrupt handler, interrupt unmask or wait.
* The new loops are bounded by eight general counters, three fixed counters, 300 filter entries or the existing vCPU limit. There is no new polling loop. The existing external-interrupt exits and VMX preemption timer still bound guest execution. PMI delivery happens under the big lock before the next entry, through the existing local APIC path.
* The new model runs the list builder, simulated list loads and stores, counter collection and PMI preparation in that order. It verifies that the host list stops counting and that a second vCPU sees no residue. It does not execute VMX or qualify hardware event encodings. The first real guest and the corpus supply that remaining evidence.

The SDM reference is [Intel's volume 3C](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3c-part-3-manual.pdf). The trial is silent and headless, with `mixer vol 1` after every Rach2 boot. It uses the kept GNU trial root and Debian guest from 81-3 and never commits a trial kernel. Its ordered commands, Linux comparison and return to the release are on task 3363. No hardware was written during this implementation session.

## The testing PC

On 2026-11-11 the six rows ran on the testing PC, an x86-64 Rach2 booting the GNU test disk with the rows' lists narrowed to them, by `tests/run kvm` with `RACH2_CASES`: `machine.kvm.unit-tests-nested` and `machine.kvm.selftests-nested` under WSL's KVM on `host-svm`, so that Rach2's guest counters are the counters WSL's KVM gives Rach2, and `machine.kvm.unit-tests` and `machine.kvm.selftests` under TCG, which gives Rach2 none. The processor has PerfCtrExtCore and no PerfMonV2, at both depths.

| Row | Linux on the testing PC | Rach2 under WSL's KVM | Rach2 under TCG |
| --- | --- | --- | --- |
| `pmu` | fail, 7 to 10 overflows | fail, as Linux 6.12.115 at the same depth | skip: `enable_pmu` is `N` |
| `pmu_lbr`, `pmu_pebs` | skip | skip | skip: `enable_pmu` is `N` |
| `pmu_event_filter_test` | pass | pass | skip |
| `pmu_counters_test` | skip: not Intel | skip: not Intel | skip |
| `vmx_pmu_caps_test` | skip: no PDCM | skip: no PDCM | skip |

Three faults in Rach2 kept kvm-unit-tests from comparing at first, each fixed on this task. Its runner skips `pmu` unless `/proc/sys/kernel/nmi_watchdog` reads 0, and `pmu_lbr` unless KVM's `ignore_msrs` parameter reads `N`; Rach2 had neither file, and now gives both as a Linux without the hard lockup detector does, read-only. `corpus.sh` threw away the runner's log of a failed test; it now prints it, so a failure names its subtests.

`pmu` cannot pass under a hypervisor on this PC, on Linux or on Rach2. Linux's KVM clears the Guest-only bit of a guest's event selector ([upstream](upstream.md#linuxs-kvm-drops-the-guest-only-and-host-only-bits-of-an-amd-guests-event-selectors)), so a counter that a hypervisor inside it enables counts the work done for that hypervisor's guest on each exit. Run directly by WSL's Linux 6.18.58, the test fails 7 to 10 of its overflow subtests, by turns, in five runs. Run by Debian 13's Linux 6.12.115 in a guest of WSL's KVM, as deep as Rach2's KVM is, it fails 21 or 22 of 77 in five runs: nearly every instruction count of its 10,000,000-instruction loop is high, at 10,205,211 to 10,283,110 against a bound of 10,200,000, as are the six counters together and every overflow; its branch counts pass. Rach2's KVM there fails 30 or 31 in two runs: instruction counts of 10,396,086 to 10,767,419, the six together, every overflow, and eight of ten branch counts, 1,103,547 to 1,140,045 against a bound of 1,100,000. Rach2 took 30,781 exits in the test's 16.7 s, Linux 8,800 in 6.3 s, of which 197 to 224 were interrupts; Rach2's tick is 1000 Hz and Debian's 250 Hz.

Before this run, Rach2 started each AMD counter in the middle of the writes that switch the others, each of which is an exit to WSL's KVM while the counter runs; its counts were 10,744,235 to 11,032,074 and its branches up to 1,418,622, with 32 failures. It now stops and clears every counter before it starts any, and stops all before it reads them. The row expects `pmu` to pass on a machine of its own, fail under a hypervisor, and skip without counters, which kvm-unit-tests' configuration requires.

The logs are in [81-9/](81-9): `linux-wsl-pmu.1.log` to `.5.log`, `linux-nested-pmu.log` and `rach2-nested-pmu.log`. The kvm-unit-tests binary was the GNU root's, `pmu.flat` SHA-256 a8244678e9743de87f023a6ee18a049a9be1ce9300ba6a98282914ed1910a681, in every run.

# Linux's KVM selftests against Linux at the same depth (81-26)

Linux 6.12.115's x86 KVM selftests ran on 2026-11-12 with Rach2 as the KVM host, and the same programs with Debian's Linux 6.12 as the host, each under the testing PC's KVM in the same outer QEMU, so that every difference is one between the two kernels' KVM. Rach2 differs from Linux on 3 of the 66 tests, and on 3 more inside tests that both pass or skip. Five causes cover the six, each a card of milestone 81: no consecutive frames for SVM's MSR permission map (4670), no Xen HVM emulation (4671), no dirty ring (4672), 256 memory slots where Linux has 32764 (4673), and no KVM_CAP_VM_DISABLE_NX_HUGE_PAGES (4674).

## The run

* The machine. The testing PC, a Ryzen 9 7950X3D, with WSL's Linux 6.18.58 and QEMU 10.2.1 outside, under KVM, on the `host-svm` processor of etude (`tools/etude/processor.c`): `host,svm=on,npt=on,nrip-save=on,tsc-scale=on,vmcb-clean=on,flushbyasid=on,pause-filter=on,decodeassists=off,v-vmsave-vmload=off,vgif=off,invtsc=on`, two processors and 6 GiB, the GNU root's disk and the KVM suite's data disk on AHCI, each behind a qcow2 overlay. The selftests' guests run a level below Rach2 or Linux, three hypervisors deep with Hyper-V.
* Rach2. The x86-64 kernel and GNU root of the milestone branch at 922369cee with this task's runner commits, which change no kernel code, as `machine.kvm.selftests-nested` boots them, with `RACH2_KVM_SELFTESTS=selftests-gap.list`.
* Linux. Debian's 6.12.107+deb13-cloud-amd64 with its own `kvm` and `kvm-amd` modules, booted by `tests/kvm/linux-corpus.sh` with the same disks; `corpus.sh` runs in a chroot of the same GNU root.
* The programs. The KVM layer's build of the selftests of Linux 6.12.115 (`vendor/gnu/kvm`), static with the GNU root's glibc, in `/opt/kvm-selftests`, the same files on both sides. Rach2's KVM ABI (`rach2/sys/kvm/kvm_abi.h`) is Linux's, so the programs need nothing of their own for Rach2.
* The subset, `tests/kvm/selftests-gap.list`: the 66 programs `selftests.list` runs, without the 19 the owner excluded, with smaller sizes for six: `demand_paging_test`, `dirty_log_perf_test` and `memslot_modification_stress_test` with `-b 64M`, `kvm_page_table_test` with `-b 128M`, `dirty_log_test` with `-i 4`, and `max_guest_memory_test` with `-m 4`. At their defaults a first run took 124 s on Linux and 267 s on Rach2 for `demand_paging_test` alone (2,115 and 985 pages a second of demand paging), 312 s on Linux for `dirty_log_perf_test`, of which 160 s populated its gigabyte, and 207 s on Linux for the first of `dirty_log_test`'s three modes; that run was stopped once those figures were read.

| System | Pass | Skip | Fail | Seconds in the programs | The run |
|---|---|---|---|---|---|
| Linux 6.12.107 | 49 | 15 | 2 | 1,337 | 21 min, and 105 s for `hardware_disable_test` alone |

Linux's first run gave `hardware_disable_test` a segmentation fault at once: its `sem_open` needs `/dev/shm`, which the Linux host's chroot lacked. With a tmpfs there, as `linux-host-init` now mounts, it passed alone in 105 s, and the table counts that pass. The host also named its two disks in the order their probes ended, which once made the data disk `sda`; `linux-host-init` now takes the disk with a partition as the root.

The two systems took about the same time on most programs, which here is the cost of the nested layers more than of either kernel. Rach2 was slower where guest pages are first touched: 662 s against 484 s for `max_guest_memory_test` at 4 GiB, 40 s against 18 s for `dirty_log_perf_test`, whose 64 MiB took 13.3 s against 10.1 s to populate, and 1,290 against 1,570 pages a second of demand paging. The cost of an exit is 81-24's.

### No consecutive frames for SVM's MSR permission map (4670)

`hardware_disable_test` forks 512 children, each with a VM of four vCPUs and 64 other threads, and kills each one. On Rach2 a KVM_CREATE_VCPU fails with ENOMEM within 18 s. It is not a leak: a sampler of `/proc/stat` and `/proc/meminfo` each second saw at most 2 VMs and 7 vCPUs alive, 6 GiB free and 12 MB of heap in use when the call failed, and every KVM count back to 0 after. A log line in `svm_vcpu_init`, in a kernel of this run's alone, printed `kvm: diag: vcpu_init: vmcb 1 host 1 msrpm 0 fpu 1`: the 8 KiB MSR permission map failed. It comes from `kvm_map_pages(2, ...)` (`rach2/sys/kvm/svm.c:2633`, `rach2/sys/kvm/vcpu.c:221-254`), which takes runs of heap pages until one has consecutive frames and gives up after 16. The heap's pages are consecutive only in virtual memory (`rach2/sys/mm/kheap.h:4-6`) and nothing after the boot gives consecutive frames (`rach2/sys/mm/heap.h:1-8`), so the map depends on the order in which the frame allocator hands out what process exits gave back. Linux takes an order-1 block of the buddy allocator (`arch/x86/kvm/svm/svm.c:870-880`). VMX's maps are single pages.

### No Xen HVM emulation (4671)

Debian's kernel has CONFIG_KVM_XEN, and its KVM answers KVM_CAP_XEN_HVM with the hypercall MSR, the hypercall intercept, the shared info page and the event channels (`arch/x86/kvm/x86.c:4267-4280`, `arch/x86/kvm/xen.c`). Rach2's answers 0 (`rach2/sys/kvm/kvm.c:189-265`), so both Xen tests skip. The reference run under WSL's Linux 6.18.58, `ref/linux-selftests.status`, skipped them too: WSL's kernel is built without CONFIG_KVM_XEN.

### No dirty ring (4672)

`dirty_log_test` passes on both, but Rach2 prints `Log mode 'dirty-ring' not supported, skipping test` for its third mode, where Linux runs it with the vCPU stopping on a full ring and on a kick. Rach2 logs only in the slot's bitmap (`rach2/sys/kvm/dirty.c`) and answers 0 for KVM_CAP_DIRTY_LOG_RING and its ACQ_REL form; Linux answers the ring's largest size (`virt/kvm/kvm_main.c:4942-4951`) and keeps the rings in `virt/kvm/dirty_ring.c`.

### 256 memory slots (4673)

Linux answers KVM_CAP_NR_MEMSLOTS with 32764, SHRT_MAX less x86's 3 internal slots (`virt/kvm/kvm_main.c:4940-4941`, `include/linux/kvm_host.h:712-713`, `arch/x86/include/asm/kvm_host.h:69`), so `memslot_perf_test`'s map case prints `Memslot count too high for this test, decrease the cap (max is 8209)`. Rach2 answers 256, `KVM_MEM_SLOTS` (`rach2/sys/kvm/kvm.h:46-47`), the size of the array `by_id` that `rach2/sys/kvm/slots.c:52`, `159` and `173` keep and walk, and runs the case with 255.

### No KVM_CAP_VM_DISABLE_NX_HUGE_PAGES (4674)

Both skip `nx_huge_pages_test`, Linux because the program wants the token its script passes, Rach2 already at `kvm_has_cap(KVM_CAP_VM_DISABLE_NX_HUGE_PAGES)`. Linux answers 1 (`arch/x86/kvm/x86.c:4249-4253`) and takes the capability from a caller with CAP_SYS_BOOT before the first vCPU (`x86.c:6262-6290`); Rach2 answers 0.

## What is not a gap

* `memslot_perf_test` fails on both in its RW case, killed by SIGALRM: the host gives the guest 10 s to answer each sync (`alarm(10)` in `host_perform_sync`, `memslot_perf_test.c:418-426`), which neither guest meets three levels deep. Under WSL's Linux, one level up, it passes.
* `x86_64/fix_hypercall_test` fails on both in `disable_quirk`, at `fix_hypercall_test.c:75`, where the guest's VMCALL on AMD should end in the #UD that returns -EFAULT. WSL's Linux 6.18.58 passes it one level up. The cause was not traced, since the two kernels give the same result.
* The skips differ in three tests that both skip for a lack of the machine's: `dirty_log_page_splitting_test` skips on Linux for no hugetlb pages and on Rach2 first at `eager_page_split`, which Rach2's `/sys/module/kvm/parameters` reads as N (`rach2/sys/kvm/kvm.c:869`) and Linux as Y; `sev_migrate_tests` skips on Linux for no SEV and on Rach2 first at KVM_CAP_VM_MOVE_ENC_CONTEXT_FROM, which only SEV uses; and `nx_huge_pages_test`, above.
* KVM_CAP_MAX_VCPUS and KVM_CAP_MAX_VCPU_ID read 1024 and 4096 on Rach2 and 4096 and 16384 on Debian's kernel. Linux's default is 1024, and 4096 only under MAXSMP (`arch/x86/kvm/Kconfig:205-210`), which Debian sets; Rach2 has the default.
* `state_test` prints `will skip nested state checks` on Rach2, whose guests have no SVM, as the owner decided on 2026-11-10.
* The 19 tests that `selftests.list` excludes, by the owner's decisions of 2026-11-10, did not run.

No fault in another project's code was found.

# Milestone 23: installing the kernel from the machine

## The goal

Milestone 22 made Rach2 build its kernel. This milestone lets root install that kernel with `install-kernel` and reboot into it without a host tool. The same procedure works on today's QEMU GRUB disk and on a real BIOS notebook after the bare-metal milestone restores that target. A failed installation, invalid kernel, or power cut at any point must leave at least one bootable kernel. The interruption matrix identifies the possible kernel after every cut.

Stock GRUB remains the loader. Its FAT boot partition gains a second kernel and a GRUB environment block. Through a new root-only raw device, the guest updates only candidate-kernel and environment data sectors, never FAT metadata. GRUB's one-boot `next_entry` state makes each installation a trial that a power cycle revokes. The design adds no custom GRUB module, bootloader, or kernel FAT driver.

## Settled requirements

* The boot partition is a 16 MiB FAT32 volume created with `mformat -F` in `tools/mkdisk_grub.sh`; it is partition 1, while KRFFS is partition 2. MBR parsing currently lives inside `init_krffs_disk` and identifies KRFFS by reading partition contents. Phase 1 extracts a pure parser and retains its results so the boot-partition bounds come from the same table.
* GRUB loads one of two 8.3-safe short-name files. `/boot/kernel` remains the candidate path and is preallocated to the 2 MiB slot size. `/boot/fallback` contains the same kernel at image build and is never changed afterward. Add `--id` menu entries named `candidate`, `fallback`, and `debug`; the debug entry uses the fallback with `rach2.rescue`. Their command lines include either `rach2.slot=candidate` or `rach2.slot=fallback`, and `/proc/cmdline` tells the guest which entry booted.
* Create `/boot/grub/grubenv` at build time with `grub-editenv` and initialize it to `saved_entry=candidate`, making the candidate the fresh disk's default. The environment format has a header but no checksum, so a torn block can still load. `grub.cfg` therefore reads only `saved_entry` and `next_entry` and requires exact menu ids. Any other value, missing block, or failed `load_env` selects `fallback`. GRUB and the installer both rewrite the same 1024 bytes in place without moving or resizing the file.
* Accept valid fragmented FAT chains and write them cluster by cluster. Do not assume contiguity because "fresh file system, first file copied" is not a contract. The image build checks every staged chain with `mshowfat` and fails on a broken chain.
* Phase 0 replaced three hypotheses with observations, recorded in the phase 0 section below. GRUB's multiboot loader ignores trailing zeros after the ELF. `save_env` rewrites this FAT32 environment block in place. This GRUB build does not consume `next_entry` automatically, so the configuration uses Ubuntu's scripted pattern: require the exact id, set the default, clear the variable, and write it with `save_env`. Phase 0 also found that `fallback` cannot resolve an `--id` string and instead parses it as entry number 0. The configuration therefore sets `fallback=1` and fixes menu order in a comment.
* Keep existing `/dev` entries at mode 0666. These match Linux's mem and pty device modes, and session code opens the console as an ordinary user. The boot-partition device is the first restrictive entry, so add the permission model in the same phase.
* `/dev/bootpart` is synchronous and write-through. ATA and AHCI already flush the drive cache after every write, so a successful return means durable data. `file_ops` has no fsync operation, while `sys_fsync` flushes the KRFFS page cache for any valid descriptor. Preserve that behavior: fsync on this device harmlessly flushes the unrelated cache. Leave the close callback NULL and add no file or block operation.
* Require Docker because the container assembles the GRUB disk and every runtime test boots it. `make install-test` must fail with a named reason rather than skip when the daemon is absent. Start Docker before the goal run.
* Leave these items for the bare-metal milestone: the AHCI real-hardware reset sequence, the fixed `(hd0,msdos1)` prefix that should become a file-system-identifier search, reset methods beyond port 0xCF9, and UEFI-only machines. The installation mechanism must not depend on them.

## The interruption matrix

Installation follows this order: validate the named kernel; validate the fallback as a kernel; write `saved_entry=fallback`; write candidate data cluster by cluster and zero the rest of the slot; read back and revalidate the slot; then write `next_entry=candidate`. `install-kernel --commit` runs only when `/proc/cmdline` contains `rach2.slot=candidate`, and it writes `saved_entry=candidate`. A power cut has these outcomes:

* Before `saved_entry=fallback` completes, the environment is stale or torn. A stale block still identifies a bootable kernel. A torn block can fail `load_env`, fail the exact-id comparison, or retain a complete valid value. The old kernel or fallback boots, and both are valid.
* During the slot write, `saved_entry=fallback` is set and `next_entry` is absent. The fallback boots.
* After the slot write but before `next_entry`, the state is unchanged. The fallback boots, and rerunning `install-kernel` finishes installation.
* During the `next_entry` write, a torn block can fail to load, fail the exact-id comparison, retain the complete old value, or contain the complete new value. Either the fallback or newly validated candidate boots.
* During `--commit`, the same four tear cases apply to values that identify bootable kernels. Rerunning `--commit` completes the operation.

The phase 2 host test uses fault injection to create every row's on-disk state. Phase 4 boots host-built images for determinate states: a destroyed header, a complete old value, and a complete new value. It checks the predicted entry. The matrix guarantees that no state selects an invalid kernel; it does not require every state to select fallback. Torn states include sector prefixes and mixtures of old and new data across the block's two sectors because the block crosses a sector boundary. Phase 0 booted three examples. A destroyed header selects fallback because `load_env` fails. A value torn in the middle of a word fails the exact-id comparison and selects fallback. A block with intact leading lines and a torn, unterminated tail still loads through `load_env`; its intact `saved_entry` determines the boot. That observation defines the complete-old-value row.

## Phase 0: the GRUB experiment

Before changing the repository, assemble a variant GRUB disk by hand with scratch scripts and Docker. Include both kernels, a padded candidate, an environment block created by `grub-editenv`, and `loadenv` in the core image. Boot every state below in QEMU. These observations replace the earlier hypotheses:

* A 661548-byte host kernel padded with zeros to 2 MiB reached the login prompt. GRUB's multiboot loader takes load extents from program headers, so the padded and unpadded files booted to the same prompt.
* A configuration `save_env` wrote `exp_probe=written` to the same 1024 environment bytes in place. The host read the value back at the block's image offset.
* This GRUB build did not consume `next_entry` automatically. With the plain configuration, it ignored `next_entry=fallback` and left the value set. Scripted consumption compares the exact id, sets the default, runs `set next_entry=`, and runs `save_env next_entry`. With that script, the same state booted fallback once, saved an empty `next_entry=`, and returned to the candidate on the next boot.
* After zeroing the candidate's first 8192 bytes, `set fallback=fallback` made GRUB parse the id as entry number 0, retry the broken default, and print "Failed to boot both default and fallback entries". Changing it to `set fallback=1` booted fallback without a keypress. The `fallback` variable requires an entry number, making menu order part of the configuration contract.
* Three torn blocks matched the matrix: a destroyed header selected fallback; a value torn in the middle of a word selected fallback; and intact leading lines with an unterminated tail loaded, leaving the intact `saved_entry` to select the kernel.
* The container includes `grub-editenv` and `mshowfat`. On the 16 MiB partition, `mformat -F` creates a small FAT32 with 512-byte sectors, 1 sector per cluster, 32 reserved sectors, two FATs of 252 sectors, root cluster 2, first data sector 536, and about 32 thousand clusters. This lies below the conventional 65525-cluster boundary. Retain the raw BPB bytes with the experiment artifacts. `mshowfat` reports ranges such as `::/boot/kernel <5-4100>`. GRUB menus and errors reach the serial log only with `terminal_output serial console` and the `serial` and `terminal` modules in the core image. Phase 3 adopts these settings so the harness sees loader errors.

* Contingency: the scripted `next_entry` form was adopted as anticipated. Padding and `save_env` behaved as required, so no re-planning was necessary.
* Proof: one driver reproduces the sequence. For each step, it retains the input environment bytes, boot log, and post-boot readback so every observation has a recorded input and result rather than only a log.
* Readmes: none; no repo change beyond this plan.

## Phase 1: add device permissions, /dev/bootpart, and /proc/cmdline

Extract MBR parsing from `init_krffs_disk` into a pure function with a host test, and retain the parsed table. Give each `devfs` entry a mode. At open, enforce it against the caller's credentials with the same nine-bit permission check used by the file systems. Make `devfs_stat` and the `fstat` path read that mode; `fstat` currently reports 0666 for every device. A dynamically absent device must be absent from lookup, `stat`, open, and `/dev` getdents. Keep all existing modes at 0666 so existing opens do not change.

Add root-only `/dev/bootpart` with mode 0600. Publish it only when a block device is mounted and MBR partition 1 has nonzero bounds within the disk, a FAT type byte of 0x0b or 0x0c, and a half-open sector range disjoint from KRFFS. The partition layer otherwise only clamps each view to the disk and does not compare them, so these checks prevent boot-partition writes from reaching the mounted file system. Expose a bounded, seekable window. Both `lseek` and `_llseek` already handle devices and gain this case; `SEEK_SET`, `SEEK_CUR`, and `SEEK_END` use the partition size. Accept only whole 512-byte sectors and return `-EINVAL` otherwise. A read at the end returns 0, and a write past it returns `-ENOSPC`. Move every transfer through a kernel 512-byte bounce buffer with `copy_from_user` or `copy_to_user`, because AHCI programs physical DMA addresses and must never receive a user pointer. Writes remain synchronous and write-through.

Add `/proc/cmdline` as a global proc file beside the pid tree. Its contents are the captured boot command line followed by a newline. Add cases for classification, snapshot generation, inode and `stat` data, root `/proc` getdents, and `/proc/self/fd` origin rendering. Add a getter to `sys/cmdline` beside `kcmdline_has`.

* Proof: test the MBR parser on valid, zero-length, overflowing, type-mismatched, and partially overlapping tables; a missing 55AA signature; and a range that wraps past the disk end. Run `bootprobe` on a fixture disk with valid KRFFS in partition 2, whose mount publishes the device, and known raw FAT bytes in partition 1. Root must open it, seek to and read known bytes, write and read back a sector, read exactly 0 at the end, receive `-ENOSPC` past the end, and receive `-EINVAL` for unaligned I/O. An unprivileged open must return `-EACCES`. On a disk containing only KRFFS, the device must be absent and open must return `-ENOENT`. For `/proc/cmdline`, test every independent implementation branch: content equals the harness argument, `/proc` getdents lists the name, `stat` and `fstat` report the same identity, and `/proc/self/fd/N` renders the origin of an open descriptor. Give the host classifier the same cases.
* Shown failing: removing the device's end-bound translation changes the end read from 0 to the partition view's error, so the exact-value assertion fails. Removing the credential check lets the unprivileged open succeed, so the probe fails.
* Readmes: `rach2/sys/fs/synthfs.Readme.md` (the mode column, both new files), `rach2/Readme.md` where it lists devices.

## Phase 2: install-kernel

Implement the tool as two parts, following the host-test structure used by `pwauth`. A pure core parses the BPB, walks FAT, validates kernels, edits the environment, and performs all sector I/O through caller-supplied callbacks. A small guest `main` connects those callbacks to `/dev/bootpart`. Validate the BPB before using any field. Require 512-byte sectors to match the device, two FATs, and in-range cluster geometry, total sectors, FAT size, and root cluster, with overflow-safe arithmetic. A malformed BPB must not map a plausible cluster into another part of the partition. Accept the observed build product rather than a textbook threshold. On this 16 MiB partition, `mformat -F` creates FAT32 below the conventional 65525-cluster boundary. Phase 0 records that BPB, the valid fixture reproduces it, and phase 3 runs the host core on the staged partition, preventing the validator from rejecting the shipped image. Read both FAT copies and exit nonzero when they differ. Walk the namespace recursively from root, reading short entries and skipping `.`, `..`, deleted, free, LFN, and volume-label entries. The three required names are 8.3-safe; failure to resolve one as a short entry is an error. Resolve `/boot/kernel`, `/boot/fallback`, and `/boot/grub/grubenv`. Require every chain to be loop-free through a visited bound, contain only legal in-range clusters, and end properly. A regular file's chain length must match its directory size. FAT32 directory sizes are zero, so check directory chains only for range, loops, and a valid end. Every chain the installer writes must be pairwise disjoint and share no cluster with any other reachable chain, including directories and `grub.cfg`; a cross-linked candidate must not overwrite directory or loader data. Validate ELF32 kernels as `ET_EXEC` for `EM_386`, with multiboot magic, flags, and checksum aligned to four bytes within the first 8192 bytes, and a size that fits the slot. Edit the 1024-byte environment block in place and require GRUB's header. Follow the interruption matrix for installation and `--commit`, including fallback validation before writing `saved_entry=fallback`. After writing, compare the complete padded slot byte for byte with the intended image. Structural validation alone would miss a lost load sector away from the headers. `install-kernel --where` prints each file's sector extents for the phase 4 harness. Require `rach2.slot=` in `/proc/cmdline` before installation and `rach2.slot=candidate` before `--commit`. If the token is absent, exit nonzero and identify the missing state. This also handles a `-kernel` boot with a boot partition attached. Every error returns nonzero with one diagnostic that identifies its cause.

Build the tool as an `SBIN_PROGS` member. The `UTILITIES` list drives the os-simple scan for executables in the top-level build directory, where this program must not appear. `tools/check_guest.py` already reads `UTILITIES` and `SBIN_PROGS`, adding `sbin/` to the latter paths. Stage the tool as `/bin/install-kernel` in os-real only through an explicit manifest entry. Add it to the set-id checker's trusted inventory and to `utils/guest.mk` so Rach2 can build its installer. Increase the count in `tools/selfbuild_test.sh` to 25, and add a smoke case that checks the documented exit status when the disk has no boot partition.

* Proof: the host test compiles the core against fixture images from an independent Python builder in the test tree. Fixtures include well-formed FAT32 with the three files preallocated; a fragmented candidate chain, which must be installed cluster by cluster; disagreeing FAT copies; a chain loop; an out-of-range cluster; a chain shorter than the directory size; a candidate chain cross-linked into a directory or `grub.cfg`; and malformed BPBs. Each malformed BPB case has a separate exit: a non-512 sector size, an oversized FAT, an out-of-range root cluster, or overflowing geometry. A valid image with nested directories exercises the recursive scan's skip rules against the shape built by `mmd`. Other fixtures provide a candidate too small for the kernel and a missing grubenv. The write callback also injects faults. It can report success while dropping a selected sector, making the byte-for-byte readback testable. It can stop after any selected write, cut within a sector by writing only a prefix, or cut between the environment block's two sectors to produce an old/new mixture. These cases produce the bytes for each row of the interruption matrix.
* Shown failing: removing the checksum rule lets the installer accept a corrupted multiboot header, and the host test fails. Removing the readback comparison lets a dropped load sector away from the headers pass, and the host test fails.
* Readmes: `utils/Readme.md`, `tools/Readme.md`.

## Phase 3: the GRUB disk stores the slots

`tools/mkdisk_grub.sh` builds the new layout. It pads `/boot/kernel` to the 2 MiB slot, adds `/boot/fallback`, and initializes `/boot/grub/grubenv` with `saved_entry=candidate`. Add `loadenv` to the core image's module list. The new `grub.cfg` loads the environment and accepts only exact menu ids in `saved_entry` and `next_entry`, treating other values as absent under the settled torn-block rule. It implements the one-boot consumption proved in phase 0: match the value, set the default, run `set next_entry=`, and run `save_env next_entry`. When no valid value selects the candidate, choose the fallback. Set `set fallback=1`, the numeric entry required by the phase 0 observation, and document the fixed menu order. Define three `--id` entries with `rach2.slot=` tokens, adding `rach2.rescue` to the debug entry. Use `terminal_output serial console` and include the `serial` and `terminal` modules so the harness log receives loader errors. The container checks for `grub-editenv` and `mshowfat`, validates every staged chain, and fails when a chain is broken or the kernel exceeds its slot. Keep the script interface unchanged: its kernel argument supplies both files, preserving `make os-real-grub-disk` and the GRUB half of selfbuild-test. Rewrite the stale-kernel warning in `rach2/run_from_disk.sh` because the disk now stores the installed kernel state and rebuilding the disk would discard the candidate.

* Proof: boot the disk to a QEMU login without `-kernel`, and require the guest to read `rach2.slot=candidate` from `/proc/cmdline`. Read the environment block from the host image and check its documented format. On a copy of the image, use `grub-editenv` to set `next_entry=debug`; require it to boot the debug entry and observe `rach2.rescue`. This proves the third entry and the one-boot path without serial menu interaction.
* Shown failing: corrupting the candidate's multiboot header in the host image makes the same boot report `rach2.slot=fallback`, proving loader-level fallback.
* Readmes: `tools/Readme.md`, `rach2/Readme.md` (the disk layout and menu).

## Phase 4: the install loop proven on the machine

`make install-test` builds the GRUB disk, boots it without `-kernel`, logs in as root, and runs the complete installation loop. Preserve the harness contract: marker-paced input, split tokens, guest-side assertions, bounded waits, and QEMU termination on every exit path. Run the loop twice in one harness invocation. The second pass starts with the disk modified by the first and proves that the procedure is idempotent. In each pass, the guest first requires `rach2.slot=candidate`. It adds a distinct marker to the kernel's serial boot-banner source and builds the kernel in `/src/rach2` with the staged toolchain. The banner prints separately to serial and VGA, and the log shows the serial copy. This marker proves which bytes executed; the slot token identifies only menu text, while a slot hash proves only the bytes at rest. Run `install-kernel` on the result and reboot with `reboot -f`. In the next session, require `rach2.slot=candidate` and the marker in the banner. Run `install-kernel --commit`, terminate QEMU, and cold-boot the same disk. Both checks must still pass, proving the saved default. Scope every marker-presence and marker-absence assertion to the log interval beginning at that reboot. Record the starting offset before each boot because the accumulated log retains earlier banners. Next, test recovery. Through `/dev/bootpart`, corrupt the candidate's first sector at an extent reported by `install-kernel --where`. Reboot and require `rach2.slot=fallback` with no marker in that boot interval. Run `install-kernel` again, reboot into the repaired candidate, and run `--commit`. A final cold boot proves that the repair is also the saved default. Finally, boot host-built images for the interruption matrix's determinate states: a destroyed header, a complete old value, and a complete new value. Check the entry predicted for each. If Docker is absent, fail the target with the named reason.

* Proof: the harness passes, including the second installation pass, recovery sequence, and matrix boots.
* Shown failing: remove the installer's `next_entry` write. The plan predicted a fallback boot, but the failure occurs earlier. Without the armed line, the mid-pass commit-refusal probe instead commits the unbooted candidate. The reboot then runs that candidate as the saved default, with its marker present, so the identity interval would pass. The decisive assertion is the refusal: before reboot, the host requires the armed commit to return exit status 1. The mutation fails that assertion.
* Readmes: `tools/Readme.md`.

## Risks, in expected order

1. The three GRUB hypotheses. Phase 0 observes them before implementation begins. Only the `next_entry` behavior has a local contingency. A failed padding or `save_env` observation stops the work for a revised plan.
2. The FAT chain walk. The design uses two independent implementations: the installer's C code and the fixture builder's Python code. The host test compares their interpretation of the same images. Every malformed shape listed in phase 2 has its own fixture and exit.
3. The environment block has two writers. Both rewrite 1024 bytes in place within a preallocated file, without changing its size or position. The installer exits nonzero when the header line is not GRUB's. The matrix requires every torn state to select a bootable kernel, using fallback whenever the torn value does not identify one itself.
4. The harness must pace reboots correctly. A timed GRUB menu delays the transition from reboot to login, so the waits must cover it. The marker procedure follows make_test.sh with one addition: assertions use a boot-specific log interval beginning at a recorded offset, whereas make_test.sh searches the complete accumulated log.
5. Docker. The milestone's proofs require the daemon, so the goal run must start it first. Without it, `install-test` fails with the named reason; the optional GRUB half of selfbuild-test instead skips.

## What must not be broken

* Leave the QEMU `-kernel` development flow, `run.sh`, and every existing suite unchanged. Without a `rach2.slot=` token, `install-kernel` exits nonzero and identifies the missing state.
* Preserve the interface of `tools/mkdisk_grub.sh`: one kernel argument supplies both staged files. The GRUB half of selfbuild-test continues to pass when Docker runs.
* Preserve the modes of existing `/dev` entries and every probe that opens a device as an unprivileged user. The permission model changes no existing open.
* Preserve the 512-byte sector contract, the register rule in every committed line, and the vendored trees.

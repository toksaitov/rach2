# Milestone 23: installing the kernel from the machine

## The goal

Milestone 22 made the machine build its own kernel; this milestone lets it install one. Root, on the machine, runs `install-kernel` on a kernel it just built and reboots into it, with no host tool anywhere in the loop, so the same flow works on the GRUB disk in QEMU today and on a real BIOS notebook when the bare-metal milestone revives that target. A failed install, a bad kernel, or a power cut at any point in the install must leave the machine bootable, and the plan carries an interruption matrix that says which kernels can boot after a cut at each point, every one of them bootable.

The design, argued to agreement before this plan: stock GRUB stays the loader. The FAT boot partition it already reads gains a second kernel file and GRUB's environment block; the guest updates only the data sectors of the candidate kernel and the environment block through a new root-only raw device, never any FAT metadata; GRUB's one-boot `next_entry` state makes every install a trial that a power cycle revokes. No custom GRUB module, no new bootloader, no FAT driver in the kernel.

## What was settled before the first phase

* The boot partition is FAT32 (`mformat -F` in `tools/mkdisk_grub.sh`), 16 MiB, partition 1; KRFFS is partition 2. The kernel's MBR reading today is a local piece of `init_krffs_disk` that identifies KRFFS by reading partition contents; phase 1 lifts it into a pure parser whose results are kept, because the boot partition's bounds must come from the same parse.
* The kernel file GRUB loads becomes two files, both 8.3-safe so the FAT walk reads short directory entries only: `/boot/kernel` (the candidate, its name unchanged from today, preallocated at the 2 MiB slot size) and `/boot/fallback` (the same kernel at build time, never written afterward). The menu gains `--id` entries `candidate`, `fallback`, and `debug` (the fallback kernel plus `rach2.rescue`); each entry's command line carries `rach2.slot=candidate` or `rach2.slot=fallback`, and a new `/proc/cmdline` lets the guest read which one booted.
* The environment block `/boot/grub/grubenv` is created at build by `grub-editenv` and initialized to `saved_entry=candidate`, so a fresh disk boots the candidate. GRUB's block format has a header and no checksum, so a torn write can leave a block that still loads; `grub.cfg` therefore reads only `saved_entry` and `next_entry` and compares each against the exact menu ids, and any other value, a missing block, or a failed `load_env` all select the `fallback` entry. Both writers (GRUB and the installer) rewrite the 1024 bytes in place and never move or resize the file.
* The installer accepts a valid fragmented FAT chain and writes it cluster by cluster; contiguity is not assumed, because "fresh file system, first file copied" is not a contract. The image build verifies every staged chain with `mshowfat` and fails if one is broken.
* Trailing zeros after the ELF are believed ignored by GRUB's multiboot loader (Rach2's flags select the ELF path, so load extents come from the program headers), `save_env` is believed to work on our FAT32 partition, and `next_entry` is believed to be consumed and cleared by GRUB before handoff. All three are hypotheses until phase 0 observes them.
* Existing `/dev` entries stay mode 0666 (they match Linux's own modes for the mem and pty devices, and the session code opens the console as an ordinary user); the new device is the first with a restrictive mode, so the permission model is introduced in the same phase.
* `/dev/bootpart` is synchronous and write-through: the ATA and AHCI drivers already flush the drive cache after every write, so a returned write is a durable write. `file_ops` has no fsync operation and `sys_fsync` flushes the KRFFS page cache for every valid descriptor; that existing behavior stands (an fsync on this device flushes the unrelated cache, harmlessly), the device's close callback is NULL, and no new file or block operation is added.
* Docker is required: the GRUB disk is assembled in a container, and every runtime proof in this milestone boots that disk. `make install-test` fails with the named reason when the daemon is absent rather than skipping, because it is the milestone's proof. The goal run must start Docker first.
* Out of scope, recorded for the bare-metal milestone: the AHCI driver's deferred real-hardware reset sequence, the `(hd0,msdos1)` embedded prefix (should become a search by file-system identifier), reset fallbacks beyond port 0xCF9, and UEFI-only machines. The install mechanism must not depend on any of them.

## The interruption matrix

The installer's order is: validate the named kernel; validate the fallback file as a kernel; write `saved_entry=fallback`; write the candidate's data sectors cluster by cluster, zeros to the slot end; read the slot back and validate it again; write `next_entry=candidate`. `install-kernel --commit`, run only on a machine whose `/proc/cmdline` carries `rach2.slot=candidate`, writes `saved_entry=candidate`. A power cut:

* before `saved_entry=fallback` completes: the block is stale or torn. A stale block still names a bootable kernel; a torn block can fail `load_env`, fail the config's exact-id comparison, or keep a complete valid value. Boots the old state's kernel or fallback, both bootable.
* during the slot write: `saved_entry=fallback`, no `next_entry`. Boots fallback.
* after the slot write, before `next_entry`: same state. Boots fallback; rerunning `install-kernel` completes the install.
* during the `next_entry` write: a torn block can fail the load, fail the exact-id comparison, keep the complete old value, or already hold the complete new one. Boots fallback or the just-validated candidate; every outcome is a bootable kernel.
* during `--commit`: the same four torn cases, over values that both name bootable kernels; rerunning `--commit` finishes.

Every row's on-disk state is produced by fault injection in the phase 2 seam test. Phase 4 boots host-crafted images of the states whose outcome is determinate (a header-destroying tear, a complete old value, a complete new value) and asserts the entry each predicts; the matrix's guarantee is that no state selects an unbootable kernel, not that every state selects the fallback. Torn states include partial-sector prefixes and old/new sector mixes across the block's two sectors, because the block spans a sector boundary and a cut can produce any of these.

## Phase 0: the GRUB experiment

Before any repo change, assemble a variant GRUB disk by hand (scratch scripts, Docker) with the two kernel files, a padded candidate, a `grub-editenv`-created environment block, and `loadenv` in the core image, and observe five behaviors in QEMU: a zero-padded kernel boots exactly as the unpadded one; `save_env` from the GRUB shell rewrites the environment block in place on our FAT32 (verified by reading the bytes back on the host); `next_entry=candidate` boots the candidate entry once and is cleared before handoff; a candidate whose multiboot header is destroyed makes the `fallback` variable boot the fallback entry; and a hand-torn environment block (a partial first sector, a partial second, an old/new sector mix) behaves as the exact-id config predicts, which matters because the block format has no checksum and a torn block can still load. Also confirm `grub-editenv` and `mshowfat` exist in the container image, and record the current kernel sizes (the host build measured 661548 bytes, the guest tcc build near 300 KiB, both far under the 2 MiB slot). Record each observation in this plan, replacing the hypotheses above.

* Contingencies, named now: if `next_entry` is not consumed built-in, the same one-boot semantics are scripted in `grub.cfg` (`if [ "${next_entry}" ] ; then set default="${next_entry}"; unset next_entry; save_env next_entry; fi`), which uses only `loadenv`/`save_env`. If padding is not ignored, or `save_env` does not work on the partition, this plan stops for a re-plan: the first would put FAT metadata writes into the installer and the second would remove the mechanism the commit depends on, and neither is a local adjustment.
* Proof: the recorded observations, each tied to a command and an artifact from the run.
* Readmes: none; no repo change beyond this plan.

## Phase 1: the device permission model, /dev/bootpart, and /proc/cmdline

Lift the MBR parse out of `init_krffs_disk` into a pure function with a host seam test, and keep the parsed table. Give every `devfs` entry a mode, enforced at open with the caller's credentials through the same nine-bit check the file systems use, and reported consistently: `devfs_stat` and the `fstat` path both read the entry's mode (the `fstat` path reports 0666 for every device today), and a dynamically absent device is absent from lookup, `stat`, open and `/dev` getdents alike. All existing entries keep 0666, so no current open changes.

Add `/dev/bootpart`, mode 0600 root: present only when a block device is mounted and the parsed MBR holds a partition 1 with nonzero bounds contained in the disk, a FAT type byte (0x0b or 0x0c), and a half-open sector range mathematically disjoint from the KRFFS partition's, because the partition layer only clamps each view to the disk and compares nothing, and a boot-partition write must never be able to land in the mounted file system. It is a bounded window over that partition: seekable (`lseek` and `_llseek` both special-case devices today and both gain a case for this device; `SEEK_SET`/`SEEK_CUR`/`SEEK_END` resolve against the partition size), reading and writing whole 512-byte sectors only (`-EINVAL` otherwise), a read at the end returning 0 and a write past it `-ENOSPC`, every transfer staged through a kernel 512-byte bounce buffer with `copy_from_user`/`copy_to_user` because the AHCI driver programs physical DMA addresses and must never see a user pointer. Writes are synchronous write-through as settled above.

Add `/proc/cmdline`: the captured boot command line and a newline, which is a new global proc file beside the pid tree, so the classifier, the snapshot generation, the inode and `stat` shape, root `/proc` getdents, and the `/proc/self/fd` origin rendering each gain a case for it, and `sys/cmdline` gains a getter beside `kcmdline_has`.

* Proof: the MBR parser's host seam test over crafted tables (valid, zero-length, overflowing, type-mismatched, partially overlapping partitions, a missing 55AA signature, a range that wraps past the disk end); a new `bootprobe` against a fixture disk whose partition 2 is a valid KRFFS image (the mount is what makes the device appear) and whose partition 1 is raw known bytes typed FAT: root opens, reads known bytes at a seek, writes and reads back a sector, reads exactly 0 at the end, gets `-ENOSPC` writing past it and `-EINVAL` unaligned; an unprivileged open returns `-EACCES`; on a disk whose only partition is KRFFS the device is absent and open returns `-ENOENT`. For `/proc/cmdline` the probe covers each implementation site, which are independent branches today: the content equals what the harness passed, `/proc` getdents lists the name, `stat` and `fstat` agree on its identity, and `/proc/self/fd/N` for an open descriptor renders the origin path; the host classifier seam gains the same classification cases.
* Shown failing: the device's end-bound translation removed turns the end read's 0 into the partition view's error and the probe's exact-value assertion fails; the credential check removed lets the unprivileged open succeed and the probe fails.
* Readmes: `rach2/sys/fs/synthfs.Readme.md` (the mode column, both new files), `rach2/Readme.md` where it lists devices.

## Phase 2: install-kernel

A new tool in two parts, shaped for the host seam the way `pwauth` is: a pure core (the BPB parse, the FAT walk, the kernel validation, the environment-block edit) that does all sector I/O through caller-supplied read and write callbacks, and a thin guest `main` that binds the callbacks to `/dev/bootpart`. The core: validate the BPB before trusting it (512-byte sectors, matching the device contract; two FATs; cluster geometry, total sectors, FAT size and root cluster all in range and computed with overflow-safe arithmetic, because a malformed BPB must not map a legal-looking cluster into another part of the partition). The acceptance rule is the observed product, not a textbook threshold: `mformat -F` builds a FAT32 below the conventional 65525-cluster line on this 16 MiB partition, phase 0 records that exact BPB, the well-formed fixture reproduces it, and phase 3 runs the host core against the actual staged partition, so the validator cannot reject the image the build ships. Read both FATs and exit nonzero if the copies differ; scan the namespace recursively from the root, reading short entries and skipping `.`, `..`, deleted, free, LFN and volume-label entries (the three names are 8.3-safe by design; a name that does not resolve to a short entry is an error); resolve `/boot/kernel`, `/boot/fallback` and `/boot/grub/grubenv`; require every chain loop-free (a visited bound) with legal in-range cluster values and a proper end mark, a regular file's chain length matching its directory size (a FAT32 directory's size field is zero, so directory chains are checked by the range, loop and end rules alone), and the chains it will write pairwise disjoint and sharing no cluster with any other reachable chain, the directories and `grub.cfg` included, because a cross-linked candidate chain must not let an install overwrite directory or loader data; validate a kernel image (ELF32 `ET_EXEC` for `EM_386`, the multiboot magic, flags and checksum four-byte-aligned in the first 8192 bytes, size within the slot); and edit the 1024-byte environment block in place, requiring GRUB's header line. The install order and `--commit` are the interruption matrix's, including validating the fallback file before `saved_entry=fallback` is written, and the post-write readback compares the complete padded slot byte for byte against the intended image, because structural validation alone would pass a slot missing a load sector away from the headers. `install-kernel --where` prints each file's sector extents, which phase 4's harness uses. The tool requires a `rach2.slot=` token in `/proc/cmdline` before installing and `rach2.slot=candidate` before `--commit`; without the token it exits nonzero and names the missing state, which also covers a `-kernel` boot that happens to have a boot partition attached. Every error exits nonzero with one diagnostic naming the cause.

Built as an `SBIN_PROGS` member (the `UTILITIES` list feeds os-simple's exec-dir sweep over the top-level build directory, where this program must not appear, and `tools/check_guest.py` already reads `UTILITIES` plus `SBIN_PROGS` with `sbin/` paths), staged as `/bin/install-kernel` in os-real only by an explicit manifest line, added to the set-id sweep's trusted inventory and to `utils/guest.mk` so the machine can build its installer; `tools/selfbuild_test.sh` grows the count to 25 and a smoke case asserting the tool's documented exit status on a machine whose disk has no boot partition.

* Proof: the host seam test compiles the core against fixture images written by an independent python builder in the test tree: a well-formed FAT32 with the three files preallocated; a fragmented candidate chain (installed correctly, cluster by cluster); disagreeing FAT copies, a chain loop, an out-of-range cluster, a chain shorter than the directory size, a candidate chain cross-linked into a directory or `grub.cfg`, and malformed BPBs (a non-512 sector size, an oversized FAT, an out-of-range root cluster, geometry whose arithmetic overflows), each its own exit; a valid image with nested directories, so the recursive scan's skip rules are exercised against the shape `mmd` builds; a candidate too small for the kernel; a missing grubenv. The write callback doubles as the fault injector: it can report success and drop a chosen sector, which is what makes the byte-for-byte readback falsifiable; it can stop the run after any chosen write, and it can cut inside a sector (a partial prefix) or between the environment block's two sectors (an old/new mix), which is what produces each interruption-matrix row's bytes for assertion.
* Shown failing: the validator's checksum rule removed lets a corrupted multiboot header install and the seam test fails; the readback comparison removed lets a dropped load sector away from the headers pass and the seam test fails.
* Readmes: `utils/Readme.md`, `tools/Readme.md`.

## Phase 3: the GRUB disk carries the slots

`tools/mkdisk_grub.sh` builds the new layout: `/boot/kernel` padded to the 2 MiB slot, `/boot/fallback`, `/boot/grub/grubenv` initialized to `saved_entry=candidate`, `loadenv` in the core image's module list, and the new `grub.cfg` (load the environment; compare `saved_entry` and `next_entry` against the exact menu ids and treat any other value as absent, per the settled torn-block rule; default to the fallback entry when nothing valid selects the candidate; the `fallback` variable set so a candidate GRUB cannot load falls to the fallback entry; the three `--id` entries with their `rach2.slot=` tokens, the debug entry carrying `rach2.rescue`). The container run checks that `grub-editenv` and `mshowfat` exist, verifies every staged chain and fails the build on a broken one or a kernel over the slot. The script's interface is unchanged: the kernel it is handed becomes both files, so `make os-real-grub-disk` and selfbuild-test's GRUB half work as before. `rach2/run_from_disk.sh`'s stale-kernel warning is rewritten: the disk now owns its kernel state, and advice to rebuild the disk would discard an installed candidate.

* Proof: the disk boots to a login in QEMU with no `-kernel` and the guest reads `rach2.slot=candidate` from `/proc/cmdline`; the host reads the environment block's bytes from the image and finds the documented format; a copy of the image with `next_entry=debug` set by `grub-editenv` boots into the debug entry (`rach2.rescue` observed), which proves the third entry and the one-boot path without any menu interaction over serial.
* Shown failing: the candidate file's multiboot header corrupted on the host image makes the same boot come up with `rach2.slot=fallback`, which is the fallback proof at the loader level.
* Readmes: `tools/Readme.md`, `rach2/Readme.md` (the disk layout and menu).

## Phase 4: the install loop proven on the machine

`make install-test`: build the GRUB disk, boot it (no `-kernel`), log in as root, and run the whole loop under the established harness contract (marker-paced feed, split tokens, guest-side assertions, bounded waits, the machine killed on every exit path), with the loop run twice inside one harness invocation so the second pass starts from the disk the first modified and proves the flow idempotent. One pass: the guest proves `rach2.slot=candidate`; edits a marker into the kernel's serial boot banner source (the banner prints separately to serial and VGA, and the serial occurrence is the one the log shows), builds the kernel in `/src/rach2` with the staged toolchain, and the marker is what later proves which bytes run, because the slot token alone is menu text and a hash of the slot proves only bytes at rest; runs `install-kernel` on the built kernel; reboots with `reboot -f`; the next session proves `rach2.slot=candidate` and the host proves the marker appeared in the banner; runs `install-kernel --commit`; the harness kills QEMU, cold-boots the same disk, and both proofs hold again (the saved default). The markers are distinct per pass, and every presence and absence assertion reads only the log interval after the reboot that starts its boot, from an offset the harness records first, because the accumulated log still holds every earlier banner. Then the recovery half: the guest corrupts the candidate's first sector through `/dev/bootpart` at the extent `install-kernel --where` names, reboots, comes up with `rach2.slot=fallback` and with no marker in that boot's interval, repairs itself by running `install-kernel` again, reboots into the repaired candidate, and runs `--commit` so the repair is also the saved default, which the closing cold boot proves. The harness then boots host-crafted images of the interruption matrix's determinate states (a header-destroying tear, a complete old value, a complete new value) and asserts the entry each predicts. Docker absent fails the target with the named reason.

* Proof: the harness, green, including the second pass, the recovery half and the matrix boots.
* Shown failing: the `next_entry` write removed from the installer makes the post-install reboot come up as `fallback` without the marker and the harness fails at the identity assertion.
* Readmes: `tools/Readme.md`.

## Risks, in expected order

1. The three GRUB hypotheses. Phase 0 exists to observe them before any code; only the `next_entry` behavior has a local contingency, and a failed padding or `save_env` observation stops the plan for a re-plan.
2. The FAT chain walk. Two independent implementations exist by design (the installer's C and the fixture builder's python), the seam test compares their view of the same images, and every malformed shape named in phase 2 has a fixture and its own exit.
3. The environment block's two writers. Both rewrite 1024 bytes in place into a preallocated file; neither changes its size or position; the installer exits nonzero on a block whose header line is not GRUB's; and the matrix holds that every torn state selects a bootable kernel, the fallback in every case where the torn value does not itself name one.
4. The harness's reboot pacing. A GRUB menu with a timeout sits between reboot and login; the wait bounds must cover it. The marker discipline follows make_test.sh with one extension: assertions are scoped to a boot's log interval from a recorded offset, where make_test.sh searches the whole accumulated log.
5. Docker. The milestone's proofs need the daemon; the goal run must start it first, and `install-test` fails with the named reason without it, unlike selfbuild-test's optional GRUB half.

## What must not be broken

* The QEMU `-kernel` developer flow, `run.sh` and every existing suite: untouched. `install-kernel` without a `rach2.slot=` token exits nonzero naming the missing state.
* `tools/mkdisk_grub.sh`'s interface: one kernel argument, both files staged from it; selfbuild-test's GRUB half keeps passing where Docker runs.
* Existing `/dev` modes and every probe that opens devices unprivileged; the model changes no current open.
* The 512-byte sector contract, the register rule in every committed line, and the vendored trees.

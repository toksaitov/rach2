# 87-6d: Firefox's slow WebGL rounds on the Lenovo under the fair scheduler

On the Lenovo's gate of 19 November (#5483), one Firefox run in three had WebGL rounds 1.5 to 3 times Linux's while all four processors were full of Firefox's startup work, and Firefox's main thread waited 240 to 849 ms for a processor. This record holds what QEMU on the testing host showed of it, which settles less than the task asks: under KVM Rach2 and Debian do the same work in the same time, so the cause lies in what only the Lenovo has, and the next step is a measured run there.

## Results

Every run below was on the testing host, 2026-11-19 from 23:33 to 00:05 UTC+6, under KVM with QEMU 10.2.1, `-cpu host,invtsc=on`, 8 GiB and virtio-vga at 1280x800. Rach2 was the x86-64 kernel of `milestone/76-display` at 777d69bbd on a raw `gnu-test.disk` built at the same head, booted with `rach2.root=ext2`, the probe run as `test` with `GRAPHICS_CLASS=performance GRAPHICS_DONE=1` and `guest-env.sh` sourced. Debian was `debian.sh probe` in Debian 13's 6.12.115+deb13.1-amd64. Both ran Firefox 153.6.0esr on llvmpipe under a headless Weston.

So this profile cannot show the Lenovo's fault, where the GPU draws and the processors are free for the startup work alone.

To come nearer the Lenovo, the second set gave QEMU the i3-4030U's shape, two cores of two threads (`-smp 4,sockets=1,cores=2,threads=2`), and made the draws cheap: a copy of `probe.html` with a 256-pixel canvas and `LP_NUM_THREADS=1`, so that llvmpipe's one thread takes one processor. In WebGL2's ALU window three of Rach2's processors were idle 1.23 to 1.27 s of 1.31 s, and Debian's four 0.57 to 1.25 s of 1.36 s, yet Rach2's main thread waited about 18 us a run (10 ms over 564 runs in the first) and Debian's about 1.4 us (2 ms over 1,432). Part of that difference is in the counting: Linux queues a wake for an idle processor on that processor's wake list and starts the wait when it takes the wake there (ttwu_queue_wakelist, sched_info_enqueue in enqueue_task), while Rach2 starts it at the waker (`sched_wait_begin`), so Rach2's figure includes the halted processor's interrupt and exit under KVM. A pipe ping-pong between two threads in the same guests, beside 0 to 3 spinning threads, made 20,000 round trips in 1.3 to 2.6 us each on Rach2 and 13.8 to 14.3 us on Debian, 4.2 us with three spinners. Debian put each pinger on a processor once a trip, 20,000 times, with 0 to 0.1 us of wait a run, 1.1 us with three spinners; Rach2 put them on a processor 1,231 to 2,804 times, 20,001 with three spinners, with 5.1 to 5.6 us a run, 0.7 us with three spinners. With one spinner each of Rach2's pingers ran on a processor of its own, as Debian's did.

Two things measured on the way, neither the cause:

* Reading `/proc/PID/status` walks every page table of the process to split its resident pages into RssAnon, RssFile and RssShmem (`rss_by_kind`, `procfs.c`), where Linux reads counters it keeps. A snapshot that read it for each of Firefox's 120 threads put 15% of the run's kernel samples in `paging_user_count`. `probe.sh -t` reads `stat`, which reads Rach2's counter, and so does `ps`'s default output.
* `su test -s /bin/sh -c CMD` over SSH without a terminal did not end within ten minutes; with its output sent to a file it returned 0 without the command's output. `sudo -u test` works and served the runs.

## Design

Under KVM on this host the systems do not differ, so the fault needs something the Lenovo has: the i915 GPU and its waits, Rach2's desktop session as the compositor, four slower logical processors on two cores, or a Firefox whose startup does more on Rach2 when the GPU is real. The measured run that separates these is the instrumented gate on the Lenovo with the new figures, with the whole-kernel profile, on Rach2's trial and on Debian 13 on the same machine: if Firefox's threads ran more user or system time on Rach2 in the slow windows, the extra work is named by thread and, for system time, by kernel function; if they ran the same and waited longer while a processor was idle, the fault is in placement; if they ran the same with every processor busy, Linux's runs fill the processors too and its rounds hold for another reason, which the same figures name.

[`87-6d/prof.py`](87-6d/prof.py) reads a whole-kernel profile, `bkl/profile` after a write of `kernel`, against the kernel's symbols.

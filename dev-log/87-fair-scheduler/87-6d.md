# 87-6d: Firefox's slow WebGL rounds on the Lenovo under the fair scheduler

On the Lenovo's gate of 19 November (#5483), one Firefox run in three had WebGL rounds 1.5 to 3 times Linux's while all four processors were full of Firefox's startup work, and Firefox's main thread waited 240 to 849 ms for a processor. This record holds what QEMU on the testing host showed of it, which settles less than the task asks: under KVM Rach2 and Debian do the same work in the same time, so the cause lies in what only the Lenovo has, and the next step is a measured run there.

## Results

Every run below was on the testing host, 2026-11-19 from 23:33 to 00:05 UTC+6, under KVM with QEMU 10.2.1, `-cpu host,invtsc=on`, 8 GiB and virtio-vga at 1280x800. Rach2 was the x86-64 kernel of `milestone/76-display` at 777d69bbd on a raw `gnu-test.disk` built at the same head, booted with `rach2.root=ext2`, the probe run as `test` with `GRAPHICS_CLASS=performance GRAPHICS_DONE=1` and `guest-env.sh` sourced. Debian was `debian.sh probe` in Debian 13's 6.12.115+deb13.1-amd64. Both ran Firefox 153.6.0esr on llvmpipe under a headless Weston.

In WebGL2's ALU window three of Rach2's processors were idle 1.23 to 1.27 s of 1.31 s, and Debian's four 0.57 to 1.25 s of 1.36 s, yet Rach2's main thread waited about 18 us a run (10 ms over 564 runs in the first) and Debian's about 1.4 us (2 ms over 1,432). Part of that difference is in the counting: Linux queues a wake for an idle processor on that processor's wake list and starts the wait when it takes the wake there (ttwu_queue_wakelist, sched_info_enqueue in enqueue_task), while Rach2 starts it at the waker (`sched_wait_begin`), so Rach2's figure includes the halted processor's interrupt and exit under KVM. A pipe ping-pong between two threads in the same guests, beside 0 to 3 spinning threads, made 20,000 round trips in 1.3 to 2.6 us each on Rach2 and 13.8 to 14.3 us on Debian, 4.2 us with three spinners. Debian put each pinger on a processor once a trip, 20,000 times, with 0 to 0.1 us of wait a run, 1.1 us with three spinners; Rach2 put them on a processor 1,231 to 2,804 times, 20,001 with three spinners, with 5.1 to 5.6 us a run, 0.7 us with three spinners. With one spinner each of Rach2's pingers ran on a processor of its own, as Debian's did.

Two things measured on the way, neither the cause:

* Reading `/proc/PID/status` walks every page table of the process to split its resident pages into RssAnon, RssFile and RssShmem (`rss_by_kind`, `procfs.c`), where Linux reads counters it keeps. A snapshot that read it for each of Firefox's 120 threads put 15% of the run's kernel samples in `paging_user_count`. `probe.sh -t` reads `stat`, which reads Rach2's counter, and so does `ps`'s default output.
* `su test -s /bin/sh -c CMD` over SSH without a terminal did not end within ten minutes; with its output sent to a file it returned 0 without the command's output. `sudo -u test` works and served the runs.

## Design

Under KVM on this host the systems do not differ, so the fault needs something the Lenovo has: the i915 GPU and its waits, Rach2's desktop session as the compositor, four slower logical processors on two cores, or a Firefox whose startup does more on Rach2 when the GPU is real. The measured run that separates these is the instrumented gate on the Lenovo with the new figures, with the whole-kernel profile, on Rach2's trial and on Debian 13 on the same machine: if Firefox's threads ran more user or system time on Rach2 in the slow windows, the extra work is named by thread and, for system time, by kernel function; if they ran the same and waited longer while a processor was idle, the fault is in placement; if they ran the same with every processor busy, Linux's runs fill the processors too and its rounds hold for another reason, which the same figures name.

[`87-6d/prof.py`](87-6d/prof.py) reads a whole-kernel profile, `bkl/profile` after a write of `kernel`, against the kernel's symbols.

## Lenovo comparison

The same Lenovo ran Debian 13.7's 6.12.115+deb13.1-amd64 with `intel_iommu=off` on 2026-11-20. Each of three pairs ran Chromium and then Firefox from 12:03:40 to 12:04:20 UTC+6. The probes used the same staged files as Rach2's diagnostic at 11:46. Debian ran them under stock Weston 14.0.2 on the panel with `kernel.sched_schedstats=1`. Rach2 used its Weston build and an ext2 loop root. Both used four processors, Mesa 25.0.7-2+deb13u1 on the Intel GPU, Firefox 153.6.0esr and a fresh browser profile and shader cache per run.

All six Debian probes exited 0 and gave four measures, two sets of rounds and four thread reports. The Firefox runs below are diagnostic. On Rach2, run 2's WebGL1 ALU window used 1910 ms of system CPU time against 110, 120 and 220 ms on Debian. Its 1560 ms of user time fell within Debian's 1350 to 2070 ms. Firefox's main thread waited 152 ms on Rach2 in that window and 22, 60 and 56 ms on Debian. Rach2's other busy ALU window, in run 1, used 1790 ms of system time with rounds of 106 to 112 ms. The main process accounted for 1340 ms of system time among threads present in both snapshots of Rach2 run 2's slow window. Newly seen threads of the privileged content and utility processes accounted for another 400 ms. Debian's third WebGL1 ALU window also had privileged content startup and used 2520 ms of processor time by the per-processor counters, while its longest round was 109 ms.

The comparison puts the extra time in the kernel during Firefox startup. It leaves the particular call that delayed the slow rounds open. Rach2's whole-run profiles have `openat` first and show ext2 directory scans. The sampled chain through `vfs_name_path` leads to `exe_file_path`, which supplies names for several `/proc` reads, including maps and descriptor links. Those samples do not by themselves identify a relative open through a directory descriptor. Both mechanisms can reach `ext2_path`. Rach2's submission worker waited 101.5, 194.2 and 0.9 ms in the three WebGL1 ALU windows. Debian's high-priority flip worker waited 8.6, 6.7 and 11.5 ms. The workers serve different queues. The comparison does not show which Rach2 fence depended on the submission worker during the slow rounds. A trace needs to align each slow draw with its syscall and lock times and the waits of Firefox's main thread, CanvasRenderer and i915. It also needs a sample with the whole-kernel profiler off, since only Rach2 had it on. The gate still needs the six uninstrumented passes after the fix.

The Mac's `build/runs/t5483-6d/debian-probe.tar` holds each browser's own `run.log`, `lenovo.out`, `events`, `measures`, `record` and `threads`. The earlier Rach2 records are in the same directory. The Debian runner was copied with its output path under `/srv/ref80/out/sched5483` so the earlier reference runs stayed in place.

The one-shot Debian boot staged its menu and GRUB files on the boot partition and used trial files under `/data/trial/5483-debian`. At 12:07 the boot partition matched its original SHA-256, both slots matched the installed release kernel, and the candidate was booted with no trial armed. Weston was stopped, term and login were present, and the backlight was set to 1. The trial files on both systems were removed and the Lenovo lock was freed.

The browser takes a fresh profile each run. A control uses the same probe without marks. A marked run adds two requests to the local server around each timed round of one draw. The thread rows pair IDs and names seen at both marks. They omit new and departed threads, and user and system time count whole ticks. ## Long lock holds during path reconstruction

On 2026-11-20 at 13:19 UTC+6 the same trial kernel and timestamped probe booted again with the ordinary GPU settings. Three Firefox runs gave all four measures. The second run had WebGL1 ALU rounds of 105, 171, 428, 163 and 207 ms. These runs used neither round marks nor an outside sampler. The kernel's existing `bkl/long` ring was cleared before each run and copied afterwards. TSC and monotonic clock pairs bracketed each run, with the largest difference between the pairs' offsets 1.04 ms. Browser and lock times below use those pairs.

All 14 long holds the ring captured were `openat` calls on Firefox's `MainThread` with ext2 directory scans on the stack. They had sampled ages from 23.2 to 91.1 ms. One stack took the chain `procfs_maps_names`, `procfs_file_target`, `exe_file_path`, `vfs_name_path`, `vfs_node_path`, `ext2_path` and the directory scan. The 428 ms round overlapped a hold sampled at 75.8 ms in the same scan. In run 1, holds sampled at 72.2, 52.0 and 38.5 ms overlapped its 198, 123 and 175 ms ALU rounds. The longest lock acquisition in these runs waited 101.1 ms, of which one `openat` hold lasted 100.9 ms. Total big-lock wait across the four processors grew by 6.54, 6.21 and 6.45 s during the three probes.

The path formatter rebuilds each mapped file's name when it opens a maps file. For each ancestor it finds the child's name in its parent by inode number. `dir_name_of` read each record's header and name through the buffer cache separately, with the big kernel lock held across the search. Linux's maps formatter follows the opened file's dentry parents with `d_path`. Rach2 still reads the directories when it needs to reconstruct a path, so `dir_name_of` now copies each block once, as the ext2 name lookup does, and gives back the caller's big-lock hold during the search. The parent's node lock still covers the directory and the name found, and the call restores the big lock depth before it returns.

The raw captures, boot checks and resolved stacks are in `build/runs/t5483-locks`. The candidate kernel and data partition's trial files were written and the verified release was restored in both boot slots. Weston was stopped and the console login returned before the Lenovo lock was released.

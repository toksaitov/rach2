# 5580: ext2 write-back, block I/O and vblank timing against Linux

Task 5580 gathered six costs where Rach2 measured slower than Linux. Four had tasks before it (5381, 5342 with 5344, 5339, 5333 and 5334); this record says what each left, what this task changed and what is still open.

## The flushes of a sync

A sync on a write-through disk with a volatile cache, a virtio disk under QEMU's `cache=writeback`, sent one or two flushes for each block that waits by an order. The new row `async_flush_row` of `tests/host/ext2_async_rows.h` (`ext2_hosttest --flushes-only`) makes 64 directories and 64 files in the root of a mount that writes back and syncs it, on a model disk that keeps its `unflushed` mark as the virtio and AHCI drivers do. Before the change the sync sent 197 flushes; after it, 4.

The trace of the 197: each mkdir changes the shared inode-table block after an order on its new directory block, while the root's entries wait for the table block, so each mkdir leaves an image of the table block that waits for its own directory block. The sync wrote the directory block without the flush, flushed, then wrote the image with the flush, once for each mkdir; and every block that waits by orders had the disk flushed before it whenever any write was unflushed, even one an earlier flush had covered (`ordered` in `flush_before`, from eb3cb5d867).

The change, in `rach2/sys/fs/bcache.c`:

* A sync runs three passes: the firsts, then the blocks that wait for nothing, then the blocks that wait. What the waiting blocks need is then mostly written before the first of them, and one flush covers it.
* A block another block waits for is written without the flush, but for a first, whose flush the counts of firsts rely on.
* The cache keeps a list of the writes the disk answered without its flush that no flush begun since has covered, 128 blocks, each with its class at the write (`unflushed`, `count_written`). Before a block that waits, `flush_owed` asks for the flush only when one of those writes is a block the class rules put before it (`class_precedes`, the rules of `must_precede`, now shared), or a block one of its orders names, or the block has an older image not yet written. A write of the block's own number is not needed, since the block's write takes its place. A write the list has no room for leaves its count in `writes_lost`, which owes the next waiting block a flush. A flush that ends well drops the writes answered before it began; a lost device drops all of its.

The four flushes left are the depth of the orders: the directory blocks, then the root's inode, then the new inodes' table blocks, then the root's entries, and the sync's own flush at its end. Linux's ext4 driver, which mounts the volume without a journal, sends one flush for the sync and keeps no order across a crash; ext4 with a journal sends its commit's flushes once for the transaction. Rach2 keeps the order of milestone 21, so one flush for each level is its floor without a journal.

So the 5 to 10 ms that one 4 KiB virtio-blk write took under QEMU (`dev-log/76-display/vblk-write.md`: the host's `fdatasync` for each FLUSH, two on a qcow2 overlay's fresh cluster) is now paid once for each level of a sync's orders instead of once for each block that waits. The `after` mark of a new block, whose flushes subtask 5582 counted at about 140 for each Chromium start, went in b61e26268c (5344); an `after` keeps its flush only while a first answered without the flush is not yet covered.

Not done here: the create latency and the flushes of a Chromium start in a guest, which need a boot of the GNU root, and the machine suites (ext2, ext2stop, persist, crash) and the interruption matrices on the change, which run after Codex's review. A removal still writes its directory block at once and waits for it (`DIR_NOW`, 5381), where Linux's ext4 driver waits for none.

## Creates

5381 made an operation that adds a name write nothing before it returns (`async_create_row`, 0 writes for 64 of each kind, against 256 for creates and 448 for mkdirs before). That row fails without its change, and the release's end review read that code (5519). Nothing was left for this task.

## vkms

5339 moved `vkms_tick` off the big lock and stamps each vblank with its due time, as Linux's vkms does. This task compared Rach2 with Debian's Linux 6.12 under the same load: 3600 vblanks at 60 Hz in a 4-processor KVM guest, with busy loops pinned to the host cores the guest runs on. `drmcapture -v` (`tests/graphics/capture/drmcapture.c`), the same program on Rach2 and in the Debian guest, keeps four WAIT_VBLANK events queued, reads each as its reader would and counts how late it arrives, with each processor's steal over the run.

The timer itself is not behind Linux's. With the handler's lateness taken from the time each event is sent against its stamp, Rach2 sent 279 and 306 of 3600 events 1 ms or more late and 45 and 62 by 5 ms or more, in two runs; Linux's hrtimer, read from the `drm_vblank_event` tracepoint's time on the mono clock, sent 1023 and 1065 late by 1 ms and 140 and 158 by 5 ms.

What the reader sees was worse on Rach2 with CRCs on: 814 and 821 events 5 ms or more late, against 462 to 763 in Debian. Three changes cut it to 705 and 682:

* A wake no longer chooses an idle processor whose virtual processor the hypervisor has preempted, as Linux's `available_idle_cpu` checks `vcpu_is_preempted` (`rach2/sys/proc/balance.c`). The row `preempted_rows` of `tests/host/balance_hosttest.c` fails without it.
* The fine deadline that `timer_service_wake_at` publishes runs only the lock-free services; the locked work and its 1 ms retry run only at the whole tick or a poll that is due, and vkms no longer asks for whole ticks of its own. The boot processor's timer interrupts fell from 337 a second to 100 with CRCs, and from 111 to 72 without.
* A DRM node's poll and a CRTC's `crc/data` poll no longer take the big lock, as Linux's `drm_poll` and `crtc_crc_poll` take only their own locks.

Without CRCs, Rach2's tail is no worse than Debian's with them: 492 and 280 events late by 5 ms, against 509 and 517.

What is left is the big lock in the reader's path: the read of a device node and of debugfs's `crc/data`, which `file_ops_unlocked` keeps under the lock for every device and synthetic node, and WAIT_VBLANK, since vkms does not set DRIVER_KMS_UNLOCKED. A reader that waits for the lock while the holder's virtual processor is preempted waits for the host. Taking those paths off the lock is work on the VFS's locking rules and on vkms's KMS locking, larger than this task.

The composer read each page of each row through `kmap_cpu`, a mapping, an `invlpg` and interrupts off for each page on i686. It now maps each plane's pinned frames into one window of the MMIO region for the composition (`compose_pages_map`), as Linux's `prepare_fb` maps the framebuffer with `vmap`, and reads the rows through it; x86-64 reads through the direct map as before.

On the Mac, an i686 QEMU TCG guest with one processor and 256 MiB ran `drmcapture -p -v 240 -c /dev/dri/card0` on vkms at 1024x768. Two builds of 36acb1a2f1 timed `vkms_compose` from entry through `compose_pages_put` with `vkms_now`. The comparison build skipped `compose_pages_map`, so it read through `kmap_cpu`. The timing records confirmed which path each composition took. Median times with the window were 39.51 and 39.64 ms in runs of 101 and 100 compositions. With `kmap_cpu` they were 39.13 and 39.61 ms in runs of 101 and 100. The window removes the per-page mapping from row reads. The timings show no speedup in this single-processor TCG guest.

## CRC-32

7fdfdd4635 (5334) made `gpt_crc32` and `wlan_crc32` `~crc32_le(~0u, p, len)`. The bytes they compute are the same as before, so no row can fail without the change; the gpt, partition, diskinfo, usbdisk and devfs host tests and the ath9k and wlan rows check the values.

## Memory

memprobe-64 failed on x86-64 at the milestone's head: the machine was back at 64 MiB (da8761f3ae), and the kernel had since grown, the HDMI audio driver's DMA buffers to 1 MiB in 355d296cac and the TCP and UDP port tables by 768 KiB. Two static buffers of a megabyte each, kept by every machine whether or not it has the device, now come from the heap when the device is found, as Linux allocates them:

* The HDMI audio PCMs' DMA buffers (`hda_hdmi.c`) are made when the display binds, as Linux preallocates a PCM's buffer, and a PCM without one is not offered. Each is 64 frames taken one at a time, as Linux's snd-hda-intel takes a scattered buffer, mapped as one window of the MMIO region, with a descriptor entry for each piece of a period within one frame, as `azx_setup_periods` splits a period; a buffer of 64 consecutive frames would leave a PCM out on a machine whose free memory is scattered. On a controller whose GCAP lacks 64OK the frames come from below 4 GiB, through `alloc_frame_below`, as `azx_first_init` limits its DMA mask. A bind that cannot make a buffer gives back the frames it took.
* The RTL8168's receive and transmit buffers (`rtl8168.c`) are made when a card of the GU family is found, as `rtl_open` allocates them: each receive buffer four consecutive frames, as Linux takes one of order 2, and the transmit buffers two to a page, so that no longer run is needed. A bring-up that cannot make them all fails holding none, and one that fails later gives them back in its stop, once bus mastering is off. The descriptors now carry the buffers' high address half, which Linux also gives the 8168GU, its version 42, with a 64-bit DMA mask.

Codex's review of these two changes found the runs of consecutive frames, the buffer above 4 GiB given back instead of one sought below it, and the buffers kept after a failed bring-up; 5605 fixed them. The host rows of `hdmi_audio_hosttest.c` and `rtl8168_hosttest.c` now run the drivers' own allocation against models of the frame allocator and the heap whose frames are never adjacent, with an address limit, partial failure and a window that cannot be mapped, where they used static buffers before. The same review found two faults in `drmcapture -v`, fixed there too: a read's later events took the time of the requests made for the earlier ones as lateness, and a read of several events could count past COUNT. The figures above were measured before that fix; a read that returned more than one event counted its later ones later by the time the replacement requests took.

x86-64's kernel now ends at 10.1 MiB and i686's at 9.7 MiB. In 64 MiB, x86-64 manages 36,096 KiB, against 33,980 before, and i686 35,860; memprobe 16 says MEMPROBE OK on both. The TCP and UDP port tables were left as they are: they count the users of every one of the 65536 ports, so that a choice of an ephemeral port reads one entry and not a list, and a write of `ip_local_port_range` may move the range over any of them.

x86-64 os-real, now 42 MiB (e5a15a0718), leaves 646,112 bytes free, 134 KiB above its 512 KiB floor; the half megabyte the kernel gave back leaves the module's window 11.7 MiB for the drivers' frames, against 11.2 before. The Makefile's comment has the new figures.

The Lenovo trial boot on 2026-11-20 used 36acb1a2f1, with a 4,249,408-byte kernel from the Mac. The RTL8168GU linked at 1000 Mb/s full duplex. A 64 MiB file's SHA-256 matched before upload, on disk on the Lenovo and after download. The HDMI codec reported three pins and two PCMs. A write of 32,000 bytes of silence to `/dev/dsp1` completed in four seconds with no stream error in the log. The trial wrote the candidate slot and staged its one-shot GRUB entry. It then cleared the entry, restored release 7a2168e3c2, verified its kernel digest in both slots, and removed the files staged on the data partition.

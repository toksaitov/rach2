## Phase 4: the warnings, the dialect and the analysers

* The kernel's warning flags are curated in `mk/warnings.mk`, measured on the testing host's GCC 15.2. `-Wpedantic -Wno-long-long` reported 40 sites there, not the one the plan had counted on the Mac: three redefinitions of one typedef and 37 designated initialisers in four driver tables, which the C89 the kernel is held to does not have; the tables are positional now, with the field order named beside them. Then, one flag and one commit each, with the sites fixed by a type or a declaration: `-Wmissing-prototypes` (a `kernel.h` for the three functions kernel.c exports, replacing file-scope externs), `-Wwrite-strings` (the default environment in writable arrays), `-Wredundant-decls` (five), `-Wduplicated-branches` (two pairs merged), `-Wswitch-default` (three), `-Wswitch-enum` (every enumerator named in five switches), `-Wbad-function-cast` (a pointer-returning `mem_reserve_ptr`, the other results held in variables), `-Wcast-qual` (sixteen: the formatter and its six callers read their arguments through stdarg instead of walking the stack from the format, which the plan had listed among the -O2 hazards; the exec readers take a context struct; the descriptor holds its device entry in a field of its own; the ATA transfer takes a source and a destination; the audio DMA buffer lost a volatile it never needed) and `-Wcast-align=strict` (the register bases are addresses, the identify buffer is words, the heap walks its pages as memory, the dirent records are built in unions). * Two of those fixes were wrong for the 64-bit host tests and the tier found them: `uintptr_t` is the kernel's 32-bit integer, so ring and context arithmetic through it truncated a host pointer. They are pointer arithmetic again, in units of the descriptor type.
* `k_memset` took `char`, so a byte above 127 overflowed under `-Wpedantic`; it takes `int` like memset. The compilers emit `strlen` at -O2, which the kernel now defines over `k_strlen`; the -O2 kernel links and its four null-dereference sites are fixed (a node accessor the window operations need no check for, the first transfer block put before the loop condition). `k_panic` is `noreturn` and the allocators carry `malloc(kfree)` behind macros in `kdef.h`, empty for TinyCC, clang and the host tests, whose panic stubs return.
* clang parses the kernel as a second front end in the style suite with the five flags that showed signal (`-Wcast-align -Wconditional-uninitialized -Wshadow-all -Wtypedef-redefinition -Wcomma`), judged by the recorded version; its twelve remaining sites are fixed (nine initialisations, the page directory unpacked, two comma loops). sparse runs with `__CHECKER__` defined and found four places the annotations were wrong and two devices reading their user buffers directly, the loop control and the frame-fail switch, which now copy from user space; `-Wnon-pointer-null` is left out, with the reason in `tools/verify/exceptions.md`.

The analyser gives up on 2533 program points, most in the system call dispatcher and the boot sequence; they are counted and listed, not held against the build.

## Phase 5: the checked kernels and the fuzzers

* `tests/run` boots every suite on the kernel `RACH2_KERNEL` names, built as a component beside the harness kernel: `ubsan` is `-fsanitize=undefined -fsanitize-undefined-trap-on-error`, in which undefined behaviour is a `ud2` the fault handler already reports with its vector and address before it panics, and `o2` is the optimised kernel the close boots once. The suites' recipes boot `$(BOOT_KERNEL)`; the disks they make carry the default kernel, since a checked kernel does not fit a disk's kernel slot and a disk suite proves the boot path. The runner's own tests drop the name, since the trees they copy have no such target.
* The first core tier on the trap kernel failed seven suites, and the mount suite failed on the default kernel too: phase 4's `-Wcast-qual` change had moved a descriptor's device entry from `priv` to a field of its own and left eight checks in `devfs.c` testing the old one, so every seek on a device window was refused. The core tier had not run since that change. Fixed, the core tier passes on the default kernel and on the trap kernel.
* `-Wframe-larger-than=4096` joined the kernel's flags, a quarter of the 16 KiB stack; the bound is the owner's to move. The four frames above it on the testing host's GCC, read from `-fstack-usage`, were the debug shell's `elf` command at 8400 bytes (a file buffer, static now), the console and pty reads at 4176 and 4160 (a 4 KiB bounce, a 1 KiB chunk now, the caller looping), and the USB scan's completion buffer at 4176 (in the scan's state now). The largest frames left are exFAT's volume check at 2544 bytes and its path walk at 1808, the VFS path resolver at 1760 and a datagram read at 1584. The deepest chain read by hand from the table is a system call's read through the VFS, a file system, the cache and a driver, eight frames under a fault or an interrupt frame, and it sums to under 12 KiB.
* The fuzz harnesses are under `tests/fuzz/`, one per parser in the plan's order: the ELF loader, the receive path, MBR, GPT, KRFFS, FAT, exFAT and ext2. Each defines the one entry `fuzz.h` declares and names the kernel sources it links in `fuzz-deps:` lines; `build.sh replay` makes a program that replays the files on its command line under the sanitizers, with a main of its own, and `build.sh fuzz` the libFuzzer program. The receive harness stands on the packet host test's interface and stubs. The three block file systems share `fs_common.h`: the driver's kernel calls stubbed as the host tests stub them, a block device over a volume in memory, and one walk that mounts, lists the root, reads every file and unmounts. FAT and exFAT take a focused input and scatter it over a volume the fixture makers build in memory, through builders the makers now expose: for FAT the boot sector, 4 KiB of the first FAT and 16 KiB from the start of the data region, where the root directory is; for exFAT the twenty-four boot sectors, 4 KiB of the FAT and 32 KiB from the start of the cluster heap, with both boot checksums recomputed after the scatter. Where an input ends early the rest of its regions are zero, not the seed's bytes: with the seed as the fill, libFuzzer shortened every input to its boot sector and called the coverage the same, and the directory regions were never mutated, and the block cache is invalidated before every mount, since it outlives the call and answered a mutated input with the blocks the last input's mount had read. Together the two faults are why the first planted faults in these three parsers went unfound for 400 s each and why their coverage lines barely moved. The first form, the input laid over the first 256 KiB of the volume, spent its mutations on the reserved sectors and the second FAT, and the coverage line did not move; ext2 and KRFFS take the whole 64 KiB volume as the input. The corpora are committed under `tests/fuzz/corpus/`, and the host tier replays each through its harness.
* The proofs, on the testing host with libFuzzer 21: in 30 s on its seed each harness's coverage line grew, ELF from 49 to 103 edges, packets 32 to 46, MBR 15 to 44, GPT 28 to 76, KRFFS 33 to 83, FAT 197 to 202, exFAT 260 to 265, ext2 195 to 198; the three block file systems start high because the seed volume already walks most of the read path, and the harness reads and never writes, so the write half of each driver is out of its reach. A planted fault in each parser, the ELF loader's chunk bound, the Ethernet length check, the GPT and MBR entry loops, the KRFFS name bound, was found from the corpus in under 90 s as a sanitizer report. With the two harness faults fixed, in 30 s FAT grew from 236 to 507 edges, exFAT from 310 to 379 and ext2 from 199 to 222, and ext2's unplanted run found entry 111 of the shortcomings list, a null mount read when the root inode is not a directory, in its first 113 inputs; the fix is in and the input is in the corpus. The exFAT plant, the cluster shift bound, was found after 401,294 inputs as a shift too large under UBSan; the ext2 plant, the block size shift bound, after 8,065 on the fixed source. The FAT plant, the long name's sequence bound, was not found in 1,455,609 inputs over 15 minutes: its trigger is one of eleven values in one byte at one of the directory's entry positions, and a mutation that lands there adds no coverage on its own, so nothing leads the fuzzer to it. The harness does reach the fault: a crafted input with that byte set, replayed through the harness with the plant applied, reports the stack overflow at once. That plant stays recorded as unfound by mutation, and the FAT harness stands on its coverage growth.
* `tools/verify/coverage.sh` builds a host test again with `--coverage`, runs it, and prints the lines executed and the branches taken for every kernel source the test compiled, whether linked from its `host-deps` or included into it; nothing is summed. On the Mac `gcov` is llvm-cov's.

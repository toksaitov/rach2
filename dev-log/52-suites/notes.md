# Milestone 52: notes

## Phase 1: the counters and the kernel faults

* The ext2 truncate cost three synchronous requests for every block it freed: the pointer slot, the bitmap byte and the group descriptor each written through, since a free ran outside the batch a write opens, whose order is the wrong one for a free. A 64 MiB shrink was 49000 commands and a hundred seconds alone on the emulated disk, and the large suite stalled after its rate line under both full sets. Entry 100 of the shortcomings list. The fix is a free batch with the order reversed, the pointer blocks and the inode `first` and the bitmaps and descriptors `after`; `bigfileprobe` counts the disk's commands around its truncate and holds them under a few per pointer block freed. Fixed 129 s, mutated 135 s failing on the bound, restored 128 s, on the testing host; the ext2 host test's 329 stops walk clean.
* The wait-tick counter was the ATA driver's alone; it is counted in the request layer now, a tick for every request in flight, on every device, and the polled AHCI driver counts its polls. The disk rate suite's device rows are held under ticks in flight per command and no quarantine instead of 120 s. The emulator's full set measured the boot's driver at 65 status reads and 0 ticks in flight a command, and every device row at 0.
* Under KVM the USB key latency rows dropped their record: the reader ran 20.4 ms after its wake, two ticks, where the emulator runs it in 0.3 ms. An instrumented boot said what the wake found, under both accelerators: the reader itself was the current process, inside a system call, with no switch pending. It was still writing its `KEYLAT READING` line, whose token the harness had already seen. `k_putc` redrew the whole screen after every byte, two thousand cells to the adapter's memory, which the emulator does in microseconds and nested KVM traps cell by cell: the two bytes after the token cost twenty milliseconds there, and every line the kernel or a program prints cost the same, which is where the slow boot output and the slowed hub scan under KVM came from. Entry 101 of the shortcomings list. The driver writes one cell per byte now, scrolls by moving the CRTC start address through the eight screens the adapter maps, copies the rows that stay to the front once in 179 lines, and places the cursor once per write, held across a record, a console chunk and a kernel print. `tests/host/vga_text_hosttest.c` counts it, one cell a byte, eighty cells and four port writes a scroll, and four mutations of the driver fail it; the screen after 1300 lines under the emulator reads right.
* The boot's timing record judged the 200 ms delay and the tick against time the host owns; under KVM in a full pool the delay read 410 ms, since a hypervisor that stops a machine delivers the ticks it missed afterwards, and the default suite failed on it. The record's level is the clock's self-agreement alone now, and the delay and the tick are printed as warnings when they disagree.
* Under KVM the mount suite's dirty row took 800 s in a run of two suites where the emulator takes 65 s: a flush answered and a duplicate completion dropped every 0.55 s for the whole run, and nothing between them in the log. In the KVM full set of round 8 the same row took 60 s and passed, with the probe's counters: 4176 commands, 1822 flushes and 794 ticks in flight for a megabyte left dirty and reclaimed, every lagged flush costing its three ticks and no more. What made a flush cycle cost forty ticks on the idle host is not known yet; the scheduler experiment is queued for it beside the key latency's.

* Under KVM in the full pool the self-build suite's second copy panicked with `pagecache: unrecoverable disk fault` and no record before it, and the halted machine was stopped as idle 300 s later. The page cache fills with interrupts off, polling, and the ATA driver's polled wait read the status ten million times in a row; each read is a trap that takes the emulator's lock, and QEMU's main loop, which completes the DMA, did not get in. On the idle host the same build takes 17 s and its `du` 0.3 s. Entry 102 of the shortcomings list. The polled wait reads a few hundred times plainly and then pauses ten thousand `pause` instructions off the device before each read, bounded by rounds, and records the status it saw when it gives up; the spins before a sleeping wait's sleep are 8, not 64, since a DMA command answers by interrupt and each spin is a trap.
* The record that wait now leaves named the next fault: a polled wait for data after 200256 reads saw the drive ready with DRQ clear and the bus master's interrupt pending, since the polled path had written its PIO command while the channel owner's DMA was in flight. The emulator shows a drive in a DMA transfer as ready with DRQ set and BSY clear, the polled path waited for BSY alone, the drive refused the second command, and the polled path then read the DMA's data phase as its own sectors, which is where round 12's `No space left on device` on a disk half free and its fault at a garbage address came from. Entry 103. A caller without the channel waits for the drive idle, DRQ clear as well; the owner's DMA is written and started with interrupts off; a data-port transfer runs with interrupts off whoever the caller is.

* The acceptance's emulator set failed the self-build once more, with its disk kept: the KRFFS checker found the node after `ata.c` holding the text of `ata.c` itself where a header should be, and the kernel's record named the fault's instruction, a directory read. The root file system's data operations took no lock; the disk driver sleeping inside them, which this milestone brought, let a second process's growth move a node under the first one's write. Entry 104. The five operations hold the mount's lock now, and its release yields to a waiter: the first acceptance after the review failed the default suite and both self-builds under KVM because the zombie probe's victim starved on the lock while the self-build's writer released and retook it.
* The Codex review of the milestone's diff, thirteen units, found what the sets could not: a page written back while the driver slept could be marked clean with bytes the disk did not get, a shutdown could wait forever for a channel's owner with the scheduler off, a flush could go to the other drive, a failed DMA could be erased by a polled command after it, the read-only policy refused the 28-bit DMA read, the ATA sleeper's ticks were not counted, the console could scroll past its memory when a keyboard's echo cut a scroll in two and moved the picture's start address in a graphics mode, the runner read the wrong fields of a process's stat and killed a silent computation before its first sample, the checker let a sleep through quotes and measured a typed line short of an escaped quote, the image race suite touched a shared prerequisite and the usb suite copied another suite's stick, and five probe rows proved less than they said. Each is fixed; the host tests count the fixes where a model can, and the sets the rest. The later units found the suites' side: nineteen suite targets called the wait helper without declaring it, so a suite run alone could fail at its first wait; five suites' waits could pass the run's deadline inside a wait; the helper's `\|` needs `REG_ENHANCED` on macOS; the flood count read a failed `netstat` as zero; the metal suite overwrote its output prefix; the load suite's second boot could sleep in the driver it meant to keep busy, which `rach2.atapio` now keeps on the data port; the exitline suite waited for half a diagnostic; and the probes said `READING` or `HOLDING` before the state they named, which the kernel's `disk-in-flight` count and a record when the console's reader parks now establish. Rejected: the images check cannot say which suite wrote a file, only that every file made has one declared owner, which the Readme now says.

## Phase 2: the harness and the checker

* The runner stops a suite as hung only when it is idle: no output, no console output, and next to no processor time in its group, under a tenth of a processor over the silent span, the time of reaped children counted from `/proc` and the group's process count watched, since a shell running one short command after another keeps no time of its own. The rate is there because a halted machine still takes a few percent for its timer under either accelerator: the KVM set of round 7 held three suites for half an hour at three percent each, silent, and the first form of the check, any growth at all, called that work. The self-test passes on the testing host.
* `runutil gone` reports an ended child gone before its parent has waited for it: a child stays a zombie until then and `kill` still reaches it, so the first form waited every bound out, and the self-build's bounded disk assembly spent 900 s that the idle limit then cut. The zombie is read from `ps -o stat=`.
* `runutil until FILE PATTERN SECS [COUNT]` and `runutil gone PID SECS` are the suites' waits; every hand-rolled loop of `grep` and `sleep 1` in nineteen suites became one of them, and the callers' `$(scaled N)` went with them, since the helper scales.
* The harness's `wait=` step is gone; `tcp=` reads the first bytes the guest's server sends and connects again until they come, so a capture is complete when the step ends. The suites' 68 `wait=` steps are tokens: the kernel's new `net: eth0: IPv4 a.b.c.d/p` and `IPv4 none` lines for an address set or dropped, the USB device line before the prompt, the probes' words for a pending read (`KEYLAT READING`, `TTYPROBE RAW`, `LOADPROBE read`) and for a hold established after its first request (`USBDISKPROBE HOLDING` and its kin), ping's reply count, a second renewal, and `tail -f | grep -m 1` of a service log in the guest.
* `tools/verify/suitecheck.sh` in `tests/run style`: no `sleep N`, no `wait=`, no upper bound on a duration in a probe, unless marked `interval: REASON` and listed in `tests/system/intervals`; twenty-two intervals are listed, each a load period, a holder, a file time or a poll of a server. Twenty-seven self-test cases.
* Pooled suites share nothing: the registry's fourth column declares what each suite writes under `build/images`; the runner refuses a shared glob and fails a run in which a file was made that no suite owns or two own. The usb, memory, metal and socket suites name their outputs after themselves now, as do the default, fpu, pools and raw targets, and the account suite's copy and logs of the shared os-simple image, which the KVM set of round 12 reported as an undeclared fail log.
* The lone list is deleted: usb, diskrate, install and imagerace run in the pool.
* The declarations found the shared test image restaged in the middle of two sets, by whichever suite's make came next: the metal suite made its acceptance copy with `mktemp` under `build/tests`, whose directory time the image depends on through the manifest's tree line. The copy lives under the images directory with the suite's name now and its exit trap removes it; the first form removed it before the trap, whose restoring copy then failed under `set -e` and turned a printed PASS into a failed suite.
* The harness's probe step ends when the run's token has arrived: the first form waited for the machine to leave until the step limit, which the KVM set's factor of four put at 360 s, past the runner's idle limit, and the three disk suites were stopped as idle at their prompts with `BLOCKPROBE OK` printed. Under the emulator the same wait cost each `probe=` row its whole step limit after the token.
* The clean build of the acceptance found what the rounds could not: two usb rows attached their sticks by the old name, which a stale file from before the rename had answered in every round, and the clean tree had none. The names are the suite's now. The host's compiler raised two warnings in `setidcheck`, an unused variable and a path that could be cut; both are fixed.
* The console fix moved the shell's prompt ahead of a deep hub's keyboard line under the emulator, and two usb rows that expected the two in the other order waited out their limits behind the cursor. The harness has a `seen=` step now, satisfied by a token anywhere since the last send, so two of them hold in either order; the twelve usb rows that wait for a keyboard and the prompt use it. Two self-test cases hold the difference from `expect=`.
* The harness's probe step types its line again when the shell answers `Unknown command`: a line typed at boot, before the shell was reading, arrives without its first bytes, and the shell's answer to `xec /hello` is neither silence nor a running probe. The exitline suite's no-token row lost its first byte that way in round 10 under the emulator's load.

## Phase 3: the probes

* The load, ping, loopback and sleep probes are judged by counts and ticks: the load probe prints the kernel's timer, disk, disk-wait and console counters and the lines it typed, and each stage's bound is a count the kernel keeps; the ping and loopback probes count a round trip's ticks; the sleep probe's rows are ticks slept against ticks asked.
* The AHCI and lag probes are judged by order and counts: the quarantine row reads `disk-quarantines` from `/proc/disk` around its request, the lag probe's dirty row prints commands, flushes, wait ticks and lag completions, and its deadline rows require at least one quarantine and one release per read past the deadline, with the counts printed, since the exact one the first form required is two under KVM when the tick that quarantines also releases.
* The console load probe's first stage is judged by the interrupt counter (entry 98), and its writer is waited for under a limit instead of failed at the stage.
* Every probe a suite typed at and then waited seconds for says when it is ready: `KEYLAT READING` and `KEYLAT HOG` before the read, `TTYPROBE RAW` when the terminal is raw, `LOADPROBE read` for every line the load probe takes, `USBDISKPROBE HOLDING` and `READING`, `LOOPPROBE HOLDING` and `KRFFSPROBE HOLDING` once the first request is in, and `usbprobe N` settles on the hub scan and says so. The big file probe counts the disk's commands around its truncate. The exFAT crash row is judged by the two checkers' agreement on the repaired copy, and the SSH flood by its presence and its release.
* The expected values are read from the set logs of both accelerators as the sets run; the Readme records them at the close.

## Phase 5: the cuts

* `selfbuild-ext2` builds the kernel once; the second build, the hash comparison and the userland half are the KRFFS run's. The three installer suites are partitions of one script and not repetitions. The account suite's 62 fed lines at six seconds each were its whole cost, 400 s, and under KVM the feed lost lines to `login`, which flushes its input before asking: the command sequences are typed through the harness now, each line at the prompt or the marker it answers, and the last marker is the harness's token, since a run without one waits for the machine to exit. The os-simple arc's last marker was written split, `TRY""END`, as the busybox arcs write theirs, and the ISH shell does no quote removal, so it printed the quotes; the marker is plain there, and the step before it waits for su's answer, since a line typed while su reads a password is not echoed and the marker would otherwise end the machine before the answer. The same arc's adduser expects were in the busybox order, the password prompts first and the created line after, where this project's adduser prints the created line first; an expect behind the cursor waits out its whole limit, 240 s under the KVM set's factor, and the arc then reads as a failed step with every marker printed.
* A kernel-mode page fault record names the instruction pointer now, and a page cache write-back that fails is recorded, since the self-build's second copy under KVM ended in `No space left on device` and a fault at a garbage address with no record before either.
* A line typed at the console longer than 255 characters is cut by the line discipline, which KVM showed in six rows the emulator had passed by the shell's own editing; the lines are split and `style` refuses a `send=` over 240 characters.

# 84-72: the tick's work under the big lock, and the round's user time

The tick's locked part fell from 12.4 to 4.7 us a tick in a vkcube round on the testing PC, and its worst single pass from 28.7 ms to 2.5 ms. The fall comes from three changes: a card's carrier is kept for two seconds, COM1 is read by the tick only when its interrupt cannot be trusted, and the boot processor's HDA, lag-device, block-request and speaker work runs before the lock. Tick accounting now charges ticks that interrupts-off kernel code held back where Linux would have taken them. Exact cycle counts show the charged user time matches the real user time to within 0.06 s a round. Rach2's round still spends 0.1 to 0.25 s more real user time than Debian's, in short-lived processes, and this task did not find why.

## Method

Each figure comes from `77-11/profile.sh` with `FRAMES=346 PERF=0`, the 346-present round of 77-11b. Rounds alternated a base kernel (origin/milestone/76-display at this task's start, x86-64, 3,444,848 bytes), the task's kernel and Debian's reference guest, on the testing PC from 2026-11-12 22:18 to 2026-11-13 00:32 (UTC+6), with other workers' load on the host. Every round's held frames had Debian's checksums, 0x75d4ad32 and 0x1a0d31d7. Tick figures are debugfs's `bkl/tick` for the round, and user and system time are `stat.py` over `/proc/stat`. Linux file and line references are to 6.12.115 at `build/research/linux-6.12.115-full`.

## The tick's locked work

The base kernel's locked part, the rows after `lock` in `bkl/tick`, cost 67.4 ms a round, 12.4 us for each of 5,451 locked ticks (means over 12 rounds). Two rows held most of it, and both read device registers. Under KVM a register read exits to QEMU and waits for QEMU's main lock while virgl works, which takes 0.2 to several ms:

* `ip6`, 16.5 to 49.7 ms a round, worst pass 28.7 ms. IPv6's timers, netlink's watch and each transmit asked `netdev_running`, which read the e1000's STATUS register every time. Linux reads the carrier from kept state (`netif_carrier_ok`, include/linux/netdevice.h:4257), which e1000's watchdog sets every two seconds and on a link-change interrupt (drivers/net/ethernet/intel/e1000/e1000_main.c:2547, 3757-3761). Rach2 now keeps a reading that found the carrier up for two seconds, and the e1000's and RTL8168's link-change interrupts and an administrative change of the interface drop it (`netdev_carrier_changed`).
* `console`, 5.8 to 45.8 ms, worst pass 24.4 ms. The tick read COM1's line status every fifth of a second as a backup for its interrupt. Linux reads an 8250 that has an interrupt from no timer (drivers/tty/serial/8250/8250_core.c:207-213, 269-275), and its handler bounds a pass with PASS_LIMIT (line 41). Rach2's tick now reads the port only while its interrupt is off, or after the handler stopped at its pass limit with data still waiting (`serial_rx_line_high`).

The HDA tick, the lag device, the block requests' deadlines and the end of a speaker's tone now run on the boot processor before the tick tries for the lock (`timer_own_work`, `kernel.c`). Each runs under the lock of its own that row 11 of the lock-order table in `proc/Readme.md` already lists: HDA's `stream_lock`, `block_lag_lock`, `block_req_lock` and the speaker's lock. Linux runs a driver's timer under the driver's own lock in the timer softirq (`call_timer_fn`, kernel/time/timer.c:1769-1795). debugfs's `bkl/tick` lists these rows before `lock`.

|---|---|---|
| locked part, all rows after `lock` | 67.4 (12.4 us a tick) | 25.7 (4.7 us a tick) |
| `ip6` | 16.5-49.7, mean 26.9 | 2.8-5.3, mean 3.5 |
| `console` | 5.8-45.8, mean 15.0 | 1.6-2.1, mean 1.9 |

The work left under the lock is the network stack's periodic work (`tcp` 6.8 ms, `platform` 4.1, `netdev` 1.3, `input` 1.1, `netlink` 1.1), the signals and the load average. Linux runs that work under the socket and device locks that the network stack would need, which Rach2's network stack does not have yet. That conversion is the size of a milestone and was not part of this task.

## The user time

### Ticks held behind interrupts-off code

Rach2 runs a system call with interrupts off, so a tick that comes during the call is held and taken only when interrupts come back on: at the first user instruction after the call, or when an idle wait's halt begins. `sched_account_tick` charged such a tick to the mode it found, which made a system call's time into user time or idle time. Linux runs system calls with interrupts on and charges a tick to the mode it interrupts (`update_process_times(user_mode(regs))`, kernel/time/tick-sched.c:276; `account_process_tick`, kernel/sched/cputime.c:474-500). It charges a tick taken in its idle task, outside an interrupt, as idle (lines 496-499).

Now the one-shot APIC timer records the time of the last tick that has passed (`timer_tick_due`). Each return to user mode, entry from user mode, and start and end of an idle wait records a cycle count. A tick counted at a return to user mode, or at an idle wait's halt, is charged where Linux would have taken it if it would have arrived before that point: as system time, or as idle when the code that held it ran after an earlier idle wait ended. A tick's arrival time is its due time plus the processor's average interrupt delay, measured on ticks that arrived with interrupts on (`tick_late_ns`). That average matters under a hypervisor. Without it, a tick due in a call but delivered a few microseconds late, in user mode, counted as system time, and the ping-pong probe below fell to 0.000 to 0.016 s of user time against Debian's 0.04 to 0.10 s.

Earlier versions of the rule failed against measurement, and the commits record each one. Charging every tick by the mode at its due time disagreed with the exact counts below. Keeping only the latest change of each kind lost user stretches that an older idle wait hid. A tick that arrived several periods late had also reported its first missed deadline instead of its last, so it counted back from the wrong time. The APIC timer now reports the last deadline.

### Proof against exact counts

A throwaway kernel, not committed, also summed each processor's user time from the cycle counts at every return to user mode and the next entry. In four rounds it counted exact user time of 2.210, 2.239, 2.178 and 2.362 s. The task's rule charged 2.13, 2.16 and 2.21 s in the first three rounds, and the old rule charged 2.157, 2.241, 2.208 and 2.418 s in all four. Both tick rules are within 0.06 s of the exact figure. In rounds at this host load, held ticks were not what kept Rach2's user time above Debian's. During heavier host load earlier in the evening, the base kernel's user time ran 0.19 to 0.50 s above that of a version charging every held tick as system time.

A probe of 20,000 rounds of two processes that pass a page-touching turn through a pipe shows the difference that remains:

| touch ping-pong, user s | free | one processor | two processors |
|---|---|---|---|
| base | 0.065, 0.295 (one placement only) | | |
| task | 0.076-0.086 | 0.069-0.070 | 0.059-0.068 |
| Debian | 0.056-0.101 | 0.044-0.078 | 0.037-0.077 |

The touching alone costs 0.030 to 0.035 s on both systems, and a spinning loop's user time equals its wall time on both.

### What remains

Rach2's processes do more user work in the round. Over seven paired rounds at the end (cycles 34 to 40), Rach2's user time was 2.18 to 2.65 s, mean 2.32, the base kernel's 2.20 to 2.45, mean 2.30, and Debian's 2.02 to 2.34, mean 2.12. The exact counts above put Rach2's real user time at 2.18 to 2.36 s. Three measurements narrow it down:

* Steady rendering: over 10 s in the middle of a 3,346-present round, all threads spent 0.36 s of user time on Rach2 against 0.30 s on Debian. Weston's share was 0.28 against 0.22 s.
* The round's start phases, with `PHASES=5`: the GCC build of `vkhold.c` took 0.035 to 0.048 s of user time against 0.030 to 0.039 s, vkcube's start 0.018 to 0.023 against 0.026 to 0.040, the screenshooter 0.019 to 0.024 against 0.015 to 0.024, and `frame.py` 0.31 to 0.33 against 0.30 to 0.33.
* With every thread sampled every 0.1 s through a round, the threads that lived long enough to be seen spent 1.53 s of user time on Rach2 against 1.51 s on Debian, of which python3 took 1.27 against 1.22 s. Rach2's round forked 221 to 229 processes against Debian's 281 to 282.

The difference is therefore spread over the round's short-lived processes, a few hundredths of a second each, and none of these measurements names a cause. The Lenovo's gap, 1.4 to 1.7 s a round in 77-11, was not measured with this kernel. On bare hardware the big lock's waits keep interrupts off for longer, which makes held ticks more frequent than in a guest, so the accounting change may close more of the gap there. A trial boot on the Lenovo would show how much.

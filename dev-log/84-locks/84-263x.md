# 84-263x: rseq_test made too few KVM_RUNs because Rach2's nanosleep had no timer slack

KVM's `rseq_test` failed in `machine.kvm.selftests` and `-nested` on x86-64 with "Only performed 23407 KVM_RUNs, task stalled too much?", under the 50,000 it needs. The cause was not in KVM and not in the migration: Rach2 ended a nanosleep at the time asked for, where Linux ends it at the end of the thread's timer slack, 50 us later. The test's migration thread sleeps 1 to 10 us between migrations, so on Rach2 it came back while the vCPU was still in the guest and kicked it out, at a cost of some 280 us each time. Rach2 now keeps Linux's per-thread timer slack, applies it to nanosleep and clock_nanosleep, and has prctl's PR_SET_TIMERSLACK and PR_GET_TIMERSLACK. rseq_test passes three times in a row on each profile with 90,374 to 97,235 KVM_RUNs, where Linux at the same depth makes 97,349 to 98,457.

## The test

`tools/testing/selftests/kvm/rseq_test.c` of Linux 6.12.115 runs a vCPU whose guest does nothing but GUEST_SYNC, an `in` that exits to user space, in a loop until a second thread has made 100,000 migrations. The migration thread bumps a sequence count, moves the vCPU thread to the next processor with `sched_setaffinity`, bumps the count again and sleeps `usleep((i % 10) + 1)`. After each KVM_RUN the vCPU thread compares rseq's processor with getcpu's, spinning while the count is odd. The test then requires more than 50,000 KVM_RUNs, a migration to KVM_RUN ratio of 2:1.

The `errno=4` the failure prints is not a KVM_RUN's EINTR. Every `get_ucall` ends with `vcpu_run_complete_io` (`lib/ucall_common.c:157`), a KVM_RUN with `immediate_exit` set, which returns EINTR by design and leaves errno 4. Linux's trace shows the same EINTR, `kvm_userspace_exit: reason restart (4)`, after every ucall. Counters in Rach2's run loop found no KVM_RUN that a signal or KVM_REQ_EXIT ended in a failing run.

## Measurements

All runs are on the testing PC under WSL's KVM, two processors, 6 GiB, the GNU root of the main clone booted with the task's kernel and the KVM suite's data disk. KVM_RUNs are the I/O exits that `tests/kvm/exits.sh` counts, one per GUEST_SYNC, which match the test's own count where it printed one.

Rach2 at 201efa847, the milestone's head, which has 752263c8d, on `max-svm`:

| Run | KVM_RUNs | Seconds | Interrupt exits |
| --- | --- | --- | --- |
| 1 | 18,989, failed | 14 | 33,358 |
| 2 | 24,766, failed | 14 | 25,492 |
| 3, with counters | 26,325, failed | 17.4 | 26,306 |
| 4, with counters | 20,585, failed | 15.8 | 23,401 |

So 752263c8d does not cover it. Temporary counters in run 3 (not committed) gave, for the 99,103 moves of the running vCPU thread: 90.8 us on average in `sched_setaffinity`'s wait for it to leave its processor, 24.7 us off any processor before it ran on the other, and 37,256 of them (38%) found it inside KVM_RUN. The migration thread's 100,000 sleeps of 1 to 10 us took 46.9 us on average. An I/O exit's round trip cost 176 us, 116 us of it in the guest's entry and exit, three hypervisors deep. An interrupt exit cost 285 us, entry, the run until the kick, the switch away and back and the next entry. Neither KVM_RUN loop returned EINTR (`KVM_REQ_EXIT` 0, signal 0).

Linux 6.12.107, Debian's kernel of `tests/kvm/guests/mklinuxhost.sh`, booted the same way on `max-svm`: 97,640, 97,349 and 98,457 KVM_RUNs in 28 to 30 s, with 2,857, 4,079 and 2,418 interrupt exits. An ftrace of a fourth run, over its last 10 s, gave 35,825 `sched_setaffinity` calls at 77.5 us, of which 2,508 (7%) found the vCPU in the guest; 35,825 sleeps at 171.6 us; a guest stay of 157.5 us; and 1,015 interrupt exits beside 35,043 I/O exits. The trace shows the migration thread's timer waking it on the other processor within a few microseconds of each vCPU exit, so that each migration lands while the vCPU is in user space, one KVM_RUN for each.

The difference is the sleep. Linux's `hrtimer_nanosleep` gives its timer the range of the request to the request plus `current->timer_slack_ns` (`kernel/time/hrtimer.c:2141`), 50 us for a thread that is not real-time, and the clock event is armed for the range's end when no earlier timer is due, so `usleep(1)` sleeps at least 51 us. Rach2 armed the request itself, and its migration thread came back after 47 us, mostly the wake's latency, while the vCPU was in its 116 us guest round trip. With the slack applied to those sleeps alone in a test kernel, the sleeps took 160 us, the wait in `sched_setaffinity` fell to 36.7 us, and the test passed twice with 96,292 and 96,203 KVM_RUNs.

## The change

* `process_t` has `timer_slack_ns` and `default_timer_slack_ns`, 50,000 for every new record (`PROC_TIMER_SLACK_NS`, Linux's `init_task`). Fork gives the child the parent's slack as both, as Linux's `copy_process` sets `default_timer_slack_ns` (`kernel/fork.c:2331`).
* A change to SCHED_FIFO, SCHED_RR or SCHED_DEADLINE sets the slack to 0, and a change back gives the default (`sched_store`), as Linux's `__setscheduler_params` does (`kernel/sched/syscalls.c:318-324`).
* prctl's PR_SET_TIMERSLACK sets the slack, or the default for 0, and changes nothing for a real-time or deadline thread; PR_GET_TIMERSLACK returns it (`kernel/sys.c:2566-2580`).
* `sleep_for`, behind nanosleep and a relative clock_nanosleep, and the absolute clock_nanosleep on real time, time since boot and boot time sleep to the time plus the slack (`sleep_slack`). A CPU clock's sleep takes none, as Linux's CPU timers have none. The sleep of zero, which already lasted Linux's 50 us, now lasts the thread's slack. A remainder now runs to the slack's end, as Linux's `hrtimer_expires_remaining` does, so nanosleep(2) loses that difference from Linux.

Linux applies the slack also to the timeouts of poll, select, epoll_wait and a futex wait; Rach2's still end at their time, which makes them earlier than Linux's and is no limit. This task leaves them.

## Proof

The fixed kernel on `max-svm`: 90,374, 93,422 and 97,161 KVM_RUNs in 24, 27 and 36 s. On `host-svm`, the nested case's profile: 97,235, 97,169 and 97,157 in 21, 28 and 23 s. All six runs exit 0.

In the same boot, through prctl from Python: the slack reads 50,000, usleep(1) takes 59.3 us on average, a slack of 1000 reads back and usleep(1) takes 15.2 us, 0 gives 50,000 back, a forked child reads 50,000, and under `chrt -f 10` the slack reads 0 and a set leaves it 0.

`prctlmusl` has four rows for the slack: the default, a value set, the default after 0, and a child forked with 2000 that reads 2000 and gets 2000 back for 0. `syscall_hosttest.c` gives its model thread no slack, as a real-time thread has, for its rows of whole ticks, and checks the sleep of zero and one of 250 us with 50 us of slack, ending 50 us past the request between ticks, and a sleep of zero without slack, which does not block. Both host builds, 1000 Hz and 250 Hz, pass.

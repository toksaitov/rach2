# 84-264u: why Proton's d3d9:device crashes after DXVK's submission timeout on Rach2 and not on Debian

The task's premise does not hold: Debian's lavapipe submission in `test_occlusion_query` also runs past DXVK's 5 s timeout, in every run. What differs is what happens after it. DXVK resets the command list that lavapipe's queue thread is still walking, and the queue thread then reads the freed commands. Debian's glibc 2.41 leaves those commands readable; Rach2's glibc 2.44 writes free-list pointers over them, and the walk crashes. With Rach2's glibc 2.44 bound over Debian's, the same unit crashes on Debian's kernel as it does on Rach2's, with exit 245 after 142 lines, in 3 of 8 runs. The kernel takes no part in it, so there is no Rach2 fault to fix and nothing that Linux with the same glibc would do differently.

## Debian times out too

Every run of the unit in the Debian reference guest logs `DxvkSubmissionQueue: Timeout occured, GPU likely hung.` five seconds after `device.c:6759: Expects 0x0000000104000000 samples.`: the 12 runs of 84-262t (stamped 18.631 s and 23.598 s in [d3d9-device.txt](84-262t/d3d9-device.txt)) and the 10 of this task ([results.txt](84-264u/results.txt)). Debian's submission lasts some 15.7 s, to the `device.c:6780` record at 34.330 s, where DXVK reports the device lost and the unit later dies with an access violation, exit 5. So a 5 s submission is Linux's behaviour on this unit, and the scheduling and fault counts the task asked for, which would explain a submission that is slower on Rach2 alone, measure a difference that does not exist.

## glibc decides the crash

The GNU root builds its own glibc 2.44 (`vendor/gnu/sources.txt`) and takes Mesa 25.0.7's lavapipe from Debian 13's packages, which also run on glibc 2.41-12+deb13u4 in the reference guest. One boot of the reference guest under KVM, with 8 CPUs, 16 GiB, virtio-vga and lavapipe as 84-262t's, ran Proton's `d3d9:device` twice on Debian's glibc and then eight times with the root's x86-64 glibc 2.44, all fifteen of its libraries and `ld-linux-x86-64.so.2`, bound over Debian's files by [ref244.sh](84-264u/ref244.sh) on 2026-11-14 between 22:44 and 22:52 UTC+5:

| glibc | runs | exit 5 after some 57,177 log lines | exit 245 after 19,674 log lines, 142 test lines |
|---|---|---|---|
| Debian's 2.41, this task and 84-262t | 14 | 14 | 0 |
| Rach2's 2.44, on Debian's kernel | 8 | 5 | 3 |
| Rach2's 2.44, on Rach2's kernel, 84-262t | 66 | 28 | 38 |

Each crash on Debian ends as Rach2's do, with the timeout as the log's last line ([results.txt](84-264u/results.txt)). Debian's glibc gave no crash in 14 runs and Rach2's gave 3 in 8 on the same kernel; at Rach2's rate of 38 in 66, 3 or fewer crashes in 8 runs come one time in five.

## What glibc 2.44 changed

glibc 2.44's `malloc.c` has no fastbins: `_int_free_chunk` merges every freed chunk that its thread cache does not take with its free neighbours at once and puts the result on a small bin or the unsorted bin (`malloc/malloc.c:4056-4072`, `4153-4205`), which writes the bin's forward and back pointers into the first 16 bytes of the chunk's memory, and a merge that reaches the top of a thread's arena may give the pages back with `MADV_DONTNEED` (`malloc.c:4225-4250`, `arena.c:486-495`), after which they read as zeros. The thread cache keeps 16 chunks of each size (`TCACHE_FILL_COUNT`, `malloc.c:309`) and also writes the first 16 bytes, a mangled link and its key (`malloc.c:2707-2712`). glibc 2.41 keeps 7 chunks of each size in its thread cache and puts freed chunks of up to 128 bytes on fastbins unmerged, writing only their first 8 bytes.

In Mesa 25.0.7 each recorded command, a `vk_cmd_queue_entry`, begins with its list link, the previous pointer and then the next one (`src/vulkan/util/vk_cmd_queue_gen.py:142-143`, `src/util/list.h:47-51`); the reset frees the commands in list order (`vk_cmd_queue_gen.py:192-195`, `332-342`), and lavapipe's walk takes each next command from the one before (`src/gallium/frontends/lavapipe/lvp_execute.c:4953-4959`). A command whose chunk lands on a 2.41 fastbin keeps its next pointer and its body, so the queue thread's walk goes on through freed memory to the end of the list; on 2.44 the walk reads a merged chunk's bin pointer, zeros, or the cache's key as its next command. Those are the three kinds of read that 84-262t found in Rach2's crashes: a command type read from a malloc arena's bins, a NULL `pipeline_nir`, and a non-canonical command pointer.

## What remains

The fault is DXVK's use after free on its submission timeout, recorded in [upstream.md](upstream.md#dxvk-frees-a-command-list-that-lavapipe-is-still-executing-after-its-submission-timeout); glibc 2.44 only stops it from passing unseen. Rach2's kernel needs no change. `tests/graphics/d3d/ref/linux.json` keeps its stop at the unit's `device.c:6759` record, since the rest of the unit follows a race that Debian's glibc happens to win and Rach2's loses about half the time.

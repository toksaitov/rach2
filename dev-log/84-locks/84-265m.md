# 84-265m: the soft lockup of CPU 3 under dEQP-VK on Venus

The release's rerun failed `machine.venus.fraction-1` on x86_64 with `watchdog: BUG: soft lockup - CPU#3 stuck for 23s! [deqp-vk:187]`, 437 s into the boot. CPU 3 is where the virtio-gpu control queue's interrupt arrives. Each answer the device gave walked every command the driver had not yet freed, under the device's spinlock with interrupts off. Four dEQP-VK processes kept enough commands alive that one interrupt's answers held CPU 3 for seconds, while the thread it had interrupted held the big lock and every other processor waited for it. The answer now walks only the fences in flight, as Linux's does, and the two other walks of the same lists take constant time.

The release's console was in the CI account, which this account cannot read, so every figure below is from this task's runs of the case alone on the testing PC under KVM, `RACH2_QEMU_ACCEL=kvm ARCH=x86_64 RACH2_CASES=machine.venus.fraction-1 tests/run venus`, at the milestone branch's head.

## Where CPU 3 stopped

The first run passed in 848 s with the default threshold, but its `/proc/stat` showed a hold of the big lock of 9.86 s and a wait for it of 9.87 s. The second run booted with `watchdog_thresh=3` and `softlockup_all_cpu_backtrace=1`, which report at 6 s. It reported `CPU#3 stuck for 9s! [deqp-vk:184]` at 456.8 s, with CPU 3 at the end of `schedule`, just past `schedule_tail`'s take of the big lock. Every other processor that logged its trace was waiting for the big lock in `bkl_acquire`: deqp-vk's process 177, which like 184 had slept on the ext2 writeback lock in a close from `mmap`, two deqp-vk processes back from `clock_nanosleep`, the writeback thread and two `etude-guest` calls. The longest wait of that boot was 17.1 s. It spanned holds of 7.6 s after a switch, 4.7 s in an ioctl and 3.3 s in a kernel thread. CPU 6's own trace was among the 26 records klog dropped.

The third run kept the 3 s threshold and added a report, for the run alone, from a waiter for the big lock: once a hold had lasted 3 s, the waiter named the holder and had it log its stack from an NMI. All three reports named CPU 3, held for 3.556 s, 3.595 s and 3.597 s, twice by the `virtio_gpu` worker just switched in and once by `etude-guest` in `wait4`. Each time CPU 3 was in the queue's interrupt, `vp_slot19`, `virtio_interrupt_queue`, `virtqueue_reap`, `cmd_done`, at the walk over `vg->live`:

```

    if (prior->queued && prior->fence && dma_fence_is_later(cmd->fence, prior->fence)) {
        dma_fence_signal(prior->fence);
```

The second hold also drew `watchdog detected hard LOCKUP on cpu 3`, since the handler runs with interrupts off, and `CPU#3 stuck for 30s! [etude-guest:85]`; its longest hold was 29.1 s.

## Cause

`vg->live` holds every command not yet freed: those held for a full queue, those in it, the answered ones nobody waits for until the reaper frees them, and the answered ones their waiters still hold. Each fenced answer walked all of them. Two other walks were as long: `vgpu_cmd_free` searched the same list for the command it unlinked, and `done_add` walked the done list to its tail on every answer, from the same handler. The reaper is the `virtio_gpu` worker. While the handler held the processor the worker was switched in on, the done list and the live list grew, and so did the cost of each answer.

Linux walks `drv->fences` in `virtio_gpu_fence_event_process` (drivers/gpu/drm/virtio/virtgpu_fence.c:134-174 in 6.12.115), the fences not yet signalled, and takes each one off when it signals. Its `virtio_gpu_queue_ctrl_sgs` waits for room in the queue before it emits a fence (virtgpu_vq.c:338-355), so that list never holds more than the queue.

## The fix

* A fenced command goes on the device's list of fences in flight in `pending_push`, as it enters the queue, oldest first. An answer signals its own fence and each earlier one of its context on that list, and takes each off. The list holds no more than the queue, and a command held for room is not on it, since its answer cannot come before it is in the queue.
* The live list has a back link, so a free unlinks its command at once and takes it off the fence list if it is still there.
* The done list has a tail, so an answer appends to it at once.
* An unplug empties the fence list before it signals every fence that is still live with `-ENODEV`.

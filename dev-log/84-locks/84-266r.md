# 84-266r: why WineD3D's d3d11 unit on Venus counted 500 failures where Linux's reference has 502

The release's second rerun, at 8b77e86d5, failed `machine.d3dvenus.wine-wined3dvk-d3d11-d3d11` on x86_64: Wine's `d3d11:d3d11` through WineD3D on Vulkan counted 500 failures, two fewer than `venus.json`'s 502, with the same 5,640,691 checks, 632 todo and 8 skips. The release's run of 2026-11-14 had counted 502. The unit's count varies from run to run on Linux and on Rach2, because WineD3D draws with a destroyed shader's pipeline when the heap gives a new shader module the destroyed one's address. Rach2 has no fault to fix: the unit is now judged by the lines its failures are on, as vkd3d-proton's varying tests are.

## The runs

The rerun's unit log was not kept, so its two checks cannot be named. Each run below kept the unit's failure lines. Rach2's ran at the head of `milestone/76-display` of 2026-11-15 (f6dc157af), its scenario changed in the clone alone to run the row several times in one boot and print each run's lines; the Debian guest's ran with `tests/graphics/d3d/reference.sh`, as the reference was taken.

Every failure of every run is on a source line that the stored Debian runs failed on. By line, against the stored runs:

* Rach2's 321: `test_texture`'s `d3d11.c:10263` failed 12 checks, test 24's, where the Debian runs fail 193: tests 60 to 72, `SampleLevel` at mip level 2 and the blends near it, drew the level asked for, where the Debian runs read level 0.
* Rach2's 482: `test_update_subresource`'s `d3d11.c:14621` and `14671` failed none of their 4 and 16.

* Rach2's 492: `test_resinfo_instruction`'s `d3d11.c:24057` failed 16 checks that the Debian runs pass, in place of the 26 they fail there.

Each of Rach2's 21 runs that counted 502 failed the stored runs' checks, message for message. Twelve processes spinning in the guest slowed a run some fivefold; the one such run on Rach2 counted 502, and the Debian guest's was stopped before its first run ended.

The Debian crash, `d3d11c`'s third run, ended with exit 1 after 39 test lines: its threads waited 16 minutes on WineD3D's `wined3d_cs` critical section, held by thread 0154, which then raised an exception outside its stack's limits. No Rach2 run crashed.

## The cause

WineD3D's Vulkan backend keeps each graphics pipeline it makes in `context_vk->graphics_pipelines`, a tree whose key compares each stage's `VkShaderModule` handle first (`wined3d_graphics_pipeline_vk_compare`, `dlls/wined3d/context_vk.c:2273` in Wine 11.0), and looks a draw's pipeline up there before it makes one (`context_vk.c:3723`). Destroying a graphics shader destroys its modules but leaves the pipelines made with them in the tree (`shader_spirv_destroy`, `dlls/wined3d/shader_spirv.c:1078`), where a compute shader's pipeline is destroyed with it (`shader_spirv_destroy_compute_vk`). A non-dispatchable Vulkan handle of Mesa's is the address of the driver's object, so a module that the heap puts at a destroyed module's address matches the destroyed shader's pipelines, and the draw runs the old shader.

`test_quad_tessellation` shows it directly. It releases its counter-clockwise hull shader and makes the clockwise one at once (`d3d11.c:26633-26634` in Wine 11.0's test). In the runs that fail its three checks, the stream output holds the counter-clockwise triangles and the back buffer stays white, as the culled counter-clockwise draw leaves it: the draw ran the released shader's pipeline. In the run that passes them, the new module landed elsewhere. Which address the heap gives follows its history in the process, which differs between runs; Rach2's GNU root has glibc 2.44 where the Debian guest has 2.41, whose heaps reuse chunks differently, which fits Rach2 varying in more tests and more often (5 runs of 26 against 1 of 31). The other varying tests also replace shaders between draws; their stale pipelines are not proved one by one.

Marking Venus's driver DF_1_NODELETE, as Rach2's root does since 2d38de52f, did not change Debian's count, so that change is not the cause of the rerun's 500.

## What changed

* `run.py` judges a Wine unit whose Linux runs counted different failures by `varying_lines`: each failure, a failed check or one inside a todo block that passed, must be on one of the source lines the Linux runs failed on, and the log must print as many as the summary counts. Any other unit's count must still equal Linux's.
* `mkref.py` folds such a unit with every count, its exit only where the runs agreed, and those lines.
* `venus.json` is folded again with the Debian runs of 2026-11-15, the crash set apart: `d3d11:d3d11` on WineD3D keeps 499 and 502 and the stored runs' 33 lines. Each Rach2 run above passes it; a failure on a line no Debian run failed on fails it.
* The runs are in `tests/graphics/ref/d3d-venus-wsl/` (`wined3dvk-d3d11.tar.gz`, `wined3dvk-d3d11-crash.tar.gz`), Rach2's six distinct runs' failure lines in `84-266r/rach2-runs.tar.gz`, and the fault in [upstream.md](upstream.md#wined3d-draws-with-a-destroyed-shaders-pipeline-when-a-new-shader-module-gets-its-handle).

The Debian crash is not in the reference. A Rach2 run that crashed the same way would fail the row; none did in 26 runs.

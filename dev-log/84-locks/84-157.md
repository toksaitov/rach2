# 84-157: EXECBUFFER2's per-call work that Linux does not do

84-146 left EXECBUFFER2 at 68.9 and 71.5 us a call on the Lenovo, over 1,003 calls of WineD3D's GL round trip, and the round trip at 349.9 and 350.9 ms per 1000 trips against Linux's 224 to 251. Its second boot's 49 profile samples fell in the command parser (8), the user interrupt's enable for each request (8), bindings (7), requests (5), the heap (4) and the GT's unpark (3), with the parser's shadow made anew on some calls. This task reads each of the six against Linux 6.12.115's i915 and closes the work Linux does not do for each call.

## The cause common to four of them

Each call the loop makes is waited for: Crocus signals a syncobj from the call, and WineD3D's command thread sleeps in SYNCOBJ_WAIT for it. The request's signal to that listener had the retire worker retire the engine at once and park the GT whenever every engine was idle, which on this loop is after every call. The park masked the user interrupt and let every idle shadow of the parser's pool go; the next call unparked the GT, raising RPS and waking the worker for the heartbeat, unmasked the interrupt, and made a new shadow, with its pages, its binding and the GTT search for it.

Linux does not park there. Its engine parks only after a switch to the engine's kernel context has run on the chip and retired (`__engine_park` and `switch_to_kernel_context`, gt/intel_engine_pm.c:151-288; every request moves `engine->serial`, i915_request.c:668, so after a user's request the switch is always made), and that request asks for its own interrupt (`dma_fence_add_callback` for its duration, gt/intel_engine_pm.c:232). On the Lenovo, Linux's loop of 1,003 calls took 1,013 interrupts on the GPU's line (IRQ 50 in `/proc/stat` at the loop's start and end, `dev-log/80-games/80-27/evidence/lenovo-linux/trip-gl-0.loop.txt`): one for each call's request and about ten besides, where a park after each call would add a second for each. So Linux's GT stayed awake from one call to the next on almost every call. What in Linux holds the engine's wakeref between calls, the retire worker's timing or something else, I did not settle from the code; the count is the evidence.

Now the GT parks only at the retire worker's pass, which runs on the first whole second after a second from the last, or at a wait for its idle, when every engine is idle (`retire_pass` in i915_request.c). A listened request still retires at once, so its objects and the shadow go back as before; only the park waits. While the GT is awake and idle, RC6 and RPS's down timeout lower its power, as they did already between unwatched requests, which waited for the same pass.

## The six paths

The shadow batch. Linux keeps a pool of shadows by size and takes a node back when its request signals (`pool_retire`, gt/intel_gt_buffer_pool.c:98-122), and frees a node only once it has been idle a second (`pool_free_work`, 87-96); the GT's park leaves the pool alone (`__gt_park`, gt/intel_gt_pm.c:101-125). Rach2's pool follows that, but its park drops every idle shadow, since no pass ages them while the GT sleeps. With the park after every call, every call made a new shadow. That is closed with the park. One difference is left that allocates nothing per call: Rach2 takes a shadow back when its request retires, which for a waited request is at its interrupt, but for an unwatched one is at the next request's creation, after the next call has already taken its shadow, so such a ring keeps two shadows where Linux keeps one.

The user interrupt. Linux arms the breadcrumbs' interrupt when a request gets a listener and keeps it armed until the engine parks or an interrupt finds no listener left (gt/intel_breadcrumbs.c:29-84, 182-207, 266-272, 317-324), since enabling and disabling it "is rather costly" (184). Rach2 unmasked it, a RING_IMR write with its posting read and the GT bank's unmask, with each request added to an empty ring, and masked it when a retirement emptied the ring, so once in each call. Now each engine's first request after the GT unparks takes the interrupt (`irq_armed`), and the GT's park lets it go. Every Rach2 breadcrumb interrupts, as before; with requests no one waits for, Linux would disarm after one interrupt, and Rach2 takes one for each.

The GT's unpark. Above. The unpark's `i915_rps_unpark` and the wakeups `request_new` makes for it (the heartbeat's kick and the worker's queue) no longer run for each call.

Bindings. The samples in `vma_create`, `i915_ggtt_find`, `ggtt_room`, `vma_bind` and `i915_ggtt_insert` are the new shadow's binding; a reused shadow keeps its binding, as Linux's pool node keeps its vma. `i915_vma_pin_args` for each object of the call is Linux's `eb_pin_vma` for each.

Requests. `request_new`'s wakeups were the unpark's. `intel_context_pin_image` returns at once for an image already pinned. `engine_submit` is Linux's submission from `i915_request_add`. The request itself is one block, as Linux's comes from its slab.

The heap. A call took four blocks besides a new shadow's: the call's object array and its fence array, which Linux's call also allocates (`kvmalloc_array` of the exec objects, gem/i915_gem_execbuffer.c:3584; the fence array's `krealloc`, 2942), the request, which Linux takes from `slab_requests`, and the request's hold, the references to the call's objects that keep them until the request retires. Linux allocates nothing for that each call: a vma's activity is a node of its `i915_active` for each timeline, made once and kept (`active_instance`, i915_active.c:288-341). The hold now lies in the request's own block (`i915_request_create_room`), so a call takes three. That every block is taken under the heap's one lock with interrupts off, where Linux's slab has a free list per processor, is the allocator 84-146 left alone; it is not changed here.

The command parser's own work, the copy, the check of each command and the trampoline, is Linux's too: Linux 6.12 parses every Haswell render batch whose length the call gives (`eb_use_cmdparser`).

## Measured

QEMU has no i915, so the measure here is the exec host test's chip model. Its new row `park_per_call` makes the call as Crocus does (`NO_RELOC`, `HANDLE_LUT`, `BATCH_FIRST`, a batch with a length, a target written, a syncobj signalled), puts a listener on the syncobj's fence while the request runs, as SYNCOBJ_WAIT's sleeper is, takes the interrupt and runs the retire worker, as on the machine between one call and the next, and counts over eight calls after one to warm. Run alone, with the same test file, on the milestone's head and on this task's:

| Over 8 calls | Before | After |
|---|---|---|
| GT unparks | 8 | 0 |
| GT parks | 8 | 0 |
| User interrupt unmasks | 8 | 0 |
| Shadow pages taken | 8 | 0 |
| Heap blocks | 64 | 24 |

84-146's `heap_per_call`, the same call not waited for, now takes 3 blocks a call on an idle ring and 6 on a busy one, against 4 and 7: the hold's block. The whole exec test passes at the head; at the milestone's head the new row fails, as it should, and so does `unbind_wait_spin`'s check that the GT parks when the unbind's wait ends, which now waits for the worker's pass.

The context host test's park rows, which checked the old rule, now check that a listened signal lets the engine go and that the worker's pass parks the GT; I changed them by reading and did not run them, as the milestone's rules have it, and split `row_park_watched`, which the change took past the size limit, into `row_park_waited` and itself.

# 84-264g: a virtio network driver, and the cases moved to it

Rach2 drove QEMU's RTL8139 and e1000, whose every register access under KVM is an exit that QEMU answers: 7,959 RTL8139 accesses in the default suite and 3,447 in `ssh` ([84-264e](84-264e.md)). The kernel now drives the virtio network device as Linux's `drivers/net/virtio_net.c` does, on the transport, queues and bus the virtio GPU driver uses, and 314 machines of 30 case families boot with it in place of the RTL8139.

## What changed

* `rach2/sys/network/driver/virtio_net.c` and `virtio_net.h` are the driver ([the network](../../rach2/sys/network/Readme.md#the-drivers), virtio-net(4)). It takes `VIRTIO_NET_F_MAC`, `STATUS`, `MTU`, `MRG_RXBUF`, `CTRL_VQ`, `CTRL_RX`, `CTRL_MAC_ADDR` and `SPEED_DUPLEX`, and the core takes `VIRTIO_F_EVENT_IDX` and indirect descriptors. It has a receive, a transmit and a control queue, each with an MSI-X vector where the machine has them, the function's line where it has not, and the tick where the device has neither.
* No checksum or segmentation offload is asked for. Linux asks for them because its stack can leave a checksum to the device and take a 64 KiB segment; Rach2's stack builds each frame whole, at most 1514 bytes, computes every checksum and checks every one it receives, so it could use none of them. The driver asks for what the stack has, as Linux's does.
* The shared virtio code gained four small things, none of which changes the GPU driver: a queue's `batch`, called once at the end of a reap that took buffers; `virtqueue_irq`, Linux's `virtqueue_disable_cb` and `virtqueue_enable_cb`; `dev->polled`, set when a device has no interrupt; and `dev->config_atomic`, which says a handler may read the configuration ([virtio](../../rach2/sys/virtio/Readme.md)).
* `kernel.c` calls `virtio_pci_probe` before the network starts, since the network's probe asks the transport for its devices.
* The driver is last in the probe's table. The table's order is the order of the interfaces' names, and a machine that has a PC's card beside a virtio device, as `machine.assign` has an e1000 beside the virtio device it gives to a guest, keeps the card as `eth0`.
* A link's speed is now 32 bits, and a driver may say that it does not know the speed or the duplex: `/sys/class/net/*/speed` then reads -1 and `duplex` reads `unknown`, as Linux's read for a virtio device without `VIRTIO_NET_F_SPEED_DUPLEX`. An interface has a largest MTU of its own, which a virtio device's `VIRTIO_NET_F_MTU` sets.
* A write to `/sys/bus/pci/drivers/virtio-pci/unbind` stops the device and leaves its interface without a carrier; `bind` brings the same function up again as the same interface.

## Tests

* `tests/host/virtio_net_hosttest.c` runs the driver and `virtqueue.c` against a model device: the bring-up, receive in one buffer and across several, transmit and its reclaim, a device without the event index, the link, the MTU, the control queue and a device that does not answer it, the failures of each step of the bring-up, the unbind and the bind, and a device with no interrupt. `tests/host/virtqueue_hosttest.c` has a row for a silenced queue and the batch.
* The suite `virtionet`, `tests/cases/machine.virtionet.json`, boots the device in five forms: as QEMU makes it, without MSI-X vectors, without mergeable buffers, the event index and the control queue, with a speed, a duplex and a largest MTU, and beside an RTL8139. `tests/vnetprobe.c` reads the interface's link files, pings, lets the driver go and binds it again through `/sys`, and pings again; one case pulls the cable through QMP's `set_link`.

## What was run

All on the Mac, QEMU 11.1.3 under TCG, on i686 and x86-64, at the task's head.

* The new host test and the changed ones, and the host tests of the files the task changed (`virtqueue`, `virtio_gpu`, `virtio_pci_shm`, `virtio_bus`, `e1000`, `rtl8139`, `rtl8168`, `netdev`, `wlan_dev`, `procfs`, `netif`, `netconf`, `synthfs`): each passes.
* `tests/run virtionet`: its five cases pass on each architecture.
* By hand, the test image with the device in nine forms (`vectors=0`, `mrg_rxbuf=off`, `event_idx=off`, `ctrl_vq=off`, `host_mtu=1400`, `status=off`, `speed=1000,duplex=full`, another station address, and none of these): `pingtest` and `tcptest`, against an echo server on the host, pass in each on each architecture. With four processors `vnetprobe` and `tcptest` pass on each. A device with `disable-modern=on`, tried on x86-64, is refused by the transport and the machine boots without a card.
* Of the moved families, `socket`, `subset`, `procfiles`, `pools` and `kvmclock`, and ten cases of `default` that use the network, pass on each architecture; `guest.default.callsmusl` failed its `itimer-first-tick` row twice on i686 at a host load average above 11 and passed twice on each card after, the row 84-264e names as failing under load.
* The suites kept on the RTL8139 whose machines have one card, `ping`, `packet`, `dgram`, `raw` and `netconsole`, were run once with the virtio device in its place, the manifests changed for the run and put back: each passes on each architecture.

## Not measured

The Mac has no KVM for an x86 guest, so the device was not run under KVM and its exits were not counted. Under KVM a notification is a write that KVM's ioeventfd takes without QEMU, as 84-264e found for Debian's virtio devices. The release's run on WSL is the first run under KVM, and the first of `machine.assign`, in which Rach2 now drives the virtio device as `eth1` until the case's script unbinds it for vfio-pci, and of the moved families that need the GNU root.

## Limits

* An interface is made only at boot. An unbound device's interface stays, with its addresses and without a carrier, where Linux removes the interface, and a device bound later that had no interface at boot is refused.
* `/sys/class/net/ethN/device` leads to the PCI function, where Linux's leads to the virtio device below it.
* `VIRTIO_NET_F_MQ`, `GUEST_ANNOUNCE` and `CTRL_VLAN` are not taken, and a legacy-only device is refused by the transport.

## The cases

The families whose subject is the wire keep the RTL8139, which a PC may have: `ping`, `packet`, `netif`, `dhcp`, `dgram`, `raw`, `netconsole`, `addressed` and `e1000`. So do those that boot an installer, a recovery image or firmware as a PC does, `uefi`, `installer`, `installer-repair`, `metal`, `grow`, `drill` and `sealed`, and the host checks' fixtures. The e1000's cases are as they were. Every other family's machines have the virtio device. `rach2/run.sh` keeps the RTL8139 as its default, and `NIC=virtio-net-pci` chooses the device.

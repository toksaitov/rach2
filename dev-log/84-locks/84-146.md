# 84-146: WineD3D's kernel time in EXECBUFFER2 after the forcewake fix

84-58 (#4733) measured WineD3D's GL round trip on the Lenovo at 394.9 to 408.1 ms a 1000-trip loop against Linux's 224 to 251 ms, with the loop's two threads' user time Linux's and their system time twice it: the main thread 29 ticks against 14, `wined3d_cs` 18 against 6. `I915_GEM_EXECBUFFER2` took 1,003 calls of 121.5 us over the loop, 126 profile samples, of which 62 were the forcewake handshake that 428e5e668 (84-58) fixes as Linux's `fw_domain_arm_timer`. This task looks at the other 64 and closes what differs from Linux 6.12.115's i915 on that path. The record of 84-58 is `dev-log/80-games/80-27.md`, section The Lenovo, "After 84's lock work", with its evidence in `80-27/evidence/lenovo-rach2-84/`.

## What differed from Linux

Each call, for each object, built fences Linux never builds:

* `dma_resv_add_fence_locked` made an object's writer the merge of its old writer and the request's fence (`dma_fence_merge`: three blocks, a context and a walk of both), even when both were points of the same ring, and kept every reader until it signalled. Linux replaces a fence that has signalled or that the new one is as late as on the same context (`dma_resv_add_fence`, dma-resv.c:287-326). Now a reservation does the same; a writer is merged only with one of another context, or when the new fence holds others, and a run of submissions on one ring keeps one fence in each slot.
* `eb_move_to_gpu` took `dma_resv_snapshot_locked` of each object, an array and a merge, to wait for it. Linux walks the reservation's fences in place (`i915_request_await_object`, i915_request.c:1602-1618). Now EXECBUFFER2 waits for the writer and, for a write, each reader in place, under the reservation's lock it already held.
* `i915_gem_object_wait` copied the reservation's fences into a new array before it looked at them, for the parser's `prepare_read` of the batch and `pool_get`'s move of the shadow to the processor's domain among others. Now it returns at once, with no copy, when no fence it would wait for is busy, as Linux's walk makes none (gem/i915_gem_wait.c:67-90).
* The call copied every object's relocations into the kernel before the GEM lock, Crocus's `I915_EXEC_NO_RELOC` calls included. Linux reads them only when an object has moved (gem/i915_gem_execbuffer.c:1912-1924), and then lets its locks go to copy them (`eb_relocate_parse_slow`, 1779-1821). Now the call copies them up front only without `I915_EXEC_NO_RELOC`; with it, a placement that moves an object lets the pins and the GEM lock go, copies them in, and places the objects again.

## Measured

QEMU has no i915, and this machine has no trial root, so the measure here is the kernel's own count on the exec host test's chip model: `heap_per_call` in `tests/host/i915_exec_hosttest.c` makes the call as Crocus does (`NO_RELOC`, `HANDLE_LUT`, `BATCH_FIRST`, a batch with a length and a relocation, a buffer read, a target written, a syncobj signalled) and counts the heap's blocks of four calls each on an idle ring and on a busy one, run alone at each head with the same test files:

| | Before, at 428e5e668 | After |
|---|---|---|
| Blocks a call, idle ring | 21 | 4 |
| Blocks a call, busy ring | 23 | 7 |
| The target's writer after four busy calls | a merge | the last request |

The four left are the call's object array, its fence array, the request's hold and the request, which Linux allocates too; on a busy ring the pool's one shadow is in use, and a new one takes the other three. The whole test passes at the head; before, the busy row fails on the merged writer, as it should. The test stopped at its pool row at both heads, the first the milestone's head with 428e5e668 alone, which does not touch the shrinker: the row calls the shrinker's scan on a device whose shrinker the model never registers, so the scan read a null device. The row now names the device first.

Every heap block is taken under the one `heap_lock` with interrupts off, which the profile's `kirq_restore` samples under `kmalloc` show; Linux's slab has a free list per processor. That allocator is the size of a milestone and is not changed here.

## What is left, and the Lenovo

The Lenovo step, [84-146-lenovo.md](84-146-lenovo.md), boots one trial of the kernel with 84-58's forcewake fix and these four commits, and runs one plain loop of `trip.sh` with `rach2.cycleaccount` and the whole-kernel profile, to read EXECBUFFER2's time a call and `wined3d_cs`'s system ticks beside 84-58's.

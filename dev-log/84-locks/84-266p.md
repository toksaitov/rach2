# 84-266p: the Lenovo's hang in native.kvm.vmexit

The Lenovo stopped answering at 06:46 on 2026-11-15, in the native run of cc8b45c24, as `native.kvm.vmexit` started its first guest; it stayed off the network, with no netconsole and so no kernel log of the moment (#5202). Reading the VMX path found a loop that holds a processor with interrupts off for ever under any VMX guest with the in-kernel PIT armed. It is fixed; the rerun on the Lenovo, with netconsole to the Mac, is the manager's.

## The cause

Two changes met on the Lenovo for the first time, since every suite's KVM host is an AMD machine, which runs the SVM backend, and the last VMX run on the Lenovo (81-24's K3 in [81-7](../81-kvm/81-7.md), 2026-11-12) came before both:

* 72c7fc215 gave VMX Linux's fast path: with host interrupts still off, `vmx_fast` takes a preemption timer exit, delivers the APIC timer's expiry if it is due, and `run_enter` enters the guest again, ending the loop only on a request, a signal, a switch or a split controller's interrupt window (`fast_ends`).
* b6d0a169f made the run's bound, `kvm_lapic_run_bound`, the earliest of the APIC timer's, the PIT's and the Hyper-V synthetic timers' expiries (`kvm_lapic_next_ns`), where it had been the APIC timer's alone.

Once the PIT's time came, `kvm_lapic_run_bound` gave 0 at every entry, and only the run loop's `kvm_vcpu_timers` delivers the PIT and moves its deadline on. So the guest exited at once on the preemption timer, `vmx_fast` found no APIC timer due and took the exit as handled, and nothing in the loop raised a request: the processor entered and exited without end. The SDM gives a VM exit for a preemption timer of 0 priority over external interrupts and NMIs, so the host's tick and IPIs never ended the loop, and the other three processors, waiting on that one for an IPI or a lock, would stop too, which the machine's silence on the network fits.

kvm-unit-tests boots each test through SeaBIOS, which programs the PIT's counter 0 at 18.2 Hz, and QEMU with the kernel's irqchip puts that PIT in the kernel, so by this reading the first test of the group, `vmexit_cpuid`, met the loop at the PIT's first expiry, some 55 ms after SeaBIOS armed it. Any guest with that PIT would have, the Debian guest's boot among them; the run shows only that the machine stopped in the case's first minutes.

Linux's hv timer is the APIC timer alone (`start_hv_timer`, `kvm_lapic_expired_hv_timer`), and its PIT has a host timer that kicks the vCPU, so its fast path never re-enters for an expiry it cannot deliver.

## The fix

* `vmx_fast` leaves the preemption timer's exit to the run loop when the PIT's or a synthetic timer's time has come (`kvm_lapic_other_due`), so the fast path re-enters only for the APIC timer, as Linux's does. A TSC deadline's WRMSR re-entered at a bound of 0 meets the same test at its next exit.
* The slow path's preemption timer exit raises KVM_REQ_TIMER, so the run loop looks at every timer, whichever bounded the run, and not only when `timer_ns` has passed.
* `kvm_vmx_hosttest --fast` has a row for it: a preemption timer exit with the PIT's time come goes through the run loop, which runs `kvm_pit_check`, and delivers no APIC timer from the fast path. The row fails on the old `vmx_fast` and passes on the new one; it ran alone, with the fast path's other rows.

Both kernels link.

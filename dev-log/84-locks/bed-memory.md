# 5698: the bed VM's memory, sized from the machine's

Native `bed/shm` gave the bed's VM a fixed 8 GiB, left piglit's streaming-texture-leak out of the bed's piglit scene because no VM of the bed held it, and passed a run whose scenes had failed: `bed-shm.sh` waited for each measurement without reading its status, `measure.sh` recorded a piglit test that failed as a result like any other, and `bed.sh` read only `bed-shm.sh`'s last line. By the owner's terms the VM's memory now comes from each machine's own, a check that cannot fit in it is skipped with a line that says so, a failed check fails the run, and streaming-texture-leak is back in the scene.

## Design

* `tests/native/bed.sh` gives the VM the machine's MemTotal less a reserve of 3072 MiB for Rach2 and its session, at most 16384 MiB, and prints it as `bed: vm: N MiB: ...`; a machine that would leave the VM less than 2048 MiB, the size `bed-shm.sh` takes by default, fails the rung. The Lenovo's MemTotal of 16,247 MiB gives 13,175 MiB.
* The reserve holds what runs on Rach2 beside the VM: Rach2 itself, 233 MiB in use on the Lenovo with no session (#5698's figure), the session, the scenes' programs, QEMU's own memory beyond the VM's, KVM's page tables for the VM and the page cache their files need. In QEMU, below, Rach2 used at most 226 MiB apart from QEMU's resident memory during the piglit scene and 432 MiB during the game's first minute; the reserve also holds QEMU's own memory beyond the VM's, which no run has read apart, and the rest of the race. The Lenovo step reads the same figures there.
* `bed.sh` mounts the data partition read-only for the run and unmounts it at the exit; when the partition is mounted already, as `/data` is on the Lenovo while a disk is copied to it, it reads it there and leaves it mounted, finding it in `/proc/mounts` by its device number, whatever path the table names, since Rach2 refuses a second mount of a mounted device with EBUSY (`mount_source` in `rach2/sys/fs/vfs.c`).
* A comment `# need N MiB` in `bed/measure/piglit.txt` gives the next test's need of the memory of a VM that renders on its GPU, and of one on llvmpipe unless `, llvmpipe M MiB` or `, llvmpipe never` follows. `measure.sh -M MIB` skips a test that needs more than MIB, and `-M MIB:llvmpipe`, which `bed-shm.sh` passes when no `-g` gives the VM a GPU, judges by the llvmpipe need, with `measure: piglit: skipped: TEST: needs N MiB, and the VM has MIB MiB`; `piglit.sh`, which drops comments, reads the list unchanged. `bed-shm.sh` passes its VM's size with `-M`, prints each skip as `bed-shm: skipped: piglit: ...` and ends a run that passed with `bed-shm: result: pass: N skipped`; `bed.sh` ends with `bed: result: pass: N skipped`. A skipped test counts in neither the passed tests nor the tests run.
* `piglit.txt` gives streaming-texture-leak a need of 16384 MiB, the bed's largest VM, so that the Lenovo's bed, whose VM has 13175 MiB, skips it. The Lenovo trial at 5ed20375c below read i915's objects through the test: in a VM of 13175 MiB the test took i915 from 38 MiB to 8605 MiB, all of it its own, since i915 was back at 28 MiB at the test's end, ran the VM out of room, and had 3141 of its creates refused, the first of which ends the test's rendering. Task 5676 measured, under QEMU's virgl with the guest's Mesa 25.0.7, that Mesa holds some 1,250 textures of 4 MiB and the 4 MiB staging buffer of each upload until each of the test's six submissions, 2,525 resources and 4.93 GiB of guest pages at the peak, on Linux and on Rach2 alike; a staging buffer is only guest memory to virglrenderer 1.1.0 (`src/vrend_renderer.c:8369-8370`), its backing in the bed's VM, and a texture is a GL texture, which i915 keeps in the VM's memory on the Lenovo, so the bed's VM holds both. Whether 16384 MiB holds the test no run has shown. Under llvmpipe, which keeps the textures it frees in the C library's heap, a VM of 14 GiB ran out ([5259](5259.md)), so the list says `llvmpipe never` and QEMU's bed skips it with `no VM has held it on llvmpipe`.
* `tests/kvm/readback.txt` keeps the test out, since `machine.bed-shm.virgl`'s VM has 2 GiB.
* A piglit test that did not pass fails the scene, as does a chosen test with no result or more than one in a round, or a result of a test not chosen: `measure.sh` lists each with its result, `missing` or its count of results, in `runner: measure: K of T tests did not pass: ...` and exits 1. `bed-shm.sh` reads each scene's status and its `measure: result:` line, and prints `bed-shm: scene: pass` or `fail` for each, so that a failed scene fails the run. `bed.sh` also requires `bed-shm: scene: pass: game on shm-virgl`, since a run whose game measurement did not complete is no run of the bed.
* The VM's memory comes from inside it. `bed-vm-memory`, a service of the VM's own beside the backend's, reads MemAvailable and the first line of i915's `i915_gem_objects` once a second and writes `bed-vm: memory: available A kB, least L kB; i915 N objects, K kB, most M kB` on the console only when either has moved 64 MiB since its last line, with the least MemAvailable and the most i915 memory of the seconds between, so that a steady VM writes nothing to its console, each byte of which is an exit. A scene is the console's bytes from its size when the scene began to its size when the scene ended, and its lines are the whole lines that begin and end within them. The figures read in the scene are the values of those lines and the extremes of each of them after the first; the first one's extremes may be of seconds before it. A second no line read is within 64 MiB of the line before it, the last one before the scene or one within it, so `bed-shm: memory:` gives the figures read and the bound that holds from the scene's start to the reading of its last line: no MemAvailable below the least of those lines less 64 MiB, and no i915 memory above the most plus 64 MiB. The seconds after that reading have no bound, since a line the VM wrote in the scene, at any figure, may reach the console after the scene's end, and a scene with no line in it, or none before it, has none. The VM's disk is rebuilt for it, SHA-256 2523b124420118d4c89e44e78a653bd93d57ba2afd33505731a25053c85c532a, which `tests/kvm/ref/lenovo-bed.sha256` pins.
* On Rach2's side `bed-shm.sh` samples once a second during each scene MemAvailable, `kvm_gpa_map_pages`, the VM's pages Rach2 maps for its buffers, the backings among them, and QEMU's resident memory, and prints the least and most of both sides as `bed-shm: memory: RUNG-SCENE: ...`, `-` for a figure no sample gave, keeping the samples in `memory-RUNG-SCENE.vm` and `.rach2` of its directory.

## On the Lenovo

The step at 4aecf98221 ran on 22 November from 16:55:45 to 16:59:26 UTC+6 and failed; its rollback put the old disk back. `bed: vm: 13175 MiB: MemTotal 16247 MiB less 3072 kept for Rach2 and its session, at most 16384`, the checks before passed, and `gpu.sh` started QEMU with `-m 13175`. QEMU connected to ivshmemd and closed the connection; the guest never offered its device (`driver 1, device 0`); `out/gpu/console` and `out/gpu/qemu.err` were empty; session, load, death and fallback failed with `virtio-gpu did not bind over the region: card ''`, and handoff with `status 126:` and no text. The evidence is in the owner's main checkout, `build/runs/task-5698/out.tar.gz`, and in toksaitov-d's clone under `build/runs/task-5698/lenovo-ev/`.

### Why the VM died

* `gpu.sh` stopped with status 126 and its exit trap gave the function back. Its log ends with the start of QEMU and then the two lines of the function's return, `unbind: ... from vfio-pci` and `bind: ... to i915`, with no result line, which only the trap leaves. The log does not say whether QEMU still ran: the trap kills a QEMU that runs, but a QEMU that had ended on its own, followed by a failure of the `cat` of its console or messages, leaves the same lines, since the script clears QEMU's pid before those `cat`s.
* 126 is bash's status for a command it found but could not run: an `execve` that fails with any error but ENOENT or ENOEXEC makes the child exit 126, and `set -e` ends the script with it. A failed fork gives 254, as bash 5.3 gave on the testing PC under `ulimit -u 1`. The status names neither the command, the loop's `wc` or `sleep` or a later `cat`, nor its error, and bash's message did not reach `gpu.log`. `gpu.sh` now names the command in `gpu: stopped: line N: status S: COMMAND`.
* VFIO maps every page of the VM into the GPU's VT-d domain with 4 KiB leaves, and every page of the domain's tables came from `alloc_kernel_frame`, the window below 64 MiB, which also holds the kernel's image and gives the frames of one-page disk requests (`sys/block/request.c`), AHCI's and the disk page cache's. The VM's 13175 MiB needs some 6,620 frames of tables, 26 MiB; the 8192 MiB VM that passed before needed some 4,110, 16 MiB. The Lenovo's window had at best 13,080 frames free, 51 MiB, at its least since the boot in 84-7's runs (`window_free_min` in `dev-log/84-locks/84-7/boot-b2/lenovo.out`), a boot that assigned no device.
* The Lenovo's dmar0 has neither pass-through (ECAP 0xf0101a, bit 6 clear) nor 2 MiB pages (CAP 0xc0000020660462, SLLPS 0), so its first assignment since the boot also builds the host's identity domain (`identity_new`), every 4 KiB page below the end of RAM, kept until the next boot: one leaf table for each 2 MiB, more than 8,100 tables, over 31 MiB, above MemTotal's 16,247 MiB, from the same allocator as the VM's tables and so from the window as well.
* Forced in QEMU, a VM whose tables outgrow the window fails as the window empties: with 32 GiB and the VM of 29650 MiB that `bed.sh`'s rule gives it, `window_free_min` fell from 53 MiB to 0 and QEMU stopped with `vfio_container_dma_map(..., 0x100000000, 0x6bd200000, ...) = -12 (Cannot allocate memory)`.
* Not settled: in QEMU, VMs whose tables left the window 4 to 512 frames, with the root and the VM's disk on AHCI as on the Lenovo, booted and passed, so a window that the map leaves nearly empty did not kill `gpu.sh` there. Whether the Lenovo's window emptied, and what failed in `gpu.sh`, the next step's `gpu: memory:` and `gpu: stopped:` lines and its kernel log, which `bed-shm.sh` now keeps, can show for that run; they cannot show what failed in this one.

### The fix

* A VT-d domain's page tables, the identity domain's among them, come from `alloc_dma64_frame` on x86-64, from above the window, as Linux's `iommu_alloc_page_node` takes any page; each unit takes their addresses in 64 bits, and the Lenovo's host address width is 39 bits. The root, context, invalidation queue and interrupt remapping tables stay in the window, so a boot of the Lenovo, which uses a domain only while the GPU is assigned, does as before.
* `gpu.sh` prints `gpu: memory: before:` and `end:`, the free memory, LowFree and `window_free_min`, and a stop of the script while QEMU runs fails with `gpu: result: fail: the script stopped with status S while QEMU ran, and killed it; ...` and QEMU's messages.
* `bed-shm.sh` reaps a QEMU that ends before the bind and prints `bed-shm: vm: QEMU ended before the bind: gpu.sh status S: gpu: result: ...`, or QEMU's own status without `-g`, with QEMU's messages and `gpu.sh`'s memory lines; each check that needed the bind fails with that line. It watches `gpu.sh` while QEMU's pid file is missing, and keeps the kernel's log at the end in `dmesg.txt`.
* The rule for the VM's size stays. In QEMU with 16 GiB, 16354 MiB managed, the rule's 13282 MiB VM pinned whole after its disk had been read through the cache, and Rach2 kept 1084 MiB free and 2895 MiB available beside it; the pin cost some 140 MiB beyond the VM.

## The session the failed step left

The step of 16:55 UTC+6 found no desktop session (`pgrep -x weston` status 1) and left one: about 14 s after `bed.sh` exited at 16:59:26, `rach2-desktop` started `rach2-session --bus drm card0 gl` as the desktop user, so the panel showed the desktop without a login.

### Cause

`bed.sh`'s end judged the session by Weston alone. With none before, `session_end` returned at once when `pgrep -x weston` found nothing, and sent `rach2-desktop` no SIGUSR2. But the supervisor's own record of a session, the group of `su`, the bus, PulseAudio and Weston, outlives its Weston and comes before it, and while it holds one it starts a session by itself: when its card goes, when a card appears while it is headless, and when the session ends with its card gone. Only SIGUSR2 clears the record, after which nothing but SIGHUP starts a session.

The run shows that state at the end. `check-after.txt` has no `desktop: weston ended` line, so no Weston ran when `check.sh after` began, and `bed.sh`'s end found none, yet a session started 14 s later. The only SIGHUP was `bed.sh`'s after `check.sh before`, answered at once; `bed-shm.sh` sends none with `-g`. So the supervisor held a session with no Weston when `bed.sh` ended, and started one by itself afterwards. Which of its paths it took, and why that session had no Weston, the kept evidence cannot tell: the workspace has no services log and nothing in it has a timestamp.

### Fix

* `bed.sh`'s exit trap first waits until the GPU's return has reached the supervisor and it has acted on it: `udevadm settle`, then two turns of its loop begun since, each seen as a new `sleep 1` child of it, 120 s at most.
* With no session before, it sends SIGUSR2 whether or not a Weston runs, waits two more turns and then until no process of the desktop user runs, 60 s at most. With one before, SIGHUP starts it unless it runs.
* It prints the supervisor's lines of the services log since its start as `bed: desktop: ...` and `bed: session: before STATE, after STATE, restored yes|no`, STATE `running`, `none` or `partial: N processes`, and fails a run that leaves a session where none ran, or none where one ran, or whose restore did not end within its waits. The result line comes last, after these.
* The step of record ends with the same check from the Mac, against `weston-pre.txt`.

### The fix

`vm.sh rach2` masks `serial-getty@ttyS0.service` in the VM, as `bed/nctx/reverse-vm.sh` does for its own: no one logs in on the console, and without the getty nothing hangs it up.

## The Lenovo trial at 5ed20375c and why streaming-texture-leak failed

The manager ran the step on the Lenovo from 05:36 to 06:02 UTC+6 on 23 November, with the trial kernel of 5ed20375c, `db4ee42b...`, disk bcedd483 and a kit whose `piglit.txt` gave the test `# need 12288 MiB`, so that it ran; the figures are from its evidence, which `build/runs/task-5698-r7/` of toksaitov-m's clone keeps. The VM came up at 13175 MiB, `bed: vm: 13175 MiB: MemTotal 16247 MiB less 3072 kept for Rach2 and its session, at most 16384`. bed.sh ended `bed: result: fail: the shm run failed, status 1` on the piglit scene alone, 9 of 10 tests passed and streaming-texture-leak failed; every other scene and row passed, glmark2 on virgl at 1.408 ms a frame, the game at 13.221 ms with 46690 round trips, glmark2 on Venus at 2.558 ms, and the GPU went back to i915.

The sampler read i915 through the test, 25 lines in the scene:

* i915 rose some 430 to 530 MiB a line, to 1305 objects of 5719016 kB with 2348860 kB available, where the backend refused its first create.

### Why the test failed

piglit's record of the test gives `fail`, the probe `Probe color at (5,5) Expected: 0.000000 1.000000 0.000000 Observed: 0.000000 0.000000 0.000000`, and on stderr `got error from kernel - expect bad rendering 12` twice. The failure is the account's refusals and what the renderer does after the first.

* The backend refused 3141 of the test's creates, `backend: create: resource N: refused: B bytes: no room in the VM's counts`, 2292 of 16777216 bytes, a texture of 1024 by 1024 at the bound's 16 bytes a texel, and 849 of 4194304, the staging buffers. No backing was refused, so the console has no `backend: back:` line; the creates' refusals are there. Rach2 logged each as `command 0x204: error 0x1201`.
* A later submission of the test named resource 2379, the first refused: virglrenderer logged `check_copy_transfer3d_handles: context error reported 2 "streaming-textu" Illegal resource 2379`, `context 2 failed to dispatch COPY_TRANSFER3D: 22` and `vrend_decode_ctx_submit_cmd: context error reported 2 "streaming-textu" Illegal command buffer 917549`. A context error marks the context (`vrend_report_context_error_internal` sets `in_error`), `vrend_hw_switch_context` refuses a marked context, and `vrend_decode_ctx_submit_cmd` then returns EINVAL for each later submission of it before it decodes one, as virglrenderer 1.3.0's `src/vrend/vrend_renderer.c` and `src/vrend/vrend_decode.c` read; Rach2 logged the VM's 1.1.0's answers to that submission and the later ones as `command 0x207: error 0x1205`, five from 453 s on. The test drew nothing after its first refused create, and the probe read black. Linux under QEMU's virgl meets the same: a create the host refuses leaves the resource missing, and the renderer ends the context at its first use.
* Rach2's side failed two submissions with ENOMEM, Mesa's two messages. Each refused create's backing was refused for want of the resource, `refused: the VM's backing: error -121`, 2917 times, and Rach2 then attached pages of the region's heap, 8189 pages shared with the commands' own; 2079 of those attaches were sent and answered `ERR_INVALID_RESOURCE_ID`, and for the other 838 none could be made, which keeps the object from use with the attach's error. With the heap full of such pages, a submission fails with ENOMEM both when it names one of those objects and when its payload's pages do not come within five seconds; the run does not say which of the two Mesa met. Linux attaches guest memory to such a resource and sends the submission, which the host refuses; that difference goes to the list for later.
* Rach2 also dropped two submissions at their send, `command 0x207: refused: 45 segments do not fit one chain` at 462 s and 473 s, failing their fences with E2BIG and telling Mesa nothing. `vgpu_cmd_payload` bounded the pages it sends one each by the queue's 128 descriptors, where the region's transport takes 16 in one chain; a payload of 43 pages that found no free block of the heap went a page each and the send refused it whole. Both came after the context's error and change nothing of the result.

The test therefore needs more memory of the VM than 13175 MiB, the most the Lenovo's 16247 MiB gives beside the reserve. `piglit.txt` keeps `# need 16384 MiB`, the bed's largest VM, which the Lenovo's bed skips with its line; whether that size holds the test no run has shown.

### The fix

This task's change to the kernel bounds the pages `vgpu_cmd_payload` sends one each by the queue's `max_chain` less the header and the answer, so a longer payload waits for one block of the pool and fails with ENOMEM when the wait gives up, never at its send. `vgpu_backing_entries` judges an `ATTACH_BACKING` or `RESOURCE_CREATE_BLOB` with its entry pages and answer by `virtqueue_chain_fits`, as the send does, and refuses one that does not fit with E2BIG, where it compared its pages with the queue's size. Both kernels link; the change was read and not run, since it needs the heap full, as this test fills it, to take its path.

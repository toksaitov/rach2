# 84-262t: why Proton's d3d11 stops after 4 tests with a summary and d3d9ex runs two checks fewer than Linux

The release run's `machine.d3d-wine` failed three rows on x86_64 under KVM: `proton-d3d11-d3d11` printed a summary of 4 tests where Linux printed none, and `proton-d3d9-d3d9ex` and `wined3d-d3d9-d3d9ex` ran 2583 and 2764 checks against the stored minimums of 2585 and 2766. Neither is a fault of Rach2's. The d3d11 row ran in an account that Debian's reference account is not: Rach2's `test` is in `kvm`, which opens `/dev/udmabuf`, and with it Proton offers DXVK a keyed mutex that Debian's run never had. The d3d9ex count varies with timing in Linux too, and today's Debian run under KVM gives Rach2's counts exactly.

The release's evidence is the CI runner's and cannot be read from a team account, so every figure below comes from runs of this task on the testing PC: the Debian 13 reference guest by `reference.sh -a lavapipe -p virtio-vga` with 8 CPUs and 16 GiB, and the three rows on Rach2 by `tests/run d3d-wine` with `RACH2_QEMU_ACCEL=kvm`. Each Rach2 row gave the release's result again: d3d11 exit 5 with the summary `[4, 0, 0, 0, 0]` and 2649 test lines (the release's had 2882), d3d9ex `[2583, 47, 4, 98, 2]` on Proton and `[2764, 108, 0, 0, 2]` on WineD3D. The task's comment read the WineD3D row as 108 failures; the 108 are checks marked todo, and its failures are 0, as Linux's.

## The accelerator of the reference

`linux.json` holds no machine record. Debian's Proton d3d9ex row under TCG exits with 245 before its summary, after 12 test lines, where the reference has its summary and 98 failures, so the reference's Proton rows were not taken under TCG. Under KVM Debian gives the reference's exits, failures and skips on all three rows ([debian-results.txt](84-262t/debian-results.txt), [debian-kvm.record](84-262t/debian-kvm.record)).

## d3d11

Wine's `d3d11` unit runs its tests on one thread per processor (`dlls/d3d11/tests/d3d11.c:209-240`). The first, `test_create_device`, starts a child process that runs `test_create_device_child`, whose four checks pass and which prints its own summary, `d3d11: 4 tests executed` (`d3d11.c:2061-2107`, `2337-2344`). An unhandled exception ends a Wine test with no summary of its own, and the process's exit is the low byte of the exception's code, 5 for `0xc0000005`, since `include/wine/test.h:886` installs its exception filter on Windows alone.

Debian's run died 34 test lines in, in `test_texture2d_interfaces`, case 3, which makes a texture with `D3D11_RESOURCE_MISC_SHARED_KEYEDMUTEX` (`d3d11.c:3246-3250`, `3312`). DXVK's last lines are `Failed to open shared D3DKMT handle` and `Exporting semaphores of type 4 not supported by device`; the child had not yet printed its summary ([debian-d3d11-tail.txt](84-262t/debian-d3d11-tail.txt)). On Rach2 the same case goes on, DXVK logging `DxvkFence::DxvkFence: Failed to open shared D3DKMT handle` and `D3D11: Failed to write shared resource info for a texture` and the test its result for case 3 ([rach2-d3d11-keyedmutex.txt](84-262t/rach2-d3d11-keyedmutex.txt)), and the process dies thousands of lines later, after the child's summary.

DXVK enabled two device extensions on Rach2 that it did not on Debian, `VK_KHR_external_semaphore_win32` and `VK_KHR_win32_keyed_mutex` ([extensions.diff](84-262t/extensions.diff)). Proton's Wine offers both only when the host driver has `VK_KHR_external_semaphore_fd` and timeline semaphores (`dlls/win32u/vulkan.c:542-543`, `2930-2931`). Mesa 25.0.7's lavapipe offers `VK_KHR_external_semaphore_fd` only when llvmpipe can make sync files (`lvp_device.c:1297-1300`), and llvmpipe makes them only from a buffer of `/dev/udmabuf`, which it opens when its screen is made (`lp_screen.c:1094`, `lp_fence.c:310-337`).

Both guests have `/dev/udmabuf` as root:kvm with mode 0660: Debian by systemd's rule, its kernel having the driver built in, and Rach2's GNU root by its own udev rule. Debian's `gfx` is in sudo, audio, video, render and input. Rach2's `test` is in video, render and kvm, kvm since `7eb38d84d`, two days after the reference was taken, for the `kvm` suite's QEMU; BusyBox's `su`, which the scenario ran the row through, gives the account every group. With `/dev/udmabuf` opened to `gfx` (mode 0666), Debian's d3d11 ran as Rach2's does: exit 5, the summary `[4, 0, 0, 0, 0]` and 3268 test lines, past case 3 ([debian-udmabuf-d3d11.txt](84-262t/debian-udmabuf-d3d11.txt)).

The scenario now starts the row as `test` with the supplementary groups `video` and `render` alone, those of `gfx`, set by a few lines of Python as root, in place of `su`. Every family that `d3d_scenario.c` runs, `d3d`, `d3d-wine`, `d3d-vkd3d` and `d3dvenus`, so runs in the reference's conditions. Proton's crash in Linux's run is recorded in [upstream.md](upstream.md#proton-dies-on-a-keyed-mutex-texture-when-the-vulkan-driver-has-no-external-semaphores).

## d3d9ex

`d3d9:d3d9ex`'s window procedure counts each message it did not expect, but `WM_DISPLAYCHANGE` and `WM_IME_NOTIFY`, as a check marked todo (`dlls/d3d9/tests/d3d9ex.c:2513-2520`), and how many arrive depends on timing. Debian's WineD3D run under KVM had 21 such checks and 2764 in all; under TCG 42 and 2785, the summaries' todo counts 108 and 129, and every other test line of the two logs the same. Debian's Proton run under KVM had 6 and 2583. The stored minimums came from the discovery's runs at 2, 4 and 8 CPUs, whose logs were not kept; two more such messages there give their 2585 and 2766. Rach2's runs under KVM gave Debian's counts exactly.

`linux.json` now keeps 2583 and 2764 as the fewest checks of the two units, as `mkref.py` folds a run into a reference, and its `coverage_source` names the run. The Readme of the graphics tests gives the reason.

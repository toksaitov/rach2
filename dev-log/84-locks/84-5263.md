# 84-5263: glmark2's empty HUD frame times in bed/shm

The Lenovo's first native bed/shm run of #5259's driver fixes (kernel 8eae65c3e, the release's VM disk) drew glmark2's four scenes at 26 FPS, as #5259's worker reported, and failed the scene with `runner: measure: the scene gave no frame times`. The cause is Mesa's: its Gallium HUD takes a frame's time only after it has mapped memory for the vertices it would draw, and in that run virgl's memory for them was a persistent mapping of a host blob, which the VM's backend refused to export. With #5259's backend at c43dbc843a the HUD filled in QEMU. That backend also crashes on a persistent buffer when the VM has no render node, which hangs `machine.bed-shm.nocopy`; #5259 has both findings.

## The cause

`hud_stop_queries` (Mesa 25.0.7, `src/gallium/auxiliary/hud/hud_context.c:703-710`) asks the context's stream uploader for the HUD's vertex memory and returns when it gives none, before the loop that calls each graph's `query_new_value` (line 730). The frametime graph's `query_fps` (`hud_fps.c:42-65`) is the only writer of the dump file, through `hud_graph_add_value`, so a frame whose upload failed writes nothing, and the next recorded frame spans both. `GALLIUM_HUD_VISIBLE=false` hides the drawing but not this path.

virgl's stream uploader maps its buffers persistent and coherent when the screen's `buffer_map_persistent_coherent` is set (`u_upload_mgr.c:75-81` and `202-205`), which needs the host's `VIRGL_CAP_ARB_BUFFER_STORAGE`, host feature check 4 or later, and the kernel's `blob` and `host_visible` parameters (`virgl_screen.c:497-500`, `virgl_drm_winsys.c:1287-1288`). Rach2's virtio-gpu over the region offers both parameters. The VM's backend started virglrenderer 1.1.0 without `VIRGL_RENDERER_USE_EXTERNAL_BLOB`, under which it offers the capability and allocates a persistent buffer with `glBufferStorage` (`vrend_renderer.c:8310-8312`, `12673-12701`), which has no descriptor to export, so each map ended as `backend: map: resource N: refused: not exported: -22` in the VM and `virtio_gpu: resource N: refused: its page list: error -5` in Rach2.

## The measurements

QEMU 10.2.1 on the testing PC under WSL's KVM, Rach2's kernel at 8eae65c3e on the x86-64 GNU root's `gnu-test.disk` of 2026-11-15 under `host-svm` with 4 processors and 6 GiB, `bed-shm.sh -w -x measure -S glmark2` with the harness of this tree; the VM disks made by `bed/vm/image/vm.sh rach2` from the milestone's backend and from task/5259's. The VM renders on llvmpipe.

| VM's backend | Mesa in Rach2 | HUD frame times | Exports refused in the VM | Page lists refused in Rach2 | glmark2 FPS: build, texture, shading, bump |
|---|---|---|---|---|---|
| milestone 8eae65c3e | as installed | 0 | 185 | 282 | 1, 1, 5, 9 |
| milestone 8eae65c3e | `VIRGL_DEBUG=nocoherent` | 416, mean 98.0 ms | 113 | 124 | 1, 11, 14, 18 |
| task/5259 c43dbc843a | as installed | 323, mean 125.0 ms | 0 | 0 | 1, 9, 12, 13 |

`VIRGL_DEBUG=nocoherent` turns the persistent mappings off in the Mesa of what `bed-shm.sh` starts, the scene among them, but not in the session's Weston, which the desktop's service starts, so that row still has refusals; which client made each was not read. Each run's other rows (attach, session, load, death, fallback) passed. The first row is the Lenovo's failure again; there #5259's worker read 26 FPS on the GPU.

With the external-blob flag virglrenderer offers the capability only on a GBM device of i915 or amdgpu (`vrend_renderer.c:12703-12712`). The backend passes no GBM descriptor, and virglrenderer opens a render node of its own (`vrend_winsys_gbm.c:266-287`). The QEMU VM has none, only `card0` and `card1`, so there Mesa asks for no persistent buffer at all; on the Lenovo, i915's node gives the device, and persistent buffers become GBM buffers, a path these runs do not prove.

## The crash

With the flag and no GBM device, `vrend_create_buffer` takes the memory-object branch for a persistent buffer, which llvmpipe's `EXT_memory_object_fd` allows, and calls `gbm_bo_create(gbm->device, ...)` with `gbm` NULL (`vrend_renderer.c:8315-8321`; the same in virglrenderer's main at 01637fc7). In QEMU, `bed-shm.sh -k` with task/5259's disk passed attach, build, pages, coherent and release, and then `vgshmprobe refuse` waited 17 minutes for the answer to its first persistent GL buffer's MAP_BLOB, until a SIGINT ended it with `virtio_gpu: command 0x208: no answer before SIGKILL`. In the same VM booted alone, `virgl_renderer_init` with the backend's flags and `virgl_renderer_resource_create` of a 64 KiB `PIPE_BUFFER` with `MAP_PERSISTENT | MAP_COHERENT` returned 0 without the flag and died of SIGSEGV with it. The fix is #5259's, whose file the backend is.

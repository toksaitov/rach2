# 84-260g: why the station did not come back to network A in machine.wifi.robust on i686

The release run's `machine.wifi.robust` on i686 failed its `back` row: the station rejoined network A with its route and servers, and the echo to the endpoint failed with `nc: bad address 'endpoint.wifi.test'`. The station was right. The AP guest's dnsmasq, run with `bind-dynamic`, had no UDP socket on 192.168.71.1:53 though br0 held the address, so the kernel refused every IPv4 query. The station's lookup went to that server alone, since the RA's IPv6 server had not yet reached resolv.conf, and timed out. A Linux station under musl's resolver would fail the same way. The AP's dnsmasq now listens on the wildcard address ([upstream.md](upstream.md#dnsmasqs-bind-dynamic-loses-an-addresss-udp-socket-when-the-address-leaves-and-returns)).

## What the station did

The release console (`build/runs/release-343804-wifi.robust.i686/evidence/station.1.console`, kept on the testing PC) has the lease at 283.436 s and resolv.conf with 192.168.71.1 alone, then the echo:

```
<6>[283.436000] net: wlan0: IPv4 192.168.71.50/24
...
nameserver 192.168.71.1
...
nc: bad address 'endpoint.wifi.test'
STATUS=1
```

The lookup took 5.0 to 5.3 s: `/tmp/echo.out` was last written at 283.670 s and the next row's `mkfifo` at 289.164 s, read from the station's disk image. musl 1.2.5 sends A and AAAA on an unconnected UDP socket, which ignores a port unreachable, and gives up at 5 s. ndwatch adds the RA's server, `fe80::...%wlan0`, about 1.2 to 1.4 s after a lease; the lookup began 0.3 s after it. Later lookups went to that server and passed, which is why the station answered names 25 s later.

## What the AP did

Six copies of the case at once on i686 under TCG reproduced it, with the station's lookups and the AP's sockets read at each row. On the failing copy `nslookup endpoint.wifi.test` said `read: Connection refused` for 192.168.71.1 three times, and the AP's capture had each query arrive on wlan0 and br0 with no answer, while its IPv6 twin was answered within 1 ms. The AP's `netstat -lnu` after the failure:

```
udp        0      0 127.0.0.1:53            0.0.0.0:*
udp        0      0 192.168.72.1:53         0.0.0.0:*
udp        0      0 0.0.0.0:67              0.0.0.0:*
udp        0      0 fd72::1:53              :::*
udp        0      0 fe80::ff:fe00:200:53    :::*
udp        0      0 ::1:53                  :::*
udp        0      0 fd71::1:53              :::*
```

and `ip addr` had `inet 192.168.71.1/24 scope global br0`. The socket was gone by the end of the `subnet-busy-back` row, after the case moved br0 to 192.168.73.1/24 and back twice. It was lost in 2 of 12 copies and stayed lost through the rest of the case. A replay of the case's `ip addr` and dnsmasq commands with the same gaps and no station kept it. dnsmasq's path to the loss is not proved; the candidate is in the upstream entry.

The station's path was read and cleared: ARP had 192.168.71.1 at the AP's address with no failed resolutions, the queries left (the AP saw them), the port unreachables came back (Icmp InDestUnreachs 18), and every `wlan_` counter was 0.

## The fix

`tests/system/wifi/root/etc/wifiap/dnsmasq.conf` drops `bind-dynamic`. dnsmasq then binds 0.0.0.0:53 and [::]:53 once and answers queries that arrive on br0 and wlan2, whatever their addresses become. The robust case now asks the network's IPv4 server for the endpoint by name at each check of routes and servers, so a server that does not answer is named in the report as `an answer from 192.168.71.1`, and an echo that fails names nc's or cmp's complaint, such as `the echo (nc: bad address 'endpoint.wifi.test')`.

## Runs

* Six copies at once on i686 under TCG, with the fix and an `nslookup endpoint.wifi.test 192.168.71.1` after the `back`, `subnet-back` and `subnet-busy-back` rows: four copies passed all 26 rows and every IPv4 query was answered. A fifth passed its other 25 rows and failed its first join's echo: the AP deauthenticated the station with reason 16 during the 256 KiB transfer, a group key exchange that timed out under the load of six TCG copies beside the release run. That is the drop #2471 traced to wpa_supplicant's blocked disk writes after `wifi connect`, which the case survives where a rejoin follows. It has no part in DNS: the lookup succeeded and the transfer was cut off (`cmp: EOF on /tmp/echo.in`). The sixth copy waited behind the release run for processors and was stopped.
* At 55c2eae73, `RACH2_CASES=machine.wifi.robust tests/run wifi` on i686 and then with `ARCH=x86_64`, on the testing PC under TCG through the admission ledger beside the release run: each passed all 23 rows, in 312 s and 308 s, with the IPv4 server's answer checked at every row that checks the routes.

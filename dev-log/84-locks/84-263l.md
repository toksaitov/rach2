# 84-263l: Proton's d3d10core and d3d11 units on Venus read at 0x2f0

The release ran `machine.d3dvenus.wine-proton-d3d10core-d3d10core` on x86-64. It ended with exit 245, death by SIGSEGV, 21 lines short of the reference's 143, which expects exit 5, the low byte of Wine's unhandled access violation 0xC0000005. `machine.d3dvenus.wine-proton-d3d11-d3d11` ended the same way, with exit 245 against exit 5. Both units died in Wine's signal handler. The handler read 0x2f0, an offset into a TEB whose pointer was NULL.

## Cause

The thread died in a destructor of thread-specific data. That destructor belonged to a copy of Mesa's Venus driver that had been unloaded, and the driver had been loaded again at another address.

* The Vulkan loader loads `libvulkan_virtio.so`, unloads it with dlclose and loads it again. On first use the driver makes a key with a destructor: `pthread_key_create` is called from offset 0x36590, through the wrapper at 0x115f60, with the key at 0x1aa4b0 and the destructor at 0x363c0. The driver imports no `pthread_key_delete`, so the key and its destructor stay registered after the unload.
* A thread that used the driver exits through `__nptl_deallocate_tsd`, which calls the destructor at the first copy's base plus 0x363c0 (the call at libc 0x9270f). In Rach2's traced run the first copy sat at 0x7ea775523000 and the second at 0x7ea7754a8000, so the call landed at offset 0xb13c0 of the second copy, inside another function. That function's stack check, `mov 0x2508(%rsp),%rdx` at offset 0xa8bf3, read past the top of the stack.
* Wine's `segv_handler` took the fault on a thread that Wine no longer knew. `save_context` calls `NtCurrentTeb()`, which is `pthread_getspecific(teb_key)` and returns NULL there, and then reads the TEB's `GdiTebBatch` at 0x2f0. That second fault killed the process.

Linux runs the same driver without the fault because, in its runs, the second load returns to the first address. In the Debian reference run with `LD_DEBUG=files`, the process that loaded the driver twice got base 0x7f52db653000 both times. Two things decide where the driver lands, and Rach2 differed from Linux in both.

The first was the kernel. Linux 6.12 gives a 64-bit private mapping of a file on ext2, ext4 or xfs (`thp_get_unmapped_area`) an address congruent to its file offset modulo 2 MiB whenever the mapping covers a whole aligned 2 MiB of the file. It does the same for private anonymous memory of a multiple of 2 MiB mapped without a hint. That memory includes glibc's thread arenas and the segments of big libraries such as libstdc++, which Debian placed at 0x7f52db800000. The padded searches leave holes above those mappings, and the smaller libraries fill them. Rach2 placed every mapping at the top of the highest free gap without padding, so its holes were elsewhere, and the d3d10core unit's driver came back 0x7b000 lower.

The second was the libraries. With the kernel aligned as Linux aligns, the d3d10core unit passed, but the d3d11 unit still died in 4 of 9 runs. A trace of every mmap and munmap of the d3d11 process showed why. The driver is unloaded together with wineopenxr.so (0x83158 bytes) and libopenxr_loader.so.1 (0x7a598), and while all three are out, another thread maps 64 KiB of anonymous memory at the top of wineopenxr's hole. Debian does the same: its wineopenxr also comes back 0x10000 lower. On the reload libopenxr_loader no longer fits in its own hole and needs another:

| | libstdc++ | libzstd | Where libzstd went | Where libopenxr_loader went on the reload | Driver |
|---|---|---|---|---|---|
| Debian 13 | 0x2650c0 | 0xc9038 | the hole above libstdc++ | libzstd's hole | same base |
| Rach2's GNU root | 0x2b6480 | 0xfd380 | below the driver, too large for the hole | the top of the driver's hole | 0x7b000 lower |

The GNU root builds libzstd and libstdc++ itself, newer than Debian 13's, as its Readme says. Rach2's kernel now chooses addresses by Linux's rule, so this layout comes from the libraries. No placement rule makes a stale destructor safe, and the fault is Mesa's.

## Fix

* `mmap_place` in `rach2/sys/syscall_proc.c` follows `__thp_get_unmapped_area` for a 64-bit process on x86-64. It covers a private or shared mapping of an ext2 file whose range holds an aligned 2 MiB of the file, and private anonymous memory of a multiple of 2 MiB without a hint. It searches for the length plus 2 MiB. If the search returns the hint, the mapping goes there; otherwise it moves the base up to the file offset's position modulo 2 MiB, or by a whole 2 MiB when that position is 0, as Linux's top-down search does. A 32-bit kernel or a compat call is not aligned, and neither are tmpfs, `/dev/zero`, shared memory and devices, as on Linux. `rach2/sys/mm/Readme.md` and `brk(2)` state the rule. `mapmusl`'s `ext2-thp` row maps a 4 MiB file at offsets 0 and 4096 and requires each mapping to sit at its offset modulo 2 MiB. The kernel before the fix fails that row: offset 4096 was mapped at 0x7effffc00000. The fixed kernel passes it on i686 and x86_64.
* `vendor/gnu/debian/fetch_venus.sh` marks the staged Venus driver, amd64's and i386's, `DF_1_NODELETE` with `vendor/gnu/debian/nodelete.py`, which writes a DT_FLAGS_1 entry over the dynamic section's terminating DT_NULL, so that the first of its four spare zero entries becomes the terminator. The loader's dlclose then leaves the driver mapped, its destructor stays valid, and the next dlopen takes the same copy. The Debian reference guest installs Debian's driver unchanged, and its layout brings the driver back to its address, so both systems call a live destructor.

## Results

Each Rach2 row is a run of the case alone under KVM on the testing PC, in a boot of its own. Each Debian row is a run of `reference.sh` in the Debian reference guest; the 2026-11-14 runs are three to a boot.

The d3d10core unit has no summary on either system: one of its threads takes the access violation that ends it with exit 5, while the others run their tests. How far those threads get decides the count. Rach2's 139-line run and Debian's 146- and 144-line runs differ only in lines that repeat, 2190, 2777, 2778 and 3798, and in single lines that some runs printed and others did not: 1725, 4771 and 4773 in Rach2's alone, 1861, 2380 and 2564 in both Debian runs alone, and 1743 in Rach2's and one Debian run. On Debian the unit also ended with SIGSEGV twice; the second boot's `dmesg` had no segfault, and the first boot's log was not kept, so their cause was not read. Once it ended with exit 1 after one test line, Wine reporting that an exception frame was outside its thread's stack. The reference had taken exit 5 and 143 lines from two runs that happened to agree. `mkref.py` keeps a crashing unit's exit only when every run gives the same one, and its fewest lines, so with Debian's six new runs the row in `tests/graphics/d3d/ref/venus.json` is now exit null, no summary, no failures and 1 line, and its source line names the runs. The `LD_DEBUG` run is left out, since it ran with the loader's tracing.

One of the 9 d3d11 runs with the mapping fix alone ended with exit 5 and no child summary, with no fault in the kernel's log but the unit's own access violation. Its unit log was not kept, and none of the runs with both fixes did so.

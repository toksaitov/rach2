# kms_rmfb@close-fd on the Lenovo

Task 5239 takes `igt@kms_rmfb@close-fd` of the Lenovo's native `gpu/igt-kms.8` at 4add94748, which failed on `pipe-A-eDP-1` and passed on pipes B and C, where Linux's reference passes all three. The evidence is igt_runner's own output of the run, which the owner copied to `build/tmp/lenovo-igt/5380f1ecd49300cf`. IGT's source was read from the pinned `intel-gpu-tools_2.0.orig.tar.xz`, whose SHA-256 matched `vendor/gnu/igt/sources.txt`. Linux 6.12's `drm_file.c` and `drm_fb_helper.c` were not read in this task; the functions of theirs named below are from memory, and the reference's pass agrees with them.

## The cause

The subtest shows framebuffer 91 on every plane of pipe A, reads it back from GETCRTC, closes the card with `drm_close_driver`, opens it again as master and asserts that the CRTC's `buffer_id` is 0 (`tests/kms_rmfb.c:160`). It read 86, not the test's framebuffer. Rach2's close had already removed the file's framebuffers from every plane, as Linux's `drm_fb_release` does (`drm_mode_file_release`, `fb_remove`). The 86 was the console's own buffer, since the console is the only code that sets a framebuffer on a CRTC when a file closes: the release of the master's file told the console that no master held the card, and the console took the screen back at once, setting its mode and buffer on pipe A, the one CRTC the panel's console uses. Pipes B and C passed because the console does not light them.

Linux's fbdev emulation takes the screen back from a master at the device's last close, through `drm_lastclose` and `drm_client_dev_restore`, at a hotplug while no master holds the device, and through fbcon's `drm_fb_helper_set_par` on a return to a text VT. It does not at the close of a master's file while another file of the device is open. IGT keeps one open: `drm_open_driver` in `lib/drmtest.c` opens the card a second time for an i915 device, `at_exit_drm_fd`, which it holds until the process exits. So on Linux the master's close leaves the CRTC with no framebuffer, and the test reads 0.

## The fix

Task 84-266z17 had already made the change on the milestone branch, in 770e01d3e, for IGT's kms_flip_event_leak: the console's master listener only hands the screen over, and the screen comes back at the device's last close (`drm_client_dev_lastclose`, from `drm.c`'s release of a file when the open count reaches 0) or at a hotplug while no master holds the card, never at DROP_MASTER or at the close of a master's file while another file of the card is open. 4add94748 predates it. In kms_rmfb@close-fd the master's close leaves IGT's second file open, so the console keeps away, the CRTC keeps no framebuffer, and the test reads 0, as on Linux. `drmcon_hosttest.c`'s `row_drop_master` checks that a master's close with another file open gives nothing back and that the last close does. Task 5239 changes no code; its own version of the same change, on `task/5239`, was left out when it reached the milestone branch.

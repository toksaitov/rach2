# 84-166: a woken thread preempts a busy processor's thread or finds an idle one sharing its cache

84-157's Lenovo loop left WineD3D's command thread, wined3d_cs, 44.5 ms ready and not running over 1000 round trips of 281.6 ms; without that wait the loop would be 237 ms, inside Linux's 224 to 251 ([84-163](https://github.com/toksaitov/rach2/issues/4889), Fable's second answer). Three differences from Linux's wake path were read in the code. This task closes all three, measures the changed path beside Linux in QEMU, and prepares the Lenovo loop that reads the ready wait.

## What was different

* The idle test of placement was only that a processor runs its idle task (`sched_cpu_idle`). A processor with a woken thread already queued still counted idle, so the GPU's interrupt, which wakes wined3d_cs through the fence and then ki915 through `retire_kick` (`sys/drm/i915/i915_request.c`), put both on one processor; ki915 then preempted wined3d_cs 43 times of its 61 involuntary switches in 84-157's loop. Linux counts a processor idle only when its queue is empty and no wake is pending (`idle_cpu`, kernel/sched/syscalls.c:202-218).
* Placement was the last processor if idle, else the lowest-numbered idle one, else the last. Linux chooses between the waker's processor and the last one (`wake_affine`, kernel/sched/fair.c:7443-7542), then looks for an idle processor sharing the target's last-level cache (`select_idle_sibling`, fair.c:7934-8058).
* A wake of an ordinary thread onto a busy processor set no `need_resched` and sent no kick (`sched_preempt_cpu` asked only an idle processor or one running a lower real-time priority). The woken thread waited for that processor's next interrupt, a yield or a block. Linux reschedules the running task at once when the woken one should run first (`check_preempt_wakeup_fair`, fair.c:8862-8951).

## The change

All in `rach2/sys/proc/sched.c`, with the contract in [the processes Readme](../../rach2/sys/proc/Readme.md#scheduling):

* `sched_cpu_free`: idle task current, empty queue, and the idle task's `need_resched` clear, which `sched_preempt_cpu` sets when it queues a wake there. Placement and `sched_choose` use it.
* `sched_wake_choose`: Linux's choice for a wake. The target is the waker's processor when it is free and shares a cache with the last one, unless the last one is free too; else the last one when it is free; else the waker's when its count of threads, with the woken one, is below the last one's by Linux's margin for a cache domain (WA_BIAS with imbalance_pct 117: 100 against 108); else the last one. Then the target if it takes the wake at once (free, or running a SCHED_IDLE thread with nothing queued, as `sched_idle_cpu`), else the last one if it shares the target's cache and does, else the first that does among the target's cache peers from the one after the target, else the target. Linux's sync wakes, per-processor kernel threads and `recent_used_cpu` have no counterpart.
* The cache peers come from `cpuid` at each processor's start: `cpuinfo_llc_shared` (`sys/arch/x86/cpuinfo.c`) gives the `shared` mask of the highest-level data or unified cache, or the package without one, and `sched_cache_join` records it both ways under `sched_lock`, so the boot processor learns its peers from theirs and two starting processors in either order end with the same sets.
* `sched_wake_preempt`: after `sched_preempt_cpu`, a woken or new ordinary thread asks an ordinary running thread to switch, with Linux's exceptions: a SCHED_IDLE thread gives way only to a thread of another policy, a SCHED_BATCH or SCHED_IDLE thread preempts nothing, and a thread already asked is not asked again. Within the running thread's protected slice Linux preempts only when that thread is no longer eligible (RUN_TO_PARITY, fair.c:926-944); Rach2 keeps no virtual runtime and takes every woken ordinary thread as the one to pick, which its interrupts already did within the slice (`sched_tick`), so the wake now does at once what the next interrupt would have done.
* Kernel threads switch where they did: the request waits in `need_resched` for their next sleep or service point, as Linux's kernel thread without CONFIG_PREEMPTION takes TIF_NEED_RESCHED at cond_resched or schedule; Debian's 6.12 kernel below is PREEMPT_VOLUNTARY. ki915 reaches a service point between passes (`submit_thread_main`). A kernel thread so asked gets no kick, since the interrupt switches only a thread in user mode (`isr_local_router`).

## The shared structures

* The run queues, their counts, `rt_queued`, `cpu_table[].current` and the new `cache_peers` are written only under `sched_lock`, and every read the change adds (`sched_cpu_free`, `sched_cpu_load`, `sched_cpu_takes`, `sched_share_cache`) runs under it, from `sched_ready_locked` or `sched_choose`. The unlocked reads that were there are unchanged: `sched_yield_alone`'s look at its own queue, and `sched_idle_balance`'s first look before it takes the lock.
* `need_resched` is set under `sched_lock` by every remote request, the new one among them, and by its own processor with interrupts off; `schedule` clears it under the lock after its selection. A request set before the selection is answered by it, one set after it is kept, and a wake that finds it set asks nothing. The idle task's flag, the marker `sched_cpu_free` reads, is set under the lock by the wake that queues work there and cleared by that processor's selection, which takes the work or, when another processor stole it, finds the processor free again.
* `WORK_RESCHED` is set with `proc_work_set`, an atomic or with a full barrier, before the lock is let go; the kick is sent after it (`smp_kick` in `sched_make_ready`, `sched_wake_signal`, `sched_wake_due`, and the wait queue's wake after its own lock). An interrupt that arrives after the target switched away finds the new thread without the bit and does nothing; the old thread's switch was the request's answer.

## Measured in QEMU

`tests/musl/wakemusl.c` gains `busy`, two rows on four processors with the main thread spinning on processor 0:

* a futex wake onto processor 1 while a thread spins there in user mode, which measures the preemption;
* one FUTEX_WAKE of two sleepers that may run anywhere, the GPU interrupt's two wakes, with a thread spinning on each processor of 1 to 3 that either sleeper ran on last, so that each wake must find a processor of its own; each sleeper spins 20 us before it answers, so that one placed behind the other waits for it.

The testing PC, QEMU under KVM in WSL nested under Hyper-V, `qemu-system-x86_64 -accel kvm -cpu max -smp 4 -m 2048`, serial console, one run at a time, on 2026-11-13 between 09:15 and 09:24 UTC+6. Rach2 booted the x86-64 kernel with the test image and ran `/musl/wakemusl 2000 50 busy` from the debug shell: "before" is the milestone's head 7a3cdcad0, "after" is this task's kernel commit on it. Linux was Debian's 6.12.107+deb13-cloud-amd64 (PREEMPT_VOLUNTARY) from the GNU cache with an initramfs of static BusyBox and the same binary, SHA-256 `bcb73dac9f452333...`; it saw one package whose L3 all four processors share, as Rach2's `cpuid` gave. Output is in [84-166/qemu.txt](84-166/qemu.txt).

| Wake onto a spinning thread's processor, median us | 871.952 | 7.815 | 8.156 |

| Two wakes, second to run, p99 us | 51.938 | 32.431 | 3694.478 |

Before, the woken thread waited for the spinner's processor's next interrupt, the 250 Hz tick, and of two wakes the second always went to the processor the first had just been queued on, the lowest-numbered idle one, and waited out the first's 20 us. Now both match Linux. The waker's call costs what Linux's does, 5 us, which is the kick's interprocessor interrupt under KVM. Linux's second wake has a tail of 3.7 ms where the preempted spinner kept its protected slice to the next tick; Rach2 takes every woken thread as the one to pick and has none.

The idle rows, `/musl/wakemusl 20000 50`, which pin the waiter to an idle processor, are unchanged within the run's noise: futex wake to run 5.500 us median before and 5.631 after, eventfd 5.581 and 5.631, pipe 5.751 and 5.730, the hand-off 12.816 and 12.261 us a round.

QEMU has no i915 and no ki915, so the GL loop's own figure is the Lenovo's: [84-166-lenovo.md](84-166-lenovo.md).

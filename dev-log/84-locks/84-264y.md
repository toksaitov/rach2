# 84-264y: virtio-net's interface at each bind and unbind, its queue pairs, the legacy transport and PCI hot plug

virtio-net(4) named three limits Linux does not have: one interface for the boot's life, one pair of queues, and no device of the legacy interface. Task #5159 removed the three and added what the hot plug case needed: PCI hot plug through ACPI, which the kernel lacked. Each part has host rows and a `virtionet` case that passes on i686 and x86_64 and fails on the code before it.

## The interface at bind and unbind

An unbind through `/sys/bus/pci/drivers/virtio-pci/unbind` now withdraws the interface, as Linux's virtnet_remove unregisters it: its addresses, routes and neighbours go, and a packet socket bound to it reads `ENETDOWN`. A bind makes a new one, `ethN` for the lowest N free, with a new index, down. A withdrawn record keeps no device, so a pointer that netconsole or a socket kept reaches nothing a later bind made, and netconsole holds a target whose index no longer names an interface. vnetprobe checks the interface gone after the unbind and a new one, down, after the bind, which it configures and pings through.

## The legacy transport

A function without the virtio 1.x capabilities, QEMU's `disable-modern=on`, is driven through BAR0's ports as Linux's virtio_pci_legacy drives it. There is no FEATURES_OK and no generation. The queue has the size the device states, up to 1024, in a run of pages whose used ring is aligned to 4096. The MSI-X vector registers exist only while MSI-X is on. virtio-net's header is 10 bytes without `MRG_RXBUF` or `VERSION_1`. virtio-gpu, which needs `VERSION_1`, refuses such a device, as Linux's does. Case `machine.virtionet.legacy` (mergeable buffers off) passes 12 of 12 rows on each architecture.

## Queue pairs

With `VIRTIO_NET_F_MQ` the driver sets up every pair the device has, up to NR_CPUS (64), as Linux's virtnet_find_vqs does. It fills and uses one pair for each processor online, as Linux's `curr_queue_pairs`, and sets the count through `VIRTIO_NET_CTRL_MQ_VQ_PAIRS_SET`. A send goes out on the pair of the sending processor. The core's queue bound went from 8 to 1024, QEMU's `VIRTIO_QUEUE_MAX`, since the control queue follows the device's last pair; virtio-blk keeps its own bound of 8.

The first run of the case logged `1 of 4 queue pairs`. The boot's probe binds the device before `smp_start` brings the other processors up, while Linux probes with every processor online. `virtio_net_cpus_started`, called after `smp_start`, now fills the remaining pairs and sets the count again. The case logs `virtio_net: virtio0: 4 of 4 queue pairs, 4 carrying sends`.

QEMU's user network has one queue, and `mq=on` needs a backend with as many queues as the card. etude's scenario cards gained `tap_queues`. QEMU runs under `unshare --user --map-root-user --net`, whose shell makes a multi-queue tap `etude-tap0` at 10.0.2.2/24 and execs QEMU, so the guest's default static address reaches its gateway and nothing else. That works on Linux without privilege; the launcher refuses the card elsewhere with `ENOTSUP`. Two launcher faults turned up on the way:

* The tap's `-netdev` had a `%u` that etude's formatter, which knows only `%s`, passed to QEMU as it stood.
* textcheck reads the double hyphen that ends unshare's options, with a space on each side, as an em-dash. unshare needs none before `/bin/sh`, so it is gone.

Case `machine.virtionet.mq`, four processors and `mq=on` over a tap of four queues, passes 14 of 14 rows on each architecture.

## PCI hot plug

The kernel had no PCI hot plug: the PCI list was built once at boot. `sys/acpi/pcihp.c` now takes the slots of bus 0's host bridge, each child with `_ADR` and `_EJ0`, as Linux's acpiphp does. QEMU's `pc` machine has 30.

* On Notify 1, `pci_slot_add` lists the slot's new functions. `pci_assign_bars` gives each BAR without an address the lowest free one, aligned to its size, in the host bridge's `_CRS` windows, past other functions' BARs and any bridge's windows. virtio-pci then binds the function.
* On Notify 3, virtio-pci lets go of each function, the functions leave the list, and the slot's `_EJ0` runs, after which QEMU sends `DEVICE_DELETED`.

An I/O BAR takes ports from 0xC000. The fixed ports below that are not read from the namespace as Linux reads them. On QEMU these are the PM registers at 0x604, as the boot logs them, the GPE block at 0xafe0 and the hot plug controller at 0xae00.

The first run of the case saw the plug, but `device_del` brought no Notify. The monitor's `i /b 0xafe2` read GPE 1's enable bit clear after the delete, and its status was clear too. So the SCI had been taken, and the method's work was waiting on kacpid. The work ran the moment the debug shell started a program: `exec /vnetprobe if=none` gave `pci: hotplug: ejected: slot 6` and QEMU's `DEVICE_DELETED` at once. kacpid starts with the first program and does not run while the debug shell waits at its prompt. The shell runs in a process's place and lets no thread run. The plug had worked only because vnetprobe was running then. A booted system runs init and is not affected, so the fix is the case: vnetprobe `plugged=1` prompts for the card, for its removal and for its return, and waits for each while it runs. The limit is in acpi(4) and the ACPI Readme.

Case `machine.virtionet.hotplug` boots with no card. It adds a user network, puts a virtio-net card in slot 6 with `device_add` and runs vnetprobe's rows on it. It then takes the card out with `device_del`, after which QEMU's `query-pci` has nothing in slot 6, and puts it in again, which the probe configures and pings through. It passes 15 of 15 rows on each architecture. `pciwalk_hosttest.c` gained rows for:

* a slot's functions joining the list in their place and leaving it again;
* a multi-function card;
* BARs placed around a taken I/O BAR, a taken memory BAR and a bridge's window;
* a BAR that fits no window keeping no address.

## Left as limits

* The pairs in use change only as processors start; there is no `ethtool -L`, and no `VIRTIO_NET_F_RSS`.
* Hot plug covers bus 0, gives a card to virtio-pci alone, and does not eject a card another driver has.
* Work that ACPI's SCI queues waits while the debug shell idles at its prompt.

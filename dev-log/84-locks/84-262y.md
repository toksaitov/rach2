# 84-262y: why test_unused_attachments_mix_and_match held machine.d3d-vkd3d.5 past its bound

The release run's `machine.d3d-vkd3d.5` on x86_64 under KVM went 900 s without progress and was stopped, as if vkd3d-proton's `test_unused_attachments_mix_and_match` hung; the same unit stopped `machine.d3dvenus.vkd3d-5`. It does not hang on Rach2. It is one test of 5,225 checks that takes some 900 s of one processor on Linux, where every other unit of the row takes seconds, and the row's bounds could not hold it even on Linux. The row now starts it first, the row's initial bounds are its ceilings, run.py judges its failures by their line, since their count varies on Linux too, the scheduler no longer moves a thread whose cache is warm, as Linux's does not, and the host's Mesa keeps the shaders of Venus's render server under the tree's `build/cache` in place of the home directory.

## What the unit does

Every run of the unit alone, on Rach2 and on Linux, ends with its summary: 5,225 checks, all failing ones at `d3d12_render_target.c:2888`, render targets 1 to 7 reading back `-nan` or a sum short of the 256 blended draws ([upstream.md](upstream.md#vkd3d-protons-test_unused_attachments_mix_and_match-reads-nan-and-short-sums-from-render-targets-1-to-7-on-lavapipe)). Nearly all of its time is lavapipe's queue thread compiling shader variants with LLVM. The d3d12 process had one thread running throughout, its other threads asleep in futex waits; nothing waits on the kernel.

The case times include the boot, some 60 s. The host's three user spaces ran alike, so the GNU root's builds are not the cause; Mesa's disk cache behaved the same in both guests, a static C loop ran at the same speed in both, and interrupts stayed below 500 a second.

In the paired run Rach2 took 1.6 times Linux's time. Sampling the host's `/proc/PID/task/*/stat` showed Rach2's vCPU threads 1,718 s in guest mode against Debian's 1,110 s, and 100 s in the host's kernel against 14 s, so the time was the guest's own work, not the host's. Rach2's busy thread ran in turn on all eight processors, at 635 to 730 switches a second, where Linux's stayed mostly on one. Run alone on a quiet host, the gap shrank to 1,237 s against 888 to 950 s, and why a loaded host costs Rach2 more than Linux was not traced further.

## The scheduler

An idle processor took the first eligible thread from the busiest other queue (`sched_steal`), however recently it ran. A thread a wake had just preempted then moved to a processor whose caches it filled anew. Linux's load balancing leaves a task that ran within `sysctl_sched_migration_cost`, 0.5 ms, where it is (`task_hot`, kernel/sched/fair.c:9147-9175). `sched_steal` and the tick's kick of an idle processor (`sched_idle_balance`) now take only an ordinary thread that left its processor 0.5 ms ago or more, or a real-time one; each record keeps when it was last switched off (`ran_ns`). Alone, one run after the other, the case took 1,141 s with the new rule in `sched_steal` and 1,237 s without it, the busy thread's user time 973 s against 1,057 s, where Linux's was 942 s; an earlier run with the new rule took 1,347 s, so one pair does not prove the gain. The tick's kick took the same rule after these runs.

## The row

`run.py` gives a part's tests to four workers in list order, and this unit was 74th of row 5's 82, so it ran last and alone. The d3d-vkd3d rows report only the manifest's steps as progress, so the gap bound spans the whole row: 900 s initial, 2,700 s ceiling, and the case 1,320 s initial, 3,960 s ceiling. A case with fewer than five passed samples keeps its initial bounds, and a failed one gives no sample, so the row could never pass and learn longer ones. `run.py` now starts the long unit first in its part (`VK_LONG`), and row 5 of both families starts at its ceilings.

Linux's reference recorded 0, 1670, 1673, 1674 and 1677 failures for the unit, and Rach2's runs gave 1684 to 1687, which the count rule refused though every failure was at line 2888, as Linux's are. `mkref.py` now keeps, for a test whose runs failed two or more different nonzero counts, the lines its failures were on (`varying_lines`), and `run.py` judges such a test by every failure being on one of them; `linux.json` has `[2888]` for this unit. Placement tests keep their own rule, which comes first.

## Runs

Three runs of the unit alone under KVM on the testing PC completed and matched under the new judging rule: 1,347 s and 1,141 s with the new steal rule, and 1,237 s without it.

On the final kernel, one `tests/run -S 5107 -R 3` ran row 5 of both families three times each, one case at a time, and every attempt passed:

| Row | Attempts | Unit's failures |
|---|---|---|
| `machine.d3d-vkd3d.5` | 1,255 s, 1,339 s, 1,206 s | 1692, 1684, 1686 |
| `machine.d3dvenus.vkd3d-5` | 101 s, 89 s, 74 s | 1792 each |

Each lavapipe attempt ran past the old gap bound of 900 s, and the second past the old case bound of 1,320 s.

## Venus and the host's shader cache

Venus's row took 74 to 101 s here where the unit alone took 882 s an hour earlier, because the host's Mesa kept the shaders the render server's lavapipe compiled. QEMU and its render server ran with the account's own environment, so Mesa wrote its cache to the home directory's `.cache/mesa_shader_cache`: the Venus run between 19:20 and 19:45 wrote 196,614 files there, against the rule that nothing goes in a home directory, and every Venus and `virgl` case's time depended on what earlier runs had left there. The launcher now sets `MESA_SHADER_CACHE_DIR` to the tree's `build/cache/mesa-host` under both GL displays, when the environment names the tree in `ETUDE_TREE`, as every case's does, and sets no cache of its own. The cache still outlives a run, as the old one did, so a row's time still depends on whether an earlier run compiled its shaders; the first Venus run in a tree, or after a change of the host's Mesa, compiles them all. With the launcher's change, row 5 on Venus ran once more on an empty `build/cache/mesa-host` and passed in 824 s, 76 s short of the old gap bound, which spans nearly the whole case; it wrote 196,917 files, 793 MiB, there and none in the home directory.

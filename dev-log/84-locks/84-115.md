# 84-115: one word of work for the entry and the return

84-104 traced 759 of a one-byte call's instructions to the system call's entry and exit, more than Linux's whole call, and 84-114 left the call at 1,312 counted instructions against Linux's 708 once it had taken the descriptor's classification out. This task gave the thread one word of work flags, as Linux's thread flags, so that the entry and the return each test one word; ran a call that takes no big lock through no big-lock bookkeeping; charged CPU time on the tick, as the Linux kernel measured does; and then traced the pipe's remaining difference to its wakes and its sleeping lock and took both out.

## The changes

* Charge CPU time on the tick as Linux does, with the held-tick correction behind `rach2.cycleaccount`. The Debian kernel 80-92 measured has `CONFIG_VIRT_CPU_ACCOUNTING_GEN`, which acts only on `nohz_full` processors, and no `nohz_full=` on its command line, so it charges each tick to the mode it interrupted. Rach2 read the time-stamp counter at every entry from user mode and every return to it, `entry_cycles` and `user_cycles`, so that a tick held while interrupts were off in the kernel and taken at the first user instruction is charged as system time, and `bkl/calls` timed each system call. Both now run only with `rach2.cycleaccount` (`sched_cycle_account`), read in `init_syscall`. No measurement here shows a program that needs them; the switch keeps them for one that does.
* Give each thread a word of work flags that entry and return test once, and run an unlocked call through no big-lock frame or entry bookkeeping.
  * `process_t.work` holds `WORK_SIGNAL`, `WORK_RESCHED`, `WORK_TRACE`, `WORK_SECCOMP`, `WORK_RSEQ`, `WORK_LOOP`, `WORK_DEBUGREG` and `WORK_WAKETIME`. Whoever makes work sets its bit after the state it stands for, by compare-and-exchange (`proc_work_set`): a signal woken or posted, a mask to put back, a restart, a group stop and the tick's signals; a reschedule at each `need_resched`; a tracer's `PT_SYSCALL` or `PT_STEP`, and its attach; a seccomp filter, and a fork of a filtered thread; an rseq notice; a datagram on the loopback ring; debug registers to load; a timed wake to record. A fork gives the child every return bit, so its first return does the full work once.
  * The entry tests `WORK_ENTRY`, the tracer and seccomp bits, once (`syscall_entry_locked`, `_syscall_handler`), as Linux's `syscall_enter_from_user_mode_work` tests `SYSCALL_WORK_ENTER` (include/linux/entry-common.h:190-202). The return tests `WORK_EXIT` and the count of ended threads once (`isr_leave`); only when one is set does it call `isr_leave_work`, which takes the bits, drains the loopback ring, takes a switch, takes the big lock for signal and rseq work, loads debug registers and records a timed wake, each behind its bit, and sets again the bits whose work remains, as Linux's `exit_to_user_mode_loop` acts on the flags it read (kernel/entry/common.c:90-127). The bits are cleared before their work is tested, so a bit set meanwhile stays for the next return.
  * `syscall_entry` calls `isr_syscall`, which decides the lock and dispatches: a call marked to run without the big lock shifts a clear bit into the thread's frame record, `bkl_frames`, with interrupts left off as they are, and does nothing else; a locked call keeps `bkl_enter`, the frame, the entry note and the key. A hold an unlocked call takes on the way is charged to its call by number (`isr_call_entry`, read from `orig_nr` and the frame while `in_syscall` is `PROC_IN_CALL`). `bkl_frame_push`, `bkl_frame_pop` and `bkl_frame_top` no longer save and restore interrupts, which are off at every caller. The i386 fast entry (`ia32_fast_syscall`) goes through `isr_syscall` too.
  * The loopback ring is drained at the return of the thread that put a datagram on it (`WORK_LOOP`), not at every call's exit, as Linux's sender raises the softirq that its own `local_bh_enable` runs; a return that finds the big lock held elsewhere leaves the bit for its next return or the tick.
* Wake a pipe's queue only with a sleeper on it until a poll has asked about the pipe. The pipe woke its other end's queue after every transfer, which took the queue's spinlock with interrupts saved, some 70 instructions, with nobody on it. Linux's `pipe_write` wakes the readers only of a pipe that was empty or has been polled (`poll_usage`), and `pipe_read` the writers only of one that was full. The pipe now has `polled`, which the first `pipe_poll` sets and nothing clears, since epoll's edge test compares the queues' counts of wakes (`wq_wakes`); before it is set, `pipe_wake` passes a full barrier and wakes the queue only when `wq_active` finds a sleeper. The barrier pairs with the unlock of the queue a sleeper files itself on before it tests its condition (`wq_wait`), and with the barrier `pipe_poll` passes after setting `polled`.
* Draw a sleeping lock's place by compare-and-exchange and serve the next by exchange, with no spinlock. The pipe's lock is a sleeping lock (`sleep_lock`), whose take and give each passed its spinlock with interrupts saved, about 50 instructions a call, where Linux's uncontended `mutex_lock` and `mutex_unlock` are one atomic operation each. A taker now draws its place from `next` by compare-and-exchange and has the lock when `serving` reaches it; the holder alone writes the other fields, and its last give frees them and advances `serving` by an exchange, the full barrier before its test of the queue. The order of the line is unchanged.
* Count each processor's context switches and report their sum in `/proc/stat`'s `ctxt`, which read 0. The trace of the pipe needed the switch counts of both kernels, and Rach2's line was a constant, which `vmstat` shows as its `cs` column.

## The setting

As 84-104's and 84-114's: the Windows PC's WSL, QEMU 10.2.1's TCG, `-cpu max`, one processor, 512 MiB. Rach2 ran the x86-64 kernel with the os-real image in the debug shell, `rach2.rescue` and then `exec /bin/sh`, typed through the serial console by a script. Linux was Debian's 6.12.107 cloud kernel with an initramfs whose only program is Rach2's static BusyBox. The commands, three runs of each, timed by BusyBox dd:

* `dd if=/dev/zero of=/dev/null bs=1 count=400000`, 400,000 reads and 400,000 writes of one byte;
* `dd bs=1 count=100000 </dev/zero | dd bs=1 >/dev/null`, a one-byte pipe, 100,000 bytes.

Each kernel ran again with `-icount shift=0,sleep=off`, where a nanosecond is an instruction. A block log came from `-d nochain` at boot and `log exec,nochain` through the monitor during a long run of the same command, and a block's instructions were counted in the kernel's disassembly, as 84-114 counted them; Linux's symbols came from `/proc/kallsyms` with `nokaslr`.

Before is the milestone branch at 84-114's last commit. After is this task's branch rebased onto the milestone branch, whose ten newer commits are in it; the kernel before that rebase, with every change of this task but the milestone's newer commits, is named v7 below. Under TCG the testing PC's load was 2.4 to 7.8, with other accounts' guests running beside these, and a TCG figure moved by up to 0.1 s between runs, so each TCG figure here is paired with a Linux run made beside it; the counted figures repeat to the microsecond.

## What remains

* The layout of the code under TCG. The final kernel and v7 run the same counted instructions to within 0.2%, yet under TCG the final kernel took 0.589 to 0.693 s and 0.421 to 0.480 s against v7's 0.557 to 0.565 s and 0.396 to 0.414 s, in alternate runs. Reverting the milestone's commit that keeps a PROT_NONE entry not present gave 0.556 and 0.572 s and 0.394 and 0.399 s with the same counted instructions, 0.566905 and 0.363730 s against the final kernel's 0.566921 and 0.363558 s; nothing it changed runs in these calls. The final kernel with 64 bytes of padding after the loader's code, and no other change, gave 0.555 to 0.573 s and 0.401 to 0.426 s. Under TCG the time of these calls thus moves by up to 0.07 s with where the kernel's code lies, while the kernel's work does not change; which part of QEMU's translation makes it so was not traced, and no layout is chosen for QEMU here.
* Switches. Over the pipe v7 made 757 switches against Linux's 183. Each kernel switched about twice a tick while both dd processes could run, and Rach2 ticks at 1000 Hz, Linux at 250 Hz. Under TCG every address-space switch flushes QEMU's translation lookaside buffer, which neither guest avoids, since QEMU offers no PCID here (80-92). A test kernel ticking at 250 Hz, not committed, gave the pipe's writer 0.360 to 0.377 s under TCG against the 1000 Hz kernel's 0.367 to 0.386 s, so the tick's rate costs the one-byte pipe little; the counted figures include the switches and are below Linux's. The tick's rate is not this task's to change.
* Program start. Ten starts of `/bin/busybox true` took 0.04 s under TCG on Rach2 against Linux's 0.01 s, and both 0.01 s counted. It is outside the one-byte calls, and was not traced further.

## Checks

`make ARCH=x86_64 rach2` and `make ARCH=i686 rach2` both link at the rebased head. The host tests the changes touch, `vdso32`, `smp`, `syscall`, `packet`, `usbdisk`, `sched`, `pipe_copy`, `sleeplock`, `ext2`, `ext2_reserve`, `unix` and `procfs`, were compiled and linked on both architectures beside the milestone head's, with no symbol missing that the milestone head did not miss, and the fixtures `krffs_open` and `krffs_root_lock` were built; `vdso32_hosttest`, rewritten for the new entry, was run alone and passed. On QEMU, on the kernel of each step: with the work word, on two processors, kill of a sleeping and of a busy program, `SIGSTOP` and `SIGCONT`, a trapped `SIGUSR1`, `ping 127.0.0.1`, a UDP datagram through `nc`, and `timeout`; with the pipe's wake, on two, a reader that sleeps on an empty pipe, `read -t` on a pipe and a 4 KiB pipe of 8 MB; with the sleeping lock, on four, `seq | md5sum` against the file's sum, four `seq | cat | cat | md5sum` pipelines at once, a FIFO, and three one-byte pipelines at once, every sum equal. The three one-byte pipelines at once took 1.9 to 3.1 s on four processors, against 4.1 to 4.5 s before the sleeping lock's change. No suite or style check ran. No fault in another project's code was found.

# 84-151: the calls of WineD3D's yield spin and its wake paths beside Linux's

84-58 left WineD3D's GL round trip at 342.3 ms per 1000 round trips on the Lenovo, against Linux's 224 to 251 ([80-27](../80-games/80-27.md), "With forcewake held between accesses"). This task measured in QEMU, beside Linux in the same QEMU, the calls the loop's two threads spend their time in outside EXECBUFFER2, which 84-146 takes: getrusage(RUSAGE_THREAD) and sched_yield in Wine's yield spin, and the time from a futex wake, or an eventfd or pipe write that ends an epoll_pwait2, to the woken thread running. Rach2 was faster than Linux in every row but one, sched_yield while another processor also yields, which took the scheduler's global lock; it now returns without it, as Linux's does. The eventfd's read and write took the big lock, where Linux's take only the counter's own lock; they now run without it. SYNCOBJ_WAIT follows Linux's path. A per-thread filter in `bkl/calls` splits a thread's sleeps by call and its preemptions by the thread that took the processor, for the Lenovo loop that remains.

## The probe

`tests/musl/wakemusl.c` is one static musl program that runs unchanged on both systems. It reads the TSC between `lfence`s, calibrated against CLOCK_MONOTONIC over 200 ms, and pins its threads with sched_setaffinity.

* The per-call rows run 200,000 calls on processor 0 while a sibling on processor 1 is idle, spins, or calls sched_yield in a loop: getrusage(RUSAGE_THREAD), sched_yield, and the yield turn of Wine's `NtYieldExecution` spin, getrusage, sched_yield and getrusage again.
* The wake rows wake a thread pinned to processor 1, named `wakewaiter`, after the waker has spun for 50 us, so that the waiter is asleep: by FUTEX_WAKE_PRIVATE, by an eventfd write that ends its epoll_pwait2, and by a one-byte pipe write that ends it. The waker stamps the TSC before its call and the waiter after its return; each row gives the mean, median, 90th and 99th percentile of the difference, and the waker's call. The last row hands a futex to the waiter and back.
* `load` adds two threads on processors 2 and 3 that hand a futex back and forth for the whole run, so that the scheduler and the futex table have other users.
* `calls` writes `thread wakewaiter` to `bkl/calls` before the wake rows and prints the file after them.

## The setting

The testing PC, QEMU under KVM in WSL, nested under Hyper-V: `qemu-system-x86_64 -enable-kvm -cpu max -smp 4 -m 2048`, serial console, no network. Rach2 booted its x86-64 kernel with the test image and ran `/musl/wakemusl 20000 50` and `/musl/wakemusl 20000 50 load`. Linux was Debian's 6.12.107+deb13-cloud-amd64 kernel from the GNU cache, with an initramfs of static BusyBox and the same binary, once as Debian boots it and once with `mitigations=off` since Debian's entry pays for speculation mitigations on each call. The runs were on 2026-11-13 between 07:15 and 07:42 UTC+6, one at a time in this account. Their output is in [84-151/qemu.txt](84-151/qemu.txt).

## sched_yield

`sys_sched_yield` marked the thread yielded and called `schedule()`, which takes the scheduler's global lock (`sched_lock`) and looks at every run queue. With a sibling on another processor that also yields, the two contend for that lock on every call: 0.148 us a call against 0.071 with the sibling spinning. Linux's `do_sched_yield` (kernel/sched/syscalls.c:1410-1425) takes only this processor's run queue lock, and CFS's `yield_task_fair` returns at once when the queue holds only the caller (fair.c:9109-9110). `sched_yield_alone` now answers, with interrupts off and no lock, whether the scheduler could pick anything else here: the thread is not the idle thread and has no pending reschedule, this processor's run queue is empty, no real-time thread is queued anywhere (`rt_queued`, kept with the queue counts), the thread may run here, and no suspend holds it. When so, the call returns 0 at once. sched_yield now costs 0.04 us with the sibling idle, spinning or yielding, against Linux's 0.08 with mitigations off.

On the Lenovo, 84-58's third trial charged 44 of `sched_yield`'s 62 profile samples to `schedule`. The main thread's queue is empty while wined3d_cs runs on another processor, so these calls now return without it.

## eventfd

`eventfd`'s file operations declared no FILE_OPS_UNLOCKED, so every read and write took the big lock: in the filtered run, the waiter's 10,000 eventfd reads made 5,000 holds, 413 us held and 318 us waited in all (`syscall 0`, [84-151/qemu.txt](84-151/qemu.txt), `rach2c.out`). Linux's `eventfd_read` and `eventfd_write` take only the counter's wait-queue lock, and its release only drops the context's reference (fs/eventfd.c:109-116, 214-280). The counter, its hooks, the closed flag and its waiters were already under the counter's own spinlock, and `poll` already ran without the big lock. The read, write and poll now run without it (FILE_OPS_UNLOCKED and FILE_OPS_POLL_UNLOCKED), and the last close takes it only around the hang-ups of KVM's irqfds and ioeventfds that hook the counter, which are added and removed under it. In the head's filtered run the same reads made no holds (`rach2ec.out`).

The references were a plain counter that `eventfd_get` and `eventfd_put` changed without a lock. DRM's `SYNCOBJ_EVENTFD` runs without the big lock and took a reference beside KVM's irqfd, which took one under it, so two processors could lose an update and free the counter early or never. The references are now counted under the counter's spinlock, and the counter is freed after it is dropped.

## SYNCOBJ_WAIT

`drm_syncobj_wait_ioctl` is DRM_UNLOCKED and its `array_wait` (rach2/sys/drm/drm_syncobj.c) follows Linux's `drm_syncobj_array_wait_timeout` (drivers/gpu/drm/drm_syncobj.c:1033): the same four allocations, of the handles, the syncobjs, the points and the waits, a first pass that finds each point's fence and ends at once when enough are signalled, a wait for submission under WAIT_FOR_SUBMIT, the deadline hint passed to each fence, and a loop that arms a callback on each unsignalled fence and sleeps until one fires or the deadline passes. Nothing on this path takes a lock that Linux's does not, and nothing is done twice. The Lenovo's 2,976 calls of 39.6 us over the loop are mostly the sleep for the GPU; the filter below splits wined3d_cs's sleeps by request, so that the next trial gives how many of the calls slept.

## The thread filter

`bkl/calls` counted every thread together. A write of `thread TID` or `thread NAME` to it now zeroes its counts and counts one thread alone, a name being the comm of up to 15 bytes; any other write zeroes them and counts all again. While a thread is chosen, the file's call, hold and wait rows are that thread's, and it adds the thread's involuntary switches by the thread switched to (`switch PID YIELDS PREEMPTS COMM`, yields being switches from a sched_yield), and its sleeps by the call and, for an ioctl, by the request it slept in (`block syscall NR N`, `block ioctl 0xCMD N`). `trip.sh -t THREAD` chooses the thread for its runs and restores the default on exit, and `trip.py` gives each thread's run time and its time ready but not running from `/proc/PID/task/TID/schedstat`, and the chosen thread's switches and sleeps over the loop. In QEMU the filter counted wakemusl's waiter alone: 9,998 sleeps in futex and 9,998 in epoll_pwait2 over 5,000 rounds of each of the four wake rows, and 4 in exit.

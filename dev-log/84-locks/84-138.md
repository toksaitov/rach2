# 84-138: getpid, the identity calls and KVM_CHECK_EXTENSION off the big lock

84-130 left two bare calls slower than Linux's on the same machine ([84-110](84-110.md), "Again after 84-115 and 84-129"): getpid at 1,224 to 1,266 ns against 566 to 588, and KVM_CHECK_EXTENSION of `/dev/kvm` at 1,699 to 1,883 ns against 1,190 to 1,224. Both held the big lock for every call. With the lock gone from both, getpid takes 577 to 755 ns, a median of 598 over eight boots against Linux's 574 over five runs, and KVM_CHECK_EXTENSION 988 to 1,210 ns, a median of 1,022 against Linux's 1,065.

## Where the time went

`sys_getpid` was not marked to run without the big lock (`syscall_unlock`), so the entry took the lock, pushed the frame's record and named the hold for `bkl/calls` (`isr_router_locked`), and the return gave it back. getpid, gettid, getppid, getpgrp, getpgid, getsid, the four id getters, getresuid, getresgid and getgroups, native and i386 with the i386 16-bit forms, now run without it (`syscall_ids_unlock`): each reads a word of the caller's own record once, and only the thread itself changes its credentials (`sys_setuid` and the rest change `current_proc` alone), as Linux's read the task and its credentials under RCU. A word another thread writes under the big lock, the parent's PID at a reparenting or the group a setpgid gives, reads as its old value or its new one, as on Linux. A call takes the lock itself for what it guards (`ids_lock`): getpgid and getsid of another process, which look it up in the process table, and any of them in a user or PID namespace below the first, whose ID maps and PID lookups read state the lock covers.

The ioctl already entered without the lock, since `sys_ioctl` is marked, but `/dev/kvm`'s operations did not declare FILE_OPS_UNLOCKED, so `ioctl_fd` took the big lock around the request and ran `ioctl_locked`'s chain before `dev_ioctl`: the hung terminal's check, the file attribute and clone requests, the socket and interface requests and the terminal requests, each a test that fails for `/dev/kvm`. The descriptor's lookup, `fd_get`, is the same on both paths. `/dev/kvm` now declares FILE_OPS_UNLOCKED, as Linux's `kvm_dev_ioctl` takes no lock, and `dev_ioctl` answers KVM_GET_API_VERSION, KVM_CHECK_EXTENSION, KVM_GET_VCPU_MMAP_SIZE and KVM_X86_GET_MCE_CAP_SUPPORTED without it, from constants, the backend and its capabilities, the host's CPUID and processor count and the cached host XCR0; every other request takes the lock (`dev_ioctl_locked`).

The unlocked ioctl path sent every request straight to the type's own ioctl, so FICLONE and FICLONERANGE on a pipe or a device answered ENOTTY where Linux's `do_vfs_ioctl` answers them for a descriptor of any type, and an interface request such as SIOCGIFINDEX on an AF_UNIX socket answered ENOTTY since Unix sockets went off the lock, where Linux's `sock_do_ioctl` passes it to `dev_ioctl`: musl's `if_nametoindex` asks through such a socket, and failed. `/dev/kvm` would have joined them. `ioctl_unlocked` now takes the big lock for those two, in Linux's order. The KVM suite's preparation also stopped at `tests/rngprobe`, which includes `kcpu.c` and lacked the `exits_count` that its cpuid and MSR accesses now call; the probe has a no-op one.

## The setting

As 84-130's: the testing PC, the KVM suite's machine under QEMU's TCG with SVM and one processor (`RACH2_QEMU_ACCEL=tcg ARCH=x86_64 RACH2_CASES=machine.kvm.unit-tests tests/run kvm`), and Debian's Linux 6.12.107+deb13-cloud-amd64 as the KVM host of the same machine with one processor (`tests/kvm/linux-corpus.sh -a tcg -k unit unit-subset.list`). 84-130's timing script was not committed, so this one is new, and its figures compare only with each other. A temporary `corpus.sh`, not committed, waited 30 s after its start and then ran, in one perl, five rounds of 100,000 getpid calls by `syscall(39)` and 100,000 KVM_CHECK_EXTENSION ioctls of `/dev/kvm` for KVM_CAP_USER_MEMORY, timed by CLOCK_MONOTONIC through `syscall(228)`, since the root's perl has no Time::HiRes, and then printed the lines of `bkl/calls` for getpid and the ioctl:

    sleep 30
    perl -e '
    sub now { my $t = "\0" x 16; syscall(228, 1, $t); my ($s, $n) = unpack("q q", $t);
        return $s * 1e9 + $n; }
    my $c = 100000;
    open(my $f, "<", "/dev/kvm") or die "kvm: $!";
    for my $r (1 .. 5) {
        my $t = now(); syscall(39) for 1 .. $c; my $g = (now() - $t) / $c;
        $t = now(); ioctl($f, 0xAE03, 3) for 1 .. $c; my $k = (now() - $t) / $c;
        printf "kvm-corpus: time: getpid %d ns, KVM_CHECK_EXTENSION %d ns\n", $g, $k;
    }'

Each run ran alone in this account, one after the other; the other accounts' work kept the PC's load average between 3.6 and 7.0 of its 32 threads throughout. The times are the runs' starts in UTC+6 on 2026-11-13, and each cell is the median of the run's five rounds, in ns.

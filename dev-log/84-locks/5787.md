# 5787: wineboot's stall in games-wine.maps, forced

A lone run of `machine.games-wine.maps` on x86_64 at the head (card 5782) printed Weston's start and then nothing until etude's gap bound of 900 s, in `make_prefix`'s `wineboot.exe -u`. Cards 5786 and 5787 forced it in two guests at the head's kernel (19a1eb6354, unchanged through 9bed40b7a). It is a stall of GE-Proton 11-12 when the guest reads its disk very slowly on the first run after boot, and Linux 6.12.115 stalls the same way under the same load; Rach2's kernel is not its cause. The lone run that stalled shared the testing PC with a build writing a 24 GiB GNU image (card 5786).

## Loads

Each guest is the games-wine machine: KVM, 4 processors, 8 GiB, virgl, overlays of the head's `gnu-test.disk` and the probes' disk, claimed through the ledger.

| Load | Runs | Each took | Stalled |
|---|---|---|---|
| One boot, run.py's Weston once, `make_prefix` in a fresh prefix again and again | 1000 | 6.3 to 30.7 s | 0 |
| A fresh boot for each `run.py maps`, the virtio disks unthrottled | 1 | 34 s | 0 |
| The same, QEMU's throttle at 300 IOPS and 30 MiB/s | 1 | 66 s | 0 |
| The same, at 100 IOPS and 10 MiB/s | 1 | 169 s | 0 |
| The same, at 40 IOPS and 4 MiB/s | 2 | | 2 |

Card 5786's four loads, 500 prefixes with fresh boots among them, did not stall. QEMU's throttle (`throttling.iops-total`, `throttling.bps-total` on each `-drive`) slows the guest's reads as a saturated host disk serves them and writes nothing on the host, which the testing skill bars a forcing load from doing.

## The stall

Both stalled boots were read at 900 s of the row and 30 s later, the second live through its root shell, with registers, stacks, the kernel's data and a compressed dump of guest memory saved through QMP.

* All four processors halted in the idle loop with interrupts on; the load average was 0.05. All 93 threads slept, none in a disk wait.
* wineboot.exe, rundll32.exe (`setupapi,InstallHinfSection PreInstall`), conhost.exe, steam.exe, services.exe, two winedevice.exe, plugplay.exe, svchost.exe, lsass.exe and rpcss.exe waited in `futex_waitv` with no timeout or in `pipe_read` on their server pipes; wineserver, Weston and Xwayland in `ep_poll`. No explorer.exe ran.
* Each of the 40 futex and `futex_waitv` words, read through `/proc/PID/mem`, held the value its waiter expected.
* Each pipe, socket and anonymous file of wineserver and of every Wine process, duplicated with `pidfd_getfd` and polled, was neither readable nor hung up, with no bytes queued: wineserver had no event left to read.
* The threads' user stacks, named from the symbols of Proton's `win32u.so` and `ntdll.so`: rundll32 and conhost in `send_message`, `send_inter_thread_message`, `wait_message_reply`; wineboot in `wait_message`; a steam.exe thread past `NtUserCreateWindowEx`.
* Proton's log of the launch, read from guest memory, ends with the desktop's failure:

```
00a4:err:ntoskrnl:ZwLoadDriver failed to create driver L"\\Registry\\Machine\\System\\CurrentControlSet\\Services\\winebth": c0000142
00fc:err:winediag:nodrv_CreateWindow Application tried to create a window, but no driver could be loaded.
00fc:err:winediag:nodrv_CreateWindow L"The explorer process failed to start."
0024:err:steamclient:steamclient_init unable to load native steamclient library
```

win32u writes the last `nodrv_CreateWindow` line when the desktop's video key holds no GraphicsDriver value after its wait for `explorer.exe /desktop`. In the memory of the guest that made 1000 prefixes, the text is only win32u's string constant, never a logged line.

So no wake-up was lost: every waiter waits for a reply or an object that no thread of Wine will give, once explorer.exe has not registered the display driver in time.

## Linux

The Debian reference guest (Debian 13, Linux 6.12.115, the same QEMU profile and the same Proton tree) ran `run.py maps` with the row's processes in a cgroup whose `io.max` capped the disk at 40 IOPS and 4 MiB/s each way, after dropping the page cache, three rows in each of two boots. The first row after each boot stood still with the same picture: load 0.00, no explorer.exe, wineboot, conhost, rundll32 and steam.exe in `futex_wait_multiple`, wineserver in `epoll_wait`, every futex word at its expected value, and Proton's log ending in the same `nodrv_CreateWindow` "The explorer process failed to start." The cgroup had read 428 MB in 5943 requests by then. The rows after the first passed: in 20 s each in the first boot, and in 350 s each in the second, which read some 900 MB each through the cap. So the cap alone does not stall a row; the first Wine start after boot under it did, in each of the four boots, on both systems.

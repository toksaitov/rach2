# 84-266w: copypixels-draw-sync, named a flake on virgl

`machine.virgl.piglit-16` failed in the release's third rerun (run 43665453124, at f6dc157af) on the one test that failed it in the first rerun ([84-265q](84-265q.md)): `spec@!opengl 1.1@copypixels-draw-sync`, fail here and pass in the reference. The Debian reference guest fails the same test in the same way beside the same kind of load, so the test is named a flake in `tests/graphics/piglit-virgl.flakes` and in `piglit-quick-gl.flakes`, whose list holds it too. Rach2 has no fault here.

## What the test does

Its `piglit_display`, read from the disassembly of Debian's binary, sets a raster position at each pixel of the window, copies one pixel there with glCopyPixels, draws a one-pixel rectangle on it, and after the last pixel probes one pixel with glReadPixels. The guest encodes all of it in a fraction of a second; the probe's readback waits, through `DRM_IOCTL_VIRTGPU_WAIT`, for the host to run every copy and draw before it. That one wait carries the whole test's work on the host, against Linux's 15 s bound, which Rach2's `vgpu_wait_ioctl` keeps.

## The third rerun's failure

The case's kept evidence was in `build/tmp/virgl-piglit-16/evidence` of loop v's clone.

* The test ran 15.14 s, from 03:17:09 UTC on 2026-11-15, with Mesa's "waiting got error - 16, slow gpu or hang?" and its probe reading 0 0 0 0 where it expected 0 255 0 0, as in the first rerun.
* Unlike the first rerun, the host was not slow before it: the test before took 0.14 s, and the run's next longest test 7.85 s. The gap after it, 2.88 s, was the third longest of the run.
* The guest's console holds no kernel message after boot, and QEMU's standard error only virglrenderer's shader messages of other tests.
* The ledger at the case's end held four other guests: another account's `machine.d3dvenus.wine-wined3dvk-d3d11-d3d11` Venus guest and Debian reference guest, each of 8 CPUs and 17 GiB, a third account's guest of 17 GiB, and the release's `machine.virgl.piglit-quick-gl`, which draws on the same D3D12 adapter. The host's load was 12.2 to 16.1 on its 32 threads.

Its siblings check the same ordering, a copy after a draw and a draw after a copy, passed in Debian beside the same load, and stay judged in both lists.

# 84-265p: why machine.d3dvenus.vkd3d-5 failed in the release's rerun

The release's rerun failed `machine.d3dvenus.vkd3d-5` on x86_64 with "row failed: Direct3D row did not match Linux". Its one unmatched unit was vkd3d-proton's `test_unused_attachments_mix_and_match`, which ended with SIGABRT (`"exit": -6`) and no summary; every other unit of the row matched Venus's reference.

## What the evidence shows

The kept overlay of the GNU root holds the guest's `/tmp/d3d-results`. Flattened with its unreadable backing file left out (`qemu-img rebase -u -b ''`), its ext2 file system opens with debugfs at the partition's offset, 1 MiB, and the files of the results directory read whole:

* The unit's log is 1,817 bytes: vkd3d-proton's device creation, the test's `begin` line and a second device's creation, and nothing after. Its last write was at 01:20:28 UTC+5 on 2026-11-15.
* Its `.exit.json`, `{"pid": 64, "exit": -6}`, was written at 01:35:38, 910 s later. The row's other units had ended by 01:21.
* The guest's console has no kernel message after the boot's, and QEMU's standard error is empty.

## The abort

Mesa 26.1.6's Venus driver, which the GNU root and the Debian reference guest both run, waits for the host in `vn_relax` (`src/virtio/vulkan/vn_common.c`). A wait sleeps in doubling steps from 160 us; at its 16,384th step, some 895 s into one wait, or at a check of the host's alive bit that finds it unset, it calls `abort()`. `VN_DEBUG=no_abort` lifts both. Its message goes through `mesa_log_v` at the debug level, below the info level that a release build of Mesa prints (`src/util/log.h`), so the abort prints nothing; a ring the host marks fatal aborts regardless of the option.

The test makes 512 pipeline state objects, records 512 draws with each in one command list, and submits the list with its first readback, which waits for it (`d3d12_render_target.c:2733-2900`, vkd3d-proton 8293130eb). The host's lavapipe compiles the pipelines' shaders with LLVM on its queue at their first draws, so the test spends nearly all of its time in that one wait. With the host's shader cache empty the row took 824 s on a quiet host (84-262y); in the rerun, beside the release's other guests, the wait passed Venus's limit. Rach2's sleeps are not shorter than asked (`sleep_for`, `rach2/sys/syscall.c`), so the guest counted no faster than Linux would: a Debian guest on the same host, with the same driver, aborts at the same point.

## The fix

`tests/graphics/d3d/run.py` sets `VN_DEBUG=no_abort` for the vkd3d family on Venus and records `VN_` variables in `environment.json`. The Wine and probe rows keep Venus's abort, as their references were taken with it ([tests/graphics/Readme.md](../../tests/graphics/Readme.md#direct3d-on-venus)).

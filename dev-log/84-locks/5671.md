# 5671: the keyboard panic case's lost double fault under KVM

`machine.panic.kbd` on i686 failed once in loop a's full run under KVM, `t5661-kvm` (task 5661): its console ends at `kstack: overrun: pid 1 descends its stack at 0xc0021000`, with no double fault, no panic and nothing on QEMU's standard error, and its capture says `not sent` for each QMP command. This file records what is known of why, and what is not.

## What is known

The guest did not stall: it reset. The descent runs into the unmapped guard page below its kernel stack, the page fault's frame cannot be pushed there, and the processor raises a double fault, whose gate on i686 is a task gate (`rach2/sys/arch/i686/idt.c`, `tss.c`). On the testing PC, Rach2 runs under WSL's KVM, `kvm_amd` with `nested=1` and `npt=Y` on Hyper-V's nested SVM, an AMD Ryzen 9 7950X3D. There, in about 1 boot of 600, the guest resets after the descent begins and before the double fault handler's first traced statement; QEMU, started with `-no-reboot`, sends SHUTDOWN with the reason `guest-reset` and exits. Under TCG the same kernel and image never reset in 4,000 boots.

The cause is not proved. A fault in the layers that deliver the double fault, KVM's emulation of the task switch or Hyper-V's nested SVM, fits every record below, but the records do not exclude a cause in the guest:

* The `D` line of `5671/trace.patch` is a C statement of `isr_double_fault`, after its prologue. That no failed boot wrote it shows that the handler never reached that statement, not that the double fault task ran no instruction: the task switch, the prologue's pushes onto the double fault stack, or the first instructions could fault in a way that ends in a triple fault.
* `int $8`, the control that never failed, reaches the same task gate by a software interrupt. It differs from the processor's double fault in more than the fault that raises it: it pushes no error code onto the new task's stack, and it is not raised while another exception is delivered. KVM handles the error code's push apart (`emulator_task_switch` in `arch/x86/kvm/emulate.c`). The control therefore does not exclude the error code's push, or the delivery of an exception within another, whether the fault lies in the guest's setup of that path or in the host.
* Every boot judged `pass` printed `panic: rebooting in`, which is all the reproducer then checked. A boot that panicked for another reason would have passed too, and the passing boots' directories were removed as they ended. The logs cannot establish that every passing boot entered the double fault task. `5671/repro.py` now judges each variant by its own panic and trace; the runs below were made before that change.
* `info registers` at QEMU's pause shows the reset state, EIP 0xfff0, since on AMD, KVM resets the processor at its shutdown intercept, so the machine's state at the fault cannot be read.

The harness sent no query because QEMU had already ended: the console's close ended the scenario's wait before the launcher saw QEMU's process end, so the machine still counted as running, and `etude_machine_qmp` refused each command with EPIPE, since QMP had closed. The capture said `not sent` and nothing of the end.

To run these rows with the current reproducer, set `EXPECT=fault` for the two unchanged rows, `EXPECT=trace` for the trace, interrupts-off and stack-write rows, and `EXPECT=int8` for the software interrupt row. A reset counts as a lost panic only when QMP reports `guest-reset` and identifies the guest as its source. A traced reset must also show the descent's trace.

A log holds the reproducer's line for each boot that did not pass and its totals; the traced rows add, for each failed boot, its debug port's output and its console's last line. Those two lines are all that is left of the failed boots: their directories, with the console whole and the state QEMU gave at its pause, were scratch and are gone. In every failed traced boot the debug port has the descent's `Rc0024fc4 00000286 00000000` (ESP, EFLAGS with IF set, the guard's mapping: none), the same as in a passing boot, and nothing after it; a passing traced boot adds `Dc0020fa0 00120a69 c0020fa4` (CR2, and the EIP and ESP the task switch saved, the descent's `mov %al,-0x1008(%ebp)` in `kstack_descend`). No failed traced boot's console goes past the overrun's line.

The harness hits it too. `tests/run -S 2 -R 1000 panic` with `RACH2_CASES=machine.panic.kbd`, `RACH2_QEMU_ACCEL=kvm`, `ARCH=i686` and 24 workers, beside 16 boots of the unchanged kernel by the reproducer as load (`load-beside-harness.out`, stopped once the harness ended, with 15 resets in its boots), failed one repetition of 1,000, as loop a's run did (`harness-load.out`): its console ends at the overrun's line, 4,785 bytes, the size of loop a's. Its capture, with the change below, is `harness-load.r523.capture`, copied from the session that ran it, since its directory under `build/tests/failed/` is gone. The same run without the load, `-S 1`, passed 1,000 of 1,000 (`harness-alone.out`); at the rate above about 1.7 failures were to be expected, so that is a run in six.

## The fix

Rach2's double fault follows Linux's i386 one (`arch/x86/kernel/doublefault_32.c`): a task gate, a TSS with its own stack, the kernel's page directory and interrupts off, and a handler that ignores the error code. No fault was found in it, and none of the traced variants above moved the rate by more than chance. The release's full run keeps `memory` and `panic` under TCG (`tools/ci/kvm-suites` on master), and their cases pass there.

The harness now says what happened. `capture` in `tools/etude/posix/scenario.c` keeps the diagnostics of each machine's latest boot once the machines have ended, whether or not the launcher had seen QEMU end before the scenario returned, with why a command was not sent and a last line with the machine's end. A reset like this one reads:

```
query-status: not sent: QMP had closed, as it does when QEMU ends
query-cpus-fast: not sent: QMP had closed, as it does when QEMU ends
human-monitor-command: not sent: QMP had closed, as it does when QEMU ends
end: reset: SHUTDOWN, reason guest-reset, by the guest, after console byte 4785
```

A stalled guest's queries were sent before and still are; its capture now ends with the cleanup's quit, `end: stopped: SHUTDOWN, reason host-qmp-quit, by the host, after console byte N`. The instruction pointer's symbol is not added: the kernel QEMU boots has no symbols but `_start` and `_end` (`rach2/Makefile`), and `addr2line -f -e build/rach2/kernel.debug EIP` names it from the capture's `info registers -a`.

## What would settle it

* Run the rows again with the reproducer's present judgement, which requires the expected panic in every passing boot and the handler's trace in every passing traced boot.
* A trace point in the double fault task's first instruction, before any push, and a control that raises the double fault by an exception within an exception without the guard page, such as a page fault whose gate's stack is unmapped, which pushes the error code as the descent's does.
* The same boots with Linux's i386 kernel and a stack overflow, to show the reset without Rach2; on an AMD host without Hyper-V and on an Intel one under WSL, to place it in KVM or in Hyper-V; and `kvm:kvm_exit` and `kvm:kvm_inj_exception` traced as root around a failed boot.

# 5671: the keyboard panic case's lost double fault under KVM

`machine.panic.kbd` on i686 failed once in loop a's full run under KVM, `t5661-kvm` (task 5661): its console ends at `kstack: overrun: pid 1 descends its stack at 0xc0021000`, with no double fault, no panic and nothing on QEMU's standard error, and its capture says `not sent` for each QMP command. This file records why.

## The cause

The guest did not stall: it reset. The descent runs into the unmapped guard page below its kernel stack, the page fault's frame cannot be pushed there, and the processor raises a double fault, whose gate on i686 is a task gate (`rach2/sys/arch/i686/idt.c`, `tss.c`). On the testing PC, Rach2 runs under WSL's KVM, `kvm_amd` with `nested=1` and `npt=Y` on Hyper-V's nested SVM, an AMD Ryzen 9 7950X3D. There the processor's double fault through the task gate resets the guest in about 1 boot of 600, before the double fault task runs its first instruction. QEMU, started with `-no-reboot`, sends SHUTDOWN with the reason `guest-reset` and exits. The same task gate entered by `int $8` never failed, and neither interrupts nor the double fault stack's first touch change the rate. The guest's state is the same in every boot up to the fault, so the reset comes from the layers that deliver the double fault, KVM and Hyper-V; which of the two is not known (`upstream.md`, "The testing PC's nested SVM resets an i686 guest at a double fault through a task gate").

The harness sent no query because QEMU had already ended: the console's close ended the scenario's wait before the launcher saw QEMU's process end, so the machine still counted as running, and `etude_machine_qmp` refused each command with EPIPE, since QMP had closed. The capture said `not sent` and nothing of the end.

## The runs

Each run is `5671/repro.py`, which boots the case's QEMU command line, with etude's kernel and test image, many at once and stops each boot at the panic's `rebooting in`; QEMU pauses at the guest's reset, and the boots that do not pass are kept. Kernel at 3f603edb3 (milestone/76-display), image `0acab99fe92b...`, the image of the failed run, QEMU 10.2.1, 28 boots at once, 4,000 boots each.

| Kernel | Reset without the panic |
|---|---|
| unchanged | 7 |
| `5671/trace.patch`: a line on port 0xe9 before the descent, at every exception, interrupt and NMI after it, and at the double fault task's first statement | 6 |
| the trace, interrupts off for the descent | 4 |
| the trace, every page of the double fault stack written before the descent | 7 |
| the trace, `int $8` in the descent's place, which enters the double fault task with no fault | 0 |

In every failed traced boot the descent starts as in the passing ones, `Rc0024fc4 00000286 00000000` (ESP, EFLAGS with IF set, the guard's mapping: none), and nothing follows: no exception, no interrupt, no NMI reaches the kernel, and the double fault task never writes its `D`, which a passing boot writes as `Dc0020fa0 00120a69 c0020fa4` (CR2, and the EIP and ESP the task switch saved, the descent's `mov %al,-0x1008(%ebp)` in `kstack_descend`). The SHUTDOWN reason is `guest-reset` in each. `info registers` at the pause shows the reset state, EIP 0xfff0, since on AMD KVM resets the processor at its shutdown intercept, so the machine's state at the fault cannot be read.

`int $8` reaches the same gate and the same emulated task switch, without the fault: 0 in 4,000 boots, against 6 expected from the unchanged rate. The double fault the processor raises while it delivers a page fault, and not the task switch alone, is what fails.

## The fix

Rach2's double fault follows Linux's i386 one (`arch/x86/kernel/doublefault_32.c`): a task gate, a TSS with its own stack, the kernel's page directory and interrupts off, and a handler that ignores the error code. Nothing in the guest is wrong, and nothing in it can keep the processor's double fault from being lost there. The release's full run keeps `memory` and `panic` under TCG (`tools/ci/kvm-suites` on master), and their cases pass there.

The harness now says what happened. `capture` in `tools/etude/posix/scenario.c` keeps the diagnostics once the machines have ended, with why a command was not sent, and a last line with the machine's end. A reset like this one reads:

```
query-status: not sent: QMP had closed, as it does when QEMU ends
query-cpus-fast: not sent: QMP had closed, as it does when QEMU ends
human-monitor-command: not sent: QMP had closed, as it does when QEMU ends
end: reset: SHUTDOWN, reason guest-reset, by the guest, after console byte 4785
```

A stalled guest's queries were sent before and still are; its capture now ends with the cleanup's quit, `end: stopped: SHUTDOWN, reason host-qmp-quit, by the host, after console byte N`. The instruction pointer's symbol is not added: the kernel QEMU boots has no symbols but `_start` and `_end` (`rach2/Makefile`), and `addr2line -f -e build/rach2/kernel.debug EIP` names it from the capture's `info registers -a`.

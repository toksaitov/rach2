# 84-167: PCI interrupt placement (task 4893)

PCI MSI and MSI-X messages are allocated to the reachable online processor with the fewest allocated messages. Ties choose the first logical processor, following Linux 6.12.115's `matrix_find_best_cpu` (`kernel/irq/matrix.c:135-152`) and `assign_irq_vector_any_locked` (`arch/x86/kernel/apic/vector.c:281-310`). Messages enabled before the secondary processors start are replayed in allocation order after `smp_start`; a six-message, four-processor model requires destinations 0, 1, 2, 3, 0, 1. Counting other boot messages at their old destination during that replay could leave the sixth message on processor 0.

`/proc/irq/N/smp_affinity` reads the requested mask and accepts a privileged hexadecimal-mask write. A zero restores the default mask. A mask with no reachable online processor is refused without changing either mask. `effective_affinity` is read-only, as on Linux, and reports the chosen processor. The records retain the requested mask when a processor departs and placement falls back to the remaining online processors. `/proc/interrupts` has a heading and a count for each online processor; its existing readers now sum those columns.

## Migration and the shared structures

The vector number and its handler chain remain globally reserved across a move. A compatibility-format move changes the address while retaining the data's vector, and reads the write back. Linux's cleanup releases a previous per-processor vector only after checking its IRR (`arch/x86/kernel/apic/vector.c:959-995`). Rach2 retains the same globally allocated vector on both processors, so migration releases no old vector slot. `irq_dispatch_edge` serializes messages arriving on the old and new destinations. This task retains the existing global vector pool.

A remapped move changes the destination in the same live interrupt-remapping entry and invalidates its cached copy. It retains the handle a message in flight carries. The aligned 64-bit write changes the destination without clearing Present or changing the source check. The message records carry the whole APIC id; the x2APIC-format remapper can select a processor whose id exceeds 254. Compatibility-format messages select only ids below 255.

The audit covered these writers and readers:

* `pci.c`: `msi_lock` guards allocation counts, requested and effective masks, destinations, message writes, enable, disable, and remapper start and stop. Changing a function from MSI-X to MSI now masks MSI-X and removes every entry's record; the old code removed entry 0 alone and left secondary entries visible as live messages.
* `pciconf.c`: configuration mechanism #1 now holds `config_lock` with interrupts off across the address/data pair. Local interrupt masking alone did not exclude an interrupt handler on another processor. ECAM's individual accesses remain loads and stores of their register width.
* `vector.c` and `isr.c`: the pool has `vector_lock`; handler arrays and names have `handler_lock`, and dispatch copies a chain before invoking it outside the lock. A newly locked handler takes the big lock even if the router read the earlier unlocked mark. NMI, double-fault and machine-check chains are immutable after boot and use no handler lock. Counts are atomic; processor counts are indexed by the processor taking the entry.
* USB's pending-state reader checks all online APICs through `smp_call`. A message acknowledged at entry remains counted in `vector_active` while it waits for the big lock or runs its chain, so the timer's pump does not report a fallback merely because the interrupt is on another processor or its hardware EOI has already been sent. The remote callback reads only its local APIC and takes no lock.
* Normal shutdown moves messages to the processor which stays running before stopping the others. Departing processors forward pending PCI vectors to it. The stop path reads only the published forwarding table and takes no PCI lock, including in an NMI. Panic without a prepared normal shutdown leaves that table empty. There is no runtime processor-hotplug interface.
* i915's interrupt uses its device-list lock and the engine, register and fence locks; AHCI uses each port's lock; NVMe uses its message-count lock, completion lock and submission lock; HDA uses `stream_lock`. xHCI, RTL8168, ath9k and VFIO's interrupt handlers retain the big lock. Virtio's transport retains its existing per-callback locked or unlocked flag. These handlers use the global vector identity and do not read the old boot-processor destination. I/O APIC lines and the VT-d fault event retain their existing boot-processor routing.

## The models and QEMU

Only new rows were run: `pci_affinity_hosttest`, `procfs_hosttest --irq-only` and `vtd_hosttest --affinity-only`, under ASan and UBSan. The first covers shared MSI/MSI-X allocation counts, boot replay, rejected masks, processor-offline fallback, mode changes and shutdown. The procfs rows cover comma-separated words, processor 63, zero, malformed input, user-copy failure, EOF and the read-only effective mask. The VT-d row runs the actual PCI and remapper paths on the Lenovo chip model, including a cached old destination, the retained live handle, a full x2APIC id, MSI-X, offline fallback and shutdown: 14 checks passed. No suite or existing host-test rows ran.

The standalone QEMU probe uses four processors and 512 MiB on q35, with an AHCI disk, an NVMe disk, a NEC xHCI controller with a USB disk and keyboard, and an HDA codec whose host audio backend is `none`. It reads 512 KiB from each disk after assigning the messages to processor 3, writes 32 KiB to HDA, runs reads beside repeated affinity changes, moves the messages to processor 0 and reads again. Each guest powers itself off. Both Rach2 architectures ran under KVM on the testing host, beside Debian Linux 6.12.115 with the same controllers. TCG on the Mac also ran the earlier form without the USB disk.

The KVM runs' complete outputs, probe and invocation are in [4893/evidence/](4893/evidence/). The exact measured kernel digests are in `kernels.sha256`. The final mask spelling is the Linux spelling, `f`, `8` and `1` on this four-processor guest. After startup, the four Rach2 messages have effective masks 1, 2, 4 and 8 in allocation order.

Both architectures completed the first reads with 384 xHCI, 128 AHCI and 128 NVMe completions on processor 3. HDA took 176 interrupts there. The return reads added 384 xHCI, 128 AHCI and 128 NVMe interrupts on processor 0. USB fallback remained 0, every read and the concurrent reader returned 0, and both machines powered off. Linux also completed the reads and concurrent reader, spread its device interrupts and powered off. Its NVMe driver uses managed per-queue affinities, which reject ordinary affinity writes; the writable AHCI affinity moves, with Linux publishing the effective destination when the new interrupt completes its move. Read timings are retained in the outputs but are not compared: Linux's block cache and readahead issue fewer device commands.

Both kernels link, including after merging the milestone branch. These probes establish interrupt delivery and migration, not the Lenovo's GPU timing. The i915, RTL8168 and ath9k hardware paths await the prepared Lenovo step; their locks and vector readers were audited above.

## The Lenovo step

The manager's follow-up on task 4893 records 84-163's result: Linux also delivered all 1,009 to 1,017 i915 interrupts to processor 0 in four loops. At the same 200 MHz GPU clock Linux was no faster; its faster loops used a higher clock. This task therefore measures placement and delivery without claiming that spreading interrupts removes the older graphics timing difference.

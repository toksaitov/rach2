# 84-239: the KVM corpus's rows under the Mac's TCG

The release's Mac run at 08c7795ac failed `machine.kvm.unit-tests` and `machine.kvm.selftests` on x86-64. Its first report quoted `access-reduced-maxphyaddr` and `access_tracking_perf_test`, which were the first tests' progress lines, not failures; a028f553b made a failed case quote its result line. The case logs, copied from the Mac to the testing PC, give the failures: of the kvm-unit-tests, `emulator`, `hyperv_connections`, `la57`, `msr`, `msr64`, `xapic` and `xsave`; of the selftests, `rseq_test`, a skip where a pass was expected, and `x86_64/debug_regs`. The Mac's outer machine runs under TCG with SVM and one processor, so `hypervisor` holds there and `outer_kvm` does not, and the rows had their `pass` branch, which 84-33 set without a run under TCG.

Each failure follows QEMU's TCG, not Rach2's KVM: Linux's KVM leaves each of the paths below to the processor, or handles it as Rach2's does, so Linux as the host of the same machine gives the same result. Linux was not run under TCG for this task. The testing PC's drive D: had 47 GiB free, and building this clone's x86-64 GNU root, which `linux-corpus.sh` boots, can take some 35 GiB more, below the 40 GiB the build's preflight and `status.sh` hold as the floor. The two codes settle the six rows that follow QEMU's faults; the release's Mac run of the corpus is the proof of the rows.

QEMU's lines are Homebrew's 11.1.3, the Mac's, at the tag `v11.1.3`; QEMU 10.2.0's, read for the WRMSR, address, XSETBV and INT3 paths, has the same code there. Linux's are 6.12's. kvm-unit-tests' are the KVM layer's commit 5a221342a.

## The rows

* `msr` and `msr64`: `Expected #GP on WRMSR(MSR_FS_BASE, 0xaaaaaaaaaaaaaaaa), got vector 0`, and the log ends after `PASS: MSR_GS_BASE`, without its SUMMARY, when the same write to GS_BASE succeeds (`x86/msr.c:136`). TCG's WRMSR stores FS_BASE and GS_BASE with no canonical check (`target/i386/tcg/system/misc_helper.c:222-227`). Linux's SVM passes both MSRs through to the guest (`arch/x86/kvm/svm/svm.c:93-94`), as Rach2's does (`svm_msr_filter_changed`). The rows are `outer_kvm?pass:hypervisor?fail:pass`, a plain `fail` since the test has no SUMMARY line.
* `la57`: its canonical test without forced emulation finds no #GP for a non-canonical base loaded by LGDT, LIDT, LTR, LLDT or WRMSR (`x86/la57.c:239-248`), and the log ends after the write of GS_BASE. TCG's LGDT and LIDT store the base unchecked (`target/i386/tcg/translate.c:3029-3059`), as do LLDT and LTR the 64-bit descriptor's upper half (`target/i386/tcg/seg_helper.c:1326-1330`, `1383-1391`). Neither KVM intercepts a descriptor-table load. Inside a machine of KVM the test already failed, at its PCIDE assertion, under both hosts; the row is `hypervisor?fail:pass`.
* `emulator`: `non-canonical rsp-based access, should #SS(0), got #GP(0)` and the same for RBP (`x86/emulator64.c:430-436`), 2 of 151. TCG raises #GP for every non-canonical linear address, whatever the segment (`target/i386/tcg/system/excp_helper.c:589-598`). Neither KVM intercepts the access. The row is `outer_kvm?pass:hypervisor?fail:pass`.
* `xsave`: `Write XCR0=(FP|SSE) without XSAVE support - expect #UD` (`x86/xsave.c:220-221`), 1 of 386. The processor's #UD for CR4.OSXSAVE clear comes before the XSETBV intercept, but TCG checks the intercept first (`target/i386/tcg/translate.c:2906-2911`) and the #UD only in the helper (`target/i386/tcg/fpu_helper.c:3219-3222`). Linux's KVM intercepts XSETBV (`svm.c:1292`) and, as its comment says, leaves the #UD to the processor (`arch/x86/kvm/x86.c:1304-1311`), so it sets XCR0, as Rach2's `kvm_emul_xsetbv` does. The row is `outer_kvm?pass:hypervisor?fail:pass`.
* `x86_64/debug_regs`: `Unhandled exception '0x3'` in the guest at `sw_bp`, the INT3 that KVM_GUESTDBG_USE_SW_BP should turn into an exit. Both KVMs set the #BP exception intercept for it (Linux's `svm.c:1979`, Rach2's `svm.c` under KVM_PART_DEBUG), but TCG checks INT3 against the INTn intercept (`target/i386/tcg/excp_helper.c:100-106`, through `raise_interrupt`, line 120), which neither sets. The row is `outer_kvm?pass:hypervisor?fail:pass`.
* `rseq_test`: `1..0 # SKIP - Requirement not met: CPU_COUNT(&possible_mask) >= 2`. Under TCG etude gives the machine one processor, as `linux-corpus.sh -a tcg` gives Linux, so the program skips on either host. The row is `outer_kvm?pass:hypervisor?skip:pass`.
* `xapic`: `TMCCT should not be reset to TMICT value`, 1 of 44, the subtest whose result the cost of a report line's exits decides, which `x2apic`'s row already takes outside a machine of KVM (`x2apic` failed the same subtest in this run and was judged as expected). The row is `outer_kvm?excluded:pass|fail~TMCCT_should_not_be_reset_to_TMICT_value`.
* `hyperv_connections`: `receive pending message: 0/2`, as Linux 6.18 fails it under the testing PC's Hyper-V (`tests/kvm/ref/linux-unit-tests.txt`) and Linux 6.12 inside a machine of KVM (84-33). The row is `hypervisor?fail:pass`, which keeps the `pass` without a hypervisor. That branch is not yet seen to pass: in 81-3 Rach2 failed the same subtest on the Lenovo, when the row was `fail` everywhere, and Linux has not run the test there.

`unit-subset.list` takes the same rows, as its header says. `debug` and `eventinj` failed as their rows expect. QEMU's four faults are in [upstream.md](upstream.md).

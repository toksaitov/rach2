# 84-103: KVM's exit handling against Linux's under TCG

84-88 left KVM's handling of an exit as one of two causes of Rach2's slower round trip under TCG: a CPUID exit took 98,200 cycles from the exit to the next entry, and the profile showed the memory slots' rwsem and the MMU's lock taken on that path, each under a spinlock with interrupts off. This task profiled the exit path again, took the slots, the MSR filter and the PMU's event filter off every lock a guest's exit took, read the run loop's switch flag with interrupts on, and measured CPUID, VMCALL and IN beside Linux. Run back to back with the kernel before it, the change takes 7 to 8 percent off each of the three exits; beside Linux they remain 1.54 to 1.57 times Linux's. The rest is traced below, the largest part to the user copy's address-space lock, which 84-104 owns.

## The setting

As 84-88's: the testing PC, the KVM suite's machine under QEMU 10.2's TCG with SVM and one processor (`RACH2_QEMU_ACCEL=tcg ARCH=x86_64 RACH2_CASES=machine.kvm.unit-tests tests/run kvm`), and for the paired run `tests/kvm/linux-corpus.sh -a tcg -k unit unit-subset.list` beside it, Debian's Linux 6.12.107 as the KVM host of the same machine with one processor. A temporary `corpus.sh`, not committed, ran kvm-unit-tests' `vmexit.flat` five times for each of `cpuid`, `vmcall`, `inl_from_qemu`, `inl_from_kernel` and `outl_to_kernel`, and in Rach2 dumped `/sys/kernel/debug/kvm/exit_stats`, `bkl/calls` and the whole-kernel profile of `bkl/profile` around each test's five. Cycles are the TSC's at 4.19 GHz; the tables give medians of five.

The GNU root's `gnu-kvm` step, which the KVM suite needs, failed twice in this copy because snapshot.debian.org answered with status 200 and a body whose digest was not the pin's, once for an `InRelease` and once for a `Packages.xz`; the next fetches matched. The runs retried the step up to four times rather than change `fetch_debs.sh`, whose change would have rebuilt every GNU step.

## Where the time went

In the first run of the milestone branch's head, `exit_stats` split a CPUID exit as follows:

| Part | Cycles |
|---|---|
| from the exit's return to the next entry (`handle`) | 105,800 |
| of which the run loop's preparation (`prepare`) | 22,600 |
| the entry | 19,500 |
| the guest's run | 47,650 |
| the exit | 22,350 |

QEMU's TCG offers no next-RIP save (`TCG_SVM_FEATURES`, target/i386/cpu.c:986-987 in QEMU 10.2.0), so the VMCB has no next RIP, and to skip CPUID or VMMCALL the kernel decodes the instruction: four reads of the guest's page tables and one of the instruction, each through `gpa_rw_page`. Linux does the same work on the same machine: `__svm_skip_emulated_instruction` uses `next_rip` only with `nrips` and otherwise calls `kvm_emulate_instruction(vcpu, EMULTYPE_SKIP)` (arch/x86/kvm/svm/svm.c:384-393), whose fetch walks the guest's tables and reads guest memory as Rach2's does. The number of reads is the same on both hosts; what each read cost was not.

The profile samples on the tick, and a region with interrupts off is charged to the instruction that turns them on again. Of the samples of the CPUID loop's KVM_RUN outside the guest's run, 24% were the slots' and the MMU's locks, 31% the user copy's address-space lock and its prefault, and 10% the preparation. For each read of guest memory, `gpa_rw_page` took the slots' rwsem to read (`down_read` and `up_read`, each under the rwsem's spinlock with interrupts off), found the slot under `mmu_lock` with interrupts off, and copied from the caller's memory with `copy_from_user`, which took the address space's rwsem the same way and walked the page tables to prefault. Linux reads guest memory under `kvm->srcu`, held across the whole run but for the guest itself (arch/x86/kvm/x86.c:11071, 10919, 10950), finds the slot with no lock (`kvm_vcpu_gfn_to_memslot`, virt/kvm/kvm_main.c:2598-2628), and copies with `__copy_from_user` (`__kvm_read_guest_page`, kvm_main.c:3255-3267), which takes no lock unless it faults. The VMCALL loop, two CPUID exits and one VMMCALL an iteration, showed the same, 27% and 28%.

Two more locks were on every exit or entry. The MSR filter was read under the VM's `filter_lock` at each RDMSR and WRMSR exit, in SVM's fast path too, and the PMU's event filter under the same lock at each entry for each enabled counter; Linux reads both under `kvm->srcu` (`kvm_msr_allowed`, x86.c:1797-1810; arch/x86/kvm/pmu.c:434). The top of the run loop turned interrupts off at every entry to call `sched_take_preempt`, where Linux reads the flag with interrupts on (`__xfer_to_guest_mode_work_pending`, x86.c:11280, include/linux/entry-kvm.h:76-95).

## The changes

* The VM has a read side, Linux's `kvm->srcu`, in `slots.c`: two counts and a generation. A reader joins `srcu_readers[srcu_gen & 1]` with an atomic add, a full barrier, before it loads what it reads, and leaves with an atomic subtract, waking the wait queue when the count reaches 0 and a replacement waits. A replacement publishes the new pointer, counts itself in `srcu_waiting`, sends new readers to the other count by an exchange of the generation and waits for the old count to reach 0, then sends them back and waits for the other count. It waits for both counts by number, so two replacements may wait at once, each letting the big lock go meanwhile. A section takes no lock and turns no interrupts off, may begin with interrupts off, and nests.
* A lookup of a guest frame from a vCPU's run takes no lock. The slots' trees and fields still change under the big lock and `mmu_lock`, and each change is now also a write of a sequence count, odd while the change is under way; a reader walks the tree by frame, each link and field read once, and walks again when the count was odd or moved, or when the walk passed 48 nodes, which only a rotation in the middle of a change can make it do. A move, a change of flags and a deletion end the count's write before the zap, which may let `mmu_lock` go, and then wait for the read side before they free the slot or its log or return, so a reader that found the slot as it was finishes its copy and its mark of the dirty log first, as before. A new slot frees nothing and no longer waits. `kvm_slot_find_locked`, for a caller that holds `mmu_lock`, keeps the last slot found as a hint; Linux keeps one for each vCPU (kvm_main.c:2608-2626).
* The MSR filter and the PMU's event filter are published and freed after `kvm_srcu_synchronize`, as Linux's `kvm_vm_ioctl_set_msr_filter` and `kvm_vm_ioctl_set_pmu_event_filter` replace them with `rcu_replace_pointer` and wait with `synchronize_srcu` (x86.c:6866-6869, pmu.c:1027-1030). `filter_lock` is gone.
* The run loop reads `need_resched` with interrupts on and turns them off only to take the switch. The tick sets the flag and never switches a thread inside a call, so a flag set just after the read is taken at the next entry or the system call's exit.

The lock order in `rach2/sys/kvm/Readme.md` now has the read side in the place of the slots' readers' lock, and `mmu_lock` covers the slots' trees and the tables but is taken by no exit that changes no table. The host tests of the slots model the read side's wait as running the reader's rest, and count two waits for each change that waits.

## What is left

Each of these is a lock, an interrupts-off region or a poll on the exit path that Linux does not have.

* The user copy's address-space lock and prefault, 40% of the CPUID and VMCALL loops' samples outside the guest's run. Each of the five reads of a CPUID exit takes and releases the address space's rwsem, each step under its spinlock with interrupts off, and walks the page tables, where Linux's `__copy_from_user` takes nothing unless it faults (kvm_main.c:3267) and its `down_read` is one atomic add. 84-104 (#4789) makes copies take no address-space lock unless they fault and gives the rwsem its fast path; this task left `usercopy.c` and `mutex.c` to it.
* The run loop's preparation, 16,500 to 17,400 cycles an entry after this task. Linux's `vcpu_enter_guest` does its per-entry work only behind `kvm_request_pending` and `KVM_REQ_EVENT` (x86.c:10714-10873), and its timers are hrtimers that raise requests: the local APIC's is a flag `kvm_cpu_has_pending_timer` reads (x86.c:11269), the PIT's hrtimer callback queues the injection (arch/x86/kvm/i8254.c:268, 361), Hyper-V's synthetic timers raise `KVM_REQ_HV_STIMER` (arch/x86/kvm/hyperv.c:594), the PMU recomputes only at `KVM_REQ_PMU` (x86.c:10795) and the dirty ring is checked once at its request (x86.c:10720). Rach2 polls each source at each entry: the deferred irqfds, the PIT, NMIs, the local APIC's timer, Hyper-V's timers and pending events (`kvm_lapic_prepare`), the master clock and the kvmclock (`kvm_clock_prepare`), the steal time, every PMU counter's run mask, and the dirty ring three times. Each poll is already behind a test that takes no lock and reads the clock only while a timer is armed; what is left is the tests themselves. Turning them into requests changes the local APIC, the PIT, Hyper-V's timers, the clock and the PMU together, the size of a milestone.
* The vCPU's mutex, taken and released at each KVM_RUN, which every exit that QEMU answers pays once: `mutex_lock_killable` and `mutex_unlock` run under the mutex's spinlock with interrupts off, where Linux's take and release are one compare-and-exchange each on the fast path (kernel/locking/mutex.c `__mutex_trylock_fast`, `__mutex_unlock_fast`). It is the same change to `mutex.c` as 84-104's rwsem fast paths.
* The descriptor lookup of each KVM_RUN under the table's spinlock (`fd_get`), which 84-104 also owns.
* The entry and the exit, 17,800 and 20,000 cycles for a CPUID exit, were not split on Linux, so no difference there is shown. The guest's run, 42,000, is QEMU's emulation of VMRUN, the guest's loop and #VMEXIT, the same work on both hosts.
* IN answered by QEMU spends 147,000 of its 267,000 cycles in the kernel's handling, the entry, the guest and the exit, by `exit_stats`, and the rest in QEMU and the system call's return and entry, where the descriptor lookup and the vCPU's mutex above are.

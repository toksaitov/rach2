# 84-265s: why machine.virgl.webgl-chromium-webgl2-03 failed in the release's rerun

The release's rerun at f7bd405d9 and loop a's run at the branch head both failed `machine.virgl.webgl-chromium-webgl2-03` on x86_64 with two pages worse than Debian's: `deqp/functional/gles3/fboinvalidate/whole.html`, 3,451,743 subtests passed against the reference's 3,451,744, and `target.html`, 5,917,078 against 5,917,082. Both pages draw on a GL context that the host's virglrenderer has already refused, in the Debian guest as on Rach2, and which of their cases pass by chance changes from run to run in the Debian guest. Rach2 has no fault to fix; the two pages are named in `tests/graphics/runners/webgl-virgl.flakes`.

## What the evidence shows

* Each page counts one subtest for each of its deqp cases, besides the millions of the reference renderer's own. Here `whole.html` failed all 19 of its cases and `target.html` all 27; the reference failed 18 and 23. The two Rach2 runs gave the same 1,372 failed subtests in the chunk and the same failed cases on pages 949 to 961, in the first run and the rerun of each.
* The failures of the chunk begin at page 949, `fbocolorbuffer/tex3d_01.html`, whose first case passes and whose later cases fail, and 49 of the 51 framebuffer and fragment output pages from there to 999 fail, all but `framebufferblit/rect_05.html` and `rect_06.html`, in the reference and on Rach2 alike. QEMU's standard error in both Rach2 runs, and in the Debian guest, holds `vrend_check_no_error: context error reported 5 "chromium" Unknown 1281` and `vrend_decode_ctx_submit_cmd: context error reported 5 "chromium" Illegal command buffer 329729` once for each browser: virglrenderer runs none of that context's commands after the GL error. The fault is recorded in [upstream.md](upstream.md#virgl-on-mesas-d3d12-driver-refuses-chromiums-context-on-a-webgl-2-page-of-3d-texture-framebuffers).
* With `webgl.html` keeping each failed case's last `debug` line, a diagnostic change not committed, the Debian guest's run of pages 949 to 961 (`-k 13 73`) shows `whole.html`'s cases differing from their references by 1,802 to 55,976 against the fuzzy comparison's threshold of 0.05: images not drawn, not near misses.
* That run, on 2026-11-15 under the same QEMU, virglrenderer and host Mesa as the reference's of 2026-11-11 (the host's packages last changed on 2026-10-31), gave on each of its two runs exactly Rach2's line for every page from 949 to 961, `whole.html` failing 19 cases and `target.html` 27. The reference's 18 and 23 are therefore one of the outcomes that the Debian guest itself gives.
* The Debian guest's run of pages 950 to 974 (`-k 25 38`), which starts after page 949, passed all 25 pages, `whole.html` and `target.html` among them, with no context error.
* Both Rach2 runs drew beside other virgl guests of the release; the reference was taken with none. The context error comes at the same page in both, so the load does not start it.

## What changed

`webgl-virgl.flakes` names every case of `fboinvalidate/whole.html` and `target.html`, which the judge then counts as passed in the virgl cases. With it, `judge.py webgl` passes both kept Rach2 runs, printing 19 and 27 failed subtests named. The chunk's other 47 failing pages, from 949 to 999, matched the reference in every run so far and stay judged; nothing wider was changed, by the owner's freeze.

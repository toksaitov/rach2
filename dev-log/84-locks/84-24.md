# 84-24: an inherited big lock in DRM

## Results

The big lock came from the descriptor wrapper before DRM dispatch. `open_device_node` keeps the file-system inode in `open_file.dev_mnt` (`syscall_fs.c:3769-3780`). `file_ops_unlocked` refuses that description even when its device operations set `FILE_OPS_UNLOCKED` (`syscall_fs.c:5586-5595`), so `ioctl_fd` takes the big lock (`syscall.c:2723-2728`). DRM honored `DRM_UNLOCKED` only for its own take. The i915 flags were already right: EXECBUFFER2 and MADVISE both carried it. The Lenovo's original calls files, read from `build/runs/t3984/a` of the main clone, have 59,782 holds in 59,583 EXECBUFFER2 calls for 0 A.D., and 267,094 holds in 267,081 MADVISE calls.

`drm_ioctl` now gives back an inherited depth for an unlocked row, before its copies, and restores it after its copy out or any error. Both depth changes mask interrupts as `bkl_drop` and `bkl_take` require. Master permission still takes the big lock; a KMS row still needs `DRIVER_KMS_UNLOCKED` to give it back. The device, file and description remain held by the caller throughout. The dispatcher is `drm.c`; this tree has no `drm_ioctl.c`.

### The locks and Linux

Linux references below are the local 6.12.115 tree at `build/research/linux-6.12.115-full` of the main clone. No upstream fault was found.

* Object references and handles: Rach2's DRM handle table and atomic object references protect `eb_lookup`. Linux's `gem/i915_gem_execbuffer.c:941-976` looks up the VMAs, then `eb_lock_vmas`, lines 980-995, takes each object's ww lock. Rach2's existing GEM mutex protects placement, bindings, pages, relocations and parsing in `eb_locked`; it is shared by all of the device's submissions, rather than Linux's finer object locks. This task adds no lock class and changes no row of the lock table.
* Contexts: `i915_gem_context_lookup` holds the file's context-list mutex while it finds or finalizes a context and acquires its reference. The list lock is given back before the GEM lock. Linux's `eb_select_context`, execbuffer lines 823-836, gets a context reference; its LUT insert takes `ctx->lut_mutex` at lines 853-863. Rach2's context state and its use by a submission are protected by the GEM lock, with engine maps held by reference.
* Requests: Rach2 holds the GEM mutex from `eb_submit`'s request creation through `i915_request_add`, and takes the engine spinlock for the timeline, ring and publication. Linux's `eb_pin_timeline`, execbuffer lines 2502-2547, uses the context timeline mutex, and its request-add path at lines 3068-3108 holds that mutex until publication. Rach2's existing wider GEM mutex provides that exclusion; its GPU and fence waits drop it and retry the state they found before sleeping.
* MADVISE is `0xc00c6466`, not SET_DOMAIN. Rach2 holds the object's reservation mutex while changing advice, and takes the GEM mutex before a purge, rechecking under the reservation. Linux's `i915_gem.c:1029-1100` takes the object's lock at 1049 and gives it back at 1099. Rach2's purge and a GTT eviction still take the big lock for `paging_zap_device`'s global address-space walk. The first submission may take it to create the worker, a userptr release for notifier unregister, and allocation pressure for the common reclaim path. These existing helpers were not made unlocked by removing their guards: the other memory task owns the page-fault path and the common memory interfaces.

### Proof

Both kernels linked with `make -j8 ARCH=i686 rach2` and `make -j8 ARCH=x86_64 rach2`. Build output is under this clone's `build/runs/4657-*-build*.log`. The x86-64 link prints the existing ACPICA missing `.note.GNU-stack` warning. The new `drm_core_hosttest` rows, selected alone by `inherited`, passed under ASan and UBSan with both architecture headers. They enter at depths one and two, check copies and handlers without the inherited lock, check restored depths on success, copy faults, allocation and permission failures, and keep the inherited lock on locked rows and KMS without opt-in. The same new rows against the original dispatcher failed 14 assertions. No suite or other host rows ran.

A short manual QEMU boot used the real i915 driver over EDU's fake chip, four TCG processors and 512 MiB. A minimal RAM root mounted tmpfs and made its own render device nodes there, which exercises the inode-retaining path above. After one warm submission it reset the counters, enabled whole-kernel profiling and ran 8,192 render submissions with relocations, each followed by MADVISE/WILLNEED, then read the counters and powered off. It used the same load and root for both kernels, whose only source difference was this dispatch change. `rach2.tscreliable` enabled TSC calibration in TCG. Evidence, the exact load source, root manifest, boot command and both kernels are in `build/runs/4657` of this clone. `bklread.sh` named each profile with its own `kernel.debug`.

The remaining per-call holds are the wrapper before the dispatcher drops its lock and after it restores it. Submissions' held time fell 96.9%; their call wall time rose from 403,900 to 433,530 us in this short TCG run. The load has almost no user work, so it does not measure the games' system/user ratio. It establishes the removal of the inherited hold, not frame performance or the native games' Done. The whole-kernel profile still samples unlocked submission work; its share is not a held-time share.

QEMU's actual game harness uses virtio-gpu, whose submission rows still lack `DRM_UNLOCKED`. Its game timings cannot measure this i915 path, and the fake chip cannot render a game. No claim about the games' Done follows from this load. A few-minute native step is therefore prepared on the task; a boot of this newly unlocked device path waits for the manager's go.

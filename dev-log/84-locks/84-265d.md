# 84-265d: the virtio network driver's link, a rebind's MTU and the interface's parent

Codex's review of the virtio network driver ([84-264g](84-264g.md)) found three faults in it and one row that held a difference from Linux. This task fixes the four, each with a row that fails on the code before it.

## What changed

* The first reading of the link could undo a newer one. The bring-up installed the configuration's callback and then read the status word with nothing held, so a link-up interrupt that arrived after the word was read and before the result was kept had its reading replaced by the older one, and the link stayed down until the next change. `vnet_link_read` now reads the configuration and keeps the result in one step under `net_lock`, with interrupts off, on a transport whose configuration reads take no lock; the interrupt is taken after the bracket and its reading stands. Linux has the same order from its one config work.
* A device with no interrupt never read its link again. Its `poll` reaped the two queues only, so a device started with its cable out never sent once the cable was in. The poll now reads the link once in `VNET_LINK_POLLS` polls, 50, a fifth of a second of ticks. It reads the status word and not the configuration's generation: virtio 1.2, 4.1.4.3.1 requires the generation to change only after a changed field has been read, so on a device that does as the note there advises, a generation alone would never show the change.
* A bind kept the largest MTU of the device before it. `vnet_interface` now gives the interface the table, the address and the limit of the device as it is at the probe and at each bind, before `up` is set and the device is told of a buffer. A limit below the interface's MTU brings the MTU down to it, with a line in the log; a larger limit or none leaves the MTU as it was, since the interface, which stays across an unbind, keeps what its administrator set.
* The interface's `device` in `/sys/class/net` led to the PCI function. It is now a link the driver adds below the interface's directory to the virtio device, `/sys/devices/pci0000:00/0000:BB:DD.F/virtioN`, which is the parent Linux's virtnet_probe gives with SET_NETDEV_DEV; the interface's `pci_key` stays -1, since the fixed link to the function would stand in the new one's place. The link goes when the device is stopped or unbound and comes back at a bind. Where the virtio device has no directory the function is the parent, as before.

## Tests

* `tests/host/virtio_net_hosttest.c` has a row for each of the first three. Its model now holds a configuration interrupt raised inside a `net_lock` bracket to the bracket's end, as a processor with interrupts off does, and can bring the link up in the middle of a read of the status word. `row_link_race` starts a device with the link down and has it come up under the first read; `row_polled` starts a polled device with its cable out, puts it in and pulls it out, and counts that the polls short of the interval read nothing; `row_rebind_mtu` binds a function again with 1300, 1450 and no largest MTU after 1400. The bring-up and rebind rows check the `/sys` link through stubs of `sysfs_anchor`, `sysfs_add_link` and `sysfs_remove`.
* `vnetprobe`'s `bus` row now requires the interface's `device` link to read `../../../devices/pci0000:00/0000:BB:DD.F/virtioN` for the device it found on the bus, with the device's own `device` file read through it; `no-carrier` requires the link gone, and `bind` requires it back.
* `procprobe`'s `net-class-device` row reads the vendor of the function the link names. For 0x1af4 it requires the link to end in `/virtioN`; for any other vendor it requires the link to end at the function.

## What was run

On the Mac, QEMU 11.1.3 under TCG, at the task's head.

* `virtio_net_hosttest` passes. Built against the driver before this task it fails twelve checks: the first read's race, the polled device's cable in and out, the four of the rebind's MTU, and the `/sys` link's.
* `tests/run virtionet` passes on i686 and x86-64, 43 assertions each.
* `procprobe`, run by hand in the test image, passes `net-class-device` on virtio-net-pci on both architectures, and on the RTL8139 and the e1000 on x86-64.
* Both kernels link.

## Not run

No device without an interrupt can be made in QEMU, whose virtio-net-pci has a line when it has no vectors, so the poll's reading of the link is proved by the host row alone.

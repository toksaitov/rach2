# 84-266e: tracing the GPU page fault of webgl2-06's chunk 6

The host's GPU page fault under `machine.virgl.webgl-chromium-webgl2-06` ([84-266a](84-266a.md)) left no address on the testing PC, so the command behind it can be named only by a run that records the fault as it happens. [84-266e/](84-266e/) holds the tool for that run.

## What the record keeps

* Windows' events 153 of nvlddmkm at 04:06:48, 04:39:38 and 05:46:12 on 2026-11-15 carry the same data, "Error occurred on GPUID: 100" and the words `0,0,0,0,2,0,48,0,0,0,0,0,153,0,...`, and no address or engine.
* The NVIDIA journal's Xid 31 record in the 04:39 live dump ([84-266a/watchdog-0439.txt](84-266a/watchdog-0439.txt)) holds the Xid and the owning process and no address; no string of the dump names a fault, an MMU or an engine. The 05:46:12 error, of loop d's Debian guest on 621.24 (#5178), left no live dump.
* QEMU ran without tracing, and Mesa's d3d12 driver turns on none of D3D12's device-removed extended data (DRED), so neither recorded the operation or the allocation at fault.

## The tool

WSL's `libd3d12core.so` carries DRED: auto-breadcrumbs, which keep each command list's operations and how far the GPU got through them, and page-fault data, which keeps the faulting GPU address and the allocations that lived or were recently freed at it. A process turns them on before it makes its device, which Mesa does not do.

`dredshim.c` is a `libd3d12.so` that Mesa loads in place of WSL's when its directory leads `LD_LIBRARY_PATH`; it forwards every export to `/usr/lib/wsl/lib/libd3d12.so`. When Mesa takes the device factory it forces auto-breadcrumbs, breadcrumb contexts and page-fault data on through the factory's DRED settings, and hooks the factory's `CreateDevice`. On each device it names every resource, heap and query heap Mesa makes, `res#N committed dim3 640x480x1 mips1 fmt28 flags0x1` and so on, with a sequence number, the kind of creation and the description, so that DRED's allocation lists name what Mesa made; a thread reads `GetDeviceRemovedReason` every 20 ms and at the removal writes the reason, the page fault's address and flags, the allocations at it, existing and freed, and each command list the GPU had not finished, with its last 24 operations before the one it stopped at and 8 after, to `DRED_SHIM_OUT`, its lines stamped in UTC. `qemu-system-x86_64` is a wrapper that runs QEMU with the shim, its log under `DRED_DIR` named by QEMU's PID, and the `virtio_gpu_cmd_*` trace events, timestamped, in `DRED_DIR/trace.PID.log`; it leads `PATH` for `debian-ref.sh`, which runs QEMU by name. `build.sh` builds the shim against a checkout of Microsoft's DirectX-Headers:

    git clone --depth 1 https://github.com/microsoft/DirectX-Headers.git build/tmp/dxh
    sh dev-log/84-locks/84-266e/build.sh build/tmp/dxh build/tmp/dred/shim
    PATH=$PWD/dev-log/84-locks/84-266e:$PATH DRED_SHIM=$PWD/build/tmp/dred/shim \
        DRED_DIR=$PWD/build/tmp/dred sh tests/graphics/runners/debian.sh webgl ...

Checked on the testing PC with a surfaceless EGL context on Mesa's d3d12 over the RTX 4080 SUPER (`MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA`): the factory accepted DRED's settings, the device came through the hooked `CreateDevice`, and a `RemoveDevice` a second later was found within 20 ms and written with reason 0x887a0005, DXGI_ERROR_DEVICE_REMOVED, no page fault and no unfinished list, as a removal by the program itself should give. Whether WSL passes a real page fault's address up to DRED is known only once one is caught.

# 84-265q: why machine.virgl.piglit-16 failed in the release's rerun

The release's rerun failed `machine.virgl.piglit-16` on x86_64 with one test worse than Debian's: `spec@!opengl 1.1@copypixels-draw-sync`, fail here and pass in the reference. Every other of its 3,534 results matched. The host stopped answering the guest's virtio-gpu commands for some 15 s, and Linux would have failed the test the same way. Rach2 has no fault to fix, and the test stays judged.

## What the evidence shows

The case's kept workspace holds piglit's results, the run's record and the host's record at the case's end.

* The test is small: it clears, copies pixels with glCopyPixels, draws one rectangle and probes it. It ran for 15.21 s, from 21:22:47 to 21:23:03 UTC on 2026-11-14. Its standard error is Mesa's "waiting got error - 16, slow gpu or hang?" and its probe read 0 0 0 0 where it expected 0 255 0 0.
* Mesa prints that line when `DRM_IOCTL_VIRTGPU_WAIT` fails (`virgl_drm_resource_wait`, `src/gallium/winsys/virgl/drm/virgl_drm_winsys.c`). Rach2's `vgpu_wait_ioctl` (`rach2/sys/drm/virtio_gpu_fence.c`) returns EBUSY after 15 s, as Linux's `virtio_gpu_wait_ioctl` does. Mesa then maps the buffer anyway.
* QEMU runs a TRANSFER_FROM_HOST_3D command when it takes it from the queue: virglrenderer reads the pixels back into the guest's pages before the command is answered. The black probe therefore means QEMU had not yet run the readback 15 s after the guest queued it. The transfer goes through `vgpu_cmd_send`, which notifies the device, so the command was not left waiting for a notify.
* The test just before it in time, `shaders@glsl-fs-texturecube-2`, took 12.12 s and passed; the run's other tests took about 0.3 s each. A fence the host answered after 12 s shows the host slow from 21:22:32. A lost interrupt in the guest would end each wait at 15 s, never at 12 s, since no other process drew meanwhile to bring an answer that signals the earlier fences.
* After the failing test ended, piglit started the next test 10.78 s later. That gap is 68 times the next longest between two tests in the run, 0.16 s.
* The guest's console has no kernel message after its boot. No command waited in the kernel went unanswered for 5 s, which `cmd_wait` would have logged.
* The host's load was 17.6 to 22.0 on its 32 threads. At 21:22:01, 46 s before the failing test, another account claimed the host for a manual run of `machine.d3dvenus.vkd3d-5`: a Venus guest with 8 CPUs and 17 GiB, whose unit compiles 512 pipelines on the host's lavapipe. By the case's end, two more virgl guests drew on the same D3D12 adapter: the release's `machine.virgl.piglit-quick-gl` and another account's `machine.virgl.webgl-chromium-webgl2-03`. The Debian reference was taken with no other guest drawing beside it ([ref/virgl-wsl](../../tests/graphics/ref/virgl-wsl/Readme.md)).

## Why it is not named a flake

Debian's reference passed the test, and no kept Debian run shows it failing. The test checks that a copy waits for earlier rendering, which is the ordering a guest fault would break. Leaving it unjudged would hide such a fault. It stays judged, and the release's second rerun proves the case.

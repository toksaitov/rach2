# 84-265r: what lost the guest in machine.virgl.webgl-chromium-webgl2-06

The release's rerun failed `machine.virgl.webgl-chromium-webgl2-06` on x86_64 with "the machine or its transport was lost". QEMU died of a segmentation fault in Mesa's D3D12 driver on the testing PC as the runner started a new browser, 164 s after the NVIDIA driver reset a GPU engine and Direct3D removed the device under it ([84-265x](84-265x.md)). The guest did not crash or hang, and Rach2 has no fault to fix. The reset follows Chromium's run of dEQP's 29 transform feedback pages some 75 pages earlier, in Debian's guest as in Rach2's, and the case now leaves those pages out.

## What the evidence shows

The case's kept workspace holds the guest's console, QEMU's standard error, the QMP capture and the guest disk's overlay; the testing PC's kernel log holds QEMU's end.

* The guest booted at 03:58:44 UTC+6 on 2026-11-15, by its own clock line. Its console ends with the runner's frame "webgl: browser: done after 250 pages": Chromium had run the chunk's 250 pages and `run_pages` in `tests/graphics/runners/webgl.sh` had stopped it. The next step of `chunk` starts a new Chromium for the pages that did not pass. The console has no kernel message after the boot's, no panic, fault or lockup.
* QEMU's standard error, kept whole, is the one line "D3D12: Removing Device.". Microsoft's `/usr/lib/wsl/lib/libd3d12core.so` prints it; Mesa holds no such string. The device was removed at 04:06:48, 164 s before the fault, and the guest drew on with black readbacks until then ([84-265x](84-265x.md)). A run that ends with no removal prints nothing there (`dev-log/77-vgpu/virgl-host/copy-rgb9e5.txt`).
* The QMP capture reads `not sent` for all three commands: the case found the machine no longer running when it came to collect, so QEMU had ended before the case's cleanup.
* The testing PC's kernel logged, at uptime 95179.21 s, 04:09:32 UTC+6:

      qemu-system-x86[4497]: segfault at 0 ip 000072c9da13d75d sp 00007fff7fc17400 error 4 in libgallium-26.0.8-1ubuntu0.3.so[f3d75d,72c9d92dc000+19a0000]
      qemu-system-x86_64: qemu-system-x86: potentially unexpected fatal signal 11.

  PID 4497 ran as UID 1002, `ghrunner`, the release's runner, and it was the only QEMU to fault in that hour. At 95178.91 s, 0.3 s before, the kernel logged an interrupted GPU wait, `dxgkio_wait_sync_object_cpu: wait_completion_interruptible: -512`. At 04:00:40 and 04:05:30 it logged `dxgkio_is_feature_enabled: Ioctl failed: -22`, the line it logged at 03:58:41, 3 s before this guest's clock line, as this case's QEMU opened the adapter: other programs opened the D3D12 adapter while the case ran.
* The faulting instruction, at offset 0xf3d75d of Ubuntu's libgallium (build ID b089ec2f62ded38e9327502246aa4ccfb7929b24), is `mov (%r14),%rax` with R14 0. The code before it divides the clock by 10^6, subtracts the member at offset 0x30 of the structure in RBX and stores the result at offset 0x10 of the structure in RSI; the code after it writes RAX and R14 into that structure and RSI into RAX's second word. That is `pb_cache_add_buffer` in Mesa 26.0.8's `src/gallium/auxiliary/pipebuffer/pb_cache.c:132-133`: `entry->start_ms = time_get_ms(mgr)`, where 0x30 is `msecs_base_time` in `struct pb_cache` and 0x10 is `start_ms` in `struct pb_cache_entry`, then `list_addtail(&entry->head, cache)`, which reads `cache->prev` through `cache = &mgr->buckets[entry->bucket_index]`. The buckets pointer was NULL.
* Only `pb_cache_deinit` (`pb_cache.c:341-347`) sets `buckets` to NULL, called from `pb_cache_manager_destroy` (`pb_bufmgr_cache.c:267-273`), which also frees the manager. The D3D12 driver destroys its cache managers only in `d3d12_deinit_screen` (`d3d12_screen.cpp:625-636`), which runs when the screen is destroyed and when `d3d12_context_create` (`d3d12_context_common.cpp:502-509`) finds the device removed and resets the screen in place. QEMU was running a guest, not ending. A new GL context made after the removal therefore reset the screen, and a buffer made before the reset, released afterwards through `pb_cache_buffer_destroy` (`pb_bufmgr_cache.c:108-120`), went back to its freed cache manager.

## What removed the device

A GPU engine reset, the NVIDIA driver's event 153 at 04:06:48.267, as page 1662 of the chunk ended; which command faulted is not traced ([84-265x](84-265x.md), [84-266a](84-266a.md)). It is the fault that `dev-log/77-vgpu/upstream.md` records as "Mesa's D3D12 driver draws on after its device is removed and faults", whose evidence includes the same case: a Chromium run of WebGL 2.0.1 ended QEMU after 67 minutes as it started the browser that runs the failed pages of its seventh chunk, chunk 06, again, while another guest drew beside it. A guest's command stream reaches Direct3D only through the host's virglrenderer and Mesa, which must refuse what the device cannot run; whatever this guest sent, the removal and the fault after it are the host's. The upstream entry for the fault this run traced is in [upstream.md](upstream.md#mesas-d3d12-driver-returns-buffers-to-the-cache-managers-it-freed-when-it-reset-the-screen-after-a-device-removal).

## The pages that lead to the removal

The same crash came again in loop a's run at 04:42, so the case could not pass by being run again. Loops m, v and z read both runs' guest disks and the Windows logs (84-265x, 84-265z, 84-266a): the device went at a change of page between pages 1659 and 1663, some 160 s before the crash, and every page after it read back black. What follows was run from this task's worktree at the milestone head cc8b45c24, in the Debian reference guest on the `virgl` profile with 8 CPUs, under NVIDIA's driver 621.24, one guest of this task at a time with other accounts' guests running beside it, as each record's ledger lines show. The times are UTC+6 on 2026-11-15; the Windows events were read with `Get-WinEvent` from WSL.

* Pages 1658 and 1659, `readpixel.html` and `samplerobject.html`, alone (`-k 2 829`, at 05:36): both pass with the reference's counts and Windows logged no event. The page at the change does not remove the device by itself. Output in [84-265r/debian-1658-1659](84-265r/debian-1658-1659).
* Chunk 6 whole (`06`, from 05:37): Windows logged nvlddmkm event 153, the engine reset, at 05:46:12; the runner printed "webgl: browser: done after 250 pages", QEMU printed "D3D12: Removing Device." and "Pure virtual function called!", and the host's kernel logged `potentially unexpected fatal signal 6` for this account's QEMU at 05:48:48, as the browser for the failed pages started. Linux's guest ends exactly as Rach2's two runs did; the guest's work directory went with it. The runner's lines are in [84-265r/debian-06/runner](84-265r/debian-06/runner).
* Pages 1600 to 1699 (`-k 100 16`, at 05:50): the same three pages fail as in the reference, the others pass, the browser for the failed pages ran, and Windows logged no event. The pages that lead to the removal come before 1600. Output in [84-265r/debian-1600-1699](84-265r/debian-1600-1699).
* Chunk 6 whole without the 29 pages of `deqp/functional/gles3/transformfeedback/`, 1557 to 1585 (`06` with them added to the omit file, from 05:57): both browsers ran to their ends, QEMU lived and Windows logged no event. Every page passes or fails as in the reference, and the seven pages after 1585 that fail in the reference too pass more of their subtests: `shadercommonfunction.html` 36,507 with 130 failed, against the reference's 36,392 with 245 (Firefox's reference fails the same 130), `shaderpackingfunction.html` 490 with 3 failed against 473 with 20, and `drawingbuffer-storage-test.html`, `ext-render-snorm.html`, `ext-texture-norm16.html`, `oes-draw-buffers-indexed.html` and `webgl-clip-cull-distance.html` likewise. Output in [84-265r/debian-06-no-tf](84-265r/debian-06-no-tf).

So Chromium's transform feedback pages leave the host's driver in a state in which it faults some 75 pages later, and they lowered later pages' counts in Debian's reference too, under 621.01, where its reset came only in the last browser. 17 of the 29 fail in every run, Debian's and Rach2's alike, with "Result comparison failed". Which of them, and which host call, is not traced; the upstream entry is in [upstream.md](upstream.md#after-chromiums-transform-feedback-pages-the-host-gpus-engine-is-reset-pages-later).

## What changed

* `tests/graphics/runners/webgl-virgl.omit` leaves `deqp/functional/gles3/transformfeedback/` out of Chromium's runs in both guests, as it leaves the RGB9_E5 uploads out.
* The reference's `chromium-2.0.1-06.pages` first had those 29 lines made `omitted` by hand, and chunk 6's line in `results` and the Readme's totals counted again from it, since `judge.py webgl` requires a page omitted on one side to be omitted on the other; `judge.py webgl` passed the Debian run without the pages against that edited reference: "judge: result: pass webgl 250 pages, 0 worse than Debian's". That held a Rach2 run to the lower counts that the transform feedback pages caused in the run of 2026-11-11.
* Task 84-266e then made the Debian run without the pages, [84-265r/debian-06-no-tf](84-265r/debian-06-no-tf), chunk 6's reference whole: its pages file, its `results` line as `results`' chunk 6 line, and its `record` as `record-06`, with the Readme's totals counted again. It ran the list `webgl-virgl.omit` now holds, page for page. A Rach2 run of chunk 6 is now held to Linux's counts without the transform feedback pages, under the driver the testing PC runs.

Rach2 has no fault here: its guest ran every page before the removal as Debian's did, and Debian's guest is lost the same way.

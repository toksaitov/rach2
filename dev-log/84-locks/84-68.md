# 84-68: an ext2 file's data read straight into the file page cache's frames

Task 84-68 (#4747) reads an ext2 regular file's data blocks into the file page cache's frames by DMA, past the buffer cache, as Linux's `mpage_readahead` and `do_mpage_readpage` (fs/mpage.c) build a bio on the folios themselves. It closes the gap 77-11b left in the first round after boot ([77-11b's What remains](../77-vgpu/77-11b.md#what-remains)): each block a file read was copied twice, from the buffer cache's staging read into a buffer and from the buffer into the page, and held twice. In three cycles against Debian in QEMU on the testing PC, the first round after boot now takes 2.56 to 3.18 s of system time against Debian's 3.60 to 4.51 s and the old kernel's 3.90 to 4.96 s, and reads 58,168 to 58,252 KiB from the disk against Debian's 109,136 and the old kernel's 74,620 to 178,168. Linux references are to its mainline tree by function name; no Linux tree was at hand to give line numbers. No upstream fault was found.

## What changed

The block layer. A read request may carry the caller's page frames in place of a buffer of its own (`block_read_frames`, `rach2/sys/block/request.c`), as a Linux bio carries its `bio_vec`s: frame i gets sectors 8i to 8i+7, and the request holds a reference on each frame until it ends, so a request given up on and quarantined cannot leave a frame to be reused under a late DMA. A device that sets `BLOCK_FRAMES` takes the frames into its transfer: AHCI writes one PRDT entry a frame, NVMe a PRP list of the frames. AHCI sets the flag when its controller addresses 64 bits or the kernel is i686, whose frames lie below 4 GiB; NVMe always. For any other device (ATA, USB disks, loop devices), or a caller that cannot sleep, the request reads into a heap buffer and copies into the frames, so every device takes the call.

The file system. `vfs_ops` gained `read_frames`, a read of whole pages of a file into given frames, which only ext2 provides. `ext2_read_frames` (`rach2/sys/fs/ext2.c`) holds the node's lock from the look at a page's blocks to the end of their transfer, so that no write, truncation or free changes a block in between, as Linux's locked folio holds off truncation until its read ends. For each page it plans one of three things: a hole, which is zeroed; a page whose bytes may be newer elsewhere than on the disk, which `ext2_read` reads as before; or the page's first sector. Pages whose sectors follow each other go to the device in one transfer, up to 32 pages a plan, and the bytes past the file's size are cleared.

Coherence with the buffer cache. A file's written data goes through the write batch and then the buffer cache, so the disk's bytes of a data block that neither holds are the file's. A page whose block the batch has an image of, or the buffer cache holds clean or dirty, is read through `ext2_read`, from them; Linux's `do_mpage_readpage` likewise gives a page that already has buffers to `block_read_full_folio`. The batch is looked at under the big lock, which a writer holds while the batch has images (`batch_guard`), and only across the look. Metadata, directories and symbolic links are read through the buffer cache as before. Writes are unchanged.

Blocks smaller than a page. A page of 1 KiB or 2 KiB blocks that are one run on the device goes straight into its frame too; one whose blocks are mixed holes and data, or not one run, which happens beside each indirect block, is read through `ext2_read`, where Linux's `do_mpage_readpage` gives it to `block_read_full_folio`. Rach2 mounts such a volume read-only, so its pages have no dirty buffers to be coherent with.

The callers. read(2) reads its readahead window, with Linux's initial size from `get_init_ra_size` (mm/readahead.c) at a file's start and 32 pages for a read that continues where the last ended (the open file's `ra_next`), into the file page cache's frames in one call (`fc_read_window`, `rach2/sys/mm/filecache.c`). A read fault's read-around (`disk_read_around`, `rach2/sys/mm/filemap.c`), 77-11b's window of Linux's `do_sync_mmap_readahead`, now reads the pages the file page cache lacks in runs through the same call, in place of one `ext2_read` a page. A file system without `read_frames` is read a page at a time as before.

## Correctness

77-11b's probe, `check.py` and `privatefilemusl`, ran on the x86-64 kernel in two boots of `gnu-test.disk` on a copy-on-write overlay, once on AHCI and once on NVMe. The first boot digests five large files of the root (`libstdc++.so.6.0.36`, `libpython3.14.so.1.0`, `libcrypto.so.4`, `/usr/bin/js` and `libc.a`) by read(2) in chunks of 4,096, 1 MiB and 777 bytes and by a mapping touched in random page order, against the host's digests; writes a 5 MiB file, overwrites pieces of it across page and block boundaries and appends to it; stores through a shared mapping and reads the stores by read(2); truncates a file that had been read and grows it again past a hole; and checks each both ways. `privatefilemusl` checks private and shared file mappings on `/dev/shm` and on ext2. The second boot reads the five files first by a mapping and then by read(2), cold, and the written files both ways. Every check passed on both devices.

A third probe mounted a 300 MiB volume of 1 KiB blocks, made by the host's `mke2fs -b 1024 -d` with a 7 MiB file, a sparse file with holes inside pages, libc and 40 small files: 172 digests by read(2) and mapping in the first boot and 86 cold in the second all matched. Reading the 7 MiB file grew the buffer cache by 5,432 KiB against the old kernel's 7,576, and faulting in libc's pages by 1,832 KiB against 9,404; what remains there is the indirect blocks, each of whose misses reads a 128 KiB run, and the pages beside them.

Both kernels link at each commit, and at the landed head, on the milestone branch's 26 commits since `ae35cd8f8`, where the x86-64 kernel is 3,457,136 bytes, 737,168 under 4,194,304, and the i686 kernel 3,008,724. The figures above are the measured branch's, before that rebase; nothing was measured again on the landed head. No i686 boot ran; i686 takes the same paths with its frames below 4 GiB.

## What remains

The old kernel's read volume in the first round is either about 75,000 KiB or about 177,000, and this task's was 140,596 KiB once, in the loaded first cycle; no measurement here has found what decides it. Linux's asynchronous readahead of a mapping, which starts the next window's read before a fault reaches it (`do_async_mmap_readahead`), is not done: a read fault waits for its window. The pages `execve` reads itself, the ELF headers and each mapped segment's last page, which it reads to check the file's length (`exec_file_read`), still go through `vfs_read` and the buffer cache.

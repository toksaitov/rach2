# 5777: piglit's dma-buf refcount-multithread test aborts on virgl

The release's full run of milestone 84 at 19a1eb6354 failed `machine.virgl.piglit-03` on x86-64 on one test, `spec@ext_image_dma_buf_import@ext_image_dma_buf_import-refcount-multithread`, crash here and pass in the Debian reference: SIGABRT with glibc's `tcache_thread_shutdown(): unaligned tcache chunk detected`. The cause is a race in Mesa 25.0's virgl winsys, which Mesa fixed in 25.2.0 and which Debian 13's Mesa 25.0.7-2+deb13u1, the Mesa of both guests, lacks: two threads destroy the same imported resource, and its memory is freed twice. Linux shows it too. Under the same forced load, Rach2 and Debian's Linux 6.12.115 each aborted in 10 of 10 runs, each run after a second GEM_CLOSE of a closed handle. Rach2's kernel has no fault here. The test is named a flake in `tests/graphics/piglit-virgl.flakes`.

## The race

The test makes a 2x2 dma-buf, and two threads each import it 100,000 times as an EGL image, make a texture of it, and drop both (`tests/spec/ext_image_dma_buf_import/refcount-multithread.c` in piglit). Each import goes to `virgl_drm_winsys_resource_create_handle`, which under `bo_handles_mutex` turns the descriptor into the file's GEM handle and looks the handle up in `bo_handles`, raising the count of a resource it finds (`src/gallium/winsys/virgl/drm/virgl_drm_winsys.c:528-541` in Mesa 25.0.7). The last drop lowers the count without the lock (`virgl_drm_resource_reference`, line 155) and only then calls `virgl_hw_res_destroy`, which takes the lock, checks the count again, and removes, closes and frees the resource (lines 75-107). Between the drop and the lock, the other thread can find the resource at a count of 0, raise it, drop it and destroy it, and the first thread then destroys it again: its GEM_CLOSE fails, since the handle is closed, and its `FREE` frees the memory a second time. glibc finds the corrupted tcache at a later allocation or at the thread's exit.

Mesa's commit 6c1c116a0fb6, "virgl: Avoid possible double free when destroying the hw resource", of 2025-05-15, first in 25.2.0, describes this interleaving and names this test as its reproducer. It counts the lookups that raise a count of 0 in `needed_references`, and 63cd410c29f1 of 2025-09-13 corrected it. Debian's `virgl_drm_winsys.c` for 25.0.7-2+deb13u1 on sources.debian.org has no `needed_references`, and its patch series backports neither commit.

## The runs

Every run was in this account's clone on the testing PC, at milestone/76-display 8bf856c08, under KVM in one claim of the site's ledger at a time, beside the release's full run. Rach2 booted `gnu-test.disk` with `drive.py`, on the case's machine: `-cpu host,invtsc=on`, 8 GiB, `virtio-vga-gl` with egl-headless on the RTX 4080 through Mesa's d3d12, the disk on virtio-blk and `rach2.root=ext2`. Debian booted the prepared reference guest with `debian-ref.sh run -p virgl`, with Debian's piglit installed for the boot. Each run was the binary as piglit's profile names it, `ext_image_dma_buf_import-refcount-multithread -auto`, as the test account (Debian's `gfx`), with the case's environment: `GRAPHICS_CLASS=conformance LP_NUM_THREADS=0 EGL_PLATFORM=surfaceless PIGLIT_PLATFORM=surfaceless_egl PIGLIT_NO_FAST_SKIP=1`. The scripts are in [5777/](5777/): `loop2.sh` runs the test, and `mkjob.sh` writes the guest's job for `drive.py`.

The test alone aborted at run 75 with `malloc(): unaligned tcache chunk detected`, after 74 passes; the leg stopped there, as the card asked. The chat then limited each leg to 3 processors.

The forced load preloads [`5777/race.c`](5777/race.c), which learns `bo_handles_mutex` as the last pthread mutex locked before the first PRIME_FD_TO_HANDLE, spins 1 ms before one lock of it in four and 200 us after each unlock, and prints each GEM_CLOSE that fails. The first spin lets the other thread's import and destroy run between a drop and its lock; the second keeps the destroying thread's `FREE` after its unlock, so the waiting thread reads the count before the memory is freed. Every forced run on both kernels printed `GEM_CLOSE 2 failed: Invalid argument`, the second close, before it aborted. On Rach2 all 10 aborts were `tcache_thread_shutdown(): unaligned tcache chunk detected`, the release's message. On Debian 7 were that, 2 `free(): double free detected in tcache 2` and 1 `free(): too many chunks detected in tcache`. The Debian guest ran glibc 2.41-12+deb13u4 and Rach2's root glibc 2.44.

## Rach2

Rach2's kernel answers each call of the race as Linux does: the second GEM_CLOSE of a handle fails with EINVAL on both, and the abort follows it on both. Rach2 changes nothing in its own code. Its Mesa is Debian's binary package, and a backport of the two commits would mean building Mesa for the GNU layer, which no task has planned. The test alone crashed once in 75 runs here. The other loops' legs, on cards #5778, #5780 and #5781 and in the entry of [upstream.md](upstream.md#mesas-virgl-winsys-frees-a-resource-twice-when-one-thread-drops-it-as-another-imports-it), counted 5 aborts in 59 runs at master on Rach2's kernel, 1 in 17 on Debian's kernel under the GNU root, and none in 37 in the Debian guest's own user space. Those are their figures. The forced load shows that the window is Mesa's on both kernels, and its width depends on how long the dropping thread waits before it takes the lock.

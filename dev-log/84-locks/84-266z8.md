# 84-266z8: ext_external_objects@vk-ping-pong-multi-sem, read against Linux

The Lenovo's native `gpu/piglit-rest` at 4add94748 failed `spec@ext_external_objects@vk-ping-pong-multi-sem`, fail here and pass in the reference. Rach2's syncobj and execbuffer paths that the test uses behave as Linux 6.12's on every point read below, and Linux on the same Lenovo fails the same test in the same setup, four piglit tests at a time, with `Data mismatch!`. No kernel change follows. Since 84-266z6 the expectation keeps Linux's failure of that run, so the judge no longer counts the test as worse.

## What the test does

piglit's `vk_ping_pong.c` as Debian's root has it (0.0~git20250409.af62c0dea), a port of crucible's `func.sync.semaphore-fd`, exports two binary Vulkan semaphores as opaque fds and imports them into GL: Vulkan's `vk_frame_ready` is GL's `vk_frame_done`, and Vulkan's `gl_frame_done` is GL's `gl_frame_ready`. For 255 iterations it alternates: on even ones Vulkan (hasvk) submits 128 dependent dispatches that wait for `gl_frame_done` and signal `vk_frame_ready`; on odd ones GL (Crocus) waits for `vk_frame_done`, runs 128 dispatches and signals `gl_frame_ready`. The multi-sem variant uses the two semaphores, the single-sem one only the first. The first Vulkan submission waits on a timeline semaphore at 7 before the CPU signals it, which the test's comment says is there to wake up the driver's submit thread; Mesa's common Vulkan code may then queue the following submissions to that thread, and a syncobj gets a submission's fence only at that thread's execbuffer, so a GL wait made before it finds the syncobj without that fence. The test then compares the buffer with the same hash computed on the CPU; any step that runs before the one it should wait for gives `Data mismatch!`.

On i915 this is DRM_IOCTL_SYNCOBJ_HANDLE_TO_FD in hasvk's file, DRM_IOCTL_SYNCOBJ_FD_TO_HANDLE in Crocus's, syncobj entries to wait for and to signal on each execbuffer, through I915_EXEC_FENCE_ARRAY or the timeline fences extension, and the SYNCOBJ waits that Mesa's common Vulkan code makes for a submission or a payload.

## What was compared

* Export and import by two files. `drm_syncobj_handle_to_fd_ioctl` puts a close-on-exec descriptor on the syncobj, holding a reference of its own; `drm_syncobj_fd_to_handle_ioctl` puts the same syncobj in the importing file's table, as Linux's `drm_syncobj_get_fd` and `drm_syncobj_fd_to_handle`. Both files then hold one object, and a fence given through either is seen through both.
* A wait on several syncobjs. `array_wait_start` and `array_wait_scan` are Linux's two passes of `drm_syncobj_array_wait_timeout`: a point not submitted is an error without WAIT_FOR_SUBMIT or WAIT_AVAILABLE and a listed wait with them; WAIT_ALL counts every syncobj ready; a fence callback is armed once per entry. Point 0 of a binary syncobj is its fence, as `dma_fence_chain_find_seqno` returns at once for seqno 0 in both.
* A signal while another file waits. `drm_syncobj_replace_fence` swaps the fence and walks the waits under the syncobj's lock, so a wait still listed for a submission gets the new fence and its thread wakes; a wait that already holds a fence keeps it, as Linux's entries keep theirs.
* The execbuffer's fence array. `eb_fence_array` takes a syncobj for each entry and its fence only for I915_EXEC_FENCE_WAIT, refusing a wait on an empty syncobj with EINVAL, as Linux's `add_fence_array`; `eb_await_fences` makes the request wait for each fence taken, and `eb_signal_fences` gives each signalled syncobj the request's fence after the request is added, as `await_fence_array` and `signal_fence_array`. The timeline extension's `eb_timeline_fence` is `add_timeline_fence_array`'s entry: it waits for the point's fence whatever the flags, leaves out a point signalled and gone, and takes a chain record for a timeline point to signal. `i915_request_await_fence` passes over a fence of the same engine, which is safe because the engine's queue gives requests to the ring strictly in order (`engine_submit` stops at the first request still waiting), as Linux waits only for such a request's submission.
* The i915 device reports DRIVER_SYNCOBJ and DRIVER_SYNCOBJ_TIMELINE, so hasvk's timeline wait is served.

## Linux's run

The test's row in step 9's `tests/graphics/ref/lenovo/piglit/results.json.bz2`, Debian 13 with Mesa 25.0.7 on the same Lenovo, four tests at a time through GBM, started at 1794168692.57 and failed in 0.46 s:

    MESA-INTEL: warning: Haswell Vulkan support is incomplete
    Data mismatch!

Its single-sem sibling crashed in the same run, while `vk-semaphores` and `vk-semaphores-2` passed beside them. Run alone in step 9's rerun, multi-sem passed. A failure that comes and goes with the load on the CPU, under the same kernel interfaces on Linux, puts the race above the kernel, in the drivers' submission or the test; this record does not trace it further.

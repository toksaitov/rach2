# 84-265b: why smptlbmusl's untorn and unmap rows failed under TCG

`guest.default.smptlbmusl` failed under TCG at its `untorn` row, and once on the Mac at `unmap`, after three fixes of the CPU-time readers (#5081, #5099, #5116). Neither row found a fault in the kernel. `untorn` failed on its own forcing hook: debugfs's cputime_test held `timer_lock` with interrupts off for far longer than the 100 ms it meant to, and a late tick on the reading processor spun on that lock for the whole window, so no read could begin in it. `unmap` failed when processor 1 ran something other than the spinner as the unmap was made, which Rach2, like Linux, does not interrupt. The fix makes the hook give up a carry no read begins in, makes a read wait for a carry that is due, bounds a reading's advance by the size of a tear and not by a second, and judges a TLB step only when the spinner ran on processor 1 throughout it.

All runs below were on the testing PC, under TCG with 4 processors, from this task's clone at the milestone head 41ccd5f7f with the task's changes, on 2026-11-19 from 10:37 to 11:53 UTC+6. The lines each run printed for these rows are in [84-265b](84-265b).

## Reproducing it

* Alone, 16 times on each architecture at a host load of 3 to 11: every row passed.
* Beside `etude stress cpu 40`, 16 times on each architecture at host loads of 42 to 51, the load 84-264e saw: `untorn` failed 13 times on each, 10 and 11 of them with "the count did not carry past 2^32 under a read" and 3 and 2 with "a CPU clock read a torn count".
* Confined with `taskset` to one host thread that four spinners pinned there share, 16 times on each architecture, the old code failed `untorn` every time, 32 of 32. This is the load the fix was run under.

## The untorn row

The carry's tick on processor 1 writes the count's lower half under `timer_lock`, with interrupts off, then waits for a read of the thread's clock or its process's to begin elsewhere before it writes the upper half (`split_add`). Tracing added to the hook gave, for each run's carry, the window's length on the kernel's stopwatch (`timer_watch_us`), its turns of the `k_udelay(10)` loop, and the processors seen spinning on `timer_lock` in `ptimer_cpu_tick` during it. At host loads of 62 to 74:

* In every failing run the loop ran all of its 10,000 turns, and the window measured 345 to 747 ms where it meant 100 ms: each `k_udelay(10)` took 35 to 75 us, since a delay reads the PIT or the reference counter through port I/O, which a loaded TCG host makes slow.
* In 17 of the 23 failing runs processor 0, the reader's, was seen waiting on `timer_lock` in `ptimer_cpu_tick`. `split_settle` waits half a tick for the other processors' ticks at the same edge to finish, but under host load processor 0's tick comes later than that, spins with interrupts off on the lock the carry holds, and the reader there can begin no read until the window ends. The trace watched only that wait; the boot processor's timer pass, `timerfd_tick`, takes the same lock, and what processor 0 did in the other 6 runs was not traced.
* In the passing runs a read began within 1 to 7 ms of the window's opening, after 0 to 68 turns.

The "torn count" failures were no tear. In each, the thread's clock read the same value twice in a row or moved by 125 to 155 ticks, while the process's clock moved by 1.0 to 1.4 s between two reads: processor 0 spent the window, and more, with interrupts off, and its next tick charged all the ticks it lost to the reader at once, as the scheduler charges the ticks a processor lost with interrupts off to what it runs at its next tick (`sched_account_one`, sched.c). With two threads charged, the process's clock passed the row's bound of one second. A read of a count with its halves apart is 2^32 ticks off, 17 million seconds at 250 Hz; no bound near a second is needed to see one.

One run of the old code also passed the thread's clock beyond its target with no carry at all (`cputime_test 0 0 0 0`): the clock the row watches is user plus system time, and only the user time carries, so system ticks took it past 2^32 + 10 ticks first.

## The unmap row

The row failed twice in the 361 runs made before its fix, each time beside `etude stress cpu 40`, once on i686 and once on x86-64, and each time read `shootdowns 0 interrupts 0`. `smp_tlb_shootdown` interrupts a processor only if its `space` is the address space being changed and its thread has one; a processor running another address space is passed over, and one running a kernel thread is marked to reload at its next switch (`space_stale`), as Linux leaves out a processor that runs another mm or is in lazy TLB mode. Under TCG the third case, a preempted vCPU, does not arise. So `0 0` means processor 1 was not running the spinner as the unmap was made.

To force it, the probe was given four processes, each the probe itself exec'd so that it shares no pages, spinning on processor 1 through the TLB rows. A fork that did not exec shared the probe's pages copy-on-write, and the probe's own writes then cost shootdowns of their own. With the four:

* The old rows failed every run, 32 of 32: `unmap` 28 times, `mprotect` 29, `unmap-span` 26. `fault`, which needs no interrupt, passed every time.
* An earlier run with one forked disturber printed the spinner's switch-in count, the third number of its `schedstat`, around each unmap: it moved by 1 to 3 in every one, and the rows read `0 0` in 9 of 16.

## The fix

In the kernel, only the debugfs hook changes (`rach2/sys/io/timerfd.c`):

* The window is timed with the kernel's stopwatch, and lasts at most five ticks. A carry no read is under way in by then is given up: the lower half is put back, and the tick is owed and added with the carry a later tick makes. cputime_test's line gains a fifth number, the carries given up.
* While the tested thread's next user tick carries (`test_split_due`, which the tick sets), a read of its clock or its process's waits in `ptimer_test_read`, with interrupts on, for up to five ticks for the halves to come apart. Its mark is already set, so the carry sees a read under way however the host runs the processors.

In the probe (`tests/musl/smptlbmusl.c`):

* A reading follows the one before when it is no less and less than 2^31 ticks past it, half the jump a tear makes, in place of one second.
* The child reads until cputime_test has counted a carry with a read, not only until the thread's clock passes its target.
* Each TLB step is made again, at most 20 times, until the spinner's switch-in count did not move between a reading just before the step and one just after it, both taken while the spinner's loop is seen turning. The row prints its tries.

## The load on the fix

* One host thread shared with four spinners, which failed the old code every time: `untorn` passed 32 of 32 with 0 to 22 carries given up a run, and every row passed in 32 runs of the final code.
* `etude stress cpu 40`, host loads of 37 to 49: every row passed, 32 of 32, with the final code, and 64 of 64 runs of the hook's first form passed `untorn` with up to 77 carries given up.
* Four disturbers on processor 1, which failed the old TLB rows every time: every row passed, 32 of 32, in 1 to 4 tries.

The hook's first form, which gave up carries but had no read wait for one, passed 14 of 16 runs on i686 at the one-thread load; the other two ran past etude's 120 s progress bound after hundreds of given-up carries, since on one host thread processor 0 runs only while processor 1 does not and always takes its overdue tick first. The read's wait closed that.

## Files

Each file in `84-265b/` holds one run's lines for these rows, named ARCH-CODE-LOAD. CODE is `old` for the milestone head, `trace1` for the head with the hook's tracing, `fix` for the hook's first form, `fix2` for its form with the read's wait, `final` for the task's last commit, and none for the head; `force-unmap-old`, `force4-old`, `force4-fix` and `force4-fix2` ran the probe with disturbers on processor 1 under the old rows, the rows' first fix bracketing the readings of `/proc/stat`, and the final rows. LOAD is `1` or `r16` for none, `load24` for etude's own `-L cpu:24`, `stress40` for 40 spinners beside the runs, `pin2` and `pin1` for the run confined to two host threads or one, and `pin1-spin4` for one host thread shared with four spinners.

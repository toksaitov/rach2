# 84-263n: why Proton's d3d9:visual exits 1 after 20 lines on Venus where Linux runs past 384

The release's `machine.d3dvenus.wine-proton-d3d9-visual` on x86_64 exited with 1 after 20 test lines, where `venus.json` asked for 245 after at least 384. Neither end is a property of the guest. Both guests can reach DXVK's 5 s limit on a submission that waits for lavapipe on the host to compile its shaders; whether they reach it, and where, follows the host's shader cache and load, and the process's exit after it follows a race in its teardown. The unit is now stopped at its `visual.c:2412` record, the last before the first place where Linux's run timed out.

The release's evidence was gone, so every figure below is from this task's runs on the testing PC under KVM: Rach2 by `tests/run d3dvenus` with the case alone, Debian by `reference.sh` on the same row ([runs.txt](84-263n/runs.txt)).

## Where the unit stops

The first 19 test lines of every run, on either guest, are the same. The 20th of the release's run and of this task's first is `visual.c:3874: Test failed: Z range failed: Got color 0x00000000, expected 0x00ffffff.`, the first check of Wine's `z_range_test` (`dlls/d3d9/tests/visual.c:3749-3986` in Wine 11.0), just after `DxvkSubmissionQueue: Timeout occured, GPU likely hung.`. The test clears, presents, draws four quads and reads a pixel; DXVK's submission queue waits for the submission with `vkWaitSemaphores` and a limit of 5 s (`src/dxvk/dxvk_queue.cpp:264-276` at f86377680682448), and takes the timeout for a lost device.

The host's shader cache decides it. Venus runs the guest's submissions on lavapipe in virglrenderer's render server, in a worker process for each Venus context, and lavapipe compiles a draw's shaders with LLVM at the first draw on its queue, unless the cache in `~/.cache/mesa_shader_cache` of the account that runs QEMU has them. With that cache moved away before each run, Rach2 timed out at `z_range_test` in 6 runs of 7 and at `stencil_cull_test`, 384 test lines in, in the seventh; the Debian guest timed out at `z_range_test` in 2 runs of 3 and in the third ran the unit to its summary. With the cache that a run before had left, Rach2 ran to the same summary as that Debian run, 208,921 checks, 142 failures, 770 todo and 24 skipped, exit 255. The stored reference runs of 2026-11-10, whose cache is not recorded, timed out at `stencil_cull_test` in both.

The host was compiling. A sampler of the render server's threads, twice a second, found in each cold run one thread of the `z_range_test` context's worker in user mode for every tick, with no voluntary context switch, from the test's device creation to the timeout, 5 s or more in each, where the earlier tests' workers were busy for 1 to 2 s ([host-threads.txt](84-263n/host-threads.txt)). The thread inherits the ring thread's name, as lavapipe's queue thread, which the ring thread makes at device creation, would.

## How the process ends

Within a second of each timeout, in all nine timeouts, the host's kernel logged a `vkr-ring-3` thread of the worker dying with SIGSEGV at the same instruction of lavapipe, offset 0x144ab7 of the host's `libvulkan_lvp.so`, on a read at 0x51 to 0x91; the three runs without a timeout logged none. It follows DXVK's timeout path, which resets the submission's command pools while lavapipe may still run them ([upstream.md](upstream.md#dxvk-frees-a-command-list-that-lavapipe-is-still-executing-after-its-submission-timeout)), here with lavapipe on the host; the host lacks the library's symbols, so the function is not named and that it is the same use after free is not proved.

The guest's Venus context dies with the worker. On Rach2 the process then waited some 30 s and aborted. Venus's wait loop, `vn_relax` (`src/virtio/vulkan/vn_common.c:263-285` in Mesa 26.1.6), aborts when the ring is marked fatal or the host's monitor has stopped setting the ring's alive bit, and logs why only at Mesa's debug level, which the runs did not print. Wine's SEH trace shows the signal as `EXCEPTION_WINE_ASSERTION` from libc's `pthread_kill` with signal 6 on a Unix stack outside the thread's Windows stack, so Wine cannot dispatch it and terminates the process with 0x80000101 (`dlls/ntdll/unix/thread.c:1609-1627`), whose low byte gives exit 1 (`thread.c:89-94`). Debian's run d3 ended the same way, the same trace and exit 1; d2, and both stored runs, logged the same lines and ended by SIGSEGV, which Proton reports as 245 ([abort.txt](84-263n/abort.txt)). Rach2 gave 1 in 7 of 7 timeouts and Debian 245 in 3 of 4; with that spread on Linux, the exit after the timeout says nothing about Rach2.

## Change

`venus.json` stops Proton's `d3d9:visual` at its single `visual.c:2412: Test failed: Untransformed vertex with vertex fog and z = 1.0 has color 00ff0000` record, which every run printed before either timeout, as it stops `d3d9:device`; the unit matches when it gets there or runs to its summary. `mkref.py` cannot make that stop from Debian's runs, which go past it, so the graphics tests' Readme and the reference's say it is set by hand.

# 84-114: mode bits set at open, and lock holds timed only on request

84-104 left a one-byte read or write at 1,345 to 1,522 kernel instructions against Linux's some 580, and traced some 370 of them to the choice of lock and the classification of the descriptor at every call, and about 150 of a pipe's to the clock read that stamped each hold of its sleeping lock. This task took both out of the call and measured the calls against Linux's in one machine, as 84-104 did.

## The changes

* A descriptor has mode bits, `fd_entry_t.mode` (fs/fd.h), as Linux's file has `f_mode`: whether pread64 takes it (Linux's FMODE_PREAD, the opposite of FMODE_STREAM); whether a read or a write checks its end at an offset; whether that offset is a raw window's own; whether it is unsigned (FMODE_UNSIGNED_OFFSET, /dev/mem and /proc/PID/mem); whether an ops-backed transfer holds the description; and whether a read, and a write, runs without the big lock. `fd_mode_of` decides them from the type, the object, the device row and the mounts, which the open set and nothing changes while the descriptor is open, and `fd_mode` keeps them in the entry for the rest of its life. They are decided by the first call that asks, not in `fd_install`: an entry is made by some fifty opens in many subsystems, and by dup, fork, a pidfd's getfd and pread64's view, which copy it; a copy keeps the bits, since it names the same object. Two sharers that ask at once store the same word.
* `rw_offset_end`, `rw_end_past`, `pio_seekable` and `ops_offset_held` test the bits. Before, `rw_offset_end` asked `devfs_fd_is_raw` twice, `devfs_fd_log_size`, `devfs_lseek_zero`, `procfs_is_mem` and `devfs_fd_is_mem` at every call, and `ops_offset_held` asked `devfs_fd_moves_offset`, which asks two of them again.
* read, write, pread64 and pwrite64 look the descriptor up once, as Linux's `ksys_read` and `ksys_write` do with `fdget_pos` (fs/read_write.c:695-743), and choose the lock by one bit (`rw_call_lock`) in place of `fd_write_lock` and `rw_read_lock`, which looked it up again and asked `file_vfs_unlocked`, `file_vfs_writes_unlocked` and `file_rw_unlocked`. The bits for the lock leave out the mounts of a device node and of a synthetic node, which `open_device_node` may add after the descriptor is published, since `file_rw_unlocked` never read them.
* A sleeping lock stamps a hold's start only while `kernel.lock_stat` is on, as Linux times a hold only under lock_stat (kernel/locking/lockdep.c, `/proc/sys/kernel/lock_stat`). It is 0 at boot and takes any int, as Linux's `proc_dointvec` does. A hold taken while it was off is not recorded, and with it off a take and a give read no clock. /proc/fs/lockwait still lists every kind, with nothing counted until the switch is on. lockwaitprobe turns it on before its rows; ext2_hosttest turns it on, since two of its rows judge that no hold crossed a disk request, which a record that counts nothing would pass; sleeplock_hosttest has rows for the switch.

## The setting

As 84-104's: the Windows PC's WSL, QEMU 10.2.1's TCG, `-cpu max`, one processor. Rach2 ran as `run.sh` runs it, `ARCH=x86_64 RESCUE=1 NET=off rach2/run.sh os-real`, the x86-64 kernel with the os-real image in the debug shell, through a wrapper that only gave QEMU another `-kernel` and the counting options. A script typed the commands into the shell, one character after the echo of the last, since the shell drops characters typed faster and holds 64 to a line; each command ran from a script that `write` made, under `/bin/busybox sh`. Linux was Debian's 6.12.107 cloud kernel, tests/kvm/guests/debian.txt's pinned package, with an initramfs whose only program is Rach2's own static BusyBox. Each ran the commands three times, and the figures are BusyBox dd's own:

* `dd if=/dev/zero of=/dev/null bs=1 count=400000`, 400,000 reads and 400,000 writes of one byte;
* `dd bs=1 count=100000 </dev/zero | dd bs=1 >/dev/null`, a one-byte pipe, 100,000 bytes.

Each kernel ran again with `-icount shift=0,sleep=off`, where a nanosecond is an instruction. A block log of each kernel came from `-d nochain` at boot and `log exec,nochain` through the monitor for half a second of the second run of each command, under the count. Without the count the log slowed the guest so much that the real-time tick filled the window; without `nochain` from boot the blocks that were already chained ran without passing the logger. A block's instructions were counted in the kernel's disassembly from its first to the first that ends a TCG block, so the counts by function are close but not exact. The change in their totals agrees with the counted runs: 308 instructions a call against 307 for the first command, and 1,334 a byte against 1,330 for the pipe.

Before is 7c7d265b4, the milestone branch where this task began, which is 45 instructions a call above 84-104's final kernel from the commits merged since.

## Results

Seconds; under TCG the median of three runs for the first command and of the six dd lines of three runs for the pipe. Rach2's counted runs repeat to the microsecond.

| Measure | Rach2 before | Rach2 after | Linux |
|---|---|---|---|
| 400,000 one-byte reads and writes, TCG | 1.751 | 1.365 | 0.711 |
| the same, counted instructions | 1.295 | 1.049 | 0.566 |
| one-byte pipe, 100,000 bytes, TCG | 1.352 | 0.923 | 0.422 |
| the same, counted instructions | 0.770 | 0.637 | 0.367 |

Linux's three counted runs of the first command gave 1.267, 0.699 and 0.566 s, as in 84-104, and the table takes the last. Under TCG this host ran both kernels slower than in 84-104 (Linux 0.711 s against 0.60 s there), with two other accounts' KVM guests running beside them; the counted figures do not depend on that.

In counted instructions a call of the first command costs Rach2 1,312, down from 1,619, against Linux's 708: 307 fewer. A byte through the pipe costs 6,367, down from 7,697, against Linux's 3,666: 1,330 fewer, four calls and two holds of the pipe's lock. Under TCG the pipe fell further than its instructions, by a third, since the stamp's clock is the HPET's counter (`clock: reference: the hpet`), a read of a device's register that QEMU serves outside the translated code.

## Where the instructions went

Instructions for one read and one write, from the block logs; the left pair is the first command, the right the pipe, whose writes include the pipe's and /dev/null's:

| Function | before | after | before | after |
|---|---|---|---|---|
| `fd_get` | 204 | 104 | 204 | 104 |
| `devfs_fd_moves_offset` | 116 | 0 | 70 | 0 |
| `devfs_fd_is_raw` | 100 | 0 | 50 | 0 |
| `file_rw_unlocked` | 64 | 0 | 64 | 0 |
| `pio_seekable` | 50 | 0 | 39 | 0 |
| `rw_offset_end` | 100 | 52 | 72 | 41 |
| `fd_write_lock` | 31 | 0 | 31 | 0 |
| `devfs_lseek_zero`, `devfs_fd_is_mem`, `devfs_fd_log_size`, `procfs_is_mem`, `file_vfs_unlocked` | 84 | 0 | 45 | 0 |
| `read_fd`, `write_fd` and `sys_write`, against `read_entry`, `write_entry` and `sys_write` | 177 | 171 | 177 | 171 |
| `timer_now_us` and the clock's functions under it | 2 | 1 | 150 | 2 |
| the whole kernel | 3,012 | 2,396 | 3,639 | 2,972 |

No function of the classification runs in the counted call after the change, and none of the clock's in the pipe's lock; the clock's 1 or 2 left in each column are the tick's own reads. What is left of the choice is `fd_mode`'s test inlined in `rw_offset_end` and `rw_call_lock`, and one lookup. `arch_cycles`, 73 instructions for a read and a write in both commands before and after, is the entry's account of CPU time, which 84-104 counted with the entry. The entry and the exit, the big lock's frame bookkeeping among them, are now most of what is left between Rach2's call and Linux's.

## Checks

`make ARCH=i686 rach2` and `make ARCH=x86_64 rach2` both link, and lockwaitprobe builds for both. The measurement is the task's check; the dd runs above ran on the changed kernel under the debug shell and returned their counts. No suite, host test or style check ran. No fault in another project's code was found.

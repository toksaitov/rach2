# 84-7: the lock split measured on the Lenovo

Task 84-7 (#3984) measures 84 locks on the Lenovo against the plan's Done in figures (`plan.md`, Done, in figures) and Linux's runs on the same machine (`dev-log/80-games/80-41/linux/`): SuperTuxKart's and 0 A.D.'s replays and the first 150 s of the 32-bit Crysis flyby in play on the branch's release kernel, then one SuperTuxKart replay on the lockdep kernel with `/proc/lockdep` read. This file holds the step and, once it has run, its results.

## The step

Two trial boots of one trial root, by a loop of the owner's under the Lenovo's lock, after the manager's go on #3984, which names the head to build, a head the reviewers have read whole. Boot A runs the branch's release kernel, boot B its `rach2-lockdep` kernel; two more reboots put the release back. It takes the screen and plays sound: the boot session's Weston on the panel, the games fullscreen, SuperTuxKart's and Crysis's sound through PulseAudio at volume 1, 0 A.D. muted by its own setting. Comment the notice on #3984 when step 1 starts, and reboot in step 5 no sooner than ten minutes after it:

```

On the first, the desktop's Weston shows on the panel and SuperTuxKart, 0 A.D. and the 32-bit Crysis each play once, fullscreen, about 12 minutes in all; SuperTuxKart's and Crysis's music and effects play at volume 1, 0 A.D. is muted. On the second, SuperTuxKart plays once more. Two more reboots put the release back.
```

### Reading

On the Mac, `mkdir -p $R/a $R/b && tar -xzf $R/out-a.tar.gz -C $R/a && tar -xzf $R/out-b.tar.gz -C $R/b`. For each game G of boot A, `supertuxkart`, `0ad` and `crysis`:

```
o=$R/a/G
t0=$(awk 'NR == 1 { print $1 }' $o/audio-before); t1=$(awk 'NR == 1 { print $1 }' $o/audio-after-game)
awk -v wall="$(echo "$t1 - $t0" | bc)" '
    FILENAME ~ /calls$/ && FNR == 1 { next }
    FILENAME ~ /calls$/ && ($1 == "ioctl" || $1 == "ioctl_lost") { next }
    FILENAME ~ /calls$/ { held += $6; if ($1 == "take" && $2 == 0) idle = $7; else if ($1 != "take") wait += $7; next }
    FILENAME ~ /stat-before$/ && $1 == "cpu" { for (i = 2; i <= 9; i++) b[i] = $i; next }
    FILENAME ~ /stat-after$/ && $1 == "cpu" { for (i = 2; i <= 9; i++) a[i] = $i }
    END {
        user = (a[2] + a[3] - b[2] - b[3]) / 100; sys = (a[4] + a[7] + a[8] - b[4] - b[7] - b[8]) / 100
        printf "held %.1f s of %.1f s, %.1f%%\n", held / 1e6, wall, 100 * held / 1e6 / wall
        printf "waits in entries %.1f s, %.1f%% of %.1f busy s\n", wait / 1e6, 100 * wait / 1e6 / (user + sys), user + sys
        printf "waits after an idle wait %.1f s\n", idle / 1e6
        printf "system %.1f s, user %.1f s, ratio %.2f\n", sys, user, sys / user
    }' $o/calls $o/stat-before $o/stat-after
grep -E 'games: result|bkl:' $R/lenovo-a.out
ADDR2LINE=x86_64-elf-addr2line sh $T/tests/system/games/bklread.sh $T/build/x86_64/rach2/kernel.debug $o/profile | head -n 20
```

The stock Debian reference kernel cannot give Weston this path. With `nomodeset` the 6.12.115+deb13.1-amd64 rehearsal on the Mac booted over UEFI and answered SSH with no `/dev/dri`. Its configuration enables efifb and disables `CONFIG_SYSFB_SIMPLEFB` and `CONFIG_DRM_SIMPLEDRM`. The cached trixie-backports 7.2.12 kernel also disables both. See [the rehearsal record](84-7/video/debian-stock.txt) and [Debian's request to enable simpledrm](https://bugs.debian.org/1125148). A comparable Linux boot needs the framebuffer exposed through DRM so that Weston can use its DRM backend with Pixman.

The Debian reference rebuild uses the signed sources of Debian's linux 6.12.115-1. Start with p5's `config-6.12.115+deb13.1-amd64`, enable `SYSFB_SIMPLEFB`, `DRM` and `DRM_SIMPLEDRM` as built-ins, and disable `FB_SIMPLE` so simpledrm takes the firmware framebuffer. The testing host used GCC 15.2 and binutils 2.46.

The first build disabled module BTF, which changes `struct module` in `include/linux/module.h:518`. Its `module_layout` CRC was 0xbe53cd4e, against 0x2f9b2b9a in Debian's e1000e. The second kept Debian's BTF options and matched that CRC. The installed modules still rejected other exported symbols, including `devm_request_threaded_irq` and `netlink_capable`. ### The big lock in the plays, 5527, 11-20

On the Lenovo, the plays above held the big lock longest in these entries. Firefox's H.264 play waited 15.79 s for it and ran 4,276 ticks of system time against 11,041 of user time:

* The tick: 0.93 s.

Chromium's H.264 play held `ioctl` for 2.83 s and the return to user mode for 0.94 s. Firefox's surplus drops came mostly in the first 9 s: 101 against Debian's 37, then 52 against 25 over the rest.

The reproduction ran in QEMU under KVM in the i3-4030U's shape: two cores of two threads and 8 GiB, on the GNU test root, with Weston on the DRM backend with Pixman. Each browser played the 60 s H.264 clip for 58 s. The scripts are in [`../87-fair-scheduler/5527/`](../87-fair-scheduler/5527/): `qemu.sh`, `play.sh` and `compare.py`. The counters of each play are in its `qemu/` directory. In QEMU the drops stay at noise, so the big lock's wait is the measure. It is the sum of `bkl_wait_us` over the processors during the play.

Three causes were found and fixed:

* A thread with a seccomp filter entered every call under the big lock. Firefox's sandboxed processes and Chromium's renderers all have filters, so their futex, read and poll calls all took the lock. The filters now run without it (`seccomp_check`), as Linux's `__seccomp_filter` runs under no global lock. The lock is taken only for a trap, a trace or a kill. The same change fixed a fault: after a SECCOMP_RET_TRACE stop, the kernel ran the number the call was made with, not the one the tracer left. seccompmusl's new `trace-redirect` row checks this. The row fails on the kernel before the fix on both ABIs and passes after it.
* Every return to user mode with an rseq notice took the big lock. glibc registers rseq in every thread, and a switch sets the notice. The rseq area is now updated without the lock (`rseq_return_unlocked`), as Linux's `rseq_handle_notify_resume` does. The lock is taken only for a pending signal or the area's SIGSEGV.
* fbdrm ran its commits under the big lock. Its device now sets `DRIVER_KMS_UNLOCKED`. A copy takes the lock only to gather its buffer's frames and copies them without it (`fbdrm_gather`).

#### The frame clock without vblanks, QEMU, 16:43 UTC+6

Chromium's remaining drops come from the display's lack of vblanks. fbdrm's CRTC had no vblank interrupt, so WAIT_VBLANK answered EOPNOTSUPP and each commit's event was sent when the commit ended. Weston 14.0.2 on DRM with Pixman then starts each repaint of an idle output with a test commit, gets its flip event at once and repaints about 9.3 ms later. It stamps the frame shown about 11 ms after the client's commit. Chromium re-phases its frame clock to each presentation time, so its refresh callbacks came 17.3 ms apart on average, from 8 to 25 ms. At 30 fps on 60 Hz its video renderer shows each frame for two refreshes, falls behind, and drops two frames at once to catch up. At QEMU's default 75 Hz no cadence applies, which is why bochs at 75 Hz looked clean. Linux 6.12 does the same: simpledrm and bochs-drm have no vblanks there.

Rach2 now has the same timer in drm_vblank.c, run from the boot processor's tick at a fine deadline, and fbdrm and bochs use it. Weston then paces its repaints by vblanks a frame apart, and each event comes at the vblank after its commit, as on hardware.

# 84-110: KVM's per-entry polls turned into Linux's vCPU requests

84-103 left the run loop's preparation at 16,500 to 17,400 cycles an entry: before every entry it looked at each source of work, the local APIC's timer, the PIT, Hyper-V's synthetic timers, the kvmclock and the steal time, the PMU, the irqfds, the NMIs other vCPUs sent, the dirty ring, and scanned the APIC for a pending interrupt. Linux's `vcpu_enter_guest` tests one word, `vcpu->requests`, and does each piece of work only behind its bit (`kvm_request_pending`, arch/x86/kvm/x86.c:10288 in 6.12.115). This task gave Rach2's vCPU the same word and order. The preparation fell from 18,000 to 4,500 cycles, and a CPUID or VMCALL round trip is now shorter under Rach2's KVM than under Linux's on the same machine. An IN that QEMU answers was still 6 to 13% longer; 84-130, at the end, traced what was left to the PKRU switch around each run and made IN, too, shorter than Linux's.

## The setting

As 84-103's: the testing PC, the KVM suite's machine under QEMU 10.2's TCG with SVM and one processor (`RACH2_QEMU_ACCEL=tcg ARCH=x86_64 RACH2_CASES=machine.kvm.unit-tests tests/run kvm`), and Debian's Linux 6.12.107 as the KVM host of the same machine with one processor (`tests/kvm/linux-corpus.sh -a tcg -k unit unit-subset.list`). A temporary `corpus.sh`, not committed, ran kvm-unit-tests' `vmexit.flat` five times each for `cpuid`, `vmcall` and `inl_from_qemu` under `exits.sh`, and later also timed 100,000 `getpid` calls and 100,000 `KVM_CHECK_EXTENSION` ioctls of `/dev/kvm` in perl, three times. Cycles are the TSC's at 4.19 GHz; the tables give medians of five. Each run below ran alone on the machine, one after the other; 84-103 found that two runs at different hours move with the machine's other work, so only runs close in time are compared.

The milestone branch at this task's start could not run the case: every boot of the GNU root locked up in the first write to an ext2 file, in `node_size`, reading an ext2 open handle as a node (`vfs_write` passed the handle to `filecache_forget`). The branch's fix of the same fault, a `handle_node` operation of the type, landed while this task traced it, and the runs below are on the branch after it.

## The request word

Whoever changes state the vCPU must act on sets its bit with an atomic or and kicks the vCPU; the run loop's preparation runs only when a bit of `KVM_REQ_NOENTER` is set or the vCPU is not runnable, and does each source's work behind its bit, as Linux's chain of `kvm_check_request` in `vcpu_enter_guest` does (x86.c:10288-10466): the dirty ring's full mark (`kvm_dirty_ring_check_request`, virt/kvm/dirty_ring.c:198-212), Hyper-V's crash, reset and exits, the PMU's recalculation and its interrupt (x86.c:10369-10372), the local APIC's irqfds, NMIs, INIT and SIPI, the I/O APIC's scan and EOI exits, the kvmclock (x86.c:10313) and the steal time (x86.c:10367). Linux takes the kvmclock first; Rach2 takes it after the APIC's work, so a halted vCPU's sleep there comes before the clock's write, not after it. A request set after its step cancels the entry, which the next pass takes, as Linux's late `kvm_request_pending` check does.

| Request | Set by |
|---|---|
| KVM_REQ_TIMER | the vCPU's deadline passing, a kick from the PIT and from KVM_SET_LAPIC, a halted vCPU's wake |
| KVM_REQ_NMI | an NMI delivered to the APIC |
| KVM_REQ_INIT_SIPI | an INIT or SIPI delivered, KVM_SET_MP_STATE's SIPI |
| KVM_REQ_IRQFD | an irqfd's eventfd rising |
| KVM_REQ_PMI | a counter's overflow at an exit or a retired instruction |
| KVM_REQ_PMU | a write of a PMU MSR, a reset |
| KVM_REQ_DIRTY_RING_FULL | the ring's push that reaches its soft limit (dirty_ring.c:194-195) |
| KVM_REQ_CLOCK_UPDATE | a move to another processor, a TSC write, the reference TSC page's enable (hyperv.c:1443-1450), each exit under `tsc_always_catchup` (x86.c:10689) |
| KVM_REQ_MASTERCLOCK_UPDATE | the host's clock stopping or starting |
| KVM_REQ_STEAL_UPDATE | each KVM_RUN and each switch of the vCPU's thread (x86.c:4611) |

Rach2 has no hrtimers, only the 1 kHz tick, so the timers keep one deadline a vCPU, `timer_ns`, in the host's nanoseconds: the earliest of the APIC timer's, the PIT's, Hyper-V's synthetic timers' and the kvmclock's resync. The vCPU's own thread lowers it as it arms a timer (`kvm_timer_arm`); another thread kicks KVM_REQ_TIMER instead. The loop reads the clock only while a deadline is set, and at KVM_REQ_TIMER checks the three timers and sets the next deadline (`kvm_vcpu_timers`). A deadline may be early, never late, and a halted vCPU's sleep still wakes at the timer's tick, so timers fire on time inside and outside the guest.

The per-entry scan for a pending interrupt is gone. An injection that leaves another interrupt pending arms the interrupt window, as Linux's `kvm_check_and_inject_events` does (x86.c:10010-10011), and a halted vCPU that wakes asks for KVM_REQ_EVENT; EOI, TPR, CR8, the PIC, an accepted interrupt, a window exit and the state ioctls already did. The PMU keeps the counters the guest enabled in two masks, recomputed at KVM_REQ_PMU, and each backend's entry starts from them.

## Against Linux

Linux alone, then this task's kernel alone, twice; the run at 01:33 had the kernel's profile on:

| Exit | Linux 01:31 | Linux 01:34 | Rach2 01:33 | Rach2 01:35 |
|---|---|---|---|---|
| CPUID | 147,755 | 149,775 | 124,942 | 123,529 |
| VMCALL | 439,742 | 455,510 | 380,108 | 380,703 |
| IN answered by QEMU | 227,343 | 235,199 | 256,287 | 250,330 |

Linux has no counter of its preparation alone, and a probe costs more than the preparation: with a synthetic event timing each `kvm_exit` to the thread's next `kvm_entry`, Linux's CPUID round trip rose from about 149,000 cycles to 174,000. That span, which holds Linux's handling and preparation, was 19,348 ns a CPUID exit, 81,100 cycles, or about 56,000 with the trace's 25,000 taken out; Rach2's same span, which holds its preparation, is 41,320.

The IN exit is the one that returns to QEMU, so each one is a KVM_RUN call more than a CPUID exit. A bare call costs Rach2 more than Linux under this TCG: `getpid` 2,426 to 2,430 ns against 691 to 702, and the ioctl 2,908 to 3,574 ns against 1,290 to 1,393, one run of each kernel giving 5,066 and 5,039. That is 7,000 to 9,000 cycles a call, about half or more of IN's 15,100 to 29,000. Each call goes through `_isr_router`: `user_entry`, the big lock's decision and its frame record (`isr_entry_lock`, `bkl_frame_push`), the entry's record for `bkl/profile` and `bkl/calls` (`bkl_note_entry`, `bkl_entry_push`), the call's accounting at its end (`smp_call_end`) and `isr_leave`'s signal and rseq work, where Linux's `do_syscall_64` does only the work its thread's flags name on entry and exit. The first entry of each KVM_RUN also costs 25,383 cycles against a CPUID exit's 18,757, the vCPU's load and the host state's save, which Linux's `vcpu_load` pays too; the two were not split on Linux. The system call's path is not the run loop's and is not changed here.

## Again after 84-115 and 84-129

84-130 measured the same cases again once 84-115 and its fix 84-129 had shortened the system call's entry and return. The setting is the one above, on the milestone branch's head at this task's start and then on this task's kernel, each pair of a kernel and Linux run one after the other within three minutes; the times are the runs' starts in UTC+6.

On the head, CPUID and VMCALL were shorter than Linux's and IN was 16 to 25% longer:

| Exit | Rach2 04:10 | Linux 04:15 | Rach2 04:16 | Linux 04:17 |
|---|---|---|---|---|
| CPUID | 126,437 | 134,019 | 125,419 | 134,874 |
| VMCALL | 382,731 | 406,401 | 385,770 | 399,096 |
| IN answered by QEMU | 242,836 | 209,523 | 248,429 | 198,806 |
| getpid, ns | 1,285 | 580 | 1,394 | 574 |
| KVM_CHECK_EXTENSION, ns | 1,686 | 1,224 | 1,727 | 1,244 |

The difference was in KVM, not in the system call. With the run loop's spans timed by the TSC in a kernel built for it, not committed, the backend's `put` at KVM_RUN's end took 25,408 cycles, of the IN round trip's 156,950 between the ioctl's entry and its return, and `exit_stats` gave a CPUID exit 18,092 cycles for the entry and 20,300 for the exit. Both backends moved PKRU around every run. The guest's FPU image, loaded at a KVM_RUN's first entry and saved at its end, was restored and saved under the host's XCR0, which on the testing PC's QEMU processor names PKRU, so each XRSTOR switched PKRU between the guest's image value, 0, and the host's; and `fpu_enter` and `fpu_leave` wrote the guest's PKRU with WRPKRU before each VMRUN and the host's after it. QEMU's TCG flushes its whole TLB on a WRPKRU and on an XRSTOR that changes PKRU (`helper_wrpkru` and the XRSTOR of the PKRU component in `target/i386/tcg/fpu_helper.c`), so every exit paid two flushes and every IN four, each followed by a refill of the pages that the host's path touches.

A guest is offered no PKU (`XCR0_KERNEL` in `cpuid.c`): its CPUID lacks the feature, CR4.PKE is reserved to it and KVM_SET_XSAVE refuses PKRU, so it can neither read nor change PKRU. Linux runs such a guest under the host's PKRU and never writes it: `fpu_swap_kvm_fpstate` restores `XFEATURE_MASK_FPSTATE`, which lacks PKRU (`arch/x86/kernel/fpu/core.c:349-388`, `arch/x86/include/asm/fpu/xstate.h:46-47, 94-95`), and `kvm_load_guest_xsave_state` writes PKRU only for a guest whose CR4 has PKE or whose XCR0 has PKRU (`arch/x86/kvm/x86.c:1019-1023`). Both backends now do the same: their XSAVE and XRSTOR of the image leave PKRU out of the mask (`KVM_XFEATURE_PKRU` in `kvm.h`), and the WRPKRUs, the backend operations that made them and the saved values are gone. KVM_GET_XSAVE already gave only the guest's XCR0 and SSE in XSTATE_BV, so the image's PKRU part, which XSAVE now leaves as it was, is never seen. The Lenovo's Haswell has no protection keys, so there PKRU was never switched; the change counts under TCG and on a host with PKU, where Linux's path is the one followed.

Among all the runs of this task, timed ones included, one IN run of five took 400,000 to 818,000 cycles in four of Rach2's ten, on the head and on this task's kernel, and in one of Linux's seven; since Linux shows it too it is not traced here, and the medians leave it out.

What remains is in the bare system call, which every call pays: getpid takes 2.2 times Linux's time and KVM_CHECK_EXTENSION 1.4 to 1.5 times. `sys_getpid` is not among the calls that run without the big lock (`syscall_unlock`), so each getpid takes the lock at its entry and gives it back at its return, and each call of either kind does the big lock's bookkeeping for `bkl/calls` and `bkl/profile` (`smp_call_end`, and `bkl_note_ioctl` for an ioctl). Neither is KVM's, and neither is changed here.

## Checks

The task's own check is the KVM suite's cases on two new lists of the tests that use each changed source, [`requests-unit.list`](../../tests/kvm/requests-unit.list) and [`requests-selftests.list`](../../tests/kvm/requests-selftests.list), run with the new variable `RACH2_KVM_UNIT` and the existing `RACH2_KVM_SELFTESTS` (tests/kvm/Readme.md), under `RACH2_QEMU_ACCEL=tcg`. Each test gives the list's result. Three of the lists' rows were wrong on the milestone's head as well, and are fixed here:

* `tsc_msrs_test` failed at its line 36 and kvm-unit-tests' `tsc_adjust` skipped: KVM_GET_SUPPORTED_CPUID passed on the host's TSC_ADJUST bit, which QEMU's TCG does not offer, so a guest's write of IA32_TSC_ADJUST was ignored. Linux sets the bit always, since it emulates the MSR (arch/x86/kvm/cpuid.c:710-711), and so does Rach2 now; both pass.
* `eventinj` fails `NP exception`, `NP PF exceptions` and `int 33 with shadowed stack` under TCG on the head and under Debian's Linux 6.12 as the host of the same machine (`linux-corpus.sh -a tcg -k unit`), so its row now expects that failure under another hypervisor, as `debug`'s does.
* `x2apic`'s subtest `TMCCT should not be reset to TMICT value` passed on the head and failed in each of four runs of this task's kernel. The APIC's count was right in both: with the kernel logging each read, the periodic period was 10.07 ms, and the guest's report line between its two reads took 11.3 ms on the head and 9.0 ms here, since each of its serial exits is cheaper. The subtest passes only when that line takes less than the count left at the first read, as on hardware, or more than that and half a period, so the clock decides it. Its row now takes either result outside a machine of KVM, with a new `A|B` form of `corpus.sh`'s lists.

The host tests that build the run loop and the APIC needed stubs of `kvm_timer_arm`, `kvm_vcpu_timers`, `kvm_lapic_timer_check`, `kvm_pit_check` and `kvm_lapic_next_ns`; their sleep rows now halt the vCPU before the loop's sleep, since the loop calls `kvm_lapic_prepare` only for a request or a vCPU that is not runnable. Run alone, `kvm_hosttest`, `kvm_vmx_hosttest`, `kvm_irq_hosttest` and `kvm_hyperv_hosttest` pass. Three faults in them predated this task: `kvm_irq_hosttest` counted a halted wait that a signal ends as one nothing ends; `kvm_vmx_hosttest`'s switch between two runs never set `need_resched`, which the loop has read since its switch moved behind that flag; and `open_hosttest` released an orphan's description twice at a table's end, which ASan stopped. All three are fixed. `open_hosttest` still fails 50 rows before that point on the branch's head as on this task's, which ASan's stop had hidden, since the rows print to a buffer the stop discards.

# 5759: an open and close of a file reached through the RAM image's root

An open and close of `/mnt/f`, a file on an ext2 volume mounted at `/mnt` of the x86-64 os-real RAM image, took 506 us a pair against some 10 us on Linux in the same QEMU. Two costs made it up: a KRFFS lookup of `mnt` that read the header of every node in the image, some 490 us, and the walk under the big lock that a path starting on the KRFFS root takes, since the walk without it cannot stand on KRFFS. With both cut the pair takes 12.63 us against Linux's 9.79 us, 1.29 times, in three paired boots.

## The trace

The bare-call timer of task #3504 (`dev-log/78-intel/78-11d/bare-call/` on `task/3504`) ran from `build/runs/t5759` with the kernel profile on: `bkl/profile` in its whole-kernel mode, written `kernel` before the timer started and read after it, symbolized against the kernel's `kernel.debug`. Every boot was on WSL with multi-threaded TCG, `-cpu max`, four processors, 3 GiB and the 64 MiB ext2 volume on virtio, mounted without access times.

On the milestone's kernel at d7f9ab4e4d, of the 7,479 samples in the profile's 80 busiest rows, 6,980 were in `krffs_find_child_err` and below it, under `kfs_lookup` of `mnt` in the root directory: 5,002 in `krffs_memory_read`'s byte loop (`_krffs_memcpy`) and 1,560 in `krffs_brief`. KRFFS has no index of a directory; a node names its directory by `parent_id`, and a lookup reads the brief header, 99 bytes in two reads, of each of the image's 1,919 nodes until it meets the name, some 260 ns a node under the emulator. The opens themselves went to the full walk under the big lock, since `open_unlocked`'s cached walk refuses a KRFFS mount (`walk_cacheable`), so each open made the futile attempt, its descriptor reservation and release included, before the full walk.

Two other paths, timed on the kernel with the lookup cache alone, bound the walk's part: a relative open of `f` with the working directory at `/mnt`, which the walk without the big lock takes whole on ext2, took 14.35 us, and `/etc/passwd`, on KRFFS itself, 31.9 us.

## The changes

* `krffs.c` keeps the boot root's lookups of one component, a node or none, in a cache of 512 entries by directory and name (`krffs_find_child_err`). Every write of the core that can change what a lookup finds, of a header's type, identifier, name, sizes or parent, moves a count once it is made (`krffs_backend_write`), and an entry stands only while the count is the one its lookup began with. A write of a file's bytes, mode, owner, times or length leaves the count (`krffs_backend_store`, `krffs_backend_field`), so writing a file on the root does not empty the cache. The kernel calls the core under the big lock; a lookup whose read slept and found the count moved keeps nothing, and a node an entry names is read again before the cache answers.
* `vfs.c`'s cached walk steps from the root directory of the KRFFS boot root, which it cannot stand on, into the mount an absolute path's first name enters (`cached_hop`): a nameless mount of that name, or the mount that covers the node the name names now. The root directory reports mode 0755 whatever its header says (`kfs_getattr`), and KRFFS has no ACLs, so the search check passes for every caller. One search of the mount table under its lock finds the mount and whether another is over its root, which `cached_cross` then crosses. The walk sequence check at the walk's end covers the step as it covers every other.

## Checks

Both kernels linked. A boot of the final kernel on the RAM image read `/mnt/f` whole, listed `/mnt/../etc` as `/etc`, and on the KRFFS root created, read, renamed and removed a file, missed a name and then found it once created, made and removed a directory with a file in it, and grew a file by a hundred appends of 4 KiB with its last 4 KiB intact. Over `/mnt` it read a tmpfs stacked on the ext2 volume and the volume again once the tmpfs was unmounted, a bind of `/mnt` elsewhere, `/proc/self/stat` and `/dev/null`, and found `/mnt/f` gone once the volume was unmounted. The scripts and the boots' consoles are in `build/runs/t5759` on WSL.

## Review

Codex's review of `50bf21ad4c` found one fault: the step matched a covering mount by its recorded path, which a rename can leave behind. Bind an ext2 file onto KRFFS `/target`, bind `/` without its mounts at `/alias`, and `mv /alias/target /alias/moved` succeeded, since `vfs_leaf_mount` counted only the mounts on the parent mount the call named; the mount still read `/target`, and an open of `/target` took the ext2 file where the full walk finds none. Both of its fixes are made:

* `vfs_leaf_mount` counts a mount over the node on any mount of the same file system, a bind or the mount it binds, that the caller's namespace sees, as Linux's `is_local_mountpoint` does, so the rename and an `rm` through `/alias` answer `EBUSY`.
* The step matches a covering mount by the node the name names now. A rename through a namespace that does not see the mount still moves the node, as on Linux. The lookup runs under the big lock, which the KRFFS core needs. Taking that lock on every step put the pair at 14.59 us against Linux's 9.77 us, 1.49 times, in three paired boots. So the step remembers eight names it looked up with the low word of the lookup cache's count read before each lookup (`hop_memos`, `krffs_names_stamp`), and an entry answers without the lock while the word reads the same. A change of a name under way when the word is read moves the walk sequence, which the walk checks at its end. The memory is read in the step's one search of the mount table, under the table's lock.

Every earlier check passed as before.

## Second review

Codex's review of the fix at `ec54bbbc1d` found three faults, each now fixed:

* The step looked its first name up on the caller's root mount after letting go of the lock it read the root under, with no hold on the mount. That mount can be a bind of the KRFFS root at `/` in a private namespace, which a thread sharing the caller's root (CLONE_FS) could move off and unmount meanwhile. The step now enters the root mount under the lock it reads it under (`vfs_enter`) and leaves it after the step, so an unmount waits for it.
* The remembered names compared the low 32 bits of KRFFS's lookup count, so after 2^32 counted writes an untouched entry could match again. They now keep the whole 64-bit count, which KRFFS moves and a caller without the big lock reads under one spinlock (`krffs_names_stamp`).
* `vfs_leaf_mount` matched a mount by the node it covers, so with `/t/a` and `/t/b` links of one file on tmpfs, `/t` bound at `/alias` and a file bound over `/alias/a`, `rm /t/b` answered `EBUSY`. Linux's mount stands on a dentry. A bind over a file of several links now counts only at the name it was bound at, the last component of its recorded path (`mount_on_name`); a directory and a file of one link have one name, and their node alone decides as before.

The boot's checks gained the hard-link case and passed whole on the final kernel. With `/t/a` and `/t/b` linked on tmpfs, `/t` bound at `/alias2` and `/mnt/f` bound over `/alias2/a`, `rm /t/b` and a rename of a third link succeeded, while `rm /t/a`, `rm /alias2/a` and `mv /alias2/a /alias2/e` answered `Resource busy`, and so did `rm /t/a` once it was the file's only name. Every earlier check, the first review's alias and namespace cases among them, passed as before.

## Third review

Codex's review of `38a408777b` found the hard-link fix only partial: a recorded name goes stale after a rename in a namespace without the cover, a bind stacked over a bind records the wrong name, and two links of one name in different directories still confuse each other. All three lie in the refusal of a rename or removal of a mountpoint through another mount of its file system, which the first review's fix added to `vfs_leaf_mount`. The step from the KRFFS root no longer needs it: it enters a covering mount only when the mount covers the node the name names now, looked up or remembered at an unchanged lookup count, so a rename through `/alias` leaves `/target` naming no node or a new one, and the step answers as the full walk does, which matches by node too. So the refusal and its hard-link code are removed, and `vfs_leaf_mount` is the milestone branch's again; renaming a mountpoint through a bind of the root is allowed, as it was before this task.

One paired boot of the final kernel, as in Results: Linux 9.85 us, Rach2 15.45 us, but every Rach2 call was slow in that boot, getpid 1,293 ns against 335 ns before, while its console matched the earlier boots' but for the clock's readings and the host was idle; the cause is not traced. A second pair, with the kernel of the first review's fix as a control: Linux 9.78 us, the final kernel 13.25 us, 1.35 times Linux's, and the control 12.52 us.

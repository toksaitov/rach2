# 84-88: KVM's exit round trip under TCG against Linux's

84-33 excluded kvm-unit-tests' `access` under another hypervisor: under the Mac's TCG every reserved-bit permutation fails with QEMU's `error code 8 expected 9`, under Linux as the host too, and Rach2 printed its failures more slowly than Linux. This task measured where Rach2's round trip of an exit spends the time Linux does not, fixed three causes, and measured `access` again. `access` stays excluded under TCG: neither host can end it there.

## The setting

Every run was on the testing PC, the KVM suite's machine under QEMU's TCG with SVM and one processor (`RACH2_QEMU_ACCEL=tcg ARCH=x86_64 RACH2_CASES=machine.kvm.unit-tests tests/run kvm`), and beside it `tests/kvm/linux-corpus.sh -a tcg -k unit`, Debian's Linux 6.12.107 as the KVM host of the same machine. That script gave Linux two processors under TCG while etude gives Rach2 one, and Linux's guest then stopped after about 400 failures with its output cut, QEMU's fault of several TCG threads that etude's single processor avoids (tools/etude/Readme.md); c990c1460 gives Linux one processor there too, so the two hosts run in the same machine.

A temporary `corpus.sh`, not committed, ran in each host before `access`: kvm-unit-tests' `vmexit.flat` with `cpuid`, `vmcall`, `inl_from_qemu`, `inl_from_kernel` and `outl_to_kernel`, three times; `dd if=/dev/zero of=/dev/null bs=1` and a one-byte `dd` into a pipe; and in Rach2 `/sys/kernel/debug/kvm/exit_stats`, `bkl/calls` and the whole-kernel profile of `bkl/profile` around each. Cycles are the TSC's at 4.19 GHz.

## What access does under TCG

access.c enumerates 19,169,280 legal permutations of a page walk per paging level and 4,915,200 that set a reserved bit, and runs the enumeration twice where LA57 is offered. A passing permutation prints nothing; every reserved-bit permutation fails under TCG, under either host, with some 223 bytes of output, and kvm-unit-tests' serial output costs two exits a byte, a read of the line status register and a write of the data register. In each run the failures counted equal the reserved-bit permutations before the last failure plus one. At Linux's rate of about 23 failures a second, one level's 4.9 million take some 2.5 days, so neither host ends the test under TCG, and its row stays `outer_kvm?pass:hypervisor?excluded:pass`.

## Where Rach2's time went

A paired run, both hosts at once, before the fixes below:

| Measure | Rach2 | Linux |
|---|---|---|
| CPUID exit, cycles | 195,000 | 128,000 |
| one-byte read and write, 400,000 calls | 2.04 s, 5.1 us a call | 0.43 s, 1.1 us |
| one-byte write into a pipe and its read, 100,000 each | 1.37 s | 0.77 s |
| access's failures in 20 s | 303 | 453 |

An earlier pair gave VMCALL 656,000 cycles against 362,000 and an IN that QEMU answers 267,000 against 195,000.

`exit_stats` split Rach2's CPUID exit into 111,600 cycles from the exit's return to the next entry, 23,200 of them in the run loop's preparation, 17,900 for the entry, 44,100 for the run and 20,000 for the exit. The profile samples on the tick, so a region with interrupts off is charged to the instruction that turns them on again. Of the one-byte calls' samples, 62% fell at a `kirq_restore` and 17% at the `arch_irq_enable` of `_syscall_handler`, the end of the entry: four fifths of a call ran with interrupts off. Under TCG a POPF that changes IF ends QEMU's translation block, and the regions were long. The largest was the big lock's take, 26% of the calls' time: the read and the write of a device each take the lock (`file_ops_lock`), and each take read the monotonic clock twice for the wake latencies (`waketime_clock` in `bkl_acquire`), with no wait to time. Next were the descriptor lookups (`fd_get`, three a call, each under the table's spinlock with interrupts off), the address space's lock taken for each copy (`down_read` and `up_read`, each under its spinlock with interrupts off), and the wake of the lock's queue at every release, which found no sleeper (`wq_wake_all` from `up_read`).

## The fixes

* c8effa4a6: SVM loaded the guest's whole XSAVE image before every run and saved it after, which TCG emulates as a copy of the image. It now loads the image at the first entry of a KVM_RUN and saves it at the end, as VMX did and as Linux's `kvm_load_guest_fpu` and `kvm_put_guest_fpu` do (`arch/x86/kvm/x86.c:11061-11074`), switching only XCR0 and PKRU around each run (x86.c:1004-1047). In paired runs just before and after it, the CPUID exit went from about 220,000 cycles to 213,000, against Linux's 120,000.
* 6cc97eef0: a free big lock that no waiter has claimed and none has lent is taken by its exchange alone, with no clock read, as Linux's `queued_spin_lock` takes a free lock and leaves the rest to its slow path.
* 6cc97eef0: `up_read`, `up_write` and `mutex_unlock` wake the lock's queue only when a sleeper is on it, as Linux's releases wake only with a waiter recorded. The unlock of the lock's spinlock and the unlock of the queue a sleeper files itself on before its test are both exchanges, full barriers, so either the sleeper's test sees the release or the release sees the sleeper.

## After

The testing PC runs other accounts' work, and single runs of one kernel moved by up to a fifth from one run to the next, so the two kernels were run one after the other in the same copy, Rach2 alone: the head of this task, then the same with `smp.c` and `mutex.c` as at c8effa4a6. Each boot ran CPUID five times and the one-byte calls three; the table gives the medians, and Linux's figures are its runs beside Rach2 in the paired runs before and after.

| Measure | Rach2 before | Rach2 after | Linux |
|---|---|---|---|
| CPUID exit, cycles | 188,500 | 182,900 | 118,600 to 128,000 |
| from the exit to the next entry, cycles | 110,500 | 98,200 | |
| one-byte read and write, 400,000 calls | 2.17 s | 1.57 s | 0.39 to 0.43 s |
| one-byte write into a pipe and its read, 100,000 each | 1.27 s | 1.08 s | 0.91 s |
| access's failures in 20 s | 258 | 322 | 453 to 466 |

`access` now prints its failures 1.4 times more slowly than Linux, where before this task it printed them 1.75 times more slowly in the same comparison.

## What is left

Two causes remain, each larger than a task:

* The kernel's handling of an exit. A CPUID exit takes Rach2 98,200 cycles from the exit to the next entry, 21,200 of them in the run loop's preparation, while Linux's whole round trip, guest and entry included, is 119,000 to 128,000. The handling runs through `vcpu.c`, `exitstat.c`, `svm.c` and `emulate.c`, and the profile of the CPUID loop shows the slots' rwsem and the MMU's lock taken in it, each under a spinlock with interrupts off, where Linux reads guest memory under SRCU (`kvm_vcpu_read_guest_page`).
* The interrupts-off regions of the file calls: a device's read and write under the big lock, `fd_get` under the table's spinlock three times a call where Linux's `fdget` takes none, and each copy's `mmap_lock` under a spinlock with interrupts off where Linux's `down_read` is an atomic add and a copy that does not fault takes no lock.

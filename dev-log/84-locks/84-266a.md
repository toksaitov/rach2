# 84-266a: the GPU error under webgl2-06's chunk 6, and the pages it fell between

Both Rach2 runs of `machine.virgl.webgl-chromium-webgl2-06` that lost QEMU ([84-265r](84-265r.md), [84-265x](84-265x.md)) lost the host's D3D12 device at a change of page, not after 2 s of work that would not finish. The NVIDIA driver's error journal, read from the Windows live dump of the 04:39:38 reset, holds two errors since the 621.24 driver was installed: Xid 31, a GPU memory page fault, owned by `qemu-system-x86`, and Xid 69, a graphics engine class error. Neither is a timeout. The guest's events show this QEMU's one D3D12 queue running at its usual speed, its readbacks right, up to the page change, which a draw stuck on that queue for 2 s would not allow. So the command at fault ran at the page change itself; which command it was is not traced. The earlier reading that the timed-out work was submitted inside page 1659 `samplerobject.html` ([84-265x](84-265x.md)) assumed a timeout and does not hold.

Debian's reference keeps no time a page: `record-06` and `chromium-2.0.1-06.pages` hold counts only, so its page is bounded by counts. Its again pass ran the 26 failed pages, and its 1723 has 1486 passed and 119 failed, where the Rach2 runs read 1431 and 174 on a removed device; 1736 and 1737 come after it, then the browser's end, `events.py` and the counters at uptime 578. ## What the live dump shows

`C:\Windows\LiveKernelReports\WATCHDOG\WATCHDOG-20261115-0439.dmp` is a triage dump whose bugcheck is 0x141, VIDEO_ENGINE_TIMEOUT_DETECTED, the live dump Windows writes as it resets a GPU engine. Its fourth argument, 0xffffb683e828a0c0, is a process object: four records of the dump hold it beside the adapter, 0xffffb683baa02000, and the name `qemu-system-x86`. So the reset was charged to a QEMU's GPU work. Windows sees every WSL process under the one Linux kernel, and the dump names no Linux process ID, so which QEMU is not shown; the guest whose device went at that second is loop a's.

The dump's blob from the NVIDIA driver holds its error journal, records of 0x68 bytes with the Xid at +0x1c and the owning process's name at +0x28. In the 62 dumps of 2026-11-10 and 11-11, when Windows logged 88 events 13 ("Graphics Exception: Shader Program Header 7 Error"), the journal holds Xid 13 records, and Xid 31, 43 and 109 records besides; the journal keeps far fewer records than the events, one Xid 13 record against the 88. In the 04:39 dump, the journal begun when the 621.24 driver was loaded at 01:40 on 2026-11-14 holds two records: Xid 31, owned by `qemu-system-x86`, and after it Xid 69, with no process. Windows logged event 153 only at 04:06:48 and 04:39:38 in that time, so both errors belong to these two crashes. Which record belongs to which crash is not settled, since the journal does not keep every error. Neither is Xid 8 or 109, the timeouts.

The decoded header, both journal records, the four process records and the Xids of the earlier dumps are in [84-266a/watchdog-0439.txt](84-266a/watchdog-0439.txt). The 04:06:48 error left no live dump.

## Why no draw ran 2 s before the reset

Mesa 26.0.8's D3D12 driver gives a screen one command queue, `screen->cmdqueue`, and every context's batch is submitted to it (`src/gallium/drivers/d3d12/d3d12_batch.cpp:311`, SHA-256 2ca7a1614c1537b473bcc46476ef8506703d02dd02913dd917ca9f9fe4cb157d); virglrenderer draws every guest context on that one screen. A queue completes its work in order, so a guest readback waits for every command submitted before it. In the 2 s before each reset, the guest read back images and checked them, 104,779 checks of `shaderbuiltinvar.html` in the rerun and the end of `samplerobject.html` in loop a's run, at the pages' usual speed. Had this QEMU's queue held work that did not finish for 2 s, those readbacks would have waited for the reset and read black. A page fault resets the engine when it happens, which fits the guest's record: right readbacks up to the page change, black ones after, and no stall between.

## What is not known

* The command that faulted. A page change ends the page's WebGL context and the iframe's objects and starts the next page's, so buffers, textures and samplers are freed and made there; a fault at that moment fits a GPU address used after its memory was freed, in Mesa's D3D12 driver or the NVIDIA driver, but no trace shows it. QEMU ran without virgl tracing, and no guest has run the pages since.
* Why the two Rach2 runs fault within a page of each other and Debian's first pass did not. Debian's run was alone on the host on the older driver, and its error came 26 pages later in its again pass.
* No guest was started for this task: under the freeze one may start only while fewer than two loop guests run, and at 05:21 UTC+6 loop a ran three, a webgl2-09 case and two Debian guests.

The run that would name the command: pages 1655 to 1665 of chunk 6 alone in a Rach2 guest on virgl, with QEMU's `virtio_gpu_cmd_*` and `virgl_*` trace events on, as many times as it takes to fault, read against the same pages in the Debian guest.

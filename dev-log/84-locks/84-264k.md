# 84-264k: the PS/2 mouse probe's waits

QEMU's PS/2 mouse leaves two of the probe's commands unanswered, ALPS's EC report (0xEC after 0xE8 0x00) and the TrackPoint's read-ID (0xE1), and answers every other at once. The probe sent each three times, and waited half a second for each try, or 100,000 reads of the status, so it took 3.0 s of every boot under KVM, where each read is an exit, and 0.12 s under TCG, where 100,000 reads pass in milliseconds. It now waits as Linux's i8042 and libps2 do and takes 0.40 to 0.41 s on both accelerators and both architectures. Linux's own probe on the same QEMU takes 0.39 s and sends neither command, since its psmouse finds QEMU's VMware mouse (vmport) first, a protocol Rach2 names and does not drive.

## The runs

All on the testing PC's WSL, QEMU 10.2.1, on 2026-11-14 between 21:15 and 21:35 UTC+5, the kernel alone (`-kernel`, no RAM disk, which halts once it finds no root), one processor and 128 MiB, with QEMU's `ps2_write_mouse` and `memory_region_ops_read` trace events. The Debian 13 reference guest ran with `tests/graphics/debian-ref/debian-ref.sh run -l -c 1 -m 2048` under KVM, its QEMU wrapped to add the same trace events.

| Rach2 after, KVM, x86-64 | 0.408 s | 515 | sent once, 0.2 s, 88 reads |
| Rach2 after, TCG, x86-64 | 0.400 s | | |
| Rach2 after, KVM, i686 | 0.404 s | | |
| Rach2 after, TCG, i686 | 0.404 s | | |
| Debian 13, Linux 6.12, KVM | 0.388 s (serio1 found to its input device) | 163, the firmware's among them | none sent |

Debian's mouse took 14 bytes: GETID twice, RESET_DIS, RESET, then the rate 100, resolution 3, 1:1 scaling and enable that `vmmouse_init` and `psmouse_initialize` send, and it registered `VirtualPS/2 VMware VMMouse`. Rach2's probe sends about 150 bytes to reach `ImExPS/2 Generic Explorer Mouse`, which `machine.input.mouse` expects; each costs three or four reads of the status, which is where its 515 reads go beside the 176 of the two waits.

## What changed

* `i8042.c`: a wait of the controller reads the status and waits 50 us, at most 10,000 times, Linux's `i8042_wait_read` and `i8042_wait_write`.
* `ps2mouse.c`: a byte is sent again once after the mouse asks for it again, and never after a timeout, as `ps2_do_sendbyte` does. Its ACK may take 200 ms, the reset's a second; a byte of an answer half a second, the reset's 0xAA four seconds and its ID 100 ms after it, as `__ps2_command` and `ps2_adjust_timeout` wait. Linux sleeps on the interrupt for the reply; Rach2's bring-up runs with interrupts off and polls, reading the status again after an eighth of the time waited so far, at least 50 us and at most a tick, so that a reply that comes is taken within an eighth of its time and one that never comes costs 89 reads in 200 ms. Inside a run of commands a wait of a tick sleeps.
* `machine.input.mouse` checks that `mouse: ready` follows `mouse: started` by less than 0.6 s of the kernel's stamps, fewer than three of Linux's 200 ms waits.

## Left

A driver for QEMU's VMware mouse would take off the last 0.4 s and about 350 reads a boot, as Linux's probe on QEMU shows, and would change the mouse that `machine.input.mouse` and the desktop cases find on QEMU from an Explorer to an absolute pointer. It is not part of this task.

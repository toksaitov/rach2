# 84-33: the KVM suite's eight failures in the rehearsal

The manager's x86-64 rehearsal at 49a8d23f5 failed eight cases of the KVM suite: five went past the 40-minute gap bound (`boot-rach2-nested`, `selftests`, `selftests-nested`, `unit-tests`, `unit-tests-nested`), and `entry`, `fuzz` and `leak` failed their checks. At the head of this task every one of them passes. The causes are below, each with its fix; none of them is in code that the -O2 build compiles differently.

## The runs

Every run was on the testing PC under WSL's KVM, with `RACH2_QEMU_ACCEL=kvm ARCH=x86_64 RACH2_MIN_FREE_GIB=25` and `RACH2_CASES` naming the cases. The first, at the head with no change of this task's, gave:

* `boot-rach2-nested`: `kvm-boot: result: pass: KVMRACH2 OK after 20 s`. It passed in each later run too, in 20 to 269 s, so the rehearsal's hang did not recur at the head. The rehearsal's evidence is in the testing account, which this account cannot read; with no hang to split, the -O0 comparison was not run.
* `entry`: `svm-entry: fail: resource 5: 190 before, 185 after`, the system's open file descriptions.
* `fuzz`: `DRMFUZZ FAIL: nobody could not open /dev/kvm at API version 12`.
* `leak`: `kvm-leak: result: fail`, with QEMU killed at `leak.sh` line 65 as the test intends.
* `selftests` and `selftests-nested`: stopped past the gap bound of 2,400 s; `unit-tests` and `unit-tests-nested`: stopped with the run.

## The causes

### The GNU image did not build

`tools/inspect/setid.allow` pinned the GNU root's `/etc/group` without the `kvm` group that the udmabuf change added, so check-setid refused every x86-64 GNU image. The pinned text now has `kvm:x:202:desktop,test`; the manager's fix of the same line reached the milestone branch as well, and the merge keeps one.

### The desktop's udevd and session

The GNU root's init starts `/usr/libexec/rach2-desktop`, which runs systemd-udevd. Debian's rule (`50-udev-default.rules:111`) gives `/dev/kvm` group `kvm` and mode 0660 when udev reaches it, so drmfuzz's child, uid 65534 with no groups, could not open it, and the desktop session opened and closed files while `entry` counted the system's open file descriptions. Each KVM case now ends the desktop first with `NET_END_DESKTOP` (`tests/cases/machine/netcase.h`), which the graphics cases share: it makes the supervisor unrunnable on the case's overlay, so that init does not start it again, ends it with SIGTERM and waits until it and every weston have gone. drmfuzz's child keeps the group of `/dev/kvm` when udev gave it one, as a Debian user who may use KVM belongs to `kvm`.

### ntpd's query socket

`leak` still failed after that, at 140 against 139 and 142 against 141, in each of three full runs and in none of four runs of fewer cases. A listing of every process's descriptors at both counts showed the one that moved: fd 4 of BusyBox's ntpd, socket 6 at the first count and socket 48 at the second. BusyBox 1.36.1's ntpd opens a UDP socket for each query (`networking/ntpd.c:904`) and closes it when the send fails (line 963) or no reply comes in RESPONSE_INTERVAL, 16 s (lines 2528-2529); the machine has no network card, so no reply ever comes. Whether a count falls inside a query's socket depends on where in its cycle the case starts, which the load of the other cases shifts.

The case's stage step now removes `/etc/ntp.conf` from the overlay, without which init does not start ntpd again (`utils/init.c`, `ntp_servers`), ends ntpd and waits until `pidof` no longer finds it; ntpd's comm is `busybox`, so it is found by its argv[0]. With that, the counts were 138 and 138, and ntpd was gone. `leak.sh` and `svm-entry` take each count once two reads a second apart agree, which a file held for a moment needs, and `leak.sh` lists each process's descriptors beside each other when its count of files fails.

An earlier commit of this task named etude-guest's exec pipe as the file held; that pipe is read and closed in `spawn` before the command's own first line runs, so it never reaches a count.

### No progress for 40 minutes

Each corpus case was one run step, and the gap bound counts witness records, not output, so a corpus that passed test after test for 40 minutes was stopped. `corpus.sh` now prints `kvm-corpus: tests: M` and `kvm-corpus: done: N of M` on standard output as each test ends, and the five corpus cases report the progress `test` on that line (`corpus_run` in `tests/cases/machine/kvm_scenario.c`). In the last full run before the ntpd fix the longest gap was 680 s, in `unit-subset-nested`, and the longest case 1,356 s, `selftests`.

### Six selftests at their default sizes

`max_guest_memory_test` touches 128 GiB at its default, and five more touch a gigabyte or more. Two hypervisors deep, Linux as the host took 484 s for `max_guest_memory_test` at 4 GiB (81-26), so the defaults would take hours under either system. `selftests.list` runs the six at the sizes of `selftests-gap.list`.

### SIGUSR1 ended dirty_log_test

`dirty_log_test` blocks SIGUSR1 in its vCPU thread and lets it through only during KVM_RUN, with KVM_SET_SIGNAL_MASK; its main thread kicks the vCPU with it. Rach2 began the end of the process at the signal's post whenever the thread's mask let the signal through at the default action, so the kick killed the test. Linux keeps the old mask in `real_blocked` for the run (`virt/kvm/kvm_main.c:3668-3689`, `kvm_sigset_activate`), and `complete_signal` does not end the process for a signal that `real_blocked` holds (`kernel/signal.c:1034-1037`). `vcpu_run` (`rach2/sys/kvm/vcpu.c`) now keeps the old mask in `sig_real_blocked` for the run, which `sig_fatal_now` already checks, so that the signal ends KVM_RUN with -EINTR and stays pending. `dirty_log_test,-i,4` passed in both selftests cases after it.

### What Linux at the same depth does not pass

Two selftests and five kvm-unit-tests fail or do not finish under Linux as the KVM host of the same nested machine (81-25, 81-26), for the outer layers' reasons:

* `memslot_perf_test` fails under any hypervisor: its RW case writes each page of its area between two of the host's syncs, each a nested exit there, and the program's `alarm(10)` ends it first, as under Linux (Rach2 made about 1,290 such writes a second and Linux 1,570). It is `hypervisor?fail:pass`.
* `x86_64/fix_hypercall_test` fails wherever the machine runs under KVM: Linux's KVM beneath takes the nested guest's #UD as its own guest's intercept (`arch/x86/kvm/svm/nested.c:1540-1545`, with vmcb01's #UD intercept, `svm.c:1248`), emulates the VMCALL (`x86.c:7313-7337`) and patches it under its own guest's quirk (`x86.c:9719-9740`), so the #UD that `disable_quirk` waits for never reaches Rach2, or a Linux in its place. It is `outer_kvm?fail:pass`; the fault is recorded in [upstream.md](upstream.md).
* kvm-unit-tests' `debug` and `xapic` did not finish in 900 s under Linux at this depth, and under Rach2 `debug` had not ended 924 s after it began, in both unit-tests cases, when that run was stopped: they are `outer_kvm?excluded:pass`. `la57`, `pcid-disabled` and `x2apic` fail under both with the same subtests: they are `outer_kvm?fail:pass` in `unit-tests.list` and in `unit-subset.list`.

The new flag `outer_kvm` holds where the case's site runs the machine under KVM, which the scenario passes to `corpus.sh` as `KVM_CORPUS_OUTER` from `etude_case_accel`.

### Two selftests that compare clocks

`x86_64/apic_bus_clock_test` failed once in `selftests`, at a divisor of 128: "Frequency = 34630469 (wanted 23750000 - 26250000)". `x86_64/hyperv_clock` failed once in the final run's `selftests`: `hyperv_clock.c:76: delta_ns * 100 < (t2 - t1) * 100`. Each compares the guest's TSC with a clock that KVM reads in an exit: `apic_bus_clock_test` counts the APIC timer down over a 100 ms `udelay` between a write of TMICT and a read of TMCCT (`apic_bus_clock_test.c:73-91`), and requires 5%; `hyperv_clock` reads HV_X64_MSR_TIME_REF_COUNT around 10^8 NOPs, about 25 ms, bracketing each read by two RDTSCs (`hyperv_clock.c:51-76`), and requires 1%. A delay between KVM's read of its clock and the guest's next instruction counts in one and not the other, so at this depth a stall of the outer host decides the result.

A list of each program 40 times, run by both selftests cases at once, failed 4 of 80 in `selftests` and 2 of 80 in `selftests-nested`, with frequencies from 16% low to 7% high, stalls of about 8 to 16 ms. Then `selftests-nested` and `linux-corpus.sh`, Debian's Linux 6.12.107 as the KVM host of the same machine on the same `host-svm` processor, ran the same lists at the same time: 80 runs each, Rach2 failing 1 and Linux none, and 200 runs each, Rach2 failing 4 and Linux 2, one of each program. Of 280 runs each, Rach2 failed 5 and Linux 2, which so few failures do not tell apart. Both rows are `outer_kvm?excluded:pass`: they run where Rach2 is not inside a machine of KVM, as on the Lenovo.

### Under the Mac's TCG

The Mac's release runs the corpora inside a machine of TCG, the one run that settles each row's `hypervisor` branch without `outer_kvm`. The rule for a row there is Linux as the host of the same machine: a test is expected to fail only where Linux fails it too, and the row names how. toksaitov-v's runs for 84-37 found two rows wrong there:

* `debug`: under TCG Rach2 and Linux 6.12 as the host both fail `MOV SS + watchpoint + ICEBP`, 24 of 25 passing. The row is `outer_kvm?excluded:hypervisor?fail:pass`, which keeps the Lenovo's pass of all 25 (81-3).
* `access`: under TCG every permutation fails with QEMU TCG's `error code 8 expected 9`, under either host, and each failure prints some 250 bytes, a serial exit to the inner QEMU a byte. With run_tests.sh's TIMEOUT at 300 s, `access` alone, both hosts at once on the testing PC: Linux's run ended by itself after 64 s and 1,600 failures, its output cut in a line and no message from the Linux host, as when the guest dies; Rach2's printed 4,710 failures in 300 s and was ended by the timeout. Neither host ends the test, so its row is `outer_kvm?pass:hypervisor?excluded:pass`, in `unit-subset.list` too.

Rach2 printed those failures at 15.7 a second and Linux at 25: Rach2's round trip through the inner QEMU for each byte takes about 1.6 times Linux's under TCG. That is the cost of the whole trip, the exit, KVM_RUN's return, QEMU's write of the byte to its pipe and the next entry, with every instruction emulated; which part of it is Rach2's longer path is not yet measured, and it decides no row.

Not done here: a run of the whole of `unit-tests.list` and `selftests.list` under TCG on both hosts, which would settle each other row's branch for the Mac. The rows that `outer_kvm` settles under the testing PC's KVM (`la57`, `pcid-disabled`, `x2apic`, `xapic`, `fix_hypercall_test` and the two clock selftests) settle to `pass` under TCG without a run there.

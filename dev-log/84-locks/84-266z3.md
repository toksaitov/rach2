# 84-266z3: QEMU's abort at 240 GL contexts in Firefox's WebGL 1.0.4 chunk 00

`machine.virgl.webgl-firefox-webgl1-00` failed in the release's third rerun (run 43665453124, at f6dc157af) when QEMU died with libepoxy's "Couldn't find current GLX or EGL context" at 10:08. The cause is the host fault that [77-vgpu's upstream record](../77-vgpu/upstream.md#virglrenderer-draws-in-a-sub-context-whose-gl-context-could-not-be-made) describes: the testing PC refuses a 241st EGL context, virglrenderer draws on in the sub-context it could not make, and the first GL entry point libepoxy resolves with no context current aborts QEMU. Firefox keeps the WebGL context of each finished page, and with it a GL context of the host's, until the browser ends, and one Firefox running the chunk's 250 pages brings QEMU to 235 or 240 in some runs, in the Debian guest as in Rach2's. Rach2 has no fault here. The virgl cases now start a new Firefox every 100 pages, `webgl.sh -n 100`, which keeps both guests near 110.

## The count

`eglcount.so` ([84-266z3/eglcount.c](84-266z3/eglcount.c)) is a library preloaded into QEMU that hands libepoxy wrappers of `eglCreateContext` and `eglDestroyContext` in place of the real calls, which it looks up with `dlsym`, and logs each call with the contexts alive. [84-266z3/qemu-system-x86_64](84-266z3/qemu-system-x86_64) runs QEMU with it, its log in `EGLCOUNT_DIR/egl.PID`; it leads `PATH` for `debian-ref.sh` and etude, which run QEMU by name:

    gcc -O1 -g -Wall -fPIC -shared -o build/tmp/egl/eglcount.so dev-log/84-locks/84-266z3/eglcount.c -ldl -lpthread
    PATH=$PWD/dev-log/84-locks/84-266z3:$PATH EGLCOUNT_SO=$PWD/build/tmp/egl/eglcount.so \
        EGLCOUNT_DIR=$PWD/build/tmp/egl/rach2 ARCH=x86_64 RACH2_QEMU_ACCEL=kvm \
        RACH2_CASES=machine.virgl.webgl-firefox-webgl1-00 tests/run virgl

Three runs of the chunk in each guest, at e52a38fdf, beside the release's own virgl cases ([84-266z3/contexts.txt](84-266z3/contexts.txt)):

| Run | Peak alive | Destroyed by then | Result |
| --- | --- | --- | --- |
| Debian 1 | 235 | 69 | pass |
| Debian 2 | 203 | 133 | pass |
| Debian 3 | 240 | 55 | QEMU aborted, as in the release |
| Rach2 1 | 240 | 59 | QEMU aborted, as in the release |
| Rach2 2 | 189 | 113 | pass |
| Rach2 3 | 120 | 56 | pass |

Both guests make as many contexts: 345 to 359 in a whole run, the page run again included, and the two failed runs ended after 295 and 299. What varies is how many of them Firefox has destroyed by then. Each run destroys 55 to 72 of the first 120 made, and then, in a run that fails, two at most of the next 175; a collection that frees more on the way, 77 at once in Debian's second run, keeps a run below the bound. Debian's third run failed its creation at 240 alive after 295 made, QEMU's last lines being virglrenderer's "Failed to complete framebuffer 0x0" and the same assertion, so a Linux guest sends the same sequence and ends QEMU the same way. The release's Debian reference passed the chunk by the luck of its collector.

## The change

`webgl.sh -n PAGES` gives each browser at most PAGES of the chunk's pages, the next browser taking the pages after them or those it left, and the record names it as `pages per browser`. `graphics_scenario.c` passes `-n 100` for Firefox's virgl chunks; Chromium shares a few contexts among its pages and runs each chunk in one browser as before. With it the chunk ran in browsers of 100, 100 and 50 pages:

| Run | Peak alive | Made | Result |
| --- | --- | --- | --- |
| Debian, `-n 100` | 105 | 358 | pass, 244 pages pass, the reference's results page by page |
| Rach2, `-n 100` | 120 | 359 | pass |

A page's verdict does not depend on the pages run before it in its browser, as the reruns of failed pages in a new browser already assume, so the references, taken with one browser for each chunk, stand.

Firefox's `webgl.max-contexts` and `webgl.max-contexts-per-principal` do not bound the host's count: 77-vgpu's runs with both at 16 still ended QEMU in three of four.

# 5665: the USB mouse, virtio block and hvc cases under KVM

Task 5661's full run under KVM, `t5661-kvm` in loop a's clone, failed `machine.input.usb-mouse` on i686 and x86_64, `guest.vblk.read` on x86_64 and `guest.hvc.ports` on i686; each passed under TCG. Two of the three are assumptions of the tests that held only under TCG, and one is a difference of the kernel's `/proc/interrupts` from Linux's. Loop a's kept workspaces were not readable from this account, so each failure was made again here.

## machine.input.usb-mouse: a test assumption

Run alone under KVM, the case failed on both architectures as in 5661, waiting for `EVPROBE: mouse: packet 2 read`. A boot driven by hand under KVM with QMP's `query-mice` showed the cause. Under KVM the kernel finds the VMware backdoor and turns VMMouse on, as Linux's `vmmouse_detect` does on KVM, and QEMU makes VMMouse its current pointer. QEMU gives each `input-send-event` to the handler last made current of those that take the event's kind. VMMouse takes absolute motion and buttons, so the motion of 10 and 5, relative, went to the USB mouse and was packet 1, and the left button's press went to VMMouse and never reached the USB mouse. Under TCG the kernel does not turn VMMouse on, and the USB mouse is the only pointer that takes buttons.

The fix gives the USB mouse's and the tablet's machines no i8042 (`"i8042": false`), and with it no PS/2 mouse and no VMMouse, as `machine.usb`'s mouse case already has. By hand with `-machine i8042=off`, `query-mice` listed the USB mouse alone and current, and evprobe read all five packets. The tablet passed in 5661's run, but by the same race: in a hand-driven boot under KVM the tablet was current, but VMMouse takes absolute motion too, so the tablet case gets the same machine.

## guest.hvc.ports: a test assumption and a missing drain

Under KVM the case failed on both architectures, `tty-out` reading `hvc-tty??`. The host's file of the virtconsole had `hvc-tty` and a carriage return and newline, but only after the records of port 3's addition: the line reached the port when the next program ran. hvcmusl's `tty` mode writes the line to `/dev/hvc0`'s terminal and exits. khvcd, the driver's thread, moves a terminal's output to the port, and the write wakes it. The debug shell, to which the mode exits, runs no thread, as the driver's Readme says under Limits. Under TCG the mode's close, open of `/dev/vport0p0` and exit took longer than a tick, which switched it out for khvcd; under KVM they end within the 4 ms tick. Linux's `hvc_write` pushes the bytes to the port in the write, and `tcdrain` would wait for them, but this kernel has neither the push nor `TCSBRK`.

A first fix had the mode sleep 100 ms after the line. On the owner's order the test has no sleep, and the kernel has the drain it lacked. TCSBRK, musl's tcdrain, and TCSBRKP wait until the terminal's device has taken its output, and so do TCSETSW and TCSETSF and their termios2 forms before they install, as Linux's `tty_wait_until_sent`. TIOCOUTQ gives the count waited for, as Linux's `tty_chars_in_buffer`. A terminal counts its output through a new `outq` of `struct tty`. An hvc terminal's is the bytes in its pair's ring and those khvcd took and has not handed to the port (`k_held`, `pty_kernel_sent`), and its fall to 0 wakes the slave's queue. The console hands each byte to the screen and COM1 in the write, and Linux's pty has no `chars_in_buffer`, so the console and a pty slave count none and their drain returns at once, as on Linux. A signal ends the wait with EINTR; TCSBRK's is never restarted, as Linux returns EINTR, and TCSETSW's restarts under SA_RESTART, as Linux's ERESTARTSYS. No terminal here sends a break, so TCSBRK with 0 and TCSBRKP return 0, as Linux's do for a driver without `break_ctl`.

hvcmusl's `tty` mode now calls tcdrain after its line and checks that TIOCOUTQ then reads 0. A further row interrupts a drain. hvcmusl and a child run at SCHED_FIFO 99 on the case's one processor. hvcmusl writes 1024 bytes and calls tcdrain, which blocks; only then the child runs, sends SIGUSR1 and drops to SCHED_FIFO 1, where its spin keeps khvcd, an ordinary thread, off the processor. The drain must fail with EINTR, though the handler has SA_RESTART, and TIOCOUTQ must count bytes still held. Once the child is killed, a drain returns 0 and TIOCOUTQ reads 0. musl's sched_setscheduler fails with ENOSYS, so the mode makes the system call itself.

## guest.vblk.read: the kernel's /proc/interrupts

Run alone, the case passed five times in five under KVM on both architectures, and once more beside the other two. `vblkprobe` now prints its counts: 2 vectors for the first disk and 64 completions, a request and an interrupt for each 32 KiB read of each disk, against the bound of 16. Each disk's 33 reads of `/proc/diskstats`, 2,049 sectors, are the boot's one sector and 32 reads of 64 sectors.

The load made it certain. Six boots of the case's machine by hand at once, with two busy loops, all on two of the host's processors (`taskset -c 30,31`), failed two of six, each with "fewer than two vectors" and 64 completions. In both, `/proc/interrupts` had one line for virtio0: its one vector had taken the boot's read and all 32 of the reader's, and the other queue's vector had taken none. The driver gives each processor a queue, and the reader of disk0 had run on the processor of the boot's read. The kernel listed only vectors that had taken an interrupt, where Linux's `show_interrupts` lists each interrupt with a handler, at a count of 0 too. On the probe's machine every reader of a disk can run on one processor whatever the accelerator; a loaded host made it the usual case.

The fix lists each vector that has a handler or a count (`procfs_gen_interrupts`). `intrprobe`'s check on a machine with no USB device, which took a line of the controller's message vector for a message taken, now requires its count to be 0. proc(5) and acpi(4) say so. With the fix the same six loaded boots passed six of six, each with 3 vectors for virtio0, its two queues' and its configuration's.

* After the fixes, at 9ae08500ff with this note: the three cases five times under KVM, five in five on each architecture, and once under TCG, passed on each architecture; `machine.input.usb-tablet` once under each, passed on both; and `intrprobe`'s cases, `machine.usb.msi`, `nomsi`, `msi-drop` and `msi-lines` and `machine.audio.hda`, once under each, passed on both.

* With the drain, at b7d5a5f38f: `guest.hvc.ports` five times under KVM, five in five on each architecture, and once under TCG, passed on each; on the ia32 profile (`RACH2_KERNEL=ia32 ARCH=i686`) under KVM, passed once. The first run of the interrupted drain failed on musl's sched_setscheduler, ENOSYS, before the system call replaced it.
* `machine.input.usb-mouse` on the ia32 profile, which loop a's run `t5661-ia32` also failed: five in five under KVM and once under TCG, passed.

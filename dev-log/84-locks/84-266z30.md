# 84-266z30: arb_query_buffer_object@qbo, a flake of Mesa's on Haswell

The release's sixth rerun at 3ffd553f6 failed the Lenovo's native `gpu/piglit-arb2` on one subtest of 12,550:

    judge: worse: spec@arb_query_buffer_object@qbo@query-gl_any_samples_passed_conservative-async_cpu_read_after-gl_unsigned_int64_arb: warn here, pass in the reference

The same subtest passed in step 9's one run of Linux on the Lenovo and in the earlier Lenovo runs of the case that day. Mesa's own CI on Linux lists `spec@arb_query_buffer_object@qbo` among crocus's flakes on Haswell, the Lenovo's GPU and driver, so the Lenovo's piglit cases now leave that test and its subtests unjudged, as the virgl and lavapipe cases leave Mesa's named flakes. No kernel change follows.

## What the subtest checks

piglit's `qbo.c` at Debian's revision af62c0dea draws a rectangle inside an occlusion query, loads the query buffer with 0xcccccccc, asks for the query's availability into the buffer's offset 8 and its result without waiting into offset 0, then reads the result on the CPU with a wait. The CPU result must be exactly 1. A fragment shader then reads the buffer as a uniform block and draws green when the buffer's availability is 0 or 1 and its result equals the CPU's, or is still 0xcccccccc while unavailable. A wrong CPU result or a probe that is not green returns `PIGLIT_WARN` for every query type but the geometry shader statistics, so `warn` says only that one of the two checks failed. The output that would say which is in the run's `quick-arb2.json` on the Lenovo, which this task could not read.

## Where the result comes from

In crocus (Mesa 25.0.7, `crocus_query.c`) both checks are of values the GPU writes in its command order. `crocus_end_query` writes the depth count with a PIPE_CONTROL and then `snapshots_landed` with another, ordered after it. The availability request flushes the batch and has the next one copy `snapshots_landed` into the buffer. The result request computes the result on the CPU when it already sees `snapshots_landed`, and otherwise has the GPU compute `end - start` with MI_MATH and store it under a predicate loaded from `snapshots_landed`; only the CPU branch is followed by a CS stall. The CPU's wait in `crocus_get_query_result` loops on `snapshots_landed` around `crocus_wait_syncobj`, so a fence that signalled early would only make it loop again, not read an unfinished result.

The kernel's share is the coherence of the query's buffer between the CPU and the GPU and the waits. Rach2's i915 gives every new object `I915_CACHE_LLC` on Haswell (`i915_gem.c`, as Linux's `shmem_object_init` on an LLC part), so a CPU read of the mapped buffer sees the GPU's writes through the LLC, and GEM_WAIT and SET_DOMAIN wait on every fence of the object's reservation (`i915_gem_object_wait` with `all` set), as Linux's do.

## Linux's evidence

Mesa added `spec@arb_query_buffer_object@qbo` to `src/gallium/drivers/crocus/ci/crocus-hsw-flakes.txt` in commit fd8e31198866 ("crocus: sync performance monitor code with iris", merge request 18099), and the line is in the file at the tag `mesa-25.0.7`, the Mesa both Debian's root and Rach2's carry. Mesa's CI runs that list on Haswell machines under Linux, and deqp-runner takes each line as a regular expression over the names, so the test's subtests are flakes there too. The same CI's `crocus-hsw-fails.txt` names the eight timestamp and time-elapsed subtests that step 9's run warned, so the reference's other non-passes are Mesa's on Linux as well.

Step 9's run is one run beside three other tests; it says the subtest passed once, not that it always passes on Linux.

## The change

[`tests/graphics/piglit-lenovo.flakes`](../../tests/graphics/piglit-lenovo.flakes) names `^spec@arb_query_buffer_object@qbo(@|$)`, with Mesa's file as its reason. The five piglit cases of `tests/native/gpu.cases` stage it, and `tests/graphics/runners/lenovo.sh` gives it to `judge.py results` as FLAKES, after an empty SAMPLE, which keeps the whole reference. The test's 271 rows go unjudged on the Lenovo; the other 71 rows of `arb_query_buffer_object` are judged as before. A judge of the failing subtest's row as `warn` against the expectations gave `1 worse` without the file and `0 worse, 271 flakes named` with it.

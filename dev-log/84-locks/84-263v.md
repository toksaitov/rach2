# 84-263v: what crashpad reads of a live Chromium child, on Rach2 and on Debian

Crashpad's handler, attached to a live Chromium child under KVM, reads the same maps, the same module list and the same register sets on Rach2 as on Debian 13, and writes an equally complete minidump on both. Four things differed, each a Rach2 fault, each fixed here with a row that fails without the fix: `/proc/PID/mem` refused every `PROT_NONE` page, which Linux reads by its forced access; the debug registers read and took values Linux does not give; the auxiliary vector of an x86-64 program lacked `AT_HWCAP`, `AT_HWCAP2`, `AT_FLAGS` and `AT_PLATFORM`, and `AT_MINSIGSTKSZ` was 0xd1e where Linux gives 0xd30; and the program's bss past its file showed in `/proc/PID/maps` as the program's file where Linux shows anonymous memory. A fifth, `AT_HWCAP2`, is 0 on Rach2 and 0x2 on Debian, whose kernel lets programs use `RDFSBASE` and its kin; enabling them needs a change of the kernel's entry code first, which is left to the manager. Whether the release run's crashpad errors under TCG come from these faults or from a crash of its own is not yet settled, as below.

## How it was read

[crashread.c](84-263v/crashread.c) reads a process as crashpad's Linux handler does: it attaches every thread with `PTRACE_ATTACH`, parses `/proc/PID/maps`, reads the auxiliary vector and the vDSO, walks `r_debug`'s link map from the program's `DT_DEBUG` and matches each module to its mappings as crashpad's `MemoryMap::FindFilePossibleMmapStarts` does, reads each thread's `NT_PRSTATUS` (216 bytes, x86-64's `user_regs_struct`), `NT_PRFPREG` (512), `NT_X86_XSTATE`, `NT_386_TLS`, `PTRACE_GETREGS`, `PTRACE_GETFPREGS`, the debug registers through `PTRACE_PEEKUSER`, `ARCH_GET_FS` and `PTRACE_GETSIGINFO`, reads 64 KiB of each stack, and reads every mapping's pages through `/proc/PID/mem` with `pread64`, all of a mapping of 512 pages or fewer and a sample of a larger one. `crashread -f PID` makes the main thread jump to address 0x10, a real `SIGSEGV` with `SEGV_MAPERR`, which crashpad then dumps. [crashprobe.py](84-263v/crashprobe.py) ran beside the sandbox case's browser, `tests/graphics/browser/run.sh chromium sandbox`, as root, through a hook in `sandbox.py` that was never committed: it read the GPU process, a renderer, the network service and the browser, then crashed the GPU process and the renderer, timed each to its end and summarized the dumps crashpad wrote under the user's `~/.config/chromium/Crash Reports`.

Debian 13 ran in the reference guest, `tests/graphics/browser/debian.sh chromium sandbox`, kernel 6.12.115+deb13.1-amd64 with Yama's `ptrace_scope` 0; Rach2 ran the case `machine.browser.chromium-sandbox` on x86-64, kernel 6.18.0-rach2. Both were under KVM on the testing PC, an AMD Ryzen 9 7950X3D, with `-cpu host` and the same Chromium 156.0.8078.79 packages, on 2026-11-15 near 00:50 UTC+6.

The one link map entry no mapping matches is the vDSO's, on both. `PTRACE_GETREGS` gave the same bytes as `NT_PRSTATUS`, `ARCH_GET_FS` the same `fs_base`, and each thread's `rip`, `rsp` and `fs_base` lay in a mapping, on both. The network service and the browser agreed in the same way (102 of 103 and 127 of 128 on Debian, 128 of 129 on Rach2, whose browser had one module more loaded at the moment it was read).

Three differences are not faults. A single `rw-p` anonymous page that both refuse is a guard page glibc 2.44's thread stacks install with `MADV_GUARD_INSTALL`, which Linux 6.18 on the host also refuses with EIO; Debian's glibc 2.41 installs none. Rach2's `[vvar]` is 2 pages and its `[vdso]` 1, Debian's 4 and 2, and both refuse `[vvar]`. Reading the maps took 18 to 23 ms on Rach2 and 1 to 2 ms on Debian, slower but not wrong.

## What differed, and the fixes

`/proc/PID/mem` of a `PROT_NONE` page. Debian read all of them: 13328 pages in 83 mappings of the GPU process, 20030 in 118 of the renderer's, 2824 in 25 of the network service's. Rach2 answered EIO for every one: 13301 pages in 72 mappings, 17930 in 99 and 2778 in 15. Linux's `/proc/PID/mem` and `PTRACE_PEEKDATA` use `FOLL_FORCE`, under which `check_vma_flags` (mm/gup.c) lets a read reach a region without `VM_READ` that has `VM_MAYREAD`, and a write reach one without `VM_WRITE` that is a private, copy-on-write mapping. Chromium reserves its V8 cage and PartitionAlloc's pools as `PROT_NONE`, so crashpad's reads of pointers into them came back short. `paging_access` now takes `PAGING_ACCESS_FORCE`, which ptrace and `/proc/PID/mem` pass and the core file and `process_vm_readv` do not: an untouched private anonymous page reads as zeros, as Linux's zero page, and any other page is backed by a fault whose entry keeps `PROT_NONE`, so the tracee itself still cannot touch it. The rows `proc-mem-protnone` and `peek-poke-protnone` of ptracemusl read a page of 'n', an untouched page and the program's own first page mapped `PROT_NONE`, and poke a word into the child's page while the parent's copy keeps its 'n'.

The debug registers. Before any write Debian read DR6 as 0xffff0ff0 and DR7 as 0; Rach2 read 0 and 0x400. Linux keeps DR6 as `virtual_dr6`, with the reserved bits flipped so that 0 reads as the register's value after reset, and DR7 as `ptrace_dr7`, the value last written, its general-detect and reserved bits among them, which `ptrace_write_dr7` masks off only for the hardware; Rach2 refused such a DR7 with EINVAL. Linux's exec clears all of them (`flush_ptrace_hw_breakpoint`); Rach2's kept them across the exec. `debugreg.c` now keeps both as Linux does and `exec_commit` clears them. The rows `debugreg-initial`, `dr6-peekuser`, `dr7-reserved-kept`, which leaves DR7 with bits 12 and 13, and on x86-64 bit 32, set while the tracee runs through the rows after, and `exec-debugreg-clear` replace `dr7-bit12-einval` and `dr7-bit32-einval`, which asserted the refusal. Linux also keeps a tracee's breakpoints after `PTRACE_DETACH`, where Rach2 clears them; crashpad never sets one, and that rule is left as it is.

The auxiliary vector. Debian's had 23 entries: `AT_SYSINFO_EHDR`, `AT_MINSIGSTKSZ` 0xd30, `AT_HWCAP` 0x178bfbff, `AT_PAGESZ`, `AT_CLKTCK`, `AT_PHDR`, `AT_PHENT`, `AT_PHNUM`, `AT_BASE`, `AT_FLAGS` 0, `AT_ENTRY`, the four ids, `AT_SECURE`, `AT_RANDOM`, `AT_HWCAP2` 0x2, `AT_EXECFN`, `AT_PLATFORM` "x86_64", `AT_RSEQ_FEATURE_SIZE` and `AT_RSEQ_ALIGN`. Rach2's had 19, without `AT_HWCAP`, `AT_FLAGS`, `AT_HWCAP2` and `AT_PLATFORM`, which it gave only to an i386 program, and with `AT_MINSIGSTKSZ` 0xd1e. Now every program has the four. `AT_MINSIGSTKSZ` was the bytes Rach2's own frames take, where Linux gives the bound `init_sigframe_size` computes once at boot: `sizeof(struct sigframe_ia32)`, 15, the state of `fpu__get_fpstate_size`, the XSAVE size of 2432 bytes both kernels report with its 4-byte end mark and 112 bytes of x87 state, and 63, rounded up to 16. The x86-64 kernel's compiler lays the i386 frame out in 736 bytes, not the 732 an i386 program sees, since the `u64` in its `struct _fpx_sw_bytes` aligns it to 8: 736 + 15 + 2548 + 63 is 3362, rounded to 3376, 0xd30, the "max sigframe size: 3376" Debian's kernel logs at boot; an i386 kernel's 732 gives 0xd20. Debian enabled no PKRU (XCR0 0xe7, no `pku` flag). `sigframe_stack_bytes` now gives the larger of its frames' need and that bound, through `fpu_linux_state_bytes`: 0xd30 on the x86-64 kernel, to i386 programs too, and 0xd20 on the i686 kernel. The auxvprobe rows `hwcap`, `hwcap2`, `flags` and `platform` check the four, and `minsigstksz` computes Linux's bound from `cpuid` leaf 0xD and the kernel's architecture.

`AT_HWCAP2` is the one difference left. Debian's 0x2 is `HWCAP2_FSGSBASE`: its kernel sets CR4.FSGSBASE, so that a program may run `RDFSBASE`, `WRFSBASE`, `RDGSBASE` and `WRGSBASE`; Rach2 does not set it, gives 0, and such an instruction raises `SIGILL`, as on a Linux booted with `nofsgsbase`. Rach2 cannot simply turn it on. Its paranoid entry, which the NMI, the double fault, the machine check and the debug exception take, judges whose GS base is loaded by the sign of the GS base MSR, and with the instructions open a program could load a kernel address into GS's base; its context switch would also have to read back the bases a program wrote without a system call, and ptrace read them live. Linux changed its paranoid entry to save and load GS's base with the instructions themselves before it enabled them (5.9). That is a change of the entry code beyond this task, and is left to the manager. Crashpad, glibc and Chromium do not use the instructions.

The bss in `/proc/PID/maps`. Debian showed the pages of Chromium's bss past its file as anonymous, `00:00 0` with no path; Rach2 named them with the program's path, device and inode (`rw-p 00000000 f0:04 16607 /usr/lib/chromium/chromium`). Linux's loader maps them with `vm_brk_flags`, an anonymous mapping. `elf_add_vmas` now makes those pages `VM_ANON`; a segment the loader copied whole, which Linux never does, keeps its one region. procprobe's row `maps-bss-anonymous` reads the line of a page of its own bss.

## After the fixes

The same probe ran again on both near 01:40 UTC+6 with the fixed kernel. Rach2 read every `PROT_NONE` page, as Debian did: 13285 pages in 72 mappings of the GPU process, 17914 in 99 of the renderer's, 2778 in 15 of the network service's and 10353 in 59 of the browser's, against Debian's 13352 in 83, 20065 in 117, 2824 in 25 and 9809 in 90. Each process read DR0 to DR7 as 0 but DR6, 0xffff0ff0, on both. Both auxiliary vectors had the same 23 types; Rach2's `AT_MINSIGSTKSZ` was still 0xd20, which the change to Linux's bound described above, made after this run, takes to 0xd30, and its `AT_HWCAP2` 0. Chromium's bss showed as `rw-p 00000000 00:00 0` on both. The pages neither could read were Debian's 4 of `[vvar]` in each process, and Rach2's 2 of `[vvar]` and 14 guard pages of glibc 2.44's thread stacks. Crashpad's dumps of the crashed GPU process and renderer had 134 and 103 modules on both, 12 and 18 threads on Debian and 12 and 13 on Rach2, each the processes' own count.

## The crashes under TCG

Not done. The owner's freeze of 2026-11-15 cut the task to landing these fixes. The kept evidence of the release run is gone, since the runner cleared its `_temp` when the job ended, and naming what crashed needs the webgl cases of x86_64:virgl run again. The release's second rerun, with these fixes, decides it: if those cases pass, the task closes; if they fail, it becomes why that Chromium child crashes.

## The rows

The new rows ran in QEMU under KVM on both architectures, `RACH2_CASES="guest.default.ptracemusl guest.default.auxvprobe guest.default.procprobe"` through `tests/run default`. On the kernel before the fixes, with the new tests, they failed on i686 and x86-64 alike: auxvprobe's `minsigstksz` (0xd1e), `hwcap`, `hwcap2`, `flags` and `platform`; procprobe's `maps-bss-anonymous`; and ptracemusl's `proc-mem-protnone`, `/proc/PID/mem` answering EIO (errno 5), where ptracemusl stops. With every fix but the debug registers' (`debugreg.c` and the clearing at exec held back), `proc-mem-protnone` and `peek-poke-protnone` passed and `debugreg-initial` failed on both. With all of them the three cases passed on both, each of their rows, `minsigstksz` reading 0xd20 on the i686 kernel and 0xd30 on the x86-64 kernel, as Linux's bound gives for each.

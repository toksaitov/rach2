# Milestone 37: writing FAT32

The kernel writes a FAT32 volume: every operation a shell expects, in an order of writes that a crash at any sector boundary leaves consistent, with a check at the next mount that repairs what that order can leave behind and refuses what it cannot. Under it, the buffer cache writes through for metadata and back for data, a failed write puts the mounts on its device read-only, and a periodic process syncs what nothing else did. The procedure for the Lenovo's fourth partition is written and rehearsed on the sealed image; nothing touched the machine.

## What was built

`sys/fs/bcache.c` writes as well as reads: `bcache_write` reaches the device before it returns, so the order in which a driver writes metadata is the order on the disk; `bcache_dirty` marks data for writeback at eviction, `fsync`, `sync` and the thirty-second `/bin/update` process that every init starts, since the kernel's timer cannot sleep and the kernel has no thread of its own. A failed write is recorded against the device: every mount on it goes read-only for the rest of its life with a log record naming the sector, and there is no finer policy because a write-back cache cannot return a later failure to the `write(2)` that dirtied the buffer. `rach2.blockfail=N` fails the Nth write through the lag device so a boot can see the transition.

`sys/fs/fat32.c` is the writer, 3218 lines against 1066 for the reader. Every mutation runs under the mount's namespace lock, which is re-entrant by holder because the unmount calls `sync` and a namespace change puts a node, and the driver asserts the lock at every mutation, so a caller without it fails on the first write and not in a race. The order of writes is fixed and documented: an entry never names a free cluster, a crash may leak clusters and never cross-link them; an extension allocates a chain of its own, writes and syncs the data, then joins it and grows the size; a directory grows with a zeroed, ended cluster before the link; unlink frees the entry first and the chain at the last `put`. The dirty flag is set in both places before the first metadata write and cleared only by a clean unmount; FSInfo is written at `sync`, unmount and after a check; both FATs are written, active first. Names are `fat32name.c`, apart from the driver so the host test reads them alone: the UTF-8 to UTF-16 check, the Windows NT short rule with the case bits, and this driver's own alias rule, which says where it agrees with mtools and where it does not. `setattr` stores the times and the read-only attribute and answers `EPERM` for what the format cannot hold. A dirty volume is walked before its mount is published: a surplus tail, orphan long-name entries and a lagging mirror are repaired in an order a second crash cannot make worse; a cross-link, a loop, a chain shorter than its size or a duplicate name mounts read-only with the fault named. The interface gained `path`, so a directory descriptor follows its directory's rename; the generic arms of `unlink`, `mkdir`, `rmdir`, `rename` and `open(O_CREAT)` lock the namespace and create on any writable type, and a create that loses the race to another opens what the winner made.

`tests/host/mkfatfixture.c` gained `--check`, an independent walk of a FAT32 image that names every fault the driver's order can and cannot leave, and nineteen fixtures for the check and the driver. `fatwriteprobe` and `lagprobe writers` are the machine's rows; `tests/run fatwrite` and `tests/run scratch` are the suites; `rach2-recovery-iso` is the stick's image. `dev-log/37-fatwrite/hardware.md` is the fourth partition's procedure under the disk rule.

## What running it found

The rows found, before any review: a write through an unlinked file's description rewrote its freed entry, so a later create found the name twice; a failed run allocation left its partial chain behind; the interruption matrix carried dirty buffers from one stop into the next fixture; a directory grew with a cluster zero-filled for writeback, so the link could reach the disk before the zeros, which only a junk-filled fixture showed; the syscall layer still refused `open(O_CREAT)` on every type but the root; the kernel log has no `%u`; mtools refuses a boot sector with no geometry; the alias walked UTF-8 bytes and turned one character into three underscores; a directory descriptor could not follow a rename without a `path` operation; the rename arm, and then the unlink, mkdir and rmdir arms, ran the type's operation outside the namespace lock; the unmount deadlocked on its own lock; FSInfo's count was stale after a repair; `lagprobe` took `write` for `writers`; and the recovery stick had no disk until its boot line named the AHCI controller. Each is in `notes.md` with the row that found it.

## What the review found

Six review units read the milestone, four of them against the final tree, and returned thirty findings; every one is fixed or recorded with its reason in `notes.md`. The serious ones: a surplus-tail repair that freed another file's clusters when the tail ran into a chain the walk had not reached yet; a sync that returned over a dirty buffer another process held, and an unmount that ignored the cache's refusal to drop such a buffer; a failed victim write that never woke the waiters for the buffer's old key; a device whose mounts went read-only while a writer was inside an operation, which the cache now stops at its next metadata write; a truncate that published zeros it had not written; a rename that destroyed its destination before finding it had no room for the new name; `ENOSPC` decided by writing part of a run; a directory that could be renamed under itself; a held directory that kept a stale entry location; two creators who could make one name twice; a read-only decision taken before the lock; a check whose free count skipped the clusters it had just freed; and a probe whose failure token was never printed, so the suite's `--never` rows could not fire. Eight rows came with the fixes, each proved by mutation.

## Verification

`tests/run host` runs the writer through every operation as a sequence on a fresh volume, then stops each sequence after every one of its writes and walks the image, which may show only what the order of writes allows; the crash state is mounted read-only and every file must read what was written or zeros, which is the oracle a size published before its data would fail. The matrix runs with short names and again with long names spanning a sector. The dirty rows mount each state the order leaves behind and require the repair; the name test runs the rules alone against the cases recorded from mtools; the check test runs `--check` over every fixture. `tests/run mount` is nine boots, the ninth a write the device fails. `tests/run fatwrite` is six boots: a program writes files of every kind and unmounts, the host walks the volume and reads it with mtools and with `fsck.fat` where it exists, the next boot reads every byte back, a boot killed inside a write sequence is followed by the mount's check, BusyBox writes through the shell, and two writers and a sync run under the lag device with the driver's assertion at every mutation. `tests/run scratch` boots the recovery ISO as a stick beside the sealed image, saves every sector the fourth partition will cover, makes recovery the saved boot default, writes the new sector 0 through `reflash`, undoes it from the saved copy and writes it again, writes and checks the volume, and boots the ordinary system to write the partition and put the boot default back. Twenty-eight mutations, each from a restoring script that rebuilt before the verdict, were each caught by a named row.

A passing run proves that the driver's order of writes holds at every sector boundary one process can stop at, that the check repairs what that order leaves and refuses what it does not, that the cache's promises hold under the fake device and the lag device, and that the fourth partition's procedure runs end to end in QEMU. It does not prove a torn sector or a disk that acknowledges and loses a write, which the host's check judges afterwards; it does not prove two processes interleaving anywhere but at a sleep, which the lock excludes; and it does not prove the Lenovo, whose disk stays in its bay until milestone 43 runs the rehearsed procedure with the owner's approval of the named target. The full set ran on the final tree in 9 minutes 0 seconds, against 8 minutes 53 seconds at the close of milestone 36, and `make test` in 4 minutes 17 seconds against 4 minutes 10 seconds; the first full run found the three things `notes.md` records under phase 6, fixed before the rerun, and the rerun found a row of milestone 33's raw-socket probe that had passed by timing, fixed and rerun alone after it.

`syscall.c` is 11648 lines against 11603 at the close of milestone 36: the arm locks and the create retry. The KRFFS fast paths beside the generic arms were not folded in this milestone, whose plan did not include them; they remain the weight that a later milestone removes.

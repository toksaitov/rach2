# Milestone 55: notes

## Where the work stands

On 2026-10-02 the plan's seven phases were built, each item of milestone 54's open lists in a commit of its own, and the GNU root was installed on the Lenovo and used there as a user for seven hours, from 15:55 to 22:55. ## The machine

The GNU root built from the seven phases was installed on the Lenovo at 15:55 with `rach2-install --update` from the recovery system, and its kernel through `bootctl`, and the machine was then used as a user would use it until 22:55, with the root reinstalled on the way from the builds of the fixes it found. The gnu suite's rows ran on the machine first. Then each ported program and each tool of the GNU root with its common flags, as root and as the account `test`: coreutils, diffutils, patch and the text tools, find, grep, sed and gawk, the archivers and compressors, Git over HTTPS and SSH with its rebase, stash, worktree, bisect and gc, curl and wget, OpenSSH's clients with a jump host, agent forwarding, forwards both ways, a SOCKS proxy and a control master, OpenSSL's keys, ciphers, client and server, Perl and its modules, SQLite's modes, bash's arrays, coprocesses, traps and job control, GCC with shared objects, threads, static links, sanitizers, coverage and profiling, G++ with C++20, GDB and GNU make, Lua and GNU hello built from their tarballs and jq from a clone, Python with asyncio, ctypes, multiprocessing's three start methods, a pty, a virtual environment, pip and HTTPS, GnuPG's keys, signatures and encryption with a passphrase through pinentry, nano, Vim, less, the manual and info in tmux, rsync locally and over SSH, strace and lsof, cron, procps-ng and util-linux, iproute2, ping and nc, D-Bus, the time zones and locales, the e2fsprogs tools on a volume in a file through a loop device, tmpfs mounts, the account tools as root, the headless browser on a page, a local server and the internet, Chawan on the same, and the clock against the CMOS clock under memory exhaustion.

Each fault was fixed when it was found, and each fix is proved by a row, a host test or a fault entry that fails under a fault:

* The clock fell 16 seconds behind the CMOS clock while memory ran out, since a page fault that reclaims runs with interrupts off and the timer's ticks were lost; on a machine whose TSC runs at one rate and no hypervisor, the timer counts the ticks it missed from the TSC (82f10254). The Lenovo's clock stayed within a second of the CMOS clock through the same test.
* A process that ran out of memory took SIGSEGV, and a handler that returned faulted again; it is ended with SIGKILL, as Linux's OOM killer ends one (ae0a7fa5).
* A server bound to 127.0.0.1 listened on every address and answered the network, so an `ssh -L` forward or a development server meant for the machine was open to the LAN, and a connection to 127.0.0.1 came from the interface's address: `bind` keeps the address it is given, a socket takes only what arrives for it, 127/8 is the machine's and leaves from 127.0.0.1, and a datagram from the wire to 127/8 is dropped (9ef7046b). `lo` is listed after the cards, with 127.0.0.1/8 and the loopback ring's traffic (e180215d).
* `mount --bind` was refused: a bind mount shows a directory of a mounted file system elsewhere, with `MS_REC` and a bind's own read-only remount, and a file is one file through both mounts for locks, watches, FIFOs, socket files and shared mappings (f41be247, f3561457).
* Python compiled each module of its library again at every import by a user, 1.8 seconds for `multiprocessing.pool`: the image gives every file the time 1, which made each byte-code file stale; the byte code records a hash of its source instead, and the import takes 0.3 seconds (4d655e54).
* glibc tried `clone3` before `clone` for every thread and fell back on `ENOSYS`; the kernel takes it (cbfa1879).
* `ip netconf` was refused (49339c41).
* A `configure` with a prefix of the user's own could not guess the build, since autoconf reads the root's site file only from its prefix; `/etc/profile` names it (b59ea017). GNU hello 2.12.2 then configured and failed to compile, as it does with this glibc on Linux: its gnulib predates the C23 type-generic `memchr`.
* bash's `pwd` failed for a user in a directory the user may not search, as `su` from root's home leaves one; `shopt -s lastpipe` turned a pipeline's exit status into a signal's, `true | false` giving 129; `printf %a` was refused; and `kill -l 40` named nothing. A cross build cannot run configure's tests of these, and its guesses were not Linux's; the recipe gives them (d94dc628). `open` of a file in such a directory's subdirectory was EACCES where `stat` of it was not (c835075f), and a user `su` had left in root's home could not stat a file below it (128b4acc).
* `ulimit -f` was accepted and ignored; writes and truncations stop at it with EFBIG and SIGXFSZ (733ff6e7).
* `losetup` and `mount -o loop` found no loop devices: they have Linux's numbers and nodes, Linux's loop ioctls with autoclear, and `/dev/loop-control` (ae44a234), and `blockdev` its queries (ac13f93f, 7f5e5c14).
* A pipe held 4096 bytes, so a write of more waited for the reader and was split where Linux's 64 KiB takes it whole, and Chawan's loader stopped on Wikipedia's article on Unix with a failed assertion that it had registered one output twice; a pipe holds 64 KiB, taken from the heap at its first write, and the article renders (4886e84a).
* Another user could read the links in root's `/proc/PID/fd`, whose directory was refused, so `lsof` run by `test` showed the SSH server's socket; the links and the `fdinfo` files are refused as the directory is (c70e7058). That check then stopped the browser's sandbox, and showed a fault under it: a descriptor of a `/proc` directory recorded its process by the kernel's number, which a name relative to it read as one of the caller's PID namespace, so inside a namespace it reached another process; it records the namespace's number (bbd958f2).
* `lslocks` exited at once: `/proc/locks` lists the advisory locks in Linux's columns (75a99788).
* `/proc/net/arp` had the hardware addresses in capitals and the IP addresses unpadded, where Linux pads the address to 16 characters and writes lowercase (a3ccdf89).
* Each breakpoint GDB hit was logged as a fatal user exception: a fault is logged only when no handler and no tracer will see its signal (0ddd53a9).
* crond logged an error at its start and at every change of a crontab, since the root had no `/etc/crontab` and no `/etc/cron.d` (176b875a), and `useradd -m` reported a mailbox it could not create, which `/etc/default/useradd` turns off, since the system delivers no mail (482f8e7b). `pwck` refused the root's account files, since `/etc/shadow` had no line for `sshd`, `messagebus` and `nobody`: the root gives each system account a locked line (65ecc0b6), and an update gives a kept system account without a line the image's (6943328b).

What the sitting found that is not a fault of Rach2: `mesg` and `watch` without a terminal fail as on Linux; `ls .` in a directory the user may not search is EACCES, as on Linux; gnulib's guesses in a cross build choose its own correct replacements of glibc's functions; a test of the sitting's own called `setuid` before `setgid`, since C leaves the order of arguments open; `script`, `ssh` and `cha` read the rest of a script given on their standard input; `zdump -c` prints the transitions only with `-v`; Python 3.14 starts a process by its fork server, which imports the main module again and needs the main guard; GCC names a data file of `--coverage` after the program since GCC 11, so `gcov m.c` finds none; ext2 keeps whole seconds, as Linux's ext2 does, so `make` does not see a header touched in the second its objects were made; and `hostname -I` is not BusyBox's option.

What it leaves open, each with its reason:

* `/dev/mqueue`: the POSIX queues work through their calls, and no program of either root lists them as files; util-linux's `lsipc` asks for the mount and lists the System V objects without it.
* Each file operation on ext2 waits for its own disk flush, which milestone 54 kept for durability; a tar of 34 MB of headers takes nine seconds, three thousand empty files take five, and an update restores a home of many small files slowly.
* The browser's 206 MB program is read again at each start, about a second, since the block cache stops at half the kernel heap.
* A pseudo-terminal belongs to its user's group, not to a group `tty`, so there is no `write`; `wall` is root's.
* The kernel's name is Rach2, which `config.guess` does not know; whether it should be Linux is the owner's decision, as milestone 54 recorded.
* A tmpfs takes `size=` and does nothing with it, and a tmpfs file stops at 1 GiB: tmpfs has no quota of its own, as its Readme says, and a limit would be a feature of shmem, the mount and the fault path. `fallocate` is EOPNOTSUPP on every type, which glibc's `posix_fallocate` answers by writing the range, as on Linux's ext2.
* ext2's file attributes: `lsattr` lists none and `chattr +i` or `+a` is EOPNOTSUPP, since the kernel takes no `FS_IOC_SETFLAGS` and enforces no immutable or append-only file.
* The boot disk's whole-disk node is published only with `rach2.diskdiag` or in recovery, a recorded policy, and a bind of a directory on KRFFS, whose nodes move, is refused.
* `ping` is Rach2's own and prints no `ttl=`, since its socket call returns the reply's length alone (ping.1).
* The GNU root's image is not reproducible to the byte: mandoc renders a page dated `$Mdocdate$`, tmux's, with the day of the build. render_man.sh can give such a page a fixed date.
* Programs a Debian user looks for that no port has: sudo, cmake, autoconf, automake, m4, flex and bison, jq, screen, dig and host. The owner's rule is to port what users expect day to day, without making the system Debian; a terminal browser drawn by Chromium or Firefox, carbonyl or browsh, waits for a framebuffer.

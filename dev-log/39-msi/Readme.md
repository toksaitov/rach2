# Milestone 39: the local APIC and message-signalled interrupts

The kernel enables the local APIC, takes the xHCI's and the audio controller's interrupts as messages instead of polling for them, and keeps the timer's pump behind both as the fallback for a message that never arrives. A keystroke on a USB keyboard now reaches its reader within about two milliseconds of the drain that took its event, instead of waiting for a tick up to ten milliseconds away. Nothing touched the Lenovo; what this milestone leaves for milestone 43 is a boot-line diagnostic and a record in the metal acceptance.

## What was built

`sys/lib/kcpu.c` is `cpuid`, `rdmsr` and `wrmsr` in one place, with the two feature bits the APIC driver reads. Three files had their own `cpuid` before it existed; all three now call this one.

`sys/apicdiag.c` is the `rach2.apicdiag` report, which reads and prints but writes nothing: the two `cpuid` bits, `IA32_APIC_BASE`, the APIC's identity, version, task priority, spurious register and its two local-vector entries, and the MSI and MSI-X capabilities of the two controllers this kernel drives by message. It runs from the boot line, so the report describes the machine it ran on, and milestone 43 runs it on the Lenovo before any kernel with MSI is installed there.

`sys/lapic.c` enables the APIC or refuses by name. It refuses a processor with no APIC, one without the model-specific registers, one in x2APIC mode, and a base address this kernel cannot reach or map; `rach2.nomsi` on the boot line refuses in the same way. The spurious register's software enable is written first, because a software-disabled APIC holds every local-vector entry masked and drops the write that would unmask one; the task priority and `LINT0` follow it. Straight after the tick starts, the boot checks that the 8259's interrupts still arrive: fifty milliseconds with no tick writes `LINT0` again and records it, and fifty more with no tick records that too.

`isr_handler.s` and `tables/idt.c` gained sixteen stubs and gates for vectors 48 to 63, and one for the APIC's spurious vector at 255, which without a gate would be a general-protection fault. `_irq_router` ends a message interrupt at the APIC after the handler chain has run, and then reschedules if it interrupted user mode or a context that is not inside a system call. `register_isr_handler` and `set_isr_handler` take the name the handler is known by, `/proc/interrupts` is new, and `/proc/stat`'s `intr` line, which said zero on every machine, is the count of every interrupt the kernel has routed.

`pci.c` programs a device's MSI capability in the order the specification requires and no other: the enable bit and the count of vectors cleared in one write, an MSI-X capability disabled beside it, the address and the data written while the mechanism is off, a per-vector mask cleared where the device has one, and the enable bit last. Every access to configuration space now runs with interrupts off, because this milestone put an interrupt handler on that path for the first time.

`usb.c` has one pump, turned by the controller's message and by the timer, with the interrupt flag left as each context found it; the handler acknowledges and drains in one call, and while the interrupter is on the drain writes the dequeue pointer back with the event-handler-busy bit even when it took nothing. How often the timer finds work that no message was coming for is counted and reported as `FBK` in `/proc/interrupts`; the question is put to the processor's request and in-service registers, not to the controller. `hda.c` takes vector 49 the same way and keeps its legacy line and its timer servicing exactly as they were.

`sys/pit.c` gained the clock the latency record needed: microseconds since the boot, from the periods of the 8254's counter and the position inside one. Neither source can be used alone. The counter says nothing about which period a reading belongs to, and two readings a period apart are in the same place in its sweep; the tick counts periods exactly but arrives a millisecond or two into the period it counts. Whichever of the two sees a wrap first counts it, and the other does not count it again.

## What running it found

Five things came out of the machine rather than the specification, and each changed the code. The controller raises no further interrupt while the event-handler-busy bit is set, so a handler whose drain found the ring already empty silenced it for good. The controller's own pending bit does not answer the question the fallback count asks, because it is set whether or not a message was sent; the processor's request register does. A wake is worth nothing if the woken reader does not run, and the reader that shows it is the one with another runnable process beside it. The kernel had no clock finer than its 10 ms tick. And the acknowledgement and the drain were made one call in the driver, which is a decision about what a test can catch: with them apart, no row could tell their order being reversed.

One defect outside this milestone's own work came out of it: a record raised by an interrupt handler while another record was being written out went to the ring and no further, so the USB suite's replug row failed about a third of the time. `klog` now queues such a record and the delivery it interrupted writes it out when its own line is finished.

## What the review found

Four units read the milestone before it closed, and every finding is fixed. Two defects would have shown on the Lenovo and not here.

`LINT0` was written before the spurious register's software enable. A processor whose APIC is software disabled holds every local-vector entry masked and ignores a write that would unmask one, so on a machine whose firmware left the APIC disabled the unmask would have been dropped and the 8259's interrupts would have stopped the moment the APIC came up. QEMU's firmware leaves `LINT0` already right, so the driver never wrote it there and the fault could not appear. The host test's model now holds the mask bit set while the APIC is disabled, which is what makes its order row mean anything.

The reschedule on the way out of a message vector asked whether the interrupted process was running, which let it preempt kernel code inside a system call whose own bookkeeping was half done: `schedule` sets a process READY and then runs on with interrupts on, and `sys_exit` marks a process a zombie before it signals its parent. A message taken in either window would have stranded a process for the life of the boot. The question is now the one the plan gave: the interrupted context is in user mode, or it is not inside a system call.

The rest: configuration space is reached through one address register that every access shares, and this milestone put an interrupt handler on that path, so every access runs with interrupts off; `pci_write_config16` was a read of the dword and a write of it back, which wrote the status word beside the command word and cleared every fault the bus had latched there, and is now one `outw`; the vector's own mask register was never written, so a device left with this vector masked would have been programmed, enabled and silent; a capability near the end of configuration space could have had its registers wrap onto the identity registers at offset zero; the two interrupter enables were set before the device's capability was programmed; a base above 4 GiB was truncated rather than refused; and the acknowledgement written at enable cleared a pending bit that was not this driver's to clear.

Six host rows and two suite boots proved nothing and were rebuilt: three refusal rows that checked one register instead of requiring no write at all, a `LINT0` row that could not tell a write from the firmware's own value, the empty-drain row whose own sequence cleared the busy bit first, the moderation-interval row that began with the register already zero, the boot for a mouse over messages that asserted only what the timer's pump would have done anyway, and the audio count that required a number rather than a rise across the notes. `lapic_pending` had no row at all.

## Verification

`tests/run host` runs two new host tests and the rows added to a third. `lapic_hosttest` drives the APIC driver against a model of the register page and the model-specific register: virtual wire, a masked `LINT0`, a `LINT0` that is not an external interrupt, the register's enable bit, each of the six refusals, the end-of-interrupt, the spurious counter, the repair, `lapic_pending`, and the order of the writes. `pcimsi_hosttest` drives `pci_msi_enable` against a model of configuration space that clears its status bits when they are written as one: a 32-bit capability on a device firmware left enabled, a 64-bit one with a stale upper address, a device that masks its own vectors, a capability that runs past the end of its space, MSI-X disabled first, the two refusals, the disable, the halfword write, and the order of the writes. `xhci_hosttest` gained the interrupter: the moderation interval a firmware left behind, the two enables, the acknowledgement that keeps the enable beside it, the dequeue pointer written with the busy bit so that the next event raises an interrupt of its own, an empty drain that still writes it, and an event written between the acknowledgement and the drain.

`tests/run usb` is fourteen boots, six of them this milestone's: the counts in `/proc/interrupts` after keys typed on messages, the same machine with `rach2.nomsi`, a mouse whose reports are counted on the vector, the four stamps of one keystroke's path, a machine silenced after three messages by `rach2.msidrop` that goes on typing on the timer's pump, and the 8259's own keyboard and timer with the APIC between them and the processor. `tests/run audio` requires the count on the audio controller's vector to have grown across the notes, and `tests/run procfiles` reads `/proc/interrupts` and `/proc/stat` on the machine and checks the timer's line and the sum of the vectors against `intr`.

Every check added here was proved by a mutation that makes it fail: six for the APIC and the MSI capability in phase 2, seven for the interrupt path in phase 3, three for the two `/proc` files, three for the clock, three for the log's queue, three for `LINT0` and the boot check that repairs it, one for the audio count, one for the mouse's, and four more for what the review round added. One mutation is recorded as not caught and cannot be: a handler registered on a vector the device does not send degrades to the legacy line this design keeps behind the messages, which is the behaviour the machine had before this milestone, and no row can tell the two apart without taking that line away.

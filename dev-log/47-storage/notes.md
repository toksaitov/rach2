# Milestone 47: notes

The record of the work as it went, phase by phase. The plan is `plan.md`; the accepted result is `Readme.md`.

## Phase 1: the registry

The registry is `rach2/sys/block/disk.c` with `disk.h`: up to eight disks, numbered in the order the drivers register them, each with its whole-disk device, transport and location, the IDENTIFY strings, the partition table state and entries, a partition view per non-empty entry, a whole-disk view for `/dev/diskN`, and the raw writer's reservation for that disk. `block_probe` scans every registered disk's first sector after the driver probe; the boot disk's views are then re-set from the table the root was chosen by, over the lag device when `rach2.blocklag` asks for one, so the nodes and the root come from one read of sector 0.

AHCI keeps up to four disks per controller, each with its own command list, received-FIS area and command table; the reset points every port at a scratch pair nothing reads, and each kept port is started with its own areas. A port that fails to start or identify is stopped and skipped with a record. The ATA driver registers its one disk. `block0` is the first disk's device, so the boot paths are unchanged.

devfs makes the nodes when a disk registers: `/dev/diskN` and `/dev/diskNp1` to `p4`, one vtable, listed while the window is published. Disk 0 keeps its minors, 1 and 4 to 7; disk N takes minors from 64 + 8N. Inodes are the table's entries first, then the disk nodes in registration order. The writer reservation is per disk; the claims are compared on the physical disk as before.

`/proc/disk` keeps its record of disk 0 and then prints one `disk N TRANSPORT LOCATION SECTORS TABLE MODEL` line per registered disk.

Proof: `tests/run disks` (new, core) boots two AHCI disks of 64 MiB and 20 MiB on one controller with `rach2.diskdiag`, and `disksprobe` requires both in `/proc/disk` with their ports and sizes, the nodes of both, no node for an absent partition or disk, and a partition of each mounted (KRFFS, FAT32), written and read back; the host then reads the FAT32 file with `mtype`. The mutation that keeps only the first port in the AHCI scan makes the suite fail; restored and rebuilt, it passes. The disk suites (`disk`, `disk-ahci`, `disk-q35`, `bootpart`, `diskdiag`, `mount`, `persist`, `persist-ahci`, `usbdisk`, `diskpolicy`, `procfiles`, `krffsmount`, `loopdev`, `ext2`, `fatwrite`, `exfat`, `sealed`, `install`, `grub`, `bootline`, `default`, `metal`, `diskfull`, `stress-ahci`) and the host tier pass unchanged.

## Phase 2: partitions and identity

The partition service is `rach2/sys/block/partition.c`: one reader for every disk, over a callback, so the host test drives it over disks in memory. An MBR gives its four primaries by position and the logical partitions of its extended entry from 5 in chain order, the chain bounded by `PART_MAX` and refused when it points outside the extended partition or back. A GPT gives every used entry with its GUIDs and its name from the primary header when it and its array check, else from the backup at the end of the disk, and a record says which served. Fifteen partitions are kept per disk; the rest are counted and logged. The registry cuts one view per entry and devfs names the nodes by the entry's number after every scan; `BLKRRPART` on a whole-disk node reads the table again, refused while a partition is claimed or another descriptor is open on the disk.

The root is named by identity: `rach2.root=PARTUUID=`, `MBRID=id,M`, `UUID=`, `LABEL=`, or `/dev/diskNpM`, with `rach2.rootfstype=` beside it when the type should be checked; every partition of every disk is compared and only one match mounts. `rach2.boot=` names the boot partition the same way; without it the boot windows are on the root's disk, else disk 0. The GRUB core searches for the boot partition by the label `RACH2BOOT` and the recovery partition by `RACH2RECOV`; the menu finds the kernel's partition by the FAT serial and passes the root and the boot partition by the MBR id. The core was regenerated through `regen_grub.sh` with the search modules added, the same container and snapshot, two rounds byte-identical. The tools grew: `mkmbr --id` and `:logical` entries, `mkgpt --seed`, `--damage-primary`, labels and fifteen entries, `grubembed` keeping the disk id.

Found on the way: the two-disk boot under SeaBIOS. SeaBIOS boots one hard disk, the one it calls its first, and a boot sector that returns to it with `int 18h` sends it to the floppy and the ROMs, not to the second disk. So the loader half of the swapped-disk proof is the disk on the second AHCI port booted by the firmware, which the kernel numbers disk 1; `hd0` in GRUB is the disk it booted from under every firmware this project has seen. The search is still what the core does, and the row proves the core finds the menu and the menu the kernel on a disk that is not the bus's first. The usbdisk suite's stick-boot row had the stick's size as a number, 45056 sectors; the ISO half grew past 6 MiB with the registry and the check now takes the size from the image.

Proof: `tests/run parts` (new, core): four AHCI disks, every disk and partition line of `/proc/disk` as built, the nodes as numbered, the backup served for the damaged clone and not for the sound disk, a logical FAT32 partition and a GPT one mounted and written, the rescan refused under the mount and done after it, both files read back by the host; then seven boots naming the root: by GUID, the same with the disks swapped, the same with the clone attached (ambiguous, nothing mounted), by MBR id and entry for a KRFFS root, by a label two disks share (ambiguous), by node, and by an identity no disk has. The mutation that takes the first match makes the ambiguous row fail; restored and rebuilt, the suite passes. `tests/run bootorder` (new, full): the GRUB disk behind a blank disk on the bus, booted by the firmware, its root found as disk 1 and the login reached. `partition_hosttest` in the host tier. The `disks`, `disk`, `disk-ahci`, `mount`, `usbdisk`, `grub`, `menu` and `install` suites pass on the change.

## Phase 3: the drivers

The ATA driver was rewritten for both channels and both drives: a channel is a pair of port ranges, legacy or from the controller's base registers when its prog-if says native, a drive is a bit of the drive register, and each drive that answers IDENTIFY with the disk signature is registered; a slave that answers as its master is the master's echo and skipped. Transfers are the 28-bit commands below sector 2^28 and the 48-bit ones above on a drive that has them, with the matching flush. Both drivers probe always, AHCI first, and the first disk found is `block0`; `rach2.disk=ahci` changes nothing now.

AHCI keeps one command active per port with a queue behind it. `ahci_start`, called after the root is mounted, takes a vector, enables the controller's messages and the ports' D2H and fatal interrupts, and switches each disk's device from fault-safe to `submit`; a request is a page in the window, one PRDT entry, a write the transfer and then a flush. The interrupt finishes the active request and starts the next. The polled `read` and `write` stay for the fault path and drain the port first: whatever command is active is finished by polling and its request completed, then the caller's command runs, and the queue resumes. `rach2.ahcipoll` keeps every transfer polled.

Two faults of my own on the way: the device queue first linked requests through the live list's `next`, which corrupted the list the moment two requests were live, and the crash showed as a jump to the BIOS reset vector; the queue has a link of its own now. And the partition views kept the flags and `submit` they were cut with, so every view cut at boot stayed polled after the switch; `block_flags` and the always-present forwarder fixed that, entry 8 of milestone 50. The raw windows' single staging buffer serialised two disks' readers, entry 7, fixed by staging through heap pages.

SeaBIOS boots one hard disk and returns to the floppy and the ROMs after `int 18h`, so a two-disk loader row under it can only vary the bus order, which `bootorder` does. QEMU's throttle group has a burst of one second's worth of bytes that cannot be made smaller than the rate, so the slow reader reads 1 MiB to get past it.

Proof: `tests/run bus` (new, full): four IDE drives of four sizes on both channels listed and each mounted and written, an AHCI and an IDE disk with the root named on each in turn, and a sparse 130 GiB IDE disk with its partition past sector 2^28 written and read back; the mutation that never chooses the 48-bit commands makes the last row fail. `tests/run queue` (new, core): a disk throttled to 256 KiB a second beside a fast one, the fast reader finishing in tens of milliseconds while the slow one reads for seconds, one read of its never waiting a slow transfer's time, the controller's vector counting the completions; and the fallback root's `blockprobe` beside a raw reader keeping a command queued on the same port, seven hundred raw reads landing between the faults. The mutation that leaves the driver polled makes the fast reader wait behind the slow disk.

## Phase 4: USB disks

A stick is a disk of the registry now. The class driver brings up every logical unit of a device, up to four, each with its own block device, and reads the capacity with `READ CAPACITY(16)` when the ten-byte answer is all ones, then moves data with the sixteen-byte commands on such a unit; eight devices at once. The disk layer registers each unit as it comes up, takes the lowest free number, and reads the table through the partition service; the service reads through a callback, so the pump, where there is no process to sleep, is given a cache of sectors it fetches a request at a time, and a pass of the service that asks for a sector the cache does not have is run again once the sector has arrived. A pulled stick hides its nodes at once, its caches are told, and it is reclaimed when the last hold goes, its number free for the next; a pull in the middle of the scan waits for the request in flight to answer before the scan is let go of. The whole-disk window of a stick is always published, since a stick without a table is mounted through it; the disk nodes are block devices now, all of them, with reads of any byte range, so `blkid` and `findfs` see every partition of every disk; and the recovery kernel writes a stick through its nodes as it writes a SATA disk. The raw USB windows, their table in devfs and `/dev/usbN` are gone; `/proc/usb` lists a stick as `diskN` with a 64-bit sector count.

Two things I got wrong on the way and the host test caught: a released record reused by a fresh stick was given a second set of nodes, and the scan of a pulled stick dropped a request the device still owned. The first row of the table read moved from a syscall entry back to the pump because a stick plugged into an idle machine would otherwise wait for the next syscall to appear, which the pull-and-replug row showed as a minute's delay.

Proof: the usbdisk suite unchanged in what it proves, its names changed to `disk0`, its GUID stick's nodes numbered by the table as `p7` and `p10`, its size line in MiB, and four rows added: three sticks at once, each mounted and read, then the middle one pulled while a reader keeps a command queued on its whole node, the read in flight answering `EIO`, the two beside it mounting and reading, the pulled one refusing to mount and reclaimed by name; the recovery kernel writing a pattern through `/dev/disk0` and reading it back, the host finding it on the image; a sparse stick of 2300 GiB with one partition past sector 2^32, listed at its size, its partition mounted, a file written and read back on the machine and on the host; and a `usb-bot` device with two units, each a disk with its own partition, both mounted. `usbdisk_hosttest` rewritten over the registry: the arrival, the table through the pump's cache across several requests for a GUID table, the pull under a hold, the reclaim, ten plugs and pulls on one record, the pull in mid-scan, two units, and the syscall entry's settle beside the pump's. `msc_hosttest` unchanged but for the slot row.

## Phase 5: sectors, volumes and files

The file offset of an open description is 64 bits, `_llseek` seeks an ordinary file anywhere below 2^63 and `lseek` answers `EOVERFLOW` for an offset it cannot return, and `ftruncate64`, the form musl calls, exists; it did not before, so `ftruncate` from any musl program had answered `ENOSYS`. Each file system refuses a write or a truncate past its own limit with `EFBIG` and names the limit in the log: ext2's is the reach of its pointers or the 32-bit `i_blocks`, whichever is smaller, 2095103 MiB at 4096-byte blocks; FAT32's is 4 GiB; exFAT's is the seek's own reach. ext2 stores the high half of a regular file's size and sets `large_file` in the superblock before the inode that needs it is stored; a file past 4 GiB, which the driver used to answer `EOVERFLOW` for, is an ordinary file now.

The ext2 descriptor table is taken from the heap at mount, `groups * 32` bytes, and the 128-group limit is gone. The check's state, its reached-inode set sized from the inode count and the block bitmap the FAT walks share, sized from the cluster or block count, come from the heap for the check's duration; `fat_walk_acquire` counts the free frames against the pages it needs and the reserve first, and a dirty volume the memory cannot hold mounts read-only with the reason, `the check's workspace is more than the free memory`, the KiB it needed in the log. The kernel's `_end` moved from 0x4831c4 to 0x3bf6c4 with the static state gone.

`resize_inode` is on in every image profile now, mke2fs's default, because it is what lets a grow keep the descriptor table in the reserve after each copy instead of moving blocks; the driver reads `s_reserved_gdt_blocks`, counts the reserve in the constructor's bound, and lets the resize inode's walk mark the reserved blocks, as `e2fsck` does; `setidcheck`'s reader and `mkext2.sh`'s superblock check take the feature.

Two faults of the driver's own came out on the way. `has_super` divided a group number by 3, 5 and 7 in turn and called the group a backup when 1 was left, so 15, 21 and 35 were taken for backups that mke2fs never wrote, and every volume of sixteen groups or more, 2 GiB at 4 KiB blocks, was refused as `group descriptor`; the sealed root has eight groups, which is why nothing had shown it; entry 9 of milestone 50, fixed here because the 5 GiB row cannot run without it, in the driver, `setidcheck` and `growset` alike, and the refusal names the group and the four numbers it judged now. And a whole block written through ext2 was read from the disk first; it takes a blank buffer now, as exFAT's did.

The port builds `resize2fs` beside `e2fsck`, 390816 bytes stripped, staged at `/sbin/resize2fs` on recovery. `growroot MBRID=ID,N` is the program that grows a root: the disk by its signature, read from sector 0 of every MBR disk `/proc/disk` lists, the entry by its number, primary only; the free space after the entry up to the next entry, the disk's end or the MBR's reach of 2^32 sectors; the entry rewritten with the LBA sentinel in its end CHS and the table read again through `BLKRRPART`; `e2fsck -f -p`, then `resize2fs`. An entry already at its size is left, so a run stopped after the entry finishes when run again, and a run stopped inside `resize2fs` leaves what the next run's checker repairs. The table write is refused outside the recovery kernel and the reread while the disk is in use, each reported as what it is. The memory it refuses below was measured by the grow of the 1 GiB root to the Lenovo-sized partition at every power of two of guest memory from 256 MiB down: the grow and the check of the grown volume finished at 16 MiB, `MemTotal` 7232 kB, and at 8 MiB the kernel does not boot (entry 12 of milestone 50), so 7 MiB is the number and no machine this system boots on is refused by it; resize2fs and e2fsck keep their bitmaps as runs, so a 931 GiB volume asks for little more than a 1 GiB one. Each grow took about three minutes, the zeroing of 7448 inode tables through the raw window, and `e2fsck -fn` on the grown volume about thirteen.

`growset [--lba START] [--map JSON] VOLUME SECTORS` computes the sectors a grow writes, from the superblock and the descriptors of the volume before it: the primary superblock, every backup copy with the descriptors and the reserve after it, both bitmaps of every group since `resize2fs` marks the whole bitmaps dirty and the library writes every one, the new groups' inode tables, the resize inode's double-indirect block and the inode-table block that holds it, and the table sector when `--lba` places the volume on a disk. It refuses a grow whose descriptors would outgrow the reserve. On the host, a 1 GiB volume grown to 8 GiB by the host's `resize2fs` changed 194 blocks, every one inside the set of 15376. `--map` reads `qemu-img map --output=json` of the overlay a grow ran in and requires every extent the overlay holds to lie inside the set; this is the save set milestone 50 needs.

The IDE driver refuses a drive whose IDENTIFY word 106 says its logical sector is not 512 bytes, by name, as the AHCI driver did; the plan allows the restriction while it is reported, and entry 11 of milestone 50 records it.

The disk path was the slow part of everything above. A 1 GiB file written through ext2 on the AHCI disk in QEMU went at 4 MiB/s, through exFAT at 1 MiB/s and falling, and a 5 GiB write took hours: the request layer moved one page per request, each a sleep until the controller's interrupt; the buffer cache found a block by walking its whole list, thousands of buffers on a machine with memory; an ext2 write wrote its bitmap byte, its descriptor and its pointer slot through for every block; and an exFAT append walked the file's chain from its first cluster because the write cleared the hint it had just made. Entries 10 and 13 of milestone 50 record them, and the owner's rule of 2026-09-07 fixed them here: a request moves up to the device's `max_sectors`, 64 on AHCI, in heap pages the command table describes page by page; the cache's sync writes a run of adjacent dirty blocks in one request through a staging buffer and finds a block through an index by device and block; an ext2 write marks its bitmap bytes, descriptors and pointer slots dirty and writes them at its end, the bitmaps and descriptors first, so no pointer reaches the disk before the bit of the block it names; the exFAT hint survives an append. Measured after on the same 1 GiB write: ext2 8 MiB/s, exFAT 10 MiB/s; the cache still walks its list for the hold rule and for the victim on every take, which is what entry 10 leaves. A request's deadline is thirty seconds now, the lag device keeping its five, since a host running two heavy machines answered late, not never, and the five-second stall turned a volume read-only twice (entry 14). And a KRFFS node whose id landed astride two units of the medium could not be created, which the mount suite showed once the staged probes' sizes moved the volume's free space there (entry 15): the id and the parent of a node no path reaches yet are written without the whole-unit rule.

The suites keep small defaults, the owner's rule of the same day: `large` writes 256 MiB unless `RACH2_LARGE_MIB` says otherwise and proves the 4 GiB line with a sparse ext2 file astride it, and `grow` grows on a 16 GiB disk unless `RACH2_GROW_LENOVO` is set; the recorded proofs ran the 5 GiB and the Lenovo-sized rows once.

Proof: `tests/run large` (new, full): GROW_LARGE_PROOF. `tests/run grow` (new, full): GROW_PROOF. `tests/run bus` gained the 4096-byte-sector disk refused by name on the IDE channel and on the AHCI controller with no node published. `ext2_hosttest` gained the file past 4 GiB stat'ed and opened, the write at the format's limit refused by name and the volume unchanged, a byte written at 4 GiB read back with the hole zero and the `large_file` flag set, the high size half read after a remount, and a dirty volume on a machine with no free frames mounted read-only by name with nothing written; the mutation that lets the walk take its bitmap on a machine with no free frames fails that row. The style, host, ext2, exfat, fatwrite and mount suites pass.

## The close

The full set from a clean tree lost `tests/run large` twice: a write waited out its deadline and the request layer declared the disk stalled. The deadline was widened from five seconds to thirty and then to two minutes, and the second run failed the same way, which said the request was not slow but lost. It was the third finding of the Codex review of the drivers, which I had left unfixed: the interrupt handler issued the next command before acknowledging the status this interrupt reported, so a command that finished quickly had its own completion bit cleared by that acknowledgement, and the next interrupt found nothing to do. The request then sat until its deadline. Acknowledging before the next command is issued fixed part of it, and the suite still lost its write in a pool of twenty machines while passing alone. That was the review's second finding on the same file: the polled path restarts the queue with interrupts on, so an interrupt could arrive between a request being published as the active one and its command being issued, find the slot's bit clear, and complete a request the disk had never seen; the queue then held requests nobody would start. Masking interrupts across the restart fixed it, and the six disk suites pass together.

The suite's own second boot had failed for a different reason, older than this milestone: `elf_load_image` kept its program headers in one static array, and a read of those headers from ext2 sleeps, so a second exec overwrote the first one's headers and the first failed with its image already destroyed, which the parent sees as a death by signal. A Codex rescue found it by instrumenting the loader and catching `login`'s headers turning into BusyBox's. The headers are per call now, and a host test that loads a second image inside the first one's read callback keeps it so.

### Engine recovery, 2026-09-07

`ahci_io_error` masks interrupts before stopping the command engine. If `PxCMD.CR` remains set after the bounded wait, it panics before completing the active request, restarting the queue, or returning a polled caller's buffer. The controller may still use both the buffer and the command table. A successful stop still clears the errors, restarts the engine and returns `EIO`. This fixes the fourth driver review finding; whether it also accounts for the pooled `large` failure remains untested.

`ahci_hosttest` models an engine whose `CR` bit stays set when `ST` is cleared. Four rows reach it: a fatal interrupt with the slot occupied, draining a queued command to its timeout, a fatal interrupt with the slot cleared, and a failed polled command. Each requires a panic with interrupts masked, no completion or new command, the same active request and queue, and the command table unchanged. The native test passed under AddressSanitizer and UndefinedBehaviorSanitizer. Replacing the panic with an interrupt restore and `return -EIO` made all four rows fail. Restoring the source, touching it and compiling the test again passed. ### Flush completion acknowledgement

A separate host-model row found that `ahci_finish_active` could issue and complete a write's flush before the handler acknowledged the write. The acknowledgement then cleared the flush's port status. The handler also cleared the controller's current status after issuing new commands, which could discard a new completion or another port's pending bit. `ahci_acknowledge` now clears a port's status and only its controller bit after judging the command, before issuing the flush or the next queued request. The handler no longer acknowledges the old command after issuing its successor. Successful and failed polled commands use the same acknowledgement before resuming the queue.

The model completes a flush and the next queued read inside the command-issue write. It requires both completion interrupts to remain pending, both requests to complete, and another port's controller bit to survive. Three more rows resume the queue after a polled success, a task-file error after completion, and a fatal error with the slot still occupied; each requires the predecessor's controller interrupt to be acknowledged before a queued command issues. The fixed source passed under AddressSanitizer and UndefinedBehaviorSanitizer. Compiling `8a12e5f`'s driver into the same test failed eleven assertions; restoring the fixed source, touching it and explicitly compiling again passed. The mutation ran in a separate source snapshot under a shell restoration trap, with foreground tests under the 60-second deadline tool. The script is `/tmp/rach2-47-close/flush-mutation.sh`; its complete logs are beside it. The working-tree driver matches the restored source byte for byte.

On the final source, `tests/run style host queue disk-ahci persist-ahci stress-ahci` rebuilt the kernel and images. `style`, `queue`, `disk-ahci`, `persist-ahci` and `stress-ahci` passed; `ahci_hosttest` passed, and the host suite failed only because `exfat_hosttest` could not create its external fixture. The final run's output and timing are `targeted-final.log` and `targeted-final.json` under `/tmp/rach2-47-close/`. No timeout or limit was widened.

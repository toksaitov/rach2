# 83-6: native context on Haswell

83-6b's check of the bed's matched native-context stack ([bed/nctx](../../bed/nctx/Readme.md)) in the usual direction, a Linux guest on a Linux host, on the only Haswell there is, the Lenovo. Native context works there: the guest's Mesa takes Crocus on the virtio-gpu node, and capsets, a triangle, 3 GiB of textures under memory pressure with eviction and rebinding, 10,000 separate submissions and fences all give what they give on Linux itself. A GPU hang is caught by the host, recovered, and a new context draws right, but the guest's robust context learns of the reset only after two more submissions, where Linux's own Crocus reports it at once; the cause is Mesa's ([upstream.md](upstream.md#crocus-asks-for-reset-statistics-past-the-virtio-path-so-a-guest-learns-of-a-reset-late)). The rung's entry condition, the graphics plan's risk 4, is met, and 83-6c may enter, with that delay expected.

## The session

* The host is the Lenovo's Debian 13.7 on p5, booted once through GRUB's `next_entry` by `tools/lenovo/debian-ref/mac.sh arm`, the route 80-2 used: Linux 6.12.115+deb13.1, `intel_iommu=off` on the boot line and `shmem_enabled` at `never`, the graphics plan's risk 15 settings, 16 GiB and 4 CPUs, the GPU 8086:0a16 under i915 on `/dev/dri/renderD128`. It left by `rtcwake -m off -s 120`, and `mac.sh restore` put p1 back.
* The guest is `nctx-alone.qcow2` (`bed/nctx/build.sh alone`) in a snapshot, under the bed's QEMU 11.1.2 and KVM, with 4 CPUs, 4 GiB of shared memfd memory, `virtio-vga-gl,blob=true,hostmem=4G,drm_native_context=on` and egl-headless on i915's render node. Its kernel is trixie-backports' 7.2.12, and its programs run on Mesa 26.1.6 through `nctx-env`.
* `bed/nctx/session.sh` runs each step on the host as root and writes `/srv/nctx/out/STEP.txt`; `nctxcheck.c` is the guest's program. The host's i915 events (objects made, bindings, unbindings, evictions, shrinker passes, requests) are counted by histogram triggers around each check, which drop nothing.
* No kernel was installed on the host. The subtask planned trixie-backports' kernel on p5's Debian for the session, but the guest image carries that kernel, the capset probe boots the host's own kernel as its guest, and the host's 6.12 i915 served every step, so p5's kernel stayed as it was. The session's setup added one package to p5, `busybox-static` 1:1.37.0-6+b9 for the probe's guest; everything else it needed was already there. p5 had 4.5 GB free before and after.

The first `pressure` run read the textures back only through the CPU: 208 bindings and 66 nodes evicted for 209 objects, every texel right, and no texture bound again, since a CPU read of a tiled texture goes through its mapping, not the GPU. The GPU copy pass, added in the session, binds each evicted texture again: the bindings rose to 378 and the evicted nodes to 176. Haswell's GPU address space holds 2 GiB, so 3 GiB of textures cannot stay bound at once.

The same `nctxcheck hang` run on the host itself, Crocus on i915 directly with Debian's Mesa 25.0.7 and with the bed's Mesa 26.1.6, gave the reset status guilty at once, after 5.91 to 6.54 s, with the same three lines from i915. The guest's QEMU did not abort when the guest powered off, since virglrenderer had started; the abort of [upstream.md](upstream.md#qemu-aborts-in-libepoxy-on-exit-after-virgl-fails-to-initialize) follows a failed start only.

### The reset notice

A trace of QEMU's ioctls on the host across the hang ([hang-strace-order.txt](83-6b/hang-strace-order.txt)) shows the guest's next submission refused by i915 with EIO, since Crocus makes its contexts unrecoverable and i915 bans one after a hang, and no `DRM_IOCTL_I915_GET_RESET_STATS` from the guest at all. Crocus asks for the statistics with `drmIoctl` (`src/gallium/drivers/crocus/crocus_batch.c:796` of Mesa 26.1.6), the only `drmIoctl` in Crocus's sources, where every other ioctl goes through `intel_ioctl` and so through the virtio path; on a virtio-gpu node the request goes to the guest's virtio-gpu driver, which has no such call, and Crocus reads no reset. The guest's submissions are asynchronous, so the first one after the hang returns at once and only the host sees its EIO, which virglrenderer records in the context's bit of `banned_ctx_mask` (`src/drm/i915/i915_ccmd.c:560-562` of virglrenderer 1.3.0); the second is refused by the guest's Mesa from that bit with EIO, and Crocus replaces its context and reports itself guilty. The context parameter that i915 refuses with ENODEV four times in the trace is the priority, which Haswell's i915 refuses natively too ([setparam-native.txt](83-6b/setparam-native.txt)).

## What 83-6c takes from this

* The reversed rung may enter: native context on Haswell works on the host side.
* Its fence-error check, on the same Mesa, should expect the reset to reach a robust context after two more submissions. Routing Crocus's query through `intel_ioctl` would make it one, since the guest asks the host only once the context's bit is set; at once, as on Linux, also needs the host to set the bit when the hung batch's fence fails, not on the next refused submission.
* The host's QEMU settings that worked: `drm_native_context=on` with `blob=true`, `hostmem=4G`, the guest's memory a shared memfd, and egl-headless on i915's render node.

## The step's commands

From the task's worktree on the Mac, under the Lenovo's lock, with `D() { sh tools/lenovo/debian-ref/mac.sh "$@"; }` and `N` the main clone's `build/cache/nctx`, which holds the three tars, `SHA256SUMS`, `nctx-alone.qcow2` with its `.sha256`, and the reference guest's key as `id_ed25519`, all brought from the testing PC's cache:

```
D arm; D wait-debian
D sh 'rm -rf /root/nctx /srv/nctx; mkdir -p /root/nctx /srv/nctx/in'
tar --no-xattrs --no-mac-metadata -cf - -C bed/nctx . | D sh 'tar xf - -C /root/nctx'
for f in SHA256SUMS id_ed25519 mesa-nctx.tar.xz virglrenderer-nctx.tar.xz qemu-nctx.tar.xz nctx-alone.qcow2; do D sh "cat > /srv/nctx/in/$f" < $N/$f; done
D sh 'cd /srv/nctx/in && sha256sum nctx-alone.qcow2'    # equal to $N/nctx-alone.qcow2.sha256
D sh 'sh /root/nctx/session.sh all /srv/nctx/in /srv/nctx/in/nctx-alone.qcow2'
D sh 'tar cf - -C /srv/nctx out' | tar xf - -C OUTDIR
D sh 'cp /root/nctx/session.sh /tmp/nctx-session.sh && rm -rf /root/nctx && sh /tmp/nctx-session.sh leave --now'
D wait-rach2    # then mixer vol 1 on Rach2
D restore       # p1's SHA-256 equal to the want
```

The session above ran the steps one by one rather than `all`, to read each before the next. Nothing plays sound, and the screen shows only Debian's console.

# Upstream faults of milestone 77

Faults this milestone found in another project's code, one section each, in the format of [dev-log/upstream.md](../upstream.md), which indexes them. Paths in the entries are relative to this directory.

## llvmpipe's JIT calls address 0 for a libm function the host program does not link

* Project: Mesa 26.0.8's llvmpipe and lavapipe, Ubuntu 26.04's 26.0.8-1ubuntu0.3 with LLVM 21.1.8, in the render server of Ubuntu's virglrenderer 1.2.0-2ubuntu2.
* Fails: a shader that llvmpipe compiles to a call of a scalar libm function calls address 0 when the host program does not itself link libm. Gallivm's MCJIT path leaves the functions it does not map itself (`src/gallium/auxiliary/gallivm/lp_bld_init.c:370` at `mesa-26.0.8`) to LLVM's `SectionMemoryManager` (`lp_bld_misc.cpp:628-633`), which looks them up in the process's global scope; `/usr/libexec/virgl_render_server` links only `libvulkan.so.1` and `libc.so.6`, so libm is there only as lavapipe's own dependency, opened locally by the Vulkan loader. The thread `vkr-ring-4` dies with "segfault at 0 ip 0000000000000000", having called through a register that holds 0 from compiled code, after a half-to-float conversion, a multiply and a negation. Which libm function, and why the failed lookup yields 0 and not an LLVM error, were not read.
* Found: 2026-11-09, the testing PC's WSL, milestone 77, task 77-7a, running VK-GL-CTS 1.4.1.1's `dEQP-VK.spirv_assembly.instruction.graphics.float_controls2.fp16.input_args.cosh_testedWithout_NotNaN_arg1_nan_arg2_one_res_nan_exec_vert` in a Debian 13 guest through Venus with Mesa 26.1.6, whose Venus offers `VK_KHR_shader_float_controls2`.
* Reproduction: start QEMU 10.2.1 with `virtio-vga-gl,venus=on,blob=on` over the host's lavapipe and run the case above in the guest; the render server dies each time and the guest's `deqp-vk` aborts in a queue submit. The same case passes when run directly on the host's lavapipe by `deqp-vk`, which links libm, and passes through Venus when QEMU runs with `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libm.so.6`.
* Evidence: `mesa-qualification.md`, "The host fault"; `mesa-qualification/out/host/render-server-segv.txt` (the core's registers and the code before the call, read by `mesa-qualification/coreread.py`), `host/dmesg-render-server.txt`, `host/versions.txt`; `mesa-qualification/out/deqp-26/` and `deqp-26m/`.
* Rach2: nothing in its own code. The experiment's `vm.sh` preloads libm into QEMU, and 76-16b's Venus profile is to do the same, as its issue notes.
* Status: unreported.
* Next: name the function from the compiled shader (`GALLIVM_DEBUG=asm` in the render server's environment), check Mesa's main branch and the ORC path, `lp_bld_init_orc.cpp`, for the same lookup, and see whether LLVM 21's RuntimeDyld reports or silently zeroes an unresolved symbol.

* Project: VK-GL-CTS 1.4.1.1 and 1.4.7.1, GitHub's archives of the tags `vulkan-cts-1.4.1.1` and `vulkan-cts-1.4.7.1`, whose SHA-256 are in `vendor/gnu/vk-gl-cts/sources.txt`.
* Fails: a program built for the surfaceless target, `glcts` or `deqp-gles2`, cannot start on a system that has the EGL and GL runtimes but not their development packages. `framework/platform/surfaceless/tcuSurfacelessPlatform.cpp` opens `libEGL.so` with `dlopen` (line 268 in 1.4.7.1, 267 in 1.4.1.1), and the GL library of a context by the defaults `DEQP_GLES2_LIBRARY_PATH` `"libGLESv2.so"` (line 72) and `DEQP_OPENGL_LIBRARY_PATH` `"libGL.so"` (line 80): the unversioned names that only `libegl-dev`, `libgles-dev` and `libgl-dev` install as links, where the runtime packages install `libEGL.so.1`, `libGLESv2.so.2` and `libGL.so.1`. * Found: 2026-11-10, the testing PC's WSL, milestone 77, task 77-9, running 1.4.7.1's `glcts` on Rach2's x86-64 GNU root, which has Debian's runtime packages alone. * Rach2: a local change in the build: the three names become the sonames before CMake runs, and the build stops if any is not found.

## QEMU answers a fenced RESOURCE_UNMAP_BLOB before the unmapping ends and runs the next command on the still mapped resource

* Project: QEMU 10.2.1, Ubuntu 26.04's 1:10.2.1+ds-1ubuntu3.3, with Ubuntu's virglrenderer 1.2.0-2ubuntu2.
* Fails: a `RESOURCE_UNMAP_BLOB` that carries `VIRTIO_GPU_FLAG_FENCE` never finishes its unmapping, and the `RESOURCE_UNREF` after it fails with `VIRTIO_GPU_RESP_ERR_UNSPEC`. `virtio_gpu_virgl_unmap_resource_blob` (`hw/display/virtio-gpu-virgl.c:143-188`) unmaps in steps: its first call removes the memory region, raises `renderer_blocked` and sets `cmd_suspended`, and a second call, once the region is freed, calls `virgl_renderer_resource_unmap`. `virtio_gpu_process_cmdq` (`hw/display/virtio-gpu.c:1052-1064`) keeps a suspended command at the head of the queue for that second call only when it has no fence; a fenced one moves to the fence queue, is never processed again, and is answered when its fence passes. The next command, the UNREF, then makes the second call itself (`virtio-gpu-virgl.c:313`), and `virgl_renderer_resource_unmap` fails on the Venus blob, so the UNREF returns before it releases the resource and its backing. Why virglrenderer fails the unmap was not read; it fails the same way for Linux, whose unfenced UNMAP gets the error (`ctrl 0x209, error 0x1200`) while the UNREF after it succeeds.
* Found: 2026-11-10, the testing PC's WSL, milestone 77, task 77-4b, running vkcube on Venus under Weston on Rach2: Rach2 sent every control command with a fence, the host answered a `RESOURCE_UNREF` with `ctrl 0x102, error 0x1200`, and Rach2's driver, which resets the device on a failed UNREF, unplugged the card under Weston.
* Reproduction: start QEMU 10.2.1 with `virtio-vga-gl,venus=on,blob=on,hostmem=...` and in the guest map a host-visible Venus blob, then send `RESOURCE_UNMAP_BLOB` with `VIRTIO_GPU_FLAG_FENCE` set and `RESOURCE_UNREF` after it; the UNREF fails. Rach2 before its fix, `RACH2_QEMU_ACCEL=kvm ARCH=x86_64 RACH2_CASES=machine.vkpresent.vkcube tests/run vkpresent`, did so in its one run of vkcube.
* Evidence: `tests/graphics/ref/venus-wsl/vkcube/log.out`, the Linux guest's QEMU lines with the failed UNMAPs; the commit "Send RESOURCE_UNMAP_BLOB unfenced, as Linux does, ..." on `rach2/sys/drm/virtio_gpu_blob.c`; the failing run's output was not kept.
* Rach2: sends `RESOURCE_UNMAP_BLOB` without a fence, as Linux's `virtio_gpu_cmd_unmap` does, in the commit above.
* Status: unreported.
* Next: check QEMU's master for the same handling of a fenced suspended command, and read virglrenderer's `virgl_renderer_resource_unmap` for why a Venus blob's unmap fails.

## Mesa's D3D12 driver frees a tessellation level variable with ralloc that the collector allocated

* Project: Mesa 26.0.8, Ubuntu 26.04's 26.0.8-1ubuntu0.3 (`libgallium-26.0.8-1ubuntu0.3.so`, build ID b089ec2f62ded38e9327502246aa4ccfb7929b24), its D3D12 gallium driver under WSL2 on an NVIDIA GeForce RTX 4080 SUPER, as the host renderer of Ubuntu's virglrenderer 1.2.0-2ubuntu2 in QEMU 10.2.1.
* Fails: a draw with a tessellation shader whose domain is isolines ends the process with SIGSEGV. `dxil_nir_fixup_tess_level_for_domain` (`src/microsoft/compiler/dxil_nir_tess.c:338`) shrinks the tessellation level arrays to the domain's sizes; for isolines the inner level's size is 0, so it removes the variable and frees it with `ralloc_free(var)` (line 362). `nir_variable_create_zeroed` (`src/compiler/nir/nir.c:273-275`) allocates a variable with `gc_zalloc_size(nir->gctx, ...)`, which has no ralloc header, so `ralloc_free` (`src/util/ralloc.c:307`) reads and unlinks memory that is not a header. The lines after the free read `var->data.location` of the freed variable. The driver compiles the variant at the draw (`nir_to_dxil` from `select_shader_variant`, `src/gallium/drivers/d3d12/d3d12_compiler.cpp:140`, from `d3d12_draw_vbo`), in QEMU's own thread, so the guest's draw ends QEMU and every guest program with it.
* Found: 2026-11-10, the testing PC's WSL, milestone 77, task 77-5, running VK-GL-CTS 1.4.1.1's dEQP-GLES31 in the Debian 13 guest on virgl. In a search that ran each case with its start and end streamed to the host, 286 guests died and each had a `_tess_eval` case of `dEQP-GLES31.functional.shaders.builtin_functions` running; none of those cases passed, where 101 `_geometry`, 71 `_compute` and 44 `_tess_control` cases of the same groups did. The framework's executor for that variant draws with `layout(isolines, equal_spacing) in`. Later searches lost guests the same way on the other cases that draw isolines, by VK-GL-CTS's source: those whose names say `isolines`, the evaluation-shader variants of `shaders.opaque_type_indexing`, those of its `ubo`, `ssbo` and `atomic_counter` groups among them, whose names end in `_tessellation_evaluation`, every case of `shaders.builtin_constants`, which checks its constant in each of the six stages (`es31fShaderBuiltinConstantTests.cpp:284`), `tessellation.fractional_spacing`, the tessellated cases of `primitive_bounding_box.lines` and `primitive_bounding_box.wide_lines` (`LineRenderCase`, `es31fPrimitiveBoundingBoxTests.cpp:1805`) and `tessellation_geometry_interaction.render.passthrough.passthrough_tessellation_geometry_shade_lines_no_change`. Of piglit's `quick` profile, the three tests of `arb_tessellation_shader` that draw isolines, `execution@isoline`, `execution@isoline-no-tcs` and `arb_tessellation_shader-tes-gs-max-output -small -scan 1 50`, each end QEMU alone, and no other test does.
* Reproduction: on WSL2 with Mesa 26.0.8 and `GALLIUM_DRIVER=d3d12`, start QEMU 10.2.1 with `virtio-vga-gl` and egl-headless, and in a Linux guest run `glcts` with the case list `dEQP-GLES31.functional.shaders.builtin_functions.common.abs.float_lowp_tess_eval`: QEMU ends with exit status 139, each time. The source alone shows the fault for any isolines program that declares `gl_TessLevelInner`.
* Evidence: `virgl-host/tess-eval.txt`, QEMU's stack with its frames named from Ubuntu's debug information. The source read is `mesa-26.0.8`'s `src/microsoft/compiler/dxil_nir_tess.c` (SHA-256 2c48e9cb0aa00e534d323fc37c7cfb623cc96e8da7b2e5430835dbcc473b27e1) and `src/compiler/nir/nir.c` (396705b7966115b258e347494110ba10a710d904f3a6dcba2b7d251e37ba1f20).
* Rach2: nothing in its own code, since the fault is in the testing PC's driver and any guest sets it off. The virgl family's lists leave the cases out, for both guests, as the headers of `tests/graphics/deqp-gles-virgl.txt.gz` and `piglit-virgl.txt.gz` say.
* Status: unreported.
* Next: check Mesa's main branch for the same `ralloc_free` in `dxil_nir_tess.c`; the change is to drop the free, since the collector owns the variable. Report to Mesa's issue tracker under the d3d12 label.

# A Venus guest's system time against Linux's (77-11)

On the Lenovo, under SDL at 1360x768@60, the Rach2 guest spent 17.3 to 20.7 s of system time in a vkcube round against Debian's 1.8 to 2.5 s for the same frames, and 35 to 36% of its four processors against Debian's 15 to 17% ([77-10's third rerun](77-10.md#the-third-reruns-results)). On the testing PC the round's system time came from five places where Rach2 left the guest for QEMU more often or for longer, or did more work, than Linux 6.12.115 does: the tick read the serial port every millisecond, the clock read the HPET, every submission carried a fence, every command notified the device, and each program started read its text through the file system. A sixth was in the count itself: each processor but the first counted the first's ticks, so a late tick there charged two ticks to whatever another processor ran next, most often a short system call, and time the host took from the guest was charged as the guest's. Each is now done as Linux does it. Rach2's system time a frame fell from 12.76 ms to 4.49 to 5.06 ms against Debian's 3.26 to 4.27 ms with the first five fixes, and with the sixth to 5.68 to 6.81 ms against Debian's 5.52 to 6.64 ms in the same cycles, on a host loaded by other work; its share of the processors fell from 32.7% to 16.4 to 18.0% against Debian's 17.0 to 17.8%. [What remains](#what-remains) gives the comparison. [The Lenovo's pair](#the-lenovos-pair) measures the fixed kernel on the machine, with no other load.

## The machine and the measure

The testing PC is the AMD Ryzen 9 7950X3D under WSL2's kernel 6.18.58.1, with Ubuntu's QEMU 10.2.1: `-accel kvm -cpu host -smp 4 -m 6G`, `virtio-vga-gl` with `venus=on,blob=on,hostmem=4G` and EDID 1280x800, the `egl-headless` display on `/dev/dri/renderD128`, and Venus over Mesa's lavapipe on the host, the machine of 77-10's `wsl-cube.sh`. Rach2 is the x86-64 kernel booted directly with `gnu-test.disk` as its root in a snapshot; Debian is `debian-ref`'s `prepared.qcow2` with `6.12.115+deb13.1-amd64`. `77-11/profile.sh` boots one guest, runs `vkcube.sh` once to warm its caches, and then once with 3,346 presents, around which it keeps the guest's `/proc/stat` and, on Rach2, debugfs's `bkl/calls`, `bkl/tick` and the whole-kernel sampling profile `bkl/profile`, which 80-92 used; on Debian, `perf record -a -g` at 1000 Hz unless `PERF=0`. It also keeps `/proc/stat` and each thread's stat line 8 and 18 s into the round, while vkcube runs, and with `TAIL=1` zeroes Rach2's counters at the second. With `TRACE` it keeps QEMU's trace of each processor's exits and of the virtio GPU's notifies and commands, or of the events `EVENTS` names. With `STATS` set to `qmpstats.py` it keeps KVM's statistics of each virtual processor, from QEMU's QMP socket, and QEMU's threads' times every half second. `stat.py` reads a round's processor time from a result directory or a runner's `record`, `prof.py` ranks `bkl/profile`'s samples against the kernel's symbols, and `exits.py` times the exits in a trace.

Every figure below is of that long round, vkcube in FIFO through Weston at the guest's preferred 1280x800 on the egl-headless display. `stat.py` reads the round's `/proc/stat`: system time is the `system`, `irq` and `softirq` columns summed over the four processors, given in milliseconds a frame, 3,346 frames; lower is better. Busy is user and system time as a share of the four processors' time over the round; lower is better. The rate is presents a second over the whole round; higher is better. Frames 300 and 345 of each round, held and read back, have Debian's checksums, `0x75d4ad32` and `0x1a0d31d7`, in every run of either guest.

## Where the time went

The milestone's kernel at 77-10's last commit, `9ff817e08`, spent 12.76 ms of system time a frame at 94.3 presents a second and 32.7% busy; Debian spent 3.59 ms at 116.2 and 13.1% with perf, 3.75 ms at 111.9 and 12.9% without. Of Rach2's 26,441 samples in the round, `bkl/profile` puts 72.0% at `kirq_restore` and 23.5% at `arch_irq_enable`, the first points at which a sample can land after a stretch with interrupts off, so the profile names the stretches by the chains that end there:

|---|---|---|
| 22.3% | EXECBUFFER | `vgpu_notify` < `cmd_submit` < `vgpu_cmd_send` |
| 9.9% | clock_gettime | `arch_irq_enable` < `_syscall_handler`: the wait for the big lock at the system call's entry |
| 9.2% | idle | `schedule` < `wq_wait` < `wq_wait_event_idle` |
| 3.7% | page fault | `bkl_enter` < `callback_begin` < `shared_fault` |

| 2.6% | clock_gettime | `rtc_monotonic` < `clock_read` < `sys_clock_gettime` |

`bkl/tick` named the rest: the tick's `console` part took 24.0 G cycles over 26,393 ticks, 909,000 cycles or some 217 us a tick on the boot processor, with the big lock held, which every other processor's entry then waited for. In Debian's profile the kernel's own functions are a few percent each, the largest `pv_native_safe_halt`, the idle loop; a notify's exit, `iowrite16`, is 3% of samples, since perf in the guest does not sample the time QEMU spends.

QEMU's trace of 1,346 presents explained the shape. A notify of the control queue is a write to the virtio-pci notify region that QEMU's virtio-gpu takes without an ioeventfd, so the processor waits in QEMU while the main loop, which holds QEMU's global lock, runs virgl's work; any other exit to QEMU's process, an HPET read or the UART's line status, waits for the same lock.

## The causes and the fixes

The serial console. `tty_console_poll`, from the boot processor's tick, read COM1 every tick until the receive interrupt had taken a first byte, as a fallback for an interrupt that never arrives. A console nobody types into never takes one, so every tick read the line status register, an exit to QEMU that waits for its global lock: 217 us of each millisecond. Linux reads an 8250 that has an interrupt from no timer (`drivers/tty/serial/8250/8250_core.c`, lines 207 to 213 poll only a port without one, and lines 269 to 275 run the backup timer only for the THRE bug). The tick now reads the port every tick only while its receive interrupt is off, and once it is on every fifth of a second, Rach2's own fallback for a lost edge. The console's part of the tick fell to 9,000 cycles, some 2 us.

The clock. Without `+invtsc` QEMU's `host` model reports no invariant TSC, so Rach2 kept its clock by the HPET, whose every read is an exit to QEMU's process, and its vDSO made `clock_gettime` a system call, under the big lock; vkcube and Weston call it several times a frame. Linux under KVM reads kvm-clock, the TSC scaled by a page KVM fills, with no exit and in its vDSO, and takes the TSC's rate from that page (`arch/x86/kernel/kvmclock.c`, lines 116 to 120 and 317 to 324; `arch/x86/kernel/pvclock.c`, lines 27 to 37). Rach2 now reads KVM's features, and where KVM offers KVM_FEATURE_CLOCKSOURCE2 and KVM_FEATURE_CLOCKSOURCE_STABLE_BIT and the clock page's PVCLOCK_TSC_STABLE_BIT is set, it takes the TSC's rate from the page and keeps the clock and the vDSO's by the TSC, as `rach2.tscreliable` already did on request. The boot log says `clock: reference: the tsc` and `vdso: clock: the tsc, 4192048 counts a tick`. The same kernel with `+invtsc`, which reached the TSC the old way, measured 7.87 ms and 104.1 presents a second.

The fences. Rach2 fenced every EXECBUFFER, and QEMU answers a fenced command only at its next poll of virgl's fences and keeps it on its list until then. Linux fences a submission only when an out-fence, an output syncobj, a buffer list or a polled ring's event reads the fence (`drivers/gpu/drm/virtio/virtgpu_submit.c`, lines 383 to 397); Rach2 now does the same.

The notifies. Rach2 negotiated no VIRTIO_F_EVENT_IDX, so it notified for every command the used ring's flag did not refuse, 5.64 notifies a frame against Linux's 4.12. Linux's split ring takes the feature and notifies only when the buffers added since the last kick pass the device's `avail_event`, and points `used_event` past each buffer it takes (`drivers/virtio/virtio_ring.c`, lines 734 to 763 and 866 to 874). QEMU's `virtqueue_pop` sets `avail_event` to the first buffer it has not taken, so a burst the device has not yet read costs one notify. Rach2 now takes the feature and does both. Its host test failed in two rows of indirect tables: `344976296` bounded a chain at the queue's length, so a chain longer than the ring was refused even with indirect tables, where Linux puts it in a table (`virtio_ring.c`, lines 576 to 580); a chain may now be as long as the queue or a table, whichever is longer.

|---|---|---|---|
| `9ff817e08`, 77-10's | 12.76 ms a frame | 94.3 a second | 32.7% |
| the same with `+invtsc` | 7.87 ms | 104.1 | 23.1% |
| the serial and fence fixes | 9.29 ms | 94.8 | 24.7% |
| and the clock | 5.46 ms | 109.0 | 17.0% |
| and the event index | 4.14 ms | 114.5 | 14.1% |
| Debian 6.12.115 with perf | 3.59 ms | 116.2 | 13.1% |
| Debian 6.12.115 without perf | 3.75 ms | 111.9 | 12.9% |

The start of each program. Rach2's exec mapped a program and its interpreter through a fill that reads each page through the file system into a frame of the image's own at every fault, where a private `mmap` of an ext2 file, the libraries among them, already borrowed the file's pages in memory. Linux's `elf_map` maps the program as any private file mapping, whose faults map the page cache's pages (`filemap_fault`). Exec now maps an ext2 program as a private `mmap` does. A warm 346-present round, Weston's and vkcube's start included, fell from 2.60 and 2.66 s of system time to 2.49 and 2.51 s, and the first round after boot from 4.60 and 4.69 s to 4.29 and 4.45 s.

The count of ticks. Each processor's tick charges one tick to what it interrupted, and a processor other than the first charged the ticks the first had counted since its own last tick, `kernel_ticks`. The first processor's tick waits while its interrupts are off, and while it was late every other processor charged none and then two at its next tick, to whatever it ran then. A thread that enters the kernel often and briefly is the likeliest to be running then: a debug build that kept each thread's ticks by system call charged Venus's submitting thread, `vn_wsi[0,0]`, 1,886 ticks in system calls other than its ioctls in a round, 304 in `close`, 328 in `futex`, 796 in `poll` and 44 in `gettid`, where the same build counting its own ticks charged 451, 27, 104, 204 and 7. Linux charges each processor's tick to that processor alone (`account_process_tick`, kernel/sched/cputime.c:474-500, from `update_process_times`, kernel/time/timer.c:2514-2519), and takes out first the time the host kept the processor ready but did not run it, which KVM reports in a record of each processor's (`steal_account_process_time`, cputime.c:253-269 and 486-492; `kvm_register_steal_time`, arch/x86/kernel/kvm.c:348-359). Rach2 now does both: a processor counts the whole ticks of its own monotonic clock since its last count, and under KVM gives KVM its steal-time record with MSR_KVM_STEAL_TIME and counts a tick's worth of steal as a stolen tick, charged to no one, in `/proc/stat`'s steal column. The same debug build counted 310 stolen ticks in a round on the loaded host. A Venus context that CONTEXT_INIT gives no name is also named after the calling thread now, as Linux's `virtio_gpu_create_context_locked` names it (drivers/gpu/drm/virtio/virtgpu_ioctl.c:42-60), where Rach2 named every one `rach2`.

With every fix Rach2's EXECBUFFER takes 635 us a call, almost all of it the notify's exit, and the big lock is held 2.74 s and waited for 0.70 s in the round, against 42.68 s of system time at the start.

# A Venus guest's system time against Linux's (77-11)

On the Lenovo, under SDL at 1360x768@60, the Rach2 guest spent 17.3 to 20.7 s of system time in a vkcube round against Debian's 1.8 to 2.5 s for the same frames, and 35 to 36% of its four processors against Debian's 15 to 17% ([77-10's third rerun](77-10.md#the-third-reruns-results)). On the testing PC the round's system time came from five places where Rach2 left the guest for QEMU more often or for longer, or did more work, than Linux 6.12.115 does: the tick read the serial port every millisecond, the clock read the HPET, every submission carried a fence, every command notified the device, and each program started read its text through the file system. Each is now done as Linux does it. Rach2's system time a frame fell from 12.76 ms to 4.49 to 5.06 ms against Debian's 3.26 to 4.27 ms in the same hours, and its share of the processors from 32.7% to 15.1 to 16.2% against Debian's 11.6 to 14.2%; [What remains](#what-remains) says where the rest goes. [The Lenovo's pair](#the-lenovos-pair) measures the fixed kernel on the machine.

## The machine and the measure

The testing PC is the AMD Ryzen 9 7950X3D under WSL2's kernel 6.18.58.1, with Ubuntu's QEMU 10.2.1: `-accel kvm -cpu host -smp 4 -m 6G`, `virtio-vga-gl` with `venus=on,blob=on,hostmem=4G` and EDID 1280x800, the `egl-headless` display on `/dev/dri/renderD128`, and Venus over Mesa's lavapipe on the host, the machine of 77-10's `wsl-cube.sh`. Rach2 is the x86-64 kernel booted directly with `gnu-test.disk` as its root in a snapshot; Debian is `debian-ref`'s `prepared.qcow2` with `6.12.115+deb13.1-amd64`. `77-11/profile.sh` boots one guest, runs `vkcube.sh` once to warm its caches, and then once with 3,346 presents, around which it keeps the guest's `/proc/stat` and, on Rach2, debugfs's `bkl/calls`, `bkl/tick` and the whole-kernel sampling profile `bkl/profile`, which 80-92 used; on Debian, `perf record -a -g` at 1000 Hz unless `PERF=0`. It also keeps `/proc/stat` and each thread's stat line 8 and 18 s into the round, while vkcube runs, and with `TAIL=1` zeroes Rach2's counters at the second. With `TRACE` it keeps QEMU's trace of each processor's exits and of the virtio GPU's notifies and commands, or of the events `EVENTS` names. `stat.py` reads a round's processor time from a result directory or a runner's `record`, `prof.py` ranks `bkl/profile`'s samples against the kernel's symbols, and `exits.py` times the exits in a trace.

Every figure below is of that long round, vkcube in FIFO through Weston at the guest's preferred 1280x800 on the egl-headless display. `stat.py` reads the round's `/proc/stat`: system time is the `system`, `irq` and `softirq` columns summed over the four processors, given in milliseconds a frame, 3,346 frames; lower is better. Busy is user and system time as a share of the four processors' time over the round; lower is better. The rate is presents a second over the whole round; higher is better. Frames 300 and 345 of each round, held and read back, have Debian's checksums, `0x75d4ad32` and `0x1a0d31d7`, in every run of either guest.

## Where the time went

The milestone's kernel at 77-10's last commit, `9ff817e08`, spent 12.76 ms of system time a frame at 94.3 presents a second and 32.7% busy; Debian spent 3.59 ms at 116.2 and 13.1% with perf, 3.75 ms at 111.9 and 12.9% without. Of Rach2's 26,441 samples in the round, `bkl/profile` puts 72.0% at `kirq_restore` and 23.5% at `arch_irq_enable`, the first points at which a sample can land after a stretch with interrupts off, so the profile names the stretches by the chains that end there:

| Share | Entry | Chain |
|---|---|---|
| 22.3% | EXECBUFFER | `vgpu_notify` < `cmd_submit` < `vgpu_cmd_send` |
| 9.9% | clock_gettime | `arch_irq_enable` < `_syscall_handler`: the wait for the big lock at the system call's entry |
| 9.2% | idle | `schedule` < `wq_wait` < `wq_wait_event_idle` |
| 3.7% | page fault | `bkl_enter` < `callback_begin` < `shared_fault` |
| 2.7% | other virtio GPU ioctls | `vgpu_notify` < `cmd_submit` < `vgpu_cmd_send` |
| 2.6% | clock_gettime | `rtc_monotonic` < `clock_read` < `sys_clock_gettime` |

`bkl/tick` named the rest: the tick's `console` part took 24.0 G cycles over 26,393 ticks, 909,000 cycles or some 217 us a tick on the boot processor, with the big lock held, which every other processor's entry then waited for. In Debian's profile the kernel's own functions are a few percent each, the largest `pv_native_safe_halt`, the idle loop; a notify's exit, `iowrite16`, is 3% of samples, since perf in the guest does not sample the time QEMU spends.

QEMU's trace of 1,346 presents explained the shape. A notify of the control queue is a write to the virtio-pci notify region that QEMU's virtio-gpu takes without an ioeventfd, so the processor waits in QEMU while the main loop, which holds QEMU's global lock, runs virgl's work; any other exit to QEMU's process, an HPET read or the UART's line status, waits for the same lock.

## The causes and the fixes

The serial console. `tty_console_poll`, from the boot processor's tick, read COM1 every tick until the receive interrupt had taken a first byte, as a fallback for an interrupt that never arrives. A console nobody types into never takes one, so every tick read the line status register, an exit to QEMU that waits for its global lock: 217 us of each millisecond. Linux reads an 8250 that has an interrupt from no timer (`drivers/tty/serial/8250/8250_core.c`, lines 207 to 213 poll only a port without one, and lines 269 to 275 run the backup timer only for the THRE bug). The tick now reads the port every tick only while its receive interrupt is off, and once it is on every fifth of a second, Rach2's own fallback for a lost edge. The console's part of the tick fell to 9,000 cycles, some 2 us.

The clock. Without `+invtsc` QEMU's `host` model reports no invariant TSC, so Rach2 kept its clock by the HPET, whose every read is an exit to QEMU's process, and its vDSO made `clock_gettime` a system call, under the big lock; vkcube and Weston call it several times a frame. Linux under KVM reads kvm-clock, the TSC scaled by a page KVM fills, with no exit and in its vDSO, and takes the TSC's rate from that page (`arch/x86/kernel/kvmclock.c`, lines 116 to 120 and 317 to 324; `arch/x86/kernel/pvclock.c`, lines 27 to 37). Rach2 now reads KVM's features, and where KVM offers KVM_FEATURE_CLOCKSOURCE2 and KVM_FEATURE_CLOCKSOURCE_STABLE_BIT and the clock page's PVCLOCK_TSC_STABLE_BIT is set, it takes the TSC's rate from the page and keeps the clock and the vDSO's by the TSC, as `rach2.tscreliable` already did on request. The boot log says `clock: reference: the tsc` and `vdso: clock: the tsc, 4192048 counts a tick`. The same kernel with `+invtsc`, which reached the TSC the old way, measured 7.87 ms and 104.1 presents a second.

The fences. Rach2 fenced every EXECBUFFER, and QEMU answers a fenced command only at its next poll of virgl's fences and keeps it on its list until then. Linux fences a submission only when an out-fence, an output syncobj, a buffer list or a polled ring's event reads the fence (`drivers/gpu/drm/virtio/virtgpu_submit.c`, lines 383 to 397); Rach2 now does the same.

The notifies. Rach2 negotiated no VIRTIO_F_EVENT_IDX, so it notified for every command the used ring's flag did not refuse, 5.64 notifies a frame against Linux's 4.12. Linux's split ring takes the feature and notifies only when the buffers added since the last kick pass the device's `avail_event`, and points `used_event` past each buffer it takes (`drivers/virtio/virtio_ring.c`, lines 734 to 763 and 866 to 874). QEMU's `virtqueue_pop` sets `avail_event` to the first buffer it has not taken, so a burst the device has not yet read costs one notify. Rach2 now takes the feature and does both. Its host test failed in two rows of indirect tables: `344976296` bounded a chain at the queue's length, so a chain longer than the ring was refused even with indirect tables, where Linux puts it in a table (`virtio_ring.c`, lines 576 to 580); a chain may now be as long as the queue or a table, whichever is longer.

| Kernel | System time | Rate | Busy |
|---|---|---|---|
| `9ff817e08`, 77-10's | 12.76 ms a frame | 94.3 a second | 32.7% |
| the same with `+invtsc` | 7.87 ms | 104.1 | 23.1% |
| the serial and fence fixes | 9.29 ms | 94.8 | 24.7% |
| and the clock | 5.46 ms | 109.0 | 17.0% |
| and the event index | 4.14 ms | 114.5 | 14.1% |
| Debian 6.12.115 with perf | 3.59 ms | 116.2 | 13.1% |
| Debian 6.12.115 without perf | 3.75 ms | 111.9 | 12.9% |

The start of each program. Rach2's exec mapped a program and its interpreter through a fill that reads each page through the file system into a frame of the image's own at every fault, where a private `mmap` of an ext2 file, the libraries among them, already borrowed the file's pages in memory. Linux's `elf_map` maps the program as any private file mapping, whose faults map the page cache's pages (`filemap_fault`). Exec now maps an ext2 program as a private `mmap` does. A warm 346-present round, Weston's and vkcube's start included, fell from 2.60 and 2.66 s of system time to 2.49 and 2.51 s, and the first round after boot from 4.60 and 4.69 s to 4.29 and 4.45 s.

With every fix Rach2's EXECBUFFER takes 635 us a call, almost all of it the notify's exit, and the big lock is held 2.74 s and waited for 0.70 s in the round, against 42.68 s of system time at the start.

Rach2's system time is 4.49 to 5.06 ms a frame against Debian's 3.26 to 4.27, and its share 15.1 to 16.2% against 11.6 to 14.2%: about 1.3 times Linux's, where it was 3.4 times, and not yet within Linux's range. The frames match Debian's in every run.

Snapshots 8 and 18 s into the round, while vkcube runs, split the rest. In those 10 s Rach2 spent 5.11, 5.14, 5.24 and 5.48 s of system time, Debian 3.88, 4.35 and 5.28 s with its interrupt time; by thread, in hundredths of a second:

| Thread | Rach2 | Debian |
|---|---|---|
| Venus's WSI thread, `vn_wsi[0,0]`, which submits | 381, 398, 409 | 317, 324, 365 |
| Weston, which composites through virgl | 67, 88, 93 | 38, 38, 50 |
| the kernel's virtio GPU and DRM threads, Linux's kworkers | 31 to 42 | 12 to 20 |

The submitting thread's time is mostly EXECBUFFER's notify, an exit that waits for QEMU's main loop: 13,659 calls at 722 us in Rach2's fourth round, 9.87 s. By QEMU's trace of a pair of 1,346 presents, Rach2 now notifies as often as Linux, 4.0 times a frame against 4.1, but each notify waits longer in QEMU, 933 us against 818 us, with a mix of commands within a few percent of Debian's. The guest's other exits in a round, 20 reads of the e1000's STATUS and 5 of the UART's line status a second, cost about 0.1% of a processor. Why QEMU's main loop keeps Rach2's notifies longer is not found. Weston's extra time is in its own system calls, which the profile does not separate from vkcube's.

The rounds' start costs more too. With the exec change a warm round's start, Weston's and vkcube's, costs about 0.35 s more system time than Debian's, 2.49 and 2.51 s for a 346-present round against 2.07 and 2.20 s, and the first round after boot about 1.6 s more, 4.29 and 4.45 s against 2.40 to 2.97 s. The long round took 128,800 page faults against Debian's 72,181, and the warm short round's profile puts a quarter of its samples in page faults, their file pages read through ext2's buffer cache (`read_piece` < `ext2_read`, `filecache_read`) and zero-filled anonymous pages. That is the path of file reads and faults that task 80-92 measures against Linux for Crysis's level load. The Lenovo's rounds are 346 presents each, the first after boot, so a round's start weighs more there than in the testing PC's long round.

## The Lenovo's pair

The pair is 77-10's third rerun's two SDL sessions, `session.py debian sdl --part cube --mode Virtual-1=1360x768@60` and the same for `rach2`, with the Rach2 guest's kernel built from this task's branch; the disk images, `session.py`, `guest.sh` and the payload are 77-10's. Both sessions show rotating cubes on the Lenovo's screen through SDL, with no sound, so the loop that runs the pair posts a `Lenovo notice:` on this task first and waits ten minutes before the first session. The guest kernel runs only inside QEMU on the Lenovo's Debian, with virtual devices; the machine boots only Debian's established kernel and the installed release, as in 77-10, so no trial boot is involved.

Build the kernel at the head of `task/4586` in the checkout `T` that runs the step, whose status must be clean and whose head must be that one, and check it against the 4 MiB slot:

```sh
git fetch origin && git status --short && git log -1 --format=%H origin/task/4586
test "$(git rev-parse HEAD)" = "$(git rev-parse origin/task/4586)"
make -j8 ARCH=x86_64 build/x86_64/rach2/kernel
S=$(git rev-parse --short=9 HEAD)
R=$T/build/runs/4586
K=$R/kernel-$S
mkdir -p "$K/images"
cp build/x86_64/rach2/kernel "$K/images/kernel"
test "$(wc -c < "$K/images/kernel")" -le 4194304 && wc -c < "$K/images/kernel"
(cd "$K" && shasum -a 256 images/kernel > SHA256SUMS && git rev-parse HEAD > source && cat SHA256SUMS source)
```

Then run 77-10's [Take and prepare the machine](77-10.md#take-and-prepare-the-machine) through the mount of the data partition, with its identity checks, `R=$T/build/runs/4586`, the notice on this task and `4586` in the lock's `issue`; skip its packaging and its copy of the assets. `/data/build/77-10` must still hold 77-10's images: `D 'cd /data/build/77-10 && ls images session.py payload.tar.gz'` lists `debian.qcow2`, `kernel` and `rach2.qcow2` under `images`. If it does not, the images are made again as 77-10's [Prepared files](77-10.md#prepared-files) says, from the milestone's head, and copied as that section's fetch and copy do. Set the third rerun's results aside and put the new kernel in place:

```sh
D 'cd /data/build/77-10 && test -d runs && test ! -e runs-20ec89e75 && mv runs runs-20ec89e75 && cp images/kernel images/kernel-20ec89e75'
COPYFILE_DISABLE=1 tar -cf - -C "$K" images/kernel SHA256SUMS | D 'mkdir -p /data/build/77-11 && tar -xf - -C /data/build/77-11 && cp /data/build/77-11/images/kernel /data/build/77-10/images/kernel'
(cd "$K" && cat SHA256SUMS) | D 'cd /data/build/77-10 && sha256sum -c && sync'
```

Passes: `images/kernel: OK`. Run the two sessions one at a time, reading each one's logs every 30 seconds as 77-10's [Run and read](77-10.md#run-and-read) says, and stop a session whose record stops changing:

```sh
D 'cd /data/build/77-10 && python3 session.py debian sdl --part cube --mode Virtual-1=1360x768@60' > "$R/debian-sdl-cube.out" 2>&1
D 'cd /data/build/77-10 && python3 session.py rach2 sdl --part cube --mode Virtual-1=1360x768@60' > "$R/rach2-sdl-cube.out" 2>&1
```

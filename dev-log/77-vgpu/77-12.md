# dEQP-GLES in QEMU against Debian (77-12)

On 2026-11-12, on the testing PC, Rach2 at the head of `milestone/76-display` and the Debian 13 reference guest (Linux 6.12.115+deb13.1-amd64) ran the same dEQP-GLES subset in the same QEMU 10.2.1 on both GL profiles, and Rach2 gave every case the Debian guest's status. No case passes on Linux and fails, crashes or is missing on Rach2, so the list of gaps is empty and no subtask was filed.

## The subset

The subset is every 10th case of each suite of [`tests/graphics/deqp-gles-virgl.txt.gz`](../../tests/graphics/deqp-gles-virgl.txt.gz), VK-GL-CTS 1.4.1.1's AOSP lists less the cases that end the testing PC's QEMU from any guest: 1,717 cases of dEQP-GLES2, 4,344 of dEQP-GLES3 and 3,668 of dEQP-GLES31, 9,729 in all, each suite in one boot with four `glcts` processes on surfaceless EGL. It is the cases `machine.virgl.deqp-SUITE-subset` and `machine.venus.deqp-SUITE-subset`, SUITE being gles2, gles3 or gles31, and `tests/graphics/Readme.md` says how to run it in each guest. The virgl cases judge against the Debian guest's whole stored list in `tests/graphics/ref/virgl-wsl/deqp/`, and the Venus cases against the Debian run below, stored in `tests/graphics/ref/venus-wsl/gles/`.

The two profiles:

* `virgl`: GL through virglrenderer on the host's D3D12 driver and the RTX 4080 SUPER, which both guests name `virgl (D3D12 (NVIDIA GeForce RTX 4080 SUPER))`, OpenGL ES 3.1.
* `venus`: the Venus profile, whose GL is virgl over the host's llvmpipe, `virgl (LLVMPIPE (LLVM 21.1.8, 256 bits))`, OpenGL ES 3.2, beside Venus's Vulkan. OpenGL on Venus itself would be Zink, which the graphics plan leaves out, so the profile's GL is what this subset runs there.

## Results

No case crashed, timed out or was missing in either guest, and no flake was named. Each of Rach2's six cases passed its judge, `judge.py deqp`, which finds a case worse when the reference passes it, Pass or a warning, and the run does not, NotSupported among the statuses that do not pass. The Debian guest's new virgl run, judged by the same program against its own stored whole list of 2026-11-10 and 2026-11-11, has no case worse either, so the stored reference still holds under the host's present drivers.

Rates, each from the runner's summary line with 8 CPUs, 8 GiB and KVM; the host ran other accounts' work beside them, so only the ratio means anything, and here not much: the Debian runs started under host loads of 16 to 43, with the two profiles' guests running at once, and Rach2's virgl cases ran three guests at once and its Venus cases one at a time, under host loads not recorded.

## Runs

From the top of the tree on the testing host, in the owner's copy `build/worktrees/m1`, with VK-GL-CTS 1.4.1.1 of the GNU layer's build:

    sh tests/graphics/runners/debian.sh deqp -p PROFILE -c 8 -m 8192 OUT -v 1.4.1.1 -e 10 -s 1 \
        -l /tmp/deqp-gles-virgl.txt.gz SUITE
    RACH2_QEMU_ACCEL=kvm ARCH=x86_64 \
        RACH2_CASES="machine.virgl.deqp-gles2-subset machine.virgl.deqp-gles3-subset machine.virgl.deqp-gles31-subset" \
        tests/run virgl
    RACH2_QEMU_ACCEL=kvm ARCH=x86_64 \
        RACH2_CASES="machine.venus.deqp-gles2-subset machine.venus.deqp-gles3-subset machine.venus.deqp-gles31-subset" \
        tests/run venus

Both `tests/run` lines ended `PASS`. No fault in another project's code was met.

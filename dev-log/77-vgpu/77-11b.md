# A round's start against Linux's: file faults, the heap and the idle poll (77-11b)

After 77-11, a 346-present vkcube round on the testing PC cost Rach2 more system time than Debian, most of it in the round's start, Weston's and vkcube's: the first round after boot 4.29 and 4.45 s against Debian's 2.40 to 2.97 s, a warm round 2.49 and 2.51 s against 2.07 and 2.20 s ([77-11's What remains](77-11.md#what-remains)). Four causes were found and fixed, each as Linux 6.12.115 does it: a file page in memory was copied into each mapping at its fault, a read fault read one page from the disk at a time, the kernel heap flushed every processor's TLB at each free, and an idle processor's poll held a disk's completion interrupt for up to 200 us. A fifth, in this task's own first change, corrupted mappings on x86-64 and is fixed too. A warm round is now within Debian's system time and busy share, 1.94 to 2.14 s and 18.8 to 19.7% against 2.07 to 2.32 s and 18.5 to 19.6%, and 0.1 to 0.4 s longer. The first round after boot is not: 3.95 to 4.49 s against 2.79 to 2.93 s, most of the difference in copying each block a file reads twice, which [What remains](#what-remains) describes, and which needs the file read path to read into the page itself, as Linux does.

## The machine and the measure

The machine, the guests and `77-11/profile.sh` are 77-11's ([The machine and the measure](77-11.md#the-machine-and-the-measure)), with `FRAMES=346 PERF=0`: each profile boots one guest and runs `vkcube.sh`'s rounds of 346 presents, the first after boot (`cube-1`) and a warm one (`cube-2`), and `stat.py` reads each round's `record`. A cycle is one Rach2 profile and one Debian profile in turn, so that the host's load, from other accounts' work, falls on both. Each round's frames 300 and 345 have Debian's checksums, `0x75d4ad32` and `0x1a0d31d7`, in every run below.

`profile.sh`'s `PHASES=N` runs `77-11/phases.py` in the guest after the rounds: each phase of a round's start, the GCC build of `vkhold.c`, Weston to its socket, vkcube to its end with `--c 1`, the screenshooter and `frame.py`, runs N times alone, the first kept apart as cold, with its wall time, its children's user and system time and faults, and the kernel's time from `/proc/stat`. `PHASE_PROFILE=NAME` counts the named phase's warm runs alone in debugfs's `bkl/calls`, `bkl/tick` and the whole-kernel `bkl/profile`.

Narrower loads, each in a Rach2 guest booted by hand with `gnu-test.disk` and no GPU, 4 processors and 2 GiB, isolated the causes: a cold `gcc` build of `vkhold.c` with `bkl/profile`; a churn of four shells each running `/bin/true` and `/bin/ls /usr/lib` 150 times, three rounds, timed by `/proc/uptime` and `/proc/stat`; and `rnd.py`'s 2,000 `pread`s of 4 KiB at random offsets of the raw disk, `/dev/sda` in Debian and `/dev/disk0` in Rach2, with the reader's own user and system time.

## The causes and the fixes

The file pages. A private read mapping of an ext2 file copied the file page cache's page into a frame of the mapping's own at each fault. Linux maps the page cache's folio itself and, at a read fault, maps the folios already in memory around it (`do_fault_around`, mm/memory.c:5194-5195 and 5254, and `filemap_map_pages`, mm/filemap.c:3634). Rach2 now lends the cache's frame to the mapping (`filecache_lend`), keeps it in the cache while any mapping holds it, and maps up to 16 pages around a read fault from the cache (`share_around`). The first form of the window masked the fault's address with a 32-bit mask, which on x86-64 put the window at its region's start and wrote its entries into another table's pages; it corrupted other mappings, and the mask is now a `uintptr_t`.

The read fault's disk reads. Each page a fault missed was one request to the disk, and the buffer cache reads ahead only a miss that lands where its last read ended, so faults scattered over a library's text read one page at a time. Linux's read-around reads a window of `VM_READAHEAD_PAGES`, 128 KiB, starting half a window before the fault, into the page cache, until a file's faults have missed `MMAP_LOTSAMISS` times, a count each fault-around hit lowers (`do_sync_mmap_readahead`, mm/filemap.c:3092 and 3187-3203; include/linux/pagemap.h:1375; `filemap_map_pages`, mm/filemap.c:3712-3716). Rach2 now does the same for an ext2 regular file (`disk_read_around`). A cold `gcc` build of `vkhold.c`, whose profile had put 75% of its samples in page faults waiting on the disk, fell from 0.75 s, 645 samples and 9,087 faults to 0.30 s, 198 samples and 3,860 faults; Debian's takes 0.256 s.

The heap's frees. The kernel heap maps its pages on demand, and each free of a run unmapped it and flushed every processor's TLB (`smp_kernel_flush`) under the heap's lock with interrupts off. In the warm round's profile the heap's allocations and frees were 6.2 to 8.9% of the kernel's samples, most of them frees: 216 samples under `vm_free` < `mm_put`, 75 under `wait_done`, 72 under `fd_table_delete` and 69 under `path_bufs_free`. Linux keeps a freed vmalloc area mapped and purges such areas with one flush once they pass `lazy_max_pages` (`free_vmap_area_noflush` and `__purge_vmap_area_lazy`, mm/vmalloc.c:2150, 2306-2348 and 2411-2455), and flushes a range of more than 33 pages whole (`flush_tlb_kernel_range`, arch/x86/mm/tlb.c:998 and 1109-1125). Rach2's heap now keeps up to 64 freed runs, 512 pages, mapped and unmapped, then frees them with one flush of every processor, and gives a kept run back to the next request of its length; `smp_kernel_flush` flushes a range of more than 33 pages whole. The churn's system time fell from 134 to 168 ticks a round to 85 to 115, and its wall time from 0.46 to 0.55 s to 0.32 to 0.40 s.

The idle poll. An idle processor in a guest polls for a wake before it halts, for up to 200 us, adapting the length as Linux's haltpoll governor does, and polled with interrupts off. A disk's completion interrupt then waited until the poll's end: 2,000 random reads of the raw disk took 0.52 to 0.57 s against Debian's 0.369 s, and 0.31 to 0.34 s with the poll off. Linux's `poll_idle` polls with interrupts on (drivers/cpuidle/poll_state.c:22-41). Polling with them on, whether every interrupt ended the poll or only a device's did, made the churn's wall time 0.52 to 0.73 s against 0.32 to 0.40 s with them off, the same as with no poll at all, 0.58 to 0.93 s. Counters in the poll showed why: the churn's exits flush every processor, and each flush's interrupt, taken one by one inside the poll, cost 7 to 10 us in the guest, 18,830 of them in one processor's idle waits, about 180 ms; while a processor was inside one, a kick found it already kicked and sent an interrupt in place of the poll's wake, 24,000 to 42,000 times a processor against 1,100 to 1,600 with interrupts off. Linux sends no such flush to an idle processor in lazy TLB mode (`should_flush_tlb`, arch/x86/mm/tlb.c:912-914). The poll keeps interrupts off and answers the other processors' requests in its loop (`smp_service`), so that their interrupts are taken once at its end, and every IDLE_POLL_CHECK_US, 10 us, it reads the local APIC's request register for a device's or a timer's vector (`arch_irq_waiting`) and on one halts, which takes it at once with the processor still marked idle. The random reads now take 0.34 to 0.40 s, and the churn 0.41 to 0.51 s against 0.34 to 0.60 s with the old poll in the same runs.

Task 84-35 had changed the poll on the milestone branch to run with interrupts on and to end on any interrupt (`2193bc53c`), so that a tick, a disk or a network interrupt is taken at once. Its aim is kept: each of those, and a timed wake between ticks, is taken within 10 us of its arrival. Its form is the one the churn measured at 1.5 times the wall time, and this task's rebase replaces it.

## What remains

The first round after boot. `profile.sh`'s `MEASURE=1` profiles it: of Rach2's 2,948 kernel samples, 48.2% are in page faults, and their largest chains copy file data. The fault reads a page through `ext2_read`, which takes each block from the buffer cache, `bcache_get`; a miss there reads a 128 KiB run into a staging buffer and copies each block into a buffer of the cache (`fill_run`), and `ext2_read` copies the block again into the file page cache's frame. `arch_copy_words` under `ext2_read` took 279 to 309 samples, the cache's copy 293 once its zeroing of the same buffer was taken out, and the zeroing 323 before; taking it out moved its samples to the copy, so the cost is the processor's first touch of memory the guest has not used since boot, which the host faults in, and not the zeroing or the copy themselves. Linux reads a file's pages into the page cache's folio by DMA (`mpage_readahead`, fs/mpage.c), so QEMU's I/O thread, not the guest's processor, touches the page, and in Debian's `perf` profile of the same round no copy of file data appears: its largest kernel symbols are `clear_page_erms`, 4.06%, and the idle halt, 3.39%. Rach2's round also read 177,896 KiB from the disk against Debian's 106,428 and added 75,488 file pages against 27,956, since each block is held twice, once in each cache. Reading an ext2 file's blocks straight into the file page cache's frames, past the buffer cache, and keeping that coherent with the buffer cache's dirty blocks, is a change of the file system's read path, larger than this task.

The tick's work under the big lock. A warm round held the big lock 1.0 to 1.2 s and waited for it 0.35 to 0.58 s; the tick's parts cost some 40 us a tick on the processor that runs them: the wait for the lock 77 ms a round, the wake pass 32, IPv6's 29, the accounting 26, the console 14, TCP's 12.5 and the clock 11.7.

The user time. Rach2's rounds spend 0.2 to 0.4 s more user time than Debian's on the testing PC, and 1.4 to 1.7 s more on the Lenovo ([The Lenovo pair's results](77-11.md#the-lenovo-pairs-results)). No measurement here has found its cause.

The disk's empty ports. Rach2's AHCI driver waits 1,000 ms on each empty port, some 5 s of each boot in QEMU, where Linux's link debounce takes about 100 ms. It is in the Lenovo's disk path and was left alone here.

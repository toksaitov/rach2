# VK-CTS's api, memory and synchronization groups on Venus (77-14)

On 2026-11-12, under the owner's order of 11-11 that the vendor completeness suites keep running, one in 4 of dEQP-VK's `api`, `memory` and `synchronization` groups, 91,437 cases of VK-GL-CTS 1.4.1.1, ran through Venus over the testing PC's lavapipe, in Debian 13's Linux 6.12.115 guest and on Rach2's GNU root at the milestone's head, in the same QEMU. Rach2 has no gap against Linux: every case that passes in the Debian guest passes on Rach2, no case is missing, and the one case that fails in either, a descriptor pool case that times out, does so in both. So no subtask was filed for a gap. The subset, its case and its reference are checked in under `tests/`, and the Debian guest's results are the case's reference.

* The statuses are each case's first, as the runner records them; a case that does not pass runs once more, and one that then passes is named in `flakes`.
* `judge.py deqp` found no case worse on Rach2 in either run: none that passes or warns in the Debian guest and fails, crashes, times out for good, is unsupported or is missing on Rach2.
* `dEQP-VK.api.descriptor_pool.repeated_reset_long` times out at dEQP's 300 s limit in every run of both guests, and again when run a second time. It allocates 2,048 descriptor sets and resets their pool 4,096 times, touching the watchdog every 1,024 iterations; in both guests the host's render server logs `vkr: vkAllocateDescriptorSets resulted in CS error` beside its runs. It is the same in both, so it is no gap of Rach2's; its cause in Venus or the host's virglrenderer was not traced.
* `dEQP-VK.api.object_management.alloc_callback_fail.pipeline_layout_single` gives `QualityWarning` in both.
* `dEQP-VK.api.external.memory.opaque_fd.suballocated.host_visible.import_multiple_times` timed out at its first run in the Debian guest and in Rach2's run 2, and passed when run again in both; in Rach2's run 3 it passed at once. The second case that passed when run again in Rach2's run 2 is one that passes at once in the Debian guest and in run 3; that run's case kept only its counts, so its name is not known. The host ran other accounts' work beside each run: its load averages read 15 to 32 on its 32 threads during the Debian run and 7 to 12 during run 3; run 2's were not read.
* The rates, against the Debian guest's: 0.97 in run 2 and 1.04 in run 3, under different loads of the host, so the two systems run these groups at about the same rate. On the lavapipe fraction's first part Rach2 ran at 0.78 of Linux's ([the Venus references](../../tests/graphics/ref/venus-wsl/Readme.md#results)).
* A pilot of one in 27 of the same groups, 13,547 cases, gave 3,938 `Pass` and 9,609 `NotSupported` in both, in 391 s in the Debian guest and 427 s on Rach2; it sized the subset.

## The subset

[`tests/graphics/deqp-vk-groups.txt.gz`](../../tests/graphics/deqp-vk-groups.txt.gz) is made by `deqp-fraction.py -g api,memory,synchronization 4`: the 365,753 cases of the three groups in 1.4.1.1's `vk-default` list (299,764 `api`, 60,331 `synchronization`, 5,658 `memory`), shuffled as deqp-runner 0.20.3 shuffles a list, one in 4 taken, less the 2 cases that Mesa 25.0.7's skip files for its lavapipe job match. `-g` is new: it cuts the list to the named groups before the shuffle, and the script's output without it is unchanged, byte for byte, for the lavapipe fraction. One in 4 was chosen from the pilot's rates: Rach2 ran 31.7 cases a second, so the 91,437 cases take some 48 minutes on Rach2 and one in 3 would take more than an hour. `synchronization2`, a group of its own with 64,563 cases, is not part of it.

The case `machine.venus.groups` runs the list on Rach2, judged against the Debian guest's results in `tests/graphics/ref/venus-wsl/deqp/groups/` ([Venus's dEQP](../../tests/graphics/Readme.md#venuss-deqp)):

    RACH2_QEMU_ACCEL=kvm ARCH=x86_64 RACH2_CASES=machine.venus.groups tests/run venus

and the reference was made by

    sh tests/graphics/runners/debian.sh deqp -p venus -c 8 -m 8192 OUT -v 1.4.1.1 \
        -i /usr/share/vulkan/icd.d/venus_icd.x86_64.json \
        -l /tmp/deqp-vk-groups.txt.gz -f /tmp/deqp-vk-lavapipe.flakes vk

## Runs

All times are UTC+6 on 2026-11-12, on the testing PC's WSL as `toksaitov-d`, with the udmabuf module loaded and its limit at 16384 MiB. Both guests had 8 CPUs and 8 GiB under KVM in the `venus` profile, VK-GL-CTS 1.4.1.1 from the GNU layer's build, Mesa 26.1.6's Venus driver alone through its ICD, and four `deqp-vk` processes; Venus named its device `Virtio-GPU Venus (llvmpipe (LLVM 21.1.8, 256 bits))`, Vulkan 1.4.307, in both.

* The Debian guest, kernel `6.12.115+deb13.1-amd64`, from 13:12 to 13:55.
* Rach2, kernel 6.18.0-rach2, the image built from the task branch over the milestone's `c4c5834b8`. Run 1, from 13:56 to 14:36, was stopped by etude: the case's one run step reports nothing until dEQP ends, and its gap bound, taken from the lavapipe fraction's parts, was 40 minutes. The bound is now 90 minutes. Run 2 was from 14:37 to 15:25 and run 3 from 15:28 to 16:14; before run 3 the Venus cases were made to print their flakes and each case that did not pass, since a passing case keeps no output.

Each run's output was read and then removed, as were the images and the work directories.

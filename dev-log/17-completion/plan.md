# Milestone 17: privilege completed: accounts, the search bit, and the last mode bits

## The goal

Milestone 15 shipped with a deferral list; milestone 16 audited what shipped and deliberately did not reopen it. This milestone empties the list. Every item in `dev-log/15-privilege/Readme.md` under "What stays deferred", and the three more that `utils/su.c` records at its point of use, ends this milestone either implemented and proved or written down in an owning Readme as a decision with its cost.

Two items on the list are already closed and this plan does not redo them (see phase 3). Three more are not loose ends but the missing halves of models the tree only half-implements, and they are why this is a milestone and not a cleanup:

* The permission check never charges search on a path's ancestors. `krffs_walk_e` (`rach2/sys/fs/krffs.c:260`) matches each component by `name` and `parent_id` and never reads `mode`, `uid`, or `gid`; the syscall layer judges the endpoint (`cred_access_node`, `syscall.c:1009`) and, for a mutation, the immediate parent's write bit (`cred_parent_writable`, `syscall.c:1028`), which itself resolves that parent through the unchecked walk at `syscall.c:1047`. Nothing anywhere asks for search on a prefix. A uid-1000 process therefore reads a 0644 file inside a 0700 root-owned directory, and creates, unlinks, renames, mkdirs and rmdirs inside a 0777 directory whose only protection is a 0700 ancestor.
* The set-id bits are granted by exec and taken away by nothing. Exactly two sites write a node's permission bits, `krffs_stamp_new_node` (`syscall.c:1187`) and `krffs_chmod_node` (`syscall.c:2696`); `krffs_chown_node` (`syscall.c:2708`) writes ids only. A 04755 file stays 04755 across any amount of writing and any chown.
* The sticky bit stores and reports and is read by nothing. `KRFFS_MODE_STICKY` (`krffs.h:57`) has one occurrence in the tree: its own definition. In the shipped `1777 /tmp`, any user with write permission on the directory may unlink or rename root's file, and may rename their own file over it, which is precisely the attack the bit exists to stop.

The rest is the account workflow the milestone-15 story stops one step short of. A user can prove a password and cannot change one; an administrator cannot create an account; and the console is still an unauthenticated root shell, so the box that authenticates over the network hands uid 0 to whoever reaches the serial line.

## Scope and non-goals

In scope, as work:

* Search (`x`) charged on every directory the KRFFS walk enters, on the read paths and the mutation paths alike, with the resolver's error reaching the caller instead of being collapsed into `-ENOENT`, and charged by the real ids for `access(2)`.
* The set-id bits cleared on write, truncate, and chown, guarded against the root node whose dirty-mount flag shares the setuid bit position.
* The sticky bit's restricted-deletion rule at unlink, rmdir, and both ends of rename, and, as its prerequisite, `unlink` and `rename` reporting a real errno instead of KRFFS's bare `-1` (which userspace decodes as `EPERM`).
* The POSIX kill rule completed: the target's saved uid matches, and `SIGCONT` within the session is exempt. This is a live defect: a uid-1000 ash cannot resume a job it started through `su`.
* `utils/pwauth.c`, the shared credential library: check a password against a stored hash, read one from the terminal with echo off, mint a salt from trusted entropy, and replace a credential file by write-new-then-rename. `su` is rebuilt on it.
* `utils/passwd.c`, setuid root: the second and last setuid program in the shipped image.
* `utils/adduser.c`, root-only, which never mints a hash itself but execs `passwd`.
* `utils/login.c` on the console, with `rach2.rescue` left as the only rescue path.
* Our `ping` staged into os-real, the whole-system freeze `icmp_ping` causes removed first, and every BusyBox applet that wants privilege or a raw socket compiled out rather than merely shadowed.
* The disk-backed os-real presented and bootable as the writable image, so an account change means something after a reboot.
* Zero-length UDP datagrams; a bound local port honored by `connect`, with `-EADDRINUSE` on a port an existing listener holds; TCP simultaneous open.
* The build and test guards the above needs: a set-id sweep over every manifest, the privilege family out of the os-simple `exec-dir` sweep, a probe runner that cannot score a signal death or a forked child's status as a pass, and a style gate whose globs actually reach the new code.

Non-goals, each of which becomes a stated sentence in an owning Readme in this milestone rather than a line on a list:

* A root password over SSH. `-g` stays; root authenticates by key, and root's hash exists so `su` has something to verify. The doc also stops overstating what `-g` buys.
* A loopback interface proper. `127/8` stays a canonical alias for the machine's one address, decided at the socket boundary, and `rach2/sys/network/Readme.md` says what a program can and cannot observe (a peer that reads back as `10.0.2.15`, so a program cannot use the peer address to decide a connection is local).
* `SOCK_RAW`. It needs a raw socket type, an ICMP demux to bound sockets replacing the single global in-flight ping, the IP header delivered ahead of the message, and a privilege decision; that decision kills it, since a root-only raw socket leaves the test account's `ping` broken and an unprivileged one weakens the boundary milestone 15 hardened.
* Quotas, ACLs, capabilities, and per-user resource limits. Out of the model this system teaches, with the cost of each named. Resource limits are not deferred at all: `getrlimit`/`prlimit64` already report the kernel's honest fixed pools and `setrlimit` is a documented no-op.
* A directory descriptor as a capability. Rach2 stores the cwd and every dirfd as a canonical absolute string, so a relative open re-walks from the root and re-charges the whole prefix. That is stricter than POSIX and cannot escalate; the alternative threads an "authorized prefix" through eight call sites to model a right that was never checked at open time either.
* A PAM or `login.defs` policy layer. It would be a second authentication implementation in an image whose point is that there is one.

## The decisions that shape everything (confirm before code)

* A deferral closes or becomes a decision, and a decision lives in a component Readme with its cost, not in a dev-log record. The milestone records are frozen history; the component Readmes carry the current contract.
* The shipped image gains exactly one more setuid-root program, `/bin/passwd`, and no others. `adduser` and `login` start as root (from a root shell and from init) and refuse a non-root caller before touching a file. The build-time guard names the allowed set per image and fails on anything else, so the invariant is checked rather than intended.
* One place in the image mints a password hash, and one salt policy: `getrandom(2)`, failing closed rather than falling back to `GRND_INSECURE`, matching the kernel's own RNG policy. The refusal reaches the operator as two lines, the library's `pwauth: no trusted entropy` and the caller's own, for the reason phase 8 gives. BusyBox's hashing applets are compiled out. BusyBox's salt comes from an LCG seeded by `getpid() + monotonic_us()` (`libbb/pw_encrypt.c`), which is indefensible next to a kernel that refuses to hand out untrusted randomness.
* `CONFIG_FEATURE_DEFAULT_PASSWD_ALGO="sha512"` is a transitional setting, not a standing defense. The symbol is `depends on PASSWD || CRYPTPW || CHPASSWD` (`loginutils/Config.in:169-173`) and `build_busybox.sh` runs `yes "" | make oldconfig`, so once all three applets are off the symbol is dropped and the line in `rach2.config` is silently discarded. The standing guarantee is that all three hashing applets are compiled out.
* An applet that would want a set-id bit is compiled out, not shadowed by a staged program. Standalone ash resolves an applet name before it searches `PATH` (`shell/ash.c`), so a staged `/bin/passwd` cannot be reached by name while the applet exists: the exact trap milestone 15 solved for `su` by turning `CONFIG_SU` off. The enabled `BB_SUID_REQUIRE` set today is five applets, not three: the generated `include/applet_tables.h` carries `login`, `vlock`, `passwd`, `wall` and `crontab` and no `su`. All five go off before the invariant may be stated as "busybox contains no applet that would want a set-id bit"; stating it after only `passwd`, `login` and `vlock` would be false.
* The applet guard parses the build's own generated table, `vendor/busybox/busybox-1.36.1/include/applet_tables.h`, which holds `const char applet_names[]` as NUL-separated tokens, and matches whole tokens. A substring search over a stripped megabyte binary matches `su` inside dozens of unrelated strings. The guard asserts a positive sentinel (an applet known to be enabled, `cat`) and fails when the sentinel is absent, so an empty or unparsable scan is a build failure rather than a silent pass.
* A file the system authenticates against is replaced, never rewritten in place, and the replacement runs under a writer's lock. `krffs_write_node` can relocate a growing file and `O_TRUNC` passes through an empty state, so an in-place rewrite of `/etc/shadow` is observably broken to a concurrent reader; and a credential change is a read-modify-write, so two unserialized writers lose one of the two updates whatever the write idiom is. The idiom is `umask(077)` and restore, any leftover temp unlinked, an `O_EXCL` temp beside the target inside root-owned `/etc`, the whole text written, `fchown` then `fchmod` from the original (that order, because phase 5 makes chown clear the set-id bits, which is why `cp` and `install` chown before chmod), `fsync`, `rename`, then a second `fsync` through that same descriptor, held open across the rename because `sync(2)` discards its result and only `fsync` can report `-EIO`. Because `krffs_rename` changes only the name and the parent id, the destination inherits the source node's mode and owner: the temp's mode is the result's mode, and getting that wrong makes the file that exists to be unreadable readable.
* Search is charged on every component of the final absolute path, every time, including the prefix a dirfd or the cwd contributed. One rule, no new state, strictly stricter than Linux. `..` collapses lexically in `canonicalize_abs` before resolution, so a directory a path merely transits is not charged; with no symlinks and no directory hard links the lexical parent is the real parent, and the Readme says the equivalence depends on that.
* The search predicate carries the same `use_real` flag `cred_access_node` already takes. `do_access` judges its leaf by the real ids (`syscall.c:2635`) precisely because `access(2)` asks who the caller really is; charging its prefix by the effective ids would make `access()` inside `su`, `sudo`, or `passwd` report reachable a path the real user cannot reach, an internally inconsistent answer from the one call that exists to give a set-id program its invoker's view.
* Denial on the prefix beats absence of the leaf. The ten sites that collapse the resolver's error into `-ENOENT` or `-ENOTDIR` return it verbatim instead, and the mutation family is converted with them: `cred_parent_writable`'s parent lookup, `sys_creat`'s existence probe, `sys_mkdir`'s existence probe, `sys_rmdir`'s target resolve, and `execve`'s program resolve. Without those, a uid-1000 process still creates, unlinks, renames, mkdirs and rmdirs under a denied ancestor, and a probe whose denied directory is also unwritable goes green while proving nothing.
* Three re-resolves stay on the unchecked wrapper, each for a stated reason. `fd_node_check` (`syscall.c:851`) and `copy_path_at` (`syscall.c:927`) re-validate an already-open descriptor; a checked re-validation would turn a live fd into `-EBADF` after a chmod on an ancestor. The post-create re-resolves in `do_open` (`1296`), `sys_creat` (`4409`) and `sys_mkdir` (`4522`) run after the prefix has already been charged and after the object exists; re-charging could only differ if the tree changed underneath, and a failure there would strand a created file with no descriptor.
* The set-id clear is a syscall-layer rule, not a filesystem one. `krffs_write_node` and `krffs_truncate` are also called by the kernel debug shell (`kernel.c:2165`) and by `krffs_write`, where there is no `current_proc`. The clear runs after the write, through the updated node pointer, because a relocating write copies the old mode wholesale.
* The clear never touches the root node. `KRFFS_MODE_DIRTY` and `KRFFS_MODE_SUID` are the same bit, `0004000`, and `chown("/", 0, 0)` reaches `krffs_chown_node` from any uid today: `do_chown` resolves the empty name to `krffs_fs->node` (`syscall.c:2841`) and the function demands privilege only when a value actually differs. An unguarded clear appended there is an unprivileged clear of the crash evidence `fsck.krffs` reads. The node-identity guard is the fix; gating the store on an actual change is redundant with it and is recorded as such.
* The dirty flag stays in the mode word. Moving it is a v3 on-disk change that would make every existing image read as cleanly unmounted, and it needs coordinated edits in the kernel and two host tools. Considered and rejected here.
* The console login fails safe by refusing, never by admitting. `spawn_shell` (`utils/init.c:50-56`) loops over `Shells[]` and falls through whenever `execve` returns, whatever the errno; putting `/bin/login` first under that loop would drop the console to an unauthenticated root `/bin/sh` on any exec failure, not only on a missing binary. Narrowing the fall-through to `errno == ENOENT` inverts the danger rather than removing it, since an os-real image built without `/bin/login` is exactly the `ENOENT` case and exactly the image that must refuse hardest. So the fallback is compiled out, not narrowed: `utils/init.c` builds twice, `init-shell` with today's list unchanged and `init-login` with `-DINIT_CONSOLE_LOGIN`, whose session child execs `/bin/login` and nothing else and whose binary carries no string naming a shell. `rach2.rescue` reaches a kernel debug shell, not the image, and is the only way back in, so this is the change that can lock everyone out of the box.
* One musl stamp. See "What stays deferred".

## The phases, and why they are ordered this way

The gate before the mechanism before the userland, with the network work last. Phases 1 to 3 exist because several later proofs are worthless without them: a `-EPERM` assertion means nothing while a missing path also reports `EPERM`, a probe that dies on a signal is currently scored by its child's exit status, and the set-id sweep covers two of six manifests. Then the kernel permission rules, hardest and widest first, so the capstones every later phase runs are also shaking them out. Then the programs that spend those rules. The two network phases come after the userland arc rather than before it: nothing in the account work needs them, and a regression in the TCP state machine placed early would surface as "the SSH capstone fails" somewhere in six phases where six other things also changed. Placed last, the SSH capstone is a fixed reference across the whole userland arc. The suite stays green at every step.

### Phase 1: the harness, the scoring, and the style gate's reach

Three tooling defects, one commit, no kernel behavior beyond one diagnostic line.

`tools/runtests.py` anchors each probe on `returning to kernel shell`, which two kernel paths print: `sys_exit` (`syscall.c:412`) and the signal death in `terminate_current_process` (`kernel.c:239`). Only the first is followed by a status the runner can read, and the runner takes the last `Process exited with status N` in the window (`runtests.py:141`), so a probe that forks a child which exits 0 and then dies on `SIGSEGV` is recorded PASS. The last status in the window is not reliably the probe's own even without a signal: `sys_exit` prints the status at `syscall.c:342` and only then calls `schedule()`, so a child that outlives its parent prints its own status after the parent's and before the marker.

Fix the scoring at the source. `sys_exit` prints `sys_exit: init process %d exited with status %d, returning to kernel shell` (lowercased to match the diagnostics rule, marker text unchanged), and the runner scores that line alone, ignoring every other status in the window. A window ending in `killed by signal` fails regardless of what it contains. `runtests.py` also fails, naming the probes it never ran, when `len(results) != len(PROBES)`, since today it `break`s on the first hang and prints a smaller count as if that were the suite; and the `test` target passes an explicit `--timeout` sized for the grown suite, because the 180 s default is one global deadline shared by every probe.

`tools/harness.py:157` reads `if expect(...) is None:` while `expect` returns `True`/`False` (line 141), so `step_failures` is never incremented for an `expect=` step and the comment on line 149 describes a guard that does not run. It becomes `if not expect(...)`. The `--ok` gate itself is sound (line 204 already requires `step_failures == 0`), and `exec=` steps already count correctly, so the live exposure is the two `stress-test` targets; fix it anyway, in the commit that fixes the other scorer.

`tools/check.sh`'s `newcode_ch` is `tests/host/*.c tests/host/*.h tests/*probe.c` plus the musl port, and its cppcheck list is the kernel plus `tests/*probe.c`. Neither reaches `tests/musl/` or `utils/`, so the plan's registration rule cannot claim the globs bite for a musl probe or for `utils/pwauth.c`. Extending them wholesale fails today: `clang-format --dry-run -Werror` rejects seven files under `utils/` and nine under `tests/musl/`, the legacy tree the gate deliberately never reformats. So the rule is: each new source is added to `newcode_ch` and the cppcheck list by name, in the phase that creates it, and `tests/Readme.md` states that rule instead of the false glob claim. The `sudoprobe` entry, missing from `tests/Readme.md` since milestone 15, lands here too, since this commit already rewrites that file.

Proof: `runtests.py --selftest` scores its window rule over serial fragments held in the script (a clean run, a run whose forked child exits 0 before a signal death, a run whose orphan exits after the parent, a run with no status at all) and is run from `tools/check.sh`, so the scoring rule has a regression test that needs no boot. Separately and once, recorded rather than committed: a probe that forks, reaps a clean child, then dereferences NULL is reported PASS before the change and FAIL after. `make test` stays green at 44.

Readme: `tests/Readme.md` (a signal-killed probe fails, the registration rule, the `sudoprobe` entry), `tools/Readme.md` (the two runners' scoring contracts).

### Phase 2: the errno truth at unlink and rename

`sys_unlink` (`syscall.c:4481`) and `sys_rename` (`syscall.c:4631`) return `krffs_unlink`/`krffs_rename`'s bare `-1`, which userspace decodes as `EPERM`. Translate at the syscall boundary the way `sys_mkdir` and `sys_rmdir` already do, leaving `krffs.c`'s `-1` convention alone for the debug shell and the boot self-test. Unlink must resolve its target to do this, which it does not today; that resolve is what phase 4 then routes through the checked resolver.

The mapping follows what the filesystem actually refuses, not one blanket errno. `krffs_unlink` (`krffs.c:1089`) refuses a missing path (`-ENOENT`), the root (`-EISDIR`), and a directory (`-EISDIR`). `krffs_rename` refuses a missing or root source (`-ENOENT`), a directory *source* (`krffs.c:1127`, because a directory's children reference its id, so a move would orphan them: `-EPERM`, the errno POSIX reserves for a rename the filesystem cannot perform, not `EISDIR`), a missing destination parent (`-ENOENT`), and a directory *destination* under a non-directory source (`krffs.c:1144`: `-EISDIR`, which is what POSIX reserves for exactly that case).

Proof: `tests/rmtest.c` and `tests/mvtest.c` gain exact-errno assertions where they now check only the sign, each case creating and destroying its own fixture, including the directory-source and directory-destination cases that separate `-EPERM` from `-EISDIR`. `make test` stays green at 44.

Readme: `rach2/sys/fs/Readme.md`, whose path-resolution paragraph says today that the syscall layer returns the walk's error verbatim, which unlink and rename did not do; it now states what each returns and why a directory source is `EPERM`.

### Phase 3: the build guards and the staging rule

`tools/check_busybox_suid.py` looks up two hardcoded paths and nothing else, and the Makefile runs it on `os-real` alone (`Makefile:320`), so a set-id line anywhere else passes silently. The deeper hole is the grammar it does not know. `apply_line` (`krffs/stageimage.krffs.c:677`) carries five mode-bearing verbs, not two: `dir` (703), `text` (706), `file` and `optional-file` (723), and `exec-dir` (761). `exec-dir` applies its one mode to every executable it stages, so changing `os-simple.manifest`'s `exec-dir 0755 / build/utils` to `04755` would make every hand-written utility setuid root while never producing a `file` or `text` line for a scan to find. The repo carries six manifests, and phase 5 stages a probe into a seventh consumer of `disk-test.manifest`.

The guard becomes `tools/check_setid.py`, and it parses the manifest rather than searching it. Tokenization matches `apply_line` exactly, because a guard that reads the grammar differently from the tool that stages it is a guard with a hole: fields split on spaces and tabs, a comment is a line whose first token begins with `#` (there is no trailing-comment form, so `file 0755 /x build/x # note` is a directive with an ignored tail), the mode is the second token for all five verbs, and an omitted owner reads as `0:0` the way `parse_mode` defaults it. The rules per verb:

* `file`, `optional-file` and `text`: a mode carrying `04000` or `02000` must appear in that manifest's allowlist at the same path with the same mode and the same owner. `optional-file` is half of the pair the old `parts[0] in ("file", "text")` test missed outright.
* `exec-dir`: a set-id mode is refused, with no allowlist escape. The set of paths it privileges is a property of what happened to be built into the host directory, not of the manifest, so there is nothing stable to declare; a binary that must be privileged is named with `file`.
* `dir`: a set-id mode is refused as well, deliberately and with the reason stated. KRFFS implements no setgid-directory inheritance: `krffs_stamp_new_node` takes the creator's ids and nothing anywhere reads a parent's setgid bit, so a setgid directory would be a stored bit no reader consults, which is the exact defect phase 6 closes for sticky. Sticky is not a set-id bit and stays legal; `dir 1777 /tmp` is the only one in the tree and phase 6 gives it meaning. When a later milestone implements group inheritance, the allowlist is where a setgid directory becomes declarable.
* An unknown verb is a hard error, so the next directive added to the grammar arrives through the guard instead of past it.

It fails on an undeclared set-id entry, on a declared entry no manifest stages, on a mode or owner mismatch, on a malformed mode field (`0999` and `08`, which `check_busybox_suid.py`'s `staged()` reported as "not staged", and `04755:0`, which it misreads instead: `partition(":")` hands it the bits `04755` and the owner `0`, so the entry is reported as owned by the wrong owner), and on a manifest the table does not name. The per-entry owner is required rather than a global root-ownership assertion: the test image deliberately stages `file 04755:5:0 /suidhelper.u5` and `file 02755:0:5 /suidhelper.sgid` to prove the bit grants the file owner's identity whoever that is. The busybox-unprivileged assertion is kept. As of this phase the allowlists are: os-real, one entry, `/bin/su` (04755:0:0); the test image, six, `/suidhelper.suid` (04755:0:0), `/suidhelper.u5` (04755:5:0), `/suidhelper.sgid` (02755:0:5), `/suidhelper.nox` (04644:0:0, setuid without execute, still a set-id line), `/sudo` (04755:0:0) and `/musl/suidmusl.suid` (04755:0:0); os-simple, `disk-test`, `persist-test` and `stress-test`, none. Phase 11 commits two more manifests, `login-test-strict` and `login-test-shell`, and each takes its own entry in this table then, with no set-id entry and a sentinel node of its own, since a manifest the table does not name is a hard error and both are staged through `mkimage.sh` like any other.

The sweep still trusts one thing it cannot check: that this parser agrees with `apply_line`. A divergence in tokenizing or in the octal parse is invisible to it, and `exec-dir` expands to a set the text does not name at all. So the guard has a second half that reads the artifact. `check_setid.py --image <file> --manifest <path> [--offset BYTES] [--size BYTES]` walks the staged image's node chain the way `fsck.krffs` does (each node advances by its own `size`, wrapping at the region end, with the iteration bounded by the region divided by the node size), reconstructs every reserved node's path from `parent_id` (0 is the root, and `krffs_mix_id` never returns 0, so the chain terminates only at the root), and compares the nodes carrying `04000` or `02000` against the allowlist that manifest owns. The manifest is an argument and not an inference: the allowlist is per manifest and an image carries no record of which one staged it. `struct krffs_node` (`krffs/krffs_node.h`) is `#pragma pack(1)` and is the v2 on-disk ABI, so this is one `struct` format string, not a port of the file system. An unresolvable or cyclic `parent_id` is an error, never a skipped node.

It is not `fsck.krffs`. That tool prints a reserved node's owner but never its mode, and prints the bare `name` rather than a path, since it never reads `parent_id`, so it cannot answer the question being asked; and it opens the image `O_RDWR` and clears the dirty flag whenever it finds one, so teaching it the missing fields would leave the build writing to the artifact it inspects, which is the artifact phase 5's disk capstone reads back. The layout duplication gets the positive-sentinel treatment the applet-table guard gets in phase 9: the inventory must find every declared entry, which is itself the control wherever the declared set is nonempty, and the four allowlists that declare no set-id entry each name one ordinary node the inventory must report exactly (`/hello.txt` 0644:0:0 in os-simple, the staged probe in the three disk manifests), so a wrong offset or a walk that finds nothing fails the build rather than reading as a clean image.

The two halves run at the two places they belong. The sweep runs over every manifest from `tools/check.sh` as one more numbered step, which means renumbering both hardcoded places, the `hr "N/M"` labels and the header comment's list; the gate carries nine steps today, numbered 0 through 8, and phase 1 has already added one, so this phase asserts no total and just counts what is there. `check-busybox-suid` becomes `check-setid`, still a prerequisite of `os-real-image`, `os-real-disk` and `os-real-grub-disk`. The inventory runs from `krffs/mkimage.sh` and `krffs/mkdisk.sh`, the two chokepoints every image passes through, so an image built by a script rather than by a make target is checked too; each passes through the manifest it already holds in `$1` (`MANIFEST`), `mkdisk.sh` passes both the partition offset and the partition size it already computes and already hands to `mkfs.krffs` and `stageimage.krffs`, and `mkimage.sh` passes neither, since there the region is the whole file. The size is not optional on a disk: the region is a 48 MB partition inside a 64 MB file, so without it both the wrap at the region end and the iteration bound are computed off the wrong end, which is why `fsck.krffs` takes the pair too. `mkimage.sh` runs the inventory on the `$TMP` file before the rename, so a failing image is never moved into place. `mkimage.sh` now requires `python3`, which `mkdisk.sh` already does.

`utils/Makefile` builds the privilege family (`su`, `sudo`, and the coming `passwd`, `adduser`, `login`) into `build/utils/sbin/` the way `SBIN_INIT` already does, so `os-simple.manifest`'s `exec-dir 0755 / build/utils` sweep stops staging an inert `su` and `sudo` at that image's root; `stage_exec_dir` is not recursive and a subdirectory fails its `S_ISREG` filter, which is the same mechanism that already keeps `init` out of that image's root. Both consumers follow the new paths: `os-real.manifest`'s `/bin/su` and `test.manifest`'s `/sudo`, which the phase must repoint or the test image fails to build and `sudoprobe` disappears.

`krffs/Makefile` gains the `libc-check` order-only guard `utils/Makefile` already has, testing for the extracted musl source `MUSL_CRYPT` names, with `krffs: vendored musl source not extracted; run make deps first`; without it a standalone `make -C krffs` in a `make distclean`d tree fails with make's "No rule to make target".

Two scoped items are already closed. `88d8d93` added `krffs: $(LIBC_STAMP)`, and `verify-host` already reaches the same stamp through `check-libc`, which also checks the extracted source and the installed libc separately. `tools/hosttest.sh:44` already names a missing `host-deps` file and the repair, rather than leaking a compiler error. Only the standalone `make -C krffs` path was left.

### Phase 4: search on every path component

The widest blast radius in the milestone: every path syscall.

`krffs_walk_e` takes a `may_search` predicate and reports its negative return through `*err`, covering the `.` and `..` arms too. `krffs_resolve_x` is the new entry point; `krffs_resolve` and `krffs_resolve_e` become NULL-predicate wrappers and stay bit-identical, which is load-bearing for the three re-resolves named in the decisions. In `syscall.c`, `cred_may_search` wraps `cred_access_node(dir, CRED_X, 0)` and `cred_may_search_real` wraps `cred_access_node(dir, CRED_X, 1)`; `do_access` installs the second, everything else the first. The predicate dereferences `current_proc`, so `krffs_resolve_x`'s header states that it may only be installed from syscall context.

The conversion sites are enumerated, not counted:

* The ten that collapse the walk's error: `syscall.c` 1285 (`do_open`), 1936, 2371, 2578, 2630 (`do_access`), 2749 (`path_exists`), 2794 (`do_chmod`), 2843 (`do_chown`), 3411, 4725. Each returns the walk's error instead.
* `cred_parent_writable`'s parent lookup at `syscall.c:1047`. This one carries the whole mutation family: `creat`, `unlink`, `mkdir`, `rmdir` and both ends of `rename` reach the filesystem through it.
* `sys_creat`'s existence probe at `4390`, `sys_mkdir`'s at `4509`, and `sys_rmdir`'s target resolve at `4553`, so a denied ancestor answers `-EACCES` rather than `-EISDIR`, `-EEXIST`, or `-ENOENT`.
* `execve`'s program resolve at `3818`, moved ahead of `krffs_open` so a denied ancestor answers `-EACCES` whether or not the program exists.
* `sys_unlink`'s target resolve, added in phase 2 for the errno, and `sys_rename`'s two ends.

`do_open` answers `-EACCES` before considering `O_CREAT`: its fall-through reaches `krffs_create`, which walks unchecked. `do_access`'s header stops claiming there is no credential model, false since milestone 14.

Cost: none worth measuring. `krffs_find_child` already scans the node list per component and the predicate reads `mode`, `uid`, and `gid` out of the same header the matcher just compared, so it adds no page fault on the windowed and disk mounts.

### Phase 5: the set-id bits cleared on write, truncate, and chown

One helper, `cred_kill_setid`, beside `cred_privileged`: return early for the root node and for a directory, always drop `SUID`, drop `SGID` only when the group-execute bit is set, since setgid without group-execute is the mandatory-locking mark rather than a grant. Three call sites with the two different privilege rules POSIX specifies: after a successful `krffs_write_node` (`syscall.c:589`), through the updated node pointer and gated on `!cred_privileged()`; in `do_open`'s `O_TRUNC` branch (`syscall.c:1340`), gated the same way; and in `krffs_chown_node` on every successful chown of a non-directory, not gated on privilege, since Linux kills the bits whoever asks and that is why `cp` and `install` chown before chmod. The euid-0 write exemption is the `CAP_FSETID` analogue and matches V7; without it any root process silently disarms `/bin/su` by rewriting it. `krffs_chown_node` also gains the no-change gate described in the decisions.

`creat(2)` on an existing file is a documented hole that this phase closes or names. `sys_creat` (`syscall.c:4395-4400`) checks `CRED_W` and hands back a write-only fd at offset 0 with no `krffs_truncate`, unlike POSIX `creat` = `O_WRONLY|O_CREAT|O_TRUNC`. Either fix the missing truncate here, in which case the clear rides the same branch, or state in the Readme that `creat` reaches the clear only through the first write. Decide before code; do not leave both readings in the tree.

Proof: `tests/modeprobe.c` (46), which builds its own fixtures and removes them, because the probes share one boot and a probe that disarmed `suidprobe`'s staged fixtures would buy a green run by breaking a later probe's premise. As root: the 04755 baseline, the privileged write exemption, chown to 1000:1000 dropping the bit (no privilege exemption, the assertion that separates the two rules), and a chowned 04755 directory keeping it. As uid 1000 on its own files: a small in-place write clears; a write that grows the file past `node->size - sizeof(krffs_node_t)` and forces `krffs_resize_reserved_node` to relocate it also clears, asserted against the relocated node by stat after the append, which is the one case a clear applied through the stale pointer would fail; `O_TRUNC` clears; `creat` on an existing set-id file behaves as the decision above says; 02755 clears; 02644 survives; a plain 0755 file reads back 0755 as the control. Every operation's return value is checked before its mode assertion.

The root-node guard cannot be proved from the RAM image, where the flag is never set and stat reports the root with a fixed mode. So `tests/dirtyprobe.c` is staged into `krffs/manifests/disk-test.manifest` and `tools/crash_test.sh` gains a third phase: boot the disk image with `rach2.fsdisk rach2.rescue`, `exec /dirtyprobe`, wait for `DIRTYPROBE OK` (a token, not a sleep, as the two existing phases already do), kill QEMU, and require offline `fsck.krffs` still to report "not cleanly unmounted". The probe hammers every path that reaches the root node with a mode-adjacent operation, asserts each returns exactly what it returns today, and calls `sync(2)` after each attempt before printing its token. The `sync` is the whole proof: the page cache is write-back, so a spurious clear would sit in a dirty frame and never reach the platter before QEMU is killed, and the phase would go green on a broken kernel. The phase is demonstrated failing once with the node-identity guard deleted, and that run is recorded.

### Phase 6: the sticky bit enforced, and the permission model's verdicts

Split `cred_parent_writable` into a `cred_parent_dir` that returns the parent node and keep the old function as its thin caller, so the create paths are untouched. Add `cred_sticky_ok(dir, victim)`: with the directory's sticky bit set, the entry may be removed or renamed only by the entry's owner, the directory's owner, or a privileged caller; otherwise `-EPERM`, which is POSIX's errno and not `EACCES`. The SVR4 relaxation that also permits it when the caller can write the file is not in POSIX and is not adopted. Four call sites: unlink (whose target resolve phase 2 already added), rmdir, and both ends of rename. The destination side is the one whose omission leaves the attack fully open while an unlink-side probe goes green. Order: the directory write check first, so a caller with no write permission still sees `-EACCES`. The root is non-sticky by identity, the same fixed-mode rule `cred_access_node` uses, so the dirty flag never enters a permission answer. The debug shell's direct `krffs_unlink` and `krffs_rename` calls stay exempt: it is the rescue root and has no credentials.

Proof: `tests/stickyprobe.c` (47), with a paired non-sticky control directory beside the sticky one, which is what makes the denials mean anything. As uid 1000: unlink of a root-owned file denied in `/sticky` and permitted in `/plain`; rename within `/sticky` denied; rename of its own file over the root-owned file denied; rmdir of a root-owned subdirectory denied; unlink of its own file permitted. Then the directory-owner clause through a 01777 directory owned by 1000, and a third uid denied in both. Phase 2 is a hard prerequisite: without the errno translation, `-EPERM` is not diagnostic. `/tmp` is the only sticky directory in any manifest and is staged empty, but the SSH capstone runs before the claim stands, since ash heredocs and dropbear are the plausible temp-file users.

This is the last phase that rewrites `rach2/sys/fs/Readme.md`'s "Deliberate simplifications" bullet, so the permission model's verdicts land here rather than in a later text-only pass: quotas, ACLs and capabilities each recorded with their cost (the node header has no room for a quota table or an ACL block without a v3 format; the `euid == 0` override sites are the capability model this system teaches), and the statement that per-user resource limits are not deferred at all, since `getrlimit`/`prlimit64` report the kernel's honest fixed pools and `setrlimit` is a documented no-op. The gate on those sentences is the independent review reading each verdict against the code it claims, since `make verify-style` will pass any grammatical sentence including a wrong one.

### Phase 7: the kill rule completed

`cred_may_signal` takes the signal it is judging: euid 0 passes; `SIGCONT` within the same session passes; otherwise either of the sender's real or effective uids must match either of the target's real or saved uids. Both call sites (`syscall.c:5519`, `5559`) pass `signo`. The signo-0 existence probe keeps the strict rule, which is the correct POSIX outcome, since the exception is for `SIGCONT` and not for probing.

This closes a live defect in the shipped image. `/bin/su` is 04755 and calls `setuid(pw->pw_uid)`, so the exec'd shell runs with ruid 0; ash implements `fg` as `killpg(pgid, SIGCONT)` and ignores the return (`shell/ash.c:4230`); so today a uid-1000 shell cannot resume a job it started through `su`: the `killpg` returns `-EPERM` silently and `restartjob` waits on a job that will never run. The Doxygen block states the rule as shipped, says why the session exception cannot extend a sender's reach (`setsid` only ever creates a session, never joins one), names the exposure it does create (an unprivileged session member can make a root process's `SIGCONT` handler run at a time of its choosing), and records that `tty_signal_group` stays unchecked because the terminal generates those signals, not a process.

### Phase 8: the shared credential library, and su rebuilt on it

`utils/pwauth.c` and `pwauth.h`, linked into `su` (and later `passwd`, `adduser`, `login`) the way `utils/resolv.c` is already linked into `ping` and `nc` (`utils/Makefile:88-96`). It is the only code in the image that compares a password against a stored hash, mints a salt, or replaces a credential file. Reading the databases for a rewrite stays with the writer, inside its transaction, which is exactly why `pwauth_check` takes the stored hash as a string. A pure reader is different: `pwauth_verify` resolves the entry itself and takes no lock, since a reader that loses a race against a concurrent writer sees one file or the other and never a torn one, the rename being atomic. Eight entry points:

* `pwauth_check(stored, password)`: the pure comparison, factored out of `su.c`'s private copy (`su.c:51-64`) with its behavior unchanged (a missing or non-`$` hash denies everyone). Pure so the host seam test can reach it.
* `pwauth_verify(user, password)`: `getspnam` plus `pwauth_check`.
* `pwauth_read_password(prompt, buf, size)`: decides on `isatty(0)` and reads fd 0 either way. The prompt goes to fd 2 unbuffered whatever `isatty(0)` says, and only the echo suppression is conditional; that is what lets a driver holding a pipe on fd 0 rendezvous on the prompt instead of guessing at a sleep. On a terminal it clears `ECHO` through `tcgetattr`/`tcsetattr` and restores it on every exit path including a signal. It owns that restoration itself rather than leaning on the transaction's handlers, because the readers that matter most hold no transaction: `su` and `login` authenticate without writing anything. So when no transaction is held it installs `SIGINT`, `SIGTERM`, `SIGHUP` and `SIGQUIT` around the read and restores the previous dispositions after, which leaves the transaction's own handlers in force when there is one. Without this a `^C` at the `su` or `login` prompt leaves the console with `ECHO` off, on the image where phase 11 makes that console the only way in. otherwise it reads plain stdin, so the recorded capstone's `echo <root-password> | su -c 'id'` keeps working. It never opens `/dev/tty`: a probe runs as init under the debug shell with fd 0 bound to the console (`fd_init_stdio`, `fd.c:87`), so a `/dev/tty` reader would block forever and `runtests.py` would report a hang and skip every later probe.
* `pwauth_salt_map(bytes, n, out)`: the mapping onto `./0-9A-Za-z`, a function of the bytes alone. It is separate from the draw so the host test can exercise it without entropy.
* `pwauth_mint_salt(out, size)`: `getrandom(2)` with no `GRND_INSECURE`, then the mapping. On failure it writes no byte of `out`, prints `pwauth: no trusted entropy`, and returns -1. The diagnostic names `pwauth` and not `passwd` because the library is the component that failed; each caller adds its own refusal line (`passwd: password unchanged`). That is the milestone decision's single message split across the two components that each know one half of it. The rule the library follows throughout, so the two halves of it do not look arbitrary: a line reporting the library's own failure names `pwauth`, and a line an operator must act on names the calling program, which is why `cred_txn_begin` takes `prog` and the busy lines below carry it while this one does not.
* `cred_txn_begin(const char *prog)` and `cred_txn_end`: the writer's exclusive lock, below. The program name is a parameter because only the library knows when an acquire first has to wait, and the line it prints then must name the program the operator ran.
* `cred_rewrite(path, text, len)`: the replacement, below. It returns -1 without touching anything unless the transaction is held, so a caller that forgot to take it cannot ship quietly.

A credential change is a read-modify-write, and the replacement idiom does not make that interval exclusive. `passwd` reads `/etc/shadow`, authenticates the caller against the hash it read, prompts twice, and writes the file back; two sessions can read the same pre-image and rename in turn, and the second rename restores the first one's old hash. `O_EXCL` on the temp file guards nothing here, because the two runs are not racing on the temp, they are racing on a snapshot. The kernel offers no help: `F_SETLK`, `F_SETLKW` and their 64-bit twins return 0 for every request (`syscall.c:3309-3316`) and `F_GETLK` always answers `F_UNLCK` (`syscall.c:3317`), a documented no-conflict contract dropbear depends on, so an advisory lock records nothing at all.

So the library carries its own transaction, and it is a lock file. `cred_txn_begin` creates `/etc/.pwlock` with `O_CREAT|O_EXCL|O_WRONLY` at mode 0600 and writes the holder's pid into it; `cred_txn_end` unlinks it and closes. The exclusive create is the whole of the exclusion: it is one syscall, and a syscall on this kernel does not yield (`timer_handler` skips `schedule()` while `current_proc->in_syscall`, `kernel.c:138-140`, and a page-cache window fault polls with interrupts off), so nothing can interleave between the existence test and the create at `syscall.c:1307`. `O_EXCL` on the lock file is a lock; `O_EXCL` on the temp file stays what it always was, a corruption check. A `mkdir` lock would serve as well and is the shape `krffs/gen_demo_password.sh:37-40` uses on the host; a file is chosen because it carries the holder's pid, which is what makes the recovery rule cheap.

Every writer takes the lock before its first read and holds it through its last rename: `passwd` before it reads `/etc/shadow` to authenticate, `adduser` before it reads `/etc/passwd` to test the name and across all three of its replacements. `cred_txn_begin` registers the release with `atexit`, so an ordinary `exit` cannot leak it, and installs handlers for `SIGINT`, `SIGTERM`, `SIGHUP` and `SIGQUIT` for the transaction's whole lifetime, because `atexit` runs on no signal death: the handler restores the terminal, unlinks any temp, and leaves through `exit` so the registered release drops the lock rather than the handler duplicating it. That is why a caller does not install its own: the lock outlives the terminal read, and the terminal read is only one part of what a signal must undo. Readers do not lock. `su` and `login` open, read and close, and a rename publishes a whole file, so a reader sees the old file or the new one and never a mixture; only writers serialize, which is why a wedged writer cannot lock anyone out of authentication. The one case that is not seamless is a reader holding a descriptor across a replacement: `krffs_rename` frees the node the destination name had (`krffs.c:1140-1147`), so that descriptor goes stale and its next use is `-EBADF` (`fd_node_check`, `syscall.c:837-855`) rather than stale bytes. Nothing in the image does that (`getspnam` opens, reads and closes), and the Readme states it as the contract rather than leaving "atomic against a concurrent reader" to be read as more than it is.

A crash leaves at most three residues, and each has a rule.

* A lock whose holder is gone. `cred_txn_begin` reads the pid and tests it with `kill(pid, 0)`; `ESRCH` means the holder died, so the lock is unlinked and the create retried once. This is the ordinary recovery and it costs no wait.
* A lock whose recorded pid is live but is not the holder: pid reuse, or an empty file left by a crash between the create and the write. The backstop is age. A lock whose mtime is older than `CRED_LOCK_STALE` (300 s, far longer than a human typing two passwords under the lock) is broken the same way. Between the two rules no lock is permanent; the cost is that a reused pid delays recovery to the age bound, and the Readme says so.
* Otherwise the lock is genuinely held. `cred_txn_begin` prints `<prog>: credential database busy, waiting` once, the first time an acquire has to wait, then retries `CRED_LOCK_TRIES` (10) times one second apart and fails, naming the holder: `<prog>: credential database busy (pid N)`. Both lines go to fd 2 unbuffered, so a driver reading a child's stderr sees the wait as it happens; the notice is the library's, not the caller's, because only the library knows it blocked. It never breaks a live lock.

A stray temp needs no rule of its own: `cred_rewrite` runs under the lock, so a temp it finds cannot belong to a live writer. It unlinks it and creates its own with `O_EXCL`; an `EEXIST` after that is a real fault and is reported, not retried. A multi-file transaction can also crash between two renames, and no lock helps: `/etc/shadow` is replaced and `/etc/passwd` is not. The library cannot fix that, but the ordering can, so `pwauth.h` states the contract and phase 10 honors it: a writer orders its replacements so that every prefix is a state the system reads safely (shadow with a locked `!` first, then group, then passwd, so a crash leaves at worst an account nobody can enter and no name that points at it).

The durability step must be able to fail, and the earlier draft's could not. It fsynced before the rename and called `sync(2)` after; `sys_sync` returns 0 unconditionally and discards `pc_sync`'s result by design (`syscall.c:1494-1506`), so a writeback failure would let `passwd` report success over credentials that never reached the platter. `sys_fsync` propagates `-EIO` (`syscall.c:1478-1491`), and its flush is whole-cache while KRFFS keeps its metadata in the same image the cache backs, so one `fsync` through any open descriptor also covers the rename's node header. `cred_rewrite` therefore keeps the temp's descriptor open across the rename: `umask(077)` and restore, unlink any leftover temp, `open(O_CREAT|O_EXCL)`, write the whole text, `fchown` then `fchmod` from the original (that order, because phase 5 makes chown clear the set-id bits), `fsync`, `rename`, `fsync` again through the same descriptor, `close`, every step checked. The descriptor survives the rename because the node is renamed rather than replaced, so `fd_node_check` still rebuilds a path that resolves back to it. A failure before the rename unlinks the temp and leaves the target untouched. A failure of the second `fsync` returns -1 with the file system already carrying the new file and the disk possibly still carrying the old one; the block comment states that the caller must then report failure, which is exactly the `-EIO` that the `sync(2)` version threw away. Both flushes are no-ops on a RAM-module boot, which is why the durability claim belongs to the disk image phase 13 presents. The comment also says why there is no hard-link backup (KRFFS has no links; `link` returns `-EPERM`) and why the temp's mode is the result's mode.

`su` is rebuilt on the library and its three point-of-use deferrals close. `read_line` and `password_ok` (`su.c:40-64`) become `pwauth_read_password` and `pwauth_verify`. The login form is parsed rather than ignored: today the option loop takes any argument beginning with `-` other than `-c` as a flag to discard (`su.c:75-83`), so `su - test` silently runs a non-login shell, and a chdir alone would not fix it, because this project makes a shell a login shell with a leading-dash `argv[0]` (`utils/init.c:21-26` passes `-sh` and `-ish`) while `su` passes the plain shell path (`su.c:131-135`). A bare `-`, `-l` and `--login` select login mode; any other unrecognized option is now a usage error rather than silence. Login mode is three things: `chdir(pw->pw_dir)`, an `argv[0]` of `-` plus the shell's base name (`-sh` for `/bin/sh`), and the environment `su` already builds from nothing. A chdir failure is fatal (`su: cannot enter %s`) rather than util-linux's warn-and-continue, because the home directory and the dash are the whole of `-` and continuing would run a login shell in the caller's directory and call it a login. Non-login mode is unchanged, cwd and `argv[0]` included, which is what makes the paired assertions below mean anything. PAM stays a non-goal.

This is the highest-consequence phase in the milestone: `cred_rewrite` replaces `/etc/shadow`, phases 9, 10 and 11 all build on it, and phase 11 makes the console unusable if it is wrong. It gets a probe of its own and one of the three harder reviews. The existing regression net does not cover it: there is no `su` probe anywhere in `tests/`, `sudoprobe` drives `sudo`, and the recorded capstone pipes a password, so it exercises only the non-tty path.

### Phase 9: passwd in the guest

`utils/passwd.c`, setuid root, in the `su`/`sudo` mould and built into `build/utils/sbin/`. The caller's identity is `getuid()`, never an argument, and the administrative exception that lets a caller name another account is `getuid() == 0`, not `geteuid() == 0`: this binary is 04755, so its effective uid is 0 for every caller, and a euid test would authorize the whole world. This is the milestone-16 `su` finding in a second place, so state it as the rule: a set-id program decides what its caller may do from the real uid, and uses the effective one only to do it.

Everything `passwd` does happens inside one credential transaction, phase 8's, taken before it reads anything and released only after the replacement is published:

* `cred_txn_begin` first, before the databases are opened and before any password is read or checked. Then `passwd` reads `/etc/passwd` and `/etc/shadow` through the transaction and works on those bytes: it maps `getuid()` to a name from that copy, checks the old password with `pwauth_check` against the hash from that copy, and rewrites the same copy. It does not call `getspnam`, which would be a second, independent read that can see a different file than the one about to be replaced; `pwauth_check` takes the stored hash as a string precisely so the caller can supply it from wherever the account was found. This is the ordering the review asked for: authentication and replacement see one image, under one lock.
* `cred_rewrite("/etc/shadow", ...)` publishes the new file and `cred_txn_end` drops the lock. There is no separate abort: `cred_rewrite` either renamed its temp or unlinked it, so ending after a failure publishes nothing and leaves nothing behind, and every exit path ends the transaction. A caller who arrives with the descriptor table nearly full (`MAX_FDS` is 16) makes one of `cred_rewrite`'s opens fail; the temp is unlinked and -1 returned, which is what makes that outcome a refusal rather than a half-written database.
* The lock is phase 8's `O_CREAT|O_EXCL` file in root-owned `/etc`, and it has to be that rather than a POSIX lock: `sys_fcntl64` grants every `F_SETLK` unconditionally as documented no-conflict semantics (`syscall.c:3309-3316`), so an `fcntl` lock would prove nothing here, while `do_open` really refuses an exclusive create of an existing name (`syscall.c:1307`, the KRFFS branch; the `1139` refusal is the synthetic-filesystem branch and never sees `/etc/.pwlock`) and a syscall is not preempted (`kernel.c:138-140`), which makes the create the indivisible test-and-set a transaction needs. Only writers take it. `login`, `su` and dropbear read the databases and take nothing, so no stale lock can keep anyone out of the box; that is the whole reason the reader side rests on rename instead.
* Because the lock is held across the terminal read, the four handlers `cred_txn_begin` installs for the transaction's lifetime (`SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`) are what drop it: each restores the terminal, unlinks any temp, and leaves through `exit`, so the release registered with `atexit` runs. `passwd` installs nothing of its own. A program that catches a signal to fix the terminal must also drop the lock, and the transaction is the only place that knows it is held. `SIGKILL` leaves the file behind, which the next writer breaks after finding the recorded holder pid dead, and the Readme states the pid-reuse cost of that.

The salt is minted after authentication and before the new password is prompted for, so a machine with no trusted entropy refuses without first asking for a password it cannot use. `pwauth_mint_salt` calls `getrandom(2)` with no flags, never `GRND_INSECURE`, and a short read counts as a failure; the library then prints `pwauth: no trusted entropy` and `passwd` adds its own `passwd: password unchanged`, ends the transaction without a replacement, and exits non-zero with every file byte-identical and no temp and no lock left. Nothing in `passwd` hashes with an untrusted salt, and nothing falls back. The new password is read twice through `pwauth_read_password` and must agree; an empty new password is refused, since an empty shadow field admits everyone and that is exactly what phase 11's `login` must never see.

Staged `04755:0:0 /bin/passwd` in os-real and `04755:0:0 /passwd` in the flat test image (which has no `/bin`), and named in both of `check_setid.py`'s allowlists. The test image gains a second unprivileged account, `probe2` (uid 1001, its own committed `$6$` hash beside `probe`'s and its own line in the `/etc/group` phase 8 staged), because a lost update is only visible when two accounts change.

`CONFIG_PASSWD` goes off, without which a bare `passwd` reaches busybox's applet and dies with `must be suid to work properly`, and `CONFIG_FEATURE_DEFAULT_PASSWD_ALGO` becomes `sha512` as a transitional setting that matters only until phase 10 turns off the last of `CHPASSWD`/`CRYPTPW`/`MKPASSWD` and `oldconfig` drops the symbol. `tools/check_setid.py` gains its third check here, beside phase 3's manifest sweep and image inventory: it parses `include/applet_tables.h` for whole NUL-delimited tokens and fails when `su` or `passwd` is present, when the `cat` sentinel is absent, or when the header cannot be found. It hangs off the `check-setid` make target, already a prerequisite of `os-real-image`, `os-real-disk` and `os-real-grub-disk`, and not off the source-only sweep in `tools/check.sh`, which must pass in a tree where busybox was never built and the generated header does not exist. Phase 11 extends the forbidden list rather than this phase asserting names that are still enabled, since `CONFIG_LOGIN`, `CONFIG_VLOCK`, `CONFIG_WALL` and `CONFIG_CRONTAB` are all still `y` at this point and a guard naming them would fail every os-real build for two phases.

Proof: `tests/musl/passwdmusl.c` (49), musl-linked because it needs `crypt` and the `pw`/`sp` parsers, which is also what gives it `pipe`, `poll` and `waitpid`. It runs as root, snapshots `/etc/passwd`, `/etc/shadow` and `/etc/group`, and restores them byte-for-byte before exiting. Three parts:

* The sequential arc. A uid-1000 child with scripted input on a `pipe`/`dup2`d fd 0 (so `pwauth_read_password` takes the non-tty path) execs `/passwd`, and the parent asserts on the file's bytes and metadata rather than on the exit status: the entry changed, the new hash is `$6$` with a different salt, `crypt(new, newhash)` reproduces it, every other line is byte-identical to the pre-image (a check through `getspnam` alone would pass on a file that lost every other account), `stat` still reports 0600 root, and no temp and no `/etc/.pwlock` remain. Then the negatives: a wrong old password exits non-zero with the file byte-identical, and uid 1000 asking to change root's password is refused.
* The concurrent case, which is what the lock exists for and what nothing in the earlier draft tested. The parent gives each child a pipe on fd 0 and a pipe on fd 2, forks, drops to the child's uid, and execs `/passwd`. It feeds A (uid 1000) its old password and then reads A's stderr until the exact prompt `New password:`; A can only have printed that after authenticating, so the parent knows, rather than assumes, that A holds the transaction. Only then does it fork B (uid 1001) and feed B its whole script. B's stderr is read with `poll` against a deadline, and the one line that may appear is the library's `passwd: credential database busy, waiting`: a prompt from B fails the probe on the spot, because B can only reach a prompt by reading the databases A is holding. The parent then feeds A its two new-password lines and reaps it, and only then does B's prompt appear, get answered, and B exit. Both waits guard on `WIFEXITED`. The closing assertion is that both accounts carry new hashes that `crypt` reproduces and that root's line is untouched.
* The entropy implication, stated as an implication and not a branch, so it cannot go green either way. The probe reads CPUID leaf 1 (ECX bit 30, RDRAND, saving and restoring EBX) and asserts the two directions: with RDRAND present, `getrandom` must succeed and `passwd` must change the file; with it absent, `getrandom` must return `-EIO` and every `passwd` run must exit non-zero printing both `pwauth: no trusted entropy` and `passwd: password unchanged`, with all three files byte-identical. The token names which side ran, `PASSWDMUSL OK (trusted)` or `PASSWDMUSL OK (fail-closed)`, the way `rngprobe` already does. The suite's `-cpu max` boot must show the first; the second comes from the invocation this phase adds to phase 8's `make test-noentropy`, on the same `-cpu qemu64`, gated on the `PASSWDMUSL OK (fail-closed)` token. It cannot come from `runtests.py --cpu qemu32`: that boots the whole suite without RDRAND, where `rngprobe` fails closed by design, so such a run can never be green.

What makes the concurrent case deterministic, and it is the same machinery phase 10 reuses: the probe's own children are the only user processes on the machine (the harness `exec`s the probe from the kernel debug shell, so there is no init and nothing else runnable), the kernel does not preempt a process inside a syscall (`kernel.c:138-140`), and every blocking point in the test is a pipe the parent controls or the transaction's acquire. So a child runs to its next blocking point whenever the parent blocks, and the parent's rendezvous is a token on the child's stderr, never a sleep: the holder's prompt and the loser's busy notice, both written to stderr unbuffered so a piped stdout cannot swallow them and the notice printed exactly once, when the acquire first has to wait. The deadline on the loser's read bounds a failure rather than deciding a pass, since the pass condition is one token and the failing build produces a different one; with the lock removed, B prints `Old password:` and the probe fails there, and if it printed nothing the deadline fails it too.

### Phase 10: adduser

`utils/adduser.c`, root-only and deliberately not setuid: it refuses a caller whose `getuid()` is not 0 before it opens anything. It carries no set-id bit, so its real and effective uids are the same and there is nothing to confuse, but it tests the same identity the same way, because the rule is the rule. Usage: `adduser [-u number] [-s shell] name`, the shell defaulting to `/bin/sh` and not checked for existence (an account may legitimately be created before its shell is staged).

It writes three databases and a home directory, and holds one transaction across all four. After `cred_txn_begin` it reads all three files through the transaction and does every check against that one image: the name must be absent from both `/etc/passwd` and `/etc/group`, the number must be free as a uid and as a gid, and with no `-u` the lowest number at or above 1000 that is free in both is chosen. Choosing a number outside the lock is how two concurrent runs hand out the same uid, so the read, the choice and the writes are one transaction and not three.

The publication order is chosen so that every prefix of it is a consistent system, because the lock excludes a concurrent writer and only the order survives a crash: KRFFS has no journal, `krffs_rename` publishes one file at a time, and ending the transaction after a failure publishes nothing further while undoing nothing already published. So: `cred_rewrite` on `/etc/shadow` with a locked `!` field first, then `cred_rewrite` on `/etc/group`, then the home directory (created 0700 and chowned to the new uid and gid, chown before any mode change, phase 5's rule), and `cred_rewrite` on `/etc/passwd` last. The account becomes visible only at the final step, so no interruption can leave a passwd field of `x` with no shadow entry, nor a gid that names no group. A crash before the last step leaves a shadow and a group entry that no account names, which nothing reads and the next run refuses to duplicate by name, and the refusal diagnostic says which database already holds it so an operator can finish the job by hand.

Then `cred_txn_end` drops the lock, and only then does it exec the password program (`/bin/passwd`, falling back to `/passwd` on `ENOENT` for the flat test image: os-real stages a `/bin` and the test image does not, so a program that must run under both looks in both, in that order), passing the new name. Releasing before the exec is required and not incidental: the lock is a file, it outlives `execve`, and a transaction carried across the exec would deadlock `passwd` against its own predecessor. Until that `passwd` succeeds the field stays `!` and the account cannot be entered, which is why shadow is written first and why a failure there needs nothing undone.

`CONFIG_ADDUSER`, `CONFIG_ADDGROUP`, `CONFIG_CHPASSWD`, `CONFIG_CRYPTPW` and `CONFIG_MKPASSWD` go off: each mints a hash through `libbb/pw_encrypt.c` and its LCG salt. `CONFIG_DELUSER` and `CONFIG_DELGROUP` go off with them, reversing what the earlier draft said, and for a different reason: they do not mint a hash, but they replace the same files without taking the lock, so a removal concurrent with a `passwd` silently loses one of the two changes, and an invariant that only one side of a race honors is not an invariant. The cost is that account removal is root editing the databases, and the Readme says so in a sentence rather than pretending the applets were inadequate. `/etc/skel` is not staged, and the Readme says the absence is deliberate.

Staged `file 0755:0:0 /bin/adduser` in os-real and `file 0755:0:0 /adduser` in the flat test image, from `build/utils/sbin/`. It adds no line to any allowlist, and `check_setid.py` fails the build the day it grows a bit. The test image already carries `/etc/group` and `dir 0755 /home` from phase 8, so this phase stages neither again; `adduser` creates the home's leaf and refuses a missing parent.

Proof: `tests/musl/addusermusl.c` (50), running as root, snapshotting the three files, and restoring them byte-for-byte along with removing the created homes and any lock file before it exits. It sits at the tail of `PROBES`, after `musl/passwdmusl`. Every wait guards on `WIFEXITED`.

* The end-to-end case: create an account with a scripted password on a `pipe`/`dup2`d fd 0, and assert `getpwnam` and `getgrnam` parse it back with the same number for uid and gid (proving libc can read what we wrote, not merely that bytes landed), that the shadow field is a `$6$` hash `crypt` reproduces from the scripted password, that the home exists 0700 owned by the new uid and gid, and that every pre-existing line in all three files is byte-identical.
* The failed-password case, which is what proves the order bought something: a second name whose two new-password lines disagree. The exec'd `passwd` exits non-zero, the account still exists in all three databases, and its shadow field is still `!`, so it cannot be entered and there is nothing to roll back.
* The refusals, each followed by all three files byte-identical and no `/etc/.pwlock` left behind: an existing name, `-u 0`, a number already taken as a uid or as a gid, and a uid-1000 child, which is refused before any file is opened.
* The concurrent case, `passwd` against `adduser`, driven by the rendezvous phase 9 describes. A uid-1000 `/passwd` child is stopped at `New password:` and therefore holds the transaction. The parent forks the root `adduser` and reads its stderr for the library's `adduser: credential database busy, waiting`; while that holds, `waitpid(..., WNOHANG)` reports `adduser` still alive and all three databases still byte-identical to the pre-image. That pair is the assertion an unlocked `adduser` fails: it would have read the pre-image and published all three replacements inside this window. The parent then feeds `passwd`, reaps it, feeds the two new-password lines `adduser`'s exec'd `passwd` now wants (which also proves the exec'd child re-acquires a lock its own predecessor released rather than deadlocking on it), reaps `adduser`, and asserts that both results survive: the new account present in all three files with a hash of its own, and the concurrently changed account's new hash still verifying under `crypt`. The closing cross-check is the invariant the review asked for, run over the final files: every `/etc/passwd` line has an `/etc/shadow` line and an `/etc/group` line whose gid it names. An `adduser` that ignored the lock leaves exactly the state that check names, an `x` field with no shadow line.

Manual half: root creates an account at the os-real prompt, sets its password, logs in over SSH as that account, and is refused a read of `/etc/shadow`.

### Phase 11: a real login on the console

`utils/login.c`, no setuid bit because init is root, built into `build/utils/sbin/`: prompt for a user, read the password through `pwauth_read_password`, verify, sleep and re-prompt on failure with a bounded retry count and no leaked descriptors (`MAX_FDS` is 16), then `setgroups(0, NULL)`, `setgid`, `setuid` in that order, build the environment from nothing, chdir to `pw_dir`, print `/etc/motd`, and `execve(pw_shell)` with a leading-dash argv[0]. It must not `setsid` or claim the terminal again: init's child already did, an exec by the owning session leader re-publishes the console across the destructive load, and a second claim after the identity drop would fail `-EPERM` for a non-leader.

Init stops being one program with a fallback list. `spawn_shell` (`utils/init.c:39-58`) walks `Shells[] = { "/bin/sh", "/ish" }` with the matching `-sh`/`-ish` argv[0]s (`init.c:25-26`) and execs each in turn, falling through whenever `execve` returns, whatever the errno. Putting `/bin/login` at the head of that loop drops the console to an unauthenticated root shell on any failure, and narrowing the fall-through to `errno == ENOENT` inverts the danger instead of removing it: `ENOENT` is precisely the case of an os-real image built without `/bin/login`, and that image is the one that must refuse hardest. So the fallback is not narrowed, it is compiled out. `utils/init.c` builds twice from the one source: `build/utils/sbin/init-shell`, today's behavior unchanged, and `build/utils/sbin/init-login`, built with `-DINIT_CONSOLE_LOGIN`, whose session child execs `/bin/login` with argv[0] `login` and nothing else. `Shells[]`, `Shell_Arg0[]` and the exec loop live inside `#ifndef INIT_CONSOLE_LOGIN`, so the strict artifact contains no code path and no string that names a shell. The reaper loop, the respawn backoff, and the `setsid` plus `TIOCSCTTY` dance are shared and unchanged. Neither artifact is named plain `init`: `os-simple.manifest:10` becomes `file 0755 /sbin/init build/utils/sbin/init-shell` and `os-real.manifest:31` becomes `build/utils/sbin/init-login`, so a manifest left on the old path fails to stage rather than silently getting whichever init the tree happens to build.

The mode is a compile-time split rather than a runtime one because every runtime signal is a thing an edit can drop, and the drop must not be the permissive direction. A marker file removed from a manifest, or a `rach2.login` token lost from the command line the way `rach2.rescue` can be lost, would hand the console back to an unauthenticated root shell: the same fail-open in a new place. Two artifacts carry no such state, and which init an image gets is visible in the manifest diff.

In `init-login` every `execve` failure is one case, `ENOENT` included. The child writes `init: cannot exec /bin/login: <strerror>` and, on the first failure, `init: boot rach2.rescue for the kernel debug shell`, then `_exit(127)`; the parent's existing fast-death backoff respawns it, at 5 s rather than 1 s in this build so a permanent failure states its reason on the console without scrolling it away. It retries forever and never gives up, because giving up means init exits, and an exited init is `panic_init_died` (`kernel.c:1247`): a panic refuses a shell no harder than the retry does while turning a transient failure (a full process table, a fault on the demand-paged window) into a permanent one.

This is the change that can lock everyone out, so the way back in is stated rather than assumed. `rach2.rescue` (`rach2/run.sh:81`) sets `rescue_mode` before the boot home is chosen, and the kernel then never calls `boot_init_process` at all (`kernel.c:2679-2683`): the image's init is not consulted, and the debug shell comes up with the filesystem mounted and writable, so a broken os-real is repairable in place. That is the only way back in, and it must stay so: SSH is not a second one, since dropbear is started by hand from the console session and nothing starts it at boot. The trade is deliberate and asymmetric. The failure being removed (an unauthenticated root shell on any exec failure) is reachable by whoever walks up to the serial line; the failure being accepted (a console that will not offer a prompt until the image is repaired) is reachable only by rebooting with a flag the operator controls. os-simple cannot reach either: it stages `init-shell` and is untouched by this phase.

`tools/check_setid.py` gains its fourth check, beside phase 3's manifest sweep and image inventory and phase 9's applet table, and it splits by what each half must read. The manifest half joins the sweep in `tools/check.sh`, since it reads text alone: each manifest's `/sbin/init` line must name the artifact its table entry declares, and a manifest whose entry declares no init must carry no such line. The byte-string half joins the artifact-dependent `check-setid` target beside the applet table, since it reads a built binary: `init-login` must contain neither of the byte strings `/bin/sh` and `/ish`, and `init-shell` must contain both. That positive requirement is the sentinel: an unreadable or empty scan fails rather than passes, which is how the same script already guards `applet_names[]`. The check is exact in this tree because a musl-static util that never calls `system` carries neither string (`build/utils/cat` carries neither today; only init's own table puts them in a binary).

`CONFIG_LOGIN`, `CONFIG_VLOCK`, `CONFIG_SULOGIN`, `CONFIG_GETTY`, `CONFIG_WALL` and `CONFIG_CRONTAB` go off once ours is proven, and the applet guard's forbidden list grows to `su`, `passwd`, `login`, `vlock`, `wall`, `crontab`. `wall` and `crontab` are on that list because they are `BB_SUID_REQUIRE` too (`util-linux/wall.c:16`, `miscutils/crontab.c:22`), and the generated applet table confirms both are enabled today; without them the stronger invariant ("busybox contains no applet that would want a set-id bit") would be false the day it was written. `sulogin` and `getty` are `BB_SUID_DROP` and go off for a different reason, which the Readme states: they are the console-login path ours replaces.

### Phase 12: ping, the raw-socket applets, and the freeze

One commit, not two: the staging must not exist in any tree state without the kernel fix, since staging `/bin/ping` alone hands every SSH user a whole-system freeze, and the kernel fix alone changes nothing a user can reach.

The freeze first. `icmp_ping` (`rach2/sys/network/ip/icmp.c:93`) polls `sti; hlt` at lines 123-126 from inside a syscall, and `timer_handler` skips `schedule()` while `current_proc->in_syscall` (`rach2/kernel.c:138-140`), so nothing else on the machine runs for `ICMP_PING_ATTEMPTS * ICMP_PING_WAIT` = 4 s per unanswered call; `utils/ping.c` issues `PING_COUNT` 4 of them, so `ping 10.0.2.99` freezes every process for about 16 s. Today that is confined to the single-console os-simple image; staging `/bin/ping` into a multi-user os-real would make it a denial of service any SSH user can fire.

The wait becomes a real sleep, and the timeout is carried by the wait predicate rather than by the timer alone. The slot keeps a `ping_deadline` beside its other state; each attempt sets it to `kernel_ticks + ICMP_PING_WAIT`, arms `current_proc->wakeup_tick` from that same word, and blocks in `wq_wait_event` on an ICMP wait queue that `icmp_rx` wakes after it sets `ping_replied`. The predicate is `ping_replied || (int32_t)(kernel_ticks - ping_deadline) >= 0`. Arming `wakeup_tick` alone bounds nothing, which is the trap in the obvious implementation: `proc_wake_sleepers` only clears the deadline and marks the process READY (`rach2/sys/proc/process.c:109-119`), and `wq_wait_event` then re-tests its condition and re-enqueues on any wake that is neither the satisfied condition nor a signal (`rach2/sys/proc/wait_queue.c:75-81`, `97-146`), so a predicate that reads only `ping_replied` blocks again with its timer now disarmed and never wakes again. The two halves are both load-bearing and must read the same word: the armed tick is the scheduling half, since a BLOCKED process that nothing wakes is one `schedule()` never picks, and the deadline in the predicate is the terminating half, so a timer that has fired implies a condition that is true.

A `wq_wait_event_timeout` returning `-ETIMEDOUT` would be the reusable form and is not adopted: it duplicates the interrupt-discipline argument that `wait_queue.c` proves once, for one caller, and `poll.c:152-218` already open-codes its own timed wait rather than growing that primitive. The cost of the predicate form is stated where it bites: `wq_wait_event` returning 0 does not mean the ping was answered, so `icmp_ping` decides reply against expiry by reading `ping_replied`, and the header says so. `wakeup_tick` is cleared on every exit path and between attempts, since a stale arming wakes the process early out of its next unrelated block (`nanosleep` and `poll` both read it). A signal cuts the whole call short: `wq_wait_event` returns `-EINTR`, the remaining attempts are abandoned, and the syscall returns `-EINTR`.

The debug shell keeps the spin. `netping` and `netbad` (`kernel.c:2197`, `2211`) run on `proc_table[0]` with the scheduler disabled once init has exited, so there is no process to block and nothing else to run; `icmp_ping` sleeps when `current_proc && current_proc->in_syscall` and spins with `sti; hlt` otherwise. Both paths share one deadline, one claim, and one release. The file's header block (`icmp.c:10-15`) documents the spin as the contract and is rewritten with the rest.

Then the slot itself, which the sleep makes racy. `ping_active`, `ping_replied`, `ping_seq_wait` and `ping_peer_ip` are one global in-flight request (`icmp.c:36-41`), rewritten unguarded at every attempt (`113-116`). One caller at a time was structural only because the spin could not be preempted; once the pinger sleeps, a second caller overwrites the peer and the sequence under the first, and the first then either matches a reply that is not its own or waits out a deadline for a request nobody is tracking. So the slot gets an owner: claimed under `net_lock` by a test-and-set of `ping_active`, the claiming `process_t *` recorded (NULL for the debug shell), `icmp_rx` matching a reply only against a claimed slot, and the whole slot released under `net_lock` on every exit path, reply, expiry and `-EINTR` alike. A second caller that finds the slot claimed returns `-EBUSY` and sends nothing. It does not queue behind the first: that needs a second wait queue and a fairness rule to give a shell command a wait it cannot see, and the raw-socket non-goal is the reason there is one slot at all. Nothing but `icmp_ping` claims the slot and every path out of `icmp_ping` releases it as its last act, so a killed pinger cannot strand it: the signal makes the blocked process READY, `wq_wait_event` breaks with `-EINTR`, and the release runs before the syscall returns.

`icmp_ping` also stops reporting a timeout as a bare `-1`, which musl's syscall return convention decodes as `EPERM`; it returns `-ETIMEDOUT`, so `-EBUSY` and the timeout reach userland as themselves. All three callers test only `rtt < 0` (`kernel.c` netping and netbad, `tests/pingtest.c`, `utils/ping.c`), so nothing breaks, and `utils/ping.c` starts distinguishing them: a refused claim prints `ping: another ping in flight` and is not counted as a timeout. `PING_COUNT` stays 4, so a ping at a dead address holds the slot for about 16 s and other users are refused for that long. That is the honest cost of one in-flight request, and it is written down rather than hidden.

Then the staging. `CONFIG_PING`, `CONFIG_PING6`, `CONFIG_FEATURE_FANCY_PING`, `CONFIG_TRACEROUTE`, `CONFIG_TRACEROUTE6` and `CONFIG_ARPING` go off: all of them want `SOCK_RAW` or `AF_PACKET`, `do_socket` accepts neither (`syscall.c:6510`), and busybox's ping dies with `can't create raw socket: Invalid argument`. Our `ping` (the `SC_PING` socketcall, which canonicalizes `127/8`) is staged `0755 /bin/ping` into os-real, which only reaches a bare `ping` because the applet is gone. `utils/resolv.c` reads the flat `/hosts` and `/resolv.conf` while os-real stages `/etc/hosts` and `/etc/resolv.conf`, so it learns to try the `/etc` path first and fall back to the flat root, keeping `dnstest` working against the flat test image; that is the two-location rule phase 10 already gives `adduser`'s exec of the password program. The applet guard grows the raw-socket names.

Proof: `tests/pingtest.c` grows in place, so the probe count stays at 51 and its two existing cases (three gateway replies, one clean timeout) stay as the positive controls. It is freestanding on `int 0x80`, so it reads the raw negative returns the assertions need. Nothing runs it today, so the new assertions would be gated by nothing: `pingtest` is outside `runtests.py`'s `PROBES` (its docstring lists it among the probes run by hand, since it wants the SLIRP gateway), and no make target and no script names it. So the phase adds `make ping-test`, a harness target in the shape phase 8 gives `test-noentropy`, spelled out rather than left to the shape: `--timeout 120 --ok "PINGTEST OK" "expect=Type 'help'" "send=exec /pingtest" wait=60`, and `pingtest` prints `PINGTEST OK` at the end of a clean run for that gate to match. The explicit `wait=` is the point of spelling it out. After its last step `harness.py` drains only `--grace`, three seconds, and then kills QEMU, while the existing timeout case alone costs `ICMP_PING_ATTEMPTS` times `ICMP_PING_WAIT` (four seconds) and the additions below add a four-second progress ping and a child the probe requires to live three to eight seconds. Without the wait the token arrives after QEMU is dead and the new gate fails on a correct tree. The target joins `make help` and the milestone's gate list. Four additions, in one fork round:

* Progress. The parent forks a child that pings 10.0.2.99 and then samples `gettimeofday` in a loop guarded by a `WNOHANG` wait, requiring that the samples taken while the child was still alive span at least 2 s. On the current spin the parent gets no CPU at all for the child's whole 4 s, so its live-window samples span milliseconds and the case fails; this is the assertion the whole kernel change exists for.
* Serialization. The child writes one byte to a pipe immediately before its ping; the parent reads it, sleeps 200 ms so the child is certainly inside the syscall, then issues `SC_PING` to `127.0.0.1` and requires exactly `-EBUSY`. Neither side of the race can score a false pass: if the parent claimed the slot first its loopback ping is answered and the assertion fails, and if it arrives after the claim it gets the `-EBUSY` it asserts. The earlier draft's non-pinging parent could not see this defect at all.
* The bounded timeout. The child exits 0 only when its ping returned exactly `-ETIMEDOUT` and a distinct nonzero code otherwise, so a wrong errno is not scored as a pass; the parent reaps it under a `WIFEXITED` guard and requires the child's whole lifetime to fall between 3 s and 8 s. A lost wakeup fails as a hung probe rather than as a green one, which the new target's timeout reports as a failure since the token never appears.
* The release. After the reap the parent's own `SC_PING` to `127.0.0.1` must return a non-negative round-trip time, which proves the slot was released and is also the loopback echo's only end-to-end assertion; `loopprobe` does not duplicate it, so only one probe ever touches the global slot.

The build-time guard is checked by flipping a config line once and watching the build stop. Then the capstones at the os-real prompt: `ping 127.0.0.1` and `ping localhost` reply and `command -v ping` reports `/bin/ping` (a probe that invokes an absolute path proves nothing about name resolution in ash), and over two SSH sessions one runs `ping 10.0.2.99` while the other stays responsive and its own `ping` reports `another ping in flight` rather than blocking or lying about a timeout.

### Phase 14: zero-length UDP datagrams

The receive slot uses length as occupancy (`socket.h:52`, `recv_len == 0 means empty`), so an empty datagram is built, transmitted, accepted by `udp_rx`, delivered to the right socket, and then dropped at the last step; a blocked `recvfrom` stays blocked. Split occupancy from length across the six sites in `socket.c`: alloc (75), deliver (166), the wait predicate (177), `socket_recv` (223, 234), `socket_try_recv` (253, 268), and `socket_poll` (496). The clear in `socket_recv` already lives inside the `net_lock` region that protects the read-out; it must stay there, or the RX IRQ can deliver a datagram between the copy and the clear and the clear drops it.

Proof: `loopprobe` grows three assertions: a 0-byte `sendto` to our own bound port followed by a blocking `recvfrom` returning exactly 0 with the source reading back as the canonical address and port; a following nonzero datagram intact, proving the slot was cleared; and a `MSG_DONTWAIT` `recvfrom` on the drained socket still `-EAGAIN`, which is the assertion a fix that made the slot unconditionally ready would fail while passing the first two. A hang instead of a pass is also a detection, since the runner reports a probe that never returns.

Readme: `rach2/sys/network/Readme.md` states that a datagram read may now return 0 and that this reaches `read` on a socket fd too; `socket.h`'s comment states the new rule. ### Phase 15: the bound local port, and TCP simultaneous open

`do_bind` records `sock->local_port` for a stream socket (`syscall.c:6581`, which runs for both socket types) and `tcp_connect` then discards it and allocates a fresh ephemeral (`tcp.c:682-691`), so a TCP client cannot pin its source port. `tcp_connect` settles the local port first: the bound port when `sock->local_port` is nonzero, the existing ephemeral scan when it is zero. The TCB is allocated after the port is settled rather than before it, so neither scan has to reason about the caller's own half-built block, which is what today's loop leans on (the comment at `tcp.c:677-681` argues from the fresh TCB still holding port 0). A local port already paired with this exact destination, meaning some TCB holds the same local port, remote address and remote port, is refused with `-EADDRINUSE`: `tcp_find` keys on exactly that triple, so a duplicate would deliver one connection's segments to the other. Only an identical triple is refused. A bound port shared with a listener, or with a connection to a different peer, stays legal, because `tcp_find` returns the exact match and falls back to the LISTEN TCB only when there is none. `tcp_connect` therefore returns 0, `-EADDRINUSE`, or `-ENOBUFS` for pool exhaustion instead of a bare `-1`, and `do_connect` returns that verbatim rather than collapsing every failure into `-ECONNREFUSED` (`syscall.c:6774`); the refusal userspace sees for a closed port still comes from the handshake, not from this return.

Listener exclusivity is enforced where the listener is published. `tcp_listen` allocates and publishes a `TCP_LISTEN` TCB without checking the port at all (`tcp.c:633-654`), and `bind` and `listen` are separate syscalls with arbitrary user code between them, so a check that lives only in `do_bind` is bypassed by ordering: `bind(A, P)`, `bind(B, P)`, `listen(A)`, `listen(B)` leaves two LISTEN TCBs on P, and `tcp_find` and `tcp_find_listen_sock` then disagree about which one owns the port, which is the state the refusal exists to prevent. So `tcp_listen` scans for an in-use TCB in `TCP_LISTEN` on the port inside the same `net_lock` region that publishes the new one, before allocating, and returns `-EADDRINUSE`; a full pool returns `-ENOBUFS`; a socket that never bound (`local_port == 0`) returns `-EDESTADDRREQ`, since this stack assigns no port at `listen` and a port-0 listener no segment can ever reach would otherwise be the thing that makes the next one collide. `do_listen` already returns `tcp_listen`'s value verbatim (`syscall.c:6823`), so `listen(2)` reports these instead of the `-1` userspace decodes as `EPERM`, the same defect phase 2 fixes at unlink and rename, and `tcp.h`'s two prototypes stop promising `-1`.

`do_bind`'s stream path keeps a check against the same rule, through an exported `tcp_port_listening` that wraps the same scan under `net_lock`: a program that binds a port a live listener holds learns it at `bind`, which is where httpd and dropbear report it. That check is advisory, and the invariant is `tcp_listen`'s. The scope stays `TCP_LISTEN` and not `tcp_local_port_in_use` (`tcp.c:405`), which counts every in-use TCB including accepted ESTABLISHED connections and 2 s TIME_WAIT remnants (`TCP_2MSL_TICKS` 200); with `do_setsockopt` a total no-op (`syscall.c:7031`), `SO_REUSEADDR` buys nothing, so a TCB-wide refusal would make restarting dropbear or httpd after a session fail on `bind(22)`/`bind(80)` where today it succeeds. That same comment's claim that the stack "already reuses listen ports" is corrected here, since a live listener now excludes a second one; what stays true is that a connecting, closing, or TIME_WAIT connection holds no port against anyone.

Then the RFC 793 arc the state machine is missing. Simultaneous close is implemented twice; simultaneous open is not: a bare SYN in `SYN_SENT` falls out at the first line of that case (`tcp.c:951`) and is dropped. On a SYN with no ACK, record `irs`, set `rcv_nxt` and the peer's window, rewind `snd_nxt` to `iss` before `tcp_send_flags(TCP_SYN | TCP_ACK)` emits at that sequence and re-advances it, and move to `SYN_RCVD`. The rewind is the whole of it: the first SYN left `snd_nxt` at `iss + 1`, `tcp_send_flags` emits at `snd_nxt` and takes `retx_seq` from it, and the peer's answering SYN-ACK acknowledges `iss + 1`, so a SYN-ACK sent at `iss + 1` is acknowledged by nothing, `retx_seq` names a sequence the peer will never confirm, and the connection wedges with `snd_una`, `snd_nxt` and `retx_seq` inconsistent. A SYN-ACK in `SYN_SENT` keeps today's path; a bare ACK stays dropped.

`SYN_RCVD` is now reachable two ways, and two places in `tcp_rx` must tell them apart, so the TCB records which open created it: `tcb_init` clears `passive`, `tcp_rx`'s LISTEN branch sets it on the block it allocates for an incoming SYN (`tcp.c:903-931`), and `tcp_connect` leaves it clear. It is read only in `SYN_RCVD`, where a passive block provably has no descriptor, since the socket a listener made reaches an application only through `socket_tcp_accept`, which runs on the transition to ESTABLISHED.

* Completion. The `SYN_RCVD` case hands the connection to whatever `tcp_find_listen_sock` returns for the port (`tcp.c:944-947`). It dispatches on `passive` instead: a passive block goes to the listener as now, an active one wakes the sleeping `connect` with `socket_tcp_connected`. Dispatching on whether a listener happens to hold the port would queue an active open's socket, which a descriptor already owns, onto an unrelated listener's accept queue whenever a program binds a client to a port something else listens on, which the bind rule above permits. A passive block whose listener has since closed keeps today's behavior.
* Reset. `tcp_rx`'s `TCP_RST` branch treats `TCP_SYN_RCVD` as "the connection never reached the application" and frees both the control block and the socket (`tcp.c:872-878`, `socket_unref` then `tcb_free`). That is correct only while a passive half-open is the sole way into the state. An active open in `SYN_RCVD` is owned by a live descriptor, so the same branch drops a reference the fd still holds, hands the pool slot to the next `socket_alloc` while the fd points at it, and returns without waking the sleeper: a refused simultaneous open becomes a freed socket behind an open file and a `connect` that never returns. The branch splits on `passive`: a passive block is freed exactly as now, an active one takes the same reset treatment as the connected and closing states and is freed by its own `close`. RFC 793 calls a reset in `SYN_RCVD` after a user-initiated open a refused connection, so `so_error` there is `ECONNREFUSED` rather than the `ECONNRESET` that branch's state test would otherwise give it.

Why this is not symmetry for its own sake: the ephemeral skip considers local TCB ports, not the destination port, so a dialed loopback port in the ephemeral range that nothing holds can collide with the ephemeral handed out; `tcp_find` then matches the caller's own TCB, the SYN is dropped, and the connect stalls through all seven retransmits before `-ECONNREFUSED`. Rare per attempt and unexplainable when it happens.

Proof, all of it in `loopprobe`, which already drives both protocols against the machine itself:

* Listener exclusivity in the ordering a bind-time check cannot see: two sockets bind the same unheld port and both succeed, since `bind` is not exclusive; `listen` on the first returns 0; `listen` on the second returns `-EADDRINUSE`. Then the ordering the earlier draft proved (bind, listen, second bind) still returns `-EADDRINUSE` from `bind`; `listen` on a socket that never bound returns `-EDESTADDRREQ`; and after the first listener is closed the second socket's `listen` on that port returns 0, which pins the refusal to a live listener. Immediately after `tcp_loop`'s exchange, while that connection's TIME_WAIT remnant is still in the table (2 s, and the probe is microseconds behind the close), a fresh socket binds and listens on `TCP_PORT` and must succeed: that is the assertion that fails if the refusal is ever rescoped to any in-use TCB.
* The bound source port: a client that binds P before connecting to `loopprobe`'s existing listener reports P from `getsockname`, and the accepted socket reports P from `getpeername`. A client that binds nothing still gets an ephemeral at or above 49152.
* The self-connection: bind port P in the ephemeral range, connect to `127.0.0.1:P`, assert connect returns 0 well inside the 20 s step window, that `getsockname` and `getpeername` both report the canonical address and the literal P compared against what the probe asked for, and that a byte written to the fd reads back from it. This case fails today with `-ECONNREFUSED`, promptly: `tcp_connect` discards the bound port, so the SYN reaches an unheld P and draws `tcp_send_rst_unmatched`. The 183 s stall is the rarer variant, when the allocator happens to hand out P itself.
* A two-socket case, because the self-connection is degenerate: with one socket dialing its own port, `irs == iss` and `rcv_nxt == snd_nxt`, so the `snd_nxt` rewind cannot be distinguished from getting it wrong. Two non-blocking sockets, A bound to P1 dialing P2 and B bound to P2 dialing P1, have different ISNs (`tcp_isn` mixes the port pair in order), so the rewind is load-bearing. Both connects return `-EINPROGRESS` (`do_connect` supports `OFD_NONBLOCK`), the probe polls both to completion under a bounded timeout, and each end writes a distinct byte the other reads.
* A reset arriving in `SYN_RCVD` on an active open, built out of the loopback ring's order rather than out of luck: A binds P1 and connects to P2, B binds P2 and connects to P1, and the probe closes B before the timer drains the ring. B's TCB is freed in `SYN_SENT`, so the drain pops A's SYN first, finds nothing on P2, and appends a reset behind B's SYN; pops B's SYN, which puts A in `SYN_RCVD` and appends A's SYN-ACK; then pops the reset into A. The probe requires A to report `POLLERR` within a bounded poll and `SO_ERROR` to read `ECONNREFUSED`; on the unsplit branch the socket is freed and nothing is woken, so the poll expires and the probe fails. It then closes A and sweeps for the double free: close the round's own sockets first, since `MAX_FDS` is 16 with three taken by stdio and `MAX_SOCKETS` is 16 shared with every socket the earlier cases still hold, then bind every free descriptor to a distinct port and read each back with `getsockname`. A `-ENOBUFS` from pool exhaustion is a setup failure the probe reports as one, never a pass. A pool slot handed out twice makes one descriptor report another's port, which is the only place a reference dropped at reset time becomes visible.
* The two orderings a timer tick can impose on that construction are recognized, never scored. A tick between the two connects delivers A's SYN to an unheld P2, and A is already in error before the close; a tick between B's connect and the close lets the pair reach ESTABLISHED, and no reset is ever sent. The probe polls A with a zero timeout before the close and checks for the established case after it, closes both fds, and retries the round with a fresh port pair, four times, then fails. The same retry covers the two-socket case, which loses the same race the same way. A round that took either off-path ordering is not counted as the proof.

Readme: `rach2/sys/network/Readme.md` states what makes a local port taken (a live LISTEN TCB, enforced at `listen`, checked early at `bind`, released with the listener), that a connecting or closing connection holds nothing and TIME_WAIT holds nothing either, so `SO_REUSEADDR` has nothing to reuse; the bound source port and the triple `connect` refuses; that `listen` on a socket that never bound is an error here rather than an ephemeral allocation; that simultaneous open is implemented and a connect to one's own bound port completes as a self-connection; and which kind of half-open a reset in `SYN_RCVD` frees. It keeps the loopback alias stated as a decision with what a program can and cannot observe (a peer that reads back as `10.0.2.15`, so a program cannot use the peer address to decide a connection is local). `tests/Readme.md`'s `loopprobe` entry is rewritten to name what the probe now covers.

## Verification

Every phase passes `make verify-style` and `make verify-host` and keeps `make test` green; the phases that touch the path walk, exec, or the mode bits also run the disk probes on both the ATA and AHCI paths, since the walk is on the demand-paged window path. `make test` grows from 44 probes to 51: `searchprobe`, `modeprobe`, `stickyprobe`, `musl/pwauthmusl`, `musl/passwdmusl`, `musl/addusermusl`, `musl/loginmusl`. `ownprobe`, `loopprobe`, `rmtest` and `mvtest` grow in place. `idreport` is a helper, not a probe, like `suidhelper`. `dirtyprobe` is not in the count either: it runs under `tools/crash_test.sh`'s new third phase, on the disk image where the dirty flag exists. Nor is `saltnoent`, and deliberately: it must fail where entropy is trusted, so it runs only under `make test-noentropy`. The gate carries the three targets this milestone adds, each run from a clean tree with the rest: `make test-noentropy` (phase 8, with the second invocation phase 9 adds), `make login-test` (phase 11) and `make ping-test` (phase 12).

Every new probe follows the house pattern, and its registration is five things: the source at `tests/<name>.c` or `tests/musl/<name>.c`, the name in `tests/Makefile` PROGS or the `tests/musl` sweep, the name in `tools/runtests.py` PROBES, an explicit manifest line only where a fixture needs an owner or a mode the `exec-dir` sweep cannot give, and an entry in `tests/Readme.md` with its success token, written in the same commit. A new source is also added by name to `tools/check.sh`'s `newcode_ch` and cppcheck list in the same commit, since those globs reach only `tests/host/` and `tests/*probe.c` and cannot be widened wholesale over the unformatted legacy tree.

The anti-false-pass rules, each one a mistake this tree has already made: exit non-zero on every failed check and never return 0 on a setup failure, since the exit status is all the runner reads; guard every wait with `WIFEXITED` before `WEXITSTATUS`; assert exact errnos and not signs; create and destroy your own fixtures, and snapshot and restore any shared file you must mutate, since all 51 probes share one boot in list order (the four credential-mutating probes sit at the tail, after `musl/suidmusl`, and restore `/etc/passwd`, `/etc/shadow` and `/etc/group` byte-for-byte); prove the negative case by first proving the positive one, so a denial cannot be credited to a fixture staged one bit wrong; and never read a password from `/dev/tty` in a probe, since fd 0 under the debug shell is the console and the read would hang the whole run.

The manual capstones, all recorded in the milestone record with the exact command lines beside their results, and each shown failing where the failure is the point: the console login (wrong password refused, root admitted, init respawning the prompt, a `0000` `/bin/login` not dropping to a shell, `RESCUE=1` still reaching the debug shell); `passwd` at the os-real prompt as test, followed by an SSH login with the new password and a refusal of the old; `adduser` as root, followed by an SSH login as the new account and a denied `/etc/motd`; `su` with root's unchanged password, and `su -c 'sleep 100'` suspended and resumed with `fg`; `ping 127.0.0.1` and `ping localhost` with `command -v ping` reporting `/bin/ping`, and a second shell staying responsive while a ping to a dead address runs; the SSH capstone by key and by password with root's password refused; and the power-cycle persistence run on the disk image.

Each phase ends with an independent Codex review of its diff. The chief adjudicates every finding against the code and records confirmed versus refuted; a finding counts only with a concrete failing input or trace. Four phases get a harder read than the rest, because their failure modes are silent: phase 4, where a missed conversion site quietly turns a denial into `-ENOENT` and `do_open` then creates the file, or leaves the whole mutation family unchecked while the probe goes green; phase 5, where the obvious implementation is an unprivileged clear of a persistent filesystem's crash evidence; phase 8, where a bug in `cred_rewrite` destroys authentication for the whole image and three later phases build on it; and phase 11, where the failure mode is a box nobody can log into.

## What stays deferred

* Splitting a musl extraction stamp from the musl build stamp. One stamp stays. The split's real content is removing `build_libc.sh`'s unconditional `rm -rf` and re-extract, which is also what makes a changed patch reapply to a clean tree; leave it in and ordering `krffs` against an extract stamp lets a parallel build compile `crypt_sha512.c` out of a tree being deleted. What the split buys is a bare `make krffs` that skips the libc build, and nothing else, since every image target needs libc anyway.
* A userland `reboot(2)`, and with it a clean unmount from inside the image. It would silence the dirty-flag warning on every disk boot, but it hands a syscall the power to halt the machine and to clear the crash evidence `fsck.krffs` depends on. It needs a privilege check and its own review.
* Moving `KRFFS_MODE_DIRTY` out of the mode word. A v3 on-disk change that would make every existing image read as cleanly unmounted, with coordinated edits in the kernel and two host tools. The node-identity guard makes the collision safe; this would make it unnecessary.
* `/etc/skel`. Not staged, so `adduser` creates an empty home. A convenience with no lesson in it.

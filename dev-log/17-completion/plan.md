# Milestone 17: privilege completed: accounts, the search bit, and the last mode bits

## The goal

Milestone 15 recorded a deferral list, and milestone 16 audited the work implemented for milestone 15 without reopening that list. This milestone resolves every item under "What stays deferred" in `dev-log/15-privilege/Readme.md` and the three additional items recorded at their point of use in `utils/su.c`. Each item ends either as an implementation with a meaningful proof or as a decision and its cost in the owning Readme.

Two items were already closed and are not repeated here; phase 3 identifies them. Three others complete partially implemented models and account for the size of this milestone:

* The permission check never charges search on a path's ancestors. `krffs_walk_e` (`rach2/sys/fs/krffs.c:260`) matches each component by `name` and `parent_id` and never reads `mode`, `uid`, or `gid`; the syscall layer judges the endpoint (`cred_access_node`, `syscall.c:1009`) and, for a mutation, the immediate parent's write bit (`cred_parent_writable`, `syscall.c:1028`), which itself resolves that parent through the unchecked walk at `syscall.c:1047`. Nothing anywhere asks for search on a prefix. A uid-1000 process therefore reads a 0644 file inside a 0700 root-owned directory, and creates, unlinks, renames, mkdirs and rmdirs inside a 0777 directory whose only protection is a 0700 ancestor.
* The set-id bits are granted by exec and taken away by nothing. Exactly two sites write a node's permission bits, `krffs_stamp_new_node` (`syscall.c:1187`) and `krffs_chmod_node` (`syscall.c:2696`); `krffs_chown_node` (`syscall.c:2708`) writes ids only. A 04755 file stays 04755 across any amount of writing and any chown.
* The sticky bit is stored and reported but never read. `KRFFS_MODE_STICKY` (`krffs.h:57`) occurs only in its definition. In the distributed `1777 /tmp`, any user with write permission on the directory may unlink or rename root's file or rename their own file over it. The sticky bit exists to prevent those operations.

The account workflow is also incomplete. A user can authenticate with a password but cannot change it, an administrator cannot create an account, and the console remains an unauthenticated root shell. The machine therefore authenticates network users while granting uid 0 to anyone who reaches the serial console.

## Scope and non-goals

In scope, as work:

* Search (`x`) charged on every directory the KRFFS walk enters, on the read paths and the mutation paths alike, with the resolver's error reaching the caller instead of being collapsed into `-ENOENT`, and charged by the real ids for `access(2)`.
* The set-id bits cleared on write, truncate, chown, and the `chmod` POSIX names, guarded against the root node whose dirty-mount flag shares the setuid bit position, with exec's setgid grant narrowed to a mode that has group-execute so the grant and the clear read the same bit the same way.
* The sticky bit's restricted-deletion rule at unlink, rmdir, and both ends of rename, and, as its prerequisite, `unlink` and `rename` reporting a real errno instead of KRFFS's bare `-1` (which userspace decodes as `EPERM`).
* An open descriptor on a regular file naming one file: across an `unlink`, across a `rename` onto its name, and across a write that relocates it, with the node released by the last close. Without it the write-new-then-rename idiom the whole account workflow rests on hands a concurrent reader `-EBADF`, and the reader cannot tell that from an account that does not exist.
* The POSIX kill rule completed: the target's saved uid matches, and `SIGCONT` within the session is exempt. This is a live defect: a uid-1000 ash cannot resume a job it started through `su`.
* `utils/pwauth.c`, the shared credential library: check a password against a stored hash, read one from the terminal with echo off, generate a salt from trusted entropy, and replace a credential file by write-new-then-rename. `su` is rebuilt on it.
* `utils/passwd.c`, setuid root: the second and last setuid program in the distributed image.
* `utils/adduser.c`, root-only, which never generates a hash itself but execs `passwd`.
* `utils/login.c` on the console, with `rach2.rescue` left as the only rescue path.
* Our `ping` staged into os-real, the whole-system freeze `icmp_ping` causes removed first, and every BusyBox applet that wants privilege or a raw socket compiled out rather than merely shadowed.
* The disk-backed os-real presented and bootable as the writable image, so an account change means something after a reboot.
* Zero-length UDP datagrams; a bound local port honored by `connect`, with `-EADDRINUSE` on a port used by an existing listener; TCP simultaneous open.
* The required build and test checks: a set-id scan of every manifest; removal of the privilege family from the os-simple `exec-dir` scan; a probe runner that cannot count a signal death or a forked child's status as success; and style-check inputs that include the new code.

Non-goals, each of which becomes a stated sentence in an owning Readme in this milestone rather than a line on a list:

* A root password over SSH. `-g` stays; root authenticates by key, and root's hash exists so `su` has something to verify. The doc also corrects its description of what `-g` provides.
* A loopback interface proper. `127/8` stays a canonical alias for the machine's one address, decided at the socket boundary, and `rach2/sys/network/Readme.md` says what a program can and cannot observe (a peer that reads back as `10.0.2.15`, so a program cannot use the peer address to decide a connection is local).
* `SOCK_RAW`. It needs a raw socket type, an ICMP demux to bound sockets replacing the single global in-flight ping, the IP header delivered ahead of the message, and a privilege decision; that decision kills it, since a root-only raw socket leaves the test account's `ping` broken and an unprivileged one weakens the boundary milestone 15 hardened.
* Quotas, ACLs, capabilities, and per-user resource limits. Each lies outside the model taught by this system, and its cost is stated. Resource limits are already described by `getrlimit` and `prlimit64`, which report the kernel's fixed pools, while `setrlimit` is a documented no-op; they are not deferred work.
* A directory descriptor as a capability. Rach2 stores the cwd and every dirfd as a canonical absolute string, so a relative open re-walks from the root and re-charges the whole prefix. That is stricter than POSIX and cannot escalate; the alternative threads an "authorized prefix" through eight call sites to model a right that was never checked at open time either.
* A PAM or `login.defs` policy layer. It would be a second authentication implementation in an image whose point is that there is one.

## Design decisions

* A deferral closes or becomes a decision, and a decision lives in a component Readme with its cost, not in a dev-log record. The milestone records are frozen history; the component Readmes state the current contract.
* The distributed image gains exactly one more setuid-root program, `/bin/passwd`, and no others. `adduser` and `login` start as root, from a root shell and init respectively, and refuse a non-root caller before touching a file. The build-time check lists the allowed set for each image and rejects every other set-id path.
* One implementation in the image generates password hashes under one salt policy. It uses `getrandom(2)` and fails closed instead of falling back to `GRND_INSECURE`, matching the kernel RNG policy. The refusal produces two lines: `pwauth: no trusted entropy` from the library and another from the caller, for the reason given in phase 9. BusyBox's hashing applets are compiled out because their salt uses an LCG seeded by `getpid() + monotonic_us()` (`libbb/pw_encrypt.c`), while the kernel refuses to supply untrusted randomness.
* `CONFIG_FEATURE_DEFAULT_PASSWD_ALGO="sha512"` is transitional. The symbol is `depends on PASSWD || CRYPTPW || CHPASSWD` (`loginutils/Config.in:169-173`), and `build_busybox.sh` runs `yes "" | make oldconfig`. Once all three applets are disabled, oldconfig drops the symbol and silently removes the line from `rach2.config`. Compiling out all three hashing applets provides the lasting guarantee.
* An applet that requires a set-id bit is compiled out rather than shadowed by a staged program. Standalone ash resolves an applet name before searching `PATH` (`shell/ash.c`), so a staged `/bin/passwd` cannot be invoked by name while the applet exists. Milestone 15 resolved the same conflict for `su` by disabling `CONFIG_SU`. The enabled `BB_SUID_REQUIRE` set contains five applets, not three: generated `include/applet_tables.h` lists `login`, `vlock`, `passwd`, `wall`, and `crontab`, with no `su`. All five must be disabled before stating that BusyBox contains no applet that requires a set-id bit. Disabling only `passwd`, `login`, and `vlock` would leave that claim false.
* The applet guard parses the build's own generated table, `vendor/busybox/busybox-1.36.1/include/applet_tables.h`, which defines `const char applet_names[]` as NUL-separated tokens, and matches whole tokens. A substring search over a stripped megabyte binary matches `su` inside dozens of unrelated strings. The guard asserts a positive sentinel (an applet known to be enabled, `cat`) and fails when the sentinel is absent, so an empty or unparsable scan is a build failure rather than a silent pass.
* A file the system authenticates against is replaced, never rewritten in place, and the replacement runs under a writer's lock. `krffs_write_node` can relocate a growing file and `O_TRUNC` passes through an empty state, so an in-place rewrite of `/etc/shadow` is observably broken to a concurrent reader; and a credential change is a read-modify-write, so two unserialized writers lose one of the two updates whatever the write idiom is. The idiom is `umask(077)` and restore, any leftover temp unlinked, an `O_EXCL` temp beside the target inside root-owned `/etc`, the whole text written, `fchown` then `fchmod` from the original (that order, because phase 5 makes chown clear the set-id bits, which is why `cp` and `install` chown before chmod), `fsync`, `rename`, then a second `fsync` through that same descriptor, held open across the rename because `sync(2)` discards its result and only `fsync` can report `-EIO`. Because `krffs_rename` changes only the name and the parent id, the destination inherits the source node's mode and owner: the temp's mode is the result's mode, and getting that wrong makes the file that exists to be unreadable readable.
* Write-new-then-rename is not atomic for a concurrent reader until the file system gives an open node a lifetime, so the lifetime comes first, as its own phase, and the credential library is built on a rename that is atomic in fact rather than by assertion. `krffs_rename` frees the node the destination name held (`krffs.c:1142-1147`), and the next operation through a descriptor still on that node fails `fd_node_check` and returns `-EBADF` (`syscall.c:837-855`, read at `1741-1753`). Every reader of a credential file is multi-syscall and the kernel preempts between syscalls (`timer_handler` skips `schedule()` only inside one, `kernel.c:138-140`): musl's `getspnam_r` opens `/etc/shadow` at `getspnam_r.c:99` and reads it at line 108, and dropbear reaches that call on every authentication, key or password (`common-session.c:643`, `HAVE_SHADOW_H` defined in the built `config.h`). A replacement occurring in that window makes `su`, `login` and dropbear refuse a correct password, and refuse it indistinguishably from a wrong one: musl's `fgets` loop cannot separate a read error from an absent account, so `getspnam_r` returns 0 with no entry and the caller sees a user who does not exist. The three alternatives are rejected on the record. Making the readers retry means patching musl as well as dropbear, since a dropbear-only patch cannot see the condition, and it fixes only the two programs we happen to have rather than the contract every future reader will depend on. Making the readers take the writer's lock cannot reach dropbear at all, which is the program the box exists to authenticate, and it inverts the transaction's own rule that no stale lock can keep anyone out of the box. Rebinding a stale descriptor to whatever the name now resolves to trades a loud error for a silent one, since a reader that has already consumed part of the old file would then read the rest of the new one.
* Search is charged on every component of the final absolute path, every time, including the prefix a dirfd or the cwd contributed. One rule, no new state, strictly stricter than Linux. `..` collapses lexically in `canonicalize_abs` before resolution, so a directory a path merely transits is not charged; with no symlinks and no directory hard links the lexical parent is the real parent, and the Readme says the equivalence depends on that.
* The search predicate takes the same `use_real` flag `cred_access_node` already takes. `do_access` judges its leaf by the real ids (`syscall.c:2635`) precisely because `access(2)` asks who the caller really is; charging its prefix by the effective ids would make `access()` inside `su`, `sudo`, or `passwd` report reachable a path the real user cannot reach, an internally inconsistent answer from the one call that exists to give a set-id program its invoker's view.
* Denial on the prefix beats absence of the leaf. The ten sites that collapse the resolver's error into `-ENOENT` or `-ENOTDIR` return it verbatim instead, and the mutation family is converted with them: `cred_parent_writable`'s parent lookup, `sys_creat`'s existence probe, `sys_mkdir`'s existence probe, `sys_rmdir`'s target resolve, and `execve`'s program resolve. Without those, a uid-1000 process still creates, unlinks, renames, mkdirs and rmdirs under a denied ancestor, and a probe whose denied directory is also unwritable goes passing while proving nothing.
* Three re-resolves stay on the unchecked wrapper, each for a stated reason. `fd_node_check` (`syscall.c:851`) and `copy_path_at` (`syscall.c:927`) re-validate an already-open descriptor; a checked re-validation would turn a live fd into `-EBADF` after a chmod on an ancestor. The post-create re-resolves in `do_open` (`1296`), `sys_creat` (`4409`) and `sys_mkdir` (`4522`) run after the prefix has already been charged and after the object exists; re-charging could only differ if the tree changed underneath, and a failure there would strand a created file with no descriptor.
* The set-id clear is a syscall-layer rule, not a filesystem one. `krffs_write_node` and `krffs_truncate` are also called by the kernel debug shell (`kernel.c:2165`) and by `krffs_write`, where there is no `current_proc`. The clear runs after the write, through the updated node pointer, because a relocating write copies the old mode wholesale.
* The clear never touches the root node. `KRFFS_MODE_DIRTY` and `KRFFS_MODE_SUID` are the same bit, `0004000`, and `chown("/", 0, 0)` reaches `krffs_chown_node` from any uid today: `do_chown` resolves the empty name to `krffs_fs->node` (`syscall.c:2841`) and the function demands privilege only when a value actually differs. An unguarded clear appended there is an unprivileged clear of the crash evidence `fsck.krffs` reads. The node-identity guard protects the root. The requirement that a field actually change is redundant for the root but necessary everywhere else, since `chown(path, -1, -1)` succeeds for any caller and would otherwise disarm `/bin/su` from uid 1000.
* The dirty flag stays in the mode word. Moving it is a v3 on-disk change that would make every existing image read as cleanly unmounted, and it needs coordinated edits in the kernel and two host tools. Considered and rejected here.
* The console login fails safe by refusing, never by admitting. `spawn_shell` (`utils/init.c:50-56`) loops over `Shells[]` and falls through whenever `execve` returns, whatever the errno; putting `/bin/login` first under that loop would drop the console to an unauthenticated root `/bin/sh` on any exec failure, not only on a missing binary. Narrowing the fall-through to `errno == ENOENT` inverts the danger rather than removing it, since an os-real image built without `/bin/login` is exactly the `ENOENT` case and exactly the image that must refuse hardest. The fallback is compiled out. Narrowing it would still fail open: `utils/init.c` builds twice, `init-shell` with today's list unchanged and `init-login` with `-DINIT_CONSOLE_LOGIN`, whose session child execs `/bin/login` and nothing else and whose binary contains no string naming a shell. `rach2.rescue` reaches a kernel debug shell, not the image, and is the only way back in, so this is the change that can lock everyone out of the box.
* One musl stamp. See "What stays deferred".

## The phases, and why they are ordered this way

Checks precede kernel mechanisms, which precede userland; network work comes last. Phases 1 through 3 are prerequisites for later evidence. An assertion of `-EPERM` is ambiguous while a missing path also reports `EPERM`; a probe killed by a signal is scored from its child's status; and the set-id scan covers only two of six manifests. The kernel permission rules follow, ordered by scope and difficulty, so every later end-to-end test also exercises them. Descriptor lifetime is the final kernel phase because it implements the file-system contract required by write-new-then-rename and the credential library. The userland programs then use those rules. The two network phases follow the account work because the accounts do not depend on them. Placing a TCP state-machine change earlier would make an SSH failure ambiguous across six changing phases. At the end, the SSH end-to-end test remains a fixed reference for the entire userland sequence. Every step must leave the suite passing.

### Phase 1: harness scoring and style-check coverage

One commit fixes three tooling defects and changes no kernel behavior beyond one diagnostic line.

`tools/runtests.py` anchors each probe on `returning to kernel shell`, which two kernel paths print: `sys_exit` (`syscall.c:412`) and the signal death in `terminate_current_process` (`kernel.c:239`). Only the first is followed by a status the runner can read, and the runner takes the last `Process exited with status N` in the window (`runtests.py:141`), so a probe that forks a child which exits 0 and then dies on `SIGSEGV` is recorded PASS. The last status in the window is not reliably the probe's own even without a signal: `sys_exit` prints the status at `syscall.c:342` and only then calls `schedule()`, so a child that outlives its parent prints its own status after the parent's and before the marker.

Fix the scoring at the source. `sys_exit` prints `sys_exit: init process %d exited with status %d, returning to kernel shell` (lowercased to match the diagnostics rule, marker text unchanged), and the runner scores that line alone, ignoring every other status in the window. A window ending in `killed by signal` fails regardless of what it contains. `runtests.py` also fails, naming the probes it never ran, when `len(results) != len(PROBES)`, since today it `break`s on the first hang and prints a smaller count as if that were the suite; and the `test` target passes an explicit `--timeout` sized for the grown suite, because the 180 s default is one global deadline shared by every probe.

`tools/harness.py:157` reads `if expect(...) is None:` while `expect` returns `True` or `False` (line 141). It therefore never increments `step_failures` for an `expect=` step, and the comment on line 149 describes an inactive guard. The condition becomes `if not expect(...)`. The `--ok` check is otherwise correct because line 204 requires `step_failures == 0`, and `exec=` steps already count failures. The two `stress-test` targets expose the defect. This commit fixes it with the other scorer.

`tools/check.sh` defines `newcode_ch` as `tests/host/*.c tests/host/*.h tests/*probe.c` plus the musl port, while its cppcheck list contains the kernel and `tests/*probe.c`. Neither list includes `tests/musl/` or `utils/`, so the registration rule cannot claim coverage for a musl probe or `utils/pwauth.c`. Extending the globs to both directories would fail on the legacy tree: `clang-format --dry-run -Werror` rejects seven files under `utils/` and nine under `tests/musl/`, which the check deliberately does not reformat. Each phase therefore adds each new source to `newcode_ch` and the cppcheck list by name. `tests/Readme.md` records this rule. This commit also adds the `sudoprobe` entry omitted from `tests/Readme.md` since milestone 15.

Proof: `runtests.py --selftest`, invoked by `tools/check.sh`, scores embedded serial fragments for a clean run, a forked child exiting 0 before a signal death, an orphan exiting after its parent, and a run without a status. This regression test requires no boot. A separate recorded mutation uses a probe that forks, reaps a successful child, and dereferences NULL; the runner reports PASS before the change and FAIL afterward. `make test` continues to pass 44 probes.

Readme: `tests/Readme.md` (a signal-killed probe fails, the registration rule, the `sudoprobe` entry), `tools/Readme.md` (the two runners' scoring contracts).

### Phase 2: unlink and rename errnos

`sys_unlink` (`syscall.c:4481`) and `sys_rename` (`syscall.c:4631`) return `krffs_unlink`/`krffs_rename`'s bare `-1`, which userspace decodes as `EPERM`. Translate at the syscall boundary the way `sys_mkdir` and `sys_rmdir` already do, leaving `krffs.c`'s `-1` convention alone for the debug shell and the boot self-test. Unlink must resolve its target to do this, which it does not today; that resolve is what phase 4 then routes through the checked resolver.

The mapping distinguishes each file-system refusal. `krffs_unlink` (`krffs.c:1089`) refuses a missing path with `-ENOENT` and refuses the root with `-EISDIR` and another directory with `-EISDIR`. `krffs_rename` refuses a missing source with `-ENOENT`. A root source never reaches it because `copy_path_cwd` canonicalizes `/` to a path without a component, and the empty-name check returns `-EINVAL`. POSIX assigns that errno to a root pathname; `-ENOENT` would incorrectly say that the existing root is absent. A directory source returns `-EPERM` at `krffs.c:1127` because moving it would orphan children that reference its id; POSIX reserves this errno for a rename the file system cannot perform rather than `EISDIR`. A missing destination parent returns `-ENOENT`. A directory destination under a non-directory source returns `-EISDIR` at `krffs.c:1144`, as POSIX requires for that case.

Proof: `tests/rmtest.c` and `tests/mvtest.c` replace sign-only checks with exact-errno assertions. Each case creates and removes its own fixture, including the directory-source and directory-destination cases that distinguish `-EPERM` from `-EISDIR`. `make test` continues to pass 44 probes.

Readme: `rach2/sys/fs/Readme.md`, whose path-resolution paragraph says today that the syscall layer returns the walk's error verbatim, which unlink and rename did not do; it now states what each returns and why a directory source is `EPERM`.

### Phase 3: the build guards and the staging rule

`tools/check_busybox_suid.py` checks only two hardcoded paths, and the Makefile runs it only for `os-real` (`Makefile:323`), so other set-id lines are unchecked. It also omits part of the manifest grammar. `apply_line` (`krffs/stageimage.krffs.c:677`) supports five mode-bearing verbs rather than two: `dir` (703), `text` (706), `file` and `optional-file` (723), and `exec-dir` (761). `exec-dir` applies one mode to every staged executable. Changing `os-simple.manifest` from `exec-dir 0755 / build/utils` to `04755` would therefore make every in-house utility setuid root without producing a `file` or `text` line for the current scan. The repository contains six manifests, and phase 5 stages a probe in a seventh consumer of `disk-test.manifest`.

The replacement, `tools/check_setid.py`, parses manifests instead of searching their text. Its tokenization must match `apply_line`: fields split on spaces and tabs; a comment is a line whose first token begins with `#`; trailing comments do not exist, so `file 0755 /x build/x # note` is a directive with an ignored tail; the second token is the mode for all five verbs; and an omitted owner defaults to `0:0` as in `parse_mode`. The rules for each verb are:

* `file`, `optional-file` and `text`: a mode with `04000` or `02000` must appear in that manifest's allowlist at the same path with the same mode and the same owner. `optional-file` is half of the pair the old `parts[0] in ("file", "text")` test missed outright.
* `exec-dir`: a set-id mode is refused, with no allowlist escape. The set of paths it privileges is a property of what happened to be built into the host directory, not of the manifest, so there is nothing stable to declare; a binary that must be privileged is named with `file`.
* `dir`: a set-id mode is refused as well, deliberately and with the reason stated. KRFFS implements no setgid-directory inheritance: `krffs_stamp_new_node` takes the creator's ids and nothing anywhere reads a parent's setgid bit, so a setgid directory would be a stored bit no reader consults, which is the exact defect phase 6 closes for sticky. Sticky is not a set-id bit and stays legal; `dir 1777 /tmp` is the only one in the tree and phase 6 gives it meaning. When a later milestone implements group inheritance, the allowlist is where a setgid directory becomes declarable.
* An unknown verb is an error. A new staging directive must therefore be added to the checker with the manifest grammar.

It fails on an undeclared set-id entry, on a declared entry no manifest stages, on a mode or owner mismatch, on a malformed mode field (`0999` and `08`, which `check_busybox_suid.py`'s `staged()` reported as "not staged", and `04755:0`, which it misreads instead: `partition(":")` hands it the bits `04755` and the owner `0`, so the entry is reported as owned by the wrong owner), and on a manifest the table does not name. The per-entry owner is required rather than a global root-ownership assertion: the test image deliberately stages `file 04755:5:0 /suidhelper.u5` and `file 02755:0:5 /suidhelper.sgid` to prove the bit grants the file owner's identity whoever that is. The busybox-unprivileged assertion is kept. As of this phase the allowlists are: os-real, one entry, `/bin/su` (04755:0:0); the test image, six, `/suidhelper.suid` (04755:0:0), `/suidhelper.u5` (04755:5:0), `/suidhelper.sgid` (02755:0:5), `/suidhelper.nox` (04644:0:0, setuid without execute, still a set-id line), `/sudo` (04755:0:0) and `/musl/suidmusl.suid` (04755:0:0); os-simple, `disk-test`, `persist-test` and `stress-test`, none. Phase 12 commits two more manifests, `login-test-strict` and `login-test-shell`, and each takes its own entry in this table then, with no set-id entry and a sentinel node of its own, since a manifest the table does not name is a hard error and both are staged through `mkimage.sh` like any other.

The sweep still trusts one thing it cannot check: that this parser agrees with `apply_line`. A divergence in tokenizing or in the octal parse is invisible to it, and `exec-dir` expands to a set the text does not name at all. So the guard has a second half that reads the artifact. `check_setid.py --image <file> --manifest <path> [--offset BYTES] [--size BYTES]` walks the staged image's node chain the way `fsck.krffs` does (each node advances by its own `size`, wrapping at the region end, with the iteration bounded by the region divided by the node size), reconstructs every reserved node's path from `parent_id` (0 is the root, and `krffs_mix_id` never returns 0, so the chain terminates only at the root), and compares the nodes with `04000` or `02000` against the allowlist that manifest owns. The manifest is an argument and not an inference: the allowlist is per manifest and an image has no record of which one staged it. `struct krffs_node` (`krffs/krffs_node.h`) is `#pragma pack(1)` and is the v2 on-disk ABI, so this is one `struct` format string, not a port of the file system. An unresolvable or cyclic `parent_id` is an error, never a skipped node.

It is not `fsck.krffs`. That tool prints a reserved node's owner but never its mode, and prints the bare `name` rather than a path, since it never reads `parent_id`, so it cannot answer the question being asked; and it opens the image `O_RDWR` and clears the dirty flag whenever it finds one, so teaching it the missing fields would leave the build writing to the artifact it inspects, which is the artifact phase 5's disk end-to-end test reads back. The layout duplication gets the positive-sentinel treatment the applet-table guard gets in phase 10: the inventory must find every declared entry, which is itself the control wherever the declared set is nonempty, and the four allowlists that declare no set-id entry each name one ordinary node the inventory must report exactly (`/hello.txt` 0644:0:0 in os-simple, the staged probe in the three disk manifests), so a wrong offset or a walk that finds nothing fails the build rather than reading as a clean image.

The two halves run at the two places they belong. The sweep runs over every manifest from `tools/check.sh` as one more numbered step, which means renumbering both hardcoded places, the `hr "N/M"` labels and the header comment's list; the check has nine steps today, numbered 0 through 8, and phase 1 has already added one, so this phase asserts no total and just counts what is there. `check-busybox-suid` becomes `check-setid`, still a prerequisite of `os-real-image`, `os-real-disk` and `os-real-grub-disk`. The inventory runs from `krffs/mkimage.sh` and `krffs/mkdisk.sh`, the two scripts every image passes through, so an image built by a script rather than by a make target is checked too; each passes through the manifest it already receives in `$1` (`MANIFEST`), `mkdisk.sh` passes both the partition offset and the partition size it already computes and already hands to `mkfs.krffs` and `stageimage.krffs`, and `mkimage.sh` passes neither, since there the region is the whole file. ### Phase 4: search on every path component

This phase affects every path syscall, the widest scope in the milestone.

`krffs_walk_e` takes a `may_search` predicate and reports its negative return through `*err`, covering the `.` and `..` arms too. `krffs_resolve_x` is the new entry point; `krffs_resolve` and `krffs_resolve_e` become NULL-predicate wrappers and stay bit-identical, as the three re-resolves named in the decisions require. In `syscall.c`, `cred_may_search` wraps `cred_access_node(dir, CRED_X, 0)` and `cred_may_search_real` wraps `cred_access_node(dir, CRED_X, 1)`; `do_access` installs the second, everything else the first. The predicate dereferences `current_proc`, so `krffs_resolve_x`'s header states that it may only be installed from syscall context.

The conversion sites are enumerated, not counted:

* The ten that collapse the walk's error: `syscall.c` 1285 (`do_open`), 1936, 2371, 2578, 2630 (`do_access`), 2749 (`path_exists`), 2794 (`do_chmod`), 2843 (`do_chown`), 3411, 4725. Each returns the walk's error instead.

### Phase 5: the set-id bits cleared on write, truncate, and chown

The clear rule cannot be written without the grant rule it assumes, and in this tree the two disagree. `cred_access_node` (`syscall.c:1009`) demands an execute bit somewhere in `0111` and then judges one identity class alone, the owner's first (`cred_access_bits`, `syscall.c:992`), while `execve` applies setgid because `KRFFS_MODE_SGID` is set and for no other reason (`syscall.c:3831`, `3869-3871`). A 02700 file owned `1000:0` therefore passes the execute check on its owner bits and hands its executor `egid` 0. So the reading that setgid without group-execute is an inert mandatory-locking mark, which is the only thing that would let a clear rule spare that mode, is false here twice over: nothing in this kernel implements mandatory locking (`F_SETLK` and its family are advisory and always granted, `syscall.c:3309-3316`), and exec grants on the mode anyway.

The fix narrows the grant rather than widening the clear. `execve` applies `KRFFS_MODE_SGID` only when the group-execute bit is set as well, which is Linux's rule (`bprm_fill_uid` in `fs/exec.c`) and the one the inert-mark reading has always assumed. Widening the clear instead would leave the hole open, because that mode needs no write to appear: `krffs_chmod_node` (`syscall.c:2690`) lets an owner store any `07777` on their own file, so uid 1000 generates 02710 on a `gid`-0 file it owns by `chmod` alone and execs it for `egid` 0 without the write path ever running. `chmod` is the third place POSIX specifies a set-id clear, after write and chown, and it is implemented here with them: on a `chmod` by an unprivileged caller whose groups do not include the file's group, setgid drops, which is `chmod(2)`'s own language and what Linux does in `setattr_prepare`. Setuid needs no such rule there, since only the owner may `chmod` and the setuid grant is the owner's own identity. Every set-id file the tree stages has group-execute (`/bin/su` 04755, `/suidhelper.sgid` 02755), so the narrowed grant moves no existing case.

One helper, `cred_kill_setid`, beside `cred_privileged`: return early for the root node and for a directory, always drop `SUID`, drop `SGID` only when the group-execute bit is set. The root test is by node identity and the directory test does not stand in for it: `mkfs` stamps the root's mode a bare `0755` with no type bits (`krffs_file_system.h:20`), so `KRFFS_IS_DIR` reads false on the root and only the identity test keeps the dirty flag out of the clear. Four call sites, with the two different privilege rules POSIX gives them:

* After a successful `krffs_write_node` (`syscall.c:589`), through the updated node pointer, only when the write moved bytes, and checked on `!cred_privileged()`. `writev` shares that body, so one site covers both calls.
* `do_open`'s `O_TRUNC` branch (`syscall.c:1340`), checked the same way, applied through the node `do_open` already holds: a shrink returns the same node and only a grow relocates (`krffs_resize_reserved_node`, `krffs.c:848-853`). The branch is already past the `-EISDIR` for a directory or the root, so nothing but a regular file reaches it.
* `sys_creat`'s existing-file branch, checked the same way, on the truncate it gains below.
* `krffs_chown_node` (`syscall.c:2708`) on every chown of a non-directory that actually changed a field, not checked on privilege, since Linux kills the bits whoever asks and that is why `cp` and `install` chown before chmod.

The `chmod` drop is not one of them. It is its own two lines inside `krffs_chmod_node`, clearing `SGID` from the mode being stored on a non-directory when the caller is unprivileged and `cred_in_group(node->gid)` is false, and it is not conditioned on group-execute the way `cred_kill_setid` is: the caller is choosing that bit in the same call, so reading it back as a reason to spare the mode would defeat the rule. The existing `node != krffs_fs->node` guard there already keeps the dirty flag out of it. `fchmod` and `fchown` reach these same two helpers (`syscall.c:2914`, `3001`), so they are covered by construction rather than by two more sites.

The euid-0 write exemption is the `CAP_FSETID` analogue and matches V7; without it any root process silently disarms `/bin/su` by rewriting it. The chown site's no-change check is redundant only on the root node, which the identity test already covers, and necessary on every other node. `chown(path, -1, -1)` succeeds for any caller by design because a value that changes nothing requires no right under `krffs_chown_node`'s stated contract. A clear that ran after a no-change chown would let any uid disarm `/bin/su` with one call. Linux avoids that because the implied mode change goes through `inode_owner_or_capable`; here the existing `uid_changes || gid_changes` condition provides the check.

`creat(2)` on an existing file is fixed, not documented. `sys_creat` (`syscall.c:4395-4400`) checks `CRED_W` and hands back a write-only descriptor at offset 0 with no `krffs_truncate`, so `creat` over a longer file leaves the old tail behind, which is not the `O_WRONLY|O_CREAT|O_TRUNC` contract. It truncates, and the clear rides that branch. No userland notices the change: musl's `creat` is `open(path, O_CREAT|O_WRONLY|O_TRUNC, mode)`, so syscall 8 is reached only by the freestanding probes that issue it directly.

Proof: `tests/modeprobe.c` (46), which builds its own fixtures and removes them, because the probes share one boot and a probe that disarmed `suidprobe`'s staged fixtures would produce a passing run by breaking a later probe's premise. As root: the 04755 baseline, the privileged write exemption, chown to 1000:1000 dropping the bit (no privilege exemption, the assertion that separates the two rules), and a chowned 04755 directory keeping it. From a uid-1000 child, `chown(path, -1, -1)` on the root-owned 04755 file returns 0 and leaves the mode alone, which is the no-change check. As uid 1000 on its own files: a small in-place write clears; a write that grows the file past `node->size - sizeof(krffs_node_t)` and forces `krffs_resize_reserved_node` to relocate it also clears, asserted against the relocated node by stat after the append, which is the one case a clear applied through the stale pointer would fail; `O_TRUNC` clears; `creat` on an existing set-id file clears and leaves it empty; 02755 clears; 02644 survives; a plain 0755 file reads back 0755 as the control. Every operation's return value is checked before its mode assertion, and every wait guards on `WIFEXITED`.

The escalation needs a program and not just a mode, so the probe makes one. The root parent copies the staged `/suidhelper` byte for byte to `/mp_sgid0` (a few kilobytes through one `read`/`write` loop, so no manifest entry and no new allowlist line in phase 3's table), chmods it 02700 and chowns it `1000:0`. A uid-1000 child rewrites a byte of it and stats it back at 02700, the survival this phase's clear rule deliberately allows; then a grandchild execs it with `suidhelper`'s existing `plain` scenario, which exits 0 only if all three uids and all three gids read 1000 and `AT_SECURE` is 0. Today that grandchild runs with `egid` 0 and fails. The same child then chmods the copy 02710, stats it back at 0710, and execs it again for the same verdict, which is the half no write-clear can reach. `/suidhelper.sgid` (02755:0:5) is the paired positive: `suidprobe` runs in the same image and still requires that exec to move the effective gid to 5, so the narrowed grant is pinned in both directions. Recorded rather than committed, each shown failing first: the 02700 case with the group-execute condition removed from `execve`, the 02710 case with the chmod drop removed, and the `chown(-1, -1)` case with the no-change check removed.

The root-node guard cannot be proved from the RAM image, where the flag is never set and stat reports the root with a fixed mode. So `tests/dirtyprobe.c` is staged into `krffs/manifests/disk-test.manifest` and `tools/crash_test.sh` gains a third phase: boot the disk image with `rach2.fsdisk rach2.rescue`, `exec /dirtyprobe`, wait for `DIRTYPROBE OK` (a token, not a sleep, as the two existing phases already do), kill QEMU, and require offline `fsck.krffs` still to report "not cleanly unmounted". The probe hammers every path that reaches the root node with a mode-adjacent operation (`chown("/", -1, -1)` and `chown("/", 0, 0)`, the two the unguarded clear would reach; `chmod("/", 0755)`; `open("/", O_WRONLY|O_TRUNC)`; `creat("/")`; a write through a descriptor on `/`), asserts each returns exactly what it returns today, and calls `sync(2)` after each attempt before printing its token. The `sync` is the whole proof: the page cache is write-back, so a spurious clear would sit in a dirty frame and never reach the platter before QEMU is killed, and the phase would go passing on a broken kernel. ### Phase 6: the sticky bit enforced, and the permission model's verdicts

Split `cred_parent_writable` into a `cred_parent_dir` that returns the parent node and keep the old function as its thin caller, so the create paths are untouched. Add `cred_sticky_ok(dir, victim)`: with the directory's sticky bit set, the entry may be removed or renamed only by the entry's owner, the directory's owner, or a privileged caller; otherwise `-EPERM`, which is POSIX's errno and not `EACCES`. The SVR4 relaxation that also permits it when the caller can write the file is not in POSIX and is not adopted. Four call sites: unlink (whose target resolve phase 2 already added), rmdir, and both ends of rename. The destination side is the one whose omission leaves the attack fully open while an unlink-side probe goes passing. Order: the directory write check first, so a caller with no write permission still sees `-EACCES`. The root is non-sticky by identity, the same fixed-mode rule `cred_access_node` uses, so the dirty flag never enters a permission answer. The debug shell's direct `krffs_unlink` and `krffs_rename` calls stay exempt: it is the rescue root and has no credentials.

Proof: `tests/stickyprobe.c` (47), with a paired non-sticky control directory beside the sticky one, which is what makes the denials mean anything. ### Phase 7: the kill rule completed

`cred_may_signal` takes the signal it is judging: euid 0 passes; `SIGCONT` within the same session passes; otherwise either of the sender's real or effective uids must match either of the target's real or saved uids. Both call sites (`syscall.c:5519`, `5559`) pass `signo`. The signo-0 existence probe keeps the strict rule, which is the correct POSIX outcome, since the exception is for `SIGCONT` and not for probing.

This closes a live defect in the distributed image. `/bin/su` is 04755 and calls `setuid(pw->pw_uid)`, so the exec'd shell runs with ruid 0; ash implements `fg` as `killpg(pgid, SIGCONT)` and ignores the return (`shell/ash.c:4230`); so today a uid-1000 shell cannot resume a job it started through `su`: the `killpg` returns `-EPERM` silently and `restartjob` waits on a job that will never run. The Doxygen block states the rule as distributed, says why the session exception cannot extend a sender's reach (`setsid` only ever creates a session, never joins one), names the exposure it does create (an unprivileged session member can make a root process's `SIGCONT` handler run at a time of its choosing), and records that `tty_signal_group` stays unchecked because the terminal generates those signals, not a process.

### Phase 8: an open descriptor names one file

Three later phases require this file-system fix instead of a workaround in each reader. A descriptor open on a regular file names that file from open to close: across an `unlink`, across a `rename` onto its name, and across a write that relocates it. This is the refinement `rach2/sys/fs/Readme.md` already names and defers, in its own words, that "pinning the inode in the description, so the fd follows the file the Unix way instead of failing, is a later refinement".

It comes before the credential library because the library's whole idiom rests on it. `krffs_rename` walks the destination and calls `krffs_remove_reserved_node` on it (`krffs.c:1142-1147`), which stamps `KRFFS_FREE_NODE` and coalesces the extent with its free neighbors (`884-924`); `fd_node_check` then rejects a node whose type is not `KRFFS_RESERVED_NODE` (`syscall.c:837-855`), so the next read through a descriptor still on that node returns `-EBADF` (`sys_read`'s file arm, `1751`), and so do write, lseek, fstat and fchmod. Every reader of a credential file is multi-syscall, and the kernel preempts freely between two syscalls, since `timer_handler` skips `schedule()` only while `current_proc->in_syscall` (`kernel.c:138-140`): musl's `getspnam_r` opens `/etc/shadow` at `getspnam_r.c:99` and does its first `read` inside `fgets` at line 108, and a file needing more than one 1024-byte buffer keeps the descriptor live through several more. Dropbear reaches that call on every authentication, key or password (`common-session.c:643`; the built `config.h` defines `HAVE_SHADOW_H` at line 233). A replacement occurring in that window makes `su`, `login` and dropbear refuse a correct password, and refuse it indistinguishably from a wrong one: `getspnam_r`'s loop ends when `fgets` returns NULL and leaves `rv` at 0 with `*res` NULL, so a read error reads back as an absent account, dropbear falls back to `pw->pw_passwd`, which is `x`, and denies. `getpwnam` has the identical open-then-read shape, so phase 11's `/etc/passwd` replacement breaks a concurrent reader the same way.

The three alternatives are rejected on the record. Making the readers retry means patching musl as well as dropbear, since a dropbear-only patch cannot see the condition, and it fixes only the two programs we happen to have rather than the contract every later reader will depend on. Making the readers take the writer's lock cannot reach dropbear at all, which is the program the box exists to authenticate, and it inverts the transaction's own rule that no lock can keep anyone out of the box. Rebinding a stale descriptor to whatever the name now resolves to trades a loud error for a silent one, since a reader that has already consumed part of the old file would then read the rest of the new one.

`fd_node_holders(node, except)` in `syscall.c` implements the complete reference count: it scans every slot of `proc_table` and every descriptor of each table for an `FD_TYPE_FILE` entry whose `node` matches, skipping one entry the caller names. `MAX_PROCS` is 16 (`proc/process.h:11`) and `MAX_FDS` is 16 (`fs/fd.h:20`), so it is at most 256 pointer compares of kernel RAM and it touches the page-cache window not at all. A scan and not a counter, deliberately: a counter has to be incremented in `fork`'s table copy (`syscall.c:4112`), in `dup`, in `dup2`, and in every future path that copies an `fd_entry_t`, and one missed increment is a use-after-free that no test would show. The descriptor tables are the count, so there is nothing to keep in step.

A node no path can reach is a reserved node whose `name` is empty. `krffs_find_child` (`krffs.c:237-249`) matches a component through `krffs_name_eq` (`200`), and `krffs_walk_e` (`260`) never hands it a component shorter than one character: the entry point strips leading slashes and returns the root for an empty remainder, and each iteration strips the separators before testing for the last component. So an empty name is unmatchable by construction, which is a property of the parser rather than of a hash. A sentinel `parent_id` was the other candidate and is not used, because `krffs_mix_id` (`188`) can in principle return any nonzero value and the argument would then rest on a collision that cannot be ruled out. This is a state a v2 image already holds, not a v3 format change; the node header is full (`krffs/krffs_node.h`) and adding a field is the same change this milestone refuses for the dirty flag.

Unmatchable by construction covers the resolver and nothing else, so the same rule is written into the three scans that enumerate by `parent_id`: an orphan keeps the parent id it had, and each of them skips a reserved node whose `name` is empty. They are `sys_getdents64`'s child loop (`syscall.c:5050`), the debug shell's child lister (`krffs.c:1267`), and `krffs_rmdir`'s emptiness test (`krffs.c:1228`). Without the skips the orphan is hidden from lookup and visible to everything else: `mkdir /d`, open `/d/f`, unlink it under the descriptor, then `rmdir /d` answers `-ENOTEMPTY` where POSIX succeeds, and `ls /etc` shows a nameless entry for as long as dropbear holds `/etc/shadow` across a `passwd`.

The decision is made above the file system, so `krffs.c` gains one exported function, `krffs_orphan_node`, and loses none. `sys_unlink` (`syscall.c:4435`) resolves its target, which phase 2 already added for the errno, and orphans it instead of calling `krffs_unlink` when a holder exists; `sys_rename` (`4574`) resolves the destination and orphans it on the same condition, when a holder exists, after which `krffs_rename`'s own walk at `1142` finds nothing to free and the call does nothing but rename; with no holder it leaves the destination alone and `krffs_rename` frees it exactly as it does today. The condition is not a refinement: the release lives at the last close, so a node orphaned with nobody to close it is never released, and an unconditional orphan would leak an extent on every credential replacement made while nothing happened to be reading, which is almost all of them. Both run inside one syscall, so no reader can observe the interval between the orphan and the rename.

The orphan is the last decision and never the first, because orphaning bypasses the refusals the file system call would have made. `sys_unlink` decides the root and the directory cases itself, which `krffs_unlink` decided for it before (`krffs.c:1089-1092`). `sys_rename` decides all of them before it touches the destination: the source resolves, is not the root and is not a directory; the destination's base name is not empty and its parent resolves; the destination is not a directory. Otherwise `rename("/somedir", "/etc/shadow")` returns `-EPERM` by phase 2's mapping with `/etc/shadow` already orphaned and its name gone, which is a refusal that destroyed the file it refused to touch. Phase 2's errno mapping is unchanged by the move; `-EISDIR` for a directory destination now comes from the pre-orphan check rather than from `krffs_rename`'s own walk, and says the same thing.

The release is implemented in `fd_release_backing` (`syscall.c:108`) and not in `fd_free`. Its contract already is this one ("release every backing reference a descriptor holds before its slot is freed"), every teardown site routes through it (`sys_close` at `1460`, the `dup2` replacement of an open target at `1845`, the `execve` CLOEXEC sweep at `3540`, `release_fd_table` at `314`, and the socket path at `6884`), and its block comment already argues why none can forget a backing kind as new ones are added. A KRFFS node is now such a kind. It runs while the slot is still populated, which is exactly what the scan's `except` parameter is for: the closing descriptor is skipped rather than cleared first, so "the last holder" needs no ordering rule between two functions. `fd.c` stays generic and learns nothing about KRFFS, and `fd_free` keeps doing what it does, which is clear a slot.

Relocation is the other half of the same contract and is implemented in the same commit. `krffs_write_node` updates the writing descriptor's `entry->node` when a grow moves the file (`syscall.c:589`) and leaves every other descriptor pointing at the node it just freed; `krffs_truncate` moves it through `krffs_resize_reserved_node` on a grow (`krffs.c:1059`) and updates nobody. Both now repoint every holder through the same scan. Without it the contract would read "a descriptor names one file, unless another descriptor grows it", the same defect in a second place, and also exercised by phase 5's `modeprobe`, which forces a relocating write.

`fd_node_check` is rewritten around the new invariant. A held node is never freed, so the path round-trip stops being the identity test and becomes what it always was in fact, a resolution: an orphan is live, and a named node must still resolve back to itself. That closes, for every regular-file descriptor, the hole the Readme states today, that the round-trip "cannot tell a freed node from a different file that the allocator later places at the same address". No address a descriptor holds is handed out while it holds it.

Directories remain outside scope. `sys_rmdir` still frees the node under an open directory descriptor and `copy_path_at` still answers `-EBADF` (`syscall.c:912-929`). A directory descriptor in Rach2 is a name, which is the decision phase 4 rests on, and an orphan directory has no name for a relative path to join; giving one a lifetime is the authorized-prefix model the milestone already refused.

The debug shell needs no exemption, and that is the check on the layering. `kernel.c` calls `krffs_unlink` and `krffs_rename` directly and they free as they always did, because no process holds a descriptor when they run: the rescue shell comes up without consulting the image's init (`kernel.c:2679-2683`), and the post-init shell runs after every table has been released.

The page cache requires one durability rule. The scan reads kernel RAM only, so it costs no window fault, and the orphan stamp is one field written through the same window `krffs_unlink`'s free stamp goes through today. But the window is write-back, so an orphan can reach the platter: a crash while a descriptor is open leaves a reserved node that no path references. That costs space and never a wrong answer, since nothing can resolve to it. `fsck.krffs` reaps them in the pass that already opens the image `O_RDWR` to clear the dirty flag (`fsck.krffs.c:87`, `214-216`), reporting each one; it is the only host tool that must learn the state, since `defrag`, `edfs`, `fsviz` and the FUSE driver find files by name and an orphan has none, so they treat it as occupied space and never resolve to it. That leak, repaired offline, is the cost of not having a v3 field to write "open" into.

Proof: `tests/fdstale.c`, rewritten in place, keeping its name, its `FDSTALE OK` token and its slot in `PROBES`, so the count stays 47 and no probe registration changes. One registration does change, and it is overdue: `newcode_ch` is `tests/host/*.c tests/host/*.h tests/*probe.c` and the cppcheck list is the kernel plus `tests/*probe.c`, so neither has ever matched a file named `fdstale.c`, and a rewrite that adds `fork`, `pipe`, `dup` and a 256-round loop must not stay ungated; it is added to both by name in this commit, per phase 1's rule. The probe today asserts exactly the behavior this phase inverts (`fdstale.c:104-124`), so leaving it standing fails the build. Its cases:

* The control first, so a later result cannot be credited to a mis-staged fixture: open, read, read again, with nothing else happening.
* Unlink under an open descriptor: `read` returns the original bytes in full, `lseek(SEEK_END)` reports the original size, `fchmod` succeeds, and a fresh `open` of the name returns `-ENOENT`. The last assertion separates a lifetime from a lookup that merely forgot to fail.
* The orphan hidden from the scans and not only from the resolver: after that unlink, `getdents64` on the parent directory must not list the name and must not list a nameless entry either, and `rmdir` on a directory whose only child is an orphan held by the probe's own descriptor must succeed. Both fail on an orphan that keeps its `parent_id` and nothing else changes, the second with `-ENOTEMPTY`.
* The reader-open, writer-rename, reader-read case, across two processes, because a scan that looked only at `current_proc` would pass a single-process version of it. The parent creates `/fdstale.old` containing a known line and forks; the child opens it, writes a byte to a pipe, blocks on a second pipe, then reads. The parent takes the byte, writes `/fdstale.new`, renames it onto `/fdstale.old`, and only then releases the child, which must read the old line whole and exit 0. The parent reaps it under `WIFEXITED` and then reads the name itself, which must give the new line. No sleep anywhere: each side blocks on a pipe the other writes, and a syscall on this kernel is not preempted, so the interleaving is the one the test names.
* A rename that fails after the destination was resolved: with a descriptor open on `/fdstale.old`, `rename("/fdstale.dir", "/fdstale.old")` must return `-EPERM` for the directory source and leave the name readable, through the held descriptor and through a fresh open alike. That is the assertion an implementation that orphans before it refuses cannot pass.
* The name re-created under the descriptor: the parent unlinks the file and creates a different one at the same name, and the child's descriptor must still read the old content. This is the case that separates a real lifetime from re-resolving the path, which would hand the reader the new file or half of each.
* Two descriptors on one orphan through `dup`, closing one and reading the other; and a child that holds the last descriptor and `_exit`s without closing it. The first proves the release counts descriptors and not files, the second that `release_fd_table` reaches the same release `sys_close` does.
* Relocation: two descriptors on one file, one of them growing it past its extent so `krffs_resize_reserved_node` must move it, the other reading the new content and stating the new size rather than `-EBADF`.
* The leak, which is the only free-space assertion a probe can make on a file system with no `statfs`: 256 rounds of open, unlink under the descriptor, close, on a 64 KB file. A kernel that orphans and never releases needs 16 MB inside a 10 MB image (`Makefile:158`) and fails with `-ENOSPC` at or before round 160; a correct one uses one extent 256 times. Then the same count of the other sequence, 256 rounds of write-new-then-rename onto a name no descriptor holds, which is what every credential replacement actually does. It must not exhaust the image either, and it is the case that fails if the orphan is made unconditional, which no other case here reaches.
* The directory case asserted rather than assumed: a descriptor on a directory that is then `rmdir`'d still answers `-EBADF`, so the scope line is a test and not a sentence.

Recorded rather than committed: the rewritten probe run against the kernel as it stands, where the cross-process case reports `-EBADF`, which is the review's failing input reduced to one assertion; and an offline `fsck.krffs` over the disk image after a boot that orphaned and released, showing the reserved-node count unchanged, since the durability half cannot be seen from the RAM module. The disk probes run on both buses, as for every phase that touches the walk.

Remaining limitations: a directory descriptor still fails `-EBADF` when its directory is removed; a crash with an orphan open leaves an extent only `fsck.krffs` can reclaim, and only offline, since there is no userland `reboot(2)`; and this phase makes a replacement atomic for a reader, not serializable against a second writer, so the read-modify-write still needs the transaction phase 9 implements. Nothing here makes a multi-file change atomic either; `adduser`'s ordering is still what a crash between two renames is judged by.

Readme: `rach2/sys/fs/Readme.md`, whose "Deliberate simplifications" bullet on open-file descriptions (line 55) says today that KRFFS nodes are not refcounted and ends by naming this exact refinement as later work. Phase 6's claim to be the last rewrite of that section's permission-model bullet stands; this is the bullet beside it. It is rewritten to state the contract: a regular-file descriptor names one file from open to close, across unlink, across a rename onto its name, and across a relocating write; the identity is the node, kept alive by the descriptor tables and released by the last close; a directory descriptor is still a name and still fails; and an orphan is a v2 state rather than a v3 field, which is why a crash can leave one for `fsck.krffs`. The same file gains the rename contract the credential library then depends on: metadata-only, so the destination inherits the source node's mode and owner, atomic against a concurrent reader whether it opens before or after the rename, and not atomic against a crash. `krffs/Readme.md` states fsck's new repair. `tests/Readme.md`'s `fdstale` line stops describing a use-after-free defense and says what the probe now proves.

### Phase 9: the credential library, locking and durability

`utils/pwauth.c` and `pwauth.h`, linked into `su` (and later `passwd`, `adduser`, `login`) the way `utils/resolv.c` is already linked into `ping` and `nc` (`utils/Makefile:88-96`). It is the only code in the image that compares a password against a stored hash, generates a salt, or replaces a credential file. Reading the databases for a rewrite stays with the writer, inside its transaction, which is exactly why `pwauth_check` takes the stored hash as a string. A pure reader is different: `pwauth_verify` resolves the entry itself and takes no lock, because phase 8 made the replacement atomic for a reader in fact rather than by assertion. A reader that loses the race against a writer sees the old file or the new one, whole, whether it opened before the rename or after it. Readers never lock, which is what keeps a stuck writer from keeping anyone out of the box. Eight entry points:

* `pwauth_check(stored, password)`: the pure comparison, factored out of `su.c`'s private copy (`su.c:54-64`) with its behavior unchanged (a missing or non-`$` hash denies everyone). It remains pure so the host test can call it directly.
* `pwauth_verify(user, password)`: `getspnam` plus `pwauth_check`.
* `pwauth_read_password(prompt, buf, size)`: decides on `isatty(0)` and reads fd 0 either way. The prompt goes to fd 2 unbuffered whatever `isatty(0)` says, and only the echo suppression is conditional; that is what lets a driver holding a pipe on fd 0 rendezvous on the prompt instead of guessing at a sleep. On a terminal it saves the modes with `tcgetattr` and installs a copy with `ECHO` cleared, and it restores them on every exit path. It never opens `/dev/tty`: a probe runs as init under the debug shell with fd 0 bound to the console (`fd_init_stdio`, `fd.c:87`), so a `/dev/tty` reader would block forever and `runtests.py` would report a hang and skip every later probe. Its signal handling is split by what each signal endangers, and the split is the point:
    * Echo is taken away only while the reader's process group owns the terminal, the same question the resume asks: a background `su &` would otherwise silence the shell's own terminal and then stop on `SIGTTIN`, leaving it echoing nothing with no program left to fix it. The modes are prepared regardless, so a `fg` picks them up through the resume path. The question and the action are one step with the job-control signals blocked around them, since a `^Z` served between them lets a shell reclaim the terminal and continue the reader in the background holding a stale answer; the resume path uses the same helper, and `SIGSTOP` stays the documented residue.
    * A stop is not a death, so it is handled here and always, transaction or none. The tty maps `^Z` to `SIGTSTP` through `VSUSP` (`n_tty.c:151`, `193-210`), so a user can suspend any password prompt with one keystroke and would otherwise leave the console with echo off and, in a writer, with the transaction held. The `SIGTSTP` handler restores the saved modes, resets its own disposition to `SIG_DFL`, and re-raises; the `SIGCONT` handler re-installs the `SIGTSTP` handler, re-applies the echo-off modes with `TCSETSF` so that characters typed and echoed while stopped are flushed instead of silently becoming password bytes, and reprints the prompt. Two handlers rather than the usual one that re-raises and continues after the raise, because `signal_setup_frame` blocks the handler's own signal for the run (`sys/proc/signal.Readme.md`): a `raise` inside the `SIGTSTP` handler stays pending until `sigreturn` restores the mask, so everything written after it would run before the stop rather than after the continue. Both handlers touch only `write`, `tcsetattr`, `sigaction` and `kill`, which are async-signal-safe.
    * The read itself loops on `-EINTR`. `SA_RESTART` is accepted and deliberately not honored (`sys/lib/ksignal.h:51-54`), so every signal that reaches a blocked read returns `-EINTR`, and a stop-and-continue must not read as end of input. On the resume the buffer is cleared and the prompt reprinted, since `n_tty` already flushed the edit line and every unread byte when it recognized the `VSUSP` char.
    * A death is the transaction's business, so those handlers are installed here only when no transaction is held, which leaves `cred_txn_begin`'s in force when there is one. The readers that matter most hold no transaction: `su` and `login` authenticate without writing anything, and a `^C` at their prompt would otherwise leave the console with `ECHO` off, on the image where phase 12 makes that console the only way in. So with no transaction held it installs the same death set around the read and restores the previous dispositions after, as it does for the two stop signals in both cases.
    * `SIGSTOP` cannot be caught, so a stop that way leaves the console with echo off until the reader is continued or killed. The rule below still protects correctness: no lock is broken and no update is lost.
    * The prompt's final teardown window is closed with the blocked-signal mask. The modes go back, a newline is written, and only then do the two stop handlers come off; a `SIGCONT` served inside that sequence runs a handler that re-applies echo-off, and the call returns with the terminal silenced and nothing installed to undo it. Any process in the same session may send that signal (`kill`'s `SIGCONT` exception, `syscall.c:5978`), so `SIGTSTP`, `SIGCONT`, `SIGTTIN` and `SIGTTOU` are blocked with `rt_sigprocmask` across the whole teardown and the pending signal is delivered afterwards, against the dispositions the caller had.
    * `SIGPIPE` is caught for the length of the call, transaction or none, because echo is taken away before the prompt is written to fd 2. A caller whose standard error is a pipe with no reader (which is how a driver rendezvouses on the prompt, and how dropbear runs a program) would otherwise be killed by the default action at exactly that point, leaving the console with echo off. The prompt's write already ignores its result, so a failed write is the expected outcome.
* `pwauth_salt_map(bytes, n, out)`: the mapping onto `./0-9A-Za-z`, a function of the bytes alone. It is separate from the draw so the host test can exercise it without entropy.
* `pwauth_mint_salt(out, size)`: `getrandom(2)` with no `GRND_INSECURE`, then the mapping. On failure it writes no byte of `out`, prints `pwauth: no trusted entropy`, and returns -1. The diagnostic names `pwauth` and not `passwd` because the library is the component that failed; each caller adds its own refusal line (`passwd: password unchanged`). That is the milestone decision's single message split across the two components that each know one half of it. The rule the library follows throughout, so the two halves of it do not look arbitrary: a line reporting the library's own failure names `pwauth`, and a line an operator must act on names the calling program, which is why `cred_txn_begin` takes `prog` and the lock lines below carry it while this one does not.
* `cred_txn_begin(const char *prog)` and `cred_txn_end`: the writer's exclusive lock, below. The program name is a parameter because only the library knows when an acquire has to wait or has to give up, and the lines it prints then must name the program the operator ran.
* `cred_rewrite(path, text, len)`: the replacement, below. It returns -1 without touching anything unless the transaction is held, so a caller that forgot to take it cannot ship quietly.

A credential change is a read-modify-write, and the replacement idiom does not make that interval exclusive. `passwd` reads `/etc/shadow`, authenticates the caller against the hash it read, prompts twice, and writes the file back; two sessions can read the same pre-image and rename in turn, and the second rename restores the first one's old hash. `O_EXCL` on the temp file guards nothing here, because the two runs are not racing on the temp, they are racing on a snapshot. The kernel offers no help: `F_SETLK`, `F_SETLKW` and their 64-bit twins return 0 for every request (`syscall.c:3309-3316`) and `F_GETLK` always answers `F_UNLCK` (`3317`), a documented no-conflict contract dropbear depends on, so an advisory lock records nothing at all.

The library implements its transaction with a lock file. `cred_txn_begin` creates `/etc/.pwlock` with `O_CREAT|O_EXCL|O_WRONLY` at mode 0600 and writes the holder's pid as one decimal line; `cred_txn_end` closes that descriptor, reads the recorded pid back through the slot it just freed, and unlinks the file if it is still this process's. The release opens no descriptor it did not first give back, because `MAX_FDS` is 16 and a writer can arrive at its release with the table full: an ownership check that needed a new descriptor would read `EMFILE` as another writer's lock, decline to unlink, and strand the lock for everyone while reporting success. `cred_txn_end` returns -1 when it could not look at the lock or could not remove it, so the caller reports a lock left behind rather than a clean finish, and `CRED_UNFLUSHED` when the lock is gone from the file system but its removal did not reach the disk. That third answer is the one the second review added: the release is the last write a transaction makes and, for a transaction that ends without a replacement, the only one, so a printed line alone would let a writer report a clean finish over a lock that comes back with the next boot. The exclusive create provides the exclusion: it is one syscall, and a syscall on this kernel does not yield (`timer_handler` skips `schedule()` while `current_proc->in_syscall`, `kernel.c:138-140`, and a page-cache window fault polls with interrupts off), so nothing can interleave between the existence test and the create at `syscall.c:1307`. `O_EXCL` on the lock file is a lock; `O_EXCL` on the temp file stays what it always was, a corruption check. A `mkdir` lock would exclude just as well and follows the pattern in `krffs/gen_demo_password.sh:37-40`; a file is chosen because it records the holder's pid, and the pid is what lets a refusal name the process an operator has to deal with.

Every writer takes the lock before its first read and holds it through its last rename: `passwd` before it reads `/etc/shadow` to authenticate, `adduser` before it reads `/etc/passwd` to test the name and across all three of its replacements. `cred_txn_begin` registers the release with `atexit`, so an ordinary `exit` cannot leak it, catches `SIGPIPE` for the transaction's whole lifetime (a writer reports as it goes, and a diagnostic into a standard error that is a pipe with no reader would otherwise kill it where no `atexit` runs, leaving the lock in `/etc`), and installs handlers for every catchable signal this kernel default-terminates for, which is all of them but the four it ignores, the four it stops for, the two that cannot be caught, the three this libc reserves (32 to 34) and `SIGPIPE` (see the final review round: `ksig_default_action` terminates by default and `cred_may_signal` lets the real uid that ran a setuid writer send anything, so `SIGUSR1` strands the lock exactly as `SIGTERM` would), for that same lifetime, because `atexit` runs on no signal death: the handler restores the terminal, unlinks any temp, and leaves through `exit` so the registered release drops the lock rather than the handler duplicating it. Two details came from the second review. The `SIGPIPE` disposition is a handler that does nothing rather than `SIG_IGN`, which no write can tell apart, because an `exec` resets a caught disposition and preserves an ignored one in the new image, and a child forked under a transaction would otherwise hand this library's policy to a program that never linked it. And the deaths are blocked wherever the state a handler reads is published: from just before the lock file is created until the pid is in it, and across the write of the temporary file's name, since neither is one store and the truncation of that name at one exact length is the credential database itself. The third review round added two more stretches with reasons of their own: the release, whose unlink and durability flush are one step (a death between them leaves through `exit`, and the registered release then finds the lock gone and reports a clean finish, so the flush is owed to nobody), and the registered release itself, which runs inside `exit` and would otherwise be re-entered through the `exit` the handler leaves by. That is why a caller does not install its own: the lock outlives the terminal read, and the terminal read is only one part of what a signal must undo.

The lock is never broken. The rule replaces the defective age bound from an earlier draft. An acquire that finds `/etc/.pwlock` present prints `<prog>: credential database busy, waiting` once, the first time it has to wait, then retries the create `CRED_LOCK_TRIES` (10) times one second apart. If the lock is still there it fails, and the pid in the file decides only which diagnostic is printed, never whether anything is removed:

* The recorded pid answers `kill(pid, 0)`, or answers `EPERM`: `<prog>: credential database busy (pid N)`. The holder may be running, or blocked at its own password prompt, or stopped. Nothing is broken and nothing is lost.
* The recorded pid is gone (`ESRCH`): `<prog>: stale lock /etc/.pwlock (pid N is gone)` and `<prog>: remove it as root and retry`.
* The file is empty or does not parse, which is what a crash between the create and the write leaves: the same two lines with `(no holder recorded)`. Recovery is explicit, and it is `rm /etc/.pwlock` by the root that owns `/etc`.

Three reasons, because "never break it" is the sentence a later reader will want to overturn. An age bound cannot tell a stopped holder from an abandoned one: `^Z` at the prompt is one keystroke, `SIGSTOP` cannot be caught at all, and a holder can therefore sit for any length of time. Breaking its lock lets a second writer read, publish and finish; the first then resumes, renames its own snapshot over that change, and the lost update the lock exists to prevent happens with the lock's blessing. Nor can the break itself be made safe once the decision to break has been taken: between reading the pid and unlinking the name there is no `funlink` and no way to bind the removal to the file that was inspected, so a second breaker can have already removed that lock and created its own, and the unlink then takes a live writer's lock. And the cost of refusing is bounded and falls on the right person, because no reader takes the lock: `su`, `login` and dropbear authenticate with none, so nothing about entering the box depends on it, and what a `SIGKILL`ed or segfaulted writer leaves behind is one `rm` for root. This is what `lckpwdf` does on Linux, and why `vipw` and `passwd` there report a lock rather than breaking one. The rule the later phases inherit: no caller breaks a lock, no caller installs handlers of its own, and a lock left behind is root's to remove.

A second `cred_txn_begin` in one process is a programming error and not contention, so the library keeps the held state and refuses it immediately with `<prog>: credential database already locked by this program`, without touching the file.

A stray temp needs no rule of its own, because a temp belongs to one writer: the name is `<path>.tmp.<pid>`, so a file `cred_rewrite` finds at its own name was left by a dead incarnation of this pid and by nothing else. It unlinks it and creates its own with `O_EXCL`; an `EEXIST` after that is a real fault and is reported, not retried. The cost of the pid is that nothing reclaims a temp its writer did not live to rename: sweeping `<path>.tmp.*` would be the never-break rule broken against a different file, since a pid names nothing across a reboot. It blocks nothing, is never read, and is root's to remove beside the lock. A fixed `<path>.tmp` would be shared, and the lock is not enough to make that safe: a writer whose lock had been removed by hand could unlink and recreate the file a successor already had open and written, and the successor's rename, which is by name, would publish it over the database. For the same reason the lock is checked before the temp is touched at all, so a replacement refused for a lock that is not this transaction's changes nothing on disk. A multi-file transaction can also crash between two renames, and no lock helps: `/etc/shadow` is replaced and `/etc/passwd` is not. The library cannot fix that, but the ordering can, so `pwauth.h` states the contract and phase 11 honors it: a writer orders its replacements so that every prefix is a state the system reads safely (shadow with a locked `!` first, then group, then passwd, so a crash leaves at worst an account nobody can enter and no name that points at it).

The durability step must be able to fail, and the earlier draft's could not. It fsynced before the rename and called `sync(2)` after; `sys_sync` returns 0 unconditionally and discards `pc_sync`'s result by design (`syscall.c:1494-1506`), so a writeback failure would let `passwd` report success over credentials that never reached the platter. `sys_fsync` propagates `-EIO` (`1478-1491`), and its flush is whole-cache while KRFFS keeps its metadata in the same image the cache backs, so one `fsync` through any open descriptor also covers the rename's node header. `cred_rewrite` therefore keeps the temp's descriptor open across the rename: check the lock, `umask(077)` and restore, unlink any leftover temp of this writer's own, `open(O_CREAT|O_EXCL)`, write the whole text, `fchown` then `fchmod` from the original (that order, because phase 5 makes chown clear the set-id bits), `fsync`, `rename`, `fsync` again through the same descriptor, `close`, every step checked. The descriptor follows the file through the rename because phase 8 makes it name the node rather than the name, so the second flush goes through a descriptor on the published file; phase 8 also orphans the destination the rename replaces instead of freeing it, so a reader that opened the old `/etc/shadow` keeps reading it whole. A failure before the rename unlinks the temp and leaves the target untouched. A failure of the second `fsync` returns `CRED_UNFLUSHED` with the file system already containing the new file and the disk possibly still containing the old one; the block comment states that the caller must then report failure, which is exactly the `-EIO` that the `sync(2)` version threw away. Both flushes are no-ops on a RAM-module boot, which is why the durability claim belongs to the disk image phase 14 presents. The comment also says why there is no hard-link backup (KRFFS has no links; `link` returns `-EPERM`) and why the temp's mode is the result's mode: `krffs_rename` changes only the name and the parent id, so the destination inherits the source node's mode and owner, and getting that wrong makes the file that exists to be unreadable readable.

`su` is rebuilt on the library and its three point-of-use deferrals close. `read_line` and `password_ok` (`su.c:40-64`) become `pwauth_read_password` and `pwauth_verify`. The login form is parsed rather than ignored: today the option loop takes any argument beginning with `-` other than `-c` as a flag to discard (`su.c:75-83`), so `su - test` silently runs a non-login shell, and a chdir alone would not fix it, because this project makes a shell a login shell with a leading-dash `argv[0]` (`utils/init.c:21-26` passes `-sh` and `-ish`) while `su` passes the plain shell path (`su.c:131-135`). A bare `-`, `-l` and `--login` select login mode; any other unrecognized option is now a usage error rather than silence. Login mode is three things: `chdir(pw->pw_dir)`, an `argv[0]` of `-` plus the shell's base name (`-sh` for `/bin/sh`), and the environment `su` already builds from nothing. A chdir failure is fatal (`su: cannot enter %s`) rather than util-linux's warn-and-continue, because the home directory and the dash define the login-specific behavior of `-` and continuing would run a login shell in the caller's directory and call it a login. Non-login mode is unchanged, cwd and `argv[0]` included, which is what makes the paired assertions below mean anything. PAM stays a non-goal.

### Phase 10: passwd in the guest

`utils/passwd.c`, setuid root, in the `su`/`sudo` mould and built into `build/utils/sbin/`. The caller's identity is `getuid()`, never an argument, and the administrative exception that lets a caller name another account is `getuid() == 0`, not `geteuid() == 0`: this binary is 04755, so its effective uid is 0 for every caller, and a euid test would authorize the whole world. This is the milestone-16 `su` finding in a second place, so state it as the rule: a set-id program decides what its caller may do from the real uid, and uses the effective one only to do it.

Everything `passwd` does happens inside one credential transaction, phase 9's, taken before it reads anything and released only after the replacement is published:

* Review moved the transaction after the prompts, and this plan preserves that correction. The draft above took it before the first read so that the account found, the hash authenticated against and the file replaced were one image by construction. That property remains required, but the early transaction held the lock across two or three terminal reads. Any account could start `passwd`, leave it at the prompt, and stop every other writer for as long as it liked on a machine with sixteen process slots. `passwd` therefore surveys and prompts with no lock, takes the transaction with nothing left to type, re-reads `/etc/shadow` under it, and refuses unless the record it authenticated against is still the record it is about to replace. A changed record is detected after the lock is taken; passwd reports it and changes nothing. The obsolete wording follows because it states the required one-image property, although review changed the mechanism:
* `cred_txn_begin` before the databases are opened and before any password is read or checked. Then `passwd` reads `/etc/passwd` and `/etc/shadow` through the transaction and works on those bytes: it maps `getuid()` to a name from that copy, checks the old password with `pwauth_check` against the hash from that copy, and rewrites the same copy. It does not call `getspnam`, which would be a second, independent read that can see a different file than the one about to be replaced; `pwauth_check` takes the stored hash as a string precisely so the caller can supply it from wherever the account was found. This is the ordering the review asked for: authentication and replacement see one image, under one lock.
* `cred_rewrite("/etc/shadow", ...)` publishes the new file and `cred_txn_end` drops the lock. Both returns reach the exit status: a replacement that published but could not be flushed, and a lock that was removed but not flushed, are each a failure `passwd` reports, since the point of returning them at all is that nobody reports a clean finish over a change the next boot may not have. There is no separate abort: `cred_rewrite` either renamed its temp or unlinked it, so ending after a failure publishes nothing and leaves nothing behind, and every exit path ends the transaction. A caller who arrives with the descriptor table nearly full (`MAX_FDS` is 16) makes one of `cred_rewrite`'s opens fail; the temp is unlinked and -1 returned, which is what makes that outcome a refusal rather than a half-written database.
* The lock is phase 9's `O_CREAT|O_EXCL` file in root-owned `/etc`, and it has to be that rather than a POSIX lock: `sys_fcntl64` grants every `F_SETLK` unconditionally as documented no-conflict semantics (`syscall.c:3309-3316`), so an `fcntl` lock would prove nothing here, while `do_open` really refuses an exclusive create of an existing name (`syscall.c:1307`, the KRFFS branch; the `1139` refusal is the synthetic-filesystem branch and never sees `/etc/.pwlock`) and a syscall is not preempted (`kernel.c:138-140`), which makes the create the indivisible test-and-set a transaction needs. Only writers take it. `login`, `su` and dropbear read the databases and take nothing, so no stale lock can keep anyone out of the box; that is the whole reason the reader side rests on rename instead.
* Because the lock is held across the terminal read, the handlers `cred_txn_begin` installs for the transaction's lifetime are what drop it: each restores the terminal, unlinks any temp, and leaves through `exit`, so the release registered with `atexit` runs. `passwd` installs nothing of its own. A program that catches a signal to fix the terminal must also drop the lock, and the transaction is the only place that knows it is held. `SIGKILL` leaves the file behind, and by phase 9's rule the next writer reports it rather than breaking it, so recovery is `rm /etc/.pwlock` as root.

`passwd` refuses a name that appears more than once in either file it read, changing nothing and saying which file contains the duplicate. It parses the text itself, so the count is free. Every one of musl's three parsers stops at the first match (`getspnam_r.c:108-120`, `getpw_a.c:36-39`, `getgr_a.c:35-39`), so a duplicate is an error nowhere and a silent ambiguity everywhere: which of two shadow lines authenticates a login, and which one a password change rewrites, would be decided by file order. Guessing is the worse rule, because the two decisions can pick different lines and the account would then authenticate against a hash `passwd` reported as changed. Nothing in the distributed tree creates duplicates once phase 11's absence check covers all three databases; this refusal is what keeps a hand-edited or pre-fix image loud instead of order-dependent.

The reader side is phase 8's, and `passwd` is the program that would otherwise break it. A `getspnam` is an `open` and then one or more `read`s, and the kernel preempts freely between syscalls, so before phase 8 a replacement landing in that window turned an authentication into `-EBADF`, which musl's `fgets` loop cannot distinguish from an absent account: dropbear would refuse a correct password and refuse it as an unknown user. With an open descriptor naming one file, a reader that opens before the rename reads the file it opened, whole, and a reader that opens after reads the new one. That is what makes "replaced, never rewritten in place" mean what it says, and it is why `passwd` needs no cooperation from any reader.

The salt is generated after authentication and before the new password is prompted for, so a machine with no trusted entropy refuses without first asking for a password it cannot use. `pwauth_mint_salt` calls `getrandom(2)` with no flags, never `GRND_INSECURE`, and a short read counts as a failure; the library then prints `pwauth: no trusted entropy` and `passwd` adds its own `passwd: password unchanged`, ends the transaction without a replacement, and exits non-zero with every file byte-identical and no temp and no lock left. Nothing in `passwd` hashes with an untrusted salt, and nothing falls back. The new password is read twice through `pwauth_read_password` and must agree; an empty new password is refused, since an empty shadow field admits everyone and that is exactly what phase 12's `login` must never see.

Staged `04755:0:0 /bin/passwd` in os-real and `04755:0:0 /passwd` in the flat test image (which has no `/bin`), and named in both of `check_setid.py`'s allowlists. The test image gains a second unprivileged account, `probe2` (uid 1001, its own committed `$6$` hash beside `probe`'s and its own line in the `/etc/group` phase 9 staged), because a lost update is only visible when two accounts change. `utils/passwd.c` and `tests/musl/passwdmusl.c` are added by name to `tools/check.sh`'s `newcode_ch` and cppcheck lists in this commit, per phase 1's registration rule.

`CONFIG_PASSWD` goes off, without which a bare `passwd` reaches busybox's applet and dies with `must be suid to work properly`, and `CONFIG_FEATURE_DEFAULT_PASSWD_ALGO` becomes `sha512` as a transitional setting that matters only until phase 11 turns off the last of `CHPASSWD`/`CRYPTPW`/`MKPASSWD` and `oldconfig` drops the symbol. `tools/check_setid.py` gains its third check here, beside phase 3's manifest sweep and image inventory: it parses `include/applet_tables.h` for whole NUL-delimited tokens and fails when `su` or `passwd` is present, when the `cat` sentinel is absent, or when the header cannot be found. Unordered, the guard therefore fails a correct tree on a missing header, or, in the case that matters, reads the old table after `rach2.config` was edited, passes, and lets the image stage the busybox whose re-enabled applet the check exists to forbid. Phase 12 extends the forbidden list rather than this phase asserting names that are still enabled, since `CONFIG_LOGIN`, `CONFIG_VLOCK`, `CONFIG_WALL` and `CONFIG_CRONTAB` are all still `y` at this point and a guard naming them would fail every os-real build for two phases.

Proof: `tests/musl/passwdmusl.c` (49), musl-linked because it needs `crypt` and the `pw`/`sp` parsers, which is also what gives it `pipe`, `poll` and `waitpid`. It runs as root, snapshots `/etc/passwd`, `/etc/shadow` and `/etc/group`, and restores them byte-for-byte before exiting. Three parts:

* In the sequential case, a uid-1000 child with scripted input on a `pipe`/`dup2`d fd 0 (so `pwauth_read_password` takes the non-tty path) execs `/passwd`, and the parent asserts on the file's bytes and metadata rather than on the exit status: the entry changed, the new hash is `$6$` with a different salt, `crypt(new, newhash)` reproduces it, every other line is byte-identical to the pre-image (a check through `getspnam` alone would pass on a file that lost every other account), `stat` still reports 0600 root, and no temp and no `/etc/.pwlock` remain. Then the negatives: a wrong old password exits non-zero with the file byte-identical; uid 1000 asking to change root's password is refused; and a hand-written second `probe:` line in `/etc/shadow` makes `passwd` exit non-zero naming the duplicate, with both files byte-identical, which is the assertion that an ambiguous database is refused here rather than resolved by file order.
* The concurrent case, which is what the lock exists for and what nothing in the earlier draft tested. The parent gives each child a pipe on fd 0 and a pipe on fd 2, forks, drops to the child's uid, and execs `/passwd`. It feeds A (uid 1000) its old password and then reads A's stderr until the exact prompt `New password:`; A can only have printed that after authenticating, so the parent knows, rather than assumes, that A holds the transaction. Only then does it fork B (uid 1001) and feed B its whole script. B's stderr is read with `poll` against a deadline, and the one line that may appear is the library's `passwd: credential database busy, waiting`: a prompt from B fails the probe on the spot, because B can only reach a prompt by reading the databases A is holding. The parent then feeds A its two new-password lines and reaps it, and only then does B's prompt appear, get answered, and B exit. Both waits guard on `WIFEXITED`. The closing assertion is that both accounts carry new hashes that `crypt` reproduces and that root's line is untouched.
* The entropy implication, and it is `getrandom`'s answer that decides which side runs, never a CPUID bit. The kernel prefers RDSEED (leaf 7, EBX bit 18) and falls back to RDRAND (leaf 1, ECX bit 30), and it marks the generator trusted only when a source actually delivered eight words (`hw_key`, `rach2/sys/lib/krandom.c:254-273`; `krandom_is_trusted`, `169-171`; the fail-closed check at `syscall.c:5318`). So an RDSEED-only CPU has trusted entropy while advertising no RDRAND, and a CPU advertising an RDRAND that does not deliver has none; a probe that read ECX bit 30 as the trust outcome would assert the wrong direction on both. The probe therefore reads both bits, each checked on the CPUID max leaf the kernel checks it on and each saving and restoring EBX, and uses them only as preconditions; then it calls `getrandom(buf, 16, 0)` and takes that as the outcome, the method `rngprobe` already uses (`tests/rngprobe.c:1-15`). Success means trusted: `passwd` must change the file, and the token is `PASSWDMUSL OK (trusted)`. `-EIO` means untrusted: every `passwd` run must exit non-zero printing both `pwauth: no trusted entropy` and `passwd: password unchanged`, with all three files byte-identical, and, since salt generation precedes the new-password prompt, the script ends after the old password and the probe asserts `New password:` never appears; the token is `PASSWDMUSL OK (fail-closed)`. Any other return from `getrandom` fails the probe with no token at all. The two bits provide two assertions nothing else makes: neither bit present with `getrandom` succeeding is a broken fail-closed check, since `hw_key` can only have returned `KRANDOM_SRC_JITTER`, and the probe fails there; either bit present with `-EIO` is legal, the advertised instruction having failed to deliver, and is reported as the reason the fail-closed side ran, so a log reader is not left with a mystery.

The two checks read different things, which is what stops the probe choosing which side counts as a pass. The suite scores a probe on the kernel's own exit line and matches no token at all, phase 1's rule, so the probe exits 0 only on the trusted side and a fail-closed run under `-cpu max` fails the suite by its status. `harness.py --ok` is the opposite, matching a token and never reading the status, so the invocation this phase adds to phase 9's `make test-noentropy` is checked on `PASSWDMUSL OK (fail-closed)`. Neither check can be satisfied by the side the other expects. That target keeps `-cpu qemu64` exactly because it advertises neither instruction, which is the only configuration in which the fail-closed side is the correct outcome rather than an accident; the probe asserts that as its precondition, so a QEMU that started advertising one fails the target by name instead of inverting the test. The fail-closed side cannot come from `runtests.py --cpu qemu32` either: that boots the whole suite without RDRAND, where `rngprobe` fails closed by design, so such a run can never be passing.

What makes the concurrent case deterministic, and it is the synchronization that phase 11 reuses: the probe's own children are the only user processes on the machine (the harness `exec`s the probe from the kernel debug shell, so there is no init and nothing else runnable), the kernel does not preempt a process inside a syscall (`kernel.c:138-140`), and every blocking point in the test is a pipe the parent controls or the transaction's acquire. So a child runs to its next blocking point whenever the parent blocks, and the parent's rendezvous is a token on the child's stderr, never a sleep: the holder's prompt and the loser's busy notice, both written to stderr unbuffered so a piped stdout cannot swallow them and the notice printed exactly once, when the acquire first has to wait. The deadline on the loser's read bounds a failure rather than deciding a pass, since the pass condition is one token and the failing build produces a different one; with the lock removed, B prints `Old password:` and the probe fails there, and if it printed nothing the deadline fails it too.

### Phase 11: adduser

`utils/adduser.c`, root-only and deliberately not setuid: it refuses a caller whose `getuid()` is not 0 before it opens anything. It has no set-id bit, so its real and effective uids are the same and there is nothing to confuse, but it tests the same identity the same way, because both programs apply the same real-uid rule. Usage: `adduser [-u number] [-s shell] name`, the shell defaulting to `/bin/sh` and not checked for existence (an account may legitimately be created before its shell is staged).

It writes three databases and a home directory, and holds one transaction across all four. After `cred_txn_begin` it reads all three files through the transaction and does every check against that one image: the name must be absent from `/etc/passwd`, from `/etc/group` and from `/etc/shadow`; the number must be free as a uid and as a gid; and with no `-u` the lowest number at or above 1000 that is free in both is chosen. Choosing a number outside the lock is how two concurrent runs hand out the same uid, so the read, the choice and the writes are one transaction and not three.

Shadow is in the absence check and not only in the write list, and this phase records that correction. It is published first, so a crash after that one rename leaves the name in `/etc/shadow` and nowhere else; a run that tested only passwd and group would pass both tests and append the name a second time. Nothing then reports the duplicate: musl's parsers all stop at the first match (`getspnam_r.c:108-120`, `getpw_a.c:36-39`, `getgr_a.c:35-39`), so which of two shadow lines authenticates a login, and which one `passwd` rewrites, is decided by file order, and the two can differ. The number is checked against `/etc/passwd` and `/etc/group` only, because `/etc/shadow` has no uid field; that same absence is why the shadow line is the smallest fact the publication can begin with, since it consumes no number and references no group.

The publication order is chosen so that every prefix of it is a consistent system, because the lock excludes a concurrent writer and only the order survives a crash: KRFFS has no journal, `krffs_rename` publishes one file at a time, and ending the transaction after a failure publishes nothing further while undoing nothing already published. Phase 8 gives each replacement a lifetime a reader can trust and gives two replacements nothing, which is exactly the boundary here: a reader sees each of these files whole, and no reader sees the four of them as one change. So: `cred_rewrite` on `/etc/shadow` with a locked `!` field first, then `cred_rewrite` on `/etc/group`, then the home directory (created 0700 and chowned to the new uid and gid, chown before any mode change, phase 5's rule), and `cred_rewrite` on `/etc/passwd` last. The account becomes visible only at the final step, so no interruption can leave a passwd field of `x` with no shadow entry, nor a gid that names no group.

Each prefix has a stated recovery, and they are stated here because a rule that exists only in the order is a rule nobody can act on:

* If nothing was published, no file changed and there is nothing to do. A crash here can still leave the lock.
* If only shadow was published, a locked field remains under a name no account claims. No reader reaches it, since every path into `getspnam` starts from a passwd entry (`su`, `login`, and dropbear's `fill_passwd`). A later run refuses, naming `/etc/shadow`; root removes the line. No number was consumed, so an unrelated account created meanwhile may legitimately take the one the dead run had chosen.
* If shadow and group were published, a group remains with no members whose gid no account names. `getgrnam` and `getgrgid` both find it, so the number is consumed and a later run's free-number scan skips it, which is correct rather than a leak. A later run refuses, naming both files; root removes both lines.
* If shadow, group and home were published, a 0700 directory remains owned by a uid and a gid that resolve to no name, so `ls -n` reports the numeric ids. The refusal names the two files and the directory.
* If all four were published, this is the intended end state before `passwd` runs, an account that exists and cannot be entered. `passwd NAME` completes it, and a later `adduser NAME` refuses as an existing account, which is a different diagnostic from the residue cases.

The lock is the fifth residue, and by phase 9's rule the next writer reports it rather than breaking it, so recovery is `rm /etc/.pwlock` as root.

So the refusal distinguishes a live account from a residue, because the two want different repairs. A name present in all three databases is `adduser: bob already exists`; a name present in some of them is `adduser: bob is in /etc/shadow and /etc/group but not /etc/passwd; remove the leftover lines and retry`, naming exactly the files that contain it and the uid and gid where one was recorded. `adduser` never resumes a partial account, and it never rolls one back. Resuming would mean deciding that a partial state is a residue rather than something an operator wrote by hand, and adopting a uid it did not choose; rolling back would mean a second series of replacements, each of which can fail in the same way the first did, on files another writer may since have changed. The cost is that a crashed name is refused until root removes the leftover lines, which is the same editing that account removal already requires, and the Readme says so. Where `adduser` fails rather than crashing there is someone to tell, so it tells them: any failure after the first publication prints `adduser: failed after writing /etc/shadow and /etc/group; nothing was rolled back`, listing what it published.

Then `cred_txn_end` drops the lock, and only then does it exec the password program (`/bin/passwd`, falling back to `/passwd` on `ENOENT` for the flat test image: os-real stages a `/bin` and the test image does not, so a program that must run under both looks in both, in that order), passing the new name. Releasing before the exec is required and not incidental: the lock is a file, it outlives `execve`, and a transaction carried across the exec would deadlock `passwd` against its own predecessor. Until that `passwd` succeeds the field stays `!` and the account cannot be entered, which is why shadow is written first and why a failure there needs nothing undone.

`CONFIG_ADDUSER`, `CONFIG_ADDGROUP`, `CONFIG_CHPASSWD`, `CONFIG_CRYPTPW` and `CONFIG_MKPASSWD` go off: each generates a hash through `libbb/pw_encrypt.c` and its LCG salt. `CONFIG_DELUSER` and `CONFIG_DELGROUP` go off with them, reversing what the earlier draft said, and for a different reason: they do not generate a hash, but they replace the same files without taking the lock, so a removal concurrent with a `passwd` silently loses one of the two changes, and an invariant that only one side of a race honors is not an invariant. The Readme states the cost: account removal requires root to edit the databases. `/etc/skel` is not staged, and the Readme says the absence is deliberate.

Staged `file 0755:0:0 /bin/adduser` in os-real and `file 0755:0:0 /adduser` in the flat test image, from `build/utils/sbin/`. It adds no line to any allowlist, and `check_setid.py` fails the build the day it grows a bit. The test image already contains `/etc/group` and `dir 0755 /home` from phase 9, so this phase stages neither again; `adduser` creates the home's leaf and refuses a missing parent. `utils/adduser.c` and `tests/musl/addusermusl.c` join `tools/check.sh`'s `newcode_ch` and cppcheck lists here, per phase 1's registration rule.

The ordering claim is proved by injection, so it rests on behavior rather than on a reading of the source. `utils/adduser.c` builds twice from one source, following phase 12's two-build init pattern: `build/utils/sbin/adduser` as distributed, and `build/utils/sbin/adduser-crash` with `-DADDUSER_CRASH_POINT`, which takes a leading count argument and `_exit(9)`s the instant publication number N has landed. It dies inside the transaction and through `_exit`, so it leaves the lock a real crash leaves, which is the same residue the recovery rule must clear. Everything the crash build adds lives under that one `#ifdef`, so the distributed binary has neither the argument nor the code, and it is staged `file 0755:0:0 /adduser-crash` in the test image and nowhere else: os-real never contains it, and the manifest sweep refuses a set-id bit on either artifact. It is a helper like `idreport` and `suidhelper`, not a probe, and takes no slot in `PROBES`.

Proof: `tests/musl/addusermusl.c` (50), running as root, snapshotting the three files, and restoring them byte-for-byte along with removing the created homes and any lock file before it exits. It appears at the tail of `PROBES`, after `musl/passwdmusl`. Every wait guards on `WIFEXITED`.

* The end-to-end case: create an account with a scripted password on a `pipe`/`dup2`d fd 0, and assert `getpwnam` and `getgrnam` parse it back with the same number for uid and gid (proving libc can read what we wrote, not merely that bytes landed), that the shadow field is a `$6$` hash `crypt` reproduces from the scripted password, that the home exists 0700 owned by the new uid and gid, and that every pre-existing line in all three files is byte-identical.
* The failed-password case, which proves the benefit of the publication order: a second name whose two new-password lines disagree. The exec'd `passwd` exits non-zero, the account still exists in all three databases, and its shadow field is still `!`, so it cannot be entered and there is nothing to roll back.
* The refusals, each followed by all three files byte-identical and no `/etc/.pwlock` left behind: an existing name, `-u 0`, a number already taken as a uid or as a gid, and a uid-1000 child, which is refused before any file is opened.
* The residue no crash of ours can produce, which is what separates a per-file absence check from a check on the ordered prefix: a hand-written line for an unused name in `/etc/group` alone, after which `adduser` on that name must refuse naming `/etc/group`, with all three files byte-identical afterwards.
* The injection, one round per publication point, each run through `/adduser-crash N`. The crash build dies holding the transaction, so every round leaves `/etc/.pwlock` behind; the probe asserts the lock is there and records the crash child's pid, unlinks it the way root would, and only then runs the real `adduser`, which by phase 9's never-break rule would otherwise spend ten seconds and refuse on the lock rather than on the residue the round is about. After point 1 the probe requires `/etc/shadow` to hold exactly one line beginning with the name and a `!` field, `/etc/passwd` and `/etc/group` byte-identical to the pre-image, `getspnam` to find the entry while `getpwnam` and `getgrnam` find nothing, and the following real `adduser` on that name to exit non-zero naming `/etc/shadow` and to leave `/etc/shadow` still holding exactly one such line. That count is the review's failing input reduced to a single assertion, and it is the case that reads two with the shadow check removed; it is demonstrated failing that way once, and the run is recorded. Point 2 adds `/etc/group` to what must hold the name and to what the refusal must name, with `/etc/passwd` still byte-identical; point 3 adds `/home/<name>` at 0700 owned by the chosen numbers, untouched by the refused re-run; point 4 leaves the complete account with its `!` field, where the refusal is the existing-account one and a `passwd <name>` with scripted input completes it, which is the assertion that the last prefix is finishable rather than wedged.
* The contention case incorporates the later rework described below. The paragraph above was drafted while `passwd` still took its transaction before prompting, and phase 10's review moved it after: a `passwd` held at `New password:` now holds no lock at all, so the window this case was to be staged in no longer exists, and by design, since holding a lock across a terminal read was the defect that rework fixed. No live writer here holds the lock across anything a test can synchronize on, so the deterministic half is built on the lock a real writer really leaves: the crash build dies inside its transaction, and against that lock `adduser` must print the library's `adduser: credential database busy, waiting`, must still be alive under `waitpid(..., WNOHANG)`, and must have published nothing, all three databases byte-identical to the pre-image. That is the same pair the original case asserted and it fails the same way for an `adduser` that ignored the lock, which would have read the pre-image and published inside the window. The lock is then removed the way root would and the run must complete. The live half keeps two real writers racing without pretending the race is scheduled: a uid-1000 `passwd` on the staged account and a root `adduser` on a new name, started together and both fed, after which both results must survive, which is what a lost update destroys; and two `adduser` runs for two names at once, which must come out with two different uids, since choosing a number outside the lock is exactly how two runs hand out the same one. The exec'd `passwd` completing proves it re-acquires a lock its own predecessor released rather than deadlocking on it.

The closing cross-check runs over the final files and is the invariant the review asked for, in both directions: every `/etc/passwd` line has an `/etc/shadow` line and an `/etc/group` line whose gid it names, and no name appears twice in any of the three. An `adduser` that ignored the lock leaves exactly the first failure, an `x` field with no shadow line; an `adduser` that checked only two databases leaves exactly the second.

Manual half: root creates an account at the os-real prompt, sets its password, and logs in over SSH as that account, which reads `/etc/motd`, is refused a write of it, and is refused a read of `/etc/shadow`. Those are the three answers os-real's own modes give: `/etc` is staged `dir 0755` and `/etc/motd` `text 0644`, both root's, so an unprivileged account reads that file and cannot modify it, and phase 12's `login` depends on the read, since it prints the file after dropping to the caller's identity. `/etc/shadow` is `file 0600` root and is the only one of the three that denies a read, which makes it the required denial to record. An assertion that the new account is denied `/etc/motd` could be satisfied only by breaking one of those two modes.

### Phase 12: a real login on the console

`utils/login.c`, no setuid bit because init is root, built into `build/utils/sbin/`: prompt for a user, read the password through `pwauth_read_password`, verify, sleep and re-prompt on failure with a bounded retry count and no leaked descriptors (`MAX_FDS` is 16), then `setgroups(0, NULL)`, `setgid`, `setuid` in that order, build the environment from nothing, chdir to `pw_dir`, print `/etc/motd`, and `execve(pw_shell)` with a leading-dash argv[0]. It must not `setsid` or claim the terminal again: init's child already did, an exec by the owning session leader re-publishes the console across the destructive load, and a second claim after the identity drop would fail `-EPERM` for a non-leader.

Init stops being one program with a fallback list. `spawn_shell` (`utils/init.c:39-58`) walks `Shells[] = { "/bin/sh", "/ish" }` with the matching `-sh`/`-ish` argv[0]s (`init.c:25-26`) and execs each in turn, falling through whenever `execve` returns, whatever the errno. Putting `/bin/login` at the head of that loop drops the console to an unauthenticated root shell on any failure, and narrowing the fall-through to `errno == ENOENT` inverts the danger instead of removing it: `ENOENT` is precisely the case of an os-real image built without `/bin/login`, and that image is the one that must refuse hardest. The fallback is compiled out; narrowing it would still fail open. `utils/init.c` builds twice from the one source: `build/utils/sbin/init-shell`, today's behavior unchanged, and `build/utils/sbin/init-login`, built with `-DINIT_CONSOLE_LOGIN`, whose session child execs `/bin/login` with argv[0] `login` and nothing else. `Shells[]`, `Shell_Arg0[]` and the exec loop live inside `#ifndef INIT_CONSOLE_LOGIN`, so the strict artifact contains no code path and no string that names a shell. The reaper loop, the respawn backoff, and the `setsid` plus `TIOCSCTTY` dance are shared and unchanged. Neither artifact is named plain `init`: `os-simple.manifest:10` becomes `file 0755 /sbin/init build/utils/sbin/init-shell` and `os-real.manifest:31` becomes `build/utils/sbin/init-login`, so a manifest left on the old path fails to stage rather than silently getting whichever init the tree happens to build.

The mode is a compile-time split rather than a runtime one because every runtime signal is a thing an edit can drop, and the drop must not be the permissive direction. A marker file removed from a manifest, or a `rach2.login` token lost from the command line the way `rach2.rescue` can be lost, would hand the console back to an unauthenticated root shell: the same fail-open in a new place. Two artifacts contain no such state, and which init an image gets is visible in the manifest diff.

In `init-login` every `execve` failure is one case, `ENOENT` included. The child writes `init: cannot exec /bin/login: <strerror>` and, on the first failure, `init: boot rach2.rescue for the kernel debug shell`, then `_exit(127)`; the parent's existing fast-death backoff respawns it, at 5 s rather than 1 s in this build so a permanent failure states its reason on the console without scrolling it away. It retries forever and never gives up, because giving up means init exits, and an exited init is `panic_init_died` (`kernel.c:1247`): a panic refuses a shell no harder than the retry does while turning a transient failure (a full process table, a fault on the demand-paged window) into a permanent one.

This is the change that can lock everyone out, so the way back in is stated rather than assumed. `rach2.rescue` (`rach2/run.sh:81`) sets `rescue_mode` before the boot home is chosen, and the kernel then never calls `boot_init_process` at all (`kernel.c:2679-2683`): the image's init is not consulted, and the debug shell comes up with the filesystem mounted and writable, so a broken os-real is repairable in place. That is the only way back in, and it must stay so: SSH is not a second one, since dropbear is started by hand from the console session and nothing starts it at boot. The trade is deliberate and asymmetric. The failure being removed (an unauthenticated root shell on any exec failure) is reachable by whoever walks up to the serial line; the failure being accepted (a console that will not offer a prompt until the image is repaired) is reachable only by rebooting with a flag the operator controls. os-simple cannot reach either: its manifest line is repointed to `init-shell`, which is today's init unchanged, and nothing else in that image moves.

`tools/check_setid.py` gains its fourth check, beside phase 3's manifest sweep and image inventory and phase 10's applet table, and it splits by what each half must read. The manifest half joins the sweep in `tools/check.sh`, since it reads text alone: each manifest's `/sbin/init` line must name the artifact its table entry declares, and a manifest whose entry declares no init must contain no such line. The byte-string half joins the artifact-dependent `check-setid` target beside the applet table, since it reads a built binary: `init-login` must contain neither of the byte strings `/bin/sh` and `/ish`, and `init-shell` must contain both. That positive requirement is the sentinel: an unreadable or empty scan fails rather than passes, which is how the same script already guards `applet_names[]`. The check is exact in this tree because a musl-static util that never calls `system` contains neither string (`build/utils/cat` contains neither today; only init's own table puts them in a binary). Both binaries come from the `utils` sub-make, which the image targets list beside the guard and not ahead of it, so this commit adds `utils` to `check-setid`'s prerequisites the way phase 10 added `$(BUSYBOX_STAMP)`. Without it a parallel build scans a `build/utils/sbin/` that contains the old single `init` and fails the sentinel on a correct tree, or, after an edit to the `#ifndef` block, scans yesterday's clean `init-login` and passes while today's, containing both strings, is staged.

`CONFIG_LOGIN`, `CONFIG_VLOCK`, `CONFIG_SULOGIN`, `CONFIG_GETTY`, `CONFIG_WALL` and `CONFIG_CRONTAB` go off once ours is proven, and the applet guard's forbidden list grows to `su`, `passwd`, `login`, `vlock`, `wall`, `crontab`. `wall` and `crontab` are on that list because they are `BB_SUID_REQUIRE` too (`util-linux/wall.c:16`, `miscutils/crontab.c:22`), and the generated applet table confirms both are enabled today; without them the stronger invariant ("busybox contains no applet that would want a set-id bit") would be false the day it was written. `sulogin` and `getty` are `BB_SUID_DROP` and go off for a different reason, which the Readme states: they are the console-login path ours replaces.

Proof, three layers, because the harness cannot boot a console login at all (it types `exec <name>` at the kernel debug shell against an image with no `/sbin/init`, so neither init nor login runs there):

The success case needs something to exec, and the test image stages no shell at all: that is why the `probe` account phase 9 committed names the `idreport` helper as its shell, with `/home/probe` as its home. This phase drives that account unchanged and asserts on `idreport`'s exit status. It snapshots and restores the three credential files and appears at the tail of `PROBES`.
* `tools/login_test.sh` (`make login-test`), following the pattern of `crash_test.sh`, is the absent-binary proof: the case the earlier draft never tested, having tested only a `chmod 0000` login, which yields `EACCES` and never exercises the `ENOENT` path the fall-through was checked on. Its two fixtures are committed manifests rather than generated ones, `krffs/manifests/login-test-strict.manifest` (declaring `init-login`, with no `/bin/login` line) and `krffs/manifests/login-test-shell.manifest` (declaring `init-shell`, with no `/bin/login` line either), each named in phase 3's table: a manifest the table does not name is a hard error at `mkimage.sh` time, and an os-real-derived manifest repointed at `init-shell` on the fly would fail this phase's own init invariant. `login_test.sh` stages those two names with `krffs/mkimage.sh` and boots each under QEMU with the serial log captured, typing `id` at the console. The strict boot must print `init: cannot exec /bin/login` at least twice (once is a failure, not a retry) and must never print `uid=0`. The permissive boot must print `uid=0`, which is what makes the strict boot's absence mean anything and is the exact defect: `id` is a standalone-ash applet, so `uid=0` on the console is an unauthenticated root shell and nothing else. A third boot, `RESCUE=1` against the real os-real image, must reach `Kernel debug shell active (rescue mode)`.

### Phase 13: ping, the raw-socket applets, and the freeze

The kernel fix and staging form one commit. Staging `/bin/ping` without the fix hands every SSH user a whole-system freeze, while the kernel fix alone changes nothing a user can reach.

First, fix the freeze. `icmp_ping` (`rach2/sys/network/ip/icmp.c:93`) polls `sti; hlt` at lines 123-126 from inside a syscall, and `timer_handler` skips `schedule()` while `current_proc->in_syscall` (`rach2/kernel.c:138-140`), so nothing else on the machine runs for `ICMP_PING_ATTEMPTS * ICMP_PING_WAIT` = 4 s per unanswered call; `utils/ping.c` issues `PING_COUNT` 4 of them, so `ping 10.0.2.99` freezes every process for about 16 s. Today that is confined to the single-console os-simple image; staging `/bin/ping` into a multi-user os-real would make it a denial of service any SSH user can fire.

The wait becomes a real sleep, and the timeout is carried by the wait predicate rather than by the timer alone. The slot keeps a `ping_deadline` beside its other state; each attempt sets it to `kernel_ticks + ICMP_PING_WAIT`, arms `current_proc->wakeup_tick` from that same word, and blocks in `wq_wait_event` on an ICMP wait queue that `icmp_rx` wakes after it sets `ping_replied`. The predicate is `ping_replied || (int32_t)(kernel_ticks - ping_deadline) >= 0`. Arming `wakeup_tick` alone does not bound the wait. `proc_wake_sleepers` only clears the deadline and marks the process READY (`rach2/sys/proc/process.c:109-119`), and `wq_wait_event` then re-tests its condition and re-enqueues on any wake that is neither the satisfied condition nor a signal (`rach2/sys/proc/wait_queue.c:75-81`, `97-146`). A predicate that reads only `ping_replied` therefore blocks again with its timer disarmed and never wakes. Both parts are required and must read the same word. The armed tick is the scheduling part because `schedule()` never selects a BLOCKED process that nothing wakes. The deadline in the predicate terminates the wait because a fired timer makes the condition true.

A `wq_wait_event_timeout` returning `-ETIMEDOUT` would be the reusable form and is not adopted: it duplicates the interrupt-discipline argument that `wait_queue.c` proves once, for one caller, and `poll.c:152-218` already open-codes its own timed wait rather than growing that primitive. The cost of the predicate form is stated where it matters: `wq_wait_event` returning 0 does not mean the ping was answered, so `icmp_ping` decides reply against expiry by reading `ping_replied`, and the header says so. `wakeup_tick` is cleared on every exit path and between attempts, since a stale arming wakes the process early out of its next unrelated block (`nanosleep` and `poll` both read it). A signal cuts the whole call short: `wq_wait_event` returns `-EINTR`, the remaining attempts are abandoned, and the syscall returns `-EINTR`.

The debug shell keeps the spin. `netping` and `netbad` (`kernel.c:2197`, `2211`) run on `proc_table[0]` with the scheduler disabled once init has exited, so there is no process to block and nothing else to run; `icmp_ping` sleeps when `current_proc && current_proc->in_syscall` and spins with `sti; hlt` otherwise. Both paths share one deadline, one claim, and one release. The file's header block (`icmp.c:10-15`) documents the spin as the contract and is rewritten with the rest.

The sleeping path also makes the slot racy. `ping_active`, `ping_replied`, `ping_seq_wait` and `ping_peer_ip` are one global in-flight request (`icmp.c:36-41`), rewritten unguarded at every attempt (`113-116`). One caller at a time was structural only because the spin could not be preempted; once the pinger sleeps, a second caller overwrites the peer and the sequence under the first, and the first then either matches a reply that is not its own or waits out a deadline for a request nobody is tracking. So the slot gets an owner: claimed under `net_lock` by a test-and-set of `ping_active`, the claiming `process_t *` recorded (NULL for the debug shell), `icmp_rx` matching a reply only against a claimed slot, and the whole slot released under `net_lock` on every exit path, reply, expiry and `-EINTR` alike. A second caller that finds the slot claimed returns `-EBUSY` and sends nothing. It does not queue behind the first: that needs a second wait queue and a fairness rule to give a shell command a wait it cannot see, and the raw-socket non-goal is the reason there is one slot at all. Nothing but `icmp_ping` claims the slot and every path out of `icmp_ping` releases it as its last act, so a killed pinger cannot strand it: the signal makes the blocked process READY, `wq_wait_event` breaks with `-EINTR`, and the release runs before the syscall returns.

`icmp_ping` also stops reporting a timeout as a bare `-1`, which musl's syscall return convention decodes as `EPERM`; it returns `-ETIMEDOUT`, so `-EBUSY` and the timeout reach userland as themselves. All three callers test only `rtt < 0` (`kernel.c` netping and netbad, `tests/pingtest.c`, `utils/ping.c`), so nothing breaks, and `utils/ping.c` starts distinguishing them: a refused claim prints `ping: another ping in flight` and is not counted as a timeout. `PING_COUNT` stays 4, so a ping at a dead address holds the slot for about 16 s and other users are refused for that long. The Readme records that cost of one in-flight request.

The same commit changes staging. `CONFIG_PING`, `CONFIG_PING6`, `CONFIG_FEATURE_FANCY_PING`, `CONFIG_TRACEROUTE`, `CONFIG_TRACEROUTE6` and `CONFIG_ARPING` go off: all of them want `SOCK_RAW` or `AF_PACKET`, `do_socket` accepts neither (`syscall.c:6510`), and busybox's ping dies with `can't create raw socket: Invalid argument`. Our `ping` (the `SC_PING` socketcall, which canonicalizes `127/8`) is staged `0755 /bin/ping` into os-real, which only reaches a bare `ping` because the applet is gone. `utils/resolv.c` reads the flat `/hosts` and `/resolv.conf` while os-real stages `/etc/hosts` and `/etc/resolv.conf`, so it learns to try the `/etc` path first and fall back to the flat root, keeping `dnstest` working against the flat test image; that is the two-location rule phase 11 already gives `adduser`'s exec of the password program. The applet guard grows the raw-socket names.

Proof: `tests/pingtest.c` grows in place, so the probe count stays at 51 and its two existing cases (three gateway replies, one clean timeout) stay as the positive controls. It is freestanding on `int 0x80`, so it reads the raw negative returns the assertions need. Nothing runs it today, so the new assertions would be checked by nothing: `pingtest` is outside `runtests.py`'s `PROBES` (its docstring lists it among the probes run by hand, since it wants the SLIRP gateway), and no make target and no script names it. So the phase adds `make ping-test`, a harness target following the pattern used by phase 9's `test-noentropy`, stated explicitly: `--timeout 120 --ok "PINGTEST OK" "expect=Type 'help'" "send=exec /pingtest" wait=60`, and `pingtest` prints `PINGTEST OK` at the end of a clean run for that check to match. The explicit `wait=` is required. After its last step `harness.py` drains only `--grace`, three seconds, and then kills QEMU, while the existing timeout case alone costs `ICMP_PING_ATTEMPTS` times `ICMP_PING_WAIT` (four seconds) and the additions below add a four-second progress ping and a child the probe requires to live three to eight seconds. Without the wait the token arrives after QEMU is dead and the new check fails on a correct tree. The target joins `make help` and the milestone's check list. Four additions, in one fork round:

* Progress. The parent forks a child that pings 10.0.2.99 and then samples `gettimeofday` in a loop guarded by a `WNOHANG` wait, requiring that the samples taken while the child was still alive span at least 2 s. On the current spin the parent gets no CPU at all for the child's whole 4 s, so its live-window samples span milliseconds and the case fails; this is the assertion the whole kernel change exists for.
* Serialization. The child writes one byte to a pipe immediately before its ping; the parent reads it, sleeps 200 ms so the child is certainly inside the syscall, then issues `SC_PING` to `127.0.0.1` and requires exactly `-EBUSY`. Neither side of the race can score a false pass: if the parent claimed the slot first its loopback ping is answered and the assertion fails, and if it arrives after the claim it gets the `-EBUSY` it asserts. The earlier draft's non-pinging parent could not see this defect at all.
* The bounded timeout. The child exits 0 only when its ping returned exactly `-ETIMEDOUT` and a distinct nonzero code otherwise, so a wrong errno is not scored as a pass; the parent reaps it under a `WIFEXITED` guard and requires the child's whole lifetime to fall between 3 s and 8 s. A lost wakeup fails as a hung probe rather than as a passing one, which the new target's timeout reports as a failure since the token never appears.
* The release. After the reap the parent's own `SC_PING` to `127.0.0.1` must return a non-negative round-trip time, which proves the slot was released and is also the loopback echo's only end-to-end assertion; `loopprobe` does not duplicate it, so only one probe ever touches the global slot.

### Phase 15: zero-length UDP datagrams

The receive slot uses length as occupancy (`socket.h:52`, `recv_len == 0 means empty`), so an empty datagram is built, transmitted, accepted by `udp_rx`, delivered to the right socket, and then dropped at the last step; a blocked `recvfrom` stays blocked. Split occupancy from length across the six sites in `socket.c`: alloc (75), deliver (166), the wait predicate (177), `socket_recv` (223, 234), `socket_try_recv` (253, 268), and `socket_poll` (496). The clear in `socket_recv` already lives inside the `net_lock` region that protects the read-out; it must stay there, or the RX IRQ can deliver a datagram between the copy and the clear and the clear drops it.

Proof: `loopprobe` grows three assertions: a 0-byte `sendto` to our own bound port followed by a blocking `recvfrom` returning exactly 0 with the source reading back as the canonical address and port; a following nonzero datagram intact, proving the slot was cleared; and a `MSG_DONTWAIT` `recvfrom` on the drained socket still `-EAGAIN`, which is the assertion a fix that made the slot unconditionally ready would fail while passing the first two. A hang instead of a pass is also a detection, since the runner reports a probe that never returns.

Readme: `rach2/sys/network/Readme.md` states that a datagram read may now return 0 and that this reaches `read` on a socket fd too; `socket.h`'s comment states the new rule. No in-tree consumer is affected (`resolv.c` treats `n <= 0` as failure, `nc` reads only streams, `udptest` always sends a payload), but that is checked, not assumed.

### Phase 16: the bound local port, and TCP simultaneous open

`do_bind` records `sock->local_port` for a stream socket (`syscall.c:6581`, which runs for both socket types) and `tcp_connect` then discards it and allocates a fresh ephemeral (`tcp.c:682-691`), so a TCP client cannot pin its source port. `tcp_connect` settles the local port first: the bound port when `sock->local_port` is nonzero, the existing ephemeral scan when it is zero. The TCB is allocated after the port is settled rather than before it, so neither scan has to reason about the caller's own half-built block, which is what today's loop assumes (the comment at `tcp.c:677-681` argues from the fresh TCB still holding port 0). A local port already paired with this exact destination, meaning some TCB holds the same local port, remote address and remote port, is refused with `-EADDRINUSE`: `tcp_find` keys on exactly that triple, so a duplicate would deliver one connection's segments to the other. Only an identical triple is refused. A bound port shared with a listener, or with a connection to a different peer, stays legal, because `tcp_find` returns the exact match and falls back to the LISTEN TCB only when there is none. `tcp_connect` therefore returns 0, `-EADDRINUSE`, or `-ENOBUFS` for pool exhaustion instead of a bare `-1`, and `do_connect` returns that verbatim rather than collapsing every failure into `-ECONNREFUSED` (`syscall.c:6774`); the refusal userspace sees for a closed port still comes from the handshake, not from this return.

Listener exclusivity is enforced where the listener is published. `tcp_listen` allocates and publishes a `TCP_LISTEN` TCB without checking the port at all (`tcp.c:633-654`), and `bind` and `listen` are separate syscalls with arbitrary user code between them, so a check that lives only in `do_bind` is bypassed by ordering: `bind(A, P)`, `bind(B, P)`, `listen(A)`, `listen(B)` leaves two LISTEN TCBs on P, and `tcp_find` and `tcp_find_listen_sock` then disagree about which one owns the port, which is the state the refusal exists to prevent. So `tcp_listen` scans for an in-use TCB in `TCP_LISTEN` on the port inside the same `net_lock` region that publishes the new one, before allocating, and returns `-EADDRINUSE`; a full pool returns `-ENOBUFS`; a socket that never bound (`local_port == 0`) returns `-EDESTADDRREQ`, since this stack assigns no port at `listen` and a port-0 listener no segment can ever reach would otherwise be the thing that makes the next one collide. `do_listen` already returns `tcp_listen`'s value verbatim (`syscall.c:6823`), so `listen(2)` reports these instead of the `-1` userspace decodes as `EPERM`, the same defect phase 2 fixes at unlink and rename, and `tcp.h`'s two prototypes stop promising `-1`.

`do_bind`'s stream path keeps a check against the same rule, through an exported `tcp_port_listening` that wraps the same scan under `net_lock`: a program that binds a port used by a live listener learns it at `bind`, which is where httpd and dropbear report it. That check is advisory, and the invariant is `tcp_listen`'s. The scope stays `TCP_LISTEN` and not `tcp_local_port_in_use` (`tcp.c:405`), which counts every in-use TCB including accepted ESTABLISHED connections and 2 s TIME_WAIT remnants (`TCP_2MSL_TICKS` 200); with `do_setsockopt` a total no-op (`syscall.c:7031`), `SO_REUSEADDR` has no effect, so a TCB-wide refusal would make restarting dropbear or httpd after a session fail on `bind(22)`/`bind(80)` where today it succeeds. That same comment's claim that the stack "already reuses listen ports" is corrected here, since a live listener now excludes a second one; what stays true is that a connecting, closing, or TIME_WAIT connection reserves no port.

The state machine also lacks the RFC 793 simultaneous-open sequence. Simultaneous close is implemented twice; simultaneous open is not: a bare SYN in `SYN_SENT` falls out at the first line of that case (`tcp.c:951`) and is dropped. On a SYN with no ACK, record `irs`, set `rcv_nxt` and the peer's window, rewind `snd_nxt` to `iss` before `tcp_send_flags(TCP_SYN | TCP_ACK)` emits at that sequence and re-advances it, and move to `SYN_RCVD`. The rewind is required because: the first SYN left `snd_nxt` at `iss + 1`, `tcp_send_flags` emits at `snd_nxt` and takes `retx_seq` from it, and the peer's answering SYN-ACK acknowledges `iss + 1`, so a SYN-ACK sent at `iss + 1` is acknowledged by nothing, `retx_seq` names a sequence the peer will never confirm, and the connection wedges with `snd_una`, `snd_nxt` and `retx_seq` inconsistent. A SYN-ACK in `SYN_SENT` keeps today's path; a bare ACK stays dropped.

`SYN_RCVD` is now reachable two ways, and two places in `tcp_rx` must tell them apart, so the TCB records which open created it: `tcb_init` clears `passive`, `tcp_rx`'s LISTEN branch sets it on the block it allocates for an incoming SYN (`tcp.c:903-931`), and `tcp_connect` leaves it clear. It is read only in `SYN_RCVD`, where a passive block provably has no descriptor, since the socket a listener made reaches an application only through `socket_tcp_accept`, which runs on the transition to ESTABLISHED.

* Completion. The `SYN_RCVD` case hands the connection to whatever `tcp_find_listen_sock` returns for the port (`tcp.c:944-947`). It dispatches on `passive` instead: a passive block goes to the listener as now, an active one wakes the sleeping `connect` with `socket_tcp_connected`. Dispatching on whether a listener happens to hold the port would queue an active open's socket, which a descriptor already owns, onto an unrelated listener's accept queue whenever a program binds a client to a port something else listens on, which the bind rule above permits. A passive block whose listener has since closed keeps today's behavior.
* Reset. `tcp_rx`'s `TCP_RST` branch treats `TCP_SYN_RCVD` as "the connection never reached the application" and frees both the control block and the socket (`tcp.c:872-878`, `socket_unref` then `tcb_free`). That is correct only while a passive half-open is the sole way into the state. An active open in `SYN_RCVD` is owned by a live descriptor, so the same branch drops a reference the fd still holds, hands the pool slot to the next `socket_alloc` while the fd points at it, and returns without waking the sleeper: a refused simultaneous open becomes a freed socket behind an open file and a `connect` that never returns. The branch splits on `passive`: a passive block is freed exactly as now, an active one takes the same reset treatment as the connected and closing states and is freed by its own `close`. RFC 793 calls a reset in `SYN_RCVD` after a user-initiated open a refused connection, so `so_error` there is `ECONNREFUSED` rather than the `ECONNRESET` that branch's state test would otherwise give it.

The change also prevents an ephemeral self-collision. The ephemeral skip considers local TCB ports, not the destination port, so a dialed loopback port in the ephemeral range that nothing holds can collide with the ephemeral handed out; `tcp_find` then matches the caller's own TCB, the SYN is dropped, and the connect stalls through all seven retransmits before `-ECONNREFUSED`. The collision is rare per attempt and difficult to diagnose.

Proof, all of it in `loopprobe`, which already drives both protocols against the machine itself:

* Listener exclusivity in the ordering a bind-time check cannot see: two sockets bind the same unheld port and both succeed, since `bind` is not exclusive; `listen` on the first returns 0; `listen` on the second returns `-EADDRINUSE`. Then the ordering the earlier draft proved (bind, listen, second bind) still returns `-EADDRINUSE` from `bind`; `listen` on a socket that never bound returns `-EDESTADDRREQ`; and after the first listener is closed the second socket's `listen` on that port returns 0, which proves that the refusal applies only to a live listener. Immediately after `tcp_loop`'s exchange, while that connection's TIME_WAIT remnant is still in the table (2 s, and the probe is microseconds behind the close), a fresh socket binds and listens on `TCP_PORT` and must succeed: that is the assertion that fails if the refusal is ever rescoped to any in-use TCB.
* The bound source port: a client that binds P before connecting to `loopprobe`'s existing listener reports P from `getsockname`, and the accepted socket reports P from `getpeername`. A client that binds nothing still gets an ephemeral at or above 49152.
* The self-connection: bind port P in the ephemeral range, connect to `127.0.0.1:P`, assert connect returns 0 well inside the 20 s step window, that `getsockname` and `getpeername` both report the canonical address and the literal P compared against what the probe asked for, and that a byte written to the fd reads back from it. This case fails today with `-ECONNREFUSED`, promptly: `tcp_connect` discards the bound port, so the SYN reaches an unheld P and draws `tcp_send_rst_unmatched`. The 183 s stall is the rarer variant, when the allocator happens to hand out P itself.
* A two-socket case, because the self-connection is degenerate: with one socket dialing its own port, `irs == iss` and `rcv_nxt == snd_nxt`, so the `snd_nxt` rewind cannot be distinguished from getting it wrong. Two non-blocking sockets, A bound to P1 dialing P2 and B bound to P2 dialing P1, have different ISNs (`tcp_isn` mixes the port pair in order), so the rewind is required. Both connects return `-EINPROGRESS` (`do_connect` supports `OFD_NONBLOCK`), the probe polls both to completion under a bounded timeout, and each end writes a distinct byte the other reads.
* A reset arriving in `SYN_RCVD` on an active open, built out of the loopback ring's order rather than out of luck: A binds P1 and connects to P2, B binds P2 and connects to P1, and the probe closes B before the timer drains the ring. B's TCB is freed in `SYN_SENT`, so the drain pops A's SYN first, finds nothing on P2, and appends a reset behind B's SYN; pops B's SYN, which puts A in `SYN_RCVD` and appends A's SYN-ACK; then pops the reset into A. The probe requires A to report `POLLERR` within a bounded poll and `SO_ERROR` to read `ECONNREFUSED`; on the unsplit branch the socket is freed and nothing is woken, so the poll expires and the probe fails. It then closes A and sweeps for the double free: close the round's own sockets first, since `MAX_FDS` is 16 with three taken by stdio and `MAX_SOCKETS` is 16 shared with every socket the earlier cases still hold, then bind every free descriptor to a distinct port and read each back with `getsockname`. A `-ENOBUFS` from pool exhaustion is a setup failure the probe reports as one, never a pass. A pool slot handed out twice makes one descriptor report another's port, which is the only place a reference dropped at reset time becomes visible.
* The two orderings a timer tick can impose on that construction are recognized, never scored. A tick between the two connects delivers A's SYN to an unheld P2, and A is already in error before the close; a tick between B's connect and the close lets the pair reach ESTABLISHED, and no reset is ever sent. The probe polls A with a zero timeout before the close and checks for the established case after it, closes both fds, and retries the round with a fresh port pair, four times, then fails. The same retry covers the two-socket case, which loses the same race the same way. A round that took either off-path ordering is not counted as the proof.

Readme: `rach2/sys/network/Readme.md` states what makes a local port taken (a live LISTEN TCB, enforced at `listen`, checked early at `bind`, released with the listener), that a connecting or closing connection reserves no port, and neither does TIME_WAIT, so `SO_REUSEADDR` has nothing to reuse; the bound source port and the triple `connect` refuses; that `listen` on a socket that never bound is an error here rather than an ephemeral allocation; that simultaneous open is implemented and a connect to one's own bound port completes as a self-connection; and which kind of half-open a reset in `SYN_RCVD` frees. It keeps the loopback alias stated as a decision with what a program can and cannot observe (a peer that reads back as `10.0.2.15`, so a program cannot use the peer address to decide a connection is local). `tests/Readme.md`'s `loopprobe` entry is rewritten to name what the probe now covers.

Every new probe follows the house pattern, and its registration is five things: the source at `tests/<name>.c` or `tests/musl/<name>.c`, the name in `tests/Makefile` PROGS or the `tests/musl` sweep, the name in `tools/runtests.py` PROBES, an explicit manifest line only where a fixture needs an owner or a mode the `exec-dir` sweep cannot give, and an entry in `tests/Readme.md` with its success token, written in the same commit. A new source is also added by name to `tools/check.sh`'s `newcode_ch` and cppcheck list in the same commit, since those globs reach only `tests/host/` and `tests/*probe.c` and cannot be widened wholesale over the unformatted legacy tree.

The anti-false-pass rules, each one a mistake this tree has already made: exit non-zero on every failed check and never return 0 on a setup failure, since the exit status is all the runner reads; guard every wait with `WIFEXITED` before `WEXITSTATUS`; assert exact errnos and not signs; create and destroy your own fixtures, and snapshot and restore any shared file you must mutate, since all 51 probes share one boot in list order (the four credential-mutating probes sit at the tail, after `musl/suidmusl`, and restore `/etc/passwd`, `/etc/shadow` and `/etc/group` byte-for-byte); prove the negative case by first proving the positive one, so a denial cannot be credited to a fixture staged one bit wrong; and never read a password from `/dev/tty` in a probe, since fd 0 under the debug shell is the console and the read would hang the whole run.

The manual end-to-end tests, all recorded in the milestone record with the exact command lines beside their results, and each shown failing where the failure is the point: the console login (wrong password refused, root admitted, init respawning the prompt, a `0000` `/bin/login` not dropping to a shell, `RESCUE=1` still reaching the debug shell); `passwd` at the os-real prompt as test, followed by an SSH login with the new password and a refusal of the old; `adduser` as root, followed by an SSH login as the new account that reads `/etc/motd`, cannot write it, and is denied `/etc/shadow`; `su` with root's unchanged password, and `su -c 'sleep 100'` suspended and resumed with `fg`; `ping 127.0.0.1` and `ping localhost` with `command -v ping` reporting `/bin/ping`, and a second shell staying responsive while a ping to a dead address runs; the SSH end-to-end test by key and by password with root's password refused; and the power-cycle persistence run on the disk image.

Each phase ends with an independent Codex review of its diff. The chief adjudicates every finding against the code and records confirmed versus refuted; a finding counts only with a concrete failing input or trace. Five phases get a harder read than the rest, because their failure modes are silent: phase 4, where a missed conversion site quietly turns a denial into `-ENOENT` and `do_open` then creates the file, or leaves the whole mutation family unchecked while the probe goes passing; phase 5, where the obvious implementation is an unprivileged clear of a persistent filesystem's crash evidence; phase 8, where a mistake in the release path is a use-after-free in the file system that every later phase runs on top of; phase 9, where a bug in `cred_rewrite` destroys authentication for the whole image and three later phases build on it, read together with phase 8's diff since the two contracts are one; and phase 12, where the failure mode is a box nobody can log into.

## What stays deferred

* Splitting a musl extraction stamp from the musl build stamp. One stamp stays. The split's substantive change is removing `build_libc.sh`'s unconditional `rm -rf` and re-extract, which is also what makes a changed patch reapply to a clean tree; leave it in and ordering `krffs` against an extract stamp lets a parallel build compile `crypt_sha512.c` out of a tree being deleted. The benefit of the split is a bare `make krffs` that skips the libc build, and nothing else, since every image target needs libc anyway.
* A userland `reboot(2)`, and with it a clean unmount from inside the image. It would silence the dirty-flag warning on every disk boot, but it hands a syscall the power to halt the machine and to clear the crash evidence `fsck.krffs` depends on. It needs a privilege check and its own review.
* Moving `KRFFS_MODE_DIRTY` out of the mode word. A v3 on-disk change that would make every existing image read as cleanly unmounted, with coordinated edits in the kernel and two host tools. The node-identity guard makes the collision safe; this would make it unnecessary.
* `/etc/skel`. Not staged, so `adduser` creates an empty home. A convenience with no lesson in it.
* Binding an unlink or a rename to an open descriptor. The credential library resolves every name twice, once to read the lock and once to unlink or rename, and nothing here can tie the second to the file the first saw: there is no `funlink`, no rename that takes a descriptor for its source, and no inode identity to compare, since `st_ino` is a hash of the name. So a release that has just read its own pid out of the lock can still unlink a successor's, if a lock removed by hand is replaced inside that window, and a publish that has just checked the lock still renames by name. The window is one scheduling boundary wide, since a syscall does not yield, and it opens only past the never-break rule; the library narrows it as far as the system-call interface allows (nothing between the read and the unlink, a temporary named for its writer) and says in `pwauth.h` that it is not closed. Closing it is a kernel change of its own, and it would require the same primitive twice over.
* A stop served between the resume check and the read syscall, which costs one character of the next password. The prompt drops the line it has whenever a resume is seen, because a byte typed behind the suspend character in the same burst is returned by a read before the stop is served and must not become a password byte; and it consumes a resume before the read as well as after one, so a stop taken while the modes are set or the prompt written costs nothing. What is left is the few instructions between that check and the `read` itself: a stop there is indistinguishable, afterwards, from one served while the read was outstanding, so the byte in hand is dropped. The cost of that is a whole authentication and not a keystroke, because the prompt takes `ECHO` away and leaves the line discipline canonical: the one-byte read completes only when the user submits the entire line, so the byte discarded is that line's first, the rest of it is consumed as a password missing its first character, and no caller retries (`utils/su.c` prints one refusal and exits). The user runs the command again and types the whole password again. A boolean or a counter checked around the read cannot tell the two apart, and adding another adjacent check only moves the window. Closing it needs an unblock and a wait that are one operation, which is exactly what `ppoll`'s signal mask is for and exactly what this kernel does not do: `sys_ppoll` accepts the argument and does not apply it (`rach2/sys/io/poll.c`), because there is no pending-mask swap primitive. Implementing that swap is a kernel change with its own review, and it would also make `ppoll` apply its documented mask for busybox and dropbear, which pass the argument today and are silently given nothing. The direction of the residue is the safe one: a character typed and echoed before the stop is never accepted as part of a password, and the cost is a retype.
* A lifetime for a directory descriptor. `rmdir` still frees the node under an open directory descriptor and the next use of that descriptor is `-EBADF`. A directory descriptor here is a name, which is what phase 4's search rule rests on, and an orphan directory has no name for a relative path to join; giving it one is the authorized-prefix model this milestone refuses under its own heading.
* Reclaiming an orphan online. A shutdown that does not close descriptors leaves a reserved node that no path references, which costs space and never a wrong answer. The mount reaps it, unconditionally rather than on the dirty flag, since a clean halt closes no descriptors either and checking there would strand the node the moment `fsck.krffs` cleared the flag; `fsck.krffs` reclaims it offline as well. What stays out is reaping one while the system runs, which would need a reaper with nothing to run it: there is no userland `reboot(2)`, and no other moment when the descriptor tables are known to be empty.

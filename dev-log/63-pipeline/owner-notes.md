# The owner's notes on the agent pipeline

The owner wrote these notes on 29 and 30 October 2026, after milestone 62 closed, as three messages to the coordinating session. They are kept as written. Times are UTC+6.

## 29 October, 22:24

OK, after completing a number of phases with our agent pipeline, I have come to the conclusion that most of the assumptions we have collected as software engineers no longer hold in the age of AI and LLMs. Some still work, but they need adjustment.

First, our agentic factory worked well when the tasks were routine and highly parallelizable. Rechecking and rewriting docs and comments was a perfect fit: team members and their agents could work independently on separate tasks and sets of sources, finishing in a single day what would probably have taken a month otherwise.

Still, some adjustments were needed. The first assumption to break was the classic workflow of pull requests and code reviews, which quickly became a major bottleneck. We researched how others handle multi-agent workflows and found that companies like Anthropic have dropped it entirely. Agents merge directly to master, and CI picks up the top commit and runs tests on it without blocking anyone. Commits that land during a run are skipped, and the next run starts from whatever is at the top. We also read that on another project, Anthropic runs only a small random percentage of the tests, deferring full test runs until just before release. We adopted some of these practices, and the doc and comment rewriting phase went very smoothly.

Do you agree? Please check this against the project history to make sure I'm remembering things correctly. Then, after a short answer, let me finish my musings.

However...

## 29 October, 22:45

During the phase where we rewrote the test system, the pipeline we had devised broke down and, for the most part, did not work at all. After a few initial failures, I had to switch to Codex and give it time to work on its own. It did a decent job, though it tended to overengineer things, which I believe was mostly due to our long rule files and bloated agent files. In the end, it could not deliver a full run quickly, wasting time building and rebuilding, then running and rerunning tests over and over. After a few days of struggling, I moved back to you, hoping the pipeline would pick things up and finish quickly. That failed too, so I told you to do most of the work yourself, to ignore many of the checks, assumptions, and rules, and to just plow through to the end of the phase. Only that allowed us to finish more or less on time.

I am not entirely sure why this happened, but here is my best guess. The first part of the phase struggled because many tasks had a lot of dependencies, so many of the team members' agents had to sit idle, waiting for a single agent to finish its task. The test rewrite itself seemed fast, as usual, because multiple agents could work in parallel. Then we got stuck again, because so much depended on long rebuilds and reruns that prevented any parallelism at all. On top of that, team agents without much context seemed to waste a lot of time doing and redoing things: triggering recompilations, misusing support scripts, and breaking things only to fix them again and again, which made the bottlenecks even longer. That is why, I think, a single agent with all the context, and with its tools figured out and adjusted, was able to deliver results in a reasonable amount of time, instead of a bunch of agents running around, stepping on each other's toes, and waiting for one another to make way.

In addition, I believe that engineering practices we assumed were still good in the age of AI, such as running checks of various kinds (code complexity, code style, and so on) over and over, were seriously hurting our velocity. Agents seem either to be trained to write in a particular style, to forget style rules due to context pollution, or, by their nature, to be unable to write code in a required style right away. Whatever the cause, they kept making the same style mistakes, which led to expensive check failures and more rewrites, creating even more bottlenecks and wasting even more time. That is why my instructions toward the end, to stop doing all that or to run the checks automatically as pre-commit hooks, helped speed things up and finish the process. Such checks still matter, but I believe these practices need to be rethought and done differently.

Here is what I now believe should happen in each phase. While the work is in progress, we check nothing, or nearly nothing. We let agents just churn out code at the xhigh thinking level, review it, and maybe compile it (or not even that very often). They write pretty good code that works, or nearly works, 95% of the time. Then, only at the end of the phase (or at a major milestone within it) do we run the full checks, full builds, full test runs, and so on. My controversial idea is that the following should NOT happen during a phase at all: CI running tests while others are writing code, constant checks (docs, comments, style, and so on), rebuilds (even partial ones), and test runs (even partial or selective ones). Agents should be directed to write code and focus on reaching the goal, which is having all the code for the phase (or for an internal milestone) in place. Only then should a single master agent step in, run the full process, and fix things up to make sure everything works.

## 30 October, 00:18

I agree with your "keep the check that takes seconds" point. I also agree that if an agent needs to check hardware behavior, we should let it build and run the system locally, or on the Lenovo from its own account if the machine is free. However, it should skip the tests and run such checks only when they are really necessary.

I disagree with stretches for two reasons. First, I don't give a damn who broke what, and that bisection caused a lot of blocking. Second, I have observed that a single manager who sees the big picture is much faster at putting things together at the end and fixing multiple problems at once. The other agents should not do that; their job is to crap out code at the speed of light. They can afford to, because modern models like Opus 5.5 and Astra 6 are monsters compared to humans. They one-shot giant codebases without running them even once and without a single mistake.

Finally, I am worried that member accounts sit underutilized most of the time. If there is no parallelism within the current phase, I believe we should let agents work on other phases; in other words, we should start running multiple phases at once. We were afraid that large changes touching too many files in one phase would be hard to integrate into another. Once again, we were thinking like humans. Modern LLMs are wizards that can integrate millions of lines of code and put everything together nicely, so we should not be afraid of that.

We should also reconsider how we split tasks. Small, simple tasks are good for humans, but agents end up spending more time on ceremonies (managing the tree, doing configuration management) than on one-shotting the solution in a minute. When splitting work, we should hand out longer tasks, perhaps with many subtasks from the start. On top of that, managers should batch new work more aggressively as it arrives. Likewise, instead of filing a bug or a new task and then wasting time on ceremonies or waiting for another agent to pick it up, agents should be more autonomous and do much more themselves, skipping the usual SWE configuration management routine.

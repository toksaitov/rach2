# Milestone 9: the post-disk audit

The disk milestone and its four follow-up fixes changed about 3700 lines across fifty files. This milestone then audited the tree in four areas: code correctness, comments, documentation, and support files. It checked the new code, checked that the wider changes had not broken existing code, and reconciled comments and Readmes with the implementation. The work used ten risk-ordered phases. In each phase, multiple agents proposed candidate findings, and adversarial verification decided which findings counted. As in milestone 6, most candidates were refuted. Codex independently repeated the high-risk phases, and hardware emulation reproduced the highest-risk finding before the fix.

## What the audit found

The audit refuted every candidate defect in the page cache, the MM-VM and user/window boundary, the block and ATA driver, the KRFFS disk modes, the three recent fixes, and the broader kernel changes. The verifiers traced callers and invariants and used the host tests to check each candidate. The phases found exactly one defect and several outdated comments and documents.

* Phase 1 found one defect: a user-triggerable kernel panic. The page-fault handler's window branch matched only the faulting address and ignored the CPU mode. Because the user segments are flat, any user program could form an address in the page-cache window (`[0xC0000000, 0xC0000000 + window)`) and fault there. The branch preceded the segfault case. On the default RAM boot, which has no disk backing, `pc_fault` returned 0 and the handler panicked. A user program that read `0xC0000000` therefore halted the kernel; with disk backing, it would have looped on the supervisor-only page installed by the fill. A freestanding probe reproduced the defect: the unfixed kernel wedged after the serial log reported the access. The fix requires `!user_mode` for the window branch, so a ring-3 fault in the window reaches the ordinary segfault path while supervisor-mode filesystem access remains unchanged. The manual `winprobe` regression test requires the kernel to kill a process that reads the window rather than service the fault.

* Documentation and comments also required correction. The KRFFS dirty-mount comments overstated the contract: only the debug-shell `halt` or offline `fsck.krffs` clears the bit. A normal boot has no clean-unmount path, as intended for an OS without userland reboot. The CR0.WP comment understated the copy-on-write repair. Six source comments and the `pagecache.h`, `fsync`, and `init_krffs` headers no longer matched the window, mount modes, and GP-register reset. The Readmes still described a RAM-only filesystem. The MM Readme omitted the window branch and page cache, while the kernel Readme's limitations, memory map, source tree, and debug-shell table predated disk support. `make help` omitted the disk-integrity targets. Each owning phase corrected its text. The work also strengthened one host-tool invariant: the KRFFS root node's `parent_id` is stamped with the reserved root ID instead of depending on zeroed backing, so a forced re-mkfs over a nonzero file cannot break root `..` resolution.

## Verification

The required checks passed throughout the work and at its end: `make verify-style` at 8/8, `make verify-host` with twelve host tests, and the module-path `make test` at 28 of 28. A whole-system manual pass exercised every mode under emulation: the default RAM boot; `rach2.fswindow` and `rach2.fsdisk` boots that mount and read KRFFS through the window; the SSH end-to-end test, with public-key login to BusyBox ash over a Dropbear pty, which verifies that musl fork and execve startup survive the exec GP-register reset; Doom from `/` with sound and the framebuffer active; the `os-real-grub-disk` BIOS-to-GRUB-to-kernel disk boot; and `winprobe`, which confirms that a window access now produces a normal segfault that the kernel survives. The vendored trees remained untouched, and the default boot remained byte-identical.

Scoped commits recorded the window-branch segfault fix and probe, KRFFS dirty-bit comments and `parent_id` stamp, recent-fix comment alignment, other comment corrections, Readme and `make help` updates, and explicit support-file dependencies. `plan.md` records the phase concerns.

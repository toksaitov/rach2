## Phase 7, the kernel comments the milestone-53 round did not reach

Six units read `sys/proc`, `sys/mm`, `sys/tty`, `sys/ipc`, `sys/io` and
`sys/input.c` against the code. What they found and what was done with it:

* `elf_check` bounded the program header table with a sum that wraps, and
  never required this kernel's entry size, so the debug shell's `elf` command
  read a table outside the buffer it had loaded. Entry 139 of the shortcomings
  list; fixed and proved by mutation.
* `premap_kernel_window` and `map_mmio` each carried a range check that wraps.
  Entry 140; fixed, unreachable from this tree's callers, and the row is owed
  because nothing host-compiles `mm/paging.c`.
* The idle marker was reported as leaking from a halted process to whoever the
  timer switches to. Rejected. A process becomes runnable only from a state
  that parks it in `idle_wait_irq_off` or `idle_wait_irq_on`, and both clear
  the marker as the process resumes; a process that never halted cannot be
  runnable while another is halted, since the halt happens only when the
  scheduler finds nobody. A row was written and a mutation compiled with the
  reported fix removed: `procprobe` passed on both kernels, which is the same
  answer. The row and the fix were taken out again rather than kept unproved.

The rest of what those six units reported is comment work: headers whose
claims the code no longer keeps, in-body explanations that belong in a header,
and contracts a caller needs that no header states. That is Codex's to write
and is not yet applied.

## The sitting of 2026-09-24

The owner made the Lenovo and the flash drive a sandbox this day: no backup,
restore or hash is taken for their safety, and only the Mac's own disk is
protected. CLAUDE.md says so.

The update from the stick, `rach2-install --update` reading its root image
over USB, was the part of entry 130 still owed to the machine. Its first run
wrote and grew the root and then stopped at `the new root would not mount`:
the write batch asked for 289 contiguous heap pages at a read-write mount,
and after a gigabyte had moved through the cache there was no such run,
though memory was free. That is entry 161, fixed by taking the batch one
page at a time, after which the update ran through on the machine. The
retry that followed had resumed from the archive, which then held no keys,
so the machine came back reachable by password alone; its keys were put
back by hand from its recovery system and its host key was lost. That is
entry 162. Its fix drew three findings in the closing review, one of them
the archive's own replacement window, entry 163, and its suite then found
that KRFFS gave every file of one name the same inode number, so `cp -a` on
the recovery system made every account's key one file, entry 164. A full
set found the probe's boot held to the step limit, entry 165.

With those fixed, the final installer ran its update on the machine from the
rewritten stick, on the normal path: the account files and root's key came
through unchanged and the archive holds `keys/0` and `keys/1000`. The
accepted kernel was then written with `bootctl`, tried and committed.

One failure of the first acceptance set is not explained: after a reboot,
`tests/run make` found three targets out of date that nothing had touched.
It did not recur in three runs of the suite or in the second set. The rows
now print every file's time on both sides of the reboot, and entry 166
holds it open.

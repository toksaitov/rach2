# Milestone 30 notes

Deviations from the plan and defects deferred to later work are recorded here as they are found.

* The `*-test` make targets keep their recipes through phases 3 to 5 because the runner dispatches through them; they become notice-printing aliases in phase 6 when their bodies move to `tests/system/suites/`. Documents that name them (`make ssh-test` and the like in the vendor Readmes and test documents) are renamed to `tests/run` forms in phase 6 with the moves, not before.
* `tools/doctor.sh`, `bootstrap_mac.sh`, and several image scripts still print `make doctor` or reference it in messages; the alias works this milestone, and the remaining mentions move with the scripts in phase 6.
* The grub-test manifest had drifted from os-real: the `/bin/dmesg` line added by an earlier milestone never reached it, unnoticed because the grub suite needed Docker and had not run since. Found by the first native run; fixed in the phase 8 commits.
* Two integration faults in phase 9's own conversions, both found by running the suites rather than by reading the diff. The self-build suite's space preflight and the reproducibility check reached into `check_setid.py` as a module, so converting that file meant giving the C tool `--free` and `--nodes` subcommands to answer them. And the rewritten menu-truncation fragments padded from a literal head length of 35 bytes where the head is 37, which ran two bytes past the slot and destroyed the GRUB environment block behind it; the menu suite caught it on the armed-trial boot. Both padding sites now measure what they wrote.
* The cold build's default time doubled, from the 60 s phase 1 baseline to 119 s, and this is the jobserver change working as intended rather than a regression. At phase 1 each vendor wrapper chose its own `-j`, so a serial-looking `make` was parallel inside the five vendor projects and oversubscribed the machine when the caller did ask for `-j`. The wrappers now join the caller's jobserver, so a plain `make` really is serial and `make -j8` builds cold in 34 s, faster than the baseline. The no-op build fell from 3 s to 1 s. What a reader should take from the three numbers is that the build now does what the caller asked, at whatever parallelism the caller chose.
* The independent review of the six largest new C files returned fifteen defects, four of them able to pass a broken artifact or a failed test. They are fixed in six commits after phase 10, each with a case that fails without its fix. The four serious ones were: `elfcheck` computed `p_vaddr + p_memsz` in 32 bits, so a `PT_LOAD` running past 4 GiB wrapped into low memory and slipped past the overlap and image-end rules; `setidcheck` trusted a node's `data_size` without proving the payload was inside the mapped region, so a header node near the end read past the allocation; `elfcheck` read fields through offset 36 of a section header without requiring the header to be 40 bytes, and passed symbol names to `strncmp` without proving a terminator was in the file; and `runtests` searched for a probe's end marker from the previous probe's position while measuring the window from the current one, so a marker already buffered made the length underflow. The rest were the same fail-open fault repeated: a checker that could not read something reported the same OK as a clean tree. `prosecheck` run from a directory with no `CLAUDE.md` above it printed OK having scanned nothing, and skipped in silence any file over 4 MiB or behind a symbolic link; the harness dropped steps and pattern items past its array bounds instead of stopping; `setidcheck` passed over headers it could not stat and config lines over 512 bytes. Each now says what it did not check and fails.
* A second review, of the fixes themselves, confirmed the four serious ones sound and found seven more, including one regression the first round's fixes introduced. Requiring the probe's end marker to begin a line, to stop a probe forging its own verdict, was wrong: the kernel writes that marker straight to serial with no leading newline, so a probe that dies by signal after printing a partial line leaves it mid-line, and the window would never close. The probe would read as a hang and stop the rest of the suite. The Python had the same two rules and deliberately stripped the `^` from the window-end pattern while keeping it for the score, which is the asymmetry now restored and stated in the code: forging the marker ends a probe's own window early and then scores as no exit reported, so it fails either way. The other six were the fail-open fault again, in places the first round had not reached: the harness left the steps after an early QEMU exit unrun and uncounted, `setidcheck` ignored a failed recursion into a header directory, `guestcheck` passed over sources it could not read while measuring the deepest include chain, where an omission can only shorten it, and appended three expansion tails with an unchecked `snprintf`, and `prosecheck` still printed OK for a named path that does not exist.
* Three changes go beyond restoring the Python's behaviour, and all are recorded here because the milestone's contract was to match it. The harness now fails a run whose steps failed even when the guest went on to exit cleanly: the Python counted step failures only on the `--ok` path, so a suite driven by steps alone could report a pass over a step that never matched. And the harness requires the guest status text to be digits, as the Python's `(-?\d+)` did but the C's `strtol` did not, where any text read as status 0 and passed. A third is the harness counting the steps an early QEMU exit left unrun, which the Python did not; a run that stopped before its checks reached the machine now says so.
* The Python's main-BusyBox config check was already retired upstream: `FORBIDDEN_CONFIG` was an empty tuple, so the loop compared nothing. Only its file-existence check was real, and that one is restored. No forbidden-symbol machinery was carried over, because there are no symbols left to check.
* The prose baseline is regenerated at milestone 30's numbers, and a person should read three movements in it rather than one. The C population grew by about 20000 words because the checkers and runners moved into C from Python and shell; every C phrase count rose with them, and the rise is the same prose counted in a different population. The Markdown population fell by about 45000 words, which has nothing to do with this milestone: milestone 29 rewrote and consolidated the Readmes, and the baseline had not been regenerated since milestone 26. The reference Python implementation, run today, reports the same three populations as the C tool to the word, so the movement is in the tree and not in the reader.

# Milestone 52: the audit

## The goal

Bring the whole tree, not only new code, to one engineering standard, once, after the technical milestones, and deploy the resulting images to the notebook and the stick. Every in-house source is formatted to the one style, compiled clean under a warning set that is recorded with its reasons, checked by the analysers that a serious C project runs, within a size and complexity limit that is measured rather than asserted, and proved by tests whose coverage is known; the parsers that take bytes from a disk or a wire are fuzzed from committed corpora; the kernel is booted with undefined behaviour trapping and at `-O2`, since it is built and tested at `-O0` today; every document says what the code does, the build's rules live where their subject lives, the largest source file is split by interface, and the documents a developer reads have one shape, one voice and no claim the code does not keep. The root Readme says what the project is, what it supports, how to build and run it, and where everything else is. Each component's Readme has the same parts in the same order. History stays in `dev-log/` and nowhere else.

The milestone is complete when the checks below pass on the final tree on the testing host, with the versions of the judges recorded; when every exception to a check is written down with the reason the tool is wrong about that code, and Codex has tried to break each one; when every claim in every Readme has an owner and a Codex round finds nothing stale; when a person new to the tree can find the answer to any question the milestone's own checklist asks in under a minute, or the claim is dropped; when the test set covers the system as it now is, runs in parallel, and its time on the testing host is recorded as the new allowance; when the build has no rule left over from a milestone that no longer needs it; when the whole set of images is on the notebook's disk and the stick carries recovery and the installer; and when the comments in the source and the support files have been read by Codex against the code they describe.

## Decisions

### The judges run on the testing host and their versions are recorded

Every suite, set and analysis runs on the testing host's WSL, as `CLAUDE.md` says; the Mac mini writes and commits. The versions of GCC, clang, clang-format, cppcheck, shellcheck, sparse, pmccabe and QEMU that judged the final tree are in this milestone's Readme. A check whose verdict depends on a tool's major, clang-format above all, is judged by the version recorded and nowhere else; `tools/setup/doctor.sh` reports the version it finds against the one recorded, and the Ubuntu setup builds the same cross-GCC major as the Mac's.

### The trees that decide verdicts are under every check

`tools/`, `tests/system/` and `krffs/` join `inhouse_ch`, the cppcheck list and the strict format set. Their programs are compiled through one `mk/host.mk` that sets `-Wall -Wextra -Werror` and the curated flags, replacing the 29 separate `cc` lines. Their selftests, `elfcheck --selftest`, `setidcheck --selftest`, `cfgcheck --selftest`, `runtests --selftest` and `harness --selftest`, run under ASan and UBSan in the host tier. `utils/` is cross-built against musl and is not a sanitizer target; its pure parts already run under ASan through the host tests that link them.

### One format, the whole tree

Every in-house C file is reformatted to `.clang-format` once, in one text-only commit per component, and the strict format check then covers the whole in-house set; the advisory tier ends. The proof that a reformat changed nothing is the built objects identical after `objcopy --strip-debug`, since `-g` moves line tables, and the suites unchanged. The reformat commits are listed in `.git-blame-ignore-revs`. `.clang-format` allows 100 columns and aligns trailing comments while the comment rule is 80 columns; `prosecheck columns` runs between the reformat and its commit. Formatting is never in a commit with a semantic change.

### The dialect is checked in seconds

`-Wpedantic -Wno-long-long` joins the kernel's flags: it is the mechanical form of the rule that the kernel stays inside the dialect GCC and TinyCC share, answered at compile time where `tests/run selfbuild` answers in minutes. The one site it reports is fixed. sparse is wired with `__CHECKER__` defined so the address-space annotations the tree already carries are checked, in the fast suite.

### The warning set is curated, recorded, and fixed rather than cast away

The eleven zero-debt flags join `-Werror` at once. The debt flags are added one at a time, each with its sites fixed in a commit of its own; the fix is the type or the declaration, not a cast. `-Wconversion` and `-Wsign-conversion` are triaged once by hand: a flag whose sites are mostly casts is rejected. Every rejected flag is recorded in `mk/` beside the flag list with the reason. The inventory is taken with `i686-elf-gcc -Q --help=warning`, not the host compiler. clang runs `-fsyntax-only` over the kernel with a short positive list, `-Wcast-align`, `-Wconditional-uninitialized`, `-Wshadow-all`, `-Wtypedef-redefinition`, `-Wcomma`, as a second front end in the fast suite; `-Weverything` is an exploration run once, whose useful flags are added to that list by name.

### The analysers see the kernel's allocation and its panic

`k_panic` is declared `noreturn`; `kmalloc` and `kzalloc` carry `__attribute__((malloc, malloc(kfree)))` behind a macro that is empty for compilers that do not know it, TinyCC among them. Then `-fanalyzer` runs over the kernel and the guest programs behind `make analyze`, with `-Wanalyzer-too-complex` on so the paths it abandons are reported rather than silently green. cppcheck runs at `--enable=warning,style,performance,portability` in the fast suite and at `--check-level=exhaustive` behind `make analyze`; dead code is found by the linker, `-ffunction-sections -Wl,--gc-sections,--print-gc-sections`, which honours assembly references, and not by `unusedFunction`. clang-tidy runs behind `make analyze` with `bugprone-*` and `misc-*` and reports cognitive complexity; it is advisory, not a gate, and `clang-analyzer-*` and `cert-*` are not enabled, being the third path analyser and aliases of the first two. Each analyser has its own compilation database, generated per component and per kernel variant after the build phase has removed the parse-time writes, and a run fails when a source in the tree is missing from the set it analysed.

### The kernel is proved with checks on

A UBSan-trap kernel, `-fsanitize=undefined -fsanitize-undefined-trap-on-error`, is built as a component in the way the harness kernel is, and boots through the core tier: undefined behaviour becomes `ud2` and the `#UD` handler panics with the address. One `-O2` kernel boots through the same tier at the close, and the four null-dereference sites `-O2` exposes are fixed before it. `-Wframe-larger-than=` joins the kernel's flags at a bound the owner sets against the 16 KiB stack, with `-fstack-usage` reported per function and the deepest interrupt-nested chain read by hand once.

### The parsers are fuzzed early, from committed corpora

libFuzzer harnesses live under `tests/fuzz/`, one per parser, in this order: the ELF loader, the packet path, MBR, GPT, then KRFFS, FAT, exFAT and ext2. A filesystem harness copies a small seed volume from the fixture makers into a devmodel, then mounts, walks the root, reads every file and unmounts, under ASan, with `-timeout` and `-rss_limit_mb`. A checksummed format has its checksum recomputed after mutation, or every input dies at the header check and the fuzzer reports no crash without entering the parser; the harness is rejected if libFuzzer's coverage line stops growing. The corpora are committed under `tests/fuzz/corpus/` and replayed in the host tier in seconds through a standalone `main` that needs no libFuzzer; the long runs are behind a variable and happen at the close. Every crash becomes an entry and its minimised input a regression test. The harnesses are built and proved small before the structural changes, and the corpora are rerun after them.

### Coverage is an inventory, not a score

The host tier is built with `--coverage` and `gcov`, which on the Mac is `llvm-cov` printing the same summary, reports line and branch coverage per file for the files the host tests name, through a project-owned shell script, and never a project-wide number. It is advisory. It is used to choose the next test from an uncovered branch and to notice the drop when a case is removed. It is never called kernel coverage: the host tier substitutes the allocator and the string routines and runs at 64 bits, and the kernel's proof is a boot. Once the host is Ubuntu, the tier runs at `-m32` with a 32-bit sanitizer runtime so the machine's arithmetic width is the one tested.

### The large file is split, and then the limits land

`syscall.c` is divided along the lines it already has, process, file system, network and ABI arms, with no semantic change, proved by the suites, the guest build and the source checks passing unchanged. The split is mandatory: the size limit below cannot land while the file exists. After it, the limits: cyclomatic complexity at most 25 per function, measured by `pmccabe`, which prints a table the check reads and the ratchet is kept on; functions at most 100 lines, parameters at most 6, nesting at most 4, checked by a small in-house checker in the shape of `prosecheck.c`; file length is reported and not limited, since a teaching tree keeps its explanations beside its code. The dispatchers that remain above the limit, a linear hardware sequence or a state machine, are written into a reasons file with why a split would make them worse, and are not contorted to satisfy a number. The limits ratchet down once the distribution has moved, by the owner's decision, not by default.

### An exception is defended, never convenient

Fixing is the default. A suppression is per line and per check and carries the finding, why the tool is wrong about that code, and the source or test that shows it; "false positive" alone is not a reason. A check category that is excluded is recorded separately from individual exceptions, with its reason, and the two are not mixed. A check lands red first: nothing is suppressed in the commit that adds it. No check is weakened, no assertion loosened and no suite narrowed to make a run pass; a wrong check is fixed or removed with the reason written. At the close, Codex receives every exception with the instruction to break it, and each one it breaks becomes a fix. A check is credited only when a mutation of the code makes it fail.

### Every remaining bound is classified

Find and classify every remaining capacity limit in the kernel, the tools, the image builders and the procedures: physical, format or ABI, policy and configurable, or safety invariant, each with its reason beside it. A bound that is none of those is unfinished work, and unfinished work is an entry in milestone 50's list, fixed before this milestone's documents are accepted; there is no next plan. A tool's own limit that obstructed milestone 46 or 47 was lifted there, not saved for here. An old helper or document that still imposes a limit the kernel no longer has is the fault this phase exists to find, and the inventory is reviewed by a person, not produced by a new checker.

### A suite asserts on what the kernel counts, never on the clock

The set has failed on every new machine it met, and between reruns on the same one, for one reason: pass criteria that are times, and synchronization that is waiting. A row that says "under 200 ms", "within three seconds", "at least five by then" or "the least of three runs" states a probability, and the owner has watched it lose ten times; the diskrate rework of 2026-09-18 replaced seconds with multiples of a measured baseline, which narrows the odds and does not remove them. The inventory on that day: twelve probes with a time in a pass criterion (`ahciprobe` 200 and 60 ms, `conloadprobe` 3 s, `lagprobe` windows of 1.2, 5 to 6.9 and 4.5 to 6.9 s and 80 ms floors, `loadprobe` latency ceilings of 0.2, 5 and 1 s, `loopprobe` a factor and a slack, `timeprobe` 130 ms and 2 s, `pingtest` 3 to 8 s and 2 s, and the rest completion loops), nineteen suites that `sleep` for synchronization, one hundred and thirty-three numeric thresholds in the suites to classify, the SSH flood's "five connections", and a runner that calls a silent hour a hang. Under KVM on the testing host eight suites failed on these and on two kernel faults the emulator hides.

The standard: time is never a pass criterion and never a synchronization. What a timed row was a proxy for is counted by the kernel and asserted exactly. A spin or a wait in a driver is polls per command and ticks slept per request, counters in the block layer and the drivers. A reader not held behind a slow disk is its completion ordered before the slow one's and the completion count on the controller's vector. A deadline is the kernel's tick on the log line, released on the same tick as the quarantine. Console input under load is bytes drained through the interrupt against the tick, which `/proc/stat` already counts. A sleep's correctness is ticks, not milliseconds, and its lower bound is exact. A flood is the count the server reports, equal, not a floor. A round trip that must not wait for the timer is fewer ticks than round trips. Where a proxy has no counter, the counter is added to the kernel and read through `/proc`, and the expected value is recorded from the emulator and from KVM, both on the testing host, in the suite beside the assertion. A suite waits for a token the guest prints, never a number of seconds, and never stops a machine on one line to read the next from its log. Time survives only as the run's end: generous, scaled, and a failure to be explained, never a pass. The runner tells a slow machine from a hung one by the machine's own activity, processor time and output both static, not by silence.

The standard is enforced, not remembered: the style suite rejects a `sleep` with a number in a suite, a `wait=` step in a harness line, and a millisecond constant compared in a probe, unless the line carries a reason the checker knows (`# interval:` for a deliberate load interval), and the reasons file lists each. Pooled suites share nothing: every image, socket, port, fixture and temporary carries the suite's name and the builder's process number, and the inventory of what each suite touches is checked against the others', because the second cause of the recurring races is two suites in one pool reaching one file. A suite is done when it has passed on the emulator and under KVM on the testing host and its counts are recorded from both.

No suite runs alone. The runner's lone list, `usb`, `diskrate`, `install` and `imagerace`, exists because those four cannot stand a loaded host, and a suite that cannot stand load is one whose criteria are times: `usb` waits for the emulator's monitor to answer, `diskrate` measured seconds, `install` builds under a completion bound, and `imagerace` touches the shared images. Each is made to stand in the pool by removing what made it fragile, `usb` by waiting for the guest's own report of a device's arrival and removal, `diskrate` by keeping only its counts, `install` by having no time criterion, `imagerace` by mutating targets of its own, and the list is then deleted from the runner so it cannot fill again.

### Nothing moves that does not have to

The top-level layout stays: kernel, utilities, shell, file-system tools, vendor ports, build fragments, tests. Correct stale statements, remove duplication and put each build rule in its owning component. No directory is renamed and no file is moved for tidiness alone.

### Image rules go to the build, not the tests

Every rule that makes a product, the stick images among them, moves into a build fragment under `mk/`; `suites.mk` keeps only what a suite needs. The rule is that no recipe under `tests/` makes a product, while a test may depend on one. The fingerprint's purge, and the files it writes while Make parses, become an explicit step a build runs.

### An inventory of claims before a word is rewritten

Every Readme is read against the tree and each claim gets an owner and an evidence type: a file and function for what code does; a measured record under `dev-log/` for a hardware fact; a build rule or the doctor script for a prerequisite; `CLAUDE.md` for a policy. A claim with none is removed or made true. A claim two documents make is made once and linked from the other. The inventory is a file in this milestone's directory and the rewrite is done from it.

### Four kinds of document, each with a fixed shape

The root Readme: purpose, what it supports, quick start, limits, and a map. The administration prose is split by what it is: the general procedures are the manual pages milestone 51 wrote; the measured facts of the one installed machine, its identity, geometry and offsets, stay in the milestone records under `dev-log/`; the root Readme keeps a short section that points to both, and `CLAUDE.md`'s Hardware section, which today sends an operator to the root Readme, is updated in the same commit. The kernel Readme: an architectural map, one paragraph per subsystem with a link. A component Readme: what it owns, its interface, its invariants, what it does on failure, and what proves it, in that order, then, where the component has one, how it is built and ported; what is excluded is history, not current instructions. The `dev-log/` records are history and are not rewritten to describe today.

### Inventories are generated

Generate repeated inventories and counts, the suites, the programs, the system calls, from their registries with the tool that already reads them. Remove lists that do not need to be repeated. No new tool is written for a list that appears once.

### Codex writes the documents from the inventory, and reads the comments

The claim inventory is the input: for each document, its shape and its claims with their owners. Codex writes each document from that, in units of six, and what comes back is checked here claim by claim before it is committed. Codex also reads every comment in the source and the support files against the code beside it, in the same units, and reports the ones that are stale, that narrate, or that use the register `CLAUDE.md` forbids; those are fixed here.

### The test set is made lean and the build is made clean

Every suite is listed with what it proves and how long it runs; a suite that proves what another proves is merged or removed; the new hardware arrangements, memory sizes, two disks, two controllers, two cards, get rows in existing suites where they fit and new suites only where they do not, and two suites of one subsystem with different failure modes are not duplicates; the tiers are rebalanced so the core tier still answers in the time it did. The runner today serialises style, host, USB, USB disk, sealed and mount work (`tests/run:167`) and budgets workers by processor alone; it gets a worker budget and a memory budget, since the memory matrix boots at 4 GiB, isolated artifacts per worker, console parsing that does not mistake one suite's output for another's, and deadlines sized to the row. The allowed time for the full set is measured once on the testing host at the start of this milestone and recorded in this milestone's Readme with the worker count; the set at the close takes no longer than that plus a quarter. The fast style suite stays about a minute: the curated flags, `-Wpedantic`, the clang list, sparse, the size checker and the cppcheck category change cost seconds; clang-tidy, `-fanalyzer`, exhaustive cppcheck, the long fuzz runs and the instrumented kernels are behind `make analyze` and the close. Every rule in the build is listed with its owner; a rule with none, or one kept for a milestone that ended, goes; and the result is proved by an incremental rebuild after a header, a manifest and a configuration change, by two concurrent invocations, and by the built artifacts' contents compared with the clean build's.

### The images go to the machine and the stick

The last act of the milestone is the deployment: the stick rebuilt with recovery and the installer, booted on the notebook and shown to work; the notebook's images updated through the update procedure milestone 49 wrote, under the hardware rule, since the installation was proved in QEMU in milestone 49 and on the Lenovo in milestone 50, and installed again only if the installer changed after milestone 50; the demo checked on the machine.

## Phases

The order is the reviewers': the build first, because the analysers need a compilation database it cannot produce today; the judges and the unchecked trees second, so that what follows is judged by recorded versions over the whole tree; the reformat third, so every later diff is readable; the warnings, the dialect and the analysers fourth, before any restructuring, so the restructuring is told what it must preserve; the checked kernels and the fuzzers fifth, so the corpora exist before the split and are rerun after it; the split and its limits sixth; then the test set, the bounds and the documents as before.

### Phase 1: the build

Product rules out of `suites.mk`; the purge and the parse-time writes made an explicit step; the root Makefile's duplicated declarations and stale comments removed; `mk/host.mk` written and the 29 host compile lines moved onto it; the compilation databases generated per component and per kernel variant, with a check that every source in the tree is in one. Proof: `make -n` and an inspection target run with a changed fingerprint and shown to delete nothing, a flag change within one second rebuilt, a parallel build, an incremental rebuild after a header, a manifest and a configuration change, two concurrent invocations, a check that no recipe under `tests/` names a product, and the database check failing when a source is removed from it; the clean build and the full set come at the close.

## Risks

* Moving build rules can break a suite's expectations of where an artifact is; each move runs the suites that name the artifact.
* Keep each extraction free of unrelated changes. The body comparison detects edits within functions; review and tests must also check headers, macros and linkage. Warning fixes change bodies the comparison relies on: they come before the split or after it, never between two extractions.
* A reformat commit that changes a byte of an object is not a reformat; it is read by hand before it is kept.
* A green analyser over an incomplete source set, a green fuzz run whose inputs never pass a checksum, and a green coverage number for code whose proof is a boot are the three ways this milestone can report more than it proved; each phase's proof names the mutation that shows the check is live.
* Two hosts judge with two tool majors until the versions are recorded; a verdict that differs between them is a finding about the check, not about the code.
* The size limits will argue for splitting a function that is one linear hardware sequence; the reasons file exists so that it is not done.
* Check each rewritten claim against its recorded evidence before committing it.
* Include a tool Readme in the pilot to check that the shape fits tools as well as subsystems.

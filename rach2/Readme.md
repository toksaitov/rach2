# Rach2 kernel

![Rach2 showing a kernel panic](https://raw.githubusercontent.com/rachmiroff/images/refs/heads/main/rach2/bsod.png)

Rach2 is a freestanding 32-bit x86 kernel. It boots through Multiboot or multiboot2, runs statically linked ELF32 programs, the 32-bit Executable and Linkable Format, in ring 3, the processor's user privilege level, implements a Linux i386-style `int 0x80` interface, and schedules isolated processes preemptively, each with its own floating-point state. Its KRFFS root can come from a Multiboot module or an ATA, AHCI or NVMe disk.

The [root Readme](../Readme.md) describes the complete system and its userland. This file owns the kernel-level build, boot, and debugging contract. The subsystem Readmes own their implementation details.

## Build

Run ordinary builds from the repository root:

```sh
make -C rach2          # build build/rach2/kernel only
make                   # build everything, including the three RAM images
make rach2-metal       # build/rach2-metal/kernel, with ATA and AHCI writes refused
make rach2-recovery    # build/rach2-recovery/kernel, with whole-disk authority
tests/run selfbuild    # build the kernel twice on Rach2 and compare the results
```

By default, the host Makefile compiles the kernel as freestanding C89 with `i686-elf-gcc` and links it at 1 MiB with `i686-elf-ld`. It links no C library or libgcc. `make -C rach2 ARCH=x86_64` builds the x86-64 kernel with the `x86_64-elf` cross tools into `build/x86_64/rach2/kernel`, linked at `KVA_IMAGE` plus its physical address from 1 MiB and loaded through its Multiboot header's a.out kludge, and `make ARCH=x86_64` builds its programs and images under `build/x86_64/`; `qemu-system-x86_64 -cpu max -kernel build/x86_64/rach2/kernel -initrd build/x86_64/images/os-real.krffs` boots it. Every host link runs the project ELF validator (`tools/inspect/elfcheck.c`, `--kernel`) before replacing the previous kernel, against the x86-64 kernel's profile for an ELF64 file. The link writes the kernel with its debug sections to `kernel.debug` and strips them from `kernel`, the file every loader, boot slot and stick carries: they are half of the linked file, and a boot partition's kernel slot holds 2 MiB. GDB reads `kernel.debug`.

`C_SRC` and `ASM_SRC` in `sources.mk` are explicit source lists, included by both the host `Makefile` and `guest.mk`, the POSIX makefile that pdpmake and TinyCC use on Rach2, so one file describes both builds. `make check-sources` checks the C list against the tree, and `tools/verify/guestcheck.c` checks the guest derivation and limits. Host objects and dependency files are under `build/rach2/`; the guest build writes into its writable copy of the source tree.

The metal and recovery kernels use separate component names and object trees. A configuration fingerprint under each tree rebuilds it automatically when the resolved compiler options change, so one tree never mixes objects from two option sets.

## Architecture

The loader headers and the entry point are in `sys/arch/i686/loader.s`; `sys/arch/i686/link.ld` places the GNU-linked image at physical address `0x00100000`. Each processor has its own flat global descriptor table (GDT) with ring-0 and ring-3 code and data segments, a task state segment (TSS), which holds the stack an entry to the kernel switches to, a `%gs` segment for the running thread's thread-local storage, a second TSS for the double fault, and a segment over the processor's own record, which every entry to the kernel loads into `%fs` and from which `arch_cpu_id()` reads the processor's index. The interrupt descriptor table (IDT) contains the 32 CPU exceptions, the sixteen interrupt lines at vectors 32 to 47, line N at vector 32 + N whichever controller delivers it, 16 vectors at 48 to 63 for messages from PCI devices, the local APIC's spurious vector at 255, and the user-callable system-call gate at vector `0x80`. The tick runs at 100 Hz.

Both kernels carry a Multiboot header and a multiboot2 header in their `loader.s`, and either loader starts them the same way: in 32-bit protected mode with paging off, its magic in EAX and its information in EBX. `k_main` (`sys/arch/x86/boot.c`) tells the two forms apart by the magic and reads either into one boot record, `struct boot_info` in `sys/boot.h`, through `sys/arch/x86/mbinfo.c`: the command line, the loader's name, the memory map, the modules with their command lines, ACPI's RSDP and the framebuffer. The shared boot reads the record alone; its memory map keeps Multiboot's form of entry, which `sys/mm/frame.c` walks. The record keeps its own copies of what it points at, in the kernel image, since the loader's memory goes to the frame allocator: up to 128 memory-map entries, 8 modules and a command line of 511 bytes. Under UEFI a multiboot2 loader passes the firmware's EFI memory map beside its own, and the record takes the EFI one, the firmware's at the exit from its boot services, with the memory the loader and the boot services held counted as usable and ACPI's tables and NVS, the runtime services and memory-mapped I/O kept out. The kernel calls no UEFI service: GRUB leaves the boot services before it jumps to the kernel, and the firmware's framebuffer and memory map are what the kernel takes from it. QEMU's `-kernel` reads the Multiboot header, through the a.out kludge for the x86-64 kernel, whose multiboot2 header gives its load and entry addresses in tags in the same way, since its ELF entry lies in the top 2 GiB. The log says which form and firmware it was: `boot: loader: GRUB 2.12-1ubuntu7.3, by multiboot2 on UEFI`.

GRUB starts the kernel by multiboot2 from a GPT disk, whose BIOS core and EFI image have that loader, and from an ISO under UEFI; the MBR disk's core and the ISO's El Torito image have only the Multiboot loader, and their menus use it (`tools/image/mkdisk_grub.sh`, `tools/image/mkiso.sh`). The multiboot2 header asks for a framebuffer, of any size and depth, and accepts the VGA's text mode. GRUB sets a framebuffer unless `gfxpayload` says text after the command that loads the kernel, and the disk's menu says text on the PC platform, so a machine booted by BIOS keeps the text mode, which fills its screen, and one booted by UEFI, which has no text mode, takes the firmware's framebuffer.

A CPU exception never ends in a silent reset (`init_isr` in `sys/arch/x86/isr.c`): one a program raises in user mode becomes its signal, and one in kernel mode that the kernel does not resolve, as it resolves a page fault on a lazy user page, prints a diagnostic and panics. Each kernel stack is 16 KiB with an unmapped page below it, but those the boot allocator gives the threads of the debug shell's `switch`, `preempt` and `isolate` exercises. A fork's comes from the kernel heap with its guard page (`kstack_alloc` in `sys/syscall_proc.c`), and the boot stack, which the boot, process 0, the debug shell, the first program and the programs the debug shell starts run on, has the page below it in the kernel image, which the boot unmaps once paging is on. The boot stack is never given back, not even when a thread of a program on it calls `execve` and the leader's record, whose stack it is, goes. A thread that runs its stack past the base faults at the first access to that page, and since the page fault's own frame would be pushed into the same page, the processor raises a double fault. Vector 8 has a task gate: the processor saves the state it faulted in into the kernel's TSS and starts `isr_double_fault` from the double fault's TSS, with the kernel's page directory, on a stack of its own, where an interrupt gate would have run on the exhausted stack, faulted a third time and reset the machine. It prints `isr: kernel exception: double fault (vector 8, eip X, esp Y): pid N ran past the end of its kernel stack at A` and stops with `panic: stopped: double fault: a kernel stack ran out`; a double fault with any other cause prints its instruction and stack pointers and CR2 and stops as other kernel exceptions do. A page fault in the guard that is delivered, which needs room for its frame above the guard, stops with `page fault: a kernel stack ran out`. The guard is one page, so a single frame near the 4096-byte bound of `mk/warnings.mk` that leaves its lowest bytes unwritten can step past it.

The boot reads ACPI's tables once paging is on (`sys/arch/x86/acpi.c`), from the RSDP the boot record gives (`acpi_rsdp` in `sys/boot.h`, the kernel's copy of the one a multiboot2 loader passes in its tag 14 or 15) or else from the first kibibyte of the extended BIOS data area and 0xE0000 to 0xFFFFF: the RSDT, or the XSDT where the RSDP has one; the MADT's processors, I/O APICs, interrupt source overrides and NMI inputs; the FADT's PM1 control registers, PM timer, reset register, boot flags and century register; the HPET's address; the MCFG's configuration windows; and the sleep types of `\_S5`, found by a search of the DSDT's bytes for the name and the package after it. There is no AML interpreter, so nothing else the DSDT says is known. Every table is reached through `map_mmio` and read only after its length and checksum pass; one that fails is logged as `acpi: SIG at ADDR: why, ignored` and left out. The facts go into one record (`acpi_get`), and the log says what was found: `acpi: tables: rsdt at ADDR, revision N, OEM: FACP APIC HPET ...`, then a line each for the MADT, the FADT, `\_S5`, the HPET and the MCFG. With a window for PCI segment 0 the configuration functions reach the buses behind it through ECAM, mapped for the buses the bridges reach and at most 32 of them, and configuration mechanism #1 serves the rest (`sys/arch/x86/pciconf.c`); `pci_read_config32_ext` reads the extended space, offsets 256 to 4095, that only ECAM reaches.

The interrupt controllers are one of two arrangements, chosen once by `platform_timer_start` (`sys/arch/x86/platform.c`). The local APIC is enabled in either, because a message from a PCI device is a write to its page. `sys/arch/x86/lapic.c` leaves it disabled, says in the log which of these it found, and the kernel then has no message vectors: a processor with no APIC, one without the model-specific registers, one in x2APIC mode, an APIC base this kernel cannot reach or map, and a machine booted with `rach2.nomsi`.

When the MADT lists an I/O APIC, the local APIC is in use and `noapic` is not on the boot line, the I/O APIC takes lines 0 to 15 (`sys/arch/x86/ioapic.c`) and the 8259 pair is masked for good. A line goes to the global system interrupt that the MADT's override for it gives, with the override's polarity and trigger, or to the input of its own number, edge-triggered and active high, as an ISA line is; line 2 has no input when line 0's override takes it. A line given in a PCI function's interrupt line register is level-triggered, active low unless its override gives a polarity: SeaBIOS and OVMF route each PCI interrupt pin to one of the ISA lines and set the register to it. That is the limit of the routing. Without an AML interpreter the `_PRT` is not read, so a device without MSI whose interrupt reaches only the I/O APIC's inputs above 15, as a PCH routes a PIRQ the firmware left off the ISA lines, is not served by its interrupt, and its driver's timer servicing is all it has. Every input starts masked and is unmasked when a handler is registered on its vector, and goes to the processor the kernel booted on; an input a device asserts that nothing here clears, the SCI's, stays masked (`pic_mask_irq` keeps it so). An I/O APIC input drops an edge that comes while it is masked, where the 8259 kept it in its request register, and the 8042 raises no new edge while a byte waits for a read; so after the PS/2 keyboard's and mouse's handlers go on, a byte already waiting is taken by raising the vector once. `LINT0` is masked, and `LINT1` is the NMI input the MADT gives. The tick is the local APIC's timer, periodic on vector 32, measured at boot against the HPET, against the ACPI PM timer when there is no HPET, or against the 8254 when there is neither (`sys/arch/x86/apictimer.c`, `sys/arch/x86/refclock.c`); the log says `lapic: tick: N counts, measured against the hpet`. A timer that cannot be measured, or that does not tick within 50 ms, gives way to the 8254 through the I/O APIC; one that does not tick logs `lapic: timer: no tick in 50 ms; the pit ticks instead`. The measurement and the timer's start work on the running processor's own APIC, for each processor to make. The end of an interrupt through the I/O APIC is the local APIC's, sent after the handler chain, since a level-triggered line is still asserted until its handler quiets the device; the tick's is sent first, because the tick's handler may switch processes before it returns.

Otherwise, with no MADT, no I/O APIC, `noapic`, or the local APIC refused, the 8259 pair delivers the lines and the 8254 ticks, through the local APIC's `LINT0` as an external interrupt when the APIC is enabled, which is the state firmware leaves and which `lapic.c` restores if it finds anything else. Straight after the tick starts, the boot checks that the 8259's interrupts still arrive; `lapic: timer: no tick in 50 ms; writing lint0 again` says they did not and that `LINT0` was written a second time, and a line after it says whether that worked.

A machine with no 8254, which some UEFI-only machines are, is found by reading channel 0's counter (`pit_probe`), and the short waits of `k_udelay` are then measured by the HPET or the PM timer. The AHCI and NVMe controllers take a message vector on the same terms as the other devices and poll without one. `/proc/interrupts` says which vectors have taken interrupts, where each came from (`PIC` through the 8259, `IO-APIC` through the I/O APIC, `LAPIC` for the local APIC's timer, `MSI` for a device's message) and under what names (see [synthetic file systems](sys/fs/synthfs.Readme.md)), and `/proc/stat`'s `intr` line is every interrupt the kernel has routed. The xHCI takes its interrupts as messages when the APIC is enabled and the controller's capability allows; otherwise it uses its PCI line through whichever controller has the lines. The timer pumps it every tick in either case, so a lost interrupt does not stop service; see [USB](sys/usb/Readme.md). The HDA audio controller enables messages under the same conditions and retains its legacy interrupt handler and timer servicing. Each driver calls `isr_alloc_vector`, which returns the lowest unallocated vector from 48 through 63, so the assignments depend on the order in which the drivers request them. Each successful enable reports `messages on vector N` in the boot log. Once an interrupt has arrived, `/proc/interrupts` lists the vector with its handler name, `xhci` or `hda`.

The kernel builds its physical-memory map from the boot record's memory map using 64-bit arithmetic and manages every usable whole frame below its architecture's reach after boot reservations: 4 GiB on i686, whose physical addresses are 32 bits, and on x86-64 all the memory the firmware reports, up to its direct map's 64 TiB, the frame table placed at the top of memory. On i686 only the first 32 MiB is identity-mapped, and on x86-64 all of memory is mapped at `0xFFFF800000000000`; on both the first 32 MiB is the DMA pool, below 4 GiB, which a device without 64-bit addresses is given. The kernel heap's region is 256 MiB on i686, and on x86-64 an eighth of the memory, 256 MiB at the least and 512 GiB at the most; the buffer cache stops at half of it. Device memory-mapped I/O (MMIO) is mapped into the kernel's region beginning at `0xF0000000` on i686 and `0xFFFFC08000000000` on x86-64. Process records are allocated from the kernel heap without a fixed count. Each process's descriptor table grows from 16 entries to a limit of 1024. A user address space is a set of virtual memory areas, ranges with their own permissions and backing, whose pages are allocated or read in on the fault that first touches them. It has copy-on-write fork, a growing stack, and shared supervisor-only kernel mappings. See [memory management](sys/mm/Readme.md).

Programs use Linux i386 system-call numbers and register arguments through `int 0x80`. The kernel returns negative errno values. The timer preempts the running process at every tick: at once when it is in user mode, the idle loop or a kernel thread, and at the call's exit when it is inside a system call, so a process that is always inside one still gives way. A device's interrupt requests preemption the same way. A wait-queue wake gives the sleeper one preferred selection before ordinary round-robin service resumes. At least every second selection is ordinary, and a preferred selection leaves the ordinary cursor unchanged, so repeated wakeups cannot stop the rotation. Both selections consider only READY processes, and while a suspend to idle holds the processes (`sys/proc/suspend.c`), which a privileged write of `freeze` or `mem` to `/sys/power/state` starts, only the writer, which waits until a wake event, the clock's alarm interrupt or a key, counts one; the interrupts are taken meanwhile and the clocks count on. Neither selection reads the nice value `setpriority` keeps, and no disk queue reads the I/O priority `ioprio_set` keeps; the scheduling calls report this as the one policy, `SCHED_OTHER` at priority 0. `sched_setaffinity` binds a process to a set of the started processors, and `sched_getaffinity` returns it; `getcpu` returns the processor the caller runs on; and `sched_yield` puts the caller behind the other READY processes. Selection and the context switch run with interrupts masked; each resumed caller recovers its own interrupt flag. The tick is also the CPU-time accounting: it is charged to the thread it interrupts, as user time when that thread was in ring 3 and as system time when it was in the kernel, and to no thread when the processor was idle; a process's time is its threads', and a reap adds a child's times to its parent's children's totals, which `times`, `getrusage`, the resource usage `wait4` returns and `/proc/<pid>/stat` report. Project programs are static i386 `ET_EXEC` files; `execve` also loads position-independent `ET_DYN` programs and the dynamic linker a `PT_INTERP` segment names, maps their `PT_LOAD` segments and creates a System V i386 initial stack with arguments, environment, and auxiliary-vector entries. The arguments and environment are sized as Linux sizes them: with the program's path and a pointer for each string, they may take a quarter of the soft `RLIMIT_STACK`, at least 128 KiB and at most 6 MiB, and one string may take 128 KiB. `execve` builds the whole new image, the stack's pages among them, in an address space of its own while the old one still runs, so a vector past a limit, a malformed segment or a lack of memory is an error the caller sees and survives, and the stack spans as many pages as the strings need. The loader keeps its program headers on the calling process's kernel stack, so an exec that sleeps on disk I/O cannot have its headers overwritten by another exec. An address space is counted: `vfork`, and `clone` with `CLONE_VM`, give the child the parent's own, and a `vfork` parent waits until the child calls `execve` or ends.

The kernel runs on every processor the MADT lists that is enabled, up to 64, or on as many as `maxcpus=N` allows, the boot processor counted (`sys/proc/smp.c`, `sys/arch/x86/smpboot.c`). Before the first program, the boot processor makes each one an idle task and starts the others one at a time, through INIT and two startup messages: each runs its architecture's `trampoline.s`, copied to the page at 0x8000, into protected mode and on x86-64 into long mode with the boot processor's control registers, loads a GDT and TSS of its own and the shared IDT, enables its local APIC with the MADT's NMI inputs, starts its tick at the count the boot processor measured, and waits in its idle task. A machine whose local APIC does not tick, or whose memory map does not give the trampoline's pages as free, runs on one processor, and the log says why; the log ends the start with `smp: processors: N online of M`. One lock covers the kernel. Every entry to it, a system call, a fault or an interrupt, takes the lock, again when the processor holds it, and every return gives it back; an idle wait lets it go for the halt, so user code runs on every processor at once and kernel code on one at a time, and the sections that turn interrupts off for exclusion stay correct as written. The run queues, the wait queues, the timers (`sys/io/timerfd.c`) and the console have spinlocks of their own as well, taken after the big lock; the console's is taken again by the processor that holds it, so that a panic raised inside the console still prints. Each ready process is on one processor's queue: a woken process joins the processor it last ran on, unless that one is busy and another it may run on is idle; a processor with nothing of its own to run takes a process from the busiest queue, and with nothing there runs its idle task, which halts until an interrupt, so a process that blocks or ends always leaves its processor. A wake that puts a process on an idle processor's queue sends that processor an interprocessor interrupt, which ends its halt. A change to a user page's entry in an address space other processors run has each of them drop its translation by the same interrupt, and waits for them; a change to a kernel mapping has every other processor drop all its translations before it next takes the lock. A panic, a power off and a reset stop the other processors by the same interrupt first. The boot processor alone keeps time and runs the kernel's timers; every processor's tick accounts its own time and preempts.

A process is a group of threads (`sys/proc/tgroup.h`), each a process record of its own with its own id, registers, TLS base, blocked mask and pending signals, scheduled like any other record. `clone` with `CLONE_THREAD` adds one to the caller's process; the threads share the address space, the dispositions, the signals sent to the process, the parent, and the process's end. A thread's `exit` ends it alone, `exit_group` and a fatal signal end them all, and the process ends, and its parent is told, with its last thread; the thread whose id is the process id keeps its record until then, and the others' records are freed at the next return to user mode. An `execve` in one thread first ends the others. `CLONE_FILES` shares the caller's descriptor table, a counted record the process records point to (`fs/fd.h`), and an `execve` gives a caller that shares its table a copy of its own as it commits, in storage it took before, so one that fails leaves the caller in the shared table. `CLONE_FS` shares the working directory, the root directory and the file-creation mask, which another counted record has (`struct fs_struct` in `sys/proc/process.h`); `fork` copies both records. An `execve` by a caller without effective uid 0 ignores a program's set-id bits while the caller shares these three with another process, and while one that applies them runs, `clone` with `CLONE_FS` by a thread that shares them fails with `EAGAIN`.

Normal exit and signal death release the process's files, working directory and root directory, and let a parent waiting in `vfork` run, before publishing its zombie state and notifying the parent. An exec that fails returns an error to its caller. File and cwd release may sleep on a mount lock before publication. After publication the caller must not block or permit interrupt preemption before its final schedule, because the parent can then reap its record and kernel stack. Every thread's end, a normal exit and a death by signal alike, drops its address space and clears `cr3` before it releases its files and publishes the zombie, as Linux's `exit_mm` does, so an ended process's memory and program's file go before its parent reaps it; a death by signal writes its core file first. An address space is freed with its last user, so one another thread or a `vfork` parent shares stays. A wait that reaps a zombie returns after the descriptor-table allocation, record and kernel stack have been reclaimed; `waitid` with `WNOWAIT` reports one and leaves it for a later wait.

Each boot initializes the architecture, memory, timer, RTC, entropy, input, process, audio, storage, file-system, terminal, and network layers, then runs the built-in kernel self-tests. A normal boot starts `/sbin/init` as PID 1. If that init later dies, the kernel halts. A mounted image without `/sbin/init`, such as the test image, enters the kernel debug shell instead.

`clock_gettime` reads Linux's clocks 0 to 7 and a CPU clock of any process by id, as `clock_gettime(2)` lists them. The four clocks of time since boot are one clock: they snapshot the uptime seconds and the ticks within that second with interrupts masked, and so keep 10 ms resolution across the 32-bit tick counter's wrap at about 497 days. A tick the timer did not deliver because interrupts were off is counted at the next one, from the time-stamp counter, on bare hardware whose TSC runs at one rate (`timer_calibrate` in `sys/arch/x86/pit.c`); elsewhere it is lost, and these clocks fall behind by it. Real time adds the place within the tick of the counter under it, the local APIC timer's count or the 8254's, to the microsecond, and its coarse form does not. The CPU clocks read the ticks the timer charged. `clock_nanosleep` sleeps on time since boot, boot time, real time and the CPU clocks; an absolute sleep ends at the first tick whose count reaches its time. The syscall's signed 32-bit seconds field limits monotonic time to about 68 years since boot.

Opening `/fb` acquires the display for the calling process and enters VGA mode 13h. Framebuffer mode and palette ioctls reject a descriptor held by another process with `EBUSY`, including one inherited by fork or retained after releasing the display. `FB_MODE_TEXT` releases ownership; `FB_MODE_13H` reacquires an unowned display and restores graphics mode. A repeated graphics request by the owner preserves the current image and palette.

## Root selection

The kernel accepts one root:

* With no root option, it mounts the first Multiboot module in place. Changes affect the boot-time copy and disappear when the machine stops.
* `rach2.fsdisk` and `rach2.root=disk` scan disk 0's first four entries, of an MBR or a GUID table, and mount its KRFFS partition through the write-back page cache.
* `rach2.fswindow` mounts the Multiboot module through the page-cache window. This is a development path for the cache rather than a persistent disk.
* `rach2.root=SPEC` selects a partition across all registered disks. SPEC may be `PARTUUID=GUID` for a GPT partition's 36-character GUID, `MBRID=XXXXXXXX,M` for an eight-digit hexadecimal MBR disk identifier and partition number, `GPTID=GUID,M` for a GUID table's 36-character disk GUID and partition number, `UUID=UUID` for an ext2 volume UUID, `LABEL=NAME` for a GPT partition name or ext2 volume label, or `/dev/diskNpM` for a node selected directly during recovery. UUID comparison ignores letter case. Exactly one partition must match; an absent or ambiguous identity is logged and leaves no root mounted. `rach2.rootfstype=krffs` or `rach2.rootfstype=ext2` selects the file system, with other values refused by name. Without it, the kernel checks for KRFFS first and then ext2. KRFFS uses the page-cache window with the disk-root limits; ext2 uses the buffer cache.
* `rach2.root=ext2` scans disk 0's first four entries, of an MBR or a GUID table, for the first ext2 partition the driver can mount and mounts it as the root through the buffer cache, checked before a writable mount when it was not unmounted, as [ext2.Readme.md](sys/fs/ext2.Readme.md) describes. The KRFFS module is not tried in its place.

The root is mounted before the USB stack starts, so a root is a Multiboot module or a partition of the disk the block layer found, and never a stick. An orderly stop writes an ext2 root's buffers and sets its valid bit when the mount was writable, its error bit clear and those writes succeeded; otherwise the next mount checks it.

After root mounting, `ahci_start` enables queued requests unless `rach2.ahcipoll` is present, the local APIC is unavailable, no interrupt vector is free, or the controller cannot enable message-signalled interrupts (MSI). It allocates a vector with `isr_alloc_vector`, registers the handler as `ahci`, enables MSI with `pci_msi_enable`, enables D2H Register FIS and fatal-error interrupts in each disk's `PxIE`, and sets `GHC.IE`. Each disk clears `BLOCK_FAULT_SAFE` and gains `submit`, while retaining its polled transfer functions. Success logs `ahci: interrupts: messages on vector N, K disks queued`; unavailable vectors or MSI log the reason as `ahci: polled: ...`. Once an interrupt has arrived, `/proc/interrupts` lists the MSI vector as `ahci`. `ahci_interrupts()` returns the controller's message count.

`nvme_start` follows it and moves each NVMe controller's namespaces the same way, unless `rach2.nvmepoll` is present, the local APIC is unavailable, no vector is free, or the controller has neither MSI-X nor MSI. It registers the handler as `nvme` and programs entry 0 of the controller's MSI-X table with `pci_msix_enable`, or MSI with `pci_msi_enable` when there is no MSI-X table. Success logs `nvme: interrupts: messages on vector N, msi-x, K disks queued`, with `msi` in place of `msi-x` for MSI; a controller that keeps polling logs the reason as `nvme: polled: ...`. `nvme_interrupts()` returns the messages counted.

A boot with no mounted root halts unless `rach2.rescue` was requested. The kernel also halts before mounting when `rach2.nodisk` is combined with a disk root, unless rescue mode was requested, because skipping the disk would otherwise expose an unauthenticated shell after the root failed to mount.

The page cache writes dirty pages on eviction, `fsync`, `sync`, and an orderly stop. A disk root sets a dirty-mount flag while mounted and clears it only after a successful final flush. See [block storage](sys/block/Readme.md) and [KRFFS](sys/fs/Readme.md).

## Running QEMU

Build from the repository root, then run the scripts from `rach2/`:

```sh
make
cd rach2
./run.sh os-simple              # RAM root, /sbin/init, console login
RESCUE=1 ./run.sh os-simple     # same root, kernel debug shell
RESCUE=1 ./run.sh               # kernel with no root, kernel debug shell
./run.sh test                   # init-less test image, kernel debug shell
```

The stick image boots through the emulator's firmware with no kernel given, the way a machine boots from a USB socket:

```sh
qemu-system-i386 -cpu max -device qemu-xhci,id=xhci \
    -drive if=none,id=stick,format=raw,file=../build/images/rach2-stick.img \
    -device usb-storage,bus=xhci.0,drive=stick,bootindex=0
```

GRUB loads the metal kernel and its RAM root off the stick. With no other disk registered, the kernel names the stick `disk0`, and `mount -t exfat /dev/disk0p2 /mnt` mounts its second partition. On a machine with other disks, use the stick's number from `/proc/usb`.

`run.sh` defaults to `-cpu max`, the PC speaker, an RTL8139 device, and QEMU's SLIRP network. Its second argument selects `speaker`, `sb16`, or `hda`. `CPU` overrides the CPU model, `NIC` selects `rtl8139` or `e1000`, and `NET_HOSTFWD` replaces the default `8080` to guest port `80` forwarding rule. `NET=off` omits the script's explicit network options; QEMU then supplies its default e1000 and SLIRP network, which the kernel drives.

For a persistent disk root:

```sh
make os-real-disk
cd rach2
DISK=../build/images/os-real.disk ./run.sh
DISK=../build/images/os-real.disk DISKBUS=ahci ./run.sh
```

`DISKNOMOUNT=1` attaches `DISK` without adding a disk-root option. Use it with `RESCUE=1` for raw disk diagnostics.

The other run scripts cover the two bootloader paths:

```sh
make os-simple-iso
(cd rach2 && ./run_from_iso.sh os-simple)

make os-real-grub-disk
(cd rach2 && ./run_from_disk.sh)
```

The ISO path boots GRUB from a CD image. `run_from_disk.sh` boots BIOS, the disk's boot code, and GRUB's BIOS core in its BIOS boot partition without QEMU's `-kernel` or `-initrd` options, on the disk `make os-real-grub-disk` builds, `build/images/os-real-grub.disk`, or `os-real-grub-with-key.disk` in a tree with a recovery key: the os-real system as an ext2 root on the third partition of a GUID table, with the boot and recovery partitions before it, which is the layout a machine has; UEFI firmware, OVMF under QEMU, boots the same disk through GRUB's EFI image on the boot partition. To stop at the first instruction and attach GDB, build the kernel and run `./debug.sh` from `rach2/`.

## Messages

The kernel writes diagnostics with `klog` and the debug shell's own output with `console_putc` and its two relatives. Which of the two a message uses is decided by who it is for.

A diagnostic is a record. `klog(level, subsystem, format, ...)` builds one whole line and offers it to four destinations in a fixed order:

```text
<3>[12.34] ahci: command: timed out on port 0
```

The angle brackets give the level and the square brackets the uptime in seconds and hundredths; the rest is the `subsystem: event: detail` shape every message in this tree uses. The prefix is the form BusyBox's `klogd` reads, so a userland log reader can be added later without the kernel changing what it writes.

The five levels are syslog's numbers: `KLOG_CRIT` 2, `KLOG_ERR` 3, `KLOG_WARN` 4, `KLOG_INFO` 6 and `KLOG_DEBUG` 7. The destinations, in the order a record reaches them:

| Order | Destination | Takes | Notes |
|-------|-------------|-------|-------|
| 1 | The 16 KiB ring | every level | Written before the three below, so a port or a wire that fails does not stop the machine's own copy. Whole records are evicted, so it never begins mid-line. |
| 2 | The screen | `INFO` and more urgent | Without the prefix and the timestamp, which a person in front of the machine does not need. Coloured by level. |
| 3 | COM1 | every level | Through a transmit wait with a bound, so a UART that never drains delays the caller and does not stop it. |
| 4 | Netconsole | every level | Offered every record, enabled or not. It holds what it cannot send in an 8 KiB ring and sends once netconsole is enabled and a device answers; a full ring drops the newest character and counts it. The records worth having on the wire are the early ones. |

A record is built whole before any destination sees it, and a newline inside its text is kept as a space, so one record is one line and the ring can evict by finding the next newline. A record too long for its 256-byte buffer ends in `...` before that newline.

The three destinations past the ring write byte by byte with interrupts as the caller had them, so a record raised by an interrupt handler in the middle of one being written out would put its bytes inside the other's line. Such a record goes to the ring where it is raised and waits in a queue of eight for the three past it; the delivery it interrupted writes the queue out, in order, once its own record is finished. A ninth record reaches the ring like the rest and goes no further, and the count of what the three past the ring did not get is printed when the queue is empty. Keeping it in the ring alone would keep it off the port, which is how a device could be unplugged while the machine was printing and nothing on the wire said so.

## Input

Two kinds of keyboard produce keystrokes: the PS/2 one on the 8042, and a USB one through the HID class driver. They agree on a set-1 scancode, because that is what the PS/2 hardware sends and what a program reading the raw ring expects, so the USB side translates its own usage codes instead of the rest of the kernel handling a second code set. `sys/input.c` is where a code goes after that: the modifier state, the interception of Ctrl+C where the debug shell is the supervisor, the scrollback keys, and the choice between the terminal's line discipline and the shell's own buffer. Each driver keeps only what is particular to its hardware.

The same is true of the two mice: one queue, which a program reads through the `mouse` device, and no way for it to learn which kind of mouse moved.

COM1's received bytes are taken by the port's interrupt, IRQ 4, into a ring of 4096 bytes in `sys/arch/x86/serial.c`, and by the timer tick as well, so a port whose interrupt is not enabled is still served every ten milliseconds. What runs after either service depends on who owns the console: a reader parked on it is woken and drains the ring itself, echoing what it takes when the ring held no more than 64 bytes, a person's typing or a short paste, and silently when it held a flood, since an echo waits on the transmitter with interrupts off; a session that owns the console with nobody reading has its bytes moved into the line discipline at once, without echo, so an interrupt character reaches the foreground group and type-ahead waits for the next read; and when no session owns the console the bytes stay in the ring for the kernel debug shell, which polls it. The kernel's own path drops nothing and counts what the hardware does: the ring stops taking from the UART when it is full and masks the interrupt until a reader has made room, and the discipline is filled only while it has room for a whole line, so a sender faster than the reader finds the UART's FIFO full, which is what tells an emulator to wait and what a real sender overruns, and the overrun is counted. A partial line typed in canonical mode joins the queue, behind what was committed before it, when a program switches the console to raw mode; before, it stayed in the line buffer and was lost, which is how a shell returning from a job lost the first characters of a line typed under load. A signal character typed behind input the discipline has no room for is still delivered: it would have discarded that input anyway, so the bytes before it are discarded and it is fed. `/proc/console` has the counters of this path, from the UART to the readers: what the port gave, the overruns, the services run from the interrupt and from the tick, the reader's drains, the times the ring was full and the most it held, what the kernel's own polls took, what the discipline dropped from a full line or a full queue, what a signal or a flush discarded, what a switch to raw mode made readable from a partial line, what readers got, and the most the queue and the line held. `tests/run conload` types 360 numbered, checksummed lines at a loaded machine and requires every one.

The modifier state is one and not one per keyboard, so two keyboards plugged in at once share a shift. This kernel drives one at a time in practice.

The debug shell's prompts, menus and command output are not diagnostics. They go to the screen and to COM1 through `console_putc`, `console_puts` and `console_printf`, and not to the log ring or the wire. `console_putc`, `console_puts` and `console_printf` write to the screen and COM1 and nowhere else: they are not in the machine's log, and they are not broadcast, because netconsole carries the log to whoever is on the segment and a person typing at a prompt did not agree to that.

## Debug shell

The debug shell is the supervisor for rescue boots and mounted images without `/sbin/init`. It is not authenticated. A normal os-simple or os-real boot runs init and login instead.

The commands are grouped here by purpose:

* Inspection: `help`, `info`, `modules`, `test`, and `clear`.
* Mounted KRFFS: `ls`, `cat`, `touch`, `rm`, `mv`, and `write`.
* Programs: `elf` inspects an executable; `exec <file> [args...]` runs one as a transient init process.
* Storage: `disk` reads and dumps sector 0; `ahci` re-probes AHCI and reads LBA 0. `disk write` is a destructive last-sector round trip available only in the recovery build. It does not write the last sector when one of the MBR's four entries covers it, or when LBA 1 or the last sector begins with the GPT signature `EFI PART`, since a GPT disk has its backup header there.
* Kernel exercises: `switch`, `preempt`, `isolate`, `usermode`, `netping`, `netbad`, and the `audio` command family.
* Stops: `halt`, `poweroff`, and `reboot` flush the mounted disk root before stopping. `fault` deliberately panics the kernel. A power off writes the sleep types of `\_S5` with SLP_EN to the FADT's PM1a and PM1b control registers, asking the firmware into ACPI mode first when SCI_EN is clear, and logs `poweroff: acpi: sleep types A and B`; where the tables give no `\_S5`, or the machine is still running after it, the board profile of `sys/arch/x86/board.c` is tried, and then QEMU's PIIX4. A restart writes the FADT's reset register where the FADT says it has one, then tries three mechanisms in turn, the one that resets most of the machine first: the firmware's own reset command, the chipset reset register, then the keyboard controller's pulse. The firmware's command is sent only where the firmware's SMBIOS table names the firmware that command belongs to; on every other machine it is skipped with the name that was read instead.

The VGA text console keeps scrollback. In the debug shell `PageUp`, `PageDown`, `Home`, and `End` move through it; in a login session, where those keys go to the program as the escape sequences of the `rach2` terminfo entry, `Shift+PageUp` and `Shift+PageDown` do. Typing returns to the live screen. Each byte of live output is one write to the adapter's memory, and a scroll moves the display's start address and clears the new bottom row rather than rewriting the screen, since that memory is slow on hardware and a trapped access under a hypervisor. Once every 180 scrolls the window would pass the end of that memory, and the twenty-four rows that stay are copied to its front. The console interprets the escape sequences of the `rach2` entry, draws UTF-8 text from a font with code page 437's box drawing and the Cyrillic letters, which it loads into the adapter at boot, and answers a program's query for the device attributes or the cursor position on its input, as `console(4)` describes. COM1 carries the same boot and shell output to QEMU's `-serial stdio` path.

When the boot record has a framebuffer of direct color, or of 8-bit indexed color, the console draws on it instead (`sys/display/fbcon.c`): `fbcon_init` takes it before the shared boot starts and logs `console: framebuffer: 1280x800, 32 bits a pixel; the font at 1x`. The driver above keeps its scrollback, its window through 32 KiB of cells and its cursor as it does on the adapter, and the framebuffer console keeps those cells, the start address and the cursor in place of the adapter's and draws what they select: the 80x25 cells centered on the screen, each glyph of `sys/display/vga_font.c` eight pixels by sixteen, or twice that on a screen 2000 pixels wide or more, in the VGA's sixteen text colors, with the cursor as the two lines at the foot of its cell. The font there is the whole of it, ASCII and the box drawing as well as the letters the adapter loads, since a framebuffer has no font of its own. A cell is drawn only when it shows something new, since each of its pixels is a store to the display's memory; a scroll draws the lines that moved and leaves a blank cell under a blank one alone. The framebuffer is reached through its physical address until the kernel's page tables are in force and through an uncached mapping in the MMIO region after, which `fbcon_window` in `sys/arch/x86/boot.c` makes the first time the console draws; one above 4 GiB is not reached, and the screen stays as the loader left it. The cells stay 80x25 on a screen of any size, the size the console's terminal reports and the `rach2` terminfo entry describes, so that nothing above the console's interface changes. `/fb`'s mode 13h needs a VGA, which a machine booted by UEFI may not have, so on a framebuffer console it changes the device's state and leaves the hardware alone, and its picture reaches no screen; a framebuffer for programs is later work.

## The subsystems

One paragraph per subsystem, with the document that owns it. Each names the files it is in, so this section is the map from a question to the place it is answered.

The entry and the tables are `sys/arch/i686/loader.s`, `sys/arch/i686/link.ld`, `kernel.c`, `sys/arch/i686/`, `sys/arch/x86/isr*`, `sys/arch/x86/acpi*`, `sys/arch/x86/pic*`, `sys/arch/x86/ioapic*`, `sys/arch/x86/lapic*`, `sys/arch/x86/apictimer*`, `sys/arch/x86/refclock*` and `sys/arch/x86/pit*`: the Multiboot header and the kernel stack, the link layout at 1 MiB, the boot sequence and its self-tests, the handoff to init, the debug shell, the descriptor tables, ACPI's tables, the interrupt controllers and the tick the Architecture section above describes. This Readme owns them, [acpi(4)](../man/man4/acpi.4) gives what a program sees of them, and [the architectures' Readme](sys/arch/Readme.md) describes `sys/arch/`, what each architecture defines for the shared code and what a port adds.

Processes are `sys/proc/`: process records, the round-robin scheduler with a run queue for each processor, each processor's record (`percpu.h`), which has the process it runs, `current_proc`, its idle task, the page directory it translates through, its depth in the big lock and its idle, busy and user ticks, the big lock, the requests one processor leaves another and the start of the processors (`smp.c`), the ELF loader, the initial user image, wait queues, and the floating-point state each process keeps. [Signals](sys/proc/signal.Readme.md) owns the dispositions, the masks and the delivery frame, and [thread-local storage](sys/arch/i686/tls.Readme.md) the `%gs` base musl's startup asks for.

The floating-point state is `sys/fpu.h`, with the PC's formats in `sys/arch/x86/fpu.c`, and this Readme owns it. `schedule` saves the outgoing process's registers into its area and loads the incoming one's at every switch, `fork` copies the live registers into the child's, and `execve` starts a program with the initial state: control word 0x37F, MXCSR 0x1F80 and every register zero. The kernel computes in none of these registers. Where `cpuid` reports XSAVE, the kernel sets CR4.OSXSAVE and XCR0 to x87, SSE, AVX where the processor has it, and AVX-512's opmask and ZMM components where it has all three and AVX512F, so a program sees OSXSAVE and may use those instructions; the area is the standard-format XSAVE image of those components, as large as leaf 0xD of `cpuid` says (832 bytes with AVX, 2688 with AVX-512 in Intel's layout), and `xsave` and `xrstor`, `xsave64` and `xrstor64` on x86-64, move it. `xsave` writes every component its mask names, where `xsaveopt` and `xsavec` would skip or move the ones in their initial state, so the area is always a whole image that the signal frame, ptrace and a core file copy as it is. Without XSAVE, or under `rach2.noxsave`, `fxsave` keeps the x87 and SSE state in 512 bytes, and on i686 under `rach2.nofxsr` `fnsave` keeps the x87 state alone. Each area comes from the heap at a 64-byte boundary, sized at boot, and the record points at it. The log says which format the boot chose: `fpu: fxsr: on, sse: on, xsave: on, xcr0: 0x7, area: 832 bytes`. Programs see the state as Linux's: in the signal frame, the XSAVE image marked by `FP_XSTATE_MAGIC1` and `FP_XSTATE_MAGIC2` ([sigaction(2)](../man/man2/sigaction.2)); through `PTRACE_GETREGSET` with `NT_X86_XSTATE` ([ptrace(2)](../man/man2/ptrace.2)); and in a core file's `NT_X86_XSTATE` note ([core(5)](../man/man5/core.5)).

Memory is `sys/mm/`, described by [its Readme](sys/mm/Readme.md): the physical frame map built from the firmware's, the kernel's own virtual layout above 3 GiB with a heap that frees, per-process page tables, virtual memory areas, copy-on-write fork, demand paging, the checked user-pointer boundary, and the disk page cache.

Files are `sys/fs/`, described by [its Readme](sys/fs/Readme.md) for KRFFS and the descriptors and by [vfs.Readme.md](sys/fs/vfs.Readme.md) for the mount table, the resolver and the buffer cache. The four types `mount(2)` places have documents of their own: [KRFFS](sys/fs/krffs.Readme.md), [FAT32](sys/fs/fat32.Readme.md), [exFAT](sys/fs/exfat.Readme.md) and [ext2](sys/fs/ext2.Readme.md). [Synthetic files](sys/fs/synthfs.Readme.md) owns `/dev` and `/proc`, which are generated from kernel state and stored nowhere.

Block storage is `sys/block/`, described by [its Readme](sys/block/Readme.md): the ATA, AHCI and NVMe drivers behind one interface, the block request with its deadlines and its pool, MBR and GUID partition tables, the loop device over a file, a stick as a disk, the raw windows, the disk registry, and the read-only and recovery build switches.

USB is `sys/usb/`, described by [its Readme](sys/usb/Readme.md): the xHCI controller driver, the device core and its enumeration state machine, and the three class drivers: the boot-protocol keyboard and mouse, the hub, and mass storage. One pump drains the event ring, from the controller's interrupt and from the timer.

Networking is `sys/network/`, described by [its Readme](sys/network/Readme.md): the RTL8139, e1000 and RTL8168GU drivers, Ethernet, ARP, IPv4, ICMP, UDP and TCP, the socket interface behind `socketcall`, packet and raw sockets, and the broadcast netconsole.

Terminals and pipes are `sys/tty/`, `sys/ipc/` and `sys/io/`, the last two described by [the pipe Readme](sys/ipc/Readme.md) and [the readiness Readme](sys/io/Readme.md). `sys/tty/` implements the line discipline, job control and pseudo-terminals. Canonical reads return at most one completed line, retain the received VEOL byte, and preserve a nonempty VEOF line's boundary before later input. Boundaries are stored with queued bytes and survive changes to VEOL. Closing a PTY master releases every blocked slave reader; queued input drains first, then each read returns EOF, including nonblocking reads. The slave wait checks master closure as well as discipline readiness. `tty_hangup` only sets a marker after queued input and wakes readers; canonical reads consume that marker once, so the endpoint maintains persistent hangup state. A PTY master uses one wait queue for readers, writers and pollers. Slave reads, input flushes, termios changes, and input the master writes that takes bytes out of the slave's discipline, a signal character's flush or an erase, wake it to recheck input space; writes wake it for queued output or echo even when a later user copy fails. Each wake names its kind of change for an edge-triggered epoll registration: room for the first four, and data for output or echo, or none when input written with echo off, or echo the full ring dropped, left the master nothing new to read; input written to the master wakes the slave's queue for data. A slave writer feeds the master's ring only what fits at the most its output processing can make of it, eight bytes a byte, and waits on the slave's queue while it is full; a master read wakes that queue with room, so no output is lost, as on Linux. A writer holds the pair for its whole write (`writing` in `struct pty`), and another waits on the same queue until it ends, so one write is not cut by another's, as Linux's `atomic_write_lock` keeps it. The console's readiness checks pump input with interrupts disabled, including the USB latency-recording check. `sys/input.c` routes keystrokes as the Input section describes.

The devices and the platform are `sys/display/`, `sys/audio/`, `sys/arch/x86/ps2kbd*`, `sys/arch/x86/ps2mouse*`, `sys/arch/x86/speaker*`, `sys/arch/x86/board*`, `sys/arch/x86/power*`, `sys/arch/x86/pciconf*`, `sys/arch/x86/cmos*` and `sys/arch/x86/serial*`: VGA text, the framebuffer console and mode 13h, Sound Blaster 16, Intel HD Audio and the PC speaker, the PS/2 keyboard and mouse, the board power profiles, the shutdown paths, PCI discovery, the clock and COM1. The [audio Readme](sys/audio/Readme.md) defines PCM rate selection, HDA routing and the SSH diagnostic. The Messages, Input and Debug shell sections above describe the other devices.

The log and the library are `sys/klog*` and `sys/lib/`: one record and its four destinations, described under Messages, and the freestanding integer, string, character, signal, user-ABI and text-formatting support every other file rests on. [The random generator](sys/lib/krandom.Readme.md) is its own document.

## Hardware and limits

The kernel currently supports:

* Multiboot through QEMU's direct kernel loader, and multiboot2 or Multiboot through GRUB by BIOS or UEFI firmware; under UEFI GRUB leaves the firmware's boot services before the kernel starts.
* VGA text mode, a text console on the loader's framebuffer, and Mode 13h graphics.
* PS/2 keyboard and mouse input, and USB keyboards, mice and flash drives through xHCI, on a root port or behind a hub.
* COM1 serial input and output.
* Polled ATA PIO on both channels and both drives with LBA28 and LBA48; AHCI disks; and NVMe namespaces on an admin queue and one I/O queue pair, with MSI-X or MSI. AHCI and NVMe take interrupt-driven request queues and keep a polled path for boot and page faults. Disks carry MBR or GUID partition tables.
* RTL8139, Intel 82540EM (e1000), and RTL8168GU Ethernet devices.
* Sound Blaster 16, Intel HDA, and the PC speaker.

It does not use UEFI's services, and does not implement swap, IPv6, a framebuffer device for programs, or an AML interpreter; of the DSDT it reads `\_S5` alone. FAT32, exFAT, ext2 and KRFFS partitions mount through `mount(2)`, read and written, with hard and symbolic links on ext2. A regular file can be a block device: `/dev/loop0` to `/dev/loop3` stand on one, so a file system in a file mounts like any other volume. USB is keyboards, mice and flash drives through xHCI, on root ports and behind hubs, with sixteen device table entries shared by every device, hubs included, and eight hubs driven at once; a SuperSpeed hub is driven with its high-speed half beside it, and a low or full-speed device behind a high-speed hub is addressed through that hub's transaction translator, proved only on the notebook. A machine boots from the stick image through its firmware and GRUB, and the root stays in RAM. The i686 kernel maps the first 32 MiB by identity, where a virtual address is its physical one, and reaches the rest of the usable memory below 4 GiB through mappings of its own; the x86-64 kernel maps all of memory, to 64 TiB.

Process records are allocated from the kernel heap without a fixed count; a fork the heap cannot serve returns `ENOMEM`. Each process's descriptor table grows from sixteen to 1024 entries, and an open past that limit returns `EMFILE`. With three descriptors already used for stdio, `fdfull` opens 1021 files, checks that the next open returns `EMFILE`, and checks that a closed descriptor can be reused. Sockets and TCP control blocks are allocated from the heap without a fixed count. In separate stages, `tests/run pools` opens forty-eight pipes, forty ptys and forty-eight sockets, and creates forty child processes. Each stage keeps its objects alive together. It then makes and closes a thousand pipes, a thousand ptys and a thousand sockets; after each cycle, the heap's bytes in use must equal the starting value and its page count must be within two of the starting count.

`prlimit64` maintains six resource limits in each process, each with a soft value that is enforced and a hard value that bounds it, as wide as a `long`: 32 bits on i686, where a value past them is no limit, and 64 bits on x86-64. Fork inherits both values, and exec preserves them. `RLIMIT_NPROC` limits the number of threads with the same real uid across the machine, as Linux counts them: each thread of a process counts, and one that has ended counts until it is reaped. fork and clone, a new thread's included, check the count against the caller's soft limit and return `EAGAIN` when the count has reached it. Real uid 0 is exempt. A thread whose real uid changes through `setuid` counts against the new user's total. `RLIMIT_NOFILE`, at most 1024, is one greater than the highest descriptor number the process may be given, in a table it shares under `CLONE_FILES` as in its own: each allocation reads the caller's limit (`fd_limit`). Open returns `EMFILE` when no descriptor below the soft limit is available; `dup2` returns `EBADF` for a destination at or above it. `RLIMIT_AS` limits the total bytes covered by the process's virtual memory regions. Growth beyond the soft limit makes `mmap` return `ENOMEM`, leaves the break unchanged in `brk`, and prevents stack growth. `RLIMIT_STACK` bounds the stack of the image an `execve` starts: the stack may grow until it is the soft limit's size in whole pages, and no further than the base anonymous mappings are placed below, so a change applies at the next exec; a quarter of it, between 128 KiB and 6 MiB, is what the exec's arguments and environment may take; an exec that runs with ids its caller lacks lowers a soft limit above 8 MiB to 8 MiB. `RLIMIT_CORE` bounds the bytes of a core file, holes excepted; its soft default of 0 leaves none, and its hard default is no limit ([core.5](../man/man5/core.5)). `RLIMIT_FSIZE` bounds the bytes a regular file may reach through a write or a truncation: a write that would pass it writes what fits, and one that starts at it, or a truncation past it, fails with `EFBIG` and sends the thread `SIGXFSZ`. A process may lower its hard limits; only a caller with effective uid 0 may raise them. The kernel defaults, soft and hard, are 4096 threads, 1024 descriptors and no address-space limit, and the stack's are 8 MiB soft and no hard limit. Init can replace them with settings from `/etc/rach2/limits`; see [the utilities Readme](../utils/Readme.md). `tests/run default` runs `limitprobe`, which checks the open, dup2, fork, mmap, brk, write and truncate refusals, limit inheritance, and changes to hard limits.

## Verification

`make test` runs `tests/run style`, then `tests/run host`, then `tests/run core`, the tier `tests/registry` marks `core`, which between them exercise every subsystem. `tests/run host` compiles selected kernel logic natively under AddressSanitizer and UndefinedBehaviorSanitizer. `tests/run style` builds the kernel with warnings as errors, runs the static and text checks, compares source lists, and validates the linked ELF. `tests/run NAME` runs the specialized boot, disk, network, shutdown, and self-build suites; `tests/registry` lists them.

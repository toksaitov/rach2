# `block/`: disks, partitions and the block request

The block layer is how the kernel reads and writes sector-addressed storage. Every disk is a `struct block_device`, a sector count and a small table of functions: the ATA, AHCI and NVMe drivers publish one for each disk they find, the USB mass-storage driver one for each stick, a partition is a view over its disk, and a loop device is one over a regular file. Over that interface are the block request, which lets a device sleep its caller and bounds the wait; the disk registry, which numbers the disks and reads their MBR or GUID partition tables; and the build switches that decide which kernel may write a disk. The buffer cache, the page cache, the raw device nodes and root selection reach every disk through this one interface, in 512-byte sectors, without choosing a driver.

## Interfaces

The contracts a person sees are in the manual: [disk(4)](../../../man/man4/disk.4) for the disk, partition and boot nodes, the writer reservation, write durability and `BLKRRPART`; [nvme(4)](../../../man/man4/nvme.4); [loop(4)](../../../man/man4/loop.4) and [loopctl(8)](../../../man/man8/loopctl.8); [disk(7)](../../../man/man7/disk.7) for disk and partition numbering and the identities `rach2.root=` and `rach2.boot=` take; [recovery(7)](../../../man/man7/recovery.7); [diskctl(8)](../../../man/man8/diskctl.8); [mount(8)](../../../man/man8/mount.8); and [proc(5)](../../../man/man5/proc.5) for `/proc/disk`, `/proc/diskstats`, `/proc/partitions`, `/proc/loop` and `/proc/usb`. The device table and the raw windows' offsets and staging buffers are in [synthfs.Readme.md](../fs/synthfs.Readme.md); root selection is in the [kernel Readme](../../Readme.md), and the boot-line options in [cmdline.md](../../cmdline.md).

Inside the kernel, `block.h` declares the device, `block_request` and `block_request_flags` (the entry every transfer takes), `block_flush`, the partition views and `block0`, the first disk found; `disk.h` declares the registry. `partition.h`, `mbr.h` and `gpt.h` are pure readers of tables, which the host tests, `tools/image/stickcheck.c` and the fuzz harnesses `tests/fuzz/mbr_fuzz.c` and `gpt_fuzz.c` compile unchanged. `ata.h`, `ahci.h` and `nvme.h` each declare an `io` table through which a host test puts a model of the hardware in place of the machine's registers.

The buffer cache (`fs/bcache.c`) moves the file systems' blocks through `block_request_flags`, and the file systems call `block_flush` at unmount, sync and fsync. devfs (`fs/devfs.c`) makes the nodes and moves raw transfers through `block_request`. `kernel.c` probes the disks, selects the root, and calls `ahci_start` and `nvme_start` once it is mounted; the boot processor's tick calls `block_request_tick` and `block_lag_tick` at each tick, from its part that takes no big lock, and the PC platform's tick `ata_tick` from its locked part, which it skips while another processor holds the big lock. Ticks come late, and a late interrupt counts several, so each of the three advances its clock, and the wait ticks of `/proc/disk`, by the ticks `kernel_ticks` counted since its last call, never by one a call; a request or a wait that began since then counts only the ticks since it began, and takes its deadline from the clock as it stands, its last value and the ticks `kernel_ticks` counted since (`req_clock`, `ata_clock`), read with interrupts masked; one that ends between calls counts the ticks since the last call as it ends (`req_count_rest`, `ata_count_rest`). The USB driver reports sticks to `usbdisk.c`, and the system call entry calls `usbdisk_service` (`syscall.c`).

## Design

### The block device

A `struct block_device` (`block.h`) has a sector size, always `BLOCK_SECTOR_SIZE`, 512; a 64-bit sector count; flags; and four functions. `read` and `write` move whole sectors in the call. `submit` starts one request and returns, and the driver reports its end through `block_request_complete` from whatever context it completes in. `flush` puts the device's own cache on the medium; a device with nothing to flush has none. `max_sectors` limits one request, 0 meaning `BLOCK_REQ_SECTORS`, 8, a page; `deadline_ticks` and `deadline_limit` replace the request deadline's period and count; `backing` is the device a loop device's file is on; `unflushed` is the write-through mark; `stalled` is the request pool's mark of a device that stopped answering, a word of its own so that no store to `flags` under another lock undoes it; `stats` are what `/proc/diskstats` prints, counted under the request pool's lock.

| Flag | Set by | Meaning |
| --- | --- | --- |
| `BLOCK_FAULT_SAFE` | ATA always; AHCI, NVMe and virtio-blk until `ahci_start`, `nvme_start` and `virtio_blk_start` | `read` and `write` complete in the call from any context, polling with interrupts off |
| `BLOCK_POLLABLE` | AHCI, NVMe, virtio-blk | `read` and `write` still poll from any context once the device uses `submit` |
| `BLOCK_WRITE_THROUGH` | AHCI, NVMe, virtio-blk with its write cache on, loop devices | a write is on the medium when answered, unless its request has `BLOCK_REQ_NOFLUSH`; `unflushed` records one answered without |
| `BLOCK_CALLER_SYNC` | loop devices | the device sleeps its caller and answers in the same call |
| `BLOCK_FRAMES` | AHCI with 64-bit addressing or on i686, NVMe and virtio-blk, at `ahci_start`, `nvme_start` and `virtio_blk_start` | `submit` takes a read into the caller's page frames, which the controller is given in place of a buffer |
| `BLOCK_READ_ONLY` | a write-protected stick, a virtio-blk device that offers `VIRTIO_BLK_F_RO`, a loop device attached read-only | every mount of the device is read-only (`vfs.c`) |
| `BLOCK_WRITE_FAILED` | the buffer cache | a write failed; cleared when the cache drops the device |
| `BLOCK_GONE` | `bcache_device_gone`, `loop_device_gone` | the device has gone; an unmount writes nothing |

`transfer` in `request.c` chooses the path. A fault-safe device is called directly, in pieces of at most `block_max_sectors`, from any context. A caller-sync device is called directly from a system call, or from the boot before the scheduler is on, when no other context runs and nothing in its chain can be held by another, and takes no request, because the device under it takes one from the same pool while it waits, and two requests for one transfer can fill the pool with callers waiting on each other. Any other device must have `submit`, and the transfer becomes requests; a caller that cannot sleep calls a `BLOCK_POLLABLE` device's polled functions instead. A sleeping device reached where no process can sleep stops the kernel with `block: a sleeping device was reached outside syscall context`.

The block layer runs without the big lock, as Linux's runs with no global lock: each driver serializes on locks of its own, as libata on the port's `ap->lock` (`drivers/ata/libata-core.c:5567`, `ata_scsi_queuecmd` at `libata-scsi.c:4627-4648`). `block_request_flags`, `block_flush` and `block_request_begin` call every device as they find it: its `submit` and `flush` from a caller with interrupts on and no spinlock held, with the big lock only if the caller holds it, and its interrupt completes the request from under the driver's lock, as `ata_qc_complete` runs under `ap->lock` (`libata-core.c:4915-4927`); a caller with interrupts off may hold a spinlock and calls the polled functions as it is. The drivers' locks are AHCI's port lock, NVMe's `sq_lock`, `cq_poll_lock` and `bounce_lock`, virtio-blk's `vblk_queue` and `vblk_lock`, ATA's channel lock, USB storage's `msc_intake_lock`, the loop devices' `loop_lock` and the lag device's `block_lag_lock`, each described in its driver's section. The drivers' counters (`block_count_*`, `block.c`) are under a spinlock of their own, `block_count_lock`, taken after every other.

A disk may change size while it is in use: virtio-blk's capacity changes with its configuration. Its driver sets the size with `block_set_sectors`, which masks interrupts while the count is odd, under its own lock, and the block layer's range checks, the partition views and devfs read it with `block_sectors`, which retries while a sequence count is odd or moves, as Linux's `i_size_read` reads a size on 32-bit SMP, so that a reader on i686 never joins the halves of two sizes. A disk whose driver moves its whole-disk window with its size names that lock as its `size_lock`, and `devfs_disk_publish` cuts the window under it.

Fault safety exists for the page-cache window, which maps a KRFFS root on a disk and takes its faults through an interrupt gate with interrupts off, reading the page there. A KRFFS root is mounted only on a fault-safe device (`kernel.c`). A fault outside every call reads a page of a mapped file as a system call reads it, with interrupts on (`filemap_read` in `mm/filemap.c`), so a slow disk stops only the thread that faulted. Only a thread inside a call with interrupts off reads in place, from a device that is fault-safe, or pollable and not caller-sync. AHCI, NVMe and virtio-blk keep their polled functions after they move to their interrupts for that path. A stick and a loop device never back a KRFFS root.

A partition is a `block_partition_t`, whose first member is the `struct block_device`. `block_partition_init` clamps the view to its backing device. The view's functions check the range, add `start_lba` and call the backing device; `submit` is always present, and `flush` when the backing has one. `block_flags` and `block_max_sectors` read the backing's values at each call, since a disk loses `BLOCK_FAULT_SAFE` and gains `submit` after its views exist. `block_submitter` follows views to the device a request is accounted to, and `block_physical` follows views and the lag wrapper to the disk itself, on which mount claims and `/proc/diskstats` count.

A loop device's `backing` makes a chain, which `block_depth` and `block_is_below` in `chain.c` follow; they are in a file of their own so that the buffer cache's host tests link them without the drivers. `BLOCK_MAX_DEPTH` is 1: a loop device stands on a real device and nothing stands on a loop device. A process may hold `BCACHE_HOLD_MAX`, 4, buffers (`fs/bcache.h`); a file system on a loop device holds a buffer of it while the file system under it holds two of the disk, and a second loop device in the chain would need two more. A file on the memory root has no device under it, so a loop device over it has depth 0.

### Finding the disks

`block_probe` (`block.c`) does nothing under `rach2.nodisk`. Otherwise it clears `block0` and runs `ahci_init`, `nvme_init`, `virtio_blk_init` and `platform_disks_probe`, which on the PC is `ata_init`. Each driver registers every disk it finds and the first becomes `block0`, so the probe order fixes which disk is disk 0. `block_scan_disks` then reads every disk's table. `rach2.disk=ahci` is accepted and changes nothing. `block_ready` returns at once when `block0` is set and probes otherwise; root selection, boot-device discovery and the `/proc/disk` probe all call it, and a probe resets the AHCI controller, so a success is kept. A failure is not, so the debug shell can probe again.

The boot is polled: `block_request_init` reads `rach2.blockpool` and `rach2.blockdeadline` before the memory manager starts, the drivers probe before the scheduler runs, and the root is mounted over polled transfers. After the root is mounted and the USB stack is up, `ahci_start`, `nvme_start` and `virtio_blk_start` move the disks to their interrupts, and a transfer made from a system call then sleeps its caller. `publish_disks` in `kernel.c` publishes every disk's whole-disk window, probing first under `rach2.diskdiag` or on the recovery kernel.

### The disk registry

`disk.c` keeps a `struct disk` for each of up to `DISK_MAX`, 8, disks. A driver calls `disk_register` with its device, its transport (`ahci`, `ata`, `nvme`, `usb` or `virtio`), a location on that transport and its 256-word IDENTIFY answer, from which the registry takes the serial, firmware and model strings. The NVMe driver lays its controller's strings out as IDENTIFY words, and virtio-blk its serial alone, the model and firmware blank; a stick has none and takes its model from INQUIRY (`disk_set_model`). A device whose size in bytes exceeds 64 bits is not registered. A device registered again keeps its number; otherwise the lowest released record is taken before a fresh one, and its index is N of `/dev/diskN`. A fresh record gets one whole-disk and `PART_MAX` partition node slots from devfs, and a released record keeps them for the next disk.

The whole-disk window is a view over the driver's device. The partition views are over `backing`, the device itself or, for disk 0 under `rach2.blocklag`, the lag wrapper; view `i` is the table's entry `i`, and devfs names its node by the entry's number. `disk_scan` reads the table through the device itself and builds the views. It takes one static work area, a scan at a time, since a scan sleeps on a sleeping device and a second scan would overwrite the first's array. The buffer cache drops a view's blocks before the view is rebuilt, because it keys a block by its device and its number there. `disk_rescan`, which `BLKRRPART` calls, returns `EBUSY` while a mount claims a range of the disk or a node of the disk is open by anyone but the caller.

### Partition tables

`part_scan` (`partition.c`) reads every disk's table through a callback, so the same code runs over `block_request`, over the USB scan's cache of sectors, and over an array in the host tests. When sector 0 does not read the table is `PART_UNREAD`. Without the `0x55AA` signature it is `PART_NONE`, with `volume` set when sector 0 opens as a FAT or exFAT boot sector does, and such a medium is mounted through its whole-disk node. A signed sector whose first entry has type `0xEE` is a GUID table's protective MBR; any other signed sector is an MBR, `PART_NONE` when it has no entries.

Every entry passes through `take`: it must be non-empty, inside the range the table allows, clear of every entry already taken, and numbered 1 to `PART_MAX`, 15, with at most 15 taken. A failure is counted in `refused` and the rest are still read, so one bad entry does not cost a disk its partitions. The number is the entry's own: 1 to 4 for MBR primary entries, 5 upward for logical partitions in chain order, and the array position from 1 for a GUID table, so it stays the same whatever else is on the disk; devfs gives each number its own minor, and a number past 15 would take the next disk's.

An MBR has one extended partition at most, of type `0x05`, `0x0F` or `0x85`, which has no view. `follow_logical` walks its chain of boot records. A logical partition must start after its record and end inside the extended partition. Each next record must lie further on, inside the extended partition and outside every partition taken, or the walk ends; it also ends at a record that does not read or has no signature, at one with no next entry, and after `PART_MAX` records. Moving forward ends a loop and keeps a published partition off a later record, which a write to the partition would destroy.

A GUID header is read at LBA 1 and checked by `gpt_header_ok` (`gpt.c`) before any field is used: signature, revision, size, CRC32, the header's own LBA, and an entry count, entry size and array that fit the disk, with the array's size bounded at 16 KiB before it is computed. The whole array is read and its CRC32 checked before any entry is looked at. When the primary header or its array fails, the backup at the disk's last sector is read the same way and `backup_used` is set; when both fail the table is `PART_GPT_BAD`, with no partitions. A used entry, one whose type GUID is not zero, must lie in the header's usable range, and keeps its type GUID, its own GUID and its name made ASCII. Sector addresses are 64-bit throughout.

`mbr.c` is pure code for the four-entry MBR alone. `mbr_take` selects the entries a medium can publish and is how `stickcheck` checks a stick image; `mbr_bootpart_ok`, `mbr_bootpart_pick` and `mbr_gap_clear` are the judgements `kernel.c` makes for `/dev/bootpart` and `/dev/grubcore`. On a GUID disk `part_gpt_as_mbr` gives entries 1 to 4 as MBR records for those judgements, and `part_bios_boot` finds the BIOS boot partition `/dev/grubcore` covers; disk(4) states the conditions. `gpt_parse_entries` is not called by the kernel; `gpt_hosttest` and the GPT fuzz harness use it.

### The block request

`request.c` turns a transfer on a sleeping device into requests of at most the device's `max_sectors`, held to `BLOCK_REQ_MAX_SECTORS`, 2048 sectors or 1 MiB. `req_run_one` takes a request, copies a write into its buffer, calls `submit`, sleeps until the request is no longer in flight, and copies a read out, with no big lock held. The caller sleeps on a wait queue on its own stack, which it names in the request's `waiter`, and only that request's completion or quarantine wakes it, as Linux's `submit_bio_wait` sleeps on a completion on its stack that only that bio's end completes (`block/bio.c:1453-1481`). A caller waiting for room in the pool sleeps on the pool's one wait queue, which every completion, freed request and quarantine wakes, since each may make room. The list of live requests, every field the pool keeps on one, the requests' `waiter` among them, its counts, its clock and its kept buffers, and each device's `stalled` and `stats`, are under the pool's spinlock, `block_req_lock`, taken with interrupts off; a completion takes it from under its driver's lock and wakes the request's caller under it, since the caller's queue goes when the caller takes it back under the same lock, and the pool's wait queue is woken after it is let go. Each wait the caller finishes there or in `block_flush`, and each call of a `BLOCK_CALLER_SYNC` device, adds one to the caller's `disk_waits` (`proc/process.h`), by which a sleeping lock tells a hold that crossed the disk ([../fs/vfs.Readme.md](../fs/vfs.Readme.md)); so does each sleep of an ATA caller for its drive or its channel, and of an AHCI caller for another polled caller's claim of its port (`ahci_claim`). A polled transfer adds none beyond those, since the rest of its wait spins. The buffer is the request's own because the device is given its physical address and may write into it after the caller has given up: a frame of the DMA pool (`alloc_kernel_frame`, below `HARD_MEMORY_LIMIT`, 64 MiB) for a page or less, or heap pages (`kalloc_pages_try`) for more, which the controllers are given a page at a time. A buffer of 32 pages, 128 KiB, which serves any request of 2 to 32 pages, is kept mapped when its request is freed, up to four of them, and reclaim takes them back (`req_keep_shrink`): mapping and unmapping a run's frames for each request flushes every processor's TLB, which under a hypervisor costs more than the transfer. A request the heap has no room for is asked again at half the size, down to a page.

A read into page frames, `block_read_frames`, which the file page cache's reads take ([../fs/ext2.Readme.md](../fs/ext2.Readme.md#reading)), lands in the caller's pages with no buffer and no copy on a device with `BLOCK_FRAMES`, as Linux's bio names the page cache's pages: the request carries the frames' physical addresses (`frames`) in place of a buffer, each request whole pages of at most the device's `max_sectors`, and the driver gives the controller those addresses. The request copies the list and takes a reference on each frame, which `req_drop` gives back, so a request given up on keeps its frames until the device answers late, as it keeps its own buffer, and the answer lands in pages that nothing else has been given. A caller that gets an error therefore never reads a page again into a frame it left unfilled, since the device may still fill it: a fault's read-around reads such a page again into a new frame and lets the old one go (`disk_read_around`), as Linux leaves a folio locked and not up to date until its bio ends. A transfer then touches no memory of the kernel's, and under a hypervisor the processor never touches the pages it fills, which the host's I/O thread writes. Any other device, and a caller that cannot sleep, reads through a buffer of up to 32 pages from the heap, or each frame's page through a temporary mapping when the heap has none, and the bytes are copied into the frames (`read_frames_copied`).

`block_read_frames_async` starts such a read on a `BLOCK_FRAMES` device and returns once its requests are submitted, as Linux's `mpage_readahead` submits its bio and returns: no caller sleeps for the answer, and the request names a completion (`struct block_frames_done`), which its answer calls after the pool's lock is let go, from the driver's interrupt and under the driver's lock, with the frames the request filled and its status, as `bio_endio` calls `bi_end_io`; the completion then lets go of the request for its caller. A request past its deadlines is quarantined as any other, and the tick calls its completion with `EIO` while the device keeps it and its frames until the late answer. The tick claims that call in the same hold of the pool's lock that quarantines the request, so an answer that comes before the call is made leaves it to the tick and calls none of its own. A caller that cannot sleep, or a device without `BLOCK_FRAMES`, gets `EAGAIN` and reads with `block_read_frames`. Such a read holds no lock of the file system's once it is started, so a file system about to give sectors to another file waits with `block_settle` until no started read over them is in flight, as Linux's truncation waits on each locked folio. Both ranges are compared in the sector numbers of the device that answers, `block_submitter_lba`, since a partition's submit adds the view's offset to the request's own; the file page cache's readahead is its one caller ([../mm/Readme.md](../mm/Readme.md#the-file-page-cache)).

A request is held by its caller and by its device and freed when both let go. Its `generation`, the next value of a 32-bit counter, comes back with the completion, and a completion for a request no longer live, or of another generation, is dropped and logged. The deadline starts when the request is taken. Its period is the device's `deadline_ticks`, or 30 seconds of ticks; `rach2.blockdeadline=S` sets the default to S seconds, 1 to 600. A request past one period is waited for into the next, and is given up only after `deadline_limit` periods in a row, 4 by default, two minutes, so a slow disk is waited for and only a silent one is abandoned. A request given up is quarantined: its caller wakes with `EIO`, and the request and its buffer stay the device's until a late completion frees them, so a late answer never lands in reused memory.

At most 16 requests are live (`REQ_LIMIT`), or N with `rach2.blockpool=N`, 1 to 16, and one device may have at most half of them in flight or quarantined, rounded down and at least one. A request is accounted to `block_submitter` of the device named, so a stick's views share the stick's half. A caller that finds the limit reached, or its device at its half, waits; running out is not an error. Two rules end a wait nothing else would end. A device with quarantined requests and none in flight is marked `stalled`, and its waiters and later callers get `EIO` until a late completion clears the mark. A waiter that finds every live request quarantined gets `EIO` too. The half per device leaves room for healthy devices beside a stalled one.

`block_request_begin` and `block_request_ended` are a request for a caller that cannot sleep; the USB pump reads a stick's table with them. `block_flush` flushes the device under any views. A device without `flush`, or a write-through disk with no write answered unflushed, returns 0 at once; a caller that cannot sleep flushes a pollable disk by polling, a loop device flushes in the call, and any other device takes a request marked `BLOCK_REQ_FLUSH`. The buffer cache writes its runs with `BLOCK_REQ_NOFLUSH`, letting a write-through disk answer before the data leaves its cache, and ends a durable sync with one `block_flush`. A write without `BLOCK_REQ_NOFLUSH`, and every write through a driver's polled `write`, is on the medium when it returns.

`block_request_flags` counts each transfer that ended well on the device named and on its disk, for `/proc/diskstats`. The drivers count their commands, flushes, status reads, sleeping ticks and the queued commands a polled command finished first (`block_count_*` in `block.c`) for `/proc/disk`, so a test can require batching, sleeping or a fault's command meeting the queue without timing any of them.

### The lag device

`lag.c` is a device for tests. `rach2.blocklag=N` wraps disk 0, for its partition views, `/dev/bootpart` when the boot partition is on disk 0, and the mounts on them, in a device that keeps only the disk's `BLOCK_READ_ONLY` (`block_lag_wrap`): it has no polled `read` and `write` and no cache, so it is neither fault-safe nor pollable nor write-through, and every transfer and flush on it takes a request; the whole-disk window and every other disk keep the real device. Its `submit` runs the transfer on the real disk at once, in the caller's context, and `block_lag_tick` delivers the completion N hundredths of a second later, by the tick's count, then again two hundredths after with an error, so a kernel that accepted a stale generation would fail a healthy request. A read's page is filled with `0xEE` until delivery. The wrapper's deadline is one period of five seconds, so with N above 500 a request is quarantined; `rach2.lagdeadline=T`, in hundredths of a second, and `rach2.lagperiods=N` change the period and the count. `rach2.blockfail=N` fails the Nth write with `EIO`, and `rach2.blockdead=P` builds MBR entry P's view, 1 to 4, over a device that completes nothing, so a stalled device has a healthy neighbour on the same pool. The wrapper's `flush` is delayed too, so a sync takes a request as a stick's does. The queue of entries, their generations and the hold mode are under `block_lag_lock`, a spinlock taken with interrupts off; `submit` claims an entry under it, runs the backing transfer with it let go, and marks the entry ready under it again, and the tick and an explicit answer deliver an answer under it, the request pool's lock nesting inside.

Kernel test fixtures can call `block_lag_hold(1)` after installing the wrapper. Timer delivery then stops; the real backing transfer still runs in the submitting caller, and request deadlines continue. `block_lag_answer(generation, 0)` delivers one ready answer by its captured generation, and `block_lag_answer(generation, 1)` delivers its error duplicate. An unfinished transfer or a duplicate requested before its answer returns `EAGAIN`; an unknown or consumed capture returns `ENOENT`. Explicit answers outside held mode return `EPERM`. `block_lag_hold(0)` resumes timer delivery. These are kernel fixture calls under the kernel lock, with no user interface. Host fixtures advance request deadlines by advancing their own `kernel_ticks` and calling `block_request_tick`, so completion order and expiry are independent of the host's disk and clock.

`tests/host/request_hosttest.c` drives the real request pool, partition views and lag queue through those controls. It checks the device's share of the pool, independent completion, both holders of a request and its page, read and write copies, flushes, stale generations after address reuse, quarantine and late release, and a read into page frames completed and quarantined, whose frames stay held until the late answer. The guest suites exercise the timer and real drivers alongside these assertions on request state.

### Loop devices

`loop.c` has `LOOP_DEVICES`, 4, `BLOCK_CALLER_SYNC` and `BLOCK_WRITE_THROUGH` devices over regular files. `read` is `vfs_read` of the file, `write` is `vfs_write` and marks the device `unflushed`, and `flush` is `vfs_fsync`, which clears the mark when no write was answered while it slept. The block layer follows a write without `BLOCK_REQ_NOFLUSH` with the flush in the same call, so such a write, and every durable sync of the buffer cache, leaves the blocks in the file on its medium; the cache's other writes wait for the next flush, which lets a stream of writes into an image run at the speed of the file system under it. `backing` is the device of the mount the file is on, and an attachment deeper than `BLOCK_MAX_DEPTH` fails with `ELOOP`. The file's length, a positive whole number of sectors, fixes the sector count, so a short read or write is a device error.

An attachment identifies its file by the file system it is on (`vfs_mount_base`) and its node, so a hard link, or the same file reached through a bind, is the same file, and a second attachment of it fails with `EBUSY`. `loop_attach` claims the slot before anything that can sleep, resolves the path, takes the mount's namespace lock and resolves it again, so a file a KRFFS relocation moved meanwhile is found where it is now; on a type that sets `file_locked` the lock is the file's own. It opens and syncs the file and checks its length and that it is not busy, attached or mapped shared, under the lock, before publishing the device: on ext2 any shared mapping refuses it, and on tmpfs, whose shared mappings map the file's own pages, one through a descriptor open for writing, or a seal against shrinking, which udmabuf and the virtio shared-memory transport require before they hand the pages on (`filemap_memory_shared_writable`). Private mappings may coexist with the attachment: a loop write updates their clean resident pages under the file's lock, while private copies remain unchanged. The attachment's open description keeps the volume the file is on from being unmounted. While it is attached, a write, a truncation, an fallocate, a length change, a writable shared mapping, and a core dump's write fail with `EBUSY` (`loop_backs`), each asked under the lock the attachment publishes under, so that none passes an attachment made while it waited: the file's lock or the namespace lock for a write, a truncation, an fallocate and a core dump's write, and the big lock, which both hold, for a mapping. An unlink of it and a rename over it succeed, as on Linux: the attachment's open description keeps the node as any descriptor does, and the detach's release frees it. The KRFFS root is the exception, since an attachment is not in the descriptor tables that its removal counts: there both fail with `EBUSY` under the root's namespace lock, which `loop_attach` takes too (`unlink_root_name` and `rename_root_names`). udmabuf and the virtio transport refuse a file that is attached. Linux refuses none of these; the device here keeps no copy of the file's blocks outside the file. `loop_repoint` follows a node a relocation moves.

When a stick under a loop device is pulled, `loop_device_gone` marks the device `BLOCK_GONE` and tells the buffer cache, so the mount on it can be taken down. A removal may be reported from an interrupt, and letting go of the file can sleep, so `loop_settle` releases it at the next control command or `/proc/loop` read, once no transfer and no mount remain. `LO_FLAGS_AUTOCLEAR` detaches a device at the last close of its node or the unmount that leaves it unused. loop(4) gives the control commands, the ioctls and their errors.

A transfer runs without the big lock. `loop_lock`, a spinlock taken with interrupts off, covers each device's attachment, its count of transfers in flight, its write and sync counts and its `unflushed` mark: a transfer checks the attachment, counts itself in flight and copies the file's mount and node under it, and gives the count back after the file's call. A transfer checks its range against the attachment's sector count under the same lock, as Linux checks it against the size `loop_configure` set before `Lo_bound` (`bio_check_eod`, `block/blk-core.c:549-564`; `drivers/block/loop.c:1052-1058`). A detach, a settle and a release clear the attachment only when no transfer is in flight, and a detach answers `EBUSY` while one is. Linux's `loop_clr_fd` only marks the device `LO_FLAGS_AUTOCLEAR`, and `Lo_rundown` as well for a sole opener (`loop.c:1187-1189`); with other openers the device stays `Lo_bound` until `lo_release`, at the last close, marks it `Lo_rundown` and lets go of the file (`loop.c:1707-1715`), when no I/O can be in flight. A detach syncs the device's buffers, which sleeps, so it goes on after the sync only while the slot holds the claim it began with (`claim`) and answers `ENXIO` otherwise, as `loop_clr_fd` answers a device no longer `Lo_bound` (`loop.c:1177-1180`). Linux serializes a device's configuration on `lo_mutex` (`loop.c:77`) and hands each request to a work queue that calls the file's operations (`loop_queue_rq`, `loop.c:1815-1825`); here configuration stays under the big lock of the control call, `loop_device_gone` may run from the USB pump with interrupts off, where no mutex may be taken, and the file's call runs in the caller's own context, taking the big lock for the file system under it as a descriptor's call does, unless the call is a read of a file system that reads without it. The call is counted in the caller's `device_io`, so that a `SIGKILL` pending for the caller does not end its write in the file system under the device (`write_killed`, `ext2_batch.c`): a thread may write back the cache over the device as it dies, and Linux's worker sees no signal, while a write refused there would fail the device's write and make the file system on it read-only.

### ATA

`ata.c` drives the two channels of the PC's IDE controller, at `0x1F0` and `0x170` on lines 14 and 15, or at the first IDE controller's base registers for a channel its programming interface puts in native mode. `ata_init` tries primary master, primary slave, secondary master and secondary slave. A drive is a disk when IDENTIFY's status is neither 0 nor `0xFF`, a floating bus, and the LBA mid and high registers are zero, as a packet device's are not. A slave whose IDENTIFY words 10 to 46 equal its master's is the master's echo and is skipped. The sector count is words 100 to 103 on a drive with the 48-bit commands and words 60 and 61 otherwise. Each disk is transport `ata` at location channel times 2 plus drive, `BLOCK_FAULT_SAFE`, with a `max_sectors` of 2048.

A transfer uses the controller's bus master when it has one (programming interface bit 7, BAR4) and the drive does DMA (IDENTIFY word 49 bit 8), unless `rach2.atapio` is on the boot line, and the data port otherwise, a sector at a time. A request moves in commands of at most 64 sectors: DMA through the channel's 32 KiB bounce buffer, static and aligned to its size so it lies in one 64 KiB region, and the data port with interrupts off for each command. A caller's bytes are copied into it and out of it in the caller's own context, because a fault-safe device's transfer may not let another process run against the caller's memory, which the page-cache window may evict or remap meanwhile. Each command uses the 28-bit form when its range lies below 2^28 and the 48-bit form otherwise, and a write ends with one `FLUSH CACHE` or `FLUSH CACHE EXT` after its last command, so it is on the medium when it returns. QEMU makes each flush an `fdatasync` of the disk's image file, which on a loaded host takes tens of milliseconds, so a write has one flush however many commands it takes; a flush every 32 KiB would hold a copy between two disks to about 1 MB/s.

A channel takes one command at a time. A caller that can sleep owns the channel from its first register write to its last and sleeps on the channel's queue while another owns it. A page fault with interrupts off cannot wait for an owner that cannot run; it waits for the drive to be idle and uses the data port, which touches none of the bus master's registers. For the same reason the owner issues its DMA command and starts the engine with interrupts off, and every data-port sequence runs with interrupts off, so no caller finds a command not yet started or a transfer in its data phase.

A wait reads the status 8 times, then sleeps when it can (interrupts on, inside a system call, the scheduler running), woken by the channel's interrupt and by `ata_tick`, and fails with `EIO` after `ATA_WAIT_TICKS`, 30 seconds of ticks. Where it cannot sleep no tick bounds it, so it counts: 256 plain reads, then up to 200,000 rounds of 10,000 `pause` instructions and a read. Under a hypervisor each status read takes the emulator's lock, and the pause leaves it free to complete the command.

The disks run without the big lock. Each channel's spinlock, taken with interrupts off, is libata's port lock (`ap->lock`, `drivers/ata/libata-core.c:5567`): it covers the channel's owner and sleepers, its clock, its interrupt count and the errors it noted for the owner, and is held across every sequence of the channel's registers, from a DMA command's issue to its engine's start and over each data-port command from its check of the idle drive to its end, as `ata_qc_issue` runs under the port lock (`libata-core.c:5063`) and `ata_sff_pio_task` takes it for each step (`drivers/ata/libata-sff.c:1210-1250`). A data-port command waits for the idle drive without the lock, sleeping where it can, and reads the status once more under it, waiting again if a command came between, as `ata_sff_pio_task` lets the lock go while BSY persists (`libata-sff.c:1239-1247`); after 16 such misses it waits under the lock, which bounds the wait. A wait that sleeps lets it go and takes it again to read the status. The interrupt runs without the big lock (`ISR_UNLOCKED`), and the interrupt and the tick take each channel's lock only when it is free: `__ata_sff_interrupt` spins for the host's lock (`libata-sff.c:1471`), but a holder here is reading the status itself, and a sleeper whose test found the lock held is woken by the holder when it lets the lock go.

### AHCI

`ahci.c` drives the first PCI controller in AHCI mode, through its ABAR, BAR5, mapped uncached. Bring-up requests ownership from the firmware when the controller has the BIOS/OS handoff, and goes on, with a log line, when no answer comes within a second; it resets the controller; and on Intel controllers with device IDs `0x8Cxx` and `0x9Cxx` it sets every implemented port's enable bit in PCS, configuration word `0x92`, without which a port has no PHY. It then resets every implemented port with link power management disabled, all together, or one at a time on a controller with staggered spin-up (CAP.SSS), as Linux scans them (`ATA_HOST_PARALLEL_SCAN`, `drivers/ata/ahci.c:2131`), and debounces each link as Linux's `sata_link_debounce` does with its normal timings (`libata-sata.c:22, 235-281`): 200 ms after the reset, SStatus.DET is read every 5 ms until it has held for 100 ms, or, while it reads 1, a device that has not negotiated, for up to 2 s. An empty port thus costs 300 ms, and the six ports of QEMU's `ich9-ahci` 0.35 s together. A DET that still changes after the 2 s fails the reset, as Linux's debounce returns `-EPIPE`; the port is reset again once the try's deadline has passed, 10, 10 and 35 s from its start, with SControl.SPD lowered as Linux's `ata_eh_reset` and `sata_down_spd_limit` lower it (`libata-eh.c:2942-3029`, `libata-sata.c:540`), and a link that has not held after four tries is skipped with a warning. The first limit is the controller's speeds, CAP.ISS, where Linux's would write a reserved SPD. The driver keeps up to `AHCI_DISKS`, 4, ports in port order whose link came up, whose device is ready within five seconds, and whose signature is `0x00000101`, a disk; a port not kept is stopped again, since its reset turned its FIS engine on. Each kept port has its own command list, FIS area and command table in `.bss`, and is started and identified; the probe fails only when no port has a disk. A disk is transport `ahci` at its port, with a `max_sectors` of 2048 and `BLOCK_FAULT_SAFE`, `BLOCK_POLLABLE` and `BLOCK_WRITE_THROUGH`.

The driver uses command slot 0 alone and a PRDT of up to 264 entries. A buffer whose address is below `HARD_MEMORY_LIMIT`, which only i686's identity window has, takes one entry; a read into page frames one per frame; any other takes one per page, so a 1 MiB request that starts mid-page takes 257. On a controller without 64-bit addressing (CAP.S64A clear), a piece of a buffer above 4 GiB, which only x86-64's heap has, moves through a page of the DMA pool kept for its table entry (`ahci_piece`); `rach2.dma32` treats any controller so, for a test. Reads are `READ DMA EXT`, writes `WRITE DMA EXT` and then `FLUSH CACHE EXT`. A command fails when the port reports a fatal error, the task file has ERR or DF, or the controller moved fewer bytes than asked, since a short transfer without an error would otherwise pass. A polled command reads the task file from PxTFD; the interrupt reads it from the D2H register FIS the controller wrote into the port's FIS area before raising the interrupt, the same byte without a register read. A command is issued by its bit in PxCI alone, and no buffer or table is written back from the cache or evicted from it, since x86 bus-master DMA snoops the caches, as Linux's DMA sync does nothing for a coherent device. The port is then stopped and started again (`ahci_io_error`); an engine that does not stop is a panic, since the controller may still write into the buffer.

A polled command waits in steps of 10 microseconds within one bound, 30 seconds with interrupts on and 5 with them off, as libata bounds an internal command by one timeout (`libata-core.c:1616`): the wait for another polled caller's claim, for the task file to go idle and for the slot all take from it, and a caller whose bound runs out fails with `EIO`. A caller that sleeps for the claim turns what is left of its bound into a deadline in ticks at its first sleep, keeps it across the sleeps a claim taken before it runs sends it back to, and runs its command within what is left, as libata's internal command waits with `wait_for_completion_timeout`. A write ends with a flush, which a loaded emulator host or a disk spinning up can take seconds for. With interrupts off, each step of a polled wait, the drain's included, answers the requests other processors left this one (`smp_service`), as a spinlock's waiter does, since a processor dropping a translation on every processor waits for each one's answer. `ahci_start` moves the disks to the controller's MSI message on an allocated vector, unless `rach2.ahcipoll` is on the boot line, the local APIC is not in use, or there is no free vector or no MSI capability; a controller whose MSI enable fails gives the vector back, with its handler. Each disk then has `submit` and `flush` in place of `BLOCK_FAULT_SAFE`, and `BLOCK_FRAMES` where every frame is in the controller's reach, with 64-bit addressing or on i686, and its requests wait in its own queue, oldest first. The interrupt judges the active command, then issues the flush half of a write or completes the request and starts the next, so two disks proceed independently. A write with `BLOCK_REQ_NOFLUSH` completes after its transfer and sets `unflushed`. A polled command on a queued disk first finishes the active command by polling (`ahci_drain`), which `disk-drains` counts, and starts the queue again after its own.

Each port's state, its command slot and tables, its active request, its queue, its polled claim, its bounce pages and its disk's `unflushed`, is under the port's spinlock, taken with interrupts off, as libata's under `ap->lock`. `submit` holds it to queue the request and start it when the port is idle (`ahci_start_next`), and the interrupt runs without the big lock (`ISR_UNLOCKED`), reading the controller's interrupt status once and taking the lock of each port it names in turn, where it reads and clears the port's status and then finishes the port's command and completes its request; the bits of the ports handled are cleared after them, in one write, as `ahci_single_level_irq_intr` reads `HOST_IRQ_STAT`, handles the ports under the host's lock and writes it back (`drivers/ata/libahci.c:1970-1979, 1997-2019, 2023-2056`). Libata's port lock is the host's, one for a controller; here each port has its own, since ports share nothing but the controller's interrupt status. A polled command claims the port under the lock, as libata's internal command takes the port from its queue under `ap->lock` (`libata-core.c:1546-1597`): it waits out another polled caller's claim, drains the active command, marks the port `polling`, and lets the lock go, so the command runs with interrupts as its caller had them, thirty seconds' bound with them on; while the claim lasts no queued request starts and the interrupt leaves the port alone, and its release starts the queue again. The claim's holder may take an interrupt whose handler waits for the big lock, so a caller that holds that lock must not keep it while it waits for the claim, or neither goes on. A caller that can sleep, with interrupts on, inside a system call and the scheduler running, as the ATA driver asks, sleeps on the port's queue until the release wakes it or its bound ends, and the switch gives the big lock up, as libata gives back the port's lock and the error handler's mutex before its internal command waits (`libata-core.c:1596, 1607-1616`). Any other caller spins within its bound, and when it holds the big lock, as the page-cache fault with interrupts off does across its fill, it lends the lock at each step to the holder's processor alone, while that processor still runs the holder's thread and waits for the lock (`bkl_lend`, [the scheduler's Readme](../proc/Readme.md)).

### NVMe

`nvme.c` drives up to 4 NVM Express controllers, each with an admin queue and one I/O queue pair. `nvme_map` maps BAR0 with the INTx line off and MSI-X on with every vector masked, because the I/O queues are made with interrupts enabled and a controller may tie a queue to its vector only while MSI-X is on. A BAR0 the kernel cannot map, on i686 one above 4 GiB, makes the controller unusable. Every page a controller is given, the queues, an identify page, a bounce page and a PRP-list page for each of 8 command slots, is kept for the life of the kernel, since a failed controller may still write into it.

`nvme_bring_up` requires the NVM command set and a 4 KiB page, sizes the I/O queue at most 16 entries and its slots at most 8, disables the controller, programs an admin queue of 8 entries, enables it, identifies it, and creates the I/O completion queue, with interrupts on vector 0, and then the submission queue. Namespaces come from the active namespace list, or every identifier up to the count without one, 16 at a time and at most 1024 examined; a namespace with 512-byte blocks and no metadata is published, at most 4 a controller, as transport `nvme` at location controller times 4 plus its place. An admin command not answered leaves the controller disabled and out of use. A controller brought up once is not reset by a later `nvme_init`, since its namespaces may be mounted.

A command's identifier has its slot in the low three bits. The first PRP entry is the buffer's start, and the second the next page or, past two pages, the slot's list of the rest, and a read into page frames gives the frames in the same places (`nvme_frame_prps`); a buffer not aligned to four bytes moves a page at a time through the bounce page with interrupts masked. A namespace's `max_sectors` is 8 times 2 to the power MDTS, or 2048 when MDTS is 0 or above 7. A namespace starts as `BLOCK_FAULT_SAFE`, `BLOCK_POLLABLE` and `BLOCK_WRITE_THROUGH`. A write goes with FUA, which puts its own blocks on the medium and no others (NVMe 1.4, Figure 406), so a write while the disk is marked `unflushed` is followed by a Flush. An error status fails the transfer with `EIO`. Polled commands wait as AHCI's do. A command not answered in time, or every slot busy for that long, starts `nvme_recover`: disabling the controller aborts every command in flight and is the one way to be sure it writes into none of their buffers again; each request in a slot then completes with `EIO`, and the queues are made again. A controller that does not stop is a panic; one that does not come back is out of use.

`nvme_start` moves each controller to its MSI-X entry 0, or to MSI, on a vector of its own, unless `rach2.nvmepoll` is on the boot line, the local APIC is not in use, or there is no free vector or neither capability, and a controller whose enable fails gives the vector back, with its handler; the namespaces then have `submit`, `flush` and `BLOCK_FRAMES` and keep their polled functions. Requests wait in their namespace's queue, and a controller's namespaces take its free slots in turn. A write with `BLOCK_REQ_NOFLUSH` goes without FUA, sets `unflushed` and counts one more in `wseq`; one without it goes with FUA and, while the mark is set, has a Flush issued in its slot before it completes. A Flush clears the mark when it ends well and no write was answered unflushed while it ran, not when it is issued, so a second caller's `block_flush` sees the mark and waits on a flush of its own.

The namespaces run without the big lock, on the I/O queue's two locks, as Linux's `nvme_queue` has (`drivers/nvme/host/pci.c:192-197`). `sq_lock` covers the submission queue's tail and doorbell, the slots, the namespace queues, `wseq`, `unflushed` and the controller's reset and dead marks, as `nvme_submit_cmds` writes the queue under it (`pci.c:981-1002`); `cq_poll_lock` covers the completion queue's head and phase, as the poll paths take it (`pci.c:1210-1227`), and is taken before `sq_lock`. The interrupt runs without the big lock (`ISR_UNLOCKED`) and reaps under `cq_poll_lock`, taking `sq_lock` for each entry it completes. `bounce_lock` keeps the bounce page for one polled transfer at a time and is taken before the other two. A recovery sets the reset mark under both locks and runs with them let go and this processor's interrupts masked, from the first lock until the mark is cleared, since an interrupt taken in between would wait for the big lock, whose holder may be waiting for the recovery. Each step of its waits, the ready waits and admin commands among them, answers other processors' requests as a polled command's does, since Linux's reset sleeps with interrupts on (`nvme_wait_ready`, `drivers/nvme/host/core.c:2467`) and Rach2's cannot. Another caller that finds the mark set waits it out, as `nvme_dev_disable` serializes on `shutdown_lock` (`pci.c:2785-2831`), and a polled command failed by the recovery keeps its slot until its own caller frees it.

### virtio-blk

`virtio_blk.c` drives up to 8 virtio block devices on the shared virtio core ([virtio](../virtio/Readme.md)), as Linux's `drivers/block/virtio_blk.c` does. `virtio_blk_init` takes each device `virtio_pci_find(VIRTIO_ID_BLOCK, n)` gives, brings it up and publishes it as transport `virtio` at its place among those found, the first as `block0` when no other driver has, and registers the driver for a device `bind` gives the transport later. A device bound after the boot is brought up the same way, has its table read, goes to its interrupts and then has its whole-disk window published with `devfs_disk_publish`, as the boot publishes every disk's after `virtio_blk_start`. A device brought up by an earlier call is not reset again, since its disk may be mounted.

`vblk_bring_up` follows Linux's `virtblk_probe`. It asks for one queue for each processor, as many as `num_queues` gives when the device offers `VIRTIO_BLK_F_MQ` and at most `VIRTIO_MAX_QUEUES`, 8, and for indirect tables of 256 descriptors, 8 a queue. It takes `SIZE_MAX`, `SEG_MAX`, `RO`, `BLK_SIZE`, `FLUSH`, `CONFIG_WCE`, `MQ`, `DISCARD` and `WRITE_ZEROES` where offered. A device whose `blk_size` is not 512 is refused, as NVMe refuses a namespace of other blocks. The write cache is on as Linux's `virtblk_get_cache_mode` reads it (`vblk_cache_mode`): by the configuration's `writeback` byte when `CONFIG_WCE` was taken, and otherwise exactly when the device has `FLUSH`. A cache that is on in a device without `FLUSH` could never be emptied, so the driver writes 0 to `writeback`, which sets the device to writethrough, and reads the byte back; a device that keeps its cache on all the same is driven with the cache on, the FLUSH each durable write needs is sent as Linux sends it, the device answers UNSUPP, and the write and every flush fail with EIO, so that nothing in such a cache is reported durable. A chain carries the header, at most 254 pieces of data, fewer when `seg_max` or the queue's longest chain says so, each at most a page or `size_max`, and the status byte; the driver gives each queue `size_max` as its `max_seg`, so that the virtio core, which puts pieces that follow each other in memory in one descriptor, joins none past it, as Linux makes `size_max` its queue's largest segment; `max_sectors` is the whole pages that many pieces cover, at most the block layer's 1 MiB. Each queue has a page of its own, 16 slots of 128 bytes: the request header, the status, a discard's range and `GET_ID`'s answer. With the queues set up and DRIVER_OK given, the driver asks the device for its serial with `GET_ID`, which a device that answers UNSUPP does not have. The disk starts `BLOCK_FAULT_SAFE` and `BLOCK_POLLABLE`, and `BLOCK_WRITE_THROUGH` and a `flush` when the cache is on, so that `block_flush` reaches a polled disk's cache too: on a polled disk a flush with a request is a polled FLUSH whose result answers the request before the call returns.

A polled command takes a slot of the processor's queue, waiting for one, and polls the queue with `virtqueue_reap` until its slot is answered, in steps of 10 us, answering other processors' requests between steps when interrupts are off. An answer not given in 30 s, or 5 s with interrupts off, takes the device out of use (`vblk_kill`): `virtio_halt` resets it, or turns its DMA off when the reset does not end, so that it writes into no buffer again, every request in a slot or waiting answers EIO, and every later command does too. Linux's driver has no such bound and waits for the device; a disk that never answers would hold the fault path forever. Virtio has no FUA, so on a disk with a cache a polled write is followed by a FLUSH; when that flush fails, or a command of the write that the device was given fails, the first among them, the write fails with EIO and the disk is marked `unflushed`, since a part of it may be in the cache.

`virtio_blk_start` gives each disk `submit` and `BLOCK_FRAMES` in place of `BLOCK_FAULT_SAFE`, unless `rach2.vblkpoll` is on the boot line or the transport gave the device no interrupt, and logs `virtio-blk: virtio0: interrupts: N queues` or why it polls. A request goes on the queue of the processor that submits it, as Linux's blk-mq maps a processor to its hardware queue, and is offered while the queue has room and a slot; one that does not fit waits, oldest first, and the queue's interrupt offers it when a slot comes back. Each queue's interrupt, of its own MSI-X entry where the transport has one, runs without the big lock and answers its slots under the queue's lock. A write with `BLOCK_REQ_NOFLUSH` sets the disk's `unflushed` mark and counts one more in `wseq`; any other write, on a disk with a cache, has a FLUSH issued in its slot before it completes, so it is on the medium when it is answered, which `BLOCK_WRITE_THROUGH` promises; a FLUSH clears the mark as NVMe's does, and one that fails, or cannot be offered, fails its write with EIO and sets the mark. A write of zeroes follows the same two rules, since the device holds it in its cache as it holds data. A write, a write of zeroes or a discard that fails sets the mark too, since a part of it may have reached the cache before the error, as Linux's block layer sends a FLUSH at the next fsync after any write it sent. A discard is answered at once and sets the mark, so that the `block_flush` after it sends a FLUSH, which the block layer skips on a disk not marked. A discard and a write of zeroes, `BLOCK_REQ_DISCARD` and `BLOCK_REQ_ZEROES`, become `VIRTIO_BLK_T_DISCARD` and `VIRTIO_BLK_T_WRITE_ZEROES` with one range of at most `max_discard_sectors` or `max_write_zeroes_sectors`, 0 meaning no limit, as the device gives them; `block_discard` splits a longer range, and a device that cannot write zeroes, or answers UNSUPP, has them written as data. A status other than OK fails the request with EIO, UNSUPP with EOPNOTSUPP, and a FLUSH with EIO whatever the status.

A configuration change is handled apart from any request, as Linux's `virtblk_config_changed_work` handles it from a work item: `vblk_config_work` reads the capacity, gives it to the disk and to the whole-disk window, so that `/dev/diskN` and its size ioctls have it, as `set_capacity_and_notify` gives Linux's disk its size, and logs the new size. It sets each size with `block_set_sectors` under `vblk_lock`, which is the disk's `size_lock`, so that `devfs_disk_publish`, which cuts the window under the same lock, either cuts it at the new size or is followed by the change; the partition views keep their ranges until the table is read again. It runs in the configuration's interrupt on a transport whose configuration is register reads (`config_atomic`), which virtio-pci's is, so a disk polled under `rach2.vblkpoll` has it too; at the start of each polled transfer of a device whose transport gives it no interrupt; and otherwise from `virtio_blk_service`, at the next system call's entry. A submit reads no configuration. The reader is counted in the device, as a polled caller is, and reads nothing from a disk that is out of use.

When the transport lets the device go, at an `unbind`, `vblk_removed` takes it out of use as above, hides its nodes, tells the loop devices and the buffer cache that each of its views has gone, as when a stick is pulled, waits until no polled caller and no reader of the configuration is inside the device, as Linux's `virtblk_remove` first ends its configuration work, frees the queues and gives the device back. The disk's number is freed then when nothing holds the disk. A disk that is open, mounted, under a loop device or has blocks in the buffer cache stays, answering EIO, and `virtio_blk_service`, which the system call's entry calls beside `usbdisk_service`, frees its number and its record once the last holder has let go, as a pulled stick is reclaimed; a bind that needs a record looks too.

At the machine's stop `kernel_shutdown` calls `virtio_blk_shutdown` after the file systems are unmounted and the network cards stopped, before the processors stop. Each disk refuses new commands, the commands its device has and the requests that wait are finished, a write with its flush, a cache still marked `unflushed` is flushed, and `virtio_halt` resets the device, as Linux's virtio bus resets each device at shutdown, so that a warm restart finds no device reading the rings of the kernel that stopped. The wait is bounded as a polled command's is. The driver logs `virtio-blk: virtio0: shutdown: reset with no request in flight`, or the requests left unanswered and whether the reset ended.

Each queue's `vblk_queue` lock covers its slots, the requests waiting and the chain being built, and is taken with interrupts off before the virtqueue's own lock; the disk's `vblk_lock` covers `wseq`, the `unflushed` mark, the dead and closed marks, the count of callers inside the device and the capacity, and is taken after both and before the request pool's lock, in row 11 of the kernel's lock order ([processes](../proc/Readme.md)).

### The USB stick as a disk

`usbdisk.c` makes each logical unit the mass-storage driver brings up a disk. The unit's device (`usb/msc.c`) has `submit` and no `read` or `write`, a `flush` that sends SYNCHRONIZE CACHE, a `max_sectors` of 1024, a 10-second deadline period, and `BLOCK_READ_ONLY` when write-protected. `bring_up` registers it as transport `usb` at location slot times 4 plus the unit, with its model from INQUIRY, its serial from INQUIRY's unit serial page, and `removable` set; there are `USBDISK_MAX`, 8, records.

The class driver reports a stick from the pump, which the timer runs and where nothing may sleep, so the table is read without sleeping. `part_scan` runs over a cache of up to 96 sectors, enough for sector 0, both GUID headers and arrays, and an extended chain. A pass that needs a sector the cache lacks is dropped, `block_request_begin` starts a read of a page at most, and later passes ask after it with `block_request_ended` and run the scan again, until a pass needs nothing new. One stick is read at a time. Then `disk_set_table` makes the views and `devfs_disk_publish` the whole-disk window, whatever the table was.

Registering and reclaiming change what a process inside a system call may be using, so they run where no system call is in progress: at a system call's entry (`usbdisk_service`) or on a pump pass that did not interrupt one (`usbdisk_step`). `usbdisk_left` marks a stick closing; closing hides its nodes and tells the loop devices and the buffer cache that every view has gone. The record is reclaimed when no scan is reading it and `usbdisk_holds` counts nothing: no open node, request, mount or held buffer on the device or a view. Reclaiming releases the disk number and the class driver's slot, unless another unit of the same device still has a record.

A stick's `submit` and `flush` run without the big lock. They refuse a stick that has gone, check the range and write protection, and put the request in the stick's intake ring under `msc_intake_lock`, a spinlock taken with interrupts off; when the big lock is free they take it and admit the request at once, and otherwise the next pump pass admits it. The stick's state machine and the host controller's rings stay under the big lock, as the whole USB stack is, and a request starts only when the stick is not recovering. Linux's `queuecommand` likewise hands a command to the device's control thread and returns (`drivers/usb/storage/scsiglue.c:360-396`), which runs it under `us->dev_mutex` (`usb.c:380-403`).

### Disk information

`diskinfo.c` writes `/proc/disk`, whose format proc(5) gives. Its first record has disk 0's IDENTIFY strings and its sector 0, parsed as an MBR by `diskinfo_probe`, which uses `block0` when a disk is up and probes only when none is, so the diagnostic never resets a controller under a mounted root. The counters precede the record and the registry's lines follow it. The formatting is pure, and `diskinfo_hosttest` renders records no device produces.

### Disk write policy

Which kernel may write which disk is fixed when the kernel is built, by two independent switches, because a boot-line token can be edited at the GRUB prompt. The ordinary kernel, `rach2`, has neither. The metal kernel, `rach2-metal`, is built with `-DRACH2_DISK_READONLY`; the recovery kernel, `rach2-recovery`, with `-DRACH2_RECOVERY` and the read-write driver policy (`Makefile`).

`RACH2_DISK_READONLY` is enforced in the drivers by `diskcmd_allowed` (`diskcmd.c`), where each command leaves for the device. It allows `READ SECTORS` (`0x20`), `READ SECTORS EXT` (`0x24`), `READ DMA` (`0xC8`), `READ DMA EXT` (`0x25`) and `IDENTIFY` (`0xEC`). Any other command byte is not issued: the driver logs `refused: command 0xNN: rach2: disk policy: read-only` and the transfer fails. It is a list of what is allowed, so an omission costs a failed read where an omission from a list of what is forbidden would cost a written disk. ATA checks every command in `ata_command`, and AHCI in `ahci_build_command`, which builds every command it sends. NVMe judges each I/O command in `nvme_build` by its ATA counterpart, a Read as `READ DMA EXT`, a Write as `WRITE DMA EXT` and a Flush as `FLUSH CACHE EXT`, and Identify as `IDENTIFY` in `nvme_identify`; the admin commands that set up its queues touch no medium and are not judged. The USB driver and the loop devices are not judged, so the metal kernel writes a stick. `tools/inspect/check_diskpolicy.sh` reads `diskcmd_policy_banner`, `rach2: disk policy: read-only` or `read-write`, from the built kernel; the boot logs `disk: policy:` and `/proc/disk` has a `policy` line.

`RACH2_RECOVERY` selects the write handler of every whole-disk and partition node, of every transport, in devfs (`dev_disk_write` in `fs/devfs.c`). Without it the handler returns `EPERM` and has no other path. With it the handler writes the window and checks at each write that the effective user ID is 0, since a process can open the node as root and drop privilege afterwards. The switch also makes `recovery_publishes_disk` return 1, which has the boot probe for a disk and puts the partition nodes under the writer reservation, and compiles the debug shell's `disk write`, which writes, flushes and reads back disk 0's last sector when neither LBA 1 nor that sector has a GUID header and no MBR entry covers it. `tools/inspect/check_recovery.sh` reads `recovery_policy_banner`, `rach2: disk authority: recovery` or `ordinary`.

`/dev/bootpart` and `/dev/grubcore` take writes from effective user ID 0 in every build, so an everyday kernel can install a kernel or replace GRUB's core. Their writes go through the drivers, so the metal kernel's policy applies to them as to every other write to its disks.

| What is written | Ordinary | Metal | Recovery |
| --- | --- | --- | --- |
| `/dev/diskN`, `/dev/diskNpM` | `EPERM` | `EPERM` | by root |
| `/dev/bootpart`, `/dev/grubcore` | by root | no write is issued | by root |
| a mount or loop device on an ATA, AHCI or NVMe disk | yes | no write is issued | yes |
| a mount or loop device on a stick | yes | yes | yes |

Beside the authority is the writer reservation, `writer_held` in `struct disk`: one write-capable open at a time across a disk's whole-disk node and boot windows in every build, and its partition nodes on the recovery kernel, and none over a range a mount claims (`devfs.c`). A stick with `BLOCK_READ_ONLY` mounts read-only, and a raw write to it fails with `EIO`. disk(4) gives these rules as a user meets them.

## Limits

* Sectors are 512 bytes. ATA and AHCI do not publish a drive whose IDENTIFY word 106 gives another logical sector size, nor NVMe a namespace of another block size, 4096 bytes among them, or with metadata, nor virtio-blk a device whose `blk_size` is not 512.
* The counts are fixed: 8 disks, 15 partitions a disk, one extended partition an MBR, 128 GUID entries in 16 KiB, one IDE controller of 4 drives, 4 AHCI disks of the first AHCI controller, 4 NVMe controllers of 4 namespaces, 8 virtio-blk devices of 8 queues and 16 commands a queue, 8 sticks, 4 loop devices and 16 live requests.
* An ATA drive without the 48-bit commands is used to 2^28 sectors, 128 GiB, and on i686 an NVMe controller whose BAR0 is above 4 GiB is not used.
* There are no packet devices, port multipliers, SATA hot-plug or native command queuing; no NVMe namespace management, shutdown notification at power-off or scatter-gather lists; and NVMe has one I/O queue pair however many processors there are.
* No I/O scheduler merges or orders requests. Discards and writes of zeroes come only from `BLKDISCARD` and `BLKZEROOUT` on the recovery kernel ([disk(4)](../../../man/man4/disk.4)): no file system discards the blocks it frees, and only virtio-blk issues them to a device. virtio-blk has no zoned, secure-erase or lifetime commands, no packed virtqueues and no polling queues.
* A stick whose table needs more than 96 sectors to read has no partitions, and a loop device has no offset, size limit or encryption.
* A polled transfer keeps the processor until it ends. Before `ahci_start`, `nvme_start` and `virtio_blk_start`, and under `rach2.ahcipoll`, `rach2.nvmepoll` or `rach2.vblkpoll`, every transfer is polled.

## Tests

`tests/run host` compiles the layer's pure code and its drivers natively under AddressSanitizer and UndefinedBehaviorSanitizer; [tests/host/Readme.md](../../../tests/host/Readme.md) lists each test's rows. These compile `block/` sources:

* `block_hosttest.c`: partition views and their bounds.
* `lag_hosttest.c`: the lag wrapper's queue under a transfer that sleeps.
* `mbr_hosttest.c`, `gpt_hosttest.c`, `partition_hosttest.c`: the MBR judgements, every GUID header rule, and the partition service over disks in memory, with logical partitions, a GUID table from either header, `part_gpt_as_mbr` and `part_bios_boot`.
* `ata_hosttest.c`, `ahci_hosttest.c`, `nvme_hosttest.c`, `virtio_blk_hosttest.c`: each driver against a model of its hardware, with waits, resets and commands that never end, sector sizes other than 512, and recovery; virtio-blk's model is a device behind the virtio core's table, with its features, queues, cache modes, flushes, a polled disk's flush, writes that fail after a part reached the cache, discards, `size_max` through indirect tables, capacity changes, sizes read between the halves of a change and during the window's publication, a bind after the boot, a removal with the disk held and the machine's stop.
* `diskcmd_hosttest.c`: all 256 command bytes under both policies.
* `diskinfo_hosttest.c`: IDENTIFY strings, 64-bit decimal and the `/proc/disk` record.
* `usbdisk_hosttest.c`: a stick's registration, table scan, pull, holds and reclaiming.
* `loop_attach_hosttest.c`, `open_hosttest.c`: loop attachment across a KRFFS relocation.
* `devfs_hosttest.c`: where `/dev/grubcore` is published.
* `bcache_hosttest.c`, `bcache_cost_hosttest.c`, `fat32_hosttest.c`, `exfat_hosttest.c`, `ext2_hosttest.c`: link `chain.c`.

`request.c` has no host test; the suites reach it.

`tests/run NAME` runs a system suite under QEMU, `RACH2_WORKERS=4 tests/run A B C` several, and `ARCH=x86_64` the other architecture; [tests/system/suites.md](../../../tests/system/suites.md) gives each suite's tier and needs. Those that cover this layer:

* ATA: `persist`, `crash` and `mount` (core); `stress`, `bus` and `load` (full), `load` with `rach2.atapio`.
* AHCI: `parts` and `queue` (core); `disk-q35`, `stress-ahci` and `bootorder` (full). `queue` covers the interrupt path and the fault path beside raw reads of the same port; `request_hosttest.c` and `ahci_hosttest.c` cover the deadlines and the completion of independent requests.
* NVMe: `uefi` (full), which installs onto a 4 TiB NVMe disk and boots it.
* virtio-blk: `vblk` (core), reads on two queues by their interrupts, the serial and discard limit in sysfs, on the recovery kernel a raw write, flush, discard and write of zeroes, and a restart from the debug shell in which the driver must say it reset the device before the kernel restarts; the machine cases whose disk is only the way to their system, the GNU root among them, boot from virtio-blk.
* Partition tables and identities: `parts` (core).
* The request pool and the lag device: `mount`, `fatwrite` and `exfat` (core), `krffsmount` (full).
* Sticks: `usbdisk` (core). Loop devices: `ext2` (core), `loopdev` (full).
* The write policy: `authority` and `metal` (core), `diskpolicy` and `diskdiag` (full).
* The raw and boot windows: `grub` (core); `bootpart`, `menu`, `install`, `drill`, `sealed` and `uefi` (full).

# `block/`: disks, partitions and the block request

The block layer is how the kernel reads and writes sector-addressed storage. Every disk is a `struct block_device`, a sector count and a small table of functions: the ATA, AHCI and NVMe drivers publish one for each disk they find, the USB mass-storage driver one for each stick, a partition is a view over its disk, and a loop device is one over a regular file. Over that interface are the block request, which lets a device sleep its caller and bounds the wait; the disk registry, which numbers the disks and reads their MBR or GUID partition tables; and the build switches that decide which kernel may write a disk. The buffer cache, the page cache, the raw device nodes and root selection reach every disk through this one interface, in 512-byte sectors, without choosing a driver.

## Interfaces

The contracts a person sees are in the manual: [disk(4)](../../../man/man4/disk.4) for the disk, partition and boot nodes, the writer reservation, write durability and `BLKRRPART`; [nvme(4)](../../../man/man4/nvme.4); [loop(4)](../../../man/man4/loop.4) and [loopctl(8)](../../../man/man8/loopctl.8); [disk(7)](../../../man/man7/disk.7) for disk and partition numbering and the identities `rach2.root=` and `rach2.boot=` take; [recovery(7)](../../../man/man7/recovery.7); [diskctl(8)](../../../man/man8/diskctl.8); [mount(8)](../../../man/man8/mount.8); and [proc(5)](../../../man/man5/proc.5) for `/proc/disk`, `/proc/diskstats`, `/proc/partitions`, `/proc/loop` and `/proc/usb`. The device table and the raw windows' offsets and staging buffers are in [synthfs.Readme.md](../fs/synthfs.Readme.md); root selection is in the [kernel Readme](../../Readme.md), and the boot-line options in [cmdline.md](../../cmdline.md).

Inside the kernel, `block.h` declares the device, `block_request` and `block_request_flags` (the entry every transfer takes), `block_flush`, the partition views and `block0`, the first disk found; `disk.h` declares the registry. `partition.h`, `mbr.h` and `gpt.h` are pure readers of tables, which the host tests, `tools/image/stickcheck.c` and the fuzz harnesses `tests/fuzz/mbr_fuzz.c` and `gpt_fuzz.c` compile unchanged. `ata.h`, `ahci.h` and `nvme.h` each declare an `io` table through which a host test puts a model of the hardware in place of the machine's registers.

The buffer cache (`fs/bcache.c`) moves the file systems' blocks through `block_request_flags`, and the file systems call `block_flush` at unmount, sync and fsync. devfs (`fs/devfs.c`) makes the nodes and moves raw transfers through `block_request`. `kernel.c` probes the disks, selects the root, and calls `ahci_start` and `nvme_start` once it is mounted; the timer calls `block_request_tick` and `block_lag_tick` every tick, and the PC platform's tick `ata_tick`. The USB driver reports sticks to `usbdisk.c`, and the system call entry calls `usbdisk_service` (`syscall.c`).

## Design

### The block device

A `struct block_device` (`block.h`) has a sector size, always `BLOCK_SECTOR_SIZE`, 512; a 64-bit sector count; flags; and four functions. `read` and `write` move whole sectors in the call. `submit` starts one request and returns, and the driver reports its end through `block_request_complete` from whatever context it completes in. `flush` puts the device's own cache on the medium; a device with nothing to flush has none. `max_sectors` limits one request, 0 meaning `BLOCK_REQ_SECTORS`, 8, a page; `deadline_ticks` and `deadline_limit` replace the request deadline's period and count; `backing` is the device a loop device's file is on; `unflushed` is the write-through mark; `stats` are what `/proc/diskstats` prints.

| Flag | Set by | Meaning |
| --- | --- | --- |
| `BLOCK_FAULT_SAFE` | ATA always; AHCI and NVMe until `ahci_start` and `nvme_start` | `read` and `write` complete in the call from any context, polling with interrupts off |
| `BLOCK_POLLABLE` | AHCI, NVMe | `read` and `write` still poll from any context once the device uses `submit` |
| `BLOCK_WRITE_THROUGH` | AHCI, NVMe | a write is on the medium when answered, unless its request has `BLOCK_REQ_NOFLUSH`; `unflushed` records one answered without |
| `BLOCK_CALLER_SYNC` | loop devices | the device sleeps its caller and answers in the same call |
| `BLOCK_READ_ONLY` | a write-protected stick, a loop device attached read-only | every mount of the device is read-only (`vfs.c`) |
| `BLOCK_STALLED` | `request.c` | every request of the device passed its deadlines; new requests fail with `EIO` until a late completion |
| `BLOCK_WRITE_FAILED` | the buffer cache | a write failed; cleared when the cache drops the device |
| `BLOCK_GONE` | `bcache_device_gone`, `loop_device_gone` | the device has gone; an unmount writes nothing |

`transfer` in `request.c` chooses the path. A fault-safe device is called directly, in pieces of at most `block_max_sectors`, from any context. A caller-sync device is called directly from a system call only, and takes no request, because the device under it takes one from the same pool while it waits, and two requests for one transfer can fill the pool with callers waiting on each other. Any other device must have `submit`, and the transfer becomes requests; a caller that cannot sleep calls a `BLOCK_POLLABLE` device's polled functions instead. A sleeping device reached where no process can sleep stops the kernel with `block: a sleeping device was reached outside syscall context`.

Fault safety exists for the page-cache window, which maps a KRFFS root on a disk and takes its faults through an interrupt gate with interrupts off, reading the page there. A KRFFS root is mounted only on a fault-safe device (`kernel.c`), and `mmap_fault_readable` in `syscall_proc.c` maps a file only from a device a fault can read, fault-safe or pollable and not caller-sync, and answers `ENODEV` otherwise. AHCI and NVMe keep their polled functions after they move to their interrupts for this path. A stick and a loop device back neither a KRFFS root nor a mapping.

A partition is a `block_partition_t`, whose first member is the `struct block_device`. `block_partition_init` clamps the view to its backing device. The view's functions check the range, add `start_lba` and call the backing device; `submit` is always present, and `flush` when the backing has one. `block_flags` and `block_max_sectors` read the backing's values at each call, since a disk loses `BLOCK_FAULT_SAFE` and gains `submit` after its views exist. `block_submitter` follows views to the device a request is accounted to, and `block_physical` follows views and the lag wrapper to the disk itself, on which mount claims and `/proc/diskstats` count.

A loop device's `backing` makes a chain, which `block_depth` and `block_is_below` in `chain.c` follow; they are in a file of their own so that the buffer cache's host tests link them without the drivers. `BLOCK_MAX_DEPTH` is 1: a loop device stands on a real device and nothing stands on a loop device. A process may hold `BCACHE_HOLD_MAX`, 4, buffers (`fs/bcache.h`); a file system on a loop device holds a buffer of it while the file system under it holds two of the disk, and a second loop device in the chain would need two more. A file on the memory root has no device under it, so a loop device over it has depth 0.

### Finding the disks

`block_probe` (`block.c`) does nothing under `rach2.nodisk`. Otherwise it clears `block0` and runs `ahci_init`, `nvme_init` and `platform_disks_probe`, which on the PC is `ata_init`. Each driver registers every disk it finds and the first becomes `block0`, so the probe order fixes which disk is disk 0. `block_scan_disks` then reads every disk's table. `rach2.disk=ahci` is accepted and changes nothing. `block_ready` returns at once when `block0` is set and probes otherwise; root selection, boot-device discovery and the `/proc/disk` probe all call it, and a probe resets the AHCI controller, so a success is kept. A failure is not, so the debug shell can probe again.

The boot is polled: `block_request_init` reads `rach2.blockpool` and `rach2.blockdeadline` before the memory manager starts, the drivers probe before the scheduler runs, and the root is mounted over polled transfers. After the root is mounted and the USB stack is up, `ahci_start` and `nvme_start` move the disks to their interrupts, and a transfer made from a system call then sleeps its caller. `publish_disks` in `kernel.c` publishes every disk's whole-disk window, probing first under `rach2.diskdiag` or on the recovery kernel.

### The disk registry

`disk.c` keeps a `struct disk` for each of up to `DISK_MAX`, 8, disks. A driver calls `disk_register` with its device, its transport (`ahci`, `ata`, `nvme` or `usb`), a location on that transport and its 256-word IDENTIFY answer, from which the registry takes the serial, firmware and model strings. The NVMe driver lays its controller's strings out as IDENTIFY words; a stick has none and takes its model from INQUIRY (`disk_set_model`). A device whose size in bytes exceeds 64 bits is not registered. A device registered again keeps its number; otherwise the lowest released record is taken before a fresh one, and its index is N of `/dev/diskN`. A fresh record gets one whole-disk and `PART_MAX` partition node slots from devfs, and a released record keeps them for the next disk.

The whole-disk window is a view over the driver's device. The partition views are over `backing`, the device itself or, for disk 0 under `rach2.blocklag`, the lag wrapper; view `i` is the table's entry `i`, and devfs names its node by the entry's number. `disk_scan` reads the table through the device itself and builds the views. It takes one static work area, a scan at a time, since a scan sleeps on a sleeping device and a second scan would overwrite the first's array. The buffer cache drops a view's blocks before the view is rebuilt, because it keys a block by its device and its number there. `disk_rescan`, which `BLKRRPART` calls, returns `EBUSY` while a mount claims a range of the disk or a node of the disk is open by anyone but the caller.

### Partition tables

`part_scan` (`partition.c`) reads every disk's table through a callback, so the same code runs over `block_request`, over the USB scan's cache of sectors, and over an array in the host tests. When sector 0 does not read the table is `PART_UNREAD`. Without the `0x55AA` signature it is `PART_NONE`, with `volume` set when sector 0 opens as a FAT or exFAT boot sector does, and such a medium is mounted through its whole-disk node. A signed sector whose first entry has type `0xEE` is a GUID table's protective MBR; any other signed sector is an MBR, `PART_NONE` when it has no entries.

Every entry passes through `take`: it must be non-empty, inside the range the table allows, clear of every entry already taken, and numbered 1 to `PART_MAX`, 15, with at most 15 taken. A failure is counted in `refused` and the rest are still read, so one bad entry does not cost a disk its partitions. The number is the entry's own: 1 to 4 for MBR primary entries, 5 upward for logical partitions in chain order, and the array position from 1 for a GUID table, so it stays the same whatever else is on the disk; devfs gives each number its own minor, and a number past 15 would take the next disk's.

An MBR has one extended partition at most, of type `0x05`, `0x0F` or `0x85`, which has no view. `follow_logical` walks its chain of boot records. A logical partition must start after its record and end inside the extended partition. Each next record must lie further on, inside the extended partition and outside every partition taken, or the walk ends; it also ends at a record that does not read or has no signature, at one with no next entry, and after `PART_MAX` records. Moving forward ends a loop and keeps a published partition off a later record, which a write to the partition would destroy.

A GUID header is read at LBA 1 and checked by `gpt_header_ok` (`gpt.c`) before any field is used: signature, revision, size, CRC32, the header's own LBA, and an entry count, entry size and array that fit the disk, with the array's size bounded at 16 KiB before it is computed. The whole array is read and its CRC32 checked before any entry is looked at. When the primary header or its array fails, the backup at the disk's last sector is read the same way and `backup_used` is set; when both fail the table is `PART_GPT_BAD`, with no partitions. A used entry, one whose type GUID is not zero, must lie in the header's usable range, and keeps its type GUID, its own GUID and its name made ASCII. Sector addresses are 64-bit throughout.

`mbr.c` is pure code for the four-entry MBR alone. `mbr_take` selects the entries a medium can publish and is how `stickcheck` checks a stick image; `mbr_bootpart_ok`, `mbr_bootpart_pick` and `mbr_gap_clear` are the judgements `kernel.c` makes for `/dev/bootpart` and `/dev/grubcore`. On a GUID disk `part_gpt_as_mbr` gives entries 1 to 4 as MBR records for those judgements, and `part_bios_boot` finds the BIOS boot partition `/dev/grubcore` covers; disk(4) states the conditions. `gpt_parse_entries` is not called by the kernel; `gpt_hosttest` and the GPT fuzz harness use it.

### The block request

`request.c` turns a transfer on a sleeping device into requests of at most the device's `max_sectors`, held to `BLOCK_REQ_MAX_SECTORS`, 2048 sectors or 1 MiB. `req_run_one` takes a request, copies a write into its buffer, calls `submit`, sleeps until the request is no longer in flight, and copies a read out. The buffer is the request's own because the device is given its physical address and may write into it after the caller has given up: a frame of the DMA pool (`alloc_kernel_frame`, below `HARD_MEMORY_LIMIT`, 32 MiB) for a page or less, or heap pages (`kalloc_pages_try`) for more, which the controllers are given a page at a time. A request the heap has no room for is asked again at half the size, down to a page.

A request is held by its caller and by its device and freed when both let go. Its `generation`, the next value of a 32-bit counter, comes back with the completion, and a completion for a request no longer live, or of another generation, is dropped and logged. The deadline starts when the request is taken. Its period is the device's `deadline_ticks`, or 3000 ticks, 30 seconds at the 100 Hz tick; `rach2.blockdeadline=S` sets the default to S seconds, 1 to 600. A request past one period is waited for into the next, and is given up only after `deadline_limit` periods in a row, 4 by default, two minutes, so a slow disk is waited for and only a silent one is abandoned. A request given up is quarantined: its caller wakes with `EIO`, and the request and its buffer stay the device's until a late completion frees them, so a late answer never lands in reused memory.

At most 16 requests are live (`REQ_LIMIT`), or N with `rach2.blockpool=N`, 1 to 16, and one device may have at most half of them in flight or quarantined, rounded down and at least one. A request is accounted to `block_submitter` of the device named, so a stick's views share the stick's half. A caller that finds the limit reached, or its device at its half, waits; running out is not an error. Two rules end a wait nothing else would end. A device with quarantined requests and none in flight is marked `BLOCK_STALLED`, and its waiters and later callers get `EIO` until a late completion clears the mark. A waiter that finds every live request quarantined gets `EIO` too. The half per device leaves room for healthy devices beside a stalled one.

`block_request_begin` and `block_request_ended` are a request for a caller that cannot sleep; the USB pump reads a stick's table with them. `block_flush` flushes the device under any views. A device without `flush`, or a write-through disk with no write answered unflushed, returns 0 at once; a caller that cannot sleep flushes a pollable disk by polling, a loop device flushes in the call, and any other device takes a request marked `BLOCK_REQ_FLUSH`. The buffer cache writes its runs with `BLOCK_REQ_NOFLUSH`, letting a write-through disk answer before the data leaves its cache, and ends a durable sync with one `block_flush`. A write without `BLOCK_REQ_NOFLUSH`, and every write through a driver's polled `write`, is on the medium when it returns.

`block_request_flags` counts each transfer that ended well on the device named and on its disk, for `/proc/diskstats`. The drivers count their commands, flushes, status reads and sleeping ticks (`block_count_*` in `block.c`) for `/proc/disk`, so a test can require batching or sleeping without timing either.

### The lag device

`lag.c` is a device for tests. `rach2.blocklag=N` wraps disk 0, for its partition views, `/dev/bootpart` and the mounts on them, in a device without `BLOCK_FAULT_SAFE` (`block_lag_wrap`); the whole-disk window keeps the real device. Its `submit` runs the transfer on the real disk at once, in the caller's context, and `block_lag_tick` delivers the completion N ticks later, then again two ticks after with an error, so a kernel that accepted a stale generation would fail a healthy request. A read's page is filled with `0xEE` until delivery. The wrapper's deadline is one period of 500 ticks, so with N above 500 a request is quarantined; `rach2.lagdeadline=T` and `rach2.lagperiods=N` change the period and the count. `rach2.blockfail=N` fails the Nth write with `EIO`, and `rach2.blockdead=P` builds MBR entry P's view, 1 to 4, over a device that completes nothing, so a stalled device has a healthy neighbour on the same pool. The wrapper's `flush` is delayed too, so a sync takes a request as a stick's does.

### Loop devices

`loop.c` has `LOOP_DEVICES`, 4, `BLOCK_CALLER_SYNC` devices over regular files. `read` is `vfs_read` of the file, `write` is `vfs_write` followed by `vfs_fsync`, so a block the buffer cache has written is in the file, and `flush` is `vfs_fsync`. `backing` is the device of the mount the file is on, and an attachment deeper than `BLOCK_MAX_DEPTH` fails with `ELOOP`. The file's length, a positive whole number of sectors, fixes the sector count, so a short read or write is a device error.

An attachment identifies its file by mount and node, so a hard link is the same file and a second attachment of it fails with `EBUSY`. `loop_attach` claims the slot before anything that can sleep, resolves the path, takes the mount's namespace lock and resolves it again, so a file a KRFFS relocation moved meanwhile is found where it is now; it opens and syncs the file and checks its length and that it is not busy, attached or mapped, under the lock, before publishing the device. The attachment's open description keeps the volume the file is on from being unmounted, and a write, truncation or length change of the file fails with `EBUSY` (`loop_backs`), as do an unlink of it and a rename over it on the KRFFS root. `loop_repoint` follows a node a relocation moves.

When a stick under a loop device is pulled, `loop_device_gone` marks the device `BLOCK_GONE` and tells the buffer cache, so the mount on it can be taken down. A removal may be reported from an interrupt, and letting go of the file can sleep, so `loop_settle` releases it at the next control command or `/proc/loop` read, once no transfer and no mount remain. `LO_FLAGS_AUTOCLEAR` detaches a device at the last close of its node or the unmount that leaves it unused. loop(4) gives the control commands, the ioctls and their errors.

### ATA

`ata.c` drives the two channels of the PC's IDE controller, at `0x1F0` and `0x170` on lines 14 and 15, or at the first IDE controller's base registers for a channel its programming interface puts in native mode. `ata_init` tries primary master, primary slave, secondary master and secondary slave. A drive is a disk when IDENTIFY's status is neither 0 nor `0xFF`, a floating bus, and the LBA mid and high registers are zero, as a packet device's are not. A slave whose IDENTIFY words 10 to 46 equal its master's is the master's echo and is skipped. The sector count is words 100 to 103 on a drive with the 48-bit commands and words 60 and 61 otherwise. Each disk is transport `ata` at location channel times 2 plus drive, `BLOCK_FAULT_SAFE`, with a `max_sectors` of 64.

A transfer uses the controller's bus master when it has one (programming interface bit 7, BAR4) and the drive does DMA (IDENTIFY word 49 bit 8), unless `rach2.atapio` is on the boot line, and the data port otherwise, a sector at a time. DMA moves at most 64 sectors through the channel's 32 KiB bounce buffer, static and aligned to its size so it lies in one 64 KiB region. A caller's bytes are copied into it and out of it in the caller's own context, because a fault-safe device's transfer may not let another process run against the caller's memory, which the page-cache window may evict or remap meanwhile. Each command uses the 28-bit form when its range lies below 2^28 and the 48-bit form otherwise, and each write command is followed by `FLUSH CACHE` or `FLUSH CACHE EXT`, so a write is on the medium when it returns.

A channel takes one command at a time. A caller that can sleep owns the channel from its first register write to its last and sleeps on the channel's queue while another owns it. A page fault with interrupts off cannot wait for an owner that cannot run; it waits for the drive to be idle and uses the data port, which touches none of the bus master's registers. For the same reason the owner issues its DMA command and starts the engine with interrupts off, and every data-port sequence runs with interrupts off, so no caller finds a command not yet started or a transfer in its data phase.

A wait reads the status 8 times, then sleeps when it can (interrupts on, inside a system call, the scheduler running), woken by the channel's interrupt and by `ata_tick`, and fails with `EIO` after `ATA_WAIT_TICKS`, 3000 ticks, 30 seconds. Where it cannot sleep no tick bounds it, so it counts: 256 plain reads, then up to 200,000 rounds of 10,000 `pause` instructions and a read. Under a hypervisor each status read takes the emulator's lock, and the pause leaves it free to complete the command.

### AHCI

`ahci.c` drives the first PCI controller in AHCI mode, through its ABAR, BAR5, mapped uncached. Bring-up requests ownership from the firmware when the controller has the BIOS/OS handoff, and goes on, with a log line, when no answer comes within a second; it resets the controller; and on Intel controllers with device IDs `0x8Cxx` and `0x9Cxx` it sets every implemented port's enable bit in PCS, configuration word `0x92`, without which a port has no PHY. It then resets every implemented port with link power management disabled, and keeps up to `AHCI_DISKS`, 4, ports in port order whose link comes up within a second, whose device is ready within five, and whose signature is `0x00000101`, a disk; a port not kept is stopped again, since its reset turned its FIS engine on. Each kept port has its own command list, FIS area and command table in `.bss`, and is started and identified; the probe fails only when no port has a disk. A disk is transport `ahci` at its port, with a `max_sectors` of 2048 and `BLOCK_FAULT_SAFE`, `BLOCK_POLLABLE` and `BLOCK_WRITE_THROUGH`.

The driver uses command slot 0 alone and a PRDT of up to 264 entries. A buffer whose address is below `HARD_MEMORY_LIMIT`, which only i686's identity window has, takes one entry; any other takes one per page, so a 1 MiB request that starts mid-page takes 257. On a controller without 64-bit addressing (CAP.S64A clear), a piece of a buffer above 4 GiB, which only x86-64's heap has, moves through a page of the DMA pool kept for its table entry (`ahci_piece`); `rach2.dma32` treats any controller so, for a test. Reads are `READ DMA EXT`, writes `WRITE DMA EXT` and then `FLUSH CACHE EXT`. A command fails when the port reports a fatal error, the task file has ERR or DF, or the controller moved fewer bytes than asked, since a short transfer without an error would otherwise pass. The port is then stopped and started again (`ahci_io_error`); an engine that does not stop is a panic, since the controller may still write into the buffer.

A polled command waits in steps of 10 microseconds, 30 seconds with interrupts on and 5 with them off; a write ends with a flush, which a loaded emulator host or a disk spinning up can take seconds for. `ahci_start` moves the disks to the controller's MSI message on an allocated vector, unless `rach2.ahcipoll` is on the boot line, the local APIC is not in use, or there is no free vector or no MSI capability. Each disk then has `submit` and `flush` in place of `BLOCK_FAULT_SAFE`, and its requests wait in its own queue, oldest first. The interrupt judges the active command, then issues the flush half of a write or completes the request and starts the next, so two disks proceed independently. A write with `BLOCK_REQ_NOFLUSH` completes after its transfer and sets `unflushed`. A polled command on a queued disk first finishes the active command by polling (`ahci_drain`) and starts the queue again after its own.

### NVMe

`nvme.c` drives up to 4 NVM Express controllers, each with an admin queue and one I/O queue pair. `nvme_map` maps BAR0 with the INTx line off and MSI-X on with every vector masked, because the I/O queues are made with interrupts enabled and a controller may tie a queue to its vector only while MSI-X is on. A BAR0 the kernel cannot map, on i686 one above 4 GiB, makes the controller unusable. Every page a controller is given, the queues, an identify page, a bounce page and a PRP-list page for each of 8 command slots, is kept for the life of the kernel, since a failed controller may still write into it.

`nvme_bring_up` requires the NVM command set and a 4 KiB page, sizes the I/O queue at most 16 entries and its slots at most 8, disables the controller, programs an admin queue of 8 entries, enables it, identifies it, and creates the I/O completion queue, with interrupts on vector 0, and then the submission queue. Namespaces come from the active namespace list, or every identifier up to the count without one, 16 at a time and at most 1024 examined; a namespace with 512-byte blocks and no metadata is published, at most 4 a controller, as transport `nvme` at location controller times 4 plus its place. An admin command not answered leaves the controller disabled and out of use. A controller brought up once is not reset by a later `nvme_init`, since its namespaces may be mounted.

A command's identifier has its slot in the low three bits. The first PRP entry is the buffer's start, and the second the next page or, past two pages, the slot's list of the rest; a buffer not aligned to four bytes moves a page at a time through the bounce page with interrupts masked. A namespace's `max_sectors` is 8 times 2 to the power MDTS, or 2048 when MDTS is 0 or above 7. A namespace starts as `BLOCK_FAULT_SAFE`, `BLOCK_POLLABLE` and `BLOCK_WRITE_THROUGH`. A write goes with FUA, which puts its own blocks on the medium and no others (NVMe 1.4, Figure 406), so a write while the disk is marked `unflushed` is followed by a Flush. An error status fails the transfer with `EIO`. Polled commands wait as AHCI's do. A command not answered in time, or every slot busy for that long, starts `nvme_recover`: disabling the controller aborts every command in flight and is the one way to be sure it writes into none of their buffers again; each request in a slot then completes with `EIO`, and the queues are made again. A controller that does not stop is a panic; one that does not come back is out of use.

`nvme_start` moves each controller to its MSI-X entry 0, or to MSI, on a vector of its own, unless `rach2.nvmepoll` is on the boot line, the local APIC is not in use, or there is no free vector or neither capability; the namespaces then have `submit` and `flush` and keep their polled functions. Requests wait in their namespace's queue, and a controller's namespaces take its free slots in turn. A write with `BLOCK_REQ_NOFLUSH` goes without FUA, sets `unflushed` and counts one more in `wseq`; one without it goes with FUA and, while the mark is set, has a Flush issued in its slot before it completes. A Flush clears the mark when it ends well and no write was answered unflushed while it ran, not when it is issued, so a second caller's `block_flush` sees the mark and waits on a flush of its own.

### The USB stick as a disk

`usbdisk.c` makes each logical unit the mass-storage driver brings up a disk. The unit's device (`usb/msc.c`) has `submit` and no `read` or `write`, a `flush` that sends SYNCHRONIZE CACHE, a `max_sectors` of 1024, a 10-second deadline period, and `BLOCK_READ_ONLY` when write-protected. `bring_up` registers it as transport `usb` at location slot times 4 plus the unit, with its model from INQUIRY, its serial from INQUIRY's unit serial page, and `removable` set; there are `USBDISK_MAX`, 8, records.

The class driver reports a stick from the pump, which the timer runs and where nothing may sleep, so the table is read without sleeping. `part_scan` runs over a cache of up to 96 sectors, enough for sector 0, both GUID headers and arrays, and an extended chain. A pass that needs a sector the cache lacks is dropped, `block_request_begin` starts a read of a page at most, and later passes ask after it with `block_request_ended` and run the scan again, until a pass needs nothing new. One stick is read at a time. Then `disk_set_table` makes the views and `devfs_disk_publish` the whole-disk window, whatever the table was.

Registering and reclaiming change what a process inside a system call may be using, so they run where no system call is in progress: at a system call's entry (`usbdisk_service`) or on a pump pass that did not interrupt one (`usbdisk_step`). `usbdisk_left` marks a stick closing; closing hides its nodes and tells the loop devices and the buffer cache that every view has gone. The record is reclaimed when no scan is reading it and `usbdisk_holds` counts nothing: no open node, request, mount or held buffer on the device or a view. Reclaiming releases the disk number and the class driver's slot, unless another unit of the same device still has a record.

### Disk information

`diskinfo.c` writes `/proc/disk`, whose format proc(5) gives. Its first record has disk 0's IDENTIFY strings and its sector 0, parsed as an MBR by `diskinfo_probe`, which uses `block0` when a disk is up and probes only when none is, so the diagnostic never resets a controller under a mounted root. The counters precede the record and the registry's lines follow it. The formatting is pure, and `diskinfo_hosttest` renders records no device produces.

### Disk write policy

Which kernel may write which disk is fixed when the kernel is built, by two independent switches, because a boot-line token can be edited at the GRUB prompt. The ordinary kernel, `rach2`, has neither. The metal kernel, `rach2-metal`, is built with `-DRACH2_DISK_READONLY`; the recovery kernel, `rach2-recovery`, with `-DRACH2_RECOVERY` and the read-write driver policy (`Makefile`).

`RACH2_DISK_READONLY` is enforced in the drivers by `diskcmd_allowed` (`diskcmd.c`), where each command leaves for the device. It allows `READ SECTORS` (`0x20`), `READ SECTORS EXT` (`0x24`), `READ DMA` (`0xC8`), `READ DMA EXT` (`0x25`) and `IDENTIFY` (`0xEC`). Any other command byte is not issued: the driver logs `refused: command 0xNN: rach2: disk policy: read-only` and the transfer fails. It is a list of what is allowed, so an omission costs a failed read where an omission from a list of what is forbidden would cost a written disk. ATA checks every command in `ata_command`, and AHCI in `ahci_build_command`, which builds every command it sends. NVMe judges each I/O command in `nvme_build` by its ATA counterpart, a Read as `READ DMA EXT`, a Write as `WRITE DMA EXT` and a Flush as `FLUSH CACHE EXT`, and Identify as `IDENTIFY` in `nvme_identify`; the admin commands that set up its queues touch no medium and are not judged. The USB driver and the loop devices are not judged, so the metal kernel writes a stick. `tools/inspect/check_diskpolicy.sh` reads `diskcmd_policy_banner`, `rach2: disk policy: read-only` or `read-write`, from the built kernel; the boot logs `disk: policy:` and `/proc/disk` has a `policy` line.

`RACH2_RECOVERY` selects the write handler of every whole-disk and partition node, of every transport, in devfs (`dev_disk_write` in `fs/devfs.c`). Without it the handler returns `EPERM` and has no other path. With it the handler writes the window and checks at each write that the effective user ID is 0, since a process can open the node as root and drop privilege afterwards. The switch also makes `recovery_publishes_disk` return 1, which has the boot probe for a disk and puts the partition nodes under the writer reservation, and compiles the debug shell's `disk write`, which writes, flushes and reads back disk 0's last sector when neither LBA 1 nor that sector has a GUID header and no MBR entry covers it. `tools/inspect/check_recovery.sh` reads `recovery_policy_banner`, `rach2: disk authority: recovery` or `ordinary`.

`/dev/bootpart` and `/dev/grubcore` take writes from effective user ID 0 in every build, so an everyday kernel can install a kernel or replace GRUB's core. Their writes go through the drivers, so the metal kernel's policy applies to them as to every other write to its disks.

| What is written | Ordinary | Metal | Recovery |
| --- | --- | --- | --- |
| `/dev/diskN`, `/dev/diskNpM` | `EPERM` | `EPERM` | by root |
| `/dev/bootpart`, `/dev/grubcore` | by root | no write is issued | by root |
| a mount or loop device on an ATA, AHCI or NVMe disk | yes | no write is issued | yes |
| a mount or loop device on a stick | yes | yes | yes |

Beside the authority is the writer reservation, `writer_held` in `struct disk`: one write-capable open at a time across a disk's whole-disk node and boot windows in every build, and its partition nodes on the recovery kernel, and none over a range a mount claims (`devfs.c`). A stick with `BLOCK_READ_ONLY` mounts read-only, and a raw write to it fails with `EIO`. disk(4) gives these rules as a user meets them.

## Limits

* Sectors are 512 bytes. ATA and AHCI do not publish a drive whose IDENTIFY word 106 gives another logical sector size, nor NVMe a namespace of another block size, 4096 bytes among them, or with metadata.
* The counts are fixed: 8 disks, 15 partitions a disk, one extended partition an MBR, 128 GUID entries in 16 KiB, one IDE controller of 4 drives, 4 AHCI disks of the first AHCI controller, 4 NVMe controllers of 4 namespaces, 8 sticks, 4 loop devices and 16 live requests.
* An ATA drive without the 48-bit commands is used to 2^28 sectors, 128 GiB, and on i686 an NVMe controller whose BAR0 is above 4 GiB is not used.
* There are no packet devices, port multipliers, SATA hot-plug or native command queuing; no NVMe namespace management, shutdown notification at power-off or scatter-gather lists; and NVMe has one I/O queue pair however many processors there are.
* No I/O scheduler merges or orders requests, and no discard command is issued.
* A stick whose table needs more than 96 sectors to read has no partitions, and a loop device has no offset, size limit or encryption.
* A polled transfer keeps the processor until it ends. Before `ahci_start` and `nvme_start`, and under `rach2.ahcipoll` or `rach2.nvmepoll`, every transfer is polled.

## Tests

`tests/run host` compiles the layer's pure code and its drivers natively under AddressSanitizer and UndefinedBehaviorSanitizer; [tests/host/Readme.md](../../../tests/host/Readme.md) lists each test's rows. These compile `block/` sources:

* `block_hosttest.c`: partition views and their bounds.
* `lag_hosttest.c`: the lag wrapper's queue under a transfer that sleeps.
* `mbr_hosttest.c`, `gpt_hosttest.c`, `partition_hosttest.c`: the MBR judgements, every GUID header rule, and the partition service over disks in memory, with logical partitions, a GUID table from either header, `part_gpt_as_mbr` and `part_bios_boot`.
* `ata_hosttest.c`, `ahci_hosttest.c`, `nvme_hosttest.c`: each driver against a model of its hardware, with waits, resets and commands that never end, sector sizes other than 512, and recovery.
* `diskcmd_hosttest.c`: all 256 command bytes under both policies.
* `diskinfo_hosttest.c`: IDENTIFY strings, 64-bit decimal and the `/proc/disk` record.
* `usbdisk_hosttest.c`: a stick's registration, table scan, pull, holds and reclaiming.
* `loop_attach_hosttest.c`, `open_hosttest.c`: loop attachment across a KRFFS relocation.
* `devfs_hosttest.c`: where `/dev/grubcore` is published.
* `bcache_hosttest.c`, `bcache_cost_hosttest.c`, `fat32_hosttest.c`, `exfat_hosttest.c`, `ext2_hosttest.c`: link `chain.c`.

`ata_identify_mutate.sh`, `ata_durable_mutate.sh`, `ata_wait_mutate.sh`, `ata_rate_test.sh`, `dma32_mutate.sh`, `grubwindow_mutate.sh` and `loop_attach_mutate.sh` in `tests/host/` prove rows of these tests against faults. `request.c` has no host test; the suites reach it.

`tests/run NAME` runs a system suite under QEMU, `RACH2_WORKERS=4 tests/run A B C` several, and `ARCH=x86_64` the other architecture; [tests/system/suites.md](../../../tests/system/suites.md) gives each suite's tier and needs. Those that cover this layer:

* ATA: `disk` and `persist` (core); `stress`, `bus` and `load` (full), `load` with `rach2.atapio`.
* AHCI: `disk-ahci`, `disks` and `queue` (core); `disk-q35`, `persist-ahci`, `stress-ahci` and `bootorder` (full). `queue` covers the interrupt path beside the fault path, a late answer under `rach2.blockdeadline=1`, and `rach2.blockpool`.
* NVMe: `uefi` (full), which installs onto a 4 TiB NVMe disk and boots it.
* Partition tables and identities: `parts` (core).
* The request pool and the lag device: `mount`, `fatwrite` and `exfat` (core), `krffsmount` (full).
* Sticks: `usbdisk` (core). Loop devices: `ext2` (core), `loopdev` (full).
* The write policy: `authority` and `metal` (core), `diskpolicy` and `diskdiag` (full).
* The raw and boot windows: `grub` (core); `bootpart`, `menu`, `install`, `drill`, `sealed` and `uefi` (full).

# `block/`: the disk layer and its two drivers

One disk, reached two ways. Every byte of a file system in Rach2 that does not live in the RAM module comes off a real disk through a single device, `block0`, behind a four-call vtable. Two drivers can publish that device: `ata.c`, the readable polled-PIO bring-up driver for the legacy IDE channel, and `ahci.c`, the modern SATA driver that covers most real hardware. They are siblings the way the audio drivers are: the PC speaker and SB16 are to the HD Audio controller what ATA PIO is to AHCI. The readable one shipped first and stays as the documented fallback; the modern one goes in beside it, behind the same interface, and nothing above the interface can tell which is underneath.

## The interface

`block.h` is the whole contract. A `block_device` is a sector size, a sector count, and `read`/`write` that move `count` whole 512-byte sectors to or from a buffer and return `0` or a negative errno. The one published instance is `block0`. Above it sit, in order, the MBR parse (`mbr.c`, a pure four-entry table reader plus the judgement that qualifies a FAT-typed partition 1 as the boot partition, both host-tested in `tests/host/mbr_hosttest.c`), the KRFFS root-probe and `block_partition_init` (a partition is just a `[start_lba, start_lba + count)` view that adds the offset and bounds-checks each request), the demand-paged page cache and its window, KRFFS, the dirty-mount flag, and fsck. None of them name a driver. They call `block0->read` and `block0->write`, so adding AHCI added a second producer of `block0` and changed nothing above it.

The defining clause of the contract is that `read` and `write` "are synchronous and polled: a caller may invoke them with interrupts off and without the scheduler running." That sentence is not a convenience. It is what lets the page-cache window fault use the disk at all.

## Why the I/O path polls

The page-cache window fault is the hot caller, and it runs in a place that cannot sleep. A miss on the demand-paged window at `PCWIN_BASE` (0xD0000000) is a page fault, delivered through a 32-bit interrupt gate: the CPU clears `IF` on entry and the kernel never re-enables it on the fault path. So `pc_fault` and the `block0->read` beneath it run start to finish with interrupts off. The only sleep primitive, `wq_wait_event`, would `sti; hlt` in the middle of an exception, and a fault that yielded would also break the no-yield invariant the disk milestone leans on (a fault that never sleeps keeps KRFFS metadata mutations atomic without a file-system lock).

A timer cannot bound a wait with interrupts off either, so the drivers bound their waits without one. ATA counts iterations; AHCI measures against the 8254 through `k_udelay`, so its budgets are stated in microseconds and mean the same on any processor: a wedged or absent device makes the watchdog expire and the call returns `-EIO`, and the fault handler then panics fail-closed rather than hang. ATA polls its status register; AHCI polls a memory-mapped completion bit. Neither ever waits on an interrupt.

This is why AHCI here is driven by polled completion. AHCI is normally DMA plus a completion interrupt, and the completion interrupt is exactly what the fault path cannot service. The way out is to keep the DMA and drop the interrupt: mask the HBA interrupt (`GHC.IE` and `PxIE` stay clear), set the command's bit in `PxCI`, and busy-poll `PxCI` until the HBA clears it, watching the fatal `PxIS` bits (task-file error, host-bus fatal, host-bus data, interface fatal) and, once the bit clears, `PxTFD` ERR/DF for failure, all under the same bounded-iteration watchdog ATA uses. A fatal `PxIS` error can clear `PxCI` without setting `PxTFD.ERR`, so completion tests both, and then checks the byte count the HBA wrote back into the command header: a completion that moved fewer bytes than requested without raising an error is a failure too, since a short write that later gets marked clean would be silent data loss. The HBA still does the transfer in hardware; the CPU only spins on a status bit in memory. So a 4 KiB miss stalls the machine for one DMA, not for 256 `insw` per sector as PIO does, which makes AHCI the faster of the two on the stall it cannot avoid.

## Polled vs IRQ vs async

Polled completion is a deliberate choice, and the alternative is a deliberate deferral, not an oversight.

* Polled (what this is). The fault path is unchanged: no interrupt, no `sti`, no wait queue, no allocation on the I/O path. The cost is real and accepted: a cache miss stalls the whole machine for one transfer. For a teaching kernel with a small working set this is the right trade, and it is the same idiom the HD Audio driver already uses for the same reason (legacy PCI interrupt delivery here is unreliable, so even audio polls).
* IRQ-driven. Enabling `PxIE`/`GHC.IE`, taking the completion interrupt, and waking the faulting requester on a wait queue would force the fault path itself to become sleepable, which the interrupt-gate design forbids today. It would mean reworking the window fault, giving KRFFS a real lock (the fault no longer being atomic for free), and trusting an interrupt path that the hardware here delivers unreliably. It buys nothing for this working set.
* Asynchronous (NCQ, many in-flight commands, a request queue). That is a separate, larger effort, essentially "make the kernel's disk I/O asynchronous," best done as its own milestone behind a real VFS and locking layer, not smuggled into a driver bring-up.

So IRQ and async stay out on purpose. Whoever revisits them starts from this analysis rather than rediscovering the constraint.

## The AHCI driver

`ahci.c` is the polled path made concrete, reusing the HD Audio driver's PCI and DMA idioms with storage registers swapped in.

* Bring-up. Discover the HBA on the PCI bus (class `0x01`, subclass `0x06`, prog-if `0x01`), recover the ABAR from BAR5 (not BAR0), map it cache-disabled, enable memory decoding, mask all interrupts, quiesce every implemented port, select the first port with a device and the link up, program the command-list and received-FIS bases, enable bus mastering, and start the engine. The HBA-wide reset (`GHC.HR`) is issued and waited out, and each implemented port is then COMRESET during the scan. That order matters and was learned on hardware: an HR alone leaves the SATA link needing re-establishment and the device not ready, which is why the reset was skipped entirely until the COMRESET existed to follow it.
* A transfer. One command slot, one Register Host-to-Device FIS, one PRDT entry. `READ DMA EXT` (`0x25`) and `WRITE DMA EXT` (`0x35`) carry a 48-bit LBA; a write is followed by `FLUSH CACHE EXT` (`0xEA`) so the data reaches durable media, the durability the dirty-flag and `pc_sync` write-back rely on. The page cache issues exactly 4 KiB (eight sectors) per call, which one PRDT entry covers; a larger request fails closed rather than silently truncating. On a failed or timed-out command the driver recovers the port in place (stop the engine, clear the latched errors, restart it) per AHCI 6.2.2 error recovery, then returns `-EIO`, so the next command does not issue on a stopped engine.
* DMA memory. The command list, received-FIS area, and command table are static `aligned` arrays in `.bss`, which lands below the 32 MiB identity-mapped limit, so the virtual address is the physical DMA address with no translation and the bytes are contiguous below 4 GiB. `ahci_dma_sync` flushes descriptors before issue and invalidates the read buffer after, a real-hardware requirement that is a no-op on the cache-coherent x86 DMA both QEMU and real hardware provide.

`block_probe` is where that choice is made: with `rach2.disk=ahci` it brings up AHCI (falling back to ATA if no HBA answers), and without the flag it brings up ATA, so every existing IDE image boots byte-for-byte as before. The two drivers never fight over one image, because the ATA driver refuses a SATA signature and an AHCI-only disk is invisible to it.

## Two levels of disk authority

Milestone 25 splits the authority to write this machine's disk in two, and the split is decided when the kernel is built rather than when it boots.

Level one is the boot partition and the boot loader's gap, the two bounded windows `/dev/bootpart` and `/dev/grubcore`. Every image may write them, because installing a kernel and updating GRUB are ordinary work, and a machine sealed shut has to be able to do both remotely.

Level two is the whole device at any offset, through `/dev/disk0`. That is what reflashing a broken root needs and what an everyday boot has no business being able to do at all: a mistake there destroys the machine rather than one file. So an everyday kernel compiles a write that returns `-EPERM` with no path around it, and only a kernel built with `-DRACH2_RECOVERY` compiles one that can write. `recovery.c` has a banner naming which build it is, `tools/check_recovery.py` reads it back off the artifact in both directions, and `make authority-test` boots both kernels against one image: the everyday one must refuse and leave the sector unchanged, the recovery one must write past 2 GiB and read it back.

This is deliberately not `RACH2_DISK_READONLY`, and could not be. That switch is enforced below devfs, in the drivers' command allowlist, so a kernel carrying it cannot write the boot partition either, and both builds need to. The two are independent: the recovery switch decides only whether devfs exposes a writable whole-disk node.

Every raw transfer passes through one 32 KiB staging buffer in `.bss`, sixty-four sectors at a time, which is one command for both drivers. The size is what makes a whole-disk reflash finishable: one sector per call turned a 500 MiB write into about a million driver calls, and both drivers flush the drive's cache after every write command, so it was a million cache flushes too. Batching is invisible from outside, since a transfer returns the same answer however many commands it took, so `/proc/disk` reports the batch size and a live count of driver calls and the test requires four calls for two hundred sectors rather than two hundred.

Callers go through `block_ready` rather than calling `block_probe` directly. It answers from `block0` when a disk has already answered, so a working controller is never reset a second time by the three paths that each want one: the boot-time device discovery, the disk mount, and the diagnostic. A failure is deliberately not remembered, because a controller that did not answer at boot must still be askable from the rescue shell, which exists for exactly that.

The rescue shell's `ahci` command is the one path that re-initialises a controller on purpose. `ahci_init` clears `block0` and the HBA globals before resetting, so any raw window published over the old device would be addressing a driver with no port. The command takes all three down first (`/dev/bootpart`, `/dev/grubcore` and `/dev/disk0`) and republishes from whatever answers, on the failure path as much as the success one: a re-probe that finds nothing must leave a machine with no raw windows rather than three that name a controller which has been reset out from under them.

## Compared to Linux

Linux `drivers/ata/libahci.c` enables per-port interrupts, issues commands into a tagged queue, and completes them in an interrupt handler that wakes the block layer; the block layer merges and schedules requests across a deep queue. Rach2's AHCI is that driver with the queue depth set to one, the interrupt removed, and the completion handler replaced by a bounded spin on `PxCI`, because its one caller runs in a context that cannot take the interrupt. The ATA driver is the same shape one register set down: Linux's `libata` PIO path, polled and single-sector-handshaked, with no IRQ.

## Reset, and what a port is carrying

Bring-up resets the HBA (`GHC.HR`) and then COMRESETs every implemented port. The reset was skipped until milestone 24 and for a good reason: an HBA reset leaves every SATA link needing re-establishment, and without a COMRESET to re-establish it the port reports a device that never becomes ready (on QEMU's `ich9-ahci` the task file loses DRDY, 0x50 becoming 0x130). With the COMRESET the driver can get out of that state, so the reset is worth having: a machine hands the HBA over from firmware that has been using it, and the only way to know what state the registers are in is to put them in a known one. It is also the recovery for the failure the target laptop shows after a warm reboot, a SATA link that comes up dead.

A COMRESET is DET=1 held for at least a millisecond, then DET=0 and a bounded wait for the PHY to negotiate. Two details are easy to get wrong and were: the received-FIS area must be programmed and `PxCMD.FRE` enabled BEFORE the reset, because the device answers with a FIS carrying its signature and a FIS arrives only if the port has somewhere to put it and is listening; and `PxSIG` must not be read until the task file says the device has finished its own reset, since before that it reads as all ones, which is not a signature but a port that has not answered yet.

The scan is then tolerant by construction. A port with nothing on it never reaches DET=3 and is skipped without comment, since most machines have some. A port whose device never becomes ready is skipped rather than waited on. And only the plain SATA disk signature (`0x00000101`) is taken: an optical drive answers the ATAPI signature and would fail every command this driver knows, and a port multiplier and an enclosure service answer their own. Naming the one signature this driver drives, rather than excluding the ones it happens to know about, means an unfamiliar device is skipped rather than driven as if it were a disk.

The waits here are measured rather than counted, through `k_udelay`, because what they wait for happens on the wire and inside the device rather than at the processor's speed: one second for the PHY, five for the device's own reset.

## Reading a disk without mounting it

The metal machine must be able to say what its SSD is, how big it is and what its partition table holds, and to hand out any sector for hashing, without mounting anything: the disk-root mount stamps a dirty flag, and that is a write. `rach2.diskdiag` on the boot line publishes two read-only objects and nothing else happens without it, so no image grows a raw whole-disk node by accident.

`/proc/disk` is what the drive said about itself, one fact per line: state, driver, port, the build's disk policy, whether the root file system is on this disk, model, serial, firmware, sector size, sector count, the window size, the raw batch size, the raw driver-call count, the disk-command and cache-flush counts, and the four MBR entries. Most are rendered from a record taken once at boot, so opening it issues no command. Four are live and read when the file is opened: the raw batch size, the raw driver-call count, and the counts of disk commands and cache flushes. A count of what has happened since boot would be useless if it were taken at boot. The identity comes from the ATA IDENTIFY response both drivers already ask for and both used to discard; `diskinfo.c` keeps it, un-swapping the big-endian-within-a-word strings, trimming the padding the device does not terminate, and replacing any byte outside printable ASCII with a question mark, because what parses this file is `awk` and `grep` on the machine and a device that answered with a newline would otherwise split a line.

`/dev/disk0` is the whole disk as a root-only sector window, readable on any kernel and writable only on the recovery build, and it is the only raw node that still needs `rach2.diskdiag`: `/dev/bootpart` and `/dev/grubcore` are published by disk discovery on every boot that has a disk and a usable table, because managing a boot partition is not a diagnostic. Sector hashes are computed in userland: `dd if=/dev/disk0 bs=512 skip=2048 count=8 | sha256sum`. A SHA-256 in the kernel would duplicate the `sha256sum` the image already has, and hashing on the machine the same way the host does means the two numbers are comparable. Writes are refused four times over and each refusal stands alone: the 0400 mode fails an `open` for writing, the descriptor has no write flag, the node's own write returns `-EPERM`, and under the metal build the driver's allowlist refuses the command. (The mode is the weakest of the four and is not the barrier for root, whose credential check passes whatever the mode says; the other three are.)

The window reached only the first 8388607 sectors until milestone 25, because an open file's offset was 32 bits and the byte just past that sector is the largest one such an offset can name. The raw disk windows now seek and transfer through a separate 64-bit offset, so the window covers whatever the drive reports, up to a chosen ceiling of 2^32 sectors, which is 2 TiB. That ceiling is the window's own rather than a driver's: the ATA path stops earlier at its 28-bit LBA, and AHCI programs a 48-bit one and could go further. `/proc/disk` still prints the disk's real size beside the window's, so on a larger disk the two numbers disagree visibly rather than one of them quietly lying. `make bootpart-test` reads a marker at 258 GiB of a sparse 260 GB drive over AHCI, which is the size that makes the difference visible: a few gigabytes would be satisfied by an implementation keeping 33 bits.

`make diskdiag-test` proves it on three boots of one freshly built image: the ordinary kernel mounting it, which must change it, since otherwise the comparison could not detect a write at all; the read-only kernel reading it over SSH with nothing typed at the console, where every sector hashed on the machine must equal the same offset hashed on the host; and the same kernel with no drive attached.

## The read-only build

Milestone 24 takes this kernel to a laptop whose SSD holds a Windows installation its owner has not backed up, and until a carved partition is approved after a full backup, nothing this kernel does may write that disk. A promise of that size cannot rest on remembering not to call the write path, so it is enforced in one place per driver and decided when the kernel is built.

`diskcmd.c` holds an allowlist, and both drivers consult it where a command leaves them for the device: `ahci_run_command` in `ahci.c`, and `ata_command` in `ata.c`. Under `-DRACH2_DISK_READONLY` only `READ SECTORS`, `READ SECTORS EXT`, `READ DMA EXT` and `IDENTIFY` are permitted; everything else is refused, including commands this file has never heard of, for the same reason a write is: nothing knows what an unknown command would do to somebody else's disk. It is an allowlist rather than a list of forbidden commands because a list of refusals is one somebody has to keep complete, and the cost of a missing entry is the disk this exists to protect.

A build switch rather than a boot flag, because a boot flag is editable at the GRUB prompt by whoever is sitting at the machine. The two kernels are built into two object trees (`build/rach2/` and `build/rach2-metal/`, the second from `make rach2-metal`), and a tree refuses to be rebuilt with different flags rather than mixing objects from both: make decides what to recompile from timestamps, which say nothing about compiler flags, so a tree built twice with different switches would link some objects from each and produce a kernel that reports one policy and enforces the other.

Which policy an artifact has is read off the artifact. Checking for the absence of a write path would prove nothing, since the commands are numbers and the functions that issue them are static, so `diskcmd.c` has a banner naming its policy, the kernel prints it at boot, and `tools/check_diskpolicy.py` requires the expected banner present and the other absent. `make diskpolicy-test` then shows it on the bytes: the same freshly built disk is booted with each kernel, the ordinary one must mount and change it (which is what makes the other half mean anything), and the metal one must refuse a command by name and leave the image byte for byte as it was.

## Deliberate simplifications

* One command slot, polled, no NCQ: all the page-cache fault path ever issues.
* One PRDT entry per command: every caller hands it an identity-mapped, page-aligned, physically contiguous buffer. The page cache supplies one page; the raw disk windows supply a 32 KiB staging buffer in `.bss`, declared page-aligned for this reason and sized so one command has sixty-four sectors. A caller whose buffer was not aligned or not contiguous would need a multi-entry PRDT or a bounce buffer of its own.
* First present port only, single disk: there is one `block0`, like the rest of the storage stack.
* 512-byte logical sectors, asserted: KRFFS sector math assumes them.
* No hot-plug, no port multipliers, no ATAPI: the driver scopes to a fixed boot or data disk.
* `GHC.HR`, the COMRESET handshake and staggered spin-up are all implemented, and were the deferrals this driver carried until the laptop needed them. QEMU's model comes up without any of the three, which is why they could be deferred and why their absence was invisible until real silicon.
* The BIOS/GRUB boot stays on the legacy IDE channel, since GRUB uses INT 13h and not this driver, and this driver takes over once the kernel is running. A full boot through GRUB with the disk on an AHCI controller is proved: `make sealed-test` boots the sealed disk attached to an `ich9-ahci` with no `-kernel`.

## Verify

The disk probes run on a real disk, never the RAM module, and each has an ATA form on `if=ide` and an AHCI form on an `ich9-ahci` HBA selected by `rach2.disk=ahci`:

* `make test-disk` / `make test-disk-ahci`: `blockprobe` writes a working set larger than the resident cache, fsyncs, and reads it back byte for byte, so a dropped-dirty or mis-mapped page is a mismatch, not a crash. Token `BLOCKPROBE OK`.
* `make persist-test` / `make persist-test-ahci`: `persistprobe` writes and fsyncs `/persist.txt` on one boot and reads it back on the next, proving the write reached the disk. Tokens `PERSISTPROBE OK (wrote)` then `PERSISTPROBE OK (read back)`.
* `make stress-test` / `make stress-test-ahci`: `stressprobe` writes and re-reads 33 MiB, past the 32 MiB RAM cap, proving a file system larger than memory round-trips through the cache. Token `STRESSPROBE OK`.

The capstones run over AHCI by booting `os-real` from a SATA disk (`DISK=... DISKBUS=ahci ./run.sh`): the SSH login (`ssh -i krffs/rach2_demo_ed25519 -p 2222 root@localhost`) reaches an interactive busybox ash over a dropbear pty, and Doom reads `doom1.wad` off the AHCI-mounted root and runs. At the kernel debug shell, `ahci` brings up the HBA, dumps its registers, and reads the MBR over the polled path as a one-shot self-test.

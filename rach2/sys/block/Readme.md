# `block/`: disk access

The block layer publishes one whole-disk device as `block0`. The legacy ATA driver and the AHCI driver implement the same synchronous, sector-addressed interface. MBR discovery, KRFFS, the page cache, and the raw disk devices use that interface without selecting a driver. The mounted file systems reach it through `block_request`, the one entry that also serves a device that sleeps its caller. The layer, the partition parser, the raw windows and the file systems count in 512-byte sectors, so a drive whose IDENTIFY word 106 says its logical sector is another size is refused by name by both drivers and no node is published; this is a restriction, kept as one, and `ahci_hosttest` proves the refusal with IDENTIFY words that name a 4096-byte sector.

## Block devices and partitions

A `block_device` reports a sector size, a 64-bit sector count, two transfer functions, and private driver data. Rach2 supports 512-byte sectors. A read or write moves a positive number of complete sectors and returns zero or a negative error. Requests that start at or past the device end, cross the end, or contain zero sectors fail.

A device with `BLOCK_CALLER_SYNC` is the third kind: it sleeps the caller and answers within the same call, which is what a loop device over a file does, and it is called directly, in syscall context only, taking no request. A sleeping device under it takes a request while it waits. Allocating requests at both levels could reach the limit with every outer transfer waiting for an inner transfer that cannot allocate a request. A file on the memory root has no such device under it, and one on a fault-safe device takes no request either; the rule is written for the case that does. A device of this kind reached where there is no syscall to sleep in stops the machine, as a sleeping device does.

A device may name the device its bytes live on. `block_depth` counts that chain and `block_is_below` says which of two devices is under the other; both are in `chain.c`, which has no drivers in it so that the cache's tests can link it. A chain may be one long: a loop device stands on a real device and nothing stands on it, because a file system on a loop device holds a buffer of it while the file system under it holds two of the disk, and a second loop device in the middle would want more buffers than a process may hold. An attachment that would make a longer chain answers `ELOOP`. The count is of backing devices and not of loop devices: a file on the memory root has no device under it, so a loop device over such a file is at depth zero and one more may stand on that.

A device with the `BLOCK_FAULT_SAFE` flag completes its transfer functions from any context: with interrupts off it polls, without allocating or scheduling, and from a system call it may sleep its caller until the device answers. ATA retains the flag; AHCI clears it when it enables interrupts and queued requests. The page-cache window requires polled transfers: a supervisor page fault enters through an interrupt gate with interrupts disabled, then may read or evict a 4096-byte page through the block device. AHCI retains its polled `read` and `write` functions after the switch, so an existing disk-root window continues to use them directly. A device with `BLOCK_POLLABLE` answers a polled `read` or `write` from any context with its queue drained first, and `block_request` takes that path for a caller that cannot sleep, a page fault with interrupts off; a sleeping device without the flag reached from such a caller is a kernel panic. A fill that cannot be completed causes an unrecoverable page-cache fault. A failed writeback remains dirty and is reported by `pc_sync`.

`block_ready` returns an existing `block0` or calls `block_probe`. A failed probe is not cached. `rach2.nodisk` prevents every probe. Otherwise `block_probe` runs both drivers, AHCI first, and each registers the disks it finds. The first disk found supplies `block0`; the probe fails only when neither driver finds a disk. `rach2.disk=ahci` is accepted and has no effect.

`block_partition_init` creates a half-open view of a backing device. It adds the partition start to each request and clamps a view that extends past the backing device. A start past the device produces an empty view. Every view has a `submit` forwarder, which checks the range, adds the partition offset, and forwards the same request; it returns `-EIO` if the backing device has no `submit`. `block_flags` follows any chain of partition views and returns the backing device's current flags. `block_request` uses those flags to select polled transfers or queued requests, so a view created at boot follows an AHCI disk when it enables interrupts.

## The partition service

`partition.c` reads the partition table of every registered disk through a sector-read callback. After the drivers register their disks, `block_probe` calls `disk_scan` for each one. Each disk has a `part_table` and one view per accepted entry. The scan reads through the physical device; disk 0's views use the lag device when `rach2.blocklag` is set. An unreadable sector zero produces `PART_UNREAD`; a sector without the `0x55AA` signature, or a signed table with no entries, produces `PART_NONE`. The service keeps at most `PART_MAX` (15) partitions per disk. Entries outside the permitted range, overlapping an earlier accepted entry, or beyond that limit are refused and counted. The registry reports the count as `disk: diskN: K partition entries refused`.

An MBR records the disk identifier at bytes 440 through 443 and numbers its primary entries 1 through 4 by position. One entry of type `0x05`, `0x0F`, or `0x85` may describe an extended partition; a second is refused. The service follows its chain of extended boot records. Each record's first entry describes a logical partition relative to that record, and its second describes the next record relative to the extended partition's start. Logical partitions are numbered from 5 in chain order; the extended entry itself has no partition view. An unreadable or unsigned record, an absent or invalid next link, or the limit of `PART_MAX` records ends the scan. The record limit also bounds a looping chain. A logical partition must lie after its record and within the extended partition.

A protective MBR with type `0xEE` in its first entry selects GPT. The service checks the primary header at LBA 1 with `gpt_header_ok` and reads the complete entry array before checking its CRC32. If either fails, it tries the backup header at the disk's last sector and that header's array. A successful backup is recorded and logged; failure of both copies produces `PART_GPT_BAD` with no partitions. Accepted entries retain their array positions as partition numbers, counted from 1, their type and partition GUIDs, and their names. Names contain at most 36 UTF-16 units, converted to printable ASCII with `?` for other characters and trailing spaces removed. The table also records the disk GUID. GPT extents must fit the usable range and overlap no accepted entry; the service imposes no 32-bit LBA limit.

## The loop device

`/dev/loop0` to `/dev/loop3` are the block layer's devices over regular files, so a file system can live in a file: an image on a disk, on a stick, or on a root that is nothing but memory. A read is a read of the file through the file system holding it; a write is a write followed by a sync of that file, which is what keeps the buffer cache's promise that a block it has written has reached the device.

`/dev/loop-control` takes one command per write: `attach N /path`, `attach - /path` for the first free device, `attach ro N /path` for a device that will not write, and `detach N`. The node is `0600` and owned by root, which is what says who may attach anything. `/dev/loopN` itself is `0400` root's, and `stat` reports it as a character device, since only the mount table reaches its bytes. A device number must be a number, one of the four, and nothing may follow it. `loopctl` is the program that writes them ([utils/Readme.md](../../../utils/Readme.md)). `/proc/loop` has one line per attached device: the device, its size in bytes, whether it takes writes, how many writes it has made and how many of them it has synced, and the path it was attached by. The two counts are the write's two halves, and a test that fills the cache and lets eviction alone write the blocks back asks them whether the second half happened.

The file is identified by its mount and node, so a hard link to an attached file is the same file: a second attachment answers `EBUSY`, whatever path names it. Attachment first resolves the path to keep its mount active, takes that mount's namespace lock, then resolves and opens the path again. A path that now resolves on another mount answers `EBUSY`. A writer that relocates the file while attachment waits completes before the second resolution, which finds the relocated node. Attachment syncs the file and rechecks its length and whether another description is busy before publishing the device, all under the same lock. A description still busy at that check causes `EBUSY`.

The length at attachment fixes the sector count. A non-regular file, an empty file or a length that is not whole sectors is refused. A short read or write becomes a device error. Writes, truncations and length changes through attributes answer `EBUSY` while the file is attached. Unlink and rename over the backing file also answer `EBUSY` on the KRFFS root, whose descriptor tables protect the extent. Descriptor writes check attachment before taking their description lock and again after taking it. Published loop references follow KRFFS relocation: relocation updates the stored node, and mounted KRFFS open handles retain their shared record.

A device attached read-only carries `BLOCK_READ_ONLY`, and every mount of a device that carries it is read-only whatever the caller asked for, which the mount table settles for every type rather than each type for itself.

The attachment holds a description on the mount holding the file, so unmounting that volume answers `EBUSY` until the device is detached. A detach answers `EBUSY` while a mount is placed on the device, a buffer of it is held, or an attachment is still inside the steps that sleep, which claim the slot before they run; otherwise it writes what the cache holds, drops those buffers, and releases the file. A device whose medium goes, a stick pulled out, takes its loop device with it: the device is marked gone, nothing new reaches the file through it, and its unwritable buffers are dropped, so the mount above it can be taken down rather than failing its sync for ever. What the attachment held is given back then too, since the volume the file was on cannot be unmounted while a description of it is outstanding; a transfer that is inside that volume when the medium goes finishes first, and the last one out does the giving back.

## The block request

`block_request` transfers whole sectors and sleeps the caller when the device does. On a `BLOCK_FAULT_SAFE` device it calls the transfer function and returns, from any context, at boot included. Apart from the `BLOCK_CALLER_SYNC` case above, a device without the flag has `submit` instead: `submit` starts one request and returns, and the device reports the end through `block_request_complete` from whatever context it completes in. Such a device is used from syscall context only. The transfer is split into requests of at most the device's `max_sectors`, eight when the device sets none, held to the block layer's limit of 2048 sectors: 2048 for the AHCI disk, 1024 for a USB stick and 64 for the ATA disk, so a 1 MiB raw transfer to the AHCI disk is one request and one command; a request the heap has no buffer for is asked for again at half the size, down to a page's. A `BLOCK_FAULT_SAFE` device is called in pieces of its `max_sectors` too. Each request has a buffer of its own: a page of the identity-mapped window for a transfer of a page, heap pages for a larger one, whose physical addresses a driver gives the controller. A write is copied into the page before `submit` and a read is copied out after a successful completion, so no device writes into memory the caller may have reused. The caller sleeps between `submit` and the completion or the end of the device's deadline periods: thirty seconds a period unless the device sets `deadline_ticks`, and four periods in a row unless it sets `deadline_limit`, so a request is given up after two minutes without an answer and a disk that answers late is not a disk that went away. The timer advances the deadlines once per tick; a request that passes a period is recorded as overdue and waited for, and its answer inside the periods is the answer. `rach2.blockdeadline=S` sets the period to `S` seconds, one to six hundred, for a row that cannot wait thirty. Policy limits the number of live requests to sixteen unless `rach2.blockpool=N` sets another limit. A caller that reaches the limit, or whose device already holds its share, waits. Reaching the limit is not a device failure; a transfer that failed, or a request that could not be allocated from the heap or the identity-mapped window at a page's size, returns `EIO`. Allocation failure returns before submission. The deadline starts when the request is allocated, which is when the transfer starts. A request is accounted to the device whose `submit` answers, `block_submitter` of the device the request named: a stick's partition views share the stick's allowance and its stall, since it is the stick that answers. Two rules end a wait: a device with quarantined requests and none in flight is marked `BLOCK_STALLED` with a record, and its waiters and every later request on it return `EIO` until a late completion clears the mark; and a waiter that finds every live request quarantined returns `EIO` too. `rach2.blockpool=N` sets the limit to `N` requests, one to sixteen, so a test can see a request wait on a machine with two partitions; a device's share is half of `N`, rounded down, but at least one.

A request is held by its caller and its device and is freed with its page when both have released it. A request unanswered through its periods returns `EIO` and is quarantined with its page; the device retains its reference until a late completion releases it and is recorded. Each request takes the next value of a 32-bit generation counter, which wraps after 2^32 allocations. A completion that refers to a request no longer on the live list, or supplies a generation different from that request's, is dropped with a record. A transfer that reaches the request limit waits as above.

`rach2.blocklag=N` wraps the boot disk in the lag device for the partition nodes and the mounts, while the root window keeps the real device. The wrapper has no `BLOCK_FAULT_SAFE` flag; it runs each transfer at submit time, polled, and delivers the completion `N` ticks later from the timer, twice, with the second copy carrying an error, so a kernel that accepted a stale generation would fail a healthy request. The wrapper sets one period of five seconds, so with `N` above it the request times out before its completion arrives, which is how the quarantine is exercised by `tests/run mount` without a mutation. `rach2.blockfail=N` beside it makes the Nth write through the wrapper fail with `EIO`, so the buffer cache's failure record and a mount going read-only can be seen in a boot. `rach2.blockdead=P` builds the view of MBR partition `P`, read from the disk when the wrapper is installed, over a second device that accepts every request and answers none, so a device that stalls has a healthy neighbour under the same request limit. The wrapper also has a `flush`, answered after the lag with nothing under it to flush and recorded as `lag: flush answered`, so a `sync` takes a request the way a stick's flush does.

## Partition discovery and the disk root

Boot-device discovery reads sector zero of the chosen boot disk and parses its four MBR entries for `/dev/bootpart` and `/dev/grubcore`. `rach2.boot=SPEC` selects the boot partition with the same identity forms as `rach2.root=SPEC`; it must match exactly one partition, entry 1 of an MBR disk. Otherwise the kernel logs a warning and publishes neither boot device. Without `rach2.boot`, discovery uses the disk containing the root resolved by identity, or disk 0 when no root resolves that way. The legacy disk-root paths reuse discovery's parsed MBR. Partition nodes and roots selected by identity use the registry's partition table.

`/dev/grubcore` covers LBA 1 through 2047. It is published when the disk has at least 2048 sectors and no non-empty partition overlaps that range. A partition in the gap suppresses `grubcore` only.

`/dev/bootpart` uses MBR entry 0. The entry must:

* have FAT32 type `0x0b` or `0x0c`;
* start at or after LBA 2048 and contain at least one sector;
* fit within the disk;
* overlap no other non-empty MBR entry; and
* be smaller than 2 GiB, so the 32-bit `lseek` can name every byte.

The disk-root path examines the first sector of each non-empty partition and mounts the first valid KRFFS root. The MBR type byte does not select KRFFS. The chosen partition must fit the disk and the page-cache window, and its sector count must be a multiple of eight. Its source in `/proc/mounts` is the partition node whose start matches the root, or `/dev/disk0` if no registered partition matches. If entry 0 itself contains the mounted root, the kernel withdraws `/dev/bootpart`.

`rach2.root=SPEC` also selects a partition across all registered disks: `PARTUUID=GUID` matches a GPT partition's 36-character GUID; `MBRID=XXXXXXXX,M` matches an eight-digit hexadecimal MBR disk identifier and partition number; `UUID=UUID` matches an ext2 volume UUID without regard to letter case; `LABEL=NAME` matches a GPT partition name or an ext2 volume label; and `/dev/diskNpM` selects a node directly for recovery. Exactly one partition must match. No match logs `root: SPEC: not found on any of K disks`; multiple matches log `root: SPEC: ambiguous: /dev/diskApB and /dev/diskCpD`, with `and more` when necessary. Neither case mounts a root. `rach2.rootfstype=krffs` or `rach2.rootfstype=ext2` selects the file system; another value is refused by name. Without it, the kernel checks for a KRFFS root node first, then an ext2 superblock the driver can mount.

A KRFFS root selected by identity uses the page-cache window and a `BLOCK_FAULT_SAFE` device. Its start and sector count must fit 32 bits, its length must be a multiple of eight sectors, and it must fit the disk and the window. Its source in `/proc/mounts` is the resolved node path. The kernel logs `root: SPEC: /dev/diskNpM, KRFFS` or `root: SPEC: /dev/diskNpM, ext2`; a successful ext2 mount also logs `ext2: root: /dev/diskNpM`. A KRFFS root overlapping the boot partition on the same disk withdraws `/dev/bootpart`.

## The GUID partition table

`gpt.c` provides the GUID partition table checks used by the partition service for SATA and USB disks. This is the table a stick formatted on a Mac has and a disk over two terabytes must have. A protective MBR entry of type `0xEE` at index zero selects it; the primary header is at sector 1 and the entry array is where the header specifies. The parsing is pure, so `gpt_hosttest` drives it against tables no disk would carry.

The header is judged before anything it says is used: the signature, revision 1.0, a size between 92 and 512 bytes, the CRC32 over the header with its own checksum field taken as zero, and the sector the header says it is on, which is what tells a header read from the backup apart from a copy of the primary left there. Then what it says about the array: at most 128 entries, an entry at least 128 bytes and a multiple of 128, their product at most 16 KiB, a usable range that does not run backwards or past the medium, and an array that is on the medium. The product is bounded before it is taken, because a reader that multiplied the count by the size without looking would compute an offset from two numbers read off the medium. The count and the array's first sector must both be nonzero. Array addresses are 64-bit; the USB class driver uses sixteen-byte commands on large units.

The array is read whole and covered by its own CRC32 before a single entry is looked at. A reader that took the first four entries would accept a table whose fifth entry is rubbish. The partition service judges all entries and publishes at most fifteen. An entry is used when its type GUID is not all zeros; it is accepted when its first sector is at or before its last, both lie inside the usable range, and it overlaps nothing already accepted. Sector addresses have no 32-bit limit. An entry that fails is passed over with the rest still read, and the count is reported. Accepted entries retain their array positions as partition numbers, counted from one; a sound entry beyond the fifteen-partition limit is counted among those passed over.

## The stick as a disk

`usbdisk.c` registers each logical unit the class driver has brought up as a removable disk, with `/dev/diskN` and `/dev/diskNpM` nodes. `usbdisk_arrived(slot, lun)` takes one of eight USB disk records. Registration uses transport `usb`, location `slot * 4 + lun`, and the INQUIRY vendor and product as the model. The disk gets the lowest released registry number, or a fresh number when none is free. The partition service reads its MBR, extended partition chain or GPT under the rules above. A sector with no table that opens with a FAT jump or the exFAT name is recorded as one volume; otherwise it is recorded as no table. The whole node is published after the scan even when no partitions were found, and a volume with no table mounts through it. MBR entries that include sector zero, run past the medium or overlap an accepted entry are passed over. The host's `stickcheck` uses the pure `mbr_take` function in `mbr.c` to check the stick image's MBR before a machine boots from it.

The table is read from the pump, where nothing sleeps. `part_scan` reads through a callback backed by a 96-sector cache, enough for sector zero, both GPT headers and arrays, and an extended partition chain. If a pass requests an uncached sector, its result is discarded and `block_request_begin` starts a read of at most a page. Later pump passes call `block_request_ended`; once the sectors arrive, the service runs again until a pass needs nothing new. One table is read at a time. A failed request or a table needing more cache space leaves an unread table with no partitions. Registration and reclamation run at syscall entry, before dispatch, or on a pump pass that did not interrupt a syscall. When the scan ends, `disk_set_table` installs its partition views, devfs assigns their node names, and the whole-disk window is published.

`usbdisk_left(slot)` marks every USB disk record for that device closing. At the next syscall entry or pump pass outside a syscall, each disk's `present` flag is cleared, hiding its nodes from `/dev`, and the loop devices and buffer cache are told that every partition view and the whole-disk window have gone. A clean buffer nobody holds is dropped, a dirty one has nowhere to be written and takes the mounts on the device read-only, and a held buffer is marked for removal at release. The windows remain until nothing holds them. `usbdisk_holds` sums the open descriptions on the disk's nodes, requests owned by its device, and mounts, cache buffers and requests on every view, including the whole-disk window. Mount holds include files open on the mount; request holds include quarantined requests. A pull during a table scan waits for the outstanding request to answer before discarding the scan.

A closing record is reclaimed when its scan has ended and its hold count is zero. Reclamation calls `disk_release` to free the disk number and `msc_release` to return the class driver's slot, then frees the USB disk record and logs `usbdisk: diskN: reclaimed`. The registry keeps the allocated node slots for reuse, with partition names assigned from the next disk's table. The next disk may get the same number, with a new claim and no buffers from the previous medium. `/proc/usb` reports the free USB disk records and the number reclaimed.

A completed scan logs `usbdisk: diskN: TABLE: M MiB, K partitions, R passed over`. TABLE is `mbr`, `gpt`, `gpt-bad`, `one volume`, `none` or `unread`. `/proc/usb` reports each unit as `diskN VENDOR PRODUCT SECTORS sectors K parts STATE flushes F`, followed by `ro` for write protection and `holds H` while closing. The sector count is 64-bit. STATE is `reading`, `ready` or `closing`; the name is `disk?` until registration. `/proc/disk` lists the unit and its partitions with the other registered disks.

## ATA

`ata.c` probes primary master, primary slave, secondary master, and secondary slave in that order. The primary channel uses ports `0x1f0` and `0x3f6`; the secondary uses `0x170` and `0x376`. A channel in PCI native mode uses the IDE controller's base registers instead: programming-interface bit 0 selects BAR0/BAR1 for the primary channel, and bit 2 selects BAR2/BAR3 for the secondary, with the control register at the control BAR's base plus two. Drive-register bit 4 selects the slave. The driver issues `IDENTIFY`, treats status `0` or `0xff` as an absent drive, and refuses a packet device whose LBA mid or high register is nonzero after `BSY` clears. A slave whose IDENTIFY words 10 through 46 match its master's is skipped as an echo. Each disk is registered with `BLOCK_FAULT_SAFE`, transport `ata`, and location `channel * 2 + drive`, numbered from zero; the first supplies `block0` when AHCI found no disk.

ATA moves data through the controller's bus master where it has one and the drive answers IDENTIFY word 49 bit 8, and through the data port otherwise, or always with `rach2.atapio` on the boot line, which a suite uses for a writer that must never sleep in the driver. The bus master is found in the IDE controller's BAR4 when programming-interface bit 7 is set, the primary channel's registers at its base and the secondary's eight bytes on; the driver enables bus mastering on the controller and logs each disk as `bus master DMA` or `data port PIO`. A DMA transfer moves through the channel's own bounce buffer, one request of 64 sectors, static so its address is its physical address and aligned to its size so it lies in one 64 KiB region: a write's bytes are copied into it before the command and a read's out of it after, in the caller's context, because a fault-safe device's transfer may not schedule against the caller's memory, which the page cache's window may evict or remap while another process runs. One physical region descriptor names the buffer; its address goes to the bus master, the direction and the start bit to its command register, `READ DMA` or `WRITE DMA` to the drive, and the drive's interrupt ends the command, the bus master's error bit failing it with `-EIO`. The processor's cache is coherent with this DMA and nothing is flushed. IDENTIFY word 83 bit 10 selects the 48-bit command set and the sector count in words 100 through 103. Without that support, or when that count is zero, the driver uses words 60 and 61, capped at 2^28 sectors (128 GiB). A command whose sectors all lie below 2^28 uses the 28-bit form; a range reaching beyond that uses the `EXT` form, with the count and LBA registers written twice, high bytes first. On the data port each sector has its own `BSY` and `DRQ` handshake. One command transfers at most 256 sectors; the disk declares 64 sectors a request, so the buffer cache writes and reads it in runs of 32 KiB.

A wait for the drive sleeps when it can and polls when it must. A caller that does not own the channel waits for the drive idle, BSY and DRQ both clear, before its command: a drive in a data phase, PIO or DMA, shows DRQ with BSY clear, and a second command written to it then is refused or answered with the first one's data. The owner's DMA command is written and its engine started with interrupts off, so such a caller never finds a command waiting for its engine, and a data-port transfer runs with interrupts off whoever the caller is, so no chunk is left in its data phase while another caller runs. Both channels raise their interrupts, lines 14 and 15, whose handler reads the status register, which acknowledges the drive, and wakes the channel's queue. From a system call the caller reads the status a few times, then sleeps on that queue, woken by the interrupt and by the tick, which also ends a wait that has lasted five seconds with `-EIO`. From a page fault, with interrupts off, the wait polls, since the timer cannot advance there: a few hundred plain status reads, which is what the emulator's DMA needs, then a fixed number of rounds of a pause of ten thousand `pause` instructions off the device and a read: under a hypervisor every status read is a trap that takes the emulator's lock, and a loop of nothing but reads can hold the emulator's own completion out. A polled wait that gives up records the status it saw. Each successful write command is followed by `FLUSH CACHE EXT` on a 48-bit drive or `FLUSH CACHE` otherwise. `/proc/disk` counts the commands and the flushes, every status read a driver made while a command was in flight as `disk-polls`, the ATA driver's and the polled AHCI driver's alike, and every tick a request spent in flight, or an ATA caller slept for its command, as `disk-wait-ticks`, which the request layer counts on every device, so a test can require that a driver sleeps and that a request does not wait out a deadline, rather than measure how long either took.

## AHCI

`ahci.c` finds the first PCI mass-storage controller in AHCI mode and maps BAR5 as its ABAR. An absent controller is reported at info level as `ahci: none: ...`. Bring-up requests firmware ownership when supported, resets the HBA, applies the Intel PCS port-enable correction to the supported controller families, and disables HBA and port interrupts. It power-enables and COMRESETs each implemented port, then selects up to four ports in port order whose links are present, whose devices become ready, and whose signatures are `0x00000101`. Other ports are stopped; a disk beyond the four-port limit is logged and skipped. During reset, ports use a scratch command list and received-FIS area that the driver does not read. Each selected port has its own `struct ahci_disk`, with a command list, received-FIS area, command table, capacity, and block device. The DMA areas are static, below the identity-mapped limit. Each port is started with its own areas and identified; a failure stops that port and is logged, and initialization succeeds if at least one disk answers. Each disk executes one command at a time, polled during boot.

The driver uses one command slot and one Register Host-to-Device FIS per port, with up to 264 PRDT entries describing the transfer buffer, one per page of a heap buffer, so a request of the block layer's 1 MiB limit is one command. `READ DMA EXT` and `WRITE DMA EXT` use a 48-bit LBA. A polled command transfers at most 8192 sectors, or 4 MiB, provided the PRDT can describe its buffer. A queued request transfers at most 2048 sectors, 1 MiB, described page by page; requests wait oldest first through their `queued` links, separate from the live request list's `next` links. A write is followed by `FLUSH CACHE EXT`, and a queued write completes only after the flush. Completion checks the fatal port status, task-file `ERR` and `DF`, and the transferred byte count. A failed command runs port recovery and returns `-EIO` only after the command engine has stopped. If `PxCMD.CR` remains set after the bounded stop wait, the kernel panics with interrupts masked. The active request is not completed, the queue is not restarted, and a polled caller does not regain its buffer: the controller may still use the buffer and command table. The interrupt handler examines each disk's `PxIS`, completes the active command when its `PxCI` slot bit clears, and handles fatal errors. It judges completion status before acknowledging the port and that port's controller interrupt bit. Both acknowledgements precede the flush or the next queued request, since either command may finish before the handler returns. Other ports' controller bits are left pending until those ports are handled. Request completion uses `block_request_complete` and records disk latency as `latency_disk_us`.

AHCI's polled waits are measured with the 8254 counter through `k_udelay`: one second for HBA and link waits, five seconds for a device to finish COMRESET, and for a command thirty seconds with interrupts on and five with them off, since a write ends with a flush that waits for the medium, which an emulator's host under load or a disk spinning up can take seconds for; thirty is the queued path's deadline period and Linux's ATA command timeout, and with interrupts off, where the timer does not tick and each tick of the wait is lost to the clock and to every timer, the bound is the IDE driver's. A failed or timed-out command, polled or judged at its completion, is logged with why, and the port is stopped, cleared and restarted before the error returns. Queued requests let other processes run while the caller sleeps, subject to the block request deadline. The device's `read` and `write` functions remain polled for page-cache faults with interrupts off and other direct callers. Before issuing a polled command, the driver finishes any active queued request by polling, including its flush when it is a write, and completes that request. It then polls its own command, acknowledges its interrupt and resumes the queue. A failed polled command also acknowledges its interrupt before the queue resumes. These polled transfers occupy the CPU until they finish.

The command list, received-FIS area, command table, and transfer buffer pages must have physical addresses below 4 GiB. A physically contiguous buffer in the identity-mapped window uses one PRDT entry; a queued request of a page has its page there. A heap buffer uses one entry per page, with addresses obtained through `paging_virt_to_phys`, so a 1 MiB raw-transfer buffer that starts mid-page fits the table's 264 entries as 257 without requiring physical contiguity. A buffer the table cannot describe is refused. The driver synchronizes this memory with `CLFLUSH`, or `WBINVD` when `CLFLUSH` is unavailable, around each DMA operation.

Rach2 has no NCQ, hot-plug, port multiplier, or ATAPI support. The driver registers every disk it brings up; `block0` points at the first.

## Raw disk devices

The raw disk nodes are synthetic block devices: `stat` reports `S_IFBLK` for `/dev/diskN` and `/dev/diskNpM` on SATA and USB disks, so `blkid`, `findfs` and `mount LABEL=` can find their volumes. `/dev/bootpart` and `/dev/grubcore` are character devices. Their open-file descriptions all use a 64-bit offset, and `_llseek` can address the complete window. Disk-node reads accept any byte range: the covering sectors are read into the staging buffer and the requested bytes copied out. Boot-window reads and all raw writes require a sector-aligned offset and a byte count divisible by 512. Reads at or past EOF return zero, and a read crossing EOF is shortened. A read from a pulled stick fails with `EIO`. A write that starts past or crosses the end returns `ENOSPC` before writing any sector.

Every transfer allocates its own page-aligned staging buffer with `kalloc_pages`, sized to the least of the call, the device's largest request and 1 MiB, and frees it when finished, so transfers on different disks can proceed while each caller sleeps on its device; at most eight such buffers are out at once. If the heap cannot supply the pages, or eight are out, the transfer takes the static 32 KiB buffer; another caller needing that buffer waits until it is released. The loop sends at most the buffer's sectors to the block device per call. If a later batch fails, the call returns the bytes from earlier completed batches. A failed write batch may have reached the disk in part because the block interface cannot report progress within one command. A zero-length write returns zero. A zero-length read returns zero before any device is called.

Each disk, including a USB stick, permits only one write-capable descriptor across its whole-disk and partition nodes. `/dev/bootpart` and `/dev/grubcore` share the chosen boot disk's reservation. A second write-capable open on the same disk answers `EBUSY`; an open on another disk may proceed. Readers may remain open during a write. `/dev/grubcore` additionally permits only one open description at a time. Beside that rule is the claim table: a mount claims its source's sector range on the physical disk from its constructor to its unmount, and while a range is claimed a write-capable open of a window over it answers `EBUSY`; while such a descriptor is open, a mount on the range answers `EBUSY`. The claims also prevent overlapping whole-disk and partition mounts. Ranges are compared on the same physical disk, so `/dev/bootpart` and `/dev/diskNp1` naming one partition exclude each other's writer.

The disk registry in `disk.c` has eight records shared by ATA, AHCI and USB disks. Fresh records are numbered in registration order; `disk_register` reuses the lowest released record before allocating another. A disk whose `present` flag is clear is omitted from `/proc/disk` immediately. Its record and number remain reserved while references exist; `disk_release` then frees the number and makes `disk_at` return NULL for it. Disk 0 found by the ATA or AHCI probe supplies `block0`; boot-device discovery selects the disk for the boot windows. Devfs allocates sixteen node slots when a record is first registered, one for the whole disk and fifteen for partitions, using one set of file operations for all disk nodes. Released records retain these slots. After each scan devfs names the partition nodes from the accepted entries' numbers. A node is listed and openable only while its disk is present and its window is published. Inode numbers are stable, with the static devfs entries first and disk nodes in first-registration order. The devices have these publication and permission rules:

* `/dev/bootpart` is mode 0600 and appears after its MBR entry passes the checks above.
* `/dev/grubcore` is mode 0600 and appears when the post-MBR gap is safe.
* `/dev/diskN` is mode 0400. `rach2.diskdiag` publishes the whole-disk window of every registered disk; a recovery build requests the same publication without that boot option. This publication starts at sector zero and covers the smaller of the device size and 2^32 sectors, or 2 TiB. A USB stick's scan publishes its whole-disk window without either option and covers its full sector count. `devfs_window_of` accepts the whole-disk node as a source for `mount(2)`, so a stick with one volume and no partition table mounts through `/dev/diskN`. The nodes use major 240: disk 0 has minor 1, and disk N, for N >= 1, has minor `64 + 16N`.
* `/dev/diskNpM` is mode 0400 and exposes the range of an accepted partition. M is the table's partition number: 1 through 4 for MBR primary entries, 5 upward for logical partitions, and the array position counted from 1 for GPT entries. The extended MBR entry has no node. After the driver probe, `block_probe` scans every registered disk through the partition service and publishes its views; disk 0's views use the lag device when `rach2.blocklag` is set. These nodes and `/dev/bootpart` are sources for `mount(2)`; `rach2.root=ext2` uses a partition of disk 0, while a root selected by identity may use any registered disk. Partition nodes are independent of the boot windows' publication and withdrawal. All use major 240: disk 0's partitions 1 through 4 have minors 4 through 7, its partition M for M >= 5 has minor `64 + M`, and partition M of disk N, for N >= 1, has minor `64 + 16N + M`. A write answers `EPERM` in every build but recovery, where `e2fsck` repairs a partition through its node under the same authority that publishes `/dev/diskN` there. Every raw window answers `BLKGETSIZE64` with its size in bytes and `BLKGETSIZE` with its sector count, which is how a checker sizes a device before reading it; `BLKGETSIZE64` is taken under both the 32-bit and the 64-bit request number, since the two differ only in the `size_t` the macro measures.

The modes reject unprivileged opens. Effective uid 0 bypasses the mode check, so root can open ordinary `/dev/diskN` with `O_RDWR`, subject to the writer reservation and claims. The ordinary kernel's write handler returns `EPERM` for every whole-disk and partition node, including a stick's. A recovery kernel compiles the write implementation for all these nodes and checks effective uid 0 again on every write. A raw write to a write-protected stick returns `EIO`; the USB class driver rejects the underlying request with `EROFS`. The bounded boot windows also repeat the effective-uid check when they write.

`BLKRRPART` (`0x125F`) on a whole-disk node calls `disk_rescan` to read the partition table again and rebuild its views and node names. It returns `EBUSY` while a mount claims a partition of that disk or another descriptor is open on its disk nodes, including another descriptor in the calling process. On a partition node it returns `ENOTTY`.

The debug-shell `ahci` command reports an error and performs no re-probe while KRFFS is mounted from disk. Otherwise it withdraws `/dev/bootpart`, `/dev/grubcore`, and every disk's whole-disk window, initializes AHCI directly, dumps the controller, reads sector zero of `block0`, and runs boot-device discovery again. The dump reports the first disk's port as `active` and prints the DMA addresses for each selected port. The command republishes whole-disk windows only when `rach2.diskdiag` is present; a recovery boot without that option loses those nodes after this manual re-probe.

## Disk policy and recovery authority

Two independent build switches limit writes.

`RACH2_DISK_READONLY` selects the metal kernel's driver policy. The ATA and AHCI issue paths permit only `READ SECTORS`, `READ SECTORS EXT`, `READ DMA`, `READ DMA EXT`, and `IDENTIFY`; every other command byte returns failure. This also prevents writes through `/dev/bootpart` and `/dev/grubcore`. `tools/inspect/check_diskpolicy.sh` requires exactly one policy banner in the built kernel.

The policy is the two disk drivers' allowlist and covers the disk they drive. A flash drive is written through the USB class driver, which the policy does not reach, so a machine booted from the read-only stick can still write a stick; the disk the policy exists to protect is the one in the machine.

`RACH2_RECOVERY` controls the write handler for every `/dev/diskN` and `/dev/diskNpM` node, including USB disks, and requests automatic whole-disk publication. The ordinary kernel has the `EPERM` body. The recovery kernel has the root-only write body. USB whole-disk windows are also published by their table scans, independently of this switch. The switch does not bypass `RACH2_DISK_READONLY`; the Makefile builds the recovery kernel with recovery authority and the normal read-write driver policy. `tools/inspect/check_recovery.sh` checks the authority banner.

The command and flush counters cover attempts issued since boot. `/proc/disk` reports them beside the raw-device batch size and call count. Each device also counts its own transfers for `/proc/diskstats` (`struct block_stats` in `block.h`): `block_request_flags` counts a transfer that ended well, its sectors and its milliseconds, on the device asked and on the disk `block_physical` reaches under it, and the requests in progress on both.

## Disk information

`/proc/disk` is always a resolvable read-only procfs file. Before `diskinfo_probe` it reports `state not-asked`, the driver name recorded by any earlier probe, the compiled driver policy, and the counters, which are printed whatever the disk's state because a mount can be on any device the drivers serve: the drivers' `disk-commands` and `disk-flushes`, their `disk-polls` and `disk-wait-ticks` (status reads a driver made while a command was in flight, and ticks the request layer saw requests in flight, one a request a tick), the request layer's `disk-in-flight`, `disk-overlaps`, `disk-quarantines`, `disk-releases` and `disk-release-tick` (requests in flight now, completions that found another request in flight, requests a deadline quarantined, callers released with `EIO` by a deadline or a stalled device, and the tick of the last release), the lag device's `lag-completions` (answers delivered after their lag), and the buffer cache's `cache-hits`, `cache-fills`, `cache-waits` and `cache-visits` (reads served from a buffer, reads that filled one, waits for a buffer another process held, and the buffers the cache's walks of its own lists have read: its index buckets, a process's held buffers, the release order and the whole list, which is what a get, a victim's choice and a sync cost it in bookkeeping). A requested probe reports `no-device` when no disk answers.

For a present disk, `diskinfo_probe` adopts `block0`, reads its sector zero, and publishes the whole-disk window of every registered disk. The detailed record describes disk 0: the driver, AHCI port, mount state, sanitized ATA model, serial and firmware strings, sector and window sizes, MBR signature and disk id, and four partition entries on `part1` through `part4` lines. The live raw-call, command, and flush counters are totals across the devices they serve. After this record, in every probe state, `/proc/disk` prints one line per registered disk, omitting released records, as `disk N TRANSPORT LOCATION SECTORS TABLE MODEL`. The transport is `ahci`, `ata` or `usb`. The location is the AHCI port; the ATA position, 0 for primary master, 1 for primary slave, 2 for secondary master and 3 for secondary slave; or the USB class-driver slot multiplied by four plus the logical unit number. A USB disk's model is its INQUIRY vendor and product joined by a space. The table state is `mbr`, `gpt`, `gpt-bad`, `none` or `unread`. Each disk line is followed by an `identity N SECTOR-SIZE fixed|removable mounted|free SERIAL` line, which is what a program choosing a disk to write reads: the unit the disk counts in, whether it can be pulled out, whether a mount holds any range of it, and the drive's own serial, last because it is the only field that may hold a space. Then come its accepted partitions as `part N M START COUNT ID LABEL`. N is the disk number, M the partition number, and START and COUNT are sectors. ID is the partition's 36-character GUID for GPT, or `mbr:` followed by the two-digit hexadecimal type byte for MBR. LABEL is the GPT name and is empty for MBR. Opening `/proc/disk` generates a snapshot and issues no disk command.

## Verification

`tests/run host` runs the pure block tests under AddressSanitizer and UndefinedBehaviorSanitizer. `block_hosttest` checks partition forwarding and bounds. `mbr_hosttest` checks parsing, overlap, disk-end, gap, and FAT-entry cases, and the taking of publishable entries with the passed-over count. `gpt_hosttest` checks the CRC32 against its published value, the header's every rule, the whole-array checksum, and the entry rules, including an entry array damaged beyond the fourth entry. `usbdisk_hosttest` links the registry, partition service and GPT checks over a medium in memory, with the class driver, request layer, devfs and caches stubbed. It checks an MBR unit registered as removable USB disk 0 with its INQUIRY model, its table read in one request, and its views and whole window published; a pull hiding its nodes and notifying the cache while reclamation waits for a mount hold; a six-partition GPT read across several requests after reusing number 0 without allocating nodes again; ten plugs and pulls leaving all eight records free; a pull during a scan publishing nothing; two units of one device registered as two disks and both removed by its pull; and registration deferred by a pump pass inside a syscall but performed at syscall entry. `diskcmd_hosttest` tests all 256 command bytes under both policies. `diskinfo_hosttest` checks IDENTIFY strings, 64-bit decimal conversion, the 2 TiB window, and the exact procfs record, with an empty registry stub. `pagecache_hosttest` checks fill, eviction, writeback, and failed-write retention above the block interface. `ahci_hosttest` drives the AHCI driver's first disk record, `ahci_disks[0]`, against a model of a controller through `struct ahci_io`, the register interface the driver reads and writes through; each row drives one step of initialization or one command and requires the driver's answer, including a reset that never completes, a port with no device or a device that is not a disk, a command that never completes, and a device that reports a fatal status.

`partition_hosttest` runs the partition service over disks in memory. It checks a blank disk, an unreadable sector zero, a signature without entries, an MBR with three primary and three logical partitions, a looping chain, a logical partition outside its extended partition, and overlapping or out-of-disk primary entries. Its GPT cases check six entries with names and GUIDs, GUID text conversion in both directions, recovery from a damaged primary header or array through the backup, refusal when both copies fail, and the count of entries beyond `PART_MAX`.

`tests/run usbdisk`, in the core tier, runs the thirteen numbered boots `tests/system/suites/usbdisk.sh` lists and requires `mformat`, `mcopy` and `mtype`. It checks MBR and GPT volumes through registry nodes, including GPT entries at indexes 6 and 9 as `/dev/disk0p7` and `/dev/disk0p10`; a volume without a table mounted through `/dev/disk0`; file writes checked on the host; pull and replug under a mount; ten plugs and pulls leaving all eight records free; BusyBox label lookup and mounting; a recorded 16 MiB read rate; and the stick image booted through firmware and mounted on its second partition. It also mounts and reads three sticks, pulls the middle one during continuous raw reads and requires `EIO` after at least eight reads, checks that the other two still mount and read, rejects a mount of the pulled stick, and requires its reclamation log. A recovery boot writes a 4096-byte pattern at sector 1000 through `/dev/disk0` and checks it in the guest and on the host, then writes 4 MiB of a pattern at 5 MiB in 32 KiB requests, reads it back byte for byte, and requires each direction to be exactly 128 commands as `/proc/disk` counts them. A sparse 2300 GiB stick tests its 4823449600-sector report and a 65536-sector FAT32 partition starting at sector 4294969344, with a file written and read in the guest and read back on the host. The last boot presents two logical units on one `usb-bot` device and requires both registry disks and both first partitions to mount and read.

The default `make test` boot has no data disk and does not exercise either disk driver. `tests/run disks`, in the core tier, boots one ich9-ahci controller with a 64 MiB disk containing a KRFFS partition on port 0 and a 20 MiB disk containing a FAT32 partition on port 1, with `rach2.disk=ahci rach2.diskdiag`. It checks the disk numbers, ports, and capacities in `/proc/disk`, the presence of both disks' whole-disk and first-partition nodes, and the absence of `/dev/disk1p2` and `/dev/disk2`. It mounts both partitions, writes and reads a file on each, and unmounts both; the host then reads the FAT32 file with `mtype`. The suite requires `mformat` and `mtype`. The other disk targets provide further coverage:

* `tests/run disk`, `tests/run disk-ahci`, and `tests/run disk-q35` run `blockprobe` through ATA, a separate AHCI controller, and the q35 controller at PCI function 2.
* `tests/run persist` and `tests/run persist-ahci` write and fsync on one boot, then read the file from the same disk on the next boot.
* `tests/run stress` and `tests/run stress-ahci` write and verify 33 MiB through the 4 MiB resident page cache.
* `tests/run bootpart` checks an absent boot partition, a writable FAT fixture, both bounded devices under a RAM root, and `_llseek` markers at 5 GiB and 258 GiB on a sparse AHCI disk.
* `tests/run authority` compares ordinary and recovery kernels, checks the write exclusion rule, and requires a 200-sector raw transfer to take one driver call, the batch holding it whole.
* `tests/run diskpolicy` proves that a mount write fails under the read-only artifact and leaves the disk image unchanged. `tests/run diskdiag` compares raw-sector hashes and requires the complete read-only session to leave the image unchanged.

`tests/run grub`, `tests/run menu`, `tests/run install`, `tests/run drill`, and `tests/run sealed` exercise the raw windows in their boot-loader and recovery workflows. The sealed test attaches the boot disk through AHCI and boots it through GRUB without QEMU's `-kernel` option.

`tests/run bus`, in the full tier, attaches four IDE disks of 16, 20, 24, and 28 MiB at positions 0 through 3. `busprobe four` checks their transport, locations, capacities, and MBR records in `/proc/disk`, then mounts each FAT32 partition, writes and reads a file, and unmounts it. The host reads all four files with `mtype` and checks the secondary slave's boot-log record. Two further boots attach an AHCI KRFFS disk with MBR identifier `aaaa0001` beside an IDE disk with identifier `bbbb0002`; each selects one root by `MBRID` and runs `blockprobe`, requiring `/dev/disk1p1` for IDE and `/dev/disk0p1` for AHCI. A final boot attaches a sparse 130 GiB IDE disk with a 65536-sector FAT32 partition starting at sector 268437504. `busprobe big` checks the full capacity and partition, mounts it, and writes and reads a file; the host reads the file with `mtype` and requires the capacity and `LBA48` boot-log record. The suite requires `mformat` and `mtype`.

`tests/run parts`, in the core tier, attaches four AHCI disks: an MBR with primary partitions and three logical partitions, a GPT with six labelled partitions including FAT32 and an ext2 root, a copy of that GPT with a damaged primary header, and a blank disk. `partsprobe` checks `/proc/disk` records, partition numbering and node presence, the absence of a node for the extended entry, and the boot-log record that the damaged GPT used its backup. It mounts, writes, and reads the logical FAT32 partition `/dev/disk0p6` and the GPT partition `/dev/disk1p3`. `BLKRRPART` must return `EBUSY` while the GPT partition is mounted and succeed after unmounting, with the expected nodes still present. The host reads both files back with `mtype`. Seven further boots check an ext2 root by partition GUID, the same root after swapping disks, refusal of a cloned GUID, a KRFFS root by MBR identifier on disk 1, refusal of a shared label, selection by node path, and an absent identity. The suite requires `mformat` and `mtype`.

`tests/run bootorder`, in the full tier, builds a GRUB disk with `rach2.disk=ahci`, attaches it on AHCI port 1 behind a blank disk on port 0, and boots it through firmware. It requires the ext2 root to resolve as `/dev/disk1p3` and the system to reach the login prompt. The core searches by FAT label, the menu searches by FAT serial, and the kernel resolves the root and boot partition by identity. SeaBIOS treats the hard disk it boots as its first disk, so this test changes bus order, not the boot disk's BIOS number. It requires the GRUB disk builder's mtools commands.

`tests/run queue`, in the core tier, attaches two 8 MiB FAT32 disks to one AHCI controller, with the first throttled to 256 KiB per second after a 256 KiB burst. `ahciprobe slow` starts a 1 MiB reader on that disk, then a 256 KiB reader on the other. The fast reader must finish while the slow reader is still active, and `disk-overlaps` must increase by at least one, showing a request completion while another request was in flight. Both readers must complete successfully. Elapsed time and the longest read time are printed only as diagnostics. The `ahci` vector in `/proc/interrupts` must count at least sixteen interrupts. A second boot uses an AHCI KRFFS disk root and a FAT32 second partition. `ahciprobe fault` runs `blockprobe` on the root while continuously reading the second partition through the queue, requiring `blockprobe` to succeed and at least 64 raw reads. This exercises the root's polled page faults and queued requests on the same port. The suite requires `mformat`.

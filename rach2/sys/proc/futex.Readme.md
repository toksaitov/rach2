# Futexes

`futex.c` implements `futex(2)`, system call 240: `FUTEX_WAIT`, `FUTEX_WAKE`, `FUTEX_WAIT_BITSET` and `FUTEX_WAKE_BITSET`, with `FUTEX_PRIVATE_FLAG` and, for the bitset wait, `FUTEX_CLOCK_REALTIME`. It also has the robust lists, `set_robust_list` (311) and `get_robust_list` (312), and the end of a thread's futex duties, `proc_thread_gone`. `man/man2/futex.2` gives the user contract.

A waiter files a `struct futex_q` on its own kernel stack in one of 64 buckets, hashed from its key: the address space, which is the process's page directory, and the user address, or for shared memory the frame and offset. It reads the word after making its page resident, then compares it and files itself with interrupts off, so a wake between the comparison and the sleep finds it. It then sleeps on the bucket's wait queue until a waker marks it, its deadline tick comes, or a signal arrives; the waiter that was not woken takes itself off the list. A wake marks up to the requested number of matching waiters, takes them off the list, and wakes the bucket's queue, whose other sleepers find themselves unmarked and sleep again.

Deadlines are whole 10 ms ticks, rounded up, plus the tick in progress. A relative timeout is measured from the call; an absolute one is converted against the monotonic or real-time clock when the call begins. The deadline's tick is fixed then, before the word's page is brought in, so a fault's sleep counts against it, and a deadline the fault outlasted ends the call with `ETIMEDOUT` once the word is compared.

A key names an address space by its page directory, so a waiter and its waker are threads of one process or processes that share one address space, as `vfork` and `clone` with `CLONE_VM` make them. A word in a `VM_SHARED` region is named instead by its page's frame and offset, unless the operation has `FUTEX_PRIVATE_FLAG`, so processes that map the same shared page, a file in `/dev/shm` or shared anonymous memory, wait and wake on it alike (`futex_key`). The requeue, wake-and-modify and priority-inheritance operations answer `ENOSYS`.

A thread's end, and its `execve`, call `proc_thread_gone`. It walks the thread's robust list, at most 2048 entries, and gives each futex word that still holds the thread's id `FUTEX_OWNER_DIED` in its place, keeping `FUTEX_WAITERS`, and wakes a waiter when there is one, as Linux's `exit_robust_list` does. The entry the thread was taking or giving back comes last: when its word has no owner and it is not a priority-inheritance futex, the thread ended between an unlock and its wake, or between a wake and taking the lock, and one waiter is woken with the word left as it is, as Linux's `handle_futex_death` does. A word's page is made present and writable before the word is read, and the read, the comparison and the write are one step with interrupts off, so a waiter cannot set `FUTEX_WAITERS` in a fault's sleep between them and have it written over. An `execve` calls it before a thread that is not its process's leader takes the leader's id, so the id it compares is the one the thread locked the words with. Then, when another thread shares the address space, it writes 0 to the word `CLONE_CHILD_CLEARTID` or `set_tid_address` named and wakes one waiter on it, which is how `pthread_join` learns of the end.

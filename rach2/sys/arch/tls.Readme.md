# Thread-local storage

Each thread has a thread pointer: the address of its thread control block (TCB), the structure the C library keeps for the thread. In musl it is `struct pthread`, whose first word is its own address and which has the thread's `errno` and stack-protector canary; the program's `__thread` variables lie just below it. On i686 the thread pointer is the base of the segment in `%gs`, and on x86-64 it is the FS base, so a load relative to that register reaches the running thread's own data. The kernel keeps one base for each thread, loads it into the processor when it switches to the thread, gives a new thread its parent's base or the one `clone` asks for, and sets it to 0 at `execve`. The calls' contracts are in their manual pages; this document describes how each architecture keeps the base.

## Interfaces

A program sets its own thread pointer with one call, which differs between the architectures, and `clone` sets a new thread's:

| Call | i686 | x86-64 | Manual page |
| --- | --- | --- | --- |
| `set_thread_area` | 243 | 243 by `int $0x80` | [set_thread_area(2)](../../../man/man2/set_thread_area.2) |
| `get_thread_area` | none | 244 by `int $0x80` | [set_thread_area(2)](../../../man/man2/set_thread_area.2) |
| `arch_prctl` | none | 158 | [arch_prctl(2)](../../../man/man2/arch_prctl.2) |
| `clone` | 120 | 56 | [fork(2)](../../../man/man2/fork.2) |
| `clone3` | 435 | 435 | [fork(2)](../../../man/man2/fork.2) |

* On i686, `set_thread_area` takes a pointer to a Linux i386 `struct user_desc` (`i686/tls.h`) and writes the entry number, 6, back into it; the program then loads the selector `0x33`, entry 6 at privilege level 3, into `%gs`. With `CLONE_SETTLS`, the TLS argument of `clone` and `clone3` is a pointer to the same structure, which the kernel checks as `set_thread_area` does (`tls_resolve_base` in `i686/tls.c`).
* On x86-64, `arch_prctl` sets the FS base with `ARCH_SET_FS` and the GS base with `ARCH_SET_GS`, and stores them at a user address with `ARCH_GET_FS` and `ARCH_GET_GS` (`x86_64/tls.h`). With `CLONE_SETTLS`, the TLS argument of `clone` and `clone3` is the new thread's FS base itself.
* On x86-64, 32-bit code also has Linux's three TLS entries, 12 to 14, whose selectors are `0x63`, `0x6B` and `0x73`: it sets one with `set_thread_area` and reads one with `get_thread_area`, i386 calls it makes by `int $0x80` through the compat table ([ia32(7)](../../../man/man7/ia32.7)), each with a `struct user_desc` (`x86_64/tls.h`).
* musl makes these calls itself ([the musl port](../../../vendor/musl/Readme.md)). Before `main`, its `__init_tp` calls `__set_thread_area`, which on i386 asks `set_thread_area` for entry -1 with limit 0xfffff and flags 0x51 and then loads the selector, and on x86-64 calls `arch_prctl` with `ARCH_SET_FS`. Its `pthread_create` passes the new thread's TCB with `CLONE_SETTLS`; on i386 its `__clone` builds the `user_desc` from that TCB's address and the entry of the selector in `%gs`.
* A tracer reads and sets a stopped thread's bases through [ptrace(2)](../../../man/man2/ptrace.2): `PTRACE_GET_THREAD_AREA` and `PTRACE_SET_THREAD_AREA` on both kernels, and `PTRACE_ARCH_PRCTL`, the `fs_base` and `gs_base` register words and `NT_386_TLS` on x86-64 (`i686/ptrace.c`, `x86_64/ptrace.c`).
* The shared kernel code reaches the thread pointer through three functions of `arch.h`, which each architecture's `tls.c` defines: `arch_tls_set` loads a base into the processor for the thread about to run in user mode, `arch_tls_get` reads the running thread's, and `arch_clone_tls` turns clone's TLS argument into a base.

## Design

[The architectures' Readme](Readme.md) describes each architecture's descriptor tables, entry code and context switch; this section gives the part of them that keeps the thread pointer. The paths of files under `rach2/sys/arch/` are given from there, and those of other files from the top of the tree.

### i686

* `i686/gdt.c` gives each processor a global descriptor table (GDT) of its own, of nine entries (`GDT_ENTRY_COUNT` in `i686/gdt.h`). Entry 6, `GDT_TLS_ENTRY`, is the TLS segment: present, DPL 3, writable data with a 4 GiB limit, the shape of the user data segment in entry 4, with base 0 at boot. It is present from the start, so a program that loads `0x33` before it has set a base takes no fault. `gdt_set_tls` rewrites only the three base fields of the running processor's entry 6. The segment spans 4 GiB from any base, so paging decides what a `%gs`-relative access may reach, and the kernel does not check the base.
* `process_t.tls_base` (`rach2/sys/proc/process.h`) is the thread's base. A new record is zeroed, so a new thread's base is 0.
* `sys_set_thread_area` (`i686/tls.c`) copies the `user_desc` in, has `tls_resolve_base` check it and return its base, writes the base into the running processor's entry 6 and into the record, and copies the entry number 6 back to the caller. It leaves the `%gs` selector saved at the entry as it was: the program loads `0x33` itself.
* `switch_context` (`i686/switch.s`) writes the incoming thread's `tls_base` into entry 6 with interrupts off and reloads `%gs` with `0x33`, since the processor keeps a hidden copy of a segment's descriptor that only a load of the selector refreshes. The thread's own selector comes back on its return to user mode. `isr_common_handler` (`i686/isr_handler.s`) saves `%gs`, `%fs`, `%es` and `%ds` in slots of their own in `isr_params_t` (`i686/cpu.h`) and runs the kernel with `0x10` in `%ds`, `%es` and `%gs` and the processor's own segment, `0x40`, in `%fs`; `isr_return` loads the four saved selectors back, and the load of `0x33` reads entry 6 with the base the switch wrote.
* `switch.s` reads `tls_base` at the fixed offset 80 of the record. `i686/context.c` checks that offset against the compiler's at build time, and `arch_context_check`, which `init_proc` (`rach2/sys/proc/process.c`) calls at boot, checks it again for a kernel TinyCC builds, since TinyCC cannot make the check at build time. `i686/tls.c` stops the build if `GDT_TLS_ENTRY` is not 6 or `GDT_TLS_SELECTOR` is not `0x33`, the values `switch.s` has as `.set` constants.
* `enter_program` (`rach2/kernel.c`), which starts the first program and each program the debug shell runs, goes to user mode without `switch_context`, so it calls `arch_tls_set` itself with the new record's base, 0. `arch_enter_user` (`i686/loader.s`) starts the program with the user data selector, `0x23`, in all four data segment registers.
* The signal frame (`i686/sigframe.c`) saves the `%gs` selector. A signal return restores it when it is `0x23` or `0x33` and puts `0x23` in place of any other, since the return path loads the selector in ring 0, where a bad one would fault the kernel.

### x86-64

* The FS base is the thread pointer, and the program may use the GS base as it likes. Each is a model-specific register (MSR) of the processor: IA32_FS_BASE (`0xC0000100`) and IA32_GS_BASE (`0xC0000101`), with IA32_KERNEL_GS_BASE (`0xC0000102`) beside them (`x86_64/percpu.h`). The kernel uses GS for itself: in the kernel, GS's base is the running processor's `struct cpu`, and `swapgs` exchanges IA32_GS_BASE with IA32_KERNEL_GS_BASE. Every entry from user mode runs `swapgs` first and every return to user mode runs it last (`x86_64/isr_handler.s`), so while the kernel runs, the program's GS base is in IA32_KERNEL_GS_BASE. The kernel does not use FS, and the program's FS base stays loaded while the kernel runs.
* The record has the FS base in `tls_base`, the GS base in `regs.gs_base`, and the FS and GS selectors in `regs.fs_sel` and `regs.gs_sel` (`x86_64/cpu.h`). A program may load into FS or GS the null selector, the user data selector, either user code selector (`0x23` or `0x33`), the selector of one of its TLS entries, or a readable user segment of its LDT: the kernel's descriptors have DPL 0. Each of these loads also in ring 0, so the switch may load whatever the thread left. The same holds for DS and ES, whose selectors the record has in `regs.ds_sel` and `regs.es_sel` and which the switch, fork and exec save and load beside FS and GS; long mode ignores their bases.
* `sys_arch_prctl` (`x86_64/tls.c`) loads the null selector into FS and writes an `ARCH_SET_FS` base into `tls_base` and IA32_FS_BASE, or loads it into GS and writes an `ARCH_SET_GS` base into `regs.gs_base` and IA32_KERNEL_GS_BASE, where the `swapgs` of the return finds it. Linux loads the null selector in the same way. `ARCH_GET_FS` and `ARCH_GET_GS` read IA32_FS_BASE and IA32_KERNEL_GS_BASE, since the record may be out of date: a program that loads a selector into FS or GS sets that base to the descriptor's without a system call.
* A base to set must be below `USER_ADDR_MAX`, `0x00007FFFFFFFF000` (`x86_64/cpu.h`), or `arch_prctl` fails with EPERM. `arch_clone_tls`, `PTRACE_ARCH_PRCTL` and the ptrace register writes make the same check, so every base the kernel loads is a canonical lower-half address. Two things depend on that. A `wrmsr` of a non-canonical address into a base MSR raises a general-protection fault in the kernel. And the NMI, the double fault, the machine check and the debug exception may arrive where the saved CS does not show whose GS base is loaded, such as between a `swapgs` and the `iretq` after it, so their entries read the top bit of IA32_GS_BASE, which only the kernel's upper-half `struct cpu` sets.
* `switch_context` (`x86_64/context.c`) is C. It first reads the outgoing thread's selectors from FS and GS and its bases from IA32_FS_BASE and IA32_KERNEL_GS_BASE back into its record (`arch_bases_save`), since a selector load may have changed them. Then `arch_bases_load` loads the incoming thread's selectors where they differ from the ones in the registers, and writes its bases into the same two MSRs afterwards, since a selector load sets the base as well: to the descriptor's for a user selector, and for the null selector to 0 on Intel processors and to nothing new on AMD's. All of this comes before `x86_64_switch` (`x86_64/switch.s`) changes the stacks.
* A load into GS sets IA32_GS_BASE, the kernel's base while it runs, so `x86_64_gs_load` (`x86_64/switch.s`) makes it between two `swapgs` with interrupts off, and the descriptor's base goes into the user's slot. An NMI or another paranoid entry between the two finds a lower-half base in IA32_GS_BASE and swaps, as it does for any entry where the user's base is loaded. No assembly reads the process record, so `arch_context_check` checks only the offsets of `struct cpu`.
* `enter_program` calls `arch_tls_set`, which writes IA32_FS_BASE, and `arch_enter_user` (`x86_64/context.c`) loads the record's selectors and bases with `arch_bases_load` before `x86_64_enter_user` goes to user mode through `swapgs` and `iretq`.
* The GDT has three TLS entries, 12 to 14 (`GDT_TLS_MIN` to `GDT_TLS_MAX` in `x86_64/percpu.h`), as Linux's. `regs.tls` holds the thread's three descriptors, which `sys_set_thread_area` (`x86_64/tls.c`) sets from a `user_desc` it checks as Linux's `tls_desc_okay` does, and `sys_get_thread_area` reads back as a `user_desc`. `arch_bases_load` writes the incoming thread's descriptors into the running processor's GDT before it loads a selector (`arch_tls_load`), and loads a TLS entry's selector even when the register holds it already, since the descriptor under it is the outgoing thread's. `sys_set_thread_area` loads again each data segment register of the caller that holds the changed entry's selector, with the null selector when the entry was emptied, so that the hidden copy of the descriptor is not out of date. `do_fork` copies the descriptors with the record, and `arch_exec_frame` empties them.
* `x86_64_load_gdt` puts the null selector in FS and GS when a processor starts. No entry to the kernel saves a segment selector in its frame or changes FS or GS, so a program's selectors stay in the registers while the kernel runs for it, and only the switch, exec, arch_prctl and `arch_enter_user` load them.

### Fork, clone and exec

* `do_fork` (`rach2/sys/syscall_proc.c`) gives the child the base `clone_with` got from the `CLONE_SETTLS` argument through `arch_clone_tls`, or else the parent's base as `arch_tls_get` reads it now: the record's on i686, where only `set_thread_area` changes it, and IA32_FS_BASE on x86-64. `SC_CLONE_TLS` in each `cpu.h` gives the TLS argument's position, the fourth on i686 and the fifth on x86-64, as Linux has them.
* On i686 the child's frame is a copy of the parent's, so the child returns to user mode with the parent's `%gs` selector. On x86-64 `arch_fork_frame` (`x86_64/context.c`) gives the child the parent's FS and GS selectors from the registers and its GS base from IA32_KERNEL_GS_BASE. A 64-bit `CLONE_SETTLS` changes the FS base. An i386 `CLONE_SETTLS`, through `ia32_clone_tls_set` (`x86_64/tls.c`), requires an explicit entry from 12 to 14, changes its descriptor and the saved FS or GS base when that selector names the changed entry, as Linux's `do_set_thread_area` does. The first switch can then restore the saved bases after loading the selectors without replacing the child's thread pointer with its parent's.
* A child of `fork` has the parent's TCB address, which in its copy of the address space reaches its own copy of the TCB. A thread shares the address space, so `pthread_create` gives it a TCB of its own with `CLONE_SETTLS`.
* `exec_commit` (`rach2/sys/syscall_proc.c`) sets `tls_base` to 0 and loads base 0. `arch_exec_frame` sets `%gs`, `%fs`, `%es` and `%ds` to `0x23` on i686 (`i686/context.c`), and on x86-64 loads the null selector into FS and GS and sets the GS base to 0, in the registers and in the record (`x86_64/context.c`). The new program's C library sets its own thread pointer before `main`.

## Limits

* i686 has one TLS entry, 6, where Linux has three, 6 to 8. `set_thread_area` refuses any other entry with EINVAL, and `PTRACE_GET_THREAD_AREA` reads entries 7 and 8 as Linux reads an unused one.
* The i686 segment always has a 4 GiB limit. Of a `user_desc`, only the base is used; its limit, its granularity bit and its usable bit are ignored.
* i686 registers no `get_thread_area` or `modify_ldt`, so a program has no local descriptor table, and it answers ENOSYS. The x86-64 kernel's `syscall` table registers no `set_thread_area` or `get_thread_area`, which a program reaches by `int $0x80` alone; both its tables register `modify_ldt` ([modify_ldt(2)](../../../man/man2/modify_ldt.2)).
* `arch_prctl` takes only its four codes. Linux's others, `ARCH_GET_CPUID`, `ARCH_SET_CPUID` and the rest, fail with EINVAL.
* On x86-64 a child of `clone` with `CLONE_SETTLS` keeps its parent's FS selector, where Linux gives it the null selector; its FS base is the one it asked for either way.
* A tracer may set an x86-64 data selector to 0, 3, either user code selector, the user data selector, an occupied TLS entry at RPL 3, or an LDT selector at RPL 3 (`sel_set` in `x86_64/ptrace.c`). The switch replaces an LDT selector that cannot load with null. An i386 register write updates FS and GS bases from the selected descriptors; an x86-64 write keeps its explicit base words. A TLS descriptor write, through `PTRACE_SET_THREAD_AREA` or `NT_386_TLS`, updates each saved base whose selector names that entry.

## Tests

`tests/run default` runs the probes below on the architecture in `ARCH`, i686 by default, and `ARCH=x86_64 tests/run default` runs them on x86-64 ([the tests' Readme](../../../tests/Readme.md)). `make test` runs the host tests and, in its core tier, the default suite.

* `tests/tlsprobe.c`, built for i686 alone, calls `set_thread_area` as musl does and loads the selector. It checks eight words through `%gs` across at least 40,000 system calls and busy waits, and on until its user time from `times` has risen at ten of its looks, each rise a timer interrupt taken from user mode; then it binds itself to processor 0 and forks. The child checks that the base it inherited reads the parent's words and sets a TCB of its own; then parent and child each check their own words across at least 3,000 busy waits, until the parent has seen the child's processor time, user and system, in `/proc/PID/stat` rise at twenty of its looks, each a switch to the child and back, and then across 200 rounds of a byte passed over two pipes, each round a switch to the child and one back. It prints `All TLS checks passed!`. On x86-64 the runner reports it as `i686 only, not run`.
* `tests/fsbaseprobe.c` checks on x86-64 that `arch_prctl` sets and reads both bases, that they survive fork and context switches, that loading a selector into FS or GS sets that base to 0, that `arch_prctl` and `clone` refuse a base at or above `USER_ADDR_MAX` with `EPERM`, that a selector one process loads into DS, ES, FS and GS stays its own across switches to another on the same processor, and that ptrace reads and writes a stopped thread's selectors. It prints `FSBASEPROBE OK`; on i686 it says its rows did not run and passes.
* `tests/musl/threadmusl.c` starts four threads with `pthread_create`, which passes `CLONE_SETTLS`, and checks that each has its own copy of a `__thread` variable. It and every other musl program in the suite set their thread pointer through musl's startup.
* `tests/run host` runs `tests/host/tls_hosttest.c` ([the host tests](../../../tests/host/Readme.md)), which checks i686's `tls_resolve_base`: it accepts musl's request and an explicit entry 6, and refuses another entry, a descriptor without the 32-bit flag, a code segment, a read-only or a not-present segment, and null arguments. `tests/host/tls64_hosttest.c` checks `x86_64/tls.c` over a model of the base registers: the bound on a base, the registers `arch_prctl` writes and reads, and its errors.
* `tests/musl/ptracemusl.c` moves a stopped child's thread pointer and requires the child to read through it: by `PTRACE_ARCH_PRCTL` and `POKEUSER` on x86-64, where a base at or above `USER_ADDR_MAX` must be refused by `PTRACE_ARCH_PRCTL` with `EPERM` and by `POKEUSER`, `SETREGS` and `SETREGSET` with `EIO`, and by `PTRACE_SET_THREAD_AREA` on i686, whose entries 7 and 8 must read as unused and take only an unused entry.

# The architectures

`rach2/sys/arch/` has the kernel code that differs between processors and between machines. The rest of the kernel, `kernel.c` and the files `C_SRC_SHARED` lists in `rach2/sources.mk`, is the shared code: it compiles for every architecture and reaches this directory only through `arch.h`, `uabi.h` and the subsystem headers listed below. Two architectures are complete, `i686` and `x86_64`, and both run on the PC platform of `x86/`; `arm/` and `arm64/` have headers alone, so that the shared code is compiled for them and kept free of what only an x86 has. This document covers the processor's part of each architecture: the entry from the loader, the descriptor tables, the entry from an interrupt or a system call, paging, the context switch, the kernel stacks and the double fault, and the rules the shared code keeps. [The PC platform](x86/Readme.md) covers `x86/`, and [thread-local storage](tls.Readme.md) the thread pointer on both architectures.

## Interfaces

`x86/` has the PC platform and what both x86 processors share: the primitives of `arch.h` (`cpu.c`), the interrupt routers (`isr.c`), the work of a return to user mode (`leave.c`), the debug registers (`debugreg.c`), the floating-point state (`fpu.c`), and `k_main` (`boot.c`), the C entry both `loader.s` call. `arm/` and `arm64/` have `cpu.h` and `uabi.h` and no code.

### arch.h and uabi.h

`arch.h` includes the `cpu.h` of the compiler's target, chosen by its predefined macro (`__x86_64__`, `__i386__`, `__aarch64__` or `__arm__`), so that no source list or include path can choose the wrong one; another target is an `#error`. A host test, compiled with `RACH2_HOSTTEST` by the build machine's compiler, gets i686's, or x86-64's when it also defines `RACH2_HOST_X86_64`, which a 64-bit host needs; there, as on i686, `arch_cpu_id()` is 0, or the test's `host_cpu` under `RACH2_HOST_CPU`. `cpu.h` defines the types and constants the opening comment of `arch.h` lists: the saved registers of an entry, `isr_params_t`, with the accessors of a system call's number, arguments and result (`SC_NR`, `SC_ARG`, `SC_RET`); the page and its entry; physical memory and the `mmio_` accessors of a device's registers; the kernel's layout; the user ABI, from the user address range to clone's two arguments whose order differs (`SC_CLONE_TLS`, `SC_CLONE_CTID`); the interrupt vectors; and `arch_cpu_id()`, the running processor's index in the table of `proc/percpu.h`.

`arch.h` declares the functions, which each architecture defines:

* The processor's primitives, in `x86/cpu.c` for both: interrupts on and off, the idle wait, the stop, the spin hint, the atomic exchange and compare-exchange that the spinlocks and the big lock are made of, the page table root and the TLB, the fault address, the cycle counter, `RDRAND` and `RDSEED`, the word copy and fill of `k_memcpy` and `k_memset`, the cache write-back and fence of a device's DMA, and `arch_run_on_stack`.
* A thread's frames, in `context.c`: a new thread's first switch (`arch_context_init`), a fork's child's (`arch_fork_frame`), an exec's frame (`arch_exec_frame`), the check of the offsets the switch reads (`arch_context_check`), and the entry to user mode (`arch_enter_user`, in `loader.s` on i686).
* The thread pointer, in `tls.c`; the system call table, `arch_syscall_init` in `systab.c`.
* ptrace and core files, in `ptrace.c`: the registers, the single step, the architecture's own requests (`arch_ptrace`), the register sets of `PTRACE_GETREGSET` and a core file's floating-point notes; and the hardware breakpoints (`arch_debug_switch`), in `x86/debugreg.c`.
* The debug shell's `usermode` payload, `arch_user_test_code` in `usertest.c`: code that writes `Hello from ring 3!` and exits, by `int 0x80` on i686 and by `syscall` on x86-64.

`uabi.h` chooses the target's `uabi.h` the same way. Each has the user structures whose layout differs past what C's types give: `struct user_stat`, `struct user_statfs` and the System V IPC records of `IPC_STAT`, with the macros `STAT_SET_INO` and `IPC_TIME_SET`; i686's also has `struct linux_stat` and `ARCH_WANT_OLD_STAT`, for the older structure of i386's `stat`, `lstat` and `fstat`. A structure whose C types give each processor Linux's layout is declared where it is used, as `struct kernel_iovec` and `struct kernel_msghdr` are in `sys/syscall_internal.h`.

### The subsystems' headers

These headers belong to their subsystems, and the architecture defines what they declare:

* `mm/paging.h`: the page tables, in each `mmu.c`: the reach of physical memory (`mmu_phys_reach`), the frame table's place (`mmu_frame_table`), the steps of `init_paging` (`mmu_init`, `mmu_start`, `mmu_heap_ready`), a process's directory (`clone_page_directory`, `switch_page_directory`, `get_page_dir_phys`, `free_user_pages`, `free_page_directory`), the leaf tables the shared code writes (`mmu_user_table`, `mmu_user_skip`, `mmu_kernel_table`), `paging_virt_to_phys`, `premap_kernel_window` and `paging_set_user`. A directory's layout is in `mmu.h`.
* `proc/sigframe.h`: the signal frames and the layout of `siginfo_t`, in each `sigframe.c`.
* The platform's, in `x86/` on a PC ([the PC platform](x86/Readme.md)): `fpu.h`, `lib/kirq.h`, `irq.h`, the `timer_` functions of `timer.h`, the clock's reading, setting and alarm of `rtc.h`, `udelay.h`, the configuration space and port I/O of `pci.h`, `serial.h`, `speaker.h`, `power.h`, `acpicall.h`, which `sys/acpi/call.c` defines, `module.h`, `fs/cpuinfo.h`, the boot record of `boot.h`, which `x86/boot.c` fills, and `platform.h`, the machine's devices and the start of the other processors.

## Design

### The entry from the loader

Either loader enters `_start` of `loader.s` in 32-bit protected mode with paging off, its magic in EAX and the physical address of its information in EBX; [the kernel's document](../../Readme.md) describes the two headers, `k_main` and the boot record.

On i686 the kernel is linked at 1 MiB and runs at its physical addresses. `_start` first checks, with registers alone, that the machine's memory reaches `_end`, as the next paragraph but one says. It then sets ESP to the top of the boot stack, 16 KiB, and pushes EBX and EAX. It checks that the processor has `cpuid`, by changing `EFLAGS.ID`, and that CPUID leaf 1 lists the time-stamp counter and `cmov`, which the kernel's code, compiled for the i686, uses; on a processor without one of the three, it writes `boot: refused: the processor has no cpuid, and this kernel is i686`, with `rdtsc` or `cmov` in place of `cpuid`, to COM1 and stops. It then calls `init_gdt`, so that `%fs` has the processor's own segment from the first C code on, and calls `k_main` with paging off. `init_paging` (`mm/paging.c`) turns paging on through `mmu_start`, which loads the kernel's directory and sets `CR0.PG` and `CR0.WP`; the window below `HARD_MEMORY_LIMIT`, 64 MiB, is identity-mapped, so execution goes on at the same addresses.

On x86-64 the kernel is linked at `KVA_IMAGE`, `0xFFFFFFFF80000000`, plus its physical address (`link.ld`), so the 32-bit code of `_start` refers to each symbol by its address less `KVA_IMAGE`. `_start` checks that the machine's memory reaches `_end`, as the next paragraph says, saves EAX and EBX and checks CPUID for long mode; on a processor without it, it writes `boot: refused: the processor has no long mode, and this kernel is x86-64` to COM1 and stops. It builds page tables that map the first 4 GiB in 2 MiB pages at 0 and at `KVA_DIRECT`, and the first 2 GiB at `KVA_IMAGE`; turns on PAE, `EFER.LME`, `EFER.NXE` where the processor has NX, then paging and `CR0.WP`; loads a boot GDT; and jumps to 64-bit code, which moves to the kernel's own addresses, takes the boot stack, writes the address of the boot processor's record, `cpus[0]`, into the GS base MSR, and calls `k_main` with the information's address in the direct map. `mmu_frame_table` later loads the kernel's own PML4, which maps nothing in the lower half.

A Multiboot loader, QEMU's `-kernel` among them, copies the kernel to 1 MiB and starts it whether or not the machine's memory reaches `_end`, the end of `.bss`; the boot stack and the first page tables then lie past the end of memory, and the first call or the first page walk faults with nothing printed. So on both architectures `_start`, before it writes any byte of `.bss`, compares `mem_upper` of the Multiboot information, the KiB that run on from 1 MiB without a hole, with the KiB from 1 MiB to `_end`, and on a machine that has fewer writes `memory: refused: the kernel ends past the memory the loader reports` and `memory: too little for this kernel` to COM1 and stops. GRUB's multiboot2 loader allocates the kernel's whole range from the memory map and refuses a kernel that does not fit, so a multiboot2 boot is not checked. A machine whose memory reaches `_end` but leaves too little after it is refused later, by the memory report ([mm/Readme.md](../mm/Readme.md)).

### Descriptor tables and the processor's record

On i686 each processor has a GDT of nine entries (`gdt.c`): the null descriptor; flat code and data for ring 0, 0x08 and 0x10, and for ring 3, 0x1B and 0x23; its TSS, 0x28; the TLS segment, 0x33; the double fault's TSS, 0x38; and its own data segment, 0x40, whose base is the processor's `struct i686_cpu`, so that `arch_cpu_id` is one load from `%fs:0`. Every entry to the kernel loads 0x40 into `%fs`. The TSS (`tss.c`) gives the ring-0 stack, `esp0`, that an entry from user mode takes, which the context switch rewrites, and an I/O map base past the segment's end, so that every port access from ring 3 faults. One IDT (`idt.c`) serves every processor. The exceptions, the 8259's lines on 32 to 47, the message vectors 48 to 239 but for 0x80, the interprocessor interrupt at 0xF0 and the APIC's spurious vector 255 have interrupt gates at DPL 0; the breakpoint and the overflow, 3 and 4, and the system call, 0x80, have interrupt gates at DPL 3, so that `int3`, `into` and `int 0x80` reach them from user mode; and the double fault, 8, has a task gate.

On x86-64 each processor's `struct cpu` (`percpu.h`) has a pointer to itself at offset 0, the top of the running thread's kernel stack at 8, the user stack pointer of a `syscall` at 16, the processor's index at 24, and its GDT and TSS. In the kernel the GS base points at the record, so `arch_cpu_id` is one load from `%gs:24`. The GDT has Linux's x86-64 layout, sixteen entries (`percpu.h`): kernel code 0x10 and data 0x18, user 32-bit code 0x23, user data 0x2B and 64-bit code 0x33, the TSS at 0x40, the address space's LDT at 0x50, and the thread's three TLS entries, 0x63, 0x6B and 0x73, which the context switch writes ([thread-local storage](tls.Readme.md)). The TSS has `rsp0`, which an entry from user mode takes, the closed I/O map, and four interrupt stacks for each processor (`percpu.c`): stack 1 for the double fault, 8 KiB, and 2, 3 and 4 for the NMI, the machine check and the debug exception, 4 KiB each. The boot processor's are in the kernel's data; another processor's come from the heap before it starts (`arch_ap_prepare`), so that the kernel keeps them only for the processors the machine has. The IDT (`idt.c`) has interrupt gates for the vectors i686's has, the double fault's included, and the i386 system call's at 0x80, at DPL 3; the gates of vectors 1, 2, 8 and 18 select an interrupt stack.

On x86-64 an address space has a local descriptor table once its program writes one by `modify_ldt` (`ldt.c`, [modify_ldt(2)](../../../man/man2/modify_ldt.2)): Linux's largest, 8192 entries, 64 KiB from the heap at the first write, in `struct mm`, shared by its threads, copied by fork and freed with the address space (`arch_mm_copy`, `arch_mm_release`). A write changes one 8-byte descriptor in place, so the table never moves under a processor that has it loaded. `ldt_switch`, which the switch and exec call, writes the table's 16-byte descriptor into GDT entries 10 and 11 and runs `lldt` when the processor's loaded table, `struct cpu`'s `ldt`, is another; a processor running another thread of the space when the first write makes the table loads it at that thread's first general protection fault on a selector of an LDT (`ldt_fault`), where Linux sends an interprocessor interrupt.

The context switch and the entry code read some fields at fixed offsets: three of the process record on i686, the four of `struct cpu` above on x86-64. GCC checks them at build time, and `arch_context_check`, called by `init_proc`, at every boot, for a kernel that TinyCC built, since TinyCC cannot fold an offset into an array size.

### Entry from interrupts and exceptions

Every vector has a stub in `isr_handler.s` that pushes an error code where the processor pushed none, then the vector, so that every frame has the shape of `isr_params_t`. The stubs are written out in full, since TinyCC's assembler has no `.macro`.

On i686 the exception and system call stubs jump to `isr_common_handler`, the line and message stubs to `irq_common_handler`. Each pushes the general registers and the four data segment registers, loads the kernel's segments, and calls its router, `_isr_router` or `_irq_router` (`x86/isr.c`), which takes the big lock, unless the entry is marked to run without it (`isr_entry_lock`), and runs the vector's handlers. Each return calls `isr_leave`, which delivers a pending signal on a return to user mode and gives back the big lock its entry took, then restores the registers and returns by `iret`; an entry that ran without the lock takes it on the return to user mode only for the work `signal_return_work` names, signals, ended threads and a tracer's among it, for an rseq notice (`rseq_notify`), and for loopback datagrams to deliver (`WORK_LOOP`, `syscall_loop_drain`). Signal and rseq work is marked in a call, as a user fault is, with interrupts enabled so that its user copies can take the regions' lock and fault; a timer defers its switch until user mode, so it cannot race the rseq event fetch and clear; after interrupts go off again, a new rseq notice, a deferred tick signal or a signal to act on that came meanwhile (`sig_woken`) repeats the work (`isr_leave_work`, `x86/leave.c`), as Linux's `exit_to_user_mode_loop` goes round for `_TIF_SIGPENDING` (`include/linux/entry-common.h:65`, `kernel/entry/common.c:90-132`), so that a `SIGKILL` posted while a handler's frame or the rseq area is copied ends the thread before the handler runs. A forked child's first switch lands on `isr_return`, the return of `isr_common_handler`.

On x86-64 every exception, line and message stub but those of vectors 1, 2, 8 and 18 jumps to `isr_common_handler`, which runs `swapgs` when the saved CS is at RPL 3, pushes the general registers, and calls `x86_64_route` (`idt.c`), which gives a vector below 32 to `_isr_router` and any other to `_irq_router`. The return, `isr_return`, calls `isr_leave` and falls into `isr_exit`, which pops the frame, runs `swapgs` again on a return to user mode, and returns by `iretq`. A user return address that is not canonical, which only a tracer can write, becomes 0, so that the program takes its `SIGSEGV` in user mode and `iretq` does not fault in ring 0 with the user's GS base loaded; so does one at or above 4 GiB in a frame that returns to the 32-bit code segment, 0x23.

A user selector the kernel loads can fault once the LDT entry it names has changed. The switch's loads of DS, ES, FS and GS (`switch.s`) have labels that `x86_64_fault_fixup` (`context.c`) knows: a #GP, #NP or #SS at one resumes at the load of the null selector, as Linux's fixup does. One at the `iretq` of `isr_exit`, a CS or SS that no longer loads or an address past the code segment's limit, enters `.common_bad_iret`, which turns the frame into one of a fault of the program at its return address, as Linux's `fixup_bad_iret`; the program takes its SIGSEGV or SIGBUS. A fault on the load of GS or at the `iretq` arrives with the user's GS base, so the common entry swaps for those two.

The optional MSR helpers (each architecture's `msr.s`, declared in `x86/kcpu.h`) return -1 on a #GP at their RDMSR or WRMSR instruction. `msr_fixup` (`x86/isr.c`) recognizes those instruction addresses alone and resumes at their failure return. A failed read leaves its output unchanged. `kcpu_msr_safe_regs` loads seven of the general registers from an array before its RDMSR or WRMSR and stores them back after, as Linux's `rdmsr_safe_regs`, for the msr device's register ioctls. The msr device uses the helpers for every access a program asks for, and KVM uses these helpers to probe AMD's legacy performance counters, whose presence has no CPUID bit and which an outer hypervisor may omit; to probe Intel's LBR stack, each of whose registers it reads and writes back at boot before it offers the stack (`lbr_probe`); and to try a write of a guest's LBR register before keeping it (`lbr_io`).

On both, the interprocessor interrupt and the spurious vector enter through `local_common_handler`, which takes no lock and delivers no signal. The NMI and the machine check enter through the paranoid entry, which takes no lock either, since either can arrive while the processor holds the big lock or is taking it; their handler reports a fault of the machine and stops it, but for an NMI the lockup detectors sent or raised, a backtrace request or the counter's overflow, which they take and return from (`watchdog_nmi`, [the lockup detectors](../watchdog.Readme.md)), and the NMI of another processor's stop, which halts this one (`smp_stop_nmi`). On i686 they run on the stack in use. On x86-64 they arrive on their interrupt stacks, perhaps between the `swapgs` of an exit and its `iretq`, so `paranoid_entry` reads the GS base MSR, swaps only when the base is the user's, and swaps back only when it swapped. The routers and the interrupt controllers are [the PC platform's](x86/Readme.md).

An interprocessor interrupt in user mode takes a pending reschedule before returning, without the big lock, which the switch does not need, so a remote affinity change can wait for the thread to leave its old processor. The return passes through `isr_leave` when the thread has a reschedule, signal work or an rseq notification, which consumes the notification after the switch and delivers a signal another processor posted before user instructions resume, as Linux's return from its reschedule interrupt does for `_TIF_SIGPENDING`. An interrupt inside a system call leaves the request for that call's next scheduling point.

### Entry from a system call

Both entries build the frame of an interrupt from user mode with the vector `SYSCALL_VECTOR`, 128, on which `arch_syscall_init` registers the shared dispatcher, `_syscall_handler` in `sys/syscall.c`. [syscalls(2)](../../../man/man2/syscalls.2) gives the registers and the numbers.

On i686 a program makes the call with `int 0x80`, through an interrupt gate at DPL 3: the processor clears IF and takes `esp0` from the TSS, and the stub enters `isr_common_handler`.

On x86-64 a program makes the call with `syscall`. `init_tss` (`percpu.c`) sets `EFER.SCE` and three MSRs: `IA32_STAR`, with the kernel's code selector, 0x10, for the entry and 0x23 for the return, from which `sysret` takes the user's code, 0x33, and stack, 0x2B; `IA32_LSTAR`, the entry, `syscall_entry`; and `IA32_FMASK`, 0x47700, the flags the entry clears: TF, IF, DF, IOPL, NT and AC. The processor puts the user's RIP in RCX and RFLAGS in R11 and leaves RSP as it was. `syscall_entry` runs `swapgs`, keeps the user's RSP in the processor's record, takes `kernel_rsp`, pushes the frame an interrupt would have, and calls the router and `isr_leave`. It returns by `sysretq` when the frame still describes the return the call made: RCX and R11 equal to the saved RIP and RFLAGS, neither TF nor RF set, the user's selectors, and a RIP below `USER_ADDR_MAX`. A frame that a signal, an exec, a signal return or a tracer changed returns by `iretq` through `isr_exit`. From the last pop to `sysretq` the kernel runs on the user's stack with interrupts off, and touches no memory.

On x86-64 `int 0x80` is the i386 system call, from 32-bit code or 64-bit code ([ia32(7)](../../../man/man7/ia32.7)). Its gate, at DPL 3, enters `int80_isr` (`isr_handler.s`), which pushes the error code `SC_ENTRY_IA32` and the vector 128 and goes on as any interrupt; `SC_COMPAT` in `cpu.h` knows the frame by that code, and `SC_ARG` then reads the arguments from EBX, ECX, EDX, ESI, EDI and EBP, zero-extended. `__kernel_vsyscall` enters by a faster instruction where the processor takes one from 32-bit code, as Linux's does: `cpu_ia32_entry` (`percpu.c`) picks `sysenter` for Intel's, Centaur's and Zhaoxin's processors, whose `SYSENTER_CS`, `SYSENTER_ESP` and `SYSENTER_EIP` MSRs `init_tss` sets, and `syscall` through `IA32_CSTAR` for AMD's and Hygon's, and `vsyscall_patch` (`vdso32.c`) writes the instruction over four `nop`s before the library's `int $0x80`. `sysenter_entry` and `syscall32_entry` (`isr_handler.s`) build the frame `int80_isr` would have, with the return address of the `int $0x80` that follows, `vdso32_landing`, so that a restart, a signal frame and a tracer see an `int $0x80` call; the user's stack pointer comes from EBP for `sysenter`, and EBP, which the library moved into ECX's place, back from the user's stack. `ia32_fast_syscall` runs the call and returns by `sysretl` when the frame still returns to the landing in 32-bit code with the flat segments and neither TF nor RF, and by `iretq` otherwise. `sysenter` keeps the caller's TF, so a debug exception at the first instruction of `sysenter_entry` is let pass until `sysenter_stepped` (`debugreg_drop_sysenter`), and the trap comes at the return, as on Linux. The switch loads the kernel's data selector into SS (`x86_64_ss_kernel`), since a `sysret` on AMD's processors after an interrupt left SS null returns an unusable stack segment.

### The system call tables

`systab.c` fills the shared table of `SYSCALL_TABLE_SIZE`, 463 entries on both, from `sysnr.h`, which has Linux's numbers for the architecture; the handlers are shared, and the table decides which numbers a program reaches. On x86-64 `ia32_systab.c` fills a second table, of `IA32_SYSCALL_TABLE_SIZE`, 463 entries, from `ia32_sysnr.h`, which has each of Linux 6.12's i386 numbers; the dispatcher takes it for a call that entered by `int 0x80` (`syscall_table_of` in `sys/syscall.c`), and `in_compat_syscall` tells a handler which one it runs for. A row of it is the x86-64 handler where the call's arguments and structures have one layout in both interfaces, a compat handler of an `ia32_` file where they differ, which `IA32_STUB` in `ia32.h` makes answer `ENOSYS` until its translation is written, or empty. `ia32_exec.c` has the written ones of `execve`, `execveat`, `clone` and the two `mmap` calls: the first two run the shared handlers, which read 4-byte pointers in an i386 call (`exec_vec_get` in `sys/syscall_proc.c`), `clone` passes its arguments in i386's order to `ksys_clone`, and the `mmap` calls reach `ksys_mmap_pgoff`, which first seeks an i386 call's mapping below `IA32_MMAP_BASE`, then falls back over the whole free range below the stack's growth window and its 1 MiB guard gap. [syscalls.md](../../syscalls.md) lists the calls each table registers, with their numbers, and [syscalls(2)](../../../man/man2/syscalls.2) gives the registers.

`ia32_ioctl_gpu.c` translates i915 GETPARAM's eight-byte request and 32-bit int pointer. It checks the driver's VERSION name first, since virtio-gpu uses the same request number for TRANSFER_FROM_HOST. The GEM, virtio-gpu, dma-buf, syncobj, sync_file and udmabuf requests pass with their fixed-width fields; [ia32.md](../../ia32.md) lists them.

`RACH2_IA32` (`x86_64/cpu.h`), 1 unless `make IA32=0` makes it 0, says whether the x86-64 kernel has the i386 ABI, as Linux's `CONFIG_IA32_EMULATION` does. Under 0 `cpu.h` defines neither `SC_COMPAT` nor `IA32_SYSCALL_TABLE_SIZE`, which the shared code tests, so that the compat table, the paths of the shared code that test them and the ELF32 loader drop out; the compat files, the `ia32_` files, `sigframe32.c` and `vdso32.c`, compile to nothing, and `init_idt` sets no gate at 0x80, while every manifest lists the same files. `vdso32code.s`, `sysenter_entry` and `syscall32_entry`, assembly that is not preprocessed, stay as code nothing enters, and `percpu.c` gives the entries an `ia32_fast_syscall` that answers ENOSYS. Under 1 the boot option `ia32_emulation=` turns the ABI off at run time (`ia32_enabled`, `ia32_exec.c`), as Linux 6.7's does: `init_idt` sets no gate at 0x80, so that `int 0x80` raises #GP; `init_tss` points `IA32_CSTAR` at `syscall32_ignore`, which returns ENOSYS by `sysretl`, and writes 0 into the `sysenter` MSRs, whose null code selector makes `sysenter` raise #GP, as Linux's `idt_syscall_init` sets them; and `elf_valid_exec` refuses an i386 program, whose exec then fails with ENOEXEC. Either way the GDT keeps the 32-bit code segment, as Linux's does, and `modify_ldt` and the TLS calls, which x86-64's own table has, stay.

`sys_ia32.c` has i686's forms of the calls to which i386 passes a 64-bit offset or length in two registers, low word first: `truncate64`, `ftruncate64`, `pread64`, `pwrite64`, `fallocate`, `fadvise64` and `fadvise64_64`. Each joins the halves and calls the shared `ksys_` core (`sys/syscall_internal.h`). i686 also has `socketcall`, 102, beside the direct socket calls, and x86-64 has none. x86-64's `systab.c` has adapters for the calls it makes another way: `accept` as `accept4`, and Rach2's own [ping(2)](../../../man/man2/ping.2), 400, which i386 reaches as `socketcall`'s operations 0x1000 to 0x1002.

### Paging

On i686 (`i686/mmu.c`) a directory has 1024 entries, each pointing to a table of 1024 page entries; without PAE a physical address has 32 bits, so the kernel reaches 4 GiB. A `struct page_dir` is two pages: the tables' kernel addresses, then the entries the processor reads, whose physical address CR3 takes. The kernel's directory identity-maps the window below 64 MiB, supervisor-only, in 16 tables, and has a table for each 4 MiB of the kernel's gigabyte, made at boot; `clone_page_directory` copies those entries, so every directory shares the kernel's tables and a kernel mapping made later is seen by every process. No entry can forbid an instruction fetch.

On x86-64 (`x86_64/mmu.c`) every table is reached through the direct map, at `KVA_DIRECT` plus its physical address, so a directory is its PML4 alone. The kernel's PML4 has the upper half: the direct map, in 1 GiB pages where the processor has them and 2 MiB pages where not, writable and not executable; the image in 4 KiB pages, its text read-only, its read-only data read-only and not executable, its data and `.bss` writable and not executable; and eight PML4 entries for the windows. A process's PML4 copies the 256 entries of the upper half, so the tables below them are shared. `PTE_NOEXEC` is `PTE_NX` where `EFER.NXE` is on, and 0 elsewhere (`mmu_nx`).

A page directory of the lower half that `table_for` makes once the heap exists takes two consecutive frames (`pd_alloc`), and its PDPT entry has bit 9, `PDPT_KEEPS`, which the processor ignores. The second frame holds, for each directory entry, the physical address of the leaf table a 2 MiB page replaced, so that a transparent huge page (`PTE_PS` in the directory entry, `mmu_user_huge_set`) keeps its table beneath it and `mmu_user_table` returns that table, and `mmu_user_huge_clear` gives the entry its table back with one atomic exchange, hidden: bit 9 of a directory entry with its present bit clear, `PDE_HIDDEN`, names the table while the processor faults on the range, and `table_for` and `mmu_user_skip` walk it as if present, until the shared code has flushed and shows it again (`mmu_user_table_hide`, `mmu_user_table_show`) ([memory](../mm/Readme.md#transparent-huge-pages)). A directory without the bit, made before the heap or when no two consecutive frames were free, maps no huge page. `free_user_pages` gives a huge page's entry its table back before it frees the pages, and `free_page_directory` frees the second frame with the directory.

Both kernels set `CR0.WP`, so that a write from ring 0 to a read-only page faults, which copy-on-write and the page cache's dirty tracking depend on. The kernel's layout on each architecture, and the paging code they share, are [memory's](../mm/Readme.md).

### The context switch

The switch pushes the outgoing thread's callee-saved registers on its kernel stack, saves its stack pointer in its record, takes the incoming thread's, pops the same registers and returns to where that thread last called the switch.

On i686 `switch_context` is `switch.s`. It pushes EBP, EBX, ESI and EDI and saves ESP; gives the TSS the incoming kernel stack; with interrupts off, writes the incoming thread pointer into the TLS descriptor and loads 0x33 into `%gs`; and calls `switch_space` (`context.c`), which loads the incoming page directory unless the processor has it loaded and no shootdown has passed it, and leaves a thread with none, an idle task or a kernel thread, in whatever is loaded. A change of a kernel mapping is dropped on every processor before it returns (`smp_kernel_flush`), so the switch drops nothing for it.

On x86-64 `switch_context` is C (`context.c`), around `x86_64_switch` (`switch.s`), which pushes RBP, RBX and R12 to R15 and exchanges the stack pointers. Before it, the outgoing thread's DS, ES, FS and GS selectors are read from the registers and its FS and GS bases from their MSRs, since a program changes them by loading a selector, which the kernel does not see; then the incoming kernel stack goes to `rsp0` and `kernel_rsp`, its selectors are loaded where they differ from the outgoing thread's, the FS base goes to `IA32_FS_BASE` and the GS base to `IA32_KERNEL_GS_BASE`, where the `swapgs` of the return to user mode finds it, and the PML4 is loaded by i686's rule.

`arch_context_init` lays out a new thread's stack so that its first switch returns into its entry function. `arch_fork_frame` lays out a child's: a copy of the parent's frame with 0 as the call's result, below it the return address `isr_return` and zeroed callee-saved registers, so that the child's first switch returns to user mode by the common return. `arch_exec_frame` clears the general registers other than the call's result and sets the entry, the stack pointer and the user's segments. `schedule` saves and loads the floating-point state around the switch ([the PC platform](x86/Readme.md)).

### Signal frames and ptrace

Each `sigframe.c` builds and restores Linux's frames for the architecture. On i686 a plain handler gets `struct sigframe` and an `SA_SIGINFO` one `struct rt_sigframe`, each with a return code that calls `sigreturn`, 119, or `rt_sigreturn`, 173, for an action without `SA_RESTORER`. On x86-64 every handler gets `struct rt_sigframe` and returns to the action's `sa_restorer`, which must be given and calls `rt_sigreturn`, 15. The frame saves CS and SS as they were, with `UC_SIGCONTEXT_SS`, and `UC_STRICT_RESTORE_SS` for a signal taken in 64-bit code; the handler runs in 0x33. The return restores CS when it is 0x33, or 0x23 with a RIP below 4 GiB, and SS when `lar` reads it as a present, writable data segment of DPL 3; it ends the process with `SIGSEGV` for another CS, and for another SS when the strict flag is set or CS is 0x23, and otherwise puts 0x2B in place of the SS, as Linux's `restore_sigcontext` does. [Signals](../proc/signal.Readme.md) gives the layouts.

Each `ptrace.c` has the registers in Linux's `user_regs_struct`, the words of `struct user` (284 bytes on i686, 928 on x86-64), the floating-point state and the register sets, and also on i686 `PTRACE_GET_THREAD_AREA` and `PTRACE_SET_THREAD_AREA`, and on x86-64 `PTRACE_ARCH_PRCTL`. [ptrace](../proc/ptrace.Readme.md) describes the requests.

### Kernel stacks, the guard page and the double fault

A kernel stack is `KERNEL_STACK_SIZE`, 16 KiB, with an unmapped page below it. The boot stack, on which the boot, process 0, the debug shell and the first program run, is in the image's `.bss` above its guard page (`loader.s`), which `guard_boot_stack` (`kernel.c`) unmaps once paging is on. A process's stack comes from `kstack_alloc` (`sys/syscall_proc.c`), whose `kalloc_guarded` leaves the page below it taken and never mapped.

A store into the guard page faults. While the stack pointer is above the guard, the processor can push the page fault's frame, and the page fault handler (`mm/paging.c`) finds the address in the guard below the running thread's stack (`kstack_overrun_pid`), logs `vm: fault: in kernel mode at ...: pid N ran past the end of its kernel stack` and panics with `page fault: a kernel stack ran out`. Once the stack pointer is in the guard, the processor cannot push that frame and raises a double fault, vector 8, which must run on another stack, or the processor faults a third time and resets.

On i686 the gate of vector 8 is a task gate for the selector 0x38, which each processor's GDT resolves to that processor's `double_fault_tss`. The processor saves the running state into its `kernel_tss` and loads the double fault's: the kernel's page directory, which `mmu_start` writes there before paging is on, a 16 KiB stack of its own, interrupts off, the kernel's segments, and the entry `isr_double_fault` (`x86/isr.c`). This is the kernel's one hardware task switch; processes switch by software. On x86-64 the gate of vector 8 is an interrupt gate with interrupt stack 1, so the processor moves to that processor's 8 KiB double fault stack whatever stack was in use, and `paranoid_entry` reaches `_double_fault_handler` (`x86/isr.c`).

Either handler asks `kstack_overrun_pid` whether CR2 is in the guard below the running thread's stack. If it is, the handler logs `isr: kernel exception: double fault (vector 8, eip 0x..., esp 0x...): pid N ran past the end of its kernel stack at 0x...`, with `rip` and `rsp` on x86-64, and panics with `double fault: a kernel stack ran out`; i686's pointers are the ones the task switch saved in `kernel_tss`. Any other double fault is logged with CR2 and panics with `unrecoverable CPU exception in kernel mode`. The record is written out directly, even when the fault came while another record was being written. `rach2.stackoverrun=fork` and `rach2.stackoverrun=boot` run a thread down a stack from `kstack_alloc`, or process 0 down the boot stack, before the first program (`kstack_overrun_test`).

### The debug exception on x86-64

On i686 the debug exception, vector 1, has an ordinary interrupt gate. On x86-64 it has interrupt stack 4, since a debug exception that `MOV SS` delayed can arrive after `syscall` has entered ring 0 and before `syscall_entry` has changed the stack or GS; `debug_entry` therefore reads the GS base MSR, as `paranoid_entry` does. An exception from user mode has its frame copied to the thread's kernel stack and is handled there like any other. One from kernel mode is dropped, as Linux drops it, by `debugreg_drop` (`x86/debugreg.c`), which clears DR6 and turns this processor's breakpoints off until the next switch or return to user mode. [ptrace](../proc/ptrace.Readme.md) describes the debug registers.

### The other processors

`trampoline.s` is the first code of a processor the boot processor starts, copied to physical address 0x8000. It goes from real mode to protected mode and paging on i686, and to long mode on x86-64, and calls `x86_ap_entry` on the stack it was given; `arch_ap_tables` (`i686/gdt.c`, `x86_64/percpu.c`) gives the processor its GDT, its TSS and the IDT, and on x86-64 the kernel's PML4, its GS base and `syscall`. [The PC platform](x86/Readme.md) describes the start.

### The vDSO on x86-64

The vDSO is one page of code that every new image maps and calls for the clock, and the page of data below it that the kernel writes; `../vdso.h` declares both halves, and [vdso(7)](../../../man/man7/vdso.7) has the contract.

`vdso.c` builds the image at boot in a frame of its own, as a linker would lay out a shared object of base address 0: the ELF header, a `PT_LOAD` of the whole page, read and execute, and a read-only `PT_DYNAMIC`, then a SysV `DT_HASH` table, the dynamic symbols, their strings, `DT_VERSYM` and `DT_VERDEF` with the versions `linux-vdso.so.1` and `LINUX_2.6`, the dynamic section, and from `VDSO_TEXT_OFFSET`, 0x800, the code that `vdsocode.s` assembles into the kernel between `vdso_text_start` and `vdso_text_end`, copied in; then section headers, which gdb and readelf read. Each of the five functions has a global `__vdso_` symbol and a weak one of the plain name. The code reaches the data page at `vdso_text_start - 0x1800(%rip)`, one page and `VDSO_TEXT_OFFSET` back, and KVM's clock page for the boot processor a page below that, which holds wherever they are mapped, and its only other references are to itself, so the copy runs at any address. It reads the page as a sequence lock: `seq`, then `lfence; rdtsc; lfence` and the fields, then `seq` again, and again from the start when `seq` was odd or moved. The time zone that `gettimeofday` gives is the exception: `settimeofday` stores its two fields on the page outside the sequence count (`vclock_set_tz`), and the vDSO copies them without it, as Linux's `update_vsyscall_tz` and `__cvdso_gettimeofday_data` do (`kernel/time/vsyscall.c`, lines 129 to 137, and `lib/vdso/gettimeofday.c`, lines 330 to 337), so that a program that asks for the zone on every call, as Chromium's clock does, makes no system call. Every function makes the system call when the page's `mode` is `VCLOCK_NONE`. In `VCLOCK_PVCLOCK`, the mode where KVM's clock pages are kept, the page's count is KVM's clock in nanoseconds, read as Linux's `vread_pvclock` reads it (`arch/x86/include/asm/vdso/gettimeofday.h`, lines 197 to 232): the KVM page's version made even, its PVCLOCK_TSC_STABLE_BIT checked, the TSC read and converted by the page's stamp, rate, shift and system time as `__pvclock_read_cycles` converts it (`arch/x86/include/asm/pvclock.h`, lines 44 to 90), a TSC before the stamp taken as the stamp, as the kernel's reader takes it, and the version read again, the reading made again when it moved; the top bit is dropped, as `vread_pvclock` drops it. The 32-bit code makes the 64-bit product from two 32-bit ones, as Linux's i386 `pvclock_scale_delta` does. A clear bit makes the system call at once, without waiting for the tick to stop the clock.

`vclock.c` keeps the clock behind the page. `vclock_start`, run once every processor has started, turns it on where `timer_calibrate` measured the TSC, or `timer_tsc_watch` measured one that nothing vouches for (below), and `tsc_synced` found every processor's check finished with none behind the boot processor ([the PC platform](x86/Readme.md)), or, where KVM's clock pages are kept, whatever the processors' TSCs read, since the clock can count kvm-clock; and where only the boot processor's KVM clock page stands in the way, having withdrawn its stable bit, the tick tries the start again at each pass, as after a stop; it chooses `mult` and `shift` so that `mult` / 2^`shift` is the nanoseconds of one count. The page's count is the TSC, or, where KVM's clock pages are kept, KVM's clock in nanoseconds, the TSC converted through a clock page, as Linux's kvm-clock counts its nanoseconds as its cycles at 1 GHz (`kvm_clock_read` and `kvm_clock_get_cycles`, `arch/x86/kernel/kvmclock.c`, lines 74 to 87 and 347), so a new rate or system time KVM gives its pages, with the stable bit kept or not, moves the clock as it moves KVM's clock. Which of the two the clock counts where KVM's pages are kept follows Linux's ratings (`timer_tsc_kvm`, [the PC platform](x86/Readme.md)): kvm-clock, in `VCLOCK_PVCLOCK`, unless the TSC is rated above it, the watch has not found it parted and every processor's agreed at its start (`vclock_tsc_over_kvm`), where the clock is `VCLOCK_TSC` as on a machine without KVM, while the tick's clocks, which it is steered toward, count kvm-clock. `no-kvmclock-vsyscall` refuses `VCLOCK_PVCLOCK`, so the clock then runs only on such a TSC. `vclock_tick`, at each timer pass with interrupts off, the boot processor's tick's or a late one's on another processor (`kernel.c`), moves the page's times to the page's count now and compares the monotonic and raw clocks with the reference's, `rtc_tick_both`'s reading of the tick's clocks to the place within the tick: it sets the monotonic clock's `mult` to the measured rate at the rate of the NTP state's tick length (`rtc_mono_rate`, [the kernel](../../Readme.md)) and the raw clock's `raw_mult` to the measured rate, steers each toward its reference by a proportional term of at most one part in 2000, moves a clock more than a tick behind forward at once, and never moves one back. The writer makes `seq` odd, then `mfence`, then reads the TSC, so that no reader takes the old base with a later count. `clock.c`'s monotonic, raw and real clocks read the same clock through `vclock_read` while it runs (`VCLOCK_READ_MONO`, `VCLOCK_READ_RAW`, `VCLOCK_READ_REAL`), so a system call and the vDSO agree. A watched TSC, which `vclock_begin` marks where neither `timer_calibrate` nor KVM gave a rate, is checked by `vclock_watch` as Linux's clocksource watchdog checks one (`kernel/time/clocksource.c`, lines 108 to 148 and 419 to 560 in 6.12): its counts at the measured rate over a span of at least half a second of the raw clock are set against that span, and a parting of more than 248 microseconds, the sum of Linux's margins for the TSC and the HPET, stops the clock for good at the next tick (`vclock_parted_why`). Where KVM's clock pages are kept and the TSC is the clock, the tick's clock it is set against is kvm-clock, which Linux takes for the watchdog of such a TSC as the best clock source that needs no watching itself (`clocksource_select_watchdog`), unless Linux would leave the TSC unwatched; its rate is KVM's, so no first span measures it, and a TSC that parts stops the clock only until the next tick starts it again on kvm-clock, as Linux takes its next clock source once the TSC is marked unstable. Each span ends on the next online processor after the one it began on, as Linux's watchdog moves its timer to the next online processor on each pass, so a processor whose TSC drifts from the others' after the boot's check (`tsc_synced`) parts its span from the clock; the vDSO reads whichever processor's TSC it runs on. The tick marks a span due once it is long enough and kicks the processor whose turn it is, which reads the span's end at its own tick or in the interprocessor interrupt the kick sends one with its tick stopped (`vclock_watch_cpu`, run by `timer_handler` in `kernel.c` and by `smp_ipi`), as Linux's `add_timer_on` wakes the processor it puts the timer on. A processor whose turn has lasted half a second of the raw clock and four clock passes without its reading of the span's end, since it took neither its tick nor the kick or every reading was held up, loses its turn and the span with it, unjudged, and the next online processor begins a new span, as Linux's watchdog timer, late on a processor that did not run it, skips that comparison and moves on to the next processor, with no deadline of its own; only a measured parting stops the clock, so a processor late or silent skips its own comparison but holds up no other's. A turn that passes on because its processor went offline begins anew, and the four passes keep a stretch the whole machine spent stopped, as a guest whose host did not run it, from ending a turn in one pass. A reading of the tick's clocks whose two TSC readings lie more than 124 microseconds apart is read again, three times in all, as Linux's `cs_watchdog_read` reads again a held-up read of the HPET; where all three were held up the span keeps its start and the next tick tries again. A span is due once it is long enough by the tick's clock or by the TSC at the measured rate, as Linux's watchdog timer expires by jiffies, which follow the clock source under watch (`tick_do_update_jiffies64` from `ktime_get`, `kernel/time/tick-sched.c`), so a TSC that runs fast reaches its span's end early and parts from the clock there. A span past twice its length by either clock begins again unjudged, every time, as Linux skips the comparison when the longer of the two intervals passes `WATCHDOG_INTERVAL_MAX_NS` (`clocksource.c`, lines 501 to 511), with no count and no other test of continuity: a stretch with no tick that loses a wrap of the tick's counter, as one of 43.45 s loses a wrap of the HPET's 32 bits at 100 MHz, reads short by the tick's clock and whole by the TSC, and begins its span again however often it comes. A TSC that runs more than twice fast on a processor whose tick does not end its span is skipped so too, as Linux skips it on a processor that does not keep jiffies. The first span, of a second, read on one processor, measures the rate again instead (`timer_tsc_watch_refine`), as Linux's `tsc_refine_calibration_work` does a second after boot. Where it differs from the boot's rate by more than a hundredth, the first span is measured again, and its rate is set only where two in a row agree within the watch's margin of 500 parts in a million (`vclock_watch_refine`), so the watch never judges against a rate it found wrong; a measure more than a twentieth from the boot's rate is no trial, and a TSC whose third first span still agrees with neither parts from the clock. The fine readers check the page's `mode` inside each pass of their sequence-count loops, as Linux's `do_hres` does (`lib/vdso/gettimeofday.c`, lines 141 to 169). A fine reading that the clock's stop overtakes falls back to the kernel's clock. At each tick's edge `vclock_tick_edge` publishes the coarse clocks under the same sequence count in every mode, as Linux's `update_vsyscall` does. The coarse readers and `__vdso_time` in both libraries use those fields. The stop and the start run inside `rtc_vclock_change` (`clock.c`), with real time's lock and the floors' held: the stop makes `seq` odd, reads the clock's last times at a moment after it and raises the floors of the monotonic, raw, real and coarse clocks to them before readers go on, so the tick's clocks that take over never read earlier, the coarse ones included; the start begins each base at the tick's clock or at its floor, whichever is later. Each stop and start raises the clock's generation (`vclock_generation`) after the page's count goes odd, which KVM reads to decide its master clocks again ([KVM](../kvm/Readme.md)). Every move of a running clock's base, the tick's, its step to the tick's edge, a change of real time's offset's, the stop's and that of a reading made with the boot processor's stable bit withdrawn, goes through one function, `vclock_advance`: it reads the running processor's KVM clock page and its TSC in one pass, the TSC converted through the page, with the page's stable bit (`kvmclock_read`), and takes the moment's count through `vclock_count`, the one clamp every count taken from a reading passes before a time is computed from it or it becomes the base. Linux's `__pvclock_clocksource_read` converts the TSC through the page whether or not it has the stable bit, and holds a reading without the bit to the latest such reading, its `last_value` (`pvclock.c`, lines 47 and 68 to 108); here the page's base is that value, since every reading without the bit that the kernel gives a time from becomes the base. A count behind the page's base is the base, so no time is counted twice and the base never moves back. The old bases go to their times at that count by their old rates, and the count becomes the new base (`vclock_anchor`, the only writer of the base). The tick takes the counts of its reading of the reference the same way. The start carries from no old base and puts a new one at KVM's clock read with the tick's clocks, or the TSC where no page is kept; where either reading, or the boot processor's page then, lacks the stable bit, as when KVM withdraws it after the tick decided to start, the clock stays stopped and the tick tries again. The stop and the start are decided by the boot processor's page (`kvmclock_boot_withdrawn`), the one every reader tests, as Linux's vDSO reads only that page while the bit holds (`gettimeofday.h`, line 219). The clock then runs in `VCLOCK_PVCLOCK`, as Linux's kvm-clock gives the vDSO `VDSO_CLOCKMODE_PVCLOCK` (`kvmclock.c`, lines 241 to 262): `x86/kvmclock.c` keeps the processors' clock pages in a page of memory that holds nothing else, as Linux's `hv_clock_boot` (`kvmclock.c`, lines 44 to 50), and the vDSO maps it read-only below the data page and converts through the boot processor's page inside each reading, checking its stable bit, so a reading made once KVM withdraws the bit, before the tick stops the clock, makes the system call and never reads a TSC that may be ahead of the stop's time. The kernel's `vclock_read` reads the same way (`kvmclock_boot_read`, in `vclock_pass`) and, with the bit clear, takes `vclock_lock`, advances the base to KVM's clock read from the running processor's page and gives the base's time (`vclock_withdrawn`), as the stop advances it and as Linux's kernel goes on reading kvm-clock, so the system call reads on from where the vDSO's readings left off, a later reading without the bit that reads KVM's clock behind it is held to it, and the stop's time is at or past every reading given; where KVM sets the bit again before the tick stops the clock, every reader of the boot processor's page, both vDSOs and `vclock_pass`, holds its count to that base and reads no earlier than the system call did; `vclock_read_cycles` gives no pair of a TSC and the time then, and otherwise pairs the TSC the page converted with the time. The page is built and cleared before `data` points at it, as Linux clears its clock pages before it publishes one (`kvmclock.c`, lines 202 to 239 and 264 to 285), since a timer interrupt may read the clock while it is built. Each clock has a base and a rate on the page, and the code reads each clock's rate 8 bytes before its seconds. Real time is the monotonic clock plus the offset `clock.c` keeps, which `vclock_set_wall` takes at the anchor and at each step: its base is the monotonic base plus the offset, and `real_mult` is `mult`, so a slew moves the two together and only a step parts them. The coarse clocks have no rate: their seconds and nanoseconds on the page are the monotonic clock at the tick's last edge, the clock since boot at the last tick `clock.c` counted (`rtc_tick_coarse_ns`), and real time there, which the clock's pass writes inside the tick's sequence count, before the tick count it counted shows (`vclock_tick_edge`). So, as Linux's timekeeper moves its base only by whole tick intervals (`kernel/time/timekeeping.c`, lines 2164 to 2193), a pass between ticks moves neither, and no coarse reading is a tick or more past the tick count, nor earlier than a count read before it; a TSC clock behind the edge is stepped forward to it there, so no coarse reading is later than a fine one.

`vdso32.c` builds the i386 programs' image the same way at boot, `vdso_build` calling `vdso32_build`: an ELF32 shared object of `EM_386`, `linux-gate.so.1`, with the versions `LINUX_2.6` and `LINUX_2.5` and the code of `vdso32code.s`, between `vdso32_text_start` and `vdso32_text_end`, which is 32-bit code. It has no weak names, as Linux's has none. The clock functions find the data page by `call` and `pop`, since 32-bit code has no `%rip` addressing, and do the 64-bit arithmetic of the 64-bit ones in pairs of registers. `__kernel_vsyscall` makes the call by `int $0x80`, or by the instruction `vsyscall_patch` writes before it, and `__kernel_sigreturn` and `__kernel_rt_sigreturn` are Linux's restorers, whose addresses `ia32_vdso_sigreturn` gives the i386 signal frames.

`proc/vdso.c` maps the three pages of the program's ABI (`VDSO_NATIVE` or `VDSO_IA32`), the two of `[vvar]`, KVM's clock page and the data page, and the image, into each new image, one free page above the range `mmap` places mappings in (`vdso_map`), as regions whose files hand out the kernel's frames, and a fork shares them. `[vvar]` is of `VM_SHARED` with `VM_PROT_NOWRITE` and `VM_PROT_VVAR`, as Linux maps it `VM_IO | VM_PFNMAP` and without `VM_MAYWRITE` or `VM_MAYEXEC`: it can never be made writable or executable, and `ptrace`, `/proc/PID/mem`, `process_vm_readv`, `vmsplice` and pins are refused its page, as Linux's `get_user_pages` refuses the region. `[vdso]` is a private mapping, `VM_FILE`, as Linux's is with `VM_MAYWRITE`: `mprotect` may make it writable, and a write, or a tracer's through `ptrace` or `/proc/PID/mem`, copies the page into that address space alone. The kernel keeps its own reference to the frame, so even its last mapping is copied and never written in place. `/proc/PID/maps` names them `[vvar]` and `[vdso]`.

### The rules of the shared code

`make -C rach2 check-arch` runs `tools/verify/archcheck.sh` over the shared files and fails on any of three findings:

* A shared file that does not compile for 32-bit and 64-bit ARM under clang's front end, with `-ansi` and these errors: an implicitly declared function, a conversion between an integer and a pointer, a cast between a pointer and an integer of another size, incompatible pointer types, and on 64-bit ARM a 64-bit value cut to 32 bits without a cast. A shared file that calls a function only an x86 has, or keeps an address in a `uint32_t`, fails.
* A shared file that includes, through any chain on any of the four targets, a header under `sys/arch/` other than `arch.h`, `uabi.h` and the `cpu.h` and `uabi.h` they choose, or a header beside a C file the platform lists, as `sys/block/ata.h` is beside `ata.c`.
* Inline assembly in a shared file or in any header outside `sys/arch/`, but the compiler barrier `k_barrier` of `lib/kdef.h`, which emits no instruction.

The shared code is written to pass them: an address is a `uintptr_t`, a length a `size_t` and a physical address a `phys_addr_t`; a driver reaches its device's registers through the `mmio_` accessors and memory by its physical address through `phys_to_virt`; and a system call's handler reads its arguments with `SC_ARG` as `unsigned long` and returns `long`.

### What an ARM port adds

`arm/cpu.h` describes an ARMv7-A processor with short-descriptor paging, and `arm64/cpu.h` an AArch64 processor at EL1 with 4 KiB pages and 48-bit addresses. Each gives the register frame, Linux's system call convention, the user range, the ELF class and machine and `ARCH_GREGS`; the kernel's layout and `arch_cpu_id()`, which is 0, are for a port to choose. `arm/uabi.h` has Linux's ARM layouts, which match i386's, and `arm64/uabi.h` has x86-64's, which a port replaces with AArch64's. A port keeps the shared code and adds:

* Every function `arch.h` declares and the code behind it: the entry from the loader, the exception vectors and the entry by `svc`, the page tables of `mm/paging.h`, the context switch, the signal frames, the thread pointer (`TPIDRURO` on 32-bit ARM, `TPIDR_EL0` on 64-bit ARM, as Linux uses them), the floating-point state of `fpu.h`, the ptrace registers, and a `systab.c` from Linux's numbers, the generic ones on 64-bit ARM.
* The boot record of `sys/boot.h`, filled from what its loader passes.
* The platform behind `platform.h`, `irq.h`, `timer.h` and the rest; `cpu.h` numbers the interrupts as a GIC does, from 32 to 1019.
* Its `sources.mk` and `link.ld`, a branch in `mk/arch.mk`, which refuses every `ARCH` but `i686` and `x86_64`, and its flags in `rach2/Makefile`. `guest.mk` takes `ARCH` from the class of `/bin/cc`'s ELF header, `i686` or `x86_64`, so a port that builds itself on Rach2 adds its compiler's machine there.

## Building

`make ARCH=x86_64` builds for x86-64; `ARCH` is `i686` when it is not given, and any other value stops the build (`mk/arch.mk`). The i686 build writes under `build/` and the x86-64 build under `build/x86_64/`. `rach2/Makefile` takes the architecture's flags, which [the kernel's document](../../Readme.md) gives, and its link script, `sys/arch/$(ARCH)/link.ld`.

`rach2/sources.mk` lists `C_SRC_SHARED` and includes `sys/arch/$(ARCH)/sources.mk`, which gives `ARCH_ASM_SRC` and `ARCH_C_SRC` and includes `x86/sources.mk`. That list, `PC_C_SRC`, has the files of `x86/` and the drivers the PC platform takes from other subsystems: `sys/block/ata.c`, `sys/display/vga_text.c`, `vga_gfx.c`, `vga_font.c` and `fbcon.c`, and `sys/audio/dma.c` and `sb16.c`. `loader.s` is first in `ARCH_ASM_SRC`, since the link keeps the input order and the Multiboot header must lie in the kernel's first 8192 bytes. Each architecture's list also gives TinyCC's flags for the build on Rach2, `ARCH_TCC_CFLAGS` and `ARCH_TCC_LDFLAGS` ([the kernel's document](../../Readme.md)).

## Limits

* No ARM kernel links: `arm/` and `arm64/` have headers alone.
* The i686 kernel uses no PAE: it reaches the first 4 GiB of physical memory, and every page it maps is executable.
* On i686 a program makes a system call by `int 0x80` alone; the kernel has no `sysenter`. On x86-64 it makes one by `syscall`, or an i386 call by `int $0x80`, as [ia32(7)](../../../man/man7/ia32.7) describes.
* The i686 kernel has no vDSO: every call, `clock_gettime` among them, enters the kernel.
* The x86-64 vDSO has no unwind tables; its fine clock reads enter the kernel on a machine whose TSC does not run at one rate only where neither the HPET nor the PM timer is there to watch it, or once a watched TSC has parted from the tick's clock, unless `rach2.tscreliable` is given. Under KVM they enter it while KVM's clock page lacks its stable bit and the TSC is not rated above kvm-clock, as Linux's do, and under `no-kvmclock-vsyscall`.

## Tests

* `tests/run style` runs `make -C rach2 check-arch` and builds the kernel of `ARCH` with warnings as errors.
* `tests/run host` compiles kernel files natively with i686's headers; `paging_hosttest.c` includes `mm/paging.c` with `arch/i686/mmu.c`, `debugreg_hosttest.c` includes `arch/x86/debugreg.c`, and `leave_hosttest.c` and `leave64_hosttest.c` include `arch/x86/leave.c` and post a SIGKILL during a handler frame's copy and during the rseq area's ([the host tests](../../../tests/host/Readme.md)).
* `tests/run default` runs every guest probe, `sigprobe`, `musl/sigframemusl` and `musl/ptracemusl` among them, which go through the signal frames, the register sets, and the debug exception of a step over a system call and of a watchpoint the kernel's copy to user memory hits.
* `tests/run memory` boots with `rach2.stackoverrun=fork` and with `rach2.stackoverrun=boot`, the cases `machine.memory.stackoverrun-fork` and `stackoverrun-boot` of `tests/cases/machine.memory.json`, and requires the record with the pid of the thread that descended and the panic `a kernel stack ran out`.
* `tests/run smp` starts the other processors, runs the debug shell's `usermode` payload, and raises an NMI on two processors, the case `machine.smp.nmi` of `tests/cases/machine.smp.json`, which must stop the machine with one report of the fault and one panic, both processors halted, and has the debug shell's `badop` run an invalid opcode, the case `machine.smp.exception`, which must do the same; both boot with `panic=0`, so that the processors stay halted, read the VGA's cells and require the panic's report on the screen: the instruction pointer, the fault's name after it, and `panic:` with the reason last.
* `tests/run vdso` runs `musl/vdsomusl` on two processors under `rach2.tscreliable`, with no option on QEMU's emulator, whose TSC the kernel watches, and under `rach2.notsc`, the cases of `tests/cases/guest.vdso.json`: the image's place, its symbols and versions, its clocks between two system calls' and in order across the processors, `getcpu`, and the count of the clock's system calls. The case `machine.gnu.gdb` of `tests/run gnu` has gdb name `__vdso_clock_gettime` as the system-supplied DSO's.
* `tests/run kvmclock` runs `musl/vdsomusl` with no clock option on two processors, the case of `tests/cases/guest.kvmclock.json`, which the release runs under KVM. The program takes what to require from the accelerator its runner names in `ETUDE_ACCEL` and from whether the host keeps time by the TSC in `ETUDE_KVM_STABLE`, and not from the kernel: under KVM `/sys` lists kvm-clock, the clock source is kvm-clock, or the TSC while the vDSO's clock counts it, where the host keeps time by the TSC, the x86-64 kernel's vDSO serves the fine clocks. Where it does not, fine readings make system calls, and the coarse clocks and `__vdso_time` still read the data page. On the i686 kernel each reading makes a system call. Under an emulator no kvm-clock is listed. `kvmclock_hosttest.c` includes `arch/x86/kvmclock.c` and runs it against a model of KVM's MSRs and clock pages.

Every suite in `tests/registry` runs on both architectures unless its row says otherwise; `ARCH=x86_64 tests/run NAME` runs it on x86-64.

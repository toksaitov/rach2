# The PC platform

`sys/arch/x86/` is the PC platform that the i686 and the x86-64 kernels share: the part of the machine around the processor that every PC has. It reads the loader's Multiboot or multiboot2 information into the boot record and the firmware's ACPI and SMBIOS tables; it gives the kernel PCI configuration space, the interrupt controllers, the scheduler tick and the millisecond clock, the other processors and each process's floating-point state; it drives the 8254 timer, the CMOS clock, the 8042 keyboard and mouse controller, COM1 and the speaker; and it stops and restarts the machine. Shared code reaches it only through the headers listed under Interfaces, so a port to another machine replaces this directory and keeps the rest. The processor's own layer, the descriptor tables, the entry code, paging and the context switch, is in `i686/` and `x86_64/` ([the architectures' Readme](../Readme.md)); thread-local storage has [its own document](../tls.Readme.md).

The manual describes what a user sees: [acpi(4)](../../../../man/man4/acpi.4) the controllers, the tick, the processors and the stops with the log lines they print, [proc(5)](../../../../man/man5/proc.5) `/proc/interrupts` and `/proc/cpuinfo`, [rtc(4)](../../../../man/man4/rtc.4) `/dev/rtc0`, and [reboot(2)](../../../../man/man2/reboot.2) and [halt(8)](../../../../man/man8/halt.8) the stops.

### The boot line

The platform reads these words of the kernel command line, which [cmdline.md](../../../cmdline.md) lists with the rest:

* `rach2.nomsi` (`lapic.c`): the local APIC is not enabled. No device sends messages, the I/O APIC is not used, the 8259 pair delivers every line, the 8254 ticks, and the kernel runs on one processor.
* `nox2apic` (`lapic.c`): the local APIC stays in xAPIC mode, and VT-d's remapping entries in xAPIC format, as on Linux. Where the firmware left the APIC in x2APIC mode and locked it there, or with an identity of 255 or more, it is ignored, as Linux's `setup_nox2apic` ignores it.
* `noapic` (`ioapic.c`): the I/O APIC is not used. Devices still send messages to the local APIC, but lines 0 to 15 come through the 8259 pair and the 8254 ticks, so the kernel runs on one processor. As on Linux, VT-d does not remap interrupts and the local APIC is not moved to x2APIC mode, a firmware's x2APIC mode kept only where the firmware locked it or a hypervisor allows it.
* `maxcpus=N` (`sys/proc/smp.c`): at most `N` processors, the boot processor counted; 0 and 1 both leave the kernel on the boot processor. Each occurrence is read in turn, as Linux runs its `maxcpus` early parameter once for each, and the last that gives a value sets `N`. `N` is read as Linux's `get_option` reads it (`kcmdline_option`): hexadecimal after `0x`, octal after a leading 0, a negative one as no limit, one that begins with no digit as 0 and an empty one as none. Any occurrence that gives 0 is also `noapic`, as Linux's `arch_disable_smp_support` makes it and no later occurrence undoes, so `maxcpus=0 maxcpus=4` keeps the I/O APIC off (`ioapic_disabled`) and with it the kernel on one processor, as for `noapic`: the 8254 ticks in place of the local APIC, so the limit of 4 is not reached. Linux starts four processors here: with `setup_max_cpus` at 4, `__apic_intr_mode_select` does not take its path that turns SMP off (Linux 6.12.115, arch/x86/kernel/apic/apic.c, lines 1280 to 1286).
* `rach2.nofxsr` (`fpu.c`): on i686, `fnsave` saves the x87 state and SSE is off. The x86-64 kernel ignores it.
* `rach2.noxsave` (`fpu.c`): `fxsave` saves the state on a processor that has XSAVE, and a program sees no AVX.
* `rach2.board=NAME` (`board.c`): only the power profile `NAME` is tried, and the chipset must still match it; an unknown name, or a chipset that does not match, leaves the machine with no profile.
* `rach2.nosci` and `rach2.noacpica` ([ACPI](../../acpi/Readme.md)): ACPICA takes no system control interrupt, whose line then stays masked, or is left out.
* `rach2.resetskip=N` (`power.c`): one digit; a restart leaves out its first `N` methods before the keyboard controller's pulse, which it never leaves out.
* `reboot=LIST` (`power.c`): as Linux's: the method a restart and a panic's reset begin with, `a`, `k`, `t`, `e`, `b` or `p`, and the reset's warmth, `w` warm and `c`, `h`, `g` or `s` cold, with `panic_` before a mode for a panic's alone; items are split by commas and judged by their first letter, and each `reboot=` is read in turn. With it, a restart runs the emergency sequence below in place of the default one, and `rach2.resetskip` has no effect.
* `rach2.nomouse` (`platform.c`): the PS/2 mouse is not probed.
* `rach2.diag` and `rach2.apicdiag` (`diag.c`, `apicdiag.c`): the boot reports described below. Neither is a command of the debug shell.

## Design

TSC calibration converts each measured window to counts per kernel tick by multiplying the full reference frequency before dividing by the reference counts times the kernel rate. No fraction of the rate is truncated before division.

### The watchdog

`itco.c` drives the version 2 TCO watchdog of the `ich9` and `lynxpoint-lp` profiles through the PMBASE and enabled RCBA that `board.c` exposes. It registers `/dev/watchdog` through the device registry after the board probe, with the timer halted; an exclusive open arms it. [watchdog(4)](../../../../man/man4/watchdog.4) owns the user contract. The register sequence follows Linux 6.12's `drivers/watchdog/iTCO_wdt.c`: preserve reserved bits, program 0.6-second ticks, clear NO_REBOOT before starting, reload, and read back halt and timeout writes. As `iTCO_wdt_probe` does, the probe clears NO_REBOOT first and refuses the device when it will not clear, takes a timer that is not halted as running whatever NO_REBOOT was, and sets NO_REBOOT again on a halted one. An orderly stop halts the timer through `power_prepare`. A timer that runs at boot, because firmware left it counting or the line has `rach2.itco.arm`, is fed every half timeout until a program opens the device or `watchdog.open_timeout` passes, as Linux's watchdog core feeds a watchdog that runs before user space (`watchdog_dev.c`): `itco_tick` counts elapsed milliseconds between services and wakes the kernel thread `watchdogd`, at SCHED_FIFO priority 50, which does the feed, as Linux's hrtimer queues the ping on its kthread worker of that name. A panic or a hang that stops the tick, or one that keeps `watchdogd` from running, lets the chipset reset the machine. Before the first program and in the kernel debug shell, where the scheduler runs no thread, the tick feeds the timer itself. The options `iTCO_wdt.heartbeat`, `iTCO_wdt.nowayout`, `iTCO_wdt.turn_SMI_watchdog_clear_off`, `watchdog.handle_boot_enabled` and `watchdog.open_timeout` are Linux's and are read as its module parameters: the last valid occurrence counts, a bare boolean is true (`kcmdline_param_bool`), and a value that is not valid, or a bare number option, is logged as `watchdog: refused:` and leaves the option as it was, as Linux's `parse_args` logs it (`itco_option`, `itco_bool`). All other accesses are bounded and serialized by the big lock; there is no interrupt handler. The host test supplies the register callbacks and advances the hardware ticks itself.

### Sources

`sources.mk` sets `PC_C_SRC`, which both `i686/sources.mk` and `x86_64/sources.mk` include: the C files here and the PC drivers above. `iommu/` has the VT-d driver, which `x86_64/sources.mk` alone includes. The platform has no assembly; the first code a started processor runs, and the BIOS restart of `reboot=b`, are each architecture's `trampoline.s`. Every file compiles for both architectures, with `#if defined(__x86_64__)` where they differ, and an instruction the staged TinyCC's assembler lacks, such as `rdrand`, `xsave` or a debug register move, is written as its bytes. The readers of firmware data, `mbinfo.c`, `acpi.c`, `smbios.c`, the judgements of `board.c` and the decoding of `cmos.c`, reach memory and registers only through what they are given, so that host tests can feed them tables no machine can be made to produce.

### From the loader to the boot record

Each architecture's `loader.s` calls `k_main(magic, info)` in `boot.c` ([the kernel's Readme](../../../Readme.md) has the path). `k_main` starts COM1, so that everything after can be logged, and reads the loader's information by its magic: `0x2BADB002` is Multiboot's (`mb1_read`) and `0x36D76289` multiboot2's (`mb2_read`), both in `mbinfo.c`, which reads each field by its offset a byte at a time and calls no kernel service.

* Multiboot passes one structure with pointers to the command line, the loader's name, the modules and the memory map. A pointer is followed only below 4 GiB: as the physical address itself on i686, where paging is still off, and through the direct map of the first 4 GiB that `loader.s` built on x86-64.
* multiboot2 passes a list of tags, read up to 1 MiB (`MB2_INFO_MAX`). Under UEFI the EFI memory map takes the place of the loader's own: its types become Multiboot's, the loader's and the boot services' memory counted as usable, since neither runs again. The ranges the EFI map marks `EFI_MEMORY_RUNTIME` are kept too, adjacent ones joined, up to `BOOT_EFI_RUNTIME_MAX`, 32, for EFI's `ResetSystem` below. A tag of the EFI tables or of the EFI map sets the record's `uefi`, and a tag of the RSDP, ACPI 2.0's in preference to 1.0's, is copied into the kernel's image; the record's `acpi_rsdp` is the physical address of that copy. Multiboot passes no RSDP, and `acpi_init` then searches the BIOS area.

The record keeps copies of what it points at, since the loader's memory goes to the frame allocator: up to `BOOT_MMAP_MAX`, 256, memory-map entries, `BOOT_MODULE_MAX`, 8, modules with their command lines, and `BOOT_CMDLINE_MAX`, 512, bytes of command line (`sys/boot.h`). `k_main` then records the modules in `module_table` (`module.c`), starts the framebuffer console when the loader left a framebuffer of direct or indexed color, and calls `kernel_main`. Once the kernel's page tables are in force, the console draws through a mapping of the framebuffer, write-combining where the page attribute table allows it and uncached otherwise.

### The processor and its vectors

`platform_cpu_init` writes the page attribute table, loads the architecture's GDT, TSS and IDT, and installs the exception handlers (`init_isr`), which enables interrupts. `pat_setup` (`pat.c`) makes entry 1 of `IA32_PAT` write-combining in place of write-through, for the framebuffer's mapping (`PTE_WC`), and leaves the other seven at their reset types. `init_idt` programs the 8259 pair (`pic.c`) to vectors 32 to 47 with every line unmasked but the keyboard's, whose byte would be lost if it came before its handler. `cpu.c`, `kcpu.c`, `kirq.c` and `portio.c` are the instructions: the primitives of `arch.h`, `cpuid` and the model-specific registers, the interrupt flag, and the I/O ports.

| Vectors | Use |
| --- | --- |
| 0 to 31 | the processor's exceptions |
| 32 to 47 | lines 0 to 15, line `N` on 32 + `N`, through the 8259 pair or the I/O APIC |
| 48 to 239, but 128 | devices' messages, 191 vectors (`vector.c`), given out lowest first by `isr_alloc_vector`, or lowest at a multiple of a power of two by `isr_alloc_vector_aligned`, and back by `isr_free_vector`; their stubs are one run in `isr_handler.s`, 16 bytes apart, which `init_idt` checks |
| 128 (0x80) | the system call gate, on i686 alone |
| 240 (0xF0) | the interprocessor interrupt |
| 255 (0xFF) | the local APIC's spurious vector |

Each vector has a chain of up to four handlers (`isr.c`), since PCI lines are shared and each handler must look at its own device. `_irq_router` takes the big lock, but for the tick, counts the interrupt, runs the chain and ends the interrupt at its controller: through the 8259 before the chain, and through the I/O APIC after it, since a level-triggered line still asserted would be sent again at once. A message is an edge and is ended before its chain, as Linux's `handle_edge_irq` acknowledges it first, since the handler's register reads and the kicks of the threads it wakes exit under KVM and take back a paravirtual end of interrupt still pending; a message that comes while its chain runs, once a handler turns interrupts on or on another processor, is run by that run once its chain returns (`irq_dispatch_edge`), so no handler runs inside itself. The tick is ended first on either path, since its handler may switch processes and a vector in service blocks every vector of its priority class and below. The tick is taken without the big lock: its handler runs the clock's pass, the accounting and the timer pass under spinlocks of their own, and tries the lock only for the part that still needs it (`timer_handler`, `kernel.c`; [the process subsystem](../../proc/Readme.md)), so that a long holder on one processor, such as the sound mix, does not hold up the ticks or the user code of the others. A tick of a processor past the first makes the clock's pass, which counts the tick from the reference, and the timer pass, which fires the timeouts due, when the tick count has not moved over two of its ticks (`timer_pass_late`), as when the boot processor runs with interrupts off. The NMI, the machine check, the x86-64 double fault, the interprocessor interrupt and the spurious vector are taken without the big lock, since the processor they interrupt may hold it. Every tick runs the lockup detectors' part first (`watchdog_tick`), since a processor locked up with interrupts off may hold the big lock for good.

An exception in user mode becomes a signal ([signals](../../proc/signal.Readme.md)); in kernel mode it panics, a debug exception aside. The NMI and the machine check stop the machine, but for the lockup detectors' NMIs ([the lockup detectors](../../watchdog.Readme.md)). The hard-lockup detector's NMI comes from Intel's fixed counter 1, AMD's core counter 2 on family 15h, or general counter 0 on the others, as [the lockup detectors](../../watchdog.Readme.md) say, through the local APIC's performance-counter entry, which `pmu.c` programs as an NMI and writes again on every NMI while the counter runs, since Intel's APIC masks it as it delivers one, a late one that finds no overflow too; `pmu.c` also finds the counter, Intel's architectural monitor of `cpuid` leaf 0xA or AMD's core counters, and sets FREEZE_WHILE_SMM in each processor's IA32_DEBUGCTL as it starts, on Intel's version 2 or later where IA32_PERF_CAPABILITIES offers it, as Linux's perf does, so that no counter counts SMM's work (`platform_pmu_cpu_setup`); `nmiwd.c` dumps the registers in Linux's layout. The double fault runs on a stack of its own, through a task gate on i686 and an interrupt stack on x86-64, and reports a kernel stack that ran into its guard page.

### The firmware's tables

`platform_firmware_init` runs once paging is on, since every table is reached through `map_mmio`, and before the interrupt controllers, which read the tables. It reads ACPI's tables, keeps the UEFI system table for SMBIOS, finds EFI's `ResetSystem` (`efirt.c`), maps the ECAM window, finds the reference counter, and checks the trampoline's pages, in that order.

`acpi_init` (`acpi.c`) takes the RSDP from the boot record, or searches the first KiB of the extended BIOS data area and then 0xE0000 to 0xFFFFF. It walks the XSDT, or the RSDT where there is no good XSDT, and reads the first MADT, FADT, HPET table and MCFG, and the DSDT the FADT gives. A table is read only after its length and checksum pass, and one that fails is logged and left out. `struct acpi_info` (`acpi.h`) keeps the result: the processors, I/O APICs, interrupt source overrides and NMI wiring of the MADT; the PM1 control registers, the PM timer, the reset register, the SMI command and the sleep control register of the FADT; the HPET's address; and the MCFG's windows.

ACPICA, in [`sys/acpi/`](../../acpi/Readme.md), interprets the DSDT and the SSDTs once the scheduler runs, from the RSDP `acpi_init` found. The two sleep types of `\_S5` come from the DSDT without it, so that the power off works with ACPICA left out or refused: `acpi_s5_find` searches its bytes for the name `_S5_` after NameOp, followed by a package whose first two elements are integer constants of at most 7. `acpi_isa_route` gives each ISA line its global system interrupt, trigger and polarity from the MADT's overrides, a line a PCI device uses being level-triggered and active low unless an override gives the polarity.

`smbios.c` finds the table through the UEFI configuration table's entry point or by a search of 0xF0000 to 0xFFFFF, and reads the fields Linux's `dmi_decode` keeps from the BIOS, System, Base Board and Chassis Information structures, each from the first structure long enough to hold it, for `/sys/class/dmi/id` (`dmi_field`, `sys/dmi.h`). Of them the BIOS vendor decides the restart below, and the manufacturer and product name are those by which `alps.c` and `elantech.c` choose Linux's quirks for a machine. A string of spaces alone reads empty, as in Linux; the UUID is written with its first three fields' bytes reversed from version 2.6 on.

### PCI configuration

`pciconf.c` gives `sys/pci.c` access to configuration space. Mechanism #1 writes the address to port 0xCF8 and moves the data at port 0xCFC, with interrupts off and `config_lock` held, since processors share the two ports and the USB driver reaches configuration space from its interrupt. A 16-bit or 8-bit write is one access at the data port's byte, not a read and a write of the dword, since the status word beside the command word is cleared by writing ones.

`ecam_init` (`platform.c`) maps the MCFG's window for segment 0: the first bus and those behind its bridges, found through mechanism #1, at most 32 (`ECAM_MAX_BUSES`), a MiB each. The window is used once its first function reads there as it reads through the ports; from then a function on a covered bus is 4 KiB of memory, an access is one load or store, and offsets 256 to 4095 can be reached. A device's message is its vector written to 0xFEE00000 with its chosen processor's APIC identity in bits 12 to 19, or through the interrupt remapper with the whole identity.

`pci.c` serializes message records and affinity changes with `msi_lock`. It chooses the least allocated reachable online processor, as Linux 6.12's `matrix_find_best_cpu` does, and rebalances messages enabled before `smp_start` once the other processors are online. `/proc/irq/N/smp_affinity` changes the requested mask, and `effective_affinity` reads the single chosen processor ([proc(5)](../../../../man/man5/proc.5)). A normal shutdown moves messages to the processor which stays running before stopping the others; each departing processor forwards its pending message vectors there. There is no runtime processor-hotplug interface.

A migration keeps the globally reserved vector and its chain on every processor. A message in flight to the old destination therefore still reaches the same chain; `irq_dispatch_edge` serializes it with a message on the new destination. Linux's per-processor vectors need an old-vector cleanup before reusing a slot; this pool reserves a vector globally until its device disables it, so a migration releases no slot. Without remapping only the address changes, with a readback; with remapping the same live entry gets the new destination and its cached copy is invalidated. `handler_lock` guards chain changes and copies at dispatch, and the pool has its own `vector_lock`. The NMI, double-fault and machine-check chains are immutable after boot and are read without that lock.

### The interrupt controllers and the tick

`platform_timer_start` (`platform.c`) brings the controllers up and starts the tick at `TICK_HZ` (`timer.h`), 250 a second, with interrupts off until the last step:

1. `lapic_init` (`lapic.c`) enables the local APIC unless `rach2.nomsi` is given, the processor has no APIC or no model-specific registers, the firmware left it in x2APIC mode with an identity past 254 where no remapping can come and no hypervisor allows the mode, or, in xAPIC mode, its base is above 4 GiB. It makes `LINT0` an unmasked external interrupt, so that the 8259's interrupts still reach the processor through it. The APIC runs in x2APIC mode, its registers MSRs, where Linux 6.12.115 runs it: from here under a hypervisor that delivers interrupts to it without remapping, KVM, Hyper-V or Xen, which `kcpu_x2apic_unremapped` finds by its signature, when the boot processor's identity is below 255; and on bare metal once the VT-d units remap interrupts in x2APIC format ([VT-d](iommu/Readme.md)), which moves it at the start of remapping, before the other processors start. Under `noapic` or `maxcpus=0` neither happens, as Linux's `enable_IR_x2apic` returns before either. Elsewhere it runs in xAPIC mode. A firmware's x2APIC mode is kept where the firmware locked it or a hypervisor allows it; on the x86-64 kernel, where the DMAR table offers remapping without opting out of the x2APIC format and the boot line does not turn it off (`ioapic_remappable`), it is kept until the VT-d units are up, then kept if they remap in x2APIC format and left through the disabled state if not (`lapic_x2apic_settle`), as Linux's `check_x2apic` and `try_to_enable_x2apic` keep and leave it; elsewhere it is left at once. The I/O APIC's lines, the local timer and the units' fault events are live by then and the disabled state clears the request register, so every source is quieted across the leave: the units' fault events are held in their pending bit, the 8259 and the I/O APIC's lines are masked and the handlers take and end what they sent, the timer's and the error's entries are masked, what the request register held is sent again, the timer's vector is raised once when its count reloaded while it was masked, and each edge line's vector is raised once as the line is unmasked, since the masked input drops an edge and an ISA device raises no other until its handler reads it (`ioapic_unmask_lines`). No device has a message of its own yet, since the kernel settles the mode before any driver enables one. `nox2apic` keeps xAPIC mode, as on Linux, and leaves `x2apic` out of `/proc/cpuinfo` where it took effect. In x2APIC mode an interprocessor interrupt is one write of the 64-bit command register after MFENCE and LFENCE, with no delivery status to wait on, where xAPIC mode writes the destination, writes the command and reads it back until it is sent; under KVM that is one exit in place of three. Destinations are physical in either mode.
2. `init_pit` programs the 8254's channel 0 in mode 3 with the reload 4773, 1193182 / 250 rounded to the nearest count as Linux's `PIT_LATCH` is. On a machine whose channel 0 does not count, `k_udelay` uses the reference counter, where there is one. Under `rach2.tscreliable`, or under KVM when KVM states the TSC's rate and that it is stable, the TSC is measured or its rate taken next (`timer_calibrate`), so that the first tick makes it the reference; elsewhere, where the HPET or the PM timer keeps the clock and KVM states no rate, `timer_tsc_watch` measures it the same way for the vDSO alone, before the processors' checks of it.
3. The I/O APIC (`ioapic.c`) is used when neither `noapic` nor `maxcpus=0` is given, the local APIC is enabled, and the MADT lists an I/O APIC that answers. `ioapic_init` masks every input.
4. With the I/O APIC, the local APIC's timer is measured; the 8259 pair is masked for good (`pic_retire`); `LINT0` and `LINT1` are masked but where the MADT gives either as an NMI input; the lines PCI functions' interrupt line registers give are noted as level-triggered; and lines 0 to 15 pass to the I/O APIC. The tick is the local APIC's timer, periodic on vector 32, or the 8254 through the I/O APIC when the measurement failed.
5. Without it, the tick is the 8254's line 0 through the 8259 pair.
6. Interrupts are enabled, and the tick must arrive within 50 ms. A local APIC timer that does not interrupt is replaced by the 8254; on the 8259 path `LINT0` is written again. A machine that still does not tick is logged and goes on.

A line is routed through the I/O APIC when a handler is registered on its vector (`isr.c`), to the input `acpi_isa_route` gives, on vector 32 + line, to the boot processor. A line a PCI function's interrupt line register gives is level-triggered because SeaBIOS and OVMF route the function's PIRQ to that ISA line and write the register so. `pic_mask_irq` keeps a line masked at the I/O APIC once the 8259 is retired. While VT-d remaps interrupts, a routed line's redirection entry names an entry of the remapper's table in its high half: `ioapic_remap_start` rewrites each line already routed, and `ioapic_route_line` maps each one routed later through it ([VT-d](iommu/Readme.md)).

The local APIC's timer counts at a divided bus clock that no register states, so `apic_timer_calibrate` (`apictimer.c`) runs it with interrupts off over 20 ms of the reference counter (`refclock.c`): the HPET's main counter where the HPET table gives one, the ACPI PM timer otherwise, and the 8254 where there is neither. A hypervisor may stop the processor at any point of the measurement, so the timer is read at each end between two reads of the reference, taken again when those two are more than 50 microseconds apart, and its place taken midway between them. Against the 8254, the timer's counts are divided by the counts `pit_wait_counts` (`udelay.c`) saw fall during the wait, not by the 20 ms it asked for. That wait cannot see a sweep of the counter that passes between two of its samples, so a stop makes the wait longer than it measured and never shorter: the timer is measured over three waits, and the lowest rate taken. The HPET is started with its legacy replacement and its comparators' interrupts off, so that the 8254 and the CMOS clock keep their lines; neither counter raises an interrupt.

`k_udelay` (`udelay.c`) latches channel 0 and adds up how far its count fell, each latch and its two reads with interrupts off, since a handler that latched the counter between them would leave the reads a byte of the live count each. A count that stops moving ends the wait, so a machine without an 8254 does not wait for ever.

### The clock under the tick

The clock is kept by a reference counter from the first tick on: the HPET's main counter or the ACPI PM timer, whichever `refclock.c` found, and on a machine with neither, the time-stamp counter. Under `rach2.tscreliable`, or under KVM with KVM_FEATURE_CLOCKSOURCE2 and KVM_FEATURE_CLOCKSOURCE_STABLE_BIT and a clock page whose PVCLOCK_TSC_STABLE_BIT is set (`tsc_kvm_counts_per_tick`, `tsc.c`), `platform_timer_start` measures the TSC or takes its rate before interrupts are on, and the TSC keeps the clock even where the HPET or the PM timer is, as Linux's TSC does where it is stable: under a hypervisor each read of either is an exit, the tick reads the reference at least twice, and at the third level of nesting, at some 200 microseconds an exit, the exits outlasted the tick. While the TSC keeps the clock, `k_udelay` waits on it too (`tsc_wait_us`), as Linux's `delay_tsc` does. Under KVM, `timer_calibrate` (`pit.c`) takes the rate from the clock page that KVM fills for the boot processor once it is registered with MSR_KVM_SYSTEM_TIME_NEW, a tick's nanoseconds by 2^32 divided by its `tsc_to_system_mul` and shifted against its `tsc_shift`, as Linux's `kvm_get_tsc_khz` does (`arch/x86/kernel/kvmclock.c`, lines 116 to 120; `pvclock.c`, lines 27 to 37); Linux reads kvm-clock, the TSC scaled by that page, without an exit, which the HPET's every read is. The page stays registered, since KVM writes it again when it recomputes the clock or the stable bit (`arch/x86/kvm/x86.c`, lines 2604 and 2875), and Linux takes it as it is at each reading (`pvclock.c`, line 75); each other processor registers a page of its own as it starts (`tsc_cpu_setup`), as Linux's `kvm_setup_secondary_clock` does (`kvmclock.c`, lines 190 to 193). Where the pages are kept, KVM's clock in nanoseconds stands for the TSC as the reference, read by each reader from its own processor's page, the page's system time plus the counts since its stamp at its rate (`tsc_kvm_now`; `pvclock.h`, lines 44 to 90), as Linux's kvm-clock counts its nanoseconds as its cycles (`kvmclock.c`, lines 74 to 87): it is one clock on every processor whether or not their TSCs agree, with the stable bit or without it, so the tick, the microsecond clock and the place within the tick count it and never a processor's own TSC. Each tick reads its processor's page (`tsc_kvm_sample`): the page's rate becomes the TSC's counts in a tick, and its stable bit chooses the reference (`ref_wanted` in `pit.c`): a withdrawn bit hands the clock to the HPET or the PM timer, the reference the kernel keeps where nothing vouches for the TSC, until the bit is set again. The old reference counts up to the change and the new one goes on from the same place at the same moment, as Linux's `change_clocksource` moves the time on by the old clock first (`kernel/time/timekeeping.c`, lines 692 to 710 and 1479 to 1502), so the tick count and the microsecond clock go on without a step; the counter is read between two readings of KVM's clock, of three tries the pair closest together, so a stop of the processor between the two clocks' readings moves neither against the other. A hand-over that would count more than the minute one pass counts counts that minute by the old reference and waits for a later pass, so no tick of the backlog is lost, where Linux forwards the whole interval at once. Under `rach2.tscreliable`, or with neither counter, KVM's clock keeps time still, as Linux's kernel goes on reading kvm-clock without the bit. Elsewhere `timer_calibrate` measures the TSC once, with interrupts off, where `cpuid` leaf 0x80000007 says it runs at one rate or `rach2.tscreliable` is on the command line, and never under `rach2.notsc`: against the HPET or the PM timer where one keeps the clock, over three windows of 20 ms, each end a reading of the counter between two of the TSC, of which it keeps the window whose two readings were closest; and on a machine with neither, against the 8254 as the APIC timer is, the lowest rate of three waits of 20 ms, each divided by the 8254's counts the wait saw. Where it finds no TSC at one rate and no `rach2.tscreliable`, the HPET or the PM timer keeps the clock and KVM states no rate, `timer_tsc_watch` measures the TSC the same way, on x86-64 only, for the vDSO's clock alone, as Linux takes a TSC without the invariant bit as its clock source and keeps its clocksource watchdog on it; the reference still keeps the kernel's clock, the processors' checks of the TSC (`tsc_clock_per_tick`) still run, and the vDSO's clock stops for good once the TSC parts from the tick's clock ([the architectures](../Readme.md)). Under QEMU's emulator the reads of the HPET that each `clock_gettime` system call otherwise makes wait on QEMU's global lock, which the GPU's command handling holds for most of a millisecond, and Mesa's Venus driver reads the clock after each submission to decide whether to wake the host's ring, so that a slow read can leave the ring asleep with commands in it. On x86-64 the vDSO's clock reads the TSC at this rate ([the architectures](../Readme.md)), or, where KVM's clock pages are kept, KVM's clock, the TSC converted through the boot processor's page at each reading, and stops while that page's stable bit is withdrawn, so that the vDSO makes the system call; the processors' clock pages lie in a page of their own, which the vDSO maps, and each reading converts through the boot processor's page and checks its stable bit itself (`tsc_kvm_boot_read`), as Linux's `vread_pvclock` does (`arch/x86/include/asm/vdso/gettimeofday.h`, lines 197 to 232), so it makes the system call from the withdrawal on; while it reads the TSC, `timer_clocksource` names `tsc` as the clock source in sysfs, as Linux names it where the TSC is stable, which Linux's KVM selftests require of a host; otherwise it names the reference. The tick's interrupt only prompts the count: `timer_tick_clock` gives the tick handler the reference's whole ticks since the last it counted, one for an interrupt on time, none for one a hypervisor delivers again, and every tick that fell due for one that an emulator delayed or that a stretch with interrupts off left pending, at most a minute's each time. The first tick is taken to fall half a tick into the reference's, so an interrupt early or late by less than half a tick counts the one it was raised for. A tick of the PM timer is 3579.545 counts, so the count is kept in thousandths of a count, and no fraction is lost. The boot's log says which reference keeps the clock, as `clock: reference: the hpet`.

`timer_cycles_us` converts a cycle count at the calibrated invariant TSC rate without reading hardware, or returns zero before calibration or without such a rate.

Where KVM offers its paravirtual EOI feature, each CPU registers a completion word on a separate cache line through MSR_KVM_PV_EOI_EN. `lapic_eoi` exchanges the word with zero and omits the ordinary APIC write when KVM set bit zero; otherwise it writes the normal EOI. The read and clear are one instruction, as [Linux's guest EOI routine](https://github.com/torvalds/linux/blob/v6.12/arch/x86/kernel/kvm.c#L317) requires. Setup shares the existing per-CPU KVM registration in `kvmsteal.c`.

Once the local APIC's timer rate is measured, `apic_hr_init` enables one-shot events on its existing vector, 32. A sleep or timer asks for an absolute monotonic time through `timer_wake_at`. The first request or idle entry makes the device one-shot on the next common scheduler edge (4 ms on either architecture), using the common phase of [Linux's emulated tick](https://github.com/torvalds/linux/blob/v6.12/kernel/time/tick-sched.c#L1477). Its pending bit is read between two clock readings: the first pair within 50 us, or the closest of 16, bounds a stopped processor's sampling error to half the pair's gap. A pending periodic tick uses the preceding common edge once. The timer then counts to the earlier of its next scheduler tick and its earliest requested event, on the same vector. `apic_hr_entry` classifies the interrupt before a wait for the big lock. It advances the tick by whole periods past the clock, or to the next common edge after a gap of four seconds. Only an expiry programmed for the tick has an allowance of 62.5 us for an early arrival; an earlier event cannot take a future tick. An interrupt with both expirations serves both once: the event pass first, then the scheduler tick. An event alone still calls the scheduler after its IRQ context ends, so a timed wake preempts as a device wake does. `/proc/interrupts`'s `timer` row counts every physical local timer interrupt, stale ones included; it includes events between scheduler ticks. The fixed vector needs no LVT write after setup. An event pass programs the next deadline after its queues run; the scheduler tick arms its next event before its handler, so a wait for the big lock cannot hold it back.

The event pass, `timer_hr_pass` in `kernel.c`, advances the global clock, expires sleeps, real alarms and POSIX timers, and posts deferred signals by a try for the big lock. A failed try arms a retry after one millisecond. Each future event is rearmed on the CPU which owns it. `timer_wake_hold` and `timer_wake_release` combine requests made within a pass into its earliest time, including requests made by a clock change or signal dequeue. Nothing is armed until a reference keeps the clock, since the local timer's count is itself the clock before then, or while the 8254 supplies the tick.

The scheduler idle task keeps a running tick during its optional guest poll. In a guest with a one-shot timer, after a halt shorter than one scheduler period without a scheduler tick, it retains the running tick for the next halt, using the preceding residency as its short-wait prediction. A retained scheduler tick clears the prediction even during the poll, so a quiet processor stops on the next entry. This follows the idle governors' choice to [retain the tick for a predicted short interval](https://github.com/torvalds/linux/blob/v6.12/drivers/cpuidle/governors/menu.c#L381). Otherwise it stops before halting (`timer_idle_enter`) and restarts it when the scheduler selects a non-idle thread (`timer_idle_exit`), advancing its next tick past the idle span. With no timer pending the local timer is stopped; otherwise it counts once to the pending event. An interrupt already raised before the stop runs no scheduler tick while the processor is parked. Idle preparation batches its watchdog and device queries into one program; ready work declines the halt and preserves the prior tick state. Where CPUID offers TSC-deadline mode and the TSC rate is measured, the one-shot event is written through IA32_TSC_DEADLINE, with the local-vector entry ordered before the MSR; elsewhere the divided APIC count is used. Long intervals are bounded to ten seconds and armed again when that bound expires. Callbacks in the scheduler idle wait keep their desired requests without programming until final stopped preparation, retained entry or selection of a non-idle thread. A deferred hardware change skips the optional poll, comparing both expiry and mode against the installed device; a short event is committed before another wait. A failed stopped preparation merges its held requests before committing the running timer. The programmed expiry is kept until the device fires or a different event replaces it, so repeated requests for the same event do not write the timer again; a fired one-shot device is already stopped. An idle processor with no event selects deadline mode before clearing IA32_TSC_DEADLINE, since clearing that MSR alone does not stop a periodic local timer. A sleep or alarm measured in whole ticks arms its deadline too (`timer_wake_tick`); its conversion reads pending ticks and the clock phase, so an idle global tick does not lengthen the wait. A live whole-tick request keeps its first converted expiry through nested passes, so another reading of the same target cannot reprogram it by the sampling latency. Clock and phase reads are paired to keep a host stop between them from lengthening the wait. If a slew has carried the smooth clock past that deadline but no raw tick can advance the coarse count yet, it arms the next raw edge instead of a time already passed. A timer keeps the CPU which last armed it: global passes may expire it elsewhere, but only that CPU rearms its future event. A competing local thread also arms a one-millisecond slice event, while the 0.75 ms threshold still protects a thread from an earlier device interrupt. The event's pass advances the global clock before it expires whole-tick timers, and posts both alarms and POSIX signals, retrying a failed try for the big lock after one millisecond.

The boot processor keeps device and protocol services running at their own deadlines while busy or idle. Their queries in `idle_timer.h` return the next service in whole ticks, at most a second away; a one-tick request gets a separate one-millisecond poll event, independent of the scheduler tick; `timer_idle_prepare` arms the earliest of them, timed waits and high-resolution timers before stopping the tick. A wake catches the global clock up from its reference, expires timers and runs the services (`timer_idle_work`, `kernel.c`). The one-second bound extends the HPET or PM counter before it wraps and keeps NTP's seconds current; the load average has its own phased deadline. A busy application processor checks for an earlier service on its tick, and one entering idle checks once more; either kicks the boot processor to install that published deadline, whether busy or idle. New polling work is discovered at the next scheduler pass or idle preparation; an already published service keeps its requested cadence. Sleeps and timers arm their owner directly. The queries take the same locks as their services. A busy boot processor also rearms the next service after each locked pass. A service event runs due work and retries a failed try for the big lock after one millisecond. Idle preparation which cannot take the big lock retains the scheduler tick. A polled network card, USB, active HDA streams, a feeding iTCO watchdog and a POSIX timer which defers to whole ticks keep their existing polling interval as a one-shot service event. Each CPU also arms its next enabled watchdog sample by its absolute monotonic deadline, without adding a fine-clock delay to an old coarse tick count. The idle event samples by elapsed monotonic time, without adding a scheduler tick, so idle processors keep the hard-lockup buddy check running. Settings changes kick parked processors to restart their detectors.

A device with a fine service deadline publishes it through `timer_service_wake_at` after releasing its timer-state lock. The `service_fine` spinlock protects only the earliest nanosecond timestamp; no clock read, device query or callback runs under it. A remote publisher kicks the boot processor to install the event without taking the big lock. An early service pass rearms the published deadline until it is due. The timer pass consumes it before trying the big lock, retaining the one-millisecond retry if that lock is busy.


`timer_now_us` and `timer_phase`, which `sys/clock.c` reads for the clocks, give the reference's ticks counted, the whole ticks it has gone past them and its place within the next, on every processor, within the tick's sequence count; no reading of `timer_now_us` on any processor is earlier than one given before. Before the first tick, and on a machine with no reference, they read the counter under the tick: the local APIC timer's count, or channel 0's latched count with the status bit that says which of mode 3's two sweeps it is in. A reading that finds the counter behind the last counts the period itself, so that the tick does not count it twice, and a stretch with interrupts off longer than a period loses the periods no reading fell inside.

### The other processors

`smpboot.c` starts the processors past the first for `smp_start` (`sys/proc/smp.c`). `platform_cpu_count` gives the boot processor and then the MADT's enabled processors in its order, up to the limit, and gives 1 alone when the local APIC's timer is not the tick, there is no reference counter, or the memory map does not give the trampoline's four pages at 0x8000 as available memory. A processor whose APIC identity is 255 or more is not started, since the xAPIC's messages do not reach it.

`platform_cpu_start` copies the architecture's `trampoline.s` to 0x8000 and fills the mailbox at its end with the boot processor's control registers, its EFER on x86-64, and the new processor's index, stack and entry. It sends INIT, waits 10 ms, sends a startup message for page 8, sends a second 200 microseconds later if the processor has not answered, and waits up to a second. A processor that does not reach its entry is sent INIT again, which keeps it waiting, so that it cannot start late on the next processor's mailbox. On x86-64 the trampoline enters long mode through a PML4 at 0x9000 that maps the kernel's upper half and the first 2 MiB by one executable page, since the direct map's pages are not executable; on i686 the kernel's page directory maps it. `x86_ap_entry` then writes the page attribute table, loads the processor's own descriptor tables, sets up its floating-point unit, enables its local APIC with the MADT's NMI inputs, starts its timer at the boot processor's counts, and calls the shared start. Before it says it has arrived, `tsc_cpu_setup` (`tsc.c`) sets its `IA32_TSC_AUX` to its index, which `rdtscp` and the vDSO's `getcpu` read; the boot processor sets its own in `vclock_start`. Under KVM with KVM_FEATURE_STEAL_TIME it then gives KVM its steal-time record with MSR_KVM_STEAL_TIME (`kvm_steal_cpu_setup`, `kvmsteal.c`), as Linux's `kvm_register_steal_time` does, and the boot processor gives its own in `platform_cpu_init`; the tick takes the time KVM records there out of what it charges ([processes](../../proc/Readme.md)), and a sleeping lock's waiter reads there whether a holder's processor runs (`arch_cpu_preempted`). With KVM_FEATURE_PV_EOI it gives KVM a word for the paravirtual end of interrupt with MSR_KVM_PV_EOI_EN, as Linux's `kvm_guest_cpu_init` does: KVM sets the word when it injects an interrupt whose end needs nothing of it, and `lapic_eoi` ends such an interrupt by clearing the word in one exchange, in place of the write of the EOI register, which is an exit. KVM takes the word back at the next exit, so the timer's interrupts and the interprocessor interrupt end before their handlers write the timer or send a kick (`_irq_router`, `isr_local_router`), as Linux's handlers of its own vectors end theirs first. The boot processor also notes whether KVM offers KVM_FEATURE_PV_SEND_IPI and KVM_FEATURE_PV_TLB_FLUSH, the second only with the steal time and without KVM_HINTS_REALTIME, as Linux's `pv_ipi_supported` and `pv_tlb_flush_supported` do. With the first, an interprocessor interrupt to several processors is KVM_HC_SEND_IPI, one hypercall for each span of 128 APIC IDs on x86-64 or 64 on i686 (`kvm_send_ipi_many`), as Linux's `kvm_send_ipi_mask`, by VMMCALL on AMD and Hygon and VMCALL elsewhere (`kcpu_hypercall4`); a call KVM refuses turns it off, and the APIC sends the set. With the second, a TLB shootdown sends no request to a processor whose record says KVM preempted it, once a compare-and-exchange has added KVM_VCPU_FLUSH_TLB to its `preempted` (`arch_cpu_tlb_deferred`), as Linux's `kvm_flush_tlb_multi`: KVM takes the byte with an exchange as it enters that processor again and flushes its TLB first, and the shootdown does not wait for the host to run it. Then it and the boot processor, in `tsc_sync_target` and `tsc_sync_source`, read the TSC in turn under a lock for two ticks' worth of its counts, each reading compared with the last the other took, and the boot processor waits for the other to finish its turns. Each check is a round that `tsc_sync_open` begins before the processor's INIT: one word holds the round's processor and its flags, which each side sets by compare-and-exchange against its own round, so a processor left over from an earlier round changes nothing. Each side waits for the other at each step for at most 100 ticks by the TSC, not by `k_udelay`, so that the two never latch the 8254 at once; one that times out sets the round's abort flag, and the other leaves at its next look, so neither waits on a processor that has gone. The log says what each check found, as `smp: cpu1: tsc: synchronized with cpu0`, `behind cpu0 by N counts` or `not synchronized: the check timed out`; a processor behind or a check that timed out is recorded with the processor, and `tsc_synced` then keeps the vDSO's clock off the TSC.

### The floating-point state

`fpu_init` (`fpu.c`) chooses one format for every process at boot:

* XSAVE, where the processor has XSAVE and SSE and `rach2.noxsave` is absent. `XCR0` has x87 and SSE, AVX where the processor has it, AVX-512's three components where it has them all and AVX512F, and on x86-64 PKRU where it has protection keys, each while the image stays within `FPU_AREA_MAX`, 4096 bytes. With PKRU `fpu_cpu_setup` also sets CR4.PKE, which turns the keys on ([Protection keys](../../mm/Readme.md#protection-keys)); `fpu_pkru` and `fpu_pkru_set` read and write the running thread's PKRU with `rdpkru` and `wrpkru`, and the initial state holds `PKRU_INIT`, 0x55555554. `xsave` writes every enabled component, so the area is a whole image that a signal frame, ptrace and a core file copy as it is.
* `fxsave`, 512 bytes of the x87 and XMM registers and MXCSR, where the processor has FXSR.
* `fnsave`, the x87 state in 108 bytes, on i686 without FXSR or under `rach2.nofxsr`. `CR4.OSFXSR` is then clear, so an SSE instruction, whose registers would not be saved, is an invalid opcode.

x86-64 uses the 64-bit forms of the instructions. `fpu_cpu_setup` writes CR0, CR4 and `XCR0` for the format on each processor. The state is saved and loaded at every switch, so `CR0.TS` is never set, and a save area comes from the heap aligned to 64 bytes. `fpu.h` gives the layouts of the signal frame's state and of the register sets `NT_PRFPREG`, `NT_PRXFPREG` and `NT_X86_XSTATE`, as Linux has them on each architecture.

### The power controller and the stops

`board.c` finds the chipset's power-management registers at boot (`platform_board_init`, after the tick starts). A chipset is identified before anything is written to it, since a sleep word written at a wrong base reaches whatever decodes there, among the low ports the DMA controller, the interrupt controller, the timer and the reset register:

| Profile | Function | Vendor and device | Sleep type |
| --- | --- | --- | --- |
| `piix4` | 00:01.3 | 8086:7113 | 0 |
| `ich9` | 00:1f.0 | 8086:2918 | 0 |
| `lynxpoint` | 00:1f.0 | 8086:8C40 to 8C5F | 7 |
| `lynxpoint-lp` | 00:1f.0 | 8086:9C40 to 9C4F | 7 |
| `wildcatpoint-lp` | 00:1f.0 | 8086:9CC0 to 9CCF | 7 |

A chipset that matches a row is used only when its ACPI range decodes, its base register is not zero, and `PM1_CNT`, four bytes past the base, does not read all ones; otherwise the log gives the reason. Where `PM1_CNT`'s `SCI_EN` is clear and the profile has an SMI command, the profile's ACPI enable is written to port 0xB2 and `SCI_EN` is awaited, with a bound. With `SCI_EN` set, the SCI's line, 9 on the PIIX4 and the one register 0x44 selects on the others, is masked, and held masked once the I/O APIC takes the lines (`isr_line_hold`), since until a handler clears it a level-triggered line left asserted would be taken for ever. ACPICA's OS layer releases it when it installs its handler (`isr_line_release`, which routes it level-triggered); under `rach2.noacpica` or `rach2.nosci` it stays masked. When no row matches, the log gives the identity of 00:1f.0, so that a row can be added.

`power_stop` (`power.c`) shows records of level `INFO` on the screen again, turns interrupts off, leaves VMX or SVM operation (`k_panic_hook`, [KVM](../../kvm/Readme.md)), stops the other processors, which leave it too, and does what it is given. A request is a write with no answer, so each is followed by a loop of a fixed count before the next is tried:

* `POWER_HALT` parks the processor in a loop of `cli; hlt`, since an NMI or an SMI wakes a halted processor.
* `POWER_OFF` first enters the soft-off state through ACPICA, where `power_prepare` ran the firmware's `\_PTS(5)` ([ACPI](../../acpi/Readme.md)). On a machine still running it writes `\_S5`'s sleep types with `SLP_EN`, when the FADT and `\_S5` were found: to the sleep control register on a hardware-reduced machine, and otherwise to PM1a and PM1b, once with `SLP_EN` clear and once with it set, as ACPI orders the writes. Where `SCI_EN` is clear, the FADT's ACPI enable goes to its SMI command port first. Then it writes the profile's sleep word to its `PM1_CNT`, where a profile passed its checks. Then it halts.
* `POWER_RESTART` writes the FADT's reset value to its reset register, where the FADT has one; 0xFB to port 0xB2, the reset command of an Insyde firmware's SMI handler, only when the SMBIOS vendor begins with `Insyde`, since on another firmware the byte reaches a handler written for something else; 0x02 and then 0x06 to port 0xCF9, the chipset's reset control; and 0xFE to the 8042's command port 0x64, once its input buffer is empty. The three fixed ports come in order of how much of the machine each resets. `rach2.resetskip=N` leaves out the first `N` of the first three, the FADT's register counted only where it exists. Then it halts.
* `power_emergency_restart`, which a panic calls with `panic=N` (`sys/panic.c`) and a restart calls with `reboot=` on the boot line, is the loop of Linux's `native_machine_emergency_restart` (`arch/x86/kernel/reboot.c`), with nothing shut down. From the method `reboot=` names, `a` by default: `a` writes the FADT's reset value to its reset register where the FADT says it has one, one byte in I/O space or at the full offset of a bus-0 function's configuration space whatever width the FADT gives, as Linux's `acpi_reset` does, since a 32-bit write to 0xCF9 would reach 0xCFC, and the FADT's width in memory, and waits 15 ms (`acpi_reboot`, `drivers/acpi/reboot.c`); `k` waits for the 8042's input buffer to empty and writes 0xFE to port 0x64, ten times, 50 us either side of each, and goes back to `a` once when `a` came first; `e` calls EFI's `ResetSystem`, cold or warm, with no data, as Linux's `efi_reboot` does (`efirt.c`), where the kernel booted by UEFI firmware of its own word size, whose system and runtime services tables are sound and whose `ResetSystem` lies in a runtime range: the loader never calls `SetVirtualAddressMap`, so the call runs in the firmware's physical mode, on x86-64 through a PML4 made at boot that maps every runtime range at its physical address under the kernel's upper half, uncached where the EFI map does not give the range EFI_MEMORY_WB, as Linux's `__map_region`, and on i686 with paging off on a stack in the kernel image; `b` writes 0 to CMOS's shutdown status with the NMI masked, copies the architecture's `bios_restart` to the trampoline's page, loads the trampoline's page tables with CR4's PGE and PCIDE clear, and jumps there, where the code leaves long mode on x86-64, then paging and protected mode, with real mode's IDT and the cache written back and off, and jumps to F000:FFF0, as Linux's `machine_real_restart` does; each returns when it cannot run, and the loop goes on; `p` writes port 0xCF9 twice, first with bit 1 and then with 0x0E, or 0x06 for a warm reset, over the register's other bits; `t` loads an empty IDT and raises a breakpoint, a triple fault; and the loop goes on to `k`, for ever. Linux tries 0xCF9 in its default order only once its PCI probe has found configuration mechanism 1 or 2 (`port_cf9_safe`, `arch/x86/pci/direct.c`), which every PC this kernel runs on has. The BIOS flag at 0x472 gets 0x1234 for a warm reset and 0 for a cold one first. Each method logs `reboot: emergency: METHOD` the first time it runs: `acpi: the fadt has no reset register` for an `a` with none, `efi resetsystem` or why `e` cannot run, such as `efi: not booted by uefi`, and `bios restart` or `bios: the page below 1 mib is not free`. Linux's table of machines that need another method (`reboot_dmi_table`) is not kept; the Lenovo is not in it, and its FADT, revision 5, has a reset register, so Linux begins there too.

`kernel_shutdown` in `kernel.c`, which `reboot(2)` and the debug shell's `halt`, `poweroff` and `reboot` call, calls `power_prepare` first, while the caller may still sleep, then unmounts each file system on a disk, the root last, as [../../fs/Readme.md](../../fs/Readme.md) says and stops the USB and network cards before it calls `power_stop`.

### The devices

The PS/2 keyboard's handler (`ps2kbd.c`) reads a scancode of set 1 from port 0x60, on line 1, and gives it to the input layer. A byte 0xAA outside an E0 or E1 sequence and not after the left Shift's press, 0x2A, is the keyboard's self-test code, which it sends when it was reset or plugged in again, as Linux's atkbd tells it from the Shift's release that a translating controller sends as the same byte: keys stop, and once the LED command under way has ended, as Linux's atkbd_reconnect waits for the LED work, the tick and the handler run Linux's atkbd_reconnect, GETID with its two ID bytes, which must be a keyboard's, RESET_DIS and ENABLE, or the LED command with LEDs off when GETID gets no answer, each byte written again after a RESEND or 100 ms without an ACK and failed after three writes or after the controller has refused it for 500 ms, Linux's i8042_wait_write, the ID bytes awaited 500 ms. On a portable chassis, SMBIOS chassis type 8, 9, 10, 14, 31 or 32, whose controller translates, as its configuration byte says at boot, read until two answers agree as Linux's i8042_controller_init reads it, so that a key pressed during boot is not taken for it, and taken to be on when the read fails, the probe skips GETID for RESET_DIS, as Linux's atkbd_skip_getid does, since GETID confuses some laptops' keyboards, and takes the keyboard to be there. A reconnect that finds a keyboard keeps its event device and sends the LEDs again; one that does not unbinds atkbd, its held keys released and its event device gone, and in auto mode probes serio0 anew as Linux's serio core does, binding a new event device when a keyboard answers and an event device is free; with none free serio0 stays without a driver. A port without a driver drops its bytes, and in auto mode its next byte starts that probe. The keyboard's LEDs follow what the input layer wants (`input_leds`): at each tick, when they differ from what the keyboard shows and 50 ms have passed since the last LED command, `ps2kbd_tick` writes the command 0xED, and the handler takes the keyboard's ACK, 0xFA, or RESEND, 0xFE, before the byte reaches the input layer (`input_ps2_reply`), writing the LED byte after the command's ACK. Every byte is written only when the controller's input buffer is empty, never waiting, and again after a RESEND or 100 ms without an answer; after three writes, or 500 ms of the controller refusing the byte, the command is given up with a warning, and the next starts only when the LEDs wanted change. The 8042's waits and writes, which the keyboard and the mouse share, are in `i8042.c`; the configuration read drains the output buffer before its first READ_CONFIG, and after its last writes the agreed byte back and drains it again once the controller has taken it, as Linux's i8042_controller_init writes its CTR before i8042_flush, so that the controller has answered every READ_CONFIG and an answer left over from the reads never reaches line 1's handler as a key; a wait of the status ends after 100,000 reads or half a second by the clock, Linux's bound, whichever comes first, since under a hypervisor each read is an exit and 100,000 of them took 42 s at the third level of nesting. The mouse's (`ps2mouse.c`) assembles the three-byte packets of the 8042's auxiliary port, on line 12. The bring-up asks first for a Kensington ThinkingMouse by psmouse's nine rates, and before it knocks for a wheel, for a Synaptics touchpad, as Linux's psmouse does; `synaptics.c` sets one up in absolute mode with Linux's queries and mode byte, registers its event device and takes its six-byte packets from the handler, and a pad whose setup fails goes back to relative mode and on as a mouse. Where no Synaptics pad answers, `alps.c` asks for an ALPS pad by its E6, E7 and EC reports, identifies its protocol, versions 1 to 8, as Linux's `alps.c` does, sets it up through the version's command mode, registers the pad's event device and a DualPoint's stick's, and takes the pad's packets of six or eight bytes, the stick's and those of a mouse on the pad's external port from the handler; a pad whose setup fails is reset and goes on as a mouse, and is not asked for Elantech's. Where neither answers, `elantech.c` knocks for an Elantech pad of hardware version 1 to 4, identifies it and its firmware by Linux's queries, writes its registers for absolute mode, registers the pad's event device and a pointing stick's before it, and takes the packets of each version from the handler, choosing a machine's quirks by the SMBIOS maker and product name as Linux chooses them by DMI; a pad whose setup fails is reset and goes on as a mouse. Where no touchpad answers, `ps2mouse.c` asks for a Genius NetMouse by its status after three 1:1 scalings, and `trackpoint.c` for a TrackPoint by its read-ID command, as Linux's psmouse does on any port, and sets one up on the port itself. The mouse is brought up after ACPICA, whose namespace gives the PS/2 mouse's PNP IDs (`sys/acpi/pnp.c`, `i8042_pnp_device`), by which `synaptics.c` applies Linux's quirks. A Synaptics pad's pass-through port is a line of its own (`struct ps2io`, `synaptics_pt`): a byte for the device behind it, the guest, goes sliced and ended by the rate 0x28, and each of the guest's comes back in a pass-through packet, so that `ps2mouse.c` probes the guest as Linux's psmouse probes a port of type SERIO_PS_PSTHRU and reports its packets, and `trackpoint.c` sets up a TrackPoint and gives its settings as files. After the bring-up the handler owns the port; a run of commands, a write to a stick's file or a reconnect, takes it back (`ps2mouse_cmd_begin`) and the handler leaves the bytes in the 8042 meanwhile, as Linux's PSMOUSE_CMD_MODE does; the packet under way is dropped as the run begins and ends, as Linux's `__psmouse_set_state` drops it. A wait of a driver's (`ps2mouse_msleep`) sleeps in kpsmoused and runs with interrupts on during the bring-up. The configured number (`resetafter`) of bad packets in a row, or an ALPS pad's bad bytes, or the announcement 0xAA 0x00 of a device that reset itself, stop the port until the kernel thread kpsmoused has reconnected it, as Linux's `serio_reconnect` does; a mouse keeps its event device when it speaks the same protocol after its reset. A pause of half a second inside any protocol's packet, or a packet's first byte after the port's `resync_time` idle, has kpsmoused resync the device instead (`ps2mouse_resync`): it is disabled, polled with 0xEB for a packet of its protocol's form and enabled, and reconnected when that fails, as Linux's `psmouse_resync` does. The ports' serio directories in sysfs have psmouse's files, `protocol`, `rate`, `resolution`, `resetafter` and `resync_time`, which `evdev_sysfs.c` makes from `ps2mouse.c`'s tables, and the files of the protocol beside them, a TrackPoint's settings, an Elantech pad's registers (`elantech_sysfs_add`) or a Synaptics pad's `disable_gesture` in relative mode (`synaptics_sysfs_add`), replaced at once when a write of `protocol` switches the port as Linux's `psmouse_attr_set_protocol` does; each write runs as a change (`ps2mouse_change_begin`), with the device disabled. Both ports accept Linux's whole protocol-name table as its kernel for the architecture has it, OLPC's HGPK on i686 alone; a detect not implemented, or a touchpad protocol on the pass-through port, resets the device and falls back to PS/2. `SynRelPS/2` sets a Synaptics pad up in its three-byte relative mode as Linux's `synaptics_init_relative` does, with the absolute mode byte less its absolute bit, the rate through the pad's own setter (`synaptics_set_rate`), the pad's buttons and model on a mouse's event device, and a reconnect that keeps the mode and the device. A reconnect retries absolute mode after a pad's failed setup. A protocol switch reserves its main event device before removing the old protocol; exhaustion leaves the old devices and protocol intact. Elantech's and a relative Synaptics pad's callbacks carry a generation; serio2's psmouse files compare the count of guests unbound, and a guest TrackPoint's settings the count of guest protocols replaced or unbound, with the one they saw on entry; each checks again after taking the command lock, so a callback that waited through a switch or a probe fails with `ENODEV`. serio2's psmouse files are its guest's driver files (`evdev_sysfs_serio_driver`), bound with the guest and kept across a switch of its protocol, as Linux's psmouse `dev_groups` are, so that a handle open on one stays good; the switch replaces only a TrackPoint's settings. serio2 lives as long as a Synaptics pad with a pass-through port, in either mode, made without a device below it (`evdev_sysfs_serio_add`), as Linux's serio core keeps a port whose driver went: a guest that goes, or fails its reconnect, takes only its event device and serio2's files, and a switch of serio1 away from the pad removes the port, its bus link and its callbacks. A port's `bind_mode` is `auto` until a write of `manual` (`evdev_sysfs_serio_manual`), as Linux's serio core keeps it: a reconnect of serio1 that fails in manual mode leaves the port with no driver, its event device and psmouse files gone, and the handler drops its bytes, and a guest on serio2 is not probed again; in auto mode the port's next byte has kpsmoused probe it anew, as does a pass-through packet on serio2 without a guest, as Linux's `serio_interrupt` rescans a port without a driver. A write of serio1's psmouse files that waited for the command lock while psmouse's binding ended fails with `ENODEV`, by the count of serio1's ended bindings it saw on entry, which a failed reconnect advances in either mode. serio0's mode decides the keyboard's driver after a failed reconnect, as above, and its uevent names atkbd only while atkbd has the port (`evdev_sysfs_serio_unbound`). [input(4)](../../../../man/man4/input.4) says what each file does. [Terminals](../../tty/Readme.md) says what each reports. Status bit 5 says whose the waiting byte is, and each handler reads the data port only for its own device's byte, so that the keyboard's is left for line 1 and the mouse's for line 12. The 8042 keeps its line raised while a byte waits, and an I/O APIC input misses an edge that comes while it is masked, so once either handler is routed through the I/O APIC, `ps2_waiting` (`platform.c`) raises its vector once when that device's byte already waits. The terminals above them are in [terminals](../../tty/Readme.md).

COM1 (`serial.c`) is the 16550 at 0x3F8, found by its scratch register and set to 115200 baud, eight bits, no parity and one stop bit. A byte out is dropped after a bounded wait, so that a port that does not drain delays the kernel and does not stop it. Bytes in are taken on line 4 and at every tick into a ring, which [terminals](../../tty/Readme.md) describes with the rest of the receive path.

The speaker (`speaker.c`) is the 8254's channel 2 in mode 3, gated to the speaker by port 0x61 ([audio](../../audio/Readme.md)). The CMOS clock (`cmos.c`) is read at boot as two samples that must agree, and a clear valid bit in status register D ends the read, since reading the register can set the bit again; its device is [rtc(4)](../../../../man/man4/rtc.4).

### The reports and the rest

Both boot reports read and print and configure nothing. `platform_report` runs them after the firmware's tables are read and before the interrupt controllers start.

* `rach2.diag` (`diag.c`) prints the kernel's end, the free frames and each module's range, and identifies a Realtek 10ec:8168 by its `TxConfig` register, since the family shares one device ID. Before the first program it prints them again with the board, the network card, the disk policy and the entropy source, and waits for a key or a byte on COM1, for a machine whose only output is its screen.
* `rach2.apicdiag` (`apicdiag.c`) prints what the firmware left in the local APIC, and the MSI and MSI-X capabilities of the first xHCI and HDA controllers.

`rach2.exits` (`exits.c`) counts, on each processor, the MSR accesses by register, `cpuid` by leaf, the port accesses by port and the halts that `kcpu.c`, `portio.c` and `cpu.c` make, the instructions a hypervisor may take as an exit, and the ends of interrupt by how they went: through KVM's paravirtual word, or by a write of the EOI register, by vector, after an exit took the word back between the router's start and the end or with no word set at the start (`lapic_eoi_enter`), which debugfs's `exits` prints with the interprocessor interrupts each processor sent ([debugfs(5)](../../../../man/man5/debugfs.5)). Each router keeps the vector and the initial word reading in its saved context and passes them to `lapic_eoi`, so a nested interrupt or a handler's sleep cannot change the attribution. KVM's own counters leave every MSR access unnamed.

`cpuinfo_text` (`cpuinfo.c`) writes a processor's block of `/proc/cpuinfo` from `cpuid` on the processor that reads it, leaving out `xsaves` where `kcpu_xsaves_usable` (`xsaves.c`) finds Erratum 1386 unfixed, as Linux's `fix_erratum_1386`. `cpuinfo_place` cuts a processor's APIC ID into its package, its core and its thread at the widths `topology_widths` reads: the shifts of leaf 0xB's levels, and without them leaf 1's count of logical processors, divided into cores by leaf 4 on Intel and by leaves 0x80000008 and 0x8000001E on AMD. `cpuinfo_siblings` gives the processors started that share a core or a package, from which `/proc/cpuinfo` counts `siblings` and `cpu cores` and `procfs.c` writes `/sys/devices/system/cpu/cpuN/topology`. `cpuinfo_cache` describes a processor's caches as Linux's `cacheinfo.c` reads them, for `/sys/devices/system/cpu/cpuN/cache/indexM`: leaf 4 on Intel and every vendor but AMD and Hygon, leaf 0x8000001D on Hygon and on AMD when TOPOEXT is set, and otherwise AMD's leaves 0x80000005 and 0x80000006 put into leaf 4's layout, as `amd_cpuid4` puts them, with Linux's table of associativity codes applied to the L1's eight-bit count too. A cache's id is the APIC ID above the bits that number the processors sharing it; the processors sharing it are those whose APIC IDs agree above those bits, a run of that many APIC IDs for an L1 or L2 of leaf 0x8000001D, and on AMD's older leaves the package for the L3 and the processor alone for the rest. `debugreg.c` keeps each thread's debug registers, loads them when it runs, and drops a debug exception taken in kernel mode, as Linux does, as [ptrace](../../proc/ptrace.Readme.md) describes.

## Limits

* `acpi.c` reads only `\_S5` of the DSDT, and the kernel asks ACPICA for no `_PRT`: a device without MSI is served on the ISA line its interrupt line register gives, and one whose interrupt reaches only an I/O APIC input above 15 takes none.
* In x2APIC mode an interprocessor interrupt to several processors, a TLB shootdown's, a kernel flush's or the kicks of a wake of many, is one message in logical mode for each cluster of 16, as Linux's `x2apic_cluster` sends it (`platform_cpu_ipi_many`), unless KVM's KVM_HC_SEND_IPI sends it; every other message, a device's among them, names one processor by its physical identity. An unremapped device interrupt goes to a chosen processor whose identity must be below 255, the reach of a message's 8-bit destination, unless VT-d remaps interrupts in x2APIC format. A hypervisor's x2APIC mode is not taken for a larger one; a firmware's x2APIC mode with one is refused where no remapping can come, on i686 and under `noapic`, and is a panic on the x86-64 kernel when remapping does not start in x2APIC format, as Linux's `x2apic_disable` panics; under a hypervisor that allows x2APIC mode unremapped it is kept, as Linux's `try_to_enable_x2apic` keeps it without calling `x2apic_disable` (`arch/x86/kernel/apic/apic.c`, lines 1830 to 1856), though an unremapped interrupt's 8-bit destination does not reach it. Until remapping starts, the I/O APIC's entries and the messages name such a processor by the low eight bits of its identity, and do not reach it. Linux keeps a firmware's unlocked x2APIC mode on bare metal under `noapic`, without remapping, which its own comment calls unsupported there; this kernel leaves it. VMware's leave to use x2APIC mode unremapped needs its backdoor hypercall and is not asked, so under VMware the APIC stays in xAPIC mode without remapping. On i686, which has no interrupt remapping, x2APIC mode is used under a hypervisor alone; Linux's i686 kernel has no x2APIC mode at all.
* Legacy lines stay on the boot processor. PCI messages are spread across reachable online processors, by the number of messages allocated, with the first logical processor breaking ties as Linux's interrupt matrix does.
* The ACPI record keeps 64 processors, 8 I/O APICs, 16 overrides, 8 NMI inputs and 8 NMI sources, 32 tables and 4 MCFG windows; the rest are counted and left out. A table longer than 4 MiB is not read.
* ECAM reaches segment 0 alone; other segments are not reached. On i686 no ACPI table, ECAM window or HPET above 4 GiB is used, and on both no loader pointer or framebuffer above 4 GiB.
* Both architectures schedule busy processors at 250 Hz, on physical machines and in guests; coarse clocks and CPU accounting use 4 ms units. The scheduler stops the tick while a processor runs its idle task, with a reference clock and the local APIC timer; the 8254-only path remains periodic. Polling drivers still request service at their polling interval.
* The reference counter is read in 32 bits, or 24 for the PM timer, and extended at each tick, so a stretch without a tick longer than its wrap, 4.7 s for the PM timer and 43 s for QEMU's 100 MHz HPET, loses the wraps. The time-stamp counter's rate is measured over 20 ms and is as good as that measurement. The calibrations are right under a stop of the processor shorter than the reference's wrap, and, against the 8254, when one of the three waits ran without a stop.
* Five chipsets have power profiles. The sleep type 7 and the ACPI enable 0xA0 of the Lynx Point and Wildcat Point rows are the PCH's encoding and the value their firmware publishes, and no emulator has those chipsets.
* The stops' waits are loop counts, not times.
* The serial console is COM1 alone, at 115200 baud; the PS/2 mouse speaks the plain, IntelliMouse, IntelliMouse Explorer, Kensington ThinkingMouse, Genius NetMouse or Cortron Trackball protocol, or the touchpad protocols of Synaptics, of ALPS, versions 1 to 8, and of Elantech, or a TrackPoint's, and no other vendor's, so an ALPS pad of version 9 or another vendor's touchpad works as a plain mouse; of Linux's Synaptics machine quirks only the Toshiba rate of 40 is taken, not the Cr-48's profile sensor; an Elantech register file reads the pad disabled where Linux reads it reporting; the speaker plays a square wave and no samples; of SMBIOS only the fields `/sys/class/dmi/id` shows are read, each string cut at 63 bytes.
* The CMOS clock's century is taken as 2000, and the FADT's century register is logged but not used.
* The extended state covers x87, SSE, AVX, AVX-512 and, on x86-64, PKRU alone, `XCR0` bits 0 to 2, 5 to 7 and 9. The i686 kernel turns no protection keys on, as Linux's 32-bit kernel does not.
* On the Lenovo an expiry of the TCO watchdog does not bring the machine back: under Linux 6.12, which programs the TCO as `itco.c` does and leaves SMI_EN's TCO_EN set on version 2, the first stage's expiry left the machine down until it was powered on by hand. No hang experiment may count on the watchdog to return it. `iTCO_wdt.turn_SMI_watchdog_clear_off=2` clears TCO_EN as Linux does with the same option, so that the second stage resets through the chipset; whether that brings the Lenovo back is not yet seen.

* `tests/run disk-q35` boots QEMU's `q35` machine, with its ICH9, MCFG and FADT reset register, and checks the disk alone.

No suite boots with `noapic`, `rach2.board`, `rach2.nosci`, `rach2.diag` or `rach2.apicdiag`.

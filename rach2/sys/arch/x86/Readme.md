# The PC platform

`sys/arch/x86/` is the PC platform that the i686 and the x86-64 kernels share: the part of the machine around the processor that every PC has. It reads the loader's Multiboot or multiboot2 information into the boot record and the firmware's ACPI and SMBIOS tables; it gives the kernel PCI configuration space, the interrupt controllers, the 1000 Hz tick and the clock under it, the other processors and each process's floating-point state; it drives the 8254 timer, the CMOS clock, the 8042 keyboard and mouse controller, COM1 and the speaker; and it stops and restarts the machine. Shared code reaches it only through the headers listed under Interfaces, so a port to another machine replaces this directory and keeps the rest. The processor's own layer, the descriptor tables, the entry code, paging and the context switch, is in `i686/` and `x86_64/` ([the architectures' Readme](../Readme.md)); thread-local storage has [its own document](../tls.Readme.md).

## Interfaces

The platform defines what these shared headers declare. Each header states its contract; the table says where it is carried out.

The drivers of the other devices only a PC has are kept by their subsystems and listed in this directory's `sources.mk`, and they alone include one of its headers, `portio.h`: the ATA channels ([block storage](../../block/Readme.md)), the Sound Blaster 16 and its ISA DMA ([audio](../../audio/Readme.md)), and the VGA text console, mode 13h and the framebuffer console ([display](../../display/Readme.md)).

The manual describes what a user sees: [acpi(4)](../../../../man/man4/acpi.4) the controllers, the tick, the processors and the stops with the log lines they print, [proc(5)](../../../../man/man5/proc.5) `/proc/interrupts` and `/proc/cpuinfo`, [rtc(4)](../../../../man/man4/rtc.4) `/dev/rtc0`, and [reboot(2)](../../../../man/man2/reboot.2) and [halt(8)](../../../../man/man8/halt.8) the stops.

### The boot line

The platform reads these words of the kernel command line, which [cmdline.md](../../../cmdline.md) lists with the rest:

* `rach2.nomsi` (`lapic.c`): the local APIC is not enabled. No device sends messages, the I/O APIC is not used, the 8259 pair delivers every line, the 8254 ticks, and the kernel runs on one processor.
* `noapic` (`platform.c`): the I/O APIC is not used. Devices still send messages to the local APIC, but lines 0 to 15 come through the 8259 pair and the 8254 ticks, so the kernel runs on one processor.
* `maxcpus=N` (`sys/proc/smp.c`): at most `N` processors, the boot processor counted; 0 and 1 both leave the kernel on the boot processor.
* `rach2.nofxsr` (`fpu.c`): on i686, `fnsave` saves the x87 state and SSE is off. The x86-64 kernel ignores it.
* `rach2.noxsave` (`fpu.c`): `fxsave` saves the state on a processor that has XSAVE, and a program sees no AVX.
* `rach2.board=NAME` (`board.c`): only the power profile `NAME` is tried, and the chipset must still match it; an unknown name, or a chipset that does not match, leaves the machine with no profile.
* `rach2.nosci` and `rach2.noacpica` ([ACPI](../../acpi/Readme.md)): ACPICA takes no system control interrupt, whose line then stays masked, or is left out.
* `rach2.resetskip=N` (`power.c`): one digit; a restart leaves out its first `N` methods before the keyboard controller's pulse, which it never leaves out.
* `reboot=LIST` (`power.c`): as Linux's: the method a restart and a panic's reset begin with, `a`, `k`, `t`, `e`, `b` or `p`, and the reset's warmth, `w` warm and `c`, `h`, `g` or `s` cold, with `panic_` before a mode for a panic's alone; items are split by commas and judged by their first letter, and each `reboot=` is read in turn. With it, a restart runs the emergency sequence below in place of the default one, and `rach2.resetskip` has no effect.
* `rach2.nomouse` (`platform.c`): the PS/2 mouse is not probed.
* `rach2.diag` and `rach2.apicdiag` (`diag.c`, `apicdiag.c`): the boot reports described below. Neither is a command of the debug shell.

## Design

### The watchdog

`itco.c` drives the version 2 TCO watchdog of the `ich9` and `lynxpoint-lp` profiles through the PMBASE and enabled RCBA that `board.c` exposes. It registers `/dev/watchdog` through the device registry after the board probe, with the timer halted; an exclusive open arms it. [watchdog(4)](../../../../man/man4/watchdog.4) owns the user contract. The register sequence follows Linux 6.12's `drivers/watchdog/iTCO_wdt.c`: preserve reserved bits, program 0.6-second ticks, clear NO_REBOOT before starting, reload, and read back halt and timeout writes. An orderly stop halts the timer through `power_prepare`. All accesses are bounded and serialized by the big lock; there is no interrupt handler or software feeding thread. The host test supplies the register callbacks and advances the hardware ticks itself.

### Sources

`sources.mk` sets `PC_C_SRC`, which both `i686/sources.mk` and `x86_64/sources.mk` include: the 39 C files here and the seven PC drivers above. `iommu/` has the VT-d driver, which `x86_64/sources.mk` alone includes. The platform has no assembly; the first code a started processor runs is each architecture's `trampoline.s`. Every file compiles for both architectures, with `#if defined(__x86_64__)` where they differ, and an instruction the staged TinyCC's assembler lacks, such as `rdrand`, `xsave` or a debug register move, is written as its bytes. The readers of firmware data, `mbinfo.c`, `acpi.c`, `smbios.c`, the judgements of `board.c` and the decoding of `cmos.c`, reach memory and registers only through what they are given, so that host tests can feed them tables no machine can be made to produce.

### From the loader to the boot record

Each architecture's `loader.s` calls `k_main(magic, info)` in `boot.c` ([the kernel's Readme](../../../Readme.md) has the path). `k_main` starts COM1, so that everything after can be logged, and reads the loader's information by its magic: `0x2BADB002` is Multiboot's (`mb1_read`) and `0x36D76289` multiboot2's (`mb2_read`), both in `mbinfo.c`, which reads each field by its offset a byte at a time and calls no kernel service.

* Multiboot passes one structure with pointers to the command line, the loader's name, the modules and the memory map. A pointer is followed only below 4 GiB: as the physical address itself on i686, where paging is still off, and through the direct map of the first 4 GiB that `loader.s` built on x86-64.
* multiboot2 passes a list of tags, read up to 1 MiB (`MB2_INFO_MAX`). Under UEFI the EFI memory map takes the place of the loader's own: its types become Multiboot's, the loader's and the boot services' memory counted as usable, since neither runs again. A tag of the EFI tables or of the EFI map sets the record's `uefi`, and a tag of the RSDP, ACPI 2.0's in preference to 1.0's, is copied into the kernel's image; the record's `acpi_rsdp` is the physical address of that copy. Multiboot passes no RSDP, and `acpi_init` then searches the BIOS area.

The record keeps copies of what it points at, since the loader's memory goes to the frame allocator: up to `BOOT_MMAP_MAX`, 256, memory-map entries, `BOOT_MODULE_MAX`, 8, modules with their command lines, and `BOOT_CMDLINE_MAX`, 512, bytes of command line (`sys/boot.h`). `k_main` then records the modules in `module_table` (`module.c`), starts the framebuffer console when the loader left a framebuffer of direct or indexed color, and calls `kernel_main`. Once the kernel's page tables are in force, the console draws through a mapping of the framebuffer, write-combining where the page attribute table allows it and uncached otherwise.

### The processor and its vectors

`platform_cpu_init` writes the page attribute table, loads the architecture's GDT, TSS and IDT, and installs the exception handlers (`init_isr`), which enables interrupts. `pat_setup` (`pat.c`) makes entry 1 of `IA32_PAT` write-combining in place of write-through, for the framebuffer's mapping (`PTE_WC`), and leaves the other seven at their reset types. `init_idt` programs the 8259 pair (`pic.c`) to vectors 32 to 47 with every line unmasked but the keyboard's, whose byte would be lost if it came before its handler. `cpu.c`, `kcpu.c`, `kirq.c` and `portio.c` are the instructions: the primitives of `arch.h`, `cpuid` and the model-specific registers, the interrupt flag, and the I/O ports.

| Vectors | Use |
| --- | --- |
| 0 to 31 | the processor's exceptions |
| 32 to 47 | lines 0 to 15, line `N` on 32 + `N`, through the 8259 pair or the I/O APIC |
| 48 to 239, but 128 | devices' messages, 191 vectors (`vector.c`), given out lowest first by `isr_alloc_vector`, or lowest at a multiple of a power of two by `isr_alloc_vector_aligned`, and back by `isr_free_vector`; their stubs are one run in `isr_handler.s`, 16 bytes apart, which `init_idt` checks |
| 128 (0x80) | the system call gate, on i686 alone |
| 240 (0xF0) | the interprocessor interrupt |
| 255 (0xFF) | the local APIC's spurious vector |

Each vector has a chain of up to four handlers (`isr.c`), since PCI lines are shared and each handler must look at its own device. `_irq_router` takes the big lock, counts the interrupt, runs the chain and ends the interrupt at its controller: through the 8259 before the chain, and through the I/O APIC or for a message after it, since a level-triggered line still asserted would be sent again at once. The tick is ended first on either path, since its handler may switch processes and a vector in service blocks every vector of its priority class and below. A processor takes its tick with the big lock only when no other processor holds it (`bkl_try_enter`); otherwise it ends the tick, counts it on its record, which `/proc/interrupts` and `/proc/stat` add in, and returns to what it ran, so that a long handler on one processor, such as the sound mix, does not hold up the user code of the others. Waiting would also stop that user code outright once the waits pass a tick: the next tick is then pending at the return to user mode and comes before the next user instruction, so a program that runs on the boot processor beside three that keep the lock busy made no progress for seconds. Once 4 such ticks in a row have passed with a process waiting on its queue, a tick waits for the lock (`sched_tick_waits`), since only the tick ends a slice; the boot processor's tick also waits at its fourth in a row, so that its periodic work is at most that late, and always before a reference keeps the clock, since its tick alone counts the clock then (`tick_waits`). A tick of a processor past the first that has the lock makes the timer pass, which counts the tick from the reference and fires the timeouts due, when the tick count has not moved over two of its ticks (`timer_handler`, `kernel.c`), as when the boot processor's tick found the lock held. The NMI, the machine check, the x86-64 double fault, the interprocessor interrupt and the spurious vector are taken without the big lock, since the processor they interrupt may hold it.

An exception in user mode becomes a signal ([signals](../../proc/signal.Readme.md)); in kernel mode it panics, a debug exception aside. The NMI and the machine check stop the machine. The double fault runs on a stack of its own, through a task gate on i686 and an interrupt stack on x86-64, and reports a kernel stack that ran into its guard page.

### The firmware's tables

`platform_firmware_init` runs once paging is on, since every table is reached through `map_mmio`, and before the interrupt controllers, which read the tables. It reads ACPI's tables, keeps the UEFI system table for SMBIOS, maps the ECAM window, finds the reference counter, and checks the trampoline's pages, in that order.

`acpi_init` (`acpi.c`) takes the RSDP from the boot record, or searches the first KiB of the extended BIOS data area and then 0xE0000 to 0xFFFFF. It walks the XSDT, or the RSDT where there is no good XSDT, and reads the first MADT, FADT, HPET table and MCFG, and the DSDT the FADT gives. A table is read only after its length and checksum pass, and one that fails is logged and left out. `struct acpi_info` (`acpi.h`) keeps the result: the processors, I/O APICs, interrupt source overrides and NMI wiring of the MADT; the PM1 control registers, the PM timer, the reset register, the SMI command and the sleep control register of the FADT; the HPET's address; and the MCFG's windows.

ACPICA, in [`sys/acpi/`](../../acpi/Readme.md), interprets the DSDT and the SSDTs once the scheduler runs, from the RSDP `acpi_init` found. The two sleep types of `\_S5` come from the DSDT without it, so that the power off works with ACPICA left out or refused: `acpi_s5_find` searches its bytes for the name `_S5_` after NameOp, followed by a package whose first two elements are integer constants of at most 7. `acpi_isa_route` gives each ISA line its global system interrupt, trigger and polarity from the MADT's overrides, a line a PCI device uses being level-triggered and active low unless an override gives the polarity.

`smbios.c` finds the table through the UEFI configuration table's entry point or by a search of 0xF0000 to 0xFFFFF, and reads the fields Linux's `dmi_decode` keeps from the BIOS, System, Base Board and Chassis Information structures, each from the first structure long enough to hold it, for `/sys/class/dmi/id` (`dmi_field`, `sys/dmi.h`). Of them the BIOS vendor decides the restart below, and the manufacturer and product name are those by which `alps.c` and `elantech.c` choose Linux's quirks for a machine. A string of spaces alone reads empty, as in Linux; the UUID is written with its first three fields' bytes reversed from version 2.6 on.

### PCI configuration

`pciconf.c` gives `sys/pci.c` access to configuration space. Mechanism #1 writes the address to port 0xCF8 and moves the data at port 0xCFC, with interrupts off, since every access shares the two ports and the USB driver reaches configuration space from its interrupt. A 16-bit or 8-bit write is one access at the data port's byte, not a read and a write of the dword, since the status word beside the command word is cleared by writing ones.

`ecam_init` (`platform.c`) maps the MCFG's window for segment 0: the first bus and those behind its bridges, found through mechanism #1, at most 32 (`ECAM_MAX_BUSES`), a MiB each. The window is used once its first function reads there as it reads through the ports; from then a function on a covered bus is 4 KiB of memory, an access is one load or store, and offsets 256 to 4095 can be reached. A device's message is its vector written to 0xFEE00000 with the boot processor's APIC identity in bits 12 to 19.

### The interrupt controllers and the tick

`platform_timer_start` (`platform.c`) brings the controllers up and starts the tick at `TICK_HZ` (`timer.h`), 1000 a second, with interrupts off until the last step:

1. `lapic_init` (`lapic.c`) enables the local APIC unless `rach2.nomsi` is given, the processor has no APIC or no model-specific registers, the APIC is in x2APIC mode, or its base is above 4 GiB. It makes `LINT0` an unmasked external interrupt, so that the 8259's interrupts still reach the processor through it.
2. `init_pit` programs the 8254's channel 0 in mode 3 with the reload 1193. On a machine whose channel 0 does not count, `k_udelay` uses the reference counter, where there is one. Under `rach2.tscreliable` the TSC is measured next (`timer_calibrate`), so that the first tick makes it the reference.
3. The I/O APIC (`ioapic.c`) is used when `noapic` is absent, the local APIC is enabled, and the MADT lists an I/O APIC that answers. `ioapic_init` masks every input.
4. With the I/O APIC, the local APIC's timer is measured; the 8259 pair is masked for good (`pic_retire`); `LINT0` and `LINT1` are masked but where the MADT gives either as an NMI input; the lines PCI functions' interrupt line registers give are noted as level-triggered; and lines 0 to 15 pass to the I/O APIC. The tick is the local APIC's timer, periodic on vector 32, or the 8254 through the I/O APIC when the measurement failed.
5. Without it, the tick is the 8254's line 0 through the 8259 pair.
6. Interrupts are enabled, and the tick must arrive within 50 ms. A local APIC timer that does not interrupt is replaced by the 8254; on the 8259 path `LINT0` is written again. A machine that still does not tick is logged and goes on.

A line is routed through the I/O APIC when a handler is registered on its vector (`isr.c`), to the input `acpi_isa_route` gives, on vector 32 + line, to the boot processor. A line a PCI function's interrupt line register gives is level-triggered because SeaBIOS and OVMF route the function's PIRQ to that ISA line and write the register so. `pic_mask_irq` keeps a line masked at the I/O APIC once the 8259 is retired. While VT-d remaps interrupts, a routed line's redirection entry names an entry of the remapper's table in its high half: `ioapic_remap_start` rewrites each line already routed, and `ioapic_route_line` maps each one routed later through it ([VT-d](iommu/Readme.md)).

The local APIC's timer counts at a divided bus clock that no register states, so `apic_timer_calibrate` (`apictimer.c`) runs it with interrupts off over 20 ms of the reference counter (`refclock.c`): the HPET's main counter where the HPET table gives one, the ACPI PM timer otherwise, and the 8254 where there is neither. A hypervisor may stop the processor at any point of the measurement, so the timer is read at each end between two reads of the reference, taken again when those two are more than 50 microseconds apart, and its place taken midway between them. Against the 8254, the timer's counts are divided by the counts `pit_wait_counts` (`udelay.c`) saw fall during the wait, not by the 20 ms it asked for. That wait cannot see a sweep of the counter that passes between two of its samples, so a stop makes the wait longer than it measured and never shorter: the timer is measured over three waits, and the lowest rate taken. The HPET is started with its legacy replacement and its comparators' interrupts off, so that the 8254 and the CMOS clock keep their lines; neither counter raises an interrupt.

`k_udelay` (`udelay.c`) latches channel 0 and adds up how far its count fell, each latch and its two reads with interrupts off, since a handler that latched the counter between them would leave the reads a byte of the live count each. A count that stops moving ends the wait, so a machine without an 8254 does not wait for ever.

### The clock under the tick

The clock is kept by a reference counter from the first tick on: the HPET's main counter or the ACPI PM timer, whichever `refclock.c` found, and on a machine with neither, the time-stamp counter. Under `rach2.tscreliable`, `platform_timer_start` measures the TSC before interrupts are on, and the TSC keeps the clock even where the HPET or the PM timer is, as Linux's TSC does where it is stable: under a hypervisor each read of either is an exit, the tick reads the reference at least twice, and at the third level of nesting, at some 200 microseconds an exit, the exits outlasted the tick. While the TSC keeps the clock, `k_udelay` waits on it too (`tsc_wait_us`), as Linux's `delay_tsc` does. `timer_calibrate` (`pit.c`) measures the TSC once, with interrupts off, where `cpuid` leaf 0x80000007 says it runs at one rate or `rach2.tscreliable` is on the command line, and never under `rach2.notsc`: against the HPET or the PM timer where one keeps the clock, over three windows of 20 ms, each end a reading of the counter between two of the TSC, of which it keeps the window whose two readings were closest; and on a machine with neither, against the 8254 as the APIC timer is, the lowest rate of three waits of 20 ms, each divided by the 8254's counts the wait saw. On x86-64 the vDSO's clock reads the TSC at this rate ([the architectures](../Readme.md)), and while it does, `timer_clocksource` names `tsc` as the clock source in sysfs, as Linux names it where the TSC is stable, which Linux's KVM selftests require of a host; otherwise it names the reference. The tick's interrupt only prompts the count: `timer_tick_clock` gives the tick handler the reference's whole ticks since the last it counted, one for an interrupt on time, none for one a hypervisor delivers again, and every tick that fell due for one that an emulator delayed or that a stretch with interrupts off left pending, at most a minute's each time. The first tick is taken to fall half a tick into the reference's, so an interrupt early or late by less than half a tick counts the one it was raised for. A tick of the PM timer is 3579.545 counts, so the count is kept in thousandths of a count, and no fraction is lost. The boot's log says which reference keeps the clock, as `clock: reference: the hpet`.

`timer_cycles_us` converts a cycle count at the calibrated invariant TSC rate without reading hardware, or returns zero before calibration or without such a rate.

`timer_now_us` and `timer_phase`, which `sys/clock.c` reads for the clocks, give the reference's ticks counted, the whole ticks it has gone past them and its place within the next, on every processor, within the tick's sequence count; no reading of `timer_now_us` on any processor is earlier than one given before. Before the first tick, and on a machine with no reference, they read the counter under the tick: the local APIC timer's count, or channel 0's latched count with the status bit that says which of mode 3's two sweeps it is in. A reading that finds the counter behind the last counts the period itself, so that the tick does not count it twice, and a stretch with interrupts off longer than a period loses the periods no reading fell inside.

### The other processors

`smpboot.c` starts the processors past the first for `smp_start` (`sys/proc/smp.c`). `platform_cpu_count` gives the boot processor and then the MADT's enabled processors in its order, up to the limit, and gives 1 alone when the local APIC's timer is not the tick, there is no reference counter, or the memory map does not give the trampoline's four pages at 0x8000 as available memory. A processor whose APIC identity is 255 or more is not started, since the xAPIC's messages do not reach it.

`platform_cpu_start` copies the architecture's `trampoline.s` to 0x8000 and fills the mailbox at its end with the boot processor's control registers, its EFER on x86-64, and the new processor's index, stack and entry. It sends INIT, waits 10 ms, sends a startup message for page 8, sends a second 200 microseconds later if the processor has not answered, and waits up to a second. A processor that does not reach its entry is sent INIT again, which keeps it waiting, so that it cannot start late on the next processor's mailbox. On x86-64 the trampoline enters long mode through a PML4 at 0x9000 that maps the kernel's upper half and the first 2 MiB by one executable page, since the direct map's pages are not executable; on i686 the kernel's page directory maps it. `x86_ap_entry` then writes the page attribute table, loads the processor's own descriptor tables, sets up its floating-point unit, enables its local APIC with the MADT's NMI inputs, starts its timer at the boot processor's counts, and calls the shared start. Before it says it has arrived, `tsc_cpu_setup` (`tsc.c`) sets its `IA32_TSC_AUX` to its index, which `rdtscp` and the vDSO's `getcpu` read; the boot processor sets its own in `vclock_start`. Then it and the boot processor, in `tsc_sync_target` and `tsc_sync_source`, read the TSC in turn under a lock for two ticks' worth of its counts, each reading compared with the last the other took, and the boot processor waits for the other to finish its turns. Each check is a round that `tsc_sync_open` begins before the processor's INIT: one word holds the round's processor and its flags, which each side sets by compare-and-exchange against its own round, so a processor left over from an earlier round changes nothing. Each side waits for the other at each step for at most 100 ticks by the TSC, not by `k_udelay`, so that the two never latch the 8254 at once; one that times out sets the round's abort flag, and the other leaves at its next look, so neither waits on a processor that has gone. The log says what each check found, as `smp: cpu1: tsc: synchronized with cpu0`, `behind cpu0 by N counts` or `not synchronized: the check timed out`; a processor behind or a check that timed out is recorded with the processor, and `tsc_synced` then keeps the vDSO's clock off the TSC.

### The floating-point state

`fpu_init` (`fpu.c`) chooses one format for every process at boot:

* XSAVE, where the processor has XSAVE and SSE and `rach2.noxsave` is absent. `XCR0` has x87 and SSE, AVX where the processor has it, AVX-512's three components where it has them all and AVX512F, and on x86-64 PKRU where it has protection keys, each while the image stays within `FPU_AREA_MAX`, 4096 bytes. With PKRU `fpu_cpu_setup` also sets CR4.PKE, which turns the keys on ([Protection keys](../../mm/Readme.md#protection-keys)); `fpu_pkru` and `fpu_pkru_set` read and write the running thread's PKRU with `rdpkru` and `wrpkru`, and the initial state holds `PKRU_INIT`, 0x55555554. `xsave` writes every enabled component, so the area is a whole image that a signal frame, ptrace and a core file copy as it is.
* `fxsave`, 512 bytes of the x87 and XMM registers and MXCSR, where the processor has FXSR.
* `fnsave`, the x87 state in 108 bytes, on i686 without FXSR or under `rach2.nofxsr`. `CR4.OSFXSR` is then clear, so an SSE instruction, whose registers would not be saved, is an invalid opcode.

x86-64 uses the 64-bit forms of the instructions. `fpu_cpu_setup` writes CR0, CR4 and `XCR0` for the format on each processor. The state is saved and loaded at every switch, so `CR0.TS` is never set, and a save area comes from the heap aligned to 64 bytes. `fpu.h` gives the layouts of the signal frame's state and of the register sets `NT_PRFPREG`, `NT_PRXFPREG` and `NT_X86_XSTATE`, as Linux has them on each architecture.

### The power controller and the stops

`board.c` finds the chipset's power-management registers at boot (`platform_board_init`, after the tick starts). A chipset is identified before anything is written to it, since a sleep word written at a wrong base reaches whatever decodes there, among the low ports the DMA controller, the interrupt controller, the timer and the reset register:

| Profile | Function | Vendor and device | Sleep type |
| --- | --- | --- | --- |
| `piix4` | 00:01.3 | 8086:7113 | 0 |
| `ich9` | 00:1f.0 | 8086:2918 | 0 |
| `lynxpoint` | 00:1f.0 | 8086:8C40 to 8C5F | 7 |
| `lynxpoint-lp` | 00:1f.0 | 8086:9C40 to 9C4F | 7 |
| `wildcatpoint-lp` | 00:1f.0 | 8086:9CC0 to 9CCF | 7 |

A chipset that matches a row is used only when its ACPI range decodes, its base register is not zero, and `PM1_CNT`, four bytes past the base, does not read all ones; otherwise the log gives the reason. Where `PM1_CNT`'s `SCI_EN` is clear and the profile has an SMI command, the profile's ACPI enable is written to port 0xB2 and `SCI_EN` is awaited, with a bound. With `SCI_EN` set, the SCI's line, 9 on the PIIX4 and the one register 0x44 selects on the others, is masked, and held masked once the I/O APIC takes the lines (`isr_line_hold`), since until a handler clears it a level-triggered line left asserted would be taken for ever. ACPICA's OS layer releases it when it installs its handler (`isr_line_release`, which routes it level-triggered); under `rach2.noacpica` or `rach2.nosci` it stays masked. When no row matches, the log gives the identity of 00:1f.0, so that a row can be added.

`power_stop` (`power.c`) shows records of level `INFO` on the screen again, turns interrupts off, stops the other processors, and does what it is given. A request is a write with no answer, so each is followed by a loop of a fixed count before the next is tried:

* `POWER_HALT` parks the processor in a loop of `cli; hlt`, since an NMI or an SMI wakes a halted processor.
* `POWER_OFF` first enters the soft-off state through ACPICA, where `power_prepare` ran the firmware's `\_PTS(5)` ([ACPI](../../acpi/Readme.md)). On a machine still running it writes `\_S5`'s sleep types with `SLP_EN`, when the FADT and `\_S5` were found: to the sleep control register on a hardware-reduced machine, and otherwise to PM1a and PM1b, once with `SLP_EN` clear and once with it set, as ACPI orders the writes. Where `SCI_EN` is clear, the FADT's ACPI enable goes to its SMI command port first. Then it writes the profile's sleep word to its `PM1_CNT`, where a profile passed its checks. Then it halts.
* `POWER_RESTART` writes the FADT's reset value to its reset register, where the FADT has one; 0xFB to port 0xB2, the reset command of an Insyde firmware's SMI handler, only when the SMBIOS vendor begins with `Insyde`, since on another firmware the byte reaches a handler written for something else; 0x02 and then 0x06 to port 0xCF9, the chipset's reset control; and 0xFE to the 8042's command port 0x64, once its input buffer is empty. The three fixed ports come in order of how much of the machine each resets. `rach2.resetskip=N` leaves out the first `N` of the first three, the FADT's register counted only where it exists. Then it halts.
* `power_emergency_restart`, which a panic calls with `panic=N` (`sys/panic.c`) and a restart calls with `reboot=` on the boot line, is the loop of Linux's `native_machine_emergency_restart` (`arch/x86/kernel/reboot.c`), with nothing shut down. From the method `reboot=` names, `a` by default: `a` writes the FADT's reset value to its reset register, in I/O space, memory or a bus-0 function's configuration space, where the FADT says it has one, and waits 15 ms (`acpi_reboot`, `drivers/acpi/reboot.c`); `k` waits for the 8042's input buffer to empty and writes 0xFE to port 0x64, ten times, 50 us either side of each, and goes back to `a` once when `a` came first; `e` and `b`, EFI's `ResetSystem` and the BIOS's restart, are logged and passed over, since the kernel calls neither; `p` writes port 0xCF9 twice, first with bit 1 and then with 0x0E, or 0x06 for a warm reset, over the register's other bits; `t` loads an empty IDT and raises a breakpoint, a triple fault; and the loop goes on to `k`, for ever. Linux tries 0xCF9 in its default order only once its PCI probe has found configuration mechanism 1 or 2 (`port_cf9_safe`, `arch/x86/pci/direct.c`), which every PC this kernel runs on has. The BIOS flag at 0x472 gets 0x1234 for a warm reset and 0 for a cold one first. Each method logs `reboot: emergency: METHOD` the first time it runs, `acpi: the fadt has no reset register` for an `a` with none. Linux's table of machines that need another method (`reboot_dmi_table`) is not kept; the Lenovo is not in it, and its FADT, revision 5, has a reset register, so Linux begins there too.

`kernel_shutdown` in `kernel.c`, which `reboot(2)` and the debug shell's `halt`, `poweroff` and `reboot` call, calls `power_prepare` first, while the caller may still sleep, then unmounts each file system on a disk, the root last, as [../../fs/Readme.md](../../fs/Readme.md) says and stops the USB and network cards before it calls `power_stop`.

### The devices

The PS/2 keyboard's handler (`ps2kbd.c`) reads a scancode of set 1 from port 0x60, on line 1, and gives it to the input layer. The keyboard's LEDs follow what the input layer wants (`input_leds`): at each tick, when they differ from what the keyboard shows and 50 ms have passed since the last LED command, `ps2kbd_tick` writes the command 0xED, and the handler takes the keyboard's ACK, 0xFA, or RESEND, 0xFE, before the byte reaches the input layer (`input_ps2_reply`), writing the LED byte after the command's ACK. Every byte is written only when the controller's input buffer is empty, never waiting, and again after a RESEND or 100 ms without an answer; after three writes the command is given up with a warning, and the next starts only when the LEDs wanted change. The 8042's waits and writes, which the keyboard and the mouse share, are in `i8042.c`; a wait of the status ends after 100,000 reads or half a second by the clock, Linux's bound, whichever comes first, since under a hypervisor each read is an exit and 100,000 of them took 42 s at the third level of nesting. The mouse's (`ps2mouse.c`) assembles the three-byte packets of the 8042's auxiliary port, on line 12. The bring-up asks first for a Kensington ThinkingMouse by psmouse's nine rates, and before it knocks for a wheel, for a Synaptics touchpad, as Linux's psmouse does; `synaptics.c` sets one up in absolute mode with Linux's queries and mode byte, registers its event device and takes its six-byte packets from the handler, and a pad whose setup fails goes back to relative mode and on as a mouse. Where no Synaptics pad answers, `alps.c` asks for an ALPS pad by its E6, E7 and EC reports, identifies its protocol, versions 1 to 8, as Linux's `alps.c` does, sets it up through the version's command mode, registers the pad's event device and a DualPoint's stick's, and takes the pad's packets of six or eight bytes, the stick's and those of a mouse on the pad's external port from the handler; a pad whose setup fails is reset and goes on as a mouse, and is not asked for Elantech's. Where neither answers, `elantech.c` knocks for an Elantech pad of hardware version 1 to 4, identifies it and its firmware by Linux's queries, writes its registers for absolute mode, registers the pad's event device and a pointing stick's before it, and takes the packets of each version from the handler, choosing a machine's quirks by the SMBIOS maker and product name as Linux chooses them by DMI; a pad whose setup fails is reset and goes on as a mouse. Where no touchpad answers, `ps2mouse.c` asks for a Genius NetMouse by its status after three 1:1 scalings, and `trackpoint.c` for a TrackPoint by its read-ID command, as Linux's psmouse does on any port, and sets one up on the port itself. The mouse is brought up after ACPICA, whose namespace gives the PS/2 mouse's PNP IDs (`sys/acpi/pnp.c`, `i8042_pnp_device`), by which `synaptics.c` applies Linux's quirks. A Synaptics pad's pass-through port is a line of its own (`struct ps2io`, `synaptics_pt`): a byte for the device behind it, the guest, goes sliced and ended by the rate 0x28, and each of the guest's comes back in a pass-through packet, so that `ps2mouse.c` probes the guest as Linux's psmouse probes a port of type SERIO_PS_PSTHRU and reports its packets, and `trackpoint.c` sets up a TrackPoint and gives its settings as files. After the bring-up the handler owns the port; a run of commands, a write to a stick's file or a reconnect, takes it back (`ps2mouse_cmd_begin`) and the handler leaves the bytes in the 8042 meanwhile, as Linux's PSMOUSE_CMD_MODE does; the packet under way is dropped as the run begins and ends, as Linux's `__psmouse_set_state` drops it. A wait of a driver's (`ps2mouse_msleep`) sleeps in kpsmoused and runs with interrupts on during the bring-up. The configured number (`resetafter`) of bad packets in a row, or an ALPS pad's bad bytes, or the announcement 0xAA 0x00 of a device that reset itself, stop the port until the kernel thread kpsmoused has reconnected it, as Linux's `serio_reconnect` does; a mouse keeps its event device when it speaks the same protocol after its reset. A pause of half a second inside any protocol's packet, or a packet's first byte after the port's `resync_time` idle, has kpsmoused resync the device instead (`ps2mouse_resync`): it is disabled, polled with 0xEB for a packet of its protocol's form and enabled, and reconnected when that fails, as Linux's `psmouse_resync` does. The ports' serio directories in sysfs have psmouse's files, `protocol`, `rate`, `resolution`, `resetafter` and `resync_time`, which `evdev_sysfs.c` makes from `ps2mouse.c`'s tables, and the files of the protocol beside them, a TrackPoint's settings, an Elantech pad's registers (`elantech_sysfs_add`) or a Synaptics pad's `disable_gesture` in relative mode (`synaptics_sysfs_add`), replaced at once when a write of `protocol` switches the port as Linux's `psmouse_attr_set_protocol` does; each write runs as a change (`ps2mouse_change_begin`), with the device disabled. Both ports accept Linux's whole protocol-name table as its kernel for the architecture has it, OLPC's HGPK on i686 alone; a detect not implemented, or a touchpad protocol on the pass-through port, resets the device and falls back to PS/2. `SynRelPS/2` sets a Synaptics pad up in its three-byte relative mode as Linux's `synaptics_init_relative` does, with the absolute mode byte less its absolute bit, the rate through the pad's own setter (`synaptics_set_rate`), the pad's buttons and model on a mouse's event device, and a reconnect that keeps the mode and the device. A reconnect retries absolute mode after a pad's failed setup. A protocol switch reserves its main event device before removing the old protocol; exhaustion leaves the old devices and protocol intact. Elantech's and a relative Synaptics pad's callbacks carry a generation; serio2's psmouse files compare the count of guests unbound, and a guest TrackPoint's settings the count of guest protocols replaced or unbound, with the one they saw on entry; each checks again after taking the command lock, so a callback that waited through a switch or a probe fails with `ENODEV`. serio2's psmouse files are its guest's driver files (`evdev_sysfs_serio_driver`), bound with the guest and kept across a switch of its protocol, as Linux's psmouse `dev_groups` are, so that a handle open on one stays good; the switch replaces only a TrackPoint's settings. serio2 lives as long as a Synaptics pad with a pass-through port, in either mode, made without a device below it (`evdev_sysfs_serio_add`), as Linux's serio core keeps a port whose driver went: a guest that goes, or fails its reconnect, takes only its event device and serio2's files, and a switch of serio1 away from the pad removes the port, its bus link and its callbacks. [input(4)](../../../../man/man4/input.4) says what each file does. [Terminals](../../tty/Readme.md) says what each reports. Status bit 5 says whose the waiting byte is, and each handler reads the data port only for its own device's byte, so that the keyboard's is left for line 1 and the mouse's for line 12. The 8042 keeps its line raised while a byte waits, and an I/O APIC input misses an edge that comes while it is masked, so once either handler is routed through the I/O APIC, `ps2_waiting` (`platform.c`) raises its vector once when that device's byte already waits. The terminals above them are in [terminals](../../tty/Readme.md).

COM1 (`serial.c`) is the 16550 at 0x3F8, found by its scratch register and set to 115200 baud, eight bits, no parity and one stop bit. A byte out is dropped after a bounded wait, so that a port that does not drain delays the kernel and does not stop it. Bytes in are taken on line 4 and at every tick into a ring, which [terminals](../../tty/Readme.md) describes with the rest of the receive path.

The speaker (`speaker.c`) is the 8254's channel 2 in mode 3, gated to the speaker by port 0x61 ([audio](../../audio/Readme.md)). The CMOS clock (`cmos.c`) is read at boot as two samples that must agree, and a clear valid bit in status register D ends the read, since reading the register can set the bit again; its device is [rtc(4)](../../../../man/man4/rtc.4).

### The reports and the rest

Both boot reports read and print and configure nothing. `platform_report` runs them after the firmware's tables are read and before the interrupt controllers start.

* `rach2.diag` (`diag.c`) prints the kernel's end, the free frames and each module's range, and identifies a Realtek 10ec:8168 by its `TxConfig` register, since the family shares one device ID. Before the first program it prints them again with the board, the network card, the disk policy and the entropy source, and waits for a key or a byte on COM1, for a machine whose only output is its screen.
* `rach2.apicdiag` (`apicdiag.c`) prints what the firmware left in the local APIC, and the MSI and MSI-X capabilities of the first xHCI and HDA controllers.

`cpuinfo_text` (`cpuinfo.c`) writes a processor's block of `/proc/cpuinfo` from `cpuid` on the processor that reads it, leaving out `xsaves` where `kcpu_xsaves_usable` (`xsaves.c`) finds Erratum 1386 unfixed, as Linux's `fix_erratum_1386`. `cpuinfo_place` cuts a processor's APIC ID into its package, its core and its thread at the widths `topology_widths` reads: the shifts of leaf 0xB's levels, and without them leaf 1's count of logical processors, divided into cores by leaf 4 on Intel and by leaves 0x80000008 and 0x8000001E on AMD. `cpuinfo_siblings` gives the processors started that share a core or a package, from which `/proc/cpuinfo` counts `siblings` and `cpu cores` and `procfs.c` writes `/sys/devices/system/cpu/cpuN/topology`. `cpuinfo_cache` describes a processor's caches as Linux's `cacheinfo.c` reads them, for `/sys/devices/system/cpu/cpuN/cache/indexM`: leaf 4 on Intel and every vendor but AMD and Hygon, leaf 0x8000001D on Hygon and on AMD when TOPOEXT is set, and otherwise AMD's leaves 0x80000005 and 0x80000006 put into leaf 4's layout, as `amd_cpuid4` puts them, with Linux's table of associativity codes applied to the L1's eight-bit count too. A cache's id is the APIC ID above the bits that number the processors sharing it; the processors sharing it are those whose APIC IDs agree above those bits, a run of that many APIC IDs for an L1 or L2 of leaf 0x8000001D, and on AMD's older leaves the package for the L3 and the processor alone for the rest. `debugreg.c` keeps each thread's debug registers, loads them when it runs, and moves a debug exception taken in kernel mode to the thread's return to user mode, as [ptrace](../../proc/ptrace.Readme.md) describes.

## Limits

* `acpi.c` reads only `\_S5` of the DSDT, and the kernel asks ACPICA for no `_PRT`: a device without MSI is served on the ISA line its interrupt line register gives, and one whose interrupt reaches only an I/O APIC input above 15 takes none.
* The local APIC is used in xAPIC mode alone, so a processor the firmware left in x2APIC mode runs on the 8259 pair, without messages, on one processor.
* Every line and every message goes to the boot processor.
* The ACPI record keeps 64 processors, 8 I/O APICs, 16 overrides, 8 NMI inputs and 8 NMI sources, 32 tables and 4 MCFG windows; the rest are counted and left out. A table longer than 4 MiB is not read.
* ECAM reaches segment 0 alone; other segments are not reached. On i686 no ACPI table, ECAM window or HPET above 4 GiB is used, and on both no loader pointer or framebuffer above 4 GiB.
* The tick is periodic at 1000 Hz on every processor; there is no one-shot or tickless mode.
* The reference counter is read in 32 bits, or 24 for the PM timer, and extended at each tick, so a stretch without a tick longer than its wrap, 4.7 s for the PM timer and 43 s for QEMU's 100 MHz HPET, loses the wraps. The time-stamp counter's rate is measured over 20 ms and is as good as that measurement. The calibrations are right under a stop of the processor shorter than the reference's wrap, and, against the 8254, when one of the three waits ran without a stop.
* Five chipsets have power profiles. The sleep type 7 and the ACPI enable 0xA0 of the Lynx Point and Wildcat Point rows are the PCH's encoding and the value their firmware publishes, and no emulator has those chipsets.
* The stops' waits are loop counts, not times.
* The serial console is COM1 alone, at 115200 baud; the PS/2 mouse speaks the plain, IntelliMouse, IntelliMouse Explorer, Kensington ThinkingMouse, Genius NetMouse or Cortron Trackball protocol, or the touchpad protocols of Synaptics, of ALPS, versions 1 to 8, and of Elantech, or a TrackPoint's, and no other vendor's, so an ALPS pad of version 9 or another vendor's touchpad works as a plain mouse; of Linux's Synaptics machine quirks only the Toshiba rate of 40 is taken, not the Cr-48's profile sensor; an Elantech register file reads the pad disabled where Linux reads it reporting; the speaker plays a square wave and no samples; of SMBIOS only the fields `/sys/class/dmi/id` shows are read, each string cut at 63 bytes.
* The CMOS clock's century is taken as 2000, and the FADT's century register is logged but not used.
* The extended state covers x87, SSE, AVX, AVX-512 and, on x86-64, PKRU alone, `XCR0` bits 0 to 2, 5 to 7 and 9. The i686 kernel turns no protection keys on, as Linux's 32-bit kernel does not.
* On the Lenovo an expiry of the TCO watchdog does not bring the machine back: under Linux 6.12, which programs the TCO as `itco.c` does and leaves SMI_EN's TCO_EN set on version 2, the first stage's expiry left the machine down until it was powered on by hand. No hang experiment may count on the watchdog to return it.

These suites boot the kernel ([the tests Readme](../../../../tests/Readme.md)):

* `tests/run fpu` boots with XSAVE, with `rach2.noxsave`, on a processor without XSAVE and, on i686, with `rach2.nofxsr`.
* `tests/run reset` restarts with `rach2.resetskip` 0, 1 and 2, and with QEMU's SMBIOS vendor set to Insyde.
* `tests/run panic` panics the kernel with `panic=5` and resets it by each method, `reboot=a` on `q35`, whose FADT has a reset register, `k`, `p` and `t`, by the default order on `pc`, whose FADT has none, and at once with `panic=-1`.
* `tests/run smp` boots one processor, four, and four with `maxcpus=2`, and raises an NMI on both of two.
* `tests/run clock` stops the machine's QEMU from the host thirty times in 30 s and requires its clocks to keep the host's time to within 250 ms, on x86-64 and once, under the site's accelerator.

* `tests/run uefi` boots by OVMF, through GRUB's multiboot2 loader under UEFI.
* `tests/run disk-q35` boots QEMU's `q35` machine, with its ICH9, MCFG and FADT reset register, and checks the disk alone.

No suite boots with `noapic`, `rach2.board`, `rach2.nosci`, `rach2.diag` or `rach2.apicdiag`.

# `io/`: `poll`, `select`, `epoll`, `eventfd`, `timerfd`, POSIX timers and `inotify`

The `io/` directory has the system calls that wait until one of several descriptors is ready, `poll`, `select` and `epoll` with their signal-mask forms, and four kinds of descriptor that refer to no file, whose readiness those calls report: an eventfd, a 64-bit counter; a timerfd, a timer read through a descriptor; an epoll set; and an inotify instance, a queue of changes to watched files. POSIX timers share the timerfd's timer. Every wait runs in `poll_wait`. The calls follow Linux's ABI on both architectures, for programs such as Dropbear, whose session loop waits in `select`.

### Inside the kernel

* `file_ops.poll` (`fs/file.h`) reports a backing's readiness: the requested `POLLIN` and `POLLOUT` that are true now, `POLLERR` and `POLLHUP` always, and the wait queue whose wake means the answer may have changed, or NULL. Without the method, `poll_fd` calls `socket_poll` for a network socket and `tty_poll` for the console, and reports a regular file, a directory, the framebuffer and the mouse ready at once. The rules of each backing are in [the ipc Readme](../ipc/Readme.md) for pipes, [the network Readme](../network/Readme.md) for sockets and poll(2) for the rest.
* A waker passes the kinds of change to `wq_wake`, `WQ_DATA`, `WQ_ROOM` or `WQ_HANGUP`, or all three through `wq_wake_all` for a close or a shutdown (`proc/wait_queue.h`). Each queue counts its wakes of each kind for edge-triggered epoll registrations; a wake of no kind is an edge for none.
* The timer interrupt calls `timerfd_tick` and the interrupt between ticks `timerfd_due` (`kernel.c`) and `sched_account_tick` calls `ptimer_cpu_tick` (`proc/sched.c`); exec (`syscall_proc.c`) calls `ptimer_exec`, signal code that discards signals (`sig_discard`) calls `ptimer_discard`, the exit of a thread (`proc/exit.c`) `ptimer_thread_exit`, and the exit of a process's last thread `ptimer_delete_all`. `syscall.c` has the clocks' part, `clock_now` and `clock_cpu_target`.
* The kernel uses an eventfd as Linux's eventfd_ctx (`eventfd.h`), for KVM's irqfd and ioeventfd and the drivers that follow: `eventfd_get` takes a reference from a descriptor of the caller's and `eventfd_put` drops it; `eventfd_signal` adds 1, from any context, an interrupt handler's among them; and a `struct eventfd_hook` added with `eventfd_hook_add` is told of each rise of the counter, with the counter's spinlock held, and may take the counter as a read would, and of the last close, after it has left the list. `eventfd_hook_remove` takes it off, says whether it was still on the list, and can take the counter with it; a holder that finds it gone leaves the record to the hangup the close has yet to run, since a hangup that sleeps lets other code run before the next hook's. A reference keeps the object after the last close, which detaches every hook; a hook added after that is told of the close at once.
* `struct anon_obj` (`anon.h`) begins the object of every `FD_TYPE_ANON` descriptor: the eventfd, epoll, timerfd and inotify objects, the signalfd (`syscall_proc.c`), a POSIX message queue descriptor (`ipc/mqueue.c`) and a namespace file (`proc/ns.c`). `/proc/PID/fd` prints its name after `anon_inode:`, or alone for a namespace file; a message queue's link is instead `/NAME`, the path of its file in the mqueue file system, with ` (deleted)` once `mq_unlink` has taken the name (`fs/procfs.c`).

## Design

### The wait

`poll_wait` runs a scan function, which fills an array with the wait queue of each object it looked at and returns the number ready. It allocates a waiter record (`struct wq_waiter`) for each queue from the heap, so entering a queue allocates nothing, and loops with interrupts disabled. It returns the count if an object is ready, `-EINTR` if a signal that is neither blocked nor ignored is pending, or 0 at the deadline; otherwise it puts a record on every queue, sets `wakeup_tick` for a finite timeout, marks itself blocked, and scans again; it sleeps only when that scan finds nothing ready and the same queues, and after a wake takes its records off and scans again. The records go on and come off under `poll_lock`, which `poll_let_go` takes to take another thread's records off, and each under its queue's own lock, taken after `poll_lock`. A wake from two of the thread's queues at once tests its state under the run queues' lock, so one of them makes it ready ([the wait queue](../proc/Readme.md)). A change of readiness before the second scan is seen by it, and one after finds the records and makes the thread ready, so none falls between the test and the sleep, as Linux's `poll_schedule_timeout` sleeps only after `poll_wait` has queued it (fs/select.c:233). An epoll set adds a queue for each descriptor it watches. A scan that finds more queues than the wait has records, with nothing ready, returns 1 with the number in `grow`, and the caller waits again with that many and the same deadline, which keeps a tick `deadline_passed` moved it to.

A deadline (`struct poll_deadline`) is a tick of the 1000 Hz timer and the end of the timeout by time since boot, the `CLOCK_MONOTONIC` reading at the call plus the timeout. `tick_deadline` ends a wait at the first tick at or after its end, counted from where in the tick in progress the call began (`rtc_tick_phase`), so without a lost tick a timeout ends at most a tick late; `deadline_reached` compares it with the 64-bit count (`tick_count`), which does not wrap. A zero timeout ends at that count itself, never at `rtc_tick_phase`'s, which counts a tick the timer has reached and not yet raised, since a deadline a tick ahead of the count would put a zero-timeout call to sleep until that tick, where Linux's returns at once. At that tick `deadline_passed` reads the clock. A tick the timer lost while the processor could not take it leaves the count behind the clock, which keeps its last reading (`rtc_monotonic`), and the deadline then moves to the tick at which the count reaches the end, so a timeout never ends early by the clock. A timeout of 2^40 seconds or more, which `tick_span` cuts, reaches its tick only after that span; its end by time since boot is still recorded, and an end past the largest second stops there, as Linux's does. `select` normalizes the whole seconds in its timeval's microsecond field before validating it and takes the timeout to the microsecond (`tv_deadline`). Each call converts its own timeout and saturates at the limit its manual page gives; on x86-64 `ppoll` and `pselect6` compare their 64-bit seconds with the limit before they narrow them. A wait a signal ends restarts as Linux's does ([signals](../proc/signal.Readme.md)): `poll` files its descriptors and deadline in the restart block (`poll_restart`) and resumes through `restart_syscall` when no handler runs, to its first deadline; `ppoll`, `select`, `_newselect` and `pselect6` end as `ERESTARTNOHAND` and, on every return from a wait with a timeout, write the time left back to the caller's timeout (`poll_finish`), unless the persona has `STICKY_TIMEOUTS` or the copy fails, when an interrupted call returns `EINTR` and is not restarted; the epoll waits are never restarted (`syscall_restartable` in `syscall.c`). `poll_mask_set` installs the mask of `ppoll`, `pselect6`, `epoll_pwait` and `epoll_pwait2`; `poll_mask_done` restores the old one, or, when a signal ended the wait, signal delivery restores it after the handler.

### `poll` and `select`

`poll_scan` sets `revents` to 0 for a negative descriptor and to `POLLNVAL` for one that is not open or was opened with `O_PATH`, and counts the second as ready. It polls any other for its events and `POLLERR` and `POLLHUP`, and masks the answer to those and `POLLNVAL`. `poll` takes at most `FD_TABLE_LIMIT` (1024) entries, or the caller's soft `RLIMIT_NOFILE` when that is higher; Linux takes no more than the limit, but OpenSSH's rlimit sandbox polls under a limit of 0.

`select` is `poll` over a translated array. The i386 wrappers on x86-64 keep the caller's timeout unchanged when the native handler refuses the timeout or signal mask before the wait (`select_left_out` in `arch/x86_64/ia32_fs.c`). `select_common` cuts `nfds` to the caller's table, past which no descriptor is open, but to no fewer than a long's bits, as wide as Linux's table always is, so that a bit for an unopened descriptor in the first long is `EBADF`, as on Linux, and not ignored; it reads and writes the longs that hold the sets' first `nfds` bits, no more, as Linux does, so a program that raised its limit selects a descriptor past `FD_SETSIZE` with sets as wide as it needs; the sets come from the heap. `poll_select.c` turns the three sets into one `pollfd` per selected descriptor, with `POLLIN`, `POLLOUT` and `POLLPRI` for the sets it was in, and writes each result back into those sets alone: `POLLIN`, `POLLHUP` or `POLLERR` as readable, `POLLOUT` or `POLLERR` as writable, `POLLPRI` as exceptional. The scan counts a descriptor ready by the same rule (`pollfd_select_ready`). By `poll`'s rule, a descriptor selected only for writing that reports `POLLHUP` would end the wait with every set empty, and a program that calls `select` in a loop would spin. `poll_select.c` calls no other kernel code, so the host test compiles it unchanged.

### `epoll`

A set (`struct epoll`) has a list of registrations (`struct epitem`), its own wait queue, and `holders`, the registrations of the set in other sets. A registration keeps the number it was added by, the open file description that number had and the description's serial number, which tells it from a later description at the same address, the events, the data word, and the state of its reports (`off`, `seen`, `at`, `wakes`).

A wait (`epoll_wait_common`) runs `poll_wait` with `scan_set`, which polls each registration through the caller's descriptor at its number for its events and `EPOLLERR` and `EPOLLHUP` (`item_ready`, `target_poll`). When that descriptor is another description, or none, the registration reports nothing, and the scan frees it once its description is closed in every process (`fd_ofd_live`); a registration of a set lasts until the set's last close. The scan uses the caller's descriptors alone because the wait sleeps on the queues of what it polled, and only they keep those objects open while it sleeps; a close or `dup2` of one by another thread sharing the table takes the wait off all those queues and releases the descriptor at once, as on Linux, whose epoll holds no reference to what it watches ([the descriptor tables](../fs/Readme.md)). A registration that reports is taken at once: its report state changes and it moves to the end of the list, so waits with room for fewer events than are ready report the ready descriptors in turn, and a second waiter does not report an edge-triggered or one-shot event again. The copy to the caller follows the wait, since it can sleep in a page fault; an event that cannot be copied goes back to its registration (`untook`).

An edge-triggered registration is reported when an event is ready that was not at its last report or that a scan has found gone since, or when its descriptor's queue has counted a wake of a kind its events watch since that report (`kinds_of`): data for the input events, room for the output events, and a hangup always. A pipe drained and filled again between two waits is as ready as before, and its count of data wakes shows the edge; data that comes to a socket watched for output alone is no edge, as in Linux. `EPOLL_CTL_ADD` and `EPOLL_CTL_MOD` give a registration a new id and clear its report state.

Sets nest. `set_ready` reports whether a wait on a set would report an event, taking none, and adds the queues of the set and of what it watches to the wait's; `poll` and `select` use it too (`epoll_poll_set`). The set's count of wakes (`sig`) sums its own queue's and those its registrations watch, so a registration of a set sees a change anywhere inside it. A scan looks into each set once (`scan_marks`), which ends a cycle, and at most `EP_MAX_NESTS` (4) sets deep, which bounds the kernel stack a scan uses. `EPOLL_CTL_ADD` of a set fails with `ELOOP` when it would make a cycle or a chain of more than five sets (`nests_badly`), counted through every registration that lasts, whichever process made it, since a fork's child that closed a number shares the sets with its parent. A set's last close (`epoll_close`) frees its registrations and those of it in other sets.

### `eventfd`

An eventfd is a 64-bit counter and a wait queue. A read takes the value, the whole counter or 1 with `EFD_SEMAPHORE`, and wakes the writers before it copies the value to the caller, so a second reader during a copy that sleeps in a page fault finds it gone; a failed copy loses the value, as in Linux. A read wakes the queue for room, and a write of a nonzero value for data. The counter's spinlock covers each change of the counter and the list of hooks, since a kernel signal can come from an interrupt handler; a read or a write that finds the counter changed between its wait and the lock waits again. `sys_read` sends a zero-byte read of an anonymous descriptor to its read method (`syscall_fs.c`), so a zero-byte read of an eventfd or a timerfd fails with `EINVAL`, as a short one does.

### Timers

`struct ktimer` is the timer of a timerfd and of a POSIX timer. An armed timer is on `armed`, which `timerfd_tick` walks at each tick and `timerfd_due` at each interrupt between ticks, or, on a clock of processor time, on `cpu_armed`, which `ptimer_cpu_tick` walks. A timerfd last set with `TFD_TIMER_ABSTIME` and `TFD_TIMER_CANCEL_ON_SET` on `CLOCK_REALTIME` is on `cancelable`, as on Linux's cancel_list. `timer_lock`, a spinlock taken with interrupts off, by the tick without the big lock and by a system call after it, and before the clock's own lock, covers the three lists, each timer's count, arming and cancellation, each process's list of POSIX timers and the list of timers whose signal is due.

A timer of the clocks keeps its time, `end`, in nanoseconds on its clock, `base`, and its interval, `ins`, in nanoseconds, as Linux's timerfd_setup keeps them; a relative timer of `CLOCK_REALTIME` is based on `CLOCK_MONOTONIC`, as Linux's hrtimer bases one, and a relative time or an interval past `TIME_MAX` seconds (4294967295, about 136 years) is taken as that. `due` is the first tick at or after `end`, which `rtc_tick_phase` places within the tick in progress, as a sleep ends, and which `timerfd_tick` compares with the count. The clock and the tick are read together with interrupts off under `timer_lock` (`read_now`), so that no tick comes between them and the time to `end` counts from the tick it is added to. At that tick the timer reads its clock: short of `end`, as when the clock runs ahead of the tick count, it only moves `due` on, as `deadline_passed` in poll.c does, so it never expires early. A timer has the timer's interrupt between ticks armed for its `end` however far it is (`arm_between`), as Linux starts an hrtimer when it is set, at `end` itself on the monotonic clock and at `end` less the real-time clock's offset (`rtc_offset`) on `CLOCK_REALTIME`, as Linux programs an hrtimer at its expiry less its base's offset, so that no time passed between the reading and the arming is added: `set_due` arms it when the timer is set or moved on, and `timerfd_tick` again at each tick, since a processor keeps only the earliest time asked of it. That interrupt calls `timerfd_due`, which compares each such timer's `end` with one reading of its base's clock for the pass, as Linux's hrtimer interrupt compares every timer with one reading, so the timer expires at its time, as Linux's hrtimer does, and a timer whose time is still to come is armed again. `timerfd_tick` likewise reads each base's clock once for its pass. Each pass expires the timers it finds due in the order Linux runs them, `CLOCK_MONOTONIC`'s, then `CLOCK_REALTIME`'s, then `CLOCK_BOOTTIME`'s, each base's earliest end first (`expires_first`), as __hrtimer_run_queues does (kernel/time/hrtimer.c:71-87, 1791-1811), so that POSIX timers' signals are posted, or wait, in the order the timers expired. A reader's wake is late by the time since `end` or since `end` was last counted (`set_at`), whichever is later, so that a timer set to a time past, or passed by a step of the clock, counts only the time since; the clock is read for it at the wake, not taken from the pass's reading, which the timers before it in the pass share. A POSIX timer is armed between ticks only while `between` says: when set, unless it is `SIGEV_NONE`'s, as Linux never starts that hrtimer; again at an expiration that sets its signal pending; and again once that signal is taken (`ptimer_rearm`, from the signal's dequeue), as Linux's posixtimer_rearm restarts a timer at the delivery of its signal, with `end` moved past the clock, as posixtimer_rearm forwards the timer. An expiration while the timer's signal is pending clears it, and the ticks alone then count the timer, so a short interval cannot raise interrupt after interrupt between ticks. An expiration whose signal the process ignores clears it only for an interval under a tick, as Linux restarts an ignored timer at once and moves it a tick on only when its interval is shorter. An expiration that waits for another sender's pending signal of the same number clears it too, and the dequeue of that signal posts the waiting expirations and sets it again when that sets the timer's signal pending, since Linux queues a signal for each timer and restarts each at its own. `timer_gettime` of a periodic timer the ticks alone count first expires it against its clock (`expire`), counting the intervals in `set_count`, so its time left is never one passed, as Linux's common_timer_get forwards such a timer; the time left counts from the same reading, as common_timer_get counts both from one `now`, and `timerfd_gettime` likewise counts it from the reading `timerfd_forward` moved the timer by. Past `end`, it counts its expiration and wakes its readers, each reader's wake record begun under the run queues' lock, taken after the queue's, so that a wake from elsewhere does not overwrite it; or, for a POSIX timer, it joins the list of timers whose signal is due (`ptimer_fire_later`), once however many expirations come meanwhile, since a pass runs without the big lock and a signal is posted under it, and is left to the ticks until then. The interrupt between ticks, which runs without the big lock, posts them at once when a try takes it, and otherwise leaves them to a tick; a tick's locked part, or a later tick that takes the lock, posts the tick's (`ptimer_post_due`, `timer_lock_take` in `kernel.c`), as Linux posts a timer's signal from its callback (kernel/time/posix-timers.c:318-377). A `timer_settime` or a `timer_delete` posts one still due before it changes the timer (`ptimer_post_one`), as Linux sent it at expiry, whether its expiration is the setting's first or one after the setting's last signal was taken, and drops the expirations that joined it, since Linux stops the timer once its signal is queued (kernel/time/posix-timers.c:318-377); exec drops it with the timer. A one-shot timer is disarmed. A periodic POSIX timer also counts every interval that has ended since, as Linux's hrtimer_forward does, and moves `end` on by as many intervals. A periodic timerfd stops at its expiry instead, armed but off the list with `due` at its largest and `expired` set, as Linux's timerfd_tmrproc returns HRTIMER_NORESTART (fs/timerfd.c:58-80); a read that takes the count, `timerfd_gettime`, or a setting starts it again, and the first two move `end` on past the clock as it reads then and add the intervals moved less one to the count (`timerfd_forward`), as Linux's hrtimer_forward_now and hrtimer_restart do (fs/timerfd.c:292-313, 552-565). After a step of the clock back before `end`, nothing moves and the count loses the expiration, as in Linux, so the timer is due again at the time it stopped at; a read left with no count then returns `EAGAIN`, or 0 when it blocks, as Linux's does. `timerfd_gettime` reports both to the nanosecond. The kernel has no 64-bit division of its own, so `div64` divides by shifts. A timer of processor time keeps whole seconds and ticks below a second and counts down the ticks charged to it. A read takes the count under the lock before the copy, so an expiration during the copy is kept for the next read.

A step of the real-time clock, a setting (`rtc_set_realtime`, `rtc_shift_realtime`) or a leap second (`rtc_seconds`), calls `timerfd_clock_was_set`, as Linux's clock_was_set calls timerfd_clock_was_set. It counts `due` again for each armed timer whose `base` is `CLOCK_REALTIME`, an absolute one, from one reading of the clock as it now is, and arms its `end` between ticks again, so a step forward past `end` expires it at once and a step back keeps it waiting; and it marks canceled and `stepped`, and wakes the readers of, each timerfd on `cancelable` that is canceled already or whose recorded offset of real time, `moffs_sec` and `moffs_nsec`, is not `rtc_offset`'s now. The offset is recorded when the timerfd is made and when a read or a setting reports it canceled, as Linux's `moffs` (fs/timerfd.c:97-116, 151-157, 449), so a setting refused, or an `ADJ_SETOFFSET` of zero, which leaves the offset, cancels none, and counts no step (`rtc_step_count`). A slew is no step: `clock.c` slews the tick count and real time together, so a timer's tick holds, and Linux does not count adjtimex's `ADJ_OFFSET` and `ADJ_OFFSET_SINGLESHOT` as settings (kernel/time/ntp.c:754-755, kernel/time/timekeeping.c:2490-2532), so that an NTP daemon's corrections cancel nothing. A timerfd is readable while it has a count or is `stepped`, as Linux's `ticks` counts expirations and steps, and every read or setting clears `stepped`, so a canceled timerfd set to disarmed polls unreadable and a blocking read waits for the next step, as in Linux. A read of a canceled timerfd that has something to read, or that does not block, drops the count and fails with `ECANCELED`; a periodic timer runs on, unless it is `expired`, which an expiration sets and a read, a setting or `timerfd_gettime` clears, as Linux's timer stays stopped at its expiry until one of them starts it, and then it is disarmed. The next arming setting of a canceled timerfd arms it and fails with `ECANCELED`, as Linux's timerfd_canceled answers both. A disarmed timerfd keeps the interval of its last setting, which `timerfd_gettime` reports, as Linux keeps `tintv`.

A process's POSIX timers are on `timers` in `struct tgroup`, by id from 0, at most `PTIMER_MAX` (64) with those on `timers_gone`, below. `timer_create` stores the id in the caller's memory before it lists the timer, since the store can sleep in a page fault and the lock cannot be kept across it. A timer on a clock of processor time keeps a reference to the process it counts (`clock_cpu_target`), and its `due` is the ticks left, of which each tick charged to that process or thread takes one. `ptimer_fire` posts the signal with `SI_TIMER`, the timer's id, its value and its overrun where Linux's siginfo has them. The signal is posted with an overrun of 0, as Linux's send_sigqueue queues the timer's sigqueue (kernel/signal.c:2038-2043). Every expiration of the setting in force from the first one the notification stands for, while it waits for another sender's signal and while it is pending, counts in `set_count`, Linux's it_overrun plus one, those `expire` counted as it posted the signal among them; when a periodic timer's signal of that setting is taken (`ptimer_rearm`), the dequeue forwards the timer past the clock, adds the intervals to `set_count`, and adds `set_count` less one, the expiration the signal stands for, to the signal's overrun, as Linux's posixtimer_rearm forwards the timer at delivery and adds it_overrun to si_overrun (kernel/time/posix-timers.c:237-242, 258-279). `set_count` less one alone, without what the signal's overrun carried while it was queued, becomes `overrun`, which `timer_getoverrun` reports, as it_overrun_last, which timer_overrun_to_int adds to si_overrun (kernel/time/posix-timers.c:237-242, 270-274); a setting makes both 0, as posix_timer_set_common resets it_overrun and it_overrun_last (kernel/time/posix-timers.c:881-882), so the intervals of a setting that a later setting or a deletion ended are never delivered, as on Linux, where the timer stops while its signal is queued and only a delivery under its setting forwards it. The signal's own overrun is what Linux's si_overrun holds while the sigqueue is queued: one for each later setting whose first expiration found it still pending, which then makes the signal that setting's (kernel/signal.c:2034-2042), so a signal left pending across a setting reports more in si_overrun than timer_getoverrun gives. Each timer has a `key` of its own from `next_gen`, which its signal carries in the siginfo's `timer_key`, and only a pending signal that bears it is the timer's own: not one a deleted timer of the same id left pending, nor a user's with `SI_TIMER`, whose `timer_key` is 0. While another sender's signal of the same number is pending, the timer's notification waits in `count`, as its overrun plus one, with the setting it is of in `count_gen`, which the signal carries when posted, and the time it began to wait in `wait_seq`; when that signal is taken, the waiting notifications are posted oldest first (`post_waiting`), a one-shot timer's among them and live and deleted timers' alike, as Linux queues each timer's sigqueue apart from other senders' and collect_signal delivers the first queued (kernel/signal.c:566-582, 2038-2043), so that no later expiration overtakes one. A setting keeps a waiting notification, as the timer's sigqueue stays queued across posix_timer_set_common (kernel/time/posix-timers.c:879). `timer_delete` keeps a deleted timer whose notification waits on the process's `timers_gone` until it is posted, as sigqueue_free leaves a queued sigqueue to be delivered (kernel/signal.c:1961-1984); its signal then forwards nothing, as Linux's collect_signal rearms no sigqueue that has lost SIGQUEUE_PREALLOC (kernel/signal.c:589-593). Such a record counts against `PTIMER_MAX` until it is let go, as the queued sigqueue counts against RLIMIT_SIGPENDING (kernel/signal.c:428, 1956-1959). A signal discarded by a disposition that ignores it, or by a stop or SIGCONT that cancels the other, takes the timers' waiting notifications of its number with it and frees the deleted timers' records (`ptimer_discard`), as flush_sigqueue_mask takes every sigqueue of the number off the queues and frees a deleted timer's (kernel/signal.c:444-452, 782-798, 915-931, 4249-4255); a stop or SIGCONT that a timer posts does this under `timer_lock`, which the posting processor holds (`fire_cpu`), and the records are freed as the poster lets the lock go (`gone_later`, `timer_unlock`), not at a later dequeue that may never come. An ignored signal that a blocking wait drops once the wait's mask unblocks it (`signal_pending`) is taken as a delivery takes it, through `ptimer_rearm`, which forwards its timer, starts `set_count` again and posts the notifications that waited for it, as get_signal dequeues each ignored signal before it drops it (kernel/signal.c:686-699, 2821, 2838-2839). The end of a thread drops the notifications of the `SIGEV_THREAD_ID` timers aimed at it, its pending timer signal or one waiting there, with their `set_count`, and frees a deleted timer's record whose notification goes (`ptimer_thread_exit`), as __exit_signal flushes the thread's queue (kernel/exit.c:207, kernel/signal.c:455-465). A live timer whose signal is discarded goes on expiring, where Linux 6.12.115 leaves a periodic one stopped, since its posix_timer_fn waits for the delivery to restart it (kernel/time/posix-timers.c:258-279, 318-321). Exec deletes every timer and deleted record and discards the signals of `SI_TIMER` pending for the thread and the process, keeping other senders' (`ptimer_exec`), as Linux's posixtimer_exec calls exit_itimers and flush_itimer_signals (fs/exec.c:1220-1229, kernel/signal.c:483-516); the end of the process lets all of them go (`ptimer_delete_all`). Every setting of a POSIX timer takes a new generation, `gen`, from a counter of all settings that never gives 0 (`next_gen`), and the signal carries it in the siginfo's `timer_gen`, which no user reads or writes: a dequeue forwards a timer only for a signal of its setting in force, as Linux's posixtimer_rearm compares si_sys_private with it_requeue_pending, which posix_timer_set_common moves on (kernel/time/posix-timers.c:267, 879), so a signal left pending across a setting, or by a deleted timer whose id a new one took, or sent by a user with `SI_TIMER`, moves no timer. The dequeue keeps interrupts off from taking the signal through `ptimer_rearm` and then clears `timer_gen` and `timer_key`, as dequeue_signal clears si_sys_private (kernel/signal.c:682-699), so no tick posts the timer's signal between the two and a signal put back is not counted twice.

### `inotify`

An instance (`struct inotify`) has a queue of events and a wait queue. Every watch of the machine is on one list (`watches`) and is found by the base mount of its file system (`vfs_mount_base`) and the inode number, a key an open file description has too, so no hook needs a path. `inotify_watches` counts the watches, and every path to a hook tests it first, so a machine with no watch pays one comparison per call. Each base mount counts the watches on its file system too (`inotify_watched`, kept by `vfs_mount_watches`), and the descriptor calls test that word for the description's file (`inotify_mount_watched`), as Linux's `fsnotify_sb_has_watchers` tests a superblock before any event (include/linux/fsnotify.h:34-37, 81): a read, an open or a last close of a file on a file system with no watch takes no big lock for inotify and records no name, though another file system has watches. `fs/vfs.c` reports what its namespace operations and `vfs_setattr` change (`inotify_child`, `inotify_file`, `inotify_gone`), and the descriptor calls in `syscall_fs.c` and `fs/fd.c` report reads, writes, truncations, opens and last closes through the open file description (`inotify_desc`). While a watch is on the file's file system, `open_done` records in the description the directory and last component of the name it was opened by (`open_record_parent`), so the directory's watches hear of those events under that name. The calls that change attributes, `chmod`, `chown` and `utimensat` in each form, tell the directory's watches themselves, since `vfs_setattr` has no name: through a path, `attr_told` finds the directory and the last component again (`named_parent`) and reports to it when that component is still the file; through a descriptor, `attr_told_desc` uses what the open recorded. A chown that names an owner or a group is `IN_ATTRIB` even when the file has them already, as on Linux. On the KRFFS boot root, whose changes do not pass through `vfs_setattr`, the same two tell the file's own watches as well.

`queue_event` drops an event equal to the last unread one, as Linux merges it. Past `inotify_max_queued_events` (16384), or when the heap has no room, it queues the one `IN_Q_OVERFLOW` record kept in the instance, so the overflow needs no memory. A read takes each record off the queue before it copies it. An unmount gives each watch on the mount `IN_UNMOUNT` and `IN_IGNORED` and frees it (`inotify_unmount`), since a watch keeps no reference to its mount. A user may have `inotify_max_user_instances` (128) instances and `inotify_max_user_watches` (8192) watches. The three limits start at Linux's defaults and are the files of `/proc/sys/fs/inotify`, which a privileged write sets; each is read where it applies, so a lower value refuses the next instance, watch or event and takes nothing away.

## Limits

* No backing reports `POLLPRI`, so a wait for it alone ends only at its timeout or a signal.
* An epoll wait reports a registration only while the caller's descriptor at its number is the registered description.
* `EPOLLEXCLUSIVE` changes nothing: a wake wakes every waiter on a queue.
* A node of `/dev` or `/proc` can be watched with inotify and reports nothing.

## Tests

`tests/run host` compiles `poll_select_hosttest.c`, `poll_deadline_hosttest.c`, `epoll_hosttest.c`, `eventfd_hosttest.c`, `timerfd_hosttest.c` and `wait_queue_hosttest.c` from `tests/host/` natively under AddressSanitizer and UndefinedBehaviorSanitizer. [The host tests' Readme](../../../tests/host/Readme.md) gives their rows.

`tests/run default`, in the core tier, runs these on both architectures:

* `tests/pollprobe.c`: `poll` and `select` over pipes: a timeout, `POLLIN`, `POLLHUP`, `_newselect`, a child's write waking a poller, `select`'s errors, on x86-64 a `ppoll` of 2^32 seconds, and the console.
* `tests/musl/pselectmusl.c`: `pselect6`'s three sets, a timeout, its errors, and its signal mask: a pending signal the mask unblocks ends the wait and its handler runs under the mask, a signal the mask blocks stays pending, a signal sent while the call sleeps ends it, and the mask before the call is back after each.
* `tests/musl/epollmusl.c`: the eventfd counter; epoll's level-triggered, edge-triggered and one-shot reports, nesting and `ELOOP`, a fork's child that closed a nested set's number, reports in turn, an event a wait could not store, and the edges of AF_UNIX, pipe, UDP, TCP and pseudoterminal wakes.
* `tests/musl/timerfdmusl.c`: reads, intervals, a disarmed timer, an absolute time already past, a timer waking an epoll wait, and settings of 200 days.
* `tests/musl/inotifymusl.c`: the events of a watched directory and a watched file through a file's life, reads, `FIONREAD`, `poll`, and the errors and flags of the watch calls.
* `tests/musl/callsmusl.c`: a POSIX timer's signal and overrun, a deleted id, and timers on clocks of processor time.

The `packet`, `raw`, `netif` and `dhcp` suites poll sockets. `tests/musl/pollmusl.c` is staged as `/musl/pollmusl` for a person to run; no suite runs it.

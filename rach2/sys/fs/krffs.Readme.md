# KRFFS in the kernel

KRFFS, the K&R first-fit file system, is the project's own file system and the root a Rach2 machine boots. An image is one region of bytes holding a ring of nodes, allocated first fit after the storage allocator of The C Programming Language, small enough for a reader to follow whole. `krffs.c` is the format and its operations, written once over a backend; `krffsmount.c` is the type `mount(2)` places on a block device; the adapter `krffs_ops` in `vfs.c` puts the boot root on the VFS ([vfs.Readme.md](vfs.Readme.md)). The host tools in [krffs/](../../../krffs/Readme.md) build, read and repair the same images, and their `fsck.krffs` judges what the kernel writes. This document is the one description of the format.

## Interfaces

* `mount(2)` with type `krffs` places a volume on a partition window, a whole disk or an attached loop device ([mount.2](../../../man/man2/mount.2), [vfs.Readme.md](vfs.Readme.md)).
* The boot root is the Multiboot module in place, the module through the page-cache window (`rach2.fswindow`), or a partition of disk 0 through the window (`rach2.fsdisk` or `rach2.root=disk`), as [../../Readme.md](../../Readme.md) describes.
* [statfs.2](../../../man/man2/statfs.2) gives what `statfs(2)` reports, and [rename.2](../../../man/man2/rename.2), [link.2](../../../man/man2/link.2) and [symlink.2](../../../man/man2/symlink.2) how a directory rename, a hard link and a symbolic link are refused.
* Kernel log records: `krffs: mount: refused: REASON`; `krffs: check: repaired: N backward link(s), N orphan(s), N repeated name(s)`; `krffs: check: repaired: N file(s) put back in a directory`; `krffs: check: left unfinished; run fsck.krffs`; `krffs: mount: a check is owed and this mount is read-only`; `krffs: unmount: backward link repair owed`; `krffs: unmount: a check is owed`; `krffs: refused: a field at N would reach the medium in two pieces`; and, for a disk root, `krffs: not cleanly unmounted last time; run fsck.krffs`.
* `krffs.h` has the offset interface, the `krffs_*_at` functions on a `krffs_mount_t`, and the boot root's pointer interface.

## Design

### The format

An image is a region of bytes addressed by offset from its first byte, and records no size of its own. The region is a ring of nodes that tiles it: every byte belongs to one node, and free space is free nodes in the ring, with no list beside it. A node is a packed header of 357 bytes, `krffs_node_t`, followed by its data. The fields are little-endian:

| Offset | Bytes | Field | Contents |
| --- | --- | --- | --- |
| 0 | 2 | `magic` | `0x4B52`, "KR" |
| 2 | 1 | `type` | 0 root, 1 free, 2 reserved |
| 3 | 8 | `id` | the node's identifier |
| 11 | 256 | `name` | one path component, ending in NUL within the field |
| 267 | 2 | `mode` | type, set-id, sticky and permission bits |
| 269 | 4 | `uid` | owner |
| 273 | 4 | `gid` | group |
| 277 | 16 | `access_time` | seconds and nanoseconds, signed 8 bytes each |
| 293 | 16 | `modification_time` | the same |
| 309 | 16 | `attribute_change_time` | the same |
| 325 | 8 | `size` | the node's whole size in bytes, header included |
| 333 | 8 | `previous_node_size` | the size of the node before it |
| 341 | 8 | `data_size` | the bytes of data in use |
| 349 | 8 | `parent_id` | the identifier of the directory the node is in |

The node at offset 0 is the root, which is also the root directory. Walking forward adds a node's `size` to its offset, and the walk past the last node wraps to offset 0, which makes the nodes a ring; walking backward subtracts `previous_node_size`, and the root's is the size of the last node. A reserved node is a file, a directory, a FIFO or a socket file. A free node may keep the name and `data_size` of what was removed there; only its type says it is free.

The type bits of `mode` say what a reserved node is: `S_IFDIR` (0040000) a directory, `S_IFIFO` (0010000) a FIFO and `S_IFSOCK` (0140000) a socket file, the last two with no data, and no type bits a regular file. A reader compares the whole field, `mode & 0170000`, since a socket's bits include the directory's. There is no device node, because the header has no field for a device number. The root's stored mode is 0755 with no type bits, and its bit 04000 is the dirty flag (`KRFFS_MODE_DIRTY`), so the kernel answers for the root by its position and never by its mode.

A node is found by its directory and its one-component name: `parent_id` is its directory's identifier, 0 (`KRFFS_ROOT_ID`) for the root directory whatever the root's own `id` field has, and two nodes of one directory do not share a name. A directory's `id` is `krffs_mix_hash`, a mix in the style of FNV-1a that is never 0, of its parent's identifier and the DJB hash of its name (`h = h * 33 ^ c` from 5381, in 64 bits), and its children have it in their `parent_id`; that is why a directory is never renamed or moved. Two names can have one DJB hash (`bC` and `cb` do), so `mkdir` refuses a directory whose identifier another directory has (`KRFFS_ETAKEN`, reported as `EINVAL`), which would share its children. A regular file's `id` is the DJB hash of its name alone, which the kernel writes when it creates or renames the file and the host stager writes too; files of one name share it, and nothing looks a file up by it. A parent lookup matches only reserved directories with a name, so a file, FIFO or socket with the same identifier, or a directory a failed `mkdir` left without a name, cannot replace a directory in `..` or a reconstructed path.

On the boot root a node's inode number is `krffs_node_ino`: 1 for the root, a directory's `id`, and for any other node the mix of its `parent_id` and its `id`, each folded to 32 bits, its two halves exclusive-ored, and kept off 0 and 1. It stays when the node's bytes move or its name is removed, two files of one directory whose names have one hash share it, and so may two nodes whose identifiers fold alike. It fits 32 bits, as ext4's and tmpfs's numbers do on Linux by default, so that an i386 program's `stat` and `getdents` on the x86-64 kernel, which fail with `EOVERFLOW` for a wider number, read every file. On a volume it is the node's offset plus one, which changes when the node moves. Advisory locks find a file by its node, not by this number ([lock.Readme.md](lock.Readme.md)).

A creation stamps all three times; a write or a truncation the modification and change times; a change of mode, owner or times the change time; and making, removing or renaming an entry its directory's modification and change times. Only `utimensat` changes the access time, since a stamp on every read would make reading a write.

### What a mount requires

`krffs_chain_walk` refuses the ring unless every node has the magic number and a known type, a size of at least one header that stays inside the region, a `data_size` that fits inside it (a free node excepted), and, if reserved, a name that ends within its field, and unless the walk ends exactly at the region's end. The full check (`krffs_chain_is_valid`) also requires each backward link to be the size of the node before it. Every walk is bounded by the most nodes the region can hold, so a damaged ring cannot loop.

* The boot root requires the magic number and the root type at offset 0 and the full check. A dirty disk root (`init_krffs_disk_root`) that passes the forward walk can rebuild stale or torn backward links, and has its repeated names resolved, before mounting.
* A volume (`krffs_volume_mount`) is refused when smaller than two headers (`EINVAL`) or of 4 GiB or more (`EFBIG`), and requires the magic number and the root type (`EINVAL`, or `EIO` when the first node cannot be read) and a sound forward chain (`EIO` on a failed header read, `EINVAL` on bad format). A writable mount of a volume whose dirty flag is set repairs it first, then requires the full check and sets the flag. If the constructor fails after it starts writing, it drops its buffers and device error marks while it still has the claim. Earlier durable repairs remain on the disk. A read-only mount repairs nothing, since nothing it does follows a backward link, and logs that a check is owed.

A volume's region is the whole device, so an image on a partition larger than itself fails the walk rather than mounting short.

### The dirty flag

The flag says that a check is owed, not what is wrong. A writable volume's mount sets it on the medium as its last step. Its unmount (`kv_prepare_unmount`) writes the dirty buffers and flushes the device, then clears the flag with a write and a flush of its own; if the clear fails, the mount becomes read-only and the unmount completes all the same, logged, as every unmount after a failed write does ([vfs.Readme.md](vfs.Readme.md#mount-binds-and-umount2)). A mount that went read-only, had a backward-link write fail, or whose repair left repeated names unsearched keeps the flag. After a failed link write, a removal finds its predecessor in the forward chain until the next mount repairs the links. A writeback or flush of the VFS that fails after the clear sets it again (`kv_abort_unmount`), or, if that fails, makes the mount read-only.

A disk root (`init_krffs_disk` in `kernel.c`) logs a flag it finds set, sets the flag and writes it through with any backward links and repeated names repaired at mount. A failure of that writeback fails the mount. The kernel then frees the orphans. The first failed read, free or final writeback halts the root with the dirty flag set. The page cache submits no further writes to the halted root (`krffs_disk_write`). Only `kernel_shutdown` clears the flag, unless the mount left the search for repeated names owed, when the debug shell's `halt`, `poweroff` or `reboot`, or `reboot(2)`, stops the machine, and only after the page cache has written everything back. A root in memory keeps no flag.

### The order of writes

A machine can stop between any two writes. On a volume they reach the medium a 4 KiB block at a time, and the disk writes a block as eight 512-byte sectors, so a stop can also fall between two sectors of one block; on the disk root they reach it a 4 KiB page at a time, in whatever order the page cache writes pages back. The rule is that the forward chain is the truth, and each write that reaches the medium leaves a ring that can be walked. Every operation in `krffs.c` keeps three consequences of it, with barriers (`krffs_barrier`) where everything written so far is put on the medium: a volume's sync point, and on the disk root the root's flush of the page cache as well. An operation that writes inside free space starts with a barrier, since the size an earlier operation stored to say where that space begins may still be only in the cache. A barrier or a size's store that fails marks the mount unsettled, and no write or truncation writes into a node's room until a barrier succeeds, since the size that gave the room may still be only in the cache. A shrink that keeps its surplus as room marks it unsettled too, since its shorter length may still be only in the cache, and the longer one on the medium counts the bytes a later write puts back there:

* The bytes come before the field that publishes them: a node's data before the `data_size` that counts it, a new node's header before the `size` that reveals it.
* One field publishes one change. A split writes the tail's free header inside the free node and then stores the shortened `size`, at which the ring gains a node; a removal stores the type as free. An operation may publish twice, if each store leaves a ring that can be walked.
* The backward link comes last and may lag; a stop before it is repaired leaves the one fault a check rebuilds from the walk.

A field that publishes a change must reach the medium whole. One that falls across a block or a sector boundary is written in two pieces, and a stop between them leaves a value nobody wrote. On a volume (`grain` of 4096), `krffs_put` refuses a write whose changed bytes fall in two blocks, and the operation fails as any refused write does. A size that changes the ring is held to the sector (`sector` of 512) on a volume and on the disk root alike: a split, a grow, a shrink or a merge whose size would change bytes of two sectors is not made, and the node keeps its room, takes the whole free node, or moves. A length whose four low bytes cross a sector or cache boundary is stored in pieces with a barrier between them (`krffs_store_length`). Each step leaves a length between the old and new values. The file moves if both boundaries cut the length or if the two pieces have no safe order. The copy is published with the new length. Backward links, the 1-byte type, a file's identifier, which nothing finds a file by, and fields of a node no path reaches yet are written without that check. A node being made has an empty name until the first byte of its name is stored, and a copy being filled for a move is free until its type is written. A rename holds its name and parent writes to the sector, as below. A mounted volume takes `sector_phase` from its device and includes it in every sector calculation. Its cache blocks start at multiples of 4096 bytes from the image start, so a field in an unaligned volume can cross separate cache and physical sector boundaries.

The operations in those terms:

* Create (`krffs_allocate_err`, then `krffs_create_node_at` or `krffs_mkdir_at`). Put a barrier first, since a pending merge or shrink may still name the free node a header is about to be written over. Split the free node if the rest can hold a header: its free header, a barrier, the shortened `size`; write an empty name, barrier, `data_size`, barrier, and the type, which makes it a node, barrier. Then the parent, the identifier, the mode, the owner (on a volume the caller's effective ids, but the group of a set-group-ID directory, which also gives a new directory its bit; root's on the boot root), the three times and the name starting with its second byte. A barrier puts those on the medium before the first byte makes the node reachable. The empty name matters: a free node keeps the name it had, and publishing that would bring a removed file back.
* Write past the end (`krffs_write_at`). Decide first whether the file moves, before any byte is written: it moves when no free node after it gives the room, or when its new length crosses a sector in no safe order. Otherwise take room from the free node after the file, at least a header's worth, so that the surplus's free header lands past the free node's own: a barrier, the surplus's header, a barrier, and one `size` that takes the bytes before it; or, when the rest could not hold a header, a barrier and the whole free node by one `size`. Repair the backward link and put a barrier, since the bytes written next go over the free node's old header. Then zero a hole, write the bytes, put a barrier, since the space held another file's bytes until now, and store `data_size` by `krffs_store_length`.
* Truncate (`krffs_truncate_node_at`). Store the shorter `data_size` by `krffs_store_length` and put a barrier, since the surplus's header is written inside bytes the old length counts; then the header, merged with a free successor, a barrier, and the shortened `size`. A grow decides whether the file moves as a write does, and its zeroes reach the medium by a barrier before the longer `data_size`.
* Remove (`krffs_remove_at`). Store the type as free, merge with a free successor by one `size`, then with a free predecessor by one `size`, repair the backward link, sync. A merge leaves the nodes separate when the four significant size bytes cross a sector or a block boundary, whatever bytes it changes, since different merges pending in the page cache can change different bytes. A merge's `size` whose write fails marks the links stale and fails the removal.
* Move. A file that must grow with no free node after it, or whose length must cross a sector in no safe order, is copied into a node allocated elsewhere, with the bytes a write or a grow adds written into the copy, whose fields, data and `data_size` reach the medium before its type, and the type before the old node is removed. A stop leaves the file whole in one node or in two under one name. A move whose old node will not free fails, since the running kernel would find the old node first; once the old node's type is stored as free, the file's holders follow the copy even when the removal's merge or sync then fails. A move that fails while the old node is still the file, and an allocation whose barrier after the type fails, withdraw the copy by storing its type as free and nothing else, since a merge could make it the larger of two nodes under one name. A withdrawal that does not reach the medium leaves one name on two nodes, which the repair resolves for the original of a shrink and the copy of a grow. If the store fails, the mount is halted: it refuses every write, and so every operation that changes anything, and every `fsync`, until the next mount repairs the volume, as Linux's ext4 turns read-only after an error, and lookups and listings pass over the copy. On a volume the mounts that show it turn read-only (`vfs_mount_halted`), so that an open for writing, a creation and a link are refused with `EROFS` before they reach the core, and the buffer cache writes none of the volume's blocks after the halt (`bcache_halt_writes`), for a sync, an eviction or the flusher, so that the medium keeps what the last sync point wrote, the dirty flag among it; a sync answers `EIO`, and the unmount drops the blocks left dirty. A barrier ends every move, so that the old node's free type is on the medium before a rename can give the copy another name, which would leave the file under two names.
* Rename (`krffs_rename_err`), of a file only. Put a barrier first if the mount is unsettled. Look up the destination, and refuse on a read that fails rather than take it for no destination. Plan the writes, the parent and the name, the identifier with the name, so that no halfway state shows a name already there: the parent first unless the new directory has a node of the old name, else the name first unless the old directory has a node of the new name, else a spare name neither has (a dot, `rename-`, the node's offset in hex and one more digit), then the parent, then the name. A name field whose changed bytes fall on both sides of an edge of a sector or a block is written in up to three pieces between the edges, in the first order whose every halfway name, part of each name, the directory does not have. A parent field whose changed bytes fall on both sides of an edge is written as a journal: the new parent first into the identifier field, which nothing reads of a file but the repair and which must take it whole, then the parent in pieces, in an order whose halfway parents, part of each value, no directory has, the root included, then the identifier back to the hash of the name; a stop within the pieces leaves the file under a parent no directory has, which the repair undoes. Only then remove a destination file, or orphan one the caller's holder test, asked of the destination the rename itself found, says is open, and put a barrier, which also drains an earlier removal of the name, before the writes, each followed by a barrier. A stop between leaves the file under one name, the old, the new, the spare or a halfway one, and never two nodes under one name, which the repair would resolve by clearing an unrelated file's name. A rename with no such plan, or a lookup that fails, is refused before anything is written, the destination's name included. A write of the rename's own that fails leaves the file in such a state in the running system, perhaps in no directory, so the mount halts, as after a move it cannot withdraw, and owes the check (`check_owed`), which keeps the dirty flag for the next mount's repair; a new file could otherwise take the name the repair gives the stranded file back. While the removal and the writes run, which sleep in their barriers, the mount owes the check too, so that a shutdown or an unmount that comes meanwhile keeps the dirty flag; a halted disk root's mount and its binds turn read-only, as a halted volume's do, its `chmod`, `chown` and `utimensat`, through the root or a bind of it, by path or descriptor, a named FIFO's included, answer `EROFS` before any permission check, `access` for writing answers `EROFS` before the permission check, but for a device, FIFO or socket, and a file's fsync answers `EIO`, over a mapping's `EROFS`.

A surplus too small for a header of its own stays inside its node, where a later shrink or a removal reclaims it.

The boot root's memory backend has no sync point of its own; its pages reach the disk as the page cache writes them back ([../mm/Readme.md](../mm/Readme.md)). On the disk root a barrier is the root's flush (`pc_sync_wait`), which writes every dirty page of the window, so a creation, a grow, a shrink and a move each write the page cache back several times, and a write that raises a file's length writes it back once. An unlink flushes nothing: for an unlink on a sound ring, each merged size ends at an existing node boundary even if the other merge's size or the change of type is still in the cache, and the link repair handles either order of writeback. The attributes a change of mode, owner or times stores are not flushed.

### The repair

`krffs_repair_at`, run by a writable mount of a dirty volume, repairs the three faults the order of writes can leave:

* A backward link the forward chain contradicts: rebuilt from the walk.
* One name on two nodes of a directory, an interrupted move: the node with more data keeps the name, and of two with equal data the larger. Either node holds the file whole: the copy of a grow holds the original's bytes and what the grow added, and the original of a shrink the bytes its copy left out. The node sizes cannot decide, since a move's copy may take a whole free node larger than the original, and a file that moves to cross a sector safely may leave a larger node behind. A directory keeps the name over a file whatever the sizes, since its children refer to it by identifier.
* A reserved node with no name, published before it was named or removed while open: freed and merged with its free neighbours (`krffs_reap_orphans_at`).

It rebuilds the backward links first. It then puts each named file whose parent names no directory into the directory its identifier names, or the root when that names none, which ends a rename stopped within its parent's pieces. That write goes in the parent's pieces, with a barrier after each, in an order whose halfway parents name no directory, so a second stop leaves the file for the next repair; the order that finishes the rename's own always is one. With no memory for the sorted directory identifiers, each identifier is tested by a walk of the chain, since a file left in no directory would let a new file take its name. It finds a repeated name by sorting an index of the named nodes, 16 bytes each, by directory and name hash, and sorts the nodes of one hash by their names, so that the search costs n log n steps whatever the names are. The index holds at most 262144 nodes (`KRFFS_REPAIR_NAMES`), fewer when memory is short; a volume with more is searched in passes, each over the nodes with the smallest hashes from where the last pass stopped, resolving every hash below the smallest one it left out. Only a single hash with more nodes than the index holds, or no memory for even 64 entries, leaves the search undone; it then sets `check_owed`, which keeps the dirty flag at unmount, and logs that `fsck.krffs` is owed, and the volume mounts read-only and the disk root halts, refusing writes, since a write could act on one of two nodes of one name. A read-only mount repairs nothing, so a repeated name left by a stop stays visible there until a writable mount or `fsck.krffs`. A dirty disk root has its backward links, its files in no directory and its repeated names repaired the same way before it is mounted, and frees orphans at every mount; a disk root whose search was owed, or with a node without a name it made and has not freed or named (`orphans`: a node it took the name off for a holder, a new node until its name is stored, and the copy a move makes of either, counted as they are published, named and freed, and a node a reap could not read or free, which also halts the root, so that the shutdown reads nothing of a disk that may no longer read and asks this before it reads the root), or with a change under way, whose writer holds the root's namespace lock when the shutdown turns scheduling off, keeps its dirty flag at shutdown, and so does one whose root page cannot be brought in, as a volume does at unmount, so that `fsck.krffs --strict` never finds a repair owed on a clean image. `fsck.krffs` makes the same judgements without that bound and clears the flag ([krffs/Readme.md](../../../krffs/Readme.md)).

Anything else, a torn header, a size that leaves the region, data that does not fit, a name that never ends, is not a state this order of writes produces, so the image is refused and nothing is changed.

### The core and its backends

`krffs.c` addresses every node by its offset and reaches the medium through a `krffs_backend_t` of `read`, `write` and `sync`, and the `unit` its writes store whole or not at all: a page of the disk root's cache, a block of a volume's, none for memory. A file's bytes go in such units, so a write that fails part way answers the bytes stored, as Linux's short write does, and never leaves bytes a reader sees that the writer was told were not written. A write whose length store or barrier fails after a piece of the length is stored answers the bytes the stored length counts (`krffs_store_length` reports it), and a moving write whose copy is live before a barrier fails answers every byte; `EIO` only when no byte written can be read. A `krffs_mount_t` has the backend, its context, the region's size and the grain. A walk reads a node without its name (`krffs_brief`, 99 bytes in two reads) and reads a name only to compare it.

The memory backend, which a boot root in memory uses, copies once each way over the Multiboot module in place or the page-cache window at `PCWIN_BASE`, and its `sync` does nothing. A disk root uses the page cache's copies instead (`krffs_window_backend` in `kernel.c`, over `pc_copy_out` and `pc_copy_in`), which bring each page in as a fault in the window would but answer a read the disk fails with -1, read a page at a time, so that a read needs one free slot as a fault does, and store a range of at most two pages whole or not at all, so that the walks, the mount and the boot's orphan scan answer `EIO` or halt the root where a fault in the window would panic the machine. The descriptor table, the system call layer and the boot code keep `krffs_node_t` pointers into the image, so the root has a pointer interface at the end of `krffs.c` that turns a pointer into an offset and refuses one outside the image. A pointer names a node and is never read through: its header is copied with `krffs_node_head`, its type asked with `krffs_node_is_dir`, its inode number with `krffs_ino_of`, the next node of a walk found with `krffs_next_node`, and its mode, owner and times stored with `krffs_node_set_mode`, `krffs_node_set_owner` and `krffs_node_set_time`, each one store through the backend, so that a header that cannot be read is `EIO` to the system call; a lookup (`krffs_child_err`, `krffs_parent_node_err`), a walk (`krffs_resolve_err`) and a path (`krffs_node_path`) answer `EIO` too, never a missing name or the root. Its adapter, `krffs_ops`, uses a node's address as the handle, has no `hold`, `open` or `pin`, takes the mount's lock for its data operations, and leaves attributes to the system call layer.

The block backend (`krffsmount.c`) reads through the buffer cache one block at a time. A store acquires and checks every block it touches before copying. A field crossing a block boundary holds the two buffers in ascending order. Bulk file writes are cut at block boundaries. The backend's `sync` is `bcache_sync` and then `bcache_flush`, so a sync point is on the medium. Every write the core makes that changes the ring or stores data ends at such a sync point, so what an operation leaves dirty is header fields: a file's length, size and times, a directory's times after an entry changes, and the backward link of the node after a shrunk one. `fsync(2)` therefore writes one file (`kv_fsync`): the blocks its writes and truncations dirtied, which the backend tags in the buffer cache with the file's open record (`bcache_dirty_owned`), so the tag follows the file through a move, then the one or two blocks of its header by offset, whatever their tag, since a change of mode, owner or times dirties the header outside a write, and then, when a free node follows the file, the backward link of the node after it, which a shrink fixes after its last sync point; the link goes by offset too, since a neighbour's truncate retags its block and a file opened again has a new record. `vfs_fsync` flushes the device after. A sync of the whole volume, or of a volume made read-only by a writeback error, retries every dirty buffer because a failed sync can leave any file's blocks dirty. A volume halted during recovery refuses these retries and device flushes. `fdatasync(2)` is `fsync(2)`, since the length a data sync must write is in the same header as the times. A node handle is the offset plus one, so the root's offset 0 is not NULL. An open handle is a `struct krffs_open`, one per open node: the node's current offset, the counts of opens and of `O_PATH` descriptions that keep the node (`kv_pin`), and whether its name has been removed. The data operations read the offset under the mount's lock and a relocation updates it, so a handle stays valid across moves. An unlink or a rename over a file that is open or kept removes the name and leaves the node for the last close to free. Since the type counts no holds, `rmdir` answers `EBUSY` for a directory that is open, kept or some process's working directory, found in the process records, and `chdir` keeps the directory with a pin from its walk until the working directory records it. `kv_create` and `kv_mknod` answer `EEXIST` for a name that is there; a creation the core refuses answers `ENOSPC` when no free node fits, `EINVAL` for a taken directory identifier, and `EIO` when the medium refused a read, a write or a sync (`made_errno`), as the boot root's creations do (`kfs_made_errno`). An unlink, a rename and an `rmdir` the volume refuses answer what the boot root's system call layer answers: `ENOENT` for a missing name, `EISDIR` for an unlink of a directory, `EPERM` for a directory moved, `EISDIR` for a file moved over a directory, and `ENOTDIR` for an `rmdir` of a file.

### The allocator

Allocation is first fit with split and coalesce. The first free node with room for a header and the bytes asked for is taken, and split when the rest can hold a header. A file grows into the free node after it when that is large enough, taking at least a header's worth of room, and is moved otherwise. A removal merges the node with its free neighbours where it can publish the merged size whole. A write that cannot grow its file for want of a free node answers `KRFFS_ENOSPACE`, reported as `ENOSPC`, and one the medium refused `KRFFS_EIO`. Each allocation, and each step of a lookup, walks the ring from offset 0.

## Limits

* There are no hard links, no symbolic links and no device nodes; a directory is never renamed or moved; a volume takes no options and no remount between read-only and writable.
* A region, and so a file, is smaller than 4 GiB; a write that would reach past offset `0xFFFFFFFF` is `EFBIG`.
* A name is at most 255 bytes. The namespace operations join the directory's whole path with the name, which must fit in 255 bytes (`ENAMETOOLONG`), and a directory's path is rebuilt only to 64 levels (`KRFFS_PATH_MAX_DEPTH`).
* A listing returns the stored children only, with no `.` or `..` entry.
* A lookup of one component, a creation and an allocation each walk the ring, and a listing of the boot root walks it from the start for each entry.
* A rename over an existing file removes the destination before the source takes its name, so a stop between loses the destination.
* A rename whose every plan would show a name already there, with all sixteen spare names taken, is refused with `EIO`, and so is one whose parent field an edge cuts while a block's edge cuts its identifier field, or whose every order of the parent's pieces shows a halfway parent a directory has.
* A file whose length must cross a sector in no safe order moves, so such a write or truncation, a shrink included, answers `ENOSPC` when no free node can hold the copy.
* On the disk root every write that raises a file's length writes the page cache back before it stores the length, so appending in small writes costs a disk write each.

# KRFFS in the kernel

KRFFS is this project's own file system and the root a Rach2 machine boots. `krffs.c` has the format: the node ring, the allocator, the operations the VFS adapter calls, and the check `init_krffs` makes before the root is used. The host tools under [`krffs/`](../../../krffs/Readme.md) build, read and repair the same images, and `fsck.krffs` is the independent judge of everything the kernel writes.

## The format

An image is a ring of nodes covering every byte of the region, with no gaps and no free list beside the ring itself. A node is a packed header (`krffs_node_t`, 357 bytes, the on-disk ABI) followed by its data. The header has a magic number, a type, an identifier, a name, a mode with the owner and the group, three times, the node's whole size in bytes including the header, the size of the node before it, the bytes of data in use, and the identifier of the directory it belongs to.

The first node is the root, which is also the root directory. The rest are reserved, holding a file or a directory, or free. Walking forward means adding a node's size to its address; the walk returns to the root, which is what makes it a ring. Walking backward means subtracting the size the node records for the one before it.

A directory's mode has `S_IFDIR`; a regular file's mode holds only its permission and special bits, which is why a node with no type bits is a regular file. A FIFO's and a socket file's modes have `S_IFIFO` and `S_IFSOCK`, and the node has no data; `mknod(2)` makes one and `bind(2)` makes a socket file, so an `AF_UNIX` name on a KRFFS root or volume keeps its kind. A character or block device node needs a device number, and the header has no field for one, so KRFFS keeps no device nodes: `mknod(2)` of one answers `EPERM`, as Linux answers for a kind a file system cannot keep. A host tool that reads a node's kind compares the whole type field, since a socket's type bits include the directory's. The root is a node of its own with the logical id 0 and a stored mode of 0755 without `S_IFDIR`, so stat and the permission rules answer for it by identity rather than by reading its mode.

A name is at most 255 bytes and its field is 256, so every name ends within it; the mount check refuses a node whose name does not. An id is 64 bits and no collision is detected. A regular file's id is not the same thing on both sides: the host stager writes the parent-aware mix for every node it stages, while a file created or renamed on the machine keeps the older hash of its name alone. Nothing resolves a path by a regular file's id, so the two agree where it matters; `stat` and `getdents64` report the node's position instead.

A name is one component, not a path, and a file is found by its directory and its name: `parent_id` says which directory holds it, and the root directory's identifier is zero. Two files in different directories may have the same name; two in one directory may not. A directory's own identifier is a hash of its parent's identifier and its name, and its children carry it in their `parent_id`, which is why a directory is never renamed or moved: its children reference the identifier the old name produced. A regular file's identifier is not used to find it, so nothing depends on the name it was hashed from.

The root's mode has one bit the format reserves, `KRFFS_MODE_DIRTY`: the kernel sets it before the first change of a writable mount and clears it at unmount only after writing pending buffers and flushing the device cache. The cleared flag is then written and flushed separately. If clearing or flushing the flag fails, unmount returns `EIO` and the mount becomes read-only. A mount made read-only before preparation keeps the flag set; `fsync` and `sync` still attempt pending buffer writes and report writeback errors to the VFS. An image found with the bit set says a check is owed, not what is wrong with it.

A writable mount of a volume whose bit is set repairs it before it publishes the mount: the three faults below, each counted in the line it writes to the log. A read-only mount repairs nothing, since nothing it does reads a backward link, and says that a check is owed. The repair compares named reserved nodes in pairs to find duplicate names. It permits at most 4096 such nodes. A dirty volume above that limit fails a writable mount with `EIO` before repair writes begin; `fsck.krffs` on the host can repair it without this bound.

## What a mount requires

Before an image is used the whole ring is walked, and it is refused unless every node has the magic number and a known type, unless every node's size is at least a header and stays inside the region, unless every node's data fits between its header and its end, unless every reserved node's name ends within its field, and unless the walk returns to the root, having covered it exactly.

The backward links are asked for on top of that, of a mount that will write: a writable mount repairs them first, and then requires them. A mount that only reads asks nothing of them, since nothing it does follows one, which is what lets a volume a machine stopped inside be read before it is repaired.

The backward link is the one derived thing in that list: the forward chain already says what it must be, so a disagreement is repaired from the walk rather than refused. The kernel does that at a writable mount of a volume that was not unmounted cleanly; `fsck.krffs` does it on the host, at any time, to any image.

## The order of writes

A write to an image on a disk reaches it a cache block at a time, and a machine can stop between any two of them. The rule is that the forward chain is the truth, and every field that reaches the medium leaves a ring that can be walked. Three consequences follow, and they are the order every operation in `krffs.c` keeps.

The bytes come before the field that publishes them. A node's data is written before the `data_size` that says how much of it counts, and a new node's header is written into the free space it will occupy before the size that reveals it. A machine that stops between the two leaves a ring that is intact and a file that is the length it was.

One field publishes one change. A split writes the tail's free header inside the free node, where nothing yet reaches it, and then stores the shortened size, which is the moment the ring gains a node. Freeing a node stores its type, and then adds its size to the free node before it, which is the moment the ring loses one. Nothing is published by two fields a stop could separate. An operation may publish twice, so long as each store leaves a ring that can be walked: growing a file does, because the header of the node it grows into has to go before the tail's header can be written anywhere safe.

One field is one write to the backend, and a backend that writes whole cache blocks can put half of it on the medium: a node's header is where it falls in the packed ring, so a `size` at the last bytes of a block is written in two pieces. A stop between them would leave a value that is neither the old one nor the new one, and a ring that steps by it is a ring that has lost a node. The core refuses such a write instead of making it. It compares the bytes it is about to write with the bytes that are there and refuses only when the ones that change fall in two blocks, which is why a length whose top four bytes are zero before and after is written like any other: nothing on the far side of the line changes. A refused write fails its operation, with `krffs: refused: a field at N would reach the medium in two pieces` in the log, and the volume is left as the order of writes leaves any refused write. Every field of a node no path reaches yet is written without the rule: the identifiers, the mode, the owner and the three times of a file or directory being made, and the name, the identifiers, the mode, the owner, the times and the length of a copy being filled for a move, as well as the length of a new node before its type. Nobody reads such a field torn, and under the rule a node could be neither made nor moved to a place where one of its fields falls across a block. A node being made has an empty name, so no path reaches it, until its name is written after every other field; a copy is a free node until its type is written after its name, its other fields, its data and its length. A rename asks the question first, for the id and the parent it is about to write, before it removes a destination of the same name: a rename the rule refuses leaves both names and their bytes as they were, where it once removed the destination and then refused the id. Only a mounted volume has such a unit; the root's memory backend has none, since a memory image reaches nothing in pieces. A node whose header falls across a block that way is rare (seven of every 4096 positions for the size field) and it is placement, not damage: reading it, and every operation whose changed bytes stay on one side, work as they always did.

The backward link comes last and may lag. Every operation that changes a size repairs the following node's backward link afterwards, and a machine that stops before that leaves the one thing the check can rebuild from the ring it has just walked.

The operations in those terms:

* Create. Split the free node, write the file's fields into it with an empty name, and store the type, which makes it a node. Then write the directory it belongs to, the mode, with a FIFO's or a socket's type bits, the owner, the creating process's effective ids on a mounted volume, and the three times, all the moment of the creation, and last, once those are on the medium, the name, which is what a path can reach; a write of any of them that fails fails the creation. A stop before the name leaves a node no path reaches, and the check reclaims it; a stop after it leaves a file that is finished. The empty name written before the type matters: a free node keeps whatever name it had when it was freed, and publishing that would bring a removed file back.
* Write past the end. Take the whole free node after it with one size, and split the surplus back off with a second: the tail's header is written into space the node already covers, and the size that shortens the node is what reveals it. Then write the caller's bytes, then store `data_size`. Writing that header before the free node is taken would land on the free node's own header whenever the growth is shorter than a header, and leave a torn node in the ring. The growth changes what the node can hold; the length changes only when the bytes are there.
* Truncate. Store the shorter `data_size` first and put it on the medium, since the surplus's free header is written inside the bytes the old length still counts: a stop with that header written and the shorter length not would give the file the allocator's bytes to read. Then write the header and store the shortened size. A surplus too small to hold a header of its own stays in the node, where a later shrink or a removal reclaims it.
* Remove. Store the type as free, then merge with a free successor by one size, then with a free predecessor by one size.
* Move. A file that grows with no room after it is copied into a node taken elsewhere, and the old node is then freed. The copy, its length and its name are all on the medium before the type that publishes it, and that type is on the medium before the old node is freed, so a stop leaves the file whole in one node or whole in two. Two is one name on two nodes, which the check resolves: a move only ever makes a node larger, so the larger of the two is the copy the move was making, and the smaller loses its name. A move whose old node the medium will not free is a failure the caller is told about, since a running kernel walks to the first of the two and would read what the file used to be.
* Rename. The name, the identifier and the parent are three fields, and a stop can leave a name half written. The file stays reachable under whatever name the medium has; nothing else is damaged, and the check has nothing to repair.

## What a stop can leave, and what the check does

A ring whose backward links disagree with the forward chain. The check rebuilds them from the walk it has just made, and says how many.

A reserved node with no name, which is a node published before it was named, or one unlinked while a program still had it open. No path reaches it. The check frees it and merges it with its free neighbours, and says how many.

One name on two nodes in one directory, which is a move that was interrupted. The check keeps the larger node and takes the name off the smaller, which makes it the previous case. A directory is never the one that loses its name, whatever the sizes say: its children name it by its identifier, so clearing it would put a whole tree out of reach, and a rename interrupted between the parent it published and the name it had still to write is what puts a file beside a directory of the same name.

The dirty flag of an image that was not cleanly unmounted, which says only that a check is owed. `fsck.krffs` clears it once the three above are settled.

Nothing else. A node whose header is torn, whose size leaves the region, whose data does not fit, or whose name never ends is not a state this order of writes can produce, so the check refuses the image and changes nothing rather than guessing what it should have been. The length of a free node is not asked about: a free node keeps the length of whatever was removed there, and a split publishes the smaller size before it writes the new length, so a free node whose length is larger than the node is an ordinary state. `fsck.krffs` on the host makes the same judgements and repairs the four things above; `--strict` there reports them and changes nothing, which is how a test asks whether the kernel left an image clean rather than repairable.

## The core, and the two backends

One implementation serves both media. `krffs.c` addresses every node by its offset from the first byte of the region and reaches the medium through a backend of `read`, `write` and `sync`, so what differs between a root in memory and a volume on a disk is three functions and nothing else.

The memory backend is one `memcpy` either way, over a mapped image: a Multiboot module in place, or a disk region the page-cache window maps. It cannot fail. The root is mounted this way, and the descriptor table, the syscall layer and the boot code hold `krffs_node_t` pointers into that image, so the root keeps a pointer interface, at the end of `krffs.c`, which turns those pointers into offsets and refuses one that is not in the image.

The block backend (`krffsmount.c`) reads and writes the region through the buffer cache, a 4 KiB block at a time, holding one buffer at a time. That is what `mount(2)` places, under the type name `krffs`, and what `/proc/filesystems` lists. Its region is the whole device it is given, since the format records no size of its own: an image on a partition longer than itself fails the chain check rather than mounting short. A mount without `MS_RDONLY` on a device that takes writes is writable; anything else is read-only, and `/proc/mounts` says which.

A cache is not a medium, so the order below is kept by syncing between a write and the field that publishes it. On a memory backend that costs nothing; on a volume it is what the cache has written when the machine stops. A write that the cache refuses stops the operation before the field that would have published it.

A node handle outside the file system is its offset plus one, so the root's offset of zero is not the NULL the mount table reads as the mount's root. An open handle points to a shared record containing the node's current offset, the number of opens, the number of `O_PATH` descriptions that pin the node, and whether its name has been removed. An `O_PATH` description opens nothing and pins the node instead, so an unlink or a rename over the node leaves it nameless, and `rmdir` of a pinned directory answers `EBUSY`, as for an open one. Path resolution and open-record registration hold the mount namespace lock without a gap, including for creation, loop attachment and the program and interpreter lookups of `execve`. An open during relocation waits until the move has updated the shared record. The last close or unpin frees the record, and the node too when its name has been removed. Read, write and truncate resolve its offset after taking the mount lock. The same handle remains valid across multiple calls, relocations and reuse of old offsets. Mounted-file `O_TRUNC` opens the node before truncating through its handle; failure releases the handle and descriptor.

## The allocator

Allocation is first fit with split and coalesce, after the storage allocator in The C Programming Language. It scans for the first free node large enough for a header and the bytes asked for, and splits a larger one when the remainder can hold a header of its own; a remainder shorter than that stays inside the allocated node, where a later shrink or a removal reclaims it.

A file grows into the free node after it when there is one. Otherwise it is moved: a new node is allocated, the old node's fields and data are copied into it, and the old node is freed. Write and truncate repoint references from the offset resolved under the mount lock to the new offset, even when a later step fails after relocation.

Freeing a node marks it free and merges it with whichever neighbours are free, so the ring never holds two free nodes side by side.

A write that cannot grow a file answers `KRFFS_ENOSPACE`, which the write syscall reports as `ENOSPC`, and an argument the file system cannot use, or a failure while the bytes are being written, answers `KRFFS_EBAD` and `EIO`. The first of those covers a medium that refused a write during the resize as well as a file system with no room, so `ENOSPC` from a volume on a failing device is not proof that the volume is full. A creation tells the two apart: it answers `KRFFS_ENOSPACE` only when the allocator walked the whole ring and found no free node that fits, and `KRFFS_EIO` when the medium refused a read, a write or a sync it needed, and a mounted volume reports them as `ENOSPC` and `EIO`, so a stick pulled out while `mknod`, `mkdir` or a creating `open` sleeps in a sync point is `EIO`.

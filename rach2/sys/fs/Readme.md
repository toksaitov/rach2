# KRFFS and file descriptors

KRFFS is the kernel's own writable file system: the RAM images' and the fallback root's, since the everyday root on a disk is an ext2 partition ([ext2.Readme.md](ext2.Readme.md)). It stores a hierarchical namespace in one contiguous region and uses a first-fit extent allocator. The same code can address a RAM module directly, a RAM module through the page-cache window, or a partition on an ATA or AHCI disk.

`krffs.c` and `krffs.h` implement the format, the allocator, the namespace and the file operations, and `krffsmount.c` is the type `mount(2)` places over a block device; the format, its two backends and the order in which a change reaches the medium are in [krffs.Readme.md](krffs.Readme.md). `fd.c` and `fd.h` implement descriptor tables and shared open-file descriptions, and `lock.c` the advisory locks, record, open file description and flock, as [lock.Readme.md](lock.Readme.md) describes. The syscall-facing permission, descriptor, and metadata rules are in `../syscall_fs.c`. The mount table and the resolver every path goes through are described in [vfs.Readme.md](vfs.Readme.md), the kernel-generated `/dev` and `/proc` namespaces in [synthfs.Readme.md](synthfs.Readme.md), the FAT32 type, which reads and writes, in [fat32.Readme.md](fat32.Readme.md), and the page cache and disk drivers in `../mm/Readme.md` and `../block/Readme.md`.

## Paths and directories

Every path-taking syscall resolves through the mount table's resolver, one component at a time, with `..` resolved physically ([vfs.Readme.md](vfs.Readme.md)). KRFFS answers each step with one lookup of `(parent_id, name)`; its `..` is the node whose ID is the directory's `parent_id`, and the root's `..` is the root.

Each process starts with `cwd` set to `/` and inherits it across `fork`, and has a root directory, the root of the mount table until `chroot(2)` gives it another, which absolute paths and the `cwd` string start from ([vfs.Readme.md](vfs.Readme.md)). Relative paths resolve against that string; a working directory inside a mount placed by `mount(2)` also holds that mount. `openat` and the other implemented `*at` calls accept `AT_FDCWD`, an absolute path, or a real directory descriptor. A directory descriptor is resolved back to its current absolute name before use; it is not a capability that bypasses ancestor permissions. `fchdir` makes that name the working directory.

A path may be 4096 bytes with its terminator, Linux's `PATH_MAX` (`VFS_PATH_MAX`). A call copies each path it is given into a page from `pathbuf.c` and joins a relative one to the working directory, or to the path of the directory a descriptor is open on, in place; the joined path is held to the same bound, where Linux bounds only the path the caller passed, and past it the call answers `ENAMETOOLONG`. The copy drops `.` components, and says how the path as written ended: a path that ends in a slash, or whose last component is `.` or `..`, names a directory, and every call answers it as Linux does. A last `.` is put back (`path_put_dot` in `../syscall_fs.c`), so the walk looks it up in the directory before it, which takes search permission there and answers `ENOTDIR` for a name that is not a directory, as Linux's walk does; a trailing slash alone takes no search permission on the name before it. A call that looks the path up follows a final symbolic link and answers `ENOTDIR` for anything but a directory (`resolve_named`): the stat calls, `open`, `access`, `chmod`, `chown`, `truncate`, `utimensat`, `readlink`, `statfs`, a link's source, `umount2`, a connect or a send to a socket file, and `execve` and the interpreter a script or a `PT_INTERP` names, which answer `EACCES` for a directory, since no program is one, and check the node in the walk that opens it, so a symbolic link replaced between two walks cannot change what runs; `open` with `O_CREAT` answers `EISDIR`. A call that walks to the parent of its last name gets `.` or `..` as that name, and answers for it by name: `rmdir` with `EINVAL` or `ENOTEMPTY`, `rename` with `EBUSY`, `unlink` with `EISDIR`, and the calls that make a node with `EEXIST`; after a slash, the calls that make a node other than a directory answer `ENOENT` or `EEXIST`, which a bind of a socket file answers as `EADDRINUSE`, and `unlink` and `rename` judge the name itself, a symbolic link to a directory being no directory. The root, which has no last name, is `EBUSY` to `rmdir` and `rename`, `EISDIR` to `unlink`, and `EEXIST` to the calls that make a node, which a bind answers as `EADDRINUSE`. Each process has up to eight such pages, taken the first time one of its calls needs that many at once and kept for the record's life, so a path costs a frame the first time and never after, and the count of frame allocations `rach2.framefail` keeps does not move with the paths a program names. A call takes four at most: a rename's two paths, and the target of a link the resolver follows with the path it joins the target to. The working directory's path is kept in the process record when it is shorter than 64 bytes, and in the heap up to the same 4096 when it is longer.

KRFFS, the boot root and a mounted volume alike, names a node it creates, removes or renames by its path within the volume, built in 256 bytes and climbing at most 64 directories, so on KRFFS a name whose path is longer or deeper answers `ENAMETOOLONG`. ext2 and the FAT types are given a directory and a name for those operations and have no such bound. Each of them rebuilds a directory descriptor's path by climbing its parents, though, ext2 for up to 2048 directories, as deep as a path of 4096 bytes goes, vfat for 32 and exFAT for 64, so `fchdir` and a relative `*at` call through a descriptor of a directory deeper than that answer `ENAMETOOLONG` however short its path ([vfs.Readme.md](vfs.Readme.md)).

Path resolution checks execute permission on every directory entered. Ordinary calls use effective IDs. `access` and `faccessat` use real IDs for both the prefixes and the target. The target's own read, write, or execute permission is checked separately by the operation that needs it.

KRFFS directory reads return only stored children. They do not synthesize `.` or `..` entries. Lookup and enumeration are linear scans. `getdents64` keeps its place in the open-file description: the boot root stores the last returned node's offset plus one, and a mounted volume the next node's offset, with an end of its own. Deleting entries between batches does not renumber the remaining nodes. Creating or relocating a child during enumeration may make that child appear twice or not at all; concurrent namespace modification during a directory read is otherwise unspecified.

KRFFS keeps FIFOs and socket files, whose modes have their type bits, and no device nodes, since a node has no field for a device's number ([krffs.Readme.md](krffs.Readme.md)). KRFFS has no hard links or symlink nodes. `link` and `linkat` validate their arguments and source; a read-only mount answers `EROFS` first, and a writable one `EPERM`, since no KRFFS type has the operation. Symbolic links exposed under `/proc` belong to the synthetic file system. Renaming or moving a directory is refused because its children refer to its current ID: the boot root answers `EPERM` and a mounted volume `EIO`. Files may be renamed within or across directories, and an existing regular-file destination may be replaced.

## Descriptor state and lifetime

Process allocation initializes three console descriptors, each with a separate open-file description. If any description cannot be allocated, initialization releases the partial set and process creation fails before publishing the process. Each process has a descriptor table allocated from the kernel heap. It starts with 16 entries and doubles as it fills, up to 1024, the width of a `select` set; an open past that limit returns `EMFILE`, and one for which the heap has no room to grow the table or for the open-file description returns `ENOMEM`: `fd_alloc` answers one or the other, and every call that makes a descriptor returns what it gets, as on Linux. An open of a path reserves its descriptor before it resolves the path, as Linux does, so an open that gets no descriptor has created and truncated nothing, and publishes it by giving the entry its type as the last step: until then the slot is a reservation, with no type and a description, which a lookup, a close and a `dup2` of another thread cannot take while the open sleeps in the file system's open or a truncation. The process record points to its table, which `clone` with `CLONE_FILES` shares: every thread a C library makes shares it, and `refs` counts the records that do. A table first shared grows to all 1024 entries at once, so that an entry does not move while a call of one sharer sleeps with a pointer to it and another opens descriptors. `fork` gives the child a copy whose descriptors share the parent's descriptions, and in which a slot that an open of another thread has reserved and not yet filled is free; the last sharer's end closes the table's descriptors, and `execve` first gives a caller that shares its table a copy of its own, as Linux's does. Linux keeps a file for the length of a call through the reference `fdget` takes, so a descriptor one thread closes stays open for another thread's call that is using it. Here a lookup (`fd_get`) in a shared table sets the descriptor's bit in the calling thread's `fd_held` map, and the dispatcher clears the map as the call's body returns (`fd_holds_release`). A close of a descriptor another thread's map has (`close_fd`) marks the entry `FD_FLAG_CLOSING` and leaves it whole: lookups answer `EBADF` and allocation passes over it, the call that has it goes on with it, and the release happens as the last such call ends; the closing process's record locks on the file go at the close, and that release drops none. A close that releases at once marks the entry closing too, and releasing, before the release, which may sleep, in a file system's release of the description's last reference among other places: meanwhile a lookup, a `dup2` onto the slot and a `fork`'s copy of the table pass it by, and a release the end of another thread's call would begin is left to the one under way. `dup2` onto a closing entry answers `EBUSY`. A wait over many descriptors, `poll`, `select` or `epoll_wait`, holds each one it looks at, which keeps the objects it waits on alive while it is queued on them, so a close of one of them by another thread takes effect when the wait ends; Linux takes it at once and drops the descriptor from an epoll set. Open-file descriptions are allocated separately from the heap, one per open, without a fixed pool. An open-file description contains the shared 64-bit file offset, a separate 64-bit offset for raw disk windows, the `O_APPEND` and `O_NONBLOCK` status flags, and a reference count.

A description on a mounted file system also holds its mount, its node, and the file system's per-open handle; the file system's `open` runs once per successful `open(2)` without `O_PATH` and once per `truncate(2)` that passes its checks, which truncates through a description of its own that no descriptor points at, and its `release` once at the last close, and the record written at unmount says both counts. `read`, `write`, `lseek` and `ftruncate` hold the description for the length of the operation, so two processes sharing one description cannot both read the same offset while one sleeps in a disk request; `pread64` and `pwrite64` hold it on a regular file too and leave its offset alone. A directory's offset is the cursor `getdents64` reads from, which a seek sets to 0 or to a place the listing gives, found by reading the listing from its start, since what a place means is the type's own; a `/proc` file's is the byte of its text, the snapshot its open took or, for `oom_score_adj`, the text each read makes, or the address in `/proc/PID/mem`, that it reads next, and a read or a write of one holds the description as its seek does.

Mounted descriptor operations take the mount namespace lock before the description lock. Append selects EOF under both locks, including across independently opened descriptions.

An `O_PATH` descriptor names a file and opens nothing, as on Linux. It has neither access flag and `FD_FLAG_PATH` instead. On the KRFFS boot root or a mounted type it is a file or directory descriptor whose description holds the mount and the node and no handle, since the type's `open` does not run, so its last close runs no `release`; on mounted KRFFS, which keeps a node only while it is open, the description also counts a pin in the node's open record through the type's `pin`, which its last close drops, so an unlink or a rename over the node leaves it to the descriptor as it would to an open one; on a `/dev` or `/proc` directory it is a synthetic directory descriptor; on any other `/dev` or `/proc` node it is `FD_TYPE_SYNTH_PATH`, which keeps a copy of the node's classification for `fstat` and `fstatfs` and opens no device and takes no snapshot. `fstat`, `fstatfs`, `fchdir`, the `*at` calls, duplication, `F_GETFD`, `F_SETFD`, `F_GETFL` and `close` take it; every other call on a descriptor answers `EBADF`, and `poll` reports `POLLNVAL`.

`dup`, `dup2`, `dup3`, `F_DUPFD`, `F_DUPFD_CLOEXEC`, and `fork` share the open-file description. A seek, append setting, nonblocking setting, or read through one duplicate is visible through the others. `FD_CLOEXEC` is per descriptor. Ordinary duplication clears it on the new descriptor; `dup3(O_CLOEXEC)` and `F_DUPFD_CLOEXEC` set it. A successful `execve` closes marked descriptors.

A descriptor open on a regular file continues to name that file after unlink or replacement by rename. If a name is removed while any descriptor holds its node, KRFFS clears the node's name and keeps the extent as an orphan; the ends of a FIFO hold its node too, by their descriptions, since its pipe is found by the node's address, and so does the address space of a program that runs from the file, which keeps it (`mm/Readme.md`). On the KRFFS root, `unlink` and `rename` count the holders under the root's namespace lock, which `unlink` takes with its walk and `rename` after its two walks, each keeping it through the removal, and which an open holds from its walk until it has published its descriptor, so the count sees every descriptor an open has made. Every release of a holder of a file of the root takes the same lock for its count of the other holders and for the reclaim of a nameless node (`fd_release_lock`, `fd_release_orphan`): a close, a `dup2` over the descriptor, the close-on-exec sweep, the release of a table by its last sharer, the release at the end of another thread's call, the last close of a FIFO's end, the end of a file mapping, the drop of a descriptor in flight on a socket, and the end of the last address space that keeps a program. So no allocation takes the extent while the reclaim sleeps reading a neighbouring header, and no other release counts between them. A holder the count finds in a list of its own, a mapping, a descriptor in flight or an address space, takes the lock before it leaves that list, so it is counted until its own count and release; a descriptor in a table stays in the table until its release has run. Orphans are absent from lookup, directory reads, debug listings, file counts, and directory emptiness checks. The last holder's release frees the extent: the final close, the end of the last mapping or of the last descriptor in flight, or the end of the last address space that keeps the program. Process exit releases every open descriptor and its address space and therefore performs the same work.

Regular-file relocation preserves the same lifetime across all process tables. A directory is never kept as an orphan: `rmdir` refuses a directory in use with `EBUSY`. On the boot root a directory is in use while a description has it, an `O_PATH` descriptor's or one in flight on a socket among them, or while it is a process's working directory, which the process record keeps with its mount (`vfs_cwd_set`); `rmdir` looks for both under the root's namespace lock, which an open holds until it has published its descriptor, and the refusal comes before the check for emptiness. A descriptor of the root finds its directory by the node's place, and a directory freed under one would leave it on whatever node the allocator put there next. A mounted KRFFS volume refuses a directory a descriptor has, an `O_PATH` one included, or a working directory has, before the check for emptiness too, and `chdir` pins the directory from its walk to its record, since the checks between may sleep for the disk; ext2, FAT32 and exFAT refuse a directory a descriptor or a working directory has, after the check for emptiness. tmpfs removes a directory in use, as Linux does, and leaves its descriptors and working directories on an empty directory that takes no new entry.

## Modes, ownership, and times

New files and directories receive the creator's effective uid and gid. Their requested permission bits are masked by the process umask. The kernel enforces the owner, group, and other permission bits; effective uid 0 overrides them except that executing a regular file still requires at least one execute bit.

Creating, removing, or renaming an entry requires write permission on its parent directory. A sticky directory additionally restricts removal and both ends of replacement to root, the directory owner, or the affected entry's owner. The parent write check runs first, so a caller without it receives `EACCES` rather than the sticky check's `EPERM`.

Setuid and executable setgid files change the effective and saved IDs at exec. A non-root write or truncate clears setuid and clears setgid when group execute is set. A change of owner or group applies the same clear even for root. A no-change `chown` changes neither mode nor timestamps. An unprivileged owner cannot set setgid on a regular file whose group is not one of that process's groups.

Creation initializes atime, mtime, and ctime. Data changes advance mtime and ctime; metadata changes advance ctime; directory entry changes advance the containing directory's mtime and ctime. Reads do not advance atime. `utimensat` can set atime and mtime explicitly and advances ctime when it changes them. The root's timestamps are reported but `utimensat` returns success without changing them.

There are no ACLs, quotas, file capabilities, hard-link support, link-count tracking, or journal. The boot root reports one link for every node; a mounted volume reports two for a directory and one for a file. `fcntl(2)`'s record locks and `flock(2)` locks conflict and wait as on Linux, each kind only with locks of its own kind ([lock.Readme.md](lock.Readme.md)). A POSIX record lock belongs to a descriptor table, which the processes `clone` makes with `CLONE_FILES` share, and a wait for one that would close a cycle of waiting owners fails with `EDEADLK`; waits for open file description locks and flock locks are not searched for a cycle, as on Linux, so two processes that take exclusive flock locks on two files in opposite orders can wait for each other for good.

## Mounts and durability

The root can be mounted in three ways:

* The default mounts the multiboot RAM module directly. No page-cache backing is installed.
* `rach2.fswindow` maps the RAM module through the demand-paged window.
* `rach2.fsdisk` or `rach2.root=disk` maps a disk partition through that window.

The window starts at `0xD0000000`. Its span ends at the lowest device-memory BAR that falls within it and is capped at 512 MiB. A disk partition must be nonempty, page-aligned, contained within the disk, and no larger than the available span. Disk discovery examines the four nonempty MBR entries in order and selects the first whose first sector has the KRFFS magic, root type, and a plausible root extent. It does not select by the MBR type byte. The complete mount validator then checks the extent sequence.

`fsync` validates the descriptor; on a mounted file it runs that type's `fsync`, and on a boot-root file it flushes the whole page cache rather than one file. `sync` runs every active mount's `sync` and then the page cache's writeback, and always returns success. On a direct RAM mount the cache is empty. On a windowed RAM mount, writeback copies dirty pages into the in-memory module; the result still does not survive a reboot. On a disk mount, eviction and explicit writeback reach the selected ATA or AHCI partition, so synchronized data persists.

A disk-backed boot root sets the root node's dirty bit and writes it through before it repairs any orphan, and then reclaims all nameless reserved nodes, whether or not the previous dirty bit was set. A volume mounted by `mount(2)` repairs only what a dirty flag says was left behind, and sets its own flag after. Clean shutdown first flushes all dirty data, then clears the bit and flushes again. `sync` alone does not clear it. The root dirty bit shares the stored position of setuid, so permission and mode paths exclude the root by identity.

`krffs/mkdisk.sh` limits a generated disk partition to the 512 MiB window cap. The actual kernel limit may be smaller when a device BAR shortens the window. The host KRFFS tools also accept standalone regions up to 4095 MiB; that larger host limit does not make such a region mountable through the kernel window.

## mount and umount2

The root is placed by the boot path and cannot be unmounted. `mount(2)` and `umount2(2)`, the mount table, the claims on a mounted partition's sectors, and the buffer cache the mounted types read through are described in [vfs.Readme.md](vfs.Readme.md).

## Tests

The default `make test` run includes the basic file, directory, metadata, rename, and listing probes. `dirprobe`, `dirgrow`, `unlinkdirprobe`, and `pathcanon` cover hierarchy, `*at` resolution, relocation, deletion during enumeration, and canonicalization. `fdstale` covers regular-file lifetime, orphan visibility and release, cross-process holders, relocation repointing, and the refusal to remove a directory in use. `ofdprobe` covers shared offsets, fork and duplication, close-on-exec state, and pool reuse.

`ownprobe`, `permprobe`, `modeprobe`, `searchprobe`, and `stickyprobe` cover ownership, umask, permission checks, set-ID changes, ancestor search, and sticky directories. The default run also uses the ported musl for its stat, timestamp, identity, and permission cases.

`tests/musl/catfile.c` and `tests/musl/ofdmusl.c` are built as `/musl/catfile` and `/musl/ofdmusl` in the test image but are not in the default runner. They provide manual end-to-end checks of musl stdio and directory calls, and of a duplicated stdio descriptor's shared offset.

`tests/run diskfull` writes into a disk-backed root until the write is refused, requires `ENOSPC` and requires the file to hold what was written before the refusal, then unlinks it and writes again to require the space back.

`tests/run persist` and `tests/run persist-ahci` boot the same disk image twice and require a file written through `fsync` and `sync` on the first boot to be read back on the second. `tests/run host` includes `readfile_hosttest`, which checks the host extractor's bounded path walk and malformed-image refusals, and `krffs_hosttest`, which runs the kernel's own allocator, namespace and file operations over a backend of its own.

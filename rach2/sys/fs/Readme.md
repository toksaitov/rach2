# Rach2 File System (KRFFS v2)

A small hierarchical file system with real directories and the modern `*at` file API a libc builds `FILE*` and `DIR*` on. KRFFS has directories and path resolution, so musl's `fopen`, `stat`, `opendir`, and `mkdir` work and a navigable tree exists: a program can `mkdir` a directory, create and read a file inside it, `chdir` into it and resolve relative names, list it, and `cat /etc/motd` from a tree the host staged into the image.

## Pieces

| File      | Responsibility                                                                                                                                  |
|-----------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| `krffs.*` | The on-disk format, the linear node list, and the v2 path resolver (`krffs_walk`/`krffs_resolve`, `krffs_node_path`, `mkdir`/`rmdir`/`readdir`) |
| `fd.*`    | The per-process descriptor table: type, the resolved node or socket, offset, and flags (READ/WRITE/APPEND/CLOEXEC)                              |

The descriptor, path, directory, and `*at` syscalls live in `../syscall.c`; this directory is the file system itself plus the descriptor table it attaches to.

## On-disk format

KRFFS is a flat linear list of nodes packed into one image: each `struct krffs_node` header (magic, type, id, `name[256]`, mode, uid, gid, three timestamps, `size`, `previous_node_size`, `data_size`, `parent_id`) is followed by its `data_size` bytes, and the next node sits `size` bytes on. The header is byte-identical in the kernel (`krffs.h`) and the host tools (`krffs/krffs_node.h`), so an image written by the host mounts in the guest.

v2 added one field, `parent_id`, at the end of the header (so `sizeof` propagates to every host tool automatically). That single field turns the flat list into a tree:

* A directory is a node whose `mode & S_IFMT == S_IFDIR` (`0040000`); a regular file carries bare permission bits (no type bit), which keeps old flat images readable.
* Every node has a unique id `mix(parent_id, name)`, an FNV-style mix of the parent's id and the name, never zero. Siblings have unique names, so the id is unambiguous and survives a move (it depends on name and parent, not offset).
* The root has the reserved id `KRFFS_ROOT_ID == 0`. Host-created nodes leave `parent_id` zero, so they resolve as root's children with no host change; the root node itself is matched by pointer (`node == fs->node`) since `krffs_find_node_by_id` deliberately never hands back id 0.

## On a real disk

KRFFS mounts three ways, chosen at boot: the RAM-disk multiboot module in place (the default), the same module through the page-cache window (`rach2.fswindow`), or a real disk partition through that window (`rach2.fsdisk`). The file system code is identical in all three; it only ever pointer-walks its node list, and on the window paths that walk is demand-paged.

On the disk path the kernel slices the first KRFFS (MBR type `0x7F`) partition out of the disk and maps it into a fixed kernel-virtual window (`PCWIN_BASE == 0xC0000000`, spanning up to the lowest device MMIO BAR that lands in it and capped at `PC_WINDOW_CAP == 256 MiB`, with the partition clamped to fit) backed by a fixed-size page cache (`../mm/pagecache.c`). A fault in the window polls the missing page in from the disk through the polled block driver behind `block0` (`../block/ata.c`, or `../block/ahci.c` when `rach2.disk=ahci` selects it); a write dirties it; eviction and `fsync`/`sync` write dirty pages back with a FLUSH CACHE. So `fsync` is honestly durable on the disk path: a written-and-synced file survives a reboot, proved by the two-boot `tests/persistprobe`. On the RAM-module path the image is already as durable as memory, so `fsync` is a no-op. A disk KRFFS must fit the window and KRFFS's 32-bit size, so the host tools cap a partition at 256 MiB and any KRFFS at just under 4 GiB.

## Path resolution

`krffs_walk` is the resolver. It splits a path on `/` and, starting at the root (or a given directory id), matches each component by `name` and `parent_id`, descending only into directories. `.` keeps the current directory; `..` follows the directory's own `parent_id` (and resolves a root parent back to the root rather than to NULL). `krffs_resolve_e` reports whether a failure was a missing component (`-ENOENT`) or a non-directory in the middle of the path (`-ENOTDIR`), which the syscall layer returns verbatim. `krffs_resolve_x` adds the third: a `may_search` predicate the resolver asks about every directory it enters, the root and the `.` and `..` arms included, whose refusal (`-EACCES`) becomes the walk's error. The file system knows nothing about credentials, so the rule lives in the predicate the syscall layer installs (`cred_may_search`, by the effective ids; `cred_may_search_real` for `access(2)`, which answers for the real user and must charge the prefix the same way it charges the target). The predicate reads the calling process, so it is only valid from syscall context; the boot self-test, the debug shell, and the re-resolves that confirm a descriptor still names its node pass NULL and are unchanged. The target itself is never charged: reaching a name is not reading it.

`-EACCES` from a denied ancestor outranks what the caller would otherwise learn. A missing name inside a directory the caller may not search reports `-EACCES` and not `-ENOENT`, so existence cannot be probed through it, and `open` answers it before considering `O_CREAT`, whose fall-through creates through a resolver that does not charge search. The mutating calls below it have no such reporting: `krffs_unlink` and `krffs_rename` answer every refusal with a bare `-1`, which userspace decodes as `EPERM` whatever went wrong, so `sys_unlink` and `sys_rename` decide each case themselves before calling down and the call that follows can only succeed. Unlink gives `-ENOENT` for a missing path and `-EISDIR` for the root or any directory. Rename gives `-ENOENT` for a missing source or a missing destination parent, `-ENOTDIR` when that parent is not a directory, `-EINVAL` for a destination naming no entry, `-EPERM` for a directory source (its children reference its id, so a move would orphan them: POSIX reserves `EPERM` for a rename the file system cannot perform), and `-EISDIR` for a directory destination under a plain source, which is the case `EISDIR` is actually reserved for. The root is refused by node identity rather than by `KRFFS_IS_DIR`, because the root carries `0755` with no type bits and would otherwise read as a plain file. `krffs_node_path` walks `parent_id` upward to rebuild a node's absolute, canonical path (used by `getcwd`, `chdir`, and dirfd resolution; `..` and `.` collapse for free because it follows real links).

`open`, `stat`, `unlink`, `rename`, `mkdir`, `rmdir`, `getdents64`, and `chdir` all route through the walk, so `/etc`, `/bin`, and a `mkdir`'d subtree are real directories rather than a flat namespace.

## The current directory and the `*at` API

Each process carries an absolute, canonical `cwd` string in its PCB (`"/"` at start, inherited across `fork`). A relative user path is joined onto the cwd at copy-in (`copy_path_cwd`), so the existing root-relative resolver, which already honors `.` and `..`, walks the right tree; an absolute path passes through. `chdir` resolves the target, requires a directory, and stores its canonical path; `getcwd` (183) returns it.

The `*at` calls let a libc build `FILE*` and `DIR*` and resolve against a directory descriptor:

* `openat` (295) and `fstatat64` (300): resolve relative to `AT_FDCWD` (the cwd), an absolute path, or a real directory fd (`copy_path_at` rebuilds the dir's path with `krffs_node_path`).
* `fstat64` (197): `stat` by descriptor; the root, a device, and a socket report `S_IFDIR`, `S_IFCHR`, and `S_IFSOCK`.
* `_llseek` (140): 64-bit seek; KRFFS offsets are 32-bit, so a seek past 4 GB is rejected rather than truncated.
* `fcntl64` (221): `F_DUPFD(_CLOEXEC)`, `F_GETFD`/`F_SETFD` (the close-on-exec bit), `F_GETFL`/`F_SETFL` (access mode and `O_APPEND`).
* `O_CLOEXEC` and `O_APPEND` are honored at `open`; `execve` drops `FD_CLOEXEC` descriptors at its commit point.

## Deliberate simplifications

What KRFFS deliberately leaves out, without compromising the tree structure:

* The permission model stops short of a few classic pieces. The mode is the twelve low bits: nine permission bits, enforced by one access check at every path that opens, creates, execs, or walks, plus the setuid, setgid, and sticky bits stored in the 07777 width. Exec honors setuid and setgid (the effective and saved ids take the file owner's, the real ids unchanged, and `AT_SECURE` reports the change to libc); this is how an unprivileged process regains privilege, the mechanism behind `su`. A modification takes the set-id bits away again. Setuid always goes; setgid goes only when the group-execute bit is set beside it, which is the same condition `execve` grants on, so a file that cannot hand out a gid does not have one taken away. The rule runs after a write that moved bytes, after a truncate (`O_TRUNC` and `creat` alike), and after a chown that actually changed a field. Write and truncate spare a privileged caller, or root would disarm `/bin/su` by rewriting it; chown does not, which is why `cp` and `install` chown before they chmod. The change gate on chown is load-bearing rather than an optimization: `chown(path, -1, -1)` needs no right, because nothing moves, so a clear that ran on it would let any caller disarm any set-id file with one call. `chmod` has its own rule, since an owner may mint a set-id mode with no write at all: an unprivileged caller storing a mode on a file whose group is not one of theirs does not keep setgid.

The root node is excluded from all of it by node identity and not by `KRFFS_IS_DIR`, because `mkfs` stamps the root a bare `0755` with no type bits and `KRFFS_MODE_DIRTY` is the same bit as `KRFFS_MODE_SUID`: a clear that reached the root would report an unclean image as cleanly unmounted, which is corruption rather than a permission bug.

What stays out: the sticky bit is stored and reported but its restricted-deletion rule is unenforced, and the access check judged the target and its immediate parent alone until the resolver started charging search on every directory it enters. The setuid bit shares the position of the root node's dirty-mount flag (`KRFFS_MODE_DIRTY`), which is safe because that flag lives only on the root, a directory no exec, chmod, or ordinary stat ever exposes.
* Linear scans: directory lookup and `getdents` walk the node list (no hashing or B-trees), which is fine at teaching scale.
* No hard links, no symlink chains, no journaling. `AT_SYMLINK_NOFOLLOW` is accepted but inert.
* Open-file descriptions are refcounted (the shared seek offset). `fd_entry_t` holds a `struct open_file *`, a small refcounted cell from a fixed pool (`fs/fd.c`) carrying the seek offset, so `dup`/`dup2`/`fork`/`F_DUPFD` share one offset the Unix way (a read or seek through one descriptor is seen by the others), and closing one descriptor leaves the duplicates working until the last reference goes; `release_fd_table` drops every reference when a process dies, so the pool never leaks. The backing object (KRFFS node or socket) and `FD_CLOEXEC` stay per-descriptor (a socket is refcounted per fd; `dup`/`dup2` clear the new fd's CLOEXEC, `execve` closes the marked ones). Probe: `tests/ofdprobe.c` (`OFDPROBE OK`) and the musl `tests/musl/ofdmusl.c` (`OFDMUSL OK`). One caveat remains: KRFFS nodes are not refcounted, so an `unlink`, an `rmdir`, or a write that grows and relocates a file through another descriptor (or another process, on the one shared image) can free or move the node a still-open fd points at. Every file and directory operation defends against this by re-validating the cached node before use (it must still be a live reserved node whose reconstructed path resolves back to it), rejecting a stale descriptor with `-EBADF` rather than touching freed free-list metadata; the regression is `tests/fdstale.c` (`FDSTALE OK`). Within a single syscall the operation is already atomic (the `in_syscall` flag gates timer preemption and the op bodies never block), so the node cannot move mid-call; the hazard is only across syscalls. The round-trip follows an in-place rename (the node stays put, only its name changes) and rejects a freed or relocated node, but it cannot tell a freed node from a different file that the allocator later places at the same address: such a stale fd would then act on the new file. Closing that last window needs a rename-stable inode identity KRFFS does not carry; pinning the inode in the description, so the fd follows the file the Unix way instead of failing, is a later refinement.
* The interactive host FUSE mount stays flat. Images gain directories through `krffs/stageimage.krffs` (the manifest-driven builder, which writes v2 directory nodes directly) and the in-guest `mkdir`; teaching the 1100-line FUSE mount to browse directories is a later convenience, not needed by the kernel or the integration.

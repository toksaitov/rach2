# Advisory locks

`lock.c` keeps the advisory file locks of the three kinds Linux has, and `lock.h` is its interface. The system calls that reach it are `fcntl(2)`'s lock commands and `flock(2)`, in `../syscall_fs.c`; the descriptor layer (`fd.c`) and the close path tell it when a lock's owner goes. A lock is advisory: it stops another lock, and never a read or a write.

## The kinds

A POSIX record lock (`F_SETLK`, `F_SETLKW`, `F_GETLK` and their 64-bit forms) covers a range of bytes and belongs to a process, whose threads are one owner, known by the thread group id. A second lock of the same process over the same bytes replaces the first, of either type, splitting or cutting back what it covers, and locks of one owner and one type that touch are joined, so `F_GETLK` reports one range where one was taken. Every close by the process of a descriptor of the file drops all its record locks on the file, whichever descriptor took them, as POSIX has it, at the close itself even when another thread's call still uses the descriptor and its release waits for that call to end; the close of an `O_PATH` descriptor drops none, as on Linux. A set lock command that gains its lock after another thread closed the descriptor it was called with lets go of the process's locks on the file and fails with `EBADF`, as Linux's does, so no lock outlives the close that should have dropped it. A lock is not inherited by `fork` and is kept by `execve`.

An open file description lock (`F_OFD_SETLK`, `F_OFD_SETLKW`, `F_OFD_GETLK`) is a record lock that belongs to the open file description instead: every descriptor a `dup` or a `fork` made shares it, a close drops it only with the description's last reference, and a second open of the file in the same process is another owner.

A `flock(2)` lock covers the whole file and belongs to the description, as an OFD lock does. flock locks and record locks do not meet: each kind conflicts only with its own, as on Linux.

Two owners' locks conflict when their ranges overlap and one of them is a write lock (`F_WRLCK`, or `LOCK_EX` for flock). A request that conflicts fails with `EAGAIN` (`EWOULDBLOCK` for flock with `LOCK_NB`) or waits, with `F_SETLKW`, `F_OFD_SETLKW` or a flock without `LOCK_NB`, until the conflict is gone. A wait is ended by a signal with `EINTR`, which a handler with `SA_RESTART` restarts. A flock conversion from one type to the other lets go of the old lock first, so it is not atomic, as on Linux. A flock request that waits looks for its description's lock again each time it wakes, as the first look did, so threads that share a description and wait together end with one lock, which one `LOCK_UN` removes.

## The key

A lock is on a file, found by the file's mount and a number that names the file while a description of it is open (`struct lock_key`), which `fd_lock_key` in `../syscall_fs.c` makes from the description, so a close and a lock find the key without reading the volume, even on a mount whose device is gone.

A file of KRFFS, the boot root or a mounted volume, is named by its node as its descriptions have it now: the node's address on the root and its offset plus one on a volume. That is the file itself at any moment, which two files never share and a rename does not change. A write that grows a file past its node can move it, and `vfs_repoint`, which moves every holder of the node to the new one, moves the file's locks too, and the key of every wait for one (`lock_repoint`), so a lock taken before the move meets one taken after it, and a file made at the old place meets none of them. A wait keeps a copy of its key for that, and `fcntl` takes the key again for a lock a wait gained after another thread closed its descriptor. The KRFFS inode number would not do: the root numbers a file by its directory and the hash of its name, which a rename changes and two names can share (`bC` and `cb` do), and a volume by the node's offset, which a move changes. A node's place stays the file's for as long as a descriptor has it, since neither the root nor a volume frees a file a descriptor has, and `rmdir` refuses a directory a descriptor has with `EBUSY`. The last close of a root file that lost its name while open, a FIFO's among them, lets go of the closing description's locks before the root frees the node, since the description's own end comes after the free.

A FAT32 or exFAT file is named by its node too: the driver keeps one node per file while it is held and a rename updates that node in place, where the inode number is the file's directory entry, which a rename changes. A file of another type, ext2 or tmpfs, is named by the inode number it had when the description was opened, which the description keeps (`ino` in `struct open_file`) and which stays with the file.

A descriptor that is not a file of a mounted type, a pipe, a socket, a device or a terminal, is locked by the object it is open on, with no mount, so two opens of one device share its locks as two opens of one file do.

## Deadlock

A wait for a POSIX record lock that would close a cycle of waiting processes fails with `EDEADLK`. The process that waits records whose lock it waits for, and follows the chain of those records from that lock's owner; a chain that comes back to the waiter is a cycle. It does both before it first sleeps and again each time it wakes and still meets a conflict, since the lock that stops it may by then be another owner's: a waiter behind two read locks waits for the second when the first goes, and a cycle through it is found by whichever wait closes it, as Linux finds one when it retries a woken request. The chain is followed ten steps at most, Linux's bound, so a longer cycle is not found. Waits for OFD and flock locks are not checked, as on Linux.

## Limits

The locks are a list from the heap, with no fixed count. A record lock the heap cannot give fails with `ENOLCK` before anything changes, since the records a split needs are had first. A flock lock is taken from the heap last, after a conversion has let go of the description's old lock, so a conversion that fails with `ENOLCK` leaves the description with no lock, as any failed conversion does. Every lock operation walks the whole list, and so does the close of a descriptor whenever any lock exists anywhere (`lock_any`); a close with no lock in the system costs one test.

## Verification

`tests/host/lock_hosttest.c` runs the lock rules on the host: a record lock that blocks another owner's over any byte it covers, `F_GETLK`'s report, an unlock that splits a lock, replacement and joining, a lock to the end of the file, a close that drops the closing process's locks on one file only, OFD locks against each other and against a record lock, flock locks against each other and apart from record locks, a conversion, the end of a description, a waiter whose lock passes to another owner while it sleeps, through which a later wait closes a cycle and fails with `EDEADLK`, two threads of one description that wait for a flock lock together and take one, the three kinds of lock moved with their file, and a record wait and a flock wait whose file moves while they sleep, which meet the holder where it is now and take their lock there. Its wait runs, at each sleep, what other processes do meanwhile. `tests/host/open_hosttest.c` asks `fd_lock_key` for the key of a file on the KRFFS root, on a KRFFS volume and on another type. `tests/musl/lockmusl.c`, in the default suite, runs them between processes on Rach2: a child's lock refusing the parent's, `F_GETLK` naming the child, a split, a close of another descriptor dropping the child's locks, locks of the largest offset and of every byte before it joining into one to the end of the file, `F_SETLKW` waiting for the holder, one `EDEADLK` for two processes that wait for each other, a thread's `F_SETLKW` whose descriptor another thread closes failing with `EBADF` and leaving the byte free, also when a write moves the file during the wait, a lock on a file leaving free another file whose name hashes alike, a lock taken before a rename or before a write that moves the file refusing a lock through an open after it, flock's sharing through `dup` and release at the last close, and an OFD lock conflicting with a second open and with the same process's POSIX lock.

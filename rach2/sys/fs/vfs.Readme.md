# Mounts and the VFS

The virtual file system, the VFS, is the mount table, the path resolver and the operation interface every mounted file system answers, declared in `vfs.h` and implemented in `vfs.c`. Five mounts are permanent: the root, which is KRFFS through the adapter at the end of `vfs.c` or another type placed by the boot path; `/dev` and `/proc`, answered by `synthfs.c`; the tmpfs `/dev/shm`; and the tmpfs of `memfd_create`'s files, which no path reaches. `vfat` (`fat32.c`, [fat32.Readme.md](fat32.Readme.md)), `exfat` (`exfat.c`, [exfat.Readme.md](exfat.Readme.md)), `ext2` (`ext2.c`, [ext2.Readme.md](ext2.Readme.md)), `krffs` (`krffsmount.c`, [krffs.Readme.md](krffs.Readme.md)) and `tmpfs` (`tmpfs.c`, [tmpfs.Readme.md](tmpfs.Readme.md)) are the types `mount(2)` places. A file system `mount(2)` installs, and an ext2 root, read and write the disk through the buffer cache; a KRFFS root on a disk reads and writes through the page cache instead (`bcache.h`), which goes through the block request described in [block/Readme.md](../block/Readme.md).

## The mount table

The table starts with eight slots and grows as mounts are placed. Each mount record has a stable heap address. Entry zero is the root; entries one and two are `/dev` and `/proc`, entry three the tmpfs `/dev/shm`, mounted with `nosuid` and `nodev`, entry four the tmpfs `memfd_create` makes its files on, with no parent and no path, which `/proc/mounts` does not list, and entry five `/sys`, read-only. The six are permanent (`VFS_PERMANENT`), and `umount2` on any of them it can name answers `EBUSY`. The other entries are placed by `mount(2)` and removed by `umount2(2)`.

A mount point is the covered directory's node. The directory a mount covers is held through the parent's `hold` for the mount's life, so it cannot be reached under another spelling, it is what `..` at the mount root climbs to, and it answers `EBUSY` to `unlink`, `rmdir` and `rename` while the mount exists; `mkdir` of that name is `EEXIST`. The entry records the target's path (63 bytes at most; `ENAMETOOLONG` past that) and the source string given to `mount(2)`, for `/proc/mounts` and for the unmount record. The path is the target's from the root of the mount table, which `vfs_node_path` rebuilds from the directory the walk reached on any type, so a target named through a symbolic link, from a root `chroot` gave the caller, or with `.` and `..`, is recorded where it is, and that recorded path is also what an unmount below a removed device matches.

If a removed ancestor makes unmount lookup fail with `EIO`, `umount2` can identify a child by that recorded target without reading the missing medium. The caller names the target from its own root, so the root's path from the root of the mount table is put in front of it first (`unmount_target`), and only a mount at or below the caller's root can match. The complete target must match one active mount below a removed ancestor; an ambiguous name is refused, and a target with a `.` or `..` component matches nothing, since a recorded target has none. Other lookup errors retain their meaning. Unmount still drains operations and checks references, so a held file or child mount remains `EBUSY`. Release children before parents. A live child is synced and flushed normally; a child whose device or backing disk is gone releases its resources without writes.

An entry is free, mounting, active or unmounting. Only an active mount takes new work; the two transitional states answer `EBUSY`. A namespace change sees a mounting entry as a mount point already, so a directory cannot be removed or renamed while a constructor sleeps on its device.

Removal of a backing device makes lookup, metadata, directory and data operations answer `EIO`, including those whose answer was cached. The broken mount is omitted from `/proc/mounts` but retains its references until it can be unmounted. `umount2` may resolve the removed mount's root for this purpose; it still answers `EBUSY` while a file, working directory, process root or child mount holds it, then releases it without writing to the absent device.

## The operations

`struct vfs_ops` is one set of operations per type. `struct vfs_type` is the type's name, which `mount(2)` accepts and `/proc/filesystems` reports, the constructor, and that set. A node handle is the type's own: a place in the image for KRFFS, a pool entry for vfat, a classified path for the synthetic types. Whoever receives a node from `lookup`, `create` or the mount's root owns one hold on it and puts it back; descriptions, working directories and covering mounts keep theirs for as long as they refer to the node.

`open` runs once per successful `open(2)` without `O_PATH` and once per `truncate(2)` that passes its checks, and `release` once at the last close of a description that has a handle; an `O_PATH` description has none. `pin` and `unpin` are for a type that keeps a node only while it is open, which is mounted KRFFS: an `O_PATH` description pins its node when it is made and unpins it at its last close, so that an unlink or a rename over the node leaves it to the description as it would to an open one. Every other type leaves both NULL, since a hold keeps its node, or on the KRFFS boot root the syscall layer's count of the descriptors that refer to it. The handle is the per-open object; a type that needs none returns its node. Mounted KRFFS returns a shared open record that remains valid across relocation. Mounted-file `O_TRUNC` opens first and truncates through that handle; a failed truncation releases it. `truncate(2)` opens a description that no descriptor points at, truncates through its handle under its lock, as `ftruncate` does, and closes it, so a file the truncation moves is found where it is now. Every type counts opens and releases, and the record written at unmount, `vfs: unmounted TARGET: N opens, N releases`, reports both. `read` and `write` take the handle and a 64-bit offset; `truncate` takes the handle and the length the file is to have. `readdir` fills one entry at a cursor whose meaning is the type's (an image offset for KRFFS, an entry index for vfat) and advances the cursor past it; the entry has its name, its inode number and its type as `getdents64` reports it, the type bits of its mode shifted down (`VFS_DT_OF`), or `VFS_DT_UNKNOWN` where the type cannot tell; the caller stores the cursor between calls and does not interpret it. `mknod` makes a FIFO, a socket file or a device node, by the type bits of its mode, with a device number for a device, and returns it held as `create` does: ext2 and tmpfs keep every kind, KRFFS FIFOs and sockets and no device node, since its nodes have no field for the number. `rename` is within one mount; the common layer answers `EXDEV` across two. `path` rebuilds a directory node's canonical path within the mount, for a type whose descriptors must follow a rename; a type that has no use for it leaves it NULL, and KRFFS implements it although it does not rename directories at all. `prepare_unmount` writes the volume's last metadata into cache buffers and dismantles nothing, so it can be repeated or abandoned; `unmount` frees the private state and is not undone; the cache is written between them.

An operation a type does not implement is a NULL pointer, and the wrapper in `vfs.c` answers for it: `EROFS` for the write-side operations (`write`, `truncate`, `setattr`, `create`, `unlink`, `mkdir`, `rmdir`, `rename`), `EPERM` for `link`, `symlink` and `mknod` on a writable type that has none, and `EINVAL` for `read`, `getattr`, `readdir` and `statfs`. A missing `fsync` is not answered with success: the wrapper writes the device's dirty buffers and flushes the device, and returns what either of them failed with. A read-only mount answers `EROFS` to every write-side wrapper whatever the type implements, after the argument checks the wrapper makes first, one of which refuses a size change to a file a loop device stands on. After a namespace operation or a `setattr` succeeds, its wrapper tells inotify what changed, the directory's entry by name and the file by its inode number, when any watch exists ([the io Readme](../io/Readme.md)).

## mount and umount2

Both syscalls require effective uid 0; an unprivileged caller gets `EPERM`.

`mount(source, target, type, flags, data)`: `type` selects a type from the table, which has five: `vfat`, where a mount without `MS_RDONLY` is writable and the constructor checks a volume that was not unmounted cleanly before it publishes the mount, as [fat32.Readme.md](fat32.Readme.md) says; `exfat`, which reads and writes and checks a volume the same way, as [exfat.Readme.md](exfat.Readme.md) says; `ext2`, as [ext2.Readme.md](ext2.Readme.md) says; `krffs`, whose constructor refuses a volume whose first node is not a KRFFS root or whose ring does not tile the device, and repairs a writable volume that was not unmounted cleanly before it publishes the mount, as [krffs.Readme.md](krffs.Readme.md) says; and `tmpfs`, which stands on no device, as [tmpfs.Readme.md](tmpfs.Readme.md) says. An unknown type is `ENODEV`. For `tmpfs`, `source` is any string, recorded for `/proc/mounts`, and nothing is claimed; for every other type, `source` must be a device under `/dev` that has a volume on it: a partition window of the disk (`/dev/disk0p1` to `/dev/disk0p4`, or `/dev/bootpart`), a stick or one of its partitions (`/dev/diskN` and `/dev/diskNpM`), or an attached loop device (`/dev/loop0` to `/dev/loop3`). Another device is `EINVAL`, and a name that is not published, because its MBR entry is empty, the disk was not probed or nothing is attached there, is `ENOENT`. `target` must be an existing directory on a mount that can host one: with a path of at most 63 bytes (`ENAMETOOLONG`), not `/` and not a directory of the synthetic `/dev` or `/proc` themselves, whose types take the rest of a path in one call (`EINVAL`), though a directory of the tmpfs `/dev/shm` below them is a target like any other, not the root of a placed mount and not reserved by a mount in progress (`EBUSY`), a directory (`ENOTDIR`). A relative target is joined to the working directory, and the target is recorded by its path from the root of the mount table, which `vfs_node_path` rebuilds from the directory the walk reached, whatever path named it.

The order of work is: resolve and hold the target; check it; under the parent's namespace lock, so that no namespace change runs between the check and the reservation, claim the source's sectors, or the loop device itself, and take a table slot as `mounting`, which holds the covered directory and counts on the parent; run the constructor under the new mount's namespace lock; publish. Every failure after the first step releases what the steps before it took. A source overlapping a claimed range, or one with a write-capable raw descriptor open over it, is `EBUSY`; no free slot, or a full pool in the type, is `ENOMEM`; the VFS returns the constructor's error, with the reason in the kernel log: KRFFS answers `EINVAL` for a volume whose structure it will not take, `EFBIG` for a device larger than a region it can address, `EIO` for the first read of the root, a write or a repair the medium refused, and `EINVAL` where a read failed inside the walk of the chain, since a chain with an unreadable node in it cannot be judged, and `ENOMEM` when the heap has no room for its record.

`MS_RDONLY`, `MS_NOSUID`, `MS_NOEXEC` and `MS_NODEV` are enforced: `execve` answers `EACCES` on a `noexec` mount and ignores the set-id bits on a `nosuid` one, and `open` answers `EACCES` for a device node on a `nodev` one. `MS_SYNCHRONOUS` and `MS_DIRSYNC` make ext2 flush the disk's cache after each metadata write, the order of [ext2.Readme.md](ext2.Readme.md), and are shown in `/proc/mounts` as `sync` and `dirsync`. `MS_NOATIME`, `MS_NODIRATIME`, `MS_RELATIME` and `MS_SILENT` are recorded and shown in `/proc/mounts`. `MS_REMOUNT` gives the mount whose root `target` names the other flags (`vfs_remount`): a change between read-only and writable goes through the type's `remount`, which ext2 and tmpfs have and the others do not, `EINVAL`; a mount is not made read-only while a descriptor is open on it for writing, `EBUSY`, nor writable on a device that refuses writes or has failed one, `EROFS`. `MS_MOVE` and any other flag answer `EINVAL`. `data` is the type's option string, and what a constructor does with one is the type's: `krffs` reads none at all.

`umount2(target, flags)`: `flags` must be zero (`MNT_FORCE`, `MNT_DETACH` and `UMOUNT_NOFOLLOW` are `EINVAL`), and `target` must be the root of a mount (`EINVAL`); a target that named a directory by its end must reach one (`ENOTDIR`), which the walk that finds the mount checks on the node it found, so a symbolic link replaced between two walks cannot change the answer. The mount goes to `unmounting`, which refuses new descriptions, working directories and operations with `EBUSY`; the operations in progress drain; then the mount is busy (`EBUSY`) while any description, working directory, process root or child mount refers to it, in any process. After that the type syncs and prepares, the cache writes the device's dirty buffers, `block_flush` sends the device's own flush (`SYNCHRONIZE CACHE` on a stick; a disk driver has already flushed after each write and has none), and the cache drops the buffers (a failure of the type's two operations returns the mount to `active` with the type's errno, a failed writeback or flush with `EIO`, and a buffer still held or dirty at the drop with `EBUSY`; nothing irreversible has happened), the type's `unmount` runs, and the covered directory and the claim are released. The record `vfs: unmounted TARGET: N opens, N releases` goes to the kernel log.

## Bind mounts

`MS_BIND` places a mount record that shows a directory of a mounted file system at another directory (`vfs_do_bind`). The record has the type, device and private state of the mount it was made from, its base (`bind_of`), never itself a bind, and its own root, the source directory, held for its life, its own place, and its own flags, copied from the source's mount. The target is checked and covered as a mount's is (`target_check`, `mount_place`). The base counts the bind among its references, so it cannot be unmounted while a bind of it stands; the bind is unmounted as any mount is, with nothing written, since the base still shows the file system.

A type never sees a bind: every wrapper in `vfs.c` passes the base to the type's operation, and the namespace lock of a bind is its base's, so two mounts of one file system serialise as one. A write through a bind is refused when the bind or its base is read-only (`mount_rdonly`); `MS_REMOUNT` with `MS_BIND` changes the bind's flags alone (`vfs_remount_bind`), and without it changes the base's. What names a file by its mount and inode number names it by the base (`vfs_mount_base`): record locks, inotify watches, FIFOs, socket files, shared file mappings, the descriptions an unlink or an attachment checks, and the device `stat` reports. A walk inside a bind stays on the bind, so `..` at its root climbs to the directory it covers, `vfs_node_path` gives a path below the bind's place, and the mounts below the source are not under the bind unless `MS_REC` placed a bind of each (`bind_below`).

KRFFS is refused as a source, since it moves its nodes and repoints only the references of its own mount. A synthetic type is refused but at its root, since it resolves the rest of a path by its fixed prefix: a bind of `/dev`, `/proc` or `/sys` resolves as the original, which is what a chroot needs. `/proc/PID/mountinfo` gives a bind its base's device and its root's path within the file system.

## The resolver

Every path-taking syscall calls `vfs_resolve`, which walks one component at a time: one name in one directory on one mount. Before each step the common layer checks the caller's search permission on that directory, so the check is made once per component and the same way for every type. A component on the way to the caller's working directory is not checked (`toward_cwd`): the syscall layer joins a relative name to the working directory's path and the walk starts at the root, where Linux starts at the working directory and checks nothing above it, so a process left in a directory it cannot reach by its path, as `su` to an ordinary user from root's home leaves one, still names files there. `..` is physical: at the root of a mount over a directory the resolver moves to the covered directory and resolves the same `..` there, in the parent mount; at the root of a nameless mount, which stands by name in its parent's root directory, `..` is that directory; at the root of the root and at a root `chroot` gave the process it stays; and anywhere else it is a `lookup` of `..`. A path that names a missing or unsearchable directory before its `..` fails, as on Linux. The spelling `/x/../proc` reaches `/proc` through `/x` when `/x` is a searchable directory and fails otherwise; neither answer bypasses anything.

On a type with `readlink`, a component that is a symbolic link is followed when more of the path comes after it, and at the last component unless the caller passed `VFS_WALK_NOFOLLOW`; the implementations of `lstat`, `lchown`, `readlink`, `unlink`, `rename`, `link`, `symlink`, `rmdir`, `fchownat` and `utimensat` with `AT_SYMLINK_NOFOLLOW` and `open` with `O_NOFOLLOW` or `O_CREAT|O_EXCL` pass it. The target replaces the component: an absolute target restarts at the process's root, a relative one continues from the directory the link was found in, and the target with the rest of the path must fit `VFS_PATH_MAX`, 4096 bytes with the terminator, as a path does (`ENAMETOOLONG` past it). The target and the path it is joined into are in two path pages ([Readme.md](Readme.md)), which the walk takes at its first link and gives back when it returns; a walk that meets no link takes none. Forty links along one path are followed; the forty-first answers `ELOOP`. A type's `getattr` decides whether a node is a link, and an error from it fails the walk. [ext2.Readme.md](ext2.Readme.md) has the rules by operation.

A path that enters a mount while it is mounting or unmounting answers `EBUSY`. `/dev` and `/proc` are reached by name from the root directory, because the root file system has no node for them, and `/dev/shm` by name from `/dev`'s root directory, because devfs has none; nothing else is reached by name. The synthetic types report a directory or a leaf to the resolver, so `/dev/null/x` is `ENOTDIR` like any file used as a directory.

With `VFS_WALK_LOCK`, resolution locks each mount before lookup, releases that lock when crossing to another mount, and returns with the final mount locked. Open and loop attachment use this mode and retain the lock through open-handle registration. Creating an open file retains the parent lock through creation and registration, and `mkdir` retains it from its lookup of the new name through the creation, so a directory another process makes meanwhile is `EEXIST` and not a refusal of the file system. The calls by path that read or change a node, the stat calls, `access`, `chmod`, `chown`, `utimensat` and `truncate`, keep the lock until they have read or changed it, since a node of a mounted KRFFS volume is its offset, which a growing write that holds the lock moves. A failed resolution releases its lock.

A resolution returns a `vfs_ref`: the mount and a held node, with the mount's in-progress count taken, so the mount cannot unmount while the caller uses the node. The caller ends with `vfs_ref_release`. `VFS_WALK_PARENT` stops before the last component and returns the held parent with the leaf name copied out, which is where `create`, `unlink`, `mkdir`, `rmdir` and `rename` start; `VFS_WALK_REAL_IDS` checks search permission with the real ids, for `access(2)`.

The two synthetic types are the one exception to component lookup. A type with `lookup_rest` instead of `lookup` is handed the rest of the path in one call, because its namespace is a flat table classified by string. A `..` in that remainder that would climb above the mount root answers `VFS_CLIMB` with the unconsumed remainder, and the resolver continues at the covered directory. Such a type cannot host a mount point; `mount(2)` on a directory of `/dev` or `/proc` themselves answers `EINVAL`, and one on a directory of a mount standing in them, as `/dev/shm` does, is placed as on any other type. A nameless mount can stand in its root directory instead, as `/dev/shm` stands in `/dev`'s: at such a type's root, the resolver takes the first name of the remainder and enters the mount it names before the type sees the rest, and `..` at that mount's root climbs back to the synthetic root, whose own `..` climbs on. When the type's own `.` and `..` bring the remainder back to its root directory in front of such a name, it answers `VFS_ROOT` with the rest from that name, and the resolver enters the mount the same way, so `/dev/pts/../shm` is `/dev/shm`. The `/dev` listing shows each such mount as a directory. When the node such a type returns is a link its `getattr` reports, `/proc/<pid>/exe`, the resolver follows it at the last component unless the caller passed `VFS_WALK_NOFOLLOW` or wants the parent: it goes on from the program's file itself, the node and mount the process's address space keeps (`walk_exe`), moving to the root of that mount, taking its lock for a locked walk, and reading the file again there before it holds the node, since the wait may let the file move. A link of such a type other than that one would be followed by the text its `readlink` reads, as a link of a mounted type is (`walk_link`).

## Descriptions and the working directory

An open-file description on a mounted file system holds its mount, its node and the handle (`fd.h`). A directory descriptor's `*at` calls resolve against the directory's current path: a type with a `path` operation rebuilds it, so the descriptor follows a rename of the directory; a type without one keeps the path the descriptor was opened by. The rebuilt path is the covered directory's path and then the type's, and it must fit `VFS_PATH_MAX` with the name joined to it; ext2 climbs up to 2048 directories to rebuild one, which is as deep as a path of that length goes, FAT32 32, exFAT and KRFFS 64, and a deeper directory answers `ENAMETOOLONG`. `read`, `write`, `lseek`, `getdents64` and `ftruncate` hold the description for the length of the operation, so two processes sharing one description cannot both read one offset while one of them sleeps in a disk request, and every byte of a file read through a shared description is handed out once; `pread64` and `pwrite64` hold it on a regular file too and leave its offset alone. A process whose working directory is inside a mount holds that mount, and the node through the type's `hold` where it has one; `/dev` and `/proc` need no such hold and take none. KRFFS, the boot root and a mounted volume, has no `hold`: the record keeps the mount's count and the node all the same, since `rmdir` refuses a directory that is a process's working directory, and `chdir` on a volume pins the directory (`pin`) from its walk to its record; a root placed through another type is held like any other mount. A change of working directory stores the new path and the new hold before it lets go of the old hold, whose put may sleep, so a thread that shares them (`CLONE_FS`) and changes them meanwhile replaces what is in the record, and the hold always matches the path. A child mount holds its parent. The address space of a running image keeps a description of its program's file, which holds the node and the mount as any description does (`fs_exe_open`), so a volume is busy while a program on it runs, as on Linux. The mount's reference count is its descriptions, working directories, process roots and child mounts, and it is what `umount2` reports as busy.

When KRFFS relocates a node, `vfs_repoint` moves every reference to it: descriptions, working directories, process roots, directory descriptors, covering mounts, the loop devices backed by it, and the advisory locks on the file and the waits for them, since a KRFFS file's locks are found by its node ([lock.Readme.md](lock.Readme.md)). An unmount that gets past `prepare_unmount` and then fails at the cache's writeback, the device's flush or the invalidation calls the type's `abort_unmount`, which undoes what it wrote for an unmount that is not happening: KRFFS sets the dirty flag again, ext2 clears its valid bit, and a volume whose write of it fails is made read-only. If KRFFS fails while clearing or flushing its dirty flag during preparation, it makes the mount read-only before returning the error.

## A process's root

A process has a root directory, the root of the mount table unless `chroot(2)` gave it another: `root_mnt` and `root_node` in its record, set by `vfs_root_set`, given to a child of fork by `vfs_root_copy`, kept by exec, and let go at exit by `vfs_root_clear`. `vfs_root_set` stores the new root before it lets go of the old one, whose put may sleep, and `chroot` stores the working directory's new path just before the root, with nothing between the two that sleeps, so a thread that shares them (`CLONE_FS`) always finds a root in the record, and never joins a path from one root to the other. The resolver starts an absolute path there (`walk_root`), restarts an absolute symbolic link's target there, and answers `..` there with the root itself (`dotdot_stays`); nothing else in the walk knows about it, so every call that resolves a path is confined the same way. A walk keeps the root it started from. When a thread that shares it chroots while the walk sleeps, the walk finds that at its next `..` or absolute link (`root_current`) and starts over from the new root, so no walk judges one path by two roots. `..` at the root of the mount table stays there whatever root the walk has. The root holds its node and counts on its mount, as a working directory does, so `umount2` answers `EBUSY` while a process has its root on the mount. `rmdir` answers `EBUSY` for a directory that is any process's root (`vfs_leaf_root`), where Linux refuses only `/` by the path that names it and a mount point, and removes a directory `chroot` made a root: the resolver here starts from the root's node, and the KRFFS root and a mounted KRFFS volume count no holds on their nodes, so a removed root would be memory the next walk read.

The syscall layer keeps paths as strings, and joins a relative path to the working directory's or a directory descriptor's before it resolves. The strings a process gives and sees are therefore paths from its own root: the working directory, what `getcwd` returns, and the path a directory descriptor's `*at` calls start from. What the kernel records for itself is a path from the root of the mount table: a mount's covered path, which `vfs_do_mount` takes from the directory (`vfs_node_path`) and not from the path that named it, and the path a type rebuilds for a directory. `path_in_root` in the syscall layer turns such a path into the process's by taking the root's own path off its front. A directory outside the root has no path of the process at all. The `*at` calls join a name relative to a descriptor of one to the directory's path from the root of the mount table and begin the joined path with three slashes, which no canonical path the caller wrote has, and the walk starts a path that begins with two, as it still does once the layer takes its first slash off, at the root of the mount table while it keeps the process's root for `..` and for absolute links, so the descriptor reaches the tree outside the root as it does on Linux; a browser's sandbox reads `/proc` this way through a descriptor it opened before its chroot. `fchdir` answers `ENOENT` for such a descriptor, and `chroot` moves a working directory outside the new root to the new root, while one inside keeps its place under its path from the new root. This is where the design differs from Linux, whose working directory is a place and not a path: there a working directory outside the root still reaches the tree outside it. The KRFFS root reads a file by path, so exec reads a dynamic linker there by its node's path from the root of the mount table, which is not the path the process gave; the program itself it reads through the description its new address space keeps, at the node the file is at now.

`/dev` and `/proc` stand by name in the root directory of the mount table and nowhere else, so no other root reaches them; a program in such a root makes device nodes with `mknod(2)`, which open the device with their number. A directory of either cannot be a root (`EINVAL`), because their types take the rest of a path in one call, where the resolver could not stop `..`. The root is in the record `clone` with `CLONE_FS` shares, with the working directory and the umask (`struct fs_struct`), so the threads of a process have one root; `fork` gives the child a copy.

## Locks

The order is fixed and checked: the mount table, then a mount's namespace lock, then a description, then cache buffers in ascending block order. A process holding one may take only what comes after it. The namespace lock is taken by every namespace change on the mount, by the constructor, and by the unmount; a type that writes takes it itself for `write`, `truncate`, `fsync`, `sync` and the reclamation a last `put` performs, so every mutation of a volume runs under one lock. Mounted descriptor operations take the namespace lock before the description lock, including while selecting EOF for append. The holder may take it again, because those operations are also reached under it (the unmount calls `sync`, a namespace change puts a node), and one process cannot wait for itself. The kernel does not preempt inside a syscall, so a second process meets a held lock only while the holder sleeps in a disk request. Every wait for a lock, a busy buffer or a request is uninterruptible: a pending signal would otherwise end the wait at once, and a waiter that retries without sleeping never gives the CPU to the holder. A type's `put` may sleep: it takes the namespace lock, and it may free what an unlinked file held. `release` may: the KRFFS volume's takes the mount's lock and frees the node when the last close of an unlinked file reclaims it, which is a write like any other.

## Claims

The root is entry zero: KRFFS through `vfs_init`, or a type with a device through `vfs_init_root`, which `rach2.root=ext2` uses for the partition the kernel found itself, with the window's claim kept in the entry; either way `/dev` and `/proc` are installed over it, and the syscall layer takes its KRFFS-specific paths only when entry zero is KRFFS. A claim is a sector range on the backing disk, held from the mount's constructor to its unmount. The table of eight is in `devfs.c`, beside the raw windows' single-writer rule. Ranges are compared as ranges and never as device pointers, because `/dev/bootpart` and `/dev/disk0p1` can describe one range. A loop device has no range to compare: the device is the identity, and one mount at a time may stand on it. While a range is claimed, a second mount overlapping it and a write-capable open of a raw window over it answer `EBUSY`; while such a descriptor is open, a mount on the range answers `EBUSY`. This is how a mounted boot partition and `bootctl` exclude each other.

## The buffer cache

`bcache.c` is the cache under the mounted file systems, whose buffers are made as they are needed, with the operations from Lions' commentary: get a block and hold it, release it, mark it dirty, write a device's dirty buffers, drop a device's buffers at unmount. The buffers are 4 KiB, a block being eight sectors, made as they are needed up to the smaller of half of what the caches together may hold under memory pressure and half of the kernel heap's pages (32768), and never fewer than sixteen; the last block of a device whose sector count is not a multiple of eight is read and written as the sectors that exist. A buffer is keyed and held before its fill, so two misses for one block fill it once. A miss at the block after the last one filled is a reader going through the device in order, and fills that block and the whole blocks after it that are not cached, as many as the device takes in one request, from one read. A block a writer will replace whole is taken blank, zeroed and not read, which is what the FAT drivers' whole-block writes and zero fills do; a cached block is returned as it is. The victim is an empty buffer, then a new one while the cache is under its limit, then the least recently released buffer nothing holds, passing over a dirty one whose writeback the rules below would not allow this caller to make; the keyed buffers are kept in release order and the empties on a list of their own, so neither choice reads every buffer. The cache counts the buffers its walks of its lists read, printed as `cache-visits` in `/proc/disk`, and `tests/host/bcache_cost_hosttest.c` holds a get, a victim's choice and a sync to bounds on that count.

A held buffer is busy. A second process reaching it sleeps on the buffer's queue and is woken at release; the wait is counted in `/proc/disk`. Two checked rules prevent deadlock: a process holds at most four buffers, and a buffer it takes must be a higher block of a device it already holds a buffer of, or a block of a device below every device it holds a buffer of. The buffers a process holds are on a list of its own in its process record, which is what the rules are checked against at each acquisition. A release, a dirty mark or a write by a process that does not hold the buffer is a defect too. The cache panics on a violation, so a file system that breaks a rule fails in the host test.

A type that writes its metadata with `bcache_write` has it written through: the buffer reaches the device before the call returns, so the order in which that driver writes metadata is the order in which it reaches the disk. KRFFS marks metadata dirty like data and enforces its order at the sync points in [krffs.Readme.md](krffs.Readme.md). ext2 retains regular-file data and metadata in private bounded batches and admits images to the cache only after their dependencies are durable, as [ext2.Readme.md](ext2.Readme.md) specifies. Data goes through `bcache_dirty` and reaches the disk at eviction, at `fsync`, at `sync`, and through the periodic sync. A dirty victim is written before its buffer is reused. A file system may give a dirty buffer a place in its device's order through `bcache_dirty_ordered`: a `first` buffer reaches the device before any `after` buffer of the device, whichever path writes, since an eviction or the memory reclaim that chose an after writes the device's firsts before it, or passes it over while one of them is held or failed its write, and a sync writes the firsts before the rest in requests of their own; the marks clear with the write. ext2 uses these marks for freeing blocks: pointers go first and allocation records after. A collecting file-write batch uses private images instead of the marks. `bcache_sync` writes a device's dirty buffers in ascending block order, the firsts before the rest, in runs of adjacent blocks of up to what the device takes in one request, waits for one another process holds rather than passing over it, and answers the first failed write's errno with that buffer still dirty for the next call; it gathers the blocks to write in batches of the lowest hundred and twenty-eight, so a sync of a large file scans the cache a few times and not once per run.

`fsync(2)` on a mounted file's description runs the type's `fsync`, or writes the device's dirty buffers when the type has none, and then, when that succeeded, the device's own flush; `sync(2)` runs, for every active mount that has a device and admits an operation, the type's `sync`, the cache's writeback for its device and, when the writeback succeeded, the device's own flush, before the page cache's own; it ignores every result and always answers 0, as `sync(2)` does. Data is also written back every thirty seconds by `/bin/update`, a process `init` starts on the images that run one, as V7's `update` did: the kernel's timer cannot sleep and the kernel has no thread of its own to give the work to. `rach2.blockfail=N`, beside `rach2.blocklag`, makes the Nth write through the lag device fail with `EIO`, which is how the read-only transition is seen in a boot.

## On failure

The cache answers a device that goes and a write that fails once each, for every type above it. The first is a device removed while it is mounted. When a stick is pulled out, its buffers cannot reach it again: a clean buffer nobody holds is dropped, a dirty one records the device as failed, which takes its mounts read-only by the rule below, and is then dropped, since an unmount waits for the dirty ones to go and nothing will ever write them, and a buffer a process holds is marked to be dropped when that process releases it, because a buffer cannot be reused under its holder. Every read on the mount answers `EIO` from then on, and a write `EIO`, or `EROFS` once a dirty buffer has put the mount read-only; `umount2` succeeds once nothing holds the mount, and that unmount writes nothing, since the device takes nothing, and only lets go of what the mount held.

The second is a write that fails while the device is still there. A write that fails, through `bcache_write` or through writeback, is recorded against the device: every mount on it goes read-only for the rest of its life, with a record in the kernel log naming the sector, every later write on it answers `EROFS`, and `/proc/mounts` shows `ro`. The cache refuses the device's next `bcache_write` with `EROFS` as well, so an operation that was in progress when the write failed stops at its next step instead of writing across the transition; the refusal ends when the unmount drops the device's buffers. A type that marks its metadata dirty rather than writing it through, which KRFFS does, is stopped by the mount going read-only rather than by that refusal. There is no finer policy, because a write-back cache cannot return a later failure to the `write(2)` that dirtied the buffer, and a volume whose disk has started refusing writes is not a volume to keep writing. A mount that went read-only stays so until it is unmounted; a remount does not make it writable. Its unmount still writes the dirty buffers and flushes the device; a write that fails there leaves the mount in place, and the type leaves the volume marked dirty for the next mount's check. A sector torn in the middle of a write, or a write the disk acknowledged and lost, is outside what the cache can see; the volume check on the host is what judges the disk afterwards.

## Limits

The counts here come from the heap and not from a table. The mount table starts at eight slots and doubles when they are taken; the synthetic nodes, the nodes of every placed type, the KRFFS volume records and their per-open records all come from the kernel heap, so what bounds them is memory, and a mount or an open the heap cannot serve answers `ENOMEM`. What remains fixed is the shape of a path and the rules a caller is held to: a target path of 63 bytes, a name of 255, a path of 4096 with its terminator and a followed link's target with the rest of its path in the same, forty links along one path, eight claims in `devfs.c`, four buffers held per process, and a buffer the cache makes as it needs them, up to the smaller of half of what the two caches may hold under memory pressure and half of the heap's pages, and never to a limit below sixteen. The block request below is sixteen live requests unless `rach2.blockpool` says otherwise, of at most 2048 sectors and of what a device's own limit allows, each given four deadline periods of thirty seconds, as [`block/Readme.md`](../block/Readme.md) describes. `dev-log/53-audit/bounds.md` is the whole inventory, with each bound's class and reason.

## What is absent

`MS_MOVE`, a bind of a directory on KRFFS or inside `/dev`, `/proc` or `/sys`, a remount between read-only and writable on KRFFS, FAT32 and exFAT, `MNT_DETACH` and `MNT_FORCE`; a mount point on a directory of `/dev` or `/proc` themselves; symbolic links on KRFFS, FAT32 and exFAT; access-time updates.

## Verification

`vfsprobe` runs in the default boot: the errno every path form answers, physical `..` through a missing or non-directory component, what a description keeps across unlink, rename and relocation, `ftruncate`, and the statfs identities. `tests/run mount` is fourteen boots on a disk whose second partition is a FAT32 volume: the partition nodes and a read sleeping through the lag device; a device that never answers in time; the root beside a lagged partition; a write copied into the request page before the device sleeps; `mountprobe`, which is `mount(2)` and `umount2(2)` from a program with the flags, the busy answers, the claims and the `/proc` files, plus an awk over the unmount records; the mounted half of `lagprobe`, where a rmdir of the target during a sleeping constructor, a busy-buffer wait and a shared description are observed; the boot partition mounted read-only refusing the raw writer; BusyBox on os-real mounting, listing, reading and unmounting the volume, with the listing compared against mtools; a write the device fails under `rach2.blockfail`, after which the mount is read-only and says so; a pool of two slots with three readers on one disk; a first partition that never answers, where the raw reader takes the error; sixteen requests queued behind the one the disk holds; a megabyte left dirty with the memory then taken from under it; and one process taking every frame outside the reserve before it forks. `tests/run fatwrite` is the writer's proof ([fat32.Readme.md](fat32.Readme.md)). `tests/run ext2` runs `ext2probe`'s symbolic-link rows on a mounted ext2 volume ([ext2.Readme.md](ext2.Readme.md)). `tests/run host` runs `bcache_hosttest`, `fat32_hosttest` and `ext2_hosttest` ([tests/host/Readme.md](../../../tests/host/Readme.md)).

`sh tests/system/vfs_unmount_test.sh --mutate` compiles the production unmount functions with counted filesystem substitutes. Eighteen checks cover live and removed children, open descriptions, draining operations, release of the parent reference and claim, a live child's sync failure, a removed grandparent, refusal of unrelated or ambiguous targets, a target named from a root `chroot` gave the caller, found below that root and nowhere else, and a target named as a directory by its end: one that reaches a file is `ENOTDIR` from the one walk, one that reaches the mount point of a removed device unmounts it with no read of its attributes, which that device's file system refuses, and one below a removed device unmounts by its recorded name. Removing the recovery lookup, comparing the target without the caller's root, dropping the check that the walk's node is a directory, and reading a mount point's attributes for such a target must each fail before the restored functions pass again. The `usbdisk` suite runs the fixed checks, then removes a stick with FAT32 below exFAT and with exFAT below FAT32 in its two existing pull boots. Both must release child and parent mounts, reclaim the device and accept its replacement.

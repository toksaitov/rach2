# Mounts and the VFS

The virtual file system, the VFS, is the layer between the system calls and the file systems: the mount table, the path resolver, the table of operations every type answers, `mount(2)` and `umount2(2)`, and the buffer cache the disk file systems read and write through. It exists so that one resolver, one permission check and one set of default answers serve every type, and a type implements only the operations it has. The table and the resolver are `vfs.h` and `vfs.c`; the cache is `bcache.h` and `bcache.c`. Descriptors, the copying of paths in the system calls, modes and durability are described in [Readme.md](Readme.md).

## Interfaces

* `mount(2)` and `umount2(2)`, system calls 21 and 52 on i686 and 165 and 166 on x86-64, with `MS_BIND`, `MS_REC` and `MS_REMOUNT`. [mount.2](../../../man/man2/mount.2) has the flags, the order of the checks and the errors. `sys_mount` and `sys_umount2` in `syscall_fs.c` check privilege, copy the strings and make the target absolute; `vfs_do_mount`, `vfs_do_bind`, `vfs_remount`, `vfs_remount_bind` and `vfs_do_umount` do the rest.
* The types `mount(2)` finds by name, in the order `vfs_type_at` gives them to `/proc/filesystems`: `vfat` ([fat32.Readme.md](fat32.Readme.md)), `exfat` ([exfat.Readme.md](exfat.Readme.md)), `ext2` ([ext2.Readme.md](ext2.Readme.md)), `krffs` ([krffs.Readme.md](krffs.Readme.md)), `tmpfs` ([tmpfs.Readme.md](tmpfs.Readme.md)) and `mqueue` ([../ipc/Readme.md](../ipc/Readme.md)). The type `proc` is accepted only over a directory of `/proc`, where it succeeds and changes nothing. [proc.5](../../../man/man5/proc.5) describes `/proc/mounts`, `/proc/PID/mountinfo` and `/proc/filesystems`.
* For a file system: `struct vfs_type`, with the name, the constructor, the operations and the `ns_serialised` and `nodev` bits, and `struct vfs_ops`, both in `vfs.h`.
* For the system call layer: `vfs_resolve` and its flags, `vfs_ref_release`, the wrappers `vfs_read` to `vfs_statfs`, `vfs_desc_open` and `vfs_desc_close`, `vfs_cwd_set`, `vfs_root_set`, `vfs_node_path`, `vfs_leaf_mount`, `vfs_leaf_root`, `vfs_sync_all` and `vfs_repoint`.
* For the disk file systems: `bcache_get`, `bcache_get_blank`, `bcache_release`, `bcache_dirty`, `bcache_dirty_ordered`, `bcache_write`, `bcache_write_unflushed`, `bcache_sync`, `bcache_sync_unflushed`, `bcache_invalidate` and `bcache_dirty_heavy`; for the disk layer `bcache_device_gone`, and for memory reclaim `bcache_shrink`.
* Kernel log records, which the suites read: `vfs: mounted: SOURCE on TARGET (TYPE)`, with `, read-only` after the type for a read-only mount; `vfs: bound: SOURCE on TARGET`; `vfs: remounted: TARGET (read-only)` or `(writable)`; `vfs: unmounted TARGET: N opens, N releases`; and `vfs: read-only: TARGET: write of sector N failed (ERRNO)`.
* `/proc/disk` has the cache's counters `cache-hits`, `cache-fills`, `cache-waits` and `cache-visits`.

## Design

### The mount table

`mounts` in `vfs.c` is an array of pointers to `struct vfs_mount` records. A record comes from the heap when its mount is made and goes back at the unmount, so its address does not change when the array grows. The array starts with eight slots and doubles when a new mount finds none free. The first seven entries, `VFS_PERMANENT`, are made at boot and never unmounted:

| Entry | Path | Type | Flags |
| --- | --- | --- | --- |
| 0 | `/` | KRFFS, or a type with a device | |
| 1 | `/dev` | devfs | |
| 2 | `/proc` | proc | |
| 3 | `/dev/shm` | tmpfs, root mode 1777 | nosuid, nodev |
| 4 | none | tmpfs of `memfd_create`, root mode 0555 | nosuid, nodev |
| 5 | `/sys` | sysfs | ro, nosuid, nodev, noexec |
| 6 | `/dev/mqueue` | mqueue | nosuid, nodev, noexec |

`vfs_init` installs the KRFFS root at entry 0, and `vfs_init_root` a root of another type, the ext2 root of `rach2.root=ext2` ([../../Readme.md](../../Readme.md)), with the partition's claim kept in the entry; either then installs the other six (`install_permanent`). A permanent mount that fails to construct panics. A mount placed by `mount(2)` takes a slot past the permanent ones.

A record has its type, its device (NULL for a type with none), its flags, its state, its parent and the node it covers, the covered path (its target's path from the root of the mount table, at most 63 bytes), the source string (kept to 31 bytes), a reference count, a count of operations in progress, its namespace lock, its root node, the type's private state, the counts of opens and releases, its first write error, its claim, the mask of mount namespaces that do not see it (`ns_hidden`, [../proc/ns.Readme.md](../proc/ns.Readme.md)), and for a bind its base and the path of its root within the base.

A mount is `VFS_FREE`, `VFS_MOUNTING`, `VFS_ACTIVE` or `VFS_UNMOUNTING`. `vfs_enter` counts an operation in `inprogress` and refuses with `EBUSY` unless the mount is active; `vfs_leave` ends it and wakes an unmount waiting for the count to reach zero. A resolution returns with that count taken on the mount it ends on, and `vfs_ref_release` puts the node and leaves the mount. `refs` counts what keeps a mount from being unmounted: its open file descriptions (`vfs_desc_open`), the one each address space keeps of its program among them, the working directories and process roots on it, its child mounts, and the binds that show it.

A mount point is the covered directory's node, held through the parent type's `hold` for the life of the mount. The resolver replaces it with the mount's root (`mount_covering`), `..` at the mount's root climbs back to it, and `vfs_leaf_mount` shows it to a namespace change, so `mkdir` of its name answers `EEXIST` and `unlink`, `rmdir` and `rename` answer `EBUSY`. A mount still `VFS_MOUNTING` covers its node as an active one does, so a directory cannot be removed or renamed while a constructor sleeps on its device.

The synthetic types have no node to cover, so `/dev`, `/proc` and `/sys` are nameless mounts: each is entered by the last component of its covered path from the root directory of its parent (`mount_named_at`), and `/dev/shm` and `/dev/mqueue` are entered by name from `/dev`'s root directory in the same way. The memfd tmpfs has no parent and no path, and no walk reaches it.

### Types and operations

`struct vfs_ops` is one table per type. A node handle is the type's own: an address in the mapped image for the KRFFS root, an offset plus one for a KRFFS volume, a heap record of a classified path for the synthetic types. Whoever receives a node from `lookup`, `create`, `mknod` or a mount's root owns one hold on it and puts it back; a type whose nodes need no counting leaves `hold` and `put` NULL. `open` runs once for each description that opens the node and returns the per-open handle, or the node itself for a type that needs none, and `release` runs at the description's last close; an `O_PATH` description has no handle and runs neither. The counts of opens and releases go into the unmount record.

An operation a type does not have is a NULL pointer, and the wrapper in `vfs.c` answers for it, so each default is written once: `EROFS` for `write`, `truncate`, `setattr`, `create`, `unlink`, `mkdir`, `rmdir` and `rename`; `EPERM` for `link`, `symlink` and `mknod`; `EOPNOTSUPP` for `fallocate`; and `EINVAL` for `read`, `getattr`, `readdir` and `statfs`. A missing `fsync` writes the device's dirty buffers instead. Every wrapper but `vfs_release` answers `EIO` once the mount's device has gone, and the write-side wrappers answer `EROFS` on a read-only mount, or a bind whose base is read-only, before they call the type. `vfs_truncate`, `vfs_fallocate` and a size change through `vfs_setattr` answer `EBUSY` for a file that backs a loop device.

The wrappers enforce the immutable and append-only flags a type reports through `getattr` with `flags_known` set, which only ext2 does, by Linux's rules (`notify_change`, `may_delete`, `may_create`, `vfs_link`, `vfs_fallocate`): `setattr` of anything but the flags is `EPERM` on a file with either; `unlink`, `rmdir` and `rename` take no name out of a directory with either nor away from a file with either; `rename` puts no name into an immutable directory and replaces no file that has either flag or is in an append-only directory; `link` makes no name for a file with either nor in an immutable directory; and `fallocate` changes no immutable file and on an append-only one only allocates, with or without `FALLOC_FL_KEEP_SIZE`. After a namespace change or a `setattr` succeeds, the wrapper tells inotify while any watch exists ([../io/Readme.md](../io/Readme.md)), and a write, a truncation or a size change drops the file's pages from the file cache ([../mm/Readme.md](../mm/Readme.md)).

`ns_serialised` asks for the mount's namespace lock around a description's use of the file system. The KRFFS root, KRFFS volumes, ext2 and tmpfs set it: KRFFS moves a file's bytes while the file is open, and ext2 keeps a batch of dirty blocks between calls, so an open on either must register its description under the lock. FAT32, exFAT, mqueue and the synthetic types leave it clear, so that two readers of one volume reach the buffer cache together. `nodev` marks a type with no device: `mount(2)` takes any source string for it and claims nothing.

`vfs_repoint` is how a KRFFS relocation reaches everything that refers to the moved node: the working directories and process roots, the mounts covering it, the mount's root, the descriptions (`fd_ofd_repoint`), the loop devices (`loop_repoint`), and the advisory locks and their waits (`lock_repoint`, [lock.Readme.md](lock.Readme.md)). It does this on the moving mount and on each bind of it, and on the boot root also in every descriptor table.

### The resolver

`vfs_resolve` walks a path one component at a time: one name in one directory on one mount. An absolute path, or any path when `start` is NULL, starts at the caller's root; otherwise the walk starts at the directory an `*at` call passes. The system call layer has already joined a relative path to the working directory's ([Readme.md](Readme.md)). A path that begins with two slashes starts at the root of the mount table and keeps the caller's root for `..` and absolute links; the system call layer makes one for a name relative to a directory descriptor outside the caller's root.

Before each component the resolver checks search permission on the directory (`may_search`), once and in the same way for every type: the nine-bit rule over what `getattr` reports, one identity class chosen and judged alone, by the effective ids or, with `VFS_WALK_REAL_IDS` for `access(2)`, the real ones, and uid 0 passing unless the thread gave up its capabilities. A type without `getattr` is searchable. A component on the way to the caller's working directory is not checked (`toward_cwd`): the walk starts at the root where Linux starts at the working directory and checks nothing above it, so a process left in a directory it may not reach by its path, as `su` from root's home leaves one, can still name files there.

A component longer than `VFS_NAME_MAX`, 255 bytes, is `ENAMETOOLONG`. Then:

* `.` is passed over.
* `..` is physical. At the walk's root, and at the root of the root mount whatever the walk's root is, it stays. At the root of a mount over a directory the walk moves to the covered node and takes the same `..` again there. At the root of a nameless mount it is the parent's root directory. Anywhere else it is the type's `lookup` of `..`. A missing or unsearchable directory before a `..` fails the path, as on Linux.
* In a root directory, the name of a nameless mount there enters that mount.
* Otherwise the type's `lookup` gives the node. On a type with `readlink`, a node `getattr` reports as a symbolic link is followed when more of the path comes after it, and at the last component unless the caller passed `VFS_WALK_NOFOLLOW`. The target replaces the component: an absolute one restarts at the walk's root, a relative one goes on in the directory the link was found in. The target and the rest of the path must fit `VFS_PATH_MAX`, 4096 bytes with the terminator (`ENAMETOOLONG`); the forty-first link is `ELOOP` (`VFS_LINK_MAX` is 40); an empty target is `ENOENT`. The walk takes two path pages at its first link and gives them back when it returns.
* A node a mount covers is replaced by that mount's root.

A type with `lookup_rest` in place of `lookup`, one of the three synthetic types ([synthfs.Readme.md](synthfs.Readme.md)), is handed the rest of the path in one call, since its namespace is a table classified by string. A `..` that would climb above its root answers `VFS_CLIMB` with the rest from that `..`, and the walk takes the `..` at the mount's root as at the root of any other mount: at a bind over a directory it is taken again at the covered directory, so `/mnt/x/..` is `/mnt` when `/proc` is bound on `/mnt/x`. A `..` first at that root is not handed to the type (`climbs`). A rest that comes back to the root directory in front of the name of a nameless mount there answers `VFS_ROOT`, and the walk enters that mount, so `/dev/pts/../shm` is `/dev/shm`; a nameless mount named first at such a root is entered before the type sees the rest (`named_in_rest`). The one link of these types followed to a node is `/proc/PID/exe`: `walk_exe` goes on at the program file the process's address space keeps, moving to that file's mount, taking its lock for a locked walk, and reading the file's node again once there, since the wait may let the file move. The other synthetic links are followed by the text `readlink` gives.

`VFS_WALK_PARENT` stops before the last component and returns the parent, its search permission checked, with the leaf copied out; create, unlink, mkdir, rmdir and rename start there. `VFS_WALK_LOCK` takes each mount's namespace lock before its lookups, releases it when the walk crosses to another mount, and returns with the last mount locked, all only for a type that sets `ns_serialised`; the caller releases it with `vfs_walk_unlock` once its description is registered or its change made. A walk that meets a mount whose device has gone answers `EIO`, and so does one that ends on such a mount, except the walk of `umount2`.

### Roots and working directories

A process's root is `root_mnt` and `root_node` in its `struct fs_struct`, which `CLONE_FS` shares with the working directory and the umask; NULL is the root of the mount table. `vfs_root_set` holds the new root and counts a reference on its mount, stores it, and only then lets go of the old one, whose put may sleep, so a thread sharing the record always finds one of the two. `vfs_root_copy` gives a child of `fork` its parent's root, and `vfs_root_clear` lets go at exit. The resolver uses the root in three places: an absolute path starts there (`walk_root`), an absolute link target restarts there, and `..` stops there (`dotdot_stays`). A walk keeps the root it started from. When a thread sharing it changes root while the walk sleeps, the walk sees that at its next `..` or absolute link (`root_current`) and starts over, so no walk judges one path by two roots.

The working directory is `cwd_mnt` and `cwd_node` beside the path the process record keeps; `vfs_cwd_set` takes its hold and its reference in the same order. `/dev` and `/proc` take neither. Since KRFFS counts no holds on its nodes, `rmdir` would free a directory that a process record still refers to: `vfs_leaf_root` answers `EBUSY` for a directory that is any process's root or the root of a bind, and a KRFFS volume looks for a working directory itself ([krffs.Readme.md](krffs.Readme.md)). A directory of `/dev`, `/proc` or `/sys` cannot be a root, since the resolver could not stop `..` inside a type that takes the rest of a path in one call; [chroot.2](../../../man/man2/chroot.2) has the contract and its one exception, `/proc/PID/fdinfo`.

### mount, binds and umount2

`vfs_do_mount` resolves and holds the target and checks it (`target_check`). Then, under the parent mount's namespace lock, so that no namespace change runs between the check and the reservation, it refuses a covered or reserved target, resolves the source to a device and claims its sectors (`mount_source`), and takes a slot as `VFS_MOUNTING` (`mount_place`), which keeps the covered node's hold and counts a reference on the parent. The constructor runs under the new mount's own namespace lock and may sleep on the device; the mount becomes active only when it succeeds. A failure releases what the steps before it took and drops from the cache every buffer of the device the constructor read (`mount_refused`), since a program such as mkfs may write the device past the cache before the next mount. A device that refuses writes makes the mount read-only whatever the flags ask. The target is recorded by its path from the root of the mount table, which `vfs_node_path` rebuilds from the node the walk reached, so a target named through a link, with `..`, or from a root `chroot` gave, is recorded where it is. A new mount is seen in the caller's mount namespace and in the namespaces made from it later.

`vfs_remount`, for `MS_REMOUNT`, gives an active mount new flags. A change between read-only and writable goes through the type's `remount`, which only ext2 and tmpfs have; a type without one refuses that change with `EINVAL` and takes the other flags. A mount whose device refuses writes, or has failed one, is not made writable (`EROFS`).

A bind (`vfs_do_bind`) is a record whose base (`bind_of`) is the mount whose file system it shows, never itself a bind. It has the base's type, device and private state, and its own root (the source directory, held for its life), place and flags, the flags copied from the source's mount. Every wrapper passes the base to the type, and a bind's namespace lock is its base's, so a type never sees a bind and two mounts of one file system serialise as one. A file is the same file by its inode number on the base (`vfs_mount_base`), which is what record locks, inotify, FIFOs, socket files, shared mappings and the device `stat` reports go by. A write through a bind is refused when the bind or its base is read-only, and `MS_REMOUNT` with `MS_BIND` changes the bind's own flags (`vfs_remount_bind`). The base counts the bind among its references. `..` at a bind's root climbs to the directory it covers, and `vfs_node_path` gives a path below the bind's place, or `ENOENT` for a node outside the tree it shows. With `MS_REC`, `bind_below` places a bind of each mount the caller sees below the source, shallowest first, each under the bind of its parent, and leaves out, with a log record, a KRFFS volume and a mount whose new path would be longer than 63 bytes. A bind of a synthetic type is refused except at its root, which resolves as the original does. A bind of a KRFFS directory follows the directory when its node moves (`vfs_repoint`).

`vfs_do_umount` finds the mount by a walk that may end on a mount whose device has gone. When an ancestor's device has gone the walk answers `EIO`, and the mount is found instead by its recorded path (`unmount_below_gone`): the target, made a path from the root of the mount table by putting the path of the caller's root in front of it (`unmount_target`), must equal the covered path of exactly one active mount below a gone ancestor. A target that ends in a slash, `.` or `..` must reach a directory, and the node checked is the node unmounted. A mount that another live namespace sees is hidden from the caller's namespace and stays.

The unmount itself (`unmount_mount`) sets `VFS_UNMOUNTING`, which refuses new work, waits for the operations in progress to drain, and answers `EBUSY` while `refs` is not zero. A bind ends there: its root and covered node are put and its parent and base let go, with nothing written. For any other mount, under its namespace lock, the type's `sync` and `prepare_unmount` run, the cache writes the device's dirty buffers (`bcache_sync`), the device flushes its own cache (`block_flush`, [../block/Readme.md](../block/Readme.md)), and the cache drops the device's buffers (`bcache_invalidate`). `prepare_unmount` writes the volume's last metadata into the cache and dismantles nothing, so up to here the unmount can be abandoned: a failure returns the mount to `VFS_ACTIVE`, and a failure from the writeback on also calls the type's `abort_unmount`, which puts back what `prepare_unmount` wrote (KRFFS sets its dirty flag again, ext2 clears its valid bit). Then the record is logged, the root put, inotify and the file cache told, the type's `unmount` frees its state, and the covered node, the parent's reference, the claim and the slot are released. A device that has gone takes nothing, so the sync, the preparation, the writeback and the flush are skipped for it. When a mount namespace ends, `vfs_mntns_gone` unmounts, child before parent, each mount only that namespace saw.

### Claims

A claim (`devfs_claim` in `devfs.c`) is a mount's sector range on the physical disk under its source, taken before the constructor runs and released at the unmount. There are eight (`DEVFS_CLAIMS`); a mount that finds none free answers `ENOMEM`. Ranges are compared on the disk `block_physical` reaches and never by the device they were named through, since `/dev/bootpart`, `/dev/disk0p1` and `/dev/disk0` can describe one range. While a range is claimed, a second mount overlapping it and a write-capable open of a raw window over it answer `EBUSY`, and while such a window is open, a claim of its range answers `EBUSY`. This is how a mounted boot partition and `bootctl` exclude each other ([synthfs.Readme.md](synthfs.Readme.md)). A loop device has no range: the device is the identity, and one mount at a time may use it. A source device that already has a mount is `EBUSY`.

### Locks

The mount table has no lock of its own: the kernel reads and changes it under its one lock ([../proc/Readme.md](../proc/Readme.md)), and a system call is not preempted, so a process finds a namespace lock, a description or a buffer held only while its holder sleeps for the disk. The order is a mount's namespace lock, then an open file description's lock, then buffers of the cache by the cache's rules.

The namespace lock (`vfs_ns_lock`) is taken by every namespace change on a mount, by its constructor and its unmount, and by a writing type around its data operations, so every change to a volume runs under one lock. A caller takes a place in line (`ns_next`) and waits until its place is served (`ns_serving`), so a writer that locks for each call cannot take the lock back before a waiter has had it. The holder may take it again (`ns_depth`), since a type's operations lock for the callers that arrive unlocked and are also reached under the lock. A signal does not end the wait: a waiter that retried without sleeping would never let the holder run. `vfs_ns_held_by_caller` lets the buffer cache pass over a victim whose writeback would take another mount's lock.

### The buffer cache

`bcache.c` keeps blocks of 4 KiB, eight sectors each, for the disk file systems that are mounted: FAT32, exFAT, ext2, as a mount or as the root, and KRFFS volumes. A KRFFS root on a disk goes through the page cache instead ([../mm/Readme.md](../mm/Readme.md)). The operations are those of Lions' commentary: get a block and hold it, release it, mark it dirty, write it through, write a device's dirty buffers, and drop a device's buffers.

A buffer (`struct bbuf`) is a record and a page of the heap, made when it is needed. The cache makes at most the smaller of half of what the caches together may keep under memory pressure (`mem_cache_target`, a quarter of the frames) and half of the kernel heap's pages, and never fewer than `BCACHE_MIN_BUFFERS`, 16. On i686, whose heap is 256 MiB, the cache has at most 32768 buffers; [../mm/Readme.md](../mm/Readme.md) gives the heap's size on each architecture. The last block of a device whose sector count is not a multiple of eight has only the sectors that exist.

Every buffer is on the list of all buffers. A keyed buffer is also in a hash index of 4096 buckets by device and block and on a list in release order; an empty one is on the list of empties, a dirty one on the dirty list, and a held one on its holder's list (`bcache_held` in the process record). So a get, a choice of victim and a sync read the few buffers they need and not the whole cache. `cache-visits` counts the buffers these walks read, and `bcache_cost_hosttest.c` keeps it under bounds.

A miss keys and holds a buffer before it reads the block, so a second process asking for the block waits for that buffer instead of filling another. The buffer is an empty one, else a new one while the cache is under its limit, else the least recently released one nobody holds; a dirty victim is written first, and one whose last write failed, or whose write the caller's holds would not allow, is passed over. A miss at the block after the one last filled is a reader going through the device in order: the cache reads that block and the uncached whole blocks after it in one request, up to what the device takes at once and half the cache's limit, through a staging buffer of 1 MiB (`fill_run`). `bcache_get_blank` gives a block the caller will overwrite, zeroed and not read.

A held buffer is busy: another process sleeps on its queue until the release, uninterruptibly, and the wait is counted in `cache-waits`. Two rules keep holders out of deadlock, checked at every get: a process holds at most `BCACHE_HOLD_MAX`, four, buffers, and a buffer it takes must be of a higher block than every buffer it holds of the same device, and of a device below every other device it holds a buffer of, as a loop device's read of its file is. A release, a dirty mark or a write by a process that does not hold the buffer, and a sync by one that holds a buffer of the device, are defects too. The cache panics on each, so a file system that breaks a rule fails in the host test.

`bcache_write` writes a held buffer through before it returns, so the order in which a driver writes its metadata is the order in which it reaches the disk. `bcache_dirty` leaves the buffer to be written back at eviction, at `fsync`, at `sync` or by the periodic sync ([Readme.md](Readme.md)). `bcache_dirty_ordered` gives a dirty buffer a place in its device's writeback: a `BCACHE_ORDER_FIRST` buffer reaches the device before any `BCACHE_ORDER_AFTER` buffer of that device, whichever path writes, since a sync writes the firsts in a pass of their own, and an eviction or a reclaim that chose an after writes the device's firsts before it, or passes it over while one of them is held or failed its write. ext2 uses the marks ([ext2.Readme.md](ext2.Readme.md)). `bcache_dirty_heavy` is true when the dirty buffers are a quarter of the limit, the point at which a file system that writes back writes its runs itself.

`bcache_sync` writes a device's dirty buffers, the firsts in one pass and the rest in another, each in ascending block order, in runs of adjacent blocks of up to what one request moves, 256 blocks at the most. It waits for a buffer another process holds rather than pass over it, and answers the first failed write's errno with that buffer and the rest still dirty. A pass gathers its blocks in one walk of the dirty list into a batch kept as a heap: 128 blocks on its stack, or, with more dirty than that, up to 256 pages from the heap, which hold 131072 blocks. On a disk that makes each write durable before it answers (`BLOCK_WRITE_THROUGH`), the sync writes without the disk's flush and flushes once at the end, but writes a run of firsts with the flush, so that it is on the medium before an after is written. `bcache_write_unflushed` and `bcache_sync_unflushed` make the same writes without the flush, for a caller that flushes later.

`bcache_shrink` gives buffers back under memory pressure: the empty ones, then clean ones oldest first, then dirty ones written back, and never one a process waits for.

### Failures

The cache handles a write that fails and a device that goes in one place, for every type above it.

A write that fails, through `bcache_write` or writeback, keeps its buffer dirty and calls `vfs_device_failed`: every mount on the device goes read-only for the rest of its life, with a `vfs: read-only` record, and `/proc/mounts` shows `ro`. The cache answers the device's later `bcache_write` calls with `EROFS` until the unmount drops its buffers, so an operation that was in progress stops at its next metadata write. A write-back cache cannot return a later failure to the `write(2)` that dirtied the buffer, and a disk that has begun to refuse writes is not one to go on writing. A remount does not make such a mount writable. Its unmount still writes the dirty buffers, and a write that fails there leaves the mount in place.

When the disk layer reports a device gone (`bcache_device_gone`), every mount on it goes read-only, every buffer of the device is made clean, one nobody holds is dropped at once, and a held one is dropped at its release, since a buffer cannot be given away under its holder. From then on every operation on those mounts answers `EIO`, `/proc/mounts` omits them, and an unmount writes nothing and only releases what the mount had, once nothing refers to it.

A sector torn in the middle of a write, or a write the disk acknowledged and lost, is outside what the cache can see; the volume's own check judges that afterwards.

## Limits

* There is no `MS_MOVE`, no lazy or forced unmount, and no mount propagation.
* A mount target's path from the root of the mount table is at most 63 bytes, and the source string is recorded to 31 bytes.
* Nothing is mounted on a directory of `/dev`, `/proc` or `/sys` themselves, and a bind of a directory inside them is refused; a mount inside them is entered by name, as `/dev/shm` is.
* `MS_REC` does not show a KRFFS volume below the source.
* Through a bind of the KRFFS boot root a file's mode, owner and times do not change (`EROFS`), since the root changes them only through the system call layer's own paths.
* `sysfs` is not a type `mount(2)` finds (`ENODEV`), though its privilege check admits it, and `proc` mounts only over a directory of `/proc`.
* Only tmpfs updates an access time on a read ([Readme.md](Readme.md)); `MS_NOATIME`, `MS_NODIRATIME` and `MS_RELATIME` are recorded and shown and change nothing.
* A mount that went read-only after a failed write stays read-only until it is unmounted.
* The cache keeps no list of a mount's own dirty buffers: a sync writes a whole device.
* One run at a time uses the staging buffer; while it is in use a writer writes its blocks one at a time and a sequential reader fills its block alone.

## Tests

* `tests/run default` boots the guest probes on the test image, among them `vfsprobe` (the errno each path form answers, physical `..`, what a description keeps across unlink, rename and relocation, and the statfs identities), `pathcanon`, and the musl programs `tmpfsmusl` (binds, `MS_REC`, binds of the KRFFS root and of its root directory), `chrootmusl` (process roots), `nsmusl` (mount namespaces), `pathmaxmusl` (paths of 4096 bytes) and `opathmusl`.
* `tests/run mount` boots a disk with a FAT32 partition: `mountprobe`, which is `mount(2)` and `umount2(2)` from a program with the flags, the busy answers, the claims and the `/proc` files; an `rmdir` of the target while a constructor sleeps on the lag device; the boot partition mounted read-only refusing the raw writer; BusyBox mounting, listing and reading the volume; a write the device fails under `rach2.blockfail`, after which the mount is read-only; and the cache giving buffers back under memory pressure.
* `tests/run usbdisk` first runs `tests/system/vfs_unmount_test.sh`, which compiles the unmount functions of `vfs.c` with counted substitutes and checks live and removed children, draining, a removed ancestor, a target named from a `chroot` root and a target named as a directory; with `--mutate` it compiles four faults into a private copy and requires each to fail. The suite then pulls a stick out from under its mounts.
* `tests/run host` runs `bcache_hosttest.c`, the cache against a fake device (hits, victims, the hold rules, short blocks, sync order and failed writes), and `bcache_cost_hosttest.c`, the bounds on `cache-visits`; `sh tests/host/bcache_mutate.sh` proves the second against the faults it was written for.

# Synthetic file systems

Rach2 generates `/dev`, `/proc` and `/sys` from kernel state. No tree of them is stored in KRFFS. [synthfs.c](synthfs.c) classifies a canonical absolute path, [devfs.c](devfs.c) supplies devices, and [procfs.c](procfs.c) generates process and system files and the device records of `/sys`.

## Path routing

`/dev`, `/proc` and `/sys` are the three synthetic entries of the mount table ([vfs.Readme.md](vfs.Readme.md)). The resolver reaches them by name from the root directory and passes each the remaining path. `synth_rest` resolves `.` and `..` before `synth_classify` fills a `vpath`. A two-component device path other than `/dev/pts` becomes `VNODE_DEV`; devfs checks whether the device exists. The caller checks process and descriptor existence. A `..` in that rest that would climb above the mount answers `VFS_CLIMB` and the resolver continues at the root directory. A KRFFS directory named `dev`, `proc` or `sys` cannot shadow its mount and cannot be created (`EEXIST`).

Synthetic directories can be opened and used by `chdir` and the `*at` calls. For example, `openat` can open `null` relative to an fd for `/dev`. Directory descriptors and the current working directory store canonical synthetic paths, with `/proc/self` resolved to the numeric pid when necessary. A synthetic node lives for the length of one syscall, in a record taken from the kernel heap; the open that follows a resolution binds the device's own operations onto the descriptor. An `O_PATH` open binds nothing: a directory becomes a synthetic directory descriptor that `getdents64` refuses with `EBADF`, and any other node a descriptor that keeps a copy of the node's `vpath` for `fstat` and `fstatfs`, so a device is not opened and a `/proc` file takes no snapshot.

The namespace is fixed. Creation, removal, rename, and timestamp operations on the synthetic nodes below `/dev` or `/proc` return `EROFS`, `execve` of one returns `EACCES`, and neither directory can host a mount point (`mount(2)` answers `EINVAL`). Two paths below them reach files of another type: `/dev/shm` is a tmpfs mount, where files are made, removed, renamed and stamped as on any tmpfs, and `/proc/<pid>/exe` is a link the resolver follows to the program's file itself, so an `execve` of it, or a timestamp change that follows links, reaches the program wherever it is. A KRFFS root listing does not add `dev` or `proc`; programs must address those mount paths explicitly. `/dev` enumeration lists `shm`, the tmpfs mount that stands in `/dev` by name ([tmpfs.Readme.md](tmpfs.Readme.md)), as a directory, then `fd` as a directory and `stdin`, `stdout` and `stderr` as links, then the device registry, each device as a character or a block device; it does not list the accessible `pts` subdirectory.

`/dev/fd`, `/dev/fd/N`, `/dev/stdin`, `/dev/stdout` and `/dev/stderr`, which Linux makes links to `/proc/self/fd` and its first three entries, are those nodes of the caller (`synth_classify_dev_fd`): `/dev/fd` is the caller's `/proc/self/fd` directory, and the others are its links, which an open follows as it follows them under `/proc` (below). Bash's process substitution, `diff <(...)`, and `cat /dev/stdin` name them.

## devfs

`/dev` has mode 0755 and file-system id 5. Opening an existing leaf with `O_CREAT|O_EXCL` returns `EEXIST` before descriptor allocation or special device dispatch, including `/dev/ptmx`. Its registry gives each fixed device a stable inode, a character-device number, and root ownership. Open permissions use the same owner, group, and other bits as KRFFS.

| Path | Device | Mode | Contract |
|------|--------|------|----------|
| `/dev/mem` | 1:1 | 0640 | The physical address space for a privileged caller: the first megabyte and the frames that are not the allocator's (`paging_frame_is_device`), read, written and mapped shared and uncached, as a region marked `VM_PROT_IO`; RAM is `EPERM`. |
| `/dev/null` | 1:3 | 0666 | Reads return EOF; writes are discarded. |
| `/dev/log` | link | 0777 | A link to `/var/run/log`, where a syslog daemon binds its socket and its clients' connect and send find it (`SYNTH_DEV_LOG_TARGET`). |
| `/dev/zero` | 1:5 | 0666 | Reads return zero bytes; writes are discarded. |
| `/dev/full` | 1:7 | 0666 | Reads return zero bytes; writes fail with `ENOSPC`. |
| `/dev/random` | 1:8 | 0666 | Reads use the trusted CSPRNG and fail with `EIO` when the seed is untrusted. |
| `/dev/urandom` | 1:9 | 0666 | Uses the same read and trust policy as `/dev/random`. |
| `/dev/console` | 5:1 | 0666 | Opens the kernel console terminal. |
| `/dev/tty` | 5:0 | 0666 | Opens the caller's controlling console or pty slave; a caller without one gets `ENXIO`. |
| `/dev/ptmx` | 5:2 | 0666 | Allocates a pty pair and returns its master. |
| `/dev/bootpart` | 240:0 | 0600 | Exposes a validated FAT boot partition as a raw sector window when one exists. |
| `/dev/disk0` | 240:1 | 0400 | Exposes disk 0 after a diagnostic probe, in recovery, or through USB discovery. |
| `/dev/bootlog` | 240:2 | 0400 | Reads the kernel log's 16 KiB ring from its oldest retained record. |
| `/dev/grubcore` | 240:3 | 0600 | Exposes LBA 1 through 2047 when the MBR leaves that range unused, or a GPT disk's one BIOS boot partition. |
| `/dev/disk0p1` to `/dev/disk0p4` | 240:4 to 240:7 | 0400 | One read-only window per nonempty MBR entry, the source `mount(2)` takes. |
| `/dev/diskN` | 240, the minors [`block/Readme.md`](../block/Readme.md) lists | 0400 | The whole medium of a disk or a stick; a stick's is published by its table scan, from the reading of that table until the record is reclaimed. |
| `/dev/diskNpM` | 240, the same scheme | 0400 | One window per partition the table describes, the source `mount(2)` takes. |
| `/dev/loop0` to `/dev/loop3` | 7:0 to 7:3 | 0660 | A block device over a regular file, and the source `mount(2)` takes for a file system in a file. |
| `/dev/loop-control` | 240:36 | 0600 | Attaches a file to a loop device and detaches one, a command per write. |
| `/dev/screenlog` | 240:38 | 0600 | The lowest-priority record the screen shows: one digit, read or written. |
| `/dev/rtc0` | 254:0 | 0600 | The CMOS clock, read and set through `RTC_RD_TIME` and `RTC_SET_TIME`, as `rtc(4)` gives. |

`null`, `zero`, and `full` seek to offset zero. Random devices, terminals, and pty endpoints are streams and return `ESPIPE`. `/dev/bootlog` uses an ordinary offset and supports seeks relative to the current ring length. All synthetic nodes use stable timestamps from the RTC reading taken during startup, or zero when no RTC reading was accepted.

Pty pairs are allocated from the heap without a fixed count. Each pair receives the lowest index not used by a live pair. Opening `/dev/ptmx` allocates a locked pair; `TIOCSPTLCK` must unlock it before `/dev/pts/N` can open. An allocated slave appears in `/dev/pts`, has device number 136:N, and starts with the opener's effective uid and gid and mode 0620. `chmod` and `chown` may change that slave for a login session. The slave uses the normal terminal discipline. Master writes become slave input, while slave output and echo enter a 4096-byte master ring. The pair is released after both endpoints close.

`/proc/usb` has one line per USB device the kernel has configured: its location, the speed, the vendor and product identifiers, and the class and protocol it was driven as. The location is a path, `port 5` for root port 5 and `port 5.2` for port 2 of the hub on it, one more number for each hub down. A machine that has had a stick has further lines: one per stick naming its node, the two names the drive gave to `INQUIRY`, its size in sectors, how many partitions were published, whether its table is still being read, it is ready or it is closing, with the holds left on it when it is closing, how many `SYNCHRONIZE CACHE` commands it completed, which an unmount, a sync and an fsync each send once, and `ro` when it is write protected; and a last line, `disks N free M reclaimed`, gives how many of the two names are free and how many sticks have been given up since boot. A machine that never had a stick writes neither, so a machine with no USB controller, or one booted with `rach2.nousb`, has the file and it is empty. That is a different answer from the file not being there, and it is the one a program that opens it can act on. A program that counts devices counts the lines that begin with `port`.

A loop device's node is there whether or not a file is attached, a block device with Linux's loop major, so that util-linux's `losetup` and `mount` find it; it reads and writes its device in whole sectors, as a disk node does, a write only with no file system mounted on it, and takes Linux's loop ioctls (`loop_node_ioctl`), which attach the file a descriptor has open, report the attachment and detach it, by hand or when the last description and mount let go of a device set to clear itself. An attached device is a disk of `/sys/block` and `/proc/partitions`, after the disk nodes (`devfs_disk_node_at`). `/dev/loop-control` takes one command per write, `attach N /path`, `attach - /path`, `attach ro N /path` and `detach N`; the node is root's, which is what says who may attach anything, and what the commands mean is in [block/Readme.md](../block/Readme.md). `/proc/loop` has a line per attached device: the device, its size in bytes, whether it takes writes, how many writes it has made and how many it has synced, and the path it was attached by.

Whole-disk and partition nodes report block-device mode in `stat`, on USB and on other transports. Reads accept arbitrary byte ranges: the covering sectors are read and the requested bytes copied out. Writes require whole sectors and are available only in recovery builds. The boot windows remain character devices.

`/dev/screenlog` decides how much of the kernel's own record reaches the screen, and nothing else: the ring, the serial port and netconsole keep every record whatever it says, so `/dev/bootlog` and a capture on the port are unaffected. A read gives the current level as one digit and a newline, and holds the description for its length as a read of `/dev/bootlog` does (`devfs_fd_moves_offset`), so two reads through one description give the two bytes once; a write of one digit sets it, clamped to `KLOG_CRIT` at the low end so a panic can never be hidden and to `KLOG_DEBUG` at the high end. The default is `KLOG_INFO`, which keeps the boot log, since a screen that says nothing while a machine starts cannot be told from a machine that has stopped; what it drops is `KLOG_DEBUG`. `rach2.loglevel=N` on the boot line sets it for a boot being brought up, when the screen is the only instrument there is. It exists because the screen is shared: `rach2-install` talks to a person through it and has no other way to keep the machine's routine notes out of the middle of its questions.

`/dev/bootlog` is always present. It reads the kernel log ring, which contains records but no console text. Whole records are evicted from the oldest end to make room. The offset counts from the oldest retained byte. Records may be evicted between chunk copies, including within one read; the returned bytes are not a snapshot. A read holds the description for its length, as a seek does (`ops_offset_held`, `seek_bootlog` in `syscall_fs.c`), since the read sets the offset past what it copied and may sleep first, in a fault on the caller's buffer: a seek through a descriptor that shares the description waits and moves on from where the read left the offset. A seek takes any place through 4294967295, the last the offset has, and the older 32-bit `lseek` refuses a place past 2147483647 with `EOVERFLOW`. The os-real `dmesg` script reads this device because Rach2 has no `klogctl` interface.

The framebuffer and mouse use the root paths `/fb` and `/mouse`. They are not devfs entries.

## Raw disk windows

Disk discovery reads and validates sector 0 before publishing either boot window. `/dev/bootpart` represents MBR entry 0 only when all of these conditions hold:

* its type is FAT32 `0x0b` or `0x0c`;
* its start and nonzero length fit within the disk;
* it starts at or after LBA 2048 and overlaps no other nonempty entry;
* its length is less than 2 GiB;
* it is not the partition later selected as the KRFFS root.

`/dev/grubcore` is the range that holds GRUB's BIOS core. On an MBR disk it is the fixed half-open range `[1, 2048)`, and it requires a disk large enough for that range and no nonempty partition overlapping it. On a GPT disk those sectors are the table's, and the range is the BIOS boot partition as the partition service read it, from the primary header or the backup (`devfs_grubcore_publish_gpt`, `part_bios_boot`): exactly one such partition, clear of sector 0, the headers and the entry arrays, and on the device; LBA 34 through 2047 on the disks this project builds. Sector 0 is excluded either way because it contains the partition table. `HDIO_GETGEO` gives the range's first sector and `BLKGETSIZE64` its size. Both devices are considered before root selection, so a RAM-root boot can still repair its disk.

Every boot publishes whole-disk windows for registered disks, and `rach2.diskdiag` and recovery builds also probe for a disk the boot did not find. USB discovery also publishes each discovered disk's whole-disk window. Partition windows are published separately after a table scan. A whole-disk window covers the disk's full reported sector count. An ordinary kernel permits reads but its device write handler returns `EPERM`. Only a kernel built with `RACH2_RECOVERY` has the whole-disk write implementation, and that implementation rechecks effective uid 0 for every write.

Boot, whole-disk and partition windows use a 64-bit offset shared by duplicated and inherited descriptors. `_llseek` can address the whole window. The legacy 32-bit `lseek` returns `EOVERFLOW` when it cannot return the resolved offset. A seek need not be sector-aligned. Boot-window reads and all raw writes require offsets and lengths that are multiples of 512; otherwise the transfer returns `EINVAL`. Whole-disk and partition reads accept arbitrary byte ranges.

Reads at or past the end return EOF, and a read crossing the end is shortened. A write at or across the end returns `ENOSPC` before writing any part of the request. Transfers use kernel staging buffers, so a DMA driver never receives a user pointer. Poll reports requested read and write readiness without a wait queue; a transfer may still sleep while acquiring a buffer or completing block I/O. ATA and AHCI flush the device cache after every successful write command. A fully successful raw write to ATA or AHCI is therefore durable when it returns. USB raw writes use ordinary SCSI writes without a device-cache flush and have no such return-time guarantee. If a later batch fails, the short count covers only completed earlier batches; the block interface cannot report how much of the failed batch reached the device.

Each physical disk permits one write-capable open-file description across its raw windows. A second writer on that disk gets `EBUSY`; writers on different disks and readers may coexist. `/dev/grubcore` additionally permits only one open-file description at a time because replacement of the embedded loader is a multi-step transaction. Whole-disk withdrawal clears every registered disk's whole-disk window and leaves partition windows unchanged. Reads through an unpublished whole-disk window return `EIO`. Boot windows are withdrawn separately; their descriptors receive `ENXIO` until the backing is published again.

## procfs

`/proc` has mode 0555 and file-system id 6. Directories have mode 0555, ordinary files have mode 0444, `/proc/disk` has mode 0400, and magic links have mode 0777. Its root listing contains these global entries before the live numeric pid directories:

* `/proc/audio` reports the active audio driver and cached HDA codec capabilities, selected paths, packed and expanded connection lists, and the last requested and programmed rate with format readbacks. Reading it sends no codec verb. The report survives stream shutdown and exists when audio is disabled, with `hda ready 0`; [the audio Readme](../audio/Readme.md) defines the fields and playback limits.
* `/proc/cmdline` is the captured kernel command line followed by a newline.
* `/proc/disk` is the disk diagnostic record, the live command counters, and the buffer cache's four counters. The path always exists. Before a diagnostic probe it reports `state not-asked`; only `/dev/disk0` is conditional on the probe. Opening this file requires root.
* `/proc/uptime` reports the boot processor's delivered 100 Hz ticks, idle and busy, and the idle ticks of every processor summed, as seconds with two decimal places.
* `/proc/loadavg` reports the load averages over one, five and fifteen minutes that the scheduler keeps as Linux does (`sched_load_tick` in `proc/sched.c`: every five seconds and a tick, the processes running or ready to run are folded into each average with Linux's fixed-point decays), the running and all tasks, and the last process ID given out; `sysinfo` reports the same averages.
* `/proc/stat` reports, on the `cpu` line and on a `cpuN` line for each processor online, the ticks in user mode, in the kernel and idle, which add up to the uptime since the processor started, a tick lost while its interrupts were held off counted with the next (`sched_account_tick`), the boot epoch, processes created since boot, and current runnable and blocked counts. The `cpu` line's ticks are the processors' summed in 64 bits, since one word would wrap in eight days with 64 processors. Its `intr` line is every interrupt the kernel has routed. Untracked counters are zero.
* `/proc/version` is one line, `Linux version 6.18.0-rach2 #1 Rach2 1.0.0`, from the fields `uname` gives (`UTS_SYSNAME`, `UTS_RELEASE` and `UTS_VERSION` in `syscall.h`).
* `/proc/partitions` has Linux's header and a line for each disk and partition node `/proc/diskstats` lists, with its device numbers, size in kibibytes and name.
* `/proc/diskstats` has a line for each disk and partition node in Linux's twenty fields, from the counts `block_request_flags` keeps of each device and of the disk under it (`struct block_stats`): a disk's line has every transfer to it, through any node, and a partition's has its view's and those of the kernel's own view of a boot root on it (`devfs_window_alias`). The discards and flushes are zero.
* `/proc/meminfo` reports managed physical memory as `MemTotal` and free memory as `MemFree`. `Buffers` and `Cached` report the data frames allocated to the buffer cache and page cache, respectively; both caches release frames under memory pressure. `MemAvailable` is the sum of `MemFree`, `Buffers`, and `Cached`. `HeapPages` and `HeapUsed` report the kernel heap's page count and bytes in use. The swap fields are zero. `Slab`, the last line, is the heap's pages but the buffer cache's, which the heap holds and `Buffers` counts, in kibibytes; BusyBox's `nmeter` reads it to count the memory in use.
* `/proc/cpuinfo` describes the processor in Linux's format for x86, from what `cpuid` reports (`arch/x86/cpuinfo.c`, the x86's text): the vendor, family, model, brand string and stepping, the last-level cache from leaf 4 or the extended leaf 0x80000006, the APIC ID, the feature flags of leaves 1, 7 and 0x80000001 by Linux's names, the cache line and the address sizes. There is a record for each processor online, with its number and its APIC ID; the processors are taken to be alike, so `cpuid` on the running one answers for the rest, and each is a core of one package (`siblings` and `cpu cores` are the count). There is no `cpu MHz` or `bogomips` line, since the kernel does not measure the clock.
* `/sys/devices/system/cpu` has `online`, `possible` and `present`, each the processors started as Linux lists a set of them, `0-3`; `offline`, empty; `kernel_max`, 63, one less than the most processors the kernel takes; and a directory `cpuN` for each processor online, which exists while that processor does and has an inode of its own.
* `/proc/sys` is a tree of a few of Linux's sysctl files, read-only, from a table in `synthfs.c`: `fs/inotify/max_queued_events`, `max_user_instances` and `max_user_watches`, the limits `io/inotify.c` keeps, `kernel/ostype`, `kernel/osrelease`, `kernel/pid_max`, the bound above which process IDs start again from 1, `kernel/core_pattern`, `kernel/hostname`, whose text procfs reads from what `sethostname` set when the file is opened (`SYNTH_SYS_HOSTNAME`), `kernel/domainname`, `(none)`, the limits of System V IPC (`kernel/msgmax`, `msgmnb`, `msgmni`, `sem`, `shmall`, `shmmax` and `shmmni`), `net/ipv4/ip_forward`, 0, since the stack forwards nothing, and the limits of POSIX message queues under `fs/mqueue`. Its directories and files are `VNODE_PROC_SYS_DIR` and `VNODE_PROC_SYS_FILE` with their entry in the table, which a directory descriptor's record keeps in its `pid`.
* `/proc/mounts` reports the root first, the recorded KRFFS source and options or, for a root of another type, its device, type and `rw,relatime` or `ro,relatime` from the mount's flags, then the devfs and procfs rows, then `tmpfs /dev/shm tmpfs rw,nosuid,nodev`, and then every mount placed by `mount(2)`, in the six-field `getmntent` form with the flags as words.
* `/proc/filesystems` lists `nodev devfs`, `nodev proc`, and the types `mount(2)` accepts: `vfat`, `exfat`, `ext2`, `krffs`, and `nodev tmpfs`.
* `/proc/console` is the serial receive path's counters, `name value` per line, in the order the path runs: `uart-bytes`, `uart-overruns`, `irq-drains`, `tick-drains`, `reader-drains`, `ring-full`, `ring-max`, `shell-bytes`, `line-drops`, `queue-drops`, `flush-bytes`, `partial-moved`, `read-bytes`, `queue-max`, `line-max`. What each counts is in the kernel Readme's Input section.
* `/proc/interrupts` has one line per vector that has taken an interrupt: the vector, its count, `PIC` for the sixteen vectors the 8259 pair delivers, `IO-APIC` for the lines the I/O APIC delivers on the same vectors, `LAPIC` for the tick of the local APIC's timer, or `MSI` for a device message vector allocated from 48 through 63, and the registered handler names, separated by commas where a line is shared. Message vectors are allocated in order as drivers enable messages, so identify a device by its handler name rather than a fixed vector number. A vector whose handlers registered no name at all prints `none`. A vector that has taken nothing has no line. The last two lines are counts that belong to no vector: `SPU` is the spurious interrupts the local APIC has raised, and `FBK` is the times the USB timer's pump found work that no message was coming for.
* `/proc/sysvipc` contains `shm`, `sem` and `msg`, one kind, `VNODE_PROC_SYSVIPC`, told apart by their origin number from `SYNTH_PROC_SYSVIPC`, whose text procfs makes from `sysv_row_at`; the directory is `VNODE_PROC_SYSVIPC_DIR`.
* `/proc/net` contains `dev`, `route`, `arp`, `tcp`, `udp`, `raw`, `unix`, `sockstat`, `snmp` and the directory `stat`, `VNODE_PROC_NET_STAT_DIR`, with `rt_cache` and `arp_cache`, two more of the files known by their origin, `SYNTH_PROC_NETSTAT_RT` and `SYNTH_PROC_NETSTAT_ARP`, whose names in `synth_net_name` carry the directory. There is no `tcp6` because the kernel has no IPv6 stack. The last five are one kind, `VNODE_PROC_NET_FILE`, told apart by their origin number, `SYNTH_PROC_NETUDP` to `SYNTH_PROC_NETSNMP`.
* `/proc/self` is a magic symlink to the caller's numeric pid.

The network files are snapshots taken at open of the entries then in the kernel tables. `/proc/net/dev` prints the sixteen columns Linux prints, because programs find their number by counting fields. Seven values come from the interface: bytes and frames each way, receive errors, receive drops and transmit drops. Driver counters add missed frames to receive drops and supply receive alignment errors and multicast frames, transmit errors, FIFO underruns, collisions and aborted transmissions. These hardware counters are zero when the driver supplies none. Receive FIFO and both compressed columns are always zero. `/proc/net/route` prints the on-link route and an optional default gateway. `/proc/net/arp` prints the eight-entry address cache. `/proc/net/tcp` prints every TCP control block with Linux state numbers, queue lengths, uid, and the same socket inode used by `fstat` and `/proc/<pid>/fd/N`. `/proc/net/udp` and `/proc/net/raw` print the datagram and raw sockets in the same columns, `/proc/net/unix` the `AF_UNIX` sockets with a descriptor open, `/proc/net/sockstat` the counts `ss -s` reads, and `/proc/net/snmp` the MIB counters the network layers keep in `net_mib` (`network/net.h`), in Linux's lines.

`/proc` lists a process once, by its first thread, whose id is the process id; `/proc/<tid>` of another thread still opens, and `/proc/self` is the calling thread's process. The idle process, whose id is 0, has no directory, as Linux lists no process 0. Each live `/proc/<pid>` directory contains `stat`, `cmdline`, `fd`, `maps`, `smaps`, `status`, `statm`, `auxv`, `environ`, `comm`, `mounts`, `mountinfo`, `mem`, `oom_score_adj`, `limits`, `exe`, `cwd`, `root` and `task`:

* `stat` emits fields 1 through 24. Pid, program name, parent, process group, and session come from the process table, and so do the user and system times of all the process's threads and the reaped children's, in ticks, as `times` reports them, or in a thread's `stat` under `task` the thread's own user and system times, the nice value `setpriority` keeps, with the priority Linux reports for it, 20 more, and the thread count. Running and ready processes use state `R`, blocked processes use `S`, zombies use `Z`, a process a signal stopped `T` and one in a ptrace stop `t`, as the `State` line of `status` says. The start time is the tick the process or thread was made at, counted from boot (`start_ticks` in `process.h`), which ps subtracts from the uptime for the elapsed time, and the address space's size in bytes and its pages in memory are those `statm` has. The terminal and fault fields, which the kernel does not track, are fixed values or zero.
* `cmdline` has the arguments as the program's initial stack has them, each ended by a NUL, read through its address space, so a program that rewrote them shows what it wrote. It has at most their first 128 KiB (131072 bytes), so a longer list ends inside a string, without that string's NUL, and it ends early at a page the address space cannot read. A process with no address space, as one that has ended has none, shows its program name, at most 15 bytes, as the one argument, where Linux shows nothing for one that has ended. The name is inherited by `fork` and replaced by `execve` and by `prctl(PR_SET_NAME)`; `comm` has it with a newline.
* `maps` has a line for each region in Linux's form: the range, the rights with `p` or `s`, the file offset, a device and inode of 0, which the kernel does not keep, a space, and from column 73 the path: the file a region maps, `[heap]`, `[stack]`, the program for the segments of its image, or the dynamic linker the program names for the segments of the linker's. A region with no path ends its line at that space, as on Linux, and BusyBox's `pmap` looks for it to find the end of the fields. GNU libc's `pthread_getattr_np` finds the main thread's stack by its `[stack]` line. It, `smaps` and the `fd` directory need what `environ` needs, and are `EACCES` to another caller, as on Linux.
* `stat` of `/proc/<pid>` and of each file and link in it reports the process's effective user and group IDs as the owner while the process is dumpable, and root otherwise, as Linux's `task_dump_owner` does (`procfs_oom_owner`, `synth_pid_owner` in `sys/syscall_fs.c`); BusyBox's `ps` and `top` read a process's user from its directory's owner. `fstat` of a descriptor open on one of them reports the same owner (`procfs_fd_owner`).
* `smaps` has each region's `maps` line and then Linux's fields for it, which `pmap` and `smemcap` read: the size, the page sizes, `Rss` and `Pss`, clean and dirty pages shared and private, `Referenced`, `Anonymous`, `Swap`, `SwapPss`, `Locked`, and `VmFlags`. The pages in memory are the region's present pages, clean or dirty by the page table entry's dirty bit, counted past the page tables the region lacks in one step for each absent span (`paging_user_count`), so that a large region with few pages costs few steps, and shared only in a shared region; its sizes are longs, so a region past 4 TiB on x86-64 has its kilobytes. `Anonymous` counts every page of a private region of no file and the dirty pages of a private region read from a file, a mapping or a segment of an image, which Linux has copied from the file; gdb's `gcore` leaves a region of a file with none out of a core and reads it from the file. The kernel does not count the processes that map a page, so `Pss` is `Rss`; there is no swap and no locking, so those fields are 0.
* `oom_score_adj` is the process's OOM score adjustment, kept in its thread group (`oom_score_adj` in `tgroup.h`), which a fork passes on and an exec keeps; nothing else reads it, since the kernel has no OOM killer, and it is kept for the programs that set it, as Chromium does for its renderers. A read gives the value as it is then, not a snapshot. A write takes its first 12 bytes as one integer, with the bytes Linux's `isspace` takes for spaces, 0xa0 among them, stripped at either end, and read as Linux's `kstrtoint` in base 0 reads it (`oom_parse`), from -1000 to 1000, else `EINVAL`: text that is no integer is `EINVAL` however many digits it begins with, and an integer an int does not hold is `ERANGE`. A value below the group's floor, `oom_score_adj_min`, needs a privileged caller, whose write sets the floor too, as on Linux. Opening it for writing needs a privileged caller or its owner, the owner of the process's directory, and `stat` and `fstat` report that owner and mode 0644, where every other `/proc` file has 0444.
* `status` has the lines of Linux's that programs read: the name, umask, state, the thread group, thread and parent ids, the tracer, the four user and group ids, the descriptor table's size, the groups, the memory sizes in kilobytes, the thread count, the signal sets, the capability sets, and `NoNewPrivs`. Of the capability sets, `CapPrm` and `CapEff` are full (`0x000001ffffffffff`, the 41 capabilities Linux defines) for effective user ID 0 and empty otherwise, `CapBnd` is full for every process, and `CapInh` and `CapAmb` are empty for every process. `statm` has the sizes in pages.
* `mounts` has the text of `/proc/mounts`, since the kernel has one mount table for every process. glibc's `getmntent` and GNU `df` read it as `/etc/mtab`, which the GNU system's root links to `/proc/self/mounts`, as Debian links it.
* `mountinfo` has a line for each mount of `/proc/mounts`, in its order, in Linux's form, which util-linux's libmount reads: the mount's place in the table plus one as its id, its parent's id, the root's its own, the device `stat` gives its files as `major:minor`, `/` as the root within the file system, since there are no bind mounts, the mount point, the options of `/proc/mounts`, a hyphen where Linux has its propagation fields, the type, the source, and `rw` or `ro`.
* `limits` has Linux's table of the sixteen resource limits in its columns: the six the kernel keeps, the file size, the stack, the core file, the processes, the open files and the address space, at the process's soft and hard values, and the others `unlimited`, as `getrlimit` reports them.
* `auxv` has the auxiliary vector the program was given, through its `AT_NULL` pair, and `environ` the environment strings of its initial stack, at most their first 128 KiB, cut as `cmdline` is; either needs effective user ID 0 or the process's real user ID.
* `mem` is the process's memory, not a snapshot: a read or a write at the descriptor's offset, which is the address, goes through the process's address space as a tracer's does (`paging_access`), a page at a time, and a region no access is allowed to is `EIO`; a transfer that runs into one returns the bytes it did before it and moves the offset past them. Opening it needs effective user ID 0, or the process's real user ID and a dumpable process. The descriptor holds the record of the address space those checks allowed (`mm` in its `procfs_file`, `mm_hold`) and none of its memory, and a read or a write takes a user's count of it for its length only while anything still runs in it (`mm_get_live`), a thread of the process or a process that shares it with `CLONE_VM`, as on Linux: once the last of them has ended or executed another program it returns 0, so a program executed later, a set-user-ID one among them, is out of reach of a descriptor opened before, and the pages of a process that ended went at its end.
* `cwd` and `root` are links to the process's working directory, the path `proc_cwd` gives, and its root directory, `/` unless chroot moved it, for the path `vfs_node_path` gives of the directory it moved it to (`procfs_readlink_dir`). Unlike `exe`, a walk goes on from the link's text, as from any symbolic link, and reading one needs what reading `exe` needs.
* `exe` is a link to the program the process runs, the file its address space keeps (`mm->exe_file`, `mm_exe_open`), as Linux keeps it. Reading it gives the file's present path on the KRFFS root, and for a file there that lost its name the path its `execve` found it at (`mm->exe`) followed by ` (deleted)`, as on Linux; on another type, whose node has no path of its own, it gives the path its `execve` found it at, which does not follow a rename there. Reading it, or going through it, needs a thread of the process, a privileged caller, or the process's real user ID and a process that is not privileged.
* `task` lists the process's threads by their ids, the leader first. Its link count is 2 and one for each live thread (`procfs_task_links`), as on Linux, where Chromium's zygote reads a count of 3 as the proof that it runs one thread; every other synthetic directory has a count of 1. `/proc/<pid>/task/<tid>` is classified as the process's directory with the thread's id beside the process's (`tid` in the `vpath`, from `synth_classify_pid`), and `procfs_resolve_id` finds it only when the process exists and the thread is one the directory lists. It has the files of `/proc/<tid>`, the thread's own where a thread has any, and no `task` of its own. A descriptor on it or on its `fd` keeps both ids (`tid` in its `synth_dir` record), so its listing, its `/proc/PID/fd` link and a name relative to it stay under `task`. A path is split into one component more than the deepest one, `/proc/<pid>/task/<tid>/fd/<n>`, so a deeper path is refused rather than read as a shorter one.
* `fd` lists the process's open descriptors as magic links. Targets include KRFFS paths, `/dev` paths, pty endpoints, synthetic directories, `pipe:[inode]`, `socket:[inode]`, `anon_inode:NAME`, and `/memfd:NAME (deleted)` for a file of `memfd_create`.

Following `/proc/self` produces the numeric pid directory. `/proc/<pid>/exe` is the one link the resolver follows: the procfs type reports it as a link, and the resolver goes on from the program's file itself, the node and mount the address space keeps (`walk_exe` in `vfs.c`, `procfs_exe_file`), so `open`, `stat` and `execve` of `/proc/self/exe` reach the program wherever a rename or a relocation has put it and after its name is gone, and `readlink` and `lstat` the link. Following `/proc/<pid>/fd/N` produces the target descriptor's stat identity, with a description on a mount held for the length of the stat, whose getattr may sleep while the process closes the descriptor; `lstat` sees the link itself. A descriptor that is closed has no link, as it has no entry in the `fd` listing, also while its release waits for another thread's call. This is the identity check used by musl's `ttyname` implementation. `open` of `/proc/<pid>/fd/N` follows the link, as Linux does (`proc_fd_open` in `syscall_fs.c`): a file or a directory is opened again by the node the descriptor is open on, with an open's checks and a description of its own, so a file that has lost its name opens too; a pipe, a socket, a terminal or a device gets the descriptor's own description, shared as `dup` shares it, when the descriptor has the access asked for, where Linux opens a pipe's other end anew, and is `EACCES` otherwise. Another process's descriptor needs a privileged caller or one with the process's effective user ID. Under `O_NOFOLLOW` either link answers `ELOOP`, and under `O_CREAT|O_EXCL` it answers `EEXIST`, as a link on a mounted type does. With `O_PATH`, `O_NOFOLLOW` gives a descriptor on either link, `/proc/self` without it the process directory, and `/proc/<pid>/fd/N` without it `ENOENT` again.

## sysfs

`/sys` is the third synthetic mount, read-only, with file-system id 7 and the `statfs` magic of Linux's sysfs. It has the parts of Linux's tree that BusyBox's `lspci` and `lsusb` read, as `sysfs(5)` gives them: `/sys/bus/pci/devices` and `/sys/bus/usb/devices` hold a symbolic link for each PCI function and each running USB device, to its directory under `/sys/devices/pci0000:00` or `/sys/devices/usb`, which holds its `uevent`. A PCI function is named by its configuration address, a USB device by its bus and ports, and `synth_classify` turns a name into the device's key, a number, as it turns a pid's digits into a number: whether the device is there is asked at stat, open and readlink (`sysfs_device_exists`), by the function's vendor register or by the USB table. A link is classified and not resolved, as `/proc/self` is: an lstat sees the link, and a path through it names the device's directory. A `uevent` is a snapshot like a `/proc` file's, taken at open. `/sys/class/net` holds a directory for each network interface, keyed by its index and found by its name (`sysfs_net_index`), with Linux's attribute files, a `statistics` directory of the counters `/proc/net/dev` prints, and a `device` link to the card's PCI function, which its driver records in `pci_key`; each attribute is a snapshot as well (`procfs_gen_netattr`), and the descriptor keeps the node and the attribute in `origin_task`. `/sys/class/rtc/rtc0` has the CMOS clock's date, time, seconds since 1970, name and `wakealarm`, and `device/power/wakeup` says the clock may wake the machine, which BusyBox's `rtcwake` reads; `/sys/power` has `state` and `mem_sleep`, the one sleep state, suspend to idle, by its two names (`procfs_gen_sysattr`). `wakealarm` and `state` take a privileged write (`procfs_open_sysattr`): the first sets the wake alarm of `/dev/rtc0` (`devfs_rtc_set_wakealarm`), and a write of `freeze` or `mem` to the second suspends to idle until a wake event. `/sys/block` holds a directory for each disk of devfs's table, keyed by its node's index there and found by its name (`sysfs_block_find`), with Linux's attribute files, a `queue` and a `device` directory, and a directory for each partition published; `/sys/dev/block` holds a link named by each node's numbers to its directory (`sysfs_block_devno`). Their text comes from `devfs_disk_row` (`procfs_gen_blockattr`), which is what `lsblk` reads. The classifier takes paths of up to seven components, the depth of `/sys/class/rtc/rtc0/device/power/wakeup`.

## Snapshot lifetime

Opening a proc text file builds it once in a buffer allocated from the heap. The buffer grows as text is appended, so a report includes every row. If the heap cannot supply the text buffer, open returns `ENOMEM` and logs one line identifying the file. `/proc/disk` alone uses a fixed formatter buffer of `DISKINFO_RECORD_BYTES + DISKINFO_DISKS_BYTES`: 1024 bytes for the main record plus space for every disk and partition record. The current bound is 15232 bytes, including the terminating NUL. Open rejects a result at or above that bound minus one with `EOVERFLOW` and logs the file name.

The descriptor reads this fixed image until EOF. Duplicated and inherited descriptors share the open-file description and its offset; the snapshot and its buffer are freed on the last close of the description. A per-process snapshot therefore remains readable after that process exits. Proc text files are read-only, poll as readable, and report `st_size` as zero because their size is not generated by stat. `mem` and `oom_score_adj` are no snapshots: each read and write reaches the process as it is then. A read or a write of any `/proc` file holds the description for its length, as a seek of it does (`ops_offset_held` in `syscall_fs.c`), since the transfer sets the offset past what it moved and may sleep first, in a fault on the caller's buffer or, for `mem`, in bringing in a page of the process: a seek through a descriptor that shares the description waits and then moves on from where the transfer left the offset, as Linux's position lock has it. `pread64` and `pwrite64` hold nothing, since they work on a copy of the description.

Every synthetic directory includes `.` and `..`. `/proc` enumerates live processes, `/proc/<pid>/fd` enumerates live descriptors, and `/dev/pts` enumerates allocated slaves. These listings are snapshots only at the syscall level: another `getdents` call reads the current kernel tables from its saved index.

## Verification

The default `make test` boot runs these relevant probes:

* [devprobe.c](../../../tests/devprobe.c) checks the memory devices, trusted `urandom`, a disk ioctl refused on `/dev/null`, the inode `fstat` and the `/dev` listing give `/dev/null`, `/proc/self/stat`, and the console fd link.
* [ptyprobe.c](../../../tests/ptyprobe.c) checks master allocation, slave unlocking, terminal ioctls, cooked input, echo, and output.
* [procprobe.c](../../../tests/procprobe.c) checks snapshot lifetime, process names, system files, delivered tick accounting, mount records, network formats, socket identity, and complete output for sixteen TCP listeners.
* [statmusl.c](../../../tests/musl/statmusl.c) checks stable synthetic timestamps through path and descriptor stat calls.

[devtest.c](../../../tests/musl/devtest.c) is built and staged as `/musl/devtest`, but the default runner does not invoke it. Its manual checks include `ttyname`, directory enumeration, access and symlink semantics, and `openat` relative to `/dev`.

Specialized targets cover state that one shared test boot cannot provide:

* `tests/run bootpart` uses four boots to check an absent boot partition, a writable fixture, boot devices under a RAM root, and 64-bit whole-disk offsets on a sparse AHCI disk.
* `tests/run authority` compares ordinary and recovery kernels, the one-writer reservation, 64-sector batching, and driver command and cache-flush counts.
* `tests/run procfiles` checks three root-mount sources, then BusyBox `ps`, `df`, `free`, `uptime`, `dmesg`, `route`, `arp`, and `netstat` against the generated files.
* `tests/run host` runs [synthfs_hosttest.c](../../../tests/host/synthfs_hosttest.c) for the core path classifier and [mbr_hosttest.c](../../../tests/host/mbr_hosttest.c) for MBR parsing and boot-window selection.

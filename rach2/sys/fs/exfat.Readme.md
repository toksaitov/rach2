# exFAT

`exfat.c` is the `exfat` type. It reads an exFAT volume in the partition window that `mount(2)` places, as [vfs.Readme.md](vfs.Readme.md) describes, through the buffer cache in 4 KiB blocks, one buffer held at a time. exFAT is the file system every flash drive above 32 GB and every SDXC card is sold with; this driver reads it from Microsoft's published specification, and what it shares with the FAT32 driver (the name check and conversion, the DOS timestamp fields, the allocation hint, the dirty-volume walk's bitmap and lock, the mount options) lives in `fatcommon.c`. It writes as well, under the rules below.

## The volume check

The constructor reads the boot sector and checks it field by field before the mount is published; a volume that fails is refused with `EINVAL` and a record naming the field, `exfat: refused: FIELD`. Three of those fields say only that the volume is not exFAT, `FileSystemName`, `JumpBoot` and `BootSignature`, and they are refused without a record: a mount is how a caller asks whether a volume is this file system's, and `rach2-install` asks every partition of every removable disk that way to find its image. A driver that wrote a warning each time it was asked about a partition that was never its own put `exfat: refused: FileSystemName` in front of a person installing a machine. A volume that claims to be exFAT and is broken still names its field. Both regions' checksums are read first, and the fields that are checked are those of the region the mount trusts (below). In order: `EXFAT   ` at offset 3; the jump `EB 76 90`; fifty-three zero bytes at 11; the boot signature; a bytes-per-sector shift of exactly 9, because every block device here is 512-byte sectors and a volume whose logical sector is larger is a different layout in every offset, so it is a valid exFAT this kernel does not read, refused by name; a sectors-per-cluster shift that keeps a cluster within 32 MiB; one or two FATs; a file-system revision of 1.00; a volume length within the device and of at least 1 MiB; a FAT offset at or past sector 24, so that both boot regions lie before it; a nonzero cluster count at most 2^32 less 11; a FAT length of at least `(ClusterCount + 2) * 4` bytes, so that every cluster has an entry; a cluster heap that follows the FATs; a cluster count that fits the heap; a root cluster within the heap; and an active FAT the volume has. `PartitionOffset` is not read: the block device is a partition window and gives no first sector to compare it with.

Both boot regions are checked, always, before any field is trusted: the checksum over the eleven sectors before each region's checksum sector, skipping `VolumeFlags` and `PercentInUse`, which a mount changes, every word of the checksum sector repeating it, and the backup boot sector compared with the main in every field but those. If both regions pass and agree, the mount proceeds. If the main region fails and the backup passes, the mount proceeds read-only from the backup's fields, with the main's flags, which the specification says are the live ones, and with a record, because the main copy is what the next driver will trust. If the backup fails, or the two disagree, the mount is read-only with the disagreement named, because a writer that trusted one of two conflicting descriptions could be wrong. If both fail, the volume is refused. A volume with two FATs is TexFAT and mounts read-only; so does one whose flags say `MediaFailure`. The percent in use is read and never trusted. The record is `exfat: mounted read-only: WHY`.

## The root and what it must hold

The root directory is read next, through its FAT chain; a chain that leaves the heap or loops is refused. It must hold the allocation bitmap of the active FAT and one up-case table entry, and a second of either is refused, each with a first cluster in the heap and a length that fits, the bitmap's at least `ceil(ClusterCount / 8)` bytes; a volume missing either is refused with the object named. A volume label is optional and read by nothing. A benign primary entry, such as a volume GUID, is kept byte for byte. A bitmap entry for the other FAT, which only TexFAT has, keeps the mount read-only. The reader passes over a critical entry of a type this driver does not know; a directory holding one is frozen for writing, as the section on writing says.

## The up-case table

The table is the volume's, and every comparison and every name hash goes through it, for every UTF-16 unit, because that is what exFAT's case-insensitivity means; ASCII folding is not enough. The bitmap and the table are read through their FAT chains, since their entries carry no `NoFatChain`. At mount the stored table is read once through the cache and checked: its checksum over the stored bytes must match the entry, and its runs must expand to exactly 65,536 mappings, where a `0xFFFF` followed by a count is that many identity mappings, anything else maps the next unit, a run of zero length or one past the end is a fault, and a `0xFFFF` as the very last unit is the mapping of U+FFFF to itself, which the recommended table ends with; and the first 128 mappings are the mandatory ones, each code point to itself but `a` to `z` to `A` to `Z`. A table whose stored form is at most 16 KiB is kept per mount in that form and up-cased by walking its runs. The mappings of the first 2048 code points are read once at mount by one walk of the table and kept in the mount's record, since a lookup hashes the name of every set it passes and the walk is otherwise per character. A larger table is not held: an uncompressed one, which is exactly 128 KiB of explicit units with no run marker, is indexed through the cache at unit times two; a compressed one larger than 16 KiB, whatever its size, is streamed from its beginning through the cache for every unit, which is correct and slow. The record `exfat: up-case table: FORM` says which form the mount has.

## Entry sets, names and chains

A file is a set: the file entry, then exactly one stream extension in the second position, then one name entry per fifteen units, then any benign secondaries. The set is checked before it is trusted, entry by entry as it is read, so a set with the format's 255 secondaries costs no more memory than one with two: `SecondaryCount` is at least 2; every entry after the file entry is an in-use secondary, which is what keeps a set from swallowing the next file's entries; the set checksum over every byte of every entry but its own two matches; `NameLength` is at least one and its `ceil(NameLength / 15)` name entries follow the stream at once, with the units past it zero, and only benign secondaries after them, a second stream or a critical secondary this driver does not know being a fault; the reserved flag bits are zero; `ValidDataLength` is at most `DataLength`, and a directory's two lengths are equal and at most 256 MiB; a `NoFatChain` stream has a length; the stream's `AllocationPossible` is set, as the specification requires of a stream; a stream with a nonzero length has a first cluster in the heap and one with no length has none; a `NoFatChain` stream's run fits the heap; and the name hash equals the hash of the up-cased name. A set that fails any of these is passed over as one unit, `SecondaryCount` and all, with a record, `exfat: set skipped: WHY`, and the directory's other sets are read; a set whose only failing check is its checksum is passed over the same way until the dirty-volume check rewrites it. A set may cross a sector and a cluster boundary, and the reader follows the directory's chain across both. Benign secondaries are kept and counted. A vendor allocation entry gives a first cluster and a length, which the dirty-volume walk marks like any other chain; the bytes of a vendor entry are never read.

A stream with `NoFatChain` set is contiguous and its FAT is never read; one without it follows the FAT, where the end of a chain is `0xFFFFFFFF`, a bad cluster `0xFFFFFFF7`, and a value outside the heap, or a cluster that names itself, ends the chain with `EIO`, under the same bound on steps as FAT32; a longer loop within a file's length repeats its clusters, and the dirty-volume check is what finds it. A chain that ends before the file's length answers `EIO` at the first byte it cannot reach, after the bytes it can. Bytes past `ValidDataLength` and up to `DataLength` read as zeros, whatever the disk holds there, and the file's size is `DataLength`.

Lookup converts the name (`fatcommon.c`: at most 255 bytes of UTF-8 in at most 255 UTF-16 units, none of the characters FAT forbids, which are the control characters below U+0020 and `" * / : < > ? \\ |`, no trailing dot or space), hashes it through the up-case table, and compares by hash first and then by up-cased units. `.` is the directory itself. exFAT directories have no dot entries, so `..` is the directory this one was found in, which its node remembers; when that node has been put, the parent is found again by a bounded walk of the tree from the root. A name whose UTF-8 does not fit the kernel's 255-byte component is listed by its first sixty UTF-16 units, a surrogate pair never split, and is unreachable by path, as on FAT32.

## Writing

Metadata is written through and data is written back, as [vfs.Readme.md](vfs.Readme.md) describes for the cache, with one batching: the bitmap bits and FAT entries of a run of clusters allocated together, of a chain freed and of a contiguous chain written into the FAT are set in the cache and reach the disk in runs at the sync that precedes the join, the publication or the return, followed by the device's own flush, so a file written in one go costs a few metadata writes and not three per cluster. A write that has joined a run to a file's chain and then fails, at the join's flush, ends the chain at its old tail again and frees the run through `free_chain`, which flushes before it frees a cluster; a tail that cannot be ended again keeps its run, as lost clusters a check frees. So a crash on the way leaves lost clusters and never a chain running into free ones. A file grown across a cluster by `truncate` has the join on the medium before the length that counts on it. A rename elsewhere flushes the retirements of the destination and the source before it publishes the new name, so a drive keeping writes pending cannot put the publication first and a crash between leaves no name rather than two; and `fsync` sends the device's own flush after the cache's writes, as `sync` and the unmount do. The exFAT host test's device model, which keeps every write pending until a flush and judges a crash with none, each of the newest one to six, or all of them kept, and a flush that fails with the older half on the medium, is what holds these. Every mutation runs under the mount's namespace lock, which the driver asserts at each. The order of writes is FAT32's with the bitmap in the FAT's place: a cluster's bitmap bit is set and its chain written before any entry refers to it; data is written and synced before a length is published; a set is unpublished before its clusters are freed, and the clusters of a node a description holds are freed at its last `put` and not before; a truncation shortens the stream before it frees the tail; a directory grows by a zeroed, chained cluster before an entry is written into it.

A set is made or unmade by one bit, the in-use bit of its file entry. Creation writes the entries that lie outside the file entry's sector first, then that sector, whose file entry carries the in-use bit and the checksum over the whole set; a stop before the last write leaves secondaries with no primary, which every reader passes over and the check frees. When the set reaches past the file entry's sector, a barrier comes before that sector, since a drive that holds writes may put sectors on the medium in any order and could otherwise put the file entry there first, a published set whose secondaries were never written. Every set this driver makes has its file and stream entries in one sector: when the free run in a directory would put the file entry in a sector's last slot, an inactive entry fills that slot and the set begins in the next sector. A filler an earlier set left is passed over, not written again. A scan reads each cache block of the directory once into the mount's record and takes its entries from there. A change that touches only those two entries, which is every length, time, flag and attribute change, is then one sector write, the unit the guarantee is built on. On a set another writer made whose two entries straddle a sector, the change is two writes, the stream's sector first and the file entry's last, and the stop between them leaves a set whose checksum alone fails, which the check repairs by rewriting it, as `fsck.exfat` does. Removal writes the file entry inactive, then the secondaries inactive, with a barrier between the two when a secondary lies in another sector than the file entry; the chain and its bits go at the node's last `put`, and a vendor allocation's clusters go with them, since nothing else would free them. A rename carries the set's benign secondaries to the new name. A rename within one directory that keeps the entry count rewrites the names and then the file entry's sector; any other rename finds the room at the destination first, so `ENOSPC` destroys nothing, writes the new set there with its file entry inactive, unpublishes a replaced destination (its clusters kept for its holders, as unlink does) and then the source, and publishes the new file entry last. A stop after the source is unpublished leaves a nameless chain with its data intact, which the check counts and a host tool recovers: the one way a crash costs a name.

Every file and directory this driver creates has a FAT chain and `NoFatChain` clear, which every reader accepts. A contiguous file or directory it extends has its run written into the FAT first, its stream entry changed with the flag clear, and only then grows. Every byte this driver writes is inside `ValidDataLength`; a shrink sets it to the smaller of its old value and the new length; a growth by `truncate` raises `DataLength` alone, so the new range reads as zeros without a write; a write beyond it zero-fills and syncs the gap first, the part inside the last allocated cluster included, and publishes the new lengths after. A cluster is allocated first-fit in the bitmap from the cluster after a file's last, so a file written in one go over free space takes consecutive clusters, and `ENOSPC` is decided before anything is written, the conversion of a contiguous chain included. A directory grows by one cluster at a time and not past the format's 256 MiB. A name is checked as on FAT32 and hashed through the up-case table; two names that up-case alike in one directory are one name (`EEXIST`). Timestamps are written as UTC with the offset byte valid and zero: creation once, modification at every write with its 10 ms field, access never advanced.

`VolumeDirty` is set in the main boot sector when a writable mount is constructed and stays set for its life, as Linux does; `sync` writes the percent in use beside it, the bitmap's used share rounded down, and the clean unmount, after every dirty buffer is written and the percent is on the disk, clears the bit last, so a failure anywhere before leaves the volume marked dirty. The backup boot region is never written, and the boot checksum skips the bytes that change. A directory found to hold a critical entry this driver does not know, when it is first read to its end before a change, is frozen: every change inside it answers `EROFS` with a record, and it cannot be removed or renamed; the rest of the volume is unaffected. Writes and truncations accept file lengths through 2^63 - 1 bytes, subject to available clusters; a larger request returns `EFBIG`. Directories are limited to 256 MiB.

## A dirty volume at mount

A volume whose dirty bit is set was written by something that did not unmount it. Before a writable mount is published, and under the walk bitmap the FAT drivers share, one walk at a time, the tree is walked: the root's chain, the bitmap's and the up-case table's are marked first, disjoint and allocated; then every set the tree reaches, in every directory, is checked as the reader checks it and its chains marked, a contiguous stream counted by length, a chained one followed, a vendor allocation's clusters marked. A cluster reached twice, a chain that leaves the heap or loops, a stream shorter than its length, a reached cluster whose bitmap bit is clear, an in-use set that fails any check but its checksum, a critical entry this driver does not know, an entry of a set that is not an in-use secondary, an allocation bitmap, up-case table or label entry anywhere but the root, and two names that up-case alike in one directory are faults: the volume mounts read-only with the first one named, `exfat: check: WHY; read-only`, and nothing is written. A clean volume is trusted as every other driver trusts it.

Three states this driver's own order leaves behind a crash are repaired once the whole tree is walked, each repair a metadata write, in an order a second crash cannot make worse: a set failing only its checksum, which a stop inside a straddling change leaves, has its checksum rewritten; orphan secondaries, which a stop before a file entry's write leaves, are written inactive; and a surplus tail, which a stop between a chain's join and its length's publish leaves, is detached at the last cluster the length justifies and then freed, since those clusters were never published. Then the bitmap is compared with the walk: a bit set that nothing reached is lost, counted, recorded and left allocated, because a nameless chain after a crash may be a file a rename had unpublished and not yet republished, and its bytes are the only copy; a host checker recovers such chains into files, and this driver does not. The free count is the bitmap's after the repairs. The dirty bit stays set through the mount and is cleared by the clean unmount as usual.

## Nodes, times and modes

A node is a record allocated from the heap when first needed by a lookup or creation, or for the root at mount. It is added to the mount's node list and freed at its last put. A lookup that cannot allocate a node returns `ENOMEM` and logs the failure. A directory's identity is its first cluster; a file's is its directory's cluster and the index of its file entry, and the inode number is built from the same fields: a directory's is its cluster, a file's has its directory's cluster plus one in the high word and its index plus one in the low.

Timestamps are decoded from their bit fields, which are FAT32's date and time in one word, with the year based at 1980, the 10 ms increment added where the field exists, and the UTC offset applied when its valid bit is set: the field is local time and the offset is the zone's, in quarter hours as a signed seven-bit count, so UTC is the field less the offset. A timestamp without a valid offset was written by something that did not record its zone; it is reported as if it were UTC, which is the same approximation FAT32 makes, and is not a conversion. Every entry reports the mount's `uid` and `gid` and the mode `0777` less its `umask`, the options `umask=`, `uid=`, `gid=` and `ro` that vfat takes; an entry with the read-only attribute reports no write bits. `statfs` reports the bitmap's zero bits as free, counted once and kept, with `bsize` the cluster size and the magic `0x2011BAB0` Linux reports.

## Limits

Mount records are allocated from the heap without a fixed count. A cluster is at most 32 MiB, the format's limit. The logical sector must be 512 bytes; any other size is refused by name, which excludes the SDXC cards and drives formatted with 4 KiB sectors. The format's `DataLength` is an unsigned 64-bit value. The driver limits writes and truncations to 2^63 - 1 bytes, the signed 64-bit offset limit, subject to the volume's capacity. The walk bitmap shared with FAT32 and ext2 is taken from the heap for the volume's cluster count, one walk at a time; a dirty volume whose bitmap the heap cannot supply mounts read-only and says why. The walk holds 32 levels of directories, 4096 names along the path it is walking, sixteen surplus tails, sixteen checksum-only sets and sixty-four orphan secondaries; a volume that needs more mounts read-only and says which.

## Verification

`tests/run exfat` is six boots on a disk whose second partition is an exFAT volume: a program writes a tree of every shape and unmounts it, the host's reader walks the volume and reads its bytes, and `fsck_exfat` or `fsck.exfat` judges it where the host has one; the next boot reads every byte back; a boot killed inside a write sequence leaves the dirty bit set, and the next mount checks and repairs the volume and records it; BusyBox copies, moves and removes through the shell; and two writers and a sync interleave under the lag device. `tests/run host` runs `exfatcheck_hosttest` over `mkexfatfixture`'s volumes ([tests/host/Readme.md](../../../tests/host/Readme.md)) and `exfat_hosttest` over the driver: the well-formed volume must read back what the builder wrote through every shape (the contiguous file, the file chained over clusters that are not adjacent, the tail past `ValidDataLength` as zeros, the empty file, the name of four entries, the set with vendor entries, the set straddling a sector, the set crossing a cluster boundary, the directory of two levels), a name is found by another case through the table, in each of the table's three forms; each malformed variant is refused at mount with the field named, mounts read-only with the reason named, has its set skipped, or fails at the file it damages; and, where the host has the tools, a volume its own implementation formatted (`newfs_exfat` through `hdiutil`) and filled through its own driver must mount and list every file in the manifest with the right bytes and times; where it has not, the rows say they were skipped.

# exFAT

`exfat.c` is the `exfat` type. It reads an exFAT volume in the partition window that `mount(2)` places, as [vfs.Readme.md](vfs.Readme.md) describes, through the buffer cache in 4 KiB blocks, one buffer held at a time. exFAT is the file system every flash drive above 32 GB and every SDXC card is sold with; this driver reads it from Microsoft's published specification, and what it shares with the FAT32 driver (the name check and conversion, the DOS timestamp fields, the allocation hint, the dirty-volume walk's bitmap and lock, the mount options) lives in `fatcommon.c`. Writing is milestone 38's phase 4 and is not here yet: the type has no write-side operations, so the common layer answers `EROFS` for them.

## The volume check

The constructor reads the boot sector and checks it field by field before the mount is published; a volume that fails is refused with `EINVAL` and a record naming the field, `exfat: refused: FIELD`. In order: `EXFAT   ` at offset 3; fifty-three zero bytes at 11; the boot signature; a bytes-per-sector shift of exactly 9, because every block device here is 512-byte sectors and a volume whose logical sector is larger is a different layout in every offset, so it is a valid exFAT this kernel does not read, refused by name; a sectors-per-cluster shift that keeps a cluster within 32 MiB; one or two FATs; a file-system revision of 1.00; a volume length within the device; a FAT offset at or past sector 24, so that both boot regions lie before it; a nonzero cluster count at most 2^32 less 11; a FAT length of at least `(ClusterCount + 2) * 4` bytes, so that every cluster has an entry; a cluster heap that follows the FATs; a cluster count that fits the heap; a root cluster within the heap; and an active FAT the volume has. `PartitionOffset` is read by nothing: the window does not know its first sector.

Both boot regions are checked, always: the checksum over the eleven sectors before each region's checksum sector, skipping `VolumeFlags` and `PercentInUse`, which a mount changes, and the backup boot sector compared with the main in every field but those. Both good and agreeing: the mount proceeds. Main bad and backup good: the mount proceeds read-only from the backup, with a record, because the main copy is what the next driver will trust. Main good and backup bad, or the two disagreeing: read-only with the disagreement named, because a writer that trusted one of two conflicting descriptions could be wrong. Both bad: refused. A volume with two FATs is TexFAT and mounts read-only; so does one whose flags say `MediaFailure`. The percent in use is read and never trusted. The record is `exfat: mounted read-only: WHY`.

## The root and what it must hold

The root directory is read next, through its FAT chain. It must hold one allocation bitmap entry and one up-case table entry, each with a first cluster in the heap and a length that fits, the bitmap's at least `ceil(ClusterCount / 8)` bytes; a volume missing either is refused with the object named. A volume label is optional and read by nothing. A benign primary entry, such as a volume GUID, is kept byte for byte. A second bitmap entry, which only TexFAT has, keeps the mount read-only. A critical entry of a type this driver does not know is passed over by the reader; what it means for a writer is phase 4's.

## The up-case table

The table is the volume's, and every comparison and every name hash goes through it, for every UTF-16 unit, because that is what exFAT's case-insensitivity means; ASCII folding is not enough. At mount the stored table is read once through the cache and checked: its checksum over the stored bytes must match the entry, and its runs must expand to exactly 65,536 mappings, where a `0xFFFF` followed by a count is that many identity mappings, anything else maps the next unit, a run of zero length or one past the end is a fault, and a `0xFFFF` as the very last unit is the mapping of U+FFFF to itself, which the recommended table ends with. A table whose stored form is at most 16 KiB is kept per mount in that form and up-cased by walking its runs. A larger table is not held: an uncompressed one, which is exactly 128 KiB, is indexed through the cache at unit times two; a compressed one larger than 16 KiB is streamed from its beginning through the cache for every unit, which is correct and slow. The record `exfat: up-case table: FORM` says which form the mount has.

## Entry sets, names and chains

A file is a set: the file entry, then exactly one stream extension in the second position, then one name entry per fifteen units, then any benign secondaries. The set is checked before it is trusted: `SecondaryCount` is 2 to 18; the set checksum over every byte of every entry but its own two matches; `NameLength` is at least one and covers exactly the name entries, with the units past it zero; `ValidDataLength` is at most `DataLength`; the stream's `AllocationPossible` is set, as the specification requires of a stream; a stream with a nonzero length has a first cluster in the heap and one with no length has none; a `NoFatChain` stream's run fits the heap; and the name hash equals the hash of the up-cased name. A set that fails any of these is passed over with a record, `exfat: set skipped: WHY`, and the directory's other sets are read; what such a set means for the dirty-volume check is phase 5's. A set may cross a sector and a cluster boundary, and the reader follows the directory's chain across both. Benign secondaries are kept and counted; a vendor allocation entry names clusters the walk marks, and its contents are never interpreted.

A stream with `NoFatChain` set is contiguous and its FAT is never read; one without it follows the FAT, where the end of a chain is `0xFFFFFFFF`, a bad cluster `0xFFFFFFF7`, and a value outside the heap ends the chain with `EIO`, under the same bound on steps as FAT32. A chain that ends before the file's length answers `EIO` at the first byte it cannot reach, after the bytes it can. Bytes past `ValidDataLength` and up to `DataLength` read as zeros, whatever the disk holds there, and the file's size is `DataLength`.

Lookup converts the name (`fatcommon.c`: at most 255 bytes of UTF-8 in at most 255 UTF-16 units, none of the characters FAT forbids, no trailing dot or space), hashes it through the up-case table, and compares by hash first and then by up-cased units. `.` is the directory itself. exFAT directories have no dot entries, so `..` is the directory this one was found in, which its node remembers; when that node has been put, the parent is found again by a bounded walk of the tree from the root. A name of 255 units that does not fit the kernel's 255-byte component is listed by its first bytes and unreachable by path, as on FAT32.

## Nodes, times and modes

A node is an entry in a fixed per-mount pool of 32, freed at its last put; a lookup that finds the pool full answers `ENOMEM` and logs it. A directory's identity is its first cluster; a file's is its directory's cluster and the index of its file entry, and the inode number is built from the same fields: a directory's is its cluster, a file's has its directory's cluster plus one in the high word and its index plus one in the low.

Timestamps are decoded from their bit fields, which are FAT32's date and time in one word, with the year based at 1980, the 10 ms increment added where the field exists, and the UTC offset applied when its valid bit is set: the field is local time and the offset is the zone's, in quarter hours as a signed seven-bit count, so UTC is the field less the offset. A timestamp without a valid offset was written by something that did not record its zone; it is reported as if it were UTC, which is the same approximation FAT32 makes, and is not a conversion. Every entry reports the mount's `uid` and `gid` and the mode `0777` less its `umask`, the options `umask=`, `uid=`, `gid=` and `ro` that vfat takes; an entry with the read-only attribute reports no write bits. `statfs` reports the bitmap's zero bits as free, counted once and kept, with `bsize` the cluster size and the magic `0x2011BAB0` Linux reports.

## Limits

Four volumes can be mounted at once. Clusters up to 32 MiB, the format's limit. A logical sector of 512 bytes; any other is refused by name, and the SDXC cards and drives formatted with 4 KiB sectors are the media that means. A file of 2^64 bytes on the format; 4 GiB less one reachable here, because the kernel's file offset is 32 bits. The 2^20-bit walk bitmap shared with FAT32 covers 128 GB at 128 KiB clusters, which matters at the dirty-volume check of phase 5.

## Verification

`tests/run host` runs `exfatcheck_hosttest` over `mkexfatfixture`'s volumes ([tests/host/Readme.md](../../../tests/host/Readme.md)) and `exfat_hosttest` over the driver: the well-formed volume must read back what the builder wrote through every shape (the contiguous file, the file chained over clusters that are not adjacent, the tail past `ValidDataLength` as zeros, the empty file, the name of four entries, the set with vendor entries, the set straddling a sector, the set crossing a cluster boundary, the directory of two levels), a name is found by another case through the table, in each of the table's three forms; each malformed variant is refused at mount with the field named, mounts read-only with the reason named, has its set skipped, or fails at the file it damages; and the gate: a volume the host's own tools formatted (`newfs_exfat` through `hdiutil`) and filled through the host's own driver mounts and lists every file in its manifest with the right bytes and times, where the host has those tools, and says so where it does not.

# FAT32

`fat32.c` is the `vfat` type. It reads and writes a FAT32 volume in the partition window that `mount(2)` places, as [vfs.Readme.md](vfs.Readme.md) describes. Everything on the volume is reached through the buffer cache in 4 KiB blocks, one buffer held at a time.

## What is read

The BIOS parameter block in sector 0, the active file allocation table, and the directory and file clusters the FAT chains name. Only the first 512 bytes of the boot sector are interpreted. A FSInfo sector with its signatures is read for its next-free hint at every mount; the backup boot sector is read by nothing. The active FAT is read; the other FAT is read only by the check of a dirty mirrored volume, which compares it with the active one before rewriting it.

## The volume check

The constructor reads sector 0 and checks it field by field before the mount is published. A volume that fails is refused with `EINVAL`, and the kernel log reports the field: `vfat: refused: FIELD`. In order: the boot-sector signature; the FAT32 recognition rule, which is Linux's (a zero 16-bit FAT size, a nonzero 32-bit one, no root-directory entries, FAT version zero), whatever the cluster count, because the 65525-cluster threshold is a formatting rule and volumes below it exist; a sector size of 512; sectors per cluster a power of two from 1 to 64; a nonzero reserved count; one or two FATs; a total sector count that fits the partition; FAT regions that fit before the data region; a nonempty data region whose cluster count fits a 28-bit FAT; a FAT large enough to cover the clusters; a root cluster inside the data region; and an active FAT the volume has. With mirroring on, the first FAT is read; with it off, the FAT selected by the flags.

## Directories and names

A directory is read at 32-byte entry offsets, which is what `getdents64` reports as the position. A long name is kept when its entries are in sequence and their checksum matches the short entry that follows, and fits the kernel's 255-byte component; otherwise the short name is shown, in lower case where the reserved byte says so, with the `0x05` lead byte restored and a byte above `0x7F` shown as `?`. Deleted entries, volume labels and orphaned long-name fragments are skipped. Lookup folds ASCII case and matches the long name or the short alias, as Linux's vfat does; a non-ASCII name matches exactly. `.` is the directory itself, and `..` is resolved from the directory's own entry, with cluster zero mapped to the root.

A name is checked before anything is written (`fatcommon.c`, which holds what the FAT32 and exFAT drivers share: this check and conversion, the DOS timestamp fields, the allocation hint and the dirty-volume walk's bitmap with its lock; `fat32name.c` holds FAT32's own short names and aliases): at most 255 bytes of UTF-8 converted to at most 255 UTF-16 units, none of the characters FAT forbids (`" * / : < > ? \ |` and the control characters), no trailing dot or space, and neither `.` nor `..`; a name that fails answers `EINVAL`, one past 255 units `ENAMETOOLONG`. A name of 255 non-ASCII characters is legal on FAT and does not fit this kernel's 255-byte component, which is a limit of the kernel and not of the format. A name that fits 8.3 with each of its two parts all upper or all lower case is stored as a short entry alone, with the lower-case parts recorded in the case bits, which is the Windows NT rule and what mtools writes; every other name is stored in long entries in front of a short entry that holds an alias. The alias is this driver's own rule and is not claimed to match Windows. The base is scanned until six characters are produced: dots, spaces and UTF-8 continuation bytes are skipped, ASCII lower case is raised, and a byte a short name cannot hold, or one outside ASCII, becomes `_`; then `~` and the smallest number no entry of the directory uses on the raw eleven bytes; then the first three characters of the last extension, produced the same way. `long name.txt` becomes `LONGNA~1.TXT` and a second name on the same base `LONGNA~2.TXT`, as mtools numbers them; `Mixed.c` becomes `MIXED~1.C` where mtools keeps `MIXED.C`, and `.hidden` becomes `_~1.HID` where Windows keeps `HIDDEN~1`. A name's long entries are written before its short entry and freed after it, so a reader never trusts them without it. A rename within one directory to a name that takes the same number of entries rewrites them in place; any other rename frees and writes as the order of writes says.

## Chains and bounds

A FAT entry is masked to 28 bits. The walk to cluster `n` of a chain is bounded by the volume's cluster count, so a looped chain ends in `EIO` rather than a hang; a per-call step count would not do, because a looped directory whose clusters are full never reaches a zero entry. A chain that ends before the requested index answers `ENXIO` inside the driver: a directory reads it as its end, a file as damage and answers `EIO`. A node keeps a hint from its last walk, used when the target is beyond it.

## Nodes and identities

A node is a record allocated from the heap when first needed by a lookup or creation, or for the root at mount. It is added to the mount's node list and freed at its last put. A lookup that cannot allocate a node returns `ENOMEM` and logs the failure. A directory's identity is its first cluster, so two lookups of one directory share a node. A file's identity is its directory's cluster and its entry index. The inode number is built from the identity: a directory's is its cluster, and a file's has its directory's cluster plus one in the high word and its index plus one in the low, so no two entries share a number.

## Times and modes

FAT keeps local time with no zone; it is read as UTC. Days count from 1980-01-01 through the Gregorian rule; an unset or malformed stamp reads as 1980-01-01. Every entry reports the mount's `uid` and `gid` and the mode `0777` less its `umask`, the options Linux's vfat takes and BusyBox passes through, so under the default `umask=022` a file is `0755`; an entry with the read-only attribute reports no write bits. FAT has no execute bit, so a program on a volume runs unless the mount is `noexec`. The options are `umask=`, `uid=`, `gid=` and `ro`; any other option answers `EINVAL`.

Creation time is written once at creation, with its hundredths; modification time is stamped at every write and truncate, rounded down to FAT's two seconds; access time is stored when set and never advanced by the driver. `setattr` stores a modification or access time, and a mode change in the write bits only, which sets or clears the read-only attribute; a change of any other mode bit, of the owner or of the group, or of a field this call does not store, answers `EPERM`, because the volume cannot store it, which is what Linux's vfat answers. Times pass through the kernel's 32-bit epoch, so a FAT date after 2106-02-07 reads and is written as that limit.

## Writing

Metadata is written through and data is written back, as [vfs.Readme.md](vfs.Readme.md) describes for the cache. Every FAT entry, directory entry, the boot sector's flag and FSInfo go through `bcache_write` and reach the device before the call returns, in call order; a drive that keeps writes pending may put them on the medium in another order, and the flushes named below fix the order where a later write names what an earlier one made. The one batching is inside a run: the FAT entries of a run of clusters allocated together, or of a chain freed, are set in the cache and written through one FAT block at a time, in each copy, when the run moves to another block and at its end, so a 64 KiB append costs a few FAT writes and not one per cluster; the run is whole on the disk before anything names it, as the order of writes below requires. A write that has joined a run to a file's chain and then fails, at the join's flush, ends the chain at its old tail again and frees the run through `free_chain`, which puts what unpublished a chain on the medium before it frees a cluster; a tail that cannot be ended again keeps its run, as lost clusters a check frees. So a crash on the way leaves lost clusters and never a chain running into free ones. The same rule, that a drive keeping writes pending may put a later write on the medium before an earlier one, puts a flush between every pair of metadata writes the second of which names what the first made: a new directory's cluster, chain and two entries before the parent's entry names it; a directory's new cluster, zeroed, before the chain links it; a moved directory's parent link before its new name; the old names freed before the new ones are written in a rename; a removed directory's name gone before its clusters are freed; and a file grown across a cluster by `truncate` has the join on the medium before the size that counts on it. The FAT host test's device model, which keeps every write pending until a flush and judges a crash with none, each of the newest one to six, or all of them kept, and a flush that fails with the older half on the medium, is what holds these. A file's bytes go through `bcache_dirty` and reach the disk at eviction, at `fsync`, at `sync`, and through the periodic sync; where a data write must reach the disk before a metadata write that describes it, the driver syncs the device between the two and then has the device flush its own cache, which a stick has and an ATA disk, writing through, has not. A node keeps the cluster its last walk reached, and an append leaves it at the new tail, so the next append does not walk the chain from the file's first cluster.

Every operation that changes the volume runs under the mount's namespace lock for its whole length: the namespace operations arrive with it held by the common layer, and `write`, `truncate`, `fsync`, `sync` and the reclamation a last `put` performs take it themselves. Two writers, or a writer and a sync, never interleave across the sleeps the writes make.

The rule for the order of writes: a crash may leak clusters and may never cross-link them, and an entry never names a cluster that is free.

* Create: the entry is written free of clusters, with size zero and first cluster zero. A create that needs a new directory cluster is a directory growth first.
* Extend: the new clusters are allocated as a chain of their own, ended and zero-filled, disconnected from the file; the data is written and the device synced; the FAT entry of the old tail is pointed at the new run; the entry's size grows. A crash before the last step leaves a chain longer than the size, which the walk treats as surplus. A file with no clusters yet publishes its first cluster and its size together in the one entry write.
* A write past the end zero-fills the gap before the size grows over it, so the file never reads stale bytes.
* Truncate: the entry's size shrinks first, and its first cluster goes to zero when the size does; the retained tail gets an end-of-chain mark; the detached tail is freed last. A grow is a write of zeros.
* Unlink: the entry is freed first; the chain is freed last, and only when no description holds the node. A held node keeps its chain until its last `put`, and a crash in between leaks the chain. A write through such a description changes the clusters and no entry.
* Mkdir: the cluster is allocated, ended, zeroed and given `.` and `..`, and the parent's entry is written last. A crash before the last step leaks the cluster.
* Rmdir: the directory must contain only `.` and `..` (`ENOTEMPTY`) and must not be held by a description or a working directory (`EBUSY`); then as unlink.
* Directory growth: the new cluster is zeroed and ended before the old tail is pointed at it, so the directory never shows stale entries.
* Rename within one directory to a new name: the entry is rewritten in place. Otherwise, and across directories: the new name and the room for its entries are decided first, with the destination still in place, so `ENOSPC` destroys nothing; if a destination exists it is then freed, its chain freed or left to its holders as in unlink; the source entry is freed; a moved directory's `..` is rewritten; the new entry is written last. A crash between the freeing of the source and the writing of the destination leaves a nameless chain, which the walk reports as lost.

The dirty flag is set before the first metadata write after a mount, in both places (bit 27 of FAT entry 1 cleared, bit 0 of byte 65 of the boot sector set), and stays set for the life of a writable mount. It is cleared only by the clean unmount, after every dirty buffer is written and FSInfo is current; a failure there leaves the volume marked dirty and the mount where it was, and a mount that went read-only after a failed write is unmounted without touching the volume, which stays marked dirty. FSInfo, when the volume has one with its signatures, is written at `sync` and at unmount with the free count and the next-free hint this driver keeps; the hint is read at mount and the count is computed from the active FAT the first time it is needed. With mirroring on, every FAT write goes to the active copy first and the mirror second.

A cluster is allocated first-fit from the hint, which after a file's growth is the cluster after its last, and the search wraps once. `ENOSPC` is decided before any FAT sector is written, and a run that cannot be completed is given back. The largest file is 4 GiB less one byte, answered with `EFBIG` past that.

## A dirty volume at mount

A volume whose dirty flag is set was written by something that did not unmount it. Linux mounts it and says nothing; this driver checks it before the mount is published, when the mount is writable. The walk reads the active FAT, which is the copy written first, and every chain the directory tree reaches, root included. It marks clusters in one bitmap, shared by every mount and by the ext2 check and used by one walk at a time, taken from the heap for the volume's cluster count; a volume whose bitmap the heap cannot supply is mounted read-only with a record. A cluster reached twice, a chain that leaves the volume, loops or ends in a free or bad entry, a chain shorter than its file's size, a directory whose `.` is not itself or whose `..` is not its parent, a directory with no cluster, or a name twice in one directory is a state this driver's order never leaves: the volume is mounted read-only with a record naming what was found, and the host tools are the repair.

The check permits thirty-two directory levels, including the root, and records at most sixteen surplus tails. Duplicate-name comparison requires each ordinary short entry to lie within the first 4096 directory slots; long-name and deleted slots count toward that position. Exceeding any bound mounts the volume read-only with the reason logged.

Four states are what this driver's own order leaves behind a crash, and three are repaired in an order a second crash cannot make worse, every repair a metadata write: a chain longer than its size is ended at the size's last cluster first and its tail freed after, so nothing published is lost, and only once the whole tree has been walked, because a tail that another entry's chain enters is a cross-link and not a tail; orphan long-name entries, before an entry whose checksum they do not match or at the end of a directory, are freed; and with mirroring on, a mirror that differs from the active FAT is rewritten from it, last. A cluster marked used that nothing reaches is lost: it is counted in the record and left, since freeing it would destroy what a crash between the freeing of a name and the writing of the next one left behind. The walk counts the free clusters, and FSInfo is rewritten from that count once the repairs are on the disk, so the free count a crash left there is never trusted. The flag stays set through the mount and is cleared by the clean unmount as usual.

## What is refused

A mount's record and its nodes come from the kernel heap, so what limits the volumes mounted at once is memory. `statfs` reports the free cluster count kept by the driver, with `bsize` the cluster size and magic `0x4d44`. A mount whose device fails a write goes read-only for the rest of its life, as the cache's failure record says.

## Verification

`tests/run host` runs `fatname_hosttest` over the name rules alone, against the cases recorded from mtools, and `fat32_hosttest` over `mkfatfixture`'s volumes: the `--vfs` volume must read back exactly what the builder wrote, through fragmented chains, long names across a block boundary and with a surrogate pair, a name with a bad checksum, one over a `0x05` short name, a deleted entry, and `..` back to the root; a valid FAT32 below 65525 clusters mounts; the volume whose active FAT is the second reads through it; entries with reserved high bits are masked; and each malformed volume is refused at mount with the field named or answers `EIO` at the file it damages. The write half of the same test runs each operation as a sequence on a fresh volume, reads the result back through the driver, dumps the image and walks it with `mkfatfixture --check`, and copies a file this driver wrote out with mtools where mtools is installed; then it stops each sequence after every one of its writes and walks the image, which must show nothing but what the order of writes allows: lost clusters, a surplus tail, orphan long-name entries, a lagging mirror or FSInfo, and the dirty flag; the crash state is then mounted read-only and every file a data sequence wrote must read, within its size, the bytes written or zeros, which is the content oracle a size published before its data would fail. The matrix runs twice, with short names and with long ones spanning a sector. The long-name rows write a name of every kind and read it back by its long name and by its alias, list it through the check and through mtools, rename it in place and to a short name, unlink it, rename an open file and write through its description, and set the read-only attribute and the times. The dirty rows mount a volume with the flag over a clean tree, a surplus tail, orphan long-name entries, a lagging mirror and a cross-link, and require the first four to mount writable with the fault repaired and the last to mount read-only untouched. `tests/run mount` mounts a volume that `mformat` wrote, reads it from a program and from BusyBox, and compares the listing with `mdir`'s. `tests/run fatwrite` is the writer's proof in a machine: a program writes files of every kind and unmounts, the host walks the volume and reads it with mtools, the next boot reads every byte back, a boot killed in the middle of a write sequence is followed by the mount's check and repair, BusyBox writes through the volume, and two writers and a sync interleave under the lag device with the driver's assertion at every mutation standing for the lock.

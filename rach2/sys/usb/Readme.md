# `usb/`: the USB stack

The USB stack drives keyboards, mice, tablets and other human-interface devices, flash drives and hubs attached to xHCI host controllers. `xhci.c` is the controller driver and the only code that programs a controller. `core.c` enumerates each device that appears on a root port or a hub port and passes it to a class driver: `hid.c` for a human-interface device, which reads the device's report descriptor as Linux's usbhid does, `hub.c` for a hub, `msc.c` for Bulk-Only mass storage. `usb.c` brings the controllers up and runs the stack from the timer and from the controllers' interrupts. The keyboard, mouse and removable disks of a current PC are USB devices, and the firmware's PS/2 emulation of a USB keyboard stops once the kernel takes the controller from the firmware, so the kernel drives them itself.

## Interfaces

`kernel.c` calls the stack through `usb.h`. After the root file system is mounted, unless the command line has `rach2.nousb`, it calls `usb_report_controllers`, which logs each USB controller from PCI configuration space alone, and `usb_init`, which brings up every xHCI controller and waits for the devices present at boot. `usb_poll` runs the stack from processor 0's one-millisecond service event, and `usb_stop` halts the controllers at shutdown. The terminal's read, the scheduler and `getrandom` call the `usb_stamp_` functions for the latency record.

The stack delivers:

* An event device for each application of a human-interface device ([input(4)](../../../man/man4/input.4)), with Linux's name, IDs, capabilities and events for it. A keyboard's keys go as Linux's key codes through `input_key_event`, with each key's usage as its `MSC_SCAN`, into the input layer that the PS/2 keyboard feeds too and that repeats a held key in software; a pointer with relative X and Y also gives its motion and first three buttons to the queue the PS/2 mouse fills (`mouse_push_packet`, [`mouse.h`](../mouse.h)), and a boot mouse its reports through `mouse_report`. `input_mouse_found`, called when such a pointer is configured, lets `/mouse` be opened ([`synthfs.Readme.md`](../fs/synthfs.Readme.md)).
* A block device for each logical unit of a flash drive, with `submit` and `flush` and no `read` or `write`, since a transfer completes later, in the pump. `block/usbdisk.c` registers it as a removable disk and publishes its nodes; [`block/Readme.md`](../block/Readme.md) describes that side.
* `/proc/usb` and the `FBK` line of `/proc/interrupts` ([`proc(5)`](../../../man/man5/proc.5)), and a link and a `uevent` per device under `/sys/bus/usb/devices`, which BusyBox's `lsusb` reads ([`sysfs(5)`](../../../man/man5/sysfs.5), [`busybox-util-linux(1)`](../../../man/man1/busybox-util-linux.1)).

The boot options:

* `rach2.nousb`: the stack is not started, and the boot logs `usb: skipped: rach2.nousb`.
* `rach2.nomsi`: the local APIC is not used ([`acpi(4)`](../../../man/man4/acpi.4)), so each controller interrupts on its PCI line.
* `rach2.dma32`: every controller is driven as one whose AC64 bit is clear, to test the 32-bit address path.
* `rach2.hcfail=N`: the Nth controller tried, counting from 0, fails its bring-up, to test what happens to the others.
* `rach2.msidrop=N`: the Nth interrupt turns every controller's interrupts off, leaving the timer to run the stack.
* `rach2.usblatency`: the latency record is printed.
* `rach2.hubslow=MS`: a hub's first scan waits MS milliseconds between two ports.

The stack logs under `usb`, and the mass-storage driver under `usbdisk`. A device's place in the tree is written as its root port followed by each hub's port: `5.2` is port 2 of a hub on root port 5.

## Design

| File | What it does |
| --- | --- |
| `usb.c` | The PCI inventory, the bring-up, the pump, the interrupt handler and the stop |
| `xhci.c`, `xhci.h` | Registers, rings, contexts, commands, transfers and events |
| `hcd.h` | The types the controller driver shares with the layers above |
| `core.c`, `core.h` | Device records, descriptors, enumeration, closing, and the rows of `/proc/usb` and `/sys` |
| `hid.c`, `hid.h` | The HID class driver: a device's protocol, names, reports and output reports, and the boot keyboard and mouse |
| `hid_parse.c`, `hid_parse.h` | Report descriptors parsed as Linux's hid-core.c parses them |
| `hid_input.c`, `hid_input.h` | Usages mapped to event devices and input reports read, as Linux's hid-input.c does |
| `hub.c` | The hub class driver |
| `msc.c` | Mass storage over Bulk-Only Transport |
| `stamp.c` | The keystroke latency record |

The core and the class drivers call the functions `xhci.h` declares. `hcd.h` also defines `struct usb_hcd`, an operations table for a second controller driver, which no code uses.

Nothing waits except bring-up. An operation that takes time is started in one pass of the pump and checked in a later one, against a deadline counted in milliseconds of a clock that each pass advances.

### Controllers

`xhci_discover` takes each xHCI controller on the PCI bus, up to `XHCI_MAX_CONTROLLERS`, 4, into a `struct xhci_ctrl` of its own. A UHCI, OHCI or EHCI controller, or an xHCI past the fourth, is logged and not driven. Discovery puts the function in power state D0, sets the port routing of an Intel controller, and maps the first 64 KiB of BAR 0 (`XHCI_MAP_SIZE`). A BAR above 4 GiB is mapped at its full address by the x86-64 kernel; the i686 kernel, whose addresses are 32 bits, does not drive such a controller.

`usb_init` then brings each controller up through five functions of `xhci.c`. `xhci_read_caps` reads the capability registers, rejects a controller whose registers lie outside the mapped window or that lacks 4 KiB pages, and sizes the slot table, the context base address array and the port state from the controller's own counts. `xhci_own` takes the controller from the firmware through the USB legacy support capability, if the controller has one, waiting up to a second, and turns off the firmware's SMIs. `xhci_halt_reset` halts and resets the controller, with the 1 ms pause an Intel controller needs before its registers may be read again. `xhci_scratchpads` gives it the scratchpad pages it requires; a controller that requires more than 512 (`XHCI_MAX_SCRATCHPADS`), the 8-byte entries that fit in one page, is not driven. `xhci_start` enables every device slot the controller has, programs the command ring and a one-segment event ring on interrupter 0, starts it, and powers each root port that has no power.

A controller that fails a step is given back to the firmware (`xhci_release`) and removed from the table, and the others come up. `usb_init` then waits 100 ms for the ports to settle and up to 1 s (`USB_ENUMERATE_MS`) while the timer's pump enumerates the devices present, until `usb_core_busy` is zero, so that hubs have ended their first scans and sticks have brought up their units before the `usb: devices: N configured` line is printed. It enables the controllers' interrupts last. A slower device is finished by the pump after the boot goes on.

The command and event rings and the input context are arrays in the controller's static record. The context base address array, the scratchpads, each device context and each endpoint ring are pages taken as needed: from the heap (`kalloc_pages`), anywhere in memory, for a controller with AC64 set, and from the DMA pool (`alloc_kernel_frame`), below `HARD_MEMORY_LIMIT`, 64 MiB on both architectures, for one with AC64 clear. Every address is given in both halves. On x86-64 a piece of a transfer's buffer can lie above 4 GiB; for a controller with AC64 clear it moves through a DMA pool page kept with the transfer's record, copied in before an OUT transfer and back after an IN transfer, before the completion is reported.

### The companion EHCI

On an Intel chipset with a companion EHCI, four registers in the xHCI function's configuration space route the ports: `XUSB2PR` (0xD0) sends each USB 2 port to the xHCI or the EHCI controller, `USB3PSSEN` (0xD8) enables each port's SuperSpeed side, and `XUSB2PRM` (0xD4) and `USB3PRM` (0xDC) are masks of the bits that may be changed. The firmware may leave ports on the EHCI, and this kernel has no EHCI driver, so `take_ports` switches every port the masks allow to the xHCI controller on each boot. The routing reverts at the next power cycle.

A device whose port is switched in the middle of a transfer may not respond to the xHCI controller's Address Device, so before the switch `quiesce_ehci` takes each EHCI from the firmware through its legacy support capability, turns off its SMIs, halts it, masks its interrupts, and clears its configure flag if the firmware owned it.

### Rings, commands and transfers

A controller has one command ring of 256 TRBs (`XHCI_RING_TRBS`) and one command in flight, which lets one input context serve every command. A command not completed within 5 s (`XHCI_COMMAND_MS`, Linux's `XHCI_CMD_DEFAULT_TIMEOUT`) is aborted. It stays outstanding until its completion or the Command Ring Stopped event arrives, and the next command is issued only after that event and with the Command Ring Running bit clear; an Enable Slot that succeeds during the abort still yields its slot, so the slot can be disabled ([xHCI 1.2](https://cdrdv2-public.intel.com/625472/625472_xHCI_Rev1_2b.pdf), 4.6.1 and 4.9.3).

`xhci_events` drains up to 256 events a call into an eight-entry completion queue (`XHCI_COMPLETIONS`); a transfer event that would overflow it stays on the ring for the next pass. The dequeue pointer is written back with the Event Handler Busy bit after a drain that took events and after the interrupt handler's every drain while interrupts are on, since the controller raises no further interrupt until that bit is written; a timer's drain that took nothing writes nothing, as Linux writes the pointer in its interrupt handler alone. After a drain the root ports' connect bits are read, which times the 100 ms debounce, but only when a Port Status Change Event has come since the last reading, while a connect is inside its debounce, or 250 ms after the last reading (`PORT_POLL_MS`), so that a quiet tick reads no register. A reading clears the change bits it finds, since the controller raises the next Port Status Change Event only when a port's change bits go from all clear to one set (xHCI 1.2, 4.19.2); it leaves the reset's to `xhci_port_reset_done` while a reset of the port is under way, and clears it on any other port, as Linux's `port_event` clears a stray C_RESET, so that a reset abandoned when its device left, or given up on at its deadline by `xhci_port_reset_done` with the device still there, holds back no later event. The write that starts a reset clears a reset change bit still set, so that the first poll does not take it for the new reset's end. This is Linux's root hub, read from a port change event until no change is left and every quarter second by its timer meanwhile; the quarter-second reading here does not stop, so that a change the reset's bit hid from the events is still read. The core's tick reads the connect bits of that last reading (`xhci_port_connected`), not the registers.

`xhci_submit` writes a control transfer as Setup, Data and Status TRBs, its data stage a Data TRB for the first page-bounded piece with a Normal TRB chained to it for each further piece, and a bulk or interrupt transfer as a chain of Normal TRBs, one per page-bounded piece. The first TRB's cycle bit is flipped last, so the controller never fetches half a transfer. An endpoint ring is one page of 256 TRBs, and an endpoint has two transfer records of up to 130 TRBs (`XHCI_TD_TRBS`): a 512 KiB buffer that starts within a page is 129 pieces. A transfer's generation, a number its caller chooses, comes back in its completion, so a caller that gave up on a transfer can tell its late completion from the current one.

A transfer is retired, and its buffer free, when an event reports its last TRB, when its endpoint has been quiesced, or when its slot has been disabled. QEMU posts no event for the last TRB of a transfer that ended short, so such a transfer stays the controller's until its endpoint is quiesced. A stall, a transaction error, babble or a split error halts an endpoint, and any other error puts it in the Error state (xHCI 1.2, 4.8.3); nothing is submitted on it until it is quiesced. `usb_core_endpoint_quiesce` issues Stop Endpoint on a running endpoint, Reset Endpoint on a halted one, and neither on one stopped or in the Error state, then Set TR Dequeue to the next TRB the driver will write, each on the core's command turn and each required to succeed, and then retires the endpoint's transfers.

### The pump and its two contexts

`usb_pump` is the only code that drains the event rings. It advances each controller's clock, which aborts a command past its deadline, drains each ring, and calls `usb_core_step`. The timer runs it through `usb_poll`, with the milliseconds of the ticks counted since its last call elapsed, since the boot processor's tick skips the call while another processor holds the big lock. The controller's interrupt runs it through `usb_msi_handler`, which acknowledges the interrupt and drains in one call, `xhci_interrupt_take`, acknowledging first: an event written between a drain and a later acknowledgement would have its pending bit cleared unread and wait for the timer.

Both contexts run with interrupts off, and the pump restores the interrupt flag it found and never enables interrupts, so the two are never inside a ring at once; the block layer relies on this when a process sleeps on a stick's request. A stick's `submit` and `flush`, the entries from process context, run with interrupts off too, since QEMU completes a transfer inside the doorbell write.

Each controller gets its own MSI vector from `isr_alloc_vector`, 48 to 239, when the local APIC is in use and the controller has an MSI capability; a controller whose MSI enable fails gives the vector back, with its handler. Otherwise it raises its PCI line, IRQ 1 to 15, through the I/O APIC, or through the 8259 when there is no I/O APIC in use, as under `rach2.nomsi`; the handler is registered first, since a level-triggered line the firmware left asserted would otherwise reach no handler. A controller with neither is left to the timer. Every handler is named `xhci` and drains every controller.

Once any controller's interrupts are on, a timer pass that took events while no USB interrupt was pending adds one to the fallback count, `FBK` in `/proc/interrupts`. The pending state includes the APICs of every online processor and message entries already acknowledged but waiting for the big lock or running their handler. It is read after the drain and again after the core's step, since a message can arrive after its event; a message still in flight at both reads is counted too.

### Enumeration

`usb_core_step` delivers each completion to the storage driver, the hub driver, or the device the completion's controller and slot identify, since slot numbers start at 1 on every controller. It takes down each device whose port shows no connection, gives a record to each new connection on the first 32 root ports of each controller and on the ports of each running hub, steps every device, and then steps the storage driver, the hub driver and the USB disk layer. The 16 records (`USB_MAX_DEVICES`) are shared by all controllers and hubs. A device record is one 4 KiB frame of the DMA pool, since the controller writes descriptors and reports straight into it; it has room for a configuration of 3072 bytes (`USB_DESC_MAX`).

A device moves one step per pass at most. Its port must be connected for 100 ms without a change, and a connection that does not settle within 5 s frees the record. The device then takes its controller's command turn, held by one device of each controller at a time, since the controller has one command in flight; devices on two controllers enumerate at the same time. Its port is reset, and the device is given 50 ms of reset recovery (`RECOVERY_MS`, the specification's 10 ms and the 40 that Linux adds), since a device sent Set Address sooner can leave Address Device unanswered; Enable Slot and Address Device follow, with a default control packet size of 8 bytes at low and full speed, 64 at high speed and 512 at SuperSpeed. The first 8 bytes of the device descriptor give the real packet size, which Evaluate Context sets for a full-speed device; then come the 18-byte device descriptor, the 9-byte configuration header and the whole configuration. Configure Endpoint opens each endpoint the class driver needs, a separate command for each of a stick's two and for the interrupt IN endpoint of each HID interface kept (`ST_OPEN_HID`), and `SET_CONFIGURATION` follows; a Configure Endpoint the controller refuses fails the device, as Linux fails a configuration whose bandwidth it cannot have. A stick goes to `msc_attach`, a hub to `hub_attach`, and a human-interface device to the HID setup of [Keyboards, mice and tablets](#keyboards-mice-and-tablets).

`SET_CONFIGURATION` has 5 s (`CONFIG_MS`), since a stick may still be starting its flash memory, Address Device the command deadline and 500 ms more, so that the controller aborts an unanswered command before the device gives up on it, and every other step 500 ms (`STEP_MS`); a step that fails or passes its deadline fails the device. An Address Device that fails or is aborted is tried again after another reset of the port, on the slot already given, four times in all (`ADDRESS_TRIES`, as Linux's `hub_port_init` tries a port), and only then is the port refused. When Enable Slot completes with code 9, no slot free, the device keeps its record and its reset and issues Enable Slot again every 500 ms.

`usb_parse_config` walks the configuration by each descriptor's length, stopping at a length below 2 or past the bytes that arrived, and chooses the first interface with alternate setting 0 that is a human-interface device (class 3, any subclass and protocol) or a hub (class 9, protocol 0 to 3) with an interrupt IN endpoint, or mass storage (class 8, subclass 6, protocol 0x50) with a bulk IN and a bulk OUT endpoint. A hub or a stick is the one interface driven. After a human-interface interface the walk keeps every further one on alternate setting 0 with its interrupt IN endpoint, as Linux binds usbhid to each, and passes over the other classes; one that repeats the number or the endpoint of an interface kept is passed over, as Linux drops a duplicate endpoint and usbhid then refuses its interface. The room for 15 (`USB_HID_INTERFACES`) is every HID interface a configuration can have, since each has an IN endpoint of its own and there are 15 IN endpoint numbers. Of each human-interface interface it also keeps bcdHID and the report descriptor's length from the HID descriptor, which may come before or after the endpoint. A HID device's interfaces, with their report transfers' buffers, are a second frame of the DMA pool beside its record. A SuperSpeed hub is recognized by its speed, since USB 3 puts its hub protocol in the device descriptor.

When a device fails or no class driver takes it, its port's bit is set in a bitmap, per controller or in the hub's record, and the port is left alone without spending a record. The bit is cleared when the port shows no connection, so the next device plugged in there is tried. When no record is free, the port is logged once and tried on every pass.

`usb_core_busy` counts the devices the stack has not finished with: records being enumerated, recovered or closed, hubs before the end of their first scan (`hub_starting`), and sticks whose units are being brought up (`msc_starting`). A device waiting for a slot or a free record is not counted, since it may wait for ever. `/proc/usb` gives the count as its `busy` line while it is above zero, so a program that waits for the line to go sees the end of enumeration whatever the speed of the machine. The file takes the count before it lists the devices, because the pump can run between two lines: a device that finished after its line was passed would otherwise be neither listed nor counted.

### Locations

A device is opened at a `struct usb_location` (`hcd.h`): its root port, its depth, its route string and its transaction translator. The route string has 4 bits for each of 5 tiers (`USB_TREE_TIERS`), the port on the hub nearest the root in the lowest; a device with more than 5 hubs above it is not driven. A port above 15 is written as 15, which the specification allows only for a low- or full-speed device directly below its high-speed translator, whose 8-bit port number gives the real port; anywhere else a device on such a port is not driven.

A low- or full-speed device's translator is the nearest high-speed hub above it, with that hub's port on the path and whether the hub has one translator per port. `xhci.c` writes them into the slot context, and the controller performs the split transactions. A hub's own slot context gets the hub bit, its port count, its think time and, when it has one translator per port, the multi-TT bit, through Evaluate Context.

### Keyboards, mice and tablets

For a touchscreen or touchpad with HID Contact Identifiers, `hid_input.c` groups the report fields into contacts and reports them in type B slots. A contact keeps its slot across a change in report order. A positive Contact Count starts a frame and continuation packets can complete it. Explicit lifts and devices that report only the remaining contacts use their respective rules. Precision Touchpad reports keep the first packet's buttons and carry palm and hover state.

After `SET_CONFIGURATION` the core reads a human-interface device as Linux's usbhid does, each request a step of its own (`ST_HIDSETUP`): string 0 for the first language, and the manufacturer, product and serial strings in it when the device descriptor names them, once for the device; then for each HID interface in turn, `SET_IDLE` with a duration of 0 and the report descriptor, `GET_DESCRIPTOR` of type 0x22, each to that interface's number, the descriptor of the length its HID descriptor gave. A string, `SET_IDLE` or the report descriptor that the device refuses is done without, its control endpoint reset first (`ST_EP0RESET`). The descriptor goes to `hid_attach` for that interface. For a multitouch interface the core fetches its Contact Count Maximum feature before publishing the event node, and sets the Input Mode feature to touchscreen or touchpad where present, preserving the other fields of the report. A reply that already carries the requested mode needs no write. If the count is unavailable, the driver uses a valid bound from the descriptor, or ten slots. A failed mode switch leaves the touch surface unpublished, including buttons in separate reports. Other applications register even when they share the same report ID. Each node's keymap uses only the fields assigned to that node. When it cannot be had, or the driver refuses it or finds nothing input handles in it, a boot keyboard or mouse interface (subclass 1, protocol 1 or 2) is put in the boot protocol with `SET_PROTOCOL` and goes to `hid_attach_boot`, as Linux's usbkbd and usbmouse take one. Any other interface, and one that refuses `SET_PROTOCOL`, is given up alone and the others are driven. A device runs when its driver took one interface or more; a device left with none fails when an interface was given up for a request it refused, and is a device with no driver here otherwise.

`hid_attach` parses the descriptor twice (`hid_parse`): once to count its fields, usages and collections, then into tables of those sizes, allocated for the device. The parse follows Linux's `hid_open_report`: items, global, local and main, a Push stack of four, usage pages joined to usages at each main item, usage ranges cut at 12288 usages, Report IDs 1 to 255, a Report Size of at most 256 bits, a report of at most 16384 bytes with its ID, and the fields past 256 in one report dropped. A descriptor Linux refuses, such as one with a long item, an item cut short, a logical maximum below its minimum or a collection left open, is refused with `-EINVAL`.

`hidinput_connect` then maps each usage to an event as Linux's `hidinput_configure_usage` does, for the generic desktop, keyboard, button, LED, consumer, simulation, telephony and camera pages and the vendor pages Linux maps; a usage of no known page is a button, an LED or a miscellaneous axis by the shape of its field, and the other vendor pages map to nothing; on the Generic Device Controls and Battery pages, the usages of a battery's charge, which feed Linux's power supply, are typed `EV_PWR` as Linux types them, report no event and are not keymap entries, and the rest are unknown usages, as Linux maps them. An LED usage shows the LEDs of the event device that owns its field: those a program lit with `EV_LED`, and on a keyboard Num, Caps and Scroll Lock from the console in place of its own, in the LED report the next step sends. As hid-generic does, one event device is made for each application collection, a System Control or Consumer Control application joining a keyboard's. A device's name is "MANUFACTURER PRODUCT", or "HID VVVV:PPPP" without strings; with more than one application each event device adds its application's suffix, "Keyboard", "Mouse", "Consumer Control" and so on, unless the name ends with it already. Each HID interface is a device of its own, with its own report descriptor, tables, event devices and output reports, as each is one usbhid device on Linux. bcdHID is its version, "usb-N/inputI" its place, N the core's table entry plus one and I the interface's number, and the serial string in at most 63 bytes, cut before the first character that would not fit, or "" without one, its `EVIOCGUNIQ`, as usbhid gives `hid->uniq`. An event device with keyboard usages is attached to the input layer, which repeats its keys and gives them to the console. QEMU's tablet is "QEMU QEMU USB Tablet" with `BTN_LEFT` to `BTN_EXTRA`, `REL_WHEEL` and `REL_WHEEL_HI_RES`, `ABS_X` and `ABS_Y` over 0 to 32767, and `MSC_SCAN`, as Linux gives it.

Each HID interface that runs has one interrupt IN transfer outstanding on its own endpoint, of its longest input report with the ID byte, or of the endpoint's packet in the boot protocol, as usbhid sizes its buffer: a transfer of 64 bytes or fewer goes into the interface's buffer in the frame, a longer one into a buffer from the heap of that length. A completion goes to the interface whose endpoint it came from, then to `hid_report` for that interface; it is counted in the interface's record, the device's interfaces summed as the `reports` field of its `/proc/usb` line, and the next is queued. After a failed transfer the core quiesces that endpoint and resumes. A report is read as Linux's `hid_input_report` reads one: its ID chooses the report, a short one is padded with zeros, a variable field's values are reported in usage order, and an array field's usages that left are released before those that came are pressed; an absolute value that did not change is not reported, a value out of range is clamped, or dropped where the field has a null state, and an array that holds ErrorRollOver is ignored. A key gives its usage as `MSC_SCAN` before it; a wheel gives 120ths on its hi-res axis and whole detents on the other; each event device's events end with `SYN_REPORT`.

At each pass the core asks `hid_output_report` for a report to send, of each interface in turn from the one after the interface sent last, and sends the first it is given as `SET_REPORT` to that interface on the control endpoint, which nothing else uses on a running device, one at a time for the whole device, from the record's descriptor buffer, which a running device no longer needs, or for a device whose longest output or Feature report (`hid_output_size`) is longer, from a buffer from the heap of that length, whose data stage the controller driver chains across its pages; `hid_output_sent` hears its outcome. First, on a device with a Resolution Multiplier whose Feature report holds nothing else, the report that sets each multiplier to its maximum, as Linux sends it when it connects a device; once the device takes it, each wheel in the multiplier's collection reports in fractions of a detent. Then the LEDs, when their report differs from the one last sent: the output report of the interface's first LED field, each LED usage set from the LEDs programs lit on its event device and, on a keyboard, Num Lock, Caps Lock and Scroll Lock from the input layer (`input_leds`), and every other field 0, or a boot keyboard's one byte with Num Lock in bit 0, Caps Lock in bit 1 and Scroll Lock in bit 2. A device just attached has shown nothing, so it is sent its LEDs at once. An LED report that fails, or has not completed in 500 ms, is logged once, by the interface's number, and none is sent to that interface again until it is attached again, since a keyboard without LEDs may refuse the request for good. After any output report that fails or times out, the control endpoint, which every interface's output reports share, is quiesced with `usb_core_endpoint_quiesce` before another report goes out or its buffer is reused: a stall or a transaction error leaves the endpoint halted, and the controller still owns the transfer of a report never answered. A device whose control endpoint will not quiesce fails. A report the endpoint refuses before it is sent is offered again at the next pass.

A boot keyboard's report is 8 bytes: modifier bits, a reserved byte and six key usages. `hid.c` keeps each device's previous report and sends the difference to the input layer as presses and releases of Linux's key codes, each the code `set1_keycode` gives for the usage's set-1 code, the extended form with the 0xE0 prefix for the right Ctrl and Alt, the GUI and Application keys, Print Screen and Pause, the arrows, the editing keys, and the keypad's Enter and slash. The table covers usages 0x04 to 0x65 and Mute, Volume Up and Volume Down, 0x7F to 0x81, and a usage without a code reaches only the event device, "MANUFACTURER PRODUCT" or "USB HIDBP Keyboard VVVV:PPPP", with its usage in the keyboard page, 0x70000 and up, as its `MSC_SCAN`. A report whose key slots hold an error usage, 0x01 to 0x03, has its modifiers read and its keys ignored, so the held keys stay down. A boot mouse's report is at least 3 bytes: five buttons and signed X and Y, Y positive toward the user as `mouse_report` takes it, and a signed wheel in a fourth byte when the report has one ([terminals](../tty/Readme.md)); the mouse is the event device "MANUFACTURER PRODUCT" or "USB HIDBP Mouse VVVV:PPPP", as Linux's usbmouse names it, and reports each wheel detent also as 120 of `REL_WHEEL_HI_RES`.

When a device goes, in whatever state, a later interface's setup among them, `hid_gone` has the input layer release every key each of its interfaces had down (`input_keyboard_detach`), takes their event devices away and frees their tables. `hid_attach` and `hid_attach_boot` take away a state they find for the interface first, so an entry reused by another device never reads its reports through the last one's tables.

### Hubs

`hub_attach` reads the hub descriptor, of type 0x2A for a SuperSpeed hub and 0x29 otherwise, and uses at most 31 ports (`USB_HUB_PORT_MAX`). A SuperSpeed hub is given its tier with `SET_HUB_DEPTH`, which it needs to route packets (USB 3.0, 10.14.2.8); a hub whose interface protocol is 2 is set to one translator per port with `SET_INTERFACE`, and driven with one translator if the request fails. The hub's slot context is written through the core's command turn. Each port is then powered with its own `SET_PORT_FEATURE(PORT_POWER)`, even on a hub whose ports switch together, since USB 2.0, 11.11.1, leaves a ganged hub's other ports off until each gets a request of its own. After the power-good time, twice the descriptor's byte in milliseconds and held between 100 and 510 ms, each port's status is read once, and the connected ports go to the core when the scan ends.

The running hub keeps a transfer outstanding on its status change endpoint. Bit 0 of the answer is the hub's own status, whose local-power and over-current changes are logged and cleared. For each port whose bit is set, the driver reads the status, acts on the change, clears each change bit, and reads the status once more: the hub clears a change latch when the clearing request arrives, so a change latched after the first read would be lost, and the hub would leave the port out of its bitmap from then on. A hub whose second read fails is closed. A connection change closes the device below, even with the port still connected, and so does a lost enable on a USB 2 hub; the core then enumerates whatever is connected. An over-current powers the port off, closes the device below, and powers the port on once after a second; the port stays off if the fault recurs. On a SuperSpeed hub a link in SS.Inactive closes the device below and gets a warm reset, after the earlier change bits are cleared so that clearing them cannot clear the warm reset's completion.

The core's reset of a hub port is `SET_PORT_FEATURE(PORT_RESET)`, a status read every 20 ms until the reset ends, and the clearing of `C_PORT_RESET`, within 500 ms. A hub port settles only once the hub's first scan has ended. One control request is in flight per hub, and a request not completed in 500 ms fails the hub, which the core closes with every device below it. A detached hub's record, a DMA pool frame like a device's, is kept until the hub's slot is disabled.

### Mass storage

Each SCSI command to a stick is a 31-byte command block wrapper, a data stage when there is data, and a 13-byte status wrapper, with one command in flight per stick. The wrapper's tag increases across every stick and every attach, so a completion left from a pulled stick cannot match the next stick's command.

`Get Max LUN` comes first, and a stall, a failure or an answer above 15 means one unit. Each unit, at most 4 (`MSC_MAX_LUNS`), gets `INQUIRY`, and a unit whose device type is other than direct access, such as a drive's CD-ROM unit, is passed over. The unit serial number page follows; then `TEST UNIT READY`, with `REQUEST SENSE` after each failure and 100 ms between tries, until the unit is ready or reports no medium, which passes it over; then `READ CAPACITY(10)`, whose answer is the last block's address, and `READ CAPACITY(16)` when that is 0xFFFFFFFF; then `MODE SENSE(6)` for the write-protect bit. A unit whose blocks are not 512 bytes is passed over. Each unit has 10 s to finish (`MSC_READY_MS`), and past that the stick is failed. The units kept are published, and a stick with none is failed.

A unit's block device has 512-byte sectors, `BLOCK_READ_ONLY` when the unit is write-protected, at most 1024 sectors, 512 KiB, per request (`MSC_REQ_SECTORS`), and a deadline period of 2500 ticks, 10 s (`MSC_DEADLINE_TICKS`). A read or write is `READ(10)` or `WRITE(10)`, or the 16-byte form on a unit of more than 2^32 - 1 sectors, and a flush is `SYNCHRONIZE CACHE(10)`. A write to a write-protected unit fails with `EROFS`. Requests wait in a queue of 16 (`MSC_QUEUE`), the block layer's limit on live requests, and are served in arrival order, so a flush follows every write before it.

A request succeeds only when the status wrapper reports success with no residue and the data stage moved every byte. After a check condition `REQUEST SENSE` is sent: UNIT ATTENTION sends the command once more, ILLEGAL REQUEST in answer to `SYNCHRONIZE CACHE` is a stick without a cache and counts as success, and any other sense fails the request with `EIO`. A stalled data stage has its endpoint cleared and the status wrapper read; a stalled status wrapper has the IN endpoint cleared and is read once more. A bad or missing wrapper, a phase error, or a failed data stage starts reset recovery in the order the class fixes: the Bulk-Only Mass Storage Reset, then the halt cleared on the IN endpoint, then on the OUT endpoint. Each clear is the core's quiesce of the endpoint followed by `CLEAR_FEATURE(ENDPOINT_HALT)` to the device.

A request's pages belong to the controller from the doorbell until the transfer is retired, and the request completes only after; a short transfer under QEMU is retired by a quiesce before the request completes or the next command starts. A transfer not completed in 10 s (`MSC_STEP_MS`) fails the stick during bring-up; later, the bulk endpoints are quiesced, IN then OUT, and reset recovery runs. When a quiesce, a clear or the reset fails or passes its deadline, the stick is failed and handed to the core (`usb_core_device_drop`), which closes the device and enumerates the port again through a port reset, as a replug would.

When a stick is pulled, its waiting requests fail with `EIO`, and so does the request in flight unless the controller may still reach its pages, in which case it fails when Disable Slot completes. The stick's record is kept until the disk layer has released it (`msc_release`) and its slot is disabled, since a mount or an open file may still point at its block device.

### Closing a device

A device that has gone is taken down on the next pass, the devices below a hub first: its class driver is told, then Disable Slot is issued on the command turn, and the record is freed when it succeeds. A Disable Slot that fails or does not complete within 5 s (`CLOSE_LIMIT_MS`) leaves the record a tombstone, never reused, since the controller may still write into the slot's rings. A device taken down during its port reset releases the command turn at once, since a port reset issues no command; one with a command in flight keeps the turn until the command completes or is aborted, and a slot that a late Enable Slot yields is disabled too.

### The latency record

Under `rach2.usblatency`, `stamp.c` records the path of the last USB keystroke and logs one line, `usb: latency: ...`, when a reader takes its byte: the times of the handler's entry, of the code reaching the input layer and of the read, in microseconds relative to the drain that took the event; whether a blocked reader was recorded and then dispatched; how many pumps ran before the dispatch; and how many bytes `getrandom` completed meanwhile. A code that arrives after the reader's dispatch and before its read, such as the key's release, does not replace the keystroke the reader was woken for. The controller gives no timestamp of its own.

### Stopping

`usb_stop` turns each controller's interrupts off, clears Run/Stop and waits up to 16 ms for the halt, since a controller left running can wake or reset the machine. The kernel keeps the controller; it does not give it back to the firmware.

## Limits

| Limit | Value | Defined as |
| --- | --- | --- |
| Controllers | 4 | `XHCI_MAX_CONTROLLERS`, `xhci.h` |
| Device records, all controllers and hubs | 16 | `USB_MAX_DEVICES`, `core.h` |
| Hubs, detached ones not yet disabled included | 8 | `HUB_MAX`, `hub.h` |
| Ports used on a hub | 31 | `USB_HUB_PORT_MAX`, `hcd.h` |
| Root ports scanned per controller | 32 | `usb_core_step`, `core.c` |
| Tiers of hubs | 5 | `USB_TREE_TIERS`, `hcd.h` |
| Device slots per controller | the controller's count, at most 255 | `XHCI_SLOTS`, `xhci.h` |
| Configuration descriptor | 3072 bytes | `USB_DESC_MAX`, `core.h` |
| HID interfaces driven on a device | 15, every one a configuration can have | `USB_HID_INTERFACES`, `core.h` |
| Sticks | 8 | `MSC_MAX_DEVICES`, `msc.h` |
| Logical units per stick | 4 | `MSC_MAX_LUNS`, `msc.h` |
| Requests waiting on a stick | 16 | `MSC_QUEUE`, `msc.c` |

The disk side's limits are in [`block/Readme.md`](../block/Readme.md).

* Only xHCI controllers are driven.
* A report descriptor longer than 3072 bytes (`USB_DESC_MAX`) is not read, where Linux reads 4096; such a keyboard or mouse runs in the boot protocol. A descriptor with more than 64 reports (`HID_MAX_REPORTS`), collections nested deeper than 32 (`HID_MAX_COLLECTIONS`) or more than 8 applications (`HID_MAX_INPUTS`) is refused or cut, where Linux has no such bound.
* The digitizer driver handles touchscreen and touchpad contact reports. Pen tablets and vendor-specific digitizer modes are unsupported. Tablets report through evdev.
* A Resolution Multiplier in a Feature report with other fields is not set, since its other values would have to be read with `GET_REPORT` first; output reports go over the control endpoint even where the device has an interrupt OUT endpoint, which Linux would use.
* A USB keyboard's event device has a `SYN_REPORT` after each key, as the PS/2 keyboard's has, where Linux has one after each report.
* Mass storage is SCSI over Bulk-Only Transport, with 512-byte blocks. A drive that offers only UAS is not driven.
* There are no isochronous transfers, so no USB audio or video.
* A controller has one interrupter and one command in flight, so its devices are enumerated one at a time.
* No device or port is suspended.
* The root file system is never on a USB disk, since the stack starts after it is mounted.
* A tombstone record and its slot are lost until the machine restarts.

## Tests

`tests/run host` runs these under AddressSanitizer and UndefinedBehaviorSanitizer; [`tests/host/Readme.md`](../../../tests/host/Readme.md) lists their rows:

* `usb_hosttest.c`: the core without a controller, given descriptors no device would send in buffers of exactly their length, the endpoint quiesce over a controller stub, a HID interface's descriptor, a keyboard's LED report and the control endpoint's recovery after an output report fails or times out, and devices of two, three and fifteen HID interfaces enumerated from their configuration to their running, a later interface falling back to the boot protocol among them, or unplugged during the second interface's setup.
* `xhci_hosttest.c`: the controller driver against a model controller reached through `struct xhci_io`, from discovery and the firmware handoff to commands, transfers, interrupts and the 32-bit address path.
* `hid_hosttest.c`: boot reports in, key events out, the names, the protocol a device runs in, the order and retries of the output reports, an interface attached over a stale state, and a keyboard whose consumer keys are its second interface.
* `hid_parse_hosttest.c`: the parser and the usage mapping, with QEMU's tablet, keyboard and mouse descriptors and made-up and malformed ones, checked against the capabilities and events Linux gives.
* `hub_hosttest.c`: the core and the hub driver over a model of a tree of hubs.
* `msc_hosttest.c`: the storage driver against a model stick that fails at any stage or is pulled.
* `usb_interrupt_hosttest.c`: interrupt setup and the fallback count across controllers.
* `usbstamp_hosttest.c`: the latency record with the scheduler.
* `usbdisk_hosttest.c`: `block/usbdisk.c`, the disk side.

`tests/run usb` runs the cases of [`tests/cases/machine.usb.json`](../../../tests/cases/machine.usb.json), each a machine of its own on a `qemu-xhci` controller, which [`usb_scenario.c`](../../../tests/cases/machine/usb_scenario.c) boots and drives: keyboards and mice at high and full speed, typing on machines without an 8042, plugging and pulling, a device with no driver, messages, lines and the fallback, the latency record, hubs behind hubs, a full device table, sticks pulled during a read, two controllers, and `rach2.hcfail`. `tests/run input` reads the USB keyboard's, mouse's and tablet's event devices with `evprobe` ([`machine.input.json`](../../../tests/cases/machine.input.json)): the tablet's numbers, bits and axes and the records of its moves, clicks and turns through QMP must be what Linux gives QEMU's `usb-tablet` and evtest prints. `tests/run usbdisk` tests sticks as disks, the cases of [`tests/cases/machine.usbdisk.json`](../../../tests/cases/machine.usbdisk.json), and `tests/run subset` requires `usb: skipped: rach2.nousb`; all three are in the core tier. `metal`, `loopdev`, `diskrate`, `krffsmount`, `installer` and `uefi` attach USB devices for their own checks. A suite runs on x86-64 with `ARCH=x86_64` before `tests/run`. Each case's manifest entry says what its boot requires.

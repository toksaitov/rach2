# Rach2 Network Stack

A from-scratch TCP/IP stack for the Rach2 kernel. It brings up, bottom to top: a network device, Ethernet, ARP, IPv4, ICMP, UDP, TCP, and a BSD-style socket layer exposed to user space through a Linux `socketcall` syscall. Two devices can carry it: QEMU's RTL8139 on the SLIRP user network, which every test boots against, and the RTL8168GU in the Lenovo G50-70 (`dev-log/24-metal/plan.md`).

## Layers

| Directory          | Responsibility                                                              |
|--------------------|-----------------------------------------------------------------------------|
| `driver/netdev.*`  | The device interface and the probe order; the layers above name no card     |
| `driver/rtl8139.*` | PCI NIC driver: RX ring, four TX descriptors, IRQ-driven receive            |
| `driver/rtl8168.*` | RTL8168GU (PCIe gigabit): C+ descriptor rings, four indirect access windows, polled |
| `ethernet/`        | Frame parse and build; dispatch by EtherType to ARP or IP                   |
| `arp/`             | IP-to-MAC resolution with an 8-entry cache                                  |
| `ip/ip.*`          | IPv4 header build/parse, checksum, routing, fragment drop, loopback ring    |
| `ip/icmp.*`        | Echo (ping): replies to requests, sends our own and sleeps for the reply    |
| `udp/`             | Datagrams, a port-to-socket table, length validation                        |
| `tcp/`             | RFC 793 state machine with RFC 6298 RTT/RTO and RFC 5681 congestion control |
| `tcp/rcvwnd.*`     | When a drained receive buffer is worth announcing (RFC 1122 4.2.3.3)        |
| `socket/`          | Socket pool, blocking recv/accept/connect, refcounted lifecycle             |
| `core/`            | `init_network`, byte-order helpers, shared configuration                    |
| `netconsole.*`     | The serial stream repeated as broadcast frames, for a machine with no serial port |

## The device interface

A driver publishes a `netdev_ops` (`driver/netdev.h`): a name, a bring-up, a transmit, an optional poll, a diagnostic and a detail line. `netdev_probe` tries each compiled-in driver in table order and binds the first that answers, so the layers above name no card: `init_network` probes, `ethernet_tx` calls `netdev_tx`, and the boot summary asks the bound driver what it is. The RTL8139 comes first in the table, which keeps every existing test's machine exactly what it was.

The two drivers differ in how packets arrive, and the interface says so rather than hiding it. The RTL8139 takes an interrupt and delivers from its handler, so its `poll` is NULL. The RTL8168GU runs with its own interrupts masked, because this kernel is PIC-only and polled everywhere else that matters, so its `poll` is where its receiving and its transmit reclaim will happen. The 100 Hz timer handler calls `netdev_poll`, which is where a polled device receives and reclaims. The RTL8168GU's transmit hands the frame to the chip and returns rather than waiting for it, so the tick is also what notices a completed descriptor and what rings the doorbell again for anything still outstanding, which is how a lost poll request costs 10 ms instead of the connection. A full ring is the one case a transmit still waits on, for about a millisecond, because dropping the moment a burst outruns the chip would lose frames the next tick would have made room for.

## The RTL8168GU

The chip in the Lenovo, and the one device here that cannot be tested before it is met: QEMU does not emulate it. So `driver/rtl8168.c` is a port of one pinned reference rather than a reading of a datasheet (Linux v6.16, commit `038d61fd642278bab63ee8ef722c50d10ab01e8f`, `r8169_main.c` and `r8169_phy_config.c`, for the version that file calls `RTL_GIGA_MAC_VER_42`), and each sequence names the reference function it came from.

What that buys: the chip is identified by the revision it reports in `TxConfig` rather than by its PCI device id, which covers the whole 8168 family; the out-of-band state a previous operating system can leave is cleared through the two link-list handshakes the reference uses; the twelve-step configuration runs in the reference's order, including the packet-filter bit that is cleared and then set again and the two separate read-modify-writes of the same ERI word; and every one of the four indirect windows (ERI, MAC-OCP, PHY-OCP, EPHY) is a bounded protocol whose timeout fails the bring-up rather than feeding a garbage value back into the chip, which is what the reference's own error path does.

Two departures from the reference are deliberate and are in the file's header comment: link state is read from `PHYstatus`, which the reference declares and never reads because phylib reaches the PHY over MDIO instead; and the PHY is powered up here, because the reference suspends it at probe and lets phylib wake it, and nothing here would.

`tests/host/rtl8168_hosttest.c` drives the whole driver against a software model of the chip: completion flags that move only when a command completes, an out-of-band bit that must be cleared, a link list that must be handshaked twice, descriptors whose ownership moves, and a recorded write log the test asserts the reference's order against. It cannot prove PCIe ordering, that DMA reaches the rings, the PHY's analog behavior, or whether this board needs the firmware patch the port omits; those wait for the laptop.

## Netconsole

The Lenovo has no serial port, so on it the kernel log exists only on the screen until SSH is up, and a screen cannot be scrolled back or diffed. `netconsole.c` repeats the same byte stream into broadcast Ethernet frames of EtherType `0x88b5` (IEEE Std 802 local experimental 1), which any host on the segment can capture into a file.

It sits below IP deliberately: there is no address to configure, no ARP to answer and no peer that must be reachable, so it works on the first boot on an unknown network and keeps working when the address configuration is the thing that is wrong. The cost is that the frames are broadcast and unacknowledged. This is a diagnostic, not a log transport.

The frame payload after the Ethernet header is a 16-byte header, all fields big-endian: the magic `RCH2`, a boot id (one random value per boot, so a capture spanning a reboot can be split), a sequence number from zero (so a gap is visible), the payload length, and a checksum over header and payload with the field zeroed. A receiver sums the whole payload including that field and checks for zero, the same convention as the IP header. At most 512 log bytes ride in one frame.

Three things make it safe to call from anywhere, including interrupt handlers and the panic path. It allocates nothing: one fixed ring and one fixed frame buffer. It brackets the ring update and each frame with `net_lock`/`net_unlock`, because a syscall prints with interrupts enabled while the timer and the NIC print from their handlers, and both the ring and the Ethernet layer's shared assembly buffer would otherwise be entered twice at once. And it refuses to re-enter itself: a driver reporting a transmit error through the serial port arrives back in the same call, where disabling interrupts protects nothing, so while a frame is being sent a character only joins the ring, and a drain stops at the ring head it saw when it started. Without that second half, a chip that failed every transmit would sit inside one `printf` forever, transmitting the report of its own failure to transmit; `tests/host/netconsole_hosttest.c` provokes exactly that.

`serial.c` knows nothing about any of this. It offers a tap (`serial_set_tap`), called before it checks whether a COM1 exists, and `kernel.c` installs `netconsole_putc` there when the command line carries `rach2.netconsole`. The tap is installed early, right after the command line is captured, so the memory layout, the module ranges and every device probe are already in the buffer when the network device comes up; `netconsole_enable` then sends what accumulated. Broadcasting a kernel log is a decision for whoever runs the network, so nothing happens without the boot flag.

## Configuration

The stack knows one address, one mask and at most one gateway, and the boot command line chooses them (`netconf.c`):

```
rach2.ip=192.168.1.50/24 rach2.gateway=192.168.1.1
```

With neither option the machine keeps QEMU's SLIRP tuple, `10.0.2.15/24` via `10.0.2.2`, which is what every test expects and what the constants in `net.h` still hold. With `rach2.ip=` given and `rach2.gateway=` absent there is no default gateway at all, rather than the SLIRP one: `10.0.2.2` beside a real LAN address is a router that does not exist, and a stack that kept it would send every off-subnet packet into nothing. Instead `ip_tx` drops such a datagram and says so, which is a failure someone can diagnose. The MAC address is read from the NIC at init.

The parsing refuses more than it accepts, because the only thing worse than refusing to configure is configuring something other than what was written. Out by one digit and the machine comes up on a network nobody asked for, which on a board across the room is indistinguishable from a machine that did not come up. So a leading zero is refused rather than read as octal or as decimal, a quartet over 255 is refused rather than truncated, trailing text is refused rather than ignored, and the subnet's own network and broadcast addresses, loopback, multicast and the all-zero and all-ones addresses are refused as host addresses. A gateway must be a host on the subnet just given. Either option repeated is refused rather than resolved by a first-wins rule nobody would remember. Every refusal leaves the SLIRP tuple in force and prints what was wrong on the boot line.

`tests/host/netconf_hosttest.c` holds the parser to all of that, and `make test-addressed` runs the whole probe suite with the address named on the boot line instead of compiled in: the address given is the one SLIRP already provides, so all 61 probes must pass exactly as they do without it, which is what proves the configuration reaches ARP, IP, TCP, the sockets and the boot line.

## Configuring the interface from a program

The boot line is no longer the only way this machine learns where it is. A DHCP client learns the address after the machine is running, so `netif.c` carries Linux's interface ioctls on a socket descriptor: `SIOCGIFNAME`, `SIOCGIFINDEX`, `SIOCGIFHWADDR`, `SIOCGIFMTU`, and the get and set pairs for the address, the netmask, the broadcast address and the flags, plus `SIOCADDRT` and `SIOCDELRT` for the default route. The interface is `eth0` and there is one of it; a request naming another is `ENODEV` rather than quietly applied to the only one there is. `SIOCGIFNAME` runs the other way, an index in and a name out. The descriptor these are asked through can be any socket, and a DHCP client's is a raw one: busybox opens `AF_INET/SOCK_RAW/IPPROTO_RAW` and does nothing with it but ask, so that descriptor exists here and carries ioctls alone, refusing to send or receive because this stack has no raw IP path to offer. Reading is anyone's and setting is root's, because a program that could set this machine's address could take another machine's and send from it.

The address and the netmask are set by separate ioctls, one each, so there is a moment with an address and no mask: an address given with no mask takes the classful one its first byte implies until the real one arrives, which is what Linux does and what makes a machine booted with `rach2.ip=none` configurable at all. An address of zero unconfigures and takes the mask with it, since half a configuration is not one.

Changing the address is not just a number, and `netconf_set_address` is where the rest of it happens. The whole transition is held under `net_lock`, because between publishing the address and telling the connections an interrupt would otherwise find a machine at the new address with connections still claiming the old one. Every mapping in the ARP cache was learned by a machine at the old address, so the cache is emptied. Every TCP connection recorded the address it was opened from, so those are aborted with `ENETRESET` on their sockets rather than left to send from an address this machine no longer has. A read or a write of a connection that ended returns that reason rather than a bare failure, which the C library reads as `EPERM`: a program woken because this machine's address changed under it should not be told it lacked permission. The first reader of the reason takes it, as `SO_ERROR` does on Linux. A listener is not a connection: it answers whatever address this machine has, so it follows the change instead of dying with it, and a server started before a lease arrived is still accepting after one. A gateway that is no longer a host on the new subnet is dropped. An address of zero means unconfigured, which is what a client writes when a lease ends, and the same rules that refuse a network address, a broadcast address, loopback or a multicast address on the boot line refuse them here.

The broadcast address is the subnet's and not a choice, so `SIOCSIFBRDADDR` accepts the one this machine already derives and refuses any other, rather than storing a second answer to the same question. `ip_rx` accepts a datagram addressed to this machine, to 255.255.255.255, or to that subnet broadcast: the two broadcasts are how a DHCP server answers a machine that has no address yet, and how a renewal's refusal arrives. A broadcast reaches UDP and nothing else. Answering a broadcast echo request would make this machine one of the many that reply to one packet, at whatever address the sender claimed, and a broadcast TCP segment is not a connection anyone opened.

There is one route this stack can hold, the default gateway, and everything else it reaches by being on its subnet. `SIOCADDRT` with a destination of 0.0.0.0/0 and a gateway sets it; the same route with no gateway is refused without touching anything, so `route add default dev eth0` cannot quietly remove the gateway a machine across the room is reached through. `SIOCDELRT` clears it, and reports `ESRCH` when there is nothing to clear, which is what ends the loop a DHCP client's script removes old routes in. Adding the route to the subnet this machine is already on does nothing, because it is already true; removing it is `EOPNOTSUPP`, since it cannot be removed while the address that implies it is in force. A route names a device, and one this machine does not have is `ENODEV`.

`SIOCSIFFLAGS` can take the interface down, and down means down in both directions: `ethernet_tx` drops IP and ARP, and `ethernet_rx` drops everything it is handed. A machine whose sockets saw traffic it could not answer would be worse than one that is quiet. Netconsole's transmit is not gated, deliberately: it is how a machine with no console is read, and a machine whose network was just misconfigured is exactly when its log is worth having.

The boot line gained a third answer beside an address and no option at all. `rach2.ip=none` means come up with the device probed and IPv4 unconfigured, because userland will configure it. Without it, a machine with no option keeps the SLIRP tuple, which is what every existing test boots into and why the default did not change.

## Loopback

The stack knows exactly one local address, and `127/8` is an alias for it: `connect`, `sendto`, and the `ping` sub-call canonicalize a `127/8` destination to `10.0.2.15` at the socket boundary, before any connection state exists, so no lower layer ever carries a second local address and `getsockname`/`getpeername` report the canonical one. A datagram addressed to ourselves then never touches ARP or the wire: `ip_tx` copies it onto a small loopback ring, and the 100 Hz timer delivers the queued datagrams to `ip_rx` (`ip_loop_drain`), under the same interrupts-off discipline as NIC delivery; delivering inline would reenter TCP under the sender's own call frame. A full ring drops the datagram, exactly as a full NIC ring would. There is no loopback interface proper (no routes, no `lo` device): the alias is the whole feature, and `loopprobe` proves it end to end. Because a genuine loopback datagram carries our own address as its source, `ip_rx` takes a `from_loopback` flag and drops a wire packet whose source is our own address or `127/8`: such a martian is a spoof no real peer sends, and without the check it could steer a reply onto the loopback ring or out the wire carrying a loopback source.

## The receive window

A TCP receiver has two things to tell its peer about the room left in its buffer, and until recently this stack only told it one. The inbound paths recompute `rcv_wnd` whenever a segment arrives, so a window that shrank was reported at once. A window that grew was reported to nobody: the reader advances `recv_head` in syscall context, and that path sent nothing at all. A peer that had filled the buffer therefore waited for its own persist timer before probing again, and that timer, not the network, set the rate. Bulk receive ran at about a kilobyte a second while transmit ran two hundred times faster over the same connection.

`socket_tcp_recv` and `socket_tcp_try_recv` now call `tcp_window_update` after advancing `recv_head`. It takes `net_lock` itself, the same as `tcp_send`, sends at most one bare ACK, and only from ESTABLISHED, since the closing states have no reader to make room. Whether to send at all is the whole of `tcp/rcvwnd.c`, a pure function with no state and no transmit: stay quiet until the window has grown by one maximum segment size or half the buffer, whichever is smaller, then announce the whole new window at once. Announcing sooner would spend a segment per byte read and draw segments just as small in reply, which is the silly-window syndrome RFC 1122 4.2.3.3 exists to prevent.

Measured host to guest over SSH into `/dev/null`, on the same image and the same QEMU invocation, with the call removed and restored:

| Bytes   | Without the update | With it |
|---------|--------------------|---------|
| 4096    |                    | 0.361 s |
| 65536   | 60.179 s           | 0.291 s |
| 1048576 |                    | 0.408 s |

That is 1089 B/s against 225 KB/s at 64 KiB, and 2.57 MB/s at a megabyte.

One limit belongs here, because the rule above does not cover it. `rcvwnd_update` governs the update the reader triggers, not every window this stack advertises: the inbound paths still recompute `rcv_wnd` from the free space whenever they owe an ACK, so a segment arriving after a small read can advertise a window below the bar. That is older than the update path and the update path largely hides it, since a reader draining normally announces a full-sized window before a peer has cause to probe. Fixing it properly means holding the advertised right edge fixed as data is accepted, which changes the receive state machine and wants a stateful test; it is recorded in `dev-log/25-sealed/Readme.md` rather than done here.

## Socket interface

The `ping` sub-call waits by sleeping, not by spinning, and that is a rule about who else gets to run: the timer skips `schedule()` while a process is inside a syscall, so a poll with `sti; hlt` from there gives every other process no CPU at all for as long as the wait lasts, which on a machine several people can log into is a freeze any of them can fire at a dead address. The waiter blocks on a wait queue that `icmp_rx` wakes, and the wait is bounded twice over: `wakeup_tick` is armed so the timer makes the process runnable, and the same deadline is in the wait predicate, because a woken sleeper whose condition is still false re-enqueues with its timer already disarmed and would then never wake. The deadline never lands on 0, which is `wakeup_tick`'s own "not sleeping" sentinel: one tick value in every wrap of the counter would otherwise arm nothing and hang the caller, and `sys_nanosleep` steps around the same tick. That case is argued rather than probed, since the counter wraps about every 497 days at 100 Hz and no test here can set it. The kernel debug shell keeps the spin and correctly so: it runs with the scheduler stopped and no process to block. There is one in-flight echo for the whole machine, claimed under `net_lock` and released on every exit path, which is the raw-socket non-goal made visible to users: with a real `SOCK_RAW` each caller would own a socket, and here a second caller is refused with `-EBUSY` rather than queued, since a queue needs a fairness rule to give a shell command a wait it cannot see. So the sub-call returns ticks, `-ETIMEDOUT`, `-EBUSY` or `-EINTR`, and a ping at a dead address holds the slot, and refuses everyone else, for about four seconds.

A stream socket that bound a port keeps it: `connect` uses the bound port when there is one and a fresh ephemeral only when there is not, so a client can pin its source port the way binding one is meant to. What is refused is the exact triple the connection table keys on, a local port already paired with this same peer address and port, since two such blocks would have one connection's segments delivered to the other; a bound port shared with a listener, or with a connection to a different peer, stays legal. Listener exclusivity is enforced in `listen` rather than in `bind`, because the two are separate syscalls with arbitrary user code between them: binding both sockets and only then listening on each walks past any check that lives in `bind` alone, and leaves two LISTEN blocks on one port for the exact-match and listener lookups to disagree about. The check `bind` still makes is a courtesy, so a server hears about the collision where it expects to. The scope is live listeners and not every block in the table, since an accepted connection and a TIME_WAIT remnant hold a port against nobody and `setsockopt` is a no-op here, so counting them would make restarting a server after a session fail where it succeeds today. `listen` and `connect` report `-EADDRINUSE`, `-EDESTADDRREQ` and `-ENOBUFS` rather than a bare -1, which musl's return convention decodes as `EPERM`, and `connect` passes them up unchanged: the refusal a closed port earns still comes from the handshake.

Simultaneous open is implemented, which loopback makes reachable: two sockets each bound to the port the other dials will each meet a SYN that acknowledges nothing. The answer is a SYN-ACK emitted at `iss`, not at `snd_nxt`, and the rewind is the whole of it. The first SYN left `snd_nxt` at `iss + 1` while the peer's answering SYN-ACK acknowledges `iss + 1`, so a SYN-ACK sent from `iss + 1` is acknowledged by nothing, the retransmit sequence names something the peer will never confirm, and the connection wedges. Before this, a bare SYN in SYN_SENT was dropped and both ends hung until their retransmissions gave up. An active open reaches SYN_RCVD through that arm, so the block records which kind of open made it: a passive child is handed to a listener's `accept` queue and freed on a reset, since nothing else holds it, while an active opener is woken as its own completed `connect` and never unref'd, since a descriptor holds it already. Only the first half of that is gated by a probe. The loopback ring is drained by the timer while the caller is still inside its own `connect`, so the crossing usually finishes before the wait predicate is first evaluated and the wake is never needed here; over a real interface it is, and that is where the distinction earns its keep.

Sockets are first-class file descriptors (`FD_TYPE_SOCKET`). `read`, `write`, `close`, `dup2`, `fork`, and process exit all handle them through the FD layer, with a reference count so a socket shared by `fork`/`dup2` is torn down only when its last descriptor closes. The Linux i386 `socketcall` (syscall 102) multiplexes socket, bind, connect, listen, accept, send, recv, sendto, recvfrom, plus a `ping` sub-call; every user pointer argument is range-checked before use. A datagram socket that sends before an explicit `bind` is assigned an ephemeral source port automatically, so replies can return and `close` releases the port. A datagram read may return 0, and that is a datagram of no bytes rather than end of input: UDP carries an empty payload, so the receive slot's occupancy is a flag and not its length. A slot that read its own emptiness as "nothing here" built such a datagram, sent it, accepted it, delivered it to the right socket and dropped it at the last step, leaving a blocked `recvfrom` blocked. The same 0 reaches `read` on a socket descriptor, where a stream would have meant end of input; nothing in the tree confuses the two, since the resolver requires a header's worth of bytes and `nc` reads only streams. A `readv` of a datagram socket takes one message and no more: the receive slot is waited for, copied out across the caller's buffers in pieces, and consumed once at the end (`socket_dgram_wait`, `socket_dgram_peek`, `socket_dgram_consume`, which are also the three steps `socket_recv` is made of), so a datagram wider than one buffer is not truncated at the first and a second one is never swallowed by the same call.

## The packet socket

`ip_rx` drops every datagram not addressed to this machine, and every reply a DHCP client waits for is one of those: an offer arrives before the machine owns the address it is being offered. So a client opens `socket(AF_PACKET, SOCK_DGRAM, htons(ETH_P_IP))` and reads its replies from above the Ethernet layer instead. `ethernet_rx` offers every IPv4 frame's payload to the bound packet sockets on the way past, before `ip_rx` judges the destination.

`SOCK_DGRAM` on `AF_PACKET` means the link header is not the caller's business in either direction. A receive delivers the IP packet, the same bytes `ip_rx` is given. A send takes an IP packet the caller built and a destination MAC in the `sockaddr_ll`, and this layer prepends the header and nothing else. Only IPv4 is offered: a socket asking for another EtherType is refused rather than bound to a filter that is not implemented, and only `SOCK_DGRAM`, since `SOCK_RAW` would mean handing the caller the link header too. Opening one needs effective uid 0, because it reads every IPv4 frame the machine receives, other people's connections included, and sends frames the IP layer never saw.

`bind` takes a `sockaddr_ll` and is what puts the socket in the delivery table; an unbound one receives nothing. The machine has one interface, `eth0`, index 1 (`NETDEV_IFNAME` and `NETDEV_IFINDEX`), and index 0 means any, so those two bind and anything else is `ENODEV`. Two sockets can be bound at once.

Each bound socket has a queue of eight datagrams rather than the one slot the rest of the datagram path has, and the difference is the point of the socket. Everything the machine receives arrives here, not only what is addressed to it, so on a real network the reply a client waits for is followed by other people's traffic inside the same batch of frames one interrupt drains; a single slot would hand the client whichever frame came last. A full queue drops the newest, counts it, and says so once.

`recvmsg` (socketcall 17) exists for this client: it reads through `recvmsg` rather than `read` so that it can look for `PACKET_AUXDATA` in the control data and learn whether the kernel checked the UDP checksum. There is no such offload here and no ancillary data at all, so `setsockopt(SOL_PACKET, PACKET_AUXDATA)` is refused with `ENOPROTOOPT`, which is the answer that is true, and the client verifies the checksum itself. `recvmsg` reports a control length of zero for the same reason. It scatters one datagram across the caller's buffers through the same three steps `readv` uses, and reports the sender through `msg_name` for an AF_INET socket; a packet socket's sender is a link address this stack does not keep, so its `msg_namelen` comes back zero rather than filled with something invented.

## Name resolution

The kernel resolves no names; it provides only the transport. Host names are turned into addresses in userspace by a small stub resolver (`utils/resolv.c`, shared through `utils/netdb.h`) that `ping` and `nc` call: it tries a numeric literal, then the hosts file, then a DNS `A` query over UDP to the nameserver in the resolver config (SLIRP's forwarder `10.0.2.3`). Each file is looked for under `/etc` first and in the flat KRFFS root second, since os-real stages a real `/etc` and the test image stages neither directory. This mirrors a libc stub resolver and leaves room to add `getaddrinfo` over the same files.

## Concurrency

The shared TX assembly buffers, the TCB and socket pools, and the ARP cache are unlocked, so every access to them must run with interrupts disabled. IRQ-context senders (the NIC RX handler and `tcp_tick`) already do, since IRQ handlers clear IF and do not nest. Syscalls, however, run with interrupts enabled (so the timer and audio keep working during long syscalls), so a syscall-context sender can be re-entered by an IRQ mid-build. Syscall-context code therefore brackets each access to this shared state with `net_lock()`/`net_unlock()` (save IF and disable interrupts), a harmless no-op when called from an IRQ. The full rule is documented in `net.h`; the driver's TX handoff guards itself as well. TCP timers run from the 100 Hz timer handler (`tcp_tick`).

## Testing

Userspace programs exercise the stack:

* The freestanding probes `pingtest`, `udptest`, `tcptest`, `sockettest`, and `dnstest` are staged into `test.krffs`. `make test` boots it headless and runs them, or boot it by hand and `exec` each from the kernel debug shell. `loopprobe` (in the `make test` pass) needs no host at all: it exercises the UDP and TCP paths against the machine itself over `127.0.0.1`.
* `make test-addressed` runs the whole suite with `rach2.ip=` and `rach2.gateway=` naming the network SLIRP already provides, so every probe must pass exactly as it does without them.
* `make netif-test` runs `netifprobe` twice, once on a machine that booted with the SLIRP address and once on one booted with `rach2.ip=none`. The first boot takes the interface down and proves it both ways: the gateway stops answering, and a datagram the harness sends through a host forward does not arrive until the interface is up again. That is what the harness's `udp=` step is for, and it is the only way a test here can put a frame on the guest's wire that the guest did not ask for. The second half configures the machine from nothing in the order `ifconfig` does it, an address then a mask then a route, and pings the gateway. The first reads everything the interface reports, checks the refusals (an interface that does not exist, an ordinary user setting an address, a gateway off the subnet, a route this stack cannot hold), and then changes the address with a TCP connection to this machine itself open across the change: that connection must come back `ENETRESET` rather than continue from an address the machine no longer has. It also requires the listener to accept a connection to the new address, which is what proves a server survives a lease. Then it puts the address, the netmask and the gateway back and pings the gateway.
* `make packet-test` runs `packetprobe`, which opens a packet socket, checks what it refuses (a stream socket, an EtherType other than IPv4, `PACKET_AUXDATA`, a bind to an interface that does not exist, a destination that is not a MAC address, an ordinary user), and then does a DHCP exchange for real: it builds a discover, sends it to the broadcast MAC, and waits for SLIRP's offer. That proves both halves at once, since the frame must have left well formed or nothing would answer it, and the answer is addressed to 255.255.255.255, which `ip_rx` drops. It also binds four sockets in turn through two table slots, which is what proves closing releases one. Its own target rather than a probe in the suite, for the reason `ping-test` is: it needs the network to answer.
* `make netconsole-test` boots with `rach2.netconsole`, captures every frame the guest sends through QEMU's `filter-dump`, and checks the capture with `tools/netconsole_check.py`: one boot id, sequence numbers in order with no gaps, lengths that match, checksums that sum to zero, and a line printed before the device existed, which is what proves the buffer was carried rather than dropped.
* The hand-written utilities `ping`, `nc`, and `httpd` are staged into `os-simple.krffs`, at `/bin` with everything else. Run them from the ISH shell after logging in. (os-real carries busybox, whose own `nc` applet exercises the same stack, and our `ping`, since busybox's wants a raw socket this kernel does not offer.)

The UDP and TCP tests expect a host echo server at `10.0.2.2:7777`. Boot the image that carries the program you want with a NIC, and (for an inbound server like `httpd`) a host forward. The probes need `test.krffs`, the utilities `os-simple.krffs`:

```sh
qemu-system-i386 -cpu max -kernel ../build/rach2/kernel -initrd ../build/images/test.krffs -serial stdio \
    -netdev user,id=net0,hostfwd=tcp::8080-:80 -device rtl8139,netdev=net0
```

The kernel debug shell also provides `netping` (ping the gateway) and `netbad` (ping an unreachable host to show the timeout).

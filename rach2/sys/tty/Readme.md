# Terminals

`sys/tty/` is the kernel's terminal layer: the N_TTY line discipline, which edits, echoes and recognizes signal characters in what is typed; the console terminal, which the keyboard and COM1 feed and the screen and COM1 show; and the pseudo-terminal pairs a network login gives a remote user. This document also follows a keystroke, a mouse movement and a serial byte from the hardware to a reader, through `sys/input.c`, `sys/kbd.c`, `sys/mouse.c` and `sys/arch/x86/serial.c`. The screen the console draws on is described in [the display Readme](../display/Readme.md).

## Interfaces

Programs see the console, `/dev/tty`, `/dev/ptmx` and `/dev/pts/N` as [console(4)](../../../man/man4/console.4) describes them, with the terminal requests of [ioctl(2)](../../../man/man2/ioctl.2) and the reads of [read(2)](../../../man/man2/read.2). The mouse is the path `/mouse` ([open(2)](../../../man/man2/open.2)), and the counters of the console's receive path are `/proc/console` ([proc(5)](../../../man/man5/proc.5)).

Inside the kernel, `tty.h` is the terminal. `tty_input_char` gives a terminal one input byte from any source, with interrupts off or from an interrupt handler; `tty_read`, `tty_write`, `tty_poll`, `tty_inq`, `tty_set_termios`, `tty_flush_input` and `tty_hangup` serve the descriptors; `tty_set_session` and `tty_make_sole_ctty` (in `pty.c`) set a terminal's session and foreground group. `input.h` takes a keyboard's keys (`input_key_event`, `input_set1_event`) or a mouse report (`input_mouse`) from any driver. The debug shell in `rach2/kernel.c` defines the three functions `input.c` calls: `shell_reads_input`, `shell_input_char` and `shell_interrupt`. `input_set_leds` records the LEDs every keyboard is to show and reports them on the keyboards' event devices, and each keyboard's driver sends them, the PS/2 keyboard's from the tick and taking its replies through `input_ps2_reply`, a USB keyboard's from the USB stack's step; the console's KDSETLED and KDSKBLED call it. `kd.h` is the console's keyboard as Linux's console keeps it: `kd_ioctl`, which the console's requests reach first and which answers Linux's KD* requests; `kd_key_event`, which takes every key as Linux's key code; `kd_raw_code`, which takes the raw view's set-1 bytes; `kd_translates`, whether the keyboard's mode translates keys; and `kd_state_save` and `kd_state_restore`, which keep its state and the console's termios for an owner of the screen. `kd_key_event` translates through `keymap.h`, the translator of keys through keymaps in Linux's encoding, which `term` and the host tests compile too, under `kio_key_modes` in `kio.h`, the console's cursor and keypad modes, which DECCKM and DECKPAM set.

## Design

### The line discipline

`n_tty.c` is pure logic over a `struct n_tty` and makes no kernel calls, so the kernel and a host test compile the same file. Echo and output leave through a sink function the caller supplies: the console's sink writes the screen and COM1, and a pseudo-terminal slave's writes its master's ring.

The state is the termios (`struct ktermios`, Linux's 36-byte kernel layout with 19 control characters, the same on both architectures), the line under edit (`N_TTY_LINE_MAX`, 256 bytes), and the read queue, a ring of `N_TTY_READ_MAX` (4096) bytes beside an array that marks the last byte of each committed line.

In canonical mode a byte edits the line. ERASE, WERASE and KILL remove characters: under IUTF8, which a new terminal has since Rach2's text is UTF-8, a whole UTF-8 character, and otherwise, or for bytes that end in no whole sequence, one byte. With ECHOE each removed character is rubbed out on the screen as `\b \b` once for each cell its echo took: the width `k_wcwidth` gives a UTF-8 character, which is none for a combining mark and two for a CJK character or an emoji, two for a control character echoed as `^X` under ECHOCTL, and one for any other byte. An ordinary byte joins the line while the line has room for it and a terminator, so a line has at most 255 bytes before its newline; a byte past that is dropped and counted. A newline or VEOL commits the line with its terminator. VEOF commits a nonempty line without one, and on an empty line records end of file at the queue's present position. A canonical read returns at most one line, stopping at a newline or at a marked byte, so a line committed by VEOF keeps its boundary, and a later change of VEOL leaves the queued boundaries as they were. A read that reaches the end-of-file position returns 0, once.

In raw mode each byte is readable at once, and a read waits as POSIX's VMIN and VTIME say, VTIME in tenths of a second: with both 0 it returns at once with what is there; with VMIN above 0 and VTIME 0 it waits for VMIN bytes; with VMIN 0 and VTIME above 0 it returns with the first byte, or with none once VTIME has passed since the read began; with both above 0 it waits for a first byte with no limit, and then for VMIN bytes or for VTIME to pass after the last byte, and returns what came. A read for fewer bytes than VMIN needs only as many. poll(2) and the wakes it counts see none of VTIME: the terminal is readable to poll with VMIN bytes, or at once when VMIN is 0 (`n_tty_readable`), while a read tests `n_tty_read_ready`. When a program turns ICANON off, a partial line joins the queue behind the lines committed before it, so it is neither lost nor reordered; if the queue has no room for it, it stays in the line buffer and a raw read takes it after the queue.

With ISIG set, VINTR, VQUIT and VSUSP are echoed, discard all unread input, as Linux does without NOFLSH, and are returned to the caller, which posts SIGINT, SIGQUIT or SIGTSTP to the foreground process group. A control character of 0 is disabled. The input flags ISTRIP, IGNCR, ICRNL and INLCR and the output flags OPOST, ONLCR and OCRNL are the ones implemented.

`n_tty_has_room` is true while the discipline can take a whole line more: the queue and the line together use no more than 4096 less 256 bytes. The producers that can wait, the serial pumps and a master's write, feed the discipline only while it is true, so a burst waits upstream and no byte of it is dropped.

### The terminal object

`tty.c` puts the discipline behind a wait queue. `struct tty` has the discipline, `input_wq` for readers and pollers, `space_wq` for a producer waiting for room, the window size, the sink, an optional `pump` that drains a polled input source, and the session and foreground group (`sid` and `fg_pgid`, 0 for none).

`tty_input_char` runs one byte through the discipline. It wakes `space_wq` with `WQ_ROOM` when the byte took bytes out of the discipline (an erase, or a signal character's flush), posts a recognized signal to every live user process of the foreground group, and wakes `input_wq` with `WQ_DATA` when a read would no longer block.

`tty_read` waits on `input_wq` with `tty_wait_cond` as the predicate, which runs the pump before it tests the discipline; the wait calls it with interrupts off, so no interrupt comes between a drain and the test after it. The same wait serves the console and a pseudo-terminal slave. A read with a VTIME timer arms its deadline in the process's `wakeup_tick`, which the tick acts on, before each wait and clears it after: once, from the read's start, with VMIN 0, and with VMIN above 0 again whenever the queue's count changes, for which the predicate ends the wait. `tty_input_char` wakes the readers with no kind, so poll counts nothing, for a raw byte that leaves the terminal unreadable to poll, which such a read must see. `tty_hangup` sets `hungup`, and a read that finds nothing after it returns 0, blocking or not. `tty_poll` and `tty_inq`, behind poll(2) and FIONREAD, also run the pump with interrupts off, and so does the path that records the USB latency stamps. After a wake the test and the copy run in one interrupts-off step, and a reader whose line another reader took waits again, since a read of the empty queue would return 0, end of file. One read copies at most `N_TTY_READ_CHUNK`, 1024 bytes.

`tty_write` passes each byte through output processing to the sink. On the console it runs between `console_write_begin` and `console_write_end`, so a kernel log record raised during the write waits for its end, and it then gives the screen's answers to the queries in the output (`k_take_answer` in `sys/kio.c`) to the console's input, where the program reads them as typed bytes.

`tty_hangup` records end of file after the queued input and wakes every reader. A canonical read consumes that mark once, so an endpoint that hangs up keeps its own state for the reads after it, as the pseudo-terminal slave does with `master_open`.

`tty_set_session` writes `sid` and `fg_pgid` with interrupts off, because the console's interrupt-side drain reads both. `tty_make_sole_ctty` makes a terminal the only controlling terminal of a session, dropping the console and every slave the session had, in one interrupts-off step. A session leader claims the console, when no session owns it, by reading it, and an unowned slave by reading it or by opening it without O_NOCTTY while its session has no controlling terminal; TIOCSCTTY claims either. When a session leader exits, `exit_release_session` in `sys/syscall_proc.c` releases the console and the slaves its session controls. Background reads and writes are as console(4) says.

### The console terminal

`tty_console_init` sets up `console_tty` at boot. Its sink, `console_sink`, writes each byte to the screen through `k_putc` and to COM1 through `serial_out`; its pump, `console_pump`, drains COM1's receive ring; its window size is the screen's cells (`k_console_size`). The keyboard and COM1 feed it.

### Keystrokes

Two drivers produce keystrokes, and both give `sys/input.c` Linux's `KEY_*` codes, one `struct input_keyboard` for each keyboard. The PS/2 keyboard's handler (`sys/arch/x86/ps2kbd.c`, IRQ 1, vector 33) reads the port when the status register says a byte is waiting, offers it to a command waiting for the keyboard's reply (`input_ps2_reply`), and gives any other to `input_set1_event`, which keeps the keyboard's E0 or E1 prefix and passes the key to `input_key_event` with that code as its `MSC_SCAN`, Pause's E1 1D 45 as the extended 0x45. A USB boot keyboard's reports become key events in `sys/usb/hid.c`, as [the USB Readme](../usb/Readme.md) describes, with the usage as `MSC_SCAN`. Both name a key by `set1_keycode` in `sys/kbd.c`, which gives Linux's code for a set-1 code with its release bit clear and 0x80 set after an E0 prefix: Linux numbered its keys after the plain codes 0x01 to 0x53, and the rest are two tables, the extended keys and the plain codes past the keypad. Every keyboard's interrupt and the tick run on the boot processor with interrupts off, so the events reach their consumers one at a time and in order.

`input_key_event` keeps the keys each keyboard holds. A press of a key that keyboard holds already, a PS/2 keyboard's own repeat, and a release of one it does not hold are dropped. The modifiers are derived from the held keys, each side apart and across every keyboard (`input_modifiers`): Shift stays held while either Shift key is down on any keyboard. The keyboards repeat in software, in one place (`input_tick`, from the tick): the last key pressed that is not a modifier or a lock repeats 250 ms after its press and then every 33 ms, Linux's times, which `input_set_repeat` changes; each repeat is due a period after the last was due, so the 1 ms tick keeps 33 ms on average, and a tick that comes late sends at most four. The repeat stops at the key's release, at its keyboard's detach and at `input_cancel_repeat`. Each accepted event, press, repeat or release, ends a suspend to idle (`suspend_wake`) and puts off the blanking, then goes to the keyboard's event device, to the console's keyboard (`kd_key_event` in `sys/kd.c`), below, and as its set-1 bytes, the raw view `input_raw_bytes` gives, to `kd_raw_code`, which uses them in K_RAW alone. A keyboard that goes, `hid_gone` for USB, releases every key it holds through the same path (`input_keyboard_detach`).

Each keyboard is also an event device of its own, `/dev/input/eventN` ([input(4)](../../../man/man4/input.4)), registered by `input_keyboard_attach`: the PS/2 keyboard as "AT Translated Set 2 keyboard" by `kbd_init`, and each USB keyboard as "USB keyboard N" when `hid_attach` sees it configured. Its packets are `MSC_SCAN`, the key and `SYN_REPORT` for a press or a release, and the key with value 2 and `SYN_REPORT` for a repeat; a change of the repeat's times is `EV_REP`, and of the LEDs `EV_LED`. `sys/evdev.c` keeps each device's keys down and gives each open a queue of 64 records, which a reader that falls behind loses all but a `SYN_DROPPED` and the newest record of, as Linux's evdev does. `evdev_read` waits until a whole packet is queued and then returns as many whole records as the buffer holds, so a small buffer splits a packet across reads. `evdev_report` takes the evdev lock with interrupts off and never sleeps, so the keyboards call it from their interrupts.

`kd_key_event` translates each event in K_UNICODE, the mode at boot, and K_XLATE. `keymap_key` reads the key's entry in the console's keymap under the modifiers and locks it keeps in `kd_kb`, and turns it into text, an action or nothing: a modifier or a lock changes the state and sends nothing, a dead key waits for the next key to compose with it through the accent table, and a release sends nothing, but for Alt's release after keypad digits, which sends the character they number. `keymap_encode` writes the bytes of the result as xterm sends them, under the console's cursor and keypad modes: a character as UTF-8, Ctrl with a letter as its control byte, Alt as ESC before the key's bytes, Enter as CR, Backspace as DEL, the erase character, and each function key as its string in the keymap, the arrows, Home and End as xterm's sequences and Insert, Delete, Page Up and Page Down as VT220's (`ESC [ 2 ~` and so on), as the `rach2` terminfo entry lists them. K_XLATE writes a Latin-1 character as its byte and drops a character past Latin-1, which an 8-bit map cannot hold; with KDSKBMETA's K_METABIT, Alt sets the top bit of a single ASCII byte in place of sending ESC. When the lock flags change and the LEDs follow them, `input_set_leds` lights the new ones. The bytes then go to one place:

* Shift with Page Up or Page Down, which the keymap gives as the scrollback actions, scrolls the screen and sends nothing.
* With a reader parked on the console or a session owning it, the screen comes back from the scrollback and the bytes go to the discipline. Ctrl+C there is VINTR like any other byte, and a key nobody reads waits in the discipline as type-ahead.
* Otherwise the key is the debug shell's. ETX is its Ctrl+C (`shell_interrupt`). While it reads input (`shell_reads_input`), Page Up, Page Down, Home and End scroll the screen, and other bytes go to its command buffer (`shell_input_char`) with DEL as Backspace; an escape sequence, which the shell cannot edit with, is dropped, and so is everything when it does not read.

The keymap at boot is US English, `keymap.c`'s built-in tables, and `loadkeys` replaces it, as kbd's tools on Rach2 do with the maps under `/usr/share/kbd/keymaps`. Those maps put actions of Linux's console that Rach2's has not on some keys: a switch of virtual console on Alt with F1 to F12 and the arrows, KeyboardSignal on Alt+Up, Boot on Ctrl+Alt+Delete. `keymap_key` gives such a key its entry in table 0 with the modifiers held, so that Alt+F1 sends F1 with Alt, as the built-in map does.

`kd.c` counts the keyboards that hold each key, in every mode, and gives the translator a release only from the last of them, so that Shift released on one keyboard stays held while another holds it. Leaving K_RAW, K_MEDIUMRAW or K_OFF for a translating mode rebuilds the held modifiers from the counts (`keymap_state_held`), as Linux's `compute_shiftstate` does, since the translator saw none of the presses and releases meanwhile.

The console's keyboard has Linux's five modes, which KDSKBMODE sets and [console(4)](../../../man/man4/console.4) lists. K_UNICODE, the mode at boot, and K_XLATE translate keys as above. In K_RAW, K_MEDIUMRAW and K_OFF (`kd_translates` false) the translation, the lock keys and the console's own keys, its scrollback and the debug shell's Ctrl+C, are off: `kd_raw_code` takes each byte of the raw view and in K_RAW puts it in the console's discipline as it came, prefixes, releases and repeats as make codes among them; in K_MEDIUMRAW `kd_key_event` puts there Linux's key codes, one byte for a code below 128 with 0x80 set on its release, and three for a higher one, 0x00 (0x80 on release) and then the code's high and low seven bits with 0x80 set; K_OFF puts nothing. The bytes go through the discipline as any input does, so the termios, poll, FIONREAD and nonblocking reads apply to them; a program sets raw termios itself, as on Linux. COM1's bytes are discarded in these modes (COM1, below). Each KDSKBMODE, and the restore of a mode, discards the console's unread input and stops a held key's repeat, as Linux's does.

`kd.c` keeps the rest of the keyboard's state that the KD* requests read and set: the keymap, 256 tables of 256 entries in Linux's encoding, each the built-in table of `keymap.c` until its first KDSKBENT and then a copy allocated for it, which K_NOSUCHMAP at key 0 frees, table 0 excepted; the 256 function strings, each copied when set; the accent table of at most 255 entries in code points; the lock flags and their defaults; the LEDs, which follow the lock flags until KDSETLED lights its own; and the meta setting, ESC before an Alt key at boot. The repeat's times are the input layer's (`input_set_repeat`), which evdev's EVIOCSREP sets as well. A request that sets the mode, the meta setting, the lock flags or the LEDs is open to a process of the console's session, the process that holds `/fb` and a privileged one; a request that sets the keymap, a string, the accents or the repeat is a privileged process's alone. A pty answers no KD* request, so kbd's tools, which try `/dev/tty` first, fall back to `/dev/console` inside `term`. KDGKBENT gives a code point's entry in every mode but K_XLATE, and KDSKBENT takes one in every mode, where Linux does either only in K_UNICODE, so that `loadkeys` loads a Unicode keymap while `term` holds the keyboard in K_MEDIUMRAW and translates its key codes through the console's keymap.

### Mice

The PS/2 mouse (`sys/arch/x86/ps2mouse.c`, IRQ 12, vector 44) assembles three-byte packets, finding the first byte by its bit 3, always set, and drops a packet with an overflow bit set; `rach2.nomouse` on the kernel command line skips it. A USB boot mouse's reports come from `hid.c`. Both put packets in the one queue of `sys/mouse.c`: 64 slots, each a button byte (left, right and middle in bits 0 to 2) and two signed byte movements clamped to -128 through 127, X positive to the right and Y positive away from the user. The PS/2 wire's Y has that sign already; `hid.c` negates a USB report's, which is positive toward the user. A packet that finds the queue full is dropped, and nothing in the queue says which mouse moved. `/mouse` fails with ENODEV until a mouse of either kind has been found (`input_mouse_found`); an open empties the queue and restarts the PS/2 packet framing.

### COM1

COM1 is the 16550 that [the PC platform](../arch/x86/Readme.md) sets up (`sys/arch/x86/serial.c`, IRQ 4, vector 36), with its FIFO on; on a machine without one every serial call does nothing. Received bytes go to a ring of 4096 bytes by two services: the port's interrupt takes at most 64 bytes a time, and `tty_console_poll`, which the timer tick calls every millisecond (`TICK_HZ` is 1000) and the interrupt calls when its service leaves bytes in the ring, takes at most 64 more, so a port whose interrupt is not enabled is still read. A full ring stops the service and masks the receive interrupt until a take leaves the ring less than half full. The bytes stay in the UART, whose FIFO then fills, so QEMU's sender waits and a real sender overruns, which the line status reports.

After the service, what `tty_console_poll` does depends on who reads the console:

* A reader or poller parked on the console is woken and drains the ring itself, in `console_pump`, in its own context with interrupts off, until the ring is empty or the discipline has no room for a line. It echoes what it takes when the ring had at most 64 bytes as it began, and otherwise takes them without echo, since each echoed byte waits on the transmitter, about 87 microseconds at 115200 baud, with interrupts off.
* With nobody parked and a session owning the console, as when a shell waits for its foreground job, `console_pump_irq` moves at most 64 bytes into the discipline without echo, so an interrupt character reaches the foreground group and the rest waits as type-ahead.
* With no session, the bytes stay in the ring for the debug shell, which polls it (`serial_try_getc`) and releases the console whenever it regains control.

While the console's keyboard is in K_RAW, K_MEDIUMRAW or K_OFF, the service, `console_pump` and `console_pump_irq` instead discard every byte in the ring (`console_serial_closed`), so that the console's input holds key codes alone and nothing typed on COM1 waits to arrive once the keyboard translates again.

Both pumps stop at a full discipline and leave the rest in the ring. A signal character still gets through: it would discard the input before it anyway, so `console_signal_through` discards the bytes ahead of it in the ring and feeds it. A flush of the console's input, by TCSETSF or TCFLSH, empties the ring and the UART's receive FIFO as well.

`/proc/console` has the counters of this path, in the order a byte meets them, which proc(5) lists. `uart-overruns` counts the overruns any read of the line status saw; `tick-drains` counts the runs of `console_pump_irq`, from the tick and from the interrupt, and `reader-drains` those of `console_pump`, from a read, a poll or FIONREAD; `shell-bytes` counts the bytes the debug shell and the boot diagnostic took; `flush-bytes` counts what signal characters, TCSETSF and TCFLSH discarded from the discipline, and the bytes discarded ahead of a signal character.

### Pseudo-terminals

Opening `/dev/ptmx` allocates a `struct pty` from the heap at the lowest index no live pair has, locked until TIOCSPTLCK clears the lock (`pty.c`). The pair is freed when the master and every slave description have closed. The slave is a full `struct tty` with no pump, and its sink, `pty_slave_sink`, writes the master's ring, `m_buf`, of `PTY_BUF_SIZE` (4096) bytes.

* A master write feeds the slave's discipline a byte at a time through `tty_input_char` while the discipline has room for a line. A write that fills it returns short; one that has fed nothing waits, or fails with EAGAIN when nonblocking. A signal character among the bytes that wait is fed at once, and the bytes before it are discarded and counted, as on the console.
* A master read drains `m_buf`, and in packet mode (TIOCPKT) puts the status byte 0, TIOCPKT_DATA, before the bytes. Once the last slave description has closed (`hung_up` in `struct pty`) and the ring is empty it fails with EIO, as Linux's does; before any slave has opened it returns 0.
* A slave write is output processing into `m_buf`. The writer marks the pair busy for the whole write (`writing` in `struct pty`), so another writer waits until it ends, or fails with EAGAIN when nonblocking, as Linux's `atomic_write_lock` keeps two writes apart. It copies a piece at a time, reserving two bytes of ring for each byte while OPOST is set (ONLCR's CR LF) and one otherwise (`pts_growth`), and fits the piece again after the copy from the user, which may sleep on a page fault while echo fills the ring. While the ring has no room the writer waits on the slave's queue, which a master read wakes, so no output is lost. Echo does not wait, and is dropped when the ring is full.
* TIOCSWINSZ on the master posts SIGWINCH to the slave's foreground group.

The master has one wait queue, `m_read_wq`, for its readers, writers and pollers, and the slave's `space_wq` points at it. Each wake gives its kind of change, which an edge-triggered epoll registration reports. A slave read, an input flush, a termios change, and master input that took bytes out of the slave's discipline (an erase, or a signal character's flush) wake it with `WQ_ROOM`. Slave output and echo wake it with `WQ_DATA` when they put bytes in `m_buf`, and with no kind when they put none, as input written with echo off, or echo the full ring dropped. These wakes are made even when a later user copy of the same write fails. Input written to the master wakes the slave's `input_wq` with `WQ_DATA`.

Closing the master posts SIGHUP to the slave's foreground group and hangs the slave up. Slave readers take what is queued, and then every read returns 0, nonblocking ones included, since `tty_read` tests the slave's `hungup` when the discipline has nothing, and its wait predicate tests it beside the discipline's readiness. A slave write after the close fails with EIO, and poll reports POLLHUP. When the last slave description closes, master readers are woken to read EIO, and the master's poll reports POLLHUP.

## Limits

* The keyboard feeds the console's discipline without testing for room, so a key typed into a full queue or a full canonical line is dropped and counted (`queue-drops`, `line-drops`).
* The console has one keyboard state: every keyboard shares its locks, its LEDs and its mode, and a USB keyboard and the PS/2 keyboard show the same LEDs.
* The process that owns `/fb` reads its keys from the console like any other; a game that wants every press and release sets K_RAW and raw termios itself, as Doom does. Each return of the screen restores the receiving owner's keyboard and terminal settings and flushes the console's input, so it cannot become type-ahead for the next owner or login.
* TIOCSWINSZ on the console or a slave stores the size and posts no SIGWINCH; only the master's posts it.
* Packet mode sends only TIOCPKT_DATA, never the status bytes for a flush or a stop of output.

## Tests

The host tests run with `tests/run host`:

* `tests/host/n_tty_hosttest.c`: the discipline's editing, its commit rules, VMIN and VTIME, ISIG and output mapping.
* `tests/host/tty_hosttest.c`: `tty.c` and `pty.c` under a model scheduler that runs a producer only after the consumer is blocked: each wait and wake of a pair with its kind, packet mode, TCFLSH on the master, a slave read after the master's close, VMIN and VTIME's four cases on a slave and the console under a model tick, and COM1's bytes discarded while the keyboard is in a raw mode.
* `tests/host/kd_hosttest.c`: each KD* request's answer, errors and permissions, the keymap's tables allocated and freed, the two departures from Linux, K_RAW's and K_MEDIUMRAW's bytes, the translated keys with their repeats, locks and LEDs, scrollback and the debug shell's input, K_XLATE's Latin-1 and K_METABIT, the state saved and restored, and evdev's EVIOCGREP and EVIOCSREP.
* `tests/host/keymap_keytable_hosttest.c`: every case of the key table, `tests/host/keytable.txt`, through `keymap.c` and its US keymap.
* `tests/host/hid_hosttest.c`: USB keyboard reports turned into key events.
* `tests/host/input_hosttest.c`: the keyboards' held keys and modifiers across both sides and two keyboards, the repeat by ticks and counts, and the raw view each event gives `kd_raw_code`.

The suites, each run with `tests/run NAME`:

* `console`: stdintest's line reads, and ttyprobe's cooked line with erases, its raw byte, the screen's answers to its queries, and Alt with x read as ESC and x.
* `conload`: 360 numbered, checksummed lines typed at COM1 while the machine is loaded, with the reader parked, as type-ahead, after an interrupt character to a foreground child, with that character behind 200 lines nobody read, and across an exec; every line must arrive.
* `default`: among its probes, ptyprobe, a pair driven as a network login drives it, and jobprobe, sessions, groups and job control.
* `ssh`: dropbear's logins on a pseudo-terminal, with its window size and `stty`.
* `usb`: keystrokes and mouse movement from USB devices on machines with no 8042, read through the debug shell's buffer, the terminal and the mouse queue, and keylatprobe's Enters, each read as one CR.
* `keyboard`: the Kyrgyz keymap that `loadkeys -u kg alt-shift` loads, on QEMU's PS/2 keyboard and on its USB keyboard: Latin and Cyrillic letters through `showkey -a`, the switch both ways, Caps Lock on Cyrillic, Ctrl+C on the Cyrillic layer, Enter as CR, a held key's repeats, Caps Lock's LED as `setleds` and QEMU see it, `showkey`'s key codes and `kbdrate`.

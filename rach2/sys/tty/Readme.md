# Terminals

`sys/tty/` is the kernel's terminal layer: the N_TTY line discipline, which edits, echoes and recognizes signal characters in what is typed; the console terminal, which the keyboard and COM1 feed and the screen and COM1 show; and the pseudo-terminal pairs a network login gives a remote user. This document also follows a keystroke, a mouse movement and a serial byte from the hardware to a reader, through `sys/input.c`, `sys/kbd.c`, `sys/mouse.c` and `sys/arch/x86/serial.c`. The screen the console draws on is described in [the display Readme](../display/Readme.md).

## Interfaces

Programs see the console, `/dev/tty`, `/dev/ptmx` and `/dev/pts/N` as [console(4)](../../../man/man4/console.4) describes them, with the terminal requests of [ioctl(2)](../../../man/man2/ioctl.2) and the reads of [read(2)](../../../man/man2/read.2). The mouse is the path `/mouse` ([open(2)](../../../man/man2/open.2)), and the counters of the console's receive path are `/proc/console` ([proc(5)](../../../man/man5/proc.5)).

Inside the kernel, `tty.h` is the terminal. `tty_input_char` gives a terminal one input byte from any source, with interrupts off or from an interrupt handler; `tty_read`, `tty_write`, `tty_wait_output`, `tty_poll`, `tty_inq`, `tty_set_termios`, `tty_tcflow`, `tty_flush_input` and `tty_hangup` serve the descriptors; `tty_set_session` and `tty_make_sole_ctty` (in `pty.c`) set a terminal's session and foreground group. `input.h` takes a keyboard's keys (`input_key_event`, `input_set1_event`) or a mouse report (`input_mouse`) from any driver, and gives the PS/2 keyboard a keymap of its set-1 codes (`input_keyboard_set1_keymap`), which EVIOCSKEYCODE changes as on Linux. The debug shell in `rach2/kernel.c` defines the three functions `input.c` calls: `shell_reads_input`, `shell_input_char` and `shell_interrupt`. `input_set_leds` records the LEDs every keyboard is to show and reports them on the keyboards' event devices, and each keyboard's driver sends them, the PS/2 keyboard's from the tick and taking its replies through `input_ps2_reply`, a USB keyboard's from the USB stack's step; the console's KDSETLED and KDSKBLED call it. `kd.h` is the console's keyboard as Linux's console keeps it: `kd_ioctl`, which the console's requests reach first and which answers Linux's KD* requests; `kd_key_event`, which takes every key as Linux's key code; `kd_raw_code`, which takes the raw view's set-1 bytes; `kd_translates`, whether the keyboard's mode translates keys; `kd_state_save` and `kd_state_restore`, which keep its state and the console's termios for an owner of the screen; and `kd_hold` and `kd_unhold`, with which the console's DRM client (`sys/drm/drm_client.c`) puts the keyboard in K_OFF while a DRM master holds the screen and gives its mode back after. `kd_key_event` translates through `keymap.h`, the translator of keys through keymaps in Linux's encoding, which `term` and the host tests compile too, under `kio_key_modes` in `kio.h`, the console's cursor and keypad modes, which DECCKM and DECKPAM set.

## Design

### The line discipline

Process-group signals from the terminal select one target per process through `signal_process_target` and use `signal_post_multi`, so a child being built by a member receives a signal sent during its fork ([signals](../proc/signal.Readme.md#sending)).

`n_tty.c` is pure logic over a `struct n_tty` and makes no kernel calls, so the kernel and a host test compile the same file. Echo and output leave through a sink function the caller supplies: the console's sink writes the screen and COM1, and a pseudo-terminal slave's writes its master's ring.

The state is the termios (`struct ktermios`, Linux's 36-byte kernel layout with 19 control characters, the same on both architectures), the line under edit (`N_TTY_LINE_MAX`, 4096 bytes, Linux's `N_TTY_BUF_SIZE`), and the read queue, a ring of `N_TTY_READ_MAX` (8192) bytes, two lines, beside an array that marks the last byte of each committed line.

In canonical mode a byte edits the line. ERASE, WERASE and KILL remove characters: under IUTF8, which a new terminal has since Rach2's text is UTF-8, a whole UTF-8 character, and otherwise, or for bytes that end in no whole sequence, one byte. With ECHOE each removed character is rubbed out on the screen as `\b \b` once for each cell its echo took: the width `k_wcwidth` gives a UTF-8 character, which is none for a combining mark and two for a CJK character or an emoji, two for a control character echoed as `^X` under ECHOCTL, and one for any other byte. An ordinary byte joins the line while the line has room for it and a terminator, so a line has at most 4095 bytes before its newline, as Linux's n_tty has it; a byte past that is dropped and counted. A newline or VEOL commits the line with its terminator. VEOF commits a nonempty line without one, and on an empty line records end of file at the queue's present position. A canonical read returns at most one line, stopping at a newline or at a marked byte, so a line committed by VEOF keeps its boundary, and a later change of VEOL leaves the queued boundaries as they were. A read that reaches the end-of-file position returns 0, once.

In raw mode each byte is readable at once, and a read waits as POSIX's VMIN and VTIME say, VTIME in tenths of a second: with both 0 it returns at once with what is there; with VMIN above 0 and VTIME 0 it waits for VMIN bytes; with VMIN 0 and VTIME above 0 it returns with the first byte, or with none once VTIME has passed since the read began; with both above 0 it waits for a first byte with no limit, and then for VMIN bytes or for VTIME to pass after the last byte, and returns what came. A read for fewer bytes than VMIN needs only as many. poll(2) and the wakes it counts follow Linux's `input_available_p`: the terminal is readable to poll with VMIN bytes when VMIN is above 0 and VTIME is 0, and otherwise with one byte (`n_tty_readable`), so a program that polls a VMIN 0 terminal for keys, as `play` does, sees none until one comes; a read tests `n_tty_read_ready`. A change of termios wakes the blocked readers, which test the new VMIN and VTIME. When a program turns ICANON off, a partial line joins the queue behind the lines committed before it, so it is neither lost nor reordered; if the queue has no room for it, it stays in the line buffer and a raw read takes it after the queue.

With ISIG set, VINTR, VQUIT and VSUSP are returned to the caller, which posts SIGINT, SIGQUIT or SIGTSTP to the foreground process group. Without NOFLSH the character also discards all unread input and the echo still held, and the caller flushes the terminal's output, all before the character's own echo, as Linux's `isig` does; with NOFLSH nothing is discarded. A control character of 0 is disabled. The input flags ISTRIP, IGNCR, ICRNL, INLCR, IXON and IXANY and the output flags OPOST, ONLCR and OCRNL are the ones implemented; IXOFF is kept and does nothing, as on Linux's console and pseudo-terminals, which send no flow characters for their input.

Under IXON, which a new terminal has with VSTART ^Q and VSTOP ^S as Linux's default termios, VSTOP stops the terminal's output (`stopped` in `struct n_tty`) and VSTART restarts it; neither reaches a reader. The test comes after ISTRIP and before the CR mappings, and VSTART wins when the two are one byte. Under IXANY any other byte restarts output as well and is input as usual, and a signal character restarts it under IXON alone. TCXONC's TCOOFF stops output too (`tco_stopped`), and only TCOON ends that stop: VSTART, IXANY and a signal character do not. Turning IXON off restarts a stop VSTOP made. While output is stopped, echo is held in a ring of `N_TTY_ECHO_MAX` (4096) bytes, whose oldest byte gives way when it is full, and `n_tty_echo_flush` gives it out once output restarts, as far as the sink has room, as Linux's echo buffer waits for `process_echoes`, which stops at the driver's write room. `n_tty_lookahead` acts on a flow character that waits behind a full discipline, as Linux's `n_tty_lookahead_flow_ctrl`, and `n_tty_receive_looked` then feeds that byte without acting on it again.

`n_tty_has_room` is true while the discipline can take a whole line more: the queue and the line together use no more than 8192 less 4096 bytes. The queue is two lines long so that a whole line still fits beside a queue filled that far; with a queue of one line the rule would let a producer feed only an empty discipline, and a line under edit would never be finished. The producers that can wait, the serial pumps and a master's write, feed the discipline only while it is true, so a burst waits upstream and no byte of it is dropped.

### The terminal object

`tty.c` puts the discipline behind a wait queue. `struct tty` has the discipline, `input_wq` for readers and pollers, `space_wq` for a producer waiting for room, the window size, the sink and its `room`, an optional `pump` that drains a polled input source, and the session and foreground group (`sid` and `fg_pgid`, 0 for none). A sink with a `room`, a pty slave's, takes echo and output only as far as it has room, as Linux's `tty_write_room` limits both: echo that finds no room is held, and a write stops short.

`tty_input_char` runs one byte through the discipline. It wakes `space_wq` with `WQ_ROOM` when the byte took bytes out of the discipline (an erase, or a signal character's flush), posts a recognized signal to every process of the foreground group, through its leader even when the leader has ended while other threads run, and, without NOFLSH, flushes the terminal's input and output through its `flush`, and wakes `input_wq` with `WQ_DATA` when a read would no longer block. When the byte stops or restarts output, it calls the terminal's `flow` with `TTY_FLOW_STOP` or `TTY_FLOW_START`, and a restart wakes the writers on `input_wq` with `WQ_ROOM`. A drain that feeds a byte with its echo suppressed, the console's from an interrupt or a flood, drops that byte's echo before it reaches the echo held (`echo_muted` of the discipline): the echo held, as keyboard echo typed during a stop, waits whole for the next input or write that shows it, though it fills `echo_buf`, and only a signal character's flush discards it.

`tty_read` waits on `input_wq` with `tty_wait_cond` as the predicate, which runs the pump before it tests the discipline; the wait calls it with interrupts off, so no interrupt comes between a drain and the test after it. The same wait serves the console and a pseudo-terminal slave. A read with a VTIME timer arms its deadline in the process's `wakeup_tick`, which the tick acts on, before each wait and clears it after: once, from the read's start, with VMIN 0, and with VMIN above 0 again whenever the queue's count changes, for which the predicate ends the wait. `tty_input_char` wakes the readers with no kind, so poll counts nothing, for a raw byte that leaves the terminal unreadable to poll, which such a read must see. `tty_hangup` sets `hungup`, and a read that finds nothing after it returns 0, blocking or not. `tty_poll` and `tty_inq`, behind poll(2) and FIONREAD, also run the pump with interrupts off, and so does the path that records the USB latency stamps. After a wake the test and the copy run in one interrupts-off step, and a reader whose line another reader took waits again, since a read of the empty queue would return 0, end of file. A read copies through a bounce of `N_TTY_READ_CHUNK`, 1024 bytes, on the kernel stack. A raw read returns at most that much. A canonical read that stops inside its line for want of bounce sets `n_tty_line_open`, and the read of the console or a slave takes the rest of the line with `tty_read_rest` while its user buffer has room, so that one read returns the whole line, as Linux's does; a read for fewer bytes than the line leaves the rest for the next read.

`tty_write` gives the echo held to the sink first, as far as its room allows, then passes each byte through output processing to the sink, and stops at the first byte that finds output stopped or no room for it at its largest, returning the bytes written. On the console it runs between `console_write_begin` and `console_write_end`, so a kernel log record raised during the write waits for its end, and it then gives the screen's answers to the queries in the output (`k_take_answer` in `sys/kio.c`) to the console's input, where the program reads them as typed bytes. `tty_wait_output` waits on `input_wq` until output restarts or the terminal hangs up, or fails with EAGAIN for a nonblocking caller, and the console's write loops on the two, as Linux's `n_tty_write` waits for a stopped driver; poll gives no POLLOUT while output is stopped. `tty_tcflow` is TCXONC: TCOOFF and TCOON as above, and TCIOFF and TCION, which write VSTOP or VSTART to the sink, restarting a VSTOP's stop for that byte alone, as Linux's `tty_send_xchar`; under TCOOFF's stop a sink with a `room`, a pty slave's, takes nothing, as Linux's `pty_write` refuses while stopped, and the console writes the character, as Linux's `con_write` and `uart_send_xchar` write through any stop. A termios change that ends or begins IXON with ^S and ^Q calls `flow` with `TTY_FLOW_NOSTOP` or `TTY_FLOW_DOSTOP`. `tty_lookahead` acts on a flow character that waits for room; its restart gives the echo held to the sink, as Linux's VSTART runs `process_echoes`, except in the console's interrupt-side drain and in a drain of a flood of more than `TTY_ECHO_MAX` bytes, which show no echo and leave it held.

`tty_hangup` records end of file after the queued input and wakes every reader. A canonical read consumes that mark once, so an endpoint that hangs up keeps its own state for the reads after it, as the pseudo-terminal slave does with `master_open`.

`tty_vhangup` is vhangup(2)'s hangup of a terminal, Linux's `tty_vhangup`, which the call makes on the caller's controlling terminal once `CAP_SYS_TTY_CONFIG` admits it (`sys_vhangup` in `../syscall.c`). It posts SIGHUP and SIGCONT to the session's leader, takes the terminal from its session, sets the termios back to the discipline's defaults and wakes every reader and writer. Each terminal counts its hangups in `vhangups`, and each description opened on it records the count at its open (`tty_hangups` of `struct open_file`), so a description opened before a hangup is hung up for good while a new open is not (`tty_desc_hung`): a read of it is end of input, a write `EIO`, an ioctl `EIO` but `TIOCSPGRP`'s `ENOTTY`, and poll gives `TTY_HUNG_POLL`, Linux's readable, writable, error and hangup bits. A pty slave writer already waiting for room or for another writer when the hangup comes ends with `EIO` or the bytes it wrote, as Linux's `n_tty_write` does.

`tty_set_session` writes `sid` and `fg_pgid` with interrupts off, because the console's interrupt-side drain reads both. `tty_make_sole_ctty` makes a terminal the only controlling terminal of a session, dropping the console and every slave the session had, in one interrupts-off step. A session leader claims an unowned slave by opening it without O_NOCTTY while its session has no controlling terminal, and TIOCSCTTY claims the console or a slave; a read claims nothing, as on Linux, and init's console session claims the console with TIOCSCTTY after setsid, as getty does. When a session leader exits, `exit_release_session` in `sys/syscall_proc.c` releases the console and the slaves its session controls. Background reads and writes are as console(4) says. `tty_job_check` is Linux's `__tty_check_change`: a process of a background group of the session the terminal controls takes SIGTTIN on a read, and SIGTTOU on a write under TOSTOP and on TCSETS and its kin, TCFLSH, TCXONC and TIOCSPGRP, and its call is EINTR, restarted once the group is continued. A blocked or ignored SIGTTIN makes the read EIO, a blocked or ignored SIGTTOU lets the call go ahead, and an orphaned group's call that would otherwise take the signal is EIO. A parent counts for that while any of its threads runs, its leader exited or not. TIOCSPGRP looks up the supplied number before checking its session: a negative number is EINVAL, zero or a number no thread, process group or session holds is ESRCH, and an existing number outside the terminal's session is EPERM. As Linux's `session_of_pgrp` does, it accepts a thread in the session when the number names no group.

### The console terminal

`tty_console_init` sets up `console_tty` at boot. Its sink, `console_sink`, writes each byte to the screen through `k_putc` and to COM1 through `serial_out`; its pump, `console_pump`, drains COM1's receive ring; its window size is the screen's cells (`k_console_size`). The keyboard and COM1 feed it. Its `flow`, `console_flow`, sets Scroll Lock and its LED while output is stopped (`kd_scroll_lock`), and the Hold key, Scroll Lock, stops and restarts output (`tty_console_hold`), as Linux's vt does. When the discipline has no room, the pumps look ahead in COM1's ring for flow characters (`serial_rx_lookahead`), so a ^Q typed behind a full line still restarts output; the ring marks how far it was looked at, and `tty_input_looked` feeds those bytes without acting on them again.

The console write path in `sys/syscall_fs.c` reaches `sched_service_point` after each chunk of at most 256 input bytes. It can pass the big lock to a waiting processor or run a queued thread there, after `tty_write` has ended its console bracket. A slow serial port therefore does not keep the lock across every chunk of a large write. A single chunk and its serial waits still run under the lock.

### Keystrokes

Two drivers produce keystrokes, and both give `sys/input.c` Linux's `KEY_*` codes, one `struct input_keyboard` for each keyboard. The PS/2 keyboard's handler (`sys/arch/x86/ps2kbd.c`, IRQ 1, vector 33) reads the port when the status register says a byte is waiting, offers it to a command waiting for the keyboard's reply (`input_ps2_reply`), and gives any other to `input_set1_event`, which keeps the keyboard's E0 or E1 prefix and passes the key to `input_key_event` with that code as its `MSC_SCAN`, Pause's E1 1D 45 as the extended 0x45. A USB boot keyboard's reports become key events in `sys/usb/hid.c`, as [the USB Readme](../usb/Readme.md) describes, with the usage as `MSC_SCAN`. Both name a key by `set1_keycode` in `sys/kbd.c`, which gives Linux's code for a set-1 code with its release bit clear and 0x80 set after an E0 prefix: Linux numbered its keys after the plain codes 0x01 to 0x53, and the rest are two tables, the extended keys and the plain codes past the keypad. Every keyboard's interrupt and the tick run on the boot processor with interrupts off, so the events reach their consumers one at a time and in order.

`input_key_event` keeps the keys each keyboard holds. A press of a key that keyboard holds already, a PS/2 keyboard's own repeat, and a release of one it does not hold are dropped. The modifiers are derived from the held keys, each side apart and across every keyboard (`input_modifiers`): Shift stays held while either Shift key is down on any keyboard. The keyboards repeat in software, in one place (`input_tick`, from the tick): the last key pressed that is not a modifier or a lock repeats 250 ms after its press and then every 33 ms, Linux's times, which `input_set_repeat` changes; each repeat is due a period after the last was due, so the 1 ms tick keeps 33 ms on average, and a tick that comes late sends at most four. The repeat stops at the key's release, at its keyboard's detach and at `input_cancel_repeat`. Each accepted event, press, repeat or release, ends a suspend to idle (`suspend_wake`) and puts off the blanking, then goes to the keyboard's event device, to the console's keyboard (`kd_key_event` in `sys/kd.c`), below, and as its set-1 bytes, the raw view `input_raw_bytes` gives, to `kd_raw_code`, which uses them in K_RAW alone. A keyboard that goes, `hid_gone` for USB, releases every key it holds through the same path (`input_keyboard_detach`).

Each keyboard is also an event device of its own, `/dev/input/eventN` ([input(4)](../../../man/man4/input.4)), registered by `input_keyboard_attach`: the PS/2 keyboard as "AT Translated Set 2 keyboard" by `kbd_init`, and each USB keyboard, by `input_keyboard_attach_dev`, under the name its strings give when `hid_attach` reads its report descriptor ([`usb/Readme.md`](../usb/Readme.md)). Its packets are `MSC_SCAN`, the key and `SYN_REPORT` for a press or a release, and the key with value 2 and `SYN_REPORT` for a repeat; a change of the repeat's times is `EV_REP`, and of the LEDs `EV_LED`. `sys/evdev.c` keeps each device's keys down and gives each open a queue sized as Linux's evdev sizes it, eight packets of the size the device's axes and slots suggest, at least 64 records and a power of two: 64 for a keyboard, 128 for a mouse, 256 for a touchpad with two slots. A reader that falls behind loses all but a `SYN_DROPPED` and the newest record, as with Linux's. `evdev_read` waits until a whole packet is queued and then returns as many whole records as the buffer holds, so a small buffer splits a packet across reads. `evdev_report` takes the evdev lock with interrupts off and never sleeps, so the keyboards call it from their interrupts. A write to an event device injects its records as if the device had reported them, as Linux's `evdev_write` does: a keyboard's key that reaches the opens with no grab held goes on to the console (`input_written`), and its `EV_LED` and `EV_REP` set the LEDs and the repeat every keyboard shares. Any other device that can report a key below `BTN_MISC` or a Braille key, the power and sleep buttons, a hotkey device or a keypad, gives the console its keys too, reported or written, as Linux's `kbd_match` binds the console's handler to it: `evdev_report` hands each such key that passed the filters with no grab held to `input_console_key`, which `input_written` also uses. A device whose event device an open has grabbed (EVIOCGRAB) gives the console none of its keys, as Linux's grab keeps them from the console's handler.

`sys/evdev_sysfs.c` shows each event device in `/sys` as Linux's input core does ([sysfs(5)](../../../man/man5/sysfs.5)): `/sys/class/input/inputN` and its `eventN`, below the i8042's port `serioK` for a PS/2 device, the USB interface `B-P:C.I` for a USB one, which it makes with the device, or `/sys/devices/virtual/input` for the rest, each found from the device's EVIOCGPHYS, with the capability bitmaps, modalias and uevent Linux writes, in the caller's long. A USB keyboard or mouse registers from the timer's pass of the USB stack, in an interrupt, where `/sys`'s entries cannot be made, so `evdev_sysfs_sync` makes them in a kernel thread, kinputd, started with the first program (`evdev_sysfs_start`). Each registration has a number of its own (`evdev_desc`'s `gen`), and each registration and removal bumps `evdev_changes` and wakes kinputd, which takes away the entries of each device gone, sending `remove` for its `eventN`, its `inputN` and then its USB interface, and makes those of each new one, sending `add` in the opposite order. `evdev_snapshot` copies a device's name, place, identity and bitmaps under the evdev lock, so the sync reads no device that changes under it.

`kd_key_event` translates each event in K_UNICODE, the mode at boot, and K_XLATE. `keymap_key` reads the key's entry in the console's keymap under the modifiers and locks it keeps in `kd_kb`, and turns it into text, an action or nothing: a modifier or a lock changes the state and sends nothing, a dead key waits for the next key to compose with it through the accent table, and a release sends nothing, but for Alt's release after keypad digits, which sends the character they number. `keymap_encode` writes the bytes of the result as xterm sends them, under the console's cursor and keypad modes: a character as UTF-8, Ctrl with a letter as its control byte, Alt as ESC before the key's bytes, Enter as CR, Backspace as DEL, the erase character, and each function key as its string in the keymap, the arrows, Home and End as xterm's sequences and Insert, Delete, Page Up and Page Down as VT220's (`ESC [ 2 ~` and so on), as the `rach2` terminfo entry lists them. K_XLATE writes a Latin-1 character as its byte and drops a character past Latin-1, which an 8-bit map cannot hold; with KDSKBMETA's K_METABIT, Alt sets the top bit of a single ASCII byte in place of sending ESC. When the lock flags change and the LEDs follow them, `input_set_leds` lights the new ones. The bytes then go to one place:

* Shift with Page Up or Page Down, which the keymap gives as the scrollback actions, scrolls the screen and sends nothing.
* With a reader parked on the console or a session owning it, the screen comes back from the scrollback and the bytes go to the discipline. Ctrl+C there is VINTR like any other byte, and a key nobody reads waits in the discipline as type-ahead.
* Otherwise the key is the debug shell's. ETX is its Ctrl+C (`shell_interrupt`). While it reads input (`shell_reads_input`), Page Up, Page Down, Home and End scroll the screen, and other bytes go to its command buffer (`shell_input_char`) with DEL as Backspace; an escape sequence, which the shell cannot edit with, is dropped, and so is everything when it does not read.

The keymap at boot is US English, `keymap.c`'s built-in tables, and `loadkeys` replaces it, as kbd's tools on Rach2 do with the maps under `/usr/share/kbd/keymaps`. Those maps put actions of Linux's console that Rach2's has not on some keys: a switch of virtual console on Alt with F1 to F12 and the arrows, KeyboardSignal on Alt+Up, Boot on Ctrl+Alt+Delete. `keymap_key` gives such a key its entry in table 0 with the modifiers held, so that Alt+F1 sends F1 with Alt, as the built-in map does.

`kd.c` counts the keyboards that hold each key, in every mode, and gives the translator a release only from the last of them, so that Shift released on one keyboard stays held while another holds it. Leaving K_RAW, K_MEDIUMRAW or K_OFF for a translating mode rebuilds the held modifiers from the counts (`keymap_state_held`), as Linux's `compute_shiftstate` does, since the translator saw none of the presses and releases meanwhile.

The console's keyboard has Linux's five modes, which KDSKBMODE sets and [console(4)](../../../man/man4/console.4) lists. K_UNICODE, the mode at boot, and K_XLATE translate keys as above. In K_RAW, K_MEDIUMRAW and K_OFF (`kd_translates` false) the translation, the lock keys and the console's own keys, its scrollback and the debug shell's Ctrl+C, are off: `kd_raw_code` takes each byte of the raw view and in K_RAW puts it in the console's discipline as it came, prefixes, releases and repeats as make codes among them; in K_MEDIUMRAW `kd_key_event` puts there Linux's key codes, one byte for a code below 128 with 0x80 set on its release, and three for a higher one, 0x00 (0x80 on release) and then the code's high and low seven bits with 0x80 set; K_OFF puts nothing. The bytes go through the discipline as any input does, so the termios, poll, FIONREAD and nonblocking reads apply to them; a program sets raw termios itself, as on Linux. COM1's bytes are discarded in these modes (COM1, below). Each KDSKBMODE, and the restore of a mode, discards the console's unread input and stops a held key's repeat, as Linux's does. While `kd_hold` holds the keyboard in K_OFF, a KDSKBMODE is checked and kept for `kd_unhold`, and KDGKBMODE, `kd_state_save` and `kd_translates` read the mode kept, so that a program sees the mode it set and COM1's bytes go on reaching the console, as a serial console's do on Linux while a DRM master has the screen; the hold and `kd_unhold` stop a held key's repeat and discard no input.

`kd.c` keeps the rest of the keyboard's state that the KD* requests read and set: the keymap, 256 tables of 256 entries in Linux's encoding, each the built-in table of `keymap.c` until its first KDSKBENT and then a copy allocated for it, which K_NOSUCHMAP at key 0 frees, table 0 excepted; the 256 function strings, each copied when set; the accent table of at most 255 entries in code points; the lock flags and their defaults; the LEDs, which follow the lock flags until KDSETLED lights its own; and the meta setting, ESC before an Alt key at boot. The repeat's times are the input layer's (`input_set_repeat`), which evdev's EVIOCSREP sets as well. A request that sets the mode, the meta setting, the lock flags or the LEDs is open to a process of the console's session, the process that holds `/fb` and a privileged one; a request that sets the keymap, a string, the accents or the repeat is a privileged process's alone. A pty answers no KD* request, so kbd's tools, which try `/dev/tty` first, fall back to `/dev/console` inside `term`. KDGKBENT gives a code point's entry in every mode but K_XLATE, and KDSKBENT takes one in every mode, where Linux does either only in K_UNICODE, so that `loadkeys` loads a Unicode keymap while `term` holds the keyboard in K_MEDIUMRAW and translates its key codes through the console's keymap.

### Mice

The PS/2 mouse (`sys/arch/x86/ps2mouse.c`, IRQ 12, vector 44) knocks for the IntelliMouse Explorer's and then the IntelliMouse's protocol, as Linux's psmouse does, and assembles packets of three bytes, or four with a wheel, finding the first byte by its bit 3, always set, and dropping a packet with an overflow bit set; `rach2.nomouse` on the kernel command line skips it. A USB boot mouse's reports come from `hid.c`. Each mouse is an event device registered by `mouse_register` with Linux's name for it, and gives each packet to `mouse_report`, its motion with Y positive toward the user as evdev has it: the event device gets the buttons, the motion and the wheels ([input(4)](../../../man/man4/input.4)), and the one queue of `sys/mouse.c` gets the rest: 64 slots, each a button byte (left, right and middle in bits 0 to 2) and two signed byte movements clamped to -128 through 127, X positive to the right and Y positive away from the user, so `mouse_report` negates Y. A packet that finds the queue full is dropped, and nothing in the queue says which mouse moved. A mouse whose event device an open has grabbed gives the queue no packets, and the motion and buttons a program writes to a mouse's event device reach the queue as a packet at each `SYN_REPORT` after a change (`mouse_written`), as Linux's grab and mousedev treat them. `/mouse` fails with ENODEV until a mouse of either kind has been found (`input_mouse_found`); an open empties the queue and restarts the PS/2 packet framing.

A Synaptics touchpad on the PS/2 port (`sys/arch/x86/synaptics.c`) answers the bring-up's Synaptics knock, before the wheel's, and is set up as Linux's psmouse sets it: its queries, absolute mode with W mode at 80 packets a second, and the advanced gesture mode of a pad that has it, which then sends the second finger's place in packets of its own. Its event device has the name, numbers and capabilities Linux's `set_input_params` gives the same pad ([input(4)](../../../man/man4/input.4)), and its six-byte packets reach it through the mouse's handler. A pad with an image sensor, as the Lenovo's is, reports its two contacts in two slots, which `evdev.c` keeps as Linux's input core does: `ABS_MT_SLOT` only chooses the slot the values after it are for and goes out before the first of them that changed, each slot's values are filtered against that slot's, and `evdev_mt_assign_slots`, `evdev_mt_report_slot_state`, `evdev_mt_drop_unused` and `evdev_mt_report_pointer_emulation` are Linux's `input_mt_*` calls, which match each contact to the slot that had it, number new contacts, lift the slots no contact took and report the oldest contact as the pointer. The touchpad is no mouse of `mouse_report`'s: `mouse_attach_touchpad` gives its event device a handler in `sys/mouse.c`, called with each event that passes the filters while no open holds the grab, which makes the queue's packets as Linux's mousedev makes those of `/dev/input/mice`: while a finger touches, from the third packet on, each change of `ABS_X` or `ABS_Y` moves the pointer by the change over two packets, the pad's width being 256 counts on both axes, with the fractions carried; a touch shorter than 200 ms is a click of the left button, and each `SYN_REPORT` gives a packet.

An Elantech touchpad of hardware version 1 to 4 (`sys/arch/x86/elantech.c`) answers Elantech's magic knock where no Synaptics pad answered, and is set up as Linux's elantech driver sets it: its firmware version, capabilities and range by Synaptics' sliced queries or Elantech's own, its registers written for absolute mode, and a machine's quirks chosen by the SMBIOS maker and product name as Linux chooses them by DMI. Its event device has the name, numbers and capabilities Linux's `elantech_set_input_params` gives the same pad ([input(4)](../../../man/man4/input.4)): two slots that bound two contacts on versions 2 and 3, five slots of their own on version 4. A pointing stick on a version 3 or 4 pad sends its packets into the same stream, and they go to an event device of its own, a mouse of `mouse_register`'s whose moves also move `/dev/mouse`'s pointer. The pad is attached with `mouse_attach_touchpad`, as a Synaptics pad is.

### COM1

COM1 is the 16550 that [the PC platform](../arch/x86/Readme.md) sets up (`sys/arch/x86/serial.c`, IRQ 4, vector 36), with its FIFO on; on a machine without one every serial call does nothing. Received bytes go to a ring of 4096 bytes by two services: the port's interrupt takes at most 64 bytes a pass, and the console's service, which the interrupt runs after each pass that leaves bytes in the ring, takes at most 64 more. The interrupt makes passes until the receive line drops, the FIFO empty, or a full ring has masked the interrupt, at most 256 of them (`SERIAL_RX_PASSES`), up to 32 KiB, which also bounds a flood into a console that discards COM1's input and so never fills the ring: IRQ 4 is edge-triggered, so a handler that left data in the FIFO would see no other interrupt, and Linux's `serial8250_interrupt` loops the same way. `tty_console_poll`, which the timer tick calls every millisecond (`TICK_HZ` is 1000), reads the port at each call while the receive interrupt is not enabled; once it is, the tick reads the port only while the interrupt's handler has stopped at its pass limit with a byte still in the port, which leaves IRQ 4's edge-triggered line high, every fifth of a second (`CONSOLE_BACKUP_TICKS`, `serial_rx_line_high`) until a reading empties it. Under KVM each reading leaves the guest for QEMU, which serves the port in its own process, some 217 us on the testing PC, with the big kernel lock held; a reading at every tick until a first byte, which a console that nobody types into never receives, spent a fifth of the boot processor's time. Linux reads an 8250 that has an interrupt from no timer; its backup timer only sends, for a UART with the THRE bug. A full ring stops the service and masks the receive interrupt until a take leaves the ring less than half full. The bytes stay in the UART, whose FIFO then fills, so QEMU's sender waits and a real sender overruns, which the line status reports.

After the service, what `tty_console_poll` does depends on who reads the console:

* A reader or poller parked on the console is woken and drains the ring itself, in `console_pump`, in its own context with interrupts off, until the ring is empty or the discipline has no room for a line. It echoes what it takes when the ring had at most 64 bytes as it began, and otherwise takes them without echo, since each echoed byte waits on the transmitter, about 87 microseconds at 115200 baud, with interrupts off.
* With nobody parked and a session owning the console, as when a shell waits for its foreground job, `console_pump_irq` moves at most 64 bytes into the discipline without echo, so an interrupt character reaches the foreground group and the rest waits as type-ahead.
* With no session, the bytes stay in the ring for the debug shell, which polls it (`serial_try_getc`) and releases the console whenever it regains control.

While the console's keyboard is in K_RAW, K_MEDIUMRAW or K_OFF, other than the K_OFF a DRM master's hold sets, the service, `console_pump` and `console_pump_irq` instead discard every byte in the ring (`console_serial_closed`), so that the console's input holds key codes alone and nothing typed on COM1 waits to arrive once the keyboard translates again.

Both pumps stop at a full discipline and leave the rest in the ring. A signal character still gets through: it would discard the input before it anyway, so `console_signal_through` discards the bytes ahead of it in the ring and feeds it. A flush of the console's input, by TCSETSF or TCFLSH, empties the ring and the UART's receive FIFO as well.

`/proc/console` has the counters of this path, in the order a byte meets them, which proc(5) lists. `uart-overruns` counts the overruns any read of the line status saw; `tick-drains` counts the runs of `console_pump_irq`, from the tick and from the interrupt, and `reader-drains` those of `console_pump`, from a read, a poll or FIONREAD; `shell-bytes` counts the bytes the debug shell and the boot diagnostic took; `flush-bytes` counts what signal characters, TCSETSF and TCFLSH discarded from the discipline, and the bytes discarded ahead of a signal character.

### Pseudo-terminals

Opening `/dev/ptmx` allocates a `struct pty` from the heap at the lowest index no live pair has, locked until TIOCSPTLCK clears the lock (`pty.c`). The pair is freed when the master and every slave description have closed. The slave is a full `struct tty` with no pump, and its sink, `pty_slave_sink`, writes the master's ring, `m_buf`, of `PTY_BUF_SIZE` (4096) bytes.

* Master writes hold a lock (`m_writing`) across user copies and waits, so two writes cannot interleave, as Linux's `tty_write_lock` keeps them. A `writev` imports the vector once and holds the same lock across all its elements (`pty_master_writev`); a failed later buffer returns the prefix already written. Another writer waits, or takes EAGAIN when nonblocking. A master write feeds the slave's discipline a byte at a time through `tty_input_char` while the discipline has room for a line. A write that fills it returns short; one that has fed nothing waits, or fails with EAGAIN when nonblocking. A signal character among the bytes that wait is fed at once, and without NOFLSH the bytes before it are discarded and counted, as on the console; a flow character among them is acted on at once as well, and the write feeds the bytes up to the last flow character that acted, past the discipline's room for a line, before any wait and returns that prefix. No other writer can take that space between the look ahead and the feed, as Linux's flip buffer holds the bytes its look ahead reads. The look ahead stops where its bytes would pass what the read queue can still store (`ptm_look_end`), so a byte it takes is never dropped, as Linux looks ahead only in the bytes its flip buffer has taken. TCXONC's TCOOFF on the master (`m_stopped`) stops its writes until TCOON, and TCIOFF and TCION feed ^S and ^Q to the slave. Both flow ioctls wait for the master write lock even on a nonblocking descriptor, fail with EINTR when a signal ends that wait, and hold the lock while feeding. A write goes on after every slave description has closed, as on Linux, where the master holds a count of the slave of its own, until the discipline fills.
* A master read drains `m_buf`, and in packet mode (TIOCPKT) puts the status byte 0, TIOCPKT_DATA, before the bytes. Once the last slave description has closed (`hung_up` in `struct pty`) and the ring is empty it fails with EIO, as Linux's does; before any slave has opened it returns 0.
* A slave write is output processing into `m_buf`, and while the slave's output is stopped it waits, or fails with EAGAIN when nonblocking, and poll gives no POLLOUT. The writer marks the pair busy for the whole write (`writing` in `struct pty`), so another writer waits until it ends, or fails with EAGAIN when nonblocking, as Linux's `atomic_write_lock` keeps two writes apart. It copies a piece at a time, reserving two bytes of ring for each byte while OPOST is set (ONLCR's CR LF) and one otherwise (`pts_growth`), and fits the piece again after the copy from the user, which may sleep on a page fault while echo fills the ring. While the ring has no room the writer waits on the slave's queue, which a master read wakes, so no output is lost. The echo held goes ahead of each piece as far as the ring has room, and the piece is then written only as far as it still fits (`tty_write`). Echo does not wait: what finds the ring full is held, and goes out with the next input or write.
* TIOCSWINSZ on the master posts SIGWINCH to the slave's foreground group.

The slave's flushes reach the master through the slave's `flush` (`pty_flush`), as Linux's `pty_flush_buffer` and `n_tty_packet_mode_flush`. TCFLSH on the slave with TCOFLUSH or TCIOFLUSH discards the output still in `m_buf`. In packet mode an input flush, by TCFLSH or TCSETSF, sets TIOCPKT_FLUSHREAD and an output flush TIOCPKT_FLUSHWRITE, which the master's next read takes as one status byte alone, and wakes the master's readers. A signal character without NOFLSH flushes both. The slave's `flow` (`pty_flow`) sets TIOCPKT_STOP or TIOCPKT_START when its output stops or restarts, clearing the other, and TIOCPKT_NOSTOP or TIOCPKT_DOSTOP when a termios change ends or begins IXON with ^S and ^Q, as Linux's `pty_stop`, `pty_start` and `pty_set_termios`. Pending status is readable and has POLLPRI, as on Linux. A vhangup of the slave discards its output in `m_buf` and leaves no status pending, as Linux's `__tty_hangup` clears `pktstatus` after its flush, so a nonblocking master read then fails with EAGAIN.

The master has one wait queue, `m_read_wq`, for its readers, writers and pollers, and the slave's `space_wq` points at it. Each wake gives its kind of change, which an edge-triggered epoll registration reports. A slave read, an input flush, a termios change, and master input that took bytes out of the slave's discipline (an erase, or a signal character's flush) wake it with `WQ_ROOM`. Slave output and echo wake it with `WQ_DATA` when they put bytes in `m_buf`, and with no kind when they put none, as input written with echo off, or echo the full ring held back. These wakes are made even when a later user copy of the same write fails. Input written to the master wakes the slave's `input_wq` with `WQ_DATA`.

Closing the master posts SIGHUP to the slave's foreground group and hangs the slave up. Slave readers take what is queued, and then every read returns 0, nonblocking ones included, since `tty_read` tests the slave's `hungup` when the discipline has nothing, and its wait predicate tests it beside the discipline's readiness. A slave write after the close fails with EIO, and poll reports POLLHUP. When the last slave description closes, master readers are woken to read EIO, and the master's poll reports POLLHUP.

## Limits

* The keyboard feeds the console's discipline without testing for room, so a key typed into a full queue or a full canonical line is dropped and counted (`queue-drops`, `line-drops`).
* The console has one keyboard state: every keyboard shares its locks, its LEDs and its mode, and a USB keyboard and the PS/2 keyboard show the same LEDs.
* The process that owns `/fb` reads its keys from the console like any other; a game that wants every press and release sets K_RAW and raw termios itself, as Doom does. Each return of the screen restores the receiving owner's keyboard and terminal settings and flushes the console's input, so it cannot become type-ahead for the next owner or login.
* TIOCSWINSZ on the console or a slave stores the size and posts no SIGWINCH; only the master's posts it.

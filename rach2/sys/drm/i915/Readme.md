# i915

`sys/drm/i915/` is the driver of Intel's Haswell graphics with GT2, the HD 4400 of the Lenovo G50-70 (PCI 8086:0a16) among them, after Linux 6.12's i915, whose names, register values and device table it takes. It binds the chip at 00:02.0, masks its interrupts, brings up forcewake, the display power well, stolen memory and the global GTT, reads the firmware's OpRegion and video BIOS table for the outputs and the panel, enables its MSI message, turns on RC6 and the GT's frequency control, starts the render and blitter rings with their status pages and user interrupts, and registers it as the DRM device `i915` ([`../drm.h`](../drm.h)); every access it makes to the chip goes through one hardware boundary, so that a host model and a fake chip stand in for it; the fake, under `rach2.i915fake`, stands on QEMU's `edu` device as the HD 4400, so that Mesa and libdrm reach the driver's real paths in QEMU. It does not yet take work from programs or set modes: the screen stays the firmware's framebuffer and the backlight `intelbl.c`'s ([`../../display/Readme.md`](../../display/Readme.md)). [i915(4)](../../../../man/man4/i915.4) is the interface a program sees.

## Use

The driver binds a chip only when the kernel command line has `rach2.i915` ([cmdline](../../../cmdline.md)). `drm_start` calls `i915_probe` through `arch_drm_probe(ARCH_DRM_NATIVE)`, after bochs and before the firmware framebuffer's driver. A bind on the Lenovo logs:

    i915: stolen: [mem 0xaba00000-0xaf9fffff], N KiB usable, inside the device's reserved region; DMAR active, no buffers in it
    i915: gtt: pipe A's firmware surface at 0x0, 4128 KiB, kept
    i915: gtt: 2048 MiB, 256 MiB of it through the aperture; 523256 entries to the scratch page, 1032 kept
    i915: opregion: version 2.0.0 at 0xaafb4018, mailboxes 0x1f; VBT in mailbox 4
    i915: vbt: "$VBT HASWELL        " from the OpRegion (Mailbox #4), version 177, 3 outputs
    i915: interrupts: messages on vector N
    i915: rps: RPn 200 MHz, RP1 200 MHz, RP0 1000 MHz, RPe 500 MHz, max 1000 MHz
    i915: rings: rcs0 and bcs0 started: 16 KiB each at 0x7fffb000 and 0x7fff6000, status pages at 0x7ffff000 and 0x7fffa000
    i915: found: 00:02.0: haswell/ult (device id 0a16), graphics 7.5, display version 7.00, gt2, revision 0b
    i915: registered: i915 1.6.0 for pci:0000:00:02.0 on card 0

A machine without an OpRegion, or without a valid table in it, takes the table from the option ROM's shadow at 0xc0000, `from the PCI ROM`, when the chip is the boot display; without either the bind logs `i915: vbt: no video BIOS table; Linux's defaults for each port`. An OpRegion that cannot be used logs `i915: opregion: at 0xA not used: error N`, and a table decoded only in part `i915: vbt: decoded in part: error N`.

With `rach2.i915.firstlight` as well, the bind has the render ring write a value to memory before it registers the device, as the section on rings says, and logs

    i915: first light: ok: rcs0 wrote 0x1915f157 at 0x7fff5000, breadcrumb 1, user interrupt latched

or `i915: first light:` and the failure: `no room in the ring`, `no breadcrumb`, `read back 0xV at 0xA, wrote 0x1915f157` or `no user interrupt`, the first, second and last with the ring's head, tail, ACTHD and IPEHR. `latched` says the processor had its interrupts off and the interrupt waits in the GT's identity register, `taken` that the handler ran.

With `rach2.i915fake` the probe also binds each function of QEMU's `edu` device, 1234:11e8, which `-device edu` gives a machine, with the fake chip behind it (the section on the fake chip below). A bind logs, beside the lines above but stolen memory's, which it has none of:

    i915: fake: 00:04.0: edu stands in for 8086:0a16
    i915: found: 00:04.0: haswell/ult (device id 0a16), graphics 7.5, display version 7.00, gt2, revision 0b

and a machine without the device logs `i915: fake: no edu device to stand on; QEMU's -device edu gives one`. The fake's faults are armed through `/sys/kernel/debug/dri/N/i915_fake`, as [debugfs(5)](../../../../man/man5/debugfs.5) gives it: `hang`, `irq`, `submit` or `bind`, alone, with a count or with `always`; `clear`; and `light`, which runs first light now. Each injection logs `i915: fake: injected: NAME: detail`.

Without `rach2.i915` the probe logs `i915: 00:02.0: 0a16 left to the firmware's framebuffer; rach2.i915 binds it` and touches nothing. Whether or not the option is given, the boot takes the chip's stolen memory out of the memory map before the frame allocator is made, logging `i915: stolen: reserving [mem 0xaba00000-0xaf9fffff], 0 KiB of it usable memory` on the Lenovo, whose firmware's map reserves it already. A wait that reaches its bound logs `i915: NAME: timeout after N us: register 0xR reads 0xV`.

## Design

### The hardware boundary

The driver reaches its chip only through a `struct i915_hw`: a table of `read32`, `write32`, `delay_us` and `gtt_map` and the backend's own pointer. On the machine the backend is BAR 0's first 2 MiB, the registers, mapped uncached with `map_mmio_typed`, as Linux maps them; the second 2 MiB, the GTT's entries, the backend's `gtt_map` maps write-combining when the global GTT comes up, as Linux does, or uncached on a processor without a page attribute table, so that no page of BAR 0 is mapped with two cache types. A backend without `gtt_map`, such as the model, answers for the entries as registers from 0x200000. In a host test the backend is the model of the HD 4400 (`tests/host/i915_model.c`), and in QEMU it may be the fake chip (below), a table of the same calls. An access past the backend's size reads all ones and writes nothing, as a chip that has gone reads.

A backend that stands in for a chip gives the table five more calls, which the MMIO backend and the model leave empty. `config_read32` answers for the chip's identity in configuration space: the bind then reads the ids, the class and revision, the board's ids, the GMCH control word, BDSM and MSAC from it, and the PCI function's own command word, BARs and MSI capability from the function, and has `/sys` report that identity for the function (`drm_device.pci_ident`). `fault` answers at the driver's fault points: `i915_ring_begin` asks `I915_FAULT_SUBMIT` before it takes room, and fails as a wedged GPU refuses work, and `i915_ggtt_insert` asks `I915_FAULT_BIND` before it writes an entry and fails with its error, `-ENOSPC`; `hw.faults` counts the errors injected. `attach` is told of the device once it is registered, `detach` at its unplug and `release` when its record goes: the device owns the backend from its registration, and a bind that fails leaves it to the caller.

Every wait on the chip has a bound in microseconds and a name. It reads at once, then after waits of 1 us doubling to 1 ms, counted by the backend's `delay_us`: the processor's spin on its reference counter on the machine, and the model's clock in a test, so a test of a stuck bit takes no time. A wait at its bound returns `-ETIMEDOUT`, logs its name and what the register read, and leaves the name in `last_timeout`. A wait spins and never sleeps, so its bound is short and a long wait is the caller's sleep between bounded waits.

### Locks

Everything runs under the big kernel lock, as [`../Readme.md`](../Readme.md) says. Beside it the order, outermost first, is a DRM device's `commit_lock`, then the driver's locks of buffers and contexts, which may sleep, then the hardware's: the frequency's lock, `rps.lock`, over RPS's state and its requests, then the register lock of forcewake and of any register the interrupt handler also writes, then the interrupt mask's, all taken with interrupts off and never held across a sleep. The interrupt handler takes only the hardware's locks. The register lock is `uncore.lock`, over forcewake's count, the GT FIFO's and the GTT's flush; the interrupt mask's is `irq.lock`, over the masks, the enables and the table of handlers, which the handler holds while it runs. Each part that adds a lock adds it in this order.

### Forcewake and the GT FIFO

The GT, the render and media engines and their registers, below 0x40000, sleeps in RC6 whenever it is idle, and a register of a sleeping GT reads stale. Forcewake keeps it awake. `i915_uncore_init`, the first of the bind's parts, clears the unclaimed-access bit of `FPGA_DBG` and the GT FIFO's errors in `GTFIFODBG` that the firmware left, and releases every request of `FORCEWAKE_MT`, a masked register, the firmware's among them (Linux's WaRsClearFWBitsAtReset).

The rules, Linux's for Haswell (`fw_domains_get_with_thread_status`):

* A reference is taken with `i915_forcewake_get` and dropped with `i915_forcewake_put`; the count is under the register lock, with interrupts off. Only the first reference touches the chip: it waits up to 50 ms for `FORCEWAKE_ACK_HSW` to drop the last release's acknowledgement, sets the kernel's bit, 0x00010001 in `FORCEWAKE_MT`, waits up to 50 ms for the acknowledgement, and then up to 5 ms for the GT's threads to leave their sleep (WaRsForcewakeWaitTC0). The last put writes 0x00010000 and waits for nothing.
* An acknowledgement that does not come fails the get with `-ETIMEDOUT`, the wait named `forcewake ack clear` or `forcewake ack` in the log and in `hw.last_timeout`; the request is withdrawn and no reference is held, so no caller reads a GT that did not wake. Linux logs the same timeouts and goes on. The threads' wait only counts and logs, as Linux's warning does.
* A caller that makes several accesses to the GT holds a reference across them. `i915_uncore_read` of a GT register without one takes and drops a reference around the read, where Linux keeps it for a further millisecond; a GT register whose forcewake cannot be had reads all ones.
* `i915_uncore_write` below 0x40000 or from 0x116000, Linux's `NEEDS_FORCE_WAKE`, first waits for room in the GT FIFO, as Linux's `gen6_write`; it takes no forcewake, and neither does a read from 0x116000, which Haswell's one forcewake range does not cover.
* A write to a GT register goes through the GT FIFO, which holds writes while the GT wakes and loses one that finds it full. `i915_uncore_write` counts the FIFO's free entries down from what `GTFIFOCTL` last read, and once the count is down to the 20 the FIFO keeps in reserve, reads them again until there are more, waiting up to 10 ms; a wait that reaches its bound is counted and logged and the write goes ahead, as on Linux. Writes need no forcewake.

### The display power well

Haswell has one display power well, which Linux calls "display": it powers pipes B and C, transcoders A to C, the panel fitters and the DDI lanes of ports B to E. Pipe A, the eDP transcoder and port A are outside it, always on. Four registers request it, the BIOS's, the driver's, the KVMR's and the debug register's, each with a request bit (31) and a state bit (30); the well is on while any request is set.

`i915_power_init` makes the BIOS's request the driver's, as Linux's `hsw_power_well_sync_hw`, and takes the reference Linux's `POWER_DOMAIN_INIT` holds until the display is read out: the driver's request set, then the state waited for, 1 ms at most, a timeout named `power well on`. The reference is held for the life of the bind until the display part takes it over. `i915_power_get` and `i915_power_put` count references; the last put clears the driver's request and waits up to 1 ms for the well to go off, unless another request holds it on, which is logged with the requesters, as Linux does. The last put leaves the well on, `kept`, while a part of it runs, which `i915_power_well_in_use` reads: transcoder A, B or C enabled, a panel fitter enabled, pipe B's or C's plane enabled, or the eDP transcoder fed other than from pipe A always on, which passes through pipe A's panel fitter or pipe B or C (Linux's `force_thru`). On the Lenovo the firmware drives the panel from pipe A through the eDP transcoder, always on, so the well is not in use, and Linux turns it off at idle.

### Stolen memory

The firmware takes stolen memory from the top of the memory below 4 GiB for the GPU: its base is BDSM (configuration offset 0x5c) and its size the GMCH control word's GMS field in units of 32 MiB, 64 MiB at 0xaba00000 on the Lenovo, with the GTT's 2 MiB below it. The firmware's framebuffer is its first 4128 KiB.

* At boot, after the kernel and the modules are taken out of the memory map and before the frame allocator is made from it, `platform_memory_reserve` calls `i915_stolen_reserve_early`, which reads 00:02.0's configuration space by mechanism #1 and, for a chip of the driver's ids, takes the stolen memory out of the map, as Linux's early quirk does, so that no frame of it is ever handed out even where the firmware's map offers it. The Lenovo's map reserves 0xab000000 to 0xaf9fffff itself.
* At the bind `i915_stolen_init` finds it again from the words the bind read, and checks that the allocator owns no frame of it and that it lies inside a reserved region the DMAR table names for the GPU, its RMRR, 0xab800000 to 0xaf9fffff on the Lenovo, where the table names one; on x86-64 alone, since only it reads the table. Memory that fails either check is logged and left unused. The part at its top that the firmware keeps, from `GEN6_STOLEN_RESERVED` when its enable is set, 1 MiB or 256 KiB, is kept out of `usable_size`; a part outside the stolen memory refuses it whole, as on Linux.
* As Linux on a chip before graphics version 8, no buffer is made in it while VT-d translates for the GPU (`for_objects` clear, logged `DMAR active`).

### The global GTT

The global GTT maps the GPU's global address space a 4 KiB page an entry. Its entries are BAR 0's second half: the GMCH control word's GGMS field gives their bytes, 2 MiB on the Lenovo, so 524288 entries and 2 GiB of address space. The first `mappable_end` bytes of it are what the processor reaches through the aperture, BAR 2, whose size `i915_ggtt_init` reads from MSAC (configuration offset 0x62: 128, 256 or 512 MiB, 256 on the Lenovo) rather than by sizing the BAR, since the console draws through it.

An entry is Linux's `hsw_pte_encode`: bit 0 valid, bits 31:12 the address's bits 31:12, bits 10:4 its bits 38:32, and the cache bits: none for `I915_CACHE_NONE`, `HSW_WB_LLC_AGE3` (bit 2) for every other level, since the HD 4400 has no eDRAM. Every entry that maps nothing maps the scratch page, a zeroed frame of the allocator's, uncached.

At the bind the firmware's surfaces are found from the hardware: each primary plane enabled, pipe A's always and B's and C's while the well is on, gives its surface's GTT offset in `DSPSURF` and its bytes, the stride times its rows with the plane's offset, whole tile rows of 8 for an X-tiled one. Those ranges are `kept`: the bind leaves their entries as the firmware wrote them, since the plane scans them out and the console draws on the same pages through the aperture at 0xb0000000, and `i915_ggtt_insert` and `i915_ggtt_clear_range` refuse to touch them with `-EBUSY` until the display part takes the plane over. On the Lenovo that is GTT offset 0 to 0x407fff, 1032 entries that map stolen memory from its base. Every other entry is pointed at the scratch page, as Linux's `init_ggtt` clears the holes, and the GTT's cache is flushed. Insert and clear write the entries and then flush the GTT's cache by `GFX_FLSH_CNTL_GEN6` with a posting read, under the register lock; the register write also drains the processor's write-combining buffers, so the chip sees every entry written before it.

### Rings and interrupts

The interrupts come in four banks, each an identity, mask and enable register: the GT's, power management's, the display engine's and the south display's, whose events reach the display engine as its PCH event. A bank's bit is a source. `i915_irq_reset` masks and disables every source and forgets every handler; `i915_irq_install` sets the display engine's master enable, without which no source raises the message, once the message is enabled. A source's owner registers a handler for its bits with `i915_irq_register`, which enables them, so that an event latches in the identity register once the bit is unmasked; `i915_irq_unmask` and `i915_irq_mask` then open and close it, and a bit with no handler is never unmasked. A south display source enables the PCH event with it. The master enable and the PCH event belong to no owner and are refused.

`i915_irq_handle` is the device's interrupt, as Linux's `ilk_irq_handler`: it clears the master enable and the south display's enables, so that an event that comes while it runs raises a new message once they are back; reads each identity register, writes the bits back to acknowledge them and hands them to their handlers, each handler once with all its bits, the GT's first, then the display engine's with the south display's behind the PCH event, then power management's; and restores the enables. It counts the message in `irq.messages`, a message that finds no bit set in `irq.spurious`, and a bit that has no handler in `irq.unclaimed`, which it logs, masks and disables, so that a source the firmware left latched raises it once.

The bind starts the render ring, `rcs0`, and the blitter ring, `bcs0`, which IGT's tests use both, with `i915_gt_init`, under one forcewake reference. Each has a status page, one page, and a ring of 16 KiB, Linux's legacy size, each from the kernel's heap and mapped in the global GTT at the LLC's cache level, as Linux maps its internal objects on an LLC part: the processor writes them through its cache and the chip snoops it. Their GTT space is taken from the top of the GTT down, past the firmware's kept surfaces (`i915_gt_ggtt_take`); on the Lenovo the four take 40 KiB below 2 GiB. Space comes back only when the last taken is given back, and all of it when the rings stop, so a later allocator of the GTT leaves `[gt.ggtt_bottom, total)` alone. Each ring is started as Linux's `xcs_resume`:

* Stopped: `STOP_RING` set in `MI_MODE` and `MODE_IDLE` waited for, 100 ms at most; a timeout is forgiven when the head has reached the tail, as Linux does. Then the head moved to the tail, the ring disabled and the head and tail cleared, twice if the head does not clear.
* Every write of interrupt status into the status page masked (`RING_HWSTAM`), but the render ring's bit 0, which Linux's `set_hwstam` leaves to it, and the ring's interrupts masked (`RING_IMR`); the status page's GTT offset written to its register, `RENDER_HWS_PGA_GEN7` or `BLT_HWS_PGA_GEN7`, and the command streamer's TLB flushed through `RING_INSTPM`, 2 ms at most, a timeout logged.
* `RING_START`, the PPGTT's registers through `i915_ppgtt_enable_ring`, which writes nothing until the aliasing PPGTT exists, an empty ring, and `RING_CTL` with the ring's size and `RING_VALID`, waited for 5 ms at most; a ring whose `RING_VALID` does not stay is dead, and the start fails with `-EIO` and its registers logged. Then `STOP_RING` cleared.

A ring that fails tears every ring down, and the bind goes on without them, logging `i915: rings: not started; the GPU takes no work`. Each ring's user interrupt, `GT_RENDER_USER_INTERRUPT` or `GT_BLT_USER_INTERRUPT`, is then registered, enabled and left masked, so that after the bind the master enable and the two user interrupts are the only enables set and every mask is set.

Commands go into a ring with `i915_ring_begin`, which returns room for an even number of dwords: a command that would cross the ring's end starts again at 0, the end filled with `MI_NOOP`, and a ring without room, 64 bytes always left between the tail and the head, waits up to 10 ms for the chip's head to move, a wait named `ring space`. `i915_ring_advance` orders the writes before the tail's and writes `RING_TAIL`.

A breadcrumb is `MI_STORE_DWORD_INDEX` of the ring's next sequence number into the status page's dword 0x40, Linux's `I915_GEM_HWS_SEQNO`, and `MI_USER_INTERRUPT`; sequence numbers are 32 bits, skip 0, and compare in the order of numbers that wrap. `i915_engine_wait` waits for one with a timeout: the user interrupt is unmasked for the wait, the ring's `RING_IMR` before the GT's mask as Linux's `gen6_irq_enable`, and masked again with the last waiter. A process sleeps on the ring's queue until the interrupt's handler wakes it or its deadline in ticks passes; with no process, as at boot, or no message vector, the wait polls the status page in a bounded wait named `breadcrumb`.

First light, `i915_firstlight`, runs at the bind under `rach2.i915.firstlight`, before any display code: the render ring writes 0x1915f157 with `MI_STORE_DWORD_IMM` to a page mapped in the GTT for it, followed by a breadcrumb, with the user interrupt unmasked; the driver polls for the breadcrumb, 50 ms at most, reads the page back, and then waits up to 10 ms for the interrupt, which counts as come when the handler ran or, with the processor's interrupts off at boot, when it is latched in `GTIIR`. The page is given back whatever the outcome.

### RC6 and the frequency

RC6 powers the GT down while it is idle. `i915_rc6_init` turns off whatever RC6 the firmware left, under forcewake; `i915_rc6_enable` writes Linux's values for Haswell: the wake rate limits, an evaluation interval of 125000 and idle hysteresis of 25, each engine's idle limit of 10, and the thresholds, RC6's 50000 units of 1.28 us, 64 ms, among them; and reads the pcode's RC6 voltages, which Linux corrects only on graphics version 6. Unparked, `GEN6_RC_CONTROL` enables RC6 under the hardware's timers; parked, it enables RC6 alone and `GEN6_RC_STATE` asks for it at once. `i915_rc6_residency_ms` reads `GEN6_GT_GFX_RC6`, a 32-bit count of 1.28 us units, under the register lock, adds its difference from the last read modulo 2^32 to a 64-bit total, so a wrap between reads is counted, and turns the total into microseconds rounded up and then milliseconds rounded to the nearest, as Linux.

The pcode is the chip's power controller, reached through a mailbox: `i915_pcode_read` and `write` find `GEN6_PCODE_MAILBOX` free or fail with `-EAGAIN`, write the data and then the command with `GEN6_PCODE_READY`, and wait up to 20.5 ms for the ready bit to clear, a wait named `pcode mailbox`; the low byte's status maps to an errno as Linux's.

The frequency is a multiple of 50 MHz. `i915_rps_init` reads RP0, RP1 and RPn from `GEN6_RP_STATE_CAP`, RPe from the pcode's duty cycle control (`HSW_PCODE_DYNAMIC_DUTY_CYCLE_CONTROL`, bits 15:8), held between RPn and RP0, or RP1 without the pcode, and the overclocking limit from `GEN6_READ_OC_PARAMS` where its bit 31 is set; the soft limits start at RPn and RP0, boost at the highest frequency allowed. `i915_rps_enable` writes the down timeout and idle hysteresis, turns RPS's hardware on with the busy and idle averages, sets RPn, and writes the ring's frequency table to the pcode, a ring frequency for each GPU frequency from the highest down, as Linux's `gen6_update_ring_freq`. Each request writes `GEN6_RPNSWREQ`, then the thresholds of its power mode, low, between or high, whose up interval is 16, 13 or 10 ms at 95% busy and down interval 32 ms at 85%, the interrupt limits and `GEN6_PMINTRMSK`, so that the chip raises no up interrupt at the top and no down at the bottom.

Unparked, RPS registers its handler for the up threshold, down threshold and down timeout in the power management bank and unmasks them. The handler masks what it took and records it; the work runs from `irq.deferred` once the handler has dropped the interrupt mask's lock, since Rach2 has no workqueue, and moves the frequency as Linux's `rps_work`: an up step that doubles while the GT stays busy, to RP0; on the down timeout to RPe and then RPn; a down step that doubles; each within the soft limits, and unmasks the events again. Park masks and disables the events, clears them, asks for RPn under forcewake, so that the pcode takes it before the GT sleeps, and sets the frequency of the next start a step below the last, the steps doubling at each park, never below RPe; unpark asks for that frequency. `i915_gt_unpark` unparks RC6 and then RPS, and `i915_gt_park` parks RPS and then RC6.

The card's files in /sys are Linux's: `gt_act_freq_mhz`, `gt_cur_freq_mhz`, `gt_boost_freq_mhz`, `gt_max_freq_mhz`, `gt_min_freq_mhz`, `gt_RP0_freq_mhz`, `gt_RP1_freq_mhz` and `gt_RPn_freq_mhz` in cardN, and `rc6_enable` and `rc6_residency_ms` in its `power` directory, made or found; i915(4) gives their values and writes.

### The OpRegion and the video BIOS table

The firmware describes the machine's outputs and panel in the video BIOS table (VBT), which the bind reads after the GTT and before it registers the device, so that the display part finds the ports, the panel and its power sequence already decoded in `i915->vbt`. As Linux's `intel_opregion_setup`, it reads the OpRegion's address from ASLS in the configuration space, maps its 8 KiB uncached, the cache type ACPICA gives the same pages, and refuses it without the signature `IntelGraphicsMem`. It sets CHPD in mailbox 1, since the driver handles hotplug itself, and clears ARDY in mailbox 3, since it answers no ASLE request; mailbox 2, SWSCI, is ignored from version 3. The table is the one RVDA names in mailbox 3, a physical address on version 2.0 and an offset from the OpRegion from 2.1, when it is valid; else mailbox 4's, which runs to mailbox 5, or to the OpRegion's end when there is none. Without either, the option ROM's shadow is searched on 4-byte boundaries for the signature `$VBT`, as Linux's `oprom_get_vbt`, when the chip decoded I/O and memory at boot.

`intel_bios_init` copies the table, checks its header, the BDB's and every block's size against the table's end, and copies each block it decodes into a buffer of the block's size or Linux's structure's, whichever is larger, zero past the block, so that a field a version lacks reads as zero, as Linux's `init_bdb_block`. Fields are read by their byte offsets, not through packed structures, so the same code serves both architectures. The LFP data's pointers, absolute in the table, are made relative to the data block and checked as Linux's `validate_lfp_data_ptrs`: sixteen entries of one size in step, each fp_timing ending in 0xffff; malformed ones are dropped, missing ones from version 155 made up from the data block. Each child device becomes an encoder on the port its DVO port names, and a port's lookup finds its first, as Linux uses the first; a child on DDI A loses DVI, which the port cannot carry. Without a table, or with an invalid one, `init_vbt_missing_defaults` gives each port Linux's defaults: eDP on DDI A, DisplayPort and HDMI on B to D, nothing on E.

The panel is decoded per encoder, as Linux's `intel_bios_init_panel`: its type is the table's when it names one, the EDID's product id matched to an entry's PnP id when the table gives 0xff, and 0 as a last fallback that only the late call allows; the LFP data's mode, the DRRS type, dithering, the backlight's PWM, the eDP block's bits a colour, fast link settings and power sequence, and the power conservation features follow. On the Lenovo the panel is type 2, with a 1024x768 mode at 65 MHz that Linux sets aside for the EDID's 1366x768, static DRRS, 18 bits a pixel and the power sequence 200 ms up, 50 ms down, 500 ms between cycles and 1 and 200 ms around the backlight.

### Binding

`i915_probe` walks the ids and binds function 0 of each match whose BAR 0 is set. The bind reads the board's ids, the GMCH control word and BDSM, which give the GTT's size and the stolen memory; turns on memory decoding and bus mastering; and then, as Linux's `ilk_irq_reset` on Haswell, masks every source, clears every enable, the display engine's master enable among them, and clears every identity register twice: the display engine's, the GT's, power management's and the south display's, with the error, panel self refresh and south error registers. Then it brings up the base, in Linux's order: forcewake, the display power well, stolen memory and the global GTT, as the sections above say; a well that does not come on and stolen memory that fails a check are logged and the bind goes on, and a GTT that cannot come up fails the bind. It then reads the OpRegion and the VBT, as the section on them says. Only then does it take a vector, register its handler and enable the MSI message, so no source the firmware left enabled can raise one, and turn the master enable on; then it turns off the firmware's RC6, reads the frequencies, clearing power management's identity twice more as Linux's `gen6_rps_reset_interrupts`, starts the rings and, under its option, runs first light, and enables RC6 and RPS with the GT parked. Once the device is registered it adds its files in /sys. The vector's handler counts the messages in `irqs` and hands each to `i915_irq_handle`. The DRM device is registered without `DRIVER_MODESET` and `DRIVER_ATOMIC`, as Linux's i915 is on a device without display, so programs see a render device and the console keeps the firmware's framebuffer. A failed registration gives the vector back and restores the command word. The unplug hook turns RPS and RC6 off, masks every source again, gives back the message and its vector, and stops the rings and frees their pages; the release hook gives the scratch page back and frees the record.

### The fake chip

The fake chip, [`i915_fake.c`](i915_fake.c), is a test backend that lets a program in QEMU reach the driver's real paths where no Intel GPU is: Mesa's loader picks Crocus on it, and the driver's interfaces are proved on it; it draws nothing. A function of QEMU's `edu` device stands in for the chip's. Its configuration space answers with the Lenovo's identity, 8086:0a16 revision 0b on a board of 17aa:380c, class 0x030000, a GMCH control word of 2 MiB of GTT and no stolen memory, and an aperture of 256 MiB that nothing backs, and `/sys` reports that identity for the function. Its command word, BARs and MSI capability stay edu's, so the device's message is a real MSI of edu's, which the fake sends by a write to edu's interrupt register at BAR 0 + 0x60, mapped at the attach, while the driver has its message on.

BAR 0's registers are 2 MiB of memory and the GTT's entries the 2 MiB the GMCH control word gives. A register holds what was last written, except where the chip does more, which is what the bind's bounded waits wait for: the masked registers, `FORCEWAKE_MT` and each ring's `MI_MODE`, `INSTPM` and `RING_MODE`, take the bits their high half enables; forcewake's acknowledgement follows the request at once; the GT FIFO always has 64 free entries; a power well's state follows its requests; `INSTPM`'s flush is done when asked; the identity and error registers clear the bits written and the status registers take nothing; and `GEN6_GDRST` resets the rings of the domains it names and reads 0 again. So a bind on the fake reaches its end with no wait at its bound.

A ring runs whenever the driver writes its tail, its control or its `MI_MODE`, while it is valid, not stopped and not hung, and its head reaches its tail before the write returns. Each command is read through the GTT's entries from the memory they map: `MI_STORE_DWORD_IMM`, `MI_STORE_DWORD_INDEX` and the post-sync writes of `MI_FLUSH_DW` and `PIPE_CONTROL` store their values, which is how sequence numbers reach the status page, whichever command a later part's breadcrumb uses; `MI_USER_INTERRUPT` and `PIPE_CONTROL`'s notify raise the ring's user interrupt; `MI_BATCH_BUFFER_START` completes its batch without reading it; every other command of the MI, 2D and 3D types is passed over by its length, `MI_LOAD_REGISTER_IMM`'s by 8 bits and the rest's MI commands by 6; and a command of no known type, or one the GTT maps no memory for, hangs the ring. An event latches in its identity register when its mask lets it through, a user interrupt only when the ring's `RING_IMR` does too, and the device's line, the master enable and any identity bit enabled, raises one message on each rise, as the model's does.

The faults, armed for a count or for always through `dri/N/i915_fake` and each counted and logged when injected: `submit` and `bind` at the driver's fault points; `hang`, which hangs the ring at the next command it would run with its head there, `ACTHD` at it and `IPEHR` its first dword, until a reset of its domain through `GEN6_GDRST`; and `irq`, which loses the next user interrupt, whose breadcrumb is still written. The fake's lock is taken with interrupts off around each access the driver makes, innermost in the driver's order, and the message is sent after it is dropped, so a handler on any processor sees the registers between accesses.

## Limits

* A chip is bound only under `rach2.i915`, until the driver answers Mesa's queries and drives the display; without it a program would find a card of `i915` whose own ioctls all fail.
* None of the driver's own ioctls is served: each answers `EINVAL`, as the DRM core does for a number a driver lacks.
* No program's work yet: no contexts, requests or submission, and only the render and blitter rings; no display or backlight. Nothing yet unparks the GT, so it stays at RPn with RC6 asked for at once; the code that gives it work must call `i915_gt_unpark` and `i915_gt_park` around it. No waitboost, so nothing yet asks for the boost frequency. The global GTT has no allocator but the GT's own from its top, and no part yet turns the display well off, so the VGA register touch Linux makes after turning it on again is not made.
* The boot reserves stolen memory only for the Haswell GT2 ids the driver binds; on another Intel GPU the firmware's memory map alone keeps it from the allocator, which every firmware Linux has met does but the early quirks Linux keeps for older ones.
* Haswell GT1 and GT3 chips, which Linux binds with other device data, are not bound.
* Nothing yet uses the decoded table but the log. The blocks for panel self refresh, SDVO, MIPI DSI and its sequences, compression and the generic DTDs are not decoded, nor the second panel's mode. The OpRegion's ASLE requests, backlight and lid among them, are not answered, its SWSCI calls not made, and so the panel type Linux asks the OpRegion for on a few listed machines is not asked for.
* The fake chip reads no batch and draws nothing, loads no register for `MI_LOAD_REGISTER_IMM`, backs no aperture and has no stolen memory or display; a program that needs pixels from it gets none.

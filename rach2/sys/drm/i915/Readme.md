# i915

`sys/drm/i915/` is the driver of Intel's Haswell graphics with GT2, the HD 4400 of the Lenovo G50-70 (PCI 8086:0a16) among them, after Linux 6.12's i915, whose names, register values and device table it takes. It binds the chip at 00:02.0, masks its interrupts, brings up forcewake, the display power well, stolen memory and the global GTT, enables its MSI message and registers it as the DRM device `i915` ([`../drm.h`](../drm.h)); every access it makes to the chip goes through one hardware boundary, so that a host model and a test backend stand in for the chip. It does not yet render or set modes: the screen stays the firmware's framebuffer and the backlight `intelbl.c`'s ([`../../display/Readme.md`](../../display/Readme.md)). [i915(4)](../../../../man/man4/i915.4) is the interface a program sees.

## Use

The driver binds a chip only when the kernel command line has `rach2.i915` ([cmdline](../../../cmdline.md)). `drm_start` calls `i915_probe` through `arch_drm_probe(ARCH_DRM_NATIVE)`, after bochs and before the firmware framebuffer's driver. A bind on the Lenovo logs:

    i915: stolen: [mem 0xaba00000-0xaf9fffff], N KiB usable, inside the device's reserved region; DMAR active, no buffers in it
    i915: gtt: pipe A's firmware surface at 0x0, 4128 KiB, kept
    i915: gtt: 2048 MiB, 256 MiB of it through the aperture; 523256 entries to the scratch page, 1032 kept
    i915: interrupts: messages on vector N
    i915: found: 00:02.0: haswell/ult (device id 0a16), graphics 7.5, display version 7.00, gt2, revision 0b
    i915: registered: i915 1.6.0 for pci:0000:00:02.0 on card 0

Without the option the probe logs `i915: 00:02.0: 0a16 left to the firmware's framebuffer; rach2.i915 binds it` and touches nothing. Whether or not the option is given, the boot takes the chip's stolen memory out of the memory map before the frame allocator is made, logging `i915: stolen: reserving [mem 0xaba00000-0xaf9fffff], 0 KiB of it usable memory` on the Lenovo, whose firmware's map reserves it already. A wait that reaches its bound logs `i915: NAME: timeout after N us: register 0xR reads 0xV`.

## Interfaces

* [`i915.h`](i915.h) is the contract every file of the directory keeps, in its opening comment, and the driver's device, `struct drm_i915_private`, which embeds its `struct drm_device` and is found from it with `to_i915`, and holds the state of the base: `uncore`, `power`, `stolen` and `ggtt`. The base's calls are declared there by file: `i915_forcewake_get` and `put`, `i915_uncore_read` and `write`; `i915_power_get` and `put`, `i915_power_well_on` and `i915_power_well_in_use`; `i915_stolen_reserve_early`, which `platform_memory_reserve` ([`../../platform.h`](../../platform.h)) calls at boot; and `i915_ggtt_insert`, `i915_ggtt_clear_range`, `i915_ggtt_pte`, `i915_ggtt_pte_encode` and `i915_ggtt_invalidate`. `struct i915_platform` is what Linux's device table says of Haswell GT2 (`hsw_gt2_info`): graphics 7.5, display 7, the four engines, the LLC, RC6 without RC6p, the engine reset and the aliasing PPGTT. `i915_ids` holds Linux's twenty GT2 ids, each with its subplatform, and `i915_id_lookup` finds one. `i915_driver_bind` binds a PCI function whose registers a given `struct i915_hw` reaches: the probe's way after mapping BAR 0, and any other backend's, the host model's among them.
* [`i915_hw.h`](i915_hw.h) is the hardware boundary: `i915_read`, `i915_write`, `i915_posting_read`, `i915_rmw`, `i915_read64_2x32`, `i915_delay_us`, the bounded waits `i915_wait_for` and `i915_wait_until`, `i915_hw_mmio_init`, which makes the backend over BAR 0's registers, and the GTT's entries, `i915_hw_gtt_init`, `i915_gtt_read` and `i915_gtt_write`.
* [`i915_reg.h`](i915_reg.h) has the registers by Linux's names with Haswell's values, in blocks that each name the Linux file they come from: configuration space, BAR 0's layout, uncore and forcewake, interrupts, engines, reset, fences and swizzling, the GTT's entries, RC6 and frequency, power wells, pipes, planes and cursors, DDI and its PLLs, the panel power sequencer and backlight, AUX and GMBUS.
* [`sources.mk`](sources.mk) lists the driver's files for `sys/arch/x86/sources.mk`, since the driver is PC-only.

## Design

### The hardware boundary

The driver reaches its chip only through a `struct i915_hw`: a table of `read32`, `write32`, `delay_us` and `gtt_map` and the backend's own pointer. On the machine the backend is BAR 0's first 2 MiB, the registers, mapped uncached with `map_mmio_typed`, as Linux maps them; the second 2 MiB, the GTT's entries, the backend's `gtt_map` maps write-combining when the global GTT comes up, as Linux does, or uncached on a processor without a page attribute table, so that no page of BAR 0 is mapped with two cache types. A backend without `gtt_map`, such as the model, answers for the entries as registers from 0x200000. In a host test the backend is the model of the HD 4400 (`tests/host/i915_model.c`); any other backend, such as one that completes work at once for tests in QEMU, is a table of the same three calls. An access past the backend's size reads all ones and writes nothing, as a chip that has gone reads.

Every wait on the chip has a bound in microseconds and a name. It reads at once, then after waits of 1 us doubling to 1 ms, counted by the backend's `delay_us`: the processor's spin on its reference counter on the machine, and the model's clock in a test, so a test of a stuck bit takes no time. A wait at its bound returns `-ETIMEDOUT`, logs its name and what the register read, and leaves the name in `last_timeout`. A wait spins and never sleeps, so its bound is short and a long wait is the caller's sleep between bounded waits.

### Locks

Everything runs under the big kernel lock, as [`../Readme.md`](../Readme.md) says. Beside it the order, outermost first, is a DRM device's `commit_lock`, then the driver's locks of buffers and contexts, which may sleep, then the hardware's: the register lock of forcewake and of any register the interrupt handler also writes, then the interrupt mask's, both taken with interrupts off and never held across a sleep. The interrupt handler takes only the hardware's locks. The register lock is `uncore.lock`, over forcewake's count, the GT FIFO's and the GTT's flush; each part that adds a lock adds it in this order.

### Forcewake and the GT FIFO

The GT, the render and media engines and their registers, below 0x40000 and from 0x1c0000, sleeps in RC6 whenever it is idle, and a register of a sleeping GT reads stale. Forcewake keeps it awake. `i915_uncore_init`, the first of the bind's parts, clears the unclaimed-access bit of `FPGA_DBG` and the GT FIFO's errors in `GTFIFODBG` that the firmware left, and releases every request of `FORCEWAKE_MT`, a masked register, the firmware's among them (Linux's WaRsClearFWBitsAtReset).

The rules, Linux's for Haswell (`fw_domains_get_with_thread_status`):

* A reference is taken with `i915_forcewake_get` and dropped with `i915_forcewake_put`; the count is under the register lock, with interrupts off. Only the first reference touches the chip: it waits up to 50 ms for `FORCEWAKE_ACK_HSW` to drop the last release's acknowledgement, sets the kernel's bit, 0x00010001 in `FORCEWAKE_MT`, waits up to 50 ms for the acknowledgement, and then up to 5 ms for the GT's threads to leave their sleep (WaRsForcewakeWaitTC0). The last put writes 0x00010000 and waits for nothing.
* An acknowledgement that does not come fails the get with `-ETIMEDOUT`, the wait named `forcewake ack clear` or `forcewake ack` in the log and in `hw.last_timeout`; the request is withdrawn and no reference is held, so no caller reads a GT that did not wake. Linux logs the same timeouts and goes on. The threads' wait only counts and logs, as Linux's warning does.
* A caller that makes several accesses to the GT holds a reference across them. `i915_uncore_read` of a GT register without one takes and drops a reference around the read, where Linux keeps it for a further millisecond; a GT register whose forcewake cannot be had reads all ones.
* A write to a GT register goes through the GT FIFO, which holds writes while the GT wakes and loses one that finds it full. `i915_uncore_write` counts the FIFO's free entries down from what `GTFIFOCTL` last read, and once the count is down to the 20 the FIFO keeps in reserve, reads them again until there are more, waiting up to 10 ms; a wait that reaches its bound is counted and logged and the write goes ahead, as on Linux. Writes need no forcewake.

### The display power well

Haswell has one display power well, which Linux calls "display": it powers pipes B and C, transcoders A to C, the panel fitters and the DDI lanes of ports B to E. Pipe A, the eDP transcoder and port A are outside it, always on. Four registers request it, the BIOS's, the driver's, the KVMR's and the debug register's, each with a request bit (31) and a state bit (30); the well is on while any request is set.

`i915_power_init` makes the BIOS's request the driver's, as Linux's `hsw_power_well_sync_hw`, and takes the reference Linux's `POWER_DOMAIN_INIT` holds until the display is read out: the driver's request set, then the state waited for, 1 ms at most, a timeout named `power well on`. The reference is held for the life of the bind until the display part takes it over. `i915_power_get` and `i915_power_put` count references; the last put clears the driver's request and waits up to 1 ms for the well to go off, unless another request holds it on, which is logged with the requesters, as Linux does. The last put leaves the well on, `kept`, while a part of it runs, which `i915_power_well_in_use` reads: transcoder A, B or C enabled, a panel fitter enabled, pipe B's or C's plane enabled, or the eDP transcoder fed other than from pipe A always on, which passes through pipe A's panel fitter or pipe B or C (Linux's `force_thru`). On the Lenovo the firmware drives the panel from pipe A through the eDP transcoder, always on, so the well is not in use, and Linux turns it off at idle.

### Stolen memory

The firmware takes stolen memory from the top of the memory below 4 GiB for the GPU: its base is BDSM (configuration offset 0x5c) and its size the GMCH control word's GMS field in units of 32 MiB, 64 MiB at 0xaba00000 on the Lenovo, with the GTT's 2 MiB below it. The firmware's framebuffer is its first 4128 KiB.

* At boot, after the kernel and the modules are taken out of the memory map and before the frame allocator is made from it, `platform_memory_reserve` calls `i915_stolen_reserve_early`, which reads 00:02.0's configuration space by mechanism #1 and, for a chip of the driver's ids, takes the stolen memory out of the map, as Linux's early quirk does, so that no frame of it is ever handed out even where the firmware's map offers it. The Lenovo's map reserves 0xab000000 to 0xaf9fffff itself.
* At the bind `i915_stolen_init` finds it again from the words the bind read, and checks that the allocator owns no frame of it and that it lies inside a reserved region the DMAR table names for the GPU, its RMRR, 0xab800000 to 0xaf9fffff on the Lenovo, where the table names one; on x86-64 alone, since only it reads the table. Memory that fails either check is logged and left unused. The part at its top that the firmware keeps, from `GEN6_STOLEN_RESERVED` when its enable is set, 1 MiB or 256 KiB, is kept out of `usable_size`; a part outside the stolen memory refuses it whole, as on Linux.
* As Linux on a chip before graphics version 8, no buffer is made in it while VT-d translates for the GPU (`for_objects` clear, logged `DMAR active`).

### The global GTT

The global GTT maps the GPU's global address space a 4 KiB page an entry. Its entries are BAR 0's second half: the GMCH control word's GGMS field gives their bytes, 2 MiB on the Lenovo, so 524288 entries and 2 GiB of address space. The first `mappable_end` bytes of it are what the processor reaches through the aperture, BAR 2, whose size `i915_ggtt_init` reads from MSAC (configuration offset 0x62: 128, 256 or 512 MiB, 256 on the Lenovo) rather than by sizing the BAR, since the console draws through it.

An entry is Linux's `hsw_pte_encode`: bit 0 valid, bits 31:12 the address's bits 31:12, bits 10:4 its bits 38:32, and the cache bits: none for `I915_CACHE_NONE`, `HSW_WB_LLC_AGE3` (bit 2) for every other level, since the HD 4400 has no eDRAM. Every entry that maps nothing maps the scratch page, a zeroed frame of the allocator's, uncached.

At the bind the firmware's surfaces are found from the hardware: each primary plane enabled, pipe A's always and B's and C's while the well is on, gives its surface's GTT offset in `DSPSURF` and its bytes, the stride times its rows with the plane's offset, whole tile rows of 8 for an X-tiled one. Those ranges are `kept`: the bind leaves their entries as the firmware wrote them, since the plane scans them out and the console draws on the same pages through the aperture at 0xb0000000, and `i915_ggtt_insert` and `i915_ggtt_clear_range` refuse to touch them with `-EBUSY` until the display part takes the plane over. On the Lenovo that is GTT offset 0 to 0x407fff, 1032 entries that map stolen memory from its base. Every other entry is pointed at the scratch page, as Linux's `init_ggtt` clears the holes, and the GTT's cache is flushed. Insert and clear write the entries and then flush the GTT's cache by `GFX_FLSH_CNTL_GEN6` with a posting read, under the register lock; the register write also drains the processor's write-combining buffers, so the chip sees every entry written before it.

### Binding

`i915_probe` walks the ids and binds function 0 of each match whose BAR 0 is set. The bind reads the board's ids, the GMCH control word and BDSM, which give the GTT's size and the stolen memory; turns on memory decoding and bus mastering; and then, as Linux's `ilk_irq_reset` on Haswell, masks every source, clears every enable, the display engine's master enable among them, and clears every identity register twice: the display engine's, the GT's, power management's and the south display's, with the error, panel self refresh and south error registers. Then it brings up the base, in Linux's order: forcewake, the display power well, stolen memory and the global GTT, as the sections above say; a well that does not come on and stolen memory that fails a check are logged and the bind goes on, and a GTT that cannot come up fails the bind. Only then does it take a vector, register its handler and enable the MSI message, so no source the firmware left enabled can raise one. The handler counts the messages on the device's vector, which nothing raises while every source is masked; the part that unmasks a source handles it there. The DRM device is registered without `DRIVER_MODESET` and `DRIVER_ATOMIC`, as Linux's i915 is on a device without display, so programs see a render device and the console keeps the firmware's framebuffer. A failed registration gives the vector back and restores the command word. The unplug hook masks every source again and gives back the message and its vector; the release hook gives the scratch page back and frees the record.

## Limits

* A chip is bound only under `rach2.i915`, until the driver answers Mesa's queries and drives the display; without it a program would find a card of `i915` whose own ioctls all fail.
* None of the driver's own ioctls is served: each answers `EINVAL`, as the DRM core does for a number a driver lacks.
* No rings, interrupts beyond the mask, display or backlight yet; the global GTT has no allocator, and no part yet turns the display well off, so the VGA register touch Linux makes after turning it on again is not made.
* The boot reserves stolen memory only for the Haswell GT2 ids the driver binds; on another Intel GPU the firmware's memory map alone keeps it from the allocator, which every firmware Linux has met does but the early quirks Linux keeps for older ones.
* Haswell GT1 and GT3 chips, which Linux binds with other device data, are not bound.

## Tests

* `tests/host/i915_pci_hosttest.c` binds the driver to the host model of the Lenovo's HD 4400 and probes a bus that holds the chip: the ids against Linux's, the gate, the register mapping and the GTT's, the order of the interrupt masks, the base and the message, the configuration words, the DRM identity, the refusals, a failed registration, the unplug, and the boundary's bounded waits on the model's clock.
* `tests/host/i915_base_hosttest.c` brings the base up on the model: forcewake's handshake and count, a slow acknowledgement and a stuck one that fails by name, the GT FIFO's reserve; the power well taken over, turned off, kept on for each way a pipe may need it, held on by the KVMR, slow and stuck; stolen memory reserved from a boot map that offers it and from the Lenovo's, found with the Lenovo's values and refused by each check; and the GTT's sizes, its entries' format, the firmware's 1032 entries left as they were, the rest on the scratch page, and insert and clear with their refusals.
* `tests/host/i915_model.c` is the model: BAR 0 as a register file, the configuration space of `tests/host/i915_lenovo.h`, a clock that moves only when the driver waits, a log of every access, and a table of blocks. Each later part of the driver that needs behaviour of the chip adds a block in a file of its own, which `i915_model.c` includes and lists in its table, so that parts written at once never edit one model file. `tests/host/i915_model_base.c` has the base's: forcewake's acknowledgement, the GT FIFO's free entries and the power well's state, each after a delay a test sets or never, and the firmware's GTT entries and pipe A's plane as the Lenovo boots.

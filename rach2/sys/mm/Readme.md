# Memory management

The memory subsystem accounts for the physical memory the firmware's map describes and manages every frame of it, keeps the kernel's own virtual layout above user space with a heap that frees, and keeps per-process page tables, virtual memory areas (VMAs), copy-on-write fork, demand paging, checked user access, and the disk page cache. Pages are 4 KiB.

## Physical memory

`frame.c` builds the map of physical memory from the boot record's memory map (`sys/boot.h`), in 64-bit arithmetic: the ranges the map calls available, less every range of another type where it overlaps one, sorted and merged, with the part at or above the architecture's reach (`mmu_phys_reach`) counted apart as unreachable, since the kernel addresses nothing there. The reach is 4 GiB on i686, whose physical addresses without PAE are 32 bits, and on x86-64 the 64 TiB of the direct map, which so takes every usable range the firmware reports, or 64 GiB on a processor without 1 GiB pages, where each GiB of the direct map is a page directory of 2 MiB pages that the boot carves below 32 MiB. It falls back to `mem_upper` as one range from 1 MiB when no usable map is present. The map keeps `FRAME_MAP_RANGES` ranges, the record's `BOOT_MMAP_MAX` entries and one more for each module and for the frame table: a list built from n entries has at most n ranges, since a usable entry adds at most one and an entry of another type splits at most one, and each reservation after the build splits at most one more, so every map the record can hold fits; a UEFI map, which lists the firmware's boot-time and runtime regions one by one, runs to a hundred entries where a BIOS map has a score. The boot reserves the kernel image with the boot data below it and the modules, `init_paging` reserves everything below the allocator's break, the tables it carved included, and the boot reports four numbers: usable, the available bytes below the reach; unreachable, the available bytes at or above it; reserved, what the boot took of the usable ranges; managed, the whole frames the table offers above the break, which is usable less reserved within the partial frames at the ranges' ends. The map is printed entry by entry before them. A machine with less than `FRAME_MIN_MANAGED_KIB`, 1 MiB, left as managed memory is refused there by name, `memory: refused: N KiB managed after the kernel's reservations, at least 1024 KiB needed`, and the kernel stops; one too small to hold the frame table past the kernel and its modules is refused in `init_paging` the same way, `memory: refused: the frame table needs memory past what the map offers after the kernel's reservations`, and on x86-64, whose boot carves its page tables before it places the table, one whose break lies past its memory is refused when the first table would be carved there, `memory: refused: the kernel's page tables need memory past what the map offers after the kernel's reservations`; below that it faulted in whatever first took a frame, and the recovery image on 12 MiB, with 3016 KiB managed, is the smallest boot known to work; on 10 MiB it leaves 968 KiB and is refused. `frame_hosttest` builds the map, with i686's reach, from QEMU's maps at five sizes, from the Lenovo G50-70's map as its boot of 2026-09-12 printed it, held to the four numbers it printed, and from synthetic ones with holes, overlaps, a range crossing 4 GiB and a wrapping length; and with x86-64's, from QEMU's maps at 6 GiB and 8 GiB, the Lenovo's, a range past 64 TiB, a map of the record's 256 entries shaped as a UEFI firmware gives one, with the boot's reservations on it, and the bound `FRAME_MAP_RANGES` is sized for, and it places the frame table. `tests/run memory` boots the kernel at 64 MiB, 512 MiB, 2 GiB, 3 GiB and 4 GiB and holds the four numbers to the map and to the size given, and boots the recovery pair at 8 MiB and requires the refusal with no fault; `tests/run bigmem` boots x86-64 at 8 GiB and requires all of it usable.

The window `[0, HARD_MEMORY_LIMIT)`, 32 MiB of physical memory, has the kernel image with the boot stack, the boot data, the page tables the boot carves and the DMA buffers a device is given a physical address of. The shared code reaches a physical address there through `phys_to_virt` and gives a device the physical address of such a buffer through `virt_to_phys` (`arch/arch.h`): on i686 the kernel identity-maps the window as supervisor-writable pages, so both are the identity; on x86-64 every physical address is reached through the direct map at `KVA_DIRECT`, in the largest pages the processor has, and the image through its link at `KVA_IMAGE`, and the two subtract their base. `paging_virt_to_phys`, the architecture's walk of the kernel's tables, gives the physical address of any other kernel page, the heap's among them, and on x86-64 sees through the direct map's large pages. One page of the window is left unmapped once paging is on: the page of the kernel image below the boot stack, its guard (the architecture's `loader.s`), which no allocator gives since the image's frames are reserved. Nothing above the window is reached through its physical address on i686. The frame table has one 32-bit word per frame below the map's top: 0 for a free frame, a reference count for a used one, and a state above `FRAME_REF_MAX` for a frame the map does not offer. The architecture places it (`mmu_frame_table`), and its frames are reserved in the map: on i686 it is carved at the boot allocator's break, below the window, where the kernel reaches it before paging is on; on x86-64 the boot builds and loads the direct map first and puts the table at the top of the highest usable range above the window that holds it, 4 MiB for each 4 GiB of memory, so the window keeps its room for the DMA pool whatever the machine has, and a machine with no room above the window has it at the break. The frame counts, `frame_total_count` and `frame_free_count`, are `size_t`, as wide as the frame numbers. `alloc_frame` and `alloc_user_page` take a free frame from anywhere the map offers, above 4 GiB as well on x86-64, from a hint that no frame below it is free, and a user frame is zeroed, copied for copy-on-write, and filled by the loader through a temporary mapping (`kmap_temp`, `paging_zero_frame`, `paging_copy_frame`), never through its physical address; a caller may sleep holding a temporary mapping, since each slot is its own. On i686 a released slot stays mapped until no slot is free; then every released slot is unmapped at once and every processor drops its translations, one change of kernel mappings for up to 1024 releases where unmapping each would make one for each, as Linux's `kmap` does with its pool. `alloc_kernel_frame` takes a frame of the DMA pool, the window, and returns the kernel's address of it: a frame below 4 GiB on every architecture, so a device takes `virt_to_phys` of it in a 32-bit register. The page cache, the block layer's one-page requests, the e1000's rings and buffers and the USB device and hub records come from it; the other drivers' rings and buffers are static, in the image, which lies in the window too.

The kernel's virtual layout on i686 is the gigabyte from `0xC0000000`, whose 256 page tables exist at boot and are shared by every page directory, so a mapping made there after the first fork is seen by every process: the heap at `0xC0000000`, 256 MiB, the whole region; the page-cache window at `0xD0000000`, 512 MiB; the MMIO region at `0xF0000000`, 128 MiB, into which `map_mmio` maps a controller's registers uncached wherever they are and returns the virtual address the driver then uses; the temporary mappings at `0xF8000000`, 1024 pages, through which a frame above the window is zeroed, copied or filled (`kmap_temp`), and which x86-64 does not have, since its direct map reaches every frame and `kmap_temp` returns the frame's address there; and the module region at `0xF8400000`, 64 MiB, into which the boot maps every module wherever the loader put it, so a module above the window is read like any other and `modlayout` no longer refuses one. x86-64's layout, the upper half of the address space from the direct map at `0xFFFF800000000000` to the image at `0xFFFFFFFF80000000`, has the same regions, each with PML4 entries of its own made at boot, and is described in `arch/x86_64/cpu.h`; its heap's region at `0xFFFFC00000000000` is the 512 GiB of its PML4 entry. The heap is given a part of its region at boot (`kheap_size_for`): an eighth of the memory the frame allocator manages, in grains of 4 MiB, 256 MiB at the least and at most the region, so 256 MiB on i686 whatever its memory, and on x86-64 256 MiB up to 2 GiB of memory, 1020 MiB for QEMU's 8 GiB and the region's whole 512 GiB from 4 TiB; `kheap_init` makes the page tables of that part, from frames anywhere once the allocator is counted, and the map of its pages, a bit each, is in the image for a heap of 256 MiB and in the heap's own first pages for a larger one, a frame for each 128 MiB. The heap (`kheap.c`) allocates and frees objects of any size: an object of at most 2048 bytes from a page carved into blocks of one size class, a larger one as whole pages, each page grown by a frame from anywhere and each page starting with a header that `kfree` finds at the pointer's page base; `kheap_class` gives a class's block size, its blocks to a page, the blocks in use and the pages carved, which `/proc/slabinfo` reports. The buffer cache's pages (`kalloc_cache_page`) are taken from the top of the heap down and every other allocation from the bottom up, the lowest run that fits, as Linux keeps reclaimable pages apart from the rest: the cache holds up to half the heap a page at a time and gives its pages back in any order, and its holes then lie among its own pages, so a pipe's buffer or a socket's ring of 17 pages is found after the cache has filled. The top 16 MiB of the heap is a reserve of sixteen runs of 256 pages that allocations under 64 pages never enter, from which a run of 64 pages to a megabyte comes when the rest of the heap has no such run. `kalloc_guarded` gives a run of pages with the page below it marked taken and never mapped, a guard that no other allocation is given and that takes no frame, and `kfree_guarded` gives back both and refuses pages with no guard below them. A process's kernel stack, 16 KiB, comes that way (`kstack_alloc`), so a thread that runs its stack past the base faults on the guard at once instead of writing over the heap page below; the kernel Readme says how that fault ends. Page tables and directories come, once the heap exists, from it on i686, their physical addresses from the kernel directory's own mapping (`paging_virt_to_phys`), and from frames anywhere on x86-64, reached through the direct map, and a process record keeps its directory's pointer, since the physical address in `cr3` says nothing about where the kernel reads it. `rach2.framefail` is a test switch: a count written to `/dev/framefail` makes the count-th frame allocation inside a system call fail as a full machine's would, and `memprobe fail` sweeps the count over `fork` and `execve` and requires ENOMEM, no leak and no change to what survived. `rach2.framehigh` is another: the frame allocator's scan starts at 4 GiB, so on a machine with memory there the heap's pages, and the buffers of more than a page a disk driver is given from them, lie above it, and the frames between the window and 4 GiB are taken once those above are gone. `mem_reserve` is the kernel's monotonic boot allocator, and `mem_reserve_ptr` gives the kernel's address of what it reserves, `phys_to_virt` of it. Its initial break is the greater of `_end` and the highest end of a Multiboot module wholly within the 32 MiB identity-mapped window. Modules ending above that window do not advance the break; their frames are reserved separately and their contents mapped into the module region. It skips frames already allocated after paging starts and fails before crossing the memory limit.

Before reserving module memory, `modlayout.c` rejects an empty or backwards range, a module that ends past addressable memory, a module overlapping the kernel, or two overlapping modules. The rejection includes the module number and physical range.

`alloc_frame` and `alloc_user_page` search above the 32 MiB window first, then below it only while more than sixty-four frames remain free there. The last sixty-four are kept for block requests and the page cache, which use `alloc_kernel_frame` to take frames from the window's top downward; devices need buffers below 4 GiB whose physical addresses the kernel knows. The allocator maintains free-frame counts as frames are taken and returned. For a process whose effective uid is not 0, `alloc_frame` and `alloc_user_page` refuse a frame when the total free count is at or below the reserve, one thirty-second of managed memory. A user-page refusal reports `user page: refused: the free frames are the reserve's`, followed by the pid. Root, hardware interrupt handlers, and the kernel outside any process may allocate from the reserve. When no eligible frame remains, the user-page allocator reports the boot reservations, kernel and user frame counts, shared frames, and the requesting pid; this report can occur while the last sixty-four window frames are still free. User frames return to the pool when their reference count reaches zero; page directories and private page tables return to the kernel heap. The frame table, its counts and its hints are under the frame allocator's spinlock, and the heap's region, runs and free lists under the heap's, each taken with interrupts off and after the big lock (`proc/smp.h`); a frame taken for a heap page is taken under the heap's lock, so the heap's comes first, and nothing under either takes the other's again.

`mem_cache_target` defines a combined cache target of one quarter of managed memory. The buffer cache uses half that target as its capacity, at most half the heap's pages, since each buffer is a page of the heap, and at least sixteen buffers, and allocates each buffer's data frame when needed. The page cache also uses half the target as its capacity, with a minimum of one frame and a maximum of its 2048 slots, and allocates frames on demand. When the free count falls below one sixteenth of managed memory, `mem_balance` calls `mem_reclaim`, which reclaims buffers first and page-cache frames second until the free count reaches one eighth or neither cache can release more. Each cache reclaims empty or clean entries before writing dirty entries back; entries in use or whose writeback fails remain cached. Reclaim may sleep, so it runs from `fork`, `execve`, `mmap`, `brk`, and the resolution of a user page that needs a frame or a copy, a kernel prefault and a `paging_access` write included, before the resolution reads the region and the page table entry it works on. It does not run from hardware interrupt handlers or the frame allocators. A failed allocation in `fork` returns `ENOMEM`. `mmap` returns `ENOMEM` when it cannot establish a region, and a failed `brk` leaves the break unchanged; both allocate user frames later, so success does not guarantee that a later page fault can be backed. An unresolved user-mode fault sends the thread `SIGSEGV` (`signal_force`): a handler the program installed runs, and otherwise, with the signal ignored or blocked too, the process ends; a fault the frame allocator refused a frame (`frame_refused`) ends the process with `SIGKILL` instead, as Linux's OOM killer does, since a handler that returned would fault again; failure to prefault a user buffer returns `EFAULT`. There is no swap.

## Page tables and address spaces

`init_paging` creates the kernel page directory, enables paging and CR0.WP, and registers the vector 14 handler. CR0.WP makes supervisor writes honor read-only PTEs, which the page cache uses to detect its first write to a clean page.

An address space (`mm.c`) is a page directory with its regions and two counts, as Linux's `mm_struct` has `mm_users` and `mm_count`. Its users are the threads that run in it, an `execve` that builds it, and a call that reads or writes the pages of another process for the length of the call; its holds are the users, together as one, and each `/proc/PID/mem` descriptor, which keeps the record and nothing of the memory. `fork` gives the child a copy-on-write copy; `vfork`, and `clone` with `CLONE_VM`, give it the parent's own address space and one more user. `execve` builds a new one and drops its user's count of the old, and a thread's end drops its own before its death is published (`proc_exit_cleanup`), as Linux's `exit_mm` does, so a process that has ended has no address space while it waits to be reaped. The last user's put frees the pages, the page tables, the directory and the regions, and the last hold the record. A read or a write through a `/proc/PID/mem` descriptor takes a user's count for its length only while a user remains (`mm_get_live`), so the pages of a process that has ended or executed another program go at once, whatever descriptors hold them. `mm_drop` loads the kernel directory first when the address space it frees is the one in CR3. A switch to a thread with no address space, an idle task or a kernel thread, loads no directory and runs in the one loaded, whose kernel half is every directory's, as Linux's lazy TLB mode does: a process that blocks and wakes on the same processor finds its directory loaded, and the two loads of CR3 and their flushes are spared. So another processor may still translate through a directory no thread uses, and the last user's put has each such processor load the kernel's first (`smp_space_release`, `proc/smp.c`), by the interrupt that shoots down translations. A shootdown of one of its pages passes such a processor by and marks the directory stale there, and the switch to one of its threads loads it again, so an idle processor is not woken for each page a process changes after it ran there. A process record keeps the directory and its physical address beside the pointer, since `switch.s` reads them. The address space also keeps the dumpable flag of `prctl(2)`, as Linux keeps it, so every thread that shares it has one flag: a new address space and the image `execve` builds are dumpable unless the image runs with ids its caller lacks, `fork`'s copy takes the parent's flag, and a move of any sharer's effective ids clears it.

An address space keeps its program's file, as Linux's `mm->exe_file`: a description of the file that opens nothing, as an `O_PATH` open makes one (`fs_exe_open` in `syscall_fs.c`), which holds the node and counts on the mount, so a volume is busy while a program on it runs. `execve` makes the new address space first and gives it the file while the walk that found the program still holds the mount's lock; for a script the file is the interpreter's, as on Linux. `fork`'s copy shares the description, and the last user's put lets go of it. Every address space that keeps a file is on one list, whoever has it: a process, an `execve` that has not committed, or a call that works on another process's pages. On the KRFFS root the list counts among the holders of the file's node (`mm_exe_holds`, read by `fd_node_holders`), so an unlink or a rename over the program leaves its node without a name until the last address space that keeps it goes, and a relocation moves the description's node as it moves a descriptor's (`fd_ofd_repoint`). The release takes the lock the file system asks for while the address space is still on the list (`fs_exe_lock`), for a file of the KRFFS root the root's namespace lock, which an unlink and a rename of a file hold while they count its holders and an allocation of an extent holds; it then takes the address space off the list and frees a nameless node, under that lock, only when no other holder is left. So no count of the file's holders runs between the address space's leaving and the release, and no allocation takes the extent while the reclaim sleeps in the page cache.

A process page directory initially copies the kernel directory's PDEs. The referenced kernel page tables remain shared, while a user mapping first copies or allocates the page table for that process. A context switch loads the process's directory into CR3. Kernel page tables needed by every process, including the page-cache window, must exist before the first directory is cloned.

User addresses run from `USER_ADDR_MIN` through, but not including, `USER_ADDR_MAX`, the architecture's (`arch/arch.h`): `0x02000000` and `0xC0000000` on i686. `map_mmio` maps device registers uncached into the dedicated kernel MMIO region at `0xF0000000` and returns the virtual address the driver must use; `map_mmio_typed` maps with other cache bits, which the framebuffer console uses for write-combining (`PTE_WC`). A region reaching the top of the address space is refused, its pages counted by division rather than by adding a page less one, and `premap_kernel_window` refuses a window past the top and counts its tables rather than walking to an end address that would wrap; `paging_hosttest` tests both, compiling `paging.c` and the i686's `mmu.c` natively with 32-bit pointer types and its own processor primitives. Creation of a shared kernel PDE fails after the first process directory has been cloned.

## Virtual memory areas

Each address space, the `struct mm` that the threads of a process share and a `vfork` child shares with its parent, contains a `vm_space_t` whose VMA array is allocated from the heap, so a `munmap` by one thread changes the regions every sharer uses, and the limit below is the shared space's. The array starts with 16 entries and doubles as it fills, up to 65536, a limit that serves the same purpose as Linux's `max_map_count`: a mapping that needs another VMA is refused. The array is kept sorted by address, a lookup is a binary search, and neighbours of the same type and protection merge; two that map a file merge only where its pages continue. A VMA that maps a file holds a reference to a `struct vm_file`, whose owner keeps the file open, and the page of the file at its start, which splits and trims carry on. The last reference to go does not release the file: it leaves it on a list that `vm_file_reap` empties, and `munmap`, `mmap`, `mremap` and `brk` call that at their end, once the regions they changed and the page tables agree, as does the last drop of an address space. A release may sleep closing the file, and a region still in the array during that sleep would be copied by a fork, or reached by a fault, after the file had gone. A VMA is a half-open, page-aligned range with `VM_PROT_READ`, `VM_PROT_WRITE`, and `VM_PROT_EXEC` bits and one of these types:

* `VM_CODE` and `VM_DATA` describe loaded ELF segments.
* `VM_HEAP` describes the non-empty part of the `brk` heap, one VMA or several when `mprotect` has divided it.
* `VM_STACK` starts with the pages the arguments and environment took, one at least, and may grow downward to `stack_limit`, which `execve` sets from the soft `RLIMIT_STACK` in force at the exec so that the whole stack is at most that size in whole pages, never below `USER_MMAP_BASE`, and never short of the pages the arguments took. The first image gets 8 MiB, the default.
* `VM_ANON` describes an anonymous `mmap2` allocation.
* `VM_FILE` describes a private mapping of a file.
* `VM_SHARED` describes a shared mapping: of a file in memory (tmpfs), of a file on ext2, or of shared anonymous memory. Its pages are the frames of the file's `struct shmem` (`shmem.c`) or of the anonymous memory's own, so every mapping of a page maps one frame. A file on ext2 has a `struct shmem` of its own while shared mappings map it (`struct dshare` in `filemap.c`), found by its mount and inode number, which on ext2 names one file for as long as anything holds it; the other disk types derive theirs from names, so a writable shared mapping of their files is refused. A page is read from the file at its first touch, which may sleep, so `shared_fault` holds the file across the read and looks the region up again after it, as `file_fault` does. The pages are written back to the file at `msync`, with the file system's fsync after them under `MS_SYNC`, at `fsync` and `sync`, when a mapping through a descriptor open for writing goes, and before a `read` of the bytes they hold, and the bytes a `write` puts in the file are copied into them. A write-back takes a mapping that may write the file, never one whose last reference has gone, and holds it and the pages across the writes; each page is written under the mount's namespace lock, from before the file's size is read to the end of the write, so a truncation runs wholly before or after it and the write never reaches past the size. Every page in memory is written back whole, up to the file's size, since the kernel does not read the page tables' dirty bits, and never past it, so a store past the end of the file is lost where Linux sends `SIGBUS`. A file a loop device stands on is neither mapped shared through a descriptor open for writing nor written back, and `loop_attach` refuses a file whose pages shared mappings hold. A `write` to such a file holds the namespace lock from before the write to the end of the copy into the pages, so no write-back comes between them; `MS_SYNC` runs the fsync through any mapping of the file, a read-only one too, since a writable mapping gone since may have left blocks to put out. A page that fails to go back when the last mapping goes is lost, with a line in the kernel's log. A truncation of a file in memory takes the pages past its new end out of every VMA that maps them, in every address space (`filemap_shmem_cut`), before it frees them, so a later touch maps the page the file has then and a write to the file after it grows again is seen through the mapping. The pages end at `SHMEM_MAX_SIZE`, 16 TiB less a page, the most a 32-bit page index reaches, and a mapping of a tmpfs file has only the pages its size reaches, as on Linux, which sends `SIGBUS` for a page wholly past a file's end: a page past either is never backed, and its fault is unresolved. The table is a directory of leaves of 1024 frames, made as pages in their spans are, and counts the frames it holds against a tmpfs mount's limit (`struct shmem_quota`), when the memory is a tmpfs file's.

`execve` builds the new image in a new address space while the old one still runs. It loads ELF pages eagerly, a position-independent program at `ELF_ET_DYN_BASE` and the interpreter a `PT_INTERP` segment names just below `USER_MMAP_BASE`, then creates one VMA per loadable segment of each with the segment's permissions. It records an empty heap at the program's end, maps the initial stack's top page at `USER_STACK_BASE` and as many pages below it as the arguments and environment take, and places anonymous mappings below the interpreter, under `USER_MMAP_BASE`. The three are the architecture's: `0x08000000`, `0xBFFFF000` and `0xB0000000` on i686. The words of the initial stack, argc, the argument and environment pointers and the auxiliary vector, are a pointer's width. The heap receives a VMA on its first non-empty growth. Only when all of it is built does the process switch to the new address space. `fork` copies the complete `vm_space_t`.

The syscall contracts are:

* `brk` (45) grows or shrinks the heap range. Growth adds a read-write `VM_HEAP` region above the old top, which merges with a read-write top piece, and reserves virtual addresses only; pages are allocated on first access. Shrinking removes the range above the new top and releases its present frames. A collision or out-of-range request returns the old break.
* `mmap2` (192) takes one of `MAP_SHARED`, `MAP_PRIVATE` and `MAP_SHARED_VALIDATE`, and maps private anonymous memory (`MAP_ANONYMOUS`, or `/dev/zero`, with `MAP_PRIVATE`), shared anonymous memory (either with `MAP_SHARED`), a private mapping of a file from the page offset in EBP, a shared mapping of a tmpfs file (`mmap_backing`), or a shared mapping of `/dev/mem` (`mmap_devmem`): a region marked `VM_PROT_IO` whose pages are the physical frames, mapped uncached when it is made, of the first megabyte or not the allocator's (`paging_frame_is_device`), each taking a reference that only a counted frame keeps; a fault never backs a page of it, `paging_access` and a core file do not read it, it does not grow, and `madvise` does not let its pages go. Anonymous memory ignores the offset and has its pages from its own first; an offset whose last page would not fit in 32 bits is refused with `EOVERFLOW` whatever is mapped, as in Linux. The mapping holds its file through `filemap.c`, a copy of the descriptor with its open file description, so the descriptor may be closed after the call. The copy keeps the KRFFS node the file was opened on, which a relocation of the file leaves behind, so the mapping finds its file through the node of the description, which `vfs_repoint` moves: the check that keeps an unlinked file's extent while something holds it (`filemap_holds`) and the release of the mapping's hold find the file where it is now. The release of a mapping of a file of the KRFFS root takes the root's namespace lock before the mapping leaves the list `filemap_holds` reads, and frees a file that lost its name under it when nothing else holds it, as a close of the file's last descriptor does. A shared mapping of a file on ext2 maps the file's pages in memory when its descriptor is open for writing or another shared mapping has them already; a read-only one through a descriptor not open for writing is otherwise served as a private one, which reads the same bytes, as is a read-only shared mapping of a file of another disk type, which is given `VM_PROT_NOWRITE` whatever its descriptor allows, and a writable one of such a file is refused with `ENODEV`. A file on a device that a user page fault cannot read is refused with `ENODEV` (`mmap_fault_readable`). The fault reads with interrupts off and outside any call, where the block layer polls a disk that allows it and stops the machine at any other device: a loop device, which sleeps its caller, or a USB stick, which answers only through its interrupts. `MAP_FIXED` replaces what its range held; what is mapped is found and the entries the change needs are made room for before the old mapping goes, so a refusal leaves it; `MAP_FIXED_NOREPLACE` refuses a range in use with `EEXIST`. Otherwise a page-aligned hint whose range is free below the stack limit is used, and without one `vm_find_free` takes the highest free range below `USER_MMAP_BASE` and above the heap's top, so a range `munmap` freed is used again. What is mapped is found first, since finding it may sleep, and the range after (`mmap_place`), so that nothing sleeps between the checks on the range and the insertion: a thread that shares the address space cannot map the range in between.
* `munmap` (91) removes full VMAs, trims either end, or splits a VMA, then releases every present frame in the range. A never-faulted page has no frame to release.
* `mprotect` (125) requires a page-aligned address and a range that VMAs cover without a gap (`ENOMEM` otherwise). A region that may never be written has `VM_PROT_NOWRITE` beside its protection: a shared mapping of a file whose descriptor was not open for writing. Write asked of a range that reaches such a region is `EACCES`, as Linux answers for a mapping without `VM_MAYWRITE`; the range is checked for both refusals before anything changes. The bit stays through the splits, merges, copies and moves that carry the rest of the protection. `vm_protect` splits the VMAs at the range's ends, sets the new protection and merges the pieces with matching neighbours; `paging_protect_range` then changes the resident pages. It and the other walks of a range, `unmap_user_range`, `paging_move_range`, the copy a fork makes and the resident count, step past the page tables the range lacks (`user_span` in `paging.c`, after `mmu_user_skip`), so a region of terabytes with few pages costs a few steps. A page made inaccessible stays present with its frame, supervisor-only and marked `PTE_NONE`, so fork and teardown still own it. A page made writable gets the write bit only when this process alone holds its frame, and becomes copy-on-write otherwise; a page of a `VM_SHARED` region gets it in place, since its frame is shared on purpose.
* `mremap` (163) resizes a mapping whose old range lies in one VMA: a shrink cuts its end, a growth takes the free range after it, and with `MREMAP_MAYMOVE` the mapping moves to a free range, or with `MREMAP_FIXED` to the address given; `paging_move_range` moves its page-table entries, frames and flags as they are, and the new VMA maps the same pages of the same file. The two lengths are checked as they are given, before they are rounded up to pages (`remap_args_valid`): the old range must end inside user space and the new length fit in it, so neither range can wrap past the end of the address space. A growth of a file's mapping whose last page of the file would not fit in 32 bits is `EINVAL`.
* `madvise` (219) with `MADV_DONTNEED` or `MADV_FREE` releases the range's resident frames; a later access backs the page again as a first access does. Other advice is accepted and ignored, but `MADV_REMOVE` and `MADV_HWPOISON`.
* `msync` (144) checks its arguments, then writes back the pages of each shared mapping of a file on ext2 its range reaches, the file's whole, at once under `MS_ASYNC` too, and under `MS_SYNC` runs the file system's fsync of the file after them; it returns `EIO` when a write or the fsync failed. A shared mapping of a file in memory maps the file's pages themselves, and a private one has nothing to write.

`madvise` and `msync` judge the length as it is given, before rounding it up to pages: a range that runs past user space is `EINVAL`, a length within a page of 4 GiB among them, which rounds up to 0 and would pass for an empty range.

VMA allocation does not reserve physical frames. If a later user fault cannot allocate a frame, the process is killed with `SIGKILL`. A kernel prefault reports failure to its caller instead.

## Page faults

The vector 14 handler reads CR2 and the x86 error code, then handles these cases in order:

1. A user-range fault for a live process calls `vm_resolve` for an existing VMA or legal stack growth, but an instruction fetch (`FAULT_EXEC`) from a page of no region with `VM_PROT_EXEC`, which no resolution makes legal: the page is present and readable, and the fetch would fault again for ever.
2. A supervisor fault inside the backed page-cache window calls `pc_fault`.
3. A user-range fault whose resolution the frame allocator refused a frame ends the process with `SIGKILL`.
4. Any remaining user-mode fault sends the thread `SIGSEGV`, which a handler may catch; without one the process ends, and a real init's death halts the kernel.
5. Any remaining supervisor fault panics the kernel. One in the guard page below the running thread's kernel stack is that stack running out, and the panic says so: `page fault: a kernel stack ran out`. Most overruns never reach this handler, since its frame would be pushed into the same guard; the processor raises a double fault instead, which the kernel Readme describes.

`vm_resolve` checks the VMA permissions first, so a write to a present copy-on-write page reaches `cow_fault` only when its VMA is writable; a VMA `mprotect` made read-only keeps its shared pages read-only. A new heap, stack, or anonymous page receives a frame zeroed before it is mapped, and a copy-on-write fault copies the page into a new frame before it maps that, so a thread on another processor, which runs in user mode without the big lock, never sees a frame before it is ready. A page of a VMA that maps a file privately is read from the file into a frame, which is mapped once it is full, writable when the VMA is; a store changes the frame and never the file. A page of a `VM_SHARED` VMA is the shared frame itself (`shared_fault`), mapped writable when the VMA is. The read may sleep. The file is held from before it, so a thread that unmaps the VMA meanwhile cannot free the file under the read, and the VMA is looked up again after it: a page backed meanwhile, or a VMA that changed in any way, its protection included, leaves the frame unused, and the resolution runs again against what is there now (`vm_resolve_once`). A resolution that succeeds has left the page present and allowing the access, and `paging_access`, which may sleep in one, looks the VMA and the page up again before it reads or writes the frame. A read-only VMA remains read-only in its PTE, and a VMA without `VM_PROT_EXEC` has its pages no-execute (`PTE_NOEXEC`, NX on x86-64 where the processor has it, nothing on i686, whose pages without PAE are always executable): the loader's pages of a segment without `PF_X`, unless a segment with it shares the page, the stack's, a fault's new page, a file's page and a copy-on-write copy, and `mprotect` sets and clears the bit with the rest of the protection. A write prefault of a present COW page makes the page private before kernel code writes through the pointer. A present page that cannot satisfy the requested access is rejected instead of retrying the same instruction.

Stack growth extends the stack VMA down to the faulting page when the page is at or above `stack_limit`. Growth fails if it would cross another VMA. Pages between the old and new start remain unallocated until touched.

## Copy-on-write fork

`fork` maps each present user frame into the child, walking the parent's regions and, in each, the page tables the parent has there (`paging_fork_copy`), since a walk of the whole user range would be 64 million table spans on x86-64. A page of a `VM_SHARED` region keeps its flags in both, writable ones included, so a store by either is seen by both. Other writable pages become read-only and receive `PTE_COW` in both processes; the frame reference count increases. Genuine read-only pages, and the `PTE_NONE` pages of an inaccessible range, keep their existing flags and are not marked COW.

On the first write, `cow_fault` allocates and copies a frame when another process still references the old one. If the writer is the sole owner, it removes `PTE_COW` and restores write permission without copying. A write through `paging_access`, which ptrace and `/proc/PID/mem` make, takes the copy-on-write path only for a page of a writable VMA; any other shared page, a copy-on-write page of a VMA `mprotect` made read-only among them, gets a copy with its own rights, and a page the process alone holds loses its `PTE_COW` and keeps its rights, so the write never leaves a page writable that its VMA is not. Exit, `execve`, `munmap`, and failed-fork cleanup decrement the same reference counts.

## Checked user access

`copy_from_user`, `copy_to_user`, and `strncpy_from_user` reject addresses outside the user range. They call `vm_prefault_range` before dereferencing user memory, so a valid lazy page is created and an unmapped or read-only destination returns `-EFAULT` instead of faulting in supervisor mode. Bringing a page in may sleep, and a thread that shares the address space may unmap or protect a page brought in before, so once every page is in, the range is checked again with nothing that sleeps and brought in again when a page went: the answer holds until the caller sleeps. `strncpy_from_user` checks one page at a time because the terminating NUL may appear before the next unmapped page.

The kernel also prefaults ranges before passing user buffers to code that accesses them directly. A write prefault resolves COW before any part of the operation has modified the buffer.

## Page cache

The page cache maps a backing store into a supervisor-only window at `PCWIN_BASE`, the architecture's `KVA_PCWIN` (`0xD0000000` on i686). The window ends at the lowest PCI memory BAR within it, a 64-bit BAR read whole, or at the 512 MiB cap when no BAR intervenes; on x86-64 the window lies above every physical address and is the cap. Its page tables are allocated before the first process starts.

The cache reserves no data frames at boot. A slot takes a frame of the DMA pool (`alloc_kernel_frame`), which the backing reads and writes through the kernel's address of it, when first filled, and returns it through `pc_shrink` under memory pressure. The cache can therefore use up to 2048 frames, 8 MiB, but allocates only what it needs and memory permits; a compile on a KRFFS disk root needs the header page of every node in the ring resident beside its hot set, since a lookup walks the ring, and 1024 frames fell short of that once the manual's pages joined the ring. Each resident page has a hash entry, a clock-replacement state, and dirty, accessed, and pinned flags.

`pc_set_backing` installs page-sized read and write callbacks. `rach2.fswindow` uses a Multiboot module as the backing store. A disk root uses the selected ATA or AHCI block device through an MBR partition view.

On a miss, `pc_fault` reads one page into the slot's frame, allocating the frame first if the slot has none. A read maps it read-only. The first supervisor write faults again, marks the page dirty, and remaps it writable. A write miss performs the read and marks the new resident page dirty immediately. A user-mode access to the window is never served.

Clock eviction writes a dirty victim before reuse. Writeback pins the slot and frame until the backing writer returns; eviction, reclaim and competing writebacks skip it. Before writing, the cache maps the page read-only and clears dirty, so a concurrent store faults and marks it dirty again. A failed write or a store during writeback leaves the page dirty and resident. `pc_sync` attempts each resident page and returns the OR of `PC_SYNC_BUSY` for skipped busy slots and `PC_SYNC_FAILED` for failed writes, continuing with other slots. Zero means neither occurred. It leaves concurrent stores dirty for a later write. `fsync` and `fdatasync` call `pc_sync` for the whole cache and report `EIO` on either bit. `sync` retries while the busy bit is set, yielding and waiting with interrupts enabled between scans so an in-flight write can finish and a redirtied page can be written. The wait ends after 3000 kernel ticks (30 seconds) if slots remain busy. A write failure alone causes no wait; `sync` always returns zero, leaving failed pages dirty for a later call.

## File page cache

Exec reads a program's segments page by page (`exec_file_read`), and a private mapping of a file, as the dynamic linker maps a library, reads each page into a frame of its own at the first touch (`file_fault`), so a program started again reads its text from the file again, and the buffer cache, held to half the kernel's heap, does not keep a program of hundreds of megabytes. `filecache.c` keeps a copy of each whole page either reads from an ext2 file in a free frame, found by the file's mount, inode number and generation, which on ext2 name one file, ext2 giving each inode it makes a generation counted from the mount's second. A page is used only while the file's size and modification time are the ones it was read at, and a write, a truncation, a size change and a `fallocate` through the VFS drop the file's pages after they change it, an unmount every page of its files. Each of them adds one to a count of changes, and a page is not kept when the count moved while it was read, since the read may have seen part of a change; a count of the pages of each of 256 classes of files lets a write to a file with none skip the search. A mapping gets a copy, so nothing a process stores reaches the cache. The cache takes a frame only while a quarter of the frames are free and gives frames back, the least recently used first, when memory runs short (`mem_reclaim`, before the disk window's).

## Files

* `frame.*` sizes the managed physical-frame pool.
* `heap.*` implements the boot-time physical allocator.
* `modlayout.*` validates Multiboot module placement.
* `paging.*` owns page tables, frame references, faults, demand paging, COW, and kernel mappings.
* `vm.*` implements VMA lookup, insertion, removal, protection changes, the free-range search, overlap checks, and stack growth.
* `filemap.*` keeps the files and the shared anonymous memory that VMAs map, and the pages in memory of disk files that shared mappings map, with their write-back.
* `shmem.*` keeps a file's pages in memory, for tmpfs and shared anonymous memory.
* `filecache.*` keeps copies of the pages of ext2 files that private mappings and exec read.
* `usercopy.*` implements the user-pointer boundary.
* `pagecache.*` implements the disk window, residency, eviction, and writeback.

## Verification
